摘要

Beetle OS（品牌名 Beetles OS）是一个用 Rust 编写的、面向 ESP32 和 Linux 边缘设备的智能硬件 Agent 系统。它不是传统的嵌入式固件，而是一个完整的设备侧 Agent 运行时——将消息入口（飞书/钉钉/企微/QQ频道/Telegram）、大语言模型接入、工具调用、硬件控制、记忆连续性和运维诊断整合到同一套系统中。用户通过聊天通道用自然语言控制设备，系统通过 Agent 主循环处理，模型参与判断但不越界，执行由系统统一完成。

核心内容

1. 定位：设备侧 Agent 运行时

Beetle OS 解决的核心问题是：大模型让设备交互从固定指令转向目标表达，但真实设备不能把执行权直接交给模型。 凭据、文件、引脚、网络连接、硬件动作都必须由设备系统统一管理。

它不是 PLC/工控机替代品，而是部署在现有系统旁边的对话入口 + 工具调度层 + 设备控制层 + 运维可见性层。

2. 运行链路架构

聊天通道 / 定时任务 / 语音输入
        → 入站队列
        → Agent 主循环
        → 大模型 + 工具 + 记忆
        → 出站队列
        → 聊天回复 / 硬件动作 / 系统任务

关键设计：消息不直接转发给大模型。系统先进入入站队列，Agent 主循环结合配置、记忆、现场状态和资源压力，向模型提供受控上下文与工具边界，再由系统完成具体执行。

5. 记忆系统（五层架构）

记忆层 内容 用途
会话摘要 最近对话、用户目标 长对话上下文保持
长期记忆 稳定偏好、约束、事实 现场适配
事实记忆 带来源、置信度、新鲜度 区分确定/过期信息

设计理念：记忆不是聊天记录的堆积，而是设备理解现场、延续任务的依据。 重启/切换通道/换操作人员后可恢复上下文。

7. 工业场景支持

  • 设备告警：读取状态→判断异常→生成告警→推送通道
  • 现场巡检：记录状态和巡检结果，保留上下文
  • 远程维保：自然语言查询状态、触发诊断
  • 产线辅助：SOP/任务提醒/异常说明接入对话入口
  • 环境监测：温湿度/烟雾/水位/能耗监控

关键概念

Chat-First Agent：以聊天通道为第一交互入口的设备 Agent 模式。用户不需要专门 App，在工作群里发消息即可控制硬件。

受控上下文：系统只向模型暴露允许使用的工具、上下文和约束，避免模型直接访问引脚、文件和凭据。

设备智能层：介于硬件和应用之间的软件层，处理消息接入→模型推理→工具调度→硬件执行的全链路。

能力边界

适用场景：桌面终端、前台设备、设备控制器、监测节点、Linux 边缘网关、自定义智能硬件

不适用场景：
- 实时性要求极高的工业控制（ms 级响应）— Agent 链路有延迟
- 大规模集群管理 — 单设备 Agent 架构
- 安全等级 SIL2+ 的安全控制 — 未做功能安全认证

最佳实践

  1. 先单模型跑通：首次接入用一个模型 + 一组密钥跑通全链路，再增加来源
  2. Flash 配置选 16MB+：8MB 偏紧，16MB 是推荐默认
  3. 按场景选通道：企业用飞书/钉钉/企微，个人用 QQ 频道/Telegram
  4. 记忆诊断：定期检查稀疏/过期/冲突的记忆状态
  5. 安全控制：只暴露必要的工具和设备能力，禁止模型直接操作

🔍 借鉴学习进化点

# 点 原文要点 对当前系统的借鉴 行动计划
1 受控上下文 + 工具边界 只向模型暴露允许的工具和约束，执行由系统完成 Hermes delegate_task 应强化工具白名单机制，防止 subagent 越权 评估 subtask-lifecycle skill 的权限控制是否足够
2 五层记忆架构 会话/长期/事实/连续性/证据五层，带来源/置信度/新鲜度 Hermes 记忆系统可借鉴"事实记忆"的置信度和新鲜度标记 设计 MEMORY.md 条目的时效性标注方案
3 入站/出站队列 + Agent 主循环 消息不直传模型，经队列→主循环→受控执行 Hermes cron/delegate 可借鉴队列化处理，增强任务可追踪性 评估 event-journal skill 的队列实现
4 Chat-First 通道多路接入 一套系统同时接入飞书/钉钉/企微/QQ/Telegram Hermes 已有多平台接入，但缺少统一的消息路由抽象 设计统一消息路由层，解耦平台和业务逻辑
5 设备侧模型回退链 配置多个模型来源，当前不可用时自动回退 Hermes 已有 antigravity-model-failover skill，可对比借鉴其回退顺序配置 UI 对比 Beetle OS 的模型配置页设计，优化 Hermes 配置体验
