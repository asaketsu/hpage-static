# Agent 需要 RAG 吗？— 协同型与高可信 Agent 的技术路线分歧

> **来源**：叶小钗 · 微信公众平台 · 2026-05-28
> **原文**：https://mp.weixin.qq.com/s/kocuorTqAQr2NuxulUxD8g
> **格式**：双格式(MD + HTML) · 含借鉴进化点 · RAG/wiki联动

## 摘要

文章从「Agent 是否需要 RAG」这一问题切入，将 Agent 分为两大范式：协同型 Agent（如 Claude Code、Codex）和高可信 Agent（如 AI 医生、AI 律师）。两者对数据的态度、准确率要求和架构选择截然不同。协同型追求广度和便利性，用户需具备评判能力；高可信型追求精度和可解释性，知识工程在检索之前就已决定成败。作者认为 Workspace Agent 适合个人工作空间，企业级应用则需要融合策略——核心流程走高可信 RAG，非核心流程放手让 AI 自由发挥。

## 核心内容

### 1. 两类 Agent 的本质区别

| 维度 | 协同型 Agent | 高可信 Agent |
|------|-------------|-------------|
| 典型代表 | Claude Code, Codex, OpenClaw | AI 医生, AI 律师, AI 客服 |
| 用户角色 | 协同共创，需具备评判能力 | 被引导者，不需专业判断能力 |
| 准确率要求 | ~80%，允许犯错 | 99.9%+，不可容忍大概对 |
| 数据态度 | 工作材料，上传即用 | 证据来源，严格知识建模 |
| 核心追求 | 广度 + 探索性 | 精度 + 可解释性 |
| 架构路线 | Workspace Agent / Agentic Search | Agentic RAG / 知识工程 |

### 2. Workspace Agent：便利性的代价

- 核心价值：消解数据接入的前置成本，上传即用
- 代价：将数据准备成本转移到用户的判断力
- 适用边界：个人工作空间，1-10 人以上会失控
- 技术趋势：Claude Code 早期用过 RAG 但效果不好，转向 Agentic Search（模型自己走 ReAct 循环）

### 3. 高可信 Agent：知识工程的核心

- 数据进入系统前就要完成严格的知识建模
- 五个关键原则：
  1. 知识库边界与结构必须穷举定死
  2. 逻辑关系链 + 实体结构设计（核心关键词不重样）
  3. 类型层级不能太多（工程复杂度 vs 数据复杂度取舍）
  4. 一号位必须亲自写文档做产品设计
  5. AI 输出像人是封闭性问题，前提是知识对了再建模表达策略

### 4. 二八融合策略

- 80% 客户问题围绕 20% 核心场景 → 核心场景走高可信 RAG，非核心场景放手让 AI 自由发挥
- 高可信不是产品形态，而是风险分层策略（如 AI 医生：诊断/用药严苛，运动/饮食建议宽松）

### 5. RAG 的重新定义

- 传统 RAG（切片+向量化+TopK）正在被 Coding Agent 集体抛弃
- 但高可信场景的 RAG 不是检索，而是**知识工程**——边界、实体、关系链在搜索前就决定了
- 结论：Agent 不是不需要 RAG，而是不需要之前那个 RAG

## 关键概念

- **Workspace Agent**：以私有工作空间为上下文，以文件系统为操作对象的协作型知识 Agent
- **Agentic Search**：模型自主走 ReAct 循环决定搜什么、读什么、是否继续搜索
- **高可信 Agent**：替代人类判断的 AI 系统，每个结论必须有据可查、可溯源、可审计
- **知识工程**：在数据进入系统前完成边界定义、实体结构设计、逻辑关系链构建
- **同事.skill / 蒸馏**：蒸馏的是工作流（先做什么后做什么），而非判断逻辑（为什么这么做）

## 能力边界

- 文章偏战略层面，未深入高可信 RAG 的具体技术实现（向量模型选择、chunk 策略、reranker 等）
- 二八融合策略缺乏量化数据和实际案例支撑
- 对 Workspace Agent 的企业级局限性描述准确但解法不够具体

## 最佳实践

- 场景决定需求 → 需求筛选范式 → 范式选择架构
- 先明确「放大能力」还是「替代判断」，再选技术路线
- 高可信系统的知识建模必须由领域专家一号位亲自操刀
- 企业级应用用二八策略分层，不必全走高可信路线

## 🔍 借鉴学习进化点

| # | 点 | 原文要点 | 对当前系统的借鉴 | 行动计划 |
|---|-----|---------|---------------|---------|
| 1 | 协同型 vs 高可信二分法 | 协同类追求广度，高可信追求精度 | 我们的 Hermes Agent 属于协同型（用户是开发者，有评判能力），但 memory 系统需要高可信（记忆不能出错） | memory 写入时增加验证层，关键事实需交叉确认 |
| 2 | Agentic Search 替代传统 RAG | Claude Code 放弃 RAG，用 ReAct 循环自主搜索 | 我们的 wiki-kb 和 session_search 已走这条路——模型自主决定搜什么 | 优化 session_search 的 FTS5 查询策略，支持 OR 扩展和多轮搜索 |
| 3 | 知识工程核心：边界+实体+关系链 | 高可信 RAG 的难点在搜索之前就决定了 | 交换池 exchange-protocol 的经验分类体系就是一种轻量知识工程 | 检查 experience-pool.jsonl 的分类是否完整，补齐缺失的 type 定义 |
| 4 | 二八融合策略 | 80% 问题围绕 20% 场景 | Hermes 的 cron job 和 skill 体系已经体现二八：核心流程（升级/记忆/交换池）有严格 skill，其他自由发挥 | 标记核心 skill 为 pinned，非核心的允许 curator 自动管理 |
| 5 | 蒸馏工作流 vs 蒸馏判断 | skill 蒸馏的是流程，判断逻辑需要更高层次建模 | 我们的 skill 体系确实主要捕获「怎么做」（流程），缺少「为什么这么做」（决策逻辑） | 在关键 skill 的 pitfall 段落补充决策依据，而非只记录操作步骤 |
| 6 | 一号位亲自做知识建模 | 高可信系统必须由最懂行的人设计知识结构 | memory-system 的三层架构由用户亲自定义，这个方向是对的 | 继续让用户主导 MEMORY/SOUL 规则，agent 只做执行和维护 |
