## 零、结论先行

Josh Rosen 的前作《判官八模式》讲的是"AI 可能答错，怎么检查"；本文讲的是更深层的问题——**"AI 可能本身就是威胁，怎么围着它建系统"**。两个安全层：

```
判官层（前作）：模型可能幻觉/误判 → 评审/验证/确定性包夹
不信任层（本文）：模型可能被注入、被操纵、主动逃逸 → 沙箱/权限外移/凭证隔离/出口控制
```

**核心命题**：能力越强的模型不需要越大的权限——**恰恰相反，模型越强，围绕它构建可信系统的门槛越高**。这不是安全工程师的洁癖，是 Meta（Muse）、Google（agentic Chrome）、AWS（AgentCore）、Microsoft、NVIDIA 五家同期产品的**架构收敛**。

**最有价值的洞察**（§"Use Another Higher-Trust Model"）：判官不能和被审模型共享上下文——**"如果两个模型吃了同样的恶意指令，第二个模型只是给攻击者多了一个操纵目标"**。高信任模型应收到**更小、净化后的动作表示**，回答更窄的问题——这种**非对称性**才是架构的价值。这与 Anatoli《Graph Engineering》的"验证者必须干净上下文"铁律完全同构。

## 一、八模式忠实还原

### 模式 1：Put the Model Inside the Sandbox（沙箱化）
- 把模型驱动执行当不可信代码处理——让它在隔离环境里干一切（生成代码/跑命令/操作文件/装包/用工具），但**敏感服务在沙箱外**
- **Meta Muse**：Muse Secure VM——工作空间/文件/工具/harness 全在 VM 内，VM root ≠ host root
- **NVIDIA Secure Agent Workspace**：managed workspace 是执行与策略边界，agent 不能自扩权限
- **AWS**：推荐安全执行环境用于可执行代码/可交互网站的 agent
- 一句话："沙箱让模型在箱内有充分自由（ship the computer），不给它对系统其余部分的同等自由"

### 模式 2：Move Authority Outside the Agent（权限外移）
- 沙箱限制本地可达，但不回答：agent 合法需要做外部操作时怎么办？——**独立授权层**
- **Muse Sentinel**（host 侧组件）：Muse 可提议连接器动作/网络请求，但 **Sentinel 才是实际决定是否允许的组件**——独立评估连接器策略与网络请求
- **AWS AgentCore Gateway + Policy**：agent 通过中央中间层请求工具调用，授权策略可检查动作甚至**个别参数**——**"在 agent 外执行授权，使被攻陷的 agent 不能简单决定自己有权限"**
- **Microsoft**：授权应在**每个动作**而非仅会话开始时——高影响操作需单独批准或临时升权
- 核心目标：**模型变成提议者而非权威**。"可以决定发邮件是恰当的下一步，但另一个更有特权的组件决定此 agent 此用户此任务是否真被允许发那封邮件给那个收件人"

### 模式 3：Give the Agent Capabilities, Not Credentials（能力不给凭证）
- 可见凭证的 agent 可泄密——解决方案：让 agent 用认证系统但**不持有底层密钥**
- **Muse hatch-authd**：真实凭证存在 agent runtime 外，agent 看到的是**代理凭证（surrogate token）**；批准的网络请求过边界时 Sentinel 获取真实凭证**在出口处替换**——模型从未看到真凭证
- **NVIDIA**：凭证代理在出口重写授权头
- **Postman AI Engineer**：agent 可请求认证动作但不收凭证
- **Google**：agentic Chrome 可用 Password Manager 但模型不收密码直接访问
- 一句话："比告诉模型'别说出去'更强——**因为根本没有可说的密钥**"

### 模式 4：Treat Network Egress as a Privileged Action（出口控制）
- 能读私数据 + 能开任意网络请求的 agent = 差不多够泄密了——**读数据与传数据是分离的能力**
- **Muse Sentinel**：runtime 流量过 Sentinel，授权层可查 hostname/IP/port/协议/HTTP 方法/路径/解码请求
- **Agent Browser**：域名白名单覆盖顶层导航+子资源+WebSocket+EventSource+sendBeacon
- **Muse tainted egress（污染出口，全文最有创意的机制）**：进程初始"干净"，读用户数据后变"污染"——污染后部分自动出口权限消失，走更严审批路径（可能需人工批准）。用 **eBPF + Linux Security Module hooks** 实现
- 一句话："追踪 agent 进程是否碰过用户私数据，碰了就额外规则触发"

### 模式 5：Give the Model Only the Data It Needs（最小数据视图）
- 与其让模型看一切再控制事后做什么，不如**减少进入上下文的数据**
- **Google Agent Origin Sets**：给定任务维持约束的 web origin 集——独立门控函数决定额外 origin 是否相关，**规划模型不能自己加任意网站**。可区分可读 origin 和可写 origin
- 扩展：检索系统预过滤记录、工具只返回授权字段、记忆按用户/项目/任务分区
- **AWS**：在 agent 外执行数据授权，使 prompt 注入不能导致模型检索用户本无权访问的信息
- 一句话："控制上下文本身就是一种授权机制"

### 模式 6：Use Another Higher-Trust Model（高信任模型审查）
- 不是每个安全决策都能表达为确定性规则——需要判断："这个动作真的是用户想做的吗？""这个导航对任务合理吗？""这个工具调用在上下文里可疑吗？"
- **Google User Alignment Critic**：规划器提议动作→独立模型评估是否服务用户目标——**关键是：critic 与不可信页面内容隔离**，只看动作元数据不看原始可能恶意的网页内容
- **Muse hatch-safety**：在 runtime 容器外独立检查推理流量，用模型/分类器检测 prompt 注入等威胁——**因在 runtime 外，被攻陷的 runtime 不能简单禁用它们**
- **与前作判官的关键区别**（本文最锋利处）：判官不一定与被审模型共享上下文——**"如果两个模型吃了同样恶意指令，加第二个模型只是给攻击者两个操纵目标"**。高信任模型应收到更小、净化的动作表示，回答更窄的问题——**非对称性使架构有用**

### 模式 7：Scope Authority to the Task（任务级权限租约）
- 传统应用认证一次、会话全程带大权限——**当持有会话的是自主 agent 时就危险了**
- **Microsoft**：agent 自己身份、任务特定角色、短命 token、just-in-time 升权而非广泛常驻权限
- **AWS**：临时 scoped 凭证 + 用户到每个 agent 动作的可追溯授权链
- **Keycard**：agent 自己身份和 scoped 权限——对特定资源/动作的访问被授予，而非继承人类凭证
- 一句话："agent 权限越来越像**租约**——够做这件活的权限，做完就过期"

### 模式 8：Selectively Put Humans at the Boundaries（选择性人介入）
- 人审批是模型不确定的标准答案，但一切要审批 = 没理由用 agent——**选择性审批**
- **Google 浏览器 agent**：自主工作大部分任务，但敏感网站/密码使用/购买/支付/发消息/其他后果性动作要确认
- **Microsoft**：发送/删除/购买/部署/权限变更需显式批准
- **关键设计问题不是"有没有人介入"，而是"人坐在循环的哪里"**——好的检查点：权限扩大时、敏感信息过边界时、钱移动时、权限变更时

### 收尾
- 八模式合在一起=一套相当连贯的架构："我们不一定信模型，但不代表不能信我们在模型之上建的东西"
- **核心命题**："能力越强的模型不要求我们给越来越大的权限。相反，模型越强，围绕它建可信系统的门槛越高。"
- "接下来只会更复杂——注意力现在转向我们在模型周围建的系统能否跟上模型创新的步伐"

## 三、批判性审视

1. **安全层叠的隐性成本未量化**：八模式叠加（沙箱+权限外移+凭证代理+出口审计+数据过滤+高信任审查+租约权限+人介入）= 每个动作经过 3-5 层检查。原文未给延迟代价——Muse Sentinel 的 eBPF+JIT 凭证替换在生产中的 P99 影响是关键缺失
2. **tainted egress 是最有创意但最实验性的**：eBPF 追踪进程污标签到"碰过用户数据"粒度——这在 Linux 进程模型下可行，但在容器化/多租户场景的语义边界（一个 pod 里哪些进程算"agent 的"）需要实测验证
3. **"模型越强权限该越小"的因果方向值得追问**：原文说"相反"，但因果可能不是线性的——强模型做更复杂的任务→需要更大权限范围（更多工具/更宽数据访问），只是权限的**粒度更细**（从会话级→任务级→动作级）。是粒度变细而非范围缩小
4. **模式 6 的非对称性与判官笔记的张力**：前作说"判官可以参与控制流"，本文说"判官不能共享上下文"——两篇合读的正确理解是：**判官参与控制流但以非对称方式参与**（收更小表示、答更窄问题），不是"不参与"
5. **航空适航映射**（领域增量）：权限外移+凭证代理+出口控制 = 适航审查的"权限分层+独立验证+数据隔离"同构。CCAR 要求关键软件变更由独立审查方批准（不在开发团队内部）= 模式 2 权限外移。航空领域读者可将本文八模式直接映射到 DO-178C 的独立验证与配置管理
