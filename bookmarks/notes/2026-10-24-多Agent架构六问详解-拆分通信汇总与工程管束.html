一、先回答要不要拆

单 Agent 循环的四个卡点（拆的理由各不相同）：

卡点 机制 拆的理由
上下文被中间结果塞满 查日志/搜代码读进来的东西只用一次却一直占上下文、分散注意力 隔离上下文
工具太多太像、选不准 OpenAI：问题不在数量在重叠——15 个界限清楚的工具能用好，<10 个互相重叠就开始选错 隔离工具
提示词分支太多 「如果…就…否则…」改一处牵动别处；角色冲突（同上下文既写代码又审代码，审时带着写时的假设） 分开职责
互不依赖子任务只能串行 单 Agent 轮流做，每件做完上下文多一堆材料 并行（只有这个理由对应并行）
  • Anthropic 量级：子 Agent 探索可能用几万 token，交回主 Agent 的往往只一两千 token 摘要。研究系统主 Agent 一次派 3-5 个子 Agent、每个同时调 3+ 工具，复杂问题研究时间最多缩短 90%。
  • 面试关键反驳链：「单 Agent 调 Skill 也能并行」→ 若每一路只是一次查询，单 Agent 并行调工具就够；若每一路要自己搜、读、判断再搜好几轮，几路中间材料挤在一个上下文里才需要拆——拆换的是「每一路有干净上下文」。
  • 研发平台 vs 电商下单：关键不在流程固不固定，而在每一步要不要大量探索、要不要独立上下文和权限、能不能并行。

多 Agent 贵在哪（四项成本）：
- Token：Anthropic 数据——普通对话 1x、Agent 4x、多 Agent 15x。但研究系统 Opus 4 主 + Sonnet 4 子比单 Opus 4 高 90.2%（内部研究评测）；BrowseComp 上 token 用量一项能解释 80% 表现差异——多 Agent 赢的很大部分来自能花更多 token 到任务上。
- 作者自证实验：1 主 + 3 子，62 分钟，总 token ≈1.92 亿（主 3860 万 + 子 1.53 亿），预算 100 万 = 192 倍；主 Agent 只占总量 1/5，子 Agent 必须单独记账。
- 协调成本：拆任务、写说明、读报告、核对版本、纠错（曾读到还在修改中的中间产物，整轮作废重跑）。
- 交接丢信息 + 决策冲突：Cognition Walden Yan 的 Flappy Bird 案例——背景做成马里奥风格、鸟不像，两个子 Agent 各自决定说得通、放一起对不上。两条原则：共享上下文要共享完整过程记录；动作里带隐含决策，决策冲突结果就坏。
- 错误下传：上游猜测到下游成已知事实；Cemri 等分析 7 个框架 1600+ 运行记录，失败三类=系统设计、Agent 间对不齐、检查没做好。

值得拆（五条）：子任务依赖少可各做各的；过程长结论短（读大量日志只要一个结论）；需要不同工具/权限（只读检索 vs 能写执行）；需要没参与过程的人检查；任务够值钱（Anthropic：只适合价值高到付得起额外开销的任务）。

不该拆（三条）：各部分强依赖要共享同一套决策（编码即典型——能并行的部分比研究少，Agent 还不擅长实时协调分派）；几步能做完；流程固定每步可写死（用 Workflow 更稳）。

Skill vs SubAgent 判据：缺「会不会做」→ 加 Skill（说明+脚本+资料按需加载进当前上下文，活还是同一个 Agent 干）；缺「做时别弄乱主上下文/要不同权限/要独立检查者/要并行跑几轮」→ 拆 Agent（另起炉灶：独立上下文窗口、独立系统提示词、独立权限，只交回摘要）。
五概念一句话：Function Calling=调工具的基础机制；MCP=统一协议接工具和数据源；Skill=把某类事怎么做打包按需加载；Workflow=步骤由代码写死；SubAgent=另起上下文干一段活只交结果。组合：Workflow 串主流程，节点 Agent 调 MCP 工具，大量探索步骤派子 Agent。

二、怎么拆

五种结构：
1. 主从（manager）：主拆任务派活汇总，子只对主负责；Anthropic 研究系统、Claude Code 子 Agent。
2. 流水线：按阶段排死（需求→设计→编码→测试），更接近 Workflow。
3. 并行分片：同类任务切几份各做再合并（长文档按章节切）。
4. 执行+审查（evaluator-optimizer）：一调用生成、另一调用评估反馈，循环。
5. 按意图转交（decentralized）：分诊 Agent 判断意图后把整个对话单向交给专职 Agent（典型客服）。
- 套娃（主→编排→原子）每多一层多一次转述和等待，只有管不过来或各层权限确实不同才值得。
- Multi-Agent vs Sub-Agent：后者是主从结构里的子（派生→交回）；前者范围更大含平级协作互相转消息。Claude Code agent teams 队友可直接互发消息、用共享任务列表认领工作，但 token 明显更多。选型：只需各自交结果用子 Agent；要边做边对齐才平级协作。

拆分边界三判据：上下文边界（拿一份任务说明就能干完，不需要主 Agent 之前的讨论）；工具/权限边界（只读与能写分开，碰生产数据单独一个）；能单独验收（测试过没过/文件生没生成/结论有没有出处——没法单独检查的产出，汇总时也查不出错）。「产品经理 Agent/架构师 Agent」按职位起名≠找到边界——读同一批材料、做互相依赖的决定，拆完只是多几次转述。

预定义 vs 动态创建：预定义好测试、行为可预期（Claude Code 可用 tools/disallowedTools 字段限定）；动态创建灵活但必须有上限——Anthropic 早期犯错：简单问题派 50 个子 Agent。后写进提示词的规模：简单事实查询 1 Agent + 3-10 次工具调用；直接比较 2-4 子 Agent 各 10-15 次；复杂研究 10+ 子 Agent 分工清楚。常见做法=类型预定义 + 任务动态下发。

任务说明六要素：要交付什么；做什么不做什么、与其他子 Agent 怎么分界；已确认事实和相关文件路径（免重查）；用哪些工具优先看哪些来源；交回格式；做到什么程度算完成 + 步数/token 上限。检验：交给没参与讨论的新同事能否直接开工。反例：只写「研究半导体短缺」→ 一个查 2021 汽车芯片危机、两个重复查 2025 供应链。
分档派发：难的给强模型多预算，机械的给便宜模型（Opus 主 + Sonnet 子）。
嵌套与上限（Claude Code 2026-10-23 文档）：子 Agent 默认可再派、最深 3 层（环境变量可调，设 1 关嵌套）；同会话并发默认最多 20 个，超了直接失败。设计要管：深度、并发数、整棵树共用预算 + 循环检测（派生带祖先链；同工具同参数反复调用要能识别；兜底=全局步数和时间上限）。

三、怎么通信

三方式：
1. 经主 Agent 中转：子 Agent 彼此看不见，好控制好追踪，但主 Agent 成瓶颈。
2. 共享状态（黑板）：读写同一块存储（任务表/状态对象/共享目录），主 Agent 读表不靠自己记。要管写入：一个任务只能被一个 Agent 认领；同一数据只有一个权威副本、写入带版本、冲突可发现。
3. 直接对话/转交：Claude Code agent teams 可互发消息（实验性、默认关、token 多）。
- 抢答问题（百度面试）：中转时顺序主 Agent 定；共享状态靠任务认领+加锁；直接对话要有明确规则（协调者指定下一个轮到谁）。
- 派给谁：规则/分类模型/大模型按各子 Agent 说明选——说明要写清负责什么不负责什么、彼此不重叠（道理同工具重叠选不准）。评测提准确率：标一批「应该派给谁」算准确率、错例回流；路由留「拿不准的出口」（追问用户或交通用 Agent）；派错能退回（子 Agent 发现不归自己管就退回，转交限次数防踢皮球）。
- 往下传：任务说明是子 Agent 唯一上下文来源，要自带背景；大材料给路径/链接不整段贴。子 Agent 一般不参与主 Agent 运行中上下文（隔离本来就是拆的理由）；缺信息→带问题提前返回标「需要补充」，或读共享状态（A2A 的任务也可停在「需要输入」态）。
- 往回传（两派主张可兼顾）：Cognition 主张共享完整过程记录；Anthropic 主张产出存外部只交轻量引用（防传话游戏式丢失）。作者改法=默认回短结论（状态/几句话结论/证据路径/假设与未核实项），详细日志落文件，主 Agent 有疑问再读。结论绑定版本：实现交出可测版本后记文件哈希，测试结论绑哈希。
- 上下文膨胀处理：子 Agent 回短报告原文落文件；不把子 Agent 完整对话转给另一个；主 Agent 自己历史也压缩、计划类长青内容写外部（Anthropic 主 Agent 把研究计划存 Memory——上下文超 20 万 token 会被截断）。

A2A vs MCP：A2A（Google 2025-04 开放协议）连 Agent↔Agent，MCP 连 Agent↔工具。核心概念：Agent Card（JSON 自述：身份/服务地址/能力/认证，标准路径 /.well-known/agent-card.json）；任务有状态生命周期（已提交/处理中/需要输入/需要认证/完成/失败/取消/拒绝，长任务中途可停下要信息）；消息=一轮交流，artifact=任务产出物；传输=HTTP 上 JSON-RPC 2.0，长任务 SSE 推进度或回调，规范另列 gRPC 和 HTTP+JSON 绑定。本质差异：调 MCP 工具像调函数（输入输出确定、工具不判断）；A2A 找的是另一个 Agent（有自己的模型工具记忆、是黑盒、可能跑很久、中途回头要信息）。使用判据：跨团队/跨厂商/分开部署才上 A2A；同进程同框架的主从用框架自带子 Agent 或函数调用就够，上 A2A 只多网络认证版本管理成本。子 Agent 要不要做成服务同理：要独立扩缩容/独立发布/给别的团队用才值得。

四、结果谁汇总、冲突怎么办

汇总纪律：主 Agent 做；子 Agent 按统一格式交结果带出处（第几块哪一段）；汇总按字段合并、去重、标冲突，不把几份报告丢给模型自由改写；块多可分层汇总。
主 Agent 汇总幻觉四成因（蔚来面试）：报告太多太长漏看看混；模型用自己的知识补空缺；转述时改了数字和限定词；几份冲突报告被揉成一个通顺说法。
约束四条：每条结论标「来自哪个子 Agent 的哪条证据」，标不出的不写；汇总后加一道核对逐条查依据（Anthropic 专门有 CitationAgent）；关键数字名称照抄不让模型改写；汇总步不给检索工具（防半路自己找新材料）。

矛盾仲裁四步（恒生电子面试）：①确认真冲突（时间点/口径/来源不同都只是看起来矛盾）→②按规则采信（权威数据源>文档>模型推断；新版>旧版；有证据>无证据）→③规则判不了去查（调权威系统核实或派 Agent 专项复核，还判不了交给人）→④冲突写进结果，不许汇总模型自己挑一个了事。
投票（voting）：只在各 Agent 出错原因互不相关时有用——同模型读同一份错误资料，几票一起错。

Critic 五要点：①查有客观依据的（测试过没过/格式对不对/结论有没有出处/清单项做没做到），主观部分用评分标准；②不用同模型同上下文自查——Huang 等（ICLR 2024）：无外部反馈时 LLM 难以自纠推理错，改完有时更差；Critic 要独立上下文（只看需求和产出、不看执行者推理过程）、接外部信号（测试结果/工具返回）、条件允许换模型；③不通过给具体问题+证据，执行者按清单改而非整个重做；证据不足定向补证（Critic 列缺哪几条只补那几条）；④防循环：最多 N 轮 / 连续两轮问题数不降就停 / 预算到线停；停下把未解决问题写进结果或交给人；⑤Critic 自己也会错（判错好结果被打回返工、判漏坏结果放行），要拿标好对错的结果集测它。作者实证：像素检查工具曾把清屏改成不执行→残留火球被当飞机（先修工具再重验）；同一次也真抓出 NaN、撞山、机头瞬转。

幻觉不放大：证据跟着结论走（结论+出处一起传，无出处的标「未核实」）；下游把上游输出当说法不当事实；关键事实在交接处核对一次；最终引用能追到原始出处。

五、工程管住的六件事

  1. 失败/超时：每子 Agent 设超时+步数上限；偶发错（网络/限流）有限自动重试，同错反复出现就别试；失败也带做完的部分返回（做到哪步/哪些未核实），主 Agent 决定重派/换人/跳过/降级交付；长任务从出错处续跑（Agent 有状态，从头再来代价大）；副作用操作（写库/发消息/下单）必须幂等——重试不能做两遍。成功率是乘出来的：5 环节各 95% 独立不重试 → 整体 77%，要分环节看才知道哪里加检查加重试。
  2. 预算覆盖所有 Agent：预算必须是整棵树的运行时停止条件（作者实验最大教训——预算只在题面，主/子各只见自己那份）；开工前给子 Agent 留份额、运行时持续累加全树用量，时间+token 双卡哪个先到停；子 Agent 继承剩余预算不各自从头算。反向题（汇川）：预算卡死只能单 Agent 时——几个角色改成同 Agent 几个步骤+按清单自查；能用规则/代码检查的不交模型；材料先筛再给；少了独立视角更要依赖外部信号（测试/规则校验/数据核对）。
  3. 权限最小化：检索/审查只读；实现只能写自己工作目录/分支；发消息/写生产/部署等副作用操作只留给主 Agent 或要人确认；消息也限（能给谁发、能读哪些共享状态）。
  4. trace + 分 Agent 记账：一任务一 trace ID，每子 Agent 一段：收到的任务说明/调的工具/交回的结果/token/时间。出问题能定位哪个 Agent 引入错，成本能分摊到每个 Agent。
  5. 评测先有单 Agent 基线：端到端（同批任务单/多 Agent 各跑几遍——Agent 每次结果不一样，跑一遍不够——比成功率/质量分/耗时/token/费用）+ 分环节（路由选对比例/各子 Agent 完成率/Critic 判对比例/汇总结论可追溯率）。起步不用大：Anthropic 起初约 20 个代表真实用法的问题；人工测试发现早期 Agent 总挑 SEO 过的内容农场而非更权威的排名靠后来源。
  6. 延迟：会变慢。每多一层多一轮模型调用+任务说明+汇总；并行只缩短互不依赖的那几路，整体耗时取决于最慢一路；Anthropic 研究系统是同步执行——一批子 Agent 全做完才往下走，中途没法调整，一个慢全系统等。

六、面试怎么答（2 分钟主线）

为什么拆（单 Agent 卡在哪，有现象有数据；拆前在单 Agent 里试过什么）→ 怎么拆（哪种结构/几个 Agent/职责输入输出工具权限）→ 怎么通信（经谁中转/下传什么/回传什么）→ 怎么汇总（谁汇总/冲突规则/谁检查/不过怎么办）→ 工程（失败兜底/预算/权限隔离/追踪）→ 效果（vs 单 Agent 成功率耗时成本各变多少）。最好带一个具体的坑。
四个失分点：为多 Agent 而多 Agent 说不出单 Agent 哪里不够；只拿并行当理由被「单 Agent 也能并行调工具」问住；只有架构图没有对照数据和成本数字；没想过失败、冲突和停止条件。

归纳总结

  • 全文可压成一条主线：拆分是买「干净的上下文 + 独立的权限 + 独立的检查者 + 并行」，付的是 token（15x）、协调、交接失真、错误放大四笔钱；只有任务值钱到付得起这笔钱才拆。
  • 四个卡点对应四种拆的理由（隔离上下文/隔离工具/分开职责/并行），面试只说「任务复杂所以拆」或只拿「并行」当理由都是失分点——单 Agent 并行调工具就能覆盖「每路一次查询」的场景。
  • 判据速记：缺「会不会做」= Skill；缺「独立上下文/权限/检查者/并行」= SubAgent；跨团队跨部署才 = A2A。
  • 工程核心是把预算、停止条件、幂等、trace 从「写在题面」变成「运行时的系统属性」——作者的 192 倍预算事故正是缺运行时停止条件的实证。
  • Critic 有效性依赖独立性（独立上下文/外部信号/异模型），同上下文自查被 ICLR 2024 证伪。

趋势判断

  • 面试考察点从「会不会画架构图」转向「拆分的经济学」：快手直接问「做过单/多 Agent 对照评测吗」——没有基线数据的架构选型正在失去说服力，这与工程界对 LLM 系统可观测性/评测的重视同向。
  • 协议层分工趋于稳定：MCP（Agent↔工具）+ A2A（Agent↔Agent）+ Skill（Agent 内知识打包）三层概念在面试中被并列考察（美团/百度），说明已成为行业共识词汇，2026 年进入「组合使用」而非「选一个」的阶段。
  • 反方声音（Cognition Don't Build Multi-Agents）与正方（Anthropic 研究系统）实际收敛在同一组条件上——分歧在任务分布（研究=广度并行 vs 编码=强依赖），不在信仰；行业正在从「架构站队」走向「按任务结构选型」。
  • 成本侧（token 15x、延迟取决于最慢一路、成功率连乘衰减）决定了多 Agent 会继续向「高价值任务+强工程管束」收缩，而不是泛化成默认架构。

关联分析（与 Hermes / 本机多 Agent 体系的映射）

  • Hermes 的 delegate_task 即本文主从结构：subagent 拿 isolated context 只交回 final summary，正是「隔离上下文」卡点的解法；其「Children know nothing of this conversation: pass everything needed via context」约束 = 本文任务说明六要素的运行时强制。
  • 背景并发 children + 结果 re-enter 主循环对应「并行分片 + 主 Agent 汇总」；「never wait or poll on transcripts」对应「不经主 Agent 中转的死等反模式」的规避。
  • 本机 skill 体系（lark- / duck- 等 400+ skills）与 SubAgent 的边界正落在本文判据上：Skills 目录=「会不会做」的知识打包（按需加载不另起上下文）；delegate_task/kanban=需要独立执行域时才启用。当前用法符合「类型预定义+任务动态下发」的推荐形态。
  • 作者「子 Agent 用量单独记账」教训对应 Hermes 的 observability 实践（本机 observability-dashboard/error-monitoring skills 的 token 消耗分摊统计）；「结论绑定版本（文件哈希）」对应本机「三证=进程/iter/新目录」验收纪律。
  • Critic 独立性原则与本机 content-judge（LLM-as-Judge 独立评分）、ai-test-review（独立 review 而非作者自查）设计同构——「验证者不得继承执行者的推理上下文」。

拓展应用推荐

  • 面试准备：本文+作者系列题单（第 2 题单 Agent 循环、第 4 题评测、第 14 题 ReAct vs Plan-and-Execute、第 23 题 Workflow vs Agent、第 28 题死循环防护）构成 Agent 岗位面试主干，值得按题单顺序过。
  • 系统设计 checklist 化：把第五节六件事直接落成 PR 模板/review 清单（预算运行时停止条件、幂等、最小权限、trace、基线评测、延迟预算），适用于任何要上多 Agent 的项目评审。
  • Hermes 侧可借鉴：给 delegate_task 的任务说明按六要素自查（交付物/边界/已知事实/工具/格式/完成判据）；子任务回传字段固定化（状态/结论/证据路径/假设与未核实）。
  • 延伸阅读：Cemri 等 Why Do Multi-Agent LLM Systems Fail?（失败三分类的原始论文）、Anthropic 上下文工程文（2025-09-29）、Claude Code Subagents/Agent teams 官方文档（嵌套 3 层/并发 20 的默认上限出处）。

指南分析：多 Agent 决策操作顺序（下次直接抄）

  1. 先问单 Agent 卡在哪：上下文膨胀 / 工具重叠选错 / 提示词分支失控 / 串行拖慢——四者都不是 → 不拆，加 Skill 或 Workflow。
  2. 对照「值得拆五条」（依赖少/过程长结论短/异工具异权限/要独立检查/任务值钱）逐条打勾，≥2 条才继续。
  3. 选结构：只需各自交结果 → 主从/并行分片；要边做边对齐 → 平级协作（接受更高 token）；流程固定 → 退回 Workflow。
  4. 按边界拆：上下文边界（一份任务说明能干完）+ 权限边界（只读/能写/碰生产分开）+ 可单独验收（测试/文件/出处）。
  5. 写任务说明六要素，用「新同事能否直接开工」自检；难的给强模型、机械的给便宜模型。
  6. 定通信：默认经主 Agent 中转 + 子 Agent 回短报告落文件；需要共享进度才上黑板（认领制+版本化写入）。
  7. 汇总纪律：统一格式带出处→字段级合并→CitationAgent 式逐条核对→关键数字照抄→汇总步禁检索。
  8. 冲突四步仲裁（真冲突?→规则采信→查证→写进结果），投票只在错误原因互不相关时用。
  9. 工程六件事上线前逐项过：超时/重试/续跑/幂等、全树预算双卡、最小权限、trace 分账、单 Agent 基线评测、延迟按最慢一路估。
  10. 交付时带对照数据：成功率/质量分、耗时、token、费用 vs 单 Agent 基线，多轮取均值。
