一、内容整理

1.1 KV Cache 是什么：自回归生成的必然产物

Transformer 自回归生成的原始形态：每生成一个新 token，都要把整段历史序列重新过一遍注意力。序列长 n 时总计算量是 O(n²)——第 1 步算 1 个 token 的注意力，第 2 步算 2 个，……解码 1000 步就是 50 万次重复计算，其中绝大部分是对同样历史 token 的 K/V 投影重复计算。

KV Cache 的本质洞察来自因果掩码的数学性质：

  • 因果掩码保证 token i 只能看见 token ≤ i
  • 因此历史 token 的 Key/Value 投影结果永远不变——第 t 步算出的 K_i、V_i，在第 t+1 步、第 1000 步仍然完全相同
  • 而 Query 不需要缓存：每个解码步只需要当前最新 token 的 Q（用它与所有历史 K 做点积）——Q 是一次性的，K/V 是持久的

于是推理被切成两个性质完全不同的阶段：

Prefill（预填充）           Decode（解码）
─────────────────────      ─────────────────────
一次性处理整个 prompt      每步只算 1 个新 token
高度并行（大矩阵乘）       串行（逐 token）
计算密集（compute-bound）  访存密集（memory-bound）
产出：全部 prompt 的 KV    产出：新 token 的 K/V 追加进 cache
指标：TTFT（首token延迟）  指标：TBT/TPOT（逐token延迟）

KV Cache 就是把「重复计算」换成了「显存存储」：解码每步只需算 1 个 token 的 QKV 投影 + 一次对缓存的注意力读取。代价是显存线性增长。

1.2 显存账本：为什么长上下文时代 KV Cache 成了第一成本项

单条请求 KV Cache 显存公式：

KV_bytes = 2(K和V) × n_layers × n_kv_heads × head_dim × seq_len × batch × bytes_per_elem

关键量级事实（多源综合）：

  • 上下文 <32K 时，KV Cache 显存 < 模型权重，不是瓶颈
  • 128K 上下文时，KV Cache 超过参数显存
  • 1M token 时，KV Cache 吃掉 GPU 显存 70-90%、墙钟时间 60-85%——此时优化 KV 的 ROI 高于优化任何其他组件
  • KV 随上下文长度线性增长（幸运不是平方），但随 batch 也线性，多租户下迅速爆炸

这就是 2026 年 KV Cache 成为大模型推理「第一成本杠杆」的因果链：长上下文需求↑ → KV 线性膨胀 → 显存墙 + 带宽墙 → 管理与压缩技术成为工程核心。

1.3 管理机制：从连续预分配到 OS 式虚拟内存

前 PagedAttention 时代的三大浪费（cnblogs 探秘Transformer系列总结）：

  1. 按最大序列长度预分配连续大块——实际序列往往远短于上限，预留槽位大量闲置
  2. 请求生命周期内整块保留——短请求用不了别人闲置的块
  3. 伙伴分配器式外部碎片——KV 是巨大张量必须连续，请求间长短不一导致碎片率 60-80%

PagedAttention（vLLM）的核心思想：把 OS 虚拟内存搬进 GPU

  • KV Cache 切成固定大小 block（如 16 token/块），按需分配
  • 每个请求持有 block table（逻辑序号 → 物理 block 的映射表），逻辑连续、物理离散
  • 结果：有效利用率从 50-65% 升到 95%+，计算开销仅 2-5%
  • 它是地基——后续 prefix caching、驱逐、量化、层级存储全部构建在 block 抽象之上

vLLM v1 Prefix Caching 的完整数据结构（官方设计文档）：

  • 每个 block 计算 hash(block内token序列 + 前缀所有block的hash)——链式哈希保证块内容+位置唯一标识
  • v0.11 起默认 sha256，可选 sha256_cbor（跨语言可复现）/ xxhash（快但非加密安全）
  • KVCacheBlock 类四要素：block_id（物理块号）/ block_hash（内容指纹）/ ref_cnt（引用计数）/ 双向链表指针（进 free queue）
  • 只缓存满块——尾部不满的块不进缓存索引

LRU 驱逐的精确机制：

  • 请求结束 → 块按逆序进 free queue，但内容哈希仍保留（可被后续请求命中）
  • 新请求分配块时：先 touch 所有缓存命中块（移出 free queue 防误逐），再从队尾取空闲块
  • 取到队首的已缓存块仍不够时 → evict：清 block_hash、断开引用、物理复用
  • 本质：「能复用就复用，显存不够按 LRU 牺牲最久未命中」——和 OS 页面置换同构

多租户安全：cache_salt

  • 请求可带 cache_salt，注入首块哈希——只有同 salt 的请求能互相复用缓存
  • 防两类攻击：时序侧信道（通过延迟差异推断他人缓存内容）+ 跨租户内容泄漏
  • 这是共享推理平台（llm-d、vLLM Production Stack）的隐私必备件

SGLang RadixAttention：从哈希表到基数树

  • vLLM 用 block 级链式哈希；SGLang 用 radix tree 组织全部历史请求的前缀
  • 多轮对话 / Agent 分支探索 / Monte Carlo 采样等「树状前缀」负载，radix 树天然贴合，多轮缓存命中率 75-95%
  • vLLM 官方实测：10K token prompt 二次发送，TTFT 从 4.3s 降到 0.6s（约 7×）
  • 2026 工程共识：共享前缀负载（Agent/多轮/RAG）选 SGLang，独特 prompt 批处理选 vLLM

1.4 驱逐与压缩：五大优化族谱系（本地 skill 累积 + 2026 新研究）

五大族框架（digitalapplied 2026 工程指南，与本地 skill 研究互证）：

① Paged Attention（底座）   —— 分页管理，碎片 60-80% → <5%
② Prefix Caching（应用侧）  —— 命中即免算，成本省 85-95%，最高杠杆
③ 注意力架构压缩            —— MQA 32× / GQA 4-8× / MLA 7-14×（质量几乎无损）
④ KV 量化                   —— FP8 半量（生产默认）/ INT8 / KVQuant 8-16×
⑤ Token 驱逐（Eviction）    —— 丢不重要 token 的 KV，2026 研究最热

五族可叠乘：MLA(14×) × FP8(2×) = 28×；再叠驱逐可达百倍级。DeepSeek V4-Pro MLA@FP8 把 KV 从 135GB 压到 8GB（17×）。

驱逐算法五大代表（arXiv:2512.12008 综述）：

  • StreamingLLM：只保 attention sink（开头几个 token）+ 滑窗最近 token。纯位置策略，O(1) 常数时间，零打分开销——延迟最优基线
  • H2O（Heavy Hitter Oracle）：按累计注意力得分动态保留「重击者」token——计算贵但语义准
  • SnapKV：只看观察窗内 query 对其他 token 的注意力来打分，prefill 一次定型
  • K-Norm：用 Key 范数小作为高注意力代理——极廉价
  • TOVA：token 版注意力累计（Time-Orthogonal 累计近似）

Attention Sink 现象（必须理解的反直觉事实）：

  • 序列开头的少数 token 会吸走海量注意力质量（大量激活集中在 sink token）
  • Sun/Canziani/LeCun 2026 (arXiv:2603.05498) 形式化解剖了 massive activation 与 sink 的解剖学结构
  • 驱逐 sink token 是灾难性的（StreamingLLM 首次证明）——所以一切驱逐策略都必须显式保护序列头部

ACL 2026《The Pitfalls of KV Cache Compression》的关键警告：

  • 压缩评测都在「单指令长文档」上做——真实场景是多指令 prompt
  • 实测：正交指令混装时，StreamingLLM/H2O/SnapKV 系统性偏向最近指令，K-Norm 偏向早期指令——因为它们的打分函数隐含「prompt 内文本彼此相关」假设
  • 改进方向：whitelist（显式保护关键指令）+ fair eviction 可一致提升分数
  • 工程含义：别把论文压缩比直接当生产预期，先在自己的多指令负载上复测

前沿驱逐/压缩代表：

  • CompressKV（SuRE'26）：发现 GQA 模型头是异构的——用「语义检索头 SRH」而非全头聚合分数来选 token。LongBench QA 保留 3% 缓存保 97% 性能；大海捞针 0.7% 缓存达 90% 准确率
  • RocketKV（NVIDIA, ICML 2025）：两阶段（粗粒度永久驱逐 + 头/序列双维 top-k 稀疏），最高 400×压缩、3.7× 端到端加速
  • KVQuant（NeurIPS 2024）四创新：Per-Channel Key 量化 + Pre-RoPE 量化（RoPE 旋转后 Key 分布不利于量化，这是关键洞察）+ 非均匀 datatype + 每向量 outlier 隔离——目标单 A100 跑 100 万 token
  • DuoAttention（MIT, ICLR 2025）：头二八法则——少数 retrieval head 要全量 KV，多数 streaming head 只需固定窗口。MHA 内存 2.55×↓；+量化后 Llama-3-8B 单 A100 跑 333 万 token

1.5 修改与利用：四个层面的实操

层面 A：模型代码层（HuggingFace Transformers 直接操作 cache 对象）

from transformers import AutoModelForCausalLM
from transformers.cache_utils import DynamicCache

model = AutoModelForCausalLM.from_pretrained(...).cuda()
cache = DynamicCache()

# 正常生成：每步把新 K/V 追加进 cache
out = model(input_ids=tokens, past_key_values=cache, use_cache=True)
# out.past_key_values 即更新后的 cache；下步只喂 last_token

# 修改①：截断（回滚到第 k 步——分支重生成/树搜索场景）
cache.crop(max_length=k)

# 修改②：跨请求移植（把 A 会话的 KV 喂给 B 的前缀——
# 前 80% 相同的对话只需算 20%）
# 注意：直接拼接要求两段 prefix token 完全一致，且要传对
# position_ids，RoPE 对位置敏感

# 修改③：量化 cache（离线工具把 K/V 张量转 FP8/INT8 存储，
# 注意力计算前反量化）

修改 cache 的两条红线：prefix 必须逐 token 一致（否则 K/V 语义错位，输出静默劣化）；位置编码要连续正确（RoPE 下错位的 position_ids = 错误的相对距离感知）。

层面 B：推理引擎启动参数（生产最常用）

# vLLM：KV 量化（生产默认推荐 FP8）
vllm serve <model> --kv-cache-dtype fp8

# vLLM：prefix caching（v1 默认已开，v0 需显式）
#   禁用：--no-enable-prefix-caching
#   哈希算法：--prefix-caching-hash-algo sha256_cbor（跨版本可复现）

# vLLM：TurboQuant KV（vLLM Blog 2026-05 实测结论）
#   内存充裕 → fp8（2x 容量，零损失，硬件加速）
#   内存紧张 → turboquant_4bit_nc（3.4x，轻微损失）
#   3-bit 变体生产慎用：推理任务最高 -20 分（AIME25/GPQA）

# llama.cpp（边缘/本地）：K 和 V 分别量化
llama-server --model xx.gguf --cache-type-k q4_0 --cache-type-v q4_0

# SGLang：分层缓存 HiCache（GPU→CPU→磁盘，见层面D）

请求级 API 参数（OpenAI 兼容端点）：cache_salt（租户隔离）；Anthropic API 的 cache_control（显式标记可缓存段落）；DeepSeek API 自动前缀缓存（命中部分约 1/10 计价）。

层面 C：调度与路由层（集群视角）

  • llm-d / vLLM Production Stack：分布式 KV 索引 kvcache.Index 提供全集群实时缓存视图，调度器的 Precise Prefix-Cache Scorer 给每个入站请求算「路由到哪台副本命中最多」——cache-aware routing，把 prefix caching 从单机优化升级为集群调度信号
  • AIBrix：分布式前缀缓存池 + Prefix Router（hash 匹配或 radix tree 匹配两种策略）
  • KVFlow（arXiv:2507.07400）：把 Agent 工作流 DAG 的先验喂给 SGLang——工作流感知驱逐（哪些前缀即将被下游节点用到，就推迟驱逐）+ 全重叠 KV 预取。多 Agent 工作流加速显著
  • Mooncake（月之暗面）：KV Cache 为中心的分离式架构——Conductor 全局调度器 + 分块管道并行，超长上下文场景把 KV 当「一等公民」资源调度（预填充节点产出 KV → 传输给解码节点），KV 传输走 RDMA/零拷贝（NIXL）

层面 D：层级存储（打破显存墙）

  • SGLang HiCache：KV 分层 GPU → CPU RAM → 磁盘，热前缀驻显存、冷前缀下沉
  • NVIDIA KVBM（KV Block Manager）：统一内存 API 管异构存储（GPU/CPU/SSD），block 状态机管理生命周期 + NIXL 库做 GDS/RDMA 高效传输——本质是「KV Cache 专属操作系统」
  • LMCache：vLLM 生态的 KV 持久化层，跨实例复用

层面 E：应用架构层（Agent 工程师最高 ROI）

  • Reasonix 三分区模式：Immutable Prefix（system prompt+工具规格，整个会话不变，100% 命中）+ Append-Only Log（对话历史只追加禁止改写——保留前缀缓存不变量）+ Volatile Scratch（思考草稿每轮重置，根本不发 API）
  • DeepSeek API 前缀缓存实战数据：4.35 亿 input token，99.82% 命中率，实付 ~$12（无缓存要 ~$61）
  • 多轮 Agent 的禁忌：改写历史消息 = 销毁其后所有缓存。所以「不支持编辑历史消息」是缓存视角下的架构约束而非产品缺陷
  • Agent 每 30-50 轮「重新锚定」一次（重发完整上下文）防止前缀漂移累积

1.6 KV Cache 与投机解码的交互（容易被忽视的修改场景）

投机解码（EAGLE-3/MTP）会引入三个 KV Cache 特殊操作（ForceInjection/AI-fundamentals 拆解）：

  1. Placeholder 预留：验证 k 个 draft token 前先在 cache 预留 k 个槽位
  2. 猜错回退：draft 被拒时用 num_computed_tokens 回退指针撤销已写入的 KV——cache 必须支持「逻辑截断」
  3. draft/target KV 形状对齐：两套模型的 KV 布局要一致才能共享管理器

工程含义：开推测解码的引擎，KV Cache 不是只追加的——它要求管理器支持高效回滚，这也是 PagedAttention block 抽象的又一个红利（回退=丢弃部分块，无需 memmove）。

1.7 KV Cache 的语义属性：黑盒数据 → 白盒资产 → 可编辑语义（二轮增补）

命题来源：「KVcache 是可存储下来的黑盒数据，是有语义信息的、可以存下来的白盒数据（可修改内容），是一种可以修改语义的数据。」——该说法方向正确，但需要拆成三个递进层次并加约束条件，否则会误导工程实践。

1.7.1 三层递进：从黑盒到白盒的光谱

第一层：它是「可存储的黑盒数据」——成立，且已是产业事实

KV Cache 是纯张量（形状 = 层 × 头 × 序列 × head_dim），不依赖模型对象即可独立序列化存盘、跨进程加载、跨节点传输。产业证据：LMCache / SGLang HiCache 把 KV 存 CPU/SSD；Mooncake 把 KV 当集群可调度资源用 RDMA 传输；DeepSeek API 的前缀缓存本质是「平台替你存的 KV」。黑盒性体现在：张量本身不含词表映射，单看一个 K/V 向量不知道对应哪个词，但它完整保留了该 token 在该层的计算语义——重新加载后注意力计算结果与重算完全一致（cache 是确定性的纯函数输出）。

第二层：它是「有语义信息、可存的白盒数据」——成立，且有双重证据

  • 语义定位证据（读方向）：attention attribution 可以反解「哪个输出 token 依赖了 cache 中哪个位置」——这正是 CompressKV 找语义检索头、CachePrune 做归因剪枝的操作基础。位置可读 + 依赖可归因 = 不是黑盒。
  • 语义结构证据（写方向）：K 编码「这个 token 是什么」（被谁检索），V 编码「如果被检索到要交付什么内容」。检索类比下 K=倒排索引、V=文档正文——两者都有明确语义分工，这正是它能被编辑的原因。

第三层：它是「可以修改语义的数据」——成立，但受两条物理约束（光谱而非开关）

KV 可编辑，但「可编辑的自由度」取决于位置绑定度，这是整个命题最容易被忽略的约束：

位置绑定度光谱（可编辑性从低到高）
─────────────────────────────────────────────────────────────
前缀 KV          非前缀 KV         KV 内容编辑
(位置=语义锚)     (可重组+修)       (语义改写)
 │                │                │
 │ 前缀改一个词    │ 文档块在 prompt │ 定向改 V 向量→
 │ → 其后所有 KV   │ 中间任意位置    │ 事实级改写模型行为
 │ 全部作废       │ 复用(需修跨注意力)│ (CachePrune删"不要跟随"的KV)
 │                │ (CacheBlend/EPIC)│
 └─ 黑盒侧：只能整体作废/复用，不能局部改 ──→ 白盒侧：可定向增删改
─────────────────────────────────────────────────────────────

约束一（位置绑定）：RoPE 使每个 K 向量携带绝对位置信息，且每个 K/V 在计算时吸收了它前面全部上文的注意力混叠。所以前缀 KV 是「牵一发动全身」的：插入/删除早期 token 会使其后所有 KV 语义错位。改写自由度 = 1/位置绑定度。

约束二（跨注意力耦合）：非前缀复用/拼接的最大障碍不是位置，而是块间交叉注意力——独立 prefill 的块 KV 缺少「看见彼此」的计算。CacheBlend 论文的核心问题就一句话：如何组合预计算块 KV 同时保住全量 prefill 的生成质量。

1.7.2 KV 编辑的三个工程流派（2024-2026 研究版图）

流派一：语义重组派（不改变内容，改变组合）

  • PromptCache（NeurIPS 2024）：首次把 cache 当「可组合模块」——对 schema 定义的重复文本段预计算 KV，推理时按需拼接（buffer 机制修位置）。适合 prompt 模板场景，但受 schema 声明约束
  • CacheBlend（EuroSys'25 最佳论文，中科大+Microsoft）：解决「非前缀 KV 复用」——RAG 场景文档块被检索到 prompt 不同偏移处，直接拼 KV 会丢跨块注意力。方案：只选择性地重算一小部分 token 的 KV（按层间偏差选点）恢复跨注意力，其余全复用 → RAG 场景近 100% KV 命中率、TTFT 大幅下降，且重算流水线可与 KV 检索重叠
  • EPIC：位置无关缓存 + LegoLink 修正每个块开头的 attention-sink 行为
  • CacheClip（arXiv:2510.10129）：比 CacheBlend 更准的选点——同质量下重算 token 减少 3.5×（multivalue 任务 20% 重算达 96% 质量 vs CacheBlend 需 70%）
  • RAGCache：块序列前缀树，最大化 RAG 管线复用
  • 这一流派的本质：KV 成了「文档的一等公民表示」——存文档的 KV 比存文档文本再重算更接近「知识库即缓存」。CAG（Cache-Augmented Generation）甚至用「预填充整个知识库进 cache」替代 RAG 检索

流派二：语义编辑派（定向修改内容，改变模型行为）

  • CachePrune（ACL 2026）：《Teaching LLMs What Not to Follow via KV-Cache Editing》——不训练、不改权重，在 prefill 后对 KV 做归因分析，剪掉「教模型不要跟随的上下文」的 KV，直接改变生成行为。应用：防间接提示注入（对抗检索内容里的恶意指令），在不伤正常质量下显著降低注入成功率
  • Neural KV Database（ICLR 2026）：把知识编辑扩到 10 万条事实——用 KV 数据库做事实的增删改查，绕过 ROME 类方法改权重的局限。这是「KV=可编辑知识存储」命题的最直接学术实现
  • 与权重编辑（ROME/MEMIT）的关系：改 MLP 权重是「改大脑」持久但侵入；改 KV 是「改当下上下文」会话级、可逆、零训练。Editing Attack（AAAI 2026）警告反向风险：编辑技术可被用来注入偏见/错误信息——可编辑性是双刃剑
  • 工程配方（Medium 实践文总结）：attribution 识别注入候选 → pruning 剪 KV → conservative cache policy，已有可落地 pipeline

流派三：语义泄露派（可读性的阴暗面）

  • NDSS 论文证实：多租户共享 KV cache 可导致 prompt 泄漏——攻击者可通过缓存共享侧信道推断他人 prompt 内容。白盒可读性对主人是资产，对租户邻居是攻击面
  • 这正是 vLLM cache_salt（§1.3）存在的深层原因：哈希隔离不只是性能设计，更是安全边界

1.7.3 语义视角对五大优化族的重新解释

|（本节用列表替代表格）五大族在「语义资产」框架下的统一理解：

  • PagedAttention：语义资产的虚拟内存管理器（block=语义页）
  • Prefix Caching：语义资产的去重存储（同前缀=同语义，免重算）
  • 驱逐（Eviction）：语义资产的价值排序保留（attention score=语义重要性打分）
  • 量化：语义资产的有损压缩（FP8 保真、3bit 语义损伤）
  • 非前缀复用（CacheBlend 系）：语义资产的重组（块 KV=语义 Lego 积木，重算补跨注意力）

一句总纲：KV Cache 正在从「推理引擎的临时中间结果」演化为「可存储、可检索、可重组、可编辑的语义资产层」——这是 2026 年与 2023 年最大的观念差异。

1.7.4 该说法的三点修正（严谨性边界）

  1. 「黑盒→白盒」不是二选一，是位置绑定光谱：前缀 KV 近黑盒（只能整体复用/作废，局部改=灾难），非前缀块白盒度居中（可重组但必须修跨注意力），KV 内容编辑最白盒（定向增删改，CachePrune/Neural KV DB 已验证）。忽略位置绑定度会把「可编辑」误用在前缀上
  2. 「有语义信息」的正确强度：KV 的语义是张量级/依赖级的（位置对应 token、attention 可归因、K/V 有检索语义分工），不是文本级可读的（不能从 K 向量直接读出「这存的是‘巴黎’这个词」——没有词表逆映射）。它是「结构化可解释但非人类可读」的中间态
  3. 修改的两条红线依然统治一切（§1.5 红线在此升维）：prefix 一致性 + position_ids 正确性不仅是工程红线，更是 KV 语义结构的物理约束。所有编辑流派（重组/编辑/注入防御）本质都在这两条约束内做文章：重组派绕位置（重算修跨注意力），编辑派绕内容（剪/改 V），没有人能绕过「K 携带位置+上文混叠」这个数学事实

二、查询拓展

2.1 为什么 Q 不缓存（检索类比）

把注意力看作「软检索」：Q 是查询语句（每次发完即弃），K 是被检索文档的索引（要长期在线），V 是文档正文（命中后取出的内容）。因果掩码保证历史 token 的 K/V 永不变化，但 Q 只在「当下这个 token」的意义上存在——缓存它没有复用价值。

2.2 RoPE 与 Pre-RoPE 量化的关系

RoPE（旋转位置编码）对 Key 向量做位置相关旋转，旋转后的 Key 分布出现通道间大幅异方差——直接量化精度崩坏。KVQuant 的洞察：在 RoPE 之前量化（此时 Key 分布近似各向同性），需要时再旋转恢复。这是「算法层设计挤压量化空间」的典型案例，同理 PromptCache/MLA 的低秩压缩也选在旋转前做。

2.3 MLA：从「减少头」到「压缩状态」的范式转换

GQA/MQA 靠共享 K/V 头减量；MLA（DeepSeek V2/V3、GLM-5、Kimi K2 采用）把 KV 压成 512 维 latent 向量，用时重建——压缩比 7-14× 且质量不降反可能超 MHA。MHA2MLA（ACL 2025，复旦+海康）证明任意 MHA 模型可用 Partial-RoPE + 联合 SVD 迁移到 MLA，仅 0.6-1% 训练数据，KV 再降 92%。本机 zai provider 的 GLM 系列正是 MLA 架构——这是边缘部署能跑长上下文的底层原因。

2.4 TTFT/TBT/TPOT 指标体系

  • TTFT（Time To First Token）：prefill 延迟，前缀缓存直接改善（4.3s→0.6s 实测）
  • TBT（Time Between Tokens）：相邻 token 间隔，反映解码波动，比平均指标 TPOT 更细
  • KV 优化映射：prefix caching 改善 TTFT；量化/驱逐/分层存储改善 TBT（带宽与容量）；两者独立可叠加

3.2 管理生命周期（vLLM v1 视角）

新请求 → get_computed_blocks() 查哈希命中
       → allocate_slots() 分配（命中块 touch 出队 + 新块从 free queue 取）
       → 解码中逐块填满 → 满块注册 hash 进缓存索引
       → 请求结束 → 块进 free queue（hash 保留，LRU 可命中）
       → 显存耗尽 → evict 队首最久未用缓存块（清 hash 复用物理块）

3.3 「怎么修改利用」四层速查

  • 改对象（HF DynamicCache）：crop 截断 / 跨请求移植 / 离线量化——受限于 prefix 一致 + position_ids 正确两条红线
  • 改参数（引擎启动项）：--kv-cache-dtype fp8 / --cache-type-k q4_0 / prefix caching 开关与哈希算法
  • 改架构（集群）：cache_salt 隔离 / cache-aware routing / HiCache 分层 / PD 分离 KV 传输
  • 改应用（最高 ROI）：Reasonix 三分区（immutable+append-only+volatile）/ 只追加不改写历史 / 定期重新锚定

3.4 选型决策链

负载特征？
├─ 共享前缀（Agent/多轮/RAG）→ SGLang RadixAttention（命中率75-95%）
├─ 独特 prompt 批处理 → vLLM（差距<5%，生态广）

四、趋势判断

趋势1：KV Cache 从「优化对象」升格为「一等公民资源」

依据：Mooncake 把调度器命名为 Conductor 围绕 KV 组织全局；KVBM 做成 KV 专属内存操作系统；llm-d 用 KV 索引驱动集群路由。2024 年 KV 是引擎内部细节，2026 年 KV 索引/传输/调度成为独立架构层。

趋势2：驱逐研究从「打分更准」转向「负载感知」

依据：ACL 2026 揭示单指令评测与多指令现实的偏差；KVFlow 用工作流 DAG 先验指导驱逐时机；CompressKV 用头异构性（SRH）取代全头聚合。纯启发式打分的边际收益在缩小，结构先验（谁将被复用）成为新战场。

趋势3：应用层缓存工程成为 Agent 团队必修课

依据：DeepSeek 前缀缓存 10 倍价差 + Reasonix 99.82% 命中实证；多轮 Agent 禁改写历史成为架构约束；API 侧（Anthropic cache_control / vLLM cache_salt）接口标准化。缓存纪律 = 成本纪律，Agent 框架设计阶段就要内建。

趋势4：MLA 化 + KV 量化成为长上下文默认出厂配置

依据：DeepSeek/GLM/Kimi/Mistral 新模型全面 MLA；MLA(14×)×FP8(2×)=28× 已可叠加验证；MHA2MLA 让存量模型低成本迁移。模型架构层和引擎层正在「合谋」让 KV 墙变矮。

趋势5（二轮增补）：KV Cache 正在成为独立的「语义资产层」（08-21）

依据：CacheBlend 把文档 KV 当可重组积木（RAG 近 100% 命中）；Neural KV Database（ICLR 2026）把 10 万条事实的增删改查做进 KV 层；CachePrune 证明「剪 KV=改行为」零训练可行；CAG 用整库 prefill 替代检索。四条独立证据线共同指向同一结论：KV 已越过「引擎内部优化对象」阶段，正在成为与 embedding 层、RAG 索引层并列的基础设施层——存什么、复用什么、剪什么、改什么，都是独立的架构决策。这条趋势也直接验证了「白盒语义数据」命题的前瞻性。

八、拓展应用推荐

8.1 Hermes Agent 前缀缓存改造（本环境最直接的应用）

Hermes 所有会话共享 AGENTS.md + system prompt + 工具规格大段不变前缀（5-8K token），若推理后端启用 prefix caching / RadixAttention，TTFT 可省 80%+。改造路径：zai provider 走 API 时确认前缀缓存计价（智谱/DeepSeek 命中部分约 1/10 价）；本地引擎化后天然受益。

8.2 盯盘系统批处理优化

盘中扫描 cron 逐只跑 30+ 股票，prompt 模板高度一致（仅 code/name 参数变化）——把不变部分（铁律规则+输出格式说明）前置为统一前缀、变量部分放尾部，缓存命中率可 >90%，单轮扫描成本降 5-10×。

8.3 RAG 知识库服务（knowledge-query/RAG 场景）

静态参考文档场景 = prefix caching 最佳形态：文档 KV 一次 prefill 后 24h TTL 常驻，每次问答只算问题增量。配合 CompressKV 式驱逐（3% 缓存保 97%），单卡可服务的知识库容量扩大一个量级。

8.4 多 Agent 工作流（delegate_task 链）

并行 subagent 共享同一任务简报前缀 → radix tree 天然聚合；KVFlow 的工作流感知驱逐思路可借鉴：编排器把「即将被下游节点复用」的前缀标记为推迟驱逐。

按 §3.4 选型决策链入口：先判断负载形态（共享前缀 vs 独特 prompt），再按显存预算选量化档位，最后按多租户/多指令现实校准驱逐策略。三条主线索引：原理与管理机制看 §1.1-1.3，修改利用实操看 §1.5 四层面 + §3.3 速查，避坑看 §1.4 ACL 2026 偏向性警告与两条红线（prefix 一致 + position_ids 正确）。

9.2 指南的适用边界

  • 结论时效：引擎参数与压缩比数据截至 2026-08，vLLM/SGLang 迭代快，部署前以官方文档复核参数名
  • 数字口径：论文压缩比多为单指令长文档负载，多指令生产负载需按 ACL 2026 方法复测
  • 边缘特例：Jetson 8GB 统一内存下 FP8 KV 无硬件 Tensor Core 加速，Q8/Q4 软件量化路径更现实

9.3 「语义可编辑性」使用指南（二轮增补）

§1.7 的三流派选型逻辑：只省钱的场景走重组派（CacheBlend，RAG/多文档，零质量损失目标）；要改行为的场景走编辑派（CachePrune 剪上下文影响 / Neural KV DB 事实级增删改）；多租户场景先堵泄露面（cache_salt + 共享策略审计）。三者共同前置检查：目标 KV 的位置绑定度（§1.7.1 光谱）——它决定你能用哪把刀。安全红线：编辑能力=注入能力（Editing Attack），任何对外提供 KV 编辑能力的系统都同时打开了攻击面，需配套审计日志。
