## 一句话总纲

> **nativePDF-structurer 是 PDF 解析工具链的一个"确定性锚点"：零 OCR、零模型依赖，纯 PyMuPDF 图元分析重建阅读顺序/章节层级/表格/视觉区域，面向 50-500 页厂商技术手册场景。** 它不追求"最智能"（不调模型），而是追求"可审计"（provenance 追踪每个输出块的来源页面/坐标/置信度），输出 Markdown + CSV + PNG + IR + provenance。对飞机设计企业的大量技术手册/维修手册/安装说明 PDF 来说，它是 MinerU 等高成本管线之前的**确定性基线**——先跑 nativePDF 看够不够，不够再加模型。

## 一、内容详细整理

### 1.1 项目定位

**目标场景**：厂商发布的技术文档——设备操作手册、维修手册、安装说明、产品选型手册、电气手册、技术目录。典型特征：数十至数百页，反复出现页眉页尾/参数表/步骤编号/设备插图/矢量标注/图文混排。

**明确不优化的场景**：
- 复杂公式还原为 LaTeX（默认 PNG 保留，LaTeX 通道只对简单公式保守尝试）
- 学术论文的引用关系/双栏模板/语义章节分类
- 少于 20 页的论文（推荐 MinerU）

### 1.2 技术架构

**依赖唯一性**：PyMuPDF + NumPy + OpenCV headless + Pillow——**零 OCR、零 GPU、零外部服务（Poppler/Ghostscript）**。

**核心组件**：PageRunContext（页面阶段契约）+ Claim 所有权模型 + 模块边界扩展流程（见 docs/architecture.md）

**核心技术**：GapTree Sort Algorithm（基于 hiroi-sora 开源实现扩展）——按文字/表格/图片/矢量区域的统一空间排序重建阅读顺序。

### 1.3 输出结构

```
output/
├── document_with_reflowed_text_and_tables.md
├── source_images/            # 原始页面图片
├── visual_regions/           # 视觉区域（设备图/矢量标注）
├── tables/                   # 表格 PNG + CSV
├── formula_images/           # 公式 PNG
└── document_ir.json          # 调试模式的中间表示
```

**关键输出**：provenance（来源定位）——每个输出块记录来源页面/坐标/置信度，RAG 可审计。

### 1.4 视觉区域处理（核心能力）

复杂设备图同时包含位图+矢量轮廓+引线+警告符号+参数框+图内文字——项目将彼此连接的对象保留为一个视觉区域，避免拆成顺序错乱的多张小图。

**编号图+说明表保持关联**：编号引线解释设备接口 → 下页说明表逐项解释编号含义。项目保留编号图的整体几何关系，说明表紧随其后输出。

**表格与尺寸图分离**：规则表格→表格通道（PNG + CSV），相邻尺寸矢量图→视觉区域通道，保留原始版面关系。

### 1.5 可选 VLM 后处理

```
原生 PDF → nativePDF（结构恢复/切分/排序/来源定位）
  → Markdown + 图片/表格 + IR + provenance
  ├─ 直接作为最终文档或 RAG 输入（不需要图片释义）
  └─ 可选 VLM（图片语义描述/图表理解/多模态索引）
    → 语义增强后的 RAG 入库与检索
```

**设计哲学**：先确定性分析完成切分和来源定位，再只对确有需要的视觉区域调用模型——避免"全量 OCR"的浪费。

## 二、查询拓展

### 2.1 在 PDF 工具链中的定位

| 工具 | 方式 | 模型依赖 | 适合场景 | 成本 |
|------|------|---------|---------|------|
| **nativePDF** | 纯图元分析 | ❌ 零 | 数字原生技术手册 | 低（CPU 即可） |
| **MinerU** | 视觉+布局模型 | ✅ 需 GPU | 论文/扫描件/复杂排版 | 高 |
| **OpenDataLoader** | 模型管线 | ✅ 需 GPU | 通用→AI 就绪 | 中 |
| **marker-pdf** | 视觉模型 | ✅ 需 GPU | 通用→Markdown | 中 |

**nativePDF 填补的空白**：在"全量上模型"和"不处理"之间提供一个可靠的确定性基线。对于飞机设计企业的大量技术手册 PDF（文字层完整），**可能 80% 的场景不需要跑模型**。

### 2.2 与用户领域的高度匹配

飞机设计企业的技术手册/维修手册/操作手册/产品选型目录——正是 nativePDF 的核心目标场景：50-500 页，反复出现编号图+说明表/参数表/设备插图/矢量标注。**不是学术论文，不是双栏模板，正是技术文档 PDF**。

### 2.3 负责任的限制声明（项目做得比多数开源项目好）

项目 README 用大量篇幅诚实标注了不做什么：不保证公式恢复/不处理扫描件/不处理论文/不保证复杂排版完美。这比"号称什么都能做但实际不行"的工具更值得信任。

## 三、归纳总结

### 3.1 架构三特点

1. **确定性**：零模型、零随机性——同一 PDF 两次运行结果完全一致，可审计
2. **可审计**：provenance 追踪每个输出块的来源页面/坐标/置信度
3. **可组合**：输出可独立使用（RAG 输入），也可作为 VLM 的前处理层

### 3.2 三不保证

1. 不保证公式还原（复杂公式回退 PNG）
2. 不保证扫描件（必需文字层）
3. 不保证学术论文（双栏/引用/语义分类无专项建模）

## 四、趋势判断

### 趋势 1：PDF 解析的"确定性基线"将成为 RAG 管线的标准组件

> 依据：nativePDF 的零模型确定性 + provenanc 可审计 + 无 GPU 部署——当 RAG 质量可追溯成为合规要求（如飞机设计企业的适航文档），模型管线的"黑箱"不可接受。**预期"先确定性分析，不够再加模型"成为标准管线架构**，与 nativePDF 的 VLM 可选后处理设计一致。

### 趋势 2：技术文档 PDF 解析将独立于学术论文解析形成专门工具链

> 依据：nativePDF 明确说不优化论文，MinerU 偏论文但处理技术手册也有资源浪费。**两类文档的版面结构差异大**（技术手册的编号图+说明表/参数表/矢量标注 vs 论文的双栏/引用/公式），指望同一工具覆盖两端的性价比越来越低。

## 六、拓展应用推荐

1. **航空技术手册 RAG 预处理**：飞机维修手册/操作手册（50-500 页，文字层完整）→ 先用 nativePDF 做确定性结构化，不够再补 MinerU
2. **与 MinerU 交叉验证**：同一 PDF 两管线跑，合格率 >90% 可只用 nativePDF（省 GPU 成本）
3. **provenance 审计**：适航文档场景要求"每个输出块可追溯至源页面/坐标"——nativePDF 的 provenance 输出是合规加分项
4. **本地项目**：已创建 `~/uclaw/project/nativepdf-structurer/`，README 含安装/运行/场景说明

## 七、指南分析

### 7.1 项目质量

- **文档质量**：★★★★★——README 中/英双语，架构文档（architecture.md）详细，使用场景/限制/致谢完整
- **定位清晰**：不贪大，诚实标出"不做"什么（公式/论文/扫描件）——比"万能工具"可信
- **工程规范**：pyproject.toml / environment.yml / CI (GitHub Actions) / tests / LICENSE / THIRD_PARTY_NOTICES
- **视觉证明**：README 带真实 PDF 输出截图（维修手册/产品手册/操作手册三种场景）

### 7.2 局限

- v0.1.0，成熟度待验证（大规模回归结果未公开）
- GapTree 并非原创，但作者承认并致谢（MIT 保留）
- 非扫描件限制意味着对老旧 PDF 或扫描存档不可用
- 当前版本只有前 60 页回归示例，完整 500 页手册的稳定性未知
