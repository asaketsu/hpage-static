## 一、内容详细整理

### 项目画像

| 维度 | 内容 |
|------|------|
| 定位 | AI 工程化 + 文档渲染 + 异步任务编排的全栈 PPT 生成教程（求职向教学项目，代码完整开源） |
| 技术栈 | FastAPI + LangChain(LCEL) + LangGraph + python-pptx + React/TS + ARQ + Redis + SSE；另有 Java 双后端版本（174 个 Java 文件，纯教学） |
| 输入 | 三入口：一句主题 / 长文本粘贴 / 文档上传（PDF/Word/Markdown/TXT） |
| 输出 | 原生可编辑 PPTX（非整页截图） |
| 规模 | backend 25.7K 行 Python；shared/ 含布局预设 JSON + 4 套主题（ivory/midnight/obsidian/scholar） |

### 4 大核心能力（README 自述 + 源码印证）

**1）多输入 → 可改大纲**：模型不越过用户直接生成成稿，先产出结构化大纲（标题/页面目标/要点），用户可增删页、调顺序、改内容，确认后才进入逐页生成。

**2）异步并发生成**：每页拆成独立 ARQ 任务，`asyncio.Semaphore(slide_concurrency)` 控制模型调用频率，Redis 保存状态+传递事件，前端 SSE 实时进度。完成页立即预览、失败页单独重试、支持软取消。

**3）在线编辑器**：内容/布局/主题三分离数据模型；缩略图+16:9 画布+右侧 AI 修改/主题/版式/图片面板；主题切换后 Web 预览与 PPTX 导出读同一份主题数据（同源渲染）。

**4）原生 PPTX 导出 + 质量门禁**：导出前检查结构/文字占用/数字来源/页面边界，error 阻断、warning 提醒；导出后用 python-pptx **回读验证**（页数/画布/原生对象/内容完整性）。

### 源码精读发现（关键文件）

**workflows/outline.py — 来源预算裁剪**（直接可复用的模式）：
- `MAX_TOTAL_SOURCE_CHARS = 12_000` 总预算 + `MAX_SECTION_CHARS = 2_000` 单节上限
- 按整节追加，超长只截断该节正文——保证 ref 引用与文本不错位
- 标题本身超剩余预算时直接停止（不截断标题，避免语义残缺）
- 空节（无标题无正文）跳过

**workflows/slide.py — 自纠环**（LangGraph 状态机）：
```
prepare → generate → check →(route)→ repair → generate ... → END
```
check 是确定性结构校验（StructureIssue），issue 描述喂回 repair 定向修正，循环上限控制。

**llm/client.py — 结构化输出**：`_PROMPT | ChatOpenAI.with_structured_output(schema, method="json_mode")` 薄封装——LCEL 管道保证模型输出始终可解析。

**llm/edit_tools.py — AI 编辑工具集**：`bind_tools` 暴露 replace_text/replace_bullets/replace_kpi/replace_table/replace_cards/replace_callout/add_block/delete_block/change_type 共 9 个细粒度编辑工具给模型调用——AI 修改页面=模型当"操作员"调工具，而非直接重写整页 JSON。

**domain/content.py — Block 体系**：Deck → Slide → Block（TextBlock/BulletsBlock/ImageBlock/ChartBlock/TableBlock/KpiBlock/CardsBlock/CalloutBlock， discriminated union）。内容与布局与主题三分，同一份数据驱动 Web 预览和 PPTX 导出。

**render/pptx.py + verify.py — 导出与验证**：
- `_fit_stack` 按实测高度写 `normAutofit` 兜底溢出——"告警与导出同源度量"，告警说溢出和导出真溢出是一回事
- verify.py 回读产物：页数/画布尺寸（±0.5pt 容差）/整页截图检测（覆盖≥90% 画布的单 shape 为图=error）/内容完整性

**worker/ — 工程细节**：ARQ 失败必须抛 `arq.Retry` 而非原异常（只有 Retry/RetryJob 会重新入队）；Semaphore 控并发防限流。

### 质量文化（全项目最有价值的暗线）

- 44 个测试文件 + regression/corpus 回归语料
- Makefile 有独立 `regression` 目标
- 导出不是终点：字节流 → 回读 → 验证三步走
- error/warning 二分法贯穿门禁与 UI

## 归纳总结

1. **本项目真正的护城河不是 AI，是工程化**：大纲先行（用户确认点）、页级并发（Semaphore 限流）、自纠环（确定性 check）、导出门禁（回读验证）——四层防线层层兜住不可信的 LLM 输出。
2. **"生成即结束"与"生成-验证-交付"的分水岭**：多数 AI 生成项目（含我们原有 4 个 PPT skill）止步于"文件写出来了"；该项目把导出后回读验证做成硬门禁，这是 Demo 与工程的分界线。
3. **确定性优先**：check 用代码校验（schema/上限/必填）而非 LLM 评分；告警与导出同一套度量口径——可验证性优先于智能。
4. **细粒度编辑工具优于整体重写**：9 个 replace/add/delete 工具让模型做"操作员"，比让模型重吐整页 JSON 可控得多。
5. **教学项目也有真金**：虽为简历导向，但 error/warning 分级、arq.Retry 语义、预算裁剪这类细节是生产级经验。

## 二、趋势判断

1. **"结构化输出 + 自纠环"正在成为 AI 生成的标配骨架**：json_mode 保证可解析、确定性 check 保证合规、repair 循环兜底——这一模式已从前沿论文下沉到求职教学项目，说明已高度成熟。
2. **导出后验证（回读）会成为 AI 文档生成的质量底线**：随着 AI 生成 PPT/Word/Excel 泛滥，"原生可编辑 + 回读验证"将成为区分度的标志，整页截图式生成会逐渐被视为劣质品。
3. **页级并发 + 限流是成本工程必修课**：10 页 PPT 串行等 1 分钟 vs 并发 30 秒完成，Semaphore 控频同时防限流——AI 应用的延迟优化越来越围绕"任务拆分粒度"做文章。

## 三、关联分析（对我有什么提升 + 如何实施）

1. **【已落实】4 个 PPT skill 全部挂上质量门禁**：wan-pptx-generator / ppt-from-notes / powerpoint / open-kimi-ppt 的 SKILL.md 已追加"导出质量门禁（强制）"节——生成后必须跑 verify_pptx.py，exit=1 禁止交付。**这补上了我们 PPT 生产线最大的质量盲区**。
2. **【已落实】新建 skill `ppt-quality-gate`**：含实测通过的门禁脚本（正常文件 warning 路径 exit=0 ✓ / 坏文件 error 路径 exit=1 ✓）+ 两段式生成方法论 + 预算裁剪参数。
3. **来源预算裁剪可平移到 bookmark-reader**：长文档转笔记时的上下文预算（总 12000/单节 2000/整节追加/标题不截断）可直接用于超长文章笔记化——实施：超长文章（>15K 字）先按此规则裁剪再整理。
4. **自纠环可平移到 xhs-content-pipeline / wechat-pb**：内容生成的确定性 check（字数/敏感词/格式）+ repair 循环，替代现在"生成后人工抽查"的弱门禁。
5. **9 个细粒度编辑工具模式对 Hermes 文档编辑的启发**：lark-doc 编辑场景可暴露 replace/add/delete 工具集让模型调用，而非整段重写——降低破坏面。

## 指南分析

**什么时候借鉴这个项目**：

| 场景 | 借什么 |
|------|--------|
| 自建 AI 生成管线（任意格式） | 两段式（大纲确认→逐页生成）+ 自纠环 |
| 长文档压缩进上下文 | 预算裁剪四规则（总/单节/整节/标题保护） |
| LLM 输出可靠性 | with_structured_output(json_mode) + 确定性 check |
| 导出任何文档格式 | 回读验证 + error/warning 分级 |
| 并发调 LLM | Semaphore 控频 + 失败单页重试不整份重来 |

**不该借鉴的**：ARQ+Redis+SSE 全家桶（无 Web 服务的单机场景是负资产）；flex solver 双端布局树（无 Web 编辑器需求）；Java 双后端（纯简历价值）。
