# Agent 元认知：如何让 LLM 知道自己"不知道什么"

> 日期：2026-05-18 | 类型：研究笔记 | 主题：Uncertainty-aware Prompting & LLM Metacognition

---

## 摘要

LLM 在自然语言生成中表现出强大的能力，但本质上仍是一个"自信的胡说八道者"（confident hallucinator）——**模型对自身的无知缺乏感知**。Agent 元认知（Metacognition）是指让 LLM 在推理过程中意识到自身的不确定性，并据此调整行为（如拒绝回答、请求澄清、调用工具、降低置信度）的能力。

Uncertainty-aware prompting 是一系列提示工程和系统设计方法，旨在：

1. **量化不确定性**——通过多次采样、概率分析、一致性检验等手段评估模型对回答的确信程度
2. **表达不确定性**——让模型在输出中显式标注置信度或使用校准化的语言
3. **基于不确定性采取行动**——在高不确定性时触发安全策略（如 fallback 到检索、人工审核）

---

## 一、核心方法（分类列举）

### 1.1 基于采样的不确定性估计（Sampling-based）

**Self-Consistency（Wang et al., 2022）**

- 对同一问题多次采样（temperature > 0），统计多数答案的比例
- 一致性比例可作为不确定性的代理信号：高一致性 → 低不确定性
- **实践要点**：通常 5-10 次采样即可获得合理的信号；适用于有明确答案的任务（数学、事实问答）
- 局限：对开放式生成任务（如创意写作）难以直接定义"一致性"

**语义聚类变体**

- 不要求完全匹配，而是通过语义相似度（如 embedding cosine similarity）聚类采样结果
- 聚类数量 / 熵值 → 不确定性分数
- 适用于长文本生成场景

**Monte Carlo Dropout 等效方法**

- 在推理时通过不同 temperature / top-p 组合模拟模型参数不确定性
- 适用于无法直接访问 logits 的 API 调用场景

### 1.2 基于 Logits / 概率的不确定性（Logit-based）

**Token-level 概率分析**

- 提取生成 token 的 log probability（OpenAI API 支持 `logprobs` 参数）
- 平均 token 概率 → 整体置信度估计
- 最低概率 token → 局部不确定点（可能是幻觉热点）

**校准技术（Calibration）**

- LLM 原始概率通常过度自信（overconfident），需要校准
- **Platt Scaling** / **Temperature Scaling**：在小规模标注数据上学习校准映射
- **关键发现**（Kadavath et al., 2022 "Language Models (Mostly) Know What They Know"）：
  - 经过适当校准后，LLM 可以较准确地预测自己回答的正确性
  - 但在超出训练分布（OOD）的输入上校准效果显著下降

**信息熵（Entropy）**

- 对生成分布计算熵：高熵 = 高不确定性
- 可用于逐 token 检测"模型在哪里开始不确定"

### 1.3 基于 Prompting 的自评估（Prompting-based Self-evaluation）

**显式置信度提示**

```
请回答以下问题，并在回答末尾给出你对该答案的置信度（1-10分）。
格式：答案 | 置信度：X/10 | 原因：...
```

- 简单有效但存在"自评偏差"——模型倾向于高估自己的置信度
- 需配合历史校准数据来修正

**"I don't know" 触发机制**

```
如果你对答案不确定，请直接说"我不确定"，而不是猜测。
在以下情况下请说"我不确定"：
1. 你不记得相关事实
2. 多个可能的答案存在冲突
3. 问题超出你的知识范围
```

- **效果**：显著减少幻觉，但可能过度拒绝（over-refusal）
- 需通过 few-shot 示例平衡"知道但说不知道"和"不知道但假装知道"

**Chain-of-Thought + 自我反思（Self-Reflection）**

- 让模型先生成推理链，然后**审视自己的推理过程**
- 关键 prompt 模式：

```
Step 1: [正常回答问题]
Step 2: 审视你的回答。你的推理中有没有不确定的步骤？
        有没有可能存在其他解释？你的置信度是多少？
Step 3: 如果发现不确定性超过阈值，修正你的回答或标注不确定部分。
```

### 1.4 共形预测（Conformal Prediction）

**核心思想**

- 提供统计学保证的预测集（prediction set），而非单一点预测
- 对于 LLM：生成一个候选答案集合，保证真实答案在该集合内的概率 ≥ 1-α
- **不需要修改模型**，是一种 post-hoc 方法

**实践流程**

1. 在校准集上计算每个样本的"非一致性分数"（nonconformity score）
2. 对于新输入，生成多个候选答案
3. 根据分位数阈值决定输出哪些候选（形成预测集）
4. 预测集越大 → 不确定性越高

**应用于 LLM 的关键工作**

- **SCP（Semantic Conformal Prediction）**：使用语义相似度替代传统非一致性分数
- 可用于选择题、分类任务、NER 等结构化输出场景
- **局限**：对开放式生成任务，定义非一致性分数仍有挑战

### 1.5 基于外部验证的不确定性（External Validation）

**检索增强验证**

- 生成答案后，用 RAG 检索相关文档，比对答案与检索结果的一致性
- 一致性低 → 不确定性高 → 触发修正或降级

**工具使用作为校验**

- 对可验证的问题（数学计算、代码执行），调用工具验证
- 工具结果与 LLM 回答不一致 → 高不确定性

**多模型交叉验证**

- 用不同模型（GPT-4、Claude、Gemini 等）对同一问题生成答案
- 模型间一致性 → 不确定性代理

## 二、实战技巧

### 2.1 分层不确定性管理策略

| 不确定性级别 | 策略 | 触发条件 |
|-------------|------|---------|
| **低** | 直接输出答案 | self-consistency > 0.9 或置信度 > 8/10 |
| **中** | 输出答案 + 标注不确定性 | 0.5 < consistency < 0.9 |
| **高** | 拒绝回答 / 触发 RAG / 请求人工 | consistency < 0.5 或置信度 < 4/10 |

### 2.2 Prompt 设计模式

**模式 1：结构化不确定性表达**

```
你是一个谨慎的 AI 助手。对于每个回答，请遵循以下规则：
- 如果你有 >90% 的把握，直接回答
- 如果你有 60-90% 的把握，回答但明确标注"这部分我不太确定"
- 如果你的把握 <60%，说"我不确定"并解释为什么不确定
- 如果问题超出你的能力范围，明确说"我无法回答"
```

**模式 2：先验知识检查**

```
在回答之前，先问自己：
1. 我是否从训练数据中学过这个知识？
2. 这个信息最近是否可能已经过时？
3. 有没有相关领域我可能混淆？
如果以上任一答案为"是"，在你的回答中注明。
```

**模式 3：逐步置信度标注**

```
请逐步推理并解决问题。在每一步推理后，标注你的置信度 [高/中/低]。
如果任何一步是 [低]，请停下来检查是否有替代方案。
```

### 2.3 工程实现建议

1. **采样参数选择**：对于 self-consistency，推荐 `temperature=0.7`, `top_p=0.95`，采样 5-10 次
2. **logprobs 利用**：优先使用支持 logprobs 输出的 API（如 OpenAI），计算平均 log probability 作为快速不确定性信号
3. **缓存校准数据**：维护一个"问题-答案-不确定性-实际正确性"的数据集，定期校准模型的自我评估能力
4. **阈值动态调整**：根据任务类型和风险级别调整不确定性阈值（医疗 > 法律 > 闲聊）
5. **组合策略**：综合 token probability + self-consistency + self-reflection 三种信号，取加权平均

### 2.4 常见陷阱

- ❌ **过度依赖自我评估**：模型的"置信度"和实际正确率的相关性有限，尤其是 OOD 场景
- ❌ **忽视校准漂移**：模型的校准状态会随时间/上下文变化，不能一劳永逸
- ❌ **只做全局评估**：不确定性可能是局部的（某一步推理出错），需要细粒度检测
- ❌ **一致性 ≠ 正确性**：模型可能一致地给出错误答案（系统性偏差）

## 三、与 Hermes Agent 的结合点

### 3.1 任务路由中的不确定性感知

Hermes Agent 在接收任务时，可以先快速评估自身对任务的不确定性：
- **低不确定性** → 直接执行
- **高不确定性** → 主动搜索 web、读取相关文件、或向用户请求澄清
- 这与 Hermes 的 `web_search` / `web_extract` 工具链天然契合

### 3.2 工具调用的置信度门控

在 Agent 工具使用链中嵌入不确定性检查：
```
LLM 生成工具调用参数 → 不确定性检查（参数正确性）→ 
  低不确定性：执行工具调用
  高不确定性：重新生成或请求用户确认
```

### 3.3 自我反思循环

利用 Hermes 的 subagent 架构实现"执行-评审分离"：
- **执行 Agent**：生成初始回答
- **评审 Agent**：检查回答中的不确定性，标记可能的问题
- 这正是 AGENTS.md 中提到的 Harness Engineering 原则

### 3.4 输出质量门禁

在最终输出前加入不确定性评估层：
- 对代码生成：运行 linter / 测试作为外部验证
- 对事实性问答：self-consistency 检查 + logprobs 分析
- 对高风险输出（法律、医疗）：强制人工审核标记

### 3.5 学习与自我改进

- 记录每次不确定性评估和实际结果的对应关系
- 定期分析"模型不确定但正确"和"模型自信但错误"的案例
- 反馈到 system prompt 和工具使用策略中

## 四、方法论总结框架

```
不确定性感知 = 检测 → 量化 → 表达 → 行动

检测：token 概率异常、采样不一致、自我反思发现疑点
量化：一致性比例、熵值、校准后的概率、预测集大小
表达：置信度标签、不确定性措辞、预测区间
行动：拒绝回答 / 触发 RAG / 调用工具 / 请求人工 / 标注风险
```

## 六、关键洞察（Key Takeaways）

1. **没有银弹**：单一方法无法完美捕捉不确定性，最佳实践是组合多种信号
2. **校准是持续过程**：不是一次性设置，需要持续监控和调整
3. **不确定性感知是 Agent 安全的基础**：在自主 Agent 系统中，"知道自己不知道什么"比"什么都知道"更重要
4. **工程化 > 学术化**：在 Agent 系统中，不需要完美的理论保证，需要的是**实用的启发式方法** + **可量化的安全边界**
5. **与工具链深度集成**：不确定性不应只在 prompt 层面，而应渗透到 Agent 的整个决策链路中
