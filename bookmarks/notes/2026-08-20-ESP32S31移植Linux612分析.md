## 内容整理

### 1. 项目定位

- **硬件**：ESP32-S31-WROOM-3 E1H16R16V（ESP32-S31 Core Board / Korvo）
- **内核**：Linux **6.12**（最后一个保留 RISC-V XIP 支持的主线内核）
- **启动方式**：OpenSBI（改造为 XIP，flash + internal SRAM 映射到同一地址空间）
- **根文件系统**：Buildroot
- **用途**：技术可行性证明，非生产

### 2. 移植进度矩阵（原文）

| 层级 | 状态 |
|------|------|
| Buildroot rootfs | 🟢 Stable |
| Reboot / poweroff | 🟢 Stable |
| UART0 console | 🟢 Stable |
| Wireless (ESP-Hosted) | 🟡 Experimental |
| Dual hart SMP | ⚫ Not Planned |
| 大部分外围驱动（GDMA/Cache/TRNG/eFuse/Watchdog/PWM/UART1/2/GMAC/SDMMC/GPO/pinctrl） | 🟡 Experimental |
| Timers / Clock tree / Security / USB | 🟠 WIP |
| I2C / I2S / SPI / RMT / LP subsystem | 🔴 Not Implemented |

### 3. 关键硬件特性（与标准 RISC-V 的差异）

| 特性 | 标准 RISC-V | ESP32-S31 实际情况 |
|------|-------------|---------------------|
| 中断架构 | PLIC | **CLIC + CLINT + SCLIC**（定制） |
| mtvec.MODE | 可配置 | 被硬连线为 0x3（CLIC 模式） |
| S 模式 | 标准 | **非标准**，ESP-IDF 完全不用 S 模式 |
| mcliccfg.NMBITS | — | ESP-IDF 声称不可写 → **实测可写** |
| XIP | 主线已移除 | 保留（OpenSBI 改造） |
| SMP | 标准 | 双核弱异构（SIMD 只在 hart1），实际不可用 |
| PMP/APM | 标准 | 🔴 未正确实现 |

### 4. 为什么不做 SMP（作者的 5 条理由）

| 理由 | 关键信息 |
|------|----------|
| 射频 blob 闭源 | 必须跑 ESP-IDF FreeRTOS，无法反编译 |
| 双核异构 | SIMD 只在 hart1，调度复杂 |
| PSRAM 慢 + 32KB D-cache 共享 | 两核会互相踩 |
| Cache / IPC / 中断路由复杂 | 移植工程量大 |
| 需要 RTOS 处理其他任务 | 作者主动保留 FreeRTOS |

### 5. Agent-assisted 移植的诚实表述

> "Yes, it is heavily agent-assisted. It do work on real S31 dev boards... I understand the esp32 microcontroller architecture to some extent, but I barely know how to port Linux to other RISC-V platforms."

**关键洞察**：AI agent 不会自己发现 S31 的硬件特性（如 `mcliccfg` 的不可写位实际可写），人类的价值在于**指导 agent 往正确的方向猜硬件**。

## 可学到的点

1. **XIP 是嵌入式 Linux 移植的第一硬约束**：当 PSRAM 有限时，代码必须从 flash XIP 执行；而主线 Linux 6.13+ 已移除 RISC-V XIP——选内核版本就是选移植策略。
2. **CLIC 而非 PLIC 是 ESP32 系列的关键分水岭**：S3/S31 都用定制中断架构，移植 Linux 必须改 OpenSBI + 内核 CLIC 驱动，这是所有 ESP32 Linux 移植都要面对的第一关。
3. **"S 模式非标准"是隐藏的成本**：ESP32 的 S 模式在 ESP-IDF 完全不用，TRM 也不写，移植者只能靠 P4 TRM 猜测 + CSR 探针——这是"agent-assisted 移植"最需要人类介入的环节。
4. **双核异构不等于可 SMP**：hart1 有 SIMD 的事实让标准 SMP 调度不可直接套用；这提示我们任何 RISC-V 移植都要先确认核的对称性。
5. **agent 是加速器不是替代品**：作者明确"AI 不会自己发现硬件特性"——这给 Hermes 这类 Agent 生态的用法提供了现实案例：Agent 的价值在**执行具体移植任务**，但**架构判断必须靠人**。

## 归纳总结

GrieferPig 的工作是**技术可行性证明**，不是"ESP32 就该跑 Linux"。从工程角度拆解：

**关键结论**：
- **可以跑**：Linux 6.12 已在 ESP32-S31 上跑通，UART0/rootfs/重启稳定
- **不建议生产**：多数驱动 experimental/wip，作者明示 experimental
- **移植成本高**：CLIC/SCLIC/非标准 S 模式/XIP/双核异构，每一层都需要定制
- **Linux/FreeRTOS 共存是正确姿势**：射频 blob 必须跑 ESP-IDF，Linux 跑在另一个核上

**与本团队项目的关联**：我们用的是 ESP32-S3 + FreeRTOS，没有 MMU 也没有 XIP——**跑 Linux 这条路对我们当前的硬件方案不成立**（可行性评分 0/100）。如果要升级，ESP32-S31 是唯一现实选项（评分 40/100，"可行但需谨慎"）。

## 趋势判断

| 判断 | 依据 | 置信度 |
|------|------|--------|
| ESP32 家族跑 Linux 会从"炫技"走向"小众生产" | 作者已出二进制 release + Buildroot rootfs stable，工程路径在收敛 | 中 |
| RISC-V XIP 的移除会让未来 Linux 移植更难 | 主线已移除，未来只能锁定老内核或自研 XIP | 高 |
| Agent-assisted 嵌入式移植会成为主流路径 | 作者诚实表述，符合 Hermes Agent 生态定位 | 高 |
| "Linux 上层 + FreeRTOS 下层"双系统共存是 ESP32 的长期方向 | 射频 blob 无法绕开 ESP-IDF，硬件决定架构 | 高 |
| 单 SoC 跑 Linux 的成本增量（S31 vs S3）难以抵消 FreeRTOS 方案 | 对我们当前项目，S31+Linux 的 ROI 为负 | 中高 |
