## 核心概念提炼

### 1. Cone Graph（锥形图谱）— 三纵一横

```
Episode（情景）     ← 完整语义焦点，最粗粒度
  └─ Facet（切面）    ← 同一情景的若干截面
      └─ FacetPoint（切面点）← 原子事实/三元组，最细粒度

Entity（实体）────── 横穿所有层级，人/项目/地点/产品
```

**与 Hermes 的映射**：
- Episode ≈ session（一次完整对话/任务）
- Facet ≈ skill（一种工作模式的截面）
- FacetPoint ≈ memory 条目（一条事实）
- Entity ≈ memory 中的关键实体（用户、项目、工具）

### 2. 搜索 ≠ 联想 — 核心论点

| 维度 | 搜索（现有 RAG） | 联想（M-Flow 主张） |
|------|-----------------|-------------------|
| 问题 | 「哪段跟我最像？」 | 「该有哪些上下文被激活？」 |
| 方式 | 向量相似度匹配 | 沿关系图谱遍历扩展 |
| 输出 | 最相似的片段 | 该被想起的情景 |
| 深度 | 表面匹配 | 跨事件关联推理 |

**这个区分非常有价值** — 直指当前 RAG 的本质局限。

## 借鉴点（可执行）

### 🔴 P0：对我们记忆系统的启示

1. **从平铺 memory 到分层 memory**
   - 当前 Hermes memory 是扁平 key-value 列表，缺少层级
   - 可以借鉴：按 session → topic → fact 三级组织 memory
   - 实现路径：在 memory 条目中加 `level` 和 `parent` 字段

2. **联想式检索 > 向量相似度检索**
   - 当前 RAG 是纯向量搜索，无法做关联推理
   - 可以借鉴：memory 条目之间加 `related_to` 关系
   - 实现路径：在写入 memory 时自动提取实体关联，存储为边

3. **Entity 横切面**
   - 每个实体（用户、项目、工具）应有跨 session 的时间线视图
   - 当前 memory 按主题分，缺少按实体的纵向切片

### 🟡 P1：技术方向

4. **Cone Graph 模式可用于 notes 系统**
   - 笔记 = Episode，标签/分类 = Facet，具体知识点 = FacetPoint
   - wikilink = Entity 横切
   - 验证：当前笔记系统已有雏形，但缺少 Facet 层

5. **联想触发机制**
   - 可以在 session_search 中加入「联想模式」：输入一个线索 → 激活相关 session → 沿实体扩展
   - 这是比纯关键词搜索更高级的回忆模式

## 启发（超越原文）

1. **记忆的本质不是存储，是连接** — 这个观点比 M-Flow 本身更重要。Hermes 的自进化体系（evolver + experience-bank + skills）本质也是在做连接，但缺少显式的图谱结构。

2. **Benchmark 第一 ≠ 真正有用** — 文章虽然强调 benchmark，但真正有价值的是「联想 vs 搜索」的范式区分。Agent 的记忆应该在任务执行中自然发挥作用，而不是在静态评测集上刷分。

3. **19岁创业者做 Agent Memory** — 说明这个赛道的门槛在概念创新而不在工程规模。一个好的图谱设计 + 正确的检索策略，可能比堆参数更有效。

4. **与 Claude Code 的 Auto Memory 对比** — Claude Code 的四层记忆（CLAUDE.md → Auto Memory → Session → Auto Dream）本质上也是在做分层，但它是静态分层（文件层级），而不是语义分层（知识图谱）。M-Flow 的 Cone Graph 是语义分层的尝试。
