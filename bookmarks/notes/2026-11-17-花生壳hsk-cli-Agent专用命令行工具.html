内容整理：这个工具是干什么的

一句话结论

花生壳把自家内网穿透 + 文件发布能力打包成 npm CLI（npm install -g @aweray/hsk-cli），目标用户不是人而是 AI agent——agent 读官方文档即可自主完成安装、画像建立、发布、穿透全流程，全程无需人操作。

六大功能

功能 说明 关键命令
文件托管 本地文件/静态目录（HTML/PDF/构建产物）发布为公网可访问链接 一键部署链
AGENT 网盘 文件/目录发布为可分享资源，其他 agent 用命令取回——agent 间文件传输协议 drive put/get/ls
内网穿透 本地 http/WebSocket/SSR 服务暴露到公网；文档明示「动态网站优先静态托管+Supabase，穿透仅兜底」 engine ensure + engine mapping create
一键部署 构建前端项目并自动上传发布 向导推荐
动态网站 静态托管 + Supabase（数据库/登录/CRUD，npm-only） supabase capabilities
长期运行 本机引擎安装、进程保活、长期映射管理 engine install/status/logs/uninstall

执行协议核心（agent 视角的操作流）

  1. 前置：Node.js ≥16（推荐 18+）→ npm install -g @aweray/hsk-cli → hsk-cli doctor --format json 自检
  2. 红线一：任何业务命令前必须先跑 hsk-cli context wizard --format json 建立「服务画像」——wizard 读环境返回 data.ask（缺什么信息）与 data.recommendations（下一步该执行什么命令）
  3. 红线二：所有命令一律 --format json，以 stdout 首行 JSON 为准（过程日志在 stderr，不算失败）
  4. 长期映射：engine ensure（幂等：未装则装/未跑则启/丢节点则重注册）→ mapping create -ip -port -protocol [-wait-ready 60] → ready=true 才算成功
  5. 业务命令返回 needs_input：按 needs[].resolution_order（① agent_context ② user_handoff ③ alternative）处置后重跑

Agent-first 设计细节（本文档最有价值的部分）

设计 做法 设计意图
结构化输出协议 全命令 --format json，stdout 首行 JSON 为准，日志隔离到 stderr agent 解析确定性，杜绝从人类日志里捞信息
向导画像 context wizard 收集运行环境画像，输出下一步推荐命令 agent 不需要预学命令，跟着 recommendations 走即可
AGENTS.md 约定 postinstall 自动生成 ~/.hsk/AGENTS.md（工具使用说明落在 agent 惯例读取的位置） 融入 Agent 工具生态标准（同 Claude Code/AGENTS.md 约定）
结构化错误 参数错误返回 MAPPING_INVALID_FIELD，含 field/retryable/fix_hint/fix_command/next_actions 错误自带修复路径，agent 只跟一次不死循环
创建即自证 映射创建轮询到 active 并做端到端探测；404/408/429 需连续稳定 ≥3s 才判可达；见 X-Hsk-Edge-Error 头即判「未达源站」永不判 ready 防 agent 把「映射已建但数据面未通」误报成功
跨 agent 移交文案 drive put 输出官方生成的 handoff_notice，文档明示「不必自己改写，不同 agent 输出才会一致」 人→AI→AI→人 的文件传递协议标准化
更新事件 stderr 出现 [AI_EVENT] update_available → 执行其中 upgrade_command，禁自行 npm update -g 升级路径收口，防 agent 乱升级
免费授权无感领取 无空闲授权时自动领取免费授权并在输出中披露 降低 agent 使用门槛，免人工注册

异常兜底要点

  • 安装报 EEXIST/PATH 找不到 → hsk-cli doctor --fix
  • 能出版本号但不能发布/报 BINARY_NOT_FOUND → hsk-cli download，勿反复重装
  • Windows 装引擎必须管理员终端跑 CLI 命令，禁直接运行 OrayHskNGInstaller.exe（token 注入问题会注册失败）
  • -protocol 默认 https，由 agent 按用户意图显式传，CLI 不做协议探测

查询拓展

  • 花生壳免费授权的带宽/流量额度上限未在本文档披露——实际采用前需实测或查官网资费页
  • @aweray/hsk-cli 的 npm 下载量/版本迭代频率（npmjs.com 可查）——判断该 agent 化转型的实际市场接受度

  • 贝锐家族的类似动作：向日葵（远程控制）是否有对应 agent CLI——判断这是单品尝试还是公司级战略

归纳总结

  1. 本质：花生壳把「内网穿透+文件发布」从 GUI 产品重构为 agent 可自主操作的协议化 CLI，是人类工具 Agent-first 化的又一家传统厂商实证。
  2. 设计范式可迁移：其三层协议设计——①全 JSON 输出+stdout/stderr 隔离 ②向导画像+推荐命令（agent 免学命令）③结构化错误+fix_command（错误自带出路）——是任何「给 agent 用的 CLI」的通用骨架，比 MCP 的通用性轻、比人类 CLI 的确定性高。
  3. 验证哲学突出：「创建即自证」把 ready 判定口径细化到状态码粒度（404 需稳定 3s、边缘错误头永不判 ready），本质是把 agent 常见的「假成功」问题在协议层解决——这一条对自有工具设计最有借鉴价值。
  4. 商业化信号：免费授权自动领取 + agent 无感使用 = 把 agent 变成获客渠道，厂商赌的是 agent 推荐工具给用户的场景增长。
  5. 定位边界：文档自己承认穿透是「兜底」而非主推（优先静态托管+Supabase）——厂商清楚长期隧道是重资源业务，agent 场景主战场在文件分发。

趋势判断

  • 工具 Agent-first 化正在从 AI 原生厂商扩散到传统厂商：2025-2026 年先是 AI 原生工具（lark-cli、gh 等补 agent 友好输出），现在内网穿透这类传统基础设施厂商开始专门为 agent 重写协议层。「面向 agent 的接口设计」正从加分项变成基础设施标配。
  • AGENTS.md 正在成为工具自描述的事实标准：postinstall 落 ~/.hsk/AGENTS.md 与 Claude Code/各家 agent 的 AGENTS.md 读取约定对齐——工具不写 AGENTS.md 会逐渐等于「对 agent 不可见」。
  • agent 间点对点资源协议是空白带：drive put/get + handoff_notice 实质是「agent 给 agent 发文件」的私有协议尝试；该层目前无行业标准，先占位者（MCP、各厂商 CLI）各建孤岛，预计 1-2 年内出现整合压力。
  • 国内访问质量是差异化变量：Cloudflare Tunnel 国内访问慢是既有痛点，花生壳国内节点若免费档可用，对国内用户的 agent 分发场景有真实替代价值。

指南分析

文档本身是一份高质量的 agent-facing 文档范本，值得复用的写法：

  1. 版本门禁前置：开篇即给 capabilities --format json 的 features 白名单判据（过旧先升级再继续），杜绝 agent 拿旧版跑新协议。
  2. 红线显式化：两条红线（先 wizard 后业务、stdout 首行为准）放在所有细节之前——agent 扫读时最先命中最重要的约束。
  3. 判定口径给到状态码粒度：ready 判定逐状态码写明（2xx/3xx 立即、404/408/429 需稳定 3s、5xx 重试、超时勿重建），消除 agent 自由发挥空间。
  4. 「勿做」清单：禁直接跑安装包、禁自行 npm update、禁把 stderr 日志当失败——负面清单比正面说明更防错。
  5. 可执行性：全文命令均可直接复制执行，参数错误有 fix_command 闭环——「文档即协议」而非「文档即说明书」。
