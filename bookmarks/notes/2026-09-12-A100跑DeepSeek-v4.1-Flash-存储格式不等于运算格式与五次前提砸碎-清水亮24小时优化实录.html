零、结论先行

这是一篇"把 Claude Code 的五个先入观逐个砸碎"的优化实录——A100（无 FP4/FP8 Tensor Core 的 Ampere 老卡）跑 DeepSeek v4.1 Flash，从 33 tok/s 一路拉到 528 tok/s（64 并行 674），核心武器不是高深数学，是"测量→找慢点→砸前提"的计算机科学基本功。 对我们最深的三个增量：①"存储格式"和"运算格式"不必一致——FP4 存储无损转 INT8 喂老 Tensor Core，FP8 纯当存储格式省带宽，这与《八种精度》"量化是存储优化不是运算优化"的结论完全互证；②"每 token 2000 次 kernel 启动"——细粒度固定开销吃掉一半时间，与 TTFT 笔记的"decode 性能不由 FLOPS 决定"互证；③"AI 的先入观比人更强"——Claude Code 三次说"极限了/不支持"被作者三次推翻，这是对 agentic coding 最狠的实战批评。

二、五次"前提砸碎"（文章方法论核心）

砸碎 ①：「A100 不支持 FP4」

"「不支持 FP4」并不是说「4bit 的数据在 A100 上算不了」，准确地说，是「没有像 Blackwell 那样把 FP4 连同 block scale 直接装进 Tensor Core 的指令」。"

解法：E2M1（2bit 指数+1bit 尾数）×2 后是 0、±1、±2、±3、±4、±6、±8、±12 小整数——FP4 可无损转 INT8，喂 A100 的 INT8 Tensor Core。连 LUT 都不需要。

核心认识：存储格式 ≠ 运算格式。

砸碎 ②：「GPU 算总比 CPU 快」

抓 profile 发现真瓶颈：单卡配置下 MoE expert 在主机内存，每 token 经 PCIe 传 4.5GB：

方案 每层耗时 说明
PCIe DMA 送到 A100 179 ms 4.5GB ÷ 25GB/s（Gen4 x16 实效）
CPU BF16 计算 62 ms Xeon Silver 双路 1.7TB
CPU INT8 VNNI 51 ms 比送 GPU 快 3 倍+

"为了在 GPU 上算而把数据送过去，还不如全部用 CPU 算快 3 倍以上。异构计算里这种事很常见。只盯着理论算力的人绝对发现不了。"

与 GPU 互联经济学笔记互证：带宽 ≠ 容量——1.7TB 内存装得下 expert 不等于传得动 expert。

砸碎 ③：「运算量是主要瓶颈」

CPU 侧 51ms 还不够——DRAM 理论 512GB/s 只跑出 89GB/s。不是带宽限制，是指令数限制：FP4 unpack/shuffle/scale/地址计算，每层敲掉几千万条指令。

解法：改 weight 排布——按 CPU 吃起来最顺的顺序在加载时重排（nibble 排列让多个 row 共享 activation 载入、共享 scale 计算）。

"和 GPU 一样，CPU 上同样是「少做多余的工作」比「减少运算量」更有效。"

对 Claude Code 的批评：以"怎么存进模型文件"为基准设计数据结构是三流程序员思路——推理专用场景应在加载时全部重排。

砸碎 ④：「GPU 数量越多越快」

8 卡反而比 4 卡慢——decode 是小 GEMV 连续，分到 8 张卡后同步/kernel 启动/小矩阵/GPU 间通信的比重上升。

解法：4 卡×2 副本 > 8 卡×1 副本（系统整体吞吐超 1300 tok/s）。且注意 NVLink 拓扑（GPU0-1/2-3/4-5/6-7 成对，0-3 与 4-7 不同 NUMA node）。

"GPU 不是堆数量就会变快，同理也不是越新就越好。"

砸碎 ⑤：「批处理=同时处理几个人」

Task-aware batching：把 32 个并行上下文按语义分类打包（写代码归写代码/翻译归翻译），同类 prompt 路由选出的 expert 相似→多个序列共享 expert weight→单层 distinct expert 数从 216 降到 156。

"scheduler 不只是队列管理。把 prompt 按语义分类来组 batch，这件事本身就是 GPU 优化。"

与 PagedAttention 笔记的 Prefix Caching 同构：都是"相似输入共享已加载的重量级资源"。

三、三项硬核技术

3.1 FP8 的寄存器直连

A100 无 FP8 Tensor Core。粗糙做法（FP8→BF16→写回 VRAM→GEMM）蠢在把展开后的大体积数据写回全局内存（延迟 284-426ns，比寄存器慢 400 倍）。

正确做法：FP8 纯当存储格式（省带宽快速搬运），进寄存器后位操作转 BF16 fragment 直接 mma：

FP8 → 寄存器 → BF16 fragment → mma（不落 VRAM）
dense 部分：9.2ms → 5ms 台

3.2 MTP（多 Token 预测）

自回归 decode "1 token→40 层→下一 token"串行躲不掉。MTP 一次处理多个候选 token，且 batch=1 的 GEMV 变多 row 接近 GEMM——GPU 利用率上来。实测 no MTP→K=3→K=5，速度涨 2-3 倍。

3.3 CUDA 内存层级数字表

层级 延迟 说明
寄存器 0.71 ns 每 SM 仅 256KB
共享内存 — 依次变慢
L2 — 依次变慢
VRAM 全局内存 284-426 ns 比寄存器慢 400 倍+

读 100 万个信息：BF16 981ns vs FP4 245ns。

四、「每 token 2000 次 kernel 启动」（对 agentic coding 最狠批评）

生成 1 token 花了 28.4ms，拆解：

项 耗时
expert GEMV 7.0 ms
dense GEMM 9.2 ms
"其他" ~12 ms

"其他"= RMSNorm/RoPE/量化/反量化/伪量化等元素级运算，40 层每层单独 kernel——生成 1 个 token 启动近 2000 次 CUDA kernel，光启动手续就超 10ms。

"不是 GPU 慢，是把时间花在了「拜托 GPU 干活」的手续上。"

"你能不能以微秒为单位想象 CPU 和 GPU 在干什么？听到「毫秒」就停止思考，就永远到不了那里。"

"全交给 agentic coding 的极限"——Claude Code 早早早早说"这就是极限了"，"一个刚出生没几天的毛头小子，少给我摆出一副懂了的口气"（作者 50 岁中二全开）。

五、宏观论：本地 AI 时代的黎明

5.1 经济账

项 数字
継之助（A100×8+1.7TB） 4000 万日元
8 卡 H100 服务器 ~1 亿日元
Claude Code 100 人年费 3600 万日元
结论 一台机器服务 100 人组织，比 API 订阅便宜

5.2 历史类比

"革命之所以发生，不是因为 PC 比大型机快，而是因为「性能足够的计算机，可以自己拥有」——能拥有就能随心所欲，就会诞生新的软件、新的用法，和中央巨型机里不可能出现的新文化。"

云 AI（造前沿模型+瞬间用最新模型）与本地 AI（拥有自己的 AI）将并存——组织级本地 AI 比想象中快得多地进入实用区。

5.3 与我们的三机架构互证

我们的 jc-server（Jetson）+ NAS + 远端 GPU 组合正是"组织一台 AI 超算"的微型版：凌晨 3 点一个人独占全量资源、无 API key、无月账单、可改模型改 kernel——这是云没有的奢侈。

七、批判性审视

  1. 对照系不严谨："継之助比官方 API 快"作者自己承认是"高速公路 vs 自家停车场出库速度"——官方处理全球海量请求，本地只服务自己——吞吐数字不可直接对标（吸收分析零破坏原则：吸收原则不吸收数字）
  2. 4000 万日元的幸存者偏差：这套优化只有"已有 A100×8+1.7TB 邪道内存"的人可复现——普通人从零买 B200 可能更划算；且 1.7TB 系统内存 Intel 官方不支持开机，是作者反复试错的邪道配置
  3. Claude Code 批评有失公允：粗放指令出粗糙代码是使用者责任——作者自己也说"能不能用好 AI 的分水岭就在这种地方"；且 Claude Code 在"砸前提"阶段提供了 LUT/INT8 转换的正确方案——工具的极限是使用者的极限
  4. MTP 的质量代价未讨论：多 token 预测的接受率/输出质量变化未报告——速度 2-3 倍但准确率掉多少？
