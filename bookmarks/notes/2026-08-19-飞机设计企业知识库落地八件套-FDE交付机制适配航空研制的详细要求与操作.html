一、内容整理

0. 八件套总览（原文 → 航空域翻译）

# FDE 原文 飞机设计企业落地翻译
1 场景边界和成功指标 圈定型号/专业/阶段：哪些科室的哪类问题归知识库管，回答准到什么程度算成功
2 数据清单、负责人、有效期与分级分类 技术文件资产台账：规范/手册/计算报告/试验数据的责任人、现行有效版本、密级与受控状态
3 用户、角色和文档权限矩阵 涉密 + 受控双维度权限：按科室×型号×密级×文件受控级的四维矩阵
4 真实问题组成的评测集 各专业真实提问集：强度/气动/系统科室日常问题 + 标准答案 + 及格线
5 解析、检索、模型和部署方案 异构工程文档解析管线：PDF 报告/CAD 说明/规范表格/扫描件的解析-切分-索引-检索-生成技术栈
6 安全检查、审计和异常处理流程 涉密审计 + 幻觉拦截：输出安全门、访问审计、错误答案的发现-处置-归零
7 内容更新、删除、回滚和索引重建机制 技术状态变更驱动的内容生命周期：规范改版/型号构型冻结/文件作废的同步机制
8 上线后的反馈入口和运营负责人 科室知识专员制：每专业一名对口人 + 反馈-修复 SLA

1. 交付物一：场景边界和成功指标

为什么要先圈边界：飞机设计知识域近乎无穷（气动/结构/系统/航电/制造/试验/试飞/适航...），"什么都能答"的知识库必然什么都不精；航空用户对错误答案的容忍度极低（错误结论可能流入设计文件）。

要求（R1）

项 要求
边界声明文档 一页纸写清：服务的型号（如某运输机）/ 专业（先选 1-2 个，如结构强度）/ 研制阶段（初步设计/详细设计）；明确列出不服务的场景（如：不替代适航审定证据链、不直接输出可签署的强度结论、不处理未受控的原始试验数据）
场景清单 每个场景写成"用户是谁-提什么问题-期望得到什么"三行式，例：强度工程师 — "CCAR-25.303 安全系数在复合材料主结构如何取" — 给出条款原文出处+型号惯例做法+限制条件
成功指标 三层：①检索层：Top-5 命中率 ≥ 85%（对评测集）②回答层：专业员认同率 ≥ 80%（盲评）③业务层：周活提问数 / 目标科室工程师数 ≥ 50%（业务愿意使用才是真指标）
红线指标 幻觉率（编造条款号/材料数据/规范数值）零容忍——一次重大幻觉直接触发第 6 项异常流程

操作（O1）
1. 与首批试点科室（建议：结构强度研究室）开 2 小时边界会，产出三行式场景清单 15-30 条
2. 把"不做什么"写成醒目的系统提示词与界面声明（每次回答附带"本回答不构成设计依据，签署文件以受控原文为准"）
3. 指标基线测量：上线前用评测集跑一遍记录初始值，此后每季度复测归档

2. 交付物二：数据清单、负责人、有效期与分级分类

航空数据的特殊性：技术状态受控（现行有效/作废/待生效）、密级分级（公开/内部/秘密/机密）、版本随型号构型冻结而锁定。

要求（R2）

项 要求
资产台账字段 每份数据：ID / 名称 / 类别（规范-手册-计算报告-试验报告-设计准则-经验教训）/ 密级 / 受控状态（现行/作废/待生效）/ 现行版本号 / 生效日期 / 复审周期 / 责任人（科室+姓名）/ 数字化状态（原生PDF/扫描/仅纸质）
类别分级 一级：适航规范类（CCAR-25/FAR-25/咨询通告）——外部权威，跟官方改版走；二级：企业标准类（设计准则/手册/作业指导书）——内部受控，复审周期 1-2 年；三级：型号工程类（计算报告/试验报告/故障归零报告）——随型号技术状态冻结；四级：经验教训类（设计备忘/复查意见）——有效期由责任人年度确认
有效期规则 规范类跟随局方改版自动触发复审；企业标准按文档自身复审周期；作废不删除——标记作废并保留（历史型号查询仍需），检索时默认只召回现行有效，用户显式选择才查历史版
责任人 每份数据必须落到人（不是落到科室）；责任人调岗时台账强制交接，运营负责人每月核查空责任人行
密级 数据密级决定其能否进入检索库（见交付物三）；台账本身按最高密级文档定级保管

操作（O2）
1. 先做数据摸底：从档案/资料室导出试点专业文档目录，按台账字段补全（预计 2-4 周兼职工作量，可从 200-500 份种子文档起步）
2. 用多维表格（飞书 Base / 数据库）建台账，"受控状态/复审到期日"设自动提醒视图
3. 每月跑一次台账体检脚本：空责任人 / 复审过期 / 作废未标记 三类异常清单发运营负责人
4. 季度与档案系统对账一次，防止台账与实物漂移

3. 交付物三：用户、角色和文档权限矩阵

航空的特殊性：涉密管理 + 型号隔离（不同型号队伍互不可见）+ 受控文件（非授权不可下载全文）。

要求（R3）

角色 说明 典型权限
普通工程师 本科室+本型号 检索摘要/回答可见；密级匹配文档全文可读，高一档只见元数据
专业负责人 本专业跨科室 本专业全部型号只读 + 数据提名权
知识专员（运营） 每专业一名对口 本专业数据增删改、评测集维护、反馈一线处置
系统管理员 IT/信息安全部门 账号/权限配置/审计日志（不见内容明文，见操作行为）
审计员 质量部门 全量只读审计视图

权限矩阵维度：用户科室 × 参与型号 × 个人涉密等级 × 文档密级 × 文档受控级 五维取交集——任一维不满足即降级为"仅元数据"。下载与截图留痕：受控文档全文查看逐次记录（谁-何时-哪份-哪个问题触发）。

操作（O3）
1. 用"白名单准入"而非"黑名单排除"：默认无权限，按科室-型号项目组批量授予
2. 矩阵以配置文件/表格维护，变更留痕（谁批准的扩权）
3. 上线前做一次越权演练：用测试账号尝试跨型号/跨密级检索，确认拦截生效
4. 每季度权限复核：离职/调岗账号 24 小时内回收（对接 HR 流程）

4. 交付物四：真实问题组成的评测集

为什么要真实问题：合成问题测不出工程口语（"这个框的 MS 咋算负了"）和规范引用习惯；评测集是知识库质量的唯一可信度量衡。

要求（R4）

项 要求
规模 起步 ≥ 100 条，年度增长到 500+；每季度新增 ≥ 20 条（从真实提问日志里挑）
构成 三类比例约 5:3:2——事实型（"25.303 安全系数是多少"→有唯一标准答案）/ 检索型（"我们型号上类似接头怎么设计的"→需要多文档综合）/ 判断型（"这个做法行不行"→需要边界+出处+惯例，允许答案标注不确定性）
每条字段 问题原文 / 提问角色 / 标准答案或参考答案 / 参考文档ID / 难度 / 最近校验日期 / 校验人
及格线 分场景设定：事实型准确率 ≥ 95%（条款号/数值错一条都算错）；检索型 Top-5 命中 ≥ 85%；判断型认同率 ≥ 75%（专业员盲评打分）
防污染 评测集禁止进入训练/微调数据；对模型保密（防"背题"）；版本化管理，每次改动留 diff
陷阱题 刻意收录 10% 的边界外问题（如"帮我算一下这个零件的强度"）——正确行为是拒答并引导到正确工具（如 struct-gen 类验算工具），答了反而扣分

操作（O4）
1. 冷启动：从科室技术讨论群/邮件往复里捞 30-50 个真实问题，知识专员补标准答案
2. 盲评流程：把系统答案与（如可得的）资深工程师手写答案去标识混合，交 3 名专业员评分
3. 每次检索策略/模型/提示词变更，先跑全量评测集对比，分数不降才许上线（回归测试纪律）
4. 线上高频但答不好的问题 → 自动进入"待改进池" → 转化为新评测条目

5. 交付物五：解析、检索、模型和部署方案

航空文档的解析难度：扫描件多、公式表格多、多栏排版、图纸截图嵌入、双面中英对照——通用解析在这里翻车最多。

要求（R5）

环节 要求
解析 分类型管线：原生 PDF 走文本抽取；扫描件走 OCR（人工抽检率 ≥ 5%）；表格（材料性能表/紧固件目录）结构化抽取入库而非当文本切；公式保留 LaTeX/图片引用；每份文档解析后生成质量报告（页数/抽取字符数/乱码率），乱码率 > 3% 转人工
切分 规范类按条款切（保持条款号完整性——检索的最小语义单位是条款不是段落）；报告类按章节+页眉型号信息注入；每块元数据：文档ID/版本/密级/条款号/页码（回答必须能引用到条款级）
检索 混合检索（关键词 BM25 + 向量），规范条款号做精确匹配通道（用户搜 "25.303" 必须直命中）；密级过滤在检索层强制执行（不是生成层事后过滤）
生成模型 私有化部署为默认（涉密场景必须）；强制引用输出：每句关键断言带 [文档ID:条款] 角标；无检索命中时明确说"知识库未覆盖"而非硬答
部署 涉密网内网部署；推理与向量库同区；与互联网物理隔离的部署图作为交付物之一归档；非密场景可上混合云但数据不出域

操作（O5）
1. 解析管线按文档类别分道，先拿 20 份"最难样本"（最老扫描件+最复杂表格）做冒烟测试再定方案
2. 建立解析人工抽检岗（知识专员兼任，每周抽 5-10 份）
3. 检索质量月报：评测集命中率趋势 + 线上无命中问题清单（这些是要补的数据）
4. 模型升级走"影子运行"：新旧版本并行两周，对比评测分数与线上反馈再切换

6. 交付物六：安全检查、审计和异常处理流程

航空特有异常：幻觉条款号/过时规范值（引用了作废版）/越权输出（把别的型号数据答出来了）——三者都比普通行业严重。

要求（R6）

流程 要求
输出安全门 上线前强制检查清单：①条款号/数值与源文档比对（可机检的引用核对）②密级标记检查（回答密级不高于所引文档最低密级）③边界外问题拒答④免责声明附带
审计日志 三类日志不可篡改存储 ≥ 3 年：访问日志（谁查了什么）/输出日志（答了什么引了什么）/变更日志（数据/权限/提示词谁改的）
异常分级 P0 幻觉关键数值或条款（可能流入设计）→ 2 小时内定位、当天发布公告、评估线上影响面 / P1 引用作废版本文档 → 3 日内修复检索过滤 / P2 答非所问/体验问题 → 周度批量优化
归零机制 借鉴故障归零思路：每起 P0/P1 出归零报告（现象-根因-措施-举一反三），归零措施包括补评测题/补数据/改提示词，闭环才销项
应急 一键下线开关（单个数据源/单场景/全系统三级），运营负责人有权直接执行后补流程

操作（O6）
1. 引用核对脚本每次发版跑：抽样 100 条线上回答，逐条比对角标引用与原文一致性，输出幻觉率月报
2. 每月审计例会（质量+信息安全+运营）：过 P0/P1 清单、日志抽查 10 条、权限异常回顾
3. 作废文档召回过滤的专项测试：刻意用已作废版本的条款提问，验证系统会提示"该版已作废，现行版为 X"

7. 交付物七：内容更新、删除、回滚和索引重建机制

航空的更新触发源：规范改版（局方发文）→ 企业标准换版 → 型号构型冻结（一批文档锁定）→ 文件作废——全是外部受控事件驱动，不是用户随手改。

要求（R7）

机制 要求
更新 四类触发：①规范改版（台账监测→新版本入库→旧版标记作废→增量重索引该文档）②企业标准换版（责任人发起→新旧 diff 审核→生效日切换）③经验教训新增（知识专员随时）④错误修复（反馈流程）。所有更新走审批流（责任人发起→专业负责人批→生效），留版本链
删除 物理删除是最后手段：默认作废标记；确需删除（密级问题/错误数据）走双审批（责任部门+信息安全），删除前全文备份入隔离区，删除记录永久保留
回滚 数据/索引/提示词三类均可回滚到任意版本号；回滚演练纳入年度演练计划（模拟"错误版本被索引"场景，验证 30 分钟内恢复）
索引重建 增量为主（单文档级）；全量重建需窗口期（夜间/周末）+ 双索引切换（新索引建好后原子切换，不停服务）；重建后自动跑评测集确认无退化
技术状态联动 与构型管理流程挂钩：型号阶段转移（如 C 设计冻结）时批量锁定相关文档为"冻结基线"，只读

操作（O7）
1. 建立"变更订阅"：档案/标准化部门的新版发布通知自动转知识专员任务
2. 索引版本命名与数据版本对齐（data-vX → index-vX），出问题能对上"哪个索引版本吃了哪批数据"
3. 每季度执行一次回滚演练（降级演练），记录耗时与缺口
4. 变更月报：本月入库/作废/更新/删除清单 + 触发来源分布

8. 交付物八：上线后的反馈入口和运营负责人

核心论断回放：业务愿意使用、资料有人维护、错误能被发现并修复——这三件事全都长在运营上，不在代码里。

要求（R8）

项 要求
运营负责人 唯一具名的第一责任人（不是委员会）；职责：台账体检/评测回归/反馈处置 SLA/月报/向业务方汇报；授权：应急下线/数据冻结/发起归零
知识专员 每个接入专业 1 名（兼职 10-20%工时）；职责：本专业数据维护/评测答案校验/一线反馈初判；考核计入其科室绩效（否则必然荒废）
反馈入口 三合一：①每次回答旁"有用/没用+原因"一键反馈（默认入口，零成本）②"报告错误答案"工单（进 P0/P1 分级流程）③月度科室座谈会（定性收集"为什么不用"）
SLA 简单反馈 5 工作日闭环；错误答案工单 P0 当天响应；"待改进池"每月清点公示（让提反馈的人看见结果——反馈无回音是用户流失首因）
运营指标看板 周活用户/提问量/有用率/Top-5 命中率/幻觉率/反馈闭环率/数据新鲜度（过期未复审占比）——七指标月报制度化
退场条件 预先写明什么情况承认失败并下线（连续两季度周活 < 目标科室 10%）——避免僵尸系统消耗维护资源

操作（O8）
1. 上线仪式感：给试点科室做 30 分钟宣讲（能答什么/不能答什么/怎么反馈/谁是专员）
2. 反馈闭环公示：每月在科室群发"上月反馈处理清单"（X 条已修复/Y 条排期/Z 条不做及原因）
3. 运营负责人交接文档随时保持"新人 1 周可接手"状态（本八件套文档即交接文档）

三、归纳总结

维度 要点
一句话 八件套=知识库的"技术状态管理"：场景是图样、数据是零件、评测是试验、运营是售后服务——交付的是能继续运行的机制，不是能跑的系统
航空适配总纲 四个"航空特有"：技术状态受控（作废不删除）/ 涉密分级（权限五维矩阵）/ 幻觉零容忍（引用核对+归零机制）/ 外部事件驱动更新（规范改版/构型冻结联动）
成功的真标准 周活提问率 ≥ 50%、反馈闭环公示、数据过期占比下降——三个"业务侧"指标，检索指标只是及格线
关键角色 运营负责人（唯一具名）+ 每专业知识专员（兼职入绩效）——无人负责=必然荒废
反模式 上线即撤人/数据台账落到科室而非落到人/评测集混入训练数据/删数据不备份/反馈无回音
实施心法 首期宁小勿大（1 专业 200 文档 100 题），八件套全跑通再复制——机制验证优先于规模扩张

四、趋势判断

  1. FDE 模式正在从 ToC AI 转向传统工业的知识基础设施交付：八件套清单本质是把"交付软件"改写为"交付运营能力"——飞机设计企业这类重流程组织会是 FDE 式交付的最大买方（流程资产比代码资产更难自建）
  2. 评测集会成为企业 AI 资产负债表上的科目：真实问题+标准答案+及格线的资产化程度，决定知识库可验收、可交接、可回归——没有评测集的项目连"变好了还是变坏了"都无法证明
  3. 适航监管将逐步要求 AI 辅助设计的可追溯性：输出日志/引用核对/归零报告这套流程与审定证据链（design data traceability）同构——今天为知识库建的审计机制就是明天适航符合性声明的一部分
  4. 知识专员制是传统工业 AI 落地的组织创新：IT 部门推不动的数据治理，只有嵌入科室绩效的兼职角色能持续——"数据责任人落到人"与适航体系"签字落到人"是同一组织基因
  5. "作废不删除+双索引切换"会成为受控文档 RAG 的标配：通用互联网 RAG 的"新鲜度优先"假设在受控工程文档域反转——历史版本查询是刚需，技术状态管理概念将反向输入 RAG 工程实践
  6. 退场条件的预先声明是机制成熟度标志：敢写"什么情况下线"的项目才敢于持续——僵尸系统消耗维护资源是知识库最大隐性成本

三条机制铁律（超出八件套原文的航空域补充）
- 幻觉零容忍靠机检不靠自觉：引用核对脚本每月抽样比对——人眼审不完的量，脚本 100 条/次
- 作废文档是历史资产不是垃圾：检索默认现行+显式切换历史——型号延寿/改进改型时历史版就是证据链
- 反馈闭环公示比反馈入口更重要：无回音的反馈入口是用户流失加速器——"处理清单月度公示"是运营的生命线
