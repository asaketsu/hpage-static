## 一句话总纲

> **Agent 记忆的本质不是存储过去，而是让过去继续影响下一步行动——"继续"两个字没有检索价值，但真有记忆的 Agent 应该知道继续哪个项目/哪个 bug/哪个已确认方向。Mastra Observational Memory 用五层结构（近期原文→Observations→Reflections→Extractors→Recall）把"聊天记录仓库"升级为"可恢复的工作现场"：平时用压缩状态干活，需要证据时再回查原文。长上下文解决"装得下"，长期 Agent 需要"用得对"——上下文窗口不是硬盘。**

## 一、内容详细整理

### 1.1 核心痛点：AI 聊久了为什么越来越接不上

用 Codex/Cursor 做项目：刚开始很聪明（知道项目/技术栈/报错/已试方案），但聊着聊着——你明明说过 Supabase/Vercel/不大重构/.env.local 已查/方案已失败/下一步看线上环境变量，隔了一会儿说"继续"，它又开始问：继续哪个任务？再贴下报错？要不要先查本地环境变量？

**诊断**：很多 Agent 不是没有能力，而是**没有把前面的对话整理成"可继续行动的状态"**。

### 1.2 向量 RAG 与任务状态的分野（关键区分）

| 维度 | 向量检索（传统 memory） | 长期 Agent 需要 |
|------|------------------------|-----------------|
| 解决的问题 | 哪段历史和当前问题**最相似** | 任务现在**推进到哪一步** |
| "继续"两字 | 无检索价值（太短太泛） | 应知道继续哪个项目/bug/文件/已半排查的问题/已确认方向 |

**这才叫记忆：不是把聊天记录翻出来，而是把工作现场恢复回来。**

### 1.3 长上下文为什么不够

长上下文解决"装得下"，长期 Agent 需要"用得对"。**上下文窗口不是硬盘**——桌子堆满所有会议记录/聊天截图/报错日志/文档，东西都在，但你还是不知道下一步干嘛。

### 1.4 Mastra Observational Memory 五层结构

```
近期原文（Recent Raw）   保留最新细节
    ↓ 旧对话
观察日志（Observations） 记录旧对话里发生过的重要事件
    ↓ 积累太多
反思压缩（Reflections）  压缩成长期模式
    ↓ 稳定信息
结构化状态（Extractors） 抽取用户偏好/项目状态/当前任务
    ↓ 需要精确细节
原文回查（Recall）       回查原始消息
```

**设计哲学**：不让上下文无限变长，也不完全丢信息——平时用压缩状态工作，需要证据再回原文。**比单纯 RAG 更贴近长期 Agent 实际需求。**

### 1.5 三个应用场景的"有用记忆"对照

| 场景 | 聊天记录式（没用） | 任务状态式（有用） |
|------|-------------------|-------------------|
| Coding Agent | "你之前提过 Vercel" | Vercel 部署失败/可能与生产环境变量有关/本地已查/用户要最小修复/不想换认证方案/下一步看 Vercel dashboard |
| 研究 Agent | 存下读过哪些文章 | 研究问题是什么/已排除哪些方向/关键参考论文/用户关注商业还是技术/下一步看哪条线索 |
| 个人助手 | 记住"我喜欢简洁" | 直接给结论/不要空泛建议/先跑通再优化/正在推进什么/暂停什么/等什么 |

### 1.6 工作笔记类比（最好用的心智模型）

好的 Agent memory 像工作笔记，记录七件事：**目标/当前进度/已确认决策/已失败路径/当前 blocker/下一步动作/原始证据在哪**——不记录每一句废话。

## 二、设计五问（原文方法论提炼）

做 memory 前不要先问"接不接向量库/存多少轮/要不要长上下文"，先问：

1. 哪些历史**真的会影响下一步**？
2. 哪些信息**必须保留原文**？
3. 哪些信息可以**整理成事件**？
4. 哪些信息应该变成**结构化状态**？
5. 哪些内容只是**临时上下文**，用完可忘？

否则 memory 做成聊天记录仓库——看起来什么都存了，Agent 要干活时还是不知道从哪接。

## 三、长期 Agent 的分水岭

> 长期 Agent 的分水岭，不是工具调用多强，也不是上下文多长，而是**能不能持续保持任务状态、能不能接着干**。

长期任务共同需求：中断后恢复/记住决策/避免重复踩坑/知道走到哪。这是从"会聊天的 AI"走向"能长期做事的 AI"的关键。

## 四、查询拓展（与本机记忆体系对照）

### 4.1 本机已是五层结构的实践者

| Mastra 层 | 本机对应 | 状态 |
|-----------|---------|------|
| 近期原文 | 会话消息（session DB 完整保存） | ✅ |
| Observations | session_search FTS5 检索（事件层） | ✅ |
| Reflections | 记忆压缩（compaction summary） | ✅ |
| Extractors | MEMORY.md 铁律 + USER.md 偏好（结构化状态） | ✅ |
| Recall | session_search 滚动 + active_tasks.json 断点恢复 | ✅ |

**但有一个缺口**：本机"任务状态"层分散在 active_tasks.json（断点）+ PROGRESS.md（项目）+ watchlist（持仓）——**没有统一的"当前任务状态卡"**。用户说"继续"时，恢复路径是 session-boot 检查 → active_tasks 读取 → 询问用户——比 Mastra 的 Extractors 自动抽取多一步人工确认。

### 4.2 与"用户金句式定调"的印证

用户 USER.md 中"反思压缩→结构化状态"的偏好（如 08-20 音色锁定、08-21 笔记指令语义沉淀）正是 Extractors 层的人工实践——**本文提供了该实践的理论框架名**。

### 4.3 与 SAT/active_tasks 的差距

本机 active_tasks.json 有 in_progress/paused 状态但无"已确认决策/已失败路径/blocker/下一步"四字段——**补上这四个字段 = 任务状态卡的最小实现**。

## 五、归纳总结

### 5.1 五层结构速查

```
近期原文 → Observations → Reflections → Extractors → Recall
(细节)     (事件)         (模式)        (状态)       (证据回查)
```

### 5.2 记忆设计判断树

```
信息出现 → 会影响下一步吗？
  ├─ 否 → 临时上下文，用完即忘
  └─ 是 → 需要精确原文吗？
       ├─ 是（报错/代码/承诺）→ 近期原文保留 / Recall 回查
       └─ 否（可概括）→ 是稳定模式吗？
            ├─ 否（一次性事件）→ Observations
            ├─ 是（反复出现）→ Reflections
            └─ 是且结构化（偏好/状态）→ Extractors
```

## 六、趋势判断

### 趋势 1：任务状态卡（Task State Card）将成为 Agent 基础设施标配

> 依据：Harness 系列第 2 篇（同日笔记）证明长时运行的分水岭是会话持久化——但持久化的消息流只是原料，**任务状态卡才是"恢复工作现场"的接口**。Mastra Extractors/Claude Code 三层记忆（memory.md 指针）/本机 active_tasks 是同一需求的三种实现——预期将收敛为标准 schema（目标/进度/决策/失败路径/blocker/下一步/证据指针）。

### 趋势 2："聊天记录仓库"式 memory 产品将被状态式记忆淘汰

> 依据：长上下文成本持续下降但"装得下"≠"用得对"（本文桌子类比）+ 用户对"继续"失败的容忍度极低（高频痛点）——纯存储/RAG 式记忆的信息密度劣势在长任务中指数放大。与 08-20 记忆系列"投递优先/时长反转"研究互相印证。

## 八、拓展应用推荐

1. **active_tasks.json 升级任务状态卡**：增加"已确认决策/已失败路径/当前 blocker/下一步动作"四字段（最小改动最大收益）
2. **session-boot 补 Extractors 逻辑**：恢复上下文时自动从最近会话抽取任务状态而非只列 in_progress 列表
3. **watchlist 的状态化**：持仓记录已有 strategy 字段（三档预案）——符合状态卡思想，可作模板推广到其他长期任务
4. **"继续"指令的路由**：识别到"继续"类指令时优先读任务状态卡而非全文检索——省 token 且更准
