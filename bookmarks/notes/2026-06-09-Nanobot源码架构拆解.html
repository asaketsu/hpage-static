Nanobot 源码架构拆解：3935 行代码的极简 Agent 框架

来源：腾讯云开发者 · 俞孟凡 · 原文链接
整理日期：2026-06-09

项目概况

香港大学数据科学实验室（HKUDS）开源的 nanobot，核心代码仅 3,935 行（对比 LangChain 430,000+ 行），30 天内 28,500+ GitHub Stars。

设计哲学：用最少的抽象做最诚实的 Agent 框架——代码量和功能声明完全匹配。

01 整体架构：控制面集中化

Chat Platforms (13 channels)
  ↓
MessageBus (asyncio.Queue)  ← inbound / outbound
  ↓
AgentLoop（核心控制面）
  ├── SessionManager  → 历史对话加载
  ├── ContextBuilder  → system prompt + messages 组装
  └── while loop: LLM → tool calls → execute → append → LLM...
  ↓
ToolRegistry / SubagentMgr / exec / MCP / cron

决定性特征：控制面完全集中在 AgentLoop。没有 Chain/Runnable/LCEL 编排层，没有 DAG，没有显式 PLAN 步骤。所有决策路径穿过同一个 while 循环。

可理解性最大化，但弹性空间随之缩小。

02 核心：ReAct 循环极简实现

整个 Agent 编排逻辑约 20 行：

async def _run_agent_loop(self, initial_messages, on_progress):
    messages = initial_messages
    while iteration < self.max_iterations:  # 默认 40 次
        response = await self.provider.chat(messages, tools, model)
        if response.has_tool_calls:
            for tool_call in response.tool_calls:
                result = await self.tools.execute(tool_call.name, tool_call.arguments)
                messages = append_tool_result(messages, tool_call.id, result)
        else:
            final_content = response.content
            break

关键工程细节

设计 作用 代价
错误响应不持久化到 session history 防止"400 中毒循环" —
工具结果截断为 500 字符存入 session 控制上下文增长 跨会话工具结果不可追溯
错误处理只追加一句引导提示 把恢复责任交给 LLM 弱模型可能无效循环

03 Tool 系统：最小 Python 接口

class Tool(ABC):
    name -> str           # 工具名
    description -> str    # 描述
    parameters -> dict    # JSON Schema
    execute(**kwargs) -> str  # 硬约束：必须返回 str

设计选择：execute 强制返回 str——接口统一，LLM 天然消费字符串；代价是丢失类型信息。

无装饰器、无配置文件、无元类。JSON Schema 需手写维护。

04 Skill 系统：Markdown 扩展 LLM 能力

nanobot 最独特的设计。 Skill 不是代码，而是 Markdown 文档，教 LLM 如何使用已有 CLI 工具。

Progressive Loading：文件系统做懒加载

  1. System prompt 只注入 XML 索引（name + description + location）
  2. LLM 需要某 skill 时，用 read_file 读取完整 SKILL.md
  3. 不用的 skill 零 token 开销
<skills>
  <skill available="true">
    <name>weather</name>
    <description>Get current weather...</description>
    <location>/path/to/skills/weather/SKILL.md</location>
  </skill>
</skills>

Skill vs Tool 分工

场景 Tool Skill
需要 Python 逻辑 ✓
包装已有 CLI 工具 ✓
需要直接调 API ✓
非工程师添加能力 ✓

局限

skill 数量极大时（数百个），XML 索引本身占满 context window。有规模天花板。

05 记忆系统："grep beats RAG"

两个 Markdown 文件，不用向量库：

文件 内容 加载方式
MEMORY.md 长期事实、用户偏好 每次注入 system prompt
HISTORY.md 对话摘要，追加写入 LLM 用 exec grep 按需搜索

当 unconsolidated_messages >= 100 时，异步触发 LLM 驱动的记忆整合。

适用范围：个人规模（数百条历史）成立。企业规模（数万条、多用户、跨语言）需向量库。

06 Subagent 系统：消息总线重注入

asyncio.create_task(self._run_subagent(task_id, task, label, origin))

能力约束：无 message 工具、无 spawn（防递归）、最多 15 次迭代、无 memory/history。

巧妙设计：Subagent 完成后，通过 MessageBus 重新注入 InboundMessage → 主 agent 像处理普通消息一样处理 → 无需轮询或回调。

局限：asyncio.Task 同进程，无法跨机器分布。

07 MCP 集成：零成本协议桥接

MCP 工具自动包装为原生 Tool 对象，命名空间隔离（mcp_{server}_{tool}）。支持 stdio 和 streamable-http 两种 MCP Server。

长期价值：MCP 生态扩张时，nanobot 零成本接入所有兼容工具。

08 可借鉴的架构模式

模式 核心思想 适用场景
Markdown-as-Config 能力添加不改代码、不重启 LLM 需注入领域知识
懒加载 + 文件系统 system prompt 只放索引，按需加载 降低常规 token 消耗
消息总线解耦 子任务结果重注入输入流 异步任务结果通知
最小公共类型 所有工具返回 str LLM 消费所有输出
错误恢复委托 LLM 框架不处理重试，LLM 决定下一步 强模型场景

09 使用建议

适合：个人自托管 AI 助手 / 快速原型 / Agent 框架学习材料

不适合：精确多 agent 协调 / 大规模历史记忆 / 细粒度行为控制 / 生产安全隔离

nanobot 是目前最诚实的 Agent 框架：代码量和功能声明完全匹配。这本身就值得学习。
