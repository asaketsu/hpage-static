摘要

ML 平台运维团队 4 个月的 Agent 工程化深度复盘。核心观点：不要一开始就做 Agent，而是被业务问题一步步推到 Agent。给出了 Workflow vs Agent 的清晰判断标准、「Workflow 包 Agent」的生产架构模式、Anthropic 五种 Workflow 模式的工程价值、生产 Agent 需要的四类工程托底（Guardrails/可观测性/ACI/Prompt 分层），以及下一步方向（Eval 自动化 + 多 Agent 状态协议）。文章引用 Anthropic《Building effective agents》原则，理论与实践高度结合。

核心内容

1. Workflow vs Agent 判断标准

维度 Workflow Agent
LLM 角色 填空、总结、局部判断 决定下一步行动
控制流 代码提前定义 模型动态决定
工具调用次数 固定/半固定 取决于模型判断
停止条件 流程跑完/规则命中 模型判断证据是否足够

Agent 三要素：LLM 参与决策 + 能调用工具 + 能循环推进任务。缺一个都不叫 Agent。

2. 演进路径（被问题推过去）

AI 问答 → RAG 知识库 → 工具调用 → 多节点 Workflow → 局部 Agent → Agentic Platform

判断团队是否该做 Agent 的标准：有没有足够多的失败样本，证明固定路径已经不够了。

3. 最稳架构：Workflow 包 Agent

触发 → 分诊 → Agent 调查 → 结构化提取 → 质量评估 → 汇总输出 → 通知/人工处理

Agent 只在「调查」环节，其余保持确定性。四个设计原则：
1. 前置分诊能省 token，降低误判
2. Agent 必须有边界：不能无限查、不能绕审批、必须附证据和置信度
3. 输出必须结构化，能被系统消费
4. 评估节点独立于调查节点

4. 五种 Workflow 模式都是工程底座

模式 价值 场景
Prompt Chaining 拆复杂任务为小步骤 日志分析、慢任务分析
Routing 不同问题不同策略 多服务/多地区/多严重程度
Parallelization 并行收集完整上下文 诊断任务第一步
Orchestrator-Workers 专业能力封装 下游链路分析
Evaluator-Optimizer 迭代逼近答案 证据不足时再查一轮

5. 生产 Agent 的四类工程托底

  1. Guardrails — 事实边界（事实和推断分开）、行动边界（高风险需人确认）、执行边界（最大轮数/token/耗时）、输出边界（结果结构化）
  2. 可观测性 — 节点、工具调用、token 消耗、证据引用、分类结果、人工认可全链路记录
  3. ACI（Agent-Computer Interface） — 工具对模型要友好，描述像给新同事写操作手册
  4. Prompt 分层 — 系统指令（角色边界）/ 任务指令（目标输出）/ 领域知识（知识库/SOP/规则库）/ 动态上下文（工具和检索注入）/ 评估标准（反馈 Eval Set）。Prompt 是任务合同，不是知识仓库

6. 下一步方向

  • Eval 自动化 — 历史告警+人工确认根因 → Eval Set → 改 Prompt/工具/模型前跑回归
  • 多 Agent 状态协议 — 任务创建/分配/完成/阻塞/暂停恢复/交接/失败重试，像传统状态机

💡 启发

  1. 「被问题推过去」比「主动设计」更可靠 — 不要先设计 Agentic Platform 再填功能，而是让业务问题一步步把系统推到 Agent。这与 Hermes 的 skill 积累模式一致：遇到问题 → 解决 → 沉淀 skill
  2. 生产系统最可靠的 Agent = 被约束的 Agent — 给模型恰到好处的自由，约束什么能做什么不能做，放大工具/知识/上下文/反馈
  3. Eval 是 Agent 工程的终极纪律 — 没有 Eval 只能靠感觉判断「这版好像更聪明了」，有了 Eval Set 才能把「只在效果可证明时增加复杂度」变成工程纪律
  4. 多 Agent 的关键不是怎么串，而是状态协议 — 看起来像传统状态机，但正是这种传统保证了 Agent 能被调度、暂停、恢复、审计

🔮 预判

  • 短期（3 月内）：Eval Set 成为 Agent 团队的标配实践，类似 CI/CD 之于 DevOps
  • 中期（6 月内）：多 Agent 状态协议标准化（可能由 Anthropic 或开源社区提出参考实现）
  • 长期（1 年）：「Workflow 包 Agent」成为 Agent 生产化的共识架构模式，全 Agent 系统只在特定场景出现
