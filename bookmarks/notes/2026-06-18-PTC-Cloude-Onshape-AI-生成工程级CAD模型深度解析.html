PTC Cloude + Onshape：AI 生成工程级 CAD 模型深度解析

来源：微信公众号 ENGtechnica 深度分析
事件：2026-06-10 PTC NEXT 芝加哥大会
标签：PTC Onshape CAD AI FeatureScript Text-to-CAD 工业软件

0. 核心事件

2026 年 6 月 10 日，PTC 在芝加哥 PTC NEXT 大会上展示了 Cloude 大模型 + Onshape 的结合成果：由 AI 自动生成一个管壳式换热器（2100 行代码、532 个可配置参数）的工程产品 3D 模型，并自动生成相关设计和文档。

这记重拳直接把"输入一句话，给你个 3D 模型"的 Text-to-CAD 产品打回原形。

1. Text-to-CAD 的繁荣与尴尬

1.1 赛道现状

近两年 Text-to-CAD 赛道涌现大量玩家：

产品 输出 能力边界
Zoo B-Rep 实体 STEP 文件 支持参数滑块，但同一提示词多次运行结果不一致；复杂部件精度不足
AdamCAD 2D 技术图纸 仅限 2D，无法替代 SolidWorks 等高级工具
OpenArt 风格化视觉效果 不输出可编辑 CAD 文件，仅视觉参考
DraftAid 从 3D 模型生成 2D 制造图纸 不是从文本生成几何体，是图纸自动化工具
Claude + MCP 通过 API 命令控制 CAD 语言模型不理解 3D 形状，复杂几何时受限

1.2 共同死穴

公差、表面处理、材料标注、制造约束、多部件装配 —— 这些生产必须的东西，没有一家能从文字描述中自动生成。

因此 Text-to-CAD 目前仅适用于：
- 概念阶段的快速原型探索
- 相对固定、简单、标准的零部件

到了真正的产品工程设计，基本还得重新来搞。

2. PTC 的核心论点：你的模型，有设计意图吗？

Darren Henry 在 PTC NEXT 演讲中展示了 LLM 通过 MCP 接入 CAD 系统生成的模型，并直言：

"我邀请你看看这些模型的复杂度。我想你会同意它们相当简陋。"

2.1 约束缺失是致命伤

案例 问题
垫圈 可以建出来，但编辑草图时圆从未被约束为同心
树莓派外壳 没有重合角点，没有水平/垂直关系
链轮齿 约 12-18 个几何图元，需约 80 个约束

一个垫圈需要 4 个约束，一个简单盒子需要 12 个，单个链轮齿约 80 个约束。大多数人的设计复杂度介于链轮齿和矩形之间。

2.2 核心观点

LLM 作为大语言模型，擅长写代码，但不擅长 2D/3D 形状、草图约束、特征依赖、几何关系 —— 而这些恰恰是设计意图（Design Intent） 的核心。

当前 Text-to-CAD 的产出物特征：
- 简单的零部件
- 脆弱、不稳定的结果
- 不能体现设计意图

3. FeatureScript：PTC 的破局方案

3.1 Text-to-code-to-CAD

PTC 的方案不是让 AI 直接生成 3D 几何体，而是：

文本描述 → LLM 生成 FeatureScript 代码 → CAD 引擎解释执行 → 生成参数化模型

3.2 为什么是 FeatureScript？

特性 说明
类英语语法 LLM 最擅长处理的对象
结构化、逻辑清晰 便于 AI 理解和迭代
原生集成 Onshape 代码在 Onshape 中原生执行，生成参数化模型
意外之喜 Onshape 创造 FeatureScript 时，LLM 还没出生

3.3 运行流程

  1. 用 MCP 协议 包装 FeatureScript 接口
  2. 用文本描述，让 LLM 编写、测试、迭代 FeatureScript 代码
  3. 代码在 Onshape 中原生执行，生成参数化模型
  4. 此后的编辑修改、设计人员可以直接在 CAD 中进行，不再消耗 token

杀手锏：修改模型不需要从头再来，参数化调整不消耗 token。

4. AI 设计案例：从玩具到工程

4.1 案例一：链轮配置器

输入 提示词 + 制造商目录页 + 齿形规格
输出 约 400 行 FeatureScript，封装好的特征
结果 正确的齿廓几何，内置 Martin Sprocket 标准尺寸，模型完全可编辑

让 LLM 理解草图约束来构建链轮齿，需要约 12-18 个几何图元、约 80 个约束。

4.2 案例二：流体体积特征

用途 储罐设计
代码量 约 200 行
特点 简洁、专用、可复用

4.3 案例三：管壳式换热器（最复杂工程级作品）

指标 数据
代码量 约 2,100 行 FeatureScript
可配置参数 约 532 个
提示次数 20 次（Henry 认为可压缩到 15 次）
开发时间 约 1 天（间歇性提示）
重建时间 修改后 19 秒
节省工程时间 150-200 小时

包含的技术内容：

类别 详情
标准 ASME 和 ASTM 标准法兰螺栓孔
优化 方向自动优化以避免与入口干涉（AI 自发行为）
设计 挡板设计，四种封头样式（平头/圆头/穹顶/半球形）
焊接 焊接准备切割，冷热进出口指示器（红色标热/蓝色标冷）
可视化 流体可视化，焊接时间估算器（访问网络查找电弧时间数据）
文档 所有内部管材切割清单，自动生成文档

Henry 评论："这可能是这个星球上最复杂的 AI 生成模型。你不可能在一个工程师身上找到所有这些技能。"

4.4 本质区别

维度 Text-to-code-to-CAD Text-to-CAD
输出 多学科优化的工程知识产品 简单的几何形状
可编辑性 设计人员随时参与（Human in the Loop） 修改需从文本重来
可追溯性 代码可版本控制、可审计 改了就没了

5. Token 经济学：一次投入 vs 持续消耗

5.1 Text-to-CAD 方案

  • 每次生成或编辑模型，都要消耗 token
  • 迭代 10 次 = 消耗 10 次 token
  • 只修改一个尺寸，同样消耗一次
  • 团队 5 人每人修改一版 = 消耗 5 次
  • 累计消耗巨大

5.2 Text-to-code-to-CAD 方案

  • Token 只在从文本到写代码时消耗一次
  • 之后 Feature 在 Onshape 中原生运行，参数化调整和再生不需要 token
  • 整个组织复用同一个 Feature，成本基本为零

5.3 企业资产视角

维度 FeatureScript 代码 Text-to-CAD 几何体
版本控制 ✅ ❌
可审计 ✅ ❌
可复用 ✅ ❌
可迭代 ✅ ❌
企业资产 ✅ ❌

AI 生成的 FeatureScript 代码本身成为企业资产，类似于 AI Agent 中 Skills 的文本定义。

6. AI+CAD 路线分化

6.1 两条路线

路线 定位 代表产品 适用场景
公民化路线 "人人都能设计" Zoo、AdamCAD 快速体验 3D 效果、3D 打印原型、创客
工程化路线 "让专业设计更强大" PTC + FeatureScript 产品工程设计、生产就绪的设计资产

6.2 核心差异

  • Text-to-CAD：低门槛，概念阶段，简单零部件
  • Text-to-code-to-CAD：结构化的代码可靠表达约束关系、特征依赖、拓扑逻辑、制造约束

形状可以被生成，但约束关系、特征依赖、拓扑逻辑、制造约束 —— 这些"智能"只有通过结构化的代码才能可靠地表达和传递。代码是工程知识的载体。

6.3 从 Vibe-CAD 到 Vibe-Engineering

Vibe-CAD: 一句话 → 几何体（脆弱、不可编辑）
    ↓
Vibe-Engineering: 一句话 → 代码 → 参数化模型（可编辑、可审计、可复用）

7. AI+CAD 的未来

7.1 核心问题

在世界模型、物理模型真正落地之前，如何充分利用 LLM 实现 3D 建模和产品设计的自动化，是未来很长一段时间的重要课题。

7.2 有效路径

将基于特征的 3D 参数化特征建模过程和几何&拓扑&约束等用脚本语言/编程语言进行精确描述。

PTC 的 Text-to-code-to-CAD 属于同样的尝试。

7.3 三层 AI 框架（PTC）

层级 功能
Advise 设计建议、知识检索
Assist 辅助操作、自动化编辑
Automate 自动生成 FeatureScript 代码

8. 拓展：对 CAA 开发的启示

8.1 CAA 中的代码化特征

CATIA V5 CAA 中，特征本身就是通过 C++ 接口操纵的"代码"。每个 CATIPrtFactory::CreatePad() 调用本质上是在执行一段 CAD 脚本。

CAA 概念 FeatureScript 对应
CATIPrtFactory::CreatePad() NewPart(); AddPart(); Extrude()
CATIPrtPart::Update() 编译执行
CATISpecObject 特征对象引用
CATIMechanicalFeature 特征树遍历

8.2 CAA 开发的 AI 化路径

阶段 描述
阶段 1 LLM 生成 CAA C++ 代码 → 编译为插件 → 在 CATIA 中执行
阶段 2 LLM 通过 MCP 直接调用 CATIA API → 实时生成特征
阶段 3 企业级 CAA Feature 库 → 版本控制、可审计、可复用

8.3 代码即工程知识

无论是 FeatureScript 还是 CAA C++，核心逻辑一致：

文本描述 → LLM 生成代码 → 引擎解释执行 → 参数化模型
    ↓
代码可编辑、可审计、可版本控制、可复用
    ↓
代码 = 工程知识的载体
