摘要

MMTLS 是微信基于 TLS 1.3 定制的私有安全通信协议，服务 10 亿+用户。2024 年 Citizen Lab 发布首次公开安全分析（Black Hat Asia 2025 演讲），发现 MMTLS 虽采用双层加密架构（业务层 AES-CBC + 传输层 AES-GCM），但多项修改引入了密码学弱点：确定性 IV、缺乏前向安全性、AES-CBC 的 CBC padding oracle 风险。本文综合公开资料，梳理 MMTLS 架构、已知弱点、逆向方法论（含工具链），以及安全研究结论。需要强调：截至公开研究，MMTLS 未被完全破解，但实现质量不符合十亿级用户应用应有的密码学标准。

一、MMTLS 协议架构

1.1 定位

MMTLS 在微信通信层次中介于应用层和网络连接层，类似于 TLS 在 HTTPS 中的位置。微信 TCP 连接分两种：

  • 长连接：TCP + MMTLS + 私有协议
  • 短连接：HTTP + MMTLS

1.2 双层加密

MMTLS 使用双层加密架构：

明文数据 → 业务层加密(AES-CBC) → MMTLS层加密(AES-GCM) → 网络传输
  • 业务层加密（Business-layer encryption）：2016 年 MMTLS 引入前是唯一加密层，使用 AES-CBC
  • MMTLS 层加密：基于 TLS 1.3 修改，使用 AES-GCM（AEAD 认证加密）

1.3 三个子协议

子协议 功能
Handshake 密钥协商（1-RTT ECDHE / 1-RTT PSK / 0-RTT PSK）
Record 对称加密传输数据
Alert 错误通知（仅 Server→Client）

1.4 握手模式

模式 RTT 密钥协商方式 使用场景
1-RTT ECDHE 1 临时 ECDH + ECDSA 签名 长连接首次、无 PSK
1-RTT PSK 1 预共享密钥 长连接复用
0-RTT PSK 0 预共享密钥（带业务数据） 短连接

关键设计：仅认证 Server 端（ECDSA 签名），不认证 Client。签名公钥 verify_key 硬编码在客户端，无需证书链。

1.5 密钥派生

pre_master_key → HKDF 扩展 → 4个参数：
  client_write_key  (加密)
  server_write_key  (加密)
  client_write_IV   (初始向量)
  server_write_IV   (初始向量)

密钥按 (16, 12, 16, 12) 字节分解为 AES-GCM 的 Key 和 IV。

1.6 防重放

  • 1-RTT：递增 sequence number 作为 AES-GCM nonce 的一部分
  • 0-RTT：基于客户端/服务器时间序列的防重放策略（分布式环境下无通用高效方案）

二、已知密码学弱点（Citizen Lab 发现）

2.1 确定性 IV（Deterministic IV）

MMTLS 的 AES-GCM IV 生成方式存在问题。标准 TLS 1.3 使用随机 IV 或保证不重复的 nonce 构造方法，而 MMTLS 的 IV 构造在特定条件下可能重复，违反 NIST SP 800-38D 对 AES-GCM 的 nonce 唯一性要求。

风险：IV 重复在 AES-GCM 中可导致认证密钥（H-key）恢复，进而伪造密文。

2.2 缺乏前向安全性（Forward Secrecy）

0-RTT PSK 模式下，加密完全依赖长期保存的 ticket_key。如果 ticket_key 泄露，所有基于该 key 的历史通信都可被解密。

标准 TLS 1.3 的 0-RTT 也有此问题，但 MMTLS 的 0-RTT 使用频率远高于标准 TLS（微信大量短连接）。

2.3 业务层 AES-CBC 的弱点

  • AES-CBC 不提供完整性验证（无 AEAD）
  • 存在 CBC padding oracle 攻击风险
  • 确定性 IV 问题同样存在于业务层
  • 2016 年前此层是唯一加密，历史数据风险更大

2.4 静态签名密钥风险

sign_key（服务端 ECDSA 私钥）若泄露，攻击者可伪造 Server 身份。虽然可通过强制更新客户端更换 verify_key，但存在窗口期风险。

2.5 ECDH 临时私钥泄露

微信后台大量服务器临时生成 ECDH 公私钥对，明文短暂存于内存。分布式环境下，某台服务器的 svr_pri_key 泄露可导致该次握手被中间人攻击。MMTLS 的缓解措施是将 Client_Random + svr_pub_key + Server_Random 绑定签名，防止签名值跨握手复用。

三、逆向分析方法论（详细工具链）

3.1 整体方法论

静态分析 → 动态 Hook → 网络抓包 → 协议还原 → 密码分析

3.2 静态分析（反编译）

目标：微信客户端二进制文件（Android APK / iOS Mach-O / Windows DLL）

工具：
- IDA Pro — 商业级反汇编/反编译，支持 ARM/x86
- Ghidra — NSA 开源反编译器，免费且强大
- Hopper — macOS/iOS 逆向工具

关键定位：
1. 搜索加密相关字符串："AES", "GCM", "ECDH", "mmtls", "handshake"
2. 定位网络通信模块：查找 send/recv/connect 系统调用引用
3. 定位加密函数入口：查找 OpenSSL/BoringSSL 函数符号（AES_GCM_encrypt, ECDH_compute_key, HKDF_expand）
4. 定位 MMTLS 特有逻辑：握手状态机、Record 协议解析

实操要点：
- Android 版：APK 提取 → lib/armeabi-v7a/libwechatcommon.so 或 lib/armeabi-v7a/libmm.so
- iOS 版：IPA 提取 → 用 class-dump 扫描 Objective-C 类名
- Windows 版：WeChatWin.dll — MMTLS 核心逻辑常在此 DLL 中

3.3 动态分析（运行时 Hook）

工具：
- Frida — 跨平台动态 Hook 框架（首选）
- Xposed / LSPosed — Android 框架级 Hook
- LLDB — iOS/macOS 调试器

Frida Hook 关键点：

  1. Hook AES-GCM 加密/解密函数，截获明文和密钥
  2. 搜索 AES_GCM / aesni_gcm_encrypt 等符号

  3. 参数：key, IV, plaintext/ciphertext, tag

  4. Hook ECDH 密钥协商函数，截获公私钥和协商结果

  5. 搜索 ECDH_compute_key / EC_POINT_mul 等符号

  6. Hook HKDF 密钥派生函数，截获 pre_master_key 和扩展后密钥

  7. 搜索 HKDF_expand / HKDF_extract 符号

  8. Hook 网络发送/接收函数，截获原始 MMTLS 数据包

  9. Android: write() / send() 在 libssl.so 或 libc.so
  10. Windows: Hook WSASend / recv 或 WeChat 的自实现网络库

示例 Frida 脚本思路：

// Hook AES-GCM encrypt
Interceptor.attach(Module.findExportByName("libwechatcommon.so", "AES_GCM_encrypt"), {
    onEnter: function(args) {
        // args[0]: key, args[1]: iv, args[2]: plaintext
        console.log("AES-GCM Key:", hexdump(args[0], {length: 16}));
        console.log("AES-GCM IV:", hexdump(args[1], {length: 12}));
    }
});

// Hook ECDH compute key
Interceptor.attach(Module.findExportByName(null, "ECDH_compute_key"), {
    onEnter: function(args) {
        // 截获协商出的共享密钥
    },
    onLeave: function(retval) {
        console.log("ECDH shared secret length:", retval.toInt32());
    }
});

Windows DLL 注入注意：
- MMTLS 必须在 DLL 加载时就开始注入（不能延迟）
- 可用 DLL注入工具（如 Remote DLL）或 Frida 的 -f spawn 模式

3.4 网络抓包与协议还原

步骤：
1. 抓包：Wireshark / tcpdump 在中间路由或设备上抓取微信流量
2. 识别 MMTLS 数据包：微信短连接走 HTTP，Content-Type 非标准；长连接走 TCP 私有协议
3. 定位握手包：第一个包通常包含 ECDH 公钥
4. 结合 Hook 数据：将抓到的密文与 Hook 到的密钥/IV 对应，验证加解密流程

看雪论坛实践经验（mmtls 分析帖）：
- 秘钥按 (16, 12, 16, 12) 分解为 AES-GCM 的 key 和 IV
- 需要从 DLL load 阶段就开始注入，错过初始化会丢失握手数据

3.5 密码学分析

方法：
1. 协议对比：将还原的 MMTLS 流程与标准 TLS 1.3 (RFC 8446) 逐字段对比
2. 弱点建模：基于已知弱点（确定性 IV、无 PFS），构建理论攻击模型
3. 形式化验证：用工具（如 Tamarin Prover / ProVerif）对协议建模，自动验证安全性

Citizen Lab 的分析结论：
- 未找到能完全破解 MMTLS 的实用攻击
- 但实现质量不符合十亿级应用应有的密码学标准
- 主要风险集中在业务层 AES-CBC（而非 MMTLS 的 AES-GCM 层）

四、攻击面总结

攻击面 难度 可行性 说明
被动窃听（无密钥） ★★★★★ 极低 AES-GCM 仍提供有效加密
中间人攻击（伪造Server） ★★★★ 低 ECDSA 签名 + verify_key 内置
CBC Padding Oracle ★★★ 中 业务层 AES-CBC 理论可行，需特定网络条件
ticket_key 泄露 → 历史解密 ★★ 中 依赖服务端安全，非协议层问题
0-RTT 重放 ★★★ 中 理论可行，微信有时间序列防重放
IV 重复 → H-key 恢复 ★★★★ 低 需要大量同 IV 密文样本

五、关键概念

概念 定义
MMTLS 微信基于 TLS 1.3 定制的私有安全通信协议
ECDHE 临时椭圆曲线 Diffie-Hellman 密钥协商
PSK 预共享密钥（Pre-Shared Key），由 Server 在 ECDHE 握手中下发
ECDSA 椭圆曲线数字签名算法，用于 Server 认证
verify_key 硬编码在客户端的 ECDSA 验签公钥
sign_key Server 端 ECDSA 签名私钥
ticket_key Server 端用于加密 PSK 的对称密钥
HKDF 基于 HMAC 的密钥派生函数
AES-GCM 认证加密算法（AEAD），MMTLS 传输层使用
AES-CBC 分组加密模式（非 AEAD），业务层使用
PFS 完美前向安全性（Perfect Forward Secrecy）
0-RTT 零往返时间握手，握手同时携带业务数据

🔍 借鉴学习进化点

# 点 原文要点 对当前系统的借鉴 行动计划
1 不要自造加密协议 微信修改 TLS 1.3 引入了确定性 IV、无 PFS 等弱点 Hermes 的 API 通信必须使用标准 TLS 1.3，不自定义加密层 审查所有 API 调用是否走 HTTPS + 标准 TLS
2 双层防御但不等于更安全 业务层 AES-CBC 的弱点反而成为最大风险 多层加密如果内层有缺陷，外层再强也打折扣 安全设计遵循"一层做对 > 多层凑合"
3 密钥硬编码的权衡 verify_key 硬编码简化了证书管理，但更新依赖强制升级 API key / token 不应硬编码在代码中 用 .env + secrets 管理，支持热更新
4 0-RTT 的安全代价 零延迟握手牺牲了前向安全性和防重放 Agent 通信中不能为了性能牺牲安全性 审查 Hermes gateway 通信是否在性能和安全间有正确取舍
5 逆向方法论可复用 Frida Hook + 网络抓包 + 静态分析三件套 对任何 App 的安全审计都可用此方法论 将此方法论沉淀为 App 安全审计 Skill
