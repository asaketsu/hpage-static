一、内容整理

独立技术创始人 Caspar Bannink（HomeScout 开发者）的生产级 AI Agent 开源项目选型清单（20 个）。核心视角："当一个智能体离开聊天窗口后会发生什么"——研究助手要浏览为人类构建的网站、客户助手要记住哪些问题已解决、语音助手被打断时要停——这些是各不相同的工程问题，选更贵的模型并不能消除它们。开源项目与商业服务是两个独立决策（浏览器库可开源、托管浏览器要付费）。

1.1 构建与编排（2 项）

  • Pydantic AI：Python 智能体集成进现有应用的首选。类型化依赖+验证输出给智能体与应用代码之间画清晰边界；支持中断续跑工作流所需的审批门控工具与持久执行。退款助手例：结果必须是订单号+符合 schema 的金额，付款前进独立审批步骤——"一段说明退款合理的文字不是应用契约"
  • LangGraph：工作流复杂时的低层级有状态编排——持久化+执行期间人工介入（human-in-the-loop）

1.2 浏览与抓取（4 项，互为替代）

  • Firecrawl：Web 抽取，注意开源能力与云能力的边界
  • Crawl4AI：想在 Python 环境里控制爬取时的替代——异步爬取、自托管
  • Stagehand：普通代码+模型引导动作结合——Playwright 风格操作+自然语言原语，带自愈动作（页面结构变化时恢复）。发票下载例：导航到已知 URL 保持确定性，藏在变化菜单后的发票用语义指令，下载后普通代码验文件
  • Browser Use：路线不可预测时更任务导向的开源智能体库（含托管浏览器/托管智能体商业线）

1.3 沙箱执行（2 项，互为替代）

  • E2B：智能体生成代码的隔离云环境（Python/JS SDK），Terraform 记录自托管，AWS/GCP 官方支持——比"假设任何开源 sandbox 能在闲置笔记本跑"更具体的部署主张。数据分析助手是明显用例
  • OpenSandbox：自有基础设施上跑智能体环境——本地 Docker+K8s+网络策略

1.4 记忆（2 项，互为替代）

  • Mem0：跨交互记忆层（Apache-2.0，开源库+自托管 server+托管平台）。客户助手不该每天早上重新听同一个未解决问题；比把整个对话历史盲目附加到每次调用有用。权威账户数据属于应用数据库——记忆记偏好，账户状态走权威数据核对
  • Graphiti：事实间关系+事实成立时间影响答案时用——带时间上下文的图、可溯源到源材料（Zep 关联）

1.5 MCP 工具层（2 项）

  • FastMCP：Python 构建 MCP server/client 的框架（Apache-2.0）。"查订单配送状态"这种窄范围操作是好的起点——server 验证请求只返回相关字段，比通用数据库凭据+一句"请谨慎行事"好审查得多
  • ToolHive：MCP 的运维侧——隔离容器跑 servers+发现与管理平台+身份策略

1.6 权限与网关（2 项）

  • OpenFGA：最不像"智能体品牌"的项目（这正是吸引力）——细粒度授权建模与检查的开源版。智能体代表用户行动时，权限检查不该依赖模型自觉
  • LiteLLM：多提供商统一网关+routing+支出控制。virtual keys+budgets 让不同智能体/团队受控访问而不各自管理底层凭证；模型选择变成运维决策（后台抽取走便宜路线）时它就有了位置

1.7 可观测与评估（3 项）

  • Langfuse：可检查 trace（MIT 核心）——从用户请求到最终动作的路径。助手选错账户时最终答案信息有限，trace 显示检索了哪条记录、模型选工具前收到什么
  • Promptfoo：本地/CI 可重复的声明式 eval suite+断言+红队测试
  • DeepEval：代码驱动的完整智能体运行+单步评估（轨迹/任务/工具级）

1.8 语音（2 项，互为替代）

  • Pipecat：实时语音/多模态 pipeline 框架（Telnyx/Twilio transport）。语音智能体必须把时序当交互一部分——被打断就停并纳入纠正
  • LiveKit Agents：LiveKit session 上的实时智能体构建（telephony 支持）

1.9 支付（1 项）

  • Stripe Link CLI（MIT）：智能体完成普通在线购买——Link wallet 一次性支付凭据/virtual cards，可作本地 MCP server 运行，智能体不存储底层卡号。选品与授权付款分开；现限美国 Link 账户，不适合全球受众默认支付

1.10 作者的收尾方法论（比清单更重要）

  • 20 个项目是基础设施地图，不是采购清单（多个互为替代），更不是起始架构
  • 路径：选一个有价值的工作流→定义可采取的动作→添加可靠完成与评估所需的组件
  • 文档助手：先权限感知 retrieval+评估集，再加浏览器自主性；语音产品：先窄范围干净转接的对话，再教付款
  • 记忆规则：连续性确实改善产品才用；可记住什么、什么必须走权威数据核对，要有明确规则
  • 第一版底线：能解释一次失败运行 + 不请求模型许可就能阻止危险操作。做到这点后，扩大智能体责任范围才是合理工程决策

二、查询拓展

2.1 MCP（Model Context Protocol）运维化

Anthropic 2024 年开源的协议已成工具接入事实标准。本文 ToolHive 一项标志 MCP 讨论从"怎么接工具"进入"怎么运维工具"——容器隔离、身份策略、server 生命周期管理。这与传统微服务治理（API gateway/service mesh）的演进路径同构。

2.2 ReBAC 与 OpenFGA

OpenFGA 源自 Google Zanzibar（Google 内部全球授权系统论文）的开放实现，关系型访问控制（ReBAC）代表。智能体代用户行动时引入它，等于把"AI 权限"从 prompt 层沉到策略层——模型幻觉不能越权，因为检查在代码里。

2.3 记忆层赛道格局

Mem0（向量记忆+检索）vs Graphiti（时序知识图谱，Zep 底层）是当前记忆层两大路线：前者把记忆当"可检索上下文"，后者把记忆当"带时间有效性的知识"。本文"权威数据 vs 记忆"的区分是工程界对此的共识表述——记忆是缓存不是数据库。

2.4 语音智能体的时序问题

"被打断就停"（barge-in）是语音 Agent 区别于文本的硬工程：半双工 vs 全双工、VAD（语音活动检测）、回声消除、turn-taking 协议。Pipecat/LiveKit 都把 transport 层时序处理作为核心卖点——这也是 OpenAI Realtime API 竞争的开源侧镜像。

三、归纳总结

3.1 20 项目功能地图（按智能体生命周期排列）

[构建]  Pydantic AI(契约层) → LangGraph(编排层)
[感知]  Firecrawl/Crawl4AI(抽取) → Stagehand/Browser Use(交互)
[执行]  E2B/OpenSandbox(沙箱)
[记忆]  Mem0(检索记忆) / Graphiti(时序图谱)
[工具]  FastMCP(接入) → ToolHive(运维)
[权限]  OpenFGA(细粒度授权)
[路由]  LiteLLM(模型网关+预算)
[观测]  Langfuse(trace) → Promptfoo/DeepEval(评估)
[语音]  Pipecat / LiveKit Agents
[支付]  Stripe Link CLI

3.2 三条选型原则（从对比段提炼）

  • 确定性优先原则：能用普通代码就不用模型（Stagehand 的导航/语义分工、FastMCP 窄工具 vs 通用凭据）——模型只在路线不可预测处进场
  • 开源≠服务原则：每个候选都先问开源库/自托管/托管平台的能力边界（Firecrawl 云能力、E2B Terraform、Langfuse enterprise 条款、Stripe 美国限制）
  • 责任分离原则：验证（Pydantic）与业务规则分开、选品与付款分开、记忆与权威数据分开、智能体动作与授权检查分开（OpenFGA）——每处都是"模型可以做 A，但 A 的生效由代码决定"

3.3 "第一版底线"检验

作者的验收标准可当 checklist：①能否解释一次失败运行（trace 完整）②能否不请求模型许可就阻止危险操作（硬闸门存在）③失败运行能转化为评估数据集（Langfuse→Promptfoo 闭环）。

四、趋势判断

趋势1：Agent 基础设施正在重演云原生软件栈史

依据：20 项目按层分布（网关/沙箱/观测/评估/权限/记忆）与 K8s 生态高度同构——LiteLLM≈API gateway、E2B≈Fargate、Langfuse≈Jaeger、OpenFGA≈OPA。AI infra 不是新发明，是把分布式系统治理经验平移到模型调用层。

趋势2：权限与支付是 Agent 落地的下一批卡点

依据：清单里最不像 AI 的两项（OpenFGA/Stripe Link）恰是"智能体代表用户行动"的先决条件。浏览器记忆沙箱解决能力问题，授权与支付解决信任问题——后者进度决定 Agent 商业化上限。

趋势3：评估从研究环节变为 CI 环节

依据：Promptfoo（本地/CI 可重复 suite）+ DeepEval（轨迹级）+ Langfuse（trace→数据集）三件套把 eval 推进部署管线。红队测试入列标志 Agent 安全测试的工程化开始。

趋势4：语音 Agent 独立成栈

依据：Pipecat 与 LiveKit 双候选并列，时序（打断/转接）被定义为不可由文本模型能力替代的独立工程层。

五、关联分析

5.1 与 Hermes Agent 自身架构的关联

我们自身就是一张现成的对照表：LiteLLM 的网关+预算≈Hermes 的 provider fallback 链与 zhipu-quota-monitor；Langfuse 的 trace≈executions.db 与 observability-dashboard；Mem0/Graphiti 记忆分层≈Hermes 三级记忆架构（L1 注入/L2 短期/L3 topic）；ToolHive 的 MCP 运维≈我们的 native-mcp+mcporter；Promptfoo/DeepEval≈evolution-gate 与 skill 压力测试。清单价值=逐项对照找差距：我们缺的主要是 OpenFGA 式细粒度授权（目前靠人工审批边界）与 E2B 式代码沙箱（本地 execute_code 无容器隔离）。

5.2 与已有笔记/项目的关联

  • 《EianLu Gemini4Argon》与《AI工程化真问题清单》（10-14）：本文是"真问题清单"的答案侧——每个真问题都有对应开源件
  • 《PiDurable自动恢复机制》（10-14）：Pydantic AI 的持久执行+中断续跑同题
  • 《自建Jev式决策模型-logprobs分类器与诚实评估工程法》（10-14）：DeepEval/Langfuse 轨迹评估的实践分支
  • 嗅探域 AI Agent 工程化：本文 20 项应入库为选型参照系

七、行动启示

  • 对照差距：按 3.1 地图逐层对照 Hermes 现状，短板两项（授权层/沙箱层）评估是否引入 OpenFGA 与容器化 execute_code
  • 窄工具改造：按 FastMCP 原则审计现有工具面——凡"通用凭据+谨慎行事"式的都收窄为验证型窄接口
  • eval 入 CI：Promptfoo 式断言 suite 可给 evolution-gate 加一层确定性红队（现有 8 信号全是事后，缺事前）
  • 选型备忘：未来做浏览器/记忆/语音任务时直接查本清单的对应层，替代重新调研

八、拓展应用推荐

  • 企业内部 Agent 平台建设：按 3.1 地图分层采购/自建，避免单一厂商绑定
  • Agent 产品 MVP：用"第一版底线"三问（可解释失败/可硬停/失败转化数据）做 launch checklist
  • 多智能体系统治理：OpenFGA 给每个子 Agent 建独立授权身份，替代共享凭证
  • 记忆系统设计：Mem0 vs Graphiti 二选一的判据=是否需要时间有效性（"用户上周住 A 城市这周搬走"类事实）
  • 语音产品原型：Pipecat（管线灵活）vs LiveKit（session 完整）按转接复杂度选

九、指南分析

本文的选型文写作方法论（可直接抄）：

  • 场景先于功能：每个项目都用一个具体场景引入（退款助手/发票下载/数据分析），先立"什么时候需要它"再讲"它有什么"——反转了 feature-list 异选型文
  • 替代关系显式声明：开头即警告"几个项目互为替代，不要当采购清单"，避免读者全量引入——对清单文的自我解毒
  • 许可与地域边界入正文：Apache-2.0/MIT/enterprise 条款/美国限制都写进选型段——开源合规是选型的一级维度而非脚注
  • 每个"能力"都配"不能做什么"：Stripe 段明确"地域限制使其不适合全球受众默认支付"——诚实的负面信息比正面卖点更省读者时间
  • 收尾升维：清单文最后用方法论段（从工作流开始/第一版底线）把 20 个项目降维成组件——防读者把地图当领土
