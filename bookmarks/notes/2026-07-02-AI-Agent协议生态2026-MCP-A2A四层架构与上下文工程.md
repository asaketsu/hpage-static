## 一、2026 年的协议收敛

2026 年 AI Agent 领域最重要的变化不是某个新模型，而是**协议层的标准化与收敛**。四大协议已经形成了清晰的分层架构，不再是各自为战的混乱局面：

- **MCP**（Model Context Protocol）：Agent → 工具/数据 连接层（Anthropic 创建，**9700 万下载**）
- **A2A**（Agent-to-Agent）：Agent → Agent 协调层（Google 创建，**50+ 合作伙伴**）
- **ACP**（Agent Commerce Protocol）：Agent 商业交易层（IBM + Linux Foundation）
- **UCP**（Universal Commerce Protocol）：Google 生态商业层

> 核心洞察：**这四个协议是互补的，不是竞争的。** 一个完整的 2026 企业 Agent 栈会同时使用全部四个协议：MCP 做工具访问，A2A 做 Agent 协调，ACP 或 UCP 做商业交易。

---

## 二、四层协议架构详解

### 2.1 MCP：Agent 到工具的连接层（已「获胜」）

**范围**：仅处理 Agent 到工具/数据的通信。**不处理** Agent 之间的通信、任务委派或商业交易。

**组件模型**：
- **Servers**：轻量进程，暴露工具（typed function + JSON Schema）、资源、提示词
- **Clients**：Agent 运行时（Claude Desktop、VS Code Copilot、Cursor、Gemini CLI）
- **传输**：stdio（本地）/ HTTP+SSE（远程）

**生态地位**：已被 Anthropic、OpenAI、Google、Microsoft、Amazon 五大厂全部采纳，实质上「赢得了 agent-to-tool 层」。本机的 mcporter/native-mcp 工具就是 MCP 的具体实现。

### 2.2 A2A：Agent 到 Agent 的协调层

A2A 解决的是 **「MCP 明确不解决的协调问题」**——如何让不同框架（LangChain/AutoGen/CrewAI）构建的 Agent 互相对话。

**五大设计原则**：
1. **拥抱 Agent 原生能力**：不要求共享记忆/工具/上下文，Agent 用各自自然模态协作
2. **基于现有标准**：HTTP + SSE + JSON-RPC，与现有 IT 栈无缝集成
3. **默认安全**：企业级认证授权，与 OpenAPI 认证方案对齐
4. **支持长任务**：从秒级到小时/天级，实时反馈 + 状态更新
5. **模态无关**：支持音频/视频流，不仅是文本

**核心机制：Agent Card**

Agent Card 是 A2A 的灵魂——一个 JSON 文档，描述 Agent 的能力、输入、输出、认证要求。Client Agent 通过读取 Agent Card 来发现并选择最佳协作对象。

```json
{
  "name": "code-review-agent",
  "capabilities": ["code-review", "security-scan"],
  "inputs": {"code": "string", "language": "string"},
  "outputs": {"report": "markdown", "score": "number"},
  "authentication": {"type": "oauth2", "scopes": ["read:repo"]}
}
```

**任务生命周期模型**：
- 每个任务有唯一 ID 和明确的生命周期状态
- 通过 SSE（Server-Sent Events）流式更新长任务进度
- 结构化产物（artifact）以 typed message 格式返回
- 异步任务完成时推送通知
- 错误状态有结构化错误码

> **架构要点**：每个 A2A 能力的 Agent 同时也作为 MCP client 运行——编排器通过 A2A 委派，每个子 Agent 用自己的 MCP 连接执行工具调用。

### 2.3 ACP / UCP：商业交易层

**ACP**（IBM/Linux Foundation）：
- 开放的 Agent 间商业交易协议
- 处理支付、履约、交易语义
- 交易流程：发现 → 报价请求 → 报价 → 谈判 → 接受 → 确认
- 场景：自主 B2B 采购、API 市场、跨供应商 Agent 服务市场

**UCP**（Google）：
- Google 生态商业层
- 集成 Google Shopping、Merchant Center、Business Profile
- 连接 Google Search AI Mode 到可交易商业

两者不互斥——复杂栈可以同时实现两者。

## 五、Context Engineering：从 Prompt 工程到上下文工程

协议层的标准化只是 Agent 架构 2026 演进的一半。另一半是**上下文工程（Context Engineering）**的崛起——它被普遍认为是「Prompt Engineering 的继任者」。

### 5.1 定义（Karpathy）

> "Context engineering is the delicate art and science of filling the context window with just the right information for the next step."
> — Andrej Karpathy

> 中科院研究定义：「上下文工程是一门正式学科，超越简单的提示设计，涵盖对 LLM 信息载荷的系统化优化。」

### 5.2 Prompt Engineering vs Context Engineering

| 维度 | Prompt Engineering | Context Engineering |
|------|-------------------|-------------------|
| 关注点 | 如何措辞指令 | 如何构建模型周围的系统 |
| 范围 | 单条提示 | 记忆、检索、工具、工作流 |
| 适用场景 | 单轮交互 | Agent、多轮、有状态系统 |
| 核心问题 | "如何措辞提示？" | "应给模型什么信息和环境？" |

### 5.3 上下文的七个组成部分

1. **System Prompt** — 角色定义、行为约束
2. **Instructions** — 任务指令、输出格式
3. **User Input** — 用户实际输入
4. **Structured I/O** — JSON Schema 约束的结构化输入输出
5. **Tools** — 可调用工具的定义
6. **RAG & Memory** — 检索增强 + 记忆注入
7. **States & History** — 对话状态、历史上下文

> **本机实践映射**：Hermes Agent 的 AGENTS.md（System Prompt）+ Skill 按需加载（Instructions/Tools）+ session_search（States & History）+ Memory 注入（RAG & Memory）——本质上已经是上下文工程的实践，只是没有用这个术语。

### 5.4 常见陷阱

- **过度工程化（过早）**：在简单场景引入复杂的记忆/检索系统
- **垃圾进垃圾出**：检索质量差 = 上下文质量差
- **Token 膨胀**：上下文塞太多无关信息，稀释有效信号
- **上下文漂移**：长对话中上下文逐渐偏离原始目标
- **陈旧数据**：记忆/检索结果过时导致错误决策
- **忽视记忆层安全/隐私**：敏感信息泄露风险

## 六、核心发现总结

1. **协议分层已收敛**：MCP（工具）+ A2A（协调）+ ACP/UCP（商业）的四层架构在 2026 已成为事实标准。MCP 实质上已「赢得」agent-to-tool 层，9700 万下载量 + 五大厂全采纳。

2. **A2A 的 Agent Card 是 Agent 互操作的基石**：类似于 MCP 的 JSON Schema 工具定义，Agent Card 用 JSON 描述 Agent 能力。这使得 Agent 发现、选择、委派可以完全自动化。本机的 agent-card-protocol Skill 正是这一思想的本地实践。

3. **每个 A2A Agent 同时是 MCP Client**：A2A 编排器委派任务，子 Agent 用自己的 MCP 连接执行——两个协议天然正交组合。这意味着 Agent 系统不应在 MCP 和 A2A 之间二选一，而应同时实现。

4. **Context Engineering > Prompt Engineering**：2026 年的共识是，Prompt Engineering（措辞优化）已被 Context Engineering（系统构建）取代。后者关注的是「给模型什么信息」，而非「怎么措辞」。Hermes 的 Skill/Memory/session_search 架构本质上就是 Context Engineering 的工程实现。

5. **Agent 市场化需要 ACP/UCP**：当 Agent 从「工具」进化到「自主经济主体」时，需要标准化的商业交易协议。ACP（B2B 采购）和 UCP（消费者商业）正在填补这一空白。这是 Agent 从 demo 到生产的最后一公里。

---

## 七、对现有系统的改进建议

- **agent-card-protocol Skill 应对齐 A2A Agent Card 规范**：当前 Skill 是自定义格式，建议参考 A2A 官方 Agent Card JSON Schema（name/capabilities/inputs/outputs/authentication）做格式对齐，未来可直接与 A2A 兼容的 Agent 互操作。

- **Hermes 多 Agent 群聊可引入 A2A 思想**：当前的 Feishu 群聊多 Agent 协作（dev/content/data/opm 四只猫）本质上是 A2A 的私有实现。可以借鉴 A2A 的任务生命周期模型（唯一 ID + 状态机 + SSE 流式更新）来改进 delegate_task 机制。

- **context-engineering-patterns Skill 可补充协议层**：当前 Skill 聚焦静态/动态分离、历史管理、预算检索、输出修剪。建议增加「协议层上下文」——MCP 工具描述、A2A Agent Card 如何作为上下文注入。

- **MCP 安全 Skill 应扩展到 A2A 安全**：06-29 的 MCP 协议安全攻防笔记聚焦 MCP 层。A2A 引入了新的攻击面——Agent Card 欺骗、委派链劫持、跨 Agent 数据泄露——值得单独研究。
