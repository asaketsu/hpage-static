## 一、为什么需要推测解码

### 1.1 根本瓶颈：内存带宽限制

> Token 生成的瓶颈不是计算，而是**内存带宽**——GPU 每生成一个 Token 都要从 VRAM 加载完整模型权重。

```
标准解码（逐 Token）:
  Load Weights → Generate tok1 → Load Weights → Generate tok2 → ...
  每次只产出 1 个 Token，但加载了完整权重

推测解码（批量验证）:
  Draft Model: [tok1][tok2][tok3][tok4][tok5] ← 快速生成
  Target Model: ✓  ✓  ✓  ✗ ← 单次前向传播验证全部
  Result: tok1, tok2, tok3 被接受，从 tok4 重新生成
```

### 1.2 数学原理

接受率 α = 0.8 时，每次 Target Model 前向传播的期望接受 Token 数：

```
E[accepted] = (1 - α^(N+1)) / (1 - α)
            = (1 - 0.8^6) / (1 - 0.8)
            = 3.69 tokens/step （N=5 时）
```

**输出与标准自回归解码数学等价，零质量损失。**

## 二、2026 年推测解码方法对比

### 2.1 方法矩阵

| 方法 | 原理 | 加速比 | 适用场景 | 成熟度 |
|------|------|--------|----------|--------|

## 三、Snowflake Arctic Inference：Agent 场景的突破

### 3.1 Suffix Decoding — Agent 代码生成的杀手锏

> Agent 代码生成有大量重复模式（API 调用、错误处理模板等）。Suffix Decoding 用后缀树缓存这些模式，**无需 Draft Model，CPU 上 20μs/Token**。

**工作原理：**
1. 维护历史生成序列的紧凑缓存（后缀树数据结构）
2. 根据当前上下文动态构建候选序列
3. 自适应识别历史上类似上下文后的最长序列
4. 基于频率扩展，保持长序列准确性

**SWE-Bench 实测：**
| 指标 | 加速比 |
|------|--------|
| 端到端任务完成 | **1.8x-4.5x** |
| 解码时间缩减 | **2.3x-6.3x** |

### 3.2 混合策略（Suffix + Draft Model）

```python
# 伪代码：Arctic Inference 混合决策
def hybrid_speculation(context):
    suffix_tokens = suffix_decoding(context)
    
    if len(suffix_tokens) >= max_draft_model_tokens:
        # Suffix 足够长，跳过 Draft Model
        return suffix_tokens
    else:
        # Suffix 太短，用 Draft Model 补充
        return draft_model(context)
```

**混合性能对比（tokens/sec）：**
| 负载 | 无推测 | EAGLE | LSTM Only | Suffix Only | **LSTM+Suffix** |
|------|--------|-------|-----------|-------------|-----------------|
| ShareGPT | 76.0 | 102 | 172 | 113 | **179** |
| HumanEval | 77.2 | 112 | 204 | 148 | **217** |
| **SWE-Bench** | 75.8 | — | 123 | 286 | **302** |
| 混合 | 82.9 | — | 154 | 155 | **209** |

### 3.3 优化细节

| 优化 | 效果 |
|------|------|
| FP8 量化 Speculator | 减少内存带宽瓶颈 |
| Tensor 并行 | 跨 GPU 分割计算 |
| Top-K 本地化 | allGather 前先做本地 Top-K |
| CUDA Graphs | 减少 kernel launch 开销 |
| 贪心验证替代拒绝采样 | 验证延迟降低 3.5x |
| **总体** | 达到理论最大加速的 **91%** |

## 四、生产部署配置

### 4.1 vLLM + EAGLE-3（推荐通用配置）

```bash
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --quantization fp8 \
  --speculative-model yuhuili/EAGLE3-LLaMA3.3-Instruct-70B \
  --num-speculative-tokens 6 \
  --speculative-draft-tensor-parallel-size 1 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.94 \
  --max-num-seqs 32
```

### 4.2 vLLM + Arctic Inference（Agent 代码场景推荐）

```bash
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --quantization fp8 \
  --tensor-parallel-size 2 \
  --speculative-config '{
    "method": "arctic",
    "model": "Snowflake/Arctic-LSTM-Speculator-Llama-3.1-70B-Instruct",
    "num_speculative_tokens": 3,
    "enable_suffix_decoding": true
  }'
```

### 4.3 SGLang + EAGLE-3

```bash
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.3-70B-Instruct \
  --quantization fp8 \
  --speculative-algorithm EAGLE3 \
  --speculative-draft-model-path yuhuili/EAGLE3-LLaMA3.3-Instruct-70B \
  --speculative-num-draft-tokens 6
```

## 五、调优经验

### 5.1 接受率调优

| 经验 | 说明 |
|------|------|
| `--num-speculative-tokens 5` 起步 | 接受率持续 >0.8 时可上调 |
| 监控 `acceptance_rate` | 低于 0.6 说明 Draft Model 不匹配 |
| Draft Model 尽量同源 | Llama 系列用 Llama Draft，不要混用 |

### 5.2 常见陷阱

| 陷阱 | 原因 | 解决方案 |
|------|------|---------|
| VRAM OOM | Draft Model 占用额外显存 | 降低 `--gpu-memory-utilization` 或用更小 Draft |
| 接受率低 | Draft 与 Target 分布不匹配 | 换用 EAGLE（基于隐状态）而非独立 Draft |
| Agent 场景收益低 | 重复模式未被利用 | 启用 Suffix Decoding |
| 高并发反而变慢 | 验证开销超过收益 | 并发 >32 时关闭推测解码 |
