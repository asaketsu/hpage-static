一、核心问题：Agent 不是 compute-bound，是 context-bound

Production Agent 的推理成本结构完全不同于 chatbot：

工作负载 典型输入 token 典型输出 token 输入:输出比
Chatbot 500 300 1.7:1
RAG pipeline 8,000 400 20:1
ReAct Agent（早期） 20,000 200 100:1
ReAct Agent（后期） 80,000 300 267:1
Code review Agent 120,000 1,000 120:1

一个 10 步工具调用的 ReAct Agent，总输出约 500 token，但消耗 80 万输入 token——每轮都携带完整 system prompt、tool schemas 和对话历史。

在 100:1 以上的比率下，prefill 计算占 GPU 时间的 85-95%。生成步骤不是瓶颈，上下文处理才是。

二、系统级优化：KV Cache 命中率是第一成本杠杆

2.1 KV Cache Hit Rate 经济学

当推理服务器处理输入 token 时，为每个 token 在每层 transformer 计算 key-value attention 张量并存储到 KV cache。如果后续请求共享相同前缀，服务器可复用这些张量。

命中率的数学：cost_saving = hit_rate × prefill_fraction × total_gpu_time

KV 命中率 有效 prefill token TTFT 相对成本
0%（无缓存） 80,000 ~8s 基线
50% 40,000 ~4s ~50%
90% 8,000 ~800ms ~10%
95% 4,000 ~400ms ~5%

0% → 90% 的差距不是边际优化，是 $20,000/月 vs $2,000/月 GPU 账单的差距。

2.2 Prefix Caching 两巨头

特性 SGLang RadixAttention vLLM APC
默认开启 是 V1 / v0.18.0+
粒度 Token 级（radix tree） Block 级（16 token/block）
多轮处理 强（按对话分支累积状态） 良好
监控指标 sglang_cache_hit_rate num_prefix_cache_hit_tokens

2.3 最大化命中率的操作铁律

  1. System prompt 逐字符固定——一个空白字符差异使整个缓存前缀失效
  2. Tool 定义顺序固定——[search, write, read] 和 [read, search, write] 导致 cache miss
  3. 对话历史作为稳定前缀——不重新生成或总结早期轮次
  4. 检索文档位置固定——不同轮次间交错不同位置会碎片化前缀树

60%+ 前缀重叠的工作负载可稳定达到 75-95% 命中率。

2.4 VRAM 数学：从 32K 到 1M 上下文

KV cache VRAM 与上下文长度线性增长。Llama 3.1 70B（80 层，8 GQA heads，128 head_dim）：

kv_bytes = 2 × layers × kv_heads × head_dim × context_len × bytes_per_element

上下文 BF16 KV/用户 FP8 KV/用户 推荐 GPU
32K ~10.7 GB ~5.4 GB H100 80GB
128K ~42.9 GB ~21.5 GB H200 141GB
512K ~171 GB ~85.5 GB 2× B200 192GB
1M ~343 GB ~172 GB NVMe offload 或 sequence parallelism

FP8 KV 量化是 512K 以下最有效的单一杠杆——减半 KV 内存，质量影响极小。

2.5 NVMe KV 卸载

当 GPU HBM 满时，将冷 KV block 分层到 NVMe：
- LMCache 为 vLLM 添加 NVMe 持久化
- 冷 KV 从 NVMe 读取约 7 GB/s
- H100 上重算 128K 前缀约需 11 秒——NVMe 读取仍然更快

2.6 消除上下文浪费

平均 production Agent 上下文携带 40-70% 死重：
- 从未调用的工具 schema
- 与当前任务无关的历史轮次
- 检索相似度高但实际相关性低的 chunk

30% 输入 token 减少 ≈ 30% 成本和 TTFT 降低，无需改模型。

三、算法级压缩：ChunkKV 与 RocketKV

3.1 ACL 2026 综述分类体系

jjiantong/Awesome-KV-Cache-Optimization（ACL 2026 接收）建立了系统化的 KV Cache 优化分类：

大类 子类 代表方法
结构—表示与保留 KV Cache 压缩（KVCC） 量化、低秩近似、结构压缩、编解码压缩
KV Cache 保留管理（KVRM） 分配、复用、驱逐
空间—KV 编排 内存层级编排（MHO） SmartSSD KV offload
计算设备编排（CDO） PD 分离（Mooncake）
时间—执行与调度 KV 中心调度 KV-centric scheduling

3.2 ChunkKV（arXiv 2502.00299, NeurIPS 2025）⭐ 语义保留压缩

核心创新：将压缩单元从单个 token 提升到语义 chunk——保留完整语言结构和上下文完整性。

为什么 token 级压缩不够：现有方法逐 token 评估重要性，忽略了 token 间的语义关系，导致上下文碎片化和性能退化。

指标 数值
精度提升（vs SOTA） 最高 +8.7%
吞吐量提升 +26.5%（层间索引复用）
测试基准 LongBench, Needle-In-A-HayStack, GSM8K, JailbreakV

层间索引复用：利用 ChunkKV 中保留索引的更高跨层相似性，减少计算开销。

3.3 RocketKV（arXiv 2502.14051）⭐ 两阶段无训练压缩

两阶段策略：
1. 粗粒度永久驱逐：对输入序列 token 进行永久性 KV cache 驱逐
2. 细粒度稀疏注意力：利用 head 和 sequence 维度降低来近似 attention score 的混合稀疏 top-k 注意力

指标 数值
压缩比 最高 400×
端到端加速 最高 3.7×
Decode 峰值内存降低 最高 32.6%（A100）
精度损失 可忽略（多长上下文任务）

多轮场景变体持续优于其他方法，精度接近 oracle top-k attention。

四、架构级重构：2026 最新模型如何内建 KV 优化

4.1 Gemma 4：跨层 KV 共享

Gemma 4 E2B/E4B 采用跨层注意力（Cross-Layer Attention）——后续层重用早期层的 KV 张量而非每层独立计算。

模型 总层数 自算 KV 层 共享 KV 层 节省
E2B 35 15 20 ~50% KV cache，128K 上下文省 2.7GB
E4B 42 24 18 ~50% KV cache，128K 上下文省 6GB

规则：sliding-window 层共享前一个 sliding-window 层的 KV；full-attention 层共享前一个 full-attention 层的 KV。每层仍计算自己的 query projection。

4.2 DeepSeek V4：mHC + CSA/HCA ⭐ 旗舰级创新

DeepSeek V4-Pro 是 2026 年最大发布，两大架构创新：

mHC（Manifold-Constrained Hyper-Connections）

将 transformer block 内的单残差流替换为多个并行残差流 + 学习映射：

  • 基于原始 Hyper-Connections（Zhu et al., 2024），但添加双随机矩阵约束
  • 残差映射投影到非负、行列和为 1 的流形上（doubly stochastic）
  • 使残差混合行为更像「信息的稳定重分配」
  • DeepSeek V4 用 n=4 残差流，额外训练时间开销仅 6.7%
  • 指标达基线性能仅需约一半训练 token

CSA/HCA 压缩注意力

不同于 DeepSeek V2/V3 的 MLA（压缩 per-token KV 表示），CSA/HCA 沿序列维度压缩：

机制 压缩率 注意力方式 特点
CSA（Compressed Sparse Attention） 温和（m=4） DSA 式稀疏 top-k 选择 保留更多细节，稀疏选择
HCA（Heavily Compressed Attention） 激进（m'=128） 对重压缩条目密集注意力 条目少得多，可负担密集注意力

两者互补，DeepSeek V4 交替使用 CSA 和 HCA 层，都保留 128-token 局部滑动窗口分支用于近期未压缩 token。

质量-成本权衡：CSA/HCA 在序列条目数上做文章（而非 per-token 表示），以部分 token 级信息换取极低的长上下文成本。

六、实践启发与行动清单

6.1 对 Hermes Agent / Jetson 本地推理的启发

启发 具体应用
Context Engineering > Prompt Engineering Hermes Agent 每轮携带完整 system prompt + AGENTS.md + skills 列表，输入:输出比远超 100:1，context 层优化收益最大
Prefix Caching 可直接应用 如果未来自托管模型（Jetson/服务器），固定 system prompt 和 tool schema 顺序即可大幅降低 prefill 成本
ChunkKV 语义压缩思路 对 Agent 历史轮次的压缩不应逐 token，应按语义 chunk（一次工具调用的完整上下文为一个 chunk）
FP8 KV 量化适用 Jetson Jetson Orin 的 TensorRT 支持 FP8，对长上下文本地推理是关键优化
DeepSeek V4 CSA/HCA 趋势 未来开源模型可能内建序列维度压缩，无需外部 KV cache 压缩库

6.2 快速诊断清单

  1. 测量 Agent 的输入:输出 token 比——如果超过 10:1，context engineering 影响大于模型优化
  2. 启用 prefix caching——vLLM --enable-prefix-caching，SGLang 默认开启
  3. 审计 system prompt 一致性——任何空白差异使缓存失效
  4. 计算目标上下文窗口的 VRAM 需求——2 × layers × kv_heads × head_dim × context_len × bytes
  5. 对 >128K 上下文配置 NVMe KV 卸载——LMCache + vLLM
  6. 设置 KV 命中率监控——目标 70%+（缓存预热后）
