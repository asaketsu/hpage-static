  • vLLM v0.15.1（2026.02）：PyTorch 2.10、RTX Blackwell (SM120) 支持、H200 优化

1.2 SGLang 的核心技术：RadixAttention

SGLang 源自 UC Berkeley Sky Computing Lab，核心创新是 RadixAttention——用基数树（Radix Tree）结构管理 KV Cache 复用。

在多轮对话中，历史轮次与新轮次共享 KV Cache。vLLM 用 prefix caching 处理，但 SGLang 的 RadixAttention 能跨复杂对话模式更高效地管理 Cache 复用。

真实性能影响（A100-80GB, Llama 3.1 8B）：

  • 单请求延迟：vLLM 45ms vs SGLang 48ms（vLLM 略优 +6%）
  • 多轮对话 5 轮：vLLM 180ms vs SGLang 95ms（SGLang +89%）
  • 批量吞吐 32 并发：vLLM 1847 tok/s vs SGLang 2103 tok/s（SGLang +14%）
  • Agent 工作流 10 次调用：vLLM 420ms vs SGLang 185ms（SGLang +127%）

核心发现：SGLang 在单请求延迟上不占优势，但在多轮对话和 Agent 工作流中优势巨大。Agent 场景每次工具调用共享大量 prompt 前缀，RadixAttention 的 Cache 管理在此场景优势最大化。

1.3 TensorRT-LLM：NVIDIA 专用优化

NVIDIA 官方 LLM 推理方案，将模型编译为优化的 TensorRT 引擎，通过 kernel fusion、内存布局优化和硬件特定调优，比 vLLM 快 20-40%。

真实性能（H100-80GB, Llama 3.1 70B）：

  • 吞吐 vLLM FP16: 2847 tok/s → TRT-LLM FP16: 3892 → TRT-LLM FP8: 6234 tok/s
  • 延迟 p50: vLLM 85ms → TRT-LLM FP8: 41ms
  • 显存：vLLM 140GB → TRT-LLM FP8: 78GB

隐性成本：工程量大（熟悉需 2-4 周）、引擎构建时间长（30-60 分钟/配置）、每次 batch_size/seq_len/TP 变化需重建引擎、版本与 CUDA/TensorRT 强耦合。

1.4 H200 新硬件性能

H200 提供 4.8TB/s 内存带宽（H100 的 1.4 倍），HBM3e 对内存带宽受限的 LLM 推理意义重大：

  • TensorRT-LLM (Llama2-13B): 11,819 tok/s（比 H100 +90%）
  • vLLM 估算: ~18,000 tok/s（+50%）
  • SGLang 估算: ~24,000 tok/s（+48%）

1.5 架构收敛趋势

Medium @ant-oss 的分析指出：vLLM 和 SGLang 在特性上正在收敛。两者现在都支持：

  • Continuous Batching（连续批处理）
  • PagedAttention（分页注意力）
  • RadixAttention（基数树前缀缓存）
  • Chunked Prefill（分块预填充）
  • Speculative Decoding（推测解码）
  • Disaggregated Serving（分离式服务）
  • CUDA Graphs
  • FlashInfer / FlashAttention / DeepGEMM 算子库
  • 量化（FP4/FP8/INT4/AWQ/GPTQ）
  • 多种并行策略（TP/PP/EP/DP）
  • 多 LoRA 批处理

核心论点：模型架构显示出收敛迹象，主流推理引擎在特性、算法和算子栈上越来越相似。领导者的竞争从"功能有无"转向"工程质量和调优深度"。

1.6 推测解码的下一代

vLLM 2026 推出三种并行 Draft 算法，超越传统的顺序 token 生成：

  • P-EAGLE：并行 EAGLE
  • DFlash：动态 Flash
  • DSpark：动态 Spark

SGLang 方面，2026.06 发布下一代推测解码 DFlash 和 Spec V2，并在 GB300 NVL72 上实现 25 倍推理性能。

二、查询拓展

2.1 PagedAttention 原理回顾

vLLM 的 PagedAttention（SOSP 2023）借鉴操作系统的虚拟内存分页机制。KV Cache 不连续存储，而是按固定大小的"页"（block）分配。解决了三个问题：
- 内部碎片（internal fragmentation）：最大可省 60% 显存
- 显式共享：相同 prompt 前缀可被多个请求共享
- 动态分配：请求可按需增长，不需预分配最大长度

2.2 RadixAttention 与 PagedAttention 的区别

RadixAttention 是 PagedAttention 的超集思路——不仅做分页管理，还用基数树结构自动发现和复用任意公共前缀（不限于完整 prefix）。在 Agent 工作流中，不同请求可能共享中间片段（如相同的 system prompt + 不同工具调用历史），RadixAttention 能自动识别这些共享。

2.3 Prefill-Decode 分离架构

2026 年的重要趋势是 Prefill 和 Decode 的物理分离（Disaggregated Serving）：
- Prefill（首 token 计算）是 compute-bound，需要高 FLOPS
- Decode（逐 token 生成）是 memory-bound，需要高带宽

将两者分离到不同 GPU 组，可让每组优化为最适合的计算特性。vLLM 在 AMD MI300X 上用 MORI-IO 实现单节点分离，稳定 ITL（Inter-Token Latency）。

2.4 TGI 维护模式的影响

HuggingFace 的 TGI 进入维护模式是重要信号——市场正在整合。TGI 曾是企业部署的首选（Docker 友好、HuggingFace 生态），但现在新项目应在 SGLang 和 vLLM 之间选择。TGI 的退出反映了推理引擎市场的"赢家通吃"趋势。

四、趋势判断

趋势1：SGLang 成为 Agentic 工作负载事实标准

40 万+ GPU 全球部署量、Agent 场景 127% 性能优势、PyTorch 生态正式加入——SGLang 在 Agent 时代的定位类似于 vLLM 在 Chat 时代的定位。依据：Agent 工作流天然有多轮+前缀共享特征，正是 RadixAttention 的最优场景。

趋势2：推理引擎特性趋同，竞争转向工程质量

vLLM 和 SGLang 在功能列表上已高度重叠。未来竞争不再是"有没有某特性"，而是"谁的实现更稳定、调度器更高效、边缘 case 处理更好"。依据：两者共享相同算子栈（FlashInfer/FlashAttention/DeepGEMM）。

趋势3：Prefill-Decode 分离成为生产标配

将计算密集的 Prefill 和带宽密集的 Decode 物理分离到不同 GPU，是 2026 年最重要的架构创新之一。vLLM 和 SGLang 都已支持。依据：MI300X 上的实测显示 ITL 稳定性显著改善，goodput 提升。

趋势4：推理成本继续年降 10 倍

H200/B200 硬件 + FP8/FP4 量化 + 推测解码 + 分离架构的叠加效应，使 2026 推理成本继续大幅下降。GPT-4 等价推理从 $20/M 降至 $0.40/M（-98%）。依据：硬件代际提升（2x）+ 量化（2x）+ 架构优化（2-3x）的乘积效应。

五、关联分析

5.1 与笔记《Agent在线KV-Cache压缩-代理查询选型实证》的关联

08-04 笔记聚焦 KV-Cache 压缩和代理查询选型。本篇从引擎层补充了 RadixAttention 如何自动管理 KV Cache 复用——SGLang 的基数树结构本质上是一种自动化的 KV-Cache 压缩和共享机制。Agent 场景的 KV-Cache 压缩需求，部分可通过引擎选择（SGLang）而非应用层压缩来解决。

5.2 与笔记《本地CUA推理时扩展失效模式》的关联

08-02 笔记分析本地推理时扩展的失效模式。本篇补充了引擎层面的根因——不同引擎在调度器效率、并发处理上的差异，直接影响推理时扩展的稳定性。SGLang 的零开销 CPU 调度器是其在高并发下稳定性的关键。

5.3 与 Hermes Jetson 部署场景的关联

Hermes 运行在 Jetson Orin Nano（ARM CUDA）。推理引擎选型受限：
- vLLM：Jetson 支持不成熟，CUDA wheel 适配是主要障碍
- SGLang：同样面向数据中心 GPU，Jetson 部署未见成熟案例
- llama.cpp：Jetson 最佳选择，GGUF 量化 + ARM CUDA 支持
- Ollama：基于 llama.cpp，封装友好，已有 jetson-voice-assistant 项目验证

对于 Jetson 场景，推理引擎选型结论不变：llama.cpp/Ollama 仍是首选。SGLang/vLLM 的优势在多 GPU 数据中心场景。
