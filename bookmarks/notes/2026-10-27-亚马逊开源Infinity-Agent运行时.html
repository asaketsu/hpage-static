归纳总结

一句话：Infinity 把"等待中的 Agent"从活进程降级为纯数据（约 103 KB 对话历史），用执行切片 + 消息驱动调度实现了 Agent 的 async 化，官方口号是 "Infinity does for agents what async did for threads"（Infinity 之于 Agent，如同 async 之于线程）。

维度 要点
是什么 Rust 写的开源 Agent 运行时（Apache 2.0），Hydro 项目出品，AWS 2026-10 开源博客专题介绍
核心机制 Execution Slice（执行切片）：读历史→一次 LLM 调用→存记录→发起工具调用→切片结束释放资源→事件到达再起新切片恢复
关键数字 空闲 Agent ≈ 103 KB（20 轮工具调用后）；8GB 树莓派 5 = 7.5 万个等待 Agent
并发模型 Actor 式：每 Agent 独立 mailbox，share nothing，in-order 消息；spawn_thread 派生子 Agent 并行
Serverless Lambda 上每条 SQS FIFO 消息触发一个切片，load state→completion→dispatch→exit；等待三天 CI 的 Agent 成本为零
定位澄清 解决的是运行时层（调度/状态/高并发等待），不是应用框架层（LangChain/LangGraph）；不替代关系，是分层关系

文章最锋利的一个反问："Agent 等待的时候，为什么一定要让它继续留在内存里？"——传统程序围绕持续执行流程组织，而 Agent 的工作本质是事件驱动的（等构建、等审批、等 webhook、等人回复），生命周期模型却还停留在"常驻进程"范式，这是范式错配。

内容整理：核心设计四支柱 + 核验表

1. 执行切片（Execution Slice）—— 生命周期重构

传统：启动→LLM→工具→阻塞等待→LLM→结束（全程占资源）
Infinity：执行→保存状态→**释放资源**→等事件→恢复状态→继续

  • 等待 20 分钟测试时：记录工具调用→发起任务→当前切片直接结束
  • 测试完成→结果进消息队列→新切片加载历史→LLM 继续分析
  • 与 Rust async/await 的区别：async 任务仍由运行时管理任务状态；Infinity 让等待中的 Agent 只剩持久化数据，可在另一个进程中恢复——不是把 Agent 改成异步函数，是运行时层重新设计生命周期
  • 关键表述："an idle agent is pure data: between turns, an agent is just its conversation history, with no task, no stack, and no open connection"（空闲 Agent 是纯数据：轮次之间它只是对话历史，没有任务、没有栈、没有打开的连接）

2. Actor 式消息队列 —— 并发正确性

  • 每 Agent（线程）一个 mailbox，线程间不共享可变状态，只发消息
  • 同线程消息按序处理（防并发写坏对话历史），不同线程并行
  • 主 Agent 派生子 Agent 后不等它们，子 Agent 完成后发消息回来
  • GitHub PR 事件类外部输入：100 个并发事件可为每个事件开独立子线程，不挤同一份历史

3. Serverless 原生 —— Scale to Zero 是默认态

AWS 参考部署栈（CDK 几行代码拉起）：

组件 职责
AWS Lambda 执行单个切片（load→completion→dispatch→exit）
Amazon SQS FIFO 传消息 + 保同线程顺序
Aurora DSQL 存对话历史
DynamoDB 消息去重状态
EventBridge Scheduler 定时唤醒

等待三天 CI 的 Agent 成本恰好为零（"costs exactly nothing until something happens"）。注意 Serverless ≠ 免费：LLM 调用/DB 读写/消息传递照常花钱，省的是等待期的常驻计算资源。

4. RAP（Reactive Agent Protocol）—— 工具层异步化 ⭐公众号未提

  • 异步工具网络协议：runtime 用一次 POST + callback URL 调用工具，服务器结果就绪时再回调，不保持连接
  • 工具服务器像普通 Web 服务一样水平扩展，还能服务当前完全没有进程的 hibernating Agent
  • 开放规范，任何运行时/工具服务器可实现
  • MCP 开箱兼容：stdio/HTTP MCP server 进程内连接，现有 MCP server 通过兼容层零改动运行——MCP 生态直接继承

趋势判断

  1. Agent 技术栈正在分层成熟：应用框架层（LangChain/LangGraph 编排工作流）→ 运行时层（Infinity 调度/暂停/恢复）→ 协议层（MCP/RAP 工具接入）。类比 Web 史：CGI → WSGI/ASGI → async runtime（uvicorn/gunicorn），每层独立成层后出现专门优化。运行时层是 2026-2027 的新战场。
  2. "Agent 不为等待付费"会成为基础设施默认承诺，就像 async 之于高并发 Web 是默认而非特性。常驻进程模型将在两年内被视为 Agent 部署的反模式。
  3. 工具协议的下一步是异步化：MCP 定义了工具的统一接口（同步语义），RAP 定义了工具的异步语义（callback）。两者互补而非竞争，MCP 兼容层是聪明的一步——先吃生态再改范式。
  4. 竞争维度迁移：模型效果 → 工具数量 → 运行成本/并发规模/故障恢复（文章结论，官网 "agents stop paying to wait" 呼应）。对 Agent 平台选型的启示：评估框架时除了功能清单，要看等待态资源模型。

拓展应用推荐

对我们系统的三个可执行迁移（不引入框架，只偷思想）：

  1. P0 · 训练完训回调替代 watchdog 轮询：AutoDL 训练机加完训 webhook 脚本（完训时 curl Hermes gateway API 触发收尾流程），替代"cron 每 N 分钟 grep 日志"的轮询模式——每条训练线省 24h×轮询频率次 LLM 调用。这就是 RAP 思想的 20 行 Python 版本。
  2. P1 · 长等待任务显式检查点化：delegate_task 长任务（GPU 迭代训练类）在等待窗口落盘"可恢复快照"（当前配置+进度+下一步），配合 harness-checkpoint skill，把"会话级恢复"细化为"轮次级恢复"。
  3. P2 · 跟踪 RAP 规范演进：若 MCP 官方吸收异步语义，我们浏览器工具/SSH 工具的调用模式要预留 callback 形态（browser_exec 已是会话持久型，方向对了）。

一句话收获：Agent 的成本大头不在推理而在等待；把等待态做成纯数据、用事件唤醒代替常驻轮询，是 Agent 基础设施从"能用"到"可规模化的分水岭。
