一句话定义

RW Research Skill 新增 rw-journal-submission 投稿模块，Agent 能自动读期刊要求→整理投稿包→检查文件→进入投稿系统填写→上传→复核报错——但人承担所有学术责任，Agent 只做结构化搬文件和字段核对，最终 Submit 由人按下。

内容整理（完整保留原帖内容）

背景

作者第不知道多少次做综述投稿。定下期刊后，后面的事全交给 RW Research Skill。

RW Research Skill 是一套科研工作流，全网几十万人看过介绍。它把研究问题、文献、写作和投稿拆开，给 Agent 规定材料、步骤和停止条件。

工作流程

  1. 先读期刊的投稿要求
  2. 再读本地的论文、标题页、图表和其他投稿材料
  3. 缺什么文件、哪个字段需要作者确认、哪些东西应单独上传——一项一项整理
  4. Agent 进入已登录的投稿系统，按确认过的内容填写、上传和保存
  5. 每次保存后重新读取页面，看系统还报错不

说白了，就是把主文、图表、作者资料和声明整理成一个可以提交的投稿包。

投稿前拦截错误的实例

这本期刊要求 manuscript 里面不能嵌入 Table 或 Figure，表和图需单独上传。

作者主文里当时还有表格和图片。如果照原文件继续走，这个错误会跟着文件进入投稿包。

RW Research Skill 的处理：
1. 读期刊要求 + 检查本地 DOCX
2. 发现主文仍嵌着表格和图片 → 停下上传，先处理文件
3. 文件顺序原为 Figure 1、Table 2、Figure 3 → 期刊要求图表分别编号 → 整理成 Figure 1、Table 1、Figure 2
4. 核对正文引用、单独文件和上传顺序
5. 主文改完 → Agent 重新上传文件 → 保存 → 再读一遍投稿页面
6. 系统错误消失 → 才告诉作者可以进入最后一步

不同的期刊对投稿的要求各不相同，人工投稿的时间，很多就花在这种事上。

这次更新加了什么

新增 rw-journal-submission 投稿模块：

  1. 建立 Submission Packet：把主文、标题页、图表、补充材料、作者资料、声明和门户步骤放在一起管理
  2. 期刊要求图表单独上传时：先检查主文里还有没有 Word 表格、绘图或嵌入媒体 → 核对 Figure 和 Table 的编号、正文引用、独立文件和上传顺序 → 预检不过，不进入上传
  3. 进入投稿系统后：
  4. Agent 先读当前页面和报错
  5. 只填写作者确认过的字段
  6. 保存后重新读取页面
  7. 遇到退回 → 继续处理原来的草稿 → 记录退回原因 → 修改对应文件 → 再上传和复核
  8. 不会另建一篇投稿，把记录弄乱

科研工作可以从研究问题一路走到投稿前审核，中间的文件和状态不会在不同对话里丢掉。

人、Skill 和 Agent 分别做什么（核心责任分离设计）

角色 职责
人 做研究、承担所有责任。投哪本期刊、论文写了什么、作者顺序、通讯作者、贡献/资金/伦理/利益冲突声明——都由作者和团队确认。最终的 Submit 也由人完成
Skill 负责规则。规定投稿前查哪些期刊要求、文件怎么组织、哪些字段必须等作者确认、什么情况下停止。区分四种状态：材料齐了 / 门户草稿已保存 / 可以提交 / 已经提交（不能混在一起）
Agent 实际干活。读取本地文件和网页、修改文档、上传材料、保存草稿、把页面读回来。遇到验证码、支付、权限变化或最终提交，停下来交给人

自动投稿会不会带来学术不端？

作者明确回答了这个问题：

这次没有让 AI 替我写一篇综述。论文是我的，研究内容是我的，作者信息也由我确认。

AI 处理的是这些内容的结构化。它把作者已经提供的信息放进对应字段，按照期刊要求整理文件，再检查本地材料和投稿系统是否一致。它没有生成新的数据，也没有增加一个不存在的作者。贡献、伦理、利益冲突和 AI 使用声明仍然要由作者确认。

这次自动投稿没有新增研究内容，也没有替作者作出学术声明。它减少的是人工搬文件、核对字段和重复检查的时间。论文真实性、数据、作者信息和声明仍然由人负责。投稿流程自动化以后，这些责任没有转给 Agent。

我最后做的事，是看完它给出的审核结果，自己按下 Submit。

归纳总结

这篇文章展示了 Agent 自动化科研投稿的完整责任分离设计。最有价值的不是自动化本身，而是清晰的三方边界划分：

  • 人 = 决策者 + 责任承担者（投哪个期刊、作者顺序、最终 Submit）
  • Skill = 规则层（材料标准、停止条件、四状态机）
  • Agent = 执行者（读文件/网页、填表/上传、验证报错）

关键安全设计：遇到验证码、支付、权限变化或最终提交，Agent 停下来交给人。预检不通过不上传。遇到退回继续处理原草稿不另建。四状态严格分离不混。

学术伦理方面：AI 做的是结构化搬文件和字段核对，不生成新数据、不增加作者、不替人作学术声明——责任完全留在人身上。

结合最新研究与技术变化

1. 与 Harness 解剖学笔记的交叉验证

RW Research Skill 的投稿模块完美实践了 Mastra 文章中 "工具暂停等人" 的设计——Agent 遇到验证码/支付/最终提交时自动暂停，交给人做。这正是 Harness 的 askUserTool + submitPlan 机制在科研场景的应用。

四状态机（材料齐了/门户草稿已保存/可以提交/已经提交）与 Mastra 的 Plan→Build 模式切换类似——状态不可逆推进，每一步有明确的准入和准出条件。

2. 与自进化/验证瓶颈笔记的关联

"每次保存后重新读取页面，看系统还报错不" = 验证闭环。Agent 不是提交完就结束，而是保存→读回→检查→确认无错才继续。这正是自进化笔记中"验证是最终瓶颈"的具体实践——Agent 用投稿系统的报错作为验证器。

3. 与 LLM 微调成本工程笔记的关联

RW Research Skill 走的是"Skill（规则提示）而非微调"路线。与 SkillOpt 的理念一致——用结构化规则指导 Agent 行为，不动模型权重。Skill 定义材料标准、步骤和停止条件，让通用 LLM 精确执行窄领域任务。

4. 2026 Agent 产品的责任分离范式

这个案例代表了 2026 年 Agent 产品设计的一个趋势：AI 做结构化操作，人做决策和承担责任。不是"AI 全自动替你做"，而是"AI 帮你搬文件+核对字段，你确认+签字"。这种设计在医疗、法律、金融等高风险领域尤其重要。

最值得借鉴的 3 个设计

  1. 保存→读回→验证→继续 的闭环验证模式——适用于所有"写后验证"场景（patch 后 lint、push 后 CI 检查、deploy 后健康检查）
  2. 预检门控——关键操作前先验证所有前置条件，不满足则停止。适用于 Hermes 的"不可逆操作"防护
  3. 四状态机——比简单 todo 更适合多阶段复杂工作流，每个状态有明确的准入条件

趋势判断

  • Agent 产品设计的责任分离范式成型：人做决策+承担责任 / Skill 做规则 / Agent 做执行——这三层分离将成为高风险领域 Agent 产品的标准设计
  • 科研全流程自动化成为可能：从研究问题→文献综述→实验设计→论文写作→投稿审核，全链路 Agent 辅助。投稿是最后一块拼图
  • Agent 操作 Web 界面（Browser Automation）成为刚需：投稿系统没有 API，Agent 必须通过浏览器自动化操作——这需要可靠的 Web 交互能力
  • 预检门控 + 读回验证 = 可信赖 Agent：不是盲目前进，而是每步验证——这是从"demo Agent"到"生产 Agent"的关键差异
  • 学术伦理边界清晰：AI 做结构化操作不等于学术不端。关键在于不生成新数据、不增加作者、不替人声明——这个边界正在被广泛接受
  • Skill 模块化组合：rw-research-router → rw-academic-writing → rw-journal-submission，模块化衔接形成端到端工作流——Skill 的组合编排正在标准化

关联分析

  • 与 Hermes harness-architecture Skill 的关联：四状态机 + 预检门控 + 读回验证是 Harness "质量门禁机械化"支柱的具体实践
  • 与 deterministic-guardrails Skill 的关联：RW 的停止条件（验证码/支付/最终提交）正是确定性护栏的体现
  • 与 Hermes 的 doc-qa / docx / pdf Skills 的关联：RW 投稿模块大量操作 DOCX 文件（检查嵌入表格/图片/编号），与用户的文档处理 Skills 对应
  • 与 agent-security-governance Skill 的关联：人/Skill/Agent 三方责任分离是安全治理框架的案例参考
