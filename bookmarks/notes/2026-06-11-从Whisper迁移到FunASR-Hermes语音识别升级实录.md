# 从 Whisper 迁移到 FunASR：Hermes 语音识别升级实录

> 来源：微信公众号 | 作者：jc
> 核心结论：FunASR SenseVoiceSmall 最大的惊喜不仅在于中文转写准确率的提升，更在于自带的**情绪识别**能力，使得 Agent 能够直接感知用户的情感状态并做出共情响应。

---

## 一、背景：为什么本地 STT 是必选项？

在将 AI Agent（如 Hermes）集成到飞书或企业微信等 IM 平台时，会遇到一个平台级 API 限制：

- **语音消息 API 限制**：当用户发送语音消息时，平台推送给 Webhook 的只有音频媒体文件（`media_id`/`media`），不包含文字（飞书客户端的“语音转文字”仅是客户端本地呈现，API 侧不提供）。
- 鉴于此，Agent 若想支持语音交互，**本地部署 STT（语音转文字）引擎是刚需**而非可选项。

### 1.1 原有 Whisper.cpp 方案的痛点

在升级前，系统采用的是 `whisper.cpp` 方案，但在 370 余条真实语音运行中暴露出以下硬伤：

- **口语识别不稳定**：日常口语中的语气词容易被吞或者发生奇特变换（例如“我觉得吧”常被转写为“我觉得八”）。
- **中英混合能力差**：遇到开发场景的英文术语（或代码缩写）时，强行音译为发音相近的奇怪中文。
- **长语音易截断**：长达 30 秒以上的段落有时会在末尾出现截断，导致语义丢失。

## 二、选型：为什么是 FunASR SenseVoiceSmall？

**FunASR** 是阿里达摩院的一款开源语音识别框架，可便捷地切换和集成不同的声学模型。

### 2.1 ⚠️ 核心限制说明
官网主推的 `SenseVoiceLarge` 其指标在榜单上最强，但**达摩院并未开源**其权重。目前开源且能在本地部署的仅有 **`SenseVoiceSmall`**（参数量为 234M）。

### 2.2 SenseVoiceSmall 的核心优势

- **中文口语高匹配**：其预训练数据大量来源于会议、客服、短视频等高口语化场景，采用非自回归（Non-Autoregressive）结构，10 秒音频处理时间在毫秒级别。
- **轻量且极速**：参数量仅 234M，对 CPU 非常友好。在 GPU 上拥有 170x 实时速度，在 CPU 上有 17x 实时速度（在 GPU 推理性能上比 Whisper-large-v3 快约 13 倍）。
- **多维度感知（关键惊喜）**：同时支持**语种识别（LID）**、**富文本情感识别（7 种情绪：高兴/悲伤/愤怒/中性/恐惧/厌恶/惊讶）**以及**音频事件检测（AED）**。
- **易集成**：FunASR 统一了 `AutoModel` 接口，模型更换只需修改一行 `model` 参数。

## 三、迁移实操与避坑指南

### 3.1 兼容的管道化设计（CLI Wrapper）

工程上为了将影响降到最低，不要去改动 Agent 的核心框架代码。我们的策略是写一个命令行兼容的包装脚本（CLI CLI-Wrapper），让其输入、输出规范与旧版 `whisper` 命令行保持一致。

```bash
# 包装脚本核心逻辑伪代码
# loading FunASR AutoModel -> Specify SenseVoiceSmall -> generate -> format outputs.
```

在 Agent 的配置文件中，只需将相应的可执行路径替换为该 Python Wrapper 脚本即可。

### 3.2 🔴 STT 热更新配置事故

在 5 月 30 日做 STT 配置切换的最后一步时，因在 Agent 进程重启阶段采用了不正确的 supervisor/systemd 信号，导致 Agent 进程直接崩溃掉线。

> **工程教训**：Agent 执行涉及自身的系统配置、重启变更等危险操作时，必须触发二次确认，或至少先进行配置项的 Dry-run 预检。

### 3.3 说话人/情感检测多模态下载超时

FunASR 默认包含完整的富文本处理链路，需要加载额外的说话人追踪和情感识别模型：

| 模型组件 | 大小 & 特点 | 下载避坑说明 |
|---------|-----------|-------------|
| cam++ | 说话人分离模型 | 较小，快速完成下载 |
| emotion2vec+ | 情感模型 (~1GB) | 国内源在下载到 270MB 时极易超时（默认有 300s 限制）。建议检测到超时后通过 CLI/Browser **手动多线程拉取** 到系统本地缓存目录，再由 Agent 移入正确目录。 |

> **依赖提醒**：`whisper.cpp` 几乎零外部依赖；而 `FunASR` 依赖繁重的 Python、PyTorch、torchaudio 等生态，**必须采用虚拟环境（Venv/Conda）隔离部署**，以防污染宿主机环境。

## 四、升级效果：371 条真实运行表现

以下是升级后的日志记录：
`Transcribed audio_xxx.ogg via local STT command (SenseVoiceSmall, 289 chars)`

| 维度 | Whisper.cpp 表现 | FunASR SenseVoiceSmall 表现 |
|------|-----------------|-----------------------------|
| 语气词识别 | 易吞、错别字多 | 自然记录，如“吧”、“哈”等字纠错率明显上升 |
| 中英夹杂 | 术语强行音译为奇怪中文 | 准确还原英文缩写 |
| 长语音处理 | 超过 30 秒易在末尾截断 | 60 秒以上长音频平稳转写无截断 |
| 情感输入 | ❌ 无此能力 | 🌟 **转写结果附带 [angry], [happy] 等情绪标签。Agent 据此在 Prompt 中自动调整共情语气。** |

**情感交互实例：**
当向 Agent 发送明显带着不耐烦语气的飞书语音时，SenseVoice 识别出了 `[angry]`，Agent 捕捉到该标签后直接用“我能理解你的焦虑和愤怒，这件事情我马上排查”来进行共情。交互深度从“听文字”跨越到了“听语气”。

## 五、本地 vs 云端 STT 方案权衡

在当前阶段，为什么坚持在本地宿主机（如 Mac mini 边缘主机）而不是云端（如 OpenAI Whisper API）跑语音识别？

1. **隐私安全 (Security)**：语音聊天中常包含各种未脱敏的口述隐私、技术架构、API-key、地址，发到云端意味着数据越界，本地部署是最高级别的隐私保护。
2. **零网络延迟 (Latency)**：本地 GPU/CPU 推理无需网络往返，在 10s 音频上做推理能做到低于 0.3 秒的毫秒级反应。
3. **边际成本 (Cost)**：370 条日常语音如果走 OpenAI Whisper 虽便宜，但随着大批自动化 Cron 定期推送和持续累加，本地计算资源的边际成本为零，更加经济。

## 六、行动清单总结 (Actionable Takeaway)

- 保持接口透明，通过 CLI Wrapper 实现无痛迁移。
- 对 Python 生态庞大的依赖进行 `python -m venv` 虚拟环境隔离。
- 情感模型大文件易下载超时，优先在本地环境中多线程下载完成。
- 对 Agent 变更关键配置的逻辑加入只读预检或人类确认阀门，防止断头崩溃。
