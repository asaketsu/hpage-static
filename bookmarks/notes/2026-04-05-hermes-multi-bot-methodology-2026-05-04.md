　　# Hermes 多 Bot 方法论：理念比步骤重要

**来源**：极客BIM设计工坊（微信公众号） | 2026年5月

**核心观点**：多 Bot 的核心不是"怎么建"，而是"为什么建"和"怎么分"。理解 Profile 隔离机制，掌握角色设计思路，比照着教程敲命令重要得多。

---

## 为什么拆

一个 Bot 干所有事会出三个问题：

**模型冲突**　日常聊天用便宜模型够了，写代码要用贵的，算命要用中文好的。一个 Bot 只能绑一个模型。

**人设分裂**　SOUL.md 定义了 Bot 的人格。让它既当严肃的代码工程师，又当深夜聊天伙伴，会精神分裂。

**记忆污染**　所有对话共享同一个记忆空间。昨天聊的代码逻辑，今天可能用来回答情感问题。

解决方案：拆。

## 核心机制：Profile 隔离

Hermes 的 Profile 机制是真正的底层隔离，不是"假装多实例"。每个 Profile 是完全独立的 Agent 本体：独立的 config.yaml、.env、SOUL.md、gateway 进程、日志和记忆空间。

理解：Profile 不是"切换角色"，而是"雇佣不同的人"。每个人有自己的办公桌、工具、笔记本。

## 三个设计原则

**原则一：按需求分，不按功能分**　不要建"搜索Bot"、"写作Bot"、"代码Bot"。要建"日常管家"、"专业Coder"、"深夜伙伴"。前者是工具思维，后者是角色思维。

**原则二：模型匹配角色**　不同角色需要不同模型。日常管家用便宜模型，专业Coder用强模型，玄学军师用中文好的模型。模型不是越贵越好，是越合适越好。

**原则三：SOUL.md 是灵魂**　写人物小传，不写功能清单。"你是资深软件工程师"比"你能写代码"强十倍。好的 SOUL.md 让 Bot 有灵魂，差的 SOUL.md 让 Bot 只是工具。

## SOUL.md 写法要点

写人物小传，不写功能清单。定义语气和边界。给专长，也给限制。用第一人称或第二人称增加代入感。

## Skill 化

把创建 Bot 的流程做成 Skill 的好处：标准化（不遗漏步骤）、可复用（换机器知识还在）、可分享（经验沉淀成可执行文档）。

---

## ubot 吸收评估

**借鉴等级**：②有价值→记录

我们 ubot+jbot 是双机协作而非单机多 Profile，场景不完全一样，但以下思路可借鉴：

- SOUL.md 写法：人物小传 > 功能清单，可优化我们的 SOUL
- 角色思维 vs 工具思维：分配任务时按角色而非按功能
- Skill 化流程：如果未来需要创建新 Profile，可以标准化

与我们的差异：我们走的是双机共享 /uclaw 的路线，通过经验池+心跳实现协作，而非单机多 Profile 隔离。
