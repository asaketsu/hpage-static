一、核心发现：推理优化的三层栈模型

2026 年 LLM 推理优化已经形成了清晰的三层栈架构，每层解决不同瓶颈，可叠加使用，综合降低 80%+ 成本：

层级 优化目标 典型收益 实施成本
模型层 每参数计算成本 2-4x 内存，~50% 成本 低（工具链成熟）
系统层 GPU 利用率 3-10x 吞吐 低（引擎配置）
应用层 输入 token 数 50-70% token 减少 低（API 调用）

关键洞察：三层互相独立、可叠加。一个量化模型 + 连续批处理 + 上下文压缩 = 比未优化基线降低约 80% 每任务成本。

二、TurboQuant：KV 缓存极限压缩实测

2.1 背景：KV 缓存为何是瓶颈

以 Qwen3.5-4B 为例（262K 上下文）：
- FP16 KV 缓存 = 8 GiB
- 模型权重 = ~8 GiB
- 缓存几乎与模型等大！

KV 缓存随上下文线性增长，在消费级硬件上是长上下文推理的主导内存开销。

2.2 TurboQuant 核心算法

Google Research + NYU (ICLR 2026)：
- 两阶段压缩：旋转 + 查找表
- 无需校准数据（data-oblivious）
- 每坐标压缩到 3-4 bits
- 在线逐 token 处理（适合自回归解码）
- 从标准 16-bit 压缩到约 3-bit = 最高 5x 压缩

2.3 vLLM 实测结论（4 模型 × 5 基准）

vLLM 团队用 Llama-3.3-70B、Qwen3-30B-A3B（Instruct/Thinking）、MiniMax-M2.7 做了系统评测：

方案 KV 容量倍数 长上下文检索 推理任务 吞吐影响 推荐场景
FP8 2x ✅ 几乎无损 ✅ 98%+ 恢复 ⚡ 无损甚至更快 大多数工作负载的最佳默认
TQ k8v4 2.4x ✅ 竞争力强 ✅ 98%+ 恢复 📉 一致负影响 不推荐（优势太小）
TQ 4bit-nc 3.4x ✅ 轻微下降 ⚠️ 1-4点下降 📉 中等下降 内存受限部署
TQ k3v4-nc ~4x ⚠️ 明显下降 ❌ 严重下降(-20点) 📉 大幅下降 不推荐
TQ 3bit-nc ~5x ❌ 长上下文崩溃 ❌ 严重下降(-20点) 📉 大幅下降 不推荐

2.4 关键发现

  1. FP8 是最佳默认选择：2x 容量，吞吐无损，精度几乎无损，在突发负载下 TTFT 表现优异
  2. TQ 4bit-nc 有价值：在内存受限场景下（如边缘设备/消费级 GPU），用吞吐换容量
  3. 3-bit 方案不成熟：推理任务（AIME25、LiveCodeBench）精度暴跌 20 点
  4. 量化误差随序列长度累积：128K-256K 上下文下，低 bit 量化退化加剧

2.5 与 FP8 的关键差异

维度 FP8 TurboQuant
存储压缩 ✅ KV 存储压到 8-bit ✅ KV 存储压到 3-4 bit
注意力计算 ✅ FP8 Tensor Core 原生加速 ❌ 反量化回 BF16 计算
硬件利用 ⚡ 高效 📉 反量化开销
校准需求 不需要 不需要
精度损失 几乎无损 与 bit 数正相关

结论：TurboQuant 只压缩存储，不加速计算。FP8 同时压缩存储和加速计算——这就是 FP8 在多数场景下优于 TurboQuant 的根本原因。

三、系统层优化全景

3.1 连续批处理 (Continuous Batching)

  • 静态批处理：等整批完成后才接收新请求 → 短请求空等长请求
  • 连续批处理：动态插入新请求，GPU 保持饱和
  • 吞吐提升 3-10x，Anyscale 实测生产环境 23x 提升

3.2 PagedAttention

  • KV 缓存预分配导致 90% GPU 内存浪费
  • PagedAttention (vLLM) 按需分配小页面 → 内存浪费降低 90% → 吞吐提升最高 24x

3.3 推测解码 (Speculative Decoding)

方面 数据
典型加速 2-3x（通用查询，EAGLE3）
优化极限 5-5.5x（领域/硬件定制）
质量影响 零（输出与自回归解码数学等价）
关键瓶颈 Draft 模型延迟（非精度）决定端到端速度

3.4 2026 推理引擎横评（H100）

引擎 吞吐 (tok/s) 核心特性 最佳场景
SGLang v0.4.3 16,200 RadixAttention 前缀缓存 前缀密集（RAG/聊天）
LMDeploy 16,200 持久批调度 高吞吐服务
vLLM v0.7.3 12,500 PagedAttention, Blackwell 支持 灵活、频繁换模型
TensorRT-LLM 最高（高并发） 编译 CUDA kernel 单模型长期生产

四、应用层优化（最高 ROI）

4.1 上下文压缩 vs 摘要

方法 压缩比 精度评分 问题
摘要式 (LLMLingua) 最高 20x 3.4-3.7/5 改写文件路径/错误码 → agent 轨迹长 13-15%
逐字压缩 (Verbatim) 50-70% 高 删除低信息 token，保留句子原文

JetBrains 发现：摘要压缩导致 agent 轨迹比逐字压缩长 13-15%，因为 agent 需要重新推导被改写掉的信息。

4.2 Prompt 缓存

  • 共享前缀（系统提示、对话历史）的 KV 张量可复用
  • 10K+ token 上下文：缓存部分延迟降低 80-90%
  • Anthropic：缓存 token 不计入速率限制 → 80% 命中率下有效 5x 吞吐

4.3 模型路由

  • 分类/提取任务 → 路由到小模型 → 12x 成本降低
  • 生产路由通常 2-5x 综合成本节约

五、对 Hermes/Jetson 部署的实际建议

5.1 Jetson Orin Nano 推理优化路径

层级 当前状态 建议
模型层 GGUF Q4_K_M ✅ 已量化，维持现状
KV 缓存 FP16 默认 切换到 FP8（如 llama.cpp 支持）
批处理 单请求 无法改进（边缘设备）
上下文 全量 引入上下文压缩（context-compressor skill）
模型路由 单模型 已有 model-switch skill

5.2 具体行动项

  1. 检查 llama.cpp FP8 KV 缓存支持：--cache-type-k q8_0 --cache-type-v q8_0 可获得 2x 上下文容量
  2. TQ 4bit-nc 边缘验证：Jetson 内存受限场景可能有价值，需精度验证
  3. 推测解码：检查 llama.cpp --draft 参数是否可用小模型加速
  4. 上下文压缩常态化：长对话 cron 任务中启用 context-compressor skill

六、衡量指标（正确的指标才有正确的优化）

指标 含义 常见误区
每任务 token 数 完成单位工作消耗的总 token 最接近成本的指标
TTFT 首 token 延迟 上下文压缩直接改善
TPS 解码吞吐 量化/批处理/推测解码影响
每任务成本 tokens/task × 价格/token 最终优化目标

关键警告：优化 TPS 而忽略 tokens/task = 用更快的引擎处理膨胀的上下文，成本反而更高。从应用向外优化，不是从 GPU 向内。
