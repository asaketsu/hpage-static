一句话定义

FDE 模式最反直觉的一点：第一单往往更慢、更贵、更痛苦（成本约普通项目3倍），但做到第10个同类客户时成本约降到4-4.5倍——而传统项目制交付从1倍涨到8-9倍。分水岭在于：项目结束后，团队手里到底留下了什么。

内容整理（完整保留原帖内容）

核心对比：FDE vs 传统项目制

维度 FDE（本体化交付） 传统项目制交付
第1个客户成本 ~3倍（更慢更贵更痛苦） 1倍
第10个客户成本 ~4-4.5倍 8-9倍
成本趋势 第一单更重，后续摊薄 每多一个客户继续加人
项目结束后留下了什么 Skill、模板、测试集、连接器、平台能力 只有系统本身

前者第一单更重，后者每多一个客户都继续加人。

FDE 的试金石：让下一个客户更便宜

作者用三个递进层级定义交付模式：

层级 留下了什么 叫什么
只给客户留下一个系统 系统 外包
带回经验，但下个项目还得重新访谈、建模、写接口 经验 项目制交付
把现场经验沉淀成 Skill、模板、测试集、连接器和产品能力 可复用资产 FDE

这些资产继续降低同类客户的交付成本，交付周期缩短，客户慢慢拥有自助能力，FDE 才从一项服务变成可复用的组织能力。

判断团队有没有跑通，盯两条曲线：
1. 同类客户的现场投入是否持续下降
2. 产品和平台的杠杆是否持续增加

如果第一个客户需要10个人月，第十个同类客户仍然需要10个人月——团队只是更熟练地做项目，复利还没有出现。

Echo 和 Delta：把一人全能拆成一支小队

FDE 能力分为两层：

角色 职责 核心能力
Echo 负责"该做什么" 听懂客户功能需求 → 追问业务问题：钱从哪里来？流程卡在哪？AI 能在哪个环节撬动价值？
Delta 负责"怎么做出来" 把抽象问题变成可运行原型：系统集成、Prompt调优、规则补充、测试评估、上线修复
FDPM 需求对齐、测试用例、项目节奏 项目管理

早期团队里，一个人可以同时做 Echo 和 Delta。项目多起来后角色自然分化。

这套分工像一场双人舞：Echo 把客户语言翻译成值得验证的问题 → Delta 把问题翻译成系统动作 → 客户结果反过来校正 Echo 的判断。

双向蒸馏：客户得到能力，厂商得到资产

FDE 不是单向把产品送进客户公司。同时发生两次蒸馏：

蒸馏方向 内容 产出
面向客户 把员工脑中经验、流程规则、隐性知识整理 知识库、SOP、工作流、可调用的业务能力。客户不再依赖某个老员工记住所有细节
面向厂商 把项目中出现的行业对象、系统接口、测试方法、失败案例整理 Skill、模板、连接器、评测集、平台功能。下一个客户可直接调用

承载两次蒸馏的，是一层逐渐清晰的业务语义（本体层）。

本体层回答三类问题：
1. 业务世界里有什么对象，它们有什么属性
2. 这些对象可以执行什么动作，权限和状态怎样变化
3. 实时发生了什么事件，下一步要触发什么流程

金融：客户、账户、交易、授信、风险事件
教育：学生、课程、作业、教案、评价
传媒：选题、素材、稿件、审核、发布

客户系统的字段名可以不同，业务对象和关系却经常有共性。AI 直接面对原始数据库，很容易被字段、编码和历史习惯拖住。本体层把这些混乱翻译成业务语言，Agent 才有机会进入流程执行。

Palantir 的答案：让客户在五天内看到自己的结果

Palantir 是 FDE 模式的典型案例——把现场交付变成行业学习和平台沉淀。

产品 场景
Gotham 情报与安全
Foundry 企业数据和业务操作
AIP 让 LLM 通过 Ontology 理解业务

Bootcamp 模式：FDE 带着工具进入客户现场，使用客户真实数据，在本体框架下快速搭建可运行原型。
- 周期：约 5 天
- 客户转化率：约 70%
- 获客成本降低：40%-60%

客户不再先听一套方案，再猜能不能落到自己公司；客户直接在自己的数据和流程上看到结果，再决定是否扩展。

Palantir 2025 财年约 82% 的毛利率——说明重交付可以靠资产沉淀逼近软件公司的经济结构。

国内团队：先做 Skill，再逼近本体

国内多数团队没有条件复刻完整 Palantir 技术栈，也很难一开始投入十多年去打磨跨客户本体。

更现实的顺序：
1. 先整理行业术语和高频任务
2. 把任务做成 Skill
3. 把企业微信、CRM、知识库、审批、ERP 等系统接入做成连接器
4. 几个客户跑通后，把 Skill 和连接器编成行业模板
5. 客户数量、客单价和复用率足够时，再投入更深的本体层

Skill 解决"这类任务怎么做"，连接器解决"能操作哪些系统"，行业知识库解决"调用什么专业内容"。三者组合起来，才会形成交付壁垒。

单个 Skill 不构成护城河

容易被忽略的细节：单个 Skill 很难长期构成护城河。它可能只是自然语言写成的流程和规则，容易复制，也可能被模型能力逐渐吸收。

真正有价值的组合：Skill 连接真实系统 → 系统持续产生反馈 → 反馈继续改进模板和产品。

FDE 的复利反馈链

FDE 的复利，从来不是"多做几个项目"自动产生的。它需要一个反馈链：

客户现场发现问题
    ↓
Delta 标准化提交
    ↓
Echo 判断通用性
    ↓
产品团队把可复用部分纳入平台
    ↓
下一支前线团队调用
    ↓
使用结果再回到系统中
    ↓ (循环)

这条链一旦断掉，FDE 会退化成高端外包；这条链持续运转，第一单付出的额外成本才有机会被后面的客户摊薄。

三个自检问题

  1. 上一个客户遇到的共性问题，下一个客户能直接调用吗？
  2. 一线提交反馈，会影响绩效、内部结算或产品版本吗？
  3. 每次交付完成后，客户现场的代码、流程和测试集有没有被整理进资产库？

如果答案都是否，先别急着给团队换一个更时髦的岗位名。先把一次交付变成下一次交付的起点。

归纳总结

这篇文章的核心贡献是把 FDE 从模糊的概念拆解为可操作的框架：

  1. 经济模型：第一单3倍成本→第10单4-4.5倍 vs 传统1倍→8-9倍。关键是"复利曲线"
  2. 角色分工：Echo（该做什么）+ Delta（怎么做出来）+ FDPM（项目节奏）= 双人舞
  3. 双向蒸馏：客户得到能力（SOP/知识库），厂商得到资产（Skill/连接器/评测集）
  4. 落地路径：Skill → 连接器 → 行业模板 → 本体层（渐进式）
  5. 复利条件：反馈链必须闭环（现场发现→标准化→平台吸收→下次调用→结果回流）
  6. 护城河：单个 Skill 不够，Skill+系统+反馈的飞轮才是壁垒

结合最新研究与技术变化

1. 与 AWS Context Ontology Accelerator 笔记的直接关联

本文的"本体层"概念与 AWS COA 的本体建模完全对应——都是把业务对象、属性、关系、动作、权限翻译成统一语义层，让 AI/Agent 不直接面对混乱的原始数据库。区别是：AWS COA 侧重技术实现（VKG/SPARQL/Smithy），本文侧重商业模式（什么时候投入本体层）。

2. 与 Coding Agent Harness 解剖学笔记的关联

FDE 的 Skill+连接器+反馈链，与 Mastra Harness 的 Skills 系统 + MCP 工具连接器 + Observational Memory 反馈机制形成完美对应。FDE 在组织层面的"双向蒸馏"等同于 Harness 在 Agent 层面的"OM 观测记忆"——都是从执行过程中提取结构化经验。

3. 与自进化四波浪潮笔记的关联

FDE 的反馈链（现场发现→标准化→平台吸收→下次调用→结果回流）就是自进化的"提出改动→验证→积累"三步循环在组织层面的体现。断掉反馈链 = 自进化失败 = 退化成高端外包。

4. 与 SkillOpt 笔记的关联

本文"单个 Skill 容易被模型能力逐渐吸收"直接呼应 SkillOpt 的价值——通过持续优化 Skill 质量（验证驱动的 Propose→Verify→Compound），保持 Skill 组合的竞争壁垒。

5. 与 FDE 个人方向（用户关注）的直接关联

用户 FDE 方向关注：Echo（该做什么）和 Delta（怎么做出来）的角色定义、成长路径、能力模型。本文给出了清晰的角色分工和成长方向——下一篇将进入操作层。

学习进化借鉴点

FDE 设计 Hermes Agent 现状 可借鉴方向
反馈链闭环（现场→标准化→平台→调用→回流） ⚠️ evolver 部分实现但缺闭环 每次任务完成后自动提取可复用 Skill，下次同类任务自动调用
双向蒸馏 ⚠️ 只做笔记蒸馏（面向用户），不做资产蒸馏（面向平台） 每次笔记/分析后提取"模式"→沉淀为 Skill →下次复用
Skill+连接器+反馈飞轮 ✅ 有 Skill+MCP 但缺反馈飞轮 Skill 连接真实系统 → 执行结果 → 改进 Skill
三自检问题 ❌ 从不自检复用率 定期检查：上次任务的产出下次能否直接调用
Bootcamp 5天验证 N/A 新功能/新方向用"5天真实数据验证"而非无限 POC

最值得借鉴的 3 个设计

  1. 复利反馈链——每次任务结束后强制执行：现场发现 → 标准化提交 → 通用性判断 → 纳入平台 → 下次调用。这直接对应 evolver 的设计目标，但需要更闭环的实现
  2. Skill 不构成单独护城河的判断——单个 Skill 容易被 LLM 能力吸收，真正有价值的是 Skill+系统连接+持续反馈的飞轮。这指导 Hermes 的 Skill 体系设计方向
  3. 三自检问题——可以定期（如每周/每月）自动运行，检查 Hermes 自身的复用率和反馈链健康度

趋势判断

  • FDE 正在从概念走向可操作框架：Echo/Delta/FDPM 角色分工 + 双向蒸馏 + 渐进式本体层 = 可落地的组织设计方法论
  • 第一单亏钱是 FDE 的正确姿态：3倍成本的"过度投入"不是浪费，而是资产建设——前提是反馈链闭环
  • 本体层（Ontology）是 AI 落地的关键中间层：不是直接让 AI 面对原始数据库，而是通过本体翻译成业务语义——这是 Palantir 82% 毛利率的技术基础
  • 国内路径 = 先 Skill 后本体：不追求一步到位建本体，先跑通 Skill+连接器+行业模板，客户量和复用率够了再投入本体层
  • Skill 的生命周期管理成为新课题：单个 Skill 会被模型能力吸收淘汰——需要持续评估哪些 Skill 仍有独立价值，哪些已被 LLM 内化
  • 反馈链断裂是 FDE 失败的头号原因：不是技术不够，而是组织没有形成"现场→平台→下次调用"的闭环机制

关联分析

  • 与 harness-architecture Skill 的关联：FDE 的反馈链是 Harness 六层架构中"反馈/评估层"的组织级实现
  • 与 agent-primitive-architecture Skill 的关联：FDE 的 Skill+连接器+本体层三件套与 Agent 三原语（Agents/Skills/Hooks）+SYNAPSE 知识层对应
  • 与 OttoClaw 项目的关联：OttoClaw 的 SPIFFS Agent 知识层（SOUL.md/AGENTS.md/TOOLS.md）是 FDE 本体层在嵌入式设备上的简化版
  • 与 Prime Agent 的关联：Prime Agent 的 Continual Harness /refine 机制就是 FDE 反馈链在 Agent 层面的自动化实现
