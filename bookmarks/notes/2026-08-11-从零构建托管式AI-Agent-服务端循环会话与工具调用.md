## 一句话定义

> **托管式 Agent = 你提供任务+工具+领域逻辑，Anthropic 托管 Agent loop+沙箱+会话持久化+鉴权+扩缩容。** 三件套（Agent=大脑、Environment=双手、Session=连接）组成最小可持续任务。核心设计：Agent loop 在服务端运行，工具按需在沙箱中启动，通过事件流双向通信。

## 完整原文核心内容

### 一、三层演进：从 Messages API 到托管式 Agent

| 层级 | 开发者负责 | 平台托管 |
|------|-----------|---------|
| **Messages API** | 几乎全部：上下文管理、Agent loop、工具执行、会话恢复、鉴权、可观测性 | 仅模型输入输出 |
| **Agent SDK** | 自定义工具、领域逻辑、hosting/scaling、安全容器 | Claude Code 能力封装 |
| **Managed Agents** | task + agent config + custom tool logic（含 MCP/Skills） | harness + context management + tool runtime + sandbox + session persistence + auth vault + hosting/scaling/observability |

> **"context anxiety"**：团队曾针对某模型"过早结束任务"的行为加入缓解逻辑，模型更新后该行为消失，补丁失去价值。→ **harness 必须跟着模型行为演进，不是一次性写完。**

---

### 二、三件套与"脑—手"解耦

| 原语 | 回答的问题 | 比喻 |
|------|-----------|------|
| **Agent** | 模型、系统提示词、工具和能力是什么？ | 大脑 |
| **Environment** | 工具在哪里执行？容器/网络/计算资源？ | 双手 |
| **Session** | 哪个 Agent 在哪个 Environment 中为哪个任务工作？ | 连接与事件通道 |

**"脑—手"解耦的核心价值**：
- 旧模型：每个会话一个容器，Agent loop 与工具执行绑定
- 新模型：Agent loop 由 Anthropic 管理，工具按需在 sandbox 中启动
- 收益：凭证隔离更清楚、工具容器不必和循环绑死、容器按需启动降低首 token 延迟
- TTFT P95 降低 >90%（视频归因于其架构的观测值，非通用保证）

### 三、SRE 事故响应实战演示

**事故场景**：INCIDENT-2277
- checkout 服务 P99 latency ~3638ms（约 10 倍 baseline）
- error rate 21.9%
- DB pool 100%

**工具链**：

| 工具 | 输入 | 用途 |
|------|------|------|
| `get_metrics` | 服务名+指标名 | 获取指标数据 |
| `get_recent_deploys` | 无复杂参数 | 获取最近部署记录 |
| `get_diff` | commit 标识 | 获取代码变更 |

**调查过程**：
```
用户: "debug my incident for me"
→ sandbox/bash (分析日志)
→ get_recent_deploys (找最近变更)
→ get_metrics (确认指标异常)
→ get_diff (查看代码变更)
→ 结论: database pool exhaustion（数据库连接池耗尽）
  关联到 Alice 的 order summary builder 重构查询
  建议: 回滚 + 确认连接池告警 + 增加回归测试
```

### 四、Session + 事件流（核心协议）

#### 事件类型

| 方向 | 事件 | 语义 |
|------|------|------|
| **发送** | `user.message` | 用户消息 |
| **发送** | `user.custom_tool_result` | 自定义工具调用的结果 |
| **发送** | `user.tool_confirmation` | 对需权限确认的工具批准/拒绝 |
| **发送** | `user.interrupt` | 用户发起中断 |
| **接收** | `agent.message` | Agent 的回复 |
| **接收** | `agent.tool_use` | 调用内置工具 |
| **接收** | `agent.custom_tool_use` | 调用你提供的工具 |
| **接收** | `agent.mcp_tool_use` | 调用 MCP 工具 |
| **接收** | `session.status_idle` | 循环暂停，携带停止原因 |
| **接收** | `session.error` | 发生失败 |

#### 事件流代码（按视频画面重排）

```python
with client.beta.sessions.events.stream(session_id) as stream:
    client.beta.sessions.events.send(session_id, events=[
        {"type": "user.message",
         "content": [{"type": "text", "text": user_text}]}
    ])
    for ev in stream:
        if ev.type == "agent.custom_tool_use":
            result = handle_tool(ev.name, ev.input)
            client.beta.sessions.events.send(
                session_id,
                events=[{
                    "type": "user.custom_tool_result",
                    "custom_tool_use_id": ev.id,
                    "content": [{"type": "text", "text": result}]
                }],
            )
        yield ev
```

> 关键方向：云端 Agent 发出工具事件 → 本地 handle_tool 读取 fixture → 结果作为用户侧工具结果发回 → 循环继续。

#### 会话状态机（4 种状态）

| 状态 | 说明 | 转换 |
|------|------|------|
| **idle** | 等待输入 | ← running（结束/需要动作） |
| **running** | Agent 正在执行循环 | → idle / rescheduling / terminated |
| **rescheduling** | 瞬态错误，自动重试 | → running（auto-retry） |
| **terminated** | 不可恢复错误 | 终态 |

### 五、扩展能力（Beyond the Basics）

| 能力 | 说明 |
|------|------|
| **Subagents** | orchestrator 把任务分给子 Agent，各自上下文窗口，并行化+上下文隔离 |
| **Memory / dreaming** | 从日志、用户纠正和偏好中判断哪些值得保留 |
| **Outcomes** | 用 rubric（评估量规）定义期望产物 |
| **Vaults** | 凭证独立端点加密访问，按用户管理 |
| **Webhooks** | 外部事件触发或恢复 Session |
| **Permission policies** | 工具确认和权限控制 |
| **MCP servers** | 远程工具服务器 |
| **Interrupt** | 运行中断机制 |
| **Console agent builder** | 交互式配置和可观测性 |

> ⚠️ 多数扩展带 Beta 标识，不能当成稳定接口。

### 六、完整心智模型（一张可迁移的图）

```
用户消息
   ↓
Session（绑定 Agent + Environment + 资源）
   ↓ 事件流
服务端 Agent loop（选择下一步）
   ↓ agent.custom_tool_use
工具执行端（本地脚本 / 自有容器 / 生产客户端）
   ↓ user.custom_tool_result
服务端 Agent loop 继续推理并产出 agent.message
   ↓
前端呈现 + Session 日志 + 可观测性
```

| 层 | 负责 | 证据 |
|----|------|------|
| Agent 定义 | 模型、系统提示词、工具和能力 | SRE Agent 创建代码 |
| Environment | 容器、网络和工具执行空间 | config 与 sandbox 说明 |
| 资源/上下文 | 日志、指标、部署、diff 等证据 | app.log 与本地 JSON |
| Session | 绑定资源并维持任务生命周期 | Session 创建与刷新恢复 |
| 事件流 | 用户消息、工具调用、结果、状态 | stream_reply 与事件幻灯片 |
| 工具执行端 | 真正查询数据或执行动作 | handle_tool、Datadog 替换方向 |
| 控制与观测 | 日志、状态、删除、确认和恢复 | 控制台、状态机、删除按钮 |

### 七、实践路线（从 Demo 到生产）

1. **复现输入** — 本地 fixture 启动 Streamlit，验证页面和数据格式
2. **定义边界** — 最小 Agent system prompt + 工具 schema + Environment 网络 allow list + 日志挂载规则
3. **接通会话** — 创建 Session，发送 user.message，实现事件流回传
4. **做证据闭环** — 每次工具调用+输入+输出+耗时+错误+结论写入可查询日志
5. **验证生命周期** — 测试 idle/running/rescheduling/terminated + 刷新恢复 + 删除 + 人工中断
6. **替换数据源** — 用生产客户端替代 JSON fixture，保持工具契约稳定
7. **加控制面** — 写操作增加工具确认/审批/审计/回滚/webhook 鉴权
8. **最后扩展** — 按一个目标逐次加入 Subagents/Memory/Outcomes/Vaults

## 结合最新研究与技术变化

### 1. 与 Hermes Agent 架构的直接映射

| Managed Agents 概念 | Hermes 对应 |
|-------------------|------------|
| Agent 定义（模型+系统提示词+工具） | config.yaml + Skill 系统 |
| Environment（容器+网络+执行空间） | Hermes Gateway + terminal/execute_code 沙箱 |
| Session（绑定 Agent+Env+资源） | Hermes session（会话持久化） |
| 事件流（user.message ↔ agent.custom_tool_use） | Hermes tool_call ↔ tool_result 循环 |
| Context Engineering（上下文工程） | Hermes MEMORY.md + Skill 按需加载 |
| Session 状态机（idle/running/rescheduling/terminated） | Hermes 会话生命周期 |
| Subagents | delegate_task |
| Memory / dreaming | MEMORY.md + session_search + cron memory consolidation |
| Vaults（凭证保险库） | config.yaml 环境变量注入 |

### 2. 与 PhysiClaw Turn Loop 的关联

PhysiClaw 的 `loop.py`（7 步管线：model→tool_calls→dispatch→results→model）与本课件描述的 Managed Agent loop 是同构的。区别在于：
- Managed Agents 的 loop 在服务端运行，工具在沙箱中执行
- PhysiClaw 的 loop 在本地运行，工具是物理的（相机/触控笔）
- Hermes 的 loop 也在本地运行，工具是数字的（API/文件/终端）

### 3. 与 Coding Agent Harness 解剖学的关联

Mastra 的 27 分钟深度分析也描述了同样的 Agent loop 模式——model→tool_calls→tool_results→model。三个独立来源（Anthropic/Mastra/PhysiClaw）验证了这是 2026 年 Agent 架构的共识。

### 4. 与 Context Engineering 的关联

本课件明确提出 **"context engineering（上下文工程）"** 是 Agent 质量的主要杠杆——"把更多正确上下文交给它"比不断加长系统提示词更重要。这与 Hermes 的 L1常驻/L2阶段触发/L3按需查询 三层加载策略完全一致。

## 趋势判断

1. **Agent loop 即服务（Loop-as-a-Service）** — Anthropic 把 Agent loop 托管在服务端，开发者只需提供工具和领域逻辑
2. **事件流 > 请求/响应** — 长任务可恢复、可审计、可观测的需求推动从一次性请求转向持续事件流
3. **"脑—手"解耦成为标配** — Agent loop 与工具执行分离，凭证隔离+按需启动+降低延迟
4. **Context Engineering 成为核心学科** — 比系统提示词更重要的是"上传哪些文件、怎样组织、工具返回什么证据"
5. **托管式 Agent 降低生产门槛** — 视频称 10-15x 更快到生产（非通用保证）
6. **状态机 + 持久化 + webhook = 可恢复 Agent** — 容器崩溃后从 Session 日志继续
7. **Memory/Outcomes/Vaults 是下一层扩展** — 跨会话记忆、质量量规、凭证安全
