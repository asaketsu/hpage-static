核心结论

作者做 AI 视频后遇到的最大问题不是"不会做"，而是"每做一期，都像第一次做"——选题重新查资料、写稿重新搭结构、横版做完还要重做竖版、配音语速不一致、发布前发现字幕封面简介都没准备。TudouFlow 的核心思路不是"替你生成一条视频"，而是：把重复出现的判断沉淀下来，让系统复用上一次的成果。

"我缺的不是一个更快的剪辑工具，也不是一条更厉害的提示词。我缺的是一条生产线。"

一、核心洞察：视频最消耗人的是反复做决定

视频制作不是连续动作（写稿→配音→剪辑→发布），而是一张决策网：

  • 这个选题属于哪条内容线？
  • 观众已经知道什么，这一期只讲什么？
  • Hook 要打破哪个误解？
  • 哪段用类比，哪段用流程图？
  • 屏幕上应该出现多少字？
  • 横屏构图到了竖屏还成立吗？
  • 配音、字幕和场景，谁才是时间轴真源？
  • 不同平台该拿哪张封面、哪版视频、哪套文案？

如果这些问题每期都重新回答，创作者当然会累。更糟的是，上一期踩过的坑并不会自动成为下一期的资产。

二、四个核心变化

变化 1：从内容路线出发，而非单条视频

一条视频能不能做，和现在应不应该做，是两回事。

先把主题放进系列路线，回答五个问题：属于哪个栏目？目标观众已知什么？这一期只解决什么？它承接哪一期？下一期通向哪里？

三套栏目语言（不是同模板换色，而是独立设计系统）：

栏目 风格 用途
AI 课堂 暖色卡通 解释概念
AI 前沿 极简科技 拆解趋势和新技术
工具使用 暗色界面 软件与操作演示

栏目名称、标题格式、片头片尾、字体、卡片、封面和画面气质都属于各自的设计系统。不希望所有 AI 内容长成一种"AI 味"。

变化 2：内容属于数据，组件只负责表达（最重要）

这是整套系统最重要的工程原则。

每期的标题、旁白、场景时长、Hook、类比、重点、视觉素材和音轨，都写在一个 Episode 配置中。场景组件不保存某一期的整段文案，只负责把"定义""流程""对比""类比""总结"这些关系表达清楚。

价值 说明
改旁白时 知道应该去哪里改
做下一期时 可以复用成熟场景
Agent 进入项目 先读明确结构与规则，而非猜意图

脚本原则——把"声音"和"屏幕文字"分开：

  • 旁白要像人说话
  • 屏幕文字要像路标
  • 每一段旁白只承担一种主要视觉任务

如果一段话既要定义概念、解释原理、举例子、又给结论——通常不是画面不够炫，而是脚本还没拆清楚。

变化 3：横版和竖版不是裁切关系

先做 16:9 再裁成 9:16，结果：字幕挤住角色、流程图看不清、横向卡片只剩小字。

横版 竖版
1920×1080 1080×1920
读取同一份 Episode 数据 通过方向上下文分别布局
— 字幕/角色/卡片/视觉层级按画布重新分配

增加组件设计工作量，但把每期发布前的重复劳动拿掉了。对持续更新来说，这笔账划算。

变化 4：先把声音当作时间，再让画面跟上

真源 说明
时间真源 真实成片声音
内容真源 审定脚本

关键规则：同一期所有 mini batch 必须使用完全相同的参考音频、speed、temperature、atempo 和 enhance 参数。

只要其中一项不同，就可能出现某段忽快、某段能量突变，听起来像几个人轮流说话。

字幕不是把自动转写原样贴上去。Whisper 帮助对齐时间，但最终文字回到脚本和人工审校。

Release 后必须检查：用 ffprobe 检查音频流 + volumedetect 确认不是静音。

"视频里有 audio stream"不代表它真的有正常声音。

三、一期视频的最终产物：Release

完成定义不是"视频导出来了"，而是平台真正需要的东西都已准备好且可被检查。

单期 Release 默认输出

产物 规格
横版 MP4 1920×1080
竖版 MP4 1080×1920
SRT 字幕 —
抖音封面 竖 + 横
小红书封面 —
YouTube 封面 横 + Shorts
平台文案 小红书/抖音/YouTube 的标题、简介、标签

通过一条 Release 命令串行生成（共享临时目录，并行跑多期会互相干扰）。

四、产品化：为什么打包成 TudouFlow？

一套只存在于我电脑里、只有我知道怎么运行的东西，还不能叫系统。

产品资料包含：

  • 系统总览与五层架构
  • 安装与首条样片
  • 选题、单集 Brief 和脚本工作流
  • Episode、场景、横竖版制作 SOP
  • 配音、字幕和时间轴 SOP
  • Release 与平台发布 SOP
  • 品牌定制、排错、质量检查
  • Brief、平台文案、发布状态与质检模板
  • 授权协议和交付检查清单

买家第一天正确动作

先选一个现有 Episode，原样跑通预览和 Release。

确认环境、字体、声音与渲染正常后，再替换角色、参考声音、栏目名称和选题路线。

先跑通，再改造；先固定参数，再批量生成；先验证 Release，再进入平台发布。

六、适合谁 / 不适合谁

✅ 适合

  • 个人创作者 / 一人团队 / 小型内容工作室
  • 已决定长期做某类知识视频
  • 愿意用 Codex、Claude Code 读取本地工程的 Agent 协作
  • 已感受到：内容更新靠意志力 / 品牌视觉不稳定 / 横竖版重复做 / 配音字幕返工 / 发布前临时补文件

❌ 不适合

  • 只想偶尔做一条视频，不打算建栏目
  • 期待输入一句话就自动得到无需审稿的爆款
  • 完全不想接触本地工程、Node.js、TTS/ASR 与第三方服务

明确边界

系统能降低重复劳动，不能替代选题判断；能固化质量检查，不能保证流量；能提供配音与字幕管线，但不会附带个人参考声音、账号 Cookie、API Key 或未授权资产。

把这些边界说清楚，比包装成"全自动赚钱机器"更重要。

七、核心理念总结

理念 说明
沉淀而非生成 把重复判断沉淀下来，系统复用上一次成果
内容=数据，组件=表达 Episode 配置是核心，组件只负责表达关系
声音是时间真源 声音决定时间轴，画面跟上
Release 是完成定义 不是导出 MP4，而是所有平台资产就绪且可检查
先跑通再改造 买家先原样跑通，再替换自己的内容
