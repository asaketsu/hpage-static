局域网音响系统探查与控制方案

生成日期 2026-08-15

研究日期：2026-08-15 | 类型：项目方案 | 触发：手机（必要时小型硬件）探查、进入并控制任意局域网音响系统

0. 项目定义与合规边界

目标：给定一个局域网（自有的或获得授权的），用手机完成三步——
1. 探查（Discover）：找出网内所有音响/流媒体设备，识别其协议栈
2. 进入（Access）：理解每类设备的控制通道（端口、API、鉴权要求）
3. 控制（Control）：用手机 App 或脚本对设备完成播放/音量/分组控制

合规边界：本方案仅适用于自己拥有的网络或书面授权的测试环境（如自家智能家居、公司 IT 授权审计）。对未授权网络实施设备控制在中国《网络安全法》《刑法》第285条（非法侵入计算机信息系统罪）及各国法律下均属违法。技术上"多数音响系统默认无鉴权"是本方案可行的原因，也是需要防御加固的警示。

1. 协议层全景：局域网音响的六大协议栈

任何"网络音响"本质上运行以下一种或多种协议。识别协议 = 找到控制钥匙。

协议 发现机制 关键端口/指纹 控制方式 典型设备
AirPlay / AirPlay 2（Apple RAOP） mDNS _raop._tcp / _airplay._tcp UDP 5004/5005（RTP音频）、7000（AP2）、TCP 3689（DACP远程） iOS/macOS 系统级投放；DACP HTTP 接口查状态/控制 HomePod、Sonos Era、WiiM、各类 AirPlay 音箱
Google Cast（Chromecast built-in） mDNS _googlecast._tcp TCP 8009（CASTV2，TLS+Protobuf） 支持 Cast 的 App（Spotify/YouTube/ BubbleUPnP）；CASTV2 协议库 Google Nest、Chromecast Audio、JBL/索尼 Cast 音箱
UPnP / DLNA SSDP 239.255.255.250:1900（M-SEARCH） 高位 TCP（1400/49152+，设备描述 XML 里声明） AVTransport（播放）/ RenderingControl（音量）SOAP 调用 智能电视、Hi-Fi 网播、Bose SoundTouch（部分）
Sonos（UPnP 变体 + SMAPI） SSDP + Sonos 特有 topology TCP 1400/1443（UPnP/SOAP）、3400（group rpc） soco Python 库 / Sonos app / AirPlay 2 Sonos 全系
Spotify Connect Zeroconf（mDNS _spotify-connect._tcp） TCP 4370（Zeroconf 认证）、4070（AP） Spotify App 内置设备列表；librespot 做接收端 Sonos、WiiM、各类认证音箱
Linkplay（白牌方案） mDNS/SSDP + UDP 49999 HTTP API（80/443，http://IP/httpapi.asp?...） 4Stream/WiiM Home App；pywiim Python 库直调 HTTP API WiiM、Arylic、Audio Pro、数百白牌
Snapcast（开源多房间） 自有发现 TCP 1705（控制）、1704（音频流） Snapcast App；作为 Music Assistant 的输出层 自建（RPi/ESP32/PC）

关键事实：
- Linkplay 是白牌方案——"数百个品牌"（Arylic 官方开发文档原话）用同一套 HTTP API，意味着一个 pywiim 库可控制一大类设备。Arylic 开发者文档（developer.arylic.com/httpapi）公开了完整 API：getPlayerStatus、setPlayerCmd:play、音量、EQ、多房间分组全部支持。
- Sonos 的连接安全设置（2024 勒索事件后加入）：UPnP 默认 ON、Guest Access 默认 ON、Authentication 默认 OFF——即出厂状态下局域网内任何设备可控制播放。
- Music Assistant 2.7（2025-12）新增 Sendspin 协议（Open Home Foundation 开源多媒体同步协议）和外部音源接入（Spotify Connect / AirPlay 作为输入），是当前最活跃的统一层。

2. 探查阶段：手机纯软件工具链

2.1 第一步：网络扫描（发现 IP + MAC + 端口）

工具 平台 能力 备注
Fing（免费版够用） iOS/Android ARP 扫描全网设备、MAC 厂商识别（OUI）、端口扫描、Bonjour/mDNS 服务枚举 首选，最快出全景
Network Analyzer iOS/Android 类似 Fing + WHOIS/Trace 备选
nmap（Termux/pkg install nmap） Android 完整 nmap：-sn 存活扫描、-sV 服务指纹、NSE 脚本 技术流首选，能力=桌面级

nmap 标准流程（Termux 实测命令）：

# 1. 存活扫描（ARP ping sweep，手机与设备同网段时最准）
nmap -sn 192.168.1.0/24
# 输出示例：SoundTouch-Kitchen.lan (192.168.0.160) — 主机名直接暴露设备类型

# 2. 对可疑设备做服务指纹（音频端口探测）
nmap -sV -p 5004,7000,8009,1400,1443,3400,4370,49152-49200 192.168.1.x
# 5004/7000 open → AirPlay
# 8009 open (tls) → Google Cast
# 1400 open (http UPnP) → Sonos
# 4370 open → Spotify Connect
# 49152+ open (http) → UPnP/DLNA renderer

# 3. mDNS 服务枚举（无需 root，Termux 可跑）
nmap -sn --script broadcast-mdns-discover
# 或装 avahi: avahi-browse -art | grep -E "raop|airplay|googlecast|spotify"

2.2 第二步：设备指纹识别决策树

mDNS 发现 _raop._tcp ──────────→ AirPlay 音箱（iOS 直接投）
mDNS 发现 _googlecast._tcp ────→ Cast 音箱（Cast 功能 App 投）
SSDP 响应 ST: urn:schemas-upnp-org:device:MediaRenderer:*
  ├─ SERVER 头含 Sonos ────────→ Sonos（soco / Sonos app）
  └─ 其他 ─────────────────────→ 通用 DLNA（BubbleUPnP 控制）
HTTP GET http://IP/httpapi.asp?command=getPlayerStatus 返回 JSON
  └─ 有响应 ───────────────────→ Linkplay 方案（pywiim / 4Stream app）
mDNS 发现 _spotify-connect._tcp → Spotify Connect（Spotify app 原生）

MAC OUI 辅助识别：Fing 自动做。常见：Sonos 48:44:F7/94:9F:3E、Google F4:F5:D8/6C:AD:F8、Bose B8:FF:xx（Resideo 代工线索）、Linkplay A31 模块 88:DD:EA 类。

2.3 纯软件方案的边界（什么时候不够）

场景 纯手机能否解决
网内有 AirPlay/Cast/DLNA/Sonos/Linkplay 设备 ✅ 能——所有协议都有手机控制点
音箱只有蓝牙（不入网） ❌ 不能——蓝牙不在局域网发现范围，只能一对一配对
音箱只有模拟输入（3.5mm/RCA，老功放） ❌ 不能——需要硬件给它加"网络大脑"
目标音响不支持的协议（如 Android 音源投 AirPlay 音箱） ⚠️ 需要协议桥（见 §4 AirConnect/BubbleUPnP Server），手机能装但常驻性差
多房间同步播放跨协议（AirPlay+Cast+DLNA 混合） ❌ 不能——各协议时钟同步机制不通，必须上服务器+统一输出层（Snapcast）

3. 控制阶段：按协议的控制点矩阵

协议 手机 App（零代码） 编程接口（脚本党）
AirPlay 2 iOS 控制中心原生；Android 用 AirMusic（root/ADB 可选） DACP：GET http://IP:3689/ctrl-int/1/playstatus；shairport-sync 做接收端
Google Cast 任意 Cast-Enabled App（Spotify/YouTube/浏览器）；BubbleUPnP pychromecast（Python）：cast.play_media(url)；go-chromecast（CLI）
UPnP/DLNA BubbleUPnP（10M+ 下载，12年维护，同时是控制点+渲染器+转码代理） SOAP 直接调 AVTransport/SetAVTransportURI；async-upnp-client（Python）
Sonos Sonos app soco（Python）：device.play_uri(url)、分组 zone.partymode()
Spotify Connect Spotify app（免费账户即可控制，Premium 才能手机做音源） librespot（Rust，开源接收端）；Spotify Web API + Connect endpoint
Linkplay 4Stream / WiiM Home / Audio Pro app（三家互通） pywiim（Python，mjcumming）：HTTP API 直调，支持播放/音量/EQ 10段/输出模式/多房间
QPlay（QQ音乐私有） QQ音乐 App 投放 无公开 API，放弃编程路线

BubbleUPnP 深挖（它是手机端"万能遥控"的核心）：
- 一个 App 同时控制 Chromecast + DLNA + OpenHome 渲染器
- 自带 FFmpeg 转码：格式不兼容的媒体强转后投给目标设备
- 搭配 BubbleUPnP Server（可跑在 NAS/Pi/PC，非手机）可把 Chromecast 包装成 OpenHome 渲染器——实现"无人值守播放列表"（关掉手机继续播）
- 注意：Cast 发现依赖 Google Play Services；DLNA seek 在部分 Hi-Fi 品牌（Naim 等）上有兼容性问题

4. 统一控制层：从"遥控器"到"系统"

纯手机是"遥控器模式"——每协议一个 App，切换割裂。统一层把所有设备收拢成一个控制面：

4.1 Music Assistant（当前最强统一层，开源）

  • 定位：智能家居的音乐中枢服务器，2025-12 已到 2.7
  • 播放器 Provider 覆盖：AirPlay/AirPlay 2、Google Cast、Sonos、DLNA、Snapcast、Squeezebox/Squeezelite、Home Assistant media player、Sendspin（新）
  • 音乐源 Provider：Spotify、YouTube Music、Tidal、本地库、电台……
  • 2.7 杀手锏：
  • 外部音源接入：Spotify app 直接投到 MA 服务器 → 再分发到全网音箱（哪怕音箱本身不支持 Spotify Connect）；AirPlay 同理
  • Sendspin：开源多媒体同步协议（对比闭源的 AirPlay/Cast），带专辑封面/可视化数据自适应
  • WebRTC 远程路由（借 HA Cloud 基础设施免费中继，出门在外也能控制家里）
  • 部署：Docker/Home Assistant Add-on/裸机，Web UI 手机浏览器直接用 → 手机仍是唯一终端，服务器在后台

4.2 协议桥（把"不支持"变"支持"）

工具 作用 部署位置
AirConnect 让 UPnP/Sonos/Chromecast 音箱变成 AirPlay 目标——Mac/iPhone 全局 AirPlay 菜单直接可见 NAS（Synology 一键包）/Pi/任意常驻 Linux
BubbleUPnP Server Chromecast → OpenHome 渲染器（队列驻留）；DLNA↔Cast 转译+实时转码 NAS/Pi/PC
librespot / Raspotify 任意 Linux 设备变 Spotify Connect 接收端 Pi/服务器
shairport-sync（AirPlay 2） 任意 Linux 变 AirPlay 2 接收端，支持 24bit/48kHz 无损、5.1/7.1 多声道、MQTT 元数据外发 Pi/服务器

4.3 Snapcast（多房间同步的工业方案）

  • 架构：snapserver（中心）+ snapclient（每房间一个）+ FIFO 音源（MPD/librespot/shairport-sync/line-in）
  • 同步精度毫秒级（各客户端时钟对齐），跨混合硬件同步播放的唯一开源正解
  • 音源配置示例（Botmonster 教程原文）：
source = airplay:///shairport-sync?name=AirPlay&devicename=SnapHome&port=5000   # AirPlay 1
source = airplay:///shairport-sync?name=AirPlay&devicename=SnapHome&port=7000   # AirPlay 2
source = librespot:///librespot?name=Spotify&devicename=SnapHome&bitrate=320    # Spotify
source = alsa:///hw:1,0?name=Turntable&sampleformat=48000:16:2                  # 黑胶唱机模拟输入
source = pipe:///tmp/snapfifo?name=MPD&sampleformat=48000:16:2                  # MPD 本地库
  • 5 房间方案 < $300（每房间一个 Pi Zero + DAC）
  • Music Assistant 原生集成 Snapcast 输出

7. 安全视角（攻防两面）

攻击面现实（为什么"控制任何局域网音响"技术上成立）：
- Sonos 出厂默认：UPnP ON、Guest Access ON、Authentication OFF——同网任意设备可控播放/音量/分组
- Linkplay HTTP API 无鉴权（明文 HTTP，getPlayerStatus 直接返回）
- UPnP/DLNA 生态整体零鉴权（AVTransport SOAP 任何人可调）
- SSDP/mDNS 发现协议本身无访问控制

加固建议（ defending 侧）：
1. IoT VLAN 隔离：音响设备独立网段，禁止跨段访问控制端口
2. 路由器关 IGMP Proxy/组播转发（代价：跨 VLAN 发现失效——安全与便利互斥）
3. Sonos 开启 Authentication（代价：部分第三方集成失效）
4. 企业/敏感环境：mDNS Reflector 慎用，AV 设备全部入受控 VLAN + 802.1X

历史事件：2024 Sonos 遭勒索软件攻击（源码泄露）后才有 Connection Security 设置，且默认仍偏开放——行业普遍现状。

8. 结论

  1. "探查+控制任何局域网音响"在纯软件层面约 80% 可行——六大协议全部有手机端控制点（系统 AirPlay、Cast Apps、BubbleUPnP、soco/pychromecast/pywiim 库），设备出厂默认无鉴权是根本原因
  2. 剩下 20% 必须补硬件：模拟输入设备（ESP32-S3+PCM5102A，¥60）、跨协议同步（snapserver）、协议桥常驻（AirConnect/BubbleUPnP Server）
  3. 终极形态是档位 C：Music Assistant 把"每协议一个遥控器"收敛成"一个 Web 面板"，手机始终只是终端；2.7 的 Sendspin + 外部音源接入代表开源生态正在反向吞食 AirPlay/Cast 的闭源领地
  4. 本项目最优实践路径：档位 A 立即验证 → 有老功放就上档位 B 的 ESP32 → 追求同步/自动化再上档位 C

9.3 实测结论

  1. 当前局域网内无网络音响设备——mDNS 无音频服务、SSDP 无渲染器、无 Linkplay HTTP API 响应（httpapi.asp 全部无响应）、无音频指纹端口（5004/7000/8009/1400/4370 全闭）
  2. 有线直连场景（酒店/办公室）需手机与目标设备同网段，否则 mDNS/SSDP 组播不跨路由——这也是纯软件方案的天然边界
  3. 下一步建议：当前网络无目标设备，方案A在本网实测已到边界；若你有蓝牙音箱（非 WiFi），mDNS/SSDP 探查不适用，需走 BLE 扫描路线（nRF Connect / WooTechySmart 等工具）
  4. 三档方案对照本网现状：A 已完成（无目标）→ B/C 备选，B（ESP32 空中升级版）可让任意老功放获得 AirPlay/Cast 能力，C（Pi 5 中枢）适合未来多房间需求
