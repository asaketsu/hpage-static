一句话总纲

SAG 把知识图谱的构建时机从「离线预建」挪到「查询时动态组装」：入库时用 AI 提炼「事项卡片+实体」存 SQL，查询时用 SQL JOIN 动态串联多跳线索——在 MuSiQue（地狱难度 4 跳）上 Recall@5 达 80.04%（超 HippoRAG 2 约 15 个百分点），5 亿条数据生产环境秒级延迟，且检索链条全程 SQL 可追溯，把 RAG 调优从「炼丹」变成「找 Bug」。

一、内容详细整理

1.1 真实需求场景（作者客户案例）

客户要本地「小秘书」：会议纪要/立项材料/批复文件 Agent 对话查询 + 项目金额/开始时间等确定信息高准确率 + 本地服务器/大模型 + ≤1500 文档。

核心痛点：知识库最难的从来不是「搭建」，是调优——传统 RAG 调优是黑盒，「按下葫芦浮起瓢」（调低过滤 score→范围增大→噪音增多）。某公司 6 人团队搞半年才调到满意的准确率。

1.2 多跳推理：传统 RAG 的物理上限

三份独立文档的经典例子：

文档1："2023年，A公司全资收购了B公司。"
文档2："张三被任命为A公司的CTO。"
文档3："2024年，张三离职，加入了盘古大模型项目。"

用户问："收购了B公司的企业，其CTO后来加入了哪个项目？"

传统向量/混合检索的失败机理：文档 3 里根本没出现「收购」「B公司」「CTO」——字面和语义都不沾边，线索在文档 2→3 之间断了。答案：「抱歉，资料中未找到相关内容」。

会议纪要场景这类多跳检索需求非常多。

1.3 GraphRAG 为何被排除（太重）

  • 入库前大量调用 LLM 提取三元组（谁-做了什么-对谁），离线构建全语料库知识图谱
  • 索引成本：中等规模数据集烧好几万块钱
  • 维护成本：新文件进来可能要重算关系
  • 对 1500 文档的客户项目是「杀鸡用牛刀」

1.4 SAG 核心原理（查询时动态超边）

入库侧：AI 把每个文档片段提炼成「事项卡片」（记录发生了什么事）+ 提取「实体」（公司/人名/项目名），存进 SQL 关系库和向量库。一件事一张卡，不存在切块破碎问题（「张三负责A项目」和「500万预算」不会被切开）。

查询侧（两路并行 + 挖掘新线索）：

① 向量语义搜索（与传统 RAG 相同）
② 从问题提取实体「B公司」「CTO」→ SQL 查哪些事项涉及 → 命中文档1、2
③ 关键步：扫描已命中文档，发现新实体「张三」
   （用户问题里根本没出现过，但它是文档间的连接点）
④ 自动触发第二轮 SQL：「哪些事项涉及张三」→ 命中文档3
⑤ 三份文档 + 向量结果 → 大模型拼答案

普通 RAG 做完向量搜索就停了——不会从结果里挖新线索继续追。SAG 多了实体关联这条链，多跳推理从「靠运气」变成「确定性」。

1.5 与 FastGPT 混合检索的区别

维度 FastGPT（全文+向量+重排） SAG
本质 扁平的相似度匹配 SQL 结构兜底 + 向量
单文档问答 ✅ 完全够用，速度快 一样好
跨文档逻辑串联 ❌ 物理上限 ✅ SQL JOIN 动态串联
调优方式 炼丹（改切块/向量模型/重排阈值，黑盒） 看日志找 Bug（SQL 调用记录全可追溯）
切块敏感性 高（切坏就断线索） 无（事项卡片天然完整）

1.6 消融实验：不挑模型（对企业黑话关键）

故意把底层向量模型换成普通开源弱模型：

方案 弱向量模型下表现
其他高级 RAG 准确率暴跌近 10%
SAG 几乎没变化（稳定 80% 左右）

原因：SAG 找线索的主干是确定的 SQL 实体关联，不是模糊的向量距离。企业内部黑话向量模型不认识，但只要 SQL 里存了实体就能查出来——无需专门微调向量模型。

1.7 评测数据

数据集 SAG 对照
MuSiQue（最难，4 跳强制不跳步） Recall@5 = 80.04% HippoRAG 2 = 65.13%（高 ~15pp）
HotpotQA / 2WikiMultiHop SOTA —
生产环境 5 亿条数据，在线检索秒级 一般 RAG 百万级就 OOM

HippoRAG 2（海马体索引理论 + Personalized PageRank）也需离线预建知识图谱，依赖静态全局关系；SAG 把图构建后推到查询时，避开全图重建维护开销。

1.8 落地方案（工程判断）

SAG 目前是检索架构而非完整产品——从零做产品要自建前端/权限/解析引擎/运维，烂尾风险高。

推荐组合：FastGPT（工程成熟度：界面/权限/微信飞书接入）+ SAG 作为知识库实现（MCP 工具丝滑接入）。也可通过 MCP 接入 Codex/Claude Code 等本地 Agent。

二、查询拓展

2.1 在本机 RAG 演进系列中的位置

本机 08-06 RAG 五代全景的谱系：纯向量 → 混合检索 → GraphRAG → Agentic RAG → ?。SAG 填入第五代候选：查询时动态结构层（SQL 超边），与 Agentic RAG 的「检索即 Agent 行为」正交——前者给结构，后者给决策。

2.2 「查询时动态超边」的数学直觉

超边（hyperedge）= 连接多个节点的边。GraphRAG 的静态图把超边固化在离线图谱里；SAG 在查询时用 SQL JOIN 实时 materialize 局部超边——只算问题相关的子图，不算全图。这是典型的 lazy evaluation 换实时性：空间（免全图存储）与维护（免重建）双省。

2.3 三代范式失败点对照（同一条查询）

查询："收购了B公司的企业，其CTO后来加入了哪个项目？"

向量 RAG：命中文档1、2（语义相关）→ 文档3 盲区 → 拒答
GraphRAG：离线图里有 A公司-收购->B公司 / A公司-CTO->张三 / 张三-加入->盘古
          → 顺图两跳可达 → 答对（但建图烧钱+新文档要重算）
SAG：SQL 实体关联 + 二轮挖掘「张三」→ 命中全部 → 答对（无离线建图）

2.4 可解释性链条的工程价值

传统 RAG 调优难在不知道断在哪一环；SAG 的失败可定位：实体提取漏了？同义词扩展没命中？SQL 路径断了？——日志三问即定位。这与本机 error-case-library 的「每次错误定位根因」方法论完全一致。

三、归纳总结

3.1 三代范式总对照

维度 向量/混合 RAG GraphRAG SAG
索引时机 入库向量化 离线建全图（贵） 入库提卡片+实体
关联时机 无 查询时走静态图 查询时 SQL 动态组装
多跳推理 ❌ ✅ ✅（MuSiQue +15pp）
新增文档 增量向量化 可能重算关系 增量插卡
调优 炼丹黑盒 图质量难评 SQL 日志可追溯
弱模型鲁棒 差 中 好（主干是 SQL）
规模 百万级 OOM 图维护难 5 亿条秒级
企业黑话 需微调 实体可覆盖 实体可覆盖免微调

3.2 推荐落地架构

FastGPT（成熟产品壳：对话 UI / 权限 / 微信飞书）
   └─ SAG as MCP 工具（检索内核：事项卡片 + 实体 SQL + 向量并行）
        └─ SQL 库 + 向量库（本地部署，数据不出内网）

四、趋势判断

趋势 1：SAG 将成为 Agent 的数据底座

依据：Agent 工作本质就是多跳——先查 A，用 A 的结论决定查 B，每步输出是下步输入。传统 RAG 给「大概相关的几段」，SAG 给确定的结构化事项与实体，拿到就能直接推理，幻觉概率更低；且精确查询能放大本地小模型优势（弱模型+强结构 > 强模型+弱结构）。文章原判断，与本机 Agent 记忆系列（结构化 vs 向量之争）互相印证。

趋势 2：检索架构的「返璞归真」——被验证的老工具新组合

依据：RAG 演化每步都在加复杂度（向量→混合→图），SAG 反而拉回几十年验证过的 SQL（稳定/可解释/可维护/团队熟）。创新不一定是发明新东西，有时是把已验证的工具重新组合用在对的地方。与 08-23 Agent 去MCP 化重新拥抱 CLI（Smartpig）同一思潮——工程现实主义回音的检索版。

六、拓展应用推荐

6.1 本机落地候选

  1. 企业知识库场景直接对标：用户领域的会议纪要/立项材料/批复文件查询（本文客户场景与飞机设计企业完全同构）——SAG MCP + 现有网关是低试错成本路径
  2. 本机知识检索层升级：bookmarks/notes 1800+ 篇的多跳查询（「引用了 X 论文且批评了 Y 方法的笔记」）——实体 SQL 层可复用 data.json 已有元数据
  3. Agent 数据底座：SAG as MCP 接入 Hermes——给 Agent 确定性结构化检索，替代纯向量模糊召回

6.2 验证优先（铁律）

按 quant-evidence-governance 精神：先本地 docker-compose 部署 + 自造多跳测试集验证命中率，再谈接入——不盲信 80.04% 的 paper 数字（数据集分布≠本机语料分布）。

七、指南分析

7.1 文章质量

  • 场景真实：从客户需求出发（不是论文科普），痛点-方案-落地全链
  • 对照诚实：不贬低 FastGPT（「工业标准，单文档够用」），明确 SAG 是检索内核非产品
  • 数字具体：MuSiQue 80.04% vs HippoRAG 2 65.13%；5 亿条秒级；6 人团队半年调优的对照成本
  • 类比出色：图书馆管理员/预先画大图/事项卡片三个类比把超边讲透
  • 消融实验引用：弱向量模型鲁棒性——最有说服力的企业场景论据

7.2 局限（需独立验证）

  • 1.3K Star 前几天刚开源：生产成熟度未知，「5 亿条部署」是官方口径无第三方审计
  • 入库成本未量化：AI 提炼事项卡片的 token 成本与 GraphRAG 建图成本谁高，文中只说后者贵几万，前者没给数
  • 多轮 SQL 查询延迟：4 跳 = 4 轮 SQL+实体挖掘，「秒级」在大并发下的表现未给数据
  • 实体提取质量依赖：卡片质量 = LLM 提取质量，黑话/缩写的提取错误率未讨论
  • 标题党程度：中等——「再见RAG」是营销话术（SAG 本质仍是 R+A+G，只是 Retrieval 换了实现）
