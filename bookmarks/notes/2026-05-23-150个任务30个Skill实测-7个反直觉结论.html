摘要

TRACE 严选评测在统一 prompt、统一裁判、统一评测口径下，让 30 个 Skill 与"裸模型"跑完 150 组任务级对比。核心发现：装了 Skill 只比裸模型略好（41.3% vs 36.7%），token 消耗平均多 48%，存在"Skill 虹吸"现象（13.3% 过度调用率），Skill 不稳定的最大来源不是模型而是工程链路。强推理模型（xhigh）对复杂 Skill 提升显著（+0.90 均分）但对结构化流程类 Skill 拉不开差距。

核心内容

1. 反直觉一：装了 Skill 不一定更好

  • 150 组对照：Skill 组胜 62 次（41.3%），裸模型胜 55 次（36.7%），平局 33 次
  • Skill 只略占优势，远非压倒性
  • 关键：当 Skill 补充了模型裸能力之外的东西（结构、工具、工作流）才有用
  • 当 Skill 只是"把模型本来就会的事用 Markdown 重写一遍"，反而增加负担

2. 反直觉二：Skill 虹吸——不该用却用了

  • 正确触发率 99%（普通适用），96%（边界适用）——路由系统本身不差
  • 但 13.3% 的本应 no-skill 的请求被错误调用
  • 例："不用上网，帮我想 5 个关键词组合" → 被吸进搜索类 Skill
  • 例："把这句话改得更自然" → 被吸进营销类 Skill
  • 代价：额外上下文、token 成本、更重的工作流

3. 反直觉三：装 Skill 平均贵 48%

  • Token 倍率中位数 1.48，耗时倍率中位数 1.19
  • Token 和耗时正相关（Pearson r=0.73）
  • 多媒体生成、复杂产物组织类 Skill 消耗最高
  • 少数 Skill 反而更省（给出明确流程 → 减少无效探索）

4. 反直觉四：工程债比效果更致命

  • C 维度（结构规范）问题：依赖不清、边界过宽、资源引用缺失
  • 影响：复用、评测、自动化升级越来越脆弱
  • 效果不错的 Skill 如果工程债严重，长期维护成本高

5. 反直觉五：不稳定来自工程链路而非模型

  • 近一半 Skill 至少遇到过工具链、外部调用、长等待问题
  • 从"提示词"到"带工具+脚本+文件+外部服务的完整流程" → 稳定性暴露面指数级增长

6. 反直觉六：强推理模型对 Skill 的影响不均

  • xhigh vs low：均分 3.80 → 4.70（+0.90）
  • 受益大的：隐藏约束、多步交付、强创作类 Skill
  • 不受益的：流程明确、结构性强的 Skill（pdf-extract, xmind-generator）
  • 原因：结构化流程已压缩"易错点"，模型推理强度变化拉不开差距

7. 反直觉七：好 Skill 的共同特征

  • 补充了模型裸能力之外的东西
  • 给出了明确的流程、收束的输出边界
  • 清晰的"该做/不该做"
  • 克制的触发范围

关键概念

  • Skill 虹吸：请求语义贴近某 Skill 描述时，即使本应裸模型直接回答，也被路由到该 Skill
  • Token 倍率：Skill 组平均 token / 裸模型组平均 token，> 1.0 即更贵
  • TRACE 评测：统一的 5 维度 Skill 质量评估框架（效果、稳定性、结构、成本、可迁移性）

能力边界

  • 评测覆盖 30 个 Skill，结论可能不适用于所有 Skill 类型
  • 裁判模型本身可能有偏好
  • 实验环境与真实用户场景存在差异

🔍 借鉴学习进化点

# 点 原文要点 对当前系统的借鉴 行动计划
1 No-skill baseline 先证明 Skill 真的有收益，再装 新建 Hermes skill 前先跑裸模型对比 建立 skill 质量验证流程：创建前先测裸模型
2 Skill 虹吸防御 13.3% 过度调用率，轻任务被套进重流程 Hermes skill 路由需要"克制机制" 审查 skill trigger 条件，增加"不应触发"判断
3 工程债优先治理 依赖不清、边界过宽比效果差更致命 定期 lint 已有 skill 的结构规范 执行 skill-curator-review，清理工程债
4 流程型 Skill 省资源 明确流程+收束输出 → 模型少做无效探索 skill 设计应强化流程约束 优化 skill 模板，增加 explicit do/don't
5 强模型+复杂 Skill 协同 隐藏约束、多步交付类 Skill 最受益于强推理 为复杂 skill 配置强模型，简单 skill 用轻量模型 建立 skill → model 推荐映射
