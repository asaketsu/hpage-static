## 一、内容整理

### 1.1 模型档案（2026-08-13 发布，Apache 2.0）

| 项 | 值 | 部署含义 |
|----|-----|---------|
| 架构 | dense 27B，`model_type: qwen3_5` | **与 Qwen3.6-27B 完全同构**——3.6 的全部部署经验直接迁移 |
| 层结构 | 64 层，3×(GatedDeltaNet→FFN) + 1×(GatedAttention→FFN) 循环 | 混合线性注意力，省内存但对运行时算子有要求 |
| 维度 | hidden 5120 / FFN 17408 / vocab 248,320 | 大 vocab 抬高 embedding 与输出头占比 |
| 上下文 | 262,144 原生（YaRN 可扩 1M） | 架构上限≠可用上限，见 KV 陷阱 |
| 多模态 | 原生视觉塔 | GGUF 视觉 mmproj 分离；量化需保视觉塔 BF16 |
| MTP | 自带 multi-token prediction 头 | 3.8 是弱头（见 1.5），推测解码收益有限 |
| 基准 | Terminal-Bench 73.0（3.6 为 63.4）/ GPQA-D 89.2 / HLE 30.8 | agentic/终端任务大升级；SWE-bench Pro/LiveCodeBench 反而 3.6 略胜 |

### 1.2 显存数学（决策核心）

```
总需求 = 权重文件 + KV cache + 计算缓冲(~1.5G)
KV cache = 256KB/token（实测：8K=2G / 32K=8G / 100K≈25G）
```

**KV 256KB/token 是普通 dense 27B（~80KB）的 3 倍**——混合注意力+大 vocab 的代价。直接后果：24G 卡放 17G 权重后只剩 ~5G KV，**默认 16K ctx 封顶**；想跑 100K 必须双卡 TP。

### 1.3 量化选型（AtomicChat KL 散度实测表）

| 显卡 | 推荐档 | 大小 | KL | top-1 |
|------|--------|------|-----|-------|
| 48G+ | Q8_0 | 28.9G | 0.00064 | 98.9% |
| 32G | AD-Q6_K | 25.0G | 0.00107 | 98.7% |
| **24G** | **AD-Q4_K** | **17.1G** | **0.01126** | **95.6%** |
| 16G | AD-IQ3_S | 13.8G | 0.03247 | 92.4% |
| 12G | AD-IQ2_S | 11.1G | 0.09832 | 87.2%（陡降警戒线） |

两个实测洞见：①**量化名≠质量**——三家 Q4_K_M（16.8/19.0/17.1G）KL 差近 2 倍，选有公开校准数据与 metrics 仓库的构建；②**bits 分配比 bits 数量重要**——AtomicChat 实验证明同样 17-19G，抬升首 4 层+末 12 层+attention gate+state output 的布局让 KL 从 0.0158 降到 0.0073（近半散度消失）。

| 路线 | 适用 | 速度 | 特点 |

### 1.5 八个实测坑（社区汇总）

1. CUDA 13.2 输出乱码（NVIDIA 修复中，避开）
2. MTP 无加速：3.8 弱头，temp1.0 接受率仅 44-48%（3.6 是 80-90%）
3. xhigh 默认烧 3-5× token：日常用 `reasoning_effort=medium`
4. 思考字段：vLLM 在 `reasoning`，llama.cpp 在 `reasoning_content`
5. 长 ctx OOM：KV 3 倍贵，24G 卡上限 16-20K
6. 同名量化不同质：认准 AtomicChat/unsloth 实测构建
7. effort 换档使前缀缓存失效（换档=新系统提示词=新前缀）
8. 3.8 偏好 shell 而非 MCP 工具（Terminal-Bench 训练痕迹），agent 配置需显式约束

## 二、查询拓展

- **KV cache 为何 3 倍贵**：GatedAttention 层的 KV 是标准 dense；但混合架构的 recurrent state（DeltaNet）+ 248K vocab 的 logits buffer 在长 ctx 下显著抬升每 token 显存。AtomicChat 实测口径 256KB/token 含全部注意力状态
- **philbert440 AWQ 为何被 3090 实验室选中**：唯一同时文档化①视觉塔 333 个 BF16 张量保留 ②MTP 头 BF16（`model-mtp.safetensors`）③thinking 模式校准（避免 llm-compressor #2680 空 think 块）的 4bit 构建
- **"5090 206 tok/s" 与 3090 实验室 108-147 的口径差**：5090 数字 = SGLang + NVFP4（Blackwell 专属 4bit 格式）+ DSpark 推测解码三重加持；Ampere 3090 用不了 NVFP4，走 AWQ+MTP（弱头）路线。两个数字都对，但硬件代际+量化格式不可直接比
- **双 4090 并发 ×5.9 的启示**：单流 31-32 tok/s 不起眼，但并发扩展近乎线性（8 并发 185.6 tok/s 未见拐点）——**27B 的正确打开方式是"个人用单流、小团队用并发"**，vLLM/SGLang 的连续批处理是关键放大器
- **temp 与 MTP 接受率关系**（实验室三档实测）：temp1.0→2.34-2.43 平均接受长；0.6→2.60-2.85；0.3→2.58-2.59。官方 thinking 采样 temp=1.0 正是 3.8 MTP 弱的根因——高温摊平了 draft 头要命中的分布

## 三、归纳总结

### 3.1 核心方法论

**先算后买**：`vram_calc.py` 的逻辑（权重+KV+缓冲≤显存）应内化为任何模型部署前的条件反射。本项目的计算器已实测三种典型场景（24G/12G/8G），8G 正确拒绝并建议换小模型。

**选型三问**：①显存多大（定量化档）②要不要并发（定引擎：llama.cpp vs vLLM）③要不要视觉（定路线：Ollama 出局）。

## 四、趋势判断

1. **同构迭代成为工程红利**：3.8→3.6 零成本迁移说明头部模型厂在刻意保持部署兼容性——未来买卡/搭环境按"代际"投资而非"版本"
2. **KV cache 成为新瓶颈**：模型能力竞赛把上下文推到 262K，但消费级显存没涨——**长 ctx 是双卡/大显存专属特权**，单卡用户应理性用 16K
3. **量化进入"实测问责"时代**：AtomicChat 公开 metrics 仓库+复现命令的做法会成为社区标准，"同名不同质"的乱象倒逼选型看数据不看名字
4. **27B 是新的甜点位**：3.6→3.8 的 agentic 提升（Terminal-Bench +9.6）全部发生在 27B 档，单张 24G 卡就能拿到的"前沿级"能力正在下放

## 五、关联分析

- **Qwen3.5-0.8B 零件笔记**：同一架构家族的两端——0.8B 端侧零件（8G Jetson）与 27B 家用主力（24G 卡），`qwen3_5` model_type 贯穿；两者 KV/cache 特性同源
- **lan-llm-farm 项目**：局域网 A100 场景直接采用 Q8_0/AWQ 档做生产服务；本笔记的 KV 数学同样约束 A100 的并发预算
- **edge-llm-quantization 体系**：本笔记补上"消费级 24G 档"的选型空白——端侧(0.8B)→家用(27B)→算力池(A100) 三级显存阶梯完整
- **MTP 弱头现象**与 LuxTTS/TensorRT 经验呼应：推测解码的收益强烈依赖 draft head 与主头的分布对齐，量化/温度任一失配都会让加速归零——跨引擎通用规律

## 六、金句摘录
