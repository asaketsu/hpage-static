## 一、内容详细整理

### 1.1 核心定位：模型到交付之间的那段路

> **WorkBuddy 解决的，不是模型不够强，而是模型到交付之间那段路。**

在国内做 AI 交付，真正难的是把模型放进客户现有的工作。到了政企项目，**网络、数据、采购、账号和运维**会先把方案筛一遍。国外工具再好，无法稳定访问、无法授权、无法进入采购，也只能停在演示阶段。

WorkBuddy 把模型、本地工作空间、权限、技能、连接器和产物放在同一条任务里，让 AI 能够把文件做出来、把修改留下来，再交给人验收。它不能替代业务判断，也绕不开合规，但它离国内的真实工作比一个聊天框近得多。

### 1.2 基本工作流

```
选择工作空间 → 提供资料 → 说清输出要求 → WorkBuddy 规划并执行 → 生成产物 → 查看文件变更 → 人工验收和追问
```

入口分为"日常办公""代码开发""设计创意"三大类。所有任务回到同一套界面：**工作空间**负责限定材料，**权限**负责限制动作，**模型**负责理解，**右侧面板**负责展示产物和变更。

### 1.3 三种模式：问、想、做

| 模式 | 英文名 | 适用场景 | 权限 |
|------|--------|----------|------|
| **仅问答** | Ask | 了解材料，不修改文件 — "这个文件讲了什么" | 只读 |
| **计划** | Plan | 复杂任务，先看计划再确认执行 — 竞品研究/网站改版 | 展示计划，确认后执行 |
| **默认模式** | (Default) | 目标明确、边界清晰、风险较低的日常动作 | 直接执行（高风险动作需确认） |

> **判断方法**：能否在十秒内说清输入、输出和不能做什么？可以就用默认模式；还说不清先 Ask；步骤多、代价高先 Plan。

### 1.4 文件与材料管理

**提供材料的四种方式**：
1. 选定工作空间 → 读取授权目录中的文件
2. 点加号上传文件或文件夹
3. 拖进输入框
4. 使用 @ 引用对话文件或项目材料

> **关键纪律**：文件名带日期/版本号，能减少新旧稿混用。每次任务都要确认它读到的是哪个版本。

### 1.5 权限：最小够用原则

| 权限级别 | 适用场景 |
|----------|----------|
| 默认权限 | 多数办公任务 |
| 完全访问 | 确实需要的场景，开启前先备份 |

- 文件能被本地应用读取，不等于适合交给外部模型
- 含有身份证、合同金额、未发布财报、客户名单、密钥、内部代码时，先做脱敏
- 涉及公司合规的内容，以组织自己的安全规则为准

### 1.6 模型选择

国内项目很难只按单次测评成绩选模型。组织允许使用哪些服务、数据能否送出当前环境、额度是否稳定、发票和支持能不能跟上，都会影响最终选择。

**建议**：刚开始用 Auto。以下情况再手动选择：
- 需要看图片/截图 → 选择支持视觉输入的模型
- 大段代码、复杂表格、长文档 → 更强的上下文和推理
- 成本敏感 → 避免不必要开启高消耗档位

Max/深度思考/强模型通常意味着更长等待和更多积分消耗。**用强模型重做模糊任务，仍然会得到模糊结果。先把资料和验收标准说清，再升级模型。**

### 1.7 技能（Skills）

技能是封装好的工具和操作流程 — 说明、脚本、依赖和参数，让 WorkBuddy 在特定任务上更稳定。

> **技能的意义**：减少"这次记得做、下次忘了做"的波动。

**安装前要看三件事**：它会读取什么 → 会运行什么 → 会把数据发到哪里。

**调用方式**：输入框输入 `/`，或在任务中明确说"使用某某技能"。

### 1.8 专家与专家团

| 层次 | 解决什么问题 | 适用场景 |
|------|-------------|----------|
| **技能** | 会不会使用某个工具 | 文档格式转换、图表生成 |
| **专家** | 以什么专业方法做 | 市场研究、产品需求、财务分析 |
| **专家团** | 多个角色怎样协作 | 需要研究/分析/写作/审阅共同参与的复杂交付 |

> 专家团通常带来数倍积分消耗，别用它处理一段简单改写。

### 1.9 连接器：国内生态

支持腾讯文档、QQ 邮箱、腾讯会议、企业微信、飞书、钉钉、TAPD、腾讯问卷、乐享、ima 等国内服务。

> 连接器数量多本身没有意义，关键是你需要的系统能否稳定授权、检索和写回。

**授权时注意**：确认账号归属、可读空间、写入权限和撤销方式。涉及邮件发送、创建工单、改动云文档时，先要求生成草稿或预览，确认后再执行。

### 1.10 项目

项目提供更高一层的容器，让任务共享指令、资料、连接器、专家和技能。

> 交付团队最怕"只有当时操作的人会用"。项目把固定说明、资料和工具放在一起，让验证过的做法能够被接手。

**一个项目至少准备**：
- 项目目标和不做什么
- 常用输出格式和命名规则
- 团队资料、模板和术语表
- 需要的技能、专家与连接器
- 每次任务的验收标准

### 1.11 助理（移动入口）

把 WorkBuddy 接到微信、企业微信、QQ、钉钉、飞书等移动入口。电脑需要保持开机，WorkBuddy 需要运行。

> **第一次使用助理**：从只读任务开始（如"列出今天工作空间里新增的文件"），确认链路可靠后再尝试生成文件。

### 1.12 自动化

适合重复、规则清楚、即使无人盯着也能安全执行的工作。

> **关键警告**：自动化的前提是流程已经稳定。手动运行时会漏字段、找错目录的任务，改成定时只会更稳定地制造错误。

**建议**：从低频、只读、可核验的任务开始。每月检查一次最近运行记录和失败原因。

### 1.13 记忆力与灵感

- **记忆**：长期记忆从历史对话中提取偏好和背景。定期检查，删除已失效的角色、路径、口径和临时要求。**不要存密码/密钥/验证码。**
- **灵感**：可复用的任务案例。复用前替换资料、权限、品牌和输出路径。

### 1.14 常见问题排查

| 问题 | 排查要点 |
|------|----------|
| 点击发送无反应 | 确认输入框是否有文字、工作空间是否有效、模型是否可用、登录/额度 |
| 长时间停在"准备中" | 等待1-2分钟，查看任务详情和网络状态，暂停其他大任务 |
| 找不到文件 | 检查工作空间、文件在子目录、文件名和扩展名 |
| 产物不完整 | 回到验收标准，告诉它缺哪一列/哪一节/哪几页 |
| 修改了不该动的文件 | 立即停止，记录变更，从备份恢复，修改权限 |
| 消耗比预期高 | 查看模型、专家团、深度思考和重试次数 |

### 1.15 七天学习计划

| 天 | 内容 | 目标 |
|----|------|------|
| 1 | 只读问答 | 三个文件，说明目录结构/总结文档/解释表格字段，全程不修改 |
| 2 | 行动清单练习 | 学会选择工作空间、生成产物、查看变更、继续追问 |
| 3 | CSV 数据体检 | 数据体检+汇总+图表，认识"图表正确"和"数据可靠"的差别 |
| 4 | Plan 模式做 PPT | 先做页纲，确认后再生成，重点练习验收标准 |
| 5 | 安装技能+连接服务 | 记录授权范围，完成最小测试 |
| 6 | 创建项目 | 固定说明+资料+模板，连续跑两个任务 |
| 7 | 创建自动化 | 先手动运行，再设置低频时间表 |

**七天后的判断标准**：能否稳定做到五件事——给任务划边界、选对模式和模型、提供可追踪材料、验收产物与变更、遇到失败知道从哪里排查。

## 二、查询拓展

### 2.1 与国内 AI 交付生态的关系

WorkBuddy 对应的是国内 AI 交付的"最后一公里"问题——模型能力本身不缺，但把模型放进政企客户的工作流时，网络隔离、数据主权、账号体系、采购流程、运维管理五个关卡层层过滤。国外工具（Cursor/Claude Code/Devin）在能力上可能更强，但在这五关上几乎全部卡住。

**WorkBuddy 的价值在于它是国内生态原生的**：接入了腾讯文档/飞书/钉钉/企业微信等国内高频入口，模型可选择国内厂商（混元/GLM/MiniMax/Kimi/DeepSeek），数据链路更可控。

### 2.2 与 Claude Code / Codex 的对比

| 维度 | WorkBuddy | Claude Code / Codex |
|------|-----------|---------------------|
| **定位** | 全能 AI 工作台（办公+代码+设计） | 纯代码开发 |
| **国内生态** | 原生支持（腾讯/飞书/钉钉等） | 无 |
| **模型选择** | 多模型（Auto/混元/GLM/DeepSeek 等） | 单一模型 |
| **权限系统** | 三级权限（Ask/Plan/Default） | 终端权限 |
| **技能/插件** | 技能市场+专家+专家团 | 插件系统 |
| **项目容器** | 有（共享指令/资料/工具） | 无 |
| **自动化** | 定时任务+AI 模板 | 无 |
| **移动端** | 微信/企微/飞书等助理 | 无 |

### 2.3 与 Hermes Agent 的对照

Hermes 也是 AI Agent 体系，目标和工作流有高度相似性：工作空间 ≈ 权限隔离、技能/专家 ≈ 专业 Agent 分工、项目 ≈ 多会话共享上下文、自动化 ≈ cron job。

**差异**：Hermes 更偏向技术用户（命令行/API/飞书交互），WorkBuddy 面向办公用户（GUI/文件管理/国内云服务）。两者的核心设计哲学一致——**把 AI 从聊天框带到真实工作流中**。

## 三、归纳总结

### 3.1 WorkBuddy 能力分层模型

```
┌─ 执行层 ────────────────────────────────┐
│  Default（明确目标直接执行）                │
│  Plan（复杂任务先计划后执行）               │
│  Ask（仅答疑，不修改文件）                  │
├─ 能力层 ────────────────────────────────┤
│  技能（封装工具流程）                       │
│  专家（专业方法）                          │
│  专家团（多角色协作）                       │
├─ 连接层 ────────────────────────────────┤
│  连接器（腾讯文档/飞书/钉钉/邮箱等）          │
│  云端文件                                 │
│  项目资产                                 │
├─ 持久层 ────────────────────────────────┤
│  项目（长期容器）                          │
│  记忆（长期上下文）                        │
│  自动化（定时任务）                        │
│  助理（移动入口）                          │
└─────────────────────────────────────────┘
```

### 3.2 交付成熟度模型

| 阶段 | 特征 | 关键能力 |
|------|------|----------|
| **L1 会操作** | 能跑通基本任务 | 选工作空间、写指令、看产物 |
| **L2 能交付** | 七天后稳定五件事 | 划边界、选模式、提供材料、验收、排查 |
| **L3 可重复** | 把成功过程固化 | 项目+技能+记忆，减少重复说明 |
| **L4 可规模** | 低风险自动运行 | 自动化+敏捷助手，定期维护 |

## 四、趋势判断

### 趋势 1：国内 AI 工具将从"聊天框"转向"工作台"范式

> 依据：WorkBuddy 的完整产品设计（工作空间/权限/技能/连接器/项目/自动化）代表着国内 AI 工具从"问一句答一段"向"完整的交付工作台"演进的明确路径。

### 趋势 2：国内生态集成能力将成为 AI 工具的核心竞争壁垒

> 依据：Miles 反复强调"国外工具再好，进入政企客户环境后要面对网络、账号、采购、数据和运维要求"。WorkBuddy 接入国内模型和常见服务，让这条路短了一些。国内 AI 工具的未来竞争将围绕"能接多少国内系统"而非"模型有多强"。

### 趋势 3：AI 交付的瓶颈将从模型能力转移到"人机协作纪律"

> 依据：全文反复强调的"最小权限""独立工作空间""先 Plan 再执行""看全部变更"——这些不是技术问题，是**使用方法论**。工具能执行后，交付质量取决于人能否管好边界。

## 六、拓展应用推荐

### 6.1 可直接借鉴到 Hermes 的设计

- **三模式权限分层**：Ask（仅查询）/ Plan（先计划后执行）/ Default（直接执行）——Hermes 可以按此分层管理任务，给不同任务类型分配不同权限
- **项目=共享上下文容器**：项目概念可以借鉴到 Hermes 的 topic-session 模型，让长期任务共享配置/资料/验收标准
- **"先 Plan 再执行"**：涉及多文件/高风险操作时，先出计划再确认，减少误操作
- **"查看所有变更"**：每次任务完成后展示新增/修改/删除的文件和行数

### 6.2 适合跟进的学习方向

- 下载 WorkBuddy 体验，重点关注其工作空间/权限/技能/项目四个核心设计
- 对比 WorkBuddy 的"技能"与 Hermes 的"Skills"的异同，思考如何优化自身技能封装
- 学习其"七天学习计划"的方法论——把工具使用从"会操作"推进到"能交付"
