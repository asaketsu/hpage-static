# 一个模型怎么同时兼容 Jetson 和 RK3588？— 跨平台边缘 AI 部署工程实践

> 来源：微信公众号
> URL: https://mp.weixin.qq.com/s/XCGmzwyhwQaOGuIykwUTyQ
> 主题：同一 YOLO 模型在 Jetson（TensorRT）和 RK3588（RKNN）双平台的工程化统一部署
> 评分：⭐⭐⭐⭐⭐ (5/5) — 边缘 AI 跨平台部署领域罕见的系统性工程方法论文档

## 核心结论

**"跨平台兼容"不等于"一个文件两边加载"。** 同一训练权重 `best.pt` 导出 ONNX 后，Jetson 走 TensorRT Engine，RK3588 走 RKNN 模型——两个部署文件、精度策略、Buffer 管理和加速路径完全不同。**真正需要统一的是模型契约（Model Contract）、几何语义、Detection 接口和测试 Reference；真正需要隔离的是平台 Runtime、量化和硬件加速路径。**

## 一、重新定义"同一个模型"

### 部署链路

```
best.pt (PyTorch 训练权重)
    │
    ▼
model.onnx (平台无关的中间表示)
    ├──→ model.engine (TensorRT 为 NVIDIA GPU 编译的执行策略)
    └──→ model.rknn   (RKNN-Toolkit2 为 RKNPU 生成的部署模型)
```

**三个文件不可互换**：

| 文件 | 性质 | 约束 |
|------|------|------|
| `model.onnx` | 计算图 + 张量接口描述 | 平台无关的中间表示 |
| `model.engine` | TensorRT 执行策略 | 受 TRT 版本、设备类型、OS、Compute Capability 约束 |
| `model.rknn` | RKNPU 部署模型 | 受 RKNN 工具链和 NPU 硬件约束 |

**"同一个模型"=** 同一份训练权重 + 同一网络结构 + 同一套输入输出定义 + 同一个模型版本，而非同一个二进制文件。

## 二、模型契约（Model Contract）— 跨平台最先统一的不是代码

跨平台最常见 Bug："Jetson 框正常，RK3588 框特别大"——问题通常不在 NPU，而在输入输出语义没对齐。

### 契约必填字段

| 类别 | 必须写明的内容 |
|------|--------------|
| **输入** | 名称、Shape、颜色空间（RGB/BGR）、Layout（NCHW/NHWC）、数值范围、数据类型 |
| **输出** | Tensor Shape、Box 编码（xywh/xyxy）、类别起始位置、是否含 Objectness、Sigmoid 是否已执行、Decode/NMS 在模型内部还是外部 |
| **几何** | Resize 比例、Padding 颜色、舍入规则、坐标恢复公式 |

### 常见不对齐 Bug

| Bug 类型 | 示例 |
|----------|------|
| 颜色空间 | 一端 RGB，另一端 BGR |
| 归一化 | 一端在 CPU 除以 255，另一端在转换配置重复归一化 |
| Layout | 一端 NCHW，另一端 NHWC |
| 输出格式 | 一端输出 xywh，另一端按 xyxy 读取 |

> 契约的作用不是增加文档负担，而是把"模型能跑"变成**可测试的接口**。每次更换 YOLO 版本/输入尺寸/输出 Head，只要契约变化，两端必须同时通过兼容性测试。

## 三、前处理可以特化，但数学结果必须一致

| 平台 | 硬件加速路径 |
|------|------------|
| **Jetson** | CUDA / VIC 完成 NV12→RGB、Resize、Normalize |
| **RK3588** | MPP 解码、RGA 缩放，Buffer 交给 RKNN |

**不需要代码表面一致，需要对齐数学结果。**

### Golden Input 验证

对同一张固定测试图，两端保存进入模型前的 Tensor，检查：

- Shape
- 颜色通道
- 最小值/最大值/均值
- 若干固定位置像素

### Letterbox 参数对齐

建议把预处理结果描述成结构体：除 Tensor 外，同时返回 `Scale`、`pad_x`、`pad_y` 和 Padding 颜色。坐标恢复只消费这组明确参数，不重新猜测输入尺寸。

## 四、Backend 接口设计 — 把 Runtime 差异压缩在边界内

### ❌ 最难维护的结构

```
jetson_detect.cpp  ← 各自包含：取流→前处理→推理→Decode→NMS→跟踪→业务规则
rk3588_detect.cpp  ← 几个月后必然分叉
```

**分叉模式**：一端改了类别表，另一端仍用旧顺序 → 修复 Letterbox，另一端坐标恢复仍偏差 → 阈值/日志字段逐渐不一致。

### ✅ 推荐：IBackend 抽象

```
业务层：detector.detect(frame) → std::vector<Detection>
              │
    ┌─────────┴─────────┐
    │   共享 Postprocessor  │ ← Decode + NMS + 坐标恢复
    │   (统一 TensorView)   │
    └─────────┬─────────┘
         ┌────┴────┐
         │         │
  TensorRTBackend  RKNNBackend
  ──────────────  ─────────
  • Engine         • RKNN Context
  • Exec Context   • Input 设置
  • CUDA Stream    • Runtime 执行
  • Device Buffer  • Output 获取
```

**关键设计原则**：

- 两端都输出统一 `TensorView`，交给共享 Postprocessor
- 业务层只调 `detector.detect(frame)`，读取类别/置信度/坐标/时间戳/模型版本
- Tracking/告警/控制/可视化**不需要知道**这一帧来自 TensorRT 还是 RKNN
- 平台差异被压缩在窄边界中

## 五、算子兼容性要在训练阶段提前进入决策

### 算子选择优先级

| 优先级 | 算子 | 说明 |
|--------|------|------|
| ✅ 优先 | Conv、Depthwise Conv、Add、Concat、Pooling、Resize、常见激活 | 两套工具链均稳定支持 |
| ⚠️ 谨慎 | 自定义算子、GridSample、非标准 Attention、动态循环、Runtime Plugin | 必须尽早验证能否展开为标准 ONNX 子图 |
| ❌ 避免 | 仅单平台 Plugin | 某模块在 TensorRT 有 Plugin，不等于 RKNN 也能等价实现 |

> 模型精度提升 0.3 mAP，却导致其中一块板无法部署，工程收益可能为负。

### Shape 策略

| 策略 | 建议 |
|------|------|
| **固定 Shape** | ✅ 推荐 `1×3×640×640` 先跑通两条链路 |
| 动态 Shape | TensorRT 可通过 Optimization Profile 支持，但增加 Profile/Context/Buffer/测试组合复杂度；RKNN 工具链有自己的 Shape 与编译约束 |

## 六、FP16 与 INT8 不可能靠逐元素相等验收

### 量化产物差异

| 平台 | 常用精度 | 特点 |
|------|---------|------|
| **Jetson** | FP16 | 速度与精度折中 |
| **RK3588** | INT8 | 充分利用 NPU 算力 |

由同一份 FP32 ONNX 生成两种低精度产物后，**数值不可能逐 bit 一致**。正确目标是确认它们对共同 Reference 的偏差可控。

### RKNN INT8 量化要点

- **校准集必须覆盖部署现场**：目标尺度、照明、背景、模糊、遮挡、空场景
- 随意选几十张无关图片，转换成功 ≠ 量化模型可用
- 转换日志无报错 ≠ 任务精度通过验收

### 验证顺序（每次只增加一个变量）

```
1. PyTorch ←→ ONNX Runtime 一致性确认
2. Jetson: FP32 先跑通 → 再验证 FP16
3. RK3588: 非量化模式验证结构和后处理 → 再引入 INT8
```

## 七、两块板分别对齐 Reference，不互相当标准答案

### 四层对齐法

| 层级 | 对齐内容 | 说明 |
|------|---------|------|
| **第一层** | 前处理 Tensor | Shape、颜色通道、min/max/mean、固定位置像素 |
| **第二层** | Raw Output | Shape 和统计分布 |
| **第三层** | Decode 后结果 | 类别、Box、Score |
| **第四层** | 任务指标 | Precision/Recall/mAP |

### Reference 流程

```
Golden Dataset
    │
    ▼
PyTorch / ONNX Runtime FP32 → Reference（保存输入 Tensor + 关键层输出 + Raw Tensor + Detection 结果）
    ├──→ Jetson TensorRT 结果 vs Reference → 偏差可控？
    └──→ RK3588 RKNN 结果 vs Reference → 偏差可控？
```

**诊断逻辑**：

- 若 TRT 与 ONNX 接近，RKNN 偏差明显 → 沿 RKNN 链路检查
- 若两端都与 ONNX 不一致 → 回到模型导出或共享后处理
- 用 Reference 思路，避免在两个平台之间来回猜测

## 八、模型 Manifest — 版本一致性

### model.yaml 示例

```yaml
model_name: yolov8s-custom
model_version: v1.3
input_size: [1, 3, 640, 640]
num_classes: 5
labels: [person, helmet, gloves, vest, boots]
output_format: xywh + conf + cls  # sigmoid in-graph, NMS out-graph
preprocess:
  color_space: RGB
  layout: NCHW
  normalize: /255.0
  letterbox: true
  pad_color: [114, 114, 114]
postprocess:
  nms_threshold: 0.45
  conf_threshold: 0.25

backends:
  jetson:
    file: models/yolov8s_v13.engine
    precision: FP16
  rk3588:
    file: models/yolov8s_v13.rknn
    precision: INT8
    mean: [0, 0, 0]
    std: [1, 1, 1]
```

Jetson 和 RK3588 条目指向不同文件和精度配置，但共享同一 `model_version` 和契约版本。

### 日志必须携带

模型版本 + Backend + Precision + 契约版本。

## 九、平台优化不应为"统一代码"被抹平

跨平台抽象 ≠ 最低公分母设计。

### ❌ 错误做法

强制两边都走 CPU OpenCV、频繁内存拷贝、同步推理 → 代码看起来相似，但**同时牺牲两块板的性能**。

### ✅ 成熟边界

| 层 | 职责 |
|----|------|
| **共享层** | 规定输入输出、几何语义、业务结构、测试口径 |
| **平台层** | 选择最适合该 SoC 的数据通路和执行方式 |
| **特化后处理** | Jetson 用 GPU NMS、RK3588 用 CPU NMS — 分别实现，但通过同一接口输出相同语义 Detection |

### 各平台可发挥的硬件能力

| Jetson | RK3588 |
|--------|--------|
| CUDA | MPP（媒体处理器） |
| TensorRT | RGA（2D 图形加速） |
| CUDA Stream | RKNN/NPU Core |
| Device Buffer | DMA-BUF |

## 十、五级验收标准 — 怎样定义"兼容成功"

| 级别 | 验收标准 |
|------|---------|
| **第一级** | ONNX 可分别转换为 Engine 和 RKNN |
| **第二级** | 同一张图在两端都能完成推理 |
| **第三级** | 类别、Box 与 Score 在允许误差内对齐 Reference |
| **第四级** | 两端分别满足延迟、内存、功耗和稳定运行要求 |
| **第五级** | Application 不因更换平台而修改业务代码 |

**达到第五级**：换一块板主要替换 Backend 和平台配置，Tracking/告警/控制/上层接口保持不变。

### 测试集要求

不能只有几张正常图片，必须覆盖：

- 小目标 / 遮挡 / 边缘目标
- 空场景 / 模糊 / 强光 / 密集目标
- 低置信度附近样本 / NMS 边界
- 坐标恢复误差 / 量化后类别翻转
- 长期运行：内存增长、Buffer 回收、异常输入、Runtime 恢复行为

## 💡 分析与借鉴

### 对 Jetson/RK3588 双平台部署的直接价值

| 启发 | 内容 |
|------|------|
| **IBackend 抽象** | 直接可用于 StructGen/视觉检测项目的多平台部署 |
| **Model Contract** | 项目中应强制维护 model.yaml 契约文件，消除颜色/归一化/Layout 不对齐 |
| **Reference 对齐流程** | 四层对齐法可直接照搬为 CI/CD pipeline |
| **五级验收** | 可作为跨平台部署的 CI Gate 标准 |

### 工程模式提炼

| 模式 | 核心思想 |
|------|---------|
| **共享 Core + 平台 Backend** | 业务逻辑与平台实现隔离 |
| **每次只增加一个变量** | FP32→FP16 / 非量化→INT8 分步验证 |
| **分别对齐 Reference** | 两平台不互相当标准答案 |
| **契约驱动** | 接口变化触发兼容性测试 |

### 与 Hermes Agent 设计的元启发

| 本文概念 | Hermes 对应 |
|---------|-------------|
| IBackend 接口 | Skill 的统一接口（skill_view 输入输出标准化） |
| Model Contract | Skill 的 YAML frontmatter（trigger/description 标准化） |
| 五级验收 | 任务完成定义（exit_code=0 + tests>0） |
| 平台特化保留 | 四猫团队各司其职，统一输出 |
