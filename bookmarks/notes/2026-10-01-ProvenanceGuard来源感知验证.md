## 一、命名盲区：cross-source conflation（跨来源混同）

**一条断言在证据池某处是真的，但被归因到了错误的来源。**

- 客服例：「根据账户记录，这个套餐包含 30 天退款窗口」——退款窗口是真的，但写在**政策文档**里不在账户记录里。证据汇成一池后看起来被支持了；分开看归因就是错的。用户拿"你们账户记录写了 30 天"去主张权利，麻烦就来了
- 临床例：病历工具取出的**具体患者用药细节**被当成"医学文献发现"呈现——错误归因与错误事实一样有害
- 现有检查器（RAGAS faithfulness/MiniCheck/AlignScore/SummaC）全问"断言是否被可得证据支持"，而**证据先被汇到一起**——池化之后答案永远是"有"。**faithfulness 分数对 MCP agent 不够**

## 二、五步流水线（黑盒 MCP agent 之上的生成后验证层）

读 MCP trace（工具输出+来源 ID），不重训 agent：
1. 答案拆成逐条断言（本地 LM）
2. 每条找最相关来源（MiniLM）
3. 检查该来源是否真支持它（DeBERTa NLI）
4. 该来源 vs 答案点名的来源比对
5. 逐断言来源裁决 + 答案级放行/拦截

设计要点：**绝不把证据塌缩成匿名上下文——来源身份贯穿到最后裁决**（这是能输出"断言→来源 ID"的根本）；**严格检查字面值**（不存在的数字/日期/标识符不能因"听起来合理"放行）；RARR 风格修复环节（基于来源的修订或安全兜底，再验一次）；**刻意保守**（宁可错拦送复核，不放无支持断言）。本地配置约 **0.5 秒/答案**（NLI/路由仅几十 ms）。

## 三、结果与两个难点（"已解决/未解决"分得极清）

主测（医疗 agent，281 trace，40 答案 361 断言人工核）：
- 专家判 139 条不应通过 → **抓住 138**（漏 1）
- 同时拦下 67 条专家认为有支持的（保守取向的代价）
- 来源识别 **~86% 挑对**
- 对比四检查器（断言级判定）：ProvenanceGuard 之外，MiniCheck ~0.77/RAGAS 0.758/AlignScore 0.662/SummaC-ZS 0.436，且**全都不输出"哪个来源"**

两个难点（作者自曝）：
| 测试 | 结果 | 含义 |
|---|---|---|
| 明确来源错误（50 例换点名来源，证据不变） | **50/50 全抓** | "指向的那份里没有"——能查 |
| 相似来源选择（更难测试） | 拦截 F1 0.846，但**挑对来源仅 50.3%** | "选中的那份对不对"——还是瓶颈 |

**yibie 划界读法：它能发现"指向的那份里没有"，还不保证"选中的那份是对的"。**

修复环节的诚实：173 个被拦答案全解决，但 **144 个以兜底文本收场**（"我不能验证这个"）而非实质改写——**闸门的价值在"不说错话"，不在"替你说对话"**。（重建多来源 trace 上 59 个仅 2 个兜底。）

## 四、💡 对我们的价值分析

### ✅ 已在做的
- "来源身份贯穿裁决" = 我们笔记的 URL_ID/溯源注记习惯（技术/经验分层标注）；决策收据（Jev）与决策审计思想同源
- NVIDIA NVFlow 金融 agent 跟进（SEC 摘录接地验证）——验证了我们盯"证据链"方向的行业共识

### ⚠️ 可改进的（差距）
- **我们的工具输出全部池化**：terminal/web_extract 结果进上下文后来源身份即丢失——笔记引用原文与我的推断混排时无机器可查的边界（目前靠"领域扩展标注"人肉区分）
- 笔记的"原文 fidelity"检查无验证器：分析补充型笔记的分层标注靠自觉，无 gate

### 🔥 重点行动
1. **笔记溯源最小机制**：bookmark-reader 的 7 模块校验加一条"引用块校验"——直接引语必须带 URL/文件路径锚点（机器可查），分析扩展段必须带"【扩展】"标记——ProvenanceGuard 思想的轻量版
2. **error-case/经验卡加来源 ID**：沉淀时记录"证据来自哪个 session/文档"，防跨来源混同在经验复用时发生（案例挂错项目=conflation 的碳基版）
3. 跟踪 NVFlow（github.com/NVIDIA/nvflow）的接地验证阶段实现——金融 SEC 场景与我们 A 股管线的披露核验同构

## 五、内容整理（归纳总结与关联分析）

**归纳总结**：命名 cross-source conflation——事实真但归因错，落在所有池化证据的 faithfulness 检查器的盲区。五步流水线（拆断言→找来源→NLI 验支持→比对点名来源→逐断言裁决），关键设计=来源身份不塌缩+字面值严格+保守取向。138/139 拦截、86% 来源识别、50/50 假来源全抓但相似来源仅 50.3%；修复 144/173 走兜底（不说错话>替你说对话）。0.5s/答案离线闸门。

**关联分析**：这是 9-10 月"显式契约化+证据链"主线的**验证层收官**——Jev 决策收据（判断的来源）、Zep 四时间戳（事实的时间边界）、Schema 防呆（数据的声明边界）、ProvenanceGuard（**证据的来源边界**）：四件套合起来就是完整的"可审计 Agent 输出"——每句话可答：谁说的/何时有效/声明边界/依据哪个工具。与 ROSClaw 的 Artifact Reference（图像 provenance 全可查）在视觉侧早已同构。周论文候选升级：**"可审计输出四层"**（收据/时间/声明/溯源）统一框架，四篇文献支撑，新颖性和体系性都够。

## 七、趋势判断

1. **"来源感知"将成为 MCP 生态的验证标配**：工具越多池化越严重，conflation 命名后会被当 bug 而非特性——预测 MCP 规范层出现 provenance 字段
2. **验证器分化出"接地"赛道**：faithfulness（支持吗）→grounding（指着哪份）→provenance（对得上点名的那份吗）三层精细化
3. **保守兜底成为数据敏感场景默认**："我不能验证这个"的 144/173 取向会从医疗扩散到金融/法律——与 Agent 的 NOT_EVALUED/null 出口三处收敛
4. **字面值严格检查回潮**：数字/日期/标识符的精确匹配（而非语义相似）重新被重视——LLM 时代"听起来对"是最危险的放行理由

## 八、指南分析（怎么用这篇文章）

- 自查 agent 输出：抽 10 条带"根据 X"的答案，逐条核对 X 里真有那句话——conflation 率超 20% 就需要溯源层
- 给验证器选型：池化 faithfulness 检查器对多工具 agent 结构性不够——直接上溯源感知
- 引用注意：86% 与 50.3% 必须并排引用（能力边界诚实），单引 86% 误导
