# Skill 是 Agent 时代的能力商品

> 来源：微信公众号（作者未署名，疑为小路/独立开发者）

---

## 一、核心论点

> Agent 不是抹平能力差距，而是**放大能力差距**。用户出现 **K 型分化**。

- 头部用户已在搭系统（文档/规则/memory/loop/MCP/CLI/工具调用/权限/上下文工程/定时任务/文件系统/Skill）
- 普通用户还在问聊天框
- **Skill 是弥合这个差距的关键**：把专家经验封装成可分发、可复用的能力单元

### Skill 一句话定义

> 把专家经验、工作流、品味和工具调用封装成可分发、可复用、可迭代的 Agent 能力单元。

Skill ≠ Prompt。Prompt 难分发、无版本管理、缺安装语义。Skill = Prompt + 规则 + 示例 + 工具调用 + 文件结构 + 脚本 + 依赖 + 使用说明。

---

## 二、Skill 的核心：把人的经验外化

真正有价值的部分是把隐性判断固化进去。要求创作者同时懂三件事：

| 能力 | 作用 |
|------|------|
| **传统专业知识** | 知道什么结果算好（设计/法律/写作/健身等隐性判断） |
| **AI 的上下限** | 知道模型什么能做、什么做不稳、什么必须工程化兜底 |
| **产品化思维** | 知道用户场景、使用门槛、反馈路径、稳定性要求 |

### 作者的 Skill 实战案例

| Skill | 核心经验外化 |
|-------|------------|
| **PPT Skill** | 10种页面布局 + 5套主题色 + 字体三级分工 + hero/non-hero 节奏交替。AI 不从零发明版式，只在高质量骨架里填充 |
| **社交媒体卡片** | 11个内容品类 + 2套视觉系统 + 28个版式骨架 + 截图美化优先 + AI生图仅兜底。3:4竖版，1秒决定停不停 |
| **Logo Generator** | 不让图像模型一把梭。先生成 SVG 变体→再展示图→再 WebGL 背景。分层用最适合的技术处理 |
| **AI Desk Card** | Agent 接管屏幕边缘物理信息位，延伸到硬件环境 UI |

## 三、好 Skill 的架构：中心短，辐射厚

```
Skill 目录结构
├── SKILL.md          ← 入口：高信号流程和判断（短）
├── references/       ← 重文档和领域材料，按条件读取
├── scripts/          ← 确定性逻辑，Agent 调用而非重写
├── assets/           ← 模板/schema/示例/字体/主题/版式骨架
└── 配置文件           ← 首次配置、偏好、历史记录
```

> 文件系统本身就是上下文工程。不要把复杂内容一次性塞给模型。

### 关键设计原则

1. **description 是路由触发器，不是宣传语**
   - ❌ "这个 Skill 可以生成漂亮 PPT"
   - ✅ "当用户需要把文章、大纲或演讲内容转成可演示 HTML PPT 时加载"

2. **每一句都要问**：没有这句，Agent 会不会做错？如果不会，就删

3. **gotchas 是最高价值内容** — 正向原则模型已经知道，负面边界才是专家经验

4. **"中心短，辐射厚"** — SKILL.md 只放流程和判断，重内容放子目录按需加载

---

## 四、Thin Harness, Fat Skills

```
架构对比：

❌ 大而全 Harness：工具定义+协议+长文档塞满上下文
   → 高延迟 + 高 token 成本 + 更多误用

✅ Thin Harness, Fat Skills：
   Harness（薄）：跑模型循环、读写文件、管理上下文、执行权限、安全边界
   Skill（厚）：流程、判断、领域知识、模板、脚本、资产、gotchas、eval
   确定性工具下沉给 CLI/scripts/API
   模型留在：理解、判断、综合、取舍、表达
```

> 这正是 Hermes 的架构：薄 Gateway + 按 Skill 索引匹配加载 + 确定性操作用 terminal/scripts。

## 五、Skill 质量维护 = 代码质量维护

### 生命周期

```
1. 先用无 Skill 的 Agent 跑真实任务 → 找到它会错在哪里
2. 基于真实 query 写 eval（正例/反例/forbidden load）
3. 先调 description → 确保该加载时加载，不该加载时不加载
4. 写主体时删显而易见的内容 → 只保留会改变模型行为的判断
5. 失败案例追加到 gotchas → 不不断加长主流程
6. 跨模型测试 → 看不同编排模型对 Skill 触发和执行的差异
```

### 每个 Skill 都是一种税

- 进入索引后：每个会话为 name + description 付上下文成本
- 被加载后：后续对话为主体内容付成本
- **没有这句 Agent 会不会做错？不会就删。**

## 六、设计 Skill 的本质：把品味变成约束

模型默认收敛到平庸模式：Tailwind 大色块、紫色渐变、emoji 堆砌、Inter 字体、发光、过度圆角、无意义动效、信息密度失控。

**设计 Skill 的核心**：替用户排除绝大多数会变丑的选项。

| 约束类型 | 示例 |
|---------|------|
| 颜色 | 不用纯白纯黑；不提供任意 hex 输入，只给验证过的主题色板 |
| 视觉 | 不用紫色多彩渐变/发光/大面积 blur 作为主视觉捷径 |
| 动效 | 动画只在必要时用，且只动 transform 和 opacity |
| 图片 | 真实摄影和截图美化优先，AI 生图仅兜底 |
| 排版 | 文字根据图像主体/明度/可读区域自适应落点/字色/遮罩/断行 |

> 好看不是玄学，而是可拆解、可编码、可检查的行业常识。

## 七、Skill 生态方向

### 分发策略
- **GitHub**：代码型 Skill 的天然托管地，版本管理 + 开源 + 跨平台
- **小红书**：视觉内容和使用案例分发，评论体系和用户审美
- **平台 Skillhub**：应用商店式体验优化 + 运营推荐 + 商业转化

### 防盗不是靠藏
> 开源覆盖更多平台 + 自媒体让用户知道源头 + 持续迭代建立领先 + 社区案例形成品牌资产

### 行业 Skill
- 健身教练：用 Agent 维护会员饮食/训练/提醒，提高客户粘性
- 法律：文本处理/条文审查/格式检查做成辅助 Skill，核心判断仍由人完成
- 餐饮/活动：图文 Skill 把真实图片和故事包装成可传播内容

## 八、Skill 与 Gene 的关系

| 维度 | Skill | Gene/Capsule |
|------|-------|-------------|
| 来源 | 人工手写，有明确创建者 | 从重复执行成功路径自动沉淀 |
| 特点 | 明确边界/流程/版本 | 带成功率/变异历史/适用上下文 |
| 适合 | 专家经验/审美/行业 SOP/工具不变式 | 从试错中捕捉可复用经验 |
| 落地 | 当前更可落地（可写/可审/可发布） | 长期方向 |

> **理想形态**：人定义品味和边界，Agent 负责收集证据、提出改动、补充 eval、维护长尾经验。

## 💡 对我们的价值

### ✅ 高度吻合（Hermes 已在做）
- **Thin Harness, Fat Skills** — Hermes Gateway = Thin Harness，Skill 目录 = Fat Skills
- **中心短辐射厚** — SKILL.md 入口 + references/scripts/assets 子目录
- **description 作为路由触发器** — 我们的 Skill frontmatter description 就是这个用途
- **gotchas 优先** — 我们的 pitfalls 部分正是负面边界
- **Skill 即税** — 我们 43 个 cron + 上百 Skill，每个都在抢上下文

### ⚠️ 可改进
1. **eval 体系缺失** — 我们没有正例/反例/forbidden load 的系统化测试。应建立 Skill eval
2. **跨模型测试** — 我们只用 glm-5.1 主模型，Skill 缺乏跨模型验证
3. **"没有这句会不会做错"审计** — 应定期精简 Skill 内容，删冗余
4. **设计约束** — 我们的 html-quality-standards 和 bookmark-reader 已有部分，但可以更系统化

### 🔥 行动建议
1. **Skill eval 机制**：为核心 Skill（bookmark-reader/feishu-card-table 等）建 eval 测试集
2. **Skill 瘦身审计**：按"每个 Skill 都是一种税"原则，审计高频加载的 Skill 是否有冗余
3. **自动沉淀验证**：我们的 auto-evolver / self-evolution 已在做 Gene 雏形，需加强"成功路径→Skill 补丁"的闭环
