领域专长才是真正的护城河：Agent 时代的价值重估

摘要

Aaron Brethorst 提出：写软件的核心从来不是写代码，而是在脑子里先建立领域模型。Agentic AI 切断了"领域理解→代码"之间的必要联系——你现在可以不建模型就产出软件。这打破了一个假设：需要先理解领域才能构建系统。核心论点：Agent 时代，"你能否判断输出是否正确"比"你能否构建它"更重要。领域专家（调度员、临床编码员、精算师）配上 Agent 反而比不懂领域的全栈工程师更有效。

核心内容

1. 编程的本质是领域建模而非代码转录

写软件最困难的部分从来不是写代码本身。在交付薪酬系统前，你需要理解扣押令、税前扣除、薪资期间横跨税率变更的处理。在交付公交应用前，你需要学懂 GTFS 数据源、为什么 trip 和 route 不是一回事、一辆"准时"的公交为什么仍然可能是错的。代码只是对领域理解的转录，获取理解才是工作本身。

2. Agent 切断了一条路径但保留了另一条

Agent 之前：
工程师可以学领域（慢但可行）
领域专家无法学编程（太慢不可行）

Agent 之后：
工程师的"翻译"优势变廉价（Agent 供应代码）
领域专家的"判断"优势仍然稀缺（无法 prompt 出来）
工程师失去了学领域的动力（因为 Agent 可以直接生成代码）
领域专家获得了生成代码的能力（之前没有的路径）

3. 最有价值的人：双层验证者

能同时验证两个层面的人最有价值：
1. 生成的代码是否结构合理（工程判断）
2. 代码产出的答案是否真实正确（领域判断）

Agent 做转录，人做判断——而且是两次判断。

4. 对工程师的建议

机械技能（将清晰想法转为干净代码）的价值大幅下降。仍然稀缺的是对某个真实领域的深度已验证模型。建议：
选择一个行业、一种工具、一个监管体系、一个物理过程
像学编程语言那样深入学它
这就是 Agent 做不了的事，也是现在最值钱的事

关键概念

领域模型（Domain Model）：对特定领域规则、流程、边界条件的心理表征，只能通过长期实践积累
双层验证（Dual-Layer Verification）：同时验证代码质量（工程层）和输出正确性（领域层）
绑定约束转移（Binding Constraint Shift）：从"能否构建"转移到"能否判断是否正确"
地面真相（Ground Truth）：领域专家通过多年实践获得的"正确答案直觉"，Agent 无法替代

能力边界

论点主要针对业务逻辑密集型软件，对纯基础设施/系统编程的适用性有限
低估了优秀工程师学习新领域的速度
高估了领域专家使用 Agent 工具的意愿和能力
没有讨论 Agent 自身的领域验证能力是否会随时间提升

最佳实践

Agent 辅助开发中，测试用例应来自领域专家而非工程师
代码审查需要领域专家参与验证输出正确性
工程师应主动深入 1-2 个垂直领域构建"领域+工程"双优势

🔍 借鉴学习进化点

# 点 原文要点 对当前系统的借鉴 行动计划
1 双层验证模式 领域专家+工程师同时验证代码和答案 Hermes Skill 评价体系需要引入"领域正确性"维度，不仅是代码质量 在 skill-doc-standard 中增加领域验证检查项
2 领域知识不可替代 "你无法 prompt 出 1000 次薪资对账的隐性知识" Agent 的 Memory 系统是存储领域知识的核心基础设施 强化 memory-system 的领域知识结构化存储能力
3 绑定约束转移 从"能否构建"→"能否判断正确" Hermes skill 质量评估应侧重"能否正确判断输出质量"而非"能否生成代码" 为 kanban-worker 增加"领域验证"阶段的 skill 评估
4 领域专家+Agent>工程师 不懂领域的工程师配 Agent 反而不如领域专家配 Agent 内容生产流程中应引入领域专家前置验证环节 在 content-meow 的产出流程增加领域审查步骤
5 测试用例来自领域 "你写不出'driver 不能超过 11 小时'的测试，除非你知道规则" auto-test 生成应从领域文档提取测试约束，而非从代码结构推断 调研从领域文档自动生成约束测试的可行性
