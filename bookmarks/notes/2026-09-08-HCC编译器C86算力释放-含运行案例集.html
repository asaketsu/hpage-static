一、内容整理

1.1 HCC 是什么

HCC 是海光的 C/C++/Fortran 编译器工具链，属于 C86 DevKit（海光平台开发套件）性能优化模块的一部分：

C86 DevKit
├── 安全功能模块：机密计算CSV / 可信计算 / HCT密码技术
└── 性能优化模块
    ├── 海光编译器（HCC ←本文 / HGCC / HJDK）
    ├── 数学库 / 系统库 / JDK
    └── 海光性能工具
  • 技术底座：基于开源 LLVM 16.0.4 + Flang 开发（衍生增强，不是从零自研）
  • 语言覆盖：C / C++（Clang 前端）+ Fortran（Flang 前端，flang1/flang2 两组件）+ 三语言的 OpenMP 扩展
  • 定位澄清（原文专门强调）：不是抛弃 GCC/LLVM，而是基于 LLVM/GCC 做衍生增强

1.2 海光为什么要自研编译器（四大理由）

理由一：自研硬件特性上游跟进滞后
- C86 处理器兼容标准 x86-64，但拥有自研微架构、指令及指令集、内生安全、扩展向量指令（以 C86-4G/H 为例）
- GCC/LLVM 上游社区补丁合并周期长、迭代慢，无法第一时间释放硬件能力

理由二：通用编译器对 C86 微架构不是最优解
- GCC/LLVM 的 x86 后端优化模型主要面向 Intel/AMD 经典微架构
- 对 C86 的缓存层级、流水线、访存行为理解有限

理由三：安全与信创自主可控
- 关键基础设施不能完全依赖国外工具链

理由四：软硬协同 + 国内负载定向调优
- GCC/LLVM 追求普适性；HCC 面向国内真实负载定向优化：数据库、大数据、虚拟化、AI 推理、国产中间件

1.3 架构与工作流

  • Clang：C/C++ 前端 + 完整编译驱动（预处理→LLVM IR→优化→目标代码→可执行文件）
  • Flang：Fortran 前端（flang1 + flang2），源码→LLVM IR→优化→代码生成

1.4 安装与使用（原文实操要点）

环境：C86 处理器平台
OS：  CentOS-8.0 / Ubuntu-18.04 / Ubuntu-22.04 / openEuler-24.03 / KylinOS-v11
依赖：libstdc++ ≥3.4.19；glibc ≥2.17（≥2.31 更好——能识别海光平台）

下载：https://download.sourcefind.cn:65024/8/main/c86-devkit/latest/compiler/hcc
安装：tar -zvxf hcc-{version}.x86_64.tar.gz
环境：cd /path/to/install/hgcc && source setenv_hygoncc.sh
编译：clang hello.c -o hello        # C
      clang++ hello.cc -o hello     # C++
      flang hello.f90 -o hello      # Fortran
链接：默认系统 ld；LLVM lld 用 -fuse-ld=lld 指定
运行库：export LD_LIBRARY_PATH=<compdir>/lib:<compdir>/lib32:$LD_LIBRARY_PATH

二、查询拓展

2.1 LLVM 衍生编译器的行业谱系

海光 HCC 走的"LLVM 衍生增强"路线在业界有成熟先例：Intel ICX（基于 LLVM，替代经典 ICC）、AMD AOCC（基于 LLVM，针对 Zen 微架构调优）、Apple Clang、华为毕昇编译器（OpenCV 社区 + BiSheng for Java）、以及国产 AI 编译器谱系（TVM 系）。HCC 对标的是 AOCC 模式——同一 ISA（x86-64）但自研微架构，上游优化模型不适配，于是 fork 一条深度定制分支。这条路线的工程合理性：LLVM 的 pass 框架允许厂商在"后端调度 + 向量化 + 循环优化"三层插入自研 pass，不必动前端。

2.2 Clang/Flang 双前端格局

Clang 是 LLVM 官方 C/C++ 前端，工业成熟度最高。Flang 的历史值得注意：经典 Flang（来自 PGI/NVIDIA 捐赠）分 flang1（F18 语义解析）和 flang2（LLVM IR 生成）两段；新版 Flang（"New Flang"/flang-new）已单段化并进入 LLVM 主干。HCC 2.9.0 基于 LLVM 16.0.4，其 Flang 应为 flang1/flang2 经典架构（原文明确提到两组件），Fortran HPC 代码迁移时需注意与 gfortran 的 OpenMP 行为差异。

2.3 为什么"兼容 x86-64"还需要定制编译器

ISA 兼容 ≠ 性能最优，这是计算机体系结构的经典命题。同一份 x86-64 机器码，在不同微架构上的 IPC 差异可达数倍，取决于：指令调度表（schedule model）是否匹配流水线、向量化宽度选择（AVX2 vs AVX-512 vs 自研扩展）是否匹配实际执行单元、内存访问模式是否匹配缓存预取器设计。AMD 在 Zen 系列上维护 AOCC 的动机完全同构——上游 LLVM 的 znver 调度模型更新永远滞后于新 Zen 发布，AMD 自家分支可以同步芯片 tape-out 调优。

2.4 PGO（Profile-Guided Optimization）

利用运行时 profile 反馈指导编译优化：分支概率布局（热路径直落）、函数内联决策、热点代码布局（icache 局部性）。Clang 链路：-fprofile-generate 插桩 → 运行负载生成 .profraw → llvm-profdata merge → -fprofile-use 反馈编译。HCC 继承 Clang 语义，参数一致（本项目案例 6 已全流程验证）。

2.5 C86 DevKit 与光合组织

"光合组织"是海光发起的产业生态社区（sourcefind.cn 即其下载站）。C86 DevKit 的结构（编译器+数学库+JDK+性能工具+安全模块）对标 Intel oneAPI / IBM Advance Toolchain 的"平台工具箱"模式——单点编译器竞争不过开源，但"整套平台工具 + 国产负载调优 + 信创合规"有独立生态位。

四、趋势判断

趋势1：国产芯片"配套编译器"将成为信创标配，竞争焦点从兼容转向性能代差

依据：海光 HCC/HGCC、华为毕昇、飞腾/申思生态各自成型；上游 LLVM/GCC 对国产微架构的支持永远滞后（合并周期以年计）。当 ISA 兼容不再是壁垒（都能跑 x86/ARM 二进制），"同芯片 + 自家编译器 vs 通用编译器"的性能差（业界经验 5-15%）就是下一个竞争面。AI 推理负载（原文点名的定向场景）对向量化/调度最敏感，收益最大。

趋势2：LLVM 衍生路线是国产编译器的主流选择，自研前端窗口已关闭

依据：HCC（LLVM）、AOCC（LLVM）、ICX（LLVM）、毕昇（LLVM）全部收敛到同一技术路线——LLVM 的 pass 生态和 IR 标准化让"深度定制后端"的 ROI 远高于自研全栈。 Fortran 前端 Flang 的成熟补齐了 HPC 迁移的最后一块板。

趋势3：编译器分发方式从"裸工具"转向"DevKit 套件 + 社区"

依据：C86 DevKit 把编译器/数学库/JDK/性能工具/安全模块打包，通过光合组织社区分发——单卖编译器没有商业模式，"平台工具箱 + 负载调优服务 + 认证生态"才有。这与 Intel oneAPI 的转型路径完全一致。

趋势4：glibc ≥2.31 这类细节暗示国产平台识别已进入系统库层

依据：原文软件依赖表特别注明"glibc 2.31 or later is better which could recognize Hygon Platform"——平台识别不只是编译器的事，运行时库也在做适配。工具链协同优化的深度正在从编译期延伸到链接期、装载期、运行期全链路。

五、关联分析

5.1 与「2026-09-08-AlienMind与AI-for-Science反思-航空设计视角」笔记的关联

该笔记的核心判据"验证闭环是存亡关键"在此同样成立：编译器的验证闭环=基准测试 + 真实负载回归。HCC 的差异化主张（C86 微架构调优）必须通过SPEC/真实数据库/AI 推理负载的可复现对比来兑现，否则也会沦为"国产化叙事灌水"。本项目案例集正是在搭这个最小验证闭环（本机验证逻辑正确性，C86 机器验证性能收益）。

5.2 与「AirCraft 项目」的关联

AirCraft（MiniMind LoRA 航空材料微调）的推理部署目标若落在国产化服务器（信创机房），工具链选择就会遇到 HCC 这一层：PyTorch/x86 推理栈在 C86 上的性能取决于 HCC/HGCC 编译的底层库（glibc/数学库/OpenMP runtime）。两者在"国产平台 AI 推理性能"这一点上交汇。

5.3 与 Jetson/边缘 AI 部署工作的方法论同构

本机验证逻辑 → 目标机验证性能的两段式，与 DUCK-Pi_5 的"本地代码管线就绪 → AutoDL/asa 实测"模式完全同构：代码可移植性先行，硬件特定收益后验。案例集把 HCC 命令写进注释、本机用等价编译器跑通，正是这个方法论的落地。

九、指南分析

阅读与使用指南：

  1. 文体定性：官方生态的宣传性技术文——结构完整（动机/架构/安装/使用）但性能数据缺席。它没有给出任何 HCC vs GCC 的量化对比，这是本文最大的留白，也是我们建案例集的原因。
  2. 可信度判读：技术事实（LLVM 16.0.4 基线、Flang 双组件、OS 支持列表、下载安装命令）具体可验证，可信度高；"性能优化"停留在定性层（"深度优化""定向调优"），无数字支撑，需实测检验。
  3. 本笔记的增量：①补齐了行业谱系（AOCC/ICX/毕昇同构路线）；②用 6 个真机验证案例把"文章说的能力"转化为"可运行的验证代码"；③诚实标注了验证边界——本机 ARM64 只验证逻辑正确性，C86 特有性能收益（微架构调度/扩展向量指令）必须海光机器实测，不可外推。
  4. 案例集的坑点沉淀：①Fortran 莱布尼茨级数初版误写为交错调和级数（收敛 4·ln2≠π）——数值程序必须有独立验算；②Ubuntu 的 llvm-profdata 不在 PATH（/usr/lib/llvm-14/bin/）；③/usr/bin/time -f 输出在部分调用方式下丢失，计时用 python time 更稳；④PGO 在低分支密度负载下收益可为零——不要神化任何优化手段。
