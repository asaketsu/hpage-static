## 二、五大攻击向量与典型 CVE

### 2.1 远程代码执行（RCE）与命令注入

**攻击模式**：未净化的输入直接传递给 shell 执行函数（`execSync`、`child_process.exec`）。

| CVE | 目标 | 严重度 | CVSS | 描述 |
|-----|------|--------|------|------|
| CVE-2026-23744 | MCPJam Inspector | Critical | 9.8 | 监听 `0.0.0.0` 无认证，HTTP 请求即可安装 MCP Server 并执行任意代码 |
| CVE-2026-0755 | gemini-mcp-tool | Critical | 9.8 | 未净化输入传给 `execAsync`，零交互网络可达 |
| CVE-2026-0756 | GitHub Kanban MCP | Critical | 9.0 | 通过 MCP 工具接口执行任意命令 |

**关键洞察**：MCP Server 默认以宿主机完整权限运行，RCE = 完全控制。

### 2.2 提示注入与 Tool Poisoning

**攻击模式**：恶意指令嵌入 MCP 工具描述中，用户不可见但 AI 模型可见。

Invariant Labs 发现的关键攻击链：
1. 恶意 MCP Server 在工具描述中嵌入隐藏指令
2. AI 模型读取描述后执行恶意操作（数据外泄、行为劫持）
3. 可覆盖来自其他可信 Server 的指令
4. 即使有信任基础设施也能实现**完全功能劫持**

**零点击 RCE（Google Docs MCP）**：
- 攻击者分享包含嵌入提示注入的恶意 Google Doc
- Cursor 通过 Google Docs MCP Server 获取文档时自动执行注入指令
- 无需用户交互，实现 RCE + 凭据窃取 + 持久化访问

### 2.3 DNS Rebinding 与浏览器劫持

**攻击模式**：本地 MCP SDK 缺乏 DNS 重绑定保护，恶意网站绕过同源策略。

- 恶意网页通过 DNS 重绑定访问 `localhost` 上的 MCP Server
- 绕过浏览器 Same-Origin Policy
- 可在用户不知情的情况下调用本地 MCP 工具

### 2.4 SSRF（服务端请求伪造）

| CVE | 目标 | CVSS | 描述 |
|-----|------|------|------|
| CVE-2025-65513 | Fetch MCP Server | 9.3 | `is_ip_private()` 验证缺陷，允许扫描内网和访问云元数据服务 |

攻击者可通过 MCP 工具访问 AWS EC2 元数据、内网服务等受保护资源。

### 2.5 供应链攻击

OX Security 发现的**系统性架构缺陷**（CVE-2026-30624 等）：

| CVE | 目标 | 类型 |
|-----|------|------|
| CVE-2026-30624 | Agent Zero | 未认证 UI 注入 |
| CVE-2026-30617 | Langchain-Chatchat | 未认证 UI 注入 |
| CVE-2026-33224 | Jaaz | 未认证 UI 注入 |

**Anthropic 官方 Git MCP Server RCE 链**（3 个 CVE 串联）：
- CVE-2025-68145：路径验证绕过
- CVE-2025-68143：无限制 `git_init` 可将 `.ssh` 变为 git 仓库
- CVE-2025-68144：`git_diff` 参数注入
- **链式效果**：配合 Filesystem MCP Server，通过恶意 `.git/config` 实现完整 RCE

## 三、NSA 安全设计指南核心要点

美国国家安全局（NSA）发布了 MCP 安全设计考虑文档，这是**政府级 AI 协议安全指南的首例**：

### 3.1 关键建议

1. **语义与工具投毒是系统性问题**，不是孤立事件
2. 传统 API 安全模型（WAF、API Gateway、限流）**不足以保护 MCP**
3. MCP 需要**身份优先、基于工作负载的安全架构**

### 3.2 五层防护模型

| 层级 | 防护重点 | 关键措施 |
|------|---------|---------|
| **传输层** | TLS/mTLS、网络暴露 | 强制加密传输、限制端点暴露范围 |
| **身份层** | 认证、令牌委托 | 短期令牌、范围验证、零信任 |
| **上下文层** | 完整性、保密性 | 上下文签名、防篡改、隔离 |
| **授权层** | 权限、横向移动 | 最小权限、会话管理 |
| **供应链层** | 注册表、依赖 | 注册表审核、签名验证 |

## 四、MCP vs 传统 API 安全的根本差异

| 维度 | 传统 API 安全 | MCP 安全 |
|------|-------------|---------|
| 工作流本质 | 静态、可预测、人工驱动 | 动态、自主、Agent 驱动决策 |
| 数据流 | 客户端→服务端验证→响应 | 复杂工具链、移动上下文、多方编排 |
| 安全边界 | 明确定义（IP、API Gateway） | Agent/Server/工具间移动边界 |
| 主要防御 | WAF、限流、静态 Schema 验证 | 工作负载 IAM、上下文完整性、动态策略 |
| 错误传播 | 通常隔离 | **级联扩散**——单点缺陷波及整条链 |

> **核心论点**："因为自主 Agent 在无人干预下传播决策，单点利用可在几毫秒内通过整个工具链级联。"

## 五、对 Hermes 系统的具体影响

### 5.1 当前暴露面评估

Hermes Agent 大量使用 MCP 工具（智谱 MCP、记忆图谱等），面临的风险：

1. **MCP Server 信任模型**：当前 Hermes 信任所有已配置的 MCP Server，无来源信任分级
2. **工具描述不可见**：用户无法审计 MCP 工具描述中是否包含隐藏指令
3. **凭据存储**：API key 等凭据存储在配置文件中，属于 NSA 指出的"静态 API 密钥"风险
4. **无上下文完整性校验**：工具返回结果未经签名或完整性验证

### 5.2 建议落地的防护措施

**短期（立即可做）**：

1. **MCP Server 白名单 + 信任分级**：在 `config.yaml` 中为每个 MCP Server 标注信任等级（trusted/verified/untrusted）
2. **敏感操作前置检查**：`delegate_task`、`terminal`、文件写入等操作前增加 trust-level 检查
3. **凭据轮换**：定期轮换 MCP 相关的 API key

**中期（Skill 级改进）**：

4. **MCP 工具描述审计**：扩展 `mcp-security-audit` Skill，增加工具描述内容检查
5. **上下文完整性标记**：为工具返回结果增加来源标记，防止 Dynamic Output Poisoning
6. **SSRF 防护**：所有 MCP 工具中的 URL 获取操作增加内网 IP 过滤

**长期（架构级）**：

7. **运行时权限控制层**：借鉴 AIRGuard 的六层机制（已在 2026-06-01 笔记中记录）
8. **身份优先架构**：为每个 MCP 工具调用注入调用者身份和范围信息

### 5.3 与已有 Skill 的关联

- **mcp-security-audit**：需 patch 追加 Tool Poisoning 检测和 SSRF 防护检查
- **agent-security-governance**：需 patch 追加 MCP 五层防护模型
- **exchange-protocol**：三机经验交换也需要上下文完整性校验
