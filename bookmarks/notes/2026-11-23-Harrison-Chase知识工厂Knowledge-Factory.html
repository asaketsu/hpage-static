内容整理：三动作 × 三类知识 × 三组件

核心命题

让 AI 在公司真正可用，缺的不是更好的模型，也不只是更多 context，而是更好的 knowledge——公司如何运转、操作标准是什么、数据存在哪、怎么访问。最高效的员工脑中有这些隐性知识（知道找谁问、去哪查、为什么这么做）；要让 Agent 接手这些工作，就必须收集（collect）、整理（curate）、维护（maintain）这些知识的表示——支撑这件事的系统就是「知识工厂」。

Context vs Knowledge 的关键区分

概念 定义 关系
Context Agent 执行任务时可用的全部输入 知识是 context 的一种，但不应是唯一一种
Knowledge 为「把事做对」而维护的可复用理解：指标含义、可信信源、情境处理方式 常是隐性/散落的；工厂把它转成未来任务可用的 context

已在可靠摄取/存储的其他类型数据（如数仓里的原始数据）直接喂给 agent 即可，不必复制进知识层——知识层只维护「什么数据在哪、怎么查」的指引。

范式迁移：Software Factory → Knowledge Factory

过去一年半「软件工厂」理念兴起：最好的工程师不亲自写软件，而是构建让全公司高效写软件的工厂系统，实际构建交给 agent。通用知识工作（做演示、发视频、对外触达）正走同一条路——agent 能力已够，卡点在它们缺少那些隐性、散落的知识。资源该投在建设知识工厂上，这是把更多知识型工作外包给 agent 的前提。

三类知识（pieces of knowledge）

类型 回答的问题 特征 典型形态
Skills（技能） 怎么把事做「规范」 此前常从未写下、口口相传；应当写下来 流程、指令、脚本
Domain knowledge（领域知识） 业务如何运转 不常过期；写过但常不完整/有错 产品/客户/竞争对手/组织的定义、政策、事实
Data access guidance（数据访问指引） 去哪拿当前信息 前提是已有正经数据战略（Snowflake/Databricks）；真源已全且新就不必维护副本 什么数据在哪、怎么查的清晰说明

三组件（pieces of the factory）

  1. 缺失知识标记工具（flag 工具）——agent 干活时发现信息缺失/错误就地 flag：至少报告哪里错，可选建议正确更新。这是发现知识缺口的最廉价入口。
  2. Curator agent（策展代理）——后台按节奏运行，专职更新维护知识。三条硬规则：
  3. 不该人工维护（工作量不可持续）；
  4. 不该让使用知识的 agent 自己维护——它们擅长发现缺口但以自身目标为先，自行更新会让知识库「失控且充满矛盾」；
  5. 必须能访问：全部原始散落源（Notion/Slack 等）、agent traces（看人怎么用 agent 并把用法沉淀成 skills）、flag 记录。
  6. 存储（storage）——「某种程度上最不重要」：skill 格式存 GitHub、Notion 单文件、OKF 格式存 LangSmith Context Hub、Neo4j 知识图谱皆可，curator 应会操作全部格式。行业已收敛：程序性记忆 = skills 是共识标准；语义记忆尚无标准（OKF 是候选），早期勿过度规定格式。

端到端例子：营收报告 agent

  1. Base context：BigQuery + Salesforce 里的原始收入数字（直连，不入知识层）。
  2. Knowledge 三处：报告规范 = LangChain 风格 skills（存 GitHub）；ARR 计算口径 = 长时效知识（存公司 wiki）；BigQuery/Salesforce 取数方法 = 数据访问 skills（存 Context Hub）。
  3. 闭环发生：agent 发现 BigQuery 列被改名→现场自行修正+flag 建议新列名；财务负责人同步协作修格式（新增统一 header）；当夜 curator agent 读 flag + 检查 traces 发现这场来回，自动更新对应 skills（取数用新列、报告用新 header）。

结论（作者原话要义）

目标不是「先把一切文档化再让 agent 上工」，而是建一个系统：做事暴露知识缺口 → 解决缺口 → 未来工作更好。从一个 recurring workflow 起步，观察 agent 卡在哪，闭合那个环。

查询拓展

  • OKF（Open Knowledge Format）：LangChain 力推的开源知识格式（github.com/open-knowledge-format），语义记忆标准的候选——跟踪其采纳曲线可预判知识层格式收敛时间点。
  • LangSmith Context Hub：文中知识存储的产品化载体，看它与 GitHub/Notion 等第三方存储的实际打通程度可检验「storage 格式无关」承诺。
  • Software Factory 原始论述：Chase 类比的源头，可反查「工厂化」思想从软件工程迁移到知识工程的完整谱系。
  • Anthropic Skills 格式：文中「行业已收敛 skills 为程序性记忆标准」的另一主角，与 LangChain skills 格式的竞合关系值得对照。
  • 检索关键词：knowledge factory / curator agent / agent knowledge curation / OKF open knowledge format / procedural vs semantic memory agents

归纳总结

  1. 命题升维：Agent 落地的瓶颈从「模型能力 → 上下文工程」继续上移到「知识运营」——与前两站一样，是被一线实践而非理论推动的范式站。
  2. 分工铁律是全文最有分量的判断：知识的使用者（干活 agent）只负责 flag；知识的维护者（curator agent）专职更新——「让用知识的 agent 自己维护」被点名会导致矛盾失控。这是生产与质检分离在知识系统的复刻。
  3. 三类知识分层是操作骨架：Skills（流程）/ Domain（事实）/ Data access（指针）——第三类最易被忽视：数据真源已在数仓，知识层只需维护「怎么查」的指引，不复制数据本体。
  4. 存储格式未收敛是机会窗口：程序性记忆已收敛 skills；语义记忆标准空缺（OKF 候选），早期不宜重仓单一格式。
  5. 冷启动策略反直觉：不先文档化、先跑一个 workflow 让缺口自己暴露——把知识建设从「预算项目」变成「运行时副产品」。

趋势判断

  • 知识工程正在重演数据工程的故事：数据战略（Snowflake/Databricks）→ 数据访问层 → 知识工厂，企业 AI 基础设施栈逐层加厚；Chase 所在位置（observability → traces → curator）意味着traces 正在成为知识生产的原料矿。
  • Curator agent 是下一个标配岗位：从「写 prompt」→「建 harness」→「运营知识工厂」，企业 Agent 团队的编制重心将继续上移；LangChain 把它产品化（Engine/Context Hub）是在卡位这个岗位的工具链。
  • 标准之争在语义记忆层：skills 收敛后，语义记忆格式（OKF vs 知识图谱 vs 大厂私有格式）是下一轮生态卡位战——类似当年 vector DB 之争的翻版。
  • 风险信号：方法论与产品线深度绑定（文中 5 处内链指向自家产品），外部团队照抄时需把「理念」与「LangSmith 栈」解耦——理念可独立成立，栈不可照搬。

与我们自身体系的镜像映射（关联分析核心）

Chase 的知识工厂与 Hermes 自进化体系几乎逐件对应，且双方在关键判断上互相印证：

Chase 组件 我们的对应物 印证点
Skills（程序性知识） skill_manage 体系 + 各 skill 的 references 双方都收敛到「文件式 skills」为程序性记忆标准
Domain knowledge MEMORY.md 铁律 + 项目 docs 「写过但不完整」的判断与我们 L1 精练机制一致
Data access guidance 各 skill 内嵌的 endpoint/path 引用 我们未单列此类——见行动项
flag 工具 error-case-library + error-monitoring 「最小报告+可选建议」两档设计值得吸收
Curator agent evolver + memory-consolidation + skill-review（独立 curator） 最强印证：我们也把 curator 从使用者分离，「让使用知识的 agent 自己维护会失控」与我们经验完全一致
traces 输入 session-evolution-scan（扫会话纠偏信号） Chase 把 traces 列为 curator 三大输入之一，我们已在做但仅限纠偏信号
storage 格式无关 三级记忆 L1/L2/L3 多层并存 双方都判断格式早期未收敛、勿过度规定

我们的领先与滞后：领先——闭环触发已实现「错误驱动」自动化（error-case-library 两层错误即固化 skill）；滞后——① 数据访问指引未单列成类，散在各 skill 里缺统一索引；② traces 扫描只抓失败/纠偏，未把「人机成功协作来回」沉淀为新 skill（Chase 的 header 案例正是这类）。

拓展应用推荐

  • 给做企业 Agent 落地的团队：直接照抄三组件起步法——挑一个 recurring workflow，给 agent 加一个 flag 工具，跑两周看缺口清单，再决定 curator 怎么建。不要先开文档化项目。
  • 给个人 Agent 使用者：把「curator 不是使用者」原则用在自建 agent 上——日常干活的 agent 别给它写库权限，另开一个定期整理的会话/脚本做策展。
  • 给知识管理团队：Chase 的三类知识分法可当企业知识盘点清单：Skills 盘点问「哪些流程只在老员工脑子里」，Domain 盘点问「wiki 里哪些条目已经错了」，Data access 盘点问「新人要查数第一件事问谁」。
  • 工具链观察：LangSmith Context Hub、OKF 格式、Neo4j 知识图谱三条存储路线的此消彼长，可作为企业知识基建选型的风向标。

指南分析

可直接执行的操作序列（从文中提取）：

  1. 选一个高频重复的知识型 workflow（如周报/数据提取/内容发布）。
  2. 给执行 agent 配两样东西：任务所需数据的直连访问（不入知识层）+ 一个「报告问题/建议修复」flag 工具。
  3. 记录 agent 卡点与人机协作来回（traces）。
  4. 部署 curator agent（可先人工代行）按固定节奏：读 flag → 读 traces → 对照原始源（Notion/Slack/wiki）→ 更新对应 skill/条目。
  5. 知识按三类归位：流程→skills 格式；事实→wiki；取数方法→带指针的说明，不复制数据。
  6. 扩展到第二个 workflow 前先验收第一个的闭环：缺口从 flag 到修复的周期、同类问题复发率。

禁做清单（文中明示）：① 不搞「先全量文档化再上线」；② 不让使用知识的 agent 持有写权限自行更新；③ 不在格式未收敛期重仓单一存储方案。

行动与回访

  • P0｜数据访问指引单列实验：把我们体系里散在各 skill 的 endpoint/路径引用（project-endpoints、docs 路径类内容）聚合试建一页「数据访问指引」索引，验证「指针不复制」是否降低维护成本——两周后回访使用率。
  • P1｜flag 工具两档化：给 error-case-library 的记录模板补「可选建议修复」字段（现仅记录错误），对齐 Chase 的最小报告+建议两档设计。
  • P1｜traces 信号扩展评估：评估 session-evolution-scan 增加第二信号源——不只扫纠偏/失败，也扫「用户手工修正后被采纳」的协作来回（Chase 的 header 案例模式），产出新 skill 候选。
  • P2｜OKF 格式跟踪：加入观察清单，待其 star/采纳出现拐点再做吸收分析（可用 [[2026-05-08-addyosmani-agent-skills生产级Agent技能包.md]] 的 skills 格式经验做对照基线）。
  • 证伪条件：若两个月内我们的 flag→修复周期未见缩短、或「数据访问指引」索引使用率为零，则判定该三组件模型对我们的增益不成立，回退为按需手动维护，待验证后再启用。
