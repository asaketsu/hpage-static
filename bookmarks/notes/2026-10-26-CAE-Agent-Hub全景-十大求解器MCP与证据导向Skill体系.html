归纳总结

一句话：CAE-Agent-Hub 是目前开源世界里覆盖面最广的「AI 客户端 ↔ 商业/开源 CAE 软件活连接」合集——10 个 MCP server 打通 Abaqus/ANSYS 全家桶/HyperWorks/LAMMPS/OVITO/CalculiX/Peridigm/FreeCAD-Elmer-ParaView，配 36+ 个可复用 Skill 和浏览器结果查看器，让 Codex/Cursor/Claude Code 直接操作真实求解器而非纸上谈兵。

核心判断（对飞机设计背景的读者）：

判断 依据
这是 CAE Agent 化的"基础设施层"而非单点工具 仓库自我定位是 Hub（集线器）：MCP=工具桥、Skill=工作流指令、Subagent=任务分解、Viewer=结果检视，四层职责分离
对航空结构仿真直接可用的入口是 Abaqus 系 Abaqus MCP 是全仓最活跃模块之一，配套 24 个 Skill 覆盖建模→分析→优化全链（静力/模态/动力/热/耦合/接触/疲劳/拓扑优化）——正是机身结构强度校核的常规科目
最大方法论亮点是 evidence-oriented（证据导向） 多个 Skill 显式带 evidence gates / acceptance gates——AI 完成仿真后必须出示证据链才判完成，这与适航验证的 V&V 思想同构

2. 四层职责分离（仓库核心架构）

AI 客户端 (Codex/Cursor/Claude Code)
   ├── MCP server ──────→ 活的 CAE 应用/求解器（真实计算）
   └── Skill / Subagent → 建模/设置/求解/验证工作流（指令与分解）
            ▼ 原生求解器结果
            ▼ 轻量结果导出（result_mesh.json）
            ▼ 浏览器 Viewer / 报告工作流（求解器关掉也能看结果）
  • MCP servers：对已安装 CAE 应用提供工具级访问（活的会话，不是离线示例）
  • Skills：建模/设置/求解/后处理/优化/验证的可复用指令模块（SKILL.md 目录整包复制）
  • Subagents：任务分解与专业 agent 工作流资源（Subagent/ 目录）
  • Viewer：浏览器检查 result_mesh.json 轻量结果，无需求解器在场；Peridigm 模块还带两个录制验证的回放 demo（弹性两点验证 + 3200 物质点预裂拉伸损伤，31 帧真实数据）

3. MCP Index（10 个，截至本次核验）

MCP 状态 连接方式要点 覆盖能力
Abaqus Active 本地 TCP 桥接活的 Abaqus/CAE 会话 kernel 跑 Python、查模型、提交作业、监控状态、读 ODB、viewport 截图
ANSYS Fluent Active 批处理 journal + 可选 PyFluent 活会话 Scheme/TUI/Python 探针、任务与日志跟踪
ANSYS Workbench Active Python helper + ACT 桥，文件队列/socket-timer 两种通信 控制 Workbench 与 Mechanical（含 LS-DYNA）
Ansys AEDT Active raw TCP JSON 桥 HFSS 设计创建、S 参数、AEDT Python 片段
Altair HyperWorks Active 类型化工具 + 认证的应用内 Python 桥（详见已有精读笔记） HyperMesh/HyperView/OptiStruct/Radioss
LAMMPS Active 检测本地可执行文件 分子动力学 input deck 运行 + 证据保留
OVITO Active 脚本支持检测 原子级后处理 + 证据日志
CalculiX Active 包装开源 ccx 解析/编辑 .inp、跑 ccx、读 .dat、导 result_mesh.json、模态提取、两阶段尺寸优化
Peridigm Prototype 结构化 CaseSpec + 构建特定规则 有界真实作业、弹性/损伤独立验证（工程强度未验证，README 诚实声明）
FEP Agent Hub Active 协调 FreeCAD/Elmer FEM/ParaView 三个独立 MCP 已验证热/电磁/结构/层流 profile + 证据门

观察：连接模式有三种范式——①TCP 活桥（Abaqus/AEDT，需要 CAE 应用开着）、②批处理 journal（Fluent/LAMMPS/CalculiX，不需要 GUI 在场）、③应用内插件桥（HyperWorks extension/Workbench ACT，嵌进宿主进程）。商业软件走活桥/插件，开源求解器走 CLI 包装——这个分层是踩过坑之后的工程选择。

命名规律：<ecosystem>-evidence-<domain> 是显式契约——带 evidence 的 Skill 内置验收门（acceptance gates），AI 跑完必须交证据才算数。

5. 安装与使用模式

  • MCP：各目录自带 README + 环境模板，本地 Python 起 server 后注册到客户端
  • Skill：指令模块而非二进制——整目录复制进 ~/.codex/skills/ 或 Claude skills 目录即可
  • 明确边界：装 MCP 不装商业 CAE、不给 license——软件、可执行文件、授权、本地环境全部自备
  • 源控制政策：不进 solver 二进制/license/私有路径/生成结果（ODB、case/data、截图等）；models/peridigm-* 的 curated 回放数据是唯一例外（只含选定字段+校验和+出处）

关联分析

与已有知识库的关联

  1. [[2026-09-07-HyperWorks-MCP源码精读-FastMCP工具面安全门与Qt主线程活桥的CAE-Agent架构.md]]（同仓库微观篇）：那篇的核心发现——FastMCP 类型化工具面 + Tcl 安全门 + Qt 主线程活桥 + 检查点回滚——正是本篇 MCP Index 里 HyperWorks 行的实现细节。两篇合起来 = "Hub 全景 × 单 MCP 深挖" 完整覆盖。
  2. evidence gates 与我们自己的验证门禁同构：本仓库的 evidence-oriented Skill（跑完必须交证据）与 Hermes 侧的 verification gate / 分析行动闭环（"recommendations without execution are technical debt"）是同一哲学在不同领域的落地——CAE 领域的 AI 幻觉代价是"假仿真结果"，所以证据链是生死线。
  3. Skill 组织方式对照：Abaqus 的 master router + 专项 skill 拆分（geometry/material/mesh/…）与 Hermes 的 skill 分类目录（lark- 系列、duck- 系列）结构同构——证明"路由 skill + 领域专项 skill"是 Agent 工程的通用模式，不是某一家独创。

与用户领域（飞机设计/适航）的关联【领域扩展，非仓库原文】

  • 强度校核科目直接对口：Abaqus Skill 包的七个分析类（静力/模态/动力/热/耦合/接触/疲劳）恰好是机身结构强度校核的常规科目——静强度、颤振基频、坠撞、热载、连接件接触、疲劳损伤容限，全部有现成 Skill 可套。
  • 证据链与适航 V&V 同构：适航条款要求仿真结果可追溯（模型版本、载荷工况、网格收敛性、与试验相关性）。evidence gates 的"AI 必须出示证据才算完成"如果延伸到适航语境，就是 AI 辅助 CAE 能否进入型号资料体系的准入条件——AI 生成的分析报告必须携带可复现的求解器日志与结果文件，这与 CCAR-25 下建模与试验相关性声明的证据要求是同一逻辑。
  • 构型管理视角：仓库的 source control policy（结果不入库、只入可复用源码与模板）暗合构型管理思想——生成物（ODB/结果文件）与配置项（脚本/模板/Skill 定义）分离，正是 EBOM 级别的纪律。
  • 诚实声明的价值：Peridigm 模块 README 明确"工程强度与试验精度未验证"——这种不吹牛的声明在适航语境下尤其重要，AI 辅助分析工具进入型号流程前，其能力边界声明本身就是评审对象。

趋势判断

  1. CAE Agent 化从"演示"进入"基础设施"阶段：109 commits、1.1k stars、双语 README、contributing 规范——这不是 demo 仓库，是按长期项目在运营。2026 年内预计出现更多 solver-specific MCP（README 路线图自己也这么写）。
  2. Skill 生态的产品化：Abaqus 24-Skill 包（router + 前处理 + 分析类 + 优化）是"Skill as Product"的样板——单个 Skill 从"一段 prompt"进化成带 metadata.json、references、assets、上游出处声明的完整包。
  3. 开源求解器是最大受益者：CalculiX/FEP（FreeCAD+Elmer+ParaView）全开源链路 = 零 license 成本体验 CAE Agent；商业软件受 license 与版本绑定拖累，MCP 维护成本高（每家连接方式都不同）。
  4. evidence-oriented 会成为 CAE Agent 的行业底线：仿真的下游是工程决策（甚至适航判定），无证据的 AI 仿真结果零价值。带 acceptance gates 的 Skill 会从加分项变成标配。
  5. 风险：商业 CAE 厂商（Dassault/Ansys/Altair）对脚本接口的态度决定 MCP 寿命——TCP 活桥依赖私有接口（如 Abaqus kernel Python、ACT），厂商一次改版就能废掉一个 MCP。

# 借鉴点 来源 落地方式
1 evidence gates 写进 Skill 而非靠 Agent 自觉 evidence-oriented Skills 我们的验证门禁目前散在各 skill 的文字约定里，可参考其做法：在关键工作流 skill（交付/发布类）里显式定义"完成判据 = 证据清单"，Agent 跑完必须逐项出示

3 结果轻量化导出 + 独立 Viewer result_mesh.json + browser viewer 分析类任务交付后结果常散落各处；仿照其"轻量 JSON + 浏览器可查"模式，把长任务的产物清单做成可检视的静态页
4 curated 回放数据带校验和与出处 models/peridigm-* 例外政策 我们的 golden set / 验收样例可加 hash + 出处声明，防样例被静默篡改

使用路径（若要在工作中实际启用）

  1. 零成本起步：CalculiX MCP + FEP Agent Hub（全开源），在有 Python 的 Windows/Linux 工作站即可跑通"文本→建模→求解→浏览器看结果"全链，验证 Agent 工作模式。
  2. 商业软件增量：若本机已有 Abaqus/ANSYS 授权，装对应 MCP 即可让 Codex/Claude Code 操作真实会话——TCP 桥方案不碰 license 服务器，风险低。
  3. Skill 直接复用：abaqus-static-analysis 等 Skill 是纯指令模块，复制进 .codex/skills/ 即用，与求解器是否在场均无关（离线时作为方法论指导也成立）。
