归纳总结

一句话核心：RAG 与 Agentic RAG 解决的不是同一个问题——普通 RAG 解决"把正确的信息找出来"，Agentic RAG 解决"检索决策本身需要动态规划"；选型判据是任务是否真的需要动态规划/多步检索/跨数据源/工具协作，而不是"加 Agent 就更智能"。作者最锋利的判断：把 Agentic RAG 当技术炫耀正在成为企业 AI 落地的新型反模式——混合检索 + Rerank 能解决的问题套上多层 Agent，换来的是 token 成本、延迟和错误规划的三重代价。

作者决策准则（可直接抄）：能用普通 RAG 解决的问题，就不要为了 Agent 而 Agent。真正优秀的 AI 工程师不是能把系统设计得多复杂，而是知道什么时候该复杂、什么时候该保持简单——架构以更低成本、更稳定地解决真实问题为赢，不以高级为赢。

内容整理：两种架构的本质差异与选型判据

架构对照表

维度 普通 RAG Agentic RAG
解决的问题 把正确的信息找出来，让模型基于证据回答 检索决策本身需要动态规划的任务
流程形态 固定流水线：提问 → 检索 → 证据交给模型 → 生成 把一部分检索决策权交给 Agent
决策自由度 无决策，链路写死 可决定：去哪里检索 / 调用什么工具 / 要不要拆分问题 / 失败后是否重查或切换数据源
典型场景 "公司报销制度是什么"——检索几份文档即可答 "今年报销政策比去年变了什么？哪些部门受影响？有无特殊审批？"——查多版本制度 + 确认生效时间 + 多部门规定 + 调用内部业务系统 + 证据整合
复杂度代价 低 token 消耗高、响应慢、错误规划会检索到不相关信息
适用前提 单跳问答、证据集中 动态规划、多步检索、跨数据源、工具协作四者真需要

作者的警示：Agentic RAG 正在沦为技术炫耀

  • 明明混合检索 + Rerank 就能解决，偏要加好几个 Agent 让它自己规划、自己检索、自己评估、自己重试
  • 结果三重代价：架构复杂度↑、token 成本↑、响应速度↓，外加错误规划引入不相关检索
  • 这与"加 Agent、多轮推理、工具调用，系统就一定更智能"的直觉相反——架构升级不自动等于智能升级

企业级 RAG 的真难点清单（不是选框架）

文档解析 · 权限隔离 · 增量同步 · 版本管理 · 检索质量 · 证据引用 · Evals 验证系统是否真的答对了。作者的实证观察：这些基础工程没做好，套十层 Agent 也进不了生产环境。

趋势判断

  1. 企业 AI 落地正从"架构军备赛"回归"工程基本功赛"：2025-2026 上半场比谁 Agent 叠得多，下半场的分化点会转移到文档解析质量、权限模型、Evals 体系这些"看不见"的工程——与"交付才是护城河"论互相印证
  2. Agentic RAG 不会消失但会分层：单跳问答回归普通 RAG + Rerank 的性价比组合；Agentic 层下沉为"多跳/跨源/带工具"场景的专用件，而非默认架构
  3. 决策权转移是本质变量：未来 RAG 演进的度量衡可能不是"检索精度"单指标，而是"系统在多大程度上需要自主决定检索路径"——选型问题会变成决策论问题
  4. 小账号垂直信源的信号价值：4k 粉丝 FDE 的实战判断（65 赞/2.9k 浏览）与头部 KOL 共振同题，说明该观点已在一线工程师群体形成共识面

指南分析

选型决策流程（按序自问，命中即停）：
1. 任务是否单跳可答、证据集中？→ 普通 RAG（混合检索 + Rerank 优先）
2. 是否需要跨数据源 / 多版本 / 调用外部业务系统？→ 进入 Agentic 候选
3. 检索路径是否真的无法预先穷举（失败重查、动态切换源）？→ Agentic RAG
4. 已上 Agentic 的存量系统：反向审计——砍掉规划层后用固定链能否等价交付？能则降级，省 token 省延迟

作者视角的生产化检查表：文档解析 ✅ 权限隔离 ✅ 增量同步 ✅ 版本管理 ✅ 检索质量 ✅ 证据引用 ✅ Evals ✅——七项全绿之前，Agent 层数是零增值装饰。
