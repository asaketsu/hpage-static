# MCP 已死？上下文膨胀、低可靠性与 CLI 优先替代方案

> **HN**：#23, 96 pts（但引发广泛讨论）
> **标签**：#MCP #Agent工具 #CLI #上下文优化 #Hermes生态
> **关联**：[Cloudflare Agentic Cloud](2026-05-24-Cloudflare-Agents-Week-2026-Agentic-Cloud全栈基础设施.html) [AI编码工具分层架构](2026-05-24-AI编码工具战争-CodexClaudeCodeCursor收敛为分层架构.html)

## 摘要

Quandri 工程团队实测 MCP（Model Context Protocol）在生产环境中的三个核心问题：上下文吞噬（4 个 MCP 服务器消耗 10.5% 的 200K 上下文窗口）、低运行可靠性（3x-9.4x 延迟、进程崩溃、认证失败）、与现有 CLI/API 功能重叠。提出两个替代方案：CLI-First 策略（LLM 直接用 curl/CLI）和 Skills Pattern（按需加载，非全量注入）。文章特别指出 Claude Code 已推出 Tool Search with Deferred Loading，将上下文占用减少 85%+。本文对 Hermes Agent 生态有直接参考价值——我们的 MCP + Skills 架构需要认真思考这个平衡。

## 核心内容

### 1. 问题一：上下文窗口被工具定义吞噬

实际测量（Quandri 的 4 个 MCP 服务器）：

| MCP Server | 工具数 | 字符数 | Token 数 |
|-----------|--------|--------|----------|
| Linear | 42 | 51,229 | 12,807 |
| Notion | 14 | 16,156 | 4,039 |
| Slack | 12 | 15,168 | 3,792 |
| Postgres | 9 | 1,755 | 438 |
| **总计** | **77** | **84,308** | **21,077** |

Claude 200K 上下文窗口中，10.5% 被工具定义占用。GPT-4o 128K 更严重：16.5%。Linear 一个服务就有 42 个工具定义，但日常只用到 get_issue 和 save_issue。

### 2. 问题二：运行可靠性差

- 初始化失败、反复重认证
- 需要启动和维护独立进程
- 每个 tool call 多一轮外部服务器往返
- 会话中途 MCP 进程崩溃
- 权限不透明

基准测试：Jira MCP 比直接 REST API 慢 3x，首次调用（含初始化）慢 9.4x。这不是 Jira 特有问题，是架构层面的开销。

### 3. 问题三：与 CLI/API 功能重叠

| 维度 | CLI/API | MCP |
|------|---------|-----|
| 人机对等 | 人类和 LLM 用同一套命令 | 仅存在于 LLM 对话内 |
| 可组合性 | 管道、jq、grep 自由组合 | 锁定在服务端返回格式 |
| 可调试性 | 终端立即复现 | 只能在对话上下文内复现 |
| 训练数据 | 已从 man page、StackOverflow 学习 | 需要独立工具定义 |
| 安装成本 | 大多已预装 | 服务器设置、认证、进程管理 |

Token 对比：MCP 方案查一个 Linear issue 消耗 ~12,957 tokens，CLI 方案只用 ~200 tokens，差 65 倍。

### 4. 替代方案：CLI-First + Skills Pattern

**CLI-First**：直接给 LLM curl 命令和 API 文档。LLM 已经从 StackOverflow 学会了这些。

**Skills Pattern**：不是"把所有菜单铺桌上"（MCP），而是"需要时才问图书管理员要书"。把 CLI 用法说明嵌入 Skill，只在调用时加载。

### 5. Claude Code 的回应：Deferred Loading

Claude Code 已推出 Tool Search with Deferred Loading，MCP 工具 schema 按需加载，减少 85%+ 上下文占用。这说明 Anthropic 承认问题但选择在协议内修复，而非放弃 MCP。

## 关键概念

1. **Context Window Pressure**：工具定义占用的上下文比例，直接影响 LLM 可用工作空间
2. **Deferred Loading**：按需加载工具定义而非全量注入
3. **CLI-First Strategy**：LLM 直接使用已有 CLI/API，跳过中间协议层
4. **Skills Pattern**：将工具使用说明嵌入 skill 文件，按需加载到上下文

## 能力边界

- 文章来自 Quandri（保险科技），其经验可能不适用于所有领域
- MCP 的标准化价值（"USB-C of AI"）被低估——CLI 方案缺乏统一接口
- Deferred Loading 已解决大部分上下文问题
- 文章未深入讨论 MCP 在多模态/流式场景的价值

## 最佳实践

- 评估每个 MCP 服务器的实际使用工具数，精简 schema
- 优先用 CLI/API 替代低频使用的 MCP 连接
- Skills Pattern 适合高频但工具定义庞大的场景
- 对于 Hermes：已有的 Skills 架构天然是 Deferred Loading 模式
