Agent Skills：给 AI 一本"操作手册"

来源：微信公众号文章 | 日期：2026-05-26

核心观点

Prompt 是你告诉 AI"去做这件事"，Skill 是你提前准备好了"这件事怎么做"。

Agent Skills 解决的根本问题：AI 每次都要重新解释，每次执行结果都不一样，每次都是一次性的。

一、什么是 Agent Skills

定义：Skill 是一个可被 Agent 在运行时发现、理解、调用和组合的能力模块。

四个关键动词，缺一不可：
1. 发现 — Agent 能自动匹配到合适的 Skill
2. 理解 — Skill 有清晰的结构和语义
3. 调用 — Agent 能按流程执行
4. 组合 — 多个 Skill 可以串联使用

类比：
- Agent = 手机
- Skill = App（封装好了"怎么做"）
- Skills 目录 = 应用商店

更贴切的类比：Skill 是给 Agent 发一张图书馆借阅证，不是强迫它背下整个图书馆，而是让它在需要的时候去查一本《SOP 手册》。

二、Skill vs Prompt：本质区别

维度 Prompt Skill
发现性 需用户主动提供，每次粘贴 Agent 自动语义匹配
执行性 "告诉 AI 做什么"，AI 自由发挥 结构化 Workflow，每步明确
复用性 一次性，散落在对话历史里 独立模块，一次定义到处复用

例子：补充单元测试
- Prompt：每次都要写"要用 Jest 框架，要覆盖边界情况，要检查覆盖率……"
- Skill：只说"帮我补充单元测试"，Agent 自动加载 test-driven-development Skill，按固定流程执行

三、三个架构级痛点

痛点一：巨型提示词灾难

把所有业务规则、操作流程写进系统提示词 → 上下文越来越长 → 注意力丢失（Lost in the Middle） → 中间部分的指令被忽略。

痛点二：执行能力和专业知识脱节

给 Agent 一个 SQL 查询工具，它能查，但不知道：
- 五百万行宽表该怎么写查询？
- 如何做多步关联验证？
- 数据异常了该怎么回退？

工具给不了"操作智慧"，必须单独注入。

痛点三：企业级可靠性缺失

生产环境要求：相同输入，相同输出。 但动态生成的提示词有大量随机性。

工程化系统需要确定性。需要把专家的隐性知识，转换成模型可以稳定执行的标准操作流程。

四、Agent 如何决定调用哪个 Skill（五步决策流程）

1. 识别任务类型 → 测试相关？文档处理？代码审查？
2. 判断是否需要 Skill → 是否需要结构化多步骤执行？
3. 语义匹配 → 在所有 Skill 的 description 中搜索最匹配的
4. 注入并执行 → 将完整 SKILL.md 注入系统提示词
5. 整合输出 → 返回结果

精妙设计：渐进式信息披露
- 启动时只加载 Skill 元数据（名字+描述，约 100 Token）
- 识别到任务后才加载完整 SKILL.md（几千 Token）
- 需要外部参考时才按需加载（几万 Token）

让 Agent 能"知道"几百个 Skill 的存在，但只在真正需要的时候才"学习"具体内容。

五、Skill 的结构（三层）

第一层：使用者视角（黑盒）

  • 说一句话 → Agent 按流程处理 → 返回结果

第二层：文件夹视角

my-skill/
├── SKILL.md          # 必需：核心文件
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：参考文档
├── assets/           # 可选：静态资产
└── templates/        # 可选：输出模板

第三层：SKILL.md 内部结构

---
name: test-driven-development
description: 在实现任何新功能或修复 Bug 时使用，必须在编写实现代码之前调用
---
# 测试驱动开发
## Goal
引导使用 TDD 方法论来实现具体功能。
## Workflow
1. 理解需求
2. 设计测试用例
3. 测试先行
4. 实现代码
5. 重构
## Constraints
- 绝对不能在写测试之前写实现代码
- 代码覆盖率最低要求 80%

三种类型：
| 类型 | 结构 | 示例 |
|------|------|------|
| 简单型 | 仅 SKILL.md，3-5 步 | 生成 Git 提交信息 |
| 多步骤工作流型 | 仅 SKILL.md，5-10 步含分支 | TDD 开发流程 |
| 资源依赖型 | SKILL.md + 外部资源目录 | 需要参考文档/脚本/模板 |

六、Skills vs Function Calling vs MCP

维度 Function Calling MCP Agent Skills
层级 代码级 协议级 语义级
确定性 高（代码写什么跑什么） 中 中（由 LLM 执行）
迭代速度 慢（需改代码部署） 中 快（改 Markdown 即可）
适用场景 金融交易、支付、数据库写入 跨平台/跨系统集成 工作流、非技术人员可定义

实际项目中的组合：
- 高层工作流 → Skills
- 底层精确操作 → Function Calling
- 跨系统集成 → MCP

七、生产环境四个坑

坑一：路由瘫痪 — Skills 互相打架

  • 症状：description 语义重叠，Agent 选择困难
  • 解法：每个 Skill 的 description 要有清晰边界，加"负向触发器"（明确写出"本 Skill 不处理 X"）

坑二：上下文隐性膨胀

  • 症状：Skill 没限制读取量，Agent 全量加载几万 Token
  • 解法：在 SKILL.md 里明确限制读取量（如"每次最多 5000 Token"）

坑三：description 写成了说明书

  • 症状：description 太长太复杂，路由器判断不准
  • 解法：短、精、关键词密度高，一两句话说明触发时机和核心能力

坑四：Skill 过了保质期

  • 症状：外部接口升级了 Skill 没更新，静默降级
  • 解法：建立定期审计机制，检查 Workflow 和 Constraints 是否仍对齐

八、核心引擎架构

SkillRegistry（加载所有 Skill）
       ↓
SkillRouter（根据用户输入选择 Skill）
       ↓
SkillExecutor（注入 Skill 文档并执行）

两套框架实现（OpenAI SDK / LangChain）逻辑完全一致，只是表达方式不同。

进化点

  1. 隐性知识显性化 — 文章的核心洞察：把专家的"操作智慧"结构化为 Skill，是 AI 工程化的关键一步。这和 Hermes 的 Skill 系统完全一致。
  2. 渐进式信息披露 — 只加载元数据 → 按需加载完整内容 → 按需加载外部参考，这是解决大上下文成本问题的优雅方案。
  3. 确定性与灵活性的平衡 — Skills/MCP/Function Calling 三者的边界划分，是 AI 工程架构的成熟标志。
  4. 负向触发器 — 在 description 中明确"不处理什么"，这是解决路由冲突的实用技巧，值得在 Hermes Skill 设计中借鉴。
  5. Skill 保质期问题 — 外部依赖变化导致 Skill 静默退化，需要建立审计机制。Hermes 的 skill-curator-review 正好对应这一点。

关键金句

"Prompt 是你告诉 AI'去做这件事'。Skill 是你提前准备好了'这件事怎么做'。"

"Skill 给 Agent 发的不是命令，而是一张图书馆借阅证。"

"拥有工具，不等于知道如何专业地使用工具。"
