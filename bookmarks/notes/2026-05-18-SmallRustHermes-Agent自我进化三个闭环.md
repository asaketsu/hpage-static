## 摘要

这篇文章是 Small Rust Hermes 系列的第三篇，前两篇分别讲了架构哲学和自我进化的七重困境。本文聚焦一个核心问题：Agent 的反思管道是单向的（产生→存储→遗忘），导致反思质量不随时间改善。作者通过三个闭环修复了这个问题：**记忆检索闭环**（TF-IDF + 本地嵌入实现语义检索）、**反思改进闭环**（审批历史反馈 + 延迟候选队列 + 技能有效性追踪）、**语义升级闭环**（fastembed 本地嵌入 + 混合匹配 + 冲突检测）。核心理念：**让系统的输出成为自己的输入**——管道变闭环，系统从"能反思"变成"会学习"。

## 核心内容

### 1. 诊断：三个断裂的闭环

| 断裂点 | 症状 | 根因 |
|--------|------|------|
| 记忆检索是盲的 | LLM 只能看到一行摘要，看不到正文 | 记忆被存储但不被检索回来影响推理 |
| 反思没有反馈环 | 第 N 次反思和第 1 次一样粗糙 | 审批日志被记录但从未被消费 |
| 技能匹配没质量追踪 | 低质量技能和高质量技能权重相同 | 匹配被触发但从不评估是否真的被用到 |

**共同特征：数据在产生，但没有回流。**

### 2. 闭环 1：记忆检索闭环

**问题**：一行索引的困境
- LLM 知道"有条记忆关于错误处理"，但不知道具体内容
- 类比：考试时知道学过但记不住——"知道我学过"≠"我掌握了"

**解决方案：TF-IDF 检索 + 相关记忆注入**
- 每轮对话开始时，用用户输入检索 top-k 条记忆正文
- 注入系统提示的 `Relevant Memories for This Turn` 区域

**TF-IDF 选型理由**（vs 向量嵌入）：
- 纯 Rust 实现，零外部依赖
- <1ms 延迟（<1000 条记忆）
- 不需要下载模型/GPU
- 确定性结果，可调试

**CJK 处理**：MIN_TOKEN_LEN=2（比技能匹配的 3 更低），额外生成字符 bigram

**显式学习路径**：
- `/remember <text>` — 立即持久化（Confidence::High）
- `/forget <id-prefix>` — 按前缀删除（有确认）
- `memory_search` 工具 — Agent 主动搜索记忆

### 3. 闭环 2：反思改进闭环

**问题：土拨鼠之日**
- 反复产生同类低质量候选（"用户喜欢暗色主题" → 被拒 → "用户喜欢暗色编辑器" → 被拒 → …）
- 反思不知道哪些被拒绝、为什么被拒绝

**修复：审批历史喂回反思提示词**
```
=== Recent reflection outcomes (learn from these) ===
- [ACCEPTED] memory: "用户偏好 anyhow 处理应用层错误"
- [REJECTED] memory: "用户喜欢暗色主题" — 太琐碎
- [REJECTED] skill: "自动提交工作流" — 太具体
```

**延迟候选队列**：
- "跳过"≠"丢失"
- 保存到 `deferred.jsonl`，下次会话重新展示

**技能有效性追踪**：
- 每次匹配记录 `SkillEvent::Matched`
- 检测技能正文是否出现在回复中 → `SkillEvent::Used`
- 有效性因子 = `clamp(used/matched, 0.5, 1.0)`
- 地板值 0.5：保留"低频但高价值"技能的可能性

### 4. 闭环 3：语义升级闭环

**TF-IDF 的天花板**：
- 查询"如何处理程序崩溃" vs 记忆"应用层错误使用 anyhow"
- 零字面重叠 → TF-IDF 完全无能为力

**本地嵌入模型选型**：
- 模型：AllMiniLML6V2（384 维，22MB，纯 CPU）
- 库：fastembed（基于 ONNX Runtime）
- 单条嵌入 <50ms

**双层检索**：嵌入优先，TF-IDF 兜底
- 无嵌入时退化为纯 TF-IDF
- feature gate 保护，可选编译

**混合技能匹配**：
- `最终分数 = 0.4 × token_overlap + 0.6 × embedding_score`
- token 是精确匹配保底，embedding 是语义发现

**冲突自动检测**：
- 写入时检测记忆冲突（vs 等到反思才发现）
- 余弦相似度超阈值 → 标记潜在冲突
- 阈值参数化，不硬编码

### 5. 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 检索优先级 | TF-IDF 先行，嵌入后置 | 新用户不需要等 22MB 模型下载，80% 场景 TF-IDF 够用 |
| 有效性地板值 | 0.5 而非 0.0 | "数据库迁移"技能在前端讨论时不触发但后端高价值 |
| 反馈条数 | 最近 10 条 | 足够看趋势，不占太多上下文，太早的反馈可能过时 |
| Mutex vs async 锁 | std::sync::Mutex | fastembed 是同步 API，锁持有 <50ms，不占 async runtime |
| 冲突阈值 | 参数化 | 不同场景敏感度不同 |
| embed feature | 可选 | 保证任何环境都能编译运行 |

### 6. 性能对比

| 指标 | TF-IDF | 嵌入 |
|------|--------|------|
| 初始化 | 0ms | ~2s（首次） |
| 单次检索 | <1ms | <50ms |
| 内存占用 | ~0 | ~50MB |
| 外部依赖 | 无 | ONNX Runtime |
| 语义理解 | 无 | 有 |
| CJK 支持 | bigram | 原生 |

### 7. 进化成熟度模型

| Level | 名称 | 特征 |
|-------|------|------|
| Level 2 | 主动反思 | 能提炼技能/记忆，有冲突检测，人类审批必须 |
| **Level 2.5** | **反馈驱动反思** | **审批历史影响反思、语义检索、有效性追踪** |
| Level 3 | 元认知 | 自动调整反思策略/提示词，记忆衰减，技能自动合并拆分 |

## 🔍 借鉴点

- **闭环设计模式** → Hermes Agent 的进化闭环可参考此框架，确保每条数据流都有回流
- **TF-IDF 先行策略** → 轻量方案先行、重方案后置的可选升级路径，降低用户门槛
- **有效性因子 0.5 地板值** → 技能权重调优的参考值，保护低频高价值技能
- **延迟候选队列** → "跳过≠丢失"的设计哲学，适用于任何需要用户审批的系统
- **冲突检测写入时触发** → 比事后发现早一个环节，减少数据冗余
- **最近 10 条反馈** → LLM 上下文窗口有限时的经验值

## 💡 启发

- **管道 vs 闭环**是系统设计的基础思维：不只是 Agent，任何数据系统都应该检查"数据是否回流"。CI/CD、监控系统、推荐系统都是如此
- **"知道学过"≠"掌握了"**：这个类比精准概括了 RAG 系统的核心挑战——索引只是目录，正文才是知识
- **混合匹配的权重分配**：0.4 token + 0.6 embedding 的比例值得实验——在 Hermes 的 skill matching 中可以尝试类似策略
- **feature gate 设计**：Rust 的 feature gate 思想可以推广到任何系统——核心功能零依赖，高级功能可选

## 🔮 预判

- **Level 3 元认知是下一步关键**：自动调整反思提示词比单纯读取反馈更接近真正的"学习"
- **嵌入模型会持续小型化**：22MB 的 AllMiniLML6V2 会更快更小，端侧 AI 推理的门槛继续降低
- **Hermes Agent 的 selective-proxy + watchdog 事件驱动架构** → 可以和 Small Rust Hermes 的闭环设计结合，形成更完整的自进化系统
- **Agent 之间的经验交换**（如 ubot↔jbot 的交换池） → 本质上也是一种闭环——一个 Agent 的输出成为另一个的输入
