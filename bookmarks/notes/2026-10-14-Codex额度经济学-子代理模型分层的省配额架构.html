归纳总结

Codex 额度焦虑的根因不是额度少，而是子代理默认继承主线模型——主线开 GPT-6.1 Sol（每 5h 仅 15-160 条消息），派出去扫文件的十个"小弟"也全是 Sol。解法只需 4 行配置：主线 model = "gpt-6.1-sol" + [agents] 下 default_subagent_model = "gpt-6-luna"（同套餐 350-3000 条，单价仅 Sol 的 1/20）。配套两把刀：只读侦察兵 scout（结果限 20 行）+ 修理工 fixer（只执行已定方案），加上 AGENTS.md 派活规则（架构/权衡不往下派）与需求预聊模板（ChatGPT 普通聊天与 Codex 共用额度，先聊透再开工）。三个白烧额度陷阱：Fast 模式 2.5 倍消耗不自知、什么活都派子代理（官方明说子代理比单 agent 更耗 token）、方案没对齐就开干。

内容整理：核心配置与两个子代理

4 行核心（~/.codex/config.toml）：

model = "gpt-6.1-sol"          # 顶层, 在[agents]上面
[agents]
default_subagent_model = "gpt-6-luna"
default_subagent_reasoning_effort = "high"   # Luna便宜, 官方建议从high起步

scout 侦察兵（~/.codex/agents/scout.toml）：sandbox_mode="read-only"；只做调查不提方案；先搜索定位再读具体文件禁整库扫描；返回结果 ≤20 行（文件路径+关键函数+问题，原始日志不整段贴回）——这条最值钱：子代理贴回一大坨日志，主线读它也烧额度，等于白省。

fixer 修理工：只执行主线已定方案；最小改动不碰无关文件；只验证改到的部分；方案没覆盖就停下报告不自己发挥。

内容整理：派活规则与流程

AGENTS.md 六条（最后一条别删）：
1. 主线负责理解需求、定方案、最终判断和汇总
2. 找文件/读代码/搜关键词/看日志/跑测试 → scout
3. 方案已明确的小改动（文案/批量替换/补测试/单函数）→ fixer
4. 子代理只返回结论和文件路径，不带原始输出回主线
5. 多个子代理不同时修改同一文件
6. 架构、需求不清、需要权衡取舍 → 主线自己处理，不往下派（Luna 擅长目标明确的活，要它拍板架构，省下的额度花在返工上）

标准流程：scout 摸现状(20行) → 主线定方案等确认 → fixer 并行执行(同文件只派一个) → scout 跑测试 → 主线总结。第 2 步"等确认"是故意的——改错一遍的额度比多问一句贵。

需求预聊模板：普通聊天里"先别给代码，问我 5 个最关键的问题"→ 整理 300 字任务单（目标/范围/验收标准/已知限制）→ 交给 Codex。

内容整理：三个白烧陷阱

陷阱 数据 对策
Fast 模式不知道开着 消耗=标准 2.5 倍 CLI /fast 切回
什么活都派子代理 官方明说子代理比单 agent 耗 token（每个都要自己读文件调工具） 只派读多写少的活；一句话能问完的别派
额度见底就慌 当前轮可跑完；Plus/Pro 可加 credits；可切 API key 按量计费 认识机制不慌

另：GPT-5.5 已于 10-14 从 Codex 下线，配置里的旧模型名要换。

💡 价值分析：对我们的启发

✅ 已在做的（同构验证）

  • 模型分层思想：我们的 adaptive-inference-routing skill（按任务复杂度分配 token 上限）+ 免费模型四线（智谱主力+HF+GitHub+GMX）= 同一思想在 Hermes 侧的实现；夜间智谱错峰 = 同域的额度经济学
  • scout 的"≤20 行" = 我们的 context 压缩/工具输出修剪原则；"只返回结论不贴原始输出" = 子代理摘要回传
  • fixer"方案没覆盖就停" = 昨天 GrokBot 笔记的 agent 执行规约第 7 条（与描述不符就停下来问）——两次独立出现，是委托类任务的通用铁律
  • "等确认"断点 = 我们的 mid-turn steering/人工确认门

🔥 重点行动

  1. 最直接的移植：delegate_task 的模型分层——Hermes 的子代理默认继承父模型（文档明示"Children inherit the parent model unless pinned"），我们派杂活（批量读文件/搜索汇总）给子 agent 时同样在烧 glm-5.3 额度。可以在 delegation 配置里 pin 轻模型给"读多写少"类子任务，dense 推理留给主线——这正是本文核心配置在 Hermes 的等价物
  2. 需求预聊模板收编：复杂任务先在低成本会话里"问 5 个问题→300 字任务单"，再交重模型执行——与我们"分析前置、执行后置"的分层已有实践吻合，可固化为委托模板
  3. 派活规则第 6 条进委托 SOP：架构/权衡不往下派——防止子 agent 自由发挥返工

⚠️ 保持怀疑的

  • "多干 10 倍活"是标题修辞：Sol vs Luna 的消息条数差 20 倍（160→3000），但实际取决于杂活占比——纯架构日省不了多少
  • 子代理更耗 token 是官方承认的（每个都要重建上下文读文件），文中也提了，但读者容易只记"多干 10 倍"忽略"什么活都派反而更贵"
  • Luna 单价 1/20 是 credits 计价口径，订阅额度口径的换算文中未给完整数据

📊 趋势判断

订阅额度正在成为 AI 编程的新稀缺资源，优化对象从"token 数"上移到"哪个模型烧的额度"——额度感知调度会成为 CLI agent 的标配能力（/status 消耗对比、自动降级、Fast 模式警示）。更深一层：主线贵模型+子代理便宜模型的分工，是推理扩展经济学在订阅制的镜像——简单活不值得贵模型思考，这个分层逻辑与 test-time compute scaling（难题多想）互为表里。AGENTS.md 作为"派活规则"的载体正在标准化，相当于给 agent 团队写岗位说明书。
