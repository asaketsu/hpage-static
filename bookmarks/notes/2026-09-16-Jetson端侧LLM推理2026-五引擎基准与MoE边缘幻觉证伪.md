# Jetson 端侧 LLM 推理 2026：五引擎基准、TensorRT Edge-LLM 与 MoE 幻觉证伪

> 探索日期：2026-09-16 ｜ 兴趣等级：L3 ｜ 来源：4 篇（2026-04 活体基准 + NVIDIA 官方 + arXiv 实证）
> 关联平台：本机 Jetson Orin Nano Super 8GB（67 TOPS）+ nexa-local-inference
> 前序笔记：2026-09-12-KV-Cache浪费与PagedAttention救赎 / 2026-07-19-LLM推理引擎对决

## 核心命题

2026 年端侧 LLM 完成了从"能跑"到"能产线"的跨越：**成本模型倒挂**（<1000 req/day 时边缘 TCO 胜云 API 一个量级）+ **C++ 原生运行时**（推理路径零 Python）+ **MoE 边缘幻觉证伪**（活跃参数优势在 8GB 统一内存上只兑现一部分）。对 Jetson Orin Nano 8GB 用户，选型答案已收敛：INT4 + llama.cpp/TensorRT Edge-LLM + 1.5-4B dense 模型。

## 核心发现

### 1. 2026-04 活体基准：三档 Jetson × 五引擎 × 三量化完整矩阵

iotdigitaltwinplm 季度更新的 living benchmark（首版 2026-04，GitHub 开源测试脚本）：

| 模型/配置 | 平台 | 解码吞吐 | 能效 |
|-----------|------|---------|------|
| Llama 3.2 3B INT4 (TRT-LLM, MAXN) | AGX Orin 64GB | ~85 tok/s | 3.0 tok/s/W |
| Llama 3.2 1B FP16 | Orin Nano Super | ~55 tok/s @12W | — |
| Phi-3.5-mini 3.8B INT4 | AGX Orin | ~62 tok/s | 质量保持最佳 |
| Qwen2.5-1.5B INT8 | Orin Nano Super | ~70 tok/s @10W | **7.0 tok/s/W 冠军** |
| Gemma 2 2B FP16 | AGX Orin | ~120 tok/s | 4.8 tok/s/W |

- Prefill：AGX 128-token p50 ~50ms；Nano 120-180ms（LPDDR5 带宽是瓶颈）
- 成本倒挂临界点：**<1000 req/day 边缘 TCO 胜；<100 req/day 胜一个数量级**（AGX 64GB $2,499 / 36 月摊销 / 5000 req/day ≈ $0.0004/次）
- 方法论严谨：5 次热身 + 50 样本 + 95% CI + 实测功耗（19.5V/5V 电流）

### 2. NVIDIA TensorRT Edge-LLM：推理路径零 Python 的新官方栈

Jetson AI Lab 2.0 官方教程（NVIDIA adsahu-nv 出品），定位嵌入式 C++ 推理运行时：

```
工作流：量化(INT4/NVFP4/FP8) → ONNX 导出 → TRT engine 编译 → C++ 原生推理
API 全貌：createRuntime → capture CUDA graphs → handleRequest()
```

- **Orin (SM87) 支持 INT4 AWQ；NVFP4/FP8 需 SM89+/Thor**
- Qwen3-4B-Instruct INT4 AWQ 官方演示机型就是 **Orin Nano 8GB**（与本机同款）
- 支持矩阵广：Llama 3.x / Qwen3 dense+VL / InternVL3.5 / Phi-4-Multimodal / Nemotron-Nano（Mamba2+Attention 混合）/ Alpamayo R1（VLA 机器人）
- 关键坑：FP8 ONNX 导出需 **6× 模型体积的 GPU VRAM + 20× CPU RAM**（8B 模型），边缘场景优先 INT4 AWQ；Orin Nano 编译用 `make -j4` 防 RAM 耗尽

### 3. MoE 边缘幻觉证伪（arXiv:2606.21428，实测论文）

> OLMoE-1B-7B（1.3B active / 6.9B total）vs dense 基线，Apple M2 Pro + **Jetson Orin Nano 8GB**，llama.cpp 实测：**MoE 的活跃参数优势只部分兑现，答案是设备相关的**。

对 8GB 统一内存 SoC 的含义：
- MoE 总参数全驻内存（6.9B 权重吃掉 INT4 后 ~4GB），活跃参数省的是**算力**不是**显存**
- 解码吞吐受内存带宽限制（Nano 68 GB/s），MoE 每 token 仍需读全部路由专家的权衡在 llama.cpp 上不占优
- 选型结论：**8GB 边缘选 dense 1.5-4B，不追 MoE**（与云端"MoE 省算力"直觉相反）

### 4. 8GB 内存档的现实选型梯度（NVIDIA 官方博客交叉验证）

| 档位 | 模型 | 用途 |
|------|------|------|
| Nano 8GB | Llama 3.2 3B / Phi-3 / Qwen3-4B INT4 | 隐私助手/分类/抽取/摘要 |
| AGX Orin 64GB | gpt-oss-20b / Llama 3.1 70B 量化 / Qwen2.5-VL-7B | agent 工作流/多模态 |
| AGX Thor 128GB | 100B+ 模型 | 数据中心级边缘 |

Orin Nano 8GB 的甜点区：**1.5-4B dense INT4**，能效冠军 Qwen2.5-1.5B INT8（7.0 tok/s/W）适合电池场景。

### 5. 边缘栈分层架构已成标准

```
应用层 (REST/gRPC)
  ↓
推理服务 (Triton / vLLM / Ollama)   ← 调度开销 20-50ms
  ↓
推理引擎 (TRT-LLM 编译型 / vLLM 动态 / llama.cpp 便携)
  ↓
CUDA 12.6 + Tensor Core (FP16/INT8 2-4× 加速)
```

取舍：vLLM/Triton 加 20-50ms 调度换并发；llama.cpp 直连 5ms 但单请求。单机机器人场景选后者。

## Actionable Insights

1. 本机若跑本地 LLM：Qwen3-4B-Instruct INT4 AWQ（TRT Edge-LLM 同机型官方路径）或 Qwen2.5-1.5B INT8（能效最优）
2. FP8/NVFP4 路线在 Orin (SM87) 不可用，量化选择收敛 INT4/INT8/FP16 三档
3. agent 工作流要 20B 级模型时，本机 8GB 不可行——走云 API 或换 64GB 档，不要硬塞

## 关键风险与盲点

- living benchmark 是个人站（iotdigitaltwinplm），非 NVIDIA 官方；数字方法论透明但设备热状态/批次差异未跨实验室复现（来源级别：社区实测，方法论公开）
- MoE 论文 v3 是 FAIEMA 2026 投稿（workshop 级），OLMoE 单模型结论外推到 Qwen3-MoE 系列需谨慎
- TRT Edge-LLM 的 engine 编译期长（per-model），模型频繁更换场景不如 llama.cpp 灵活

## 一页速查

> **8GB Orin Nano 铁律**：dense 1.5-4B + INT4/INT8；MoE 省算力不省显存，8GB 别碰。
> **吞吐锚点**：Qwen2.5-1.5B INT8 ≈ 70 tok/s @10W（7.0 tok/s/W）；Llama-3.2-3B INT4 @AGX ≈ 85 tok/s。
> **成本倒挂**：<1000 req/day 边缘胜；<100 req/day 边缘胜一个量级。
> **量化档位**：Orin SM87 只到 INT4 AWQ；NVFP4/FP8 是 SM89+/Thor 专属。
> **栈取舍**：并发用 vLLM/Triton (+20-50ms)；单请求低延迟用 llama.cpp/Edge-LLM 直连。
