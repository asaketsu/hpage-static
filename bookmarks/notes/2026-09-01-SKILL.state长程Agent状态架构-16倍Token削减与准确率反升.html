一、内容详细整理

问题：Agent 上下文的"垃圾场化"

推文开篇点题（原文）："Agent 跑得越久，上下文有时越像一个垃圾场"——几十步之后，旧观察、过期状态、工具输出和推理过程全堆在一起，模型每走一步都要重新判断哪些信息还有效。

论文摘要的技术表述：现有 agent runtime 通过持续追加观察、动作和中间推理 trace 到不断增长的对话历史来维持执行，导致长程任务中的延迟劣化与上下文污染（context-poisoning）失败。

解法：SKILL.state 架构

核心思想一句话：别一直保存完整历史，只维护「当前状态」。

每一步 Agent 只看到三样东西（论文定义的三元组）：

(P, Σ_t, O_t)
 P   = 固定的 Skill 规范（immutable skill specification）
 Σ_t = 当前结构化执行状态（mutable execution state）
 O_t = 最新观察（latest observation）

推理仍然正常进行，但完成这一步后就被丢弃——只把真正会影响未来执行的信息，以"验证过的状态更新 ΔΣ_t"形式写回 state。中间推理 R_t 在产出状态补丁后立即丢弃，每步 prompt 占用 O(1)，prompt 大小不随执行历史增长。

关键词：explicit, mutable execution state（显式可变执行状态）替代 append-only conversational history（只增不减的对话历史）。

实验结果（推文 + daily.dev 交叉印证）

基准 传统 Stateful Agent SKILL.state 改善
100 步仓库任务（Gemini-3-Flash） 累计 1,062,387 token / 准确率 0.91 65,408 token / 准确率 0.94 token ↓16 倍，准确率反升
InterCode CTF 基线 同时提升成功率 + 减少 token 双赢
τ-Bench 基线 同时提升成功率 + 减少 token 双赢

补充口径（daily.dev）：LangGraph 式保留全历史的 baseline 在同一任务上的对比数据。论文自述结论：跨数据集、模型、执行环境均有效，显式执行状态是架构无关（architecture-agnostic）的可扩展长程技能抽象。

归纳总结

  1. 本质是把"记忆"改成"寄存器"：append-only 历史像无限增长的内存转储，SKILL.state 像一组 CPU 寄存器——每步只保留体系结构状态（architecture state），中间计算全部挥发。这是操作系统进程切换思想在 Agent 上下文管理的重演。
  2. Token 减 16 倍且准确率反升不是免费午餐，代价在状态设计：效果好坏取决于 Σ_t 的 schema 质量——什么信息"真正影响未来执行"需要领域知识来定义，写错 schema 就是信息丢失。论文的架构无关性声明说明抽象稳健，但落地成本在状态建模。
  3. 与"压缩历史"路线的根本区别：压缩/摘要历史仍保留时序包袱（且摘要有损）；状态替换直接改变信息模型——不是"把历史变小"，是"不再需要历史"。
  4. 验证是闭环的钥匙：ΔΣ_t 必须 validated——没有验证器的状态更新就是另一种幻觉入口。这与我们 verification-gate/确定性 check 哲学完全同构。
  5. 适用边界：程序性长程任务（有明确状态变量：仓库库存/CTF 进度/工单字段）最受益；开放式创意任务（历史本身是语义资源）未必适合。

二、趋势判断

  1. "状态化上下文"会是 2026 下半年 Agent 运行时的主流改造方向：Google（SKILL.state）、LangGraph 系、各家 memory 初创都在收敛到"显式状态 + 按需检索"共识，append-only 对话历史作为执行机制正在被淘汰。
  2. Token 经济学成为架构决策的第一驱动力：16 倍差距直接改写成本模型——长程 Agent 的商业可行性（客服/运维/研究自动化）此前被 token 成本卡死，此类架构解锁市场。
  3. 准确率反升证明"context-poisoning"是真实失败模式：更多历史≠更好决策，无关信息是负资产——这会推动"少即是多"的上下文工程成为显学（与 Lost-in-the-Middle 证据链汇合）。
  4. Skill（P 不变）+ 状态（Σ_t 可变）的分离即"程序与数据分离"：这为技能复用/版本化/市场化（npx skills add 生态）提供运行时基础——skill 不再绑定具体对话，可跨任务实例化。

三、关联分析（对我有什么提升 + 如何实施）

关联对象：本机 Hermes 生态（context-compressor / harness-checkpoint / cron 长任务 / 400+ skills）

  1. 与 context-compressor skill 的对照升级：我们目前的策略是"大工具输出存文件、上下文留摘要"——属于压缩历史路线；SKILL.state 是替换历史路线。实施：在 context-compressor skill 里补一节"状态化改造模式"：长任务（>50 步）场景下，建议 cron/subagent 改用"active_tasks.json 式状态文件 + 每步只读状态"——其实 session-boot 的 active_tasks.json 已是雏形，差的是"丢弃中间推理"的纪律。
  2. 与 harness-checkpoint 的同构确认：checkpoint 保存的就是"体系结构状态"（进度快照）而非对话历史——验证了我们既有设计。实施：checkpoint 里可增加 ΔΣ 语义（每次更新写"变化了什么+为什么影响后续"），恢复时更快定位。
  3. 对长 cron 任务（auto-dream/sniff 处理）的直接启示：这些任务跑几十步、上下文膨胀明显。实施：评估 sniff-dequeue 等高频 cron 的 prompt 结构——工具输出尽量落盘、注入的只是"当前队列状态+本条内容"，已经部分符合 (P, Σ, O) 三元组，可以显式化改造。
  4. 与旧笔记 Agentic-Skills系统基础（explore/2026-09-01）的分工：那篇是 Skills 系统综述，SKILL.state 是其中"存储与记忆架构"一节的引用源之一（虚拟 OS 分页：临时推理即弃）；本篇专篇展开其 O(T²)→O(1) 机制与实证数据——两篇构成"综述→专精"两层。
  5. 对 Hermes 官方 context 管理的观察：Hermes 有 memory 注入与会话压缩，但 Agent 循环内的中间推理仍是 append-only——这是上游架构问题，不是我们能改的；可改的是我们自己的 skill/cron 设计模式（见 #1/#3）。
  6. 与量化体系"复盘"的同构（克制版）：cycle-records.json 持久化周期阶段而非全部行情历史——"只留影响未来决策的状态"与"只留周期位置不留每日波动细节"是同一原则，仅作思维印证。

指南分析

何时采用状态化上下文：

场景 适用性 理由
程序性长任务（>30 步，有明确状态变量） ✅ 强烈 token 线性化 + 免疫 context-poisoning
多阶段 pipeline（每阶段产出结构化结果） ✅ Σ_t = 各阶段已完成产物+当前阶段输入
对话式助手（用户语义依赖历史） ⚠️ 慎用 会话历史本身是语义资源，摘要+检索更合适
一次性短任务（<10 步） ❌ 不值得 状态 schema 设计成本 > 收益

落地最小模板（从论文三元组提炼）：

每步 prompt = Skill 固定指令 + 当前状态 JSON + 本步观察
状态更新 = 模型输出 ΔΣ（只含影响未来的字段）→ schema 验证 → 合并
中间推理 = 用完即弃（不写回任何历史）
