## 核心事件

Ladybird 浏览器（前 SerenityOS 浏览器引擎）宣布关闭所有公开 Pull Request。从即日起，代码变更只能由项目维护者引入。这是首个因 AI 工具影响而关闭公开贡献通道的大型开源项目。

HN 排名 #1，563 pts，引发开源社区广泛讨论。

## 决策逻辑（Andreas Kling 原文要点）

**传统开源信任模型**：
  贡献者提交补丁 → 补丁质量暗示投入程度 → 投入程度 = 善意的合理代理 → 长期贡献积累信任
  这个模型运行了几十年，是开源生态的基石

**AI 打破的假设**：
  "一个大补丁曾经意味着大量努力，而这份努力是善意的合理代理。这个假设不再成立。"
  AI 工具使任何人都能快速生成看起来像"认真贡献"的代码，成本趋近于零

**浏览器安全的特殊性**：
  浏览器在用户机器上运行来自整个互联网的不受信任输入
  一个伪装良好的漏洞就足够攻击者完成渗透
  已经观察到开源社区中有耐心、资源充足的攻击活动来赢得维护者信任

**核心原则**：
  "代码是手打的还是 AI 生成的并不重要。重要的是谁对它负责。"
  Ladybird 正在成为一个面向真实用户的浏览器，引入变更的人必须是决定这些变更属于项目的人

## 措施

1. 关闭所有当前开放的公开 PR
2. PR 功能仅对项目维护者开放
3. 不创建替代提交路径（issue、评论、邮件、fork 不作为影子贡献系统）
4. 项目仍保持开源，源代码继续公开
5. 外部参与通过：bug 报告、缩减测试用例、网站测试、标准讨论、设计讨论、安全报告、技术反馈

## 行业背景

这不是孤立事件。2025-2026 年开源社区面临系统性挑战：

  Google 报告 2025 年开源项目新增贡献者增长但代码质量下降
  多个大型项目（Linux kernel 部分子系统、FreeBSD）开始限制 AI 生成代码的提交
  GitHub 推出 AI 生成代码标记倡议，但采用率低
  npm/PyPI 出现 AI 批量生成的垃圾包问题

Ladybird 是第一个将此上升到"关闭公开贡献"级别的项目，其理由充分且逻辑自洽。

## 借鉴进化点（3条）

1. 🔧 **Hermes Skill 信任模型重建**：Ladybird 的困境直接映射到 Skill 生态。当前 Skill 通过文件系统注入，缺乏质量门控。可借鉴 Ladybird 的"维护者负责制"——将 Skill 分为"核心维护"和"社区贡献"两层，核心 Skill 经过验证后锁定，社区 Skill 标记来源和验证状态。auto-skill 的自动创建应该增加质量评估环节
2. 🔧 **AI 代码审计替代信任代理**：传统代码审查依赖"努力 = 善意"假设。AI 时代需要转向形式化验证 + 自动化安全扫描。Hermes 的 skill-vetter 和 verification-gate skill 正是这个方向。可以增强：对新生成的 Skill 自动运行 AST 级别的安全扫描，标记外部网络调用、文件系统写入、命令执行等危险操作
3. 🔧 **贡献信号多元化**：Ladybird 保留了 bug 报告、测试用例、技术讨论等非代码贡献通道。对于 Hermes 双机协作（ubot-jbot），可以设计更丰富的经验交换格式——不仅是 Skill 文件交换，还包括"问题模式"、"失败案例"、"修复历史"等元数据，使经验交换的信号更丰富，不依赖单一维度

## 深层思考

Ladybird 的决策是一个分水岭时刻。它标志着开源社区必须重新定义"贡献"的含义：

  代码不再是唯一的价值载体
  信任不能仅从代码量和质量推断
  项目治理需要从"代码审查"扩展为"能力审查"

对 AI Agent 生态的启示：当 AI 能力越来越强，人类维护者的核心价值不再是"写出好代码"，而是"判断哪些代码应该被接受"。这恰恰是 Agent 系统中人类 oversight 最应该聚焦的层面。

Ladybird 选择了保守策略——收窄贡献通道。另一个可能的未来是：开源项目发展出 AI-native 的信任模型，用更精细的信号（贡献者历史上下文、代码意图分析、行为模式）来替代粗粒度的"努力=善意"假设。两条路都可能成为主流。
