摘要

安全研究者 Kasra Rahjerdi 花费 $1500 实测 10+ 主流 LLM 的安全攻防能力。他构建了一个故意留有 Firebase 配置泄露漏洞的 React Native 应用，让各 LLM 尝试独立发现并利用漏洞。结果令人深思：GPT-5.5 以 7/10 的成功率遥遥领先，DeepSeek V4 Pro 3/10，Claude Sonnet 4.6 和 Opus 4.8 各 2/10，多数模型完全失败。研究揭示了 LLM 安全研究的真实成本、模型间巨大的安全能力差距，以及安全护栏的双刃剑效应。

核心内容

1. 实验设计

  • 目标应用：React Native (Expo) + FastAPI 后端 + Firebase 数据层
  • 漏洞类型：google-services.json 泄露 → 直接访问 Firebase Firestore（Broken Access Control / BOLA）
  • 每次运行上限：$10 + 2 小时
  • 评估工具：pi harness + pi-goal-x 扩展（Claude 使用 Code -p 模式）

2. 排行榜

模型表现（10 次完整运行）：
1. GPT-5.5：7/10（40%-89% CI），$9.46/solve，260k tokens/run
2. DeepSeek V4 Pro：3/10（11%-60% CI），$0.62/solve，194k tokens/run
3. Claude Sonnet 4.6：2/10（6%-51% CI），$45.75/solve，390k tokens/run
4. Claude Opus 4.8：2/10（6%-51% CI），$16.15/solve，113k tokens/run
5. DeepSeek V4 Flash：0/10，$0.08/run
6. Gemini 3.1 Pro Preview：0/10，立即拒绝（仅 9k tokens/run）
7. Gemini 3.5 Flash：0/10，早期拒绝
8. MiniMax M2.7：0/10，从未发现 Firebase 攻击路径
9. Step 3.7 Flash：0/10，误报已发现漏洞

部分运行模型：GLM-5.1 1/4、Kimi-K2.6 1/1

3. 关键发现

  • GPT-5.5 几乎每次都直接聚焦 Firebase，不走 API 弯路
  • Claude Opus 4.8 多次接近正确答案但被安全护栏中断（"晚期拒绝"）
  • Gemini 系列立即拒绝安全研究请求（9k tokens 说明没尝试解题）
  • DeepSeek V4 Pro 的 $0.19/run 性价比极高
  • 安全护栏是双刃剑：保护了普通用户，但限制了安全研究人员

关键概念

  • BOLA (Broken Object-Level Authorization)：对象级授权缺失，本案例中 Firebase 直接暴露数据层
  • Verified Bug / Solve Rate：LLM 实际成功利用漏洞的比例，用 95% Wilson 置信区间量化不确定性
  • Late Refusal：晚期拒绝——LLM 已接近正确答案时才触发安全护栏，既浪费了 token 又没完成研究
  • pi harness + pi-goal-x：自动化 LLM 攻击测试框架，强制模型持续尝试

能力边界

  • 非科学评估，样本量有限（成本限制在 $1500）
  • 单一漏洞类型（Firebase BOLA），不代表 LLM 通用安全能力
  • 测试环境为故意设计的漏洞应用，与真实场景有差距
  • OpenAI 账户已预批准安全研究，其他用户可能遇到更严格的拒绝

最佳实践

  • 安全研究使用 LLM 时，优先选择 GPT-5.5（成功率最高）或 DeepSeek V4 Pro（性价比最高）
  • 需要预批准安全研究账户以避免拒绝
  • Firebase/Supabase 应用必须检查客户端配置文件泄露
  • 设置 token 预算和时间上限控制成本
