归纳总结

yibie 转述的核心命题：RAG 检索不准时，调切块大小、换 embedding 模型都是表层修补——"切块 + 语义相似度"这件事本身有结构缺陷：切块破坏连续性（合同"第 3 条例外"、排障"第 5 步"必须连上下文才有意义），且术语密集领域（法律/金融/技术文档）"语义相近的词"和"答案实际所在位置"经常不是同一个地方。PageIndex 把前提翻过来：不做向量化，从文档标题结构生成可推理的目录树，让 LLM 像人翻长文档一样逐层下钻检索。本篇增量不在机制（旧笔记已覆盖），而在三条实战硬经验：①裸标题下钻必失败（抽象标题"第 4 章 运营"让每个章节都可疑），节点必须配 1-2 句摘要且人工核对一遍；②小成本验证法（5-10 题只测"该打开哪个标题"的目录导航准确率）；③最顺配置是两段式混合——目录导航粗筛到 2-3 章，章内再跑向量细筛，不必推倒现有 RAG。

内容整理：从裸标题失败到两段式混合的四段实战路径

1. 问题定义：为什么"相似 ≠ 相关"

  • 传统 RAG 隐含假设"语义相似 = 内容相关"，在专业长文档场景系统性失效
  • 两类典型断裂：连续性断裂（"第 3 条例外"切成块后失去所指）与位置错位（术语密集文档中相似词聚集处 ≠ 答案所在处）
  • 这与官方仓库口径一致：README 直呼向量检索为 "vibe retrieval"（凭感觉检索），主张推理式检索可追溯、可解释、带页码引用

2. 机制四步（与官方两步法对齐）

步骤 动作 官方对应
① 建树 抽出章/节/条层级 → 目录树 Step 1: Generate TOC tree index
② 摘要 LLM 给每个节点写一句"该节讲什么" --if-add-node-summary（默认 yes）
③ 下钻 提问时从根逐层判断"该读哪个子节点" Step 2: Reasoning-based tree search
④ 取回 定位末端小节后取正文生成答案 返回 node_id + 页码范围

人的翻文档行为对照：先看目录猜"大概在第 4 章" → 看小节标题继续缩 → 到末端小节读正文作答。副作用实在：不用搭和运维 embedding 数据库，索引重建/向量库版本管理/相似度阈值调整全部消失。

3. 失败教训与修正（本篇最有价值的增量）

  • 第一次实现失败：只把标题文字丢给模型 → 碰到"第 4 章 运营"这类抽象标题，每个章节看起来都可疑，缩不下去
  • 解法：每个标题补 1-2 句"这一节具体处理什么、谁在什么时候该读"的摘要，并人工核对一遍
  • 关键认知：自动生成的摘要不能盲信——人工看这一遍反而是最省时间的一步（坏摘要会把下钻引向错误分支，且错误静默不可见）

4. 实测与边界条件

  • 实测（日本工程师，转述未核验）：约 80 页、4 级标题的内部业务手册；问"退货处理的例外条件"，传统向量检索多次命中含相似词的错误小节；目录导航一次走对章节的概率明显提高
  • 不适用：聊天记录、纯要点笔记等没有标题结构的文本——没有可跟随的树，建目录无收益
  • 代价：每次提问多调几次 LLM 下钻，延迟和成本对实时场景要提前估算（官方参数佐证：每节点默认 max 20k tokens，索引构建本身就消耗大量 token）

5. 小成本验证法（引入前的最小实验设计)

  1. 挑一份标题清晰的文档
  2. 只抽标题做成层级列表，每个标题配一两句摘要
  3. 准备 5-10 个常见问题
  4. 让模型只看目录回答"该打开哪个标题"，与正确章节对准确率
  5. 准确率低 → 回去改标题命名或摘要粒度（不动检索代码）

6. 两段式混合（作者判断：不是二选一）

章节级粗筛交给结构，句级细匹配仍交给向量。

先目录导航缩到 2-3 个可疑章节 → 只在这几章内部跑向量检索。对已有 RAG 的团队 = 不推倒重来，在现有检索前加一层目录预筛，改动最小。

7. 引入前四条自查

# 自查项 判据
1 文档至少有章、节两级标题 无结构 → 不适用
2 每章文本量在 LLM 一次读得下范围内 超限 → 树深度/切分要重设计
3 单次提问多几次模型调用的成本延迟可接受 实时场景 → 慎用
4 能从 5-10 题小验证起步 直接废掉现有向量检索 = 错误

四条都满足才值得试；文档本来没标题 → 继续打磨向量检索是更短的路。

趋势判断

  • "结构推理"正在成为检索第三范式：关键词（精确匹配）→ 向量（语义匹配）→ 树推理（结构导航），三者不是替代而是分文档形态共存——结构化长文档走树、海量短内容走向量、精确引用走关键词
  • 混合架构是终局形态：本篇两段式（目录粗筛+章内向量）与已有笔记预判、hybrid-search 三路融合互相印证——单一检索范式的阵营化论战意义在下降，分层编排能力在上升
  • 成本曲线是变量：目录下钻的多次 LLM 调用成本随模型降价持续下降，半年前"成本高"的反对理由正在失效——这解释了 stars 五个月 +39% 的持续热度
  • 对无结构文本的补课：聊天记录/要点笔记不能建树，但可以用 LLM 先"生成结构"再建树——结构生成与树检索的合并是可预期的下一步

指南分析

对我有什么提升：
1. 检索不准时先判文档形态再选工具——标题结构是否清晰是比"换 embedding 模型"更前置的诊断问题
2. "自动生成摘要必须人工核对一遍"是所有 LLM 中间产物的通用纪律——坏摘要的错误是静默的，人工核对是最省时间而非最费时间的环节
3. 最小验证法（只测目录导航准确率，不动检索代码）可迁移到任何检索方案评估

如何实施：
1. rag-index-rebuild skill 补一路"目录树预筛"模式：利用笔记库现成的标题层级 + 模块结构，对结构化查询先做树导航再向量细筛（触发条件：用户查询含明确章节指向，如"XX 的四个步骤在第几篇"）
2. 笔记系统的 backlink/索引层在下次重建时评估树化组织——本质上 batch-note-linking 的关键词关联可升级为层级导航
3. 用户领域文档（适航/型号资料）若引入 RAG，直接按四条自查表评估目录树方案——该领域文档结构严密，是树检索的高适配场景
