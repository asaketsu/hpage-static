摘要

这是一篇写给完全没用过 Codex 的新手教程。作者将 Codex 定位为"坐在你项目目录里的 AI 编程同事"，而非聊天机器人。教程系统讲解了 Codex 的斜杠指令体系（10 条核心指令 + 2 条分支指令），并给出了新手第一次使用的完整流程。核心方法论：先 /init 让 Codex 认识项目 → 再 /status 确认状态 → 大任务先 /plan → 关键文件用 /mention → 改完必须 /diff → 提交前跑 /review。

核心内容

一、Codex 的本质定位

Codex ≠ 聊天机器人。它是"坐在你项目目录里的 AI 编程同事"，能直接读文件、改文件、跑命令、看 diff、做 review。

两种输入：
| 类型 | 示例 | 作用 |
|------|------|------|
| 普通 prompt | "帮我修一下登录页 bug" | 让 Codex 干活 |
| 斜杠指令 /xxx | /init, /model, /diff | 控制 Codex 的工作方式 |

二、3 个基础常识

  1. 指令必须放在开头 — /model 是对的，请帮我 /model 是错的（Codex 只在第一个字符看到 / 才识别为指令）
  2. 忘了指令就输入 / — 会弹出当前可用的指令列表，可继续输入字母过滤
  3. 不要把 Claude Code 的东西硬套过来 — Codex 用 AGENTS.md（不是 CLAUDE.md），用 /side//fork（不是 /btw//branch）

三、新手最该掌握的 10 条指令

# 指令 作用 最佳使用场景
1 /init 生成 AGENTS.md 项目说明文件 第一次进项目时，让 Codex 了解项目规矩
2 /status 查看当前模型、权限、目录、上下文 怕改错目录时、怀疑模型没切成功时
3 /model 切换模型（快模型 vs 强模型） 小活用快模型，大活用强模型
4 /permissions 控制读写权限 新手保守一点，先只读再逐步放开
5 /plan 让 Codex 先分析再行动 重构、迁移、复杂 bug、不确定风险的任务
6 /mention 指定文件让 Codex 只围绕该文件分析 指定报错文件、组件、配置文件
7 /diff 查看真实改动（增删文件、内容变化） 改完必须看，AI 总结会漏，diff 不会
8 /review 切换 reviewer 视角审查代码 提交前固定跑一次，重点看 bug/回归/测试/边界/安全
9 /compact 压缩对话历史，继续当前任务 对话太长太慢太贵时
10 /resume 恢复历史会话 跨天任务、大项目迁移、分阶段开发

四、两个分支指令：/side vs /fork

指令 本质 适用场景
/side 临时侧聊（小窗口） 临时问一个判断、检查方案风险、概念解释
/fork 开新线程（真分支） 试另一种架构、比较两个方案、保留主线同时开实验线

一句话总结：/side 是临时小窗口，/fork 是真正开分支。回主线用 /resume。

五、新手第一次使用流程（8 步）

1. cd my-project && codex
2. /init                          → 初始化项目说明
3. /status                        → 看状态
4. 先读项目，不要直接改            → "帮我读一下项目结构..."
5. /plan                          → 大任务先计划
6. 确认方案后再让它改              → "按方案实现，保持改动尽量小"
7. /diff                          → 看真实改动
8. /review                        → 提交前审查

核心原则：先让它读 → 再让它想 → 再让它改 → 最后你验收。

六、AGENTS.md 的核心价值

/init 只是生成脚手架，真正有价值的是你写进去的项目规则。一个好用的 AGENTS.md 包含：

  • Commands：安装/开发/测试/构建命令
  • Rules：禁止修改的目录、最小改动原则、测试要求
  • Architecture：模块分布（API 在哪、组件在哪、路由在哪）
  • Before finishing：提交前的检查清单

一次写好，长期复用。这是把 Codex 从聊天工具变成项目同事的关键。

七、常见疑问 Q&A

  • Q：看到的指令比文章少？ → 正常，取决于版本/系统/插件/实验功能
  • Q：Codex 会不会乱改代码？ → 取决于权限设置、prompt 清晰度、是否看 /diff
  • Q：/compact 会不会让 Codex 忘东西？ → 会压缩历史，可指定保留关键信息
  • Q：/new 和 /clear 的区别？ → /new 开新对话，/clear 清空终端显示
  • Q：/fork 后怎么回主线？ → 用 /resume 从历史会话选原来的那条
  • Q：Codex vs ChatGPT 写代码？ → ChatGPT 像远程顾问（你要贴代码），Codex 像项目同事（直接读改文件）

八、新手使用口诀

先 /init，让 Codex 认识项目。再 /status，确认状态。大任务先 /plan。关键文件用 /mention。改完必须 /diff。提交前跑 /review。对话长了用 /compact。明天回来用 /resume。临时问一句用 /side。想试新路线用 /fork。

🔍 借鉴点

借鉴点 如何应用
AGENTS.md 项目入职手册 我们的项目也应该有 AGENTS.md，让 subagent 进来先读规矩
/diff 强制门禁 我们已有 /diff 概念，但应强化为 Hard Gate（类似 Superpowers 的 review 门禁）
/plan 先想后做 复杂任务必须先 /plan，不能直接让 agent 动手改代码
/compact 上下文压缩 我们已有 context-compressor skill，但应整合到 agent 工作流中自动触发
/side 临时侧聊 类似我们的 delegate_task 临时咨询，但更轻量
/fork 分支实验 类似我们的 delegate_task 并行实验，但语义更清晰
10 条核心指令 + 2 条分支 精简指令体系，避免新手认知过载

💡 启发

  1. Codex 的指令设计哲学：不是功能越多越好，而是新手 10 条核心 + 2 条分支 = 90% 日常任务。我们的技能体系是否也过于复杂？
  2. AGENTS.md 是"项目入职手册"：这个概念比"项目说明"更准确。它不是文档，而是给 AI 同事的入职指南。
  3. /diff 的不可信任原则："Codex 说只做了一个小改动，你别全信。看 diff。AI 的总结会漏，diff 不会。" — 这与 Superpowers 的 "Do Not Trust" 声明完全一致。
  4. /plan 先想后做：大任务必须先计划再行动。我们已有 writing-plans skill，但应强制化（类似 Hard Gate）。
  5. 权限渐进式放开：新手保守一点，先只读再逐步放开。我们的 /permissions 概念应整合到 requesting-code-review 的 Hard Gate 中。
