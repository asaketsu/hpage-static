摘要

AI独立开发者 @yanhua1010（彦华AI路书）分享了一套面向AI编码助手的工程准则。核心理念是"谨慎优于速度"——编码前先思考、不假设不隐藏困惑、只用最少代码解决问题、只碰必须碰的代码、定义可验证的成功标准。准则分四个层面：编码行为（4条）、工作流编排（6条）、任务管理（6步）、补充原则（2条）。25赞64收藏，收藏/点赞比极高说明实用性强。

核心内容

一、编码行为（4条）

1. 编码前思考 — 不要假设，不要隐藏困惑，呈现权衡

实现之前：
- 明确说明假设，不确定就问
- 多种解释都呈现出来，不默默选择
- 有更简单的方法就说出来，适时提出异议
- 有不清楚的地方停下来，指出困惑点

2. 简洁优先 — 用最少代码解决问题，不要过度推测

  • 不添加要求之外的功能
  • 不为一次性代码创建抽象
  • 不添加未要求的"灵活性"或"可配置性"
  • 不为不可能发生的场景做错误处理
  • 写了200行但其实50行就够 → 重写

自检：资深工程师会觉得这过于复杂吗？如果是，简化。

3. 精准修改 — 只碰必须碰的，只清理自己造成的混乱

编辑现有代码时：
- 不"改进"相邻的代码、注释或格式
- 不重构没坏的东西
- 匹配现有风格，即使你偏好不同写法
- 注意到无关死代码只提一下，不删除

清理规则：
- 删除因你的改动而变得无用的 import/变量/函数
- 不删除预先存在的死代码

检验标准：每一行修改都应该能直接追溯到用户的请求。

4. 目标驱动执行 — 定义成功标准，循环验证直到达成

将任务转化为可验证目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复bug" → "编写重现bug的测试，然后让它通过"
- "重构X" → "确保重构前后测试都能通过"

多步骤任务用计划：

1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]

关键洞察：强有力的成功标准让LLM能够独立循环执行。弱标准（"让它工作"）需要不断澄清。

二、工作流编排（6条）

1. 计划模式为默认
- 非琐碎任务（3步以上或涉及架构决策）先规划
- 事情走偏立刻停下重新规划，不硬推
- 验证环节也要用计划模式，不只构建时用
- 前期写详尽规格说明，降低后续歧义

2. 子代理策略
- 大胆使用子代理，保持主上下文窗口整洁
- 研究、探索、并行分析都下放给子代理
- 复杂问题用更多子代理堆算力
- 一个子代理只做一件事，保持聚焦

3. 自我改进闭环
- 用户每次纠正后：把模式更新到 tasks/lessons.md
- 为自己写下防止同一错误再次发生的规则
- 反复迭代这些 lesson 直到错误率下降
- 每次会话开始时回顾项目相关的 lesson

4. 完成前必须验证
- 任务没有被证明可运行之前，绝不标记为完成
- 必要时对比主干和改动的行为差异
- 自问："高级工程师会批准这段改动吗？"
- 跑测试、看日志、用事实证明正确性

5. 追求优雅（有度）
- 非琐碎改动先问："有没有更优雅的方式？"
- hacky修复 → 用"以我现在所知的一切，实现一个优雅方案"的心态重写
- 简单明显的修复跳过这一步，不过度设计
- 交付前先挑战一下自己的成果

6. 自主修bug
- 接到bug报告直接修，不等用户手把手
- 指向日志、错误、失败的测试，逐一解决
- 不让用户承担上下文切换的负担
- CI失败不用被告知，直接去修

三、任务管理（6步）

  1. 先计划：写入 tasks/todo.md，每项做成可勾选条目
  2. 确认计划：实施前与用户确认一次
  3. 跟踪进度：做一项勾一项
  4. 解释改动：每一步都给出高层次摘要
  5. 记录结果：tasks/todo.md 末尾补 review 段
  6. 沉淀经验：被纠正后更新 tasks/lessons.md

四、补充核心原则

  • 不偷懒：定位根因。不要贴临时补丁。按资深开发者标准交付。
  • 最小影响面：改动只动该动的地方，避免引入新bug。

验证标志

这些准则正在发挥作用的标志：
- diff 中不必要的改动更少
- 因过度复杂而导致的重写更少
- 澄清问题在实现之前提出，而不是在犯错之后
