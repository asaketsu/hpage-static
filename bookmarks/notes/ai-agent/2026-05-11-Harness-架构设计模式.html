Harness 架构设计模式 — 复杂 Agent 任务的系统化框架

来源: ConardLi / code秘密花园 — Harness 实践：让 Agent 自动制作知识讲解视频
核心思想: 模型有能力，但需要系统来划定边界、管理状态、设立检查点、拦截错误

一、核心洞见

维度 关键发现
为什么选网页而非视频模型 可控性 — 字体、配色、时长、数字展示精确可控，改代码即可
为什么做成 Skill 而非直接让 Agent 做 模型有能力，但需要系统来划定边界、管理状态、设立检查点、拦截错误
核心产出 1 篇 Anthropic 文章 → 13 章、100+ 细粒度步骤，每步完整视觉演示

二、六层 Harness 架构

┌─────────────────────────────────────────────────────────┐
│  约束与恢复 ← 出错怎么办（重试/回滚/校验）              │
│  评估与观测 ← 怎么知道做得对不对（质量评估/错误归因）    │
│  状态与记忆 ← 跨步骤连续性（保存进度/中间结果）          │
│  执行编排 ← 模型下一步做什么（分步执行/结果回回）        │
│  工具系统 ← 模型能做什么（文件读写/API/代码执行）        │
│  上下文管理 ← 模型看到了什么（提示词/文档/历史/状态）    │
└─────────────────────────────────────────────────────────┘

2.1 各层职责

层级 解决的问题 关键设计
上下文管理 模型看到了什么 分阶段按需加载，避免注意力稀释
工具系统 模型能做什么 文件读写、API 调用、代码执行
执行编排 模型下一步做什么 分步执行、结果回写
状态与记忆 跨步骤连续性 保存进度、中间结果
评估与观测 怎么知道做得对不对 质量评估、错误归因
约束与恢复 出错怎么办 重试、回滚、校验

2.2 上下文分层加载

如果把所有文档一股脑灌进去，模型注意力会被严重稀释。

做法: 不同阶段加载不同文档，只加载当前阶段需要的内容。

2.3 三文件协同记忆

大纲管结构边界，口播稿管叙事节奏，原文章管信息密度。

文件 职责 生命周期
outline.md 最重要的记忆，固定关键决定，成为开发阶段持续记忆 全程
script.md 负责节奏，画面跟着口播走 开发阶段
article.md 负责信息密度，补充数据、案例 全程

2.4 最小切片修复

原则：先定位问题层级，再改最小切片，不要重做整章。

问题层 最小切片
节奏（太快/太慢） 调整对应 step 的 narration 文本长度
视觉（动画不对） 只改对应 step 的 CSS/动画逻辑
内容（信息薄/密） 回 article.md 补充或删减
代码（编译报错） 定位具体文件和行号，点修

三、四阶段 + 两检查点流程

阶段一：内容编写（口播稿 + 开发大纲）
    ↓
🔴 检查点 Plan（人工确认 5 件事）
    ↓
阶段二：开发（第 1 章人工验收作为基准）
    ↓
🔴 检查点 Audio（决定是否合成音频）
    ↓
阶段三：音频合成（TTS 逐段生成）
    ↓
阶段四：录屏（浏览器全屏 + 自动播放）

检查点 Plan 确认清单

  1. 稿子要不要改
  2. 大纲要不要改
  3. 用哪套视觉主题
  4. 真素材谁准备
  5. 后续章节逐章做还是并行做

第 1 章验收要点

第一章的验收非常重要，它直接决定后续章节的开发质量。

  • 画面是否舒服
  • 节奏是否顺畅
  • 信息是否太密
  • 是否有 AI 味

四、评估与观测 — 对抗自评失真

⚠️ 关键教训: 让写代码的 Agent 自己评价"这章写得怎么样"，结果几乎一定是"还不错"

三种评估方案（按优先级）

优先级 方案 说明 适用场景
🥇 最优 Agent Teams 独立 Reviewer 开独立 Agent 逐项核查，不依赖写代码的 Agent 自评 有资源、需高质量
🥈 次优 SubAgent 走同样流程 用另一条流水线验证 中等资源
🥉 兜底 当前 Agent 严格逐项核查 不许目测放行 资源受限

自检清单模板

Script 自检:
- [ ] 口语化、B站风、无 AI 味
- [ ] 信息保留 ≥ 60%
- [ ] 念出来不别扭

Outline 自检:
- [ ] 节奏规划合理
- [ ] 无动画细节（大纲只规划节奏）
- [ ] 与 script 时间误差 < 10%

单章实现自检:
- [ ] 有动图、不套模板
- [ ] 字大留白、逐个揭示
- [ ] 素材真实、代码隔离

五、Agent Teams vs SubAgent

SubAgent Agent Teams
类比 三人分别去三个城市办事 三人进会议室边讨论边改
通信 互相看不到 可互发消息、共享任务列表
适合 结果导向任务（并行开发章节） 需要反馈的任务（质检）
开销 省 Token Token 开销更高

并行上限

最多同时跑 3 个 Agent 比较合适。超过 3 个错误率显著上升。

六、可迁移的经验

经验 适用场景
Skill 不是功能，是系统 任何需要多步骤、有状态、需检查点的复杂任务
第 1 章验收决定后续质量 任何批量生成任务（文档、代码、设计）
Agent Teams vs SubAgent 选择 需要反馈 → Teams；结果导向 → SubAgent
并行上限 3 个 Agent 多 Agent 并行开发，超过 3 个错误率显著上升

七、适用场景判断

场景 是否适用 说明
多步骤复杂任务 ✅ 强烈推荐 任何超过 3 步、有状态依赖的任务
批量生成任务 ✅ 强烈推荐 文档、代码、设计等批量产出
需要质量保障 ✅ 强烈推荐 有检查点、有 Reviewer 机制
简单一次性任务 ❌ 不推荐 开销大于收益
探索性/实验性任务 ⚠️ 酌情 可简化为 1-2 层

八、Pitfalls

陷阱 症状 解决方案
上下文过载 模型注意力分散、产出质量下降 分阶段按需加载文档
自评失真 Agent 自评总是"还不错" 用独立 Reviewer Agent
第 1 章不验收 后续章节质量参差不齐 第 1 章必须人工验收作为基准
并行过多 错误率飙升、难以追踪 上限 3 个 Agent
修复过大 重做整章而非最小切片 定位问题层级 → 改最小切片
检查点缺失 错误累积到后期才发现 关键节点设检查点
