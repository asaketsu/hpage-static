Harness Engineering：模型不是关键，Harness 才是

核心观点

同一模型，换一套运行环境，编程基准成功率从42%跳到78%。变量只有一个：模型外面那层「壳」——Harness。

三层进化

  1. Prompt Engineering（2022-2024）— 打磨单次输入，few-shot/CoT/角色扮演
  2. Context Engineering（2025）— 动态构建上下文环境，文件/对话/工具/知识库
  3. Harness Engineering（2026）— 搭建整个「办公室」，让Agent持续、稳定、高质量工作

类比：写邮件 → 带附件 → 搭办公室

关键案例

案例 数据 核心做法
OpenAI Codex 5个月100万行/1500PR/人类0行代码 Harness全包，工期1/10
Stripe Minions 1300+ PR/周无人值守 Blueprint编排（确定性+Agentic交替）
Cursor 1000 commits/小时 递归Planner-Worker模型
Peter Steinberger 6600+ commits/月（单人） 同时跑5-10个Agent

Harness三大组成

  1. 上下文工程 — AGENTS.md控制60行以内，接浏览器+可观测性栈
  2. 架构约束 — 分层架构用linter和结构化测试机械执行，不靠prompt
  3. 熵管理 — 定期Agent扫描技术债、过时文档、架构漂移

七个配置杠杆

  1. AGENTS.md/CLAUDE.md规则文件
  2. 确定性约束（linter/类型检查/pre-commit hooks）
  3. 工具精简（Vercel 15→2，准确率80%→100%）
  4. Sub-Agent隔离
  5. 反馈循环（Agent自测/截图/查日志）
  6. CI限速（最多两轮，Stripe做法）
  7. 垃圾回收（定期清理技术债）

路线之争

  • Big Model：模型能力主旋律，Harness权宜（Claude Code/Noam Brown）
  • Big Harness：模型是引擎，Harness是方向盘（Jerry Liu/Cursor $50B）
  • 护栏悖论：车速越快护栏越重要

关键洞察

  • 约束解空间反而让Agent更有生产力（反直觉）
  • Harness要轻、模块化，随时准备被拆掉（Start Simple, Build to Delete）
  • 未来最值钱的是懂「管理Agent」的工程师
  • 差的初始指令在数百个Agent间会被放大

吸收与优化

对我们系统的关联

  • AGENTS.md/SOUL.md/rules体系 = 本质上的Harness ✅
  • evolver闭环 = "Agent犯错→诊断→改进Harness"飞轮 ✅
  • 龙虾法则 ≈ Mitchell Hashimoto理念 ✅

可借鉴改进

  1. AGENTS.md精简到60行以内 — 当前文件偏长，可拆分更多到rules/
  2. 确定性约束 > 软prompt — 增加脚本化校验（如lint rules文件格式）
  3. 工具精简 — 定期审计各Agent可用工具，砍掉低频工具
  4. CI限速 — cron任务设最大重试轮次，防止无限循环
  5. 熵管理cron — 定期扫描rules/和skills/的一致性、过时内容
