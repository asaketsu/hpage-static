内容整理：推文核心论证链还原

1. 核心主张与分权

「今年开发的 80% 的自定义 MCP Server，实际上只需要一个 SKILL.md 文件加上一个 Python CLI 脚本就能解决」——推主自己标注：80% 未必有统计依据，但工程思考值得讨论。这是转述链上罕见的诚实标注（一手层 Madler 与转评层 Broda 均未给出处）。

2. 论证链：抽象层为谁而存在（本文最大增量）

环节 论点
前提（历史） 软件为人设计交互界面/封装接口/编写文档，因为人类需要抽象层降低使用门槛
变量（现在） 软件使用者从人类扩展到 Agent；Agent 原生具备读文档、理解代码、执行命令、处理异常、组合工具的能力
推论 为降低人类门槛而存在的抽象层，在 Agent 具备执行能力的环境中必要性重估
实例 PDF 处理/Excel 清洗/批量转换/调 API：MCP 方案要 Schema+协议+运行环境+连接+客户端兼容五件套；Agent+SKILL.md 只需说明何时用、传什么参数、如何处理输出、异常怎么办

3. MCP 与 Skill 的本质二分（记忆锚点）

MCP 解决能力连接的标准化问题；Skill 解决任务执行经验的复用问题。前者提供能力，后者组织能力。

  • MCP：让不同 Agent 客户端通过统一协议访问外部工具/数据/服务（客户查询、订单查询等原子工具）
  • Skill：封装专业知识、业务规则、操作步骤、工具用法（识别高价值客户、判断流失风险等任务级方法）
  • 成熟系统同时使用 MCP、Skill、CLI、传统 API——非此即彼是伪问题

4. 选型判据（可复用决策表）

问题 答 CLI/Skill 答 MCP
只在本地运行？ ✅ —
只服务一个 Agent？ ✅ —
简单确定性操作？ ✅ —
多客户端共享工具？ — ✅
跨环境访问远程服务？ — ✅
统一管理接口与权限？ — ✅

总判据：技术引入的复杂度能否换来足够的业务价值。 CLI 路线不豁免安全——数据库写入、文件删除仍需明确执行边界、权限隔离、参数校验。

5. Unix 哲学回归与反技术目标化

  • Coding Agent 越强，Unix 哲学越值得重学：每个工具做好一件事，Agent 动态完成组合（过去靠人写管道）
  • 成熟 CLI/Python 脚本/传统基础设施 = 可被 Agent 直接利用的能力资产，不必重新发明
  • 批判「技术当目标」三连：学了 MCP 就万物 MCP Server、学了 Multi-Agent 就全业务多 Agent、学了 RAG 就全接向量库——「架构图越来越漂亮，技术栈越来越丰富，系统越来越难维护，业务问题没变化」

6. FDE 视角收尾

拉开 AI Engineer/FDE 差距的不是技术广度，而是面对复杂业务需求找到足够简单、可靠、成本合理的实现路径的能力。「不要因为 AI 让构建复杂系统变得容易，就毫无节制地制造复杂系统。删掉一个没必要的服务、减少一层抽象，比新增一千行代码更能体现工程师水平。」

查询拓展

  • skill:// 协议提案（本文未提的辩论终局线索）：AAIF「Skills Over MCP」提案定义 skill://index.json 技能目录与 skill://<skill>/SKILL.md URI scheme，让 MCP Server 暴露技能资源；FastMCP 已实现 SkillProvider；anthropics/claude-code issue #38253 请求 MCP 连接时自动发现 skill。方向是 skill 获得标准化分发通道而非谁取代谁
  • 一手溯源：LinkedIn Jochen Madler「MCPs are dead」帖（OpenClaw+shell+SKILL.md 实操细节）；Eric Broda 转评（补充 skill 需更多一致性/标准化的反驳面：Markdown 是文档、MCP 是契约）
  • 厂商侧对照：Anthropic Agent Skills 官方规范（渐进披露、scripts/references/assets 三资源型）
  • 可追踪后续：microsoft/skills 仓库（.github/skills/ 内建 skill 目录，配 microsoft-docs MCP 引用官方文档）——大厂把 MCP 与 Skill 组合而非对立的实证

归纳总结

  1. 命题重述：抽象层的存在理由是「降低使用者门槛」；Agent 自带读文档+执行能力，使相当一部分抽象层失去对象——这是「80% MCP Server 无必要」的理论内核，比「MCP 吞上下文」的实证路线更根本
  2. 分工模型：能力（MCP 连接标准化）/ 知识（Skill 经验复用）/ 执行（CLI 确定性操作）三层并存，选型看共享度、环境跨度、管理需求三轴
  3. 反向约束：CLI 路线把安全责任从协议层移回 Agent 层——执行边界/权限隔离不因方案简单而消失，反而更显式
  4. 元判断：技术目标化（为用而用）是比选型错误更高频的失败模式；复杂度是持续付息的债，AI 降低的只是构建成本，不是维护成本
  5. 独有贡献：推主对 80% 数字的自曝无依据，是转述链中的诚实样本——采信其框架，不采信其数字

趋势判断

  • 短期（6 个月）：「Skills 替代 MCP」叙事在单用户/本地场景持续走强（Reddit/博客实测帖密集出现），但企业侧 MCP 的 auth/审计/跨组织工具发现契约需求不动摇——分野而非替代
  • 中期：skill:// 类资源协议若被 MCP 规范吸纳，Skill 获得标准化分发通道，辩论收敛为「Skill 上 MCP 的管道」融合路线（GitHub issue #38253 与 AAIF 提案已是先声）
  • 对本机启示：Hermes 的 skill-first + CLI（lark-cli、gh、terminal）路线与该趋势同向；新 MCP 接入应逐个过四问判据表，默认从 CLI 起步
  • 证伪条件：若 6 个月内 skill:// 标准化无实质落地且 MCP 生态继续扩大企业份额，则「八成无必要」判断的适用域收窄到单机/单 Agent 场景，企业侧判伪
