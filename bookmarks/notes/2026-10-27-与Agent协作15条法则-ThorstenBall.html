内容整理：15 条法则逐条拆解

模型与心态层（#1-#3）

# 法则 原文关键句 拆解
1 用最新最强模型 "If a model is wrong 10% of the time, you don't know which 10%" 错误率是随机分布的，便宜 50% 但随机蠢 20% 的通用模型会导致多次重试，总成本反超。Opus 4.5 已是"谁还在用"的古董
2 停止担心代码变 slop "Maybe that was true six months ago. Now? I'm not convinced" 观点时效性强：作者明确说这是 2026-10 时点的判断，六个月前的"slop 焦虑"可能已过时——模型质量提升使生成的代码可维护性不再是主要矛盾
3 Prompt 写 What 不写 How "Do not stop until it's 2x faster" 描述终态+硬指标，不描述步骤。给结果规格（"这是它最终应该如何工作"）比给实现路径效果好

环境与工具层（#4-#7）

# 法则 原文关键句 拆解
4 让整个 SDLC 对 Agent 可见 "What stopped hallucinations? Tool calls. They let agents touch our reality" 全文最核心洞察：幻觉的解药不是更好的模型而是工具调用。让 Agent 端到端跑它构建的东西、读生产日志、部署、观察 rollout、切 feature flag、分诊 bug、给客户发邮件
5 给 SDLC 配工具 自定义插件：bug 报告/邮件用户/"系统健康吗？"/开 feature flag 法则 #4 的执行层——可见性是靠自定义插件堆出来的，不是靠 Agent 天生
6 评估 Agentic 知识 "Spawn five blind agents, control vs. treatment" 知识在代码库里堆积（AGENTS.md/skills/脚本/文档），但 Agent 真的用它吗？用盲测对照实验验证——"Agent 非常非常擅长跑实验"
7 本地开发变得恶心了 "Easy in remote machines, yucky in local dev" 每个 Agent 都要能装能跑它需要的任何东西——远程机器天然支持，本地开发必然资源冲突。工作负载向远程/沙箱迁移的结构性理由

协作模式层（#8-#12）

# 法则 原文关键句 拆解
8 不要和 Agent 迭代，让它造工具迭代 "Generate 20 variations and a little page that lets me combine and test them" 把"试试这个…不行换那个"的回合制，换成"生成 20 个变体+一个组合测试页"。同时适用于问题空间："给我 4 个为什么慢的理论，然后把 4 个都查了"
9 索要不可反驳的证据 "Put 'this is not evidence' in your AGENTS.md" 全文最大 game changer：end-to-end 走查、演示视频、前后对比数字。信任和直觉需要逐步建立，用 AGENTS.md 显式声明什么不算证据
10 别等 Agent，让 Agent 等你 "If you worry about TTFT, you're probably doing something wrong" TTFT（首 token 时间）焦虑=用法错误信号。拥抱异步：给更大更野心的任务，批处理代替来回 ping-pong
11 自动化/定时/唤醒/心跳是杀手级特性 "Didn't realize it, but missed it dearly once it was off" "2 小时后查日志""上线了告诉我""每天 9 点检查"——失去时才意识到多重要。作者自述这是没预料到的最高频使用特性
12 停止手动管理上下文 "Some threads are 46 messages, some are 3,714" 每个纠结"它用的是 300k 还是 380k token"的念头都是浪费。Compaction 效果极好；一条线程=一个任务，长度不重要

组织与评审层（#13-#15）

# 法则 原文关键句 拆解
13 线程就是公司记忆 "Why did we do this?" + threads 连接 git commits 团队越用知识越增值，避免重复劳动。⚠️ 带 Amp 产品立场，但"决策上下文挂接到版本历史"的思路独立成立
14 别让 Agent 给人写东西 例外：调试步骤/事故报告/部分文档 Agent 写作是机械的。例外清单恰好是"对面没有人乎不重要"的机械场景——注意这与对外发布的_human-facing_内容质量要求形成边界
15 只评审高爆炸半径的代码 "<5 central files -- those I review. Database migrations, yes." 数据库迁移必审；闭包 vs 类、更整洁的类型、变量名、甚至重复代码——不再在乎。评审四问：能跑吗？我能在图级别理解吗？Agent 端到端测过吗？一个月后我还能改吗？

🔥 重点行动（P0-P1）：

⚠️ 有分歧处（诚实记录）：#1"永远用最新最强模型"与用户的模型经济学（包月优先、智谱 GLM 日常+GPT-6 兜底、按量 API 垫底）存在张力——作者视角是单一商业团队的时间成本主导，用户视角是个人系统的 token 经济学。两者不冲突：用户的原则等价于"在包月池内选最强"，兜底链机制正是对"错误率随机分布"的工程化应对。

趋势判断

  1. "回合制聊天"→"异步员工管理"的范式迁移已过临界点：#8-#12 五条法则全部指向同一方向——衡量 Agent 协作效率的指标从"对话流畅度"变成"人的等待空闲率"。这与自建系统 2026 年的重心转移（cron 化/后台化/守望 job）完全同步
  2. AGENTS.md 正在从"指令文件"演化为"治理文件"：从写"怎么做"（SOP），到写"什么不算证据"（负向清单）——治理粒度从行为层上升到认知层
  3. 评审带宽成为新瓶颈：#15 意味着人类评审从"质量守门员"退位为"爆炸半径守门员"，评审的对象从代码行数收敛到 <5 个中央文件+数据库迁移。人机分工的边界进一步清晰化
  4. 本地开发环境的衰落：#7 提出 Agent 负载天然属于远程机器——随着 Agent 并行度上升，"开发环境"概念将从个人笔记本迁移到云端沙箱池，这是基础设施层的结构性判断

指南分析

适用场景：已深度使用 coding agent 4 周以上、日均有 3+ 个活跃 Agent 会话的开发者。新手直接套用会踩坑（#9 证据文化需要先有工具链支撑，#15 放弃细节评审需要先建立端到端测试信任）。

落地路线（按依赖顺序）：

阶段 动作 依赖
1 AGENTS.md 加"this is not evidence"负向清单 无
2 给 Agent 补 SDLC 可见性工具（健康检查/日志/部署） 插件/MCP 能力
3 把回合制迭代改成批量变体+自建测试工具 阶段 2 的工具
4 盲测对照实验验证知识库有效性 5 个并行 Agent 槽位
5 评审收敛到高爆炸半径文件 阶段 1 的证据信任已建立

反模式警告：#3"Prompt 写 What"不等于不验收——What 的描述必须含可证伪的硬指标（"2x faster"），否则退化成放任；#12"不管上下文"的前提是 one thread = one task 的隔离纪律，不是单线程里无限堆任务。

拓展应用推荐

  • 对团队知识管理：#13 的"线程挂接 git commit"思路可低成本移植——在 commit message 里强制引用会话/任务 ID，让 archaeology（为什么当年这么改）可追溯
  • 对 Skill 体系建设：#6 的盲测协议是 Skill 健康度审计（skill-health-tier）的升级版——从"扫一遍分级"升级为"对照实验证明被使用"
