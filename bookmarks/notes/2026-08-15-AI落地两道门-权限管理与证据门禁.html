一、内容整理

1.1 问题起点：2000 块的企业咨询

客户已把 Agent 用起来，一进真实业务问题一大堆：企业 Agent 怎么落地，Harness 能做到什么程度？这个问题没法只靠换更强的模型回答。

两个锚定问题（第一性原理）：
- 企业为什么敢让员工登录 CRM，却不敢把管理员账号交给新实习生？——不是怕干坏事。账号能看到什么、能改什么、出问题能不能追到人，这些边界本属于企业管理。换成 Agent 后边界不会自动消失，反而更容易被忽略。模型没有公司的职位，也不会天然理解"一笔退款"和"查一条订单"的风险差别
- 员工说"本月业绩预计增长 20%"，管理层会问：数字从哪来？是目标、按进度算的、还是财务确认过的？AI 把句子写得再顺，也不能替这 20% 补上证据

1.2 风险二分法（文章骨架）

  • 行动风险：读了不该读的数据、改了不该改的客户信息、发了不该发的邮件、未批准执行退款
  • 结论风险：拿到过期数据、把目标写成结果、把预测写成事实、工具调用失败后仍宣布完成

权限管理限制 Agent 能造成多大的影响，证据门禁决定它的结果能走多远。

完整 Harness 还会处理上下文、状态、重试、成本、日志、人工接管——但权限和证据是企业敢不敢放 Agent 进业务的两条主线。

1.3 第一道门：权限管理（以经营日报 Agent 为例）

凭据与身份分离：
- 直接把管理员 API Key 填配置文件"能跑"，但日志里只剩"管理员执行过操作"，追不到哪个 Agent、代表谁、为什么越界
- 正确姿势：Agent 拥有自己的服务身份；长期密码放企业密钥系统（不进模型上下文、不写提示词）；运行时控制系统换取短期 Token，任务结束自动失效
- 凭据解决以什么身份进门，权限决定进门后能走到哪里

最小权限落地（不只一把 Key）：
- 短期凭据限制为只读、只读日报需要的几张表、只访问本租户、只看最近 30 天
- 身份证号/手机号等字段在数据库或工具层就遮蔽——不能把完整数据交给模型再提醒"不要泄露"（这不是安全洁癖；复用管理员账户时，一条错误指令就能把客户手机号写进报告甚至写回 CRM）

权限落到动作分级：
- 自动完成：查询数据、生成草稿
- 单独授权：发进管理群
- 只生成提醒不直接改：销售任务
- 只列名单不顺手执行：退款
- 查询和退款若共用高权限凭据，模型看错币种、1000 识别成 10000，错误直接变资金损失

权限卡：把边界写成开发/业务/安全三方共看的同一份文档，让"大家应该都知道"变成系统可执行、事后可追查的规则

弹窗审批的失效数据：Anthropic 内部遥测——用户批准了约 93% 的 Claude Code 权限提示。提示越多，人越不看内容就点同意。有效设计不能把责任甩给弹窗：低风险操作在小范围自动完成，高风险动作集中到少数值得认真确认的节点；数据/网络/工具能力由模型外的系统硬性限制。人负责判断，系统守住不能长期依赖注意力的边界。企业自主权路径：先把最坏结果关进足够小的范围，再按实际运行记录扩权——不是第一天交出所有系统然后期待模型一直听话

1.4 第二道门：证据门禁

权限拦不住错误结论：Agent 没越权、数据真来自企业系统，报告照样可能错——把"本月目标 1200 万"写成"本月预计完成 1200 万"；把含退款的订单金额当收入；看到"数据实时更新"就默认每条订单已同步。权限系统认为全程合规，问题出在结论怎么形成。

方法论来源——安全工程的 Assurance Case（NIST 定义）：围绕一项主张，摆出支持它的证据和论证，写清假设，让整条判断可检查可追溯。AI 写下结论只是起点，企业真正需要的是：这句话从哪来、中间怎么算、最后能拿去做什么。

作者自我修正（方法论演进）：最初用六标签（要求/计算/模拟/实测/供应商声明/认证）做内部记录，但发现它们不在一条线上——要求是主张，计算/模拟/实测是形成方法，声明/认证是来源背书。改用 Assurance Case 框架后，六标签退居系统后台（REQUIREMENT 记录要求、CALCULATED/SIMULATED/MEASURED 记录形成方法、SUPPLIER_DECLARED/CERTIFIED 记录来源背书），不再假装是从低到高的证据等级。

证据链四要素（以"本月预计完成 1200 万"为例）：
- 主张身份：这句话是预测，与已完成的业绩、下达的销售目标分开
- 证据：本月前 20 天订单、已发生退款、剩余线索、工作日数量；还要知道数据谁生成的、何时更新、有没有被改过；销售与财务口径不同，冲突要留下，不能让 Agent 挑一个顺眼的数字
- 推导：先扣退款→按前 20 天日均估算剩余工作日→假设退款率和线索量不突变。删掉公式和假设只留数字，预测很快被传成承诺
- 适用范围（门禁判断）：带完整数据和假设的 1200 万→可进销售内部讨论；进正式日报→口径必须固定可复算；写进客户承诺/合同/对外材料→证据不够，需责任人确认甚至补正式记录

工程落地：权限卡+证据卡接成短流水线；evidence_id 指向带时间/版本/校验值的原始记录（不是复制的一段文字）；发送或执行之后回查外部系统最终状态——日志写"工具调用成功"只证明接口返回过，真实系统有没有变化才是任务完成的依据

三个反模式警告：
1. "让第二个 Agent 审查第一个"不是独立证据——两个模型可能读同一份错误数据、一起忽略统计口径。Anthropic Agent 评测专门区分运行轨迹和最终结果：Agent 回复"航班已订好"≠数据库里真有预订记录。可靠检查很朴素：重新执行查询、核对原始订单、检查公式、对比另一系统、确认数据时间、抽样复查、交真正担责的人批准。模型审查找遗漏，确定性规则和真实环境负责证明结果
2. 必须给"无法确认"留位置——OpenAI 幻觉研究：只奖励回答正确、不给放弃留位置，会鼓励模型在不确定时猜测。日报规定每栏必须填满，Agent 找不到数据也会编一个像样的数字。空着不可怕，把猜测写进经营决策才可怕
3. 证据不足不一定删段——降格措辞："已经实现"→"当前测试中观察到"，"必然完成"→"按现有数据和假设测算"

1.5 场景迁移（两道门的普适性）

  • 知识库 RAG：员工问"这个客户能不能看底价"——RAG 同时找到销售记录、旧版合同、过期权限说明。权限管理先决定提问者能不能看到文件，证据门禁再判断引用的是哪一版规则、原文是否真支持"可以查看"。RAG 能找到材料≠材料支持答案；附链接不能自动证明那句话没被曲解
  • 客服退款：政策"签收七天内无理由退款"是规则，订单签收时间和商品状态才是当前事实，两者合一才能判断。查询订单、生成回复、执行退款是三个不同权限阶段——少任何一步都不该直接退钱
  • 投标/行业分析：内部销量和客户访谈能不能读先看权限；市场规模是公开数据、内部测量还是情景估算，来源和算法要留下；一句话要进内部草稿、客户方案还是公开文章，决定需要多强的证据

1.6 FDE 的角色定位

FDE 要把客户现场藏在销售、财务、客服、管理层经验里的规则，翻译成身份、凭据、动作、审批、证据和发布门槛；现场验证过的权限模板、证据字段、门禁规则要回到研发后台沉淀为可复用资产，下个同类项目直接复用而非重做定制。

模型决定任务有没有可能完成，Harness 决定企业敢不敢让它完成。

二、查询拓展

2.1 Assurance Case（NIST）

安全工程经典框架（又名论证案例/安全案例），源自航空、核电等安全关键行业：Goal-Claim-Evidence-Argument 四层结构，GSN（Goal Structuring Notation）是常用表示法。核心思想：安全性不是测出来的，是论证出来的——每个主张都要能追溯到证据和推理链。ISO 21448（SOTIF）、UL 4600（自动驾驶安全案例）都建立在其上。

2.2 Anthropic 93% 批准率

出自 Anthropic 对 Claude Code 使用遥测的公开分析：权限提示过于频繁导致"批准疲劳"（approval fatigue），用户几乎无差别点允许——这直接推动了 Claude Code 的权限模式设计（allowlist/plan mode/bash 沙箱分级），把"每个命令都问"改成"少数高险动作才问"。

2.3 OpenAI 幻觉与"放弃回答"

OpenAI 2024 研究（Hallucination 是 RLHF 的必然产物）：只奖励正确回答的训练让模型把"不确定"和"错误"混为一谈——模型从未因为说"我不知道"得到奖励，宁可猜。解法方向：calibration 训练+显式 abstention 通道。本文把它落到企业场景：Agent 必须有制度化的"无法确认"出口。

2.4 FDE（Forward Deployed Engineer）

Palantir 创造的岗位模式：工程师驻场客户业务，把模型能力翻译成业务价值，把现场需求带回产品。AI 时代成为热门（作者另一篇文章《FDE介绍和入门：一个被 AI 重新激活的老岗位》）。核心能力不是写模型，是做领域间翻译——在 PhysicsForAI 笔记里作者也提到"方程的系数就是世界"，FDE 做的就是把这些系数挖出来。

三、归纳总结

3.1 企业 Agent Harness 双门模型

                    企业 Agent 落地
                         │
        ┌────────────────┴────────────────┐
        │                                 │
   第一道门：权限管理              第二道门：证据门禁
   （管行动）                      （管结论）
        │                                 │
   身份→凭据→数据范围→动作分级      主张→证据→推导→适用范围
        │                                 │
   服务身份+短期Token              Assurance Case 框架
   字段层遮蔽（非提示词层）         evidence_id→原始记录
   权限卡（三方共看）              证据卡+门禁流水线
   低险自动/高险集中确认           降格措辞替代删除
        │                                 │
   拦住：错误动作                   拦住：错误结论进入决策
        │                                 │
        └────────────────┬────────────────┘
                         │
      权限限制影响大小，证据决定结果走多远
      模型决定可能性，Harness 决定敢不敢

3.2 五个可复用的工程资产

  • 权限卡模板：身份/凭据/数据范围/动作范围/审批节点五字段——把口头边界变成可执行可追查的规则
  • 证据卡模板：主张身份/证据（含更新时间与来源）/推导（公式+假设）/适用范围四要素
  • 动作分级三档：自动完成（低险）→单独授权（中险）→禁止直接执行（高危如退款）
  • 双回查机制：evidence_id 指向原始记录（非复制文本）+ 执行后回查外部系统最终状态
  • 降格措辞表：证据不足时"已经实现→测试中观察到"、"必然完成→按现有数据测算"

3.3 与"弹窗依赖"的对比（管理启示）

  • ❌ 弹窗依赖：93% 批准率=审批失效；把安全建立在人类持续注意力上
  • ✅ 系统硬限：数据/网络/工具能力在模型外限制；人只在少数高价值节点判断；先关小最坏结果再逐步扩权

四、趋势判断

趋势1：企业 Agent 竞争焦点从模型能力转向 Harness 工程

依据：文章开篇即"换更强模型回答不了落地问题"；Anthropic/OpenAI 的官方研究（批准疲劳、幻觉-放弃）都在为 Harness 层设计提供依据；权限卡/证据卡这类轻量结构化资产成为交付物。
判断：未来 FDE/Agent 工程师的核心交付物就是这类"可执行边界+可追溯证据"的 Harness 资产，与 DBX 笔记的 MCP 权限三档（read_only/safe_write/high_risk_write）是同一趋势的商业化印证。

趋势2：证据工程（Evidence Engineering）将成为独立学科

依据：Assurance Case 从安全关键行业（航空/核电/自动驾驶 UL 4600）迁移到 AI；"轨迹≠结果"已是 Anthropic 官方评测原则；文章六标签→Assurance Case 的自我修正说明实践者在快速收敛到这套框架。
判断：两年内会出现"证据门禁"标准化组件（证据卡 schema、门禁 DSL、回查连接器），如同今天 MCP 标准化了工具连接。

趋势3：FDE 模式成为 AI 公司标配

依据：Palantir 模式被 AI 行业全面复活；文章描述的"现场规则→翻译成权限/证据结构→回沉淀研发资产"闭环是可规模化的组织能力。
判断：懂业务边界翻译的 AI 工程师比懂模型训练的更稀缺——与作者《FDE 介绍》一文呼应。

五、关联分析

5.1 与 Hermes/自身 Agent 体系的关联

本文两道门直接映射到 Hermes 的 AGENTS.md 三层权限模型（允许/禁止/确认）和 delegate_task 的 output_schema 契约——但文章走得更深：Hermes 的"确认"层仍是弹窗式，93% 批准率数据提示应向"权限卡+动作分级+系统硬限"演进。证据门禁则是 sensor-grid/verification-gate skill 的企业版：evidence_id 指向原始记录 ≈ verification-gate 的"机器可验证事实取代 AI 主观判断"。

5.2 与 PhysicsForAI 总纲领笔记的关联

PhysicsForAI 的主干乙（实验制度：盲分析/排除曲线/置信上限）与本文证据门禁同构——都是"把阴性结论/不确定结论制度化"。Miles 的证据卡=Assurance Case 的轻量版；PhysicsForAI 的排除曲线=阴性结论的定量上限。两文合读：物理科研制度与安全工程制度是 AI 可信性的两大源头。

5.3 与 ai-agent-supervision-protocol / CLAX-PT 案例的关联

supervision skill 的"执行/评判分离"原则与本文"第二个 Agent 不是独立证据"形成有趣张力：监督 Agent 找遗漏可以，但证明结果必须靠确定性规则和真实环境回查——这为 supervision 协议补了一条边界：监督者输出的是"待验证的疑点清单"，不是"通过认证"。

5.4 与量化和数据分析工作的关联

"把目标写成结果、预测写成事实"正是量化回测的过拟合陷阱（把 in-sample 表现当 out-of-sample 事实）；"冲突要留下不能挑顺眼的数字"对应数据治理的口径管理。证据卡的"推导+假设"要素可直接搬到策略报告：任何回测数字必须带区间、假设、数据截止时间。

七、行动启示

  • 启示1：把"权限卡+证据卡"两张卡模板沉淀进自己的 Agent 交付模式（对应 auto-skill/agent-authorization-continuity 体系）——任何对外 Agent 项目先出这两张卡再写代码
