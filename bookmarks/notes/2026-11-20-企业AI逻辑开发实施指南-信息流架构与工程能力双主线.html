内容整理：从两条推文到企业实施 Playbook

一、原文还原 A：三代技术的演变本质——不是升级路线，是理解演变

核心命题：RAG → Agentic RAG → Context Engineering 常被误解为「技术升级路线」（传统 RAG 过时 → Agentic RAG 下一代 → Context Engineering 更高级）。真正的理解是：我们对「大模型如何使用外部信息」这件事的认识在演变。

演变三阶段（原文逻辑链）：

阶段 解决的问题 暴露的死穴
基础 RAG 让模型利用训练数据之外的知识，无需每次知识更新就重训模型 检索流程提前写死：问题简单复杂走同一管道；第一次检索没找全证据也直接进生成；明明该走 SQL / 业务 API 的问题被扔进向量库做相似度搜索
Agentic RAG 检索从固定步骤变成 Agent 可动态调用的工具：判断需不需要检索、访问哪个知识源、证据是否足够、是否拆解问题多轮搜索 只解决了「取数」环节。复杂任务 Agent 需要的上下文远不止外部检索：任务目标、系统约束、历史决策、执行进度、可调用工具、已完成操作、哪些保留哪些丢弃
Context Engineering 每次模型推理之前解决五个问题：信息该从哪里来 / 哪些内容真正相关 / 如何组织 / Token 预算怎么控制 / 如何排除噪声、过期信息和不可信输入 （尚未普遍做好的层）

两个关键澄清（破除三大错觉）：

  1. 「接上组件 = 完成上下文工程」是错觉：MCP 能让 Agent 访问工具 ≠ 模型能选对工具；Memory 能存历史 ≠ 该全进当前上下文；RAG 能检索到文档 ≠ 检索结果真实、及时、适合当前任务。这些只是提供信息和能力的基础组件，不是上下文工程本身。
  2. 长时任务是上下文问题的放大器：
  3. 开发 Agent 连续几十次工具调用，读了大量代码/日志/测试结果，全量塞回 → 上下文膨胀、忘记最初目标、被无关中间结果干扰 → 需要 Context Compaction + Task State + 持久化 Memory（保留已确认的架构决策/修改记录/未完成任务/关键错误，丢弃无价值工具输出）。
  4. 数字人视频 Agent 调多个外部 API，某步超时 → 系统必须知道：前面的任务完成没有？哪些结果已保存？哪些调用已产生费用？允不允许重试？——这靠延长 Prompt 维护不了，需要明确的状态管理、持久化记录和上下文组织机制。
  5. Agent Harness 的未来核心能力 = Context Management：Harness 不只是调工具、循环执行，还要围绕任务目标管理「模型在不同执行阶段能看到什么信息」，并在上下文变化、服务异常、任务恢复后保持一致性。

复杂度匹配原则（原文判据，可直抄）：

简单问题走固定检索，复杂问题用多步工具查询，长期任务引入状态管理和上下文压缩，需要多数据源协同时再设计更完整的 Context Engineering 机制。系统越复杂，越应该关注信息来源、权限边界、证据准确性、工具调用成本和可复现的评测——而不是追求模型看起来有多自主。

FAQ 系统用基础 RAG 做到准确/低延迟/低成本，就没必要为概念先进搭多 Agent 检索；读几个文件的任务不需要每次启动多子 Agent。RAG 没有死，它从很多 AI 应用的核心架构，退位为更完整 Agent 系统中一种可选择的信息获取能力。

二、原文还原 B：技术名词 ≠ 工程能力——四个差距暴露点

核心命题：很多人学 AI 最大的问题是把掌握技术名词当成掌握工程能力。知道 RAG、会连向量库、懂 MCP、能用 LangGraph/Dify 搭 Agent、能快速做出完整 Demo——往下追问几个问题，差距立刻暴露。

差距暴露点 1：故障定位能力（RAG 链路六环节归因）

企业知识库答错了，你知不知道问题出在哪一环？

# 环节 典型故障形态
1 原始文档解析 解析失败/格式丢失/表格错乱
2 Chunking 切断了关键上下文
3 Embedding 语义表示不合适（语义近但业务无关被召回）
4 向量库召回 正确片段根本没进候选集
5 Reranking 正确资料被排到后面
6 LLM 生成 明明拿到了证据，仍在生成环节编造事实

答不出 = RAG 工程能力还停留在「把几项技术按教程连接起来」的程度。

差距暴露点 2：Agent 工程五真问题（Demo 复杂度之外）

  1. Agent 调用外部 API 超时，怎么判断任务实际上有没有执行成功？
  2. 工具已修改数据库，但模型因上下文截断忘记了这件事，再次调用同一工具怎么办（重复执行的幂等）？
  3. 任务持续几十分钟，执行到一半服务崩溃——之前的状态怎么保存？重启后从哪恢复？
  4. Agent 读到带恶意指令的外部文档，怎么防止它把文档内容当成系统命令（注入防御）？
  5. 工具有删文件/发邮件/改生产数据的权限——谁决定哪些操作允许自动执行、哪些必须人工确认（权限分级）？

差距暴露点 3：Context Engineering 的真价值

不是 Prompt 越写越长、不是接更多数据库和 Memory，而是判断当前任务的当前步骤，模型真正需要什么信息：读什么文件、调什么工具、保留哪些历史决策、丢弃哪些无关日志、哪些信息已过期、哪些工具结果不能当可信指令、Token 预算内怎么完成。不是模型知道得越多越好，而是正确的时间获得正确的信息。

差距暴露点 4：Evaluation（最易被忽略的一层）

  • 效果提升不能靠开发者觉得「这次回答好像更聪明了」
  • 需要有标准答案的评测集，分别测量：检索质量 / 答案正确性 / 证据忠实度 / 工具调用成功率 / 任务完成率 / 延迟 / 成本（七项指标）
  • 改了 Chunking、Rerank、Prompt 或模型之后：不能只测几个成功案例，要用相同数据集回归验证——原来失败的问题解决了没？原来正常的问题有没有被改坏？

两个反直觉警告：

  • 技术更先进 ≠ 业务正收益：FAQ 系统基础 RAG 稳定解决，为什么非要上多 Agent 工作流？明确的数字人视频处理流程，为什么不先用确定性 Workflow 做好任务状态/重试/幂等，而把每一步都交给 LLM 自主判断？增加技术复杂度，从来不应该成为工程能力的证明。
  • 企业客户关心清单（只有五项）：能不能解决问题 / 部署后是否稳定 / 业务数据是否安全 / 出了错误如何恢复 / 每月维护和调用成本。不关心你接了多少 MCP Server、用了几个子 Agent。

终极检验（面试清单里唯一重要的一句话）：能不能用自己实际做过的项目，解释每一项技术为什么存在、解决了什么问题、你为什么选它——真做过项目的人还能说清它什么时候不适用、系统在哪里失败过、做过什么取舍、用什么证据判断问题解决了。

三、合成框架：企业 AI 逻辑开发的双主线模型（分析层）

两条推文拼起来，企业内实施 AI 开发的完整逻辑 = 双主线咬合：

信息流架构线（推文A：系统怎么建）     工程能力线（推文B：人怎么做事）
─────────────────────────────      ─────────────────────────────
需求分级 → 架构匹配                   故障定位（分段归因）
    ↓                                   ↓
信息流设计（推理前五问）              回归评测（证据文化）
    ↓                                   ↓
状态管理（Compaction/Memory）  ←──同构──  取舍证明（何时不用X）
    ↓                                   ↓
权限与安全（注入/分级授权）           交付责任（客户五关心）

四层能力阶梯（用人/自评皆可用）：

层 名称 特征 对应人群
L1 名词层 能说出 RAG/MCP/Agent 是什么 入门者
L2 连接层 能按教程把技术组件连起来、做出 Demo 多数学习者停在这里
L3 定位层 系统出错时知道问题在链路哪一环、能归因能修复 合格工程师
L4 设计层 能做取舍证明：解释每项技术何时不用、失败在哪、什么证据闭环 成熟工程师 / FDE

原文金句级判断（直接回答「会调用 ≠ 会开发」）：

会调用模型，不等于会开发 AI 系统。会搭 Agent，不等于能够交付 Agent。知道技术名词，更不等于真正理解技术。未来优秀的 AI 应用工程师和 FDE，不一定是掌握最多框架的人，而是能够把一个模糊的业务需求转化为可以运行、可以验证、可以恢复、可以持续维护的完整系统的人。

四、企业实施 Playbook（可操作层：六个 Step 逐项执行清单）

本节为分析合成的操作化交付——把原文观点展开成企业内可直接执行的步骤、清单与判据。

Step 0｜需求分级：先判复杂度，再选架构（立项门禁）

对每个候选场景跑一遍四档分级，档位决定架构，禁止跨档上探：

档 任务特征 匹配架构 禁止事项
D1 固定问答 单跳、证据集中、高频重复（FAQ/制度查询） 基础 RAG + Rerank 禁上多 Agent
D2 动态取数 需判断信息源/多步检索/跨库（销售归因类） Agentic RAG（检索决策权下放） 禁把全部步骤交给 LLM 自主
D3 长时任务 几十分钟级、多工具调用、需断点恢复 + Task State + 持久化 Memory + Compaction 禁靠延长 Prompt 维护状态
D4 多源协同 知识库+DB+API+Web Search 混合 完整 Context Engineering（信息流设计） 禁无评测上线

分级判据四问：需要动态规划吗？需要跨数据源吗？需要多步工具协作吗？任务时长超过单次会话吗？——四个「否」→ D1；全「是」→ D4。

Step 1｜信息流设计：每次推理前五问 Checklist（架构设计文档必含）

为系统每个关键推理节点书面回答（写进设计文档，不是口头判断）：

  1. 来源：这一步的信息该从哪里来？（知识库/DB/API/Web/用户输入——选错源是 D2 场景最常见根因）
  2. 相关性：哪些内容真正相关？（相关度判据、召回截断阈值）
  3. 组织：信息以什么结构进入上下文？（证据分级排序、引用格式、系统约束置顶）
  4. 预算：Token 预算多少？超了先砍谁？（预算表 = 各信息源配额）
  5. 噪声：哪些是过期/不可信/无关信息？（时效字段、来源可信标记、工具输出不可当指令）

Step 2｜状态与上下文管理：长时任务三件套（开发规范）

  • Task State 显式化：任务目标、已完成操作、未完成步骤、关键决策记录——独立于对话历史持久化存储（DB/文件），重启可恢复。
  • Compaction 触发规则：上下文达到阈值 X% 时触发压缩——保留「已确认决策/错误教训/未完成任务」，丢弃「原始工具输出全文」（保留摘要+引用指针）。
  • Memory 分层：会话内短期记忆（当前任务）/ 跨会话长期记忆（用户偏好、已确认事实）/ 持久化任务状态（可审计）——三层分开管理，不是所有历史都该进当前上下文。

Step 3｜安全与权限：两条红线（上线门禁）

  • 注入防御：一切外部输入（检索到的文档、网页内容、API 响应）默认不可信——数据与指令隔离，工具结果永不直接作为系统指令执行。
  • 权限分级表（写进系统设计，人工逐条签核）：
权限级 操作类型 执行方式
P0 只读 查询知识库/读文件/搜索 自动执行
P1 可逆写 写草稿/生成文件到沙箱/发测试消息 自动执行+日志
P2 不可逆/外发 删文件/发正式邮件/改生产数据/产生费用 强制人工确认

Step 4｜评测门禁：改动必回归（质量铁律）

  1. 建评测集：从真实业务问题中抽取，每条带标准答案与证据文档（数量级：D1 场景 ≥50 条起步，持续积累）。
  2. 七指标分测：检索质量 / 答案正确性 / 证据忠实度 / 工具调用成功率 / 任务完成率 / 延迟 / 成本——分开测，禁用一个总分掩盖。
  3. 回归纪律：任何改动（Chunking/Rerank/Prompt/模型/参数）→ 同评测集全量回归 → 出对照表：原失败问题解决数 vs 原正常问题改坏数。改坏 > 解决 = 改动否决。

Step 5｜运维迭代：故障定位 SOP + 成本看板

  • 分段归因法（六环节链）：答错先定位环节——解析→Chunk→Embed→召回→Rerank→生成，每环节建独立探针（中间结果抽样检查），禁「整体重调一遍」。
  • 月度成本与稳定性看板：调用量 / token 成本 / 失败率 / 恢复时长 / 人工介入次数——企业客户五关心的量化呈现。
  • 故障复盘三问：为什么出问题？改哪里？用什么证明解决了？（第三问 = 补回归用例进评测集）

Step 6｜组织能力：把面试检验变成团队机制

  • 招聘/晋升用：候选人讲一个实际项目，逐项追问——这项技术为什么存在？什么时候不适用？系统在哪失败过？做了什么取舍？什么证据判断解决？——五问答全 = L4。
  • 团队自检：现有成员对自家系统的故障定位演练（注入一个已知故障，看多久定位到环节）。
  • 技术选型纪律：每次引入新技术组件，立项文档必须含「不引入的方案及理由」段——复杂度增加需要证明收益，而非证明先进。

五、飞机设计领域深化（领域扩展，原文未涉及）

本节映射逻辑借鉴适航工程 70 年沉淀，与库内 [[2026-11-19-agent-demo-to-platform-aircraft-design.md]] 的六支柱适航映射互补——那篇讲平台运维侧，本篇讲开发逻辑侧。

适航/构型管理概念 AI 开发对应物 深化洞察
构型基线 + 更改控制 Task State + Compaction 型号的「基线冻结、更改受控、记录可追溯」正是长时 Agent 状态管理的成熟范式：已确认决策 = 基线；上下文压缩 = 更改单归档；不允许「悄悄改历史」
型号资料有效性管理（受控/非受控、版次有效） 知识源分级 + 时效过滤 RAG 检索到的「过期指令」问题 = 资料有效性问题的 AI 版。企业知识库应带版次/生效状态字段，检索时过滤无效版次——航空企业现成的资料管理体系可直接复用为 RAG 的元数据层
FMEA（故障模式与影响分析） 六环节链路归因 FMEA 的「逐功能块分析故障模式→影响→探测度」方法论可直接套在 RAG/Agent 链路上：每个环节预定义故障模式+探测探针+补偿措施——把 Step 5 的分段归因从救火变成设计期分析
DO-330 工具鉴定 Eval 门禁 适航对开发工具要求「鉴定后使用」，对应 AI 系统的评测集回归纪律：改模型=换工具，须重新鉴定（全量回归）才准上线
设计保证系统 DOA（自查自证体系） 取舍证明文化 DOA 的核心是「每项设计决策有记录、可追溯、可审查」——L4 工程师的「何时不用 X + 失败记录 + 证据闭环」就是 AI 项目的 DOA 化
MC/EBOM 多视图 BOM 多数据源协同（D4） 飞机数据天然多源（构型项/EBOM/工艺/适航文档），D4 场景的「信息源路由」可借鉴 BOM 多视图思想：同一实体不同视图不同源，Agent 按任务选视图

领域落地建议（三步）：① 先用 D1 场景练手（规章制度/标准规范问答——资料体系成熟、评测集好建、风险低）；② D2 场景接入构型数据（有效性过滤是现成优势）；③ D3/D4 场景（跨 EBOM/工艺/适航文档协同分析）待评测体系成熟后启动——跳级做 D4 是航空企业 AI 项目最可能的失败路径。

归纳总结

一句话：企业 AI 逻辑开发的本质是双主线咬合——信息流架构线（按任务复杂度分级选架构：固定检索→动态工具→状态管理→完整上下文工程，上下文是被设计、管理、验证的工程资源）× 工程能力线（从名词层进阶到设计层：会故障定位、会回归评测、会取舍证明），两条线的共同终点是「把模糊业务需求转化为可运行、可验证、可恢复、可持续维护的完整系统」。

三条最锋利的原文判断：①RAG 没有被淘汰，它退位为 Agent 系统中一种可选的信息获取能力；②增加技术复杂度从来不是工程能力的证明——系统越复杂越要关注来源/权限/证据/成本/评测；③真正的工程能力不是告诉别人你会什么，而是系统出问题时你知道为什么、改哪里、怎么证明解决了。

趋势判断

  1. Context Management 将成 Agent Harness 的一等公民（原文预判，与本库多篇互证）：模型能力趋同后，竞争点转移到「把正确信息在正确时间以正确方式交给模型」的系统工程——Harness/框架的差异化特性将从「接了多少工具」转向「上下文管理能力」。
  2. 能力认证从名词清单转向实证叙事（推文 B 的面试观察外推）：招聘与采购评标都会从「罗列技术栈」转向「项目级追问」——失败史与取舍证明成为竞争力而非减分项。
  3. 企业 AI 采购的成熟化：客户五关心（解决/稳定/安全/恢复/成本）将成为标书标准问法，Demo 驱动的采购窗口收窄——与 [[2026-10-20-Agent不是竞争力-企业AI交付才是护城河.md]] 的交付护城河判断收敛。
  4. 确定性 Workflow 回潮：「能确定的不交给 LLM」从反直觉变成工程共识，多 Agent 架构进入冷静期（与 10-21 边界篇、11-19 平台篇的判断一致——本作者连续 3 篇强调同一纪律，系列信源的判断稳定性本身是信号）。

指南分析

本笔记的正确用法：

  1. 立项时：读 Step 0 四档分级——先给场景定档，档位不匹配是最大的隐性成本来源。
  2. 设计时：Step 1 五问写进设计文档、Step 3 权限表人工签核——这两步是「纸面工作最少、事后收益最大」的投入。
  3. 开发时：Step 2 三件套决定长时任务成败；六环节探针在开发期就埋（不是出事再补）。
  4. 验收/迭代时：Step 4 回归表是唯一改动放行凭据；Step 6 五问用于评估做这事的人。
  5. 误用警告：Playbook 不是「全部步骤都要上」——D1 场景只需要 Step 0+1+4；把 D1 项目套满全流程本身就是违反本篇核心纪律（复杂度匹配）的行为。
