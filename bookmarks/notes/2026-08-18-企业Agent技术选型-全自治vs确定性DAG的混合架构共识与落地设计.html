一、内容整理

0. 问题还原

现状：百人研发部门，domain knowledge 深，已积累 Skill 和 RAG；Agent 能完成阶段性任务，完整流程需人类接力。

目标链路：

项目管理软件 issue（自动触发）
→ Agent 调用内部工具和数据
→ 判断、统计、代码追踪
→ 结论写回项目记录

两条候选路线：

路线 1：Hermes 全自治 路线 2：LangGraph 确定性 DAG
形态 Agent + Goal + Cron，补齐 Skill/Codebase/MCP，自己跑完整流程 确定性 DAG 固定流程，每步独立环境执行和验收
优势 灵活、能处理步骤不确定的任务、探索性强 流程稳定、state 可控、每步可验收可回滚
风险 方向错了不知道、审计困难、高风险操作无闸门 死板、流程变更成本高、探索性任务框不住

提问者直觉：固定且高风险的主流程交给 LangGraph，探索性强、步骤不确定的任务交给 Hermes。

四条论点（讨论回复）：
1. "一般是两者结合，开放性任务交给主 agent，固定的 workflow 可以作为 agent 的子 agent、mcp 工具"
2. "技术角度按照 tools/mcp connector/skills → agent 的形式。agent 采用 langgraph + deepagents：langgraph 流程稳定+state 可控；deepagents 偏探索性发散性任务"
3. "知识库，自身团队 domain Knowledge 强是优势，但还是脏活累活辛苦活"
4. "企业 Agent 别一上来就全自治。固定主流程、高风险节点必须用 LangGraph 这类确定性 DAG 锁死，探索性任务再交给 Hermes"

1. 论点分析：四条回复其实收敛到同一个架构

表面分歧，实质一致。拆开看：

论点 关键词 指向
① 两者结合 + workflow 作为子 agent/mcp 工具 组合关系：agent 与 workflow 互为组件
② tools/mcp/skills → agent 分层 + langgraph+deepagents 技术栈分层：工具层→编排层→探索层
③ domain knowledge 强但是脏活累活 知识治理是被低估的成本中心
④ 别一上来全自治，高风险节点锁死 风险分级：确定性优先，自治渐进

四条论点合成一句话：确定性 DAG 做骨架（控制平面），自治 agent 做肌肉（数据平面），工具/MCP/skills 做手脚（执行层），知识治理做血液。

这与 2026 H2 行业共识完全吻合：
- Harness = Control Plane（OpenAI/Snowflake/Augment Code 共同提出）：生产级 Agent 成败 90% 取决于控制平面设计；模型是数据平面（执行推理），Harness 是控制平面（约束、路由、验证、回滚、监控）
- STAR-PólyaMath 同构：Orchestrator 只管流程控制不调用 LLM 推理——控制与推理分离
- Deloitte 自主性光谱：In the Loop → On the Loop → Out of the Loop 渐进，不能跳级

2. 数据支撑：为什么"别一上来就全自治"是对的

来自本仓 agent-orchestration-pattern skill 的 2026 生产数据：

数据 含义
40% 多 Agent 试点 6 个月内失败（Gartner） 编排复杂度是主要死因
88% Agent 试点失败率（Forrester 2026） 试点到生产的鸿沟
单 Agent 在 64% 基准中匹敌或超越多 Agent（Princeton NLP） 多 Agent 不是默认答案
非确定性输出被 70% 企业领导者列为最大障碍 全自治的天然天花板
Sequential Pipeline：4 Agent 流水线 950ms 协调开销 vs 500ms 实际处理 编排层本身有成本
3 Agent 消耗 29K tokens vs 单 Agent 10K token 成本 3 倍
最成功部署是最窄范围：明确输入、可测量输出、低爆炸半径 范围控制 > 能力堆叠

反向证据也成立：全确定性 DAG 处理不了"判断、统计、代码追踪"中判断的部分——issue 千奇百怪，穷举分支会把 DAG 变成维护噩梦。所以混合是必然。

3. 解决方案：混合架构完整设计

总体架构（五层）：

┌────────────────────────────────────────────────────────────┐
│ 触发层：项目管理软件 webhook / 轮询 cron → issue 入队        │
├────────────────────────────────────────────────────────────┤
│ 控制平面：LangGraph 确定性 DAG（主流程骨架）                 │
│  ┌──────┐ ┌──────┐ ┌──────────┐ ┌──────┐ ┌──────┐ ┌─────┐│
│  │分类   │→│数据  │→│分析判断   │→│统计  │→│结论  │→│写回 ││
│  │路由   │ │收集  │ │(子agent)  │ │验证  │ │生成  │ │+审计││
│  └──────┘ └──────┘ └──────────┘ └──────┘ └──────┘ └─────┘│
│   确定性    确定性    探索性节点     确定性    半确定   确定性 │
│   小模型    工具调用  (deepagents/   沙箱执行  模板约束  护栏+ │
│   /规则             Hermes子agent)           +人审门  人工确认│
├────────────────────────────────────────────────────────────┤
│ 数据平面：自治子 agent（探索性任务）                          │
│  - 输入：DAG 节点的结构化 context（目标+约束+验收标准）       │
│  - 输出：必须返回可追溯 evidence（结论+依据+置信度）          │
│  - 沙箱：独立环境执行，超时/超预算自动终止                    │
├────────────────────────────────────────────────────────────┤
│ 执行层：tools / MCP connector / skills（统一工具协议）        │
│  - 内部 API、DB 查询、代码库检索、项目管理软件写回           │
│  - 每个工具 <10 个/agent（15-tool ceiling 硬约束）           │
├────────────────────────────────────────────────────────────┤
│ 知识层：domain RAG + Skill 库（脏活累活，需要治理）           │
│  - 负责人/有效期/分级分类（权限进索引）                      │
│  - 原始资料层 vs 核验结论层分离                              │
└────────────────────────────────────────────────────────────┘

各节点设计要点：

节点 1：分类路由（确定性）
- 不用大模型自由分类——规则优先（label/关键词命中），未命中再走 DeepSeek V4 Flash 低温度分类
- 输出：issue 类型 → 子图路由（bug 分析/统计报表/代码追踪/需求澄清，各走不同分支）
- 这是 LangGraph conditional edge 的标准用法

节点 2：数据收集（确定性）
- 纯工具调用：内部 API/DB 查询/代码库 grep——写成确定性节点而非让 agent 自由探索
- MCP token 成本警示（本仓 skill 数据）：MCP 工具加载 schema 开销 32K-82K token，CLI 直接调用等效操作仅 200 token——能用 CLI/内部 SDK 就别包 MCP；MCP 只用于必须标准化的跨系统连接器

节点 3：分析判断（探索性 → 自治子 agent）
- 这里是 Hermes/deepagents 的位置：步骤不确定（要追多少层代码、查多少关联 issue 由内容决定）
- 契约式委派（SearchSwarm 四原则）：主 DAG 传入完整简报（目标+约束+已有数据+验收标准），子 agent 返回带 evidence 的报告
- 独立环境（路线 2 的核心优势保留）：容器化执行，读权限白名单，超时/超 token 预算强制终止
- 并发限制：DeepSeek V4 Flash 本地部署的并发上限要实测（本仓经验：智谱系模型并发>1 直接报错），DAG 内并行节点数按实测降级

节点 4：统计验证（确定性）
- 统计计算用代码不用模型——execute_code 节点跑 pandas/SQL，结果确定性可复现
- Evaluator-Optimizer 可选：质量不达标带反馈重跑节点 3（≤3 轮）

节点 5：结论生成（半确定）
- 模板约束 + 引用强制：每个结论必须挂节点 2/3/4 的证据 ID（对应《知识库从入门到精通》的"保留来源、暴露冲突、允许拒答"）
- 证据不足时输出"资料不足以确认"并标记 issue 需人工补充——拒答是能力不是缺陷

节点 6：写回 + 审计（确定性 + 人工门）
- 确定性护栏三件套（deterministic-guardrails skill 模式）：状态机（只允许 completed→writeback 转换）+ 权限检查（写回目标白名单）+ 哈希链审计日志（不可篡改）
- 分级人工门：低风险（追加评论）自动写回；中风险（改 issue 状态）@负责人确认；高风险（关闭 issue/改里程碑）必须人工 approve——对应权限矩阵护栏
- Lethal Trifecta 检查：子 agent 若接触私有代码+读外部内容+可外发网络 = 三腿全开，必须切断出站网络腿

4. 知识治理（论点 ③ 的展开）

"domain Knowledge 强是优势，但还是脏活累活辛苦活"——这句话的价值在于提醒：知识库是持续成本中心，不是一次性资产。

落地要点（引《2026-08-18-知识库从入门到精通》原则）：
- 元数据六字段：每份资料有标题/来源/版本/生效日期/负责人/可见范围——缺负责人和有效期的知识库会腐烂
- 权限进索引：issue 相关数据按项目/部门分级，检索前过滤而非回答后脱敏（Agent 综合页越权是隐蔽泄露）
- 两层分离：原始资料层（代码/文档/issue 原文）与核验结论层（团队判断）分开——RAG 检索原始层，Skill 沉淀结论层
- Skill = 已核验的领域判断：团队 domain knowledge 的最佳载体是 skill（可执行+可审查+可复用），RAG 兜底长尾

5. 模型约束下的分层策略（DeepSeek V4 Flash 单模型）

生产限定开源模型不等于所有节点用同一配置：

节点 配置策略
分类路由 低温度（0）+ few-shot + 结构化输出
数据收集 不用模型（纯工具）或仅做查询生成（低温度）
分析判断（子 agent） 中温度（0.3-0.7）+ 充分 context + 强 system prompt
统计验证 不用模型（代码执行）
结论生成 低温度 + 模板 + 引用强制
人工门摘要 低温度 + 字数约束

单模型的好处：部署/评测/合规成本最低；坏处：无质量分层——用提示词工程+温度+验收门补偿。若未来放宽，路由类节点可换本地小模型（3B 级，见《MiniMind 评价》笔记的分水岭判断）省出 V4 Flash 算力给探索性节点。

6. 灰度路径（Phase 设计，回应"别一上来全自治"）

Phase 1（第 1-4 周）：影子模式
  DAG 全流程跑，但只输出不写回——人类并行做同样的事，对比差异
  验收：结论一致率 >80% 才进 Phase 2

Phase 2（第 5-8 周）：半自动
  低风险写回自动（追加评论），中高风险人工门
  验收：误报率 <5%、人工修正率逐周下降

Phase 3（第 9-12 周）：扩大范围
  按 issue 类型逐类放开自动化（从统计类→代码追踪类→判断类）
  每类放开前跑 20-50 个真实 issue 的评测集

Phase 4（3 个月后）：On the Loop
  人类从每步审批退到遥测监控+异常处理
  保持：高风险节点人工门永不撤、审计日志永不删

对应 CHAP 协议的 Modes 三级阶梯：Shadow → Trial → Production——与 Deloitte 自主性光谱一致。

7. 两条原始路线的修正

原路线 修正
路线 1（Hermes 全自治） 降级为子 agent 角色：Hermes 作为 DAG 中探索性节点的执行器（或开发期快速原型工具）；Goal/Cron 保留用于触发层和巡检类任务
路线 2（LangGraph+OpenCode） 保留为主架构，但吸收路线 1 的能力：探索性节点挂自治 agent（deepagents/Hermes 二选一）；OpenCode 的独立环境执行验收推广到所有非确定性节点

为什么主从关系是 DAG 为主、agent 为辅而不是反过来（论点 ①"workflow 作为 agent 的子 agent"的镜像问题）：
- 写回项目管理软件是高风险不可逆操作——审计要求控制流可解释，DAG 天然满足；自治 agent 的控制流是 emergent 的，事后解释成本高
- 但反向组合也成立：开发/探索场景（如"帮我把这个新流程跑通"）适合 agent 为主、调用固定 workflow 当工具——生产主流程 DAG 为骨架，开发探索 agent 为骨架，方向由场景风险决定，不是教条

二、查询拓展

  1. LangGraph 的 checkpointer（状态持久化）与中断恢复——issue 处理中途失败如何从断点续跑（对照 ScienceFlow 存档段思想）
  2. deepagents 框架与 Hermes 的能力差异——探索性子 agent 选型对比（工具调用可靠性/上下文管理/成本）
  3. OpenCode 的独立环境隔离机制——容器化执行+验收的门禁设计（exit code 契约）
  4. DeepSeek V4 Flash 的结构化输出可靠性——JSON mode/function calling 的实测错误率（对照 structured-output-reliability 的四大失败模式）
  5. 项目管理软件（Jira/Linear/飞书项目）的 webhook→写回权限模型——机器人账号的最小权限设计
  6. issue 自动处理的评测集设计——什么算"结论正确"（对照 RAG 评测的六项检查）

三、归纳总结

维度 要点
一句话 确定性 DAG 做控制平面（骨架），自治 agent 做数据平面（探索性节点的执行器），工具/MCP/skills 做执行层，知识治理做底座——四条论点收敛于此
核心判据 风险分级：不可逆/可审计要求高的节点锁死为确定性；步骤不确定的节点放开给 agent（沙箱+契约+预算）
数据背书 40% 多 Agent 试点 6 个月失败、非确定性输出是 70% 企业最大障碍、Harness=Control Plane 共识
主从方向 生产主流程 DAG 为主 agent 为辅（审计可解释）；开发探索 agent 为主 workflow 为辅——方向由场景风险决定
模型策略 单模型（V4 Flash）+ 分节点温度/提示词/验收门补偿；统计类节点用代码不用模型
知识治理 domain knowledge 是优势更是持续成本：负责人/有效期/权限进索引，Skill 沉淀已核验判断
灰度路径 Shadow→Trial→Production；低风险先自动，高风险人工门永不撤

四、趋势判断

  1. "全自治 vs 确定性"之争已在 2026 收敛为伪命题：行业共识是控制平面/数据平面分离——问"哪种好"的团队还在 Phase 0，问"哪些节点该确定性"的团队已经在正确路径上
  2. Agent 框架竞争焦点从能力转向可控性：LangGraph 类状态图编排成为企业默认底座，自治 agent 框架（Hermes/deepagents）定位为"沙箱内的专家执行器"——两者互补而非竞争
  3. MCP 会在企业内被"选择性使用"：32K-82K token 的 schema 开销 vs CLI 200 token 的悬殊，使内部工具优先走 SDK/CLI，MCP 只承担跨组织标准化连接——"MCP everywhere"的叙事会修正
  4. 知识治理成为企业 Agent 的隐形胜负手：domain knowledge 强的团队反而容易高估知识库就绪度——负责人/有效期/权限三缺失会让 RAG 在 3 个月内腐烂
  5. 开源单模型约束催生"节点级优化"工艺：不能换模型就优化温度/提示词/验收门的分层配置——这套工艺本身会成为可迁移资产
  6. 人工门不会消失，只会变窄：从每步审批到遥测监控+高风险门——human-in-the-loop 的形态进化而非退场

六、拓展应用推荐

① 给该团队的直接落地清单（按周）
- W1：把现有"阶段性任务"Skill 映射到 DAG 节点——哪些已是确定性（工具调用）、哪些是探索性（agent）；列高风险节点清单（写回/关闭/修改类）
- W2：LangGraph 搭骨架（分类路由→收集→判断→验证→生成→写回），先全部接 mock，跑通状态流转
- W3：接真实工具（内部 API/DB/代码库），统计与验证节点用 execute_code；子 agent 沙箱化（容器+白名单+预算）
- W4：影子模式上线——DAG 输出与人类结论对比，建 20-50 issue 评测集
- 之后按 Phase 2-4 灰度

② 本仓可吸收
- Hermes 作为子 agent 的契约模板：delegate_task 的"上下文一次写透（目标+约束+验收标准）+ evidence 返回"模式可固化为 skill（已有 SearchSwarm 四原则，可加沙箱预算条款）
- cron 任务的风险分级：本仓 cron（推送/预警类）可按低/中/高风险分级——低风险自动执行、高风险（写操作类）加确认门
- 评测集先行：任何新自动化流程先建 20 个真实样本的影子对比——比上线后修便宜一个数量级

③ 决策速查（给同类团队）

问题 答案
第一个自动化流程选什么 统计类 issue（确定性最高、爆炸半径最小）
子 agent 选 deepagents 还是 Hermes 看团队栈：Python/LangGraph 生态→deepagents；要成熟 CLI/cron/skill 体系→Hermes
MCP 用不用 内部工具走 SDK/CLI；跨系统标准化连接才上 MCP（token 成本差 160-400 倍）
人工门放哪 写回前 + 高风险操作（关闭/修改里程碑）——永不撤
知识库先做什么 补负责人+有效期两字段——最便宜的防腐

七、指南分析

选型决策树（任何企业 Agent 项目通用）

流程步骤是否可枚举？
├─ 是 → 确定性节点（工具调用/代码执行/规则路由）
└─ 否 → 步骤是否高风险/不可逆？
    ├─ 是 → 拆解到可枚举 + 人工门（不允许自治）
    └─ 否 → 自治子 agent（沙箱+契约+预算+evidence 返回）

主流程怎么定骨架？
├─ 生产/审计要求 → DAG 为骨架，agent 为节点（本笔记方案）
└─ 开发/探索场景 → agent 为骨架，workflow 为工具（镜像组合）

什么时候扩大自治范围？
└─ 该类任务影子对比一致率 >80% 且误报 <5%，逐类放开

三条铁律（从四条论点提炼）
1. 高风险节点必须确定性锁死（论点④）——状态机+权限矩阵+审计日志，不依赖模型自觉
2. 组合方向由场景风险决定（论点①）——生产 DAG 为主，探索 agent 为主，不要教条化单向包含
3. 知识治理是持续成本不是一次性资产（论点③）——立项时就把负责人/有效期/权限预算进去

避坑清单
- 不要一开始追求 issue 100% 自动处理——分类路由先做"能处理的类型"白名单，其余转人工
- 不要让子 agent 直接持有写回权限——写回只在 DAG 的确定性节点发生（最小权限原则）
- 不要跳过影子模式——直接上线的失败率数据（40%/88%）就是跳级的代价
- 不要用模型做统计——pandas/SQL 节点确定性且免费
- 不要忽视单模型并发限制——本地 V4 Flash 的并发要实测，DAG 并行度按实测配置
- 不要把 MCP 当万能连接器——schema token 开销会在生产账单上现形

与提问者直觉的最后对照：直觉"固定高风险→LangGraph，探索性→Hermes"方向完全正确，唯一补充是主从关系要显式化——不是两套并行系统，而是 DAG 骨架内嵌 agent 节点的单系统；以及知识治理（论点③）值得从“备注”升级为“立项条件”
