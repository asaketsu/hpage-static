## 一句话定义

> MoE 和 MMoE 共享"专家+门控"的形式框架，但代表两条几乎不通信的技术路线：**稀疏 MoE 是"算多少"的技术**（让参数量摆脱算力束缚，2025 年成为大模型默认架构）；**MMoE 是"共享多少"的技术**（让不同任务学习不同参数共享组合，活跃在推荐/广告/搜索的多目标排序中）。两者"跟通用版与专用版没有关系"。

## 内容整理（完整保留原文核心论述）

### 引言：命名混乱与误解

"MoE"在 2026 年严重过载——可能指 1991 年门控加权的原始模型，可能指 Transformer 中的稀疏路由模块，也可能在推荐系统论文里泛指任何"多专家+门控"。

更麻烦的是 **MMoE**：
- 多任务学习社区：Google 2018 年的 **Multi-gate Mixture-of-Experts**
- 多模态工作（2023 年底起）：**Multimodal MoE**

两者除了共用"专家"一词没有技术交集。

**两个常见错误推论**：
1. "MMoE 是 MoE 的多任务版本，所以大模型里的 MoE 也是为多任务服务的"——完全不成立。大模型训练时只有一个目标函数。
2. "做多模态就要用 MMoE"——主流多模态模型用的是模态感知稀疏路由，MMoE 的"每个任务配独立门控"并不存在。

### 两条路线的分化

| | 稀疏路线 | 多任务路线 |
|---|---------|-----------|
| **专家是** | 容量单元 | 共享单元 |
| **核心问题** | 给定算力预算能装下多少知识 | 几个训练目标间该共享多少表示 |
| **激活方式** | 只激活一小部分 | 全部稠密计算 |
| **代表** | DeepSeek V3、Llama 4、Kimi K2 | 推荐系统多目标排序 |
| **专家数** | 数百个 | 十几个 |

### 二、共同起点：1991 年的原始形式

Jacobs、Jordan、Nowlan 与 Hinton 在 1991 年《Adaptive Mixtures of Local Experts》提出混合专家原始形式。

**核心洞察——误差信号分配**：
- 如果损失写成"加权和与目标的误差" → 专家互相配合 → 都变通才
- 作者把损失改写为**混合形式**：门控权重=专家被选中的后验概率，损失=各专家误差的加权混合 → 专家间形成**竞争关系** → 正反馈 → 输入空间隐式划分

> MoE 从第一天起就是一种**条件计算**，跟集成学习是两回事。

#### 与集成学习的本质区别

| | 集成（bagging/boosting） | MoE |
|---|---|---|
| 参与程度 | 所有基学习器参与每次预测 | 由输入决定，门控接近 one-hot |
| 收益来源 | 方差削减/偏差修正 | 容量与计算量解耦 |
| 推理成本 | 随成员数线性增长 | 理论上可省（1991 年未实现） |

#### 为什么沉寂了二十年（1994-2017）

五条原因（每条的反面正好构成复兴条件）：
1. **稠密实现省不下算力**——GPU 高效稀疏矩阵乘尚未具备
2. **门控坍塌难以控制**——2017 年负载均衡损失才实用级缓解
3. **数据规模不足**——MoE 需要数据足够多样且量大
4. **缺少硬件与并行动机**——单卡时代无法发挥模型并行优势
5. **注意力机制尚未成为主干**——FFN 层占参数大头要等 Transformer

> 这五条在 2017 年后逐一被翻转，混合专家的复兴来自五个条件**同时到位**。

### 三、分支一：稀疏 MoE 与大模型扩容

#### 3.1 2017 年的转折：稀疏门控

Shazeer 等人《Outrageously Large Neural Networks》(2017) 是整条稀疏路线的起点，做了三件事：

1. **门控稀疏化**：softmax 前加可学习高斯噪声 → 只保留 top-k → 其余置负无穷（k=2 或 4）
2. **辅助损失控制负载**：importance（门控权重之和）+ load（被选中期望次数）→ 变异系数平方惩罚
3. **规模推到 1370 亿参数**——第一次实证确认参数量与计算量可以脱钩

> 这篇论文改变的是人们对"模型大小"的定义：参数量和算力成本从"同一件事"变成"两个需要分别核算的预算"。

#### 3.2 路由器设计谱系

| 方案 | 核心思路 | 优缺点 |
|------|---------|--------|
| **Token Choice**（标准） | 每个 token 选 k 个专家 | 负载不可控，可能丢弃 token |
| **Expert Choice**（Zhou 2022） | 每个专家选固定数量 token | 负载完美均衡，但 token 可能不被选中 |
| **Hash Layers**（Roller 2021） | 哈希直接决定归属 | 无需辅助损失，对"路由学到语义分工"叙事构成挑战 |
| **BASE Layers**（Lewis 2021） | 显式建模为线性分配问题 | 严格均衡，但求解开销大 |
| **Soft MoE**（Puigcerver 2023） | 每专家分配 slot，输入为 token 加权平均 | 全可微无丢弃，但不再是稀疏计算，不能用于自回归 |
| **DeepSeek-V3 偏置**（无辅助损失） | 路由分数加可学习偏置，动态调整 | 不污染梯度，既均衡又不损害质量 |
| **ST-MoE router z-loss**（Zoph 2022） | 对 logits 对数配分函数施加惩罚 | 抑制数值爆炸，"数值卫生"在大规模训练中是能否跑完的关键 |

#### 3.3 进入 Transformer：GShard 与 Switch

**GShard**（Lepikhin 2020）——6000 亿参数多语言翻译模型，确立三个工程约定：
1. **隔层替换 FFN**（非每层）
2. **容量因子**（capacity factor）——每个专家预设 token 容量上限
3. **随机次选**——top-2 中第二个按比例随机

**Switch Transformer**（Fedus 2021）——激进的 k=1：
- top-1 可行且在同等算力下优于 top-2
- 规模推到 1.6 万亿参数
- 稳定性配方：路由器 float32 + 其余 bfloat16 + 更小初始化方差 + 专家层专用更高 dropout

#### 3.4 四个绕不开的工程问题

1. **负载均衡**：训练初期=少数专家吞掉多数 token；中后期=隐蔽不均衡（某些专家只接低信息 token）
2. **训练稳定性**：离散路由+梯度跳跃；混合精度放大（float32 路由器是直接原因）
3. **通信开销**：每层两次 all-to-all，对网络拓扑高度敏感
4. **显存 vs 算力的成本不对称**：1.6T 总参数/49B 激活 → 算力≈49B 稠密，显存≈1.6T 稠密

> **稀疏 MoE 省的是计算，不是存储**。对自托管用户来说，显存才是真正的门槛。

#### 3.5 结构演进（2024+）

**DeepSeekMoE 两大改动**：
1. **细粒度专家**（Fine-grained）：隐层缩小 + 专家数增加 → 组合爆炸 → 几乎免费提升质量
2. **共享专家**（Shared Expert）：少量常驻 + 路由专家并行 → 通用知识集中到共享专家减少冗余

> Qwen1.5-MoE：4 常驻 + 60 路由（激活 4），总参 14.3B/激活 2.7B，性能接近 Qwen1.5-7B，训练资源减约 3/4。

**其他演进**：Sparse Upcycling（稠密→MoE 改造，风险=初始冗余）、浅层保持稠密（路由不稳定会向上传播）。

#### 3.6 2024-2026 现状

稀疏 MoE 赢得了大模型架构之争。Llama 4、Qwen3、Kimi K2、GLM-4.5、gpt-oss 无一例外。

**趋势**：
- 稀疏比持续上升（Mixtral 3-4倍 → 20-30倍+）
- 小模型也用 MoE（80B 总参/3B 激活 = 消费级硬件跑强模型）
- MoE + MLA/线性注意力组合（优化不同瓶颈）

#### 3.7 Scaling Law

- MoE 相对稠密的优势随规模增大而**递减**（Clark 2022）
- **专家粒度是被忽略的独立维度**：细粒度切分能持续改善损失（Krajewski 2024）
- 经验：算力受限+显存充裕 → MoE 几乎总划算；激活参数过低 → 推理组合能力退化
- MoE 微调易过拟合（ST-MoE 讨论过，缓解=只微调非专家参数）

### 四、分支二：多任务学习与 MMoE

#### 4.1 多任务学习的结构困境

**Shared-bottom**：底层共享 + 每任务独立塔。任务高度相关时正向迁移；任务相关性低时**负迁移**——梯度方向冲突，收敛到对谁都不理想的折中点。

> Shared-bottom 把共享程度硬编码成"完全共享"，没有调节余地。

#### 4.2 MMoE（KDD 2018）

Ma 等人的**极简答案**：底层换成共享专家，但每个任务拥有自己的门控。

```
y_k = h_k( Σ g_k(x)·f_i(x) )
```

- 门控只是一层线性映射 + softmax，参数量可忽略
- 任务相关时 → 各门控学到相似分布 → 退化为近似 shared-bottom
- 任务不相关时 → 各门控学到分离分布 → 退化为近似独立模型
- **MMoE 把两个极端都包含为特例，允许连续插值**

论文的合成数据实验设计值得称赞——用显式参数控制任务标签相关系数，直接验证"多门是用来对抗低任务相关性的"因果主张。

#### 4.3 YouTube 工业落地

参与度目标（点击/观看时长）vs 满意度目标（点赞/评分）——典型低相关甚至负相关。各目标有自己的门与塔，排序分数按业务权重融合。

位置偏差处理：加一个只吃位置特征的浅层塔，训练时吸收偏差，线上推理置零。

> 工业多任务系统的真实复杂度：结构上的多任务只是其中一层，还需处理选择偏差、反馈延迟、目标融合。

#### 4.4 后续演进

| 方案 | 解决的问题 |
|------|-----------|
| **PLE**（Tang, RecSys 2020） | MMoE 的"跷跷板现象"——调整一个任务另一个就降。解法：CGC（专家显式分为任务专属组+共享组），任务门控只能看自己的专属+共享。堆叠多层=渐进抽取 |
| **SNR**（Ma, AAAI 2019） | 共享粒度下降到子网络连接，可学习二值变量决定是否连通 |
| **ESMM**（Ma, SIGIR 2018） | 利用点击与转化的因果链条，在全空间建模——共享方式来自概率关系约束而非门控 |

> PLE 获 RecSys 2020 最佳论文，至今是工业多目标排序的主流选择，实际使用频率可能高于原始 MMoE。

#### 4.5 为什么多任务路线没走向稀疏

1. **专家数量少**（十几个）——稀疏化收益有限
2. **在线延迟约束**——几十毫秒内排序，稀疏路由的动态形状导致 p99 延迟恶化
3. **训练稳定性优先**——高频重训（每天/每小时），损失尖峰不可接受
4. **动机上不需要**——瓶颈在特征工程和 embedding 表，不在模型参数量

### 五、两条分支的对比与交汇

#### 5.1 系统性对比

| 维度 | 稀疏 MoE | MMoE |
|------|---------|------|
| 动机 | 参数量脱钩算力 | 任务间共享多少表示 |
| 激活 | 稀疏（top-k） | 稠密 |
| 专家数 | 数百 | 十几个 |
| 路由器 | 单一，按 token 内容 | 每任务一个，按任务身份 |
| 负载均衡 | 核心工程问题 | 不是主要关注 |
| 失效模式 | token 丢弃/路由坍塌 | 跷跷板/负迁移 |
| 评价标准 | 单一损失在给定算力下更低 | 多指标的帕累托改进 |

#### 5.2 概念收敛：共享专家的独立发明

PLE（2020）和 DeepSeekMoE（2024）各自独立发明了"专属专家+共享专家"结构——动机完全不同，实现细节惊人接近。

> 任何基于条件计算的分工机制都面临同一个张力：完全分离=通用知识重复学习（浪费容量）；完全共享=特化知识互相干扰（损害专精）。"一部分常驻+一部分条件"是最简单的显式解法。

#### 5.3 命名速查

| 名称 | 年份 | 含义 |
|------|------|------|
| MoE | 1991 | 原始混合专家 |
| Sparse MoE | 2017 | 稀疏门控（top-k） |
| MMoE | 2018 KDD | Multi-gate（每任务独立门控） |
| PLE/CGC | 2020 RecSys | 任务专属+共享专家组 |
| Multimodal MoE | 2023+ | 模态感知路由（≠MMoE） |

> 阅读文献看到 MMoE 先确认年份+场所：KDD/RecSys/CIKM → Multi-gate；CVPR/ACL/ICML 2024+ → 可能是 Multimodal。

#### 5.4 多模态 MoE：第三条支流

| 设计模式 | 代表 | 特点 |
|---------|------|------|
| **模态感知硬路由** | VLMo MoME | 视觉 token→视觉专家，文本→文本，不需学习 |
| **模态感知软路由** | MoST | 模态专属组+跨模态共享组+模态标识路由 |
| **无先验学习路由** | LIMoE | 不告诉模态，让路由学 → 需基于熵的正则 |
| **任务引导的多模态 MoE** | M4oE | 按任务而非模态分专家——MMoE 思想在多模态的真正对应 |

> 做多模态并不必然需要 MoE。稠密 VLM 仍是主流。

### 六、系统与工程实践

#### 6.1 训练侧

- **专家并行（EP）**：新切分维度，需与 DP/TP/PP 组合
- **通信与计算重叠**：token 分块让第一块计算与第二块通信重叠
- **DeepSeek 动态重排**：高负载专家副本化跨节点重分布
- **Dropless MoE**（Megablocks）：块稀疏矩阵乘支持变长负载

#### 6.2 推理侧

- **批量效应**：单请求解码=每步 1 token，算力利用率极低；大批量→几乎所有专家被激活，稀疏性优势部分消失
- **显存带宽受限**：消费级硬件上 MoE 收益有限（除非配合量化）
- **专家 offload + 预取**：不常用专家放 CPU/磁盘，按需加载
- **投机解码交互**：验证多个 token 改变专家激活集合

#### 6.3 压缩侧

- **专家剪枝/合并**：激活频率高≠重要（可能在处理低信息 token）
- **专家级混合精度**：关键专家高位宽，次要专家更激进压缩
- **多模态陷阱**：不分模态聚合激活统计→重要性估计失真→性能退化

### 七、开放问题

1. **专家真的"专精"了吗？** Hash Layers（随机哈希效果接近学习路由）是强反证。收益可能来自参数量增加+梯度稀疏化的隐式正则，而非可解释的语义分工。"专家"隐喻可能是误导性的。
2. **路由机制理论空白**：为什么 top-k 离散选择能通过梯度下降训练？稀疏度理论上限？
3. **与长上下文耦合**：相邻 token 路由到不同专家→表示空间不连续性→长序列是否累积？
4. **条件统一**：token 内容/任务身份/模态类型能否统一到一个路由器？

### 八、结论（原文金句）

> **MoE 让不同的 token 走不同的路，MMoE 让不同的任务走不同的路。路是同一批，走法的含义完全不同。**

> 两条路线各自独立发明出"共享专家+专属专家"这一结构，或许提示了条件计算领域一个更普遍的规律：任何试图在容量与专精之间取得平衡的机制，最终都会需要一部分无条件参与的公共部分。

### 附录：八条常见误解

| 误解 | 纠正 |
|------|------|
| MoE 是为多任务服务的 | 大模型 MoE 训练时只有一个目标函数 |
| MMoE 是 MoE 的多任务版本 | 两者是同一祖先的两个分支，没有继承关系 |
| Transformer 里的 MoE 就是 MMoE | 单路由器 top-k ≠ 门控数等于任务数 |
| 做多模态就要用 MMoE | 稠密 VLM 仍是主流 |
| MoE 省显存 | 省的是计算不是存储，显存才是自托管门槛 |
| 专家有明确语义分工 | Hash Layers 反证：随机路由效果接近 |
| 稀疏比越高越好 | 激活参数过低→推理能力退化，有上限 |
| 推荐系统应该用稀疏 MoE | 不划算——专家少、延迟约束、训练不稳定不可接受 |

## 结合最新研究与技术变化

### 1. 与 LLM 微调成本工程笔记的关联

本文"MoE 微调易过拟合（ST-MoE 讨论过，缓解=只微调非专家参数）"直接关联微调笔记的"微调会侵蚀通用能力"——MoE 的专家参数比稠密模型的 FFN 参数更脆弱，微调时需要特殊策略。

### 2. 与 Jetson 边缘 AI 方向的关联

**显存 vs 算力的成本不对称**是 Jetson Orin Nano 的核心约束：MoE 模型（如 gpt-oss-20B/3.5B 激活）的算力需求≈3.5B 稠密模型，但显存需求≈20B——8GB Jetson 跑不动。**专家 offload + 预取**是 Jetson 的唯一路径。

### 3. 与量化方向（gguf-quantization）的关联

本文"专家级混合精度量化"是 GGUF 量化在 MoE 上的自然延伸——按专家重要性分配不同位宽。这对 Jetson 边缘部署 MoE 模型有直接参考价值。

### 4. 2026 最新技术变化

- DeepSeek-V3 的**无辅助损失偏置路由**已成为多个后续模型的默认选择
- 稀疏比从 Mixtral 的 3-4 倍推到 20-30 倍+——社区对"激活多少才够"的判断不断放宽
- 小模型（80B/3B）也开始用 MoE——不再只是千亿以上模型的专利
- MoE 已成为"需要专门优化的系统对象"——有专门的并行策略、量化方法、推理调度算法

| **共享专家+专属专家** | Hermes Skill 体系 | 通用 Skill（共享）+ 领域 Skill（专属），避免重复 |
| **DeepSeek 无辅助损失偏置** | Agent 负载均衡 | 不污染梯度=不影响主任务的前提下做动态调节 |
| **PLE 硬分组隔离** | delegate_task | 不同角色的子 Agent 使用不同 Skill 池，避免互相干扰 |
| **MMoE 连续插值** | 模型路由策略 | glm-5.2（通用）↔ deepseek（编码）↔ gemini（推理），按任务特性动态路由 |
| **专家 offload+预取** | Jetson 模型部署 | 超显存模型按需加载专家到 GPU |

## 趋势判断

- **稀疏 MoE 已赢得大模型架构之争**——2025 年几乎所有重要开源权重都采用，到 2026 年已成默认
- **"专家"隐喻可能是误导性的**——Hash Layers 反证表明收益可能来自参数量增加+梯度稀疏化，而非可解释的语义分工。路由只需"稳定且均衡"，不需"有意义"
- **稀疏比持续推高但存在上限**——从 3-4 倍到 20-30 倍+，但激活参数过低导致推理能力退化
- **MoE 从"架构选择"变为"系统对象"**——未来演进受系统约束（并行/量化/延迟可预测）而非建模灵感驱动
- **PLE 的跷跷板现象是 Agent 多角色协作的隐喻**——调整一个 Agent 角色可能导致另一个角色退化，需要类似 CGC 的硬隔离
- **"共享+专属"是最普遍的结构模式**——从条件计算到 Agent 架构到组织设计，"一部分公共+一部分条件性"是普遍解法
