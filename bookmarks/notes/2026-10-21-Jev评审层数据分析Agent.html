归纳总结

一句话核心命题："Guard with code when the condition is checkable. Use a model when the question actually requires judgment."（可判定的条件用代码守卫，需要语义判断的才用模型）。

这篇文章的价值不在"又做了一个 text-to-SQL Agent"，而在它把 Agent 的职责切成了三层互不越权的结构：

层 执行者 职责 关键约束
生成层 Qwen（qwen3.8-omni-flash） 读 schema、写 SQL、解释结果 只有两个工具，永远摸不到数据库直连
评审层 Jev（TypeSafe AI 独立评价模型） 三个语义审查点 只给意见，无任何执行权
守卫层 确定性代码 + Vercel eve 运行时 read-only、行数上限、人工审批 规则可判定则绝不调模型

三条最值得记住的设计原则：

  1. Confidence is not permission（置信度不是权限）——Jev 给出 93% 置信度的"clarify"判定只影响流程走向，它不能授权 unsafe SQL、不能解除行数上限、不能替人按批准键。评审意见的生效范围由运行时决定，不是评审模型自己。
  2. Fail-open 但降级为"无意见"而非"已批准"——评审器慢/挂/低置信时系统不瘫痪，答案照出但带"未评审"标注。评审缺席的正确降级是 no-opinion，绝不能静默变成 approved。
  3. 审查点按失败模式分布，不是撒胡椒面——三个 Jev 审查点分别拦截三类确定性代码拦不住的失败：问题歧义（答非所问的前置）、SQL 与意图错配（语法对但语义错）、解释脱锚（数据对但结论胡说）。

内容整理：三审查点与确定性守卫的完整分工

确定性守卫（无模型参与）

  • SQLite 以 read-only + query_only 模式打开，写操作/多语句直接拒绝
  • 只允许恰好一条 SELECT
  • 返回 >200 行拒绝，要求聚合或加 LIMIT
  • 无 WHERE 子句的宽扫描 → 暂停等人工批准
  • 作者原话级别的理由："If a rule can be checked deterministically, check it deterministically. A model call would actually make them less reliable."

Jev 三个语义审查点

审查点 时机 输入 拦截的失败 实测例
① 问题清晰度 进主循环前 用户问题 + schema 答非所问 "Who is our best customer?" → 判 ambiguous，clarify，93% 置信，反问"best 按什么定义"而非自己编指标
② SQL 意图匹配 SQL 写完、执行前 问题 + schema + SQL 语法对语义错（如问"上月营收"查成全时段） 高置信错配 → 给理由 + 一次修改机会
③ 答案落地性 最终答案产出后 答案 vs 实际返回行 数据对但结论 unsupported 不通过 → 展示为"未验证草稿"，SQL 和行数据仍可见供人核查

诚实的局限性自述（稀缺品质）

  • 只在 seeded SQLite 上测过，是控制流验证不是规模基准
  • SQL 意图检查走 eve 的 evaluate helper，不总返回置信值 → 该检查会 fail-open，作者明示这应解读为"无意见"不是"已批准"
  • 明确声明：保证数据库安全的是确定性控制，Jev 不构成正确性保证

趋势判断

  • 生成/判断职责分离正在从论文走向工程标配：2025 年是 self-critique（同一模型自评），2026 年转向独立小模型专司评审（Jev、_trajectory eval、process reward model 工程化）。经济动因明确——评审模型可以远小于生成模型。
  • "评审即服务"（Review-as-a-Service）是新商业化切口：TypeSafe AI 的 Jev 本质是把 PRM/LLM-as-Judge 包装成 API，跟 Vercel eve（agent runtime）捆绑出现在推广文里，说明 runtime + reviewer 的组合销售已经开始。
  • Agent 安全架构收敛为"最小权限 + 多层否决"：模型只有工具没有连接、代码守卫一票否决、评审只建议不执行——这套结构在人形机器人 RL 部署里同样成立（力矩门禁=代码守卫，策略=生成层）。

指南分析

若要把本文架构搬进自己的 Agent 系统，按此顺序：

  1. 先列失败模式清单再分层：把"这个环节会怎么错"分成可判定（语法/权限/数量）与需语义（意图/歧义/落地）两类，前者全部代码化。
  2. 评审点选在不可逆动作前后：本文三点的共性是卡在"信息放大"节点——执行前（SQL 要跑了）、回答前（答案要给人了）。不可逆且影响大的动作前必设审查。
  3. 给每个评审结果定义降级行为：评审挂了走哪条路必须预先写死，且降级产物必须带可见标注（未评审≠已通过）。
  4. 置信值与权限解耦：评审输出的 0-1 分数只进流程分支逻辑（重试/标注/人工转交），永远不进权限判断（放行/越权）。
  5. 限制修改机会次数：SQL 错配只给一次 revise 机会，防止评审-生成循环空转烧 token。
