# 为什么 KV Cache 只存 K 和 V、从不存 Q？

> **原推**：[x.com/_avichawla/status/2093962020962083139](https://x.com/_avichawla/status/2093962020962083139)（Avi Chawla，2026-08-30）
> 号称"热门 LLM 面试题"，配四层缓存总览图，文末引流其 X Article《The Four Caches in LLM Serving》

## 1. 原推全文（逐字翻译照录）

**问题：为什么 KV cache 存 K 和 V 向量，却从不存 Q？**

LLM 是自回归的：每个 token 由它之前的所有 token 逐个预测出来。这一性质在模型内部有直接后果——

**一次对 n 个 token 的前向传播产生 n 个隐状态，但只有最后一个被投影到 logits 并用于生成下一个 token。**

要理解 KV cache 为什么只存 K/V，必须回溯最后一个隐状态是如何产生的。用 10-token prompt 走一遍：

**1) Prefill（预填充）**：全部 10 个 token 并行过一遍模型（因果掩码）——整个 prompt 是已知的。每一层、每个位置产生 q/k/v 三个向量，每个位置对所有前置位置做 attention。这一步计算密集，**TTFT 主要就是 prefill**。

**2) 生成第 11 个 token**：只需要第 10 个位置的隐状态 → 投影到 vocab 维 → logits → softmax 采样出 token 11。

**3) 回溯隐状态**：最后隐状态是 FFN 输出的最后一行；FFN 是逐位置（position-wise）的，所以该行只来自 attention 输出的最后一行。

**4) Attention 矩阵**：10-token prompt 的 QKᵀ 是 10×10 矩阵。第 i 行 = Qᵢ 与所有 K 的点积。**第 10 行因此只含 Q₁₀**：`Q₁₀·K₁, Q₁₀·K₂, …, Q₁₀·K₁₀`。Q₁~Q₉ 只属于第 1~9 行——而那些行的隐状态已被丢弃（从不需要）。attention 最后一行经 softmax 后乘以全部 V₁~V₁₀ 得到输出最后一行。

> **结论：最后隐状态只依赖三样东西——Q₁₀、全部 Key、全部 Value。**

**5) 生成 token 12**：token 11 拼入后，需要第 11 行：Q₁₁ 对 K₁~K₁₁，乘 V₁~V₁₁。关键是：**K₁~K₁₁ 和 V₁~V₁₁ 与 prefill+首 token 产生的逐位相同**——因果掩码下，一个 token 的 K/V 只依赖它自己和之前的 token，永不依赖之后的内容，所以追加 token 11 不可能改变位置 3 的任何东西。

**6) 缓存状态**：每个解码步只需保留所有 K/V，**只为新位置计算 Q、K、V**。每步用一个 query 向量，**用完即弃，永不复用**——所以 Q 从不进缓存。

推文配图（四层缓存总览，视觉识别还原）：

```
KV CACHE       [K|V][K|V][K|V] →  ONE REQUEST      （请求内，精确匹配）
PREFIX CACHE   绿块 绿块 绿块  →  SHARED KV        （跨请求共享前缀）
PROMPT CACHE   紫块 紫块 紫块 + 文档($) → BILLED KV （服务商计费层）
SEMANTIC CACHE 查询💬 → 🔍 → ✓答案  ⚠️ FUZZY MATCH （跳过模型，模糊匹配）
──────────────────────────────
EXACT MATCH（前三层） vs FUZZY MATCH（第四层，有风险）
```

推文结尾：KV cache 只是 LLM serving 四层缓存之一，另外三层是**服务端 prefix cache、按量计费的 prompt cache、完全跳过模型的 semantic cache**——详见其 X Article。

## 2. 数学本质（领域补全，一张表说清）

| 量 | 依赖范围 | 生成后是否复用 | 缓存价值 |
|----|---------|--------------|---------|
| **Qᵢ** | 仅位置 i 的当前输入 | 当步算完 attention 即弃 | ❌ 无 |
| **Kᵢ** | 位置 i 及之前所有 token（因果掩码） | 之后**每一步**都要与最新 Q 点积 | ✅ 必须 |
| **Vᵢ** | 同 Kᵢ | 之后每一步 softmax 加权平均都要用 | ✅ 必须 |

因果掩码是根本原因：**K/V 是"只增不改"的累积量（append-only），Q 是"一次性"的消耗品**。缓存的定义就是"未来还会用的东西"——Q 不满足定义。

复杂度账（L 层、d 维、n 个已生成 token）：
- 无缓存 decode：每步 O(n·d²) 重算全部历史 → 总 O(n²d²)
- 有缓存 decode：每步只算新位置 O(d²) + attention O(n·d) → 显存换计算的教科书案例
- 这正是 [图解大语言模型部署](https://hpage.top/bookmarks/notes/2026-08-29-图解大语言模型部署.html) 显存公式中 KV Cache 项的由来：`2 × L × n × d × precision`

## 3. 四层缓存体系对照（原文框架 + 补全）

| 层 | 作用域 | 匹配方式 | 生命周期 | 典型实现 |
|----|--------|---------|---------|---------|
| 1. KV cache | 单请求内 | 精确（token 级） | 请求结束即释放 | vLLM PagedAttention、SGLang RadixAttention |
| 2. Prefix cache | 跨请求 | 精确（前缀哈希） | 分钟级驻留 | 系统提示/多轮对话公共前缀复用 |
| 3. Prompt cache | 服务商计费 | 精确 | 按策略 | OpenAI/Anthropic 输入缓存折扣（缓存命中 token 计费 1/10 价） |
| 4. Semantic cache | 跨用户跨问题 | **模糊（语义相似度）** | 小时~天 | GPTCache 等；⚠️ 相似≠相同，有答错风险 |

**层级关系**：1→2→3 是"精确匹配的扩大作用域"，4 是质变——不再匹配 token 而是匹配**意图**，收益最大（完全跳过模型）风险也最大（fuzzy match ⚠️）。

## 4. 值得记的三个点

1. **面试答案的一句话版**：因果掩码下 K/V 随序列只增不改（未来每步复用），Q 只在当步出现后即被丢弃——缓存"未来要用的"，所以只有 KV
2. **推文的推导路径本身值得学**：不自说自话，从"最后一个隐状态怎么来"回溯到 attention 矩阵行结构，每步都贴着矩阵形状走（10×10 的第 10 行只含 Q₁₀）——这是能写进教材的讲法
3. **四层缓存框架的工程价值**：把"KV cache 显存爆了”“为什么多轮对话越聊越快”“prompt cache 折扣怎么来的”"semantic cache 什么时候不能用"统一进一张图

### 4.0 三个点的展开（2026-09-03 应用户指令逐条深化）

#### 展开①：面试答案的一句话版——为什么这句话是"满分级"

**这句话的三层递进结构**：

| 层 | 内容 | 面试官听到什么 |
|----|------|----------------|
| 表层 | 复述现象（存 KV 不存 Q） | 你读过实现 |
| 机制层 | **因果掩码 → K/V 是 append-only 累积量** | 你懂因果掩码的真实工程含义，不只是"下三角矩阵"的记法 |
| 定义层 | **缓存的定义="未来还会用的东西"，Q 不满足定义** | 你有从"是什么"抽象到"为什么"的能力 |

**为什么"只增不改"是满分的锚词**：因果掩码保证位置 i 的 K/V 只依赖 token 1~i，追加 token 不改历史——这是**数学性质**不是工程选择。面试官追问"那为什么不全缓存"时，可续答：HuggingFace 早期 `use_cache=False` 默认值就是反例——无缓存时每步重算全部历史 O(n²d²)，显存换计算的权衡让"只缓存 K/V"成为唯一理性解。

**追问弹药库**（这句话能接住的三连问）：
1. "MQA/GQA 为什么省显存？"——K/V head 从全部减到 1 组/几组，Q head 不变——**因为 Q 本来就不驻留，砍它没意义**（KV cache 体积公式里根本没有 Q 项，见 §2 复杂度账）
2. "为什么多轮对话越聊越慢不是越聊越快？"——KV cache 让每步免重算（这是"越聊越快"的部分），但每步 attention 要扫全部历史 K/V（O(n·d)），上下文越长每步越贵——部署笔记实测 300→15K token decode 腰斩（39→18.2 tok/s）
3. "KV cache 会 infinite 增长吗？"——单请求内随生成线性涨（请求结束释放），跨请求靠 prefix cache 复用——衔接四层框架

**一句话的边界（防被反问击穿）**：这句话描述的是** decode 阶段**。prefill 阶段全部 Q 都要算（并行前向一次用完）——所以准确说法是"decode 的每步只需要当前 Q"。面试中主动补这个限定反而加分。

#### 展开②：推导路径本身——"贴着矩阵形状走"的讲法为什么能写进教材

**这条路径的五步还原**（从结果倒推到缓存，每步一个可验证的形状断言）：

```
目标：生成 token 11
  ↑ ① 只需最后隐状态（第10行）        —— logits 只从最后一行投影
  ↑ ② 最后隐状态 = FFN(attention 输出最后一行)  —— FFN 逐位置，行间无耦合
  ↑ ③ attention 输出最后一行 = softmax(第10行)·V —— 只含 Q₁₀·K₁..₁₀
  ↑ ④ 推广到 token 12：需要第11行 = Q₁₁·K₁..₁₁ —— K₁..₁₀ 与之前逐位相同！
  ↑ ⑤ 结论：保留全部 K/V，每步只算新位置的 Q/K/V —— Q 用完即弃
```

**教材级讲法的三个特征**（值得迁移到任何技术讲解）：

1. **从需求倒推而非从定义顺推**：不是"KV cache 是什么"，而是"要生成下一个 token 到底需要什么"——需求先行让每一步都有存在的理由，听众不会问"为什么要讲这个"
2. **每步贴着一个具体形状**（10×10 矩阵的第 10 行）：抽象概念（因果掩码/逐位置 FFN）全部锚定在可手算的对象上——"第 10 行只含 Q₁₀"是肉眼可验证的，比"因果掩码保证依赖关系"直观一个量级
3. **最小反例内嵌**：第 1~9 行的隐状态"从不需要"——顺手解释了为什么浪费的计算不可回收，为 ⑤ 的结论扫清"那前面的计算能不能也存"的天真追问

**迁移模板**（把这套讲法泛化）：`目标输出 → 输出的最小依赖集 → 依赖集的逐项来源 → 追加输入时哪些依赖不变 → 结论=缓存不变项`。适用于任何"为什么 X 要缓存/要持久化/要预计算"类问题——例如"为什么 RL 训练要存 replay buffer 而不存策略梯度"、"为什么数据库要写 WAL 不写数据页"。

**对照反面教材**：多数网文的讲法是"因为 attention 需要 K 和 V 所以缓存它们"——同义反复，没有回答"为什么 Q 不需要"。本推文的第 4 步（第 10 行只含 Q₁₀）才是唯一的论证支点：**行结构证明了历史 Q 的不可回溯使用**。

#### 展开③：四层框架的工程价值——一张图统一四类故障/现象/账单

**这张图的价值不在分类而在"把散落的运维问题归位"**——每个日常现象都能在图上找到自己的层：

| 日常问题 | 图上位面 | 框架给的行动 |
|----------|----------|--------------|
| "KV cache 显存爆了 / OOM" | 第 1 层（请求内） | 算 KV 体积（0.31MB/token@Llama70B）；开 PagedAttention 分页；部署笔记的"超配 24 倍"反向案例——按实测 usage 调池 |
| "为什么多轮对话**第二轮反而更快**" | 第 2 层（跨请求前缀） | prefix cache 命中了第 1 轮的 KV，prefill 被跳过——不是模型变快，是计算没发生 |
| "prompt cache 折扣怎么来的 / 为什么账单有 0.1× 的 token" | 第 3 层（计费） | 计费层读到的仍是 KV 张量：写 1.25×/读 0.1×——缓存命中优惠的本质是把 prefill 算力钱退给你 |
| "semantic cache 为什么不能上生产" | 第 4 层（模糊） | 前三层 miss=成本事件，第 4 层 hit 可能=**正确性事件**（200 状态码带错误答案）——失效传播的质变点 |

**框架的预测力（不只是解释力）**：知道四层的匹配键（位置→哈希链→精确前缀→embedding 相似度）后，可以**预判**哪些改动会打断缓存——§4.2②的四类隐性失效源（工具 schema 重排/设置项重渲染/历史摘要/跨模型路由）全部可从"匹配键变没变"推导出来，不需要死记。**框架即因果模型**：变前缀→断哈希链→冷 prefill→账单涨+TTFT 涨，一条链推到底。

**排障时的层定位法**：现象（慢/贵/错）→ 先判"这层失效是成本事件还是正确性事件"（1-3 层 vs 第 4 层）→ 成本事件查匹配键链路（变量在哪/摘要了吗/换模型了吗），正确性事件直接关 semantic cache 或降阈值+judge 复核。**这个决策树在 10 秒内把无限可能的"性能问题"收敛到四个可查的槽位**——这是框架对工程师的真正红利。

**与部署指标体系的合流**：四层框架回答"缓存该不该命中/为什么没命中"，部署指标体系（TTFT=Prefill+排队/P99/带宽瓶颈）回答"命中与否在延迟和钱上值多少"——两图拼接后，"用户说慢"到"哪层缓存哪个参数"的完整归因链成型。这也是本笔记与部署指标笔记（§1.9 六坑）互链的深层原因：**坑 1（TTFT 先查排队）是指标侧入口，本图是缓存侧入口，同一故障的两个坐标轴**。

### 4.1 四层缓存的精确机制（原文细节补全，含对 §3 表格的修正）

**各层"存的对象"精确化**（原 §3 表格已涉及，此处补机制细节）：

| 层 | 存的对象 | 索引/匹配键 | 原文关键机制 |
|----|----------|-------------|--------------|
| KV cache | 单请求的 attention 张量 | 请求内位置 | 请求结束即释放——20 轮对话第 20 轮要把 1~19 轮**全额重算 prefill** |
| Prefix cache | 同样的 KV 张量，但**留在服务端** | **token ID 的哈希链** | vLLM 16-token 定长块；块哈希=父块哈希+块内 token ID；引用计数 pin 住使用中的块 |
| Prompt cache | 仍是 KV 张量（**不是你的 prompt 文本**） | 完全渲染后上下文的精确前缀匹配 | 计费层：Anthropic 写 1.25×/读 0.1×；OpenAI 同结构 |
| Semantic cache | **完整响应字符串** | embedding 余弦相似度 | 命中即完全跳过模型，省输出 token+输入 token |

**对原笔记 §3 的两处修正**：
1. Prefix cache 的匹配不是笼统的"前缀哈希"——是**链式哈希**（子块哈希含父块哈希），块匹配天然蕴含"之前全部匹配"，这正是"前缀查找"的数学来源
2. Prompt cache 生命周期原写"按策略"——精确说是 **TTL+断点**双约束：只有你在断点处写入的 entry 才能被后续读；Anthropic 回溯上限 **20 块**，两次调用间插入超过 20 块对话，上一次写入就"出圈"，命中停止

### 4.2 层间交互与失效传播（重点展开）

四层不是并列菜单，是**嵌套依赖链**——上层的命中以下层的存在为前提，上层的失效会沿链向下传染：

**① 失效的物理载体：一个前缀变量污染整条链**

Prompt 前部任何变量（时间戳/请求 ID/用户名）都使其后的**每一个块**失效。失效不是"该块作废"而是"从该点起全链断裂"——因为链式哈希中子块身份依赖父块，父块变了，后面所有块的哈希全变。工程口诀（原文 Takeaways）：**稳定内容放最前、变量放最后、边界处放标记**。

**② 隐性失效源（最容易被忽视的四类）**：

| 失效源 | 机制 | 典型场景 |
|--------|------|----------|
| 工具 schema 重排 | tool schemas 通常渲染在 system prompt 之前，重排=重写前缀 | Agent 升级工具列表 |
| 设置项重渲染 | Anthropic 上开/关 web search、citations、thinking config、`tool_choice` 会**重写 prompt 文本** | A/B 测试两档 reasoning effort = 缓存裂成两半 |
| 历史摘要 | 摘要=重写前缀，下一次调用全部按冷 token 全价 | 多轮对话压缩策略 |
| 跨模型路由 | cache entry **绑定模型**，路由到便宜模型=全部历史冷 prefill | 降本切模型反而不省钱 |

**③ 缓存与批处理的内存竞争（与批处理笔记的交叉点）**：prefix cache 与运行中的 batch **共用同一 GPU 内存池**——缓存越大并发序列越少；内存压力下 vLLM 按 LRU 逐出无引用块。混合流量雪上加霜：**长共享前缀占块最多，恰好是丢了最疼的那些**。

**④ 与 RAG 的结构性冲突**：RAG prompt = 系统指令 + 检索块 + 查询，而检索块**每次变化且顺序不定**——两个请求检索到相同文档但顺序不同，在链式哈希下**共享为零**。这是 prefix caching 在 RAG 流量上欠佳的根因（朴素修法"每块独立 prefill 再拼接缓存"有更深的问题，原文留给其 RAG 课程 Part 12）。

**⑤ 层级语义总结**：1→2→3 层是"精确匹配、correctness-neutral"——miss 只损失钱和延迟，不损失正确性；第 4 层质变为 fuzzy match——hit 可能**带着 200 状态码返回错误答案**。失效传播在前三层是"成本事件"，在第四层是"正确性事件"。

### 4.3 Semantic Cache 的阈值困境与不可靠性根源（重点展开）

**① 运作与代价结构**：对入站 prompt 做 embedding → 对已存 prompt 做最近邻搜索 → 相似度超阈值即直接返回存储的响应。**省输出 token 是它与前三层的本质区别**（前三层只省 prefill、仍跑模型）；代价是**每个请求都要付一次 embedding 往返——包括所有 miss**。

**② 阈值的两难（原文）**：

| 阈值方向 | hit rate | 代价 |
|----------|----------|------|
| 调高 | 崩塌 | 每次调用仍在付 embedding 钱，命中率却没了 |
| 调低 | 上升 | **自信的错误答案**同步上升 |

已发表默认值从 **0.75 到 0.97** 不等——这个范围本身就是证据：**阈值是你流量的属性，不是可抄的常数**。

**③ 不可靠性的表征层根源**（任何阈值都挡不住的失败）：

1. **否定句在向量空间中彼此邻近**："X 有效"与"X 无效"embedding 距离极近——语义相似度对**否定词不敏感**，这是分布表征的结构性盲区
2. **句式框架主导向量**：两个 prompt 共享句式框架、只差一个操作性数值（如"利率 3% 还是 5%"），得分近乎相同——因为**框架贡献了向量的大部分**，关键差异被稀释

这两条决定了 semantic cache 的安全边界：**只适用于"问法不同但答案确实等价"的封闭类目**（FAQ/固定口径），不适用于事实精度敏感场景。

**④ 缓解前沿（增量调研）**：
- **Apple Krites**（machinelearning.apple.com）：静态阈值政策在关键路径上行为不变；对"恰好低于阈值"的最近邻**异步调用 LLM judge 复核**，通过则提升进动态缓存——对话/搜索流量上策展静态答案服务占比提升至 **3.9×**
- **阈值即产品策略**（Ace The Cloud）：阈值调优不是 ML 调参是产品决策——低阈值=高命中/低成本/高假阳性风险；配套纪律：semantic hit 需要证据链而非仅相似度、缓存响应附源哈希与策略版本、先影子模式再上线
- **SAECache**（arXiv:2605.18825）：前缀缓存逐出不应均匀对待所有块——复用概率强烈依赖 token 语义/prompt 结构/会话类型，语义感知逐出可带来 1.4–2.7× TTFT 改善——语义信息反过来救精确缓存，形成有趣闭环

**⑤ 度量学结论（原文）**：前三层报 hit rate 是对的（miss 只体现在成本与延迟）；**semantic cache 不该报 hit rate**——它的风险维度是假阳性，正确指标是安全命中率/假阳性率/过期命中拦截数/避免的成本（Ace The Cloud 指标组）。
