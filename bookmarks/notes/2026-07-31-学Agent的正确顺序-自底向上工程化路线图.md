# 学 Agent 的正确顺序：自底向上工程化路线图

> **类型**: 原创学习路线整理
> **日期**: 2026-07-31
> **标签**: `Agent` `学习路线` `工程化` `Single-Agent` `Multi-Agent` `RAG` `实践`

---

## 核心结论

**很多人学 Agent 的顺序是反的。** 一上来研究 Multi-Agent、Tree of Thought、Memory，架构图看了一堆，真到落地时连一个能稳定跑起来的单 Agent 都做不出来。正确路径是**自底向上工程化**：先把单 Agent 推理链路跑通 → 接工具 → 补 RAG → 处理状态记忆 → 最后才碰 Multi-Agent。

> 核心从来不是会多少框架，是有没有**完整跑通过一次 Agent 工程**。

---

## 一、错误顺序 vs 正确顺序

### ❌ 错误顺序（自顶向下，看架构图为主）

```
一上来就看/做:
  Multi-Agent 架构图
  Tree of Thought / Graph of Thought
  复杂记忆系统
  Agent 编排框架 (LangGraph / CrewAI / AutoGen)
  ↓
结果: 能聊概念, 但落地时:
  • 单 Agent 推理链都不稳定
  • 工具调用经常失败不知道为什么
  • RAG 检索质量差, 幻觉严重
  • 连一个可靠的 demo 都跑不通
```

### ✅ 正确顺序（自底向上，工程化实践）

```
Phase 1: 单 Agent 推理链路跑通 (最核心)
  ↓
Phase 2: 工具调用 (Tool Use)
  ↓
Phase 3: RAG + 向量检索 + 引用溯源
  ↓
Phase 4: 上下文记忆 + 状态管理 + 日志异常
  ↓
Phase 5: Multi-Agent 协同 (水到渠成)
```

> 所谓多 Agent 协同，说白了还是**多个可靠 Agent 之间的任务拆分和调度**。单个 Agent 的推理、工具调用、工作流稳定性都没打牢，系统只会越搭越复杂。

---

## 二、五阶段详细路线图

### Phase 1：单 Agent 推理链路跑通（最核心，2-3 周）

**目标**：让一个 Agent 能稳定地"想清楚→做对事→说对话"。

| 步骤 | 做什么 | 验收标准 |
|------|--------|---------|
| **1.1 理解 ReAct 模式** | 手写一个最简 ReAct Loop：Thought→Action→Observation→Thought | 不用任何框架，纯 Python + API 调用实现 |
| **1.2 Prompt 工程** | System Prompt 设计、角色定义、输出格式控制 | 同一输入 10 次跑，输出格式稳定不漂移 |
| **1.3 推理链稳定性** | 处理 LLM 输出不稳定（JSON 解析失败、格式漂移） | 加 retry + 格式校验 + fallback |
| **1.4 错误处理** | API 超时、速率限制、空响应 | 指数退避重试 + 优雅降级 |

#### 最小可用代码（不用任何框架）

```python
import json

def agent_loop(query, max_steps=5):
    """最简 ReAct Agent - 不用任何框架"""
    messages = [
        {"role": "system", "content": "你是一个助手。按 JSON 格式回复: {\"thought\": \"...\", \"action\": \"final_answer/need_tool\", \"answer\": \"...\"}"},
        {"role": "user", "content": query}
    ]

    for step in range(max_steps):
        # 1. LLM 推理
        response = call_llm(messages)
        
        # 2. 解析输出 (带格式校验)
        try:
            parsed = json.loads(response)
        except json.JSONDecodeError:
            messages.append({"role": "assistant", "content": response})
            messages.append({"role": "user", "content": "请严格按 JSON 格式回复"})
            continue
        
        # 3. 判断是否完成
        if parsed["action"] == "final_answer":
            return parsed["answer"]
        
        # 4. 需要工具 → Phase 2 再接
        messages.append({"role": "assistant", "content": response})
        messages.append({"role": "user", "content": "暂无工具可用，请基于已知信息直接回答"})
    
    return "达到最大步数限制"
```

> **Phase 1 不完成，不要进 Phase 2。** 这是最多人跳过的一步，也是最重要的一步。

---

### Phase 2：工具调用（2-3 周）

**目标**：让 Agent 能正确使用外部工具。

| 步骤 | 工具类型 | 做什么 | 验收标准 |
|------|---------|--------|---------|
| **2.1** | **搜索 API** | 接入搜索（SerpAPI / Tavily / 自建） | 能正确构造查询 + 解析结果 + 判断何时搜索 |
| **2.2** | **代码执行** | 安全沙箱执行 Python（不直接 exec） | 能运行代码 + 捕获输出/错误 + 结果回传 |
| **2.3** | **数据库查询** | SQL 生成 + 执行 + 结果格式化 | Text-to-SQL 准确率 >80% |
| **2.4** | **通用 API** | 天气/汇率/日历等 RESTful API | 能正确理解意图→选择 API→解析参数→调用 |
| **2.5** | **工具选择** | 多工具场景下的正确路由 | 给 5 个工具，选择正确率 >90% |

#### 关键工程化要点

| 要点 | 说明 |
|------|------|
| **工具描述** | 每个工具的 description 要让 LLM 理解"什么时候用、怎么用" |
| **参数提取** | 从自然语言中提取结构化参数（JSON Schema） |
| **错误传播** | 工具失败时，把错误信息返回给 LLM 让它自行修正 |
| **超时控制** | 每个工具有独立超时，不让单个工具拖垮整个 Loop |

---

### Phase 3：RAG + 向量检索 + 引用溯源（2-3 周）

**目标**：让 Agent 能基于私有知识回答问题，且**可溯源**。

| 步骤 | 做什么 | 验收标准 |
|------|--------|---------|
| **3.1 文档处理** | 文档切分（chunk size + overlap 策略） | 切分后语义完整，不割裂上下文 |
| **3.2 Embedding + 向量库** | 选 Embedding 模型 + 向量数据库（Chroma/Milvus/pgvector） | 召回率测试 |
| **3.3 检索策略** | 语义检索 + 关键词混合 + Reranking | 对比纯语义 vs 混合检索效果 |
| **3.4 引用溯源** | 回答中标注来源（chunk ID / 文档名 / 页码） | 人工抽检 10 条，引用准确率 >90% |
| **3.5 RAG 评估** | 建立评估集：query→expected answer→retrieved context | RAGAS / 人工评估，量化召回率和准确率 |

#### 关键认知

> RAG 不是"接个向量库"那么简单。**检索质量决定回答质量**——垃圾进垃圾出。Chunk 策略、Embedding 模型、Reranking 策略三者共同决定效果。

---

### Phase 4：上下文记忆 + 状态管理 + 日志异常（2-3 周）

**目标**：让 Agent 在多轮对话和长任务中**不丢记忆、不崩溃、可调试**。

| 步骤 | 做什么 | 验收标准 |
|------|--------|---------|
| **4.1 上下文管理** | 对话历史压缩/摘要/滑窗 | 50 轮对话后不爆 context window，且不丢失关键信息 |
| **4.2 状态管理** | 任务状态持久化（进行中/等待/完成） | 服务重启后能恢复任务 |
| **4.3 日志系统** | 全链路日志（输入/Prompt/工具调用/输出） | 出问题能 5 分钟内定位 |
| **4.4 异常处理** | 死循环检测、最大步数限制、成本上限 | Agent 不会无限调用工具烧钱 |
| **4.5 可观测性** | OpenTelemetry 或简化版 span tracing | 全链路可追踪 |

#### 分层记忆架构（到这一步才做）

| 记忆层 | 存储 | 用途 |
|--------|------|------|
| **短期** | 对话上下文 | 当前会话 |
| **中期** | 向量数据库 | 偏好与摘要 |
| **长期** | 关系型/图数据库 | 核心业务实体 |

> 这一步对应生产级 Agent 的 Runtime 底座——Checkpoint、状态持久化、熔断、日志。没有这层底座，Phase 5 的 Multi-Agent 全是空中楼阁。

---

### Phase 5：Multi-Agent 协同（2-3 周）

**前提**：Phase 1-4 全部通过，你有**一个可靠的 Agent**。

| 步骤 | 做什么 | 验收标准 |
|------|--------|---------|
| **5.1 任务拆分** | 把复杂任务拆成子任务 | 拆分粒度合理，子任务可独立执行 |
| **5.2 Agent 角色定义** | 规划 Agent / 执行 Agent / 审核 Agent | 每个 Agent 职责清晰不重叠 |
| **5.3 调度与编排** | 任务路由 + 结果聚合 | 选对框架（LangGraph/CrewAI）或自建 |
| **5.4 Agent 间通信** | 消息传递 / 共享状态 | 协议设计（参考 MCP） |
| **5.5 冲突处理** | 两个 Agent 结果矛盾时的仲裁 | 有明确优先级/人工兜底 |

#### 为什么 Phase 5 在最后？

> 多 Agent 协同 = 多个可靠 Agent 之间的任务拆分和调度。如果单 Agent 的推理、工具调用、工作流稳定性都没打牢，系统只会越搭越复杂，排查问题地狱级难度。

## 四、每阶段的"反模式"（常见错误）

| Phase | ❌ 反模式 | ✅ 正确做法 |
|-------|---------|-----------|
| **1** | 一上来就用 LangChain AgentExecutor | 先手写 ReAct Loop，理解原理 |
| **1** | Prompt 写一次不迭代 | 同一输入跑 10 次，检查稳定性 |
| **2** | 所有工具一股脑全给 Agent | 先接 1 个工具跑通，再逐步加 |
| **2** | 工具失败直接报错退出 | 把错误返回给 LLM，让它自行修正 |
| **3** | 用默认 chunk size 不调 | 测试不同 chunk size + overlap |
| **3** | 只做语义检索不做 Reranking | 加 BM25 混合 + Cross-encoder Rerank |
| **4** | 把所有历史对话塞进 Prompt | 分层记忆 + 定期摘要压缩 |
| **4** | 没有最大步数限制 | 设 max_steps + cost_limit 防失控 |
| **5** | 单 Agent 还不稳就上 Multi | 先确保单 Agent 可靠 |
| **5** | Agent 之间无明确边界 | 每个角色职责 MECE，不重叠 |

## 五、框架使用建议

| 阶段 | 建议 |
|------|------|
| **Phase 1-2** | **不用框架**，纯 Python + API 手写。理解原理最重要 |
| **Phase 3** | 向量库用轻量的（Chroma / FAISS），先跑通 |
| **Phase 4** | 日志用 structlog，可观测性用 OpenTelemetry |
| **Phase 5** | 此时才考虑 LangGraph / CrewAI / 自建编排 |

> 框架是加速器不是拐杖。**先用框架之前，必须知道框架帮你做了什么。** 否则出问题时完全不知道排查方向。

## 六、评估标准：怎么判断自己"过关"了？

| Phase | 过关标准 |
|-------|---------|
| **Phase 1** | 手写 ReAct Agent，同一任务 10 次成功率 >90%，格式零解析失败 |
| **Phase 2** | 5 个工具场景，工具选择正确率 >90%，参数提取准确率 >85% |
| **Phase 3** | 建立 20 条评估集，RAGAS 或人工评估，引用溯源准确率 >90% |
| **Phase 4** | 模拟服务重启，Agent 能从 Checkpoint 恢复；50 轮对话不爆 context |
| **Phase 5** | 3 个 Agent 协同完成一个复合任务（如"调研→分析→写报告"），成功率 >80% |
