## 零、结论先行

这篇 11.5KB 长文系统化了 **LLM 判官从离线评估工具进入 Agent 运行时**的八种架构模式——判官不再"评估应用"，而是**"参与控制流"**：决定继续/重试/换模型/补证据/升级人工。

**为什么此文重要**：它恰好命中我们体系反复确认的唯一系统性短板——**06 Evals 域**。《AI工程化终极路线图》自检结论："缺 golden set 回归 + token 级 trace"；姜老师文补刀"固化流程必须有业务方验收"；本文给出的是**把判官嵌入运行时的完整模式语言**——三份独立输入收敛到同一命题，这篇是操作性最强的一份。

**八模式一览**（第一章详述）：

| # | 模式 | 一句话 |
|---|------|--------|
| 1 | 另一个模型当判官 | 生成≠评审，窄属性评审可用便宜专用模型（Prometheus/Galileo） |
| 2 | 拆解判断 | 一个大模糊决策 → 多个小判断 + 结构化组合（G-Eval/DeepEval DAG） |
| 3 | 比较代替打分 | 模型分不清 7 分 8 分，但分得清哪个更好（成对评审+位置偏差随机化） |
| 4 | 评审工作过程而非答案 | 20 分钟的 agent 工作，最终结果正常≠过程没走样——在关键决策点散布判官 |
| 5 | 多判官 | 判官也是 LLM 也会错；**分歧本身是信号**（同意→置信，分歧→重试/升级人工） |
| 6 | 评审判官 | 判官有偏差（位置/文风/自恋）；LLMBar/JudgeBench/RewardBench + Anthropic Bloom 模式 |
| 7 | 判官外围包确定性 | 能确定性检查的绝不用 LLM——LLM 判断证据充分性，确定性代码决定工作流推进 |
| 8 | 判官进循环 | 判官进关键路径=判官错误变成应用故障——机会与风险同源 |

**最有价值的洞察**：模式 5 的"分歧检测"——即使不在乎三个判官 2:1 投票结果，**"他们意见不一致"这件事本身就是重试/升级的触发器**。以及模式 7 的边界划分："应用层最大的机会，就是画好确定性/非确定性的边界"。

## 一、八模式忠实还原

### 模式 1：Start With Another Model（经典双模型）
- 工作模型生成，判官模型评审（输入=原始请求+结果+rubric+参考材料+期望答案，输出=分数/标签/解释）。LangSmith/Phoenix/DeepEval 已产品化
- **选模关键洞察**：判官不必全面更聪明——**判断窄属性比做原创工作容易**。写不出好研究报告的模型，完全可以判断"每个论断是否被证据支持"
- 专用判官生态：Prometheus（开源判官模型）、Galileo（生产级廉价评估模型）。运行时高频调用下经济性重要

### 模式 2：Break the Judgment Apart（拆解判断）
- "输出好不好"是一个巨型模糊决策：答案可能对但不完整、写得好但无证据支持、结果对但过程违规
- 升级路径：G-Eval（先生成评估步骤再打分）→ DeepEval（**DAG 式评估**：单个 LLM 判断嵌入更大的确定性决策图）
- 原则：**与其让一个模型做大模糊决策，不如拆成精心设计的小判断+结构化组合**

### 模式 3：Compare Instead of Score（成对比较）
- 模型不擅长区分 7 分和 8 分，**擅长判断两个东西哪个更好**
- LangSmith/DeepEval 原生支持，含位置偏差随机化
- 运行时化想象：agent 生成多个计划→判官选优；两个 agent 独立分析→第三者比较；**提议动作与替代方案比较后再提交**

### 模式 4：Judge the Work Instead of the Answer（评审过程）
- chatbot 评最终回复即可；**跑 20 分钟的 agent，最终结果正常说明不了什么**——可能检索错文档、调错工具、绕了一大圈最后靠运气
- Phoenix 已有检索相关性/工具选择/工具调用/工具响应/整体性能评估器；LangSmith 可评单次 run 到完整 trace
- 通用化：**在重要决策实际发生的地方评审**——研究 agent 在综合前评审信源选择；编码 agent 在实现前评审方案；操作 agent 在行动前评审证据支持。"散布判官形成关键检查点"

### 模式 5：Use More Than One Judge（多判官）
- 判官也是 LLM，会犯工作模型犯的一切错。研究界已探索：判官面板/评估者人格/投票/聚合/辩论（MAJ-EVAL：多维度评估 agent 审议）
- **生产采用少，但机制在应用层有不同价值**：不在乎 2:1 投票结果，**极在乎他们不一致**
- 独立判断的一致→增信；分歧→用更强模型重试/收集更多证据/升级人工。**可据此构建重试与升级机制**

### 模式 6：Judge the Judge（评审判官）
- 判官已知偏差：位置偏差（先出现的答案）、文风偏好、质量接近时失灵、**偏爱像自己写的输出**
- 评测界基准：LLMBar（困难条件下指令遵循区分）、JudgeBench（客观偏好难题对）、RewardBench（奖励模型/生成式判官）
- **Anthropic Bloom 模式**：先用人工标注的 transcript 从候选判官池选判官，评估管线还含跨结果扫描的 meta-judge
- 应用层简化版：**定期把判官与人类对比**——判官控制重要决策时，收集决策样本让人独立评，测分歧点，分歧不可接受就改 rubric/模型/上下文/决策边界

### 模式 7：Put Determinism Around the Judge（确定性包夹）
- 诱惑是把一切决策都变成 LLM 判断、agent 套 agent——**这放弃了应用层最大优势：外围系统是我们可控的**
- 能确定性检查的（测试/schema/数据库检查/策略引擎）绝不用 LLM
- OpenAI grader 架构范例：模型判官与确定性判官（字符串检查/Python 代码）并存，可组合成更大评估
- 应用内同构：**LLM 判断证据是否充分/建议是否有据/任务是否完成；确定性代码决定这些判断+事实的组合何时放行工作流**
- 原文金句："确定性/非确定性混合逻辑是应用层最大的机会。边界画得越好，在模型之上创造的价值越大。"

### 模式 8：Put the Judge in the Loop（判官进循环）
- 前七模式的自然终点：判官进 agent 循环、进关键路径。判断指导控制流——继续/重试/路由到其他模型/收集信息/升级人工
- **代价直白**：判官错误变成应用故障。离线 eval 里判官有噪声只是烦；**在每个重要动作前的判官会造成死循环、阻塞好工作、放行坏工作、给每次执行加延迟**
- 结论："在这些架构上投入、让模式成熟之前，我们还不会舒服地把 LLM 判官放上生产关键路径。但这里有巨大的创新机会。"

## 三、Evals 短板补强：从本文到可执行路线（本笔记核心增量）

《AI工程化终极路线图》把 06 Evals 列为体系唯一系统性短板。本文的模式语言正好可以映射成**分级补强路线**——按投入成本递增排序：

### L0（已有，确认存量）
- content-judge skill = 模式 1 的离线版
- watchdog/evolver = 模式 7 的进程级确定性包夹（pgrep/mtime/head 三验）
- skill-stress-test = 模式 6 的变体（用 subagent 验证 skill 有效性）

### L1（低成本高回报，立即可做）
- **模式 2 拆解**：把"笔记质量好不好"拆成独立小判断——①URL 抓取完整性（确定性：字节数）②出处标注存在性（确定性：grep）③线上 200 验证（确定性：curl）④内容深度（LLM 判断）。**前三项全确定性=模式 7，只有第四项需要判官**
- **笔记链 golden set**：10 篇已上线笔记的断言集（字节数区间/章节数/线上状态），cron 周检——这是 roadmap 笔记 P0-1 的具体化

### L2（中成本，季度级）
- **模式 5 分歧检测**：重要决策（如 skill 去留、cron 异常处置）双判官跑，分歧→升级人工而非自动处置
- **模式 6 判官体检**：content-judge 的 rubric 定期与用户抽查对比（用户本来就是最高判官）

### L3（高成本，条件触发才做）
- **模式 8 判官进循环**：仅在出现"无人值守+高价值+不可逆操作"三要素的场景（如自动交易执行、生产部署）考虑——当前体系无此场景，**明确不做**，防止过度工程

### 判断原则（从模式 7 提炼）
> 每个想加判官的地方先问：这事能不能用确定性检查？能→确定性；只有"人类本来要做的主观判断"才值得 LLM 判官——**判官处理判断题，代码处理验证题**。

## 四、金句提取

> "The judge is no longer just evaluating the application. It's participating in its control flow."（判官不再只是评估应用，它在参与控制流。）
>
> "Even if you don't care whether three judges vote 2–1 that an answer is good, you may care enormously that they disagree."（即使不在乎 2:1 投票结果，你极其在乎他们不一致。）
>
> "Judging a narrow property can be much easier than doing the original work."（判断窄属性比做原创工作容易。）
>
> "The better we get at drawing that boundary, the more value we are adding above and beyond the models themselves."（确定性边界画得越好，模型之上创造的价值越大。）

## 五、局限性

1. **模式多为设计建议而非生产实证**：作者自己承认多判官"没有太多生产采用的证据"、模式 8"需要成熟才敢上关键路径"——这是前瞻综述，不是成熟度报告
2. **无量化数据**：全文没有延迟/成本/误判率数字（判官进运行时的延迟代价只说"add latency"没给量级）
3. **作者立场**：ThruWire 做 agent 基础设施（类型化 artifact），"判官进运行时"叙事与其产品方向一致——但内容引用扎实，营销浓度低
4. L1-L3 路线为本笔记结合自有体系的设计，非原文内容；具体阈值需实测定标
5. 判官模型的中文场景偏差（本文以英文生态为主）未覆盖——中文判官的位置偏差/文风偏好可能不同，L0 落地时需自测
