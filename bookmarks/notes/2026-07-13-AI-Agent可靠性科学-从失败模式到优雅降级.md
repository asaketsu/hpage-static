# AI Agent 可靠性科学：从失败模式到优雅降级

> **日期**: 2026-07-13
> **来源**: arXiv 2603.29231, Zylos Research, Galileo AI
> **领域**: Agent系统 (L4)
> **标签**: #AI-Agent #可靠性工程 #优雅降级 #Circuit-Breaker #Fallback

## 核心结论

**能力 (capability) ≠ 可靠性 (reliability)。** 现有 benchmark 只测 pass@1（单次成功率），但生产环境需要的是跨多次调用的一致性成功。研究表明，多 Agent 系统在生产中的失败率高达 41-86.7%，而前沿模型在长时序任务中的"崩溃率"(meltdown) 反而最高——因为它们倾向于尝试雄心勃勃的多步策略，有时会陷入螺旋。

---

## 一、可靠性科学框架：四大指标

来自 arXiv 2603.29231（Khanal et al., 2026-03），提出了超越 pass@1 的正式化框架：

| 指标 | 全称 | 含义 |
|------|------|------|
| **RDC** | Reliability Decay Curve | 任务长度增加时成功率的衰减曲线 |
| **VAF** | Variance Amplification Factor | 重复执行时的方差放大倍数 |
| **GDS** | Graceful Degradation Score | 失败时的优雅降级程度（0-1） |
| **MOP** | Meltdown Onset Point | 系统完全崩溃的任务长度阈值 |

### 五大关键发现

1. **可靠性衰减是领域分层的** —— 软件工程任务 GDS 从 0.90 跌到 0.44，而文档处理几乎不变（0.74 → 0.71）
2. **VAF 按能力层级二分** —— 高 VAF 是**能力签名**而非不稳定信号（前沿 VAF ≥ 2.37，中端 ≤ 1.26）
3. **能力和可靠性排名严重偏离** —— 长时序任务中出现多级排名反转
4. **前沿模型崩溃率最高**（达 19%）—— 因为它们尝试复杂多步策略时更容易"螺旋"
5. **记忆脚手架普遍有害** —— 所有 10 个模型加入 memory scaffold 后长时序表现反而下降

### 评估规模

- 10 个开源模型，23,392 个 episode
- 396 个任务，4 个时长桶，3 个领域

## 二、优雅降级模式：四层防御体系

来自 Zylos Research（2026-02），生产级 AI Agent 的韧性工程已从"终端错误"进化为"分层韧性"。

### 第一层：Circuit Breaker（断路器）

**三态状态机**：CLOSED → OPEN → HALF-OPEN → CLOSED

**关键配置参数**：
- 失败阈值：3-5 次
- 检测窗口：5 分钟
- 初始退避：5 分钟
- 扩展退避：15 分钟（针对 flapping 问题）
- 恢复后渐进扩容：从 1 个 worker 开始，每 5 分钟 +1

**关键区分**：断路器只对**基础设施故障**跳闸（timeout / connection refused / HTTP 502/503/504），不对**业务逻辑错误**跳闸（HTTP 400/401/验证失败）。

### 第二层：Fallback 策略

**四级升级层次**：

- **Level 1** (<2s): 低置信度/限流 → 切换备用模型
- **Level 2** (<10s): 模型类不可用 → 切换备用 Agent 系统/提供商
- **Level 3** (<30s): 复杂/模糊失败 → 人工接管
- **Level 4** (立即): 灾难性故障 → 紧急协议 + 排队重试

**模型行为一致性挑战**：不同模型输出格式不同，downstream parsing 可能断裂。Sierra AI 的方案是将**模型意图**（抽象任务规范）与**提供商适配**（如何针对特定模型 prompt）分离。

### 第三层：Rate Limit + Token Budget

- **RPM** + **TPM** + **输入TPM vs 输出TPM**（Anthropic 分开计）
- **日配额**：按计划重置的累积限制
- **指数退避 + 抖动**（±25% 随机化，防止惊群效应）
- **Token Bucket 模型**：按 token/秒 速率补充虚拟桶

### 第四层：Partial Functionality（部分功能模式）

将能力分为三档：

- **Essential**（必须保住）：语言推理 → 始终可用（本地模型）
- **Enhanced**（增强但可降级）：实时搜索 → 禁用，标注信息可能过时
- **Optional**（可选可跳过）：图像生成 → 跳过并说明限制

**核心原则**：永远向下游消费者**明确声明降级状态**。

## 三、Agent 不稳定性的根因

来自 Galileo AI（Microsoft Research Victor Dibia 总结）：

1. **非确定性 LLM 规划行为** —— 相同输入产生不同执行路径
2. **指数级编排复杂度** —— 每个 Agent 新增通信路径和冲突场景
3. **级联多步工作流失败** —— 早期工具选择错误累积传导
4. **不当终止条件** —— 死循环重试或继续处理已完成任务
5. **自治级别不当** —— 过低需频繁人工介入，过高失控
6. **共享基础模型依赖** —— 底层 LLM 出问题时所有依赖 Agent 同时失败

## 四、对我们 Hermes 系统的直接启示

### 已有的可强化项

1. **antigravity-model-failover skill** → 已实现模型级 fallback，但缺少 Circuit Breaker 状态机（只有简单重试）
2. **agent-reliability-engineering skill** → 已有七层降级架构理论，但 Zylos 的四级升级层次可以补充为具体实现模板
3. **auto-diagnose-fix cron** → 当前只检测 timeout，可以增加 GDS/RDC 维度的日志分析

### 建议改进

- **为 cron job 添加 Circuit Breaker**：连续失败 3 次的 cron 自动进入 15 分钟冷却期，而不是每次都重试浪费配额
- **可靠性衰减监控**：跟踪同类型任务在不同执行长度下的成功率，建立 RDC 曲线
- **Memory scaffold 审慎使用**：研究证明 memory scaffold 普遍损害长时序表现，应评估当前 auto-memory-keeper 对长任务的实际影响
- **VAF 作为能力指标**：高方差不再等于不稳定，前沿模型天然高 VAF，应在评估时区分"能力签名"和"真实不稳定"

## 五、代码模式速查

### Circuit Breaker 核心逻辑

```python
class CircuitBreaker:
    def __init__(self, failure_threshold=3, cooldown=300, extended_cooldown=900):
        self.failures = 0
        self.state = "CLOSED"
        self.opened_at = None
        self.flap_count = 0

    def can_execute(self):
        if self.state == "OPEN":
            if time.time() - self.opened_at > self._current_cooldown():
                self.state = "HALF_OPEN"
                return True  # probe
            return False
        return True

    def record_failure(self):
        self.failures += 1
        if self.failures >= self.failure_threshold:
            self.state = "OPEN"
            self.opened_at = time.time()
            self.flap_count += 1

    def _current_cooldown(self):
        # Flapping detection: use extended cooldown
        return self.extended_cooldown if self.flap_count > 1 else self.cooldown
```

### 指数退避 + 抖动

```python
async def retry_with_backoff(fn, max_retries=5, base=1.0, cap=60.0):
    for attempt in range(max_retries):
        try:
            return await fn()
        except RateLimitError as e:
            if attempt == max_retries - 1: raise
            delay = min(base * (2 ** attempt), cap)
            jitter = delay * 0.25 * (2 * random.random() - 1)
            await asyncio.sleep(delay + jitter)
```
