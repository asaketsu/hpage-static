# 飞机结构智能体框架主体研究 — 可扩展知识与可嵌套Agent体系的设计方向内容与流程

#飞机结构设计 #结构智能体 #多Agent框架 #知识驱动 #可扩展知识 #可嵌套Agent #对象级Agent #弹簧设计 #连接件设计 #缓冲器设计 #起落架 #独立验证 #覆盖度证书 #知识图谱 #RAG #设计契约 #插件架构 #CCAR25 #适航 #研究框架 #技术路线 #LLM工程 #CAD集成

> **任务来源**：用户研究命题——"针对飞机结构智能体技术研究，开展框架主体研究：知识可扩展、框架可嵌套多个 agent（可扩展）、agent 可独立针对某类对象（弹簧、连接件、缓冲器等）进行设计辅助、最后可单独验证和评价"
> **调研基础**（2026-08-19 实抓）：国外 4 项一手工作（arXiv 2511.03179 知识引导多 Agent 工程设计 / arXiv 2605.28978 VFEAgent 多模态 FEA / ideas-um OpenAeroStruct LLM Agent / Verification-driven closed-loop 规范合规结构设计）+ 国内知识库与型号工程方法论 + 本仓 struct-gen-agent 已有底座（CCAR-25/27 三规范、6 类零件、10 步管线）
> **一句话**：四层主体框架——**知识层（活台账）→ 编排层（框架主体）→ 对象 Agent 层（插件式可嵌套）→ 独立验证层（覆盖度证书）**；研究按 6 个方向、3 期路线展开

## 一、内容整理

### 1. 问题定义与设计要求（用户命题的工程化翻译）

| 要求 | 工程化含义 | 验收标准 |
|---|---|---|
| **知识可扩展** | 规范改版/新零件类型/新材料加入不动框架——知识是数据不是代码 | 新增一类对象（如新规范或新材料）只改数据文件与配置，零代码修改 |
| **框架可嵌套多个 Agent（可扩展）** | Agent 是插件：注册即用、可独立开发、可组合嵌套（Agent 内还可含子 Agent） | 新对象 Agent 按 SDK 模板开发，注册后主框架自动路由 |
| **Agent 独立针对某类对象设计辅助** | 每 Agent 只服务一类对象（弹簧/连接件/缓冲器/长桁/框…），封装该对象的全部设计知识 | 对象 Agent 之间零耦合，可单独部署/测试/升级 |
| **最后可单独验证和评价** | 验证层与设计层**分离**——独立复算、机检门控、可量化评分 | 设计 Agent 输出必须过独立验证 Agent 的机检+复算才能交付 |

**对象域说明**：弹簧（起落架/操纵系统弹性元件）、连接件（接头/角片/紧固件连接）、缓冲器（起落架减震支柱/油气式缓冲器）——典型"机构-结构交叉部件"，载荷工况复杂、规范条款密集、参数化程度高，是 LLM 辅助设计的理想切入点（比整体结构小、比标准件大）。

### 3. 框架总体设计（主体：四层架构）

```
┌─────────────────────────────────────────────────────────────┐
│ L4 独立验证与评价层（Verifier 体系，与设计层物理分离）          │
│   机检门（量纲/残差/条款核对/MS≥0）→ 独立路径复算 → 评测集回归  │
│   → 覆盖度证书（✓含阈值 + ✗留人判断）                         │
├─────────────────────────────────────────────────────────────┤
│ L3 对象 Agent 层（插件式可嵌套）                               │
│   弹簧Agent │ 连接件Agent │ 缓冲器Agent │ 长桁Agent │ …│ 新对象 │
│   统一契约：DesignSpec → DesignReport（含中间量与假设声明）      │
│   Agent 内部可再嵌子 Agent（检索Agent/计算Agent/建模Agent）      │
├─────────────────────────────────────────────────────────────┤
│ L2 编排层（框架主体）                                          │
│   主编排Agent（需求解析/路由/生命周期）+ 工具总线 + 协调机制      │
│   需求→载荷→选型→验算→可靠性→连接→优化→建模→验证（9 步可裁剪）   │
├─────────────────────────────────────────────────────────────┤
│ L1 知识层（可扩展的活台账）                                     │
│   知识图谱（条款/材料/截面/工况/案例）+ RAG（规范原文/报告）      │
│   + 台账（四级分类/责任人/有效期/技术状态）+ 评测集（真实问题）   │
└─────────────────────────────────────────────────────────────┘
```

**层间唯一通过契约通信**（Cumora 教训：I/O 面与 brain 解耦）：L2→L3 传 `DesignSpec`，L3→L4 传 `DesignReport`，L4→用户传 `VerifiedDelivery`（报告+证书）。

### 4. L1 知识层设计（知识可扩展的机制）

| 子模块 | 内容 | 可扩展机制 |
|---|---|---|
| **结构化知识库** | 材料库（2024-T3/7075-T6/Ti-6Al-4V/复材）、截面库（型材/参数族）、紧固件库（铆钉/螺栓）、工况库（载荷谱/边界条件模板）、弹簧/缓冲器参数库（刚度曲线/行程/充气压力） | JSON/数据库存储+`_` 前缀元数据过滤（struct-gen 已验证模式）；**新增对象=新增一组数据文件** |
| **知识图谱** | 规范条款图谱（CCAR-25.303→安全系数→材料许用→MS 公式的引用链）、零件-失效模式-验算方法图 | Graph Ontologist Agent 增量构建（借鉴 2511.03179）：新文献/新规范进来自动抽实体入图 |
| **RAG 层** | 规范原文/设计准则/历史计算报告/经验教训的条款级切分索引 | 条款级切分（检索最小语义单位=条款）；密级/受控过滤在检索层；强制引用角标 |
| **台账与治理** | 四级分类（适航规范/企业标准/型号工程/经验教训）+ 责任人 + 有效期 + 技术状态（现行/作废/冻结） | **作废不删除**（历史型号查询）；规范改版触发增量重索引；评测集防污染（禁入训练） |
| **评测集** | 真实设计问题集（事实型/检索型/判断型 5:3:2 + 10% 边界陷阱题） | 每季度从使用日志补题；回归纪律：检索/模型/提示词变更先跑全量评测 |

**知识扩展的操作定义**：加入"某新型缓冲器设计准则"= ①台账登记（责任人/有效期/密级）②RAG 入库（条款切分）③图谱挂节点（关联既有失效模式）④评测集补 3-5 题——**四步全是数据操作，零代码修改**。

### 5. L3 对象 Agent 层设计（可嵌套可扩展的机制）

**统一契约**（每个对象 Agent 必须实现）：

```python
class ObjectDesignAgent(ABC):
    spec: DesignSpec        # 输入：规范体系+对象类型+工况+材料+约束
    @abstractmethod
    def generate_candidates(self) -> list[Candidate]: ...
        # 候选生成（参数族扫描/知识图谱推荐/蓝图模板实例化）
    @abstractmethod
    def verify_check(self, c: Candidate) -> list[StressCheck]: ...
        # 对象特定验算（MS/稳定性/疲劳/行程/刚度）——每条含公式出处
    @abstractmethod
    def export_model(self, c: Candidate) -> ModelArtifact: ...
        # 参数模型/CAD 脚本（CATIA/nTop/STEP）
```

**三个示例对象 Agent 的职责域**：

| Agent | 覆盖对象 | 典型验算项 | 知识依赖 |
|---|---|---|---|
| **弹簧 Agent** | 起落架/操纵系统圆柱螺旋弹簧、碟簧、扭杆 | 刚度/剪切应力/稳定性（屈曲）/共振频率/疲劳（Goodmann）；行程-载荷曲线 | 材料库+弹簧设计准则（HB/GJB）+工况库 |
| **连接件 Agent** | 接头/角片/耳片、铆接/螺接连接 | 挤压/剪切/净截面/拉脱；钉群载荷分配（弹性/塑性重分布）；疲劳细节额定值（DFR） | 紧固件库+连接设计手册+载荷谱 |
| **缓冲器 Agent** | 油气式/橡皮式起落架缓冲器 | 能量吸收/效率系数/行程/过载曲线（缓冲过程仿真）；充气压力/油孔阻尼；落震分析工况 | 缓冲器参数库+落震试验数据+CCAR-25.723/725 条款 |

**嵌套机制**：对象 Agent 内部可挂**子 Agent**——检索子 Agent（问知识层）、计算子 Agent（调求解器）、建模子 Agent（出 CAD）；子 Agent 同样走注册表。主框架对嵌套层数设上限（建议 2 层）防失控。

**扩展操作定义**：新增"翼肋 Agent"= ①建 `rib_agent.py` 继承契约 ②注册 `@register_object_agent("rib")` ③数据文件入知识层 ④评测集补题——主框架零改动（struct-gen 的 components/codes 双注册表已验证此模式）。

### 6. L2 编排层设计（框架主体）

| 组件 | 职责 | 机制借鉴 |
|---|---|---|
| **主编排 Agent** | 需求解析（NL→DesignSpec）、对象路由（查注册表）、生命周期管理（9 步管线可裁剪）、异常处理（缺参先问不瞎猜） | OpenAeroStruct"缺信息先问"+struct-gen 10 步管线 |
| **工具总线** | 求解器（解析公式/FEA）、优化引擎（贝叶斯/Pareto）、CAD 桥（CATIA COM/nTop CLI）、绘图——全部 local subprocess+dry-run 降级 | struct-gen"绝不做远程通信层"+ARM 自动 dry-run |
| **协调机制** | 多 Agent 并发时的防碰撞：参数修改经 freshness 检查（设计状态版本号）；评审与设计分离（评审 Agent 不由设计 Agent 兼任） | Cumora"执行/评判分离"+AGENTS.md 质量门禁 |
| **人机接口** | 工程师在环检查点（需求确认/候选筛选/最终签审）；每步输出 <5KB 渐进落盘 | 小批量推进铁律 |

### 7. L4 独立验证与评价层设计（单独验证评价的机制）

**三道门 + 一张证书**（物理 AI 裁判层的三层架构移植）：

| 门 | 内容 | 机检/人检 |
|---|---|---|
| **①确定性机检** | 量纲一致、解代回方程算残差（范数<阈值）、规范条款号与原文核对（引用角标逐条比对）、MS≥0、单位制转换核验 | **全机检，秒级**；LLM 伪造的条款号/数值在此拦截 |
| **②独立路径复算** | 隔离上下文的第二 Agent 用不同方法重算（如弹簧：能量法 vs 刚度积分法；连接件：弹性分配 vs 塑性重分布）；比对中间量（不只终值）；假设清单重叠度检查 | 机检+专家抽检；差异>阈值标记待人工 |
| **③适用域声明核对** | 设计报告必须声明近似/适用区间/忽略项；反向机检（声明非相对论→查推导有没有用相对论色散的同构检查：声明线弹性→查有没有超屈服） | 机检声明一致性；缺口留人判断 |
| **覆盖度证书** | 输出：✓已验证项（含阈值与复算方法）+ ✗未验证项（留工程师）+ 引用清单（条款级）——**不给裸"通过"** | 交付物的一部分，随报告归档 |

**评价体系**（对 Agent 本身，不是对设计）：
- **设计质量指标**：验算全过率（MS≥0 比例）、候选多样性（Pareto 前沿覆盖）、知识引用准确率（条款核对通过率）
- **效率指标**：单对象设计耗时 vs 人工基线、工程师介入次数
- **回归基准**：形状对偶场景（如"该轻量化时轻量化"vs"该保守时保守"）+ 评测集全量回归——任何 Agent/知识/提示词变更先跑基准，分数不降才许上线
- **归零机制**：验证发现的设计错误进错误案例库（根因-措施-举一反三），触发评测补题

### 8. 研究方向分解（6 个方向）

| # | 方向 | 核心问题 | 关键产出 |
|---|---|---|---|
| **D1** | **可扩展航空结构设计知识体系** | 规范/材料/截面/工况/案例如何组织成"加数据不加代码"的活知识？图谱如何增量构建？ | 四级分类台账规范、条款级知识图谱 schema、RAG 条款切分方案、知识扩展 SOP（四步零代码） |

| **D5** | **工程工具链集成** | 解析计算/FEA/优化/CAD 如何以 local+dry-run 模式接入？图纸输入（VFEAgent 式多模态）如何进需求解析？ | 工具适配层（求解器/CAD/优化）、多模态需求解析原型 |
| **D6** | **人机协同与领域适配** | 工程师检查点设在哪？知识专员如何运营台账？置信度如何呈现（证书化）？ | 人机交互流程、运营手册（复用八件套）、 pilots 反馈闭环 |

### 9. 研究内容详解（按层展开的关键技术）

**知识层关键技术**：
1. 条款级切分与检索（"25.303"精确命中+语义混合检索+密级前置过滤）
2. 知识图谱增量构建（Graph Ontologist 模式：LLM 抽取+人工校验+版本化）
3. 技术状态联动（规范改版/构型冻结触发知识状态迁移与重索引）
4. 评测集工程（真实问题采集+标准答案+及格线+防污染）

**Agent 层关键技术**：
1. 候选生成策略（参数族扫描×知识图谱推荐×蓝图实例化的混合）
2. 对象特定验算库（每类对象的失效模式→验算函数→公式出处三元组）
3. 假设显式化（每步推导携带假设清单，供 L4 反向核对）
4. dry-run 降级（无 CAD/求解器环境输出参数 JSON，管线不中断）

**验证层关键技术**：
1. 残差机检（解代回+范数阈值写进证书）
2. 独立路径生成（方法对偶表：每类对象预定义 2+ 种等价方法）
3. 引用核对脚本（角标→原文逐条自动比对，幻觉率月报）
4. 覆盖度证书生成器（✓/✗/阈值/方法/引用五字段结构化输出）

### 10. 技术流程（端到端主线）

```
【输入】自然语言需求（"设计某机起落架油气式缓冲器，CCAR-25，落震工况…"）
   ↓ L2 主编排：需求解析 → DesignSpec（缺参提问清单返回用户）
   ↓ L2 路由：查注册表 → 缓冲器 Agent
   ↓ L3 缓冲器 Agent：
   │   ① 知识检索：CCAR-25.723/725 条款+缓冲器设计准则+相似型号案例
   │   ② 候选生成：参数族（行程/初压力/油孔面积）×蓝图模板 → 3-5 候选
   │   ③ 验算：能量吸收/效率系数/过载曲线/落震仿真（工具总线）
   │   ④ 优化：Pareto（重量/吸能/行程）
   │   ⑤ 建模：参数模型+CAD 脚本（dry-run 可降级）
   ↓ DesignReport（候选+验算+假设清单+引用角标）
   ↓ L4 独立验证：
   │   机检门：量纲✓ 残差 3e-9<1e-8✓ 条款核对 8/8✓ MS≥0✓
   │   独立路径：能量法复算 vs 过程仿真复算 → 中间量偏差 2%<5%✓
   │   适用域：声明"线弹性小变形/忽略摩擦" → 反查推导一致✓
   │   证书：✓12 项（含阈值）+ ✗2 项（疲劳谱待试验数据/胶接细节）
   ↓ VerifiedDelivery（报告+证书+模型）→ 工程师签审检查点
   ↓ 使用日志 → 评测集补题 / 错误案例库（归零）
```

| 维度 | 要点 |
|---|---|
| 一句话 | 四层主体框架：知识层（活台账，加数据不加代码）→ 编排层（路由+工具总线+9 步管线）→ 对象 Agent 层（插件注册、统一契约、可嵌套）→ 独立验证层（三道门+覆盖度证书） |

## 四、趋势判断

1. **工程设计的 LLM 化正从"整体优化"下沉到"对象级辅助"**：OpenAeroStruct（整体气动结构）→ AirfoilAgent（翼型）→ 本框架（弹簧/连接件/缓冲器）——粒度越细，知识封装越深、验证越可行，落地越近
2. **验证驱动闭环会成为工程 Agent 的准入门槛**：VFEAgent 的 verification-first、code-compliant 框架的闭环、物理 AI 裁判层的覆盖度证书——"生成后能被独立证明"正在从加分项变成必要条件（适航场景尤其如此）
3. **知识图谱+RAG 双轮是工程知识层的标配形态**：2511.03179 用图谱管结构关系、RAG 管原文条款——图谱答"怎么关联"、RAG 答"原文是什么"，两者互不可替代
4. **对象 Agent 的插件生态是框架价值的核心**：框架本体（编排+验证）一旦稳定，价值增长全靠对象 Agent 数量——类似 mathlib 之于 Lean（库的竞赛），先定契约再攒库
5. **国内机会在"方法论×工程数据"的结合处**：八件套式知识治理+型号工程数据积累是国内的独特资产，框架主体研究恰好是把资产变成能力的接口
6. **人机协同的检查点设计决定采纳率**：全自动不是目标——工程师签审检查点+覆盖度证书的显式缺口呈现（哪些验了/哪些没验）才是航空场景的正确形态

## 七、指南分析

**框架主体速查卡**

```
四层：L1 知识（活台账+图谱+RAG+评测集）
     L2 编排（路由+工具总线+9步管线+协调）
     L3 对象Agent（插件注册+统一契约+嵌套≤2层）
     L4 独立验证（机检门→独立路径→适用域→证书）
契约：DesignSpec（入）→ DesignReport（中间）→ VerifiedDelivery（出）
扩展：知识=四步数据操作零代码；Agent=SDK+@register 注册即用
验证：机检秒级全量 → 独立路径复算 → 证书留✗缺口给工程师
纪律：验证驱动闭环（不过即回炉）/ 执行评判分离 / 签审在人
```

**五条设计铁律（背下来）**
- 层间只传结构化契约，绝不传自然语言（LLM 只在层内）
- 知识扩展=数据操作，新对象零代码；Agent 扩展=注册即用，主框架零改动
- 能机检的绝不人检，能人检的绝不 LLM 判——验证层与设计层物理分离
- 证书永远显式留 ✗ 缺口——裸"通过"在航空场景等于撒谎
- 缺参数先问不瞎猜（OpenAeroStruct 纪律）；管线每步 <5KB 渐进落盘

**何时重读本篇**：立项写申报书时（方向/路线/成果三表）；框架设计评审时（四层架构+契约）；新对象 Agent 开发时（SDK 模板+扩展 SOP）；验证体系设计时（三道门+证书）；与国外工作对标时（现状表+趋势判断）。
