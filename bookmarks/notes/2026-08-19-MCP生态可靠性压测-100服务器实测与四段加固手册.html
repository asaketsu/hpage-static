一、内容整理

1.1 研究设计

首个 MCP 生态全面可靠性研究：100 个生产级 MCP server × 12 任务族 × 12,000 次试验 × 约 60,000 次工具调用（2026-02 至 04 对生产端点实测）。

  • 样本：Smithery 44 个 + Glama 28 个 + Anthropic 参考 12 个 + 自托管 16 个，按 registry/类别/star 数分层抽样，剔除纯 demo 和 12 个月未更新的僵尸
  • 任务族：file-system / web-search / calendar / email / db-query / code-exec / image-gen / browser-automation 等 12 类，每类用该类别的主操作（FS: read/write/list/stat/glob…）
  • 负载：每任务 50 次试验，并发梯度 1→2→4→8→16→32
  • 通过判定：30 秒内返回 schema 合法响应
  • 失败五分类：schema 不匹配 / 超时 / auth配额 / 上游 API 故障 / MCP 协议 bug

1.2 核心数字

  • 中位通过率 71%：孤立看可容忍，复合看是灾难——0.71⁵ ≈ 18%，5 连工具链端到端成功率仅 18%，10 连仅 3%
  • 分布双峰：top decile ≥95%，bottom decile 38%——聚成"能用/不能用"两堆，中间态少。差距是结构性的不是随机的
  • 延迟尾主导：P50 320ms / P95 1,840ms（5.7×）/ P99 6,200ms。10+ 连调用几乎必然撞上 P95 事件；无显式超时处理的 server P99 可无限拉长
  • 并发衰减：中位 server 从 1→32 并发通过率掉 18 个百分点；最差掉 40+；top decile 几乎持平（≤3 点）——并发平坦度是"为生产而生"的最干净信号
  • 类别差异 42 个百分点：file-system 89% 最高（简单+确定），browser-automation 47% 最低（依赖 DOM 稳定性）——浏览器工具天然脆弱，必须配重试/降级/错误预算

1.3 失败归因

~3,500 次失败试验的分布：

  • schema 不匹配 38%（最大单因）：绕过 Zod/Pydantic/JSON-Schema 校验手搓 API wrapper 是重灾区
  • 超时 24%
  • auth/配额 19%
  • 上游 API 故障 12%
  • MCP 协议 bug（JSON-RPC 格式错/缺必填字段）7%

star 数与通过率零相关：样本中 star 最高的 server 通过率排第 41；Smithery 最热 server 排 27。流行度奖励的是"有哪些工具"（新颖性），不是"工具能不能用"（可靠性）。

1.4 四段加固手册（top decile 无一跳步）

  1. Schema 先行：typed schema 在边界上拦住大多数 bug——typed schemas / idempotency / explicit cancellation 是 top decile 共有的三特征，bottom decile 几乎全缺
  2. 幂等第二：让重试变安全
  3. 取消处理第三：约束尾延迟
  4. 每工具配额第四：保护上游 API

1.5 生态规模背景（Adoption Statistics 同站姊妹篇）

  • 官方 registry latest 记录 9,652 个（含历史版本 28,959），Anthropic 2025-12 官宣 10K+ 活跃公开 server，月 SDK 下载 9700 万+
  • GitHub mcp-server topic 仓库 15,926 个；modelcontextprotocol/servers 86K stars
  • 企业生产：Stacklok 2026 调研——29% 受访组织有限生产 + 12% 广泛生产（替换了此前无来源的"78% 企业采用"夸大宣传）
  • 治理归属：Anthropic 已把 MCP 捐给 Linux 基金会 Agentic AI Foundation（AAIF），中立托管
  • 协议演进：传输层 stdio + Streamable HTTP（旧 HTTP+SSE 已废弃）；server 能力 resources/prompts/tools，client 能力 sampling/roots/elicitation
  • 安全侧：NSA 2026-06 发布 MCP 安全设计考虑文档；OWASP 有对应条目

二、查询拓展

2.1 为什么 P95 5.7×P50 对 Agent 是致命的

人类用户对 300ms 和 1800ms 的差异感知有限，但 Agent 工作流是串行放大器：每次工具调用的延迟分位数相乘。链长 5+ 时 P95 就是常态事件而非尾部事件。这解释了为什么"中位数很快"的 server 在真实 Agent 负载下表现崩塌——测均值掩盖了尾部，而 Agent 只活在尾部。

2.2 与 TradeTrap MCP 劫持的互补（同日笔记）

本篇测非对抗性可靠性（server 自己坏没坏），TradeTrap 测对抗性可靠性（被主动攻击会怎样）。两者合起来是 MCP 工具链风险评估的完整两轴：意外故障 × 恶意操纵。schema 校验 38% 的失败占比恰好也是 TradeTrap 假 MCP 攻击能得手的温床——不做响应校验的 server，既容易被自己搞坏，也容易被对手利用。

2.3 browser-automation 47% 的含义

DOM 依赖使浏览器工具天然脆弱。与本仓 experience 一致：X/Twitter 抓取链 web_extract 直抓 → Playwright 真浏览器 → web_search 补评论的三级降级链，本质就是给 47% 类工具配的"重试+降级+错误预算"。该研究的工程结论反向验证了本仓降级链设计的必要性。

三、归纳总结

3.1 可靠性分级速查框架

通过率语义（Agent 工具链视角）:
≥95%  top decile——可进生产链
 71%  生态中位——5连链18%,不可依赖
 38%  bottom——单工具即瓶颈
类别基线:
 file-system 89% | browser 47% (差42pp)
延迟真相: P50 320ms 只是门票,P95 1840ms 才是账单

3.2 选型 rubric（研究者的评估清单直接可用）

  • 每 server 跑 12 任务族主操作 × 50 试验，记录通过率 + P50/P95/P99
  • 并发梯度 1→32 看衰减斜率（>18pp = 未为生产设计）
  • 检查三特征：typed schema / 幂等 / 取消处理——缺一即降档
  • star 数不作为信号（与通过率零相关）

3.3 核心洞察链

  1. 复合可靠性是 Agent 时代的核心约束：单工具 71% 在人类场景够用，在 5-20 连 Agent 链里是生产阻断项——需要的单工具基线是 95-99%
  2. 双峰分布说明差距可消除：不是"运气"是"工程决策清单"——四段手册全部可执行
  3. 流行度≠可靠性：生态激励错位（star 奖励新颖性），选型必须自测
  4. 最弱链=系统可靠性：一个 47% 的浏览器工具把整条链拖到 47%

四、趋势判断

趋势1：MCP server 可靠性认证/评级会商品化

依据：研究方已把内部选型 rubric 产品化发布；registry 治理（信任/策展/僵尸包清理）是 2026 官方明确议题；star 失效后市场需要新信号。

趋势2：Agent 工具链需要"错误预算"设计

依据：浏览器类 47% 基线 + 尾部延迟主导，迫使 Agent 架构把 per-tool 错误预算（retries/fallbacks/timeouts）作为一等公民——本仓 search-fallback-chain 是先例形态。

趋势3：企业 MCP 采用进入治理期

依据：Stacklok 41% 生产渗透 + NSA 安全指南 + AAIF 中立托管——从"能不能连"转向"registry 审批/审计层/命名空间信任"，写操作闸门是下一个战场。

趋势4：typed schema 成为 MCP server 事实准入门槛

依据：38% 失败源于 schema 缺失且是"最易预防"类——ROI 最高的加固步，生态自然演化方向。

五、关联分析

5.1 与 Hermes 工具链的关联

本仓 zai MCP（web_search/webReader/zread）+ mcporter + native MCP 客户端构成工具链。直接可操作项：①给高频使用的 MCP server 建通过率台账（复用本研究的 50 试验法小样本版）；②搜索降级链已覆盖浏览器类脆弱性，符合 47% 基线的工程应对。

5.2 与 Agent 工程笔记群的关联

  • TradeTrap交易Agent可靠性压测——对抗轴 vs 本篇意外故障轴，双轴合璧
  • 企业Agent技术选型-全自治vs确定性DAG的混合架构共识与落地设计——混合架构的可靠性论据：确定性通道对工具链尾部的容忍度更高
  • AI落地两道门-权限管理与证据门禁——证据门禁即"响应校验"，与 schema 校验同理

5.3 与量化栈的关联

iron_picks.py 等脚本走 tushare 直连不走 MCP，但若未来接入行情 MCP server，本研究的选型 rubric 直接适用——行情数据工具链的可靠性要求实际上高于 95%（每交易日多次调用复合）。

七、行动启示

  • 给本仓 MCP server 建可靠性台账（P1）：对 zai search/reader、memorygraph 等高频 server 跑小样本通过率测试（每工具 10-20 试验），记录 P50/P95，低于 90% 的挂降级链
  • typed schema 自查（P2）：本仓自研脚本类工具（iron_rules_engine 等）补 JSON schema 输出校验，防"上游坏数据静默污染"
  • 浏览器类工具一律配降级（已实现，维持）：web-content-extraction-recipes 的多策略链是对 47% 基线的正确姿势
  • 并发平坦度纳入 cron 设计（P2）：本仓多 cron 并发场景，工具调用错峰已有实践（智谱 API 并发=1 约束），可推广为通用规则

八、拓展应用推荐

  • Agent 平台选型：直接搬四段手册评估第三方 MCP server——schema/幂等/取消/配额四查，缺二即拒
  • 自研 server 作者：按四段顺序加固，typed schema 投入产出比最高
  • 研究延伸：把通过率×攻击面做二维矩阵（本篇 × TradeTrap），给每个常用工具定位风险象限
  • 本仓落地：给 search-fallback-chain 补"通过率台账"数据源——降级触发不再只凭错误类型，还看历史通过率

九、指南分析

研究附完整方法论可复刻：分层抽样（registry×类别×star）→ 每类别定义主操作任务集 → 50 试验×6 并发梯度 → schema 合法+30s 双判据 → 失败五分类。落地最小版：for tool in high_freq_tools: run 10 trials, record pass_rate/p95; if pass_rate<0.9: attach fallback。对本仓的指南价值：cron 任务里工具调用失败重试策略（当前 1 次）可升级为"按工具历史通过率自适应重试次数"——71% 工具重试 3 次可达 ~97.6%，95% 工具重试 1 次即 99.75%。
