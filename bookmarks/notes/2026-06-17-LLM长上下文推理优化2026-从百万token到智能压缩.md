## 一、核心发现（6 条）

### 发现 1：上下文窗口已达 10M Token，但"声称"与"实际"差距巨大

2026 年各模型上下文窗口已呈数量级跨越：

| 提供商 | 模型 | 声称窗口 | 备注 |
|--------|------|----------|------|
| Meta | Llama 4 Scout | **10M** | 行业最大，10 倍跃升 |
| Google | Gemini 3.0 Pro | **2M** | 多模态原生处理 |
| Anthropic | Claude Sonnet 4 | **1M** | 从 200K 升级 |
| OpenAI | GPT-5.2 | **400K** | 输出窗口 128K |
| Meta | Llama 4 Maverick | **1-2M** | 视频/代码库处理 |

**关键现实**：
- 模型通常在声称限制的 **30-40% 之前就开始失效**——200K 模型在 ~130K 处不可靠
- 性能下降往往是**骤降而非渐降**，难以预测何时崩溃
- 约 **2/3 的测试模型**无法在仅 2K token 中找到一个简单句子
- 通过"大海捞针"测试 ≠ 真正的长上下文理解能力

### 发现 2：DuoAttention 发现 Attention Head 的"二八法则"——仅少量 Retrieval Heads 需要全量 KV Cache

ICLR 2025 论文 DuoAttention（MIT Han Lab）的核心洞察：

**Attention Head 分类**：
- **Retrieval Heads（检索头）**：少数关键 Head，负责长距离信息检索，需要全量 KV Cache
- **Streaming Heads（流式头）**：其余 Head，主要关注近端 token 和 attention sink，无需全量 KV Cache

**优化方案**：
- 仅对 Retrieval Heads 保留完整 KV Cache
- 对 Streaming Heads 使用**固定长度的轻量 KV Cache**
- 通过合成数据的优化算法精确识别 Retrieval Heads

**量化效果**：
- MHA 模型：内存减少 **2.55×**，解码加速 **2.18×**，预填充加速 **1.73×**
- GQA 模型：内存减少 **1.67×**，解码加速 **1.50×**，预填充加速 **1.63×**
- 结合量化：Llama-3-8B 在**单张 A100** 上实现 **333 万 token** 上下文

### 发现 3：Agentic 负载消耗 100×-1000× 于聊天负载，催生硬件-软件协同设计

PLENA 论文（arXiv 2509.09505）揭示了 Agent 推理的独特特征：

- **Agent 负载 vs 聊天负载**：Agent 平均消耗 **100× 更多 token**，极端情况达 **1000×**
- Agent 需要处理完整网页 DOM、复杂工具调用轨迹、大规模代码库等超长输入
- 两大**内存墙**：带宽墙（off-chip memory traffic）和容量墙（KV Cache 存储）

**PLENA 系统三条优化路径**：
1. **Pathway 1**：Flattened Systolic Array 架构——优化不规则内存访问模式
2. **Pathway 2**：非对称量化方案——attention 和 FFN 使用不同精度
3. **Pathway 3**：原生 FlashAttention 支持

**性能**：比 A100 GPU 吞吐高 **2.23×**，比 TPU v6e 高 **4.70×**，能效高 **4.04×**

### 发现 4：注意力机制加速进入"稀疏化 + 硬件对齐"双轨时代

2025-2026 年注意力优化的关键进展：

| 技术 | 来源 | 核心创新 | 加速比 |
|------|------|----------|--------|
| **FlashAttention-3** | Stanford | H100 异步+低精度 | 1.3 PFLOPs/s |
| **Star Attention** | NVIDIA | 星型拓扑长序列推理 | **11×** |
| **DeepSeek NSA** | DeepSeek | 原生可训练稀疏注意力 | 硬件对齐 |
| **MHA2MLA** | 复旦 | Multi-Head → Multi-Latent Attention | 经济推理 |
| **RetrievalAttention** | - | 向量检索替代全量 attention | 训练无关 |
| **Ring Attention** | UC Berkeley | 分布式环形拓扑 KV 传递 | 跨 GPU 扩展 |

**关键趋势**：从"让 attention 更快"到"让 attention 更稀疏"——不是计算所有 token pair 的注意力，而是智能选择最相关的子集。

### 发现 5：分层上下文管理成为 Agent 系统标配

现代 Agent 系统采用操作系统启发的**多级存储架构**：

**Tier 1 — 活动上下文（主存）**：
- 固定大小的系统指令 prompt
- 当前推理的工作上下文
- FIFO 消息缓冲区（近期交互）

**Tier 2 — 外部上下文（外存）**：
- Recall 存储：可搜索的文档/日志数据库
- Archival 存储：基于向量的长期记忆
- 语义搜索检索

**上下文感知 RAG 的效果**：
- 在减少上下文大小 **68%** 的同时保留 **91%** 的关键信息
- 关键技术：混合检索（向量 + BM25）+ 重排序 + 查询扩展 + CRAG

### 发现 6：2026 共识——"智能胜于规模"，上下文窗口将趋平

行业趋势明确指向：
- 上下文窗口的扩张将**趋平**——10M token 已接近边际效益递减点
- 焦点转向**推理时计算（Inference-Time Scaling）**：动态调整思考深度
- **混合方法**成为主流：压缩 + 缓存 + 记忆增强系统的组合
- **Prompt Caching** 可节省 **90%** 的重复内容成本
- **TTT-E2E（Test-Time Training）**：2M 上下文实现 **35×** 加速
- Claude 超 200K token 的定价（$6/$22.50 per M tokens）使盲目长上下文在经济上不可持续

## 二、KV Cache 优化技术深度分析

### 2.1 问题本质

KV Cache 的内存消耗公式：
```
KV_Cache = 2 × n_layers × n_heads × head_dim × seq_len × batch × dtype_size
```

- 1M token 的 KV Cache 需要约 **15GB**（单用户）
- Attention 计算量随序列长度**二次增长**
- 1M token 的 attention 计算量是 4K 的 **250×**

### 2.2 优化策略全景

```
KV Cache 优化
├── 压缩（Compression）
│   ├── 量化：FP16 → INT8 → INT4
│   ├── 剪枝：Token-level / Channel-level
│   └── 蒸馏：KV → 低秩近似
├── 驱逐（Eviction）
│   ├── LRU：最近最少使用
│   ├── Attention Sink 保护
│   └── DuoAttention：Head 级别差异化
├── 分层存储（Tiered Storage）
│   ├── GPU HBM（热数据）
│   ├── CPU DRAM（温数据）
│   └── SSD/NVMe（冷数据）
└── 架构创新（Architecture）
    ├── MLA（Multi-Latent Attention）
    ├── NSA（Native Sparse Attention）
    └── Ring/Context Parallelism
```

### 2.3 DuoAttention 实现细节

**Retrieval Heads 识别算法**：
1. 生成合成数据（长文档 + 事实性问题）
2. 对每个 Head 测量其 attention pattern 对远程信息的检索能力
3. 将 Head 分为 Retrieval（高检索分数）和 Streaming（低检索分数）
4. 仅对 Retrieval Heads 计算和存储全量 KV

**Streaming Heads 优化**：
- 使用固定长度窗口（如 1024 tokens）的 KV Cache
- 结合 Attention Sink 机制保留开头 token
- 由于这些 Head 的信息需求是局部的，精度损失可忽略

## 三、长上下文 Agentic 推理的硬件视角

### 3.1 PLENA 硬件-软件协同设计

PLENA 针对的**核心矛盾**：Agent 推理的 memory-bound 特性

**传统 GPU 的局限**：
- Attention 的不规则内存访问模式与 GPU 的规则矩阵乘法优化不匹配
- KV Cache 的逐 token 增长导致频繁的 off-chip memory 访问
- 计算-内存比（Arithmetic Intensity）极低，GPU 利用率不足

**PLENA 的三层解法**：
1. **Flattened Systolic Array**：打破传统 2D 脉动阵列的规则性，支持稀疏和非连续访问
2. **非对称量化**：attention score 用 FP16（精度敏感），KV Cache 用 INT4（容量敏感），FFN 用 INT8（均衡）
3. **原生 FlashAttention**：fused kernel 避免中间结果写回 HBM

### 3.2 对 Jetson Orin 平台的启示

PLENA 的发现对 Jetson 边缘推理有直接参考价值：

- **内存墙在边缘端更严重**：Jetson Orin 的 8GB LPDDR5 统一内存面对 Agent 负载时极易溢出
- **非对称量化的实用价值**：KV Cache INT4 + Attention FP16 的组合可在 Jetson 上实现更长上下文
- **Agent 负载 100× 的 token 消耗**：意味着边缘 Agent 必须实现更激进的上下文压缩
- 实践建议：Jetson 上的 Agent 应使用 **DuoAttention + INT4 KV Cache + 分层存储**组合

- 标准定价：$3/$15 per M tokens

- 输入 1M + 输出 4K = $6 + $0.09 = **$6.09/次**

## 五、对 Hermes 系统的映射与启发

### 5.1 直接可用的改进

1. **Prompt Caching 应立即启用**：对于重复性系统 prompt 和 Skill 加载，可节省 90% 成本。需检查 Hermes Gateway 是否已支持 provider-level prompt caching。

2. **"Lost in the Middle" 对 Skill 设计的启示**：将关键指令放在 prompt 的**开头和结尾**，避免中间区域放置关键信息。

3. **分层上下文管理已在实践中**：我们的 L1（MEMORY.md）/ L2（短期记忆）/ L3（Topics）三层架构与业界最佳实践一致。可进一步引入 Tier 2 的"Recall vs Archival"区分。

4. **Agent 负载 100× token 消耗**：解释了为什么我们的 cron 任务和复杂工作流经常触发 token 限制。应在 Skill 设计中更激进地压缩上下文。

### 5.2 中期技术采纳

1. **DuoAttention 式 KV Cache 优化**：如果 Hermes 支持本地模型推理（如 Jetson 上的 Ollama），可以探索 KV Cache 剪枝来延长有效上下文。

2. **混合 RAG 替代盲目长上下文**：对于需要处理大量文档的场景，优先使用 RAG 而非塞满上下文窗口。我们的 hybrid-search Skill 已有基础。

3. **上下文感知压缩**：context-compressor Skill 已有雏形，可以引入"91% 信息保留 / 68% 大小减少"的量化目标。

### 5.3 知识缺口

1. **TTT-E2E（Test-Time Training）的工程实现**：2M 上下文 35× 加速的技术细节
2. **Star Attention 的具体机制**：NVIDIA 的 11× 加速方案如何实现
3. **DeepSeek NSA 的可训练稀疏注意力**：如何在已有模型上迁移
