## 一句话总纲

> **成熟 AI 系统不只用一个最大模型，而是把任务拆开分层路由：窄任务（分类/抽取/改写/路由）交小模型，复杂任务交大模型，高风险加人工兜底——蒸馏是造小模型的方法（强模型输出→清洗→训练→评测→监控回流），成败在数据质量门禁与低置信度兜底，而非模型本身。**

## 一、内容详细整理

### 1.1 为什么小模型重新变重要

**上线后才发现的真瓶颈**（不是"能不能答"）：成本太高 / 延迟太长 / 并发不够 / 数据不能出内网 / 端侧要离线 / 任务其实很固定。

**任务分层判定**：

| 任务 | 是否需要最大模型 |
|------|-----------------|
| 判断工单类型 / 提取订单号金额 / 输出固定 JSON | ❌ 不一定 |
| 复杂法律分析 / 多文档推理 / 代码重构 | ✅ 可能需要 |

**核心认知**：很多业务任务是**窄任务**，小模型足够。

### 1.2 蒸馏是什么（含与微调的区别）

**通俗理解**：让小模型学习大模型在特定任务上的表现——大模型像专家顾问，小模型像熟练员工。

**典型流程六步**：收集真实业务输入 → 强模型生成高质量输出 → 人工/规则清洗 → 训练小模型 → 独立测试集评估 → 上线监控补样本。

**与微调的区别**（关键在数据来源）：

| 概念 | 通俗解释 |
|------|---------|
| 微调 | 用任务数据继续训练模型 |
| 蒸馏 | 用强模型输出作为训练目标，让小模型模仿 |

蒸馏通常**用**微调来实现——蒸馏是目的，微调是手段。

### 1.3 适用性矩阵

**小模型适合**（共性：输出空间固定/格式稳定/业务类型有限）：

| 任务 | 原因 |
|------|------|
| 分类 | 输出空间固定 |
| 信息抽取 | 格式稳定 |
| 文本改写 | 风格固定 |
| 意图识别 | 业务类型有限 |
| 简单摘要 | 输入结构稳定 |
| 安全初筛 | 先低成本过滤 |
| **路由** | **决定请求交给哪个模型** |

**小模型不适合**：开放知识问答（覆盖不足）/ 高复杂推理（上限不够）/ 多跳关系（漏推理）/ 高风险决策（错误代价高）/ 未见过的新任务（泛化弱）。

### 1.4 蒸馏数据质量六项检查

> "坏数据会把小模型教坏。不要把大模型原始输出不加审核地喂给小模型。"

| 检查项 | 说明 |
|--------|------|
| 输入真实 | 不全是理想化样本 |
| 输出正确 | **老师模型也会错** |
| 格式稳定 | 训练固定输出结构 |
| 覆盖均衡 | 不只覆盖高频简单问题 |
| 隐私脱敏 | 训练前处理 |
| 边界样本 | 拒答/异常/模糊问题要有 |

### 1.5 落地案例：工单分类蒸馏

```
目标：用户反馈分 6 类
① 收集 5000 条历史工单
② 大模型给分类+理由
③ 业务人员抽样校正
④ 训练小模型
⑤ 1000 条人工标注集评估
⑥ 线上低置信度样本 → 转大模型或人工
```

**架构关键**：省钱的同时保留质量兜底（低置信度路由）。

### 1.6 评测七指标

| 指标 | 说明 |
|------|------|
| 准确率 | 总体分类正确 |
| **分类别召回** | 每一类都能识别（长尾） |
| 混淆矩阵 | 哪些类易混 |
| **置信度校准** | 高置信度是否真的更准 |
| 延迟 | 实时性 |
| 成本 | 相比大模型节省 |
| **漂移** | 线上新问题是否降低效果 |

**核心提醒**：小模型常见问题是**长尾类别表现差**——不要只看总体准确率。

### 1.7 四个坑

1. **用大模型错答案做训练**——老师也会错，蒸馏前必须清洗
2. **测试集和训练集太像**——离线分高，上线翻车（分布偏移）
3. **没有低置信度兜底**——不确定样本应能转大模型/人工
4. **以为蒸馏后永远不用维护**——业务/用户表达/产品变化都会漂移

### 1.8 实践清单（七条）

高频固定低风险任务起步 → 强模型生成候选标注 → 抽样人工校验 → **训练前先定义评测集** → 评估准确率/延迟/成本/长尾 → 设计低置信度兜底 → 上线错分样本回流训练。

### 2.2 置信度路由的数学骨架（补充）

低置信度兜底的形式化：设小模型输出概率分布 p(x)，定义路由函数

```
route(x) = 小模型   if max p(x) ≥ τ_high
         = 大模型   if τ_low ≤ max p(x) < τ_high
         = 人工     if max p(x) < τ_low
```

**τ 的标定依赖置信度校准指标**（ reliablity diagram / ECE）——这正是 1.6 表中"置信度校准"的用途：**未校准的置信度会让路由形同虚设**。

### 2.3 "路由"作为小模型任务的自指性

表中"路由：决定请求交给哪个模型"——用小模型给大中小模型分诊，这是 **pm-master 分诊模式**（08-22 pm-skills 笔记）与 **adaptive-inference-routing skill**（本机已有）的同构实现。蒸馏一个专用路由器的成本远低于每次全量请求大模型。

## 三、归纳总结

### 3.1 分层架构图

```
用户请求
   ↓
[小模型·路由/初筛]  ← 蒸馏产物：分类/抽取/意图/固定JSON
   ├─ 窄任务+高置信 → 小模型直接处理（省钱省时）
   ├─ 中置信 → 大模型处理
   └─ 低置信/高风险 → 人工兜底
   ↓
[监控回流] 错分样本 → 清洗 → 补训练集 → 再蒸馏（闭环）
```

### 3.2 蒸馏工程七步（含质量门禁）

```
选任务（高频/固定/低风险）
→ 备数据（真实输入，非理想化）
→ 蒸馏生成（强模型输出）
→ ⚠️ 质量门禁（六项检查：真实/正确/格式/均衡/脱敏/边界）
→ 训练（先定义独立评测集）
→ 评测（七指标：别只看总体准确率，看长尾+校准+漂移）
→ 上线（低置信兜底 + 错分回流）
```

## 四、趋势判断

### 趋势 1：模型分层路由将成为 AI 应用的标准架构

> 依据：本文的分层架构 + OpenAI 官方蒸馏流程支持 + 本机 adaptive-inference-routing 已落地——单一大模型的"能力、成本、延迟、隐私"四维平衡只能靠分层实现。端侧（离线/隐私）与内网（合规）场景会加速这一进程。

### 趋势 2：蒸馏的瓶颈从"算法"转向"数据治理"

> 依据：本文六项质量门禁全部是数据问题（输入真实/输出正确/覆盖均衡/脱敏/边界）+ 四坑中两坑是数据问题（老师错误/测试集泄漏）——与 08-23 企业知识工程"知识准入"四道关同构。**蒸馏本质是把大模型能力沉淀为数据资产，数据治理不行就白蒸**。
