## 零、结论先行

**核心主张：指令层（instruction layer）是项目资产，必须放在项目自有的文件名下（AGENTS.md），所有厂商文件（CLAUDE.md 等）降级为四行薄适配器——"Own the handbook, rent the tools."** 对我们的判定：**不形成新 skill**——我们是单厂商生态（Hermes 三机全读 AGENTS.md，无 split-brain 问题），且四部件结构我们已全部具备且更完整；但文章的**三重验证法（tripwire/删除检查/CI 检查）是真增量**，记入笔记备用，触发条件写明（见 §六）。

## 一、事件层：8.25 之争（双方都有理）

**Lütke（Shopify CEO）**：考虑在全公司禁用 Claude Code，直到它开箱支持 AGENTS.md 和 .agents/skills。抱怨很实际：
- 每个工具坚持自己的文件名 → 多工具团队同一套规则要维护多份 → **split brain**
- 两种文件名在每个目录都生效（不只根目录）→ 千人公司要在每个文件夹保持两份一致
- Shopify 已经自动化同步，他仍称之为"税"

**Thariq（Anthropic Claude Code 团队）**："我们不认为模型家族是可互换的"——指令文件不是中性文本，每个模型家族按它偏好的写法跟随指令效果更好。**Anthropic 已为新模型砍掉 Claude Code 系统提示词约 80%**，并发布了"Claude 想要什么样的 CLAUDE.md/skills"的官方指南——通用化文件会损失性能。同时承认维护负担是真的：AGENTS.md 原生支持在路上，临时方案=import 指针。

**文章的观察（最有洞察的一段）**：两人真的在"指令应可移植 vs 应按模型调优"上分歧，**但没人质疑前提——指令文件决定 agent 好不好用**。"Nobody threatens a vendor ban over a config file that doesn't matter."

## 二、模式层：手册 + 薄适配器

### 2.1 四行适配器（Anthropic 官方文档背书）

```
CLAUDE.md 内容 = @AGENTS.md（一行 import + 可选模型特调）
```

- import 以 `@` 开头，路径相对包含它的文件，**可链式 import 最多 4 层深**——手册指向 docs/ 里的记忆文件，厂商文件不携带任何 canonical 内容
- 替代方案：`ln -s AGENTS.md CLAUDE.md`（symlink，一文件两名零漂移；Windows 需管理员/开发者模式，用 import）
- **对 Thariq 论点的回应**：如果 Claude 对指令形状有偏好，特调写进适配器 import 行之下——**模型特调留在厂商本地，项目实质归项目所有**，争论在仓库内无残留

### 2.2 四部件结构

| 部件 | 内容 | 我们的对应 |
|------|------|-----------|
| Rules | 编码规范/构建命令/测试流程/边界——"新员工第一周会被告知的" | uclaw/AGENTS.md ✓ |
| Skills | 可复用任务指令（migration 怎么写/PR 怎么格式化/发布清单怎么跑） | ~/.hermes/skills（600+）✓ |
| Workflows | 串联步骤：评审门禁/部署顺序/合并前检查 | skills 中的 pipeline 族（发布链/分析管线）✓ |
| **Memory** | **决策日志**：为何弃用某库/哪个 API 版本闯祸/哪条约定源于一次事故——"只增长，无法重建（一半没人记得了）" | MEMORY.md + error-case-library + session_search ✓（markdown 非 vendor 记忆功能锁定） |

**关键设计**：memory 指向 docs/ 里的纯 markdown 文件——版本控制内、任何 agent 和人类可读，**而不是某个厂商记忆功能里的条目（将来要导出）**。"The switching cost is the layer."——换模型是改配置，换厂商格式是重写全部规则+技能+决策史。

### 2.3 规模纪律

Anthropic 文档建议指令文件 **<200 行**（更长降低跟随质量）。"一页团队真遵守的规则胜过投机性的十二节手册。**Agents act on what you wrote——错误指令和正确指令一样快地规模化。**"

## 三、验证层：三重验证法（本文最实操的增量）

> "A portability claim you haven't tested is a hope."

| 验证 | 做法 | 判定 |
|------|------|------|
| **Tripwire（绊线）** | 只在 AGENTS.md 植入一条独特可查规则（如"每个新函数加 handbook 开头的注释"——agent 默认绝不会做），同一小任务跑两个 agent，验证都触发该规则且规则只存在一份 | 证明手册是 canonical |
| **删除检查** | 拷贝仓库到临时目录，**删光所有厂商名文件**，看剩下什么——规则/工作流/决策日志全存活=手册 canonical；消失的=放错位置 | 作者实测：import 和 symlink 两种适配器删光后 canonical 全存活 |
| **CI 检查** | 流水线像验证 lockfile 存在一样验证 AGENTS.md 存在于 agent 工作处 | "用代码而不是用警惕来堵 Lütke 说的漏文件洞" |

第二个 agent 建议至少一个**本地运行**——"因为云厂商把你逼走时你会切换到的就是本地"。

## 四、生态事实

- AGENTS.md 项目官网计数：**截至 2026-08 底 60,000+ 开源项目带此文件**（GitHub 公开搜索背书）
- 围绕该文件构建的工具：OpenAI Codex、Amp、Jules、Cursor、Factory；Aider/Gemini CLI 一行配置即可读
- Claude Code：加载当前文件夹+所有上级文件夹的 CLAUDE.md + 个人 ~/.claude/CLAUDE.md，读代码时顺带加载更深层文件

## 五、与我们体系的对照

| 文章主张 | 本机现状 | 判定 |
|---------|---------|------|
| 手册归项目所有，不进厂商文件名 | uclaw/AGENTS.md 已是项目自有手册；Hermes 原生读它 | ✅ 已满足——**我们生在正确的一侧** |
| 厂商文件=薄适配器 | 无厂商文件需要适配（Hermes 是唯一"厂商"，三机 jbot/ubot/abot 同格式） | ✅ 无此问题——split brain 是多工具团队的病 |
| Memory 是 markdown 不是厂商功能 | MEMORY.md/error-case/notes 全是纯文件 | ✅ 已满足且更完整（L3 topics + session_search） |
| <200 行纪律 | uclaw/AGENTS.md 约 200 行（含团队协议/门禁/路径铁律） | 🟡 贴线——新增条目时要有挤出的意识 |
| Tripwire/删除/CI 三重验证 | 无等价物 | 🟡 **真增量**——但当前单厂商下无验证对象 |

## 六、Skill 必要性判定（用户核心问题）

**判定：不形成新 skill。** 三条理由：

1. **无病可治**：模式解决的核心痛点（多厂商文件 split-brain + 同步税）在我们生态不存在——Hermes 单格式，三机共享 NFS 上的同一份 AGENTS.md，零适配器需求
2. **已有覆盖**：四部件结构我们已完整拥有且部分更强（skills 600+ vs 文章的"可复用任务指令"；记忆三级架构 vs "docs/ 里的决策日志"）；AGENTS.md 写作标准在 text-to-cad 笔记已有 SKILL.md 范本沉淀
3. **防止 skill 通胀**：昨天 SoL-Pi 的教训正当其时——**40:1 的候选死亡率是必要筛选强度**；一个"暂时用不上的好模式"进 skill 库就是 600+ 通胀再加一

**两个 nugget 的归宿**（不建 skill 但不丢弃）：
- Tripwire 验证思想 → 已记入本笔记；若未来做 skill 注入可靠性审计（验证 Hermes 每会话真加载了 AGENTS.md），tripwire 是现成方法
- **升级触发条件（写明）**：当出现第二个厂商 agent 协作我们的仓库（最可能的入口：CATDS Windows 端引入 Claude Code/Codex 处理 CATIA COM 侧脚本），当天把"手册+薄适配器+三重验证"提炼为 skill 并落地 AGENTS.md→CLAUDE.md 适配器——届时用本笔记即可，半天工作量

## 七、批判性审视

1. **文章的适用前提被淡化**：全文最好的场景是"多工具千人团队"；单人单工具仓库（多数读者）收益仅剩结构参考——但标题的"beats up to five vendor files"暗示普适，营销味
2. **"60,000+ 项目"的口径**：GitHub 搜文件名计数——存在 ≠ 按此模式维护；多数可能是空壳或废弃文件
3. **Thariq 的性能论未被反驳只是被绕开**："通用文件损失性能"如果为真，薄适配器模式下 Claude 仍读的是 AGENTS.md 的通用内容+一小段特调——性能损失的绝对量可能很小，但文章没有实测数字，只有架构论证
4. **import 4 层链是文档口径**：深层链的实际 token 成本与优先级覆盖行为未验证（作者只测了单层）
5. **作者自述"在磁盘上验证过文件机制"**——验证的是 import/symlink 生效，**未验证双 agent tripwire 通过**（"简单可自测"的口吻，但文中无实测结果）——这是文章最大的"叙述超前于证据"点
