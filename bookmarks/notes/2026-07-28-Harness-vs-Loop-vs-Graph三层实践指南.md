# Agent Harness vs Loop vs Graph Engineering：三层实践指南

## 核心结论

大多数人把 AI Agent 当成一个东西。它不是。当 Agent 超越玩具 Demo，开始触碰文件、API、文档、客户或生产代码时，你不再只是"提示模型"，你在**设计系统**。这个系统有三个经常被混为一谈的层：**Harness（环境）→ Loop（反馈）→ Graph（流程）**。它们解决不同问题，搞混了就会在错误的层调试。

---

## 一、30 秒答案

| 层 | 一句话 | 心智模型 |
|---|---|---|
| **Harness Engineering** | 围绕模型构建**环境** | Environment（环境） |
| **Loop Engineering** | 设计重复的**工作-反馈循环** | Feedback（反馈） |
| **Graph Engineering** | 让工作流拓扑**显式化** | Flow（流程） |

> **Environment → Feedback → Flow**

- Harness 给模型工具、记忆、控制和**工作空间**
- Loop 决定工作如何被**重试、检查、改进**
- Graph 定义**下一步允许发生什么**

---

## 二、为什么这三层现在重要？

### 裸模型无法独立完成真正的工作

它**不能**：维护跨会话状态 / 安全调用工具 / 检查浏览器 / 强制权限 / 重试失败工作 / 验证输出质量 / 跨专家路由任务 / 在正确时刻停止。

> 所有这些都来自模型周围的**系统**。

### 成熟 Agent 软件的实践技术栈

```
1. Harness → 给模型操作条件
2. Loops   → 让工作可重复且可验证
3. Graph   → 让复杂工作流显式且可控

一旦你把它们视为独立层，大量 AI 架构困惑就消失了。
```

## 三、Harness Engineering 详解

### Harness 包含的六大模块

| 模块 | 包含什么 |
|------|---------|
| **① Context Injection（上下文注入）** | 指令 / 检索知识 / 对话状态 / 记忆 / 策略 / 任务规则 |
| **② Action Surfaces（动作面）** | API 调用 / 浏览器动作 / Shell 命令 / 代码执行 / MCP 工具 / 数据库 / 自定义函数 |
| **③ Persistence（持久化）** | 文件 / 检查点 / 会话状态 / 进度日志 / Git 历史 / 长期记忆 |
| **④ Execution Control（执行控制）** | 重试 / 超时 / 预算 / 模型选择 / 子 Agent 生成 / 审批门 |
| **⑤ Safety & Governance（安全治理）** | 最小权限 / 隔离 / 白名单 / 密钥处理 / 人工审批 |
| **⑥ Observability（可观测性）** | Trace / 工具输入输出 / 状态转换 / 延迟 / 成本 / 评估结果 |

### 为什么 Harness 重要？

> 两个团队用同一个模型，结果完全不同——因为一个给了干净的**工作条件**，另一个给了模糊 Prompt + 混乱工具 + 噪声上下文。

**Harness 有问题时的症状**：

- Agent 无法访问正确能力
- 会话间丢失上下文
- 跨环境行为不一致
- 无法审计
- 权限过大
- 中断后无法干净恢复

> **如果模型无法可靠运行，第一个要看的就是 Harness。**

## 四、Loop Engineering 详解

### 每个工具使用 Agent 都有内置小循环

```
1. 调用模型
2. 观察结果
3. 运行工具
4. 反馈观察结果
5. 重复直到完成
```

> Loop Engineering 始于你**有意识地在这个行为周围设计额外循环**——不是"再问一次"或"重试"，而是真正的**工作-反馈系统**。

### 好循环的七大要素

| 要素 | 问题 |
|------|------|
| **Trigger（触发器）** | 什么开始新循环？（用户请求/测试失败/新文档/定时/Webhook/评估反馈） |
| **Goal（目标）** | 要达到什么**具体条件**？（不是"持续改进"，而是真实目标） |
| **State（状态）** | 下一循环需要知道什么？（当前草稿/上次尝试/工具结果/错误/进度） |
| **Action Policy（动作策略）** | Agent 被允许做什么？（编辑/委托/调工具/花Token/写文件/开PR） |
| **Evidence（证据）** | 怎么知道成功了？（测试/Schema 验证/引用/Diff/指标/审核批准） |
| **Feedback（反馈）** | 具体什么失败了？（反馈应紧凑且可操作） |
| **Stop Rule（停止规则）** | 何时结束？（成功/超时/预算耗尽/最大重试/不可恢复失败/升级人工） |

### Loop Engineering 最重要原则

> **不要基于信心（confidence）循环。基于证据（evidence）循环。**

❌ "Agent 说它完成了" ≠ 停止条件

✅ 真实停止条件：

- 测试通过
- Schema 验证通过
- 引用可解析
- 审核者批准
- 策略检查干净

### Loop ≠ Prompt Engineering

| Prompt | Loop |
|--------|------|
| 告诉模型在**调用期间**做什么 | 定义系统在**调用之后**做什么 |
| 改善一次响应 | 改善一个**流程** |

## 五、Graph Engineering 详解

### 它回答的问题不同

> 不是"Agent 应该做什么？"，而是"**下一步允许发生什么？**"

在图工程中：

- 步骤 = **节点**
- 转换 = **边**
- 分支 = **显式**
- 并行 = **显式**
- 汇聚 = **显式**
- 重试 = **显式**
- 人工中断 = **显式**

> 图成为系统的**控制地图**。

### 图工程师实际设计什么

| 设计点 | 说明 |
|--------|------|
| **节点边界** | 什么属于确定性函数 / LLM 调用 / 专家 Agent / 人工审核 |
| **状态 Schema** | 每个节点能读/写什么 |
| **路由条件** | 什么证据让任务前进/后退/转向/升级 |
| **并发** | 什么可以并行，什么必须等待 |
| **循环和退出** | 哪里允许重试、允许多少次、如何停止 |
| **持久性** | 检查点在哪里发生，中断后如何恢复 |

### 什么时候图值得用？

✅ **值得**：有意义的分支 / 审批 / 专家交接 / 并行工作 / 恢复路径 / 多步工作流带显式控制点

❌ **不值得**："给一个 Agent 几个工具让它干活"——这种情况下，扎实的 Harness + 几个循环就够了。

> 图增加清晰度，但也增加结构。**过早加太多结构会让系统脆弱。**

## 六、三层如何协同工作（实例）

以"研究-发布 Agent"为例（选题→收集来源→筛选引用→起草报告→法务审核→审批后发布）：

| 层 | 职责 |
|---|---|
| **Harness** | 浏览器访问 / 搜索工具 / 文件工作区 / 记忆 / 引用 / 审批 / Trace / 模型路由 |
| **Loop** | 证据弱时重试来源检索 / 修复引用失败 / 运行评分检查 / 市场变化时刷新 |
| **Graph** | 选题→研究→筛选→综合→起草→审核→发布的路径，发布前有人工门 |

> 三层不可互换，协同工作但不是同一件事。

## 七、诊断法则：先定位故障，再选修复

| 症状 | 修哪层 |
|------|--------|
| **Agent 无法运行**（缺工具/状态陈旧/记忆弱/权限坏/无可观测性） | → 修 **Harness** |
| **Agent 差一点但不稳定**（初稿接近但弱/成功不一致/重试不可控/无完成证明） | → 修 **Loop** |
| **流程本身复杂**（多专家/审批/分支逻辑/并行路径/结构化交接） | → 修 **Graph** |

## 八、五个常见错误

| 错误 | 说明 |
|------|------|
| **① 过早构建图** | 先画巨大流程图，而非观察工作实际行为。**更好**：从简单 Harness 开始 → 收集 Trace → 发现稳定模式 → 只形式化值得控制的 |
| **② 同一模型写+评分** | 自评有相同盲点。**更好**：确定性检查 / 独立审核上下文 / 外部评估器 / 高影响操作需人工审批 |
| **③ 用"持续尝试"当循环** | 那不是循环设计，是不可控的成本泄漏。每个循环需要：可测量目标 / 真实证据 / 重试限制 / 升级规则 |
| **④ 把 Harness 当杂物抽屉** | 工具越多 ≠ Agent 越好。太多工具 → 选择错误 / 噪声上下文 / 可靠性弱 / 风险面大。**好 Harness 不是拥挤的，是精准的** |
| **⑤ 把编排失败归咎于模型** | 模型无法补偿：坏 API / 陈旧状态 / 缺退出条件 / 模糊工具 Schema / 不可见失败模式。**修拥有故障的那层** |

## 九、生产检查清单

| 层 | 检查项 |
|---|---|
| **Harness** | 工具是否窄且有文档？状态是否持久？权限是否最小化？操作者能否暂停/检查/恢复？Trace 是否可见？ |
| **Loop** | 什么证据证明成功？失败时返回什么反馈？允许多少次重试？停止规则是什么？预算耗尽时怎么办？ |
| **Graph** | 哪些路径必须确定性？什么可以并行？人工门在哪里？共享什么状态？恢复路径从哪开始？ |
| **Evaluation** | 能否重放真实 Trace？能否对比版本？能否把改进归因到真实变更？ |
| **Operations** | 是否追踪成本？延迟？失败率？干预率？生产任务成功率？ |

## 十、最终记忆法

| 层 | 一句话 |
|---|---|
| **Harness** | 让模型**可运行** |
| **Loop** | 让工作**可迭代且可验证** |
| **Graph** | 让执行路径**显式且可控** |

> **None replaces the others.**
>
> 完美的图救不了弱的 Harness。强 Harness 没有好 Loop 仍然浪费钱。干净的 Loop 在分支和审批隐藏在临时代码中时会变得难以管理。
>
> **可靠的 Agent 系统在三层都被有意识设计时才会出现。**
