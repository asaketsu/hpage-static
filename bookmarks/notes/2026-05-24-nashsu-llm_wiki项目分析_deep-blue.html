摘要

nashsu/llm_wiki 是一个跨平台桌面应用，将 Karpathy 的 LLM Wiki 模式从"Agent 手动维护"升级为"应用自动构建"。与我们的 llm-wiki skill（基于 Karpathy 模式的 Agent 技能）本质不同，但核心检索架构值得借鉴。

核心内容

1. 项目定位

维度 nashsu/llm_wiki 我们的 llm-wiki skill
形态 跨平台桌面应用（Electron/Tauri） Agent 技能（纯文本/文件操作）
维护方式 应用自动构建 + 本地 API Agent 手动维护
依赖 LanceDB + Electron + Rust 无依赖，纯 markdown

结论：两个项目不是上下游关系，不能直接"升级版本"，但可以借鉴功能设计。

2. 检索架构（4 阶段）

用户查询 → 4 阶段检索管道
  ├─ Phase 1: Tokenized Search（关键词）
  │   ├─ 英文：word splitting + stop word removal
  │   ├─ 中文：CJK bigram 分词（每个 → [每个, 个...]）
  │   └─ Title match bonus (+10 score)
  │
  ├─ Phase 1.5: Vector Semantic Search（可选）
  │   ├─ Embedding：OpenAI-compatible /v1/embeddings
  │   ├─ 存储：LanceDB（Rust 后端，ANN 检索）
  │   └─ 合并：boost 已有匹配 + 添加新发现
  │
  ├─ Phase 2: Graph Expansion
  │   ├─ 种子节点：Top search results
  │   ├─ 相关性模型：4-signal
  │   └─ 遍历：2-hop with decay
  │
  └─ Phase 3: Budget Control
      ├─ 上下文窗口：4K → 1M tokens
      ├─ 分配：60% wiki + 20% chat + 5% index + 15% system
      └─ 优先级：search + graph 综合评分

3. 技术亮点

a) 本地 HTTP API
- 地址：127.0.0.1:19828
- Token 保护
- 功能：混合搜索、文件读取、图遍历、源扫描
- 我们的 skill 目前无 API 暴露

b) 中文检索优化
- CJK bigram 分词（vs 我们的 bigram 关键词匹配）
- 标题匹配加分
- 搜索范围：wiki/ + raw/sources/

c) 向量语义搜索
- LanceDB（Rust 后端，性能优于 Python）
- OpenAI-compatible 接口（可替换任何 embedding 模型）
- Cosine 相似度 + 关键词合并

d) Graph Expansion
- 2-hop 遍历（vs 我们的 [[wikilinks]] 手动链接）
- 4-signal 相关性模型
- 衰减因子控制深度

e) Context Budget Control
- 可配置窗口大小（4K → 1M）
- 比例分配策略
- 基于综合评分的优先级排序

f) Agent Skill 集成
- 一键安装：npx skills add ...
- 支持 Claude Code / Codex
- 参考：https://github.com/nashsu/llm_wiki_skill

4. 检索 vs 我们的实现

功能 nashsu/llm_wiki 我们的 skill 差距
关键词检索 CJK bigram + title bonus bigram 关键词匹配 标题加分缺失
向量检索 LanceDB + OpenAI-compatible Gemini embedding 架构不同
图扩展 2-hop 自动遍历 [[wikilinks]] 手动链接 自动化程度
预算控制 比例分配 + 优先级排序 无 完全缺失
HTTP API 127.0.0.1:19828 无 完全缺失
Agent 集成 npx skills add skill_manage 手动 安装方式

5. 搜索渠道诊断（本次会话）

渠道 状态 原因
web_search ✅ 能用 返回了结果
web_extract ❌ 拦截 "private/internal network" 误判
browser_navigate ❌ 启动失败 daemon socket 问题
curl GitHub ❌ 拦截 Cloudflare bot 检测
curl raw.githubusercontent ❌ 空响应 网络问题
r.jina.ai ❌ 空响应 网络问题
GitHub API ❌ 限流 IP 超出配额
MCP zhipu ❌ 额度用完 每周限额，6/8 重置

教训：搜索渠道单一，需建立降级链。

🔍 借鉴学习进化点

# 点 原文要点 对当前系统的借鉴 行动计划
1 本地 API 暴露 127.0.0.1:19828 JSON API Agent 技能可暴露本地 API 供其他工具调用 调研 FastAPI/Flask 轻量方案
2 向量 + 关键词混合 LanceDB + OpenAI-compatible 我们的 skill 只有关键词，可引入向量层 调研轻量 embedding（如 sentence-transformers）
3 图扩展检索 2-hop 自动遍历 我们的 [[wikilinks]] 需手动维护，可自动扩展 基于 wikilinks 图做 BFS 扩展
4 上下文预算控制 比例分配 + 优先级 长上下文场景可借鉴 在 ingest 时实现预算分配
5 搜索降级链 — 本次会话搜索渠道大面积失效 建立搜索降级链 skill
6 Agent Skill 集成规范 npx skills add 我们的 skill 安装方式不统一 统一 skill 安装/更新流程

三问自检

  1. 有无可复用方法？ — 图扩展检索（2-hop BFS）可直接用于我们的 [[wikilinks]] 系统；预算控制策略可借鉴到长文档 ingest。
  2. 有无可优化配置？ — 搜索降级链需立即建立（本次会话多个渠道失效）；本地 API 暴露可提升技能复用性。
  3. 有关键事实？ — nashsu/llm_wiki 与我们的 skill 不是上下游关系，不能直接升级版本；v0.4.12 是最新稳定版。
