# 什么是 Eval？为什么它决定了 AI 项目能不能真正落地

> **来源**：@UPing123zzz（X 长文，2026-08-28 收录）
> 一句话核心：**Eval 就是给 AI 考试。没有 Eval，你只能说 AI「看起来不错」；有了 Eval，你才能证明它真的不错。**

## 一、为什么「效果不错」这句话很危险

现在做 Agent 很容易：Prompt、RAG、Workflow、Knowledge Base、MCP、Tool Calling，一个 Demo 很快就能跑起来。然后大家说"效果不错"。

但什么叫不错？追问下去全是空白：

- 100 个问题，答对多少？
- 哪种问题最容易答错？
- Prompt 修改以后真的提升了吗？
- 知识库换了以后，幻觉减少了吗？
- V2 到底比 V1 好在哪里？

**核心论断**：没有一套固定的问题、一套明确的评分标准、一份可以对比的报告，你只有一种感觉——"它好像变聪明了"。没有 Eval，你不知道 AI 是真的变好了，还是只是"感觉变好了"。

## 二、Eval 是什么：给 AI 考试

Eval = Evaluation = 评估。最直观的比喻是**给 AI 考试**。

学校里不会因为一个学生"看起来挺聪明"就说他数学学得好，至少需要一套完整的考试制度。AI 项目同理：

| 学校里的考试 | AI 项目里的对应物 |
|-------------|------------------|
| 考试题 | **Golden Set**：一组经过验证的代表性案例 |
| 标准答案 | 参考答案、事实依据或必须满足的条件 |
| 评分标准 | **Rubric**：把"好不好"拆成可检查的维度 |
| 阅卷方式 | 阅卷规则、LLM-as-a-Judge，或人工复核 |
| 成绩单 | **Eval Report**：版本、指标与失败样本 |
| 错题本 | **Error Analysis**：失败类型与根因 |
| 下一轮复习 | 继续学习：Prompt、RAG、Workflow、模型与工具迭代 |

Eval 不只是跑一次 benchmark，也不只是给模型一个总分。它是一条闭环：

```
准备题目 → 运行系统 → 按标准评分 → 读懂失败 → 修改系统 → 再考一次
```

真正有价值的 Eval 不是告诉你"这个模型有多强"，而是告诉你：**你的 AI 产品，在你的真实任务上，哪里有效、哪里不可靠。**

## 三、为什么 AI 比传统软件更需要 Eval

传统软件测试有清晰的输入输出——输入 1+1 正确结果是 2，输出和预期不一致测试就失败。这类系统接近 **deterministic**。

AI 不一样：让 AI 写一封"礼貌但有力度的催款邮件"，可能有几十种合格答案。不能写 `actual_output == expected_output`，要问的是：

- 有没有解决用户的问题？
- 事实是否准确？有没有编造不存在的信息？
- 是否遵循了语气和格式要求？
- 是否遗漏了关键条件？
- 是否违反了业务规则？

### Testing vs Eval 的本质区别

| | Testing（测试） | Eval（评估） |
|---|---|---|
| 回答的问题 | 它能不能跑？ | 它跑得好不好？ |
| 典型对象 | API 调用、JSON 解析、工具参数 | 任务完成度、事实准确性、规则遵循 |
| 失败表现 | 抛出异常、返回错误 | 返回合法 JSON 但分错类；成功调用工具但理解错结果；流畅回答但幻觉 |

**金句**：
- Testing 保证系统**没有坏掉**。
- Eval 帮你判断系统**有没有变得更有用**。
- 软件工程靠 Test 防止代码回归；AI 工程需要 Eval 防止能力回归。

## 四、没有 Eval 的 AI 项目有多危险：凭感觉调 Prompt

典型流程：V1 做出来 → 觉得不错 → 改 Prompt → V2 更聪明了 → 换模型、换知识库、加工具、调上下文长度 → V3 看起来更快了。

全程没人能回答：V2 比 V1 提升多少？是所有任务都提升还是只有一类？哪些任务退化？幻觉率变没变？成本延迟有没有恶化？新工具带来价值还是只是更复杂？

**根因**：AI 的输出太容易让人产生错觉——一个更长、更自信、更像人写的答案，很容易被误认为更好的答案。结果就是**项目变成"凭感觉调 Prompt"**，这不是团队不认真，是方法论缺位。

## 五、Golden Set：AI 的考试题库

Golden Set = 一组经过人工验证的高质量标准案例。贴近真实任务，且已有人认真确认过"什么算对"。

### AI 招聘 Agent 示例

| 案例 | 人工标准 | 关键理由 |
|------|---------|---------|
| 简历 01 | 应通过 | 核心经验与岗位要求高度匹配 |
| 简历 02 | 应淘汰 | 缺少必须技能，且经历无法替代 |
| 简历 03 | 75–85 分 | 有相关经验，但管理范围不足 |
| 简历 04 | 不超过 60 分 | 项目名称相似，实际职责不匹配 |

Golden Set 就把"这个 AI 看起来会招聘"变成可检查的问题：在这组代表性案例上，判断是否稳定、是否接近业务标准、错误集中在哪里？

**一份有用的 Golden Set 至少包含**：高频场景 / 边界场景 / 异常场景 / 容易混淆的场景 / 高风险场景 / 历史失败案例。

**关键洞察**：
- 题库不一定一开始就大——**20 个高质量、覆盖关键风险的案例，往往比 200 个重复问题更有价值。**
- **最有价值的 Eval 数据，往往不是成功案例，而是 AI 曾经真正犯过的错。**

## 六、Rubric：AI 的阅卷标准

很多 AI 任务没有唯一标准答案，需要告诉阅卷者什么算好、什么勉强合格、什么不可接受。

### 行业文章评估 Rubric 示例（100 分制）

| 维度 | 权重 | 检查什么 |
|------|------|---------|
| 事实准确性 | 30 | 关键事实、数字、因果关系是否可靠 |
| 是否解决问题 | 25 | 是否直接回应真正的任务 |
| 引用正确性 | 20 | 引用是否存在、是否真的支持结论 |
| 品牌信息 | 10 | 产品名、功能和边界是否表达正确 |
| 合规性 | 10 | 是否出现不该承诺或不该输出的内容 |
| 格式 | 5 | 标题、长度、结构是否符合要求 |

示例得分：事实准确 28/30，问题解决 21/25，引用正确 16/20，品牌信息 9/10，合规 10/10，格式 5/5 = **总分 89**。

**Rubric 的本质：把模糊的主观判断结构化。** 分数不会从此绝对客观（仍需人设计、校准、更新），但把讨论从模糊偏好推进到可复盘维度。

**常见误区**：只写"要高质量"——几乎无法执行。要写成**可观察的标准**：

- 5 分：所有关键事实都能被给定资料支持，没有重大错误
- 3 分：主结论基本正确，但遗漏一项重要限定条件
- 1 分：出现一个会改变决策的事实错误

**Rubric 真正开始工作的标志**：两个不同的人能给出相近的分数。

## 七、谁来给 AI 打分：三种阅卷方式

| 方式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **规则评分** | 机械明确的条件：JSON 可解析、必须字段存在、类型正确、含 URL、长度限制、禁用词、数字日期格式 | 便宜、稳定、可解释 | 无法处理语义 |
| **人工评分** | 医疗、法律、招聘、金融建议、品牌内容等高风险复杂任务 | 发现没想到的错误类型、校准自动评分器 | 成本高、可能不一致 |
| **LLM-as-a-Judge** | 大规模语义判断、初筛、回归测试、发现趋势 | 速度快、规模大 | 非绝对真理，见下方局限 |

**LLM Judge 的已知偏差**：受措辞影响 / 偏好更长的答案 / 对自己熟悉的模型更宽容 / 相同输入下分数不稳定 / 被格式设计诱导出高分。

**简化 Judge 指令示例**：

```
请按照以下标准评估候选答案。
准确性：0–5 分
完整性：0–5 分
相关性：0–5 分
逻辑性：0–5 分
请输出：总分、每项理由、最严重的问题、是否建议通过。
```

**真实项目的推荐组合**：规则先挡住硬错误 → LLM Judge 大规模语义判断 → 人工复核高风险和争议样本。

## 八、Eval Report：真正的 AI 成绩单

没有报告，Eval 容易停留在"跑过了"。Eval Report 把一次考试变成可比较的证据：

| 指标 | V1 | V2 | 变化 |
|------|----|----|------|
| 总体通过率 | 71% | 91% | +20 个百分点 |
| 事实准确率 | 85% | 96% | +11 个百分点 |
| 格式正确率 | 92% | 99% | +7 个百分点 |
| 幻觉率 | 14% | 4% | −10 个百分点 |
| 平均响应时间 | 8.2s | 5.4s | −34% |
| 单次成本 | ¥0.18 | ¥0.11 | −39% |

这时才能有把握地说 V2 比 V1 更好。

**⚠️ 切片思维**：真实项目要按新老用户 / 中英文 / 简单复杂问题 / 不同客户行业 / 不同风险等级分片看。**总体平均分上涨，不代表某个高风险任务没有退化——合格的报告不应该用平均数遮掉这种问题。**

## 九、真正正确的 AI 开发流程

- 传统项目：`Build → Done`
- AI 产品：`Build → Eval → Analyze → Improve → Eval Again`

每轮迭代留下可追踪的东西：这次改了什么？哪些题目变好了？哪些退化了？新增的通过率来自哪里？成本延迟稳定性付了什么代价？还剩哪些失败类型？

**Eval Engineering vs 随便测一下**——错误定位示例：

> 客服 Agent 订单查询表现不好。跑完 Eval 发现，问题不是模型不会回答，而是订单工具在缺少订单号时被错误调用；工具返回空结果后，模型又把"查不到"编成了一个具体状态。
> 只盯最终答案 → 继续改 Prompt（错方向）。
> 看失败样本和链路记录 → 根因是参数提取、工具调用条件和空结果处理都需要修正（对方向）。

Eval Engineering 要求把**评估本身当作工程系统来建设**：数据集可版本化、运行可复现、指标可比较、失败可追踪、评分器可校准。

## 十、为什么 Eval 是 AI FDE 的核心能力

- Prompt、RAG、Agent、Workflow、MCP、Tool Calling 解决的是：**怎么把东西做出来。**
- Eval 解决的是：**怎么证明你做出来的东西真的有效。**

个人 Demo 说"我试了几个问题，感觉不错"也许够用；但真实交付中企业买的不是一个 Agent 的概念，而是一个结果。客户会问：准确率是多少？哪些场景稳定？为什么可以相信？出错谁发现？新版本提升多少？成本可接受吗？能安全进生产吗？

FDE 的价值在于**把技术能力翻译成客户结果**，Eval 提供这套翻译所需的证据：基线、指标、失败案例、改进前后对比、上线后持续监控。

> **Demo 展示能力，Eval 建立信任。**

## 十一、做任何 AI 项目先问的 6 个问题

1. 我怎么证明它真的有效？
2. 我的 Golden Set 是什么？
3. 我的评分标准是什么？
4. 当前成功率是多少？
5. 最常见的失败类型是什么？
6. 新版本相比旧版本提升了多少？

回答不了这六个问题，AI 系统可能还没真正完成——它能运行、能演示，但"能运行"和"可交付"之间，隔着一套 Eval。

## 结语：从会做 Demo，到能证明结果

过去 AI 开发的门槛是"能不能做出来"；现在模型越来越强，做 Demo 正在快速变简单。未来真正拉开差距的，不再是谁最会写 Prompt，而是谁能：**定义问题 → 建立题库 → 设计评价标准 → 找到失败案例 → 持续迭代系统 → 最终用数据证明 AI 真的有效。**

**一句话总结**：

```
Eval = 给 AI 考试
Golden Set = 考试题库
Rubric = 阅卷标准
Eval Report = 成绩单
Eval Engineering = 建立整套 AI 考试制度
```

## 思维对照：Eval 与本机 Hermes 体系的同构点

> 注：以下为本笔记附加的对照分析（原文之外的延伸），帮助理解 Eval 思想在 Agent 系统中的具体落点。

| 本文概念 | 本机已有对应物 | 差距 |
|---------|---------------|------|
| Golden Set（题库） | `error-case-library`（错误案例库）、`cron-verifier-global.yaml` 结构校验规则 | 无系统性"黄金问题集"，多为零散 case |
| Rubric（阅卷标准） | `8d4531fe5b5c` 量化评分（RSI/均线/量价等 7 维度）、`content-judge` skill | 量化选股已有明确 rubric；AI 输出质量 rubric 偏少 |
| 规则评分 | `cron-output-verifier.py`（非空/JSON 解析/字段/漂移） | ✅ 已落地（2026-08-28 新增） |
| LLM-as-a-Judge | `content-judge`（LLM-as-Judge 内容质量评分） | ✅ 已落地 |
| Eval Report（成绩单） | `cron-health-scan.py` 每日摘要 | 偏系统健康，缺"能力回归"对比报告 |
| Error Analysis（错题本） | `error-case-library`、`daily-forward-learning` | ✅ 已落地 |
| 防能力回归 | 无系统性"改 Prompt 前先跑基线"流程 | **最大缺口：需建立 Golden Set + 基线对比习惯** |

**可操作结论**：本文提出的 6 问可以直接作为 Agent 系统迭代的检查清单——尤其是"新版本相比旧版本提升了多少"这一条，对应到本机就是**任何 Prompt/Skill/Cron 修改前先留基线输出，修改后对比**（与 `skill-ab-testing`、`quant-evidence-governance` 的"改前双跑对比"原则同构）。
