一、内容详细整理（底稿骨架 + 十二节全录 + 附录清单照录）

1.1 底稿命题

核心：企业 AI 知识库从"能演示"走到"能交付"，难点不只在模型，而在资料、人员、权限、系统、边界和验收。

六大开篇追问：

  1. 为什么原始资料本身可能就是错的；
  2. 怎样找到只存在于老员工脑子里的知识；
  3. 为什么企业知识库很难直接卖一套标准产品；
  4. 复杂文档、旧系统和私有化部署应该怎样处理；
  5. 怎样通过工作范围说明（SOW）控制交付边界和需求变化；
  6. 怎样用两套测试集完成测试与客户验收。

1.2 引子：印错的纸（底稿核心案例，照录）

2023 年某传统制造业 AI 知识库交付。项目测试时系统回答错了一题，排查从模型→检索→解析→扫描图片→原始纸质设计文档，每一步技术链路都没问题，但答案就是错的。追到底发现纸质资料当年就印错了，老员工口口相传已默认改过——没人重新打印，也没人正式记录更正。AI 得到的是一份与原文一致、但知识本身错误的资料。

生成日期 2026-09-03

命题：AI 可以准确地读取一份资料，也可以准确地引用一份资料，但它无法自动保证这份资料原本就是对的——技术链路零错误，知识层面全错。

1.3 十二节骨架（每节命题照录 + 关键原句）

§一 企业做知识库，通常不是因为"想拥有一个 AI"

  • 制造业案例真需求：不让掌握专业知识的人一天到晚被相同的问题打断——不是替代研发，不是让企业从此不需要懂业务的人
  • 需求通用 ≠ 交付可标准化：资料在哪/谁能看/旧资料怎样处理/系统接不接得进/答案怎样判断正确——每家都不一样

§二 企业的很多知识，根本不在文档里

  • 长企业历史=历史遗留问题堆叠
  • 四类口传知识形态：师傅带徒弟嘴上说 / 群里说一次 / 大家用久了知道错但没正式改过 / 正式文件但不能完全照做
  • AI 看到什么就处理什么：原始资料少一条默认规则，不会自己补；原始资料错了，不会因"老员工都知道"就自动改正
  • 不能指望：客户交一个文件夹 → 导入系统 → 项目完成

§三 做知识库不能站在员工对面，要先看他们怎么干活

  • 员工第一反应："你是不是来替代我的？"
  • 交付姿态："半蹲下来"——不是站员工头顶指挥，是站辅助位置，听他讲哪里最烦/哪里重复最多/哪里最易出错
  • 老员工最有价值的信息=那些没写在文档上、模型也没学过的行业经验
  • 反误判规则：遇到看似不合理的需求，先问它从哪里来/想解决什么问题/为什么过去没用其他方式/为什么现在一定要这样——背景听清楚再讲技术方案
  • 技术团队懂模型/检索/系统，业务人员懂产品/流程/行业，哪边单独做判断都不够

§四 只和老板聊，确定不了真正的交付边界

  • 老板只能告诉你：想不想做、大概多少预算
  • 真正确定边界 = 进客户办公室/业务现场，和实际参与工作的团队沟通，可能持续几天甚至约一周
  • SOW（工作范围说明）必须写清两类：
  • ① 交付方最终要交什么（做到哪个场景/接哪些资料/包含哪些系统能力/怎样测试验收）
  • ② 项目成立所依赖的前置条件（哪些资料客户提供/谁配合确认业务/客户准备什么环境/哪个环节不提供就无法继续交付）
  • 变更流程铁律：需求变化不能拖到验收前告诉客户；项目较大走正式变更程序，合同较小也及时沟通；客户通常更可能接受验收时间后移而非追加费用

§五 知识库为什么一直没有"一统天下"的产品

  • 通用需求真，定制工作也真——三类抹不平的问题：
  • 权限：哪个部门看哪些知识、不同角色能问到什么内容
  • 数据接入：企业数据不会天然集中一个文件夹，可能在不同系统和沟通工具中
  • 数据治理：哪些过时/哪些有效/哪些冲突，需要先治理
  • 使用门槛要求：企业用户要"点点点"——不学提示词、不理解知识库技术结构；系统把重复操作提前收好
  • 知识库底层可通用，交到客户手里时入口和流程仍要贴近员工原来使用习惯

§六 数据治理不是抽象概念，首先要处理"新旧真假"

  • 头部的"印错纸"只是知识有问题的一种情况
  • 另一种：旧资料仍保留、新资料已生效，两者一起进系统，AI 能找到内容却不知企业执行哪一版
  • 没有万能治理表格，技术团队不能自行判断所有资料——知识治理不是知识库外面可有可无的整理动作，它直接决定知识库最终回答什么
  • 源头不可靠，后面的模型、检索、界面再好，也只是把不可靠知识更方便地提供给用户

§七 复杂 PDF 处理不了时，人工录入也是交付方案

  • 企业早期产品资料多为图片 PDF（含产品图/三维图/尺寸标注/不规则表格）
  • 技术演示追求"全自动"，但交付首先要保证事情能做完，而不是证明每一步都必须由 AI 完成
  • 图片/尺寸/表格只要错一个关键位置，自动化比例再高也无意义——用人力完成录入不丢人

§八 老系统没有接口，最好不要轻易碰

  • 数据可能存在 ERP/OA/业务系统里
  • 项目对老系统态度非常明确：不会轻易碰；ERP 不提供接口，这部分业务就不做
  • 强行改造遗留系统=把项目拖进无法控制的范围

§九 私有化还是云端，先看客户对数据的要求

  • 数据不能离公司/不想调外部模型 → 私有化；接受云端 → 云服务
  • 没有哪种方案天然更先进，由客户数据要求决定
  • 技术框架选择：小团队更适合用自己熟悉、出问题后能处理的技术——逐渐沉淀一套可复用的技术设施
  • 顺序铁律：先说明业务场景需要什么模型能力 → 再评估硬件和推理环境 → 绝不能反过来：先买机器，再想办法把场景塞进去

§十 模型不是看排行榜选出来的，要拿固定问题去测

  • 早期模型能力不足时，即使资料有正确答案，模型也可能答不出来
  • 正确方法：固定一组问题，同样问题测不同模型；准确率达不到要求就换下一个模型
  • 给客户的最终答案只有两种：这套流程在哪个模型下可以工作；或者，目前的模型都实现不了
  • 这句话对销售不利，却是项目能真正验收的前提

§十一 知识库一定要做测试集，因为客户最后要验收

  • 企业项目不能靠演示时问对几个问题就算完成——两套测试集：
  • 第一套：交付方测试集——按产品各小需求点设计正反测试 → 交给客户确认（客户判断是否漏/范围是否认可）→ 交付方反复测试达标
  • 第二套：客户验收测试集——不提前公开，客户测试后只反馈：达标/不达标/还差多少
  • 通过率计算思路：约 85% 题目有确定答案（可判断对错，如认证信息/电流参数）；剩余 15% 无标准答案的题目由人评估
  • 完整验收链路：按需求点设计正反用例 → 客户确认测试范围 → 交付方测试达标 → 客户用未公开题目独立验收 → 标准答案机器判断、开放答案人工判断
  • 长上下文"越用越笨"问题为何在知识库场景少：
  • 聊天型智能体上下文会无限长 → 头尾保留、中间遗忘 → 旧信息丢失
  • 企业知识库典型使用是功能性的：查一次问题得答案就离开，一次用可能只有一两问，上下文天然短
  • 工作留痕（保护双方对同一件事的共同理解）：项目开始确认范围和前置条件 / 需求确认后客户对测试范围的反馈 / 交付中变化记录（原因/影响/新安排）/ 验收时拿测试结果和客户反馈——不能只凭"当时演示过"

§十二 一个知识库项目，可能会做出第二个数据治理项目

  • 印错纸暴露出底层问题：产品资料/设计资料未完成数字化与数据治理，历史问题仍在员工脑子
  • 知识库交付过程中暴露的问题，可能继续变成新项目（先交付知识库 → 再讨论产品手册/设计资料重新数字化与数据治理）
  • 但绝不能偷偷塞回原项目——签合同前写清：哪些交付方负责/哪些客户提供/哪些属于原项目/哪些不属于
  • 知识库与数据治理可以互相连接，但不是同一件事：前者解决知识怎样被查询和使用，后者处理历史资料怎样重新整理、数字化和确认

1.4 【附录照录】企业 AI 知识库落地检查清单

模块 检查项
1. 使用场景 ☐ 已明确服务哪些内部人员 ☐ 已找到反复回答问题的岗位 ☐ 已确认知识库准备接住哪一类查询
2. 现场与边界 ☐ 已和实际干活的人沟通过（不只是听老板描述） ☐ 已了解现有流程/重复劳动/容易出错处 ☐ 已确认哪些能做/哪些暂时不能做 ☐ 已写清交付内容和客户前置条件
3. 资料与历史知识 ☐ 已检查资料是否分散在不同位置 ☐ 已检查复杂 PDF/图片/尺寸/不规则表格 ☐ 已向熟悉业务的人确认是否存在口传经验 ☐ 已区分过时知识与仍有效的知识
4. 权限与数据接入 ☐ 已确认不同部门能获取哪些知识 ☐ 已检查企业数据实际存在哪里 ☐ 已确认旧系统是否提供可用接口 ☐ 没有把无法接入的老系统默认算进交付范围
5. 技术与模型 ☐ 私有化/云端已根据客户数据要求确定 ☐ 使用团队熟悉、出问题后能处理的技术 ☐ 复杂资料自动处理成本过高时已评估人工方案 ☐ 已用一组固定问题测试模型 ☐ 模型不达标会更换，全部不达标会明确说明当前无法实现
6. 测试与验收 ☐ 已按各需求点设计正向和反向测试 ☐ 交付方测试集已交给客户确认 ☐ 客户保留独立验收测试集 ☐ 大部分题目具有可判断的确定答案 ☐ 无标准答案部分由人评估
7. 新问题与新范围 ☐ 已区分知识库项目和数据治理项目 ☐ 历史资料数字化/数据治理/旧系统改造未被默认塞进原项目 ☐ 交付中新需求会重新确认范围和条件

1.5 【末章照录】企业知识库最怕的不是 AI 不够聪明

回到 2023 年那次交付。知识库回答错了以后，交付团队一层层检查，最后发现技术链路没有出错，错的是最初那张纸。这个案例之后，再看企业知识库，就很难只把它理解成一个模型问题。它同时涉及现场流程、口传经验、权限、数据接入、旧知识治理、复杂文档处理、遗留系统、模型选型和客户验收。

做这类项目，不能等客户把一切准备好，再带着工具过去实施。客户现场一定会有资料缺失、历史问题和其他依赖。交付团队要做的，是进入现场，把哪些能做、哪些不能做、客户需要准备什么、最后怎样验收，一件一件说清楚。

有些问题用 AI。有些问题用传统技术。有些问题在当前条件下，直接用人力更可靠。还有些问题，暂时做不了，就要明确说做不了。

企业 AI 交付的目标，不是证明 AI 什么都能做，而是把客户真正要用的东西，做到可以测试、可以验收，也能稳定运行。

二、查询拓展

  • 知识治理的成熟度模型（KCS / ITIL Knowledge Management 框架）
  • 企业 RAG 系统的评测基准（RAGAS / TruLens / 85% 可判定率是否有行业标准）
  • 数据契约（Data Contract）在知识工程中的引入路径
  • 私有化部署下模型的持续对齐验证（本文提"参数不被外部随时调"——稳定≠正确，对齐仍会变）
  • SOW 变更管理在 AI 项目与传统软件交付中的异同

三、归纳总结

  1. 技术链路正确 ≠ 知识层面正确（本文最重要命题）：印错纸案例=数据链路 100% 无错 + 知识 100% 错——源头可靠性超出技术能力边界，须由业务人员+老员工共同确认
  2. "半蹲姿态"是交付方法学：技术团队懂模型、业务人员懂行业，哪边单独做判断都不够；反误判规则=遇到看似不合理的需求先问再判
  3. SOW 是唯一的边界工具：不能只和老板聊；必须写清"交付什么"+"依赖什么前置条件"；变更需走流程，客户更可能接受时间后移而非追加费用
  4. 知识库"点点点"使用门槛：企业用户不学提示词、不理解知识库结构——产品把重复操作提前收好，贴近员工原有习惯
  5. 没有"一统天下"的知识库产品（真，定制工作也真）：权限/数据接入/数据治理三类抹不平
  6. 交付铁律三连：老系统没接口不动；私有化前先说清模型能力要求再买机器；模型不达标明确说做不了
  7. 85/15 验收比例：约 85% 题目有确定答案（机器可判）、15% 由人评估——不能全部靠"读起来好像不错"
  8. 知识治理从"附属动作"升级为核心前置：源头不可靠，后面再好也只是把不可靠知识更方便地提供
  9. 工作留痕=保护双方对同一件事的共同理解：不是把客户当对手，是 AI 项目比固定软件更容易波动时减少分歧

四、趋势判断

  1. AI 交付的"最后一公里"从技术侧转向业务侧：模型成熟后，企业 AI 项目的真正瓶颈是知识治理/口传经验/权限/边界——交付团队的核心竞争力将从"调模型"转向"进现场+懂行业"
  2. "知识治理→知识库"双项目模式会越来越普遍：客户往往从知识库切入，交付中暴露出数据治理需求，再走第二单——先交付知识库+留治理伏笔成为新商业路径
  3. 测试集+工作留痕将成为 AI 项目验收的标配：从"演示时答对几个"转向"正反测试集+未公开验收+85/15 混合判断"——AI 交付正在从演示驱动走向工程驱动
  4. 私有化部署的"先能力后机器"顺序会逐渐形成行业规范：先确定模型能力门槛→再评估硬件，避免先买机器再硬塞场景
  5. "明确说做不了"会从销售不利转变为专业信誉：AI 交付从营销导向转向工程导向，"做不了"的诚实将成为交付团队的可信资产

五、关联分析（对自有体系 + 既有笔记链）

关联对象：企业 RAG 体系（BBT / MiniMind Agentic RL / KVCache / RSI / 企业 AI 知识库既有笔记）、evolver 自改进体系

  1. 与"印错纸"案例与 RSI 模型坍缩的同构：两者都是"数据源头错误→技术链路完美→最终答案错误"形态——RSI 自产数据塌缩=知识源头错误在自举闭环里被放大（关联 [[2026-09-03-RSI递归自我改进全景]]）
  2. "半蹲姿态"与 evolver 审核机制的对照：evolver 的经验库沉淀 → curator 审核 → skill 更新，本质就是技术团队+业务（用户）判断"哪边单独做判断都不够"的具体工程实现——我们的自改进体系在方法论上已经采纳了这种"半蹲"
  3. SOW 边界管理与 skill 体系治理：skill 的"哪些属于原项目/哪些不属于"问题等价于"哪些应进 error-case-library/哪些该升 skill/哪些留在 memory"——本文 SOW 思维可直接迁移到 skill 治理
  4. 85/15 验收比例与我们 skill 测试门槛的对照：本文 85% 可判定+15% 人工评估 = 我们的 skill 测试也应有"机器可判"和"需人工评估"两种——当前 skill-health-tier 的 production/beta/skeleton 三级分类可引入本文"85% 可判定率"作为 production 门槛
  5. "老系统无接口不动"与"结构空间优先，软件能替不买"：用户 DUCK 硬件选型铁律——两者都是"不强行改造基础设施，先看清边界再决定做什么"的同一种克制原则
  6. 工作留痕与 error-case-library 的家族关系：本文"工作留痕保护双方对同一件事的共同理解"= 我们的 error-case-library 就是系统对系统自身的"共同理解记录"——两者都是"记录变化/分歧/验收证据"的工程化实现
