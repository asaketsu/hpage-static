核心论点

"You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."
— Peter Steinberger (OpenClaw 创始人)，此推文浏览量破 500 万

"我现在不提示 Claude 了，我有一批 Loop 在跑，它们在提示 Claude，决定接下来做什么。我的工作是写 Loop。"
— Boris Cherny (Claude Code 负责人)

工程师的角色不是"逐轮提示 Agent"，而是"设计让系统自动提示 Agent 的系统"。

演化脉络：被工程化的对象一直在往上移

层次 解决的问题 核心局限
Prompt 工程 "怎么问"——角色、格式、示例 无状态：每轮对话结束即遗忘
Context 工程 "让模型看到什么"——RAG、记忆、工具描述 无法处理持续多天/多步骤任务
Harness 工程 "在什么条件下做、怎么做才不出错" 能干活但不会自己找活干
Loop 工程 "让系统自己驱动自己" 成本高、适用范围有限、认知负债风险
FDE "把系统搬进客户地盘"——解决落地摩擦 依赖内层可靠性，底层不可靠则推进越快问题越多

每往上移一层，被工程化的对象就抽象一层：从"提示词"→"上下文"→"执行环境"→"自治循环"→"部署落地"。

一、Harness 工程：先把"干活的地方"建好

命名者：Mitchell Hashimoto（HashiCorp/Terraform 联合创始人），2026 年初正式命名

核心公式

Agent = Model + Harness

  • 模型决定"能不能做"
  • Harness 决定"在什么条件下做、怎么做才不出错"

三层结构

层次 功能 关键设计
工具与执行层 读写文件、Bash、API、浏览器 工具表面越清晰，行为越可预期
控制与验证层 ⭐ 测试、类型检查、权限边界、审批门控 把"我希望它这样做"变成"它不可能那样做"
持久化与状态层 文件系统 + Git 持久化，支持断点续跑 解决 AI 失忆问题

关键对比：概率性合规 vs 确定性约束

  • ❌ 告诉 Agent "请遵守我们的代码规范" → 概率性合规（模型可能遵守也可能不遵守）
  • ✅ 接入违反规范时直接阻断 PR 的 Linter → 确定性约束（结构上不可能违反）

Harness 工程做的，就是把"我希望它这样做"变成"它不可能那样做"。Agent 犯错的概率不是降低了，而是那类错误直接在结构上被关掉了。

标杆：Stripe Minions

  • 规模：每周无人值守合并 1000+ 个 PR
  • 流程：隔离 devbox 运行 → pre-push 自动 Linter → 从 300 万测试中精选 CI → 失败反馈 Agent 自纠正 → 通过提 PR → 人工仅审查

二、Loop 工程：让系统自己驱动自己

核心转变

工程师从"逐轮提示 Agent 的人"变成"设计让系统自动提示 Agent 的系统的人"。

Harness 是工厂的生产线，Loop 是工厂大脑——它决定什么时候启动生产线、生产什么、检查结果是否合格、不合格怎么办。
— Addy Osmani (Chrome DevTools 负责人)

两个核心元素

  1. 触发器：定时任务（每天凌晨依赖更新）/ 事件驱动（新 PR 触发审查）/ 目标驱动（跑到所有测试通过）
  2. 可验证目标：✅ "所有 CI 通过"（好目标） / ❌ "帮我优化一下这个功能"（坏目标——无法判断何时完成）

五个核心构件（缺一不可）

构件 作用 缺失后果
自动化触发 Loop 的发动机 退化为手动脚本，失去自治意义
创作者与检验者分离 ⭐ 独立验证 Agent 评估结果 产生"模型同意自己"的幻觉，错误得不到纠正
连接器 打通 GitHub/Jira/Slack 等外部系统 Loop 变成孤岛，无法感知外部世界
隔离工作区（Worktrees） 多 Agent 并行操作同一代码库互不污染 无法规模化并行
持久化记忆 历史轨迹、失败记录写入可检索存储 每次从零开始，成本极高

标杆：Steve Yegge 的 Gas Town 项目（2026年1月上线）

  • "Mayor" Agent 协调 20-30 个 Claude Code 实例
  • 巡逻 Agent 持续循环扫描代码库健康状态 → 发现问题分配给工作 Agent → 完成后更新状态（存 Git）→ 崩溃重启从断点续跑
  • 人的角色：审查 PR + 系统卡住时踢一脚

⚠️ 必须正视的现实代价

风险类型 具体数据/描述
成本 单 Agent Loop token 消耗 ≈ 普通对话 4 倍；多 Agent 系统 ≈ 15 倍；大规模并行团队月度 token 账单可轻松进入七位数
适用范围 三个条件缺一即易失控：① 高频重复 ② 结果可验证 ③ 工具链已接通。目标模糊的 Loop 可在几小时内烧掉数百美元且无产出
认知负债 ⭐ Loop 跑得越好 → 工程师介入越少 → 慢慢不知道系统在干什么/为什么。关键路径上的人工审查是出大问题前感知不到价值、但出了问题会后悔没做的事

三、FDE：把系统搬进客户地盘的人

FDE = Forward Deployed Engineering（前向部署工程）

起源

  • Palantir 于 2003 年前后发明（代号 Delta），将精英工程师派驻军事基地和客户现场
  • 核心发现：再好的系统，客户自己也装不上、用不了——不是技术问题，是集成、认知、政治的问题
  • 沉寂近 20 年后，企业 AI 浪潮让同样问题在所有行业同时爆发
  • 2026 年初：OpenAI、Anthropic、Cohere、Databricks 的 FDE 团队已成标配

关键数据

企业 AI 项目有九成五卡在了落地阶段，不是因为模型不够好，而是因为系统性的摩擦没有人去解决

FDE 四种能力（很少在同一个人身上共存）

能力 描述
生产级工程能力 写真实代码，建真实集成，向生产环境交付——不是做 Demo，不是出 PPT
领域翻译能力 坐在 CFO 旁理解业务问题 → 转身坐到 DBA 旁理解数据约束 → 在两者之间架桥
Agent 落地专项能力 RAG 管道建设、Eval 框架设计、生产可观测性搭建——2026 年 FDE 必考项
产品反哺能力 客户现场发现的集成难题和重复部署模式 → 反向影响产品路线图

四、五层嵌套关系

每一层都依赖内层，但内层做到极致也替代不了外层。

FDE（落地部署）
 └── Loop（自治驱动）
      └── Harness（执行环境）
           └── Context（信息可见性）
                └── Prompt（指令表达）
  • Harness 再完善，没有 Loop → 系统被动，需人驱动
  • Loop 再精妙，企业数据权限没打通 → 跑不起来
  • FDE 能推进落地，但底下 Harness 不可靠 → 推进越快，问题越多

这是真正嵌套的系统，不是可以跳着走的选项清单。

🔍 借鉴点

对 Hermes Agent 系统的直接映射

文章概念 Hermes 对应 当前状态
Harness 工具与执行层 terminal/file/browser/code_exec ✅ 已有
Harness 控制与验证层 auto-defense-check、skill 审查 ⚠️ 部分
Harness 持久化层 memory + session DB + Git ✅ 已有
Loop 自动化触发 cronjob 系统 ✅ 已有
Loop 创作者与检验者分离 content-judge、critical-code-reviewer ✅ 已有
Loop 持久化记忆 三级记忆（L1/L2/L3） ✅ 已有
Loop 隔离工作区 delegate_task 独立终端 ✅ 已有
认知负债风险 无人工审查门控 ❌ 缺失

关键行动项

  1. 确定性约束优先：与其写"请遵守 X"规则，不如实现"不遵守 X 就报错"的检查机制。已有 auto-defense-check 雏形，可扩展
  2. 认知负债缓解：Loop 系统应定期输出"可读简报"——不只是 cron 执行结果，而是"做了什么决定、为什么、有什么风险"
  3. 创作者与检验者分离：delegate_task 已有此结构，但实践中需确保子 Agent 使用不同模型/不同 Skill 验证，避免同源偏差

💡 启发

  • "Prompt 没死，它升职了"：越是追求自动化，越依赖那些需要人深度思考才能写出来的东西（CLAUDE.md / SKILL.md / 系统提示）。这与 Hermes 的 Skill 体系完全一致——Skill 就是"被工程化的 Prompt"
  • 确定性 > 概率性：与其优化 prompt 让模型"大概率"做对，不如加一道 gate 让它"不可能"做错。这正是 deterministic-guardrails skill 的设计哲学
  • FDE 视角：用户的 Hermes 系统本身就是"个人级 FDE"——系统再好，不能真正融入日常工作流（cron 不跑、skill 不用），就是技术债

趋势 依据 行动
