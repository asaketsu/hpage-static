核心问题

LLM Agent 面对上万工具规模的语料库时，工具选择成为执行前的瓶颈：①工具描述全塞进上下文会溢出；②相关性检索器只会排序、不知道任务"需要哪些"；③现有解法（ToolReAGt/AnyTool 等）靠提示工程驱动 Claude/ChatGPT 等专有大模型当"检索器驾驶员"，成本高且不可本地化。论文问：一个 8B 开源小模型能否通过训练接管这个职能，并且跨工具域、跨检索器可迁移？

内容整理

一、Plan-Retrieve-Select 工作流（§3.1）

  • Plan：把用户指令分解为有序子步骤列表，每个子步骤是"单一所需能力"的自然语言短描述。理由：检索器对整条 query 打分时，多个请求的词项互相干扰。
  • Retrieve：每个子步骤一次检索调用，全库打分，保留分数 > τ（默认3）的工具并截断到 top-K（默认15）。检索器默认 BM25（bm25s 库，k1=1.8, b=1.0，无词干化），训练时不用任何语料专用检索器——保证迁移成绩来自模型而非检索器。
  • Select：候选工具描述装入上下文，LLM 从 ≤15 个候选中选 1 个工具；跨子步骤累积，并集即最终工具集。
  • 关键设计：同一个模型 π 用两套 prompt 同时充当 Plan 和 Select；每次调用无状态，上下文有界（与库规模/计划长度无关），天然适配万级工具库。
  • 假设边界：每个子步骤恰好一个工具可解、子步骤相互独立（无数据依赖链）。

二、两阶段训练配方（§3.2-3.3）

SFT 热启动（教师=Llama-4-Maverick 402B）：
- 金标过滤：ToolBench 的 gold 工具集来自参考轨迹，含噪声（有些 gold 与用户指令无关、有些是近重复冗余）。过滤规则：只保留"仅凭 query 就能识别"的 (query, gold tool) 对——先确定性初筛（query 与工具文档共享实词），余下交教师判断"query 是否包含工具功能的释义/同义词"。
- 计划分解：教师把指令分解为子步骤并对齐 gold 工具；未被任何子步骤覆盖的 gold 判为"不必要"，二次剔除。
- 推理生成：教师为 Plan/Select 各写简短论证。反泄漏校验：任何点名候选集之外工具、或泄漏候选索引的推理文本被标记并重新生成。
- SFT 目标格式：<think>教师推理</think> + JSON 动作，Qwen3 思考模式开启训练。

RL（GRPO，VeRL + vLLM）：
- Plan/Select 解耦为独立无状态调用分别训练（训 Select 时用教师的高质量子步骤，不用自己的计划）——每次调用就是标准 GRPO 单轮场景，训练稳定。
- Plan 奖励 = 检索接地的 F1：把子步骤跑一遍检索器得排序列表 Ai，按序匹配未占用的 gold 工具；precision = 匹配子步骤占比（惩罚冗余子步骤）；recall 按 rank 折减 Σ(1/ρj)/N（gold 排名越靠前分越高）；R_plan = F1(precision, recall)。
- Select 奖励 = 精确匹配指示函数 1[selected={g}]，与评测指标完全对齐。
- 超参：SFT lr=1e-5 cosine 3 epochs（LLaMA-Factory）；RL lr=1e-6 恒定 300 steps，64 prompts × 16 rollouts，KL 系数 0.001，8×A100。

三、关键实验数据

主实验（ToolBench G3：1,419 工具，21,361 训练 / 2,124 测试，精确匹配口径）：
- Qwen3-8B SFT+RL：41.5%（8B SFT 36.2% → RL +5.3pp）
- Qwen3-4B：40.3%；Qwen3-1.7B：37.6%（最小档仍碾压）
- Llama-4-Maverick(402B) 提示工程四方案：Search-R1 风格 30.6% / ReAct 28.4% / 层级搜索(AnyTool式) 8.6% / 本文工作流 10.1%
- 1.7B 训练后 > 402B 提示工程最好成绩 7 个百分点；规模差两个数量级。

跨域零迁移（同一 G3 checkpoint，无再训练，Table 2）：
- ToolBench G2（8× 语料 11,474 工具、仅 9% 与 G3 重叠）：8B 25.8%，胜过 Maverick+Search-R1 的 20.8%
- Gorilla（ML 模型枢纽单工具域）：8B 29.9% vs Maverick 最好 26.8%
- CRAFT（数学/表格/视觉 QA）：8B 69.0% vs Maverick+本文工作流 47.9%
- TaskBench（多工具全异域）：8B 72.8%，但输给 Maverick+Search-R1 的 80.6%——Plan 阶段需要领域知识时，无需分解的扁平推理流反而占优。

跨检索器迁移（§4.3）：BM25 训练的 checkpoint 推理时直接换 COLT（ToolBench 专用稠密检索器），所有规模成功率提升，零再训练——检索器是可插拔接口，模型继承更强检索器的召回。

消融（8B，Fig 9）：
- Planner 替换：训练过的 8B 计划器 > 未训练 Qwen3-8B（27.6）> Maverick 当计划器（17.2）——计划质量由训练驱动，不由规模驱动
- 候选集 K 扫描：K=20 饱和，K=30 不再涨（更大集合更可能含 gold 但干扰项也多）
- Select 价值：BM25 top-1 规则提交只有 28.6%，学习型 Select 41.5%——Select 阶段贡献 +12.9pp
- SFT 热启动：Base 20.5 / RL-only 35.7 / SFT-only 36.2 / SFT+RL 41.5——RL 可从裸模型起步但组合最优

归纳总结

创新点四条：
1. 范式转移：把"专有巨模型提示工程驱动检索器"替换为"小模型 RL 后训练接管"，工具选择从 prompt 问题变成训练问题。消融证明这是训练而非规模的胜利（Maverick 当计划器仅 17.2%）。
2. 检索接地的计划奖励：不评测计划文本本身，而是"用子步骤文本跑检索看 gold 是否高分靠前"——计划质量用它在外部世界的检索后果定义，rank 折减 recall（1/ρ）设计精巧，零人工标注。
3. 双重可迁移性证明：跨域（G2/Gorilla/CRAFT/TaskBench 零再训练）+ 跨检索器（BM25→COLT 免训热插拔），核心论据是"指令分解与按描述选工具"是领域无关的通用技能。
4. 严格承诺制评测口径：拒绝 Recall@K/NDCG@K 这类"gold 出现在候选列表就算分"的宽松指标，用精确匹配（多选漏选都算失败）——对 Agent 实际部署更有意义。

趋势判断

  • 小模型专精化路线持续验证：继 2025-2026 一系列"8B 训后胜 400B 提示"案例后，本文把该结论推进到"万级工具库选择"这个 Agent 基础设施子环节。趋势：Agent 的每个高频子程序（路由/选择/校验）都值得一个专属小模型，端侧可托管。
  • 奖励接地（reward grounding）成为新共识：Plan 奖励不评文本质量而评检索后果，与 ODA（2609.20734，按需注意力用 recall head 步级预测收益）同构——奖励信号从人工设计转向"用可验证的外部系统后果当奖励"。
  • 检索器正在被降格为可插拔接口：训练时用最笨的 BM25 保证归因干净，部署时免费继承强检索器——"模型-检索器解耦"是后续 Agent 路由系统的默认架构。
  • 局限信号：TaskBench 上输给扁平推理流说明 Plan-分解并非普适最优——分解本身需要领域知识时，让模型边想边搜（Search-R1 式）更稳。指令含数据依赖链（子步骤 B 需要 A 的输出）时本工作流直接失效，这是与真实 Agent 任务（结果驱动再规划）的最大 gap。

指南分析

对 Hermes Agent 技能路由的可操作启示：
1. 分步再检索：多部分请求先分解成"单能力子步骤"再逐条检索，不要拿整条 query 去搜技能库——词项干扰是实测量化的（Plan 阶段存在的全部理由）。
2. 候选上限 K=15~20：更多候选不涨分反添干扰（K=30 饱和），当前 hybrid-search 的 top-K 配置可对照校准。
3. 承诺制评测：技能路由 eval 应测"最终选中的技能集合是否精确等于 gold 集合"，而非"gold 是否在 top-K 里"——后者会系统性高估路由质量。
4. top-1 规则是强基线（28.6%）：任何学习型路由器上线前必须先打败"检索第一名直接提交"，否则没有存在价值。
5. 检索器解耦：路由逻辑不应硬编码绑定某个检索实现，接口化后换更强检索器可免费涨分。

拓展应用推荐

  • ✅ P1｜分步检索进 hybrid-search：把"指令分解→逐子步骤 BM25→top-15→选择"流水线补进现有 hybrid-search skill（其 BM25 基座已在），纯 prompt 层改造，零训练。收益：多部分请求（如"查X再对比Y"）的技能命中精度。
  • ✅ P1｜路由评测改精确匹配口径：notes-eval-gate 式确定性检查已有，补一个"技能路由 golden set + 精确匹配"离线评测脚本，用检索 top-1 规则当对照基线。
  • 🔨 P2｜Qwen3-4B 端侧专职路由器：论文未放出自训 checkpoint（附录 B 仅列依赖库），复现需 8×A100 GRPO——成本高；但等作者放模型后可在 Jetson Orin 上跑 4B AWQ 做 GLM 前置技能路由，节省主模型上下文。触发条件：HuggingFace 出现作者 checkpoint。
  • ⚠️ P3｜检索接地奖励自用：把"rank 折减 recall"思路用于 Hermes 技能路由的离线评测分数（不训练，只当 metric），衡量"子任务描述能否把 gold 技能顶到检索前列"。
  • ❌ 暂不照搬工作流当生产路由：子步骤独立性假设在真实 Agent 任务（后步依赖前步输出）不成立，且 TaskBench 反例说明分解非普适最优；生产系统保持 Search-R1 式"边想边搜"兜底。
