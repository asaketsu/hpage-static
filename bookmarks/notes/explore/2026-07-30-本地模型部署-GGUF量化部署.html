1. 摘要

GGUF（GPT-Generated Unified Format）是 llama.cpp 团队推出的二进制模型文件格式，将模型权重、tokenizer、超参数打包为单文件，配合 k-quants 量化算法，使 7B-70B 级大模型可在消费级 GPU/CPU 上高效推理。相比旧版 GGML 格式，GGUF 支持增量加载、兼容性更好，已成为开源模型本地部署的事实标准。

2. 关键发现

GGUF vs GGML

  • GGUF 是 GGML v1 的继任者（2023年8月起），解决了旧格式每次架构变更都破坏向后兼容的问题
  • 关键改进：所有元数据集中在文件头，支持 KV-cache 量化，支持 mmap 内存映射加载

量化等级选择（核心决策）

k-quants 采用混合精度策略——不同层使用不同量化位数，兼顾速度和精度：

  • Q4_K_M — 甜点档位。7B 模型约 4.1GB，精度损失 <2%，推理速度最快。绝大多数场景首选
  • Q5_K_M — 精度优先。约 4.8GB（7B），精度损失 <1%，适合需要高质量输出的场景（代码生成、数学推理）
  • Q8_0 — 几乎无损。约 6.7GB（7B），精度损失可忽略，但速度/显存劣势明显，仅用于基准对比
  • Q3_K_M — 极限压缩。约 3.3GB（7B），精度损失 3-5%，仅适合显存极度受限的设备
  • Q2_K — 不推荐。精度损失显著（>8%），仅做可行性验证

经验法则：显存够用 Q5_K_M，显存紧张 Q4_K_M，两者覆盖 95% 场景。

llama.cpp 部署流程

# 1. 下载 GGUF 模型（HuggingFace 搜索 model-name-GGUF）
# 2. 编译 llama.cpp
git clone https://github.com/ggerganov/llama.cpp && cd llama.cpp
cmake -B build -DGGML_CUDA=ON  # NVIDIA GPU
cmake --build build --config Release

# 3. 量化（从 FP16 转 Q4_K_M）
./build/bin/llama-quantize model-fp16.gguf model-q4km.gguf Q4_K_M

# 4. 推理
./build/bin/llama-cli -m model-q4km.gguf -p "你好" -n 512 -ngl 99
# -ngl 99 = 全部层 offload 到 GPU

硬件适配参考（7B 模型 Q4_K_M）

  • Jetson Orin Nano（8GB） — 可运行，~3GB 权重 + 2GB KV-cache，剩余空间用于上下文。功耗 7-15W
  • RTX 3060 12GB — 舒适运行 7B，可勉强跑 13B Q4
  • CPU-only（32GB RAM） — 可运行但速度约 3-8 token/s，适合非实时场景
  • Apple M2/M3（16GB 统一内存） — Metal 加速，7B 可达 30+ token/s

3. 对工作的价值

  • 直接可用：Jetson Orin 上已有 nexa-local-inference Skill 使用 Ollama，底层正是 GGUF。理解量化等级选择可优化当前部署的精度/速度平衡
  • 成本优化：Q4_K_M 相比 FP16 减少约 75% 显存占用，同等硬件可部署更大模型或留出更多上下文空间
  • 与现有研究衔接：2026-07-30 推测解码笔记提到"7B+INT4+标准KV cache"作为 Phase 1 方案，GGUF Q4_K_M 正是这个 INT4 的具体实现路径

4. 行动建议

  1. 短期（本周）：检查 Jetson 上当前 Ollama 模型的量化等级，确认是否用 Q4_K_M。如果用了 Q8 或 FP16，降级到 Q4_K_M 可释放显存给更长上下文
  2. 中期：为 nexa-local-inference Skill 补充量化等级选择的决策树（显存预算 → 推荐量化档位）
  3. 长期：探索 GGUF + KV-cache 量化组合（--cache-type-k q4_0），在 Jetson 8GB 上进一步扩展可用上下文长度
