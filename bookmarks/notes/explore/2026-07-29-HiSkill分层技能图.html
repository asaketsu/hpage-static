HiSkill：用分层技能图赋能 LLM Agent 复用历史经验

来源：arXiv preprint 2607.25853
原文链接：https://arxiv.org/abs/2607.25853
作者：Yu Hao, Jinxuan Cai, Qi Zhang, Yawen Li, Zhiqiang Zhang, Chuan Shi, Cheng Yang（北京邮电大学 GAMMA 实验室）

标签：#LLM-Agent #技能图 #分层架构 #技能复用 #经验蒸馏 #知识图谱

论文一句话总结

HiSkill 将 Agent 历史交互轨迹蒸馏为分层有向技能图——高层 skill 节点 + 可执行 AtomicOp 节点 + 五种类型边（分解/时序/兼容/支撑/恢复），推理时只检索任务相关的紧凑子图引导执行，在三个交互环境中同时提升任务成功率和大幅降低 token 消耗。

一、内容详细整理

1.1 核心问题

现有 trajectory-to-skill 方法存在两大瓶颈：

  • 粒度鸿沟：生成的 skill 多为粗粒度文本策略（"先找到物体再操作"），与具体可执行动作之间缺乏连接
  • 关系缺失：skill 以扁平集合形式独立存储和检索，skill 之间的分解、时序转换、兼容性、支撑、恢复等关系未被利用

关键洞察：技能不是孤岛（呼应 HYSET 论文"Tools Are Not Islands"的核心理念）——技能之间和技能内部的丰富结构关系是长序列任务执行的核心资产。

1.2 分层技能图结构

HiSkill 构建的有向图 G=(V, E) 包含两类节点和五种类型边：

节点类型：
- Skill 节点 (V_S)：高层过程性抽象，存储有序 AtomicOp 序列 + 结构化元数据（适用状态、预期状态变化、代表性示例、参数候选、支持计数、失败提示）
- AtomicOp 节点 (V_O)：可执行动作模板，由原始动作经 schema-based canonicalizer 标准化（替换任务特定实体为占位符），去重合并后积累支持计数

五种类型边 L = {decomposes_to, can_follow, compatible_with, supports, recovers_with}：

  • decomposes_to：skill → AtomicOp，指定 skill 如何分解为有序可执行动作模板（最核心的结构边）
  • can_follow：skill→skill 或 AtomicOp→AtomicOp，由成功轨迹中有序共现统计归纳，捕获有向时序延续
  • compatible_with：skill↔skill，频繁共现于成功轨迹且前/后状态兼容，捕获无序技能组合（对称有向边）
  • supports：AtomicOp→skill，当 AtomicOp 频繁出现在 skill 上下文中且帮助满足缺失前提条件时建立
  • recovers_with：恢复 skill/AtomicOp → 失败/停滞的 skill/AtomicOp，从失败轨迹、重复无效动作、失败提示、缺失状态证据中推断

设计哲学：成功轨迹主要产生分解、时序、兼容、支撑关系；失败轨迹主要产生恢复关系——将"失败知识"显式编码进图结构。

1.3 图构建流水线

Step 1 — AtomicOp 提取：
- 从交互轨迹提取原始动作序列
- schema-based canonicalizer 解析动作 → 识别类型和参数 → 替换实体为占位符 → 生成标准化模板
- 去重合并相同模板，跨轨迹累积支持计数

Step 2 — Skill 发现：
- 从成功轨迹的 AtomicOp 序列中挖掘频繁动作模式
- 每个保留模式抽象为一个 skill 节点（含有序 AtomicOp 序列 + 结构化元数据）
- LLM 仅用于润色名称/描述等自然语言字段，不改变挖掘出的 AtomicOp 结构

Step 3 — 类型边归纳：
- 轨迹分区：T+（成功）和 T-（失败）
- decomposes_to：skill 到其有序 AtomicOp
- can_follow：有序共现统计
- compatible_with：频繁共现 + 前后状态兼容
- supports：高频上下文 AtomicOp → skill
- recovers_with：失败轨迹推断

1.4 任务相关子图检索

推理时不使用全图，而是检索紧凑子图 G_q = (V_q, E_q)：

种子节点检索：
- 检索查询 x_q = 任务描述 + 初始观察拼接
- 混合检索分数：score(v|q) = λ·Dense(x_q, d_v) + (1-λ)·Sparse(x_q, d_v)
- Dense = 余弦相似度（embedding），Sparse = BM25（词法匹配）
- skill 和 AtomicOp 节点分别排序，各取 top-K，并集作为 V_seed

图水合（Graph Hydration）：
- 对种子节点做一跳扩展：
- 顺 decomposes_to 方向扩展（获取 skill 的组成 AtomicOp）
- 逆所有非 decomposes_to 边方向扩展（获取指向种子的前置/support/recovery 关系）
- 保留子图内所有类型边

1.5 子图引导的任务执行

运行时逐步执行，维护两个核心状态：

  • 任务状态 z_t：符号 key-value 内存，记录执行相关证据（任务进度、持有物体、当前位置、已访问实体）。状态更新：z_{t+1} = UpdateState(z_t, a_t, o_{t+1})

  • 活跃技能 s_t：当前执行锚点，通过 decomposes_to 边关联有序 AtomicOp 序列

每步决策逻辑：
- 技能切换：技能完成时，通过 can_follow 或 compatible_with 边选后继；执行卡住或重复失败时，通过 recovers_with 边切恢复技能
- AtomicOp 选择：默认从活跃技能的 decomposes_to 边取下一个未执行 AtomicOp；前提缺失时走 supports 边选支撑操作；卡住时走 recovers_with 边选恢复操作；均不适用时允许 LLM 直接出动作
- 动作接地：将选中的 AtomicOp 模板结合当前状态生成具体可执行动作

二、查询拓展

2.1 Anthropic Agent Skills 与 SKILL.md 体系

论文 Related Work 明确引用了 Anthropic 的 Agent Skills（SKILL.md 文件系统）作为手工技能的代表。HiSkill 的创新在于从轨迹自动构建技能图，而 Hermes Agent 当前使用的 SKILL.md 体系属于手工编写、扁平检索的模式。HiSkill 的类型边框架（尤其 decomposes_to 和 recovers_with）可直接指导 SKILL.md 之间的关系建模。

2.2 Graph of Skills (GoS) vs HiSkill

GoS 是最接近的 baseline（离线技能依赖图 + 语义-词法种子 + Personalized PageRank），但它只检索"技能级"依赖包，缺乏 AtomicOp 级的可执行动作连接和恢复边。消融实验中 GoS 的 OurG+GoSUse 和 GoSG+OurUse 交叉实验证明：HiSkill 的子图检索（OurG）和执行引导（OurUse）各有独立价值，组合使用效果最优。

2.3 Voyager 的技能库演进

Voyager（Minecraft）维护不断增长的代码技能库，与 HiSkill 的 AtomicOp 节点理念相似。但 Voyager 是扁平代码技能列表，无图结构和类型边。HiSkill 的五边类型设计是对"技能间关系建模"的形式化突破。

2.4 五种类型边的形式化创新

这五种边覆盖了长序列交互任务的完整生命周期：
- decomposes_to 解决"从策略到执行"的粒度鸿沟
- can_follow + compatible_with 解决"技能编排"问题
- supports 解决"前置条件补全"
- recovers_with 解决"错误恢复"——这是现有方法极少显式建模的关系

三、归纳总结

3.1 核心架构框架

┌─────────────────────────────────────────────┐
│          分层技能图 G = (V, E)               │
│                                              │
│   V_S (Skill)  ←──compatible_with──→ V_S    │
│       │                  │                   │
│   decomposes_to      can_follow              │
│       ↓                  ↓                   │
│   V_O (AtomicOp) ←─can_follow─→ V_O         │
│       │                                      │
│   supports↑     ↑recovers_with              │
│       │              │                       │
│   V_O→V_S    V_S/Op→V_S/Op(失败)            │
└─────────────────────────────────────────────┘
           ↓ 子图检索 (种子+水合)
┌─────────────────────────────────────────────┐
│     任务相关子图 G_q + 任务状态 z_t          │
│          + 活跃技能 s_t                      │
│           ↓ 执行循环                         │
│  状态更新 → 技能切换 → AtomicOp选择 → 接地   │
└─────────────────────────────────────────────┘

3.2 与现有方法的定位对比

  • Prompt-based（ReAct/Reflexion）：纯推理，无历史经验复用 → 不稳定
  • Memory-based（ExpeL/Mem0/MemP）：存储文本记忆/摘要/轨迹片段 → 缺少高层过程+可执行动作+执行关系的统一组织
  • Skill-based（Vector Skills/SkillNet/GoS）：技能级检索/依赖 → 缺少 AtomicOp 接地和恢复关系
  • HiSkill：skill + AtomicOp + 五种类型边的统一分层图 + 运行时状态引导

四、关键实验结果

4.1 主实验（Gemini-2.5-Pro 骨干模型）

ALFWorld（具身家庭操作）平均成功率：
- 最强 baseline：ExpeL 55.40%（Seen）/ MemP 64.43%（Unseen）
- HiSkill：77.50%（Seen）/ 88.72%（Unseen）

WebShop（网购交互）：
- Score：77.50（HiSkill）vs 69.73（ExpeL 最强）
- Succ：67.60%（HiSkill）vs 55.40%（ExpeL 最强）

ScienceWorld（科学实验）：
- Seen Score：84.20 vs 67.20（MemP 最强）
- Unseen Score：84.02 vs 64.05（MemP 最强）

相比所有数据集和分割中的最强 baseline，HiSkill 平均成功率提升 17.33%，平均分数提升 22.95%。

4.2 Token 消耗分析（核心亮点）

HiSkill 在所有数据集和分割上 token 消耗一致最低：
- ALFWorld Seen：6,462 tokens（最低 baseline ExpeL 15,173 → 降低 57.4%）
- WebShop：4,501 tokens（最低 baseline SkillNet 77,731 → 降低 94.2%）
- ScienceWorld Seen：7,747 tokens（最低 baseline ExpeL 24,246 → 降低 68.0%）

相比各场景最低 token baseline，HiSkill 在 ALFWorld/WebShop/ScienceWorld 分别降低 61.10%/94.12%/66.76%。性能提升不是靠更长轨迹或更大内存，而是紧凑的子图表示。

4.3 消融实验

  • w/o AtomicOp（去 AtomicOp 节点）：ALFWorld Seen 87.14%（-7.15pt），ScienceWorld Seen 78.20%（-5.84pt）
  • w/o Edge（去所有类型边）：84.29%（-10.0pt），ScienceWorld 73.46%（-7.58pt）
  • w/o Sup./Rec.（去支撑+恢复边）：87.86%（-6.43pt）
  • w/o State（去任务状态）：86.42%（-7.87pt）
  • Static Subgraph（用全子图替代动态检索）：75.00%（-19.29pt）
  • Top-K Prompt（直接给 top-K skill 文本不用子图）：66.43%（-27.86pt）
  • Full HiSkill：94.29%

结论：每个组件都有独立贡献，动态子图检索贡献最大（-19pt），其次类型边（-10pt）。

4.4 交叉消融

  • OurG + GoSUse（HiSkill 子图 + GoS 执行）：80.00%
  • GoSG + OurUse（GoS 子图 + HiSkill 执行）：72.86%
  • Full（HiSkill 子图 + HiSkill 执行）：94.29%

HiSkill 的子图检索和执行引导各有独立价值，但组合使用产生协同效应（94.29 > 80.00）。

五、趋势判断

趋势1：技能图从扁平集合向结构化图演进是必然方向

依据：GoS→HiSkill→HYSET 三条线均在2026年从"独立检索"升级为"图结构建模"，SkillNet/SkillsBench 等基础设施也在向生态级管理演进。扁平技能库的天花板已被触及。

趋势2：失败知识的显式编码将成为 Agent 系统标配

依据：HiSkill 的 recovers_with 边、Reflexion 的文本反思、Hermes evolver 的错误规则——三条路径都在解决"从失败中学习"，但 HiSkill 首次将其形式化为图结构边而非文本，可计算性更强。

趋势3：紧凑子图注入将取代全量上下文加载

依据：HiSkill 用子图检索实现 94% token 降低同时提升性能，证明了"注入更多上下文≠更好性能"。这对边缘部署（Jetson）和长会话 Agent 都有深远影响——上下文管理从"塞满窗口"转向"精准检索"。

趋势4：Agent 技能生态正在形成完整技术栈

依据：SkillsMP/ClawHub/LangSkills 做打包发布，SkillsBench 做评测，SkillNet/AgentSkillOS 做编排，HiSkill 做分层执行——2026 年 Agent 技能生态已接近 2020 年容器生态的成熟度。

六、创新点分析

  1. 统一的分层技能图：首次将高层 skill、可执行 AtomicOp、以及五种类型关系统一进单一有向图结构，弥合了策略到执行的粒度鸿沟

  2. 显式恢复关系建模：recovers_with 边从失败轨迹中提取恢复知识，将"从错误中学习"从反思文本升级为结构化图边——这是现有技能方法极少覆盖的维度

  3. 紧凑子图 + 动态执行：不注入全图或全记忆库，而是检索紧凑任务子图 + 运行时状态引导，实现 94% token 降低的同时提升性能

  4. 混合检索种子 + 图水合：Dense + BM25 混合检索种子节点，一跳方向性扩展——兼顾语义相关性和图结构完整性

  5. LLM 角色最小化：LLM 仅润色自然语言字段和做执行时决策，不改变挖掘出的 AtomicOp 结构——降低 LLM 主观性对技能质量的影响

七、局限性与未来方向

局限性

  • 离线图构建：技能图在训练阶段一次性构建，不支持在线增量更新。论文 Future Work 明确提出"online skill graph evolution"方向
  • 静态轨迹来源：依赖预收集的成功/失败轨迹，不具备自主探索新技能的能力
  • 符号状态依赖：任务状态 z_t 是符号 key-value 内存，需要环境提供结构化状态信号，泛化到纯文本交互环境可能受限
  • 三环境评测局限：ALFWorld/WebShop/ScienceWorld 都是受控文本交互环境，未验证真实世界或多模态场景
  • 代码尚未公开：GitHub 仓库为空，无法验证工程实现细节

未来方向（论文明确提出）

  • 在线技能图演进（online skill graph evolution）
  • 自适应技能精炼（adaptive skill refinement）
  • 更开放交互场景的扩展

八、借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

P0 — Hermes Agent 技能图关系建模

HiSkill 的五种类型边框架可直接应用于 Hermes Agent 的 SKILL.md 体系：

  • decomposes_to 等价：Hermes 当前 SKILL.md 内部步骤分解已经是手工版 decomposes_to。可进一步显式建模 Skill → 工具调用的标准化模板链
  • recovers_with 等价：Hermes 现有的 pitfall 章节是手工版 recovers_with 的文本形态。可升级为结构化"失败→恢复"技能边，实现自动错误恢复路由
  • can_follow / compatible_with：Hermes 的 skill chaining（如 daily-paper-reading → note-dual-format → auto-md2html）可形式化为 can_follow 边，使编排更可靠
  • supports：辅助工具（如 extract_arxiv.py）对核心技能的支撑关系可显式建模

P1 — 紧凑上下文注入策略

HiSkill 的核心教训是不注入全图，只注入任务相关子图，就能同时提升性能和降低 token。对应到 Hermes：
- 当前加载 skill 是全量 SKILL.md（部分长达数千字），可借鉴子图检索模式：按任务描述检索 skill 的关键章节 + 关联工具签名，而非全量加载
- Hybrid 检索公式（λ·Dense + (1-λ)·BM25）可直接实现为 skill 检索引擎

P1 — 失败轨迹结构化复用

HiSkill 从失败轨迹提取 recovers_with 边的理念，与 Hermes 的 evolver skill（错误模式→规则沉淀）高度互补：
- evolver 当前将错误沉淀为文本规则，可升级为结构化"错误模式→恢复策略"映射
- 借鉴 HiSkill 的五信号推断：失败轨迹、重复无效动作、失败提示、缺失状态、语义匹配

P2 — Jetson 边缘部署启示

HiSkill 的紧凑子图表示使 token 消耗降低 94%，这对 Jetson 等边缘设备上的 Agent 推理尤为重要：
- 边缘 Agent 的上下文窗口和推理速度受限，子图检索可大幅减少 prompt 长度
- AtomicOp 模板化（实体替换为占位符）适合在边缘设备上预编译常用工具调用模式

P3 — 量化交易技能编排

量化交易的多步骤工作流（行情获取 → 指标计算 → 信号检测 → 风控检查 → 下单执行）天然适合 skill 图建模：
- can_follow 边编码工作流时序
- recovers_with 边编码风控恢复（如信号失效→撤单→重算）
- 但量化场景对时延极敏感，图检索的 overhead 需要优化
