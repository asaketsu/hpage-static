一、核心问题与研究动机

1.1 问题定义

紧凑语言模型（1.5B–4B 参数）在部署工具代理时有一个被严重低估的失败模式：

生成的工具工作流图"看起来合理"但执行必崩。

具体崩溃点包括四个维度：

  • 工具解析失败 — 从动态 catalog 中找到的工具与 planner 预设的不一致
  • 参数验证不通过 — schema 不匹配、缺少必需参数、类型错误
  • 依赖追踪断裂 — 中间步骤输出没有被正确传递给后续步骤
  • 执行证据缺失 — 最终回答没有基于真实执行结果

1.2 为什么小语料蒸馏解决不了

传统方法用几百条教师 trace 做 SFT/DPO 蒸馏，但存在致命缺陷：

  • 教师轨迹能教会工作流格式，但无法覆盖恢复行为
  • 工具 catalog 是动态变化的，教师轨迹中的工具组合可能已过时
  • 小模型从固定轨迹中学到的是"记忆"而非"推理"，遇到新工具组合直接崩溃

核心论点：在教师轨迹稀缺的预算下，执行驱动的搜索比权重更新更可靠。

1.3 与现有方法的区别

方法 核心思路 问题
ReAct 逐步推理+行动，边做边修正 方差高、token 消耗大
SFT 用教师轨迹微调权重 覆盖面不足，无法处理动态 catalog
SFT+DPO 在 SFT 基础上做偏好优化 甚至可能崩溃到零样本以下
Evoflux 推理时进化搜索修复工作流 无需更新权重，执行驱动

二、方法论（详细）

2.1 核心思想：将工具调用重构为"可执行工作流修复"

Evoflux 不是让模型一次性生成正确的工具调用序列，而是：

  1. 先用 planner LLM 生成一个初始工作流图（可能不正确）
  2. 实际执行这个图，收集失败信息
  3. 基于失败信息，通过进化搜索迭代修复工作流
  4. 最终选择执行成功率最高的变体

2.2 类型化工作流图（Typed Workflow Graph）

论文定义了一套完整的 DSL（领域特定语言）来表示工具工作流：

节点类型 (NodeType)：
- tool — 工具调用节点
- validator — schema 校验节点
- router_hint — 路由提示节点
- cache — 缓存节点
- output — 输出节点

图结构 (GraphTemplate)：

Node {
    node_id: str              # 唯一标识
    kind: NodeType            # 节点类型
    tool_ref: (server, tool)  # MCP 服务器 + 工具名
    params: Dict              # 调用参数
    requires: List[node_id]   # 前置依赖
    produces: Dict            # 输出变量绑定
}

每个查询对应一个完全实例化的工作流图，由 LLM planner 为该特定查询生成。

2.3 结构化编辑算子（TypedEdit）

进化搜索通过六种原子操作来变异工作流图：

  • swap_tool — 替换节点的工具调用（换一个 MCP server 或 tool）
  • insert_validator — 在某节点后插入 schema 校验节点
  • set_param — 修改执行参数（如 strict_schema=False）
  • add_tool_step — 添加新的工具调用步骤
  • remove_tool_step — 删除节点及相关边
  • reorder_step — 重排执行顺序（修改 requires 依赖列表）

设计洞察：编辑始终相对于 LLM 生成的基础计划。一个 Action = (查询, 编辑序列, 执行策略) 三元组。

2.4 进化搜索循环

初始化: Planner LLM → 基础 GraphTemplate → 初始 Candidate
循环 (B 轮迭代, K 个候选):
  1. 选择: 从种群中选出最佳父代 (parent)
  2. 证据收集: 从父代执行结果中提取失败节点
  3. 变异: LLM 提出针对性 TypedEdit
     ↓ (LLM 失败时回退到随机编辑)
  4. 编译: 应用编辑 → CompiledWorkflow
  5. 静态检查: schema 校验 + 依赖完整性
  6. 执行: 在真实 MCP 服务器上运行
  7. 评分: 基于 MetricBreakdown 多维评分
  8. 公平比较 (CRN): 父子代用相同随机种子
  9. 接受/拒绝: 子代优于父代则替换
  10. 多样性剪枝: 保持种群多样性

2.5 关键工程细节（从源码提取）

Common Random Numbers (CRN) 公平比较机制：
- 每次比较父子代时，fork 一个全新的 executor
- 父子代看到完全相同的扰动（相同的随机种子、相同的工具 catalog 状态）
- 确保评分差异只来自工作流本身，而非随机性

证据引导的变异 (Evidence-Guided Mutation)：
- 从 D_fb（反馈数据集）中收集每个节点的错误率
- 变异时优先针对高频失败节点
- _mutate() 调用 planner.propose_edit(query, failing_nodes, graph)
- LLM 收到的是："针对这些失败节点，哪个单次修改最能改善工作流？"

AdaEvolve 自适应强度：
- 维护每个查询的增长信号 G_t（growth signal）
- 追踪局部最优 f_k*（local best）
- 当改进停滞时自动调整进化强度

LLM 引导变异 + 随机回退：
- 优先用 LLM 生成针对性编辑
- LLM 调用失败（无凭证、解析错误等）时自动回退到随机算子选择

2.6 执行评估指标（MetricBreakdown）

评估候选时使用多维指标分解：

  • feasibility — 工作流是否可执行（工具存在、schema 通过、依赖完整）
  • execution_result — 实际执行输出质量
  • score — 综合评分（用于选择）
  • feasibility_reasons — 失败原因列表（用于指导后续变异）

三、关键实验结果与数据

3.1 核心结果：执行可行性大幅提升

在 MCP-Bench（250 个工具，真实 MCP 服务器）上：

  • 零样本基线: ~3% 执行可行性
  • Evoflux: 17–24% 执行可行性（5–8 倍提升）
  • SFT: 与零样本持平或更差
  • SFT+DPO: 部分配置崩溃到零样本以下
  • ReAct: 峰值更高，但方差极大、token 消耗高

3.2 关键发现：微调的崩溃现象

SFT 和 SFT+DPO 在搜索挖掘的相同数据上训练，结果只是匹配、低于、甚至崩溃到零样本以下。

这是一个被严重低估的风险：小模型在小语料上做 SFT/DPO 微调，不仅没有提升，反而可能破坏预训练阶段获得的能力。

3.3 搜索 vs 微调的权衡

维度 Evoflux (搜索) SFT/DPO (微调)
教师轨迹依赖 不需要 需要几百条
适应新工具 ✅ 自动适应 ❌ 需重新训练
推理成本 较高（多轮执行） 低（单次推理）
可靠性 高（执行驱动） 低（可能崩溃）
部署灵活性 无需训练 需要 GPU 训练

3.4 实验配置

  • 模型: Qwen/Qwen2.5-7B-Instruct (planner), openai/gpt-oss-20b (judge)
  • 推理引擎: vLLM (双服务器: planner :8000, judge :8001)
  • 进化参数: B=5 (迭代预算), K=10 (种群上限), max_steps=15
  • 基准: MCP-Bench (complexity: single / 2server / 3server / all)

四、创新点分析

4.1 范式转变：从"一次性调用"到"工作流修复"

传统工具调用范式让模型一次性输出完整的工具序列。Evoflux 将其重构为：
- 生成 → 执行 → 发现失败 → 修复 → 重新执行
- 这是一个闭环反馈过程，而非开环预测

4.2 类型化编辑系统

六种 TypedEdit 算子覆盖了工作流修复的所有关键操作类型。这种结构化的变异空间比 ReAct 的自由文本推理更可控、更可验证。

4.3 执行驱动的评估

不依赖教师标注或代理指标，直接以真实执行结果作为适应度函数。这确保了进化搜索优化的方向与实际部署目标完全一致。

4.4 无需权重更新

整个方法在推理时运行，不修改模型权重。这意味着：
- 任何模型都可以直接使用（包括闭源 API 模型）
- 工具 catalog 变化不需要重新训练
- 可以与任意 planner 模型组合

五、局限性与未来方向

5.1 当前局限

  • 绝对成功率仍低 — 从 3% 提升到 17-24% 虽然是巨大进步，但仍有 75%+ 的查询失败
  • 延迟开销 — 多轮执行+变异带来显著的推理时间成本（论文未详细报告）
  • Token 消耗 — 进化搜索需要多次 LLM 调用，token 成本远高于单次推理
  • 仅验证了 MCP-Bench — 单一基准的结果可能不够普适
  • 搜索预算 B=5 较小 — 更大的搜索预算是否带来更多收益未充分探索

5.2 未来方向

  • 搜索+微调混合 — 用 Evoflux 搜索轨迹生成更高质量的训练数据，再微调
  • 迁移到更大模型 — 7B 以上的模型是否仍受益于进化搜索
  • 自适应搜索预算 — 根据查询难度动态分配 B 和 K
  • 并行搜索 — 多个候选并行执行，降低延迟
  • 编辑算子学习 — 从搜索历史中学习哪些编辑类型更有效

六、借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

🔨 P0 — 工作流重试与自修复机制

借鉴点: Evoflux 的"执行→失败→修复→重试"闭环

Hermes 现状: 工具调用失败时，当前是简单重试或直接报错

可落地方案:
- 在 Hermes 工具调用失败时，不直接重试相同调用
- 而是分析失败原因（参数错误？工具不存在？依赖断裂？）
- 基于失败原因自动生成修复编辑（换工具、改参数、加校验）
- 实现 1-2 轮修复循环后再上报错误

工作量: 2-3 天（需要失败分类器 + 修复策略映射表）

🔨 P1 — 类型化工作流图作为 Skill 编排中间层

借鉴点: TypedEdit 的六种结构化编辑算子

Hermes 现状: Skill 链式调用靠 CoT 推理决定，无结构化编排

可落地方案:
- 将 Hermes 多步骤任务表示为 TypedWorkflowGraph
- 支持 swap_skill（替换技能）、insert_check（插入验证步骤）、reorder（调整顺序）等编辑
- 在任务执行失败时，自动尝试编辑变体

工作量: 5-7 天（需要设计 SkillGraph DSL + 编辑算子实现）

⚠️ P2 — 证据引导的变异策略

借鉴点: 从执行结果中提取失败节点，针对性变异

Hermes 现状: 错误处理缺乏结构化的"失败归因→修复策略"映射

可落地方案:
- 对每次工具调用失败记录详细的失败类别和节点信息
- 建立失败类别→修复策略的映射表
- 长期积累形成"故障修复知识库"

工作量: 3-5 天

⚠️ P3 — 进化搜索用于 Cron Job 优化

借鉴点: 进化搜索的多样性剪枝和自适应强度

量化交易场景: 策略参数搜索可借鉴进化搜索框架

可落地方案:
- 将策略回测建模为"工作流执行"
- 用 TypedEdit 算子变异策略参数（swap_indicator, set_param, reorder_step）
- 保留多样性剪枝避免过拟合

工作量: 7-10 天（需要适配量化交易的数据结构）

❌ 暂不适用 — 紧凑模型推理

原因: Hermes 当前使用云端大模型（GLM-5.1），不在 Jetson 上跑紧凑模型做工具调用。但未来如需边缘部署自主工具代理，此方法直接可用。
