## 核心问题与研究动机

### 问题：Agent 推理中的工具等待瓶颈

LLM Agent 的 Thought-Action-Observation 循环是**严格串行**的：

```
[Prefill] → [Decode CoT] → [Emit Tool Call] → [WAIT: 工具执行] → [Resume Decode] → ...
```

工具执行期间 GPU 完全空闲。论文实测三个 benchmark：
- tau2-bench: 工具耗时占 **16%**（企业 DB API，2s 模拟延迟）
- GAIA: 工具耗时占 **19%**（真实 web 搜索 API）
- BrowseComp: 工具耗时占 **37%**（web 搜索 + 页面浏览）

更关键的是：**随着 LLM 推理越来越快（speculative decoding、硬件扩展、disaggregated serving），工具等待的占比只会增加**，成为 Agent 延迟的渐近瓶颈。

### 现有方案的不足

| 方案 | 局限 |
|------|------|
| Token-level speculative decoding | 加速 decode 但不提前 dispatch 工具调用 |
| Parallel tool calling | 仅 15-25% 的工具调用可并行 |
| Workflow optimizers | 需要静态执行图，Agent 调用是动态生成的 |
| Speculative Actions / DualSpec / PASTE | 依赖辅助预测器、验证策略或历史 trace |

**SPORK 填补的空白**：无需训练、无需辅助模型、无需历史 trace，从模型自身状态推测工具调用。

## 方法论：自推测工具使用

### 核心洞察

论文提出三个实证发现（基于 Qwen3-32B，五个 benchmark）：

**Insight 1 — 模型在完成推理前就已"知道"下一个工具调用**

在第一个 decode token 处强制 fork 一个 tool-call probe，预测准确率：
- GAIA: 98.3%（tool name）
- tau2-bench: 74.6%
- BrowseComp: 83.7%
- HotpotQA: 99.6%
- BFCL: 99.2%

参数精度（argument exact-match）较低且波动大（7.6-83.9%），因为精确参数值需要 CoT 推理才能确定。

**Insight 2 — 置信度随 CoT 推进单调上升**

- Fork-at-start: 参数精确率 7.6%
- 80% CoT: 61.0%
- Think-end: 97.5%

Logprob 可分离正确/错误预测：正确预测 mean span probability 0.90 vs 错误 0.46。无需训练分类器。

**Insight 3 — 被拒绝的 probe 仍包含已验证前缀**

即使 strict gate 拒绝了 probe（参数不匹配），probe 的 tool-call token 序列仍与最终调用共享长前缀，可作为 speculative decoding 的 draft tokens 回收利用。

### 成本模型（EQ1）

```
Ratio = T_base / (T_base* - α · t_overlap + T_oh)
```

- **α**: gate 接受率（工具名匹配的 turn 占比）
- **t_overlap**: 每个 accepted turn 的平均重叠时间
- **T_base***: 推测路径的实际 decode 成本（prefix recovery 降低）
- **T_oh**: probe 计算和浪费的推测执行开销

**Break-even 条件**: α · t_overlap ≥ T_oh

**理论上限**: Ratio = 1 / (1 - f_tool)，BrowseComp 的 f_tool=0.366 对应 1.58× 加速上限。

### SPORK 设计（D1-D2-D3）

**D1: Prefix-Cache Fork（最小化 T_oh）**
- 主 stream 第一个 token 后 fork probe
- Probe 复用主 stream 的 prefix KV cache，prefill 成本从 1.3s 降到接近 0
- Probe 仅 decode tool-call body（≤50 tokens），成本 ~0.3s
- 总 overhead: probe 从 1.6s 降到 0.35s

**D2: Adaptive Confidence Gate（最大化 α · t_overlap）**
- 监控 probe 的 logprob（min span probability over tool-name tokens）
- 置信度超过阈值 θ 时 commit 推测性工具执行
- 多次 retry：每解码 s 个 CoT token 后重新 fork，直到 gate 通过或主 stream 完成
- 动态平衡：早期 commit = 更大 overlap 窗口但更低的 α；晚期 commit = 更高 α 但更小窗口

**D3: Partial-Token Accept（降低 T_base*）**
- 被拒绝 probe 的 verified prefix 注入为 speculative decoding draft tokens
- 主 stream 只需 re-decode 第一次 mismatch 之后的 token
- 利用 vLLM 的 ngram proposer path 实现

### 执行流程

```
1. 主 stream 开始 streaming chat-completion
2. 第一个 token 到达后，fork 一个 forced tool-call prefix 的 completions 请求 (D1)
3. 监控 fork 的 logprob，达到阈值 θ 后 dispatch 推测性工具执行 (D2)
4. 主 stream 完成工具调用时，与 probe 对比：
   - 匹配 → 使用预计算结果（延迟被隐藏）
   - 不匹配 → 串行回退（D3 将 probe token 作为 draft 回收）
```

## 关键实验结果

### 端到端延迟（P95）

- **GAIA (Qwen3-32B)**: P95 降 18%（131.9s → 108.1s，真实 web 搜索）
- **tau2-bench (Qwen3.5-35B-A3B)**: P95 降 16%（59.4s → 49.8s）
- **HotpotQA (Qwen3.5-35B-A3B)**: P95 降 19.7%（18.9s → 15.2s）
- **tau2-bench (Qwen3-4B)**: mean 加速 1.15×

### 质量保持

- 所有配置中 EM/F1 在 baseline ±1pp 范围内
- HotpotQA (Qwen3-32B) 甚至提升 +1.5pp EM
- Strict gate 保证对话历史永不被推测性副作用污染

### Ablation 贡献分解

- **Ngram spec-dec（baseline）**: P50 降 31%（token-level 加速）
- **D1 on ngram**: 额外 P50 降 12%，mean 降 10%
- **D1+D2+D3**: 最佳 P95 降 18%
- 各组件正交于 token-level speculative decoding，可叠加

### 操作包络

- 工具延迟 ≥2s 时加速显著（GAIA 4.8s → 最大收益）
- 工具延迟 ~1s 时接近 break-even（HotpotQA 0.9s → 微正收益）
- EQ1 成本模型预测误差 ≤1.84%
- **Think mode 是关键**：CoT ≥2s 创造 overlap 窗口；no-think mode（0.3-0.9s decode）无足够窗口（0.79× = 略有负面影响）

### Self-Speculation vs Draft Model

- 自推测 vs Qwen3-4B 交叉模型 probe
- 自推测参数精确率更高（tau2: 0.792 vs 0.590）
- 自推测浪费更少的推测工具调用（154 vs 317 at N=155）
- 自推测无需额外 GPU（避免 KV cache 竞争）

## 创新点分析

1. **自推测范式**：首次提出用运行中的模型自身作为工具调用预测器，无需任何外部依赖（辅助模型、历史 trace、静态执行图）。这是对 CPU 分支预测器思路的类比——但预测源是模型自身。

2. **Cost Model（EQ1）的工程价值**：将推测效益分解为四个可测量参数（α, t_overlap, T_base*, T_oh），提供明确的 break-even 判断条件和理论上限。可指导部署决策。

3. **三机制分层设计**：D1（prefix-cache fork）、D2（confidence gate）、D3（partial-token accept）各自独立优化 EQ1 的一项，可组合使用，也可单独部署。

4. **Lossless 保证**：Strict gate 确保只有完全匹配的 probe 才被接受，对话历史永不被推测性副作用污染。被拒绝的 probe 通过 D3 转化为有用的工作（speculative decoding drafts）。

5. **Think Mode 的关键发现**：只有当模型产生足够长的 CoT（≥2s）时，probe 才有时间完成并创造 overlap 窗口。这意味着 thinking model 天然适配 SPORK。

## 局限性与未来方向

### 局限性

1. **仅支持 read-only 工具**：write/非幂等操作无法回滚，暂不支持推测。需要 sandboxing 或 agent-state checkpointing。

2. **依赖 open-weight 模型**：需要 serving engine 暴露 per-token logprobs 和 completions endpoint，闭源 API 无法 fork probe。

3. **重负载下收益缩小**：高并发 batch 时 probe 竞争前景 decode 资源，overlap 收益降低。

4. **No-think mode 无效**：CoT 太短（0.3-0.9s），probe 来不及完成。

5. **参数精度限制**：虽然 tool name 准确率高（>74%），但参数精确率差异大（7.6-83.9%），某些场景需要多次 retry。

### 未来方向

- **Write tool 支持**：通过 sandboxing/checkpointing 实现可回滚的推测写操作
- **空闲 batch slot 调度**：将 probe 调度到空闲 batch slot，进一步降低 T_oh
- **更深的引擎集成**：原生 vLLM 集成而非 wrapper

## 借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

### P0 — 可直接评估的改进

**1. Hermes Agent 工具调用延迟优化（最高价值）**
- Hermes Agent 的 ReAct 循环（read_file → search → terminal → patch）完全符合 SPORK 的目标场景
- 工具调用（terminal 执行命令、web_search 搜索、web_extract 抓取页面）延迟通常 2-30s，远超 break-even 阈值
- 可评估：在 Hermes Gateway 层面实现类似 probe 机制，在 Agent 产出 CoT 时提前 dispatch 可预测的工具调用
- 现有能力覆盖：无直接对应 skill。context-engineering-patterns 涉及工具输出修剪但不涉及提前 dispatch

**2. Think Mode Agent 的 overlap 窗口**
- GLM-5 的 thinking 模式产生较长 CoT，天然适合 SPORK 的 overlap 窗口
- 可评估：记录 Agent turn 中 CoT decode 时间 vs 工具执行时间的比例，确认 break-even 条件是否满足

### P1 — 工程改造后可用

**3. Prefix-Cache Fork 模式用于成本优化**
- D1 的 prefix-cache fork 技术可用于任何需要"快速预测下一步操作"的场景
- 量化交易中：预测下一步数据查询（行情 API / 历史数据）时可提前 dispatch
- 障碍：需要 vLLM 级别的 prefix cache 共享，Jetson 本地推理（Ollama）可能不支持

**4. Confidence Gate 用于 Agent 决策**
- D2 的 logprob-based confidence gate 可用于 Hermes Agent 的工具选择置信度评估
- 置信度低时可触发更保守的策略（如等待更多 CoT、不提前 dispatch）

### P2 — 参考价值

**5. 成本模型框架用于 Agent 性能分析**
- EQ1 的四参数分解（α, t_overlap, T_base*, T_oh）是通用框架
- 可用于分析 Hermes Agent 的任何优化措施是否值得
- 与 context-engineering-patterns 中的工具输出修剪互补

**6. Strict Gate 无损保证**
- Strict gate（只有完全匹配才接受）是安全设计的典范
- 可用于 Hermes Agent 的任何推测性操作（如 cache 预热、预加载 skill）

### P3 — 暂不适用

**7. D3 Partial-Token Accept**
- 需要 vLLM speculative decoding proposer path 的深度集成
- Hermes Agent 当前不是自托管 vLLM 部署，不直接适用
