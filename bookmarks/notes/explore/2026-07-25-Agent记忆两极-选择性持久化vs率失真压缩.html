一、为什么这周密集出现"记忆"论文？

最近 30 天内，arXiv cs.AI 上至少 6 篇论文从不同角度攻击同一个问题：Agent 在多轮/多会话中应该保留什么、丢弃什么。这不是巧合——生产级 Agent 普遍撞上了同一堵墙：

  • McKinsey 2025：企业 Agent 试点中只有 ~25% 进入扩展阶段，<10% 单业务规模化。首要失败原因不是推理能力，而是上下文管理。
  • 全历史持久化的反效果：2607.09493 实测，把上一轮对话全部塞回去，任务完成率从 79%（无记忆）降到 71%——比什么都不记还差。原因：无关甚至已过期的推理轨迹会"带偏"模型。

这两篇论文代表了 2026 年中两个最值得关注的解题思路。

二、论文 A：Shared Selective Persistent Memory（选择性共享持久记忆）

核心洞察

"全记"和"全忘"都是错的，正确做法是只持久化"可复用上下文"这一窄类。

作者将 Agent 会话中产生的信息分成两类：

类别 说明 处理方式
可复用上下文（Reusable Context） 任务规范、数据 schema、工具配置、输出约束 持久化，跨会话保留
会话特定推理轨迹（Session-specific Traces） 具体的思考链、试错过程、中间状态 丢弃，不保留

架构亮点

  1. 共享（Shared）：记忆被封装成 workspace，可通过 RBAC（角色权限）在不同用户间转移。A 用户配置好的"SQL schema + 工具约束"可以直接给 B 用户复用，无需重新指定。
  2. 零令牌数据刷新（Zero-token Refresh）：生成出的代码/查询与运行时数据解耦。当底层数据更新时，直接用缓存的程序重新跑数据，不需要重新调用 LLM。
  3. Git 版本化：所有 Agent 产物（dashboard、report）都 git 版本控制，可回溯。

实测数据（3 个企业场景 + 4 个公开数据集复现）

配置 任务完成率
无记忆 79%
全历史持久化 71%（反而更差）
选择性持久记忆 96%
  • 零令牌刷新：周期性数据更新场景下，任务时间缩短 14×，完全免去 LLM 重调用。
  • 摘要驱动生成：相比直接注入原始数据，单次调用 token 成本降低 97×。
  • 公开数据集复现：12/12 次零令牌刷新成功。

关键启示

  • "记更多"不等于"更好"。Agent 的记忆系统应该像数据库的视图（view）——只暴露当前任务需要的、稳定的元信息，而非原始日志。
  • Hermes 这类多会话 Agent 可以借鉴：把 skill 配置、项目 schema、工具偏好抽成持久 workspace，而把每轮 CoT 轨迹视为临时。

三、论文 B：Rate–Distortion 统一视角（率失真框架）

核心洞察

KV-Cache 驱逐、Prompt 压缩、架构状态裁剪、Agent 长期记忆——这四个看似独立的研究领域，本质上是同一个率失真问题。

作者指出，整个 AI 栈不同层都在做同一件事：在资源预算下，决定保留哪些上下文衍生信息、以什么保真度保留，以最大化下游任务效用。

七轴分类法

论文提出一个跨层统一的七维度分类，把来自推理引擎、模型架构、Agent 框架的方法放进同一张表里比较。这本身就是一个贡献——以前 KV-Cache 论文不引用 Agent 记忆论文，反之亦然。

两个横跨全栈的规律

  1. "保留信号"到处都一样，且到处都失败：每一层决定"留什么"的信号都是注意力大小（attention magnitude）或近因性（recency）。而这个信号在查询未知时就做了不可逆的丢弃决策，等真正的 query 到来时，需要的信息已经被扔了。
  2. 重复压缩从未被测量：现有基准几乎都只测单轮长上下文压缩。但 Agent 实际做的是反复压缩——每一轮都在上一轮压缩结果上再压缩，误差累积。没有任何基准固定一个预算轴来跨层评估。

论文给出的可操作输出

  • 基准提案：一个能在所有层统一固定预算的评测协议。
  • 参考实验：小型复现，展示跨层误差累积。
  • 压缩感知设计原则：一组给系统设计者的建议（例如：驱逐决策必须可撤销，或必须延迟到 query 到达后）。

四、两篇论文的交叉洞察

把 A 和 B 放在一起看，能得出 2026 年中 Agent 记忆设计的三个共识：

  1. 选择性 > 全面性。A 用"四类别分类"实现选择，B 从理论上论证"全保留"在率失真意义下不可能最优。结论一致：激进丢弃是正确的。
  2. "何时丢弃"比"丢什么"更重要。B 的核心批评是——现有系统在 query 未知时就做不可逆丢弃。A 的零令牌刷新恰恰是一种"延迟决策"：数据先不动，等真正需要时再刷新。
  3. 共享和复用是被低估的维度。A 的 workspace 共享机制在生产中带来 14× 效率提升，但 B 的七轴分类里没有"共享"这一轴。这是未来研究的空白。

五、对 Hermes/Skill 体系的具体启示

启示 当前 Hermes 现状 改进方向
把 Skill 视为"可复用上下文 workspace" Skill 主要是流程指令 可增加 context_schema 字段，声明该 Skill 依赖的数据 schema/工具配置，实现跨会话复用
区分"持久元信息"和"临时轨迹" memory 工具混存 memory 写入时强制标注类型（fact/trace/preference），trace 类自动过期
零令牌刷新思路 每次任务都重新调 LLM 对于"数据变了但逻辑没变"的周期任务，缓存程序 + 只刷数据，省 LLM 调用
驱逐可撤销 memory 删除即消失 引入"软删除 + TTL 墓碑"，过期前可恢复

六、核心发现总结

  1. 全历史持久化会让 Agent 变笨（71% vs 79% 无记忆）——这是反直觉但被实验证实的。
  2. 选择性持久化 + 共享 workspace 可达 96% 完成率，token 成本降 97×。
  3. KV-Cache / Prompt / 架构状态 / Agent 记忆是同一个率失真问题，但学界此前各自为战。
  4. 所有层的"保留信号"都用 attention/recency，且都在 query 到达前做不可逆丢弃——这是当前最大的系统性缺陷。
  5. 重复压缩的误差累积从未被基准测试覆盖，这是 Agent 可靠性的隐藏风险。
