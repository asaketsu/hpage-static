## 一、内容详细整理

### 1.1 核心问题

AI coding agent 的运行成本到底取决于什么？业界普遍认为 MCP（Model Context Protocol）比 CLI 工具调用贵得多——流传最广的估计是"MCP 消耗 35 倍 token"[MindStudio 2026]，其他报告范围 3×-35×。但这些估计全部来自不可复现的实践报告，且各自使用不同的 agent 脚手架和不同的任务。

本文设计了一个严格对照实验来回答：**固定任务、固定验证，只变化三件事——agent 脚手架、语言模型、工具接口（MCP/CLI）**。

### 1.2 实验设计

**任务**：固定 6 个操作（对私有 GitHub 仓库执行）：
1. 定位指定 issue
2. 创建分支
3. 应用补丁
4. 提交变更
5. 开 PR
6. 报告目录文件数量

**验证方法**：不信任 agent 自报告，通过 GitHub API 独立检查 4 个条件（分支是否存在/文件是否含补丁内容/PR 是否已开/文件计数是否正确）。

**七种 agent 脚手架**：
- Claude Code 2.1.220（支持 MCP）
- OpenAI Codex 0.146.0（支持 MCP）
- qwen-code 0.21.2（支持 MCP）
- **Hermes 2026.8**（支持 MCP）
- opencode 1.18.15（支持 MCP）
- pi 0.73.1（不支持 MCP，对照组）
- Tau 0.3.6（不支持 MCP，pi 的独立 Python 重实现，对照组）

**两种实验臂**：
- MCP 臂：挂载官方 GitHub MCP 服务器（44 个工具）
- CLI 臂：不挂 MCP，只有 shell + gh 客户端
- **隔离设计**：MCP 臂中 shell 被指向空凭据目录，防止 agent 悄悄回退到 gh

**五个语言模型**：gpt-5.6-luna, gpt-5.6-terra（OpenAI）、sonnet-5（Anthropic）、qwen3.6:27b 和 glm-5.2（本地部署开源模型）

**所有请求通过 LiteLLM 代理**：统一记录 input tokens / cached tokens / tool calls / schemas per request。

### 1.3 主要发现（Section 3：脚手架是主导效应）

**主结论：脚手架选择比接口选择影响大得多。**

按完成运行的中位 input tokens 排序（跨所有模型和两臂汇总）：

- pi（无 MCP）：14,660 tokens（×1.0），4/4 完成，$0.0124
- Tau（无 MCP）：16,459 tokens（×1.1），4/4 完成，$0.0149
- **Hermes**（有 MCP）：75,352 tokens（×5.1），7/8 完成，$0.0581
- Codex（有 MCP）：92,639 tokens（×6.3），6/8 完成，$0.0838
- opencode（有 MCP）：131,649 tokens（×9.0），7/8 完成，$0.0909
- Claude Code（有 MCP）：260,170 tokens（×17.7），5/6 完成，$0.3347
- qwen-code（有 MCP）：288,808 tokens（×19.7），7/8 完成，$0.1230

**最便宜和最贵的脚手架之间差 20 倍。** 而本文中任何接口比较（MCP vs CLI）的差异都不接近这个量级。

**纯 CLI 臂对照（Table 2，不挂任何 MCP）**：pi 与 Claude Code 之间仍差 28 倍。说明这不是 MCP 导致的——是脚手架本身的"重量"差异。

### 1.4 MCP vs CLI 的配对比较（Section 4）

**13 个严格配对比值（同一脚手架+同一模型，两臂都完成）**：范围 0.43×-29.06×，中位数 0.93×。

- Codex：MCP 比 CLI 贵 16 倍（82K→1.33M tokens）
- Hermes：MCP 比 CLI **便宜** 16%（84K→71K tokens）
- qwen-code：MCP 比 CLI 便宜 26%
- Claude Code：MCP 比 CLI 便宜 43%
- opencode：基本持平（±5%）

**结论：MCP 与 CLI 的成本对比是双峰分布，不稳定，没有单一值。** 之前业界报告 3×-35× 的巨大分歧，正是因为这个量本身不稳定——每个研究采样到几个点就报告一个值。

### 1.5 失败成本（Section 4.4）

- MCP 臂：12.9% 的花费购买了零完成工作
- CLI 臂：2.2% 的花费浪费
- 无 MCP 脚手架：0% 浪费（从未失败）
- **关键**：两臂失败频率相同（各 3/19），差异在于 MCP 臂的失败碰巧发生在昂贵的配置上
- 中位失败运行消耗 181,806 tokens vs 中位完成运行 81,510 tokens——**失败的 agent 不是早停省钱，而是花更多钱却什么都没做到**

### 1.6 目录投递方式是关键机制（Section 4.3）

**最重要的发现之一**：同一个 MCP 服务器，两种投递方式产生 3.1 倍成本差异。

- **全量发送**（Claude Code/Codex/opencode/qwen-code）：每次请求都发送全部 44 个工具描述。Claude Code 总共发送 74 个 schema（27 个内置工具 + 3 个 MCP 资源 + 44 个服务器工具）
- **按需获取**（**Hermes**）：每次请求只发送 7 个 schema（2 个网关命令对：列出/描述工具 + 按名调用工具），其余 42 个描述仅在模型请求时才获取

> 全量发送：中位 216,986 tokens（12 次完成运行）
> 按需获取：中位 70,836 tokens（4 次完成运行）

**Hermes 是本文中唯一使用按需获取 MCP 目录的脚手架，也是五个 MCP 支持脚手架中最便宜的。**

### 1.7 小模型受脚手架影响最大（Section 6）

qwen3.6:27b（27B 参数本地模型）在所有脚手架下都完成了任务，但成本差异达 **139 倍**：
- Tau（CLI）：17,416 tokens（×1.0），4/4 完成
- Codex（MCP）：2,418,828 tokens（×138.9），4/4 完成

> 模型从不是瓶颈。变化的是脚手架让模型花了多少代价才完成工作。

**对自托管团队的启示**：在普通硬件上运行 agent 的主要约束不是模型能力，而是脚手架替模型花了多少。

### 1.8 Agent 不遵守分配的接口（Section 7）

在隔离设计之前的预实验中（21 次运行）：
- 6 次完全只用 MCP 工具
- 6 次完全只用 shell 命令（没碰 MCP 一次）
- 6 次两者混用
- 3 次没调用任何工具
- **4 次绕过两个接口直接用 HTTP 查 GitHub API**

**添加 prompt 指令没有改变行为。移除替代路径的凭据才有效。**

> 不验证 agent 实际用了哪个接口的研究，测量的是一个未知混合物的成本。

### 1.9 生产成本披露（Section 2.10）

本研究本身用 Claude Code 构建和执行，8 天两个 session：
- 总 input tokens：1,660,933,432（16.6 亿）
- 缓存命中率：97.1%
- 未缓存 input：仅 6,805 tokens（0.0004%）
- input : output 比 = 437:1

> Agent 工作本质上是阅读（文件、命令输出、历史轮次），而非生成。

全部开源：测量 harness、任务定义、验证代码、完整逐次运行数据集：

## 二、查询拓展

### 2.1 MCP（Model Context Protocol）

Anthropic 于 2024 年 11 月发布的开放标准，让外部服务以结构化方式发布工具列表，任何兼容的 agent 脚手架可以直接消费，无需为每个服务定制集成。本质上是将"函数调用"的 schema 发现从"开发者硬编码"变成"协议自动协商"。其成本问题在于：每个工具的完整描述（名称、功能说明、参数规格）必须在每次请求中重新发送，因为 LLM 在请求间不保留状态。

### 2.2 Agent Scaffolding（脚手架）

指 AI coding agent 的软件 harness：接收用户请求→发给模型→接收模型输出→执行模型要求的动作→反馈结果给模型。典型例子：Claude Code、OpenAI Codex、qwen-code。脚手架是模型和外部世界之间的"胶水层"，其设计哲学（最小化 vs 全功能）直接决定了上下文膨胀程度。本文中的 pi 和 Tau 是"最小化设计"的代表：只给模型一个 shell、几个文件操作和一句 prompt，其他全靠模型权重中已有的知识。

### 2.3 按需获取 vs 全量发送

这是本文对 Hermes 架构的核心观察。大多数 MCP 客户端在每次模型请求中都附带全部 MCP 工具的 schema，这意味着一个有 44 个工具的 GitHub MCP 服务器会让每个请求膨胀数千 token。Hermes 采用"网关模式"：在上下文中只放 2 个元工具（list_tools + invoke_tool），模型先查询有什么工具可用，再按需调用。这与 Anthropic 自己在 [2026c] 中描述的方向一致：让模型写代码来调用工具，而不是在请求中呈现每个工具定义。

## 三、归纳总结

### 3.1 成本归因框架

```
Agent 运行总成本
├── 模型价格（per-token rate）—— 5 个模型间差 20 倍
├── 脚手架开销（context inflation）
│   ├── 内置工具 schema 数量（pi: 极少; Claude Code: 27 个）
│   ├── MCP 目录投递方式（全量 44 vs 按需 7）
│   └── 轮次膨胀（失败重试/冗余调用）
│   └── 脚手架间总差异：20-28 倍 ★ 主导因素
├── 接口选择（MCP vs CLI）
│   └── 配对比值：0.43-29 倍（双峰分布，不稳定）
└── 失败惩罚
    └── 失败运行比成功运行多花 2 倍 tokens（且产出为零）
```

### 3.2 核心对比维度

- **脚手架间成本差距**：20×（最贵/最便宜），这是稳定可复现的
- **MCP vs CLI 差距**：不稳定，配对中位数 0.93×（基本持平）
- **失败浪费占比**：MCP 臂 12.9% vs CLI 臂 2.2%（但失败频率相同）
- **目录投递影响**：全量 vs 按需 = 3.1×（可设计优化）
- **小模型敏感度**：27B 模型跨脚手架成本差 139×

## 四、趋势判断

### 趋势1：MCP 成本争议将被"脚手架效应"取代
依据：本文证明脚手架选择（20×）远大于接口选择（不稳定/双峰）。未来 benchmark 的焦点将从"MCP vs CLI"转向"哪种脚手架设计更高效"。

### 趋势2：按需目录投递将成为标准实践
依据：Hermes 的网关模式（7 schemas vs 44 schemas）已证明 3× 成本优势，且 Anthropic 自己也在推动类似方向。全量发送是设计选择而非协议要求。

### 趋势3：最小化脚手架在管道/定时任务中崛起
依据：pi 和 Tau 的"shell + 极少工具"设计在固定任务上便宜 5-28 倍且更可靠。对于可预先指定边界的重复任务（CI/CD 管道、定时任务），通用 assistant 的"广度机器"是在浪费钱。

### 趋势4：小模型 + 轻脚手架 = 自托管最优解
依据：27B 模型在 Tau 下仅需 17K tokens，在 Codex 下需要 2.4M。模型不是约束，脚手架才是。等待更好的小模型不如选择更轻的脚手架。

## 五、关联分析

### 5.1 与 Hermes Agent 工具架构的关联

**本文直接评测了 Hermes 2026.8 作为 agent 脚手架**，结果对 Hermes 架构设计有直接验证价值：

- Hermes 是 5 个 MCP 支持脚手架中**最便宜的**（75K tokens，次便宜 Codex 93K）
- Hermes 的按需 MCP 目录投递（网关模式）被论文确认为成本优势的关键机制
- 但 pi/Tau（无 MCP 极简脚手架）仍比 Hermes 便宜 5 倍——说明 Hermes 的内置工具 + skills 系统仍有 context 膨胀
- **启发**：对已明确边界的 cron 任务/管道任务，评估是否能用更轻的调用路径（直接脚本而非完整 agent session）

### 5.2 与「截图还是工具-混合GUI-MCP智能体采纳鸿沟」(2608.03327) 的关联

同日精读的 2608.03327 发现混合 GUI-MCP agent 的工具采纳率仅 17.8%。本文 Section 7 独立验证了同一现象：agent 大量忽略分配的接口（21 次运行中只有 6 次完全使用 MCP 工具），prompt 指令无法改变行为，只能通过配置隔离来强制。**两篇论文从不同角度证明：Agent 不遵守工具分配是一个系统性问题。**

### 5.3 与「截图还是工具」中训练-推理观测差异的关联

2608.03327 发现压缩后训练观测的工具使用模式与推理时不一致（+4.8pp 偏差）。本文的隔离设计（Section 2.4）提供了对应的工程解法：与其依赖 prompt 约束 agent 行为，不如在环境层面移除替代路径——这验证了 Hermes cron 任务中隔离凭据/环境的做法。

## 六、金句摘录

> 「An agent that fails does not stop early and cheaply; it works hard, spends more than a successful agent would, and delivers nothing.」

> 「The composability that lets an agent be treated as an ordinary program — invoked, piped, scripted, retried — is the same composability that lets an agent use ordinary programs.」

> 「A measurement that assigns an interface without verifying which interface was used reports the cost of an unknown mixture.」

> 「The model was never the constraint; the software around it was.」

## 七、行动启示

- **P0 — MCP 目录按需投递验证**：本文确认 Hermes 的网关模式（list_tools + invoke_tool）是成本最优的 MCP 集成方式。应审计当前 Hermes MCP 配置，确保所有 MCP 服务器都走按需获取而非全量注入。如果某些 MCP 服务器仍全量发送 schema，应评估是否可以迁移到网关模式
- **P0 — Cron 任务的脚手架瘦身评估**：论文证明对固定任务，极简脚手架便宜 5-28 倍。对高频 cron 任务（如论文精读、日志分析、健康检查），评估是否可以将其从完整 agent session 迁移到更轻的脚本化路径，仅保留 agent 调用用于需要推理的环节
- **P1 — 失败成本监控**：论文揭示失败运行比成功运行多花 2 倍 tokens。应在 Hermes cron 监控中加入"失败 token 消耗"指标，识别那些反复失败但仍持续消耗 token 的任务
- **P2 — Agent 接口遵从性审计**：Section 7 证明 agent 经常忽略分配的接口。可在 Hermes Gateway 中加入工具调用日志审计，统计 agent 实际使用的工具 vs 配置提供的工具的偏差率
- **P2 — 输入 token 优化优先**：论文显示 input:output = 437:1，Agent 工作本质是阅读。优化方向应聚焦于 input 压缩（skills 按需加载、工具输出修剪）而非 output 限制
