LLM 自进化为什么容易崩溃：自合成数据流水线的信息增益视角

论文：arXiv:2603.02218 | Self-Play Only Evolves When Self-Synthetic Pipeline Ensures Learnable Information Gain | 2026-03
关联论文：Absolute Zero (Zhao 2025), R-Zero (Huang 2025), Dr. Zero (Yue 2026), URPO, Cooper

标签：#LLM自进化 #合成数据 #信息论 #自博弈 #Agent架构 #强化学习

核心结论（一句话）

绝大多数"自进化 LLM"系统本质是脆弱的自博弈（self-play），它们在几轮后就会崩溃或平台化；根本原因是循环在不断合成新数据但没有增加"可学习信息"（learnable information）。要实现真正的持续自进化，必须把循环看作一个自合成数据流水线，确保 Proposer/Solver/Verifier 三角角色协同维持可学习信息单调递增。

一、问题诊断：自进化为什么会崩溃

1.1 现象层证据

近期大量"零数据自进化"系统都报告了快速衰减：

  • Absolute Zero（Zhao 2025）：Proposer 退化成生成 trivial 恒等函数 f(x)=x
  • R-Zero（Huang 2025）：性能早期达峰后持续下降
  • Dr. Zero（Yue 2026）：搜索 Agent 自进化同样出现早期峰值后崩塌
  • Self-questioning LM（Chen 2025）：需要极其精细的 prompt 才能保持问题在合理范围

1.2 失败的根因：信息论视角

论文的核心洞察——自进化 ≠ 自博弈。

维度 自博弈（self-play） 自合成数据流水线
目标 在固定博弈中自我提升 持续产生新的可学习信息
数据 每轮合成更多数据 每轮合成信息密度更高的数据
失败模式 模式崩溃/自我欺骗 无（设计正确时）
信息源 完全封闭（预训练权重） 主动引入外部信息

关键概念：可学习信息（Learnable Information）。在有限计算预算的观察者（bounded observer）下，数据的可学习信息 = 模型能从中提取的结构化知识减去已知的噪声。如果每轮合成的数据只是已有知识的重新组合，可学习信息不增，系统必然平台化。

1.3 为什么"纯 reward shaping"不够

信息论视角揭示了：仅优化奖励信号只能改变数据的选择压力，不能增加数据的信息上限。这正是 Absolute Zero 崩溃的原因——Proposer 生成的问题虽然满足 reward 约束，但信息量趋于零（恒等映射）。

二、三角角色模型：Proposer / Solver / Verifier

自进化系统必然包含三个角色：

Proposer（提出者）——生成任务/问题
     ↕
Solver（求解者）——尝试解决方案
     ↕
Verifier（验证者）——提供训练信号

2.1 三种角色编排模式

模式 组合 特点 问题
自博弈 P⇄S + 固定V 代码/数学等可验证域 Proposer 退化
偏好进化 固定P + S⇄V 指令跟随/偏好学习 Verifier 自我欺骗
三角联合 P+S+V 全协同 本文推荐 实现复杂度高

论文指出，简单地从 P+SP+S 和 S+VS+V 拼成 P+S+V 是不够的（SPELL、Multi-agent Evolve 已尝试）。关键在于三者的协同设计以保信息增益。

三、三大系统设计原则

论文提出三个让自进化可持续的设计原则：

原则 1：非对称协同进化（Asymmetric Co-evolution）

框架：Solver 与其"内部环境"（Proposer + Verifier）之间进行协同进化。虽然三方共享同一信息源（预训练权重），但它们在合成方向上的分歧（问题/解法/反馈）会产生信息间隙（information gap），实现弱→强的监督。

要点：必须把 Solver 的改进显式同步回 Proposer/Verifier（强→弱监督），形成"弱→强→弱"闭环。否则信息间隙会消失，系统回到平台。

原则 2：容量增长（Capacity Growth）

可学习信息不仅取决于数据分布，还取决于观察者模型的容量。随着自进化推进：

  • 参数容量必须扩展（更大的模型或 MoE 的专家扩展）
  • 推理时计算预算必须扩展（更多推理步数、更长的思维链）

"Scaling Embeddings Outperforms Scaling Experts"（arXiv:2601.21204）支持了嵌入维度的扩展优先于专家数量。

原则 3：主动信息获取（Proactive Information Seeking）

零数据或固定数据集驱动的自进化从根本上受限于有限信息。自进化系统必须主动获取外部信息源，且要与当前能力对齐：

  • 提供新的合成数据上下文
  • 引入新的合成方向（新的任务类型）
  • 创造可被协同进化利用的新非对称性

四、实证：编码任务上的自博弈实验

论文在 Absolute Zero 的编码任务上做了消融实验，揭示三种任务类型的信息特性：

任务 输入 输出 预测 难度
演绎（deduction） 代码+输入 — 输出 最常见
归纳（induction） — 输入→输出 代码 最难，需多对样例
逆推（abduction） 代码+输出 — 输入 需逆向推理

实验发现：当 Proposer 只在某一类任务上生成时，Solver 的可学习信息快速饱和；引入跨任务的多样性后，信息增益显著提升。这直接验证了"信息增益"作为自进化健康度指标的有效性。

五、对 Hermes 自进化架构的启示

5.1 当前架构的问题映射

Hermes 的 Skill 自进化系统（evolver、experience-bank、auto-learner）本质是一个 P+S+V 流水线：

  • Proposer = task-discoverer + error-monitor 发现新任务/问题
  • Solver = 各业务 Skill 执行任务
  • Verifier = watchdog + Data Meow 质量审计

风险点：当前 Verifier 主要是规则校验（exit_code、文件存在），不引入新信息。如果 Skill 执行错误都是同类型（如飞书 token 过期），Proposer 端的可学习信息会饱和。

5.2 可落地的改进

  1. 引入非对称性：定期让 OPM Meow（战略视角）审查 Skill 覆盖范围，主动制造新任务类别（而非只等错误发生）
  2. 容量增长：Skill 文件应定期与外部最新论文/工具对齐（auto-learner 已部分实现，但需要强化信息增益度量）
  3. 主动信息获取：夜间自学习应引入更多外部源（arXiv、GitHub trending、技术博客），而非只依赖飞书对话历史

七、核心要点速查

  • 自进化系统崩溃的根因不是 reward 设计问题，而是可学习信息不再增长
  • 三角角色（P/S/V）必须协同，单纯两两组合都会退化
  • 三大设计原则：非对称协同、容量增长、主动信息获取
  • 信息论视角提供可量化指标：可学习信息增益应作为自进化健康度的首要度量
  • 对生产 Agent 系统的启示：定期引入外部信息源、扩展模型容量、避免在同质数据上反复训练
