一、内容整理

1.1 核心问题：长轨迹 Agent 的 KV cache 成本-精度困境

LLM Agent 的任务轨迹越来越长（数百轮推理+工具调用），KV cache 增长带来双重挑战：

  • 成本侧：实测 KV cache 读取占总 API 成本的 82.4%（论文 Figure 14），存储+I/O 成为第一大开销
  • 精度侧：活跃 KV 状态数量或位置范围超出模型可靠处理能力后，任务精度严重退化

既有解法是 context engineering（裁剪/摘要历史消息），但它有三宗罪：

  • 编辑早期消息 = 修改轨迹前缀 = 无效化后续所有已缓存状态，触发被保留后缀的 re-prefill；编辑越早，re-prefill 越长
  • 主流 harness 因此采用"阈值触发+激进截断"（只在接近上下文上限时摘要、只保留最近几轮）——中间轮次的有效信息被扔掉
  • 形成 re-prefill 成本与任务精度之间的两难（dilemma）

论文的实证：GPT-OSS-120B 在 100 个 BrowseComp-Plus 任务上，trim 型 context engineering（保留最近 12 轮工具响应）成本是全量上下文基线的 1.85×；48K 阈值摘要省 7% 成本但精度掉 5 个百分点。

1.2 方法论：cache engineering 三原语 + history dependence 形式化

核心主张：不动文本轨迹，直接操作活跃 KV cache。

三个 cache 操作原语（形式化定义）：

  • append(x)：标准推理路径。处理新 token 并追加 cache 条目：C ← [C; C_{t+1}]。位置索引从 0 起每个 append 递增 1
  • drop(P)：把选中逻辑索引集 P 的 KV 状态从后续 attention 中排除。保留条目的位置编码、逻辑 token 序列全部不变——这是与 context engineering 的本质区别（后者必须改文本+re-prefill）
  • repos：把保留的 r 个 cache 条目的 key 位置编码按逻辑序重排为 0..r-1，后续 append 从索引 r 继续。对 RoPE 实现：K ← R(q)·R(p)⁻¹·K（旋转矩阵左右乘，纯 key 侧操作，value 不变）

history dependence 关键发现：cache 状态由 token 序列 + cache 操作序列 共同决定。相同 token 序列在不同 drop 时序下产生不同 cache 状态（B 在"有 A 前缀"与"无 A 前缀"下计算出的 KV 不同；C 在三种轨迹下全不同）。推论：

  • 服务系统的 prefix matching（前缀匹配复用）不再充分——token 前缀相同 ≠ cache 状态等价
  • 正确的 cache 复用与恢复必须同时携带 token 历史 + 操作历史

策略层经验（Figure 2/3/4 实证）：

  • 老 token 注意力低于新 token；tool response 的注意力显著低于 assistant 消息（同等相对位置）→ 主打策略选 tool-response rolling-drop（保留全部推理+最近 12 轮工具响应的 KV）
  • 被 drop 的历史信息并未完全丢失：保留条目的 KV 计算时"看过"被丢弃内容，信息部分残留

1.3 AKV 服务引擎：stateless interface, stateful serving

三大设计性质要保住：①当且仅当状态等价才复用；②驱逐不影响请求隔离；③被驱逐状态可在一次 prefill 内恢复。

三大挑战与对策：

  • 挑战1：token 前缀不再决定 cache 状态 → 扩展 radix tree：在 drop 触发点插入 drop 节点 Δ 记录被丢弃的逻辑索引集，匹配时沿"token 前缀+操作前缀"双维度复用；不同 drop 时序的轨迹共享 A-B 前缀后在 drop 节点处分叉
  • 挑战2：一个请求 drop 的 KV 可能仍被其他请求需要 → drop-aware eviction：驱逐决策考虑跨请求引用
  • 挑战3：普通因果 prefill 无法复现 drop/repos 后的状态，逐条重放操作历史需多次前向 → segment-batch attention：单次 prefill 按 segment 分批重建

接口设计（向后兼容）：标准 messages 字段提供完整逻辑 token 序列（每条消息隐式 append），可选 cache 字段用 operate-after 语法声明 drop（"第 i 条消息后 drop 第 j 条消息的 cache"）与 reposition 序列。无状态接口保证：输出分布独立于物理 cache 驻留与其他请求的操作——共享前缀 cache 的请求间互不污染；显存压力驱逐后可全量恢复。

1.4 关键实验数据（Table 1：三模型 × 四基准）

模型覆盖 MiniMax-M2.7（230B/10B active）、GPT-OSS-120B（5.1B active）、MiroThinker-1.7-Mini（30B/3B active）；基准覆盖 BCP（BrowseComp-Plus）、GAIA-Text、SWE-Verified、xbench-DeepSearch。

平均分与平均成本（美分/任务）：

  • MiniMax-M2.7：AKV 53.7 分 / 4.4 分钱 vs Standard 52.4 / 5.0 vs Text Engineering 52.8 / 5.7
  • GPT-OSS-120B：AKV 53.1 / 7.3 vs Standard 51.0 / 11.2 vs TextEng 48.3 / 10.2
  • MiroThinker-1.7-Mini：AKV 45.8 / 14.8 vs Standard 44.1 / 20.4 vs TextEng 37.1 / 18.1
  • 汇总：平均分 +1.7，平均成本 -27.7%（vs Standard）；vs TextEng -21.9%

精度提升来源：在基线各自的摘要阈值区间（48-96K / >96K）内，基线因激进上下文削减掉分，AKV 的 rolling drop 增量式移除旧工具响应 cache，双阈值区间内均不塌。

1.5 服务性能（Table 2：GPT-OSS-120B，Top-80 SWE-Verified）

并发 C=8..16 全档位 AKV 延迟/吞吐占优：

  • 峰值吞吐配置下（AKV C=14 vs Standard C=12）：mean 请求延迟加速 1.36×，P95 加速 1.51×
  • 输入吞吐 1.53×、输出吞吐 1.18×
  • 高并发（C≥14）优势扩大：Standard 的 re-prefill 工作量随 KV 压力膨胀，可并发解码请求数下降

1.6 消融与策略进化（Table 3/4 + RSI）

  • drop 目标消融（GPT-OSS-120B）：tool drop 无 repos=55.0 分；tool drop + repos=62.0 分（BCP）——repos 让探索能越过位置编码上限继续跑（55→62，+7pp）；drop reasoning cache（单独或叠加）反而降分
  • Cache-As-Tool（CAT）：把 cache 管理暴露为工具让 agent 自主决策。100 任务 BCP 子集上两个模型均最高分：GPT-OSS-120B 61.0%（成本 13.4→12.1）、MiniMax-M2.7 64.0%
  • 递归自改进（RSI）：用 MiniMax-M2.7 在 20 个 BCP 任务上迭代精炼 cache 策略，第 3/6 轮策略在 100 个留出任务上相对 Standard 再降本 15.6%/17.8%（叠加在专家设计的 rolling-drop 之上）——cache 策略本身可被进化
  • abstract 级汇总：rolling-drop 较阈值摘要 +1.7 分 / -27.7% 成本；AKV 吞吐 1.2×、P95 加速 1.5×；RSI 再降 7.1%

二、查询拓展

2.1 Context Engineering vs Cache Engineering 的分层

  • context engineering 工作在文本层：摘要（启发式触发/agent 决策触发/RL 优化摘要质量）、trim（直接删）；共同代价=前缀改变→re-prefill
  • cache engineering 工作在算法层活跃 cache：文本轨迹不动、保留 cache 不重算、位置编码可独立调整
  • 两层互补而非替代：摘要解决"模型读什么"，cache 操作解决"attention 看什么、计费算多少"

2.2 KV cache 压缩/驱逐/复用技术谱系（Related Work 梳理）

  • 压缩：低秩表示、量化、聚合合并
  • 驱逐：token 位置信号（StreamingLLm 类）或 attention 重要性信号（H2O 类）
  • 复用：位置编码调整（PrefixCache/CacheBlend 系）或部分重算
  • 本文定位：把驱逐决策权从服务端低层信号上移到 agent/harness 高层语义决策，并补上配套 serving 引擎

2.3 Radix tree 前缀复用与 SGLang 系服务

主流 serving（SGLang/vLLM）用 radix tree 做 prefix caching；本文扩展点=drop 节点，使"操作历史"成为树的分叉维度。

2.4 RoPE 位置重排的数学

repos 对 key 施加 R(q)R(p)⁻¹ 旋转：RoPE 下 attention score 只依赖相对位置，整体平移不改变保留条目间的相对几何，但压缩了与新 append token 的距离——等价于"逻辑上把历史挪近"。

2.5 API 计费中的 cache 读写经济学

KV cache 读占 82.4% 成本（Groq 口径）——按 token 计费体系中"活跃输入 token"才是计费单位，drop 掉的 cache 不再计费也不占 attention 预算。这与 Anthropic/OpenAI 的 cached input 折扣定价直接相关。

三、归纳总结

3.1 一句话

把上下文管理从文本层下移到 KV cache 层：drop（排除注意力）+ repos（位置重排）两原语让 agent 不改历史、不重算前缀地控制活跃 cache，AKV 引擎用扩展 radix tree + drop-aware 驱逐 + segment-batch attention 把"history-dependent cache 状态"变成可复用、可恢复、可隔离的一等服务对象。

3.2 三条核心洞察

  • 历史依赖性是新的正确性维度：token 序列不再唯一决定推理状态，"操作序列"成为 cache 等价性的第二坐标轴——任何想做 cache 级复用的系统都必须显式建模它
  • 保留即继承：被 drop 内容的信息部分残留于保留条目的 KV 计算中，因此"渐进 rolling drop"在信息损失上远优于"阈值触发的一次性摘要截断"
  • 驱逐决策应该语义化：服务端靠 attention 分数猜重要性，不如让知道"这是工具返回的旧搜索结果"的 agent 自己拍板；Cache-As-Tool 实验证明 agent 自主管理 cache 是最优策略形态之一

3.3 局限性与未来方向（论文自述+笔者的判断）

  • 论文自述：cache 策略空间待探索、cache engineering 下训练 agent（而非仅推理期策略）、线性 attention 模型支持是未来工作
  • 笔者补充①：drop 粒度是 message 级（整条工具响应），细粒度（段落/字段级）drop 的收益未测
  • 笔者补充②：依赖服务端支持 cache 字段扩展——在闭源 API（无此接口）上无法使用，自建/开源 serving 是前提；接口未被 vLLM/SGLang 主线采纳前生态位有限
  • 笔者补充③：保留 12 轮的 K 值与 repos 阈值仍是手调超参，RSI 进化只在小任务集上验证

四、趋势判断

  • 趋势1：Agent 成本优化主战场从 prompt 层转向 cache 层。82.4% 成本占比意味着上下文工程（省 token）的边际收益见顶，cache 工程（省 I/O 与注意力预算）是下一战场；与 2026 年下半年集中出现的 KV 驱逐/压缩/按需读取系列（MemDecay/ODA/Kara 等）共同构成"上下文经济学"技术族
  • 趋势2：Serving 接口语义化扩展成为新竞争面。messages+cache 双字段、operate-after 语法，本质是把 agent harness 的状态管理诉求下推到推理引擎——推理引擎从"无状态文本进出"走向"有状态轨迹托管"，vLLM/SGLang 跟进与否决定普及速度
  • 趋势3：资源管理策略本身可被 RSI 进化。继 HarnessPro（harness 结构进化）之后，本文证明 cache 策略也能递归自改进再降 15-18% 成本——"一切资源策略皆可进化"正在成为 Agent 自进化体系的标配组件
  • 趋势4：Agent 记忆分层从文本摘要走向注意力位阶。"保留在上下文里"与"参与注意力计算"解耦后，记忆系统出现新设计轴：一份文本可以永久留在轨迹里（供未来 re-prefill 恢复），同时按需退出注意力（省成本）

五、关联（关联论文 + 对本系统的意义）

5.1 关联论文

  • MemDecay (2607.10582)：区域感知 KV 驱逐（system 区半衰期 10× 于 scratchpad）——本文的 message 角色感知（tool response 先丢）与其同向，但决策主体从服务端衰减曲线换成 agent 显式操作
  • ODA (2609.20734)：按需注意力（recall head 步级预测 KV 收益，KV 全保留）——四路线坐标系（驱逐/压缩/复用/读取）中，本文同时推进"驱逐"与"复用"两轴并加第三坐标（操作历史）
  • Kara (2607.01237)：KV 滑动窗口压缩——同为"老 cache 让位"，Kara 服务端固定窗口，本文 agent 决策+位置重排
  • Context-Engineering Quality (2607.14275)：七维上下文质量评分——本文可视为其 token 维度之外开辟的 cache 维度姊妹篇
  • HarnessPro (2610.26770)：RSI 进化 harness——本文 RSI 进化 cache 策略，同一"策略即代码、进化即优化"范式
  • StreamingLLM / H2O / CacheBlend：本文 Related Work 中的直接技术基座

5.2 对 Hermes Agent 的关联

  • Hermes Gateway 的会话上下文管理目前是文本层裁剪+session 压缩（[SKILL_PRUNED] 机制），命中本文批判的"编辑前缀→re-prefill/信息损失"困境；本文证明 message 级 rolling drop（先丢旧工具输出）在精度-成本双轴上均优于阈值摘要
  • Hermes 的工具输出修剪 skill（context-compressor）与本文 tool-response drop 语义一致，但缺少"保留条目位置重排（repos）"这半边——长会话接近模型位置上限时无法继续而不重算
  • 三机部署（jbot/ubot/abot）共享推理后端时，跨请求 cache 隔离（drop 不污染共享前缀）是 Gateway 直连推理服务的实际设计问题

5.3 对 Jetson Orin 边缘推理的关联

  • Jetson 显存 8-16GB，长轨迹 Agent（如 DUCK 部署链的多轮工具调用）KV cache 是显存第一杀手；drop 操作零计算成本（只改活跃掩码），比摘要（要跑一次 LLM 前向）更适合边缘
  • repos 的旋转矩阵操作在 tensor core 上是逐 key 轻量矩阵乘，边缘 GPU 完全可负担
  • AKV 的 radix tree 需要常驻内存管理器——边缘单请求场景可简化为线性 cache 池+drop 位图，去掉树结构

5.4 对量化交易的关联

  • 盘神探/盯盘类 Agent 长会话累积大量行情快照工具输出（占 attention 低价值高体量）——rolling drop 恰好匹配"旧行情让位、新行情进场"的时序特征
  • 回测 Agent 轨迹中 drop 已处理完的历史数据 KV，可在不丢失"已看过"逻辑的前提下延长单会话回测长度

六、拓展应用推荐

  • P0（Heros Gateway 工具输出 rolling-drop）：在 Gateway 的会话消息序列上实现 message 级 drop 标记——超过 N 轮的工具输出在后续请求中从 messages 序列移除但保留摘要指针（模拟 attention 排除）。不依赖服务端接口、立即可做；预期显著降低智谱/Groq 长会话 token 成本。工作量：约半天（改 Gateway 消息组装层）
  • P1（Jetson 边缘 LLM 会话 cache 位图）：nexa-local-inference（Ollama）长会话加 drop 位图——LLM 输入组装时跳过旧工具输出。与 P0 同构，但边缘场景显存收益更直接。工作量：1 天
  • P1（cache 策略进纳入 evolver 体系）：把"保留轮数 K/丢什么角色"作为可进化参数进 experience-bank/evolver，用会话成本+任务完成率做双目标——复刻论文 RSI 结论（再降 15%+）的最小化版本。工作量：2-3 天
  • P2（跟踪 vLLM/SGLang 社区对 cache 操作接口的采纳）：若上游 PR 落地，Hermes 可直连 AKV 式接口获得服务端复用收益；在此之前自建文本层模拟即可。工作量：监控级
  • P3（量化盯盘会话的时序化 drop）：盯盘 Agent 工具输出按"行情时效"衰减 drop（盘中快照保留 12 轮，隔夜全丢）——需先有 P0 基础设施。工作量：P0 完成后 +2 小时

七、指南分析

若要把本文方法落地到自有 Agent 系统，按依赖链走：

  1. 第一步先做文本层近似（无需服务端支持）：把"drop 旧工具响应"实现为请求组装时跳过旧 tool message+在系统提示中保留一行指针（"第 N 轮搜索结果已归档"）。这已能拿到大部分成本收益（论文中 tool response 是低注意力高体量区）
  2. repos 不可在文本层近似：位置重排必须服务端支持。判断标准：当会话逻辑长度逼近模型位置上限且任务还需继续时，才有 repos 刚需；否则跳过
  3. drop 目标优先级：tool response > 旧的 assistant 推理 > 系统提示（永不丢）——与论文消融顺序一致，别 drop reasoning（掉分）
  4. 保留窗口起点：K=12 轮工具响应是论文验证的甜点值，从 12 起调
  5. 正确性红线：若自建 serving 支持真 cache 操作，必须实现"操作历史"随请求显式传递（history dependence），否则 prefix 复用会产生静默错误——这是论文最硬的工程警告
  6. 验证指标：任务通过率（不掉）+ 活跃输入 token（应降）+ P95 延迟（长会话应稳）；三者的基线先测再上线
