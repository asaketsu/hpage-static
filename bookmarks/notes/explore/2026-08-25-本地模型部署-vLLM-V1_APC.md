## 关键发现（增量）

1. **Decode Context Parallelism（DCP，8-7 博客）** — 历史笔记未覆盖
   - 问题：TP 按 attention head 切 KV cache，GQA 最多切到每卡 1 个 KV head，MLA（DeepSeek/Kimi 系）等效单 KV head，纯 TP 下 latent cache 在每个 rank 全量复制
   - 方案：KV cache 按**序列维度**分片，每卡只存 1/N；通信模式 AllGather Q → Compute → AllGather+ReduceScatter（online-softmax LSE 合并）
   - 硬数据：8×B200 + Kimi K2.6 NVFP4，agent 长上下文 trace（中位 67K 输入）：TP 在 c64 打满 100% KV 后吞吐钉死 1,863 tok/s/GPU；DCP 在 c512 仍达 **6,091 tok/s/GPU**（KV 仅 82%），200K+ 序列段 Pareto 前沿与短序列几乎重合
   - 用法：`--decode-context-parallel-size N`（约束：TP ≥ DCP 且整除；GQA 上限 tp // num_kv_heads）；MLA 可选 `VLLM_DCP_Q_REPLICATE=1` 省掉 decode 期 query all-gather

2. **Arm CPU 全栈优化（7-29 博客，Arm 官方）** — 与 Jetson/ARM64 生态直接相关
   - 四层优化：miminalloc 设为 PyTorch Arm 默认分配器（离线吞吐 2.3×，低并发 7×）；libgomp 启用 LSE 原子指令替代 LL/SC 重试循环（吞吐 +9%，TPOT -15%）；oneDNN + KleidiAI 权重 warmup 预打包（吞吐 +16%，低并发 TPOT -60%）；Arm 优化 paged attention kernel 补齐 chunked prefill / prefix caching 支持
   - 量化叠加：INT8 W4A8 相对 2025-10 BF16 基线 = **6.2× 吞吐、7.8× TPOT、2.6× TTFT**（llm-compressor 量化）
   - 启示：CPU 推理不再是"只能跑 demo"，ARM 服务器 + W4A8 已可承载轻量生产

3. **Qwen3.5 混合架构解耦服务达 25K TPS/GPU（8-6 博客）**
   - Qwen3.5 = full-attention + GDN（Gated Delta Network）混合层，P/D 解耦需同时搬运异构 KV cache + Mamba 式 SSM state（NIXL connector，描述符从 4,284 降到 1,650）
   - FlashInfer Blackwell GDN prefill kernel：微基准最高 5.92×，端到端 prefill 吞吐 1.13×，TTFT -12%
   - **async scheduling 两个 KV 传输竞态 bug 曾致精度归零**，修复后才跨过 25K——高吞吐特性与正确性的耦合点值得警惕
   - 排障技巧可抄：`--api-server-count 1` 恢复每 10s 吞吐/KV 利用率日志；`--stream-interval 100` 降低前端开销（代价是 ITL 变差）

4. **版本线推进：0.18 → 0.23（知识基基线止于 0.16/0.17）**
   - v0.18：gRPC server endpoint（替代 FastAPI HTTP）、GPU 加速推测解码、高级 KV offload
   - v0.19：Gemma 4 支持、**async scheduling 默认开启**
   - v0.23.0（2026-08-16）：对齐上游稳定线；vllm-ascend 同步发版
   - 7 月生态：Kimi K3 day-0 支持、GLM-5.2 在 24×B300 NVFP4 PD 生产 SLA、AFD 插件（attention/FFN 解耦）、EAGLE 3.1（5-26，EAGLE 团队×vLLM×TorchSpec 协作）

## 对工作的价值（增量）

- DCP 是长上下文 Agent 服务（64K~1M trace）多卡扩展的关键开关，但需 NVLink 级互联，Jetson 单机不适用；跟踪其思路用于未来工作站规划
- Arm CPU 优化路径（mimalloc/LSE/预打包）验证了 ARM64 边缘推理栈在持续变好，Jetson CPU-offload 模式间接受益
- async scheduling 竞态案例提示：升级 vLLM 后必须跑精度回归（如 GSM8K），不能只看吞吐

## 行动建议（增量）

1. 多卡场景部署 MLA/长上下文模型时评估 `--decode-context-parallel-size`，代替盲目加 TP
2. Hermes 本地 fallback 若走 CPU 路线，量化目标定 INT8 W4A8（llm-compressor 流水线）
3. 生产升级到 ≥0.19 自动获得 async scheduling，升级后跑一次 GSM8K/人工抽检验证正确性
