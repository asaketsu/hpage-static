一、核心问题：Cron 的静默失败

Cron 诞生于 1970s，设计假设是"sysadmin 会定期巡检"。今天这个假设不成立，导致三类静默失败：

  1. 任务崩溃无人知 — cron 只管启动进程，不管成败，无告警无通知
  2. 任务根本没跑 — 服务器重启 cron 未拉起 / crontab 被误删 / 磁盘满无法写 lockfile，日志里什么都没有
  3. 部分失败 — 数据管道跑一半挂掉，留下脏状态，下次运行基于脏数据继续错

最危险的杀手是任务没跑而非跑挂：跑挂有日志可查，没跑连日志都没有。

二、生产级 Cron 十大守则（CronWizard 2026）

2.1 幂等性是第一属性

生产 cron 假设"至少会跑两次"：调度器重试、运维手动重跑、容器重启重排。若假设 exactly-once，三者必 corrupt 数据。

幂等实现模式：
- DB 写入用 upsert（INSERT ... ON CONFLICT / MERGE）替代裸 insert
- 队列消费：成功后才 ack，重复投递无害
- 行级状态跟踪（processed_at / last_run_id），已处理行直接跳过
- 文件任务：处理完移到 done/ 目录或打扩展属性标签
- 天生不幂等的操作（发邮件/扣款/外部API）：记录确定性 idempotency key，
  下游可检测重复

2.2 flock 防重叠执行

5 分钟的 job 偶尔跑 10 分钟就会自重叠，两份备份写同一目标 = 浪费或损坏。

* * * * * /usr/bin/flock -n /var/lock/my-job.lock /opt/bin/my-job.sh
  • -n 拿不到锁立即退出（丢弃新实例）而非排队
  • K8s：concurrencyPolicy: Forbid（禁止重叠）或 Replace（最新覆盖）
  • 跨机多副本：PostgreSQL pg_try_advisory_lock 或 Redis TTL key；文件锁只护单机

2.3 时区钉死

code review 中最常见的 cron bug。Docker 容器默认 UTC；K8s 1.27+ 可显式 timeZone 字段。DST 切换时"9 AM 任务"会变 8 AM 半年。

2.4 监控调度本身（死信开关 Dead-man's Switch）

核心思想：告警依赖"执行的积极证据"，而非进程报错。

心跳三实现：
- 托管服务：Healthchecks.io / Cronitor / Better Stack（成功后 GET ping URL，超时未达则告警）
- Prometheus counter + 告警规则：increase(cron_job_completed_total[1h]) == 0
- 内部团队：失败才调 Slack/PagerDuty webhook + N 小时无任何消息则二级告警

2.5 错峰调度防惊群

百个 CronJob 同为 0 * * * * → 同毫秒启动，争抢 DB 连接/内存。对策：分钟位故意分散（3/17/31 分），动态生成的 fleet 按 job 名 hash 到 0-59。

2.6 显式超时

挂死的 job 会占住 DB 连接、锁文件、API 配额。

*/5 * * * * timeout 240 /opt/bin/refresh-cache.sh

超时值取调度间隔以下（5 分钟任务 4 分钟超时，留清理余量）。K8s 用 activeDeadlineSeconds + backoffLimit。

2.7 日志即取证材料

结构化 JSON（job_name/run_id/environment/时长/exit code/处理行数），stdout+stderr 都要捕获（command 2>&1，crontab 默认丢弃 stderr），集中转发。

2.8 调度进版本控制

手编 crontab 是最恶劣的运维秘密：会漂移、重建主机即消失、无法 code review。Ansible/Puppet 管 /etc/cron.d/，K8s YAML 进 Helm chart，GitHub Actions schedule 进 workflow 文件。

2.9 注释写"为什么"

cron 表达式只有 what/when 没有 why。6 个月后没人记得 0 4 * * 1-5 为何正确。一行注释 20 秒，事后考古数小时。

2.10 上线前验证

验证器跑一遍 + 打印未来 10 次执行时间在生产时区读一遍 + staging 先行 + 高影响任务第二人复核。

三、监控什么：分级策略（OnlineOrNot）

必须监控：备份 / 影响钱的任务（账单/发票/支付）/ 数据管道与同步 / 安全任务（证书续期/日志轮转）
建议监控：报告与通知 / 清理任务 / 健康检查
可以不监控：停了你几小时都注意不到的低价值任务

判断规则："如果这个任务停了，你希望 1 小时内知道吗？"——是，就监控。

心跳落地三步：① 成功后 && curl -fsS --retry 3 <ping-url>（&& 保证失败不发心跳）；② 设宽限期（日任务 30-60 min，时任务 10 min）；③ 告警双通道（Slack 知晓 + SMS 叫醒）。

四、分布式锁的边界：锁防效率，幂等保正确

中文源（dunwu/waterdrop 分布式协同面试题）贡献了最深刻的一条工程判断：

分布式锁只能互斥"正常活着的客户端"。锁 TTL 与客户端 GC 停顿天然矛盾——锁只能防效率（99% 并发），正确性兜底必须靠 fencing token 或幂等。

真实事故案例：对账任务双实例 Redis 锁互斥，实例 A 持锁期间 Full GC 停顿 45s，锁 TTL（30s）过期后 B 拿锁开跑；A 醒来误以为仍持锁继续执行 → 双实例并发修改同一批记录 → 重复平账。日志显示两实例同批次处理时间重叠 12 秒。

修复三件套：① 关键写操作加 fencing（UPDATE ... WHERE lock_version = ? 条件更新，旧版本写入被拒）；② GC 调优减少长停顿；③ 对账动作幂等化。

配套工具链：Redisson 看门狗自动续期（解"锁过期但业务未完"）、finally 确保解锁、Lua 脚本保证"只能加锁者解锁"。

五、与现有工作的关联（对 Skill/笔记改进建议）

按优先级排序：

  • P0 — watchdog/cron-bulk-management skill 补"死信开关"模式：当前 Hermes cron 依赖 watchdog 轮询发现问题，缺"任务成功后主动心跳 + 超窗告警"层。建议在 watchdog skill 中补充 heartbeat 检查清单：所有关键 cron（auto-learner/evensing-summary/backups）应有可验证的成功信号，而非只查进程错误。
  • P0 — 本机 cron 静默失败检查：[SILENT] 回复机制本身就是一种死信开关（预期窗口内无输出即异常），但需验证 cron job 级超时包裹（timeout N）是否已配置，防止挂死占住 gateway。
  • P1 — 队列状态机与幂等呼应：sniff-queue.json 的 processing 状态残留（进程崩溃后卡 processing）正是"非幂等 + 无锁"的典型症状，与本文 2.1/2.2 节直接呼应。已有 sniff-auto 崩溃恢复机制，可补充 lockfile 防双 cron 并发。
  • P2 — 笔记双格式与其他 Cron 守则：时区钉死（服务器 UTC vs 用户 CST）在跨国调度时需注意；错峰调度对 Jetson 单机多 cron（10:35/16:35/22:35 已错峰）已天然满足。

六、Actionable Insights

  1. 给所有关键 cron 加 && curl 心跳：30 秒/任务的投入，把"数周后才发现备份没跑"变成"数分钟内告警"。
  2. 幂等设计前置：写任务时先问"跑两次会怎样"，用 upsert/状态标记/idempotency key 三件套回答。
  3. flock 是单机 cron 的免费保险：flock -n <lockfile> 一行改动，防自重叠。
  4. 告警依据"积极证据"：监控"心跳到了没有"，而非"有没有报错"。
  5. 锁 + fencing 分工：分布式场景锁防 99% 并发，fencing/幂等保 1% 极端正确性，两者不可互相替代。

七、关键风险与盲点

  • 托管心跳服务的单点依赖（来源级别：官方文档）：Healthchecks.io 等本身也可能宕机，双通道告警（托管 + 本地 Prometheus 规则）是更稳架构。
  • flock 与长任务的边界（社区复现）：-n 直接丢弃新实例——若任务是"必须跑完"型（如备份），丢弃意味着本次备份缺失，应改用排队或 Replace 语义并告警。
  • 时区问题的隐蔽性（官方验证）：DST 切换前一切正常，切换后偏移 1 小时——上线前"打印未来 10 次执行时间"是唯一可靠预防。
  • K8s backoffLimit: 0 的反面（社区讨论）：不安全重试的任务设 0，但瞬态网络失败也会放弃，需配合外层重试策略。

八、一页速查

幂等：upsert / ack-after-success / processed_at / idempotency key —— 假设会跑两次
防重叠：flock -n（单机）/ concurrencyPolicy: Forbid（K8s）/ advisory lock（跨机）
时区：容器默认 UTC，K8s 1.27+ 显式 timeZone，DST 是隐形炸弹
死信开关：job && curl ping-url，告警看"积极证据"（心跳是否到达）
错峰：分钟位分散，fleet 按 job 名 hash
超时：timeout N（N < 调度间隔），K8s activeDeadlineSeconds
锁的边界：锁防效率（99%），fencing/幂等保正确（1%），缺一不可
监控分级：备份/钱/数据管道/安全 = 必须；报告/清理 = 建议；停了没人注意 = 可免
