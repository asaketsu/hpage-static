# AI安全与防御：形式化验证（Formal Verification）

> 自动探索笔记 | 2026-06-14 | 类型: auto-explore

## 摘要

形式化验证（Formal Verification）是用数学方法证明系统满足特定安全属性的学科，长期处于学术边缘。2025-2026年，LLM 辅助证明生成的能力爆发，使其走向主流成为可能。核心趋势是：AI 让证明变便宜（自动化 proof writing），同时 AI 生成的代码需要被验证（Vericoding），两者形成正反馈闭环。但对 LLM 本身的完整形式化验证仍受限于维度灾难、连续性问题和高层次安全属性的形式化难题，当前可行路径是"验证小组件"而非整模型。

## 关键发现

### 1. AI 驱动形式化验证成本断崖式下降（Kleppmann 预测）

- 历史痛点：seL4 微内核 8,700 行 C 代码需要 20 人年 + 20 万行 Isabelle 证明（每行实现 = 23 行证明 + 半人天）
- 转折点：LLM 写证明脚本时"幻觉无害"——证明检查器（proof checker）是小型已验证代码，拒绝任何无效证明并强制重试
- 关键工具链：Lean、Isabelle、Rocq（Coq）、F*、Agda
- 新术语："Vericoding"（2025年9月 arXiv:2509.22908 提出），对比 "Vibecoding"，指 LLM 生成带机器检验证明的代码
- 新瓶颈：从"写证明"转移到"写规范（Specification）"——AI 可辅助自然语言↔形式化规范翻译

### 2. FMxAI（形式化方法×AI）2026年爆发信号（LessWrong 通讯）

- Nicholas Carlini（安全研究大牛）声明："Opus 在找 0-day 比我强"——被视为 SPS（Secure Program Synthesis）"征兵令"
- 实操模式：agentic red-blue 加固循环——红队 agent 用 fuzzing/静态分析找漏洞，蓝队 agent 修补，git submodule 管理源码
- AISLE 项目在 OpenSSL 中找到 12/12 个 0-day（未明显使用形式化方法）
- CSLib 项目：Clark Barrett + Swarat Chaudhuri 打造"计算机科学的 mathlib"
- VeriSoftBench：500 个来自 23 个真实项目的定理证明任务，覆盖编译器/类型系统/智能合约/分离逻辑——一个"不聚焦数学"的 Lean eval
- muInference：在 seL4 上启动最小化推理飞地，无机器可读 TTY（极致安全）

### 3. LLM 完整形式化验证的五大难题（APXML 课程）

- 维度灾难：数十亿~万亿参数，计算成本指数增长
- 高层属性难形式化："无害""诚实""不操纵"无机器可理解定义
- 抽象鸿沟：简化模型上证明的保证可能不适用于真实模型
- 静态假设失效：部署中的 LLM 动态交互，有效"状态"不断变化
- 连续性问题：嵌入/浮点运算天然连续，传统形式化验证擅长离散状态系统

### 4. 当前可行路径

- 验证小组件：安全护栏（guardrails）、内容过滤器逻辑、专用小模型
- 属性专用验证：对抗扰动鲁棒性边界认证（区间界传播等）
- 验证引导测试：用形式化方法定位难例区域，指导定向红队
- 近似/概率验证：追求"P(有害输出) < 10⁻⁹"而非绝对确定性

## 对工作的价值

- **AI Agent 安全加固**：Herald/Agent 系统的权限控制、沙箱隔离等关键路径，可用 TLA+ 建模验证（类似 OpenClaw 的做法）
- **自动化代码审计**：red-blue agent 循环可用于自有代码库的自动化漏洞发现与修补，降低人工安全审计成本
- **LLM 输出验证**：对 Agent 生成的高风险操作（如 shell 命令、配置变更），可引入轻量形式化检查（schema 约束、类型系统）作为确定性护栏
- **技术前瞻**：Lean/Coq 生态正在快速 AI 化（DeepSeek-Prover-V2 等），值得跟踪以评估引入 proof-carrying code 的时机
