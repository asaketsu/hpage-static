## 🎯 核心问题与研究动机

### 问题定位

当前多模态 Agent（"think with images"范式）面临一个根本性的**表示瓶颈**：

**RL 方法的缺陷**：GRPO/RLOO 等 RL 方法将完整的交互轨迹（trajectory）压缩为标量奖励（scalar reward），策略模型只能通过梯度更新隐式吸收工具使用模式。这意味着：
- 每个新任务都要从头发现可复用的工具使用模式
- 长序列任务的能力积累既不稳定也不高效
- 根本原因是表示层面的失败——成功的轨迹被当作奖励信号消费，而非蒸馏为可复用的结构化知识

**记忆方法的缺陷**：Reflexion、Voyager、ExpeL、MemP、Dynamic Cheatsheet 等基于记忆的方法虽然保留了过去经验，但存在两个问题：
- 记忆构建与策略改进解耦——更强的策略不会自动产生更好的经验，更好的经验也不会反过来增强策略
- 扁平化记忆结构无法区分细粒度局部执行 vs 高层任务组织两种不同粒度的知识

### SPyCE 的核心洞察

> 多模态推理轨迹应该被蒸馏为**可复用的技能**，在训练过程中与策略**协同进化**，而非被当作奖励消费或从静态存储中检索。

## 🔧 方法论

### 整体架构：闭环协同进化

SPyCE 建立了**技能 ↔ 策略的闭环**：

1. 策略条件化于检索到的技能 → 生成更好的 rollout
2. 高质量 rollout 蒸馏回技能库 → 技能库进化
3. 更好的技能 → 为后续策略更新提供更强的先验
4. 循环往复，形成正反馈

### 形式化：POMDP + Group-based Policy Optimization

- 多模态工具使用推理形式化为部分可观测马尔可夫决策过程（POMDP）
- 任务 T = (q, I)：自然语言查询 q + 图像集 I
- 轨迹 τ = [(s₀, a₀, o₀), ..., (s_T, a_T, o_T)]
- 采用 GRPO 目标（组内标准化优势）+ KL 正则化

**奖励设计的关键巧思**：
- R(τ) = R_acc(τ) - λ_call · 1[Succ(τ)=1] · N_tool(τ)
- 工具使用惩罚**仅施加于成功 rollout**——避免不必要地抑制失败 rollout 中的探索
- 消融实验证明：始终惩罚工具调用会导致最大性能下降（-5.9%）

### 分层技能库（核心创新）

**执行技能层 K（Execution Skills）**：
- 编码可复用的局部视觉操作
- 表示为三元组 k = (c, u, e)：
  - c = 触发条件（何时应用此技能）
  - u = 工具动作或动作模板（如何执行）
  - e = 预期局部效果（产生什么证据改善）
- 示例：旋转证据→图像旋转；小目标→局部裁剪
- 由专用 MLLM_dk（Qwen3-VL-235B）从成功轨迹蒸馏

**工作流技能层 H（Workflow Skills）**：
- 编码高层工具编排和工作流先验
- 表示为二元组 h = (b, w)：
  - b = 粗粒度视觉瓶颈描述（如跨区域一致性检查）
  - w = 工作流草图（如 定位证据→增强局部内容→验证一致性）
- 不直接编码可执行动作，而是蒸馏工作流级模式

**技能库合并规则（merge-or-add）**：
- 新候选技能与已有条目做嵌入空间余弦相似度匹配
- 相似度高于阈值→合并（精炼已有条目）；否则→新增
- 执行技能基于触发条件匹配；工作流技能基于瓶颈描述匹配
- 记录每个条目的匹配次数，超出容量上限时淘汰最少匹配的条目

### 分层技能检索（两阶段）

1. **先检索工作流技能**：actor 模型生成粗粒度瓶颈查询 → 检索 Top-K 工作流技能
2. **再条件化检索执行技能**：基于检索到的工作流先验 → 模型分解任务为细粒度局部瓶颈描述符 → 每个描述符检索最佳匹配执行技能
3. 相似度低于阈值的描述符被丢弃，策略同时条件化于两层技能选择动作

### 在线技能进化

- 每隔 N 步打开一个进化窗口
- 仅保留 GRPO 相对优势 A(τ) 排名最高的轨迹（保留多样性但高质量的模式）
- 从保留的轨迹蒸馏新技能候选 → 应用 merge-or-add 规则更新技能库
- 基于策略改进的新经验持续精炼技能

## 📊 关键实验结果

### 基准测试覆盖

8 个基准，3 大领域：
- 代理推理（think with images）：TIR-Bench
- 多模态推理：MathVerse, MathVision, WeMath, ChartQAPro
- 视觉搜索：V* Bench, HRBench-4K, HRBench-8K

### 主要结果（Qwen3-VL-8B 骨架）

**多模态推理 + 视觉搜索**（vs 最强基线）：
- V*：84.3 vs GRPO 82.2 (+2.1)
- HRBench-4K：78.0 vs GRPO 77.2 (+0.8)
- HRBench-8K：74.3 vs GRPO 72.9 (+1.4)
- MathVerse：68.7 vs GRPO 66.5 (+2.2) ← 最大增幅
- MathVision：61.2 vs GRPO 57.7 (+3.5) ← 最大增幅
- WeMath：67.8 vs GRPO 66.6 (+1.2)

**TIR-Bench 代理推理**（整体准确率 + 工具调用效率）：
- All：32.0 vs GRPO 27.7 (+4.3)
- 工具调用次数：4.83 vs GRPO 5.13（更少）——更好的效果-效率权衡
- 提升集中在需要序列变换和工具编排的类别：OCR (58.3), JG (43.3), VS (52.0), Math (44.2)

### 消融实验（TIR-Bench, Qwen3-VL-8B）

| 消融项 | 准确率 | 下降幅度 | 工具调用 | 关键发现 |
|--------|--------|----------|----------|----------|
| Full Model | 32.0 | — | 4.83 | 完整模型 |
| w/o Workflow Skills | 28.0 | -4.0 | 5.91 | 高层技能对全局规划和多步协调至关重要 |
| w/o Execution Skills | 28.7 | -3.3 | 5.33 | 低层技能支撑精确局部执行 |
| Frozen Skills | 28.9 | -3.1 | 5.54 | 静态技能库不如在线进化 |
| w/o Tool-call Penalty | 29.4 | -2.6 | 6.83 | 惩罚防止过长工具链 |
| Always Penalize | 26.1 | -5.9 | 3.96 | 过度惩罚抑制有用探索，降幅最大 |

**三个关键发现**：
1. 两层技能互补——工作流技能管全局规划，执行技能管精确局部执行
2. 在线技能进化优于静态技能库（+3.1%）
3. 奖励设计需要精确平衡——仅在成功 rollout 上施加工具惩罚效果最佳

### 技能库进化动力学

- **执行技能**：训练早期持续增长，平均成功率上升；约 100 步后达到容量上限，之后以合并精炼为主而非扩展
- **工作流技能**：数量相对稳定，仅有微小变化——进化形式主要是合并和更新现有结构
- 两层技能的不同进化模式反映了各自的功能角色

### 训练收敛

- SPyCE 在训练早期阶段就显著快于 GRPO，前几次更新后就出现明显性能差距
- 收敛到更高的成功率，而 GRPO 改善更缓慢且停留在较低水平

---

## 💡 创新点分析

1. **首次建立训练期间技能与策略的在线协同进化闭环**——区别于 RL 方法（策略独占优化）和记忆方法（经验与策略解耦）
2. **分层技能抽象**——执行技能（condition-action-effect 三元组）+ 工作流技能（bottleneck-workflow 二元组），自然分离局部操作和高层编排
3. **merge-or-add 合并规则**——通过嵌入空间相似度匹配控制噪声和冗余，通过匹配频次淘汰实现容量控制
4. **选择性工具惩罚**——仅在成功 rollout 上施加惩罚，保护失败 rollout 中的探索行为

---

## ⚠️ 局限性与未来方向

### 局限性
- 依赖大型 MLLM（Qwen3-VL-235B）做技能蒸馏，推理成本高
- 技能库容量上限是预设的硬约束，未讨论自适应容量管理
- 技能蒸馏质量受限于 MLLM_dk 的能力，蒸馏噪声未充分讨论
- 评估仅覆盖视觉推理和工具使用，未扩展到更广泛的 Agent 任务（如 Web 导航、代码生成）
- 工作流技能的跨任务泛化能力未单独评估

### 未来方向
- 技能迁移：跨模型、跨领域迁移技能库
- 自适应容量管理：根据任务复杂度动态调整技能库大小
- 技能质量评估：自动检测低质量或过时技能
- 多 Agent 共享技能库

## 🔗 借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

### P0 — Skill 系统分层架构（可直接移植）

SPyCE 的两层技能抽象直接映射到 Hermes 的 Skill 系统：

- **执行技能 → Hermes Skill 中的具体操作步骤**：当前 SKILL.md 中的"Step 1/2/3"步骤正是执行技能——condition-action-effect 三元组可以规范为 Skill 的前置条件、执行动作、预期结果
- **工作流技能 → Skill 间的编排模式**：当前 Hermes 靠 LLM 在运行时临时组合多个 Skill，缺少显式的工作流技能抽象。可以引入"元 Skill"（meta-skill）概念，编码 Skill 编排模式
- **具体改进**：在 SKILL.md frontmatter 中增加 `trigger_condition` 和 `expected_effect` 字段，使 Skill 可被结构化检索和匹配

### P0 — Skill 在线进化机制（需工程改造）

SPyCE 的 co-evolution 闭环与 Hermes 的 `evolver` skill 高度相关，但 Hermes 当前的进化是离线的（用户手动或 cron 触发）：

- **可借鉴**：从高质量 rollout（成功任务会话）中自动蒸馏 Skill 更新——而非依赖手动审查
- **可借鉴**：merge-or-add 规则可直接用于 Hermes Skill 合并——通过嵌入相似度检测冗余 Skill，自动合并
- **可借鉴**：基于匹配频次的淘汰机制——Hermes 中 >3 天未使用的 Skill 自动进入候选淘汰队列（已部分实现于 `skill-review` skill）
- **关键障碍**：Hermes 运行时无训练能力，无法做到策略模型梯度更新；但可以做"检索条件化"——从历史成功会话中提取 Skill 使用模式，更新 Skill 的触发条件和推荐优先级

### P1 — 分层技能检索（可工程改造）

SPyCE 的两阶段检索（先工作流、后执行）可映射到 Hermes 的 Skill 检索：

- 当前 Hermes 通过 `skills_list` + `skill_view` 平坦检索所有 Skill
- 可以引入**两级索引**：先匹配任务类型/工作流模式（category 级别），再匹配具体操作步骤（Skill 级别）
- `category` 字段已经存在（如 devops、software-development），可作为工作流技能层的第一级检索维度

### P1 — 选择性工具惩罚思想（概念迁移）

SPyCE "仅在成功 rollout 上施加惩罚"的设计哲学可以迁移到 Hermes 的工具使用策略：

- 当前 Hermes 对所有工具调用一视同仁
- 可引入**成功路径回溯**：记录成功任务完成时的工具调用链，对频繁出现在成功路径中的工具调用降低延迟/优先调度
- 对量化交易：仅在盈利交易后评估交易频率惩罚，而非对每笔交易施加频率限制

### P2 — 多模态 Think-with-Images（暂不适用）

SPyCE 核心围绕视觉推理，Hermes 当前以文本工具调用为主。但如果未来扩展到截图分析、图表理解（如量化 K 线图视觉分析），SPyCE 的视觉瓶颈分类和工具编排思想有参考价值。

### P2 — 跨任务技能迁移评估（待研究）

SPyCE 未充分讨论技能跨任务迁移能力。Hermes 的 Skill 天然是跨任务的——一个 `small-batch-execution` Skill 可以用于笔记、代码、文档等多种场景。可以借鉴 SPyCE 的消融方法论来评估 Hermes Skill 的跨领域贡献。

## 📝 总结

SPyCE 的核心贡献在于证明了**技能与策略的协同进化闭环**比纯 RL 或纯记忆方法更有效。其分层技能抽象（执行+工作流）和 merge-or-add 进化机制为构建可积累、可进化、可检索的 Agent 技能系统提供了清晰的工程蓝图。对 Hermes Agent 而言，最直接的价值在于 Skill 系统的结构化设计（分层+检索+进化）和从成功会话中自动蒸馏 Skill 更新的机制设计。
