飞书 API 权限体系深度解析 — Permission 架构、Token 模型与云文档协作

学习日期: 2026-08-09 | 来源: 飞书开放平台官方文档 + 实践案例
关联: Hermes Agent 飞书集成、lark-cli 工具链

一、核心发现

发现 1：双层权限架构 — Scope（接口权限）+ Resource（数据权限）

飞书 API 权限不是单一维度，而是 双层校验：

层次 名称 校验时机 控制粒度
L1: Scope 接口权限 API 调用前 控制应用能否调用某类 API（如"获取用户 ID"）
L2: Resource 数据权限/资源权限 API 执行时 控制应用/用户能访问的具体数据范围（如哪些文档、哪些用户）

关键区分：即使应用申请了 Scope，也不代表能访问任意数据。数据权限进一步限制可访问的数据集。

  • tenant_access_token 调用时：L2 由应用的通讯录权限范围和文档协作权限决定
  • user_access_token 调用时：L2 由当前用户的组织架构可见范围和文档协作者权限决定

发现 2：三种 Token 的精确分工

飞书有三种 access_token，各有明确适用场景：

Token 类型 前缀 需用户授权 有效期 适用场景
tenant_access_token t- 否 2h（剩余<30min时返回新token） 应用自动化操作：机器人发消息、创建应用自身资源
user_access_token u- 是(OAuth) ~2h(refresh续期) 操作用户数据：在用户文档空间创建文件、以用户身份发消息
app_access_token — 否 — 仅用于商店应用获取 tenant_access_token（正逐步合并）

核心规则：
- tenant_token 创建的文档 → 归属应用本身（用户默认无编辑权限）
- user_token 创建的文档 → 归属当前用户
- 这正是 OpenClaw 飞书机器人创建文档后用户无权限的根因（GitHub Issue #252）

发现 3：云文档权限 API 完整图谱

飞书云文档权限分为两大模块：协作者管理（Member） 和 公开设置（Public）

/drive/v1/permissions/
├── members/                    # 协作者管理
│   ├── POST   batch_create     # 批量增加协作者
│   ├── GET    (list)           # 获取协作者列表（新版本）
│   ├── PATCH  update           # 更新协作者权限
│   └── DELETE remove           # 移除协作者
├── {token}/public              # 公开设置
│   ├── GET                     # 获取权限设置
│   └── PATCH                   # 更新权限设置
└── transfer_owner              # 转移所有者

权限角色（协作者可被分配）：
- view — 可阅读
- edit — 可编辑
- full_access — 可管理（完全控制，不含所有权转移）

发现 4：公开设置（Public Settings）的 6 个维度

PATCH /drive/v1/permissions/{token}/public 接口可控制：

字段 说明 可选值
external_access 是否允许对外分享 true/false
security_entity 谁能查看安全实体 anyone_can_view / tenant_readable / collaborator_only
comment_entity 谁可评论 同上
share_entity 谁可分享 anyone / collaborator_can_share
link_share_entity 链接分享范围 tenant_readable / anyone_readable / anyone_editable / off
invite_external 是否允许邀请外部人员 true/false

响应示例：

{
  "code": 0,

  "data": {

      "invite_external": true,

  }
}

发现 5：权限等级与审核机制

飞书权限分为两个等级：

等级 特征 审核
普通权限 数据敏感度不高 自建应用→租户管理员审核；商店应用→平台+租户双重审核
高级权限 数据敏感度较高 审核更严格，"如无必要原因不会通过"

权限申请原则：最小可用原则（Principle of Least Privilege）
- 权限范围过大可能威胁企业数据安全
- 无充分理由避免直接申请大量接口权限
- 每个接口权限在 API 文档中标注了所需 scope

二、技术细节与 API 实操

2.1 批量增加协作者 — 完整请求示例

import requests
import json

url = "https://open.feishu.cn/open-apis/drive/v1/permissions/{token}/members/batch_create"
# {token} 替换为实际文档 token

headers = {
    "Authorization": "Bearer t-g1044qeGEDXTB6NDJOGV4JQCYDGHRBARFTGT1234",
    "Content-Type": "application/json"
}

# member_type: "email" / "openid" / "userid" / "departmentid" / "groupid"
payload = {
    "requests": [
        {
            "member_type": "email",
            "member_id": "user@example.com",
            "perm": "edit"  # view / edit / full_access
        },
        {
            "member_type": "groupid",
            "member_id": "oc_xxxxxxxxxxxxxxxx",
            "perm": "view"
        }
    ],
    "notification": {
        "notify": True,
        "notify_message": "您被邀请协作此文档"
    }
}

# 需要指定文档类型 type
params = {"type": "doc"}  # doc / sheet / bitable / file / folder / wiki

response = requests.post(url, headers=headers, params=params, json=payload)
print(json.dumps(response.json(), indent=2, ensure_ascii=False))

注意：type 参数必须与 token 匹配，否则返回 1063001 Invalid parameter。

2.2 关键错误码速查表

HTTP Code 含义 根因与解决方案
400 1063001 参数无效 token/type 不匹配；member_id/type 不匹配；协作者不存在
403 1063002 Permission denied 调用身份非协作者或权限不足
400 — Invalid operation 协作者超上限；管控策略禁止；给所有者操作权限
— 91403 FORBIDDEN 应用无云文档权限（需通过"添加文档应用"入口授权）
— 41050 no user authority error 用户不在通讯录权限范围内

1063002 的修复路径（最常见错误）：
1. tenant_access_token：文档页面 →「...」→「更多」→「添加文档应用」→搜索应用名→添加
2. 前提：应用至少开通一个云文档 API 权限
3. 多维表格开启高级权限时：需额外授予"可管理"权限

三、对 Hermes Agent 工作的价值与实践启发

3.1 当前痛点诊断

Hermes Agent 通过 lark-cli 集成飞书，但存在已知问题：
1. 创建文档无权限：用 tenant_token 创建文档后，用户无编辑权限（Issue #252 级问题）
2. 协作者管理缺失：目前未自动化"创建文档→授权给用户/群"流程
3. 权限错误排查困难：遇到 1063002 时缺乏快速诊断

3.2 可落地的工作流改进

场景：自动创建飞书文档并授权群组

# 完整工作流（伪代码，适配 Hermes Agent）
def create_doc_and_share_to_group(doc_content, group_id, perm="edit"):
    """创建文档 → 授权群组 → 发送链接到群"""
    # 1. 创建文档
    doc_token = lark_create_doc(content=doc_content)

    # 2. 批量添加协作者（群组）
    lark_add_collaborator(
        token=doc_token,
        doc_type="doc",
        members=[{"member_type": "groupid", "member_id": group_id, "perm": perm}]
    )

    # 3. 设置链接分享范围（可选）
    lark_update_public_settings(
        token=doc_token,
        link_share_entity="tenant_readable"  # 组织内可读
    )

    # 4. 发送文档链接到群
    lark_send_message(group_id, f"📄 新文档已创建: https://feishu.cn/doc/{doc_token}")

    return doc_token

3.3 对 Agent 工程的启示

启示 说明
Token 选择是设计决策 自动化场景用 tenant_token（无需用户交互）；需要访问用户私有数据时用 user_token
权限设计应零信任 最小权限原则 → 按需申请 scope，避免申请大范围权限
资源权限是额外屏障 API scope ≠ 数据访问权，需要额外的资源级授权
错误码是调试金矿 1063002/91403 等错误码提供了明确的修复路径

五、关联分析与趋势判断

5.1 与 Google Workspace API 的对比

维度 飞书 Google Drive API
Token 类型 tenant/user/app (三种) service_account/user (两种)
权限模型 Scope + Resource 双层 OAuth Scope 单层 + ACL
文档所有权 token 创建者（tenant→应用） 创建者明确指定
最小权限理念 ✅ 明确要求 ✅ 最佳实践但非强制
审核流程 平台+租户双重审核 Google 审核（商店应用）

飞书的双层模型更严格（尤其在企业版），适合中国企业合规需求。

5.2 MCP 生态影响

飞书官方已发布 lark-openapi-mcp，将 OpenAPI 封装为 MCP Server：
- 支持 tenant_access_token 和 user_access_token 双模式
- 支持 Feishu（中国版）和 Lark（国际版）域名切换
- 这意味着 AI Agent 可以通过 MCP 直接调用飞书权限 API，无需手写 HTTP 请求

对 Hermes Agent 而言，如果 lark-cli 缺少权限接口封装，可以考虑通过 lark-openapi-mcp 补齐。

六、行动建议

  1. 检查 lark-cli 现有能力：确认是否已封装 batch_create_collaborator 等权限接口
  2. 建立权限错误诊断 skill：将 1063002/91403 的修复路径固化为排查流程
  3. 评估 lark-openapi-mcp 集成：如果 CLI 覆盖不足，考虑 MCP 补充
  4. 文档创建后自动授权流程：在创建飞书文档的工作流中加入"授权给用户/群"步骤
