核心发现（5个）

1. TGI 正式进入维护模式（2025-12-11），新项目不应选 TGI
HuggingFace 官方明确推荐 vLLM 或 SGLang 替代 TGI 用于 Inference Endpoints。TGI 仅接受 minor bugfix 和文档维护。这意味着 2026 年推理引擎选型从"五选一"变成了"四选一"（vLLM / SGLang / TensorRT-LLM / llama.cpp），TGI 降级为遗留系统迁移对象。

2. 场景分化已成定局：没有"万能引擎"，只有"场景最优"
五大引擎已各自锁定不可替代的场景壁垒：
- vLLM = 高吞吐通用默认（PagedAttention + 连续批处理）
- SGLang = 共享前缀 + 结构化输出（RadixAttention 前缀树复用）
- TensorRT-LLM = NVIDIA 极限性能（编译期内核融合，2-3× 通用引擎）
- llama.cpp = CPU/边缘/离线（GGUF 量化，零 GPU 依赖）
- Ollama = 开发者本地原型（llama.cpp 封装，一键部署）

3. SGLang 的 TTFT 优势在交互场景碾压 vLLM
SGLang TTFT 80ms vs vLLM 150ms（A100, Llama 70B），快 47%。但 vLLM 吞吐量 3,500 tok/s vs SGLang 2,800 tok/s，vLLM 高 25%。核心分水岭：批处理排队可接受 → vLLM；首 Token 延迟敏感 → SGLang。

4. MAX（Modular）是新变量：硬件可移植性赛道
MAX 不与 vLLM/SGLang 在吞吐量上正面竞争，而是押注"跨硬件部署"——OpenAI 兼容端点 + Docker/云部署 + 非 CUDA 硬件支持。适合 AMD GPU 或异构硬件团队，但模型覆盖和结构化输出支持需逐模型验证。

5. 成本差异在混合负载下可达 20-30%
Q2 2026 实测每百万 Token 成本（50% GPU 利用率，混合负载）：
- Triton-TRT: $0.48 | SGLang: $0.51 | vLLM: $0.55 | TGI: $0.63
但这是最优配置下的理论值，运维 expertise 不足会快速抹平这些差距。

选型决策树

你的场景是什么？
├── 单用户笔记本/开发机
│   └── Ollama（易用）或 llama.cpp（极致便携）
├── 边缘设备/离线/无GPU
│   └── llama.cpp（唯一选择，GGUF Q4_K_M）
├── 生产多用户API
│   ├── 混合/不确定负载 → vLLM（默认）
│   ├── 共享前缀多(RAG/Agent) → SGLang（RadixAttention）
│   ├── 结构化输出为主 → SGLang（原生语法引擎）
│   └── NVIDIA极限性能 → TensorRT-LLM（接受编译开销）
├── 异构硬件/AMD/可移植
│   └── MAX（Modular，验证模型覆盖后采用）
└── 遗留 TGI 部署
    └── 保持运行 + 规划迁移到 vLLM/SGLang

SGLang RadixAttention 原理

传统缓存: 每个请求独立计算 attention → 重复计算相同前缀
                  ┌──────────────┐
  Request A: [系统提示][文档A]    │  全量计算
  Request B: [系统提示][文档B]    │  全量计算（重复算系统提示）
                  └──────────────┘

RadixAttention (Trie 前缀树):
                  ┌──────────────┐
  [系统提示] ← 共享节点（缓存复用）
   ├── [文档A] → 只算增量
   └── [文档B] → 只算增量
                  └──────────────┘
  → 多轮对话/RAG/Agent 场景计算量骤降

P1 — Jetson 本地部署参考
llama.cpp 是 Jetson Orin Nano 上唯一可行的推理引擎（CUDA 兼容但显存受限）。GGUF Q4_K_M 是 Jetson 量化的默认选择。vLLM 理论支持但实际显存不足。nexa-local-inference skill 已覆盖此场景。

P2 — 量化格式与引擎绑定关系
引擎选型直接决定量化格式：vLLM/SGLang → AWQ/GPTQ；llama.cpp/Ollama → GGUF；TensorRT-LLM → INT4/FP8。选引擎前先确定量化方案。

Actionable Insights

  1. 新项目默认 vLLM，有共享前缀特征则优先试 SGLang — 这条铁律已在 2026-07-19 笔记中确立，本次验证仍然有效
  2. TGI 迁移窗口已打开 — 如果有任何 TGI 部署，现在就应规划迁移路径，不要等到功能停滞才行动
  3. 结构化输出场景 SGLang 有原生优势 — vLLM 的 Outlines 集成会损失 15-30% 吞吐，SGLang 的语法引擎是一等公民无此代价
  4. 成本最优不等于性能最优 — Triton-TRT 理论成本最低（$0.48/M tok），但编译开销和运维复杂度可能抵消优势

关键风险与盲点

  • ⚠️ 吞吐量基准测试高度依赖模型/硬件/提示长度/批大小，不可直接跨来源对比（deploybase 用 A100+Llama 70B，sesamedisk 用 4×A100+FP8，iotdigitaltwin 用混合负载）
  • ⚠️ SGLang 生产成熟度弱于 vLLM（生态覆盖、文档量、社区规模），企业部署需评估运维能力
  • ⚠️ MAX 的模型覆盖未完全验证，采用前必须测试你的具体模型+量化+结构化输出需求
  • ⚠️ TensorRT-LLM 编译后锁定特定 GPU 型号和 CUDA 版本，换卡需重新编译
