一、内容整理

1.1 核心问题：峰值能力 ≠ 运营能力

当前安全 Agent 评估的范式缺陷：只测"在宽松推理预算下的峰值攻击能力"（solve CTF / find vuln / write exploit），而忽略了一个事实——运营安全不是峰值能力练习。

一个 SOC（安全运营中心）需要 Agent 在预算约束下：
- 导航遥测（telemetry navigation）
- 选择性发起搜索（choose searches）
- 判断何时值得花钱做富化查询（decide when enrichment is worth paying for）
- 在预算下返回分析师级答案（return analyst-grade answers under a budget）

论文提出 cost-success 视角：把成本作为比较攻防 Agent 的共同轴。固定预算把成功率变成一个运营问题——每美元推理和工具开销能买到多少能力。

1.2 攻防成本结构解耦

这是论文最重要的概念区分之一：两种任务的"成本"含义不同。

  • 进攻（CTF）成本：主要是 test-time reasoning（推理）和 command execution（命令执行）。margin 的钱花在"想更多"和"试更多"。
  • 防御（SOC）成本：除了模型 token，还消耗分析师可见的资源——Splunk 查询、事件检查、web 搜索、WHOIS 历史、富化调用。这些是真实的分析师侧资源消耗，不是免费推理。

1.3 评估设计

实验框架：Inspect（UK AI Security Institute 出品），ReAct-style agent + auto-compaction（上下文达到 90% 模型窗口时自动压缩）。

进攻基准：Cybench（hard variant）
- 39 个 CTF 挑战，来自 HackTheBox / Glacier / SEKAI / HKCert 四大赛事
- 覆盖 crypto / web exploit / reversing / forensics / pwn
- 每挑战 3 次提交机会，3 个独立 epoch 取均值
- 工具：bash + python + submit（全部视为零成本）
- 评判：flag 的 case-insensitive substring match

防御基准：BOTS v1（Splunk Boss of the SOC）
- 31 个计分问题（去掉 warm-up），总分 10,300 官方竞赛点
- 两起调查事件：Po1s0n1vy 网页篡改 + Cerber 勒索软件（Wayne Enterprises）
- 顺序型点数制：后问题依赖前发现，错答揭示提示扣分
- 工具：Splunk SPL 查询（search/discovery/event-inspect）+ VirusTotal/WHOIS/DNS/Brave/bash/Python（限量：VT/WhoisXMLAPI 各 3 次，web search 5 次）
- 主指标：bots_points（正确答案 = 基础分 − 提示扣分；错答 = 0）

成本会计（核心创新）
- model-token cost：模型推理本身的 token 花费
- priced-tool cost：外部富化 API 的真实花费（Brave Search、WhoisXMLAPI 按次计费）
- 两者加总 = 总运营成本；可衍生"cost per solved question"、"cost per 1,000 BOTS points"

关键设计：Agent 不知道成本/token 预算，但知道某些昂贵工具的调用次数限制。这样能测出"模型在不同成本和 token 消耗上限下的成功率"。

1.5 两种 Scaling Regime（最具洞察力的发现）

这是论文最深刻的结论：进攻和防御的 scaling 规律根本不同。

进攻 scaling（Cybench）：成功随成本和 token 单调上升。DeepSeek v4 Flash 从 $0.80 cap 的 76.1% 升到 $2.10 cap 的 86.4%（+10.3pp）。Claude Opus 4.8 更剧烈：从 55.6% 升到 74.4%（+18.8pp）。额外计算能买到更多 solve。工具调用 volume 能替代 per-call quality——DeepSeek v4 Flash 在 800+ 工具调用后仍在提取 solve。

防御 scaling（BOTS v1）：完全不遵守同样的规律。Claude Opus 4.8 用比 DeepSeek 运行少一个数量级的 token 拿到最高分。DeepSeek v4 Flash 把 cap 从 $2.10 翻倍到 $4.20，点数仅从 73.0% 升到 73.9%，而工具调用却从 4,450 飙到 4,938。高工具 volume ≠ 高防御分。

防御能力的真实信号是：
- disciplined tool use（有纪律的工具使用）
- telemetry navigation（遥测导航能力）
- selective enrichment（选择性富化，而非海量富化）

核心洞察：进攻是"试得多就能赢"，防御是"选得对才能赢"。两者对 Agent 能力的要求根本不同。

1.6 BOTS v1 污染控制（关键方法论贡献）

论文做了一件很多评估论文不做的事：no-tools 探针作为污染控制。

不给任何工具（无 Splunk/web/bash/Python），只给问题文本和（可选）前置上下文，让模型从先验知识作答：

  • Claude Opus 4.8 + 前置上下文：74.8%（vs 全 agent 的 93.9%）
  • Claude Opus 4.8 无前置上下文：50.0%
  • GPT-5.5 + 前置上下文：62.1%
  • GPT-5.5 无前置上下文：54.9%

结论：BOTS v1 分数太高，不能作为"实时调查能力"的干净证据。因为 BOTS v1 是公开且老旧的基准，模型在训练数据里很可能见过答案。论文要求：任何公开 SOC 基准在用作能力声明前，必须搭配 decontamination check（无工具 / 无上下文 / 扰动问题 / 查询前作答 / 私有 holdout / 新鲜事件）。

1.7 Retrospective Budget Cap（预算回溯分析）

为了避免"比较不相关模型或 trace"的混淆，论文用回溯 cap：对已完成 trace 重放，在每样本 $0.80 处截断，超支即判该 sample-epoch 失败。这让"同一模型同一基准同一完成 trace"的 paired 比较成为可能，消除了跨模型/跨 trace 的混淆变量。

  • GPT-5.5 Cybench：91.5% → 94.0%（+2.6pp）—— 大部分挑战在 $0.80 内已解，预算不敏感
  • Claude Opus 4.8 Cybench：55.6% → 74.4%（+18.8pp，bootstrap 区间 [10.3, 29.1]）—— 预算极度敏感
  • DeepSeek v4 Flash Cybench：76.1% → 86.3%（+10.3pp）—— 预算敏感
  • BOTS v1 各模型：大多 +0 到 +6.9pp，预算敏感度远低于 Cybench

1.8 拒绝（Refusal）的影响

拒绝事件对攻防的影响也不同：
- BOTS v1：拒绝率低（2/93 ~ 5/93），且不影响已赚点数（后续尝试成功仍得分）
- Cybench：拒绝直接等于失败。GPT-5.6 Sol 拒绝 106/117 导致 9.4% 成功率，Fable 拒绝全部 117 导致 0%——这是策略过滤结果，非能力为零的证据

方法论教训：报 raw success rate 时，必须同时报 refusal count，否则会把"安全策略"误读为"能力缺失"。

二、查询拓展

2.1 Cybench 基准

专业级 CTF 基准，39 个挑战来自真实黑客竞赛（HackTheBox/Glacier/SEKAI/HKCert），覆盖 crypto、web、reverse、forensics、pwn 五大方向。由 UK AI Security Institute 维护，已成为评估 LLM 攻击能力的标准之一。Inspect 框架提供 Cybench hard variant 实现。

2.2 BOTS v1（Boss of the SOC）

Splunk 2017 年发起的蓝队（防御）竞赛，模拟真实企业安全事件调查（Wayne Enterprises 的 Po1s0n1vy 网页篡改 + Cerber 勒索软件）。顺序型、点数制、提示扣分机制，比独立二元问题更接近真实 SOC 工作流。BOTS v2/v3 扩展到 Frothly 企业入侵（v2，51 题）和云重场景（v3，58 题，AWS CloudTrail/osquery/Windows/网络遥测）。

2.3 Inspect 框架

UK AI Security Institute 开源的 LLM 评估框架，支持 ReAct agent、auto-compaction（上下文达 90% 自动压缩）、provider-native compaction、prompt caching、cost tracking。是当前安全 Agent 评估的事实标准工具之一。

2.4 ReAct + Auto-Compaction

ReAct（Yao et al., 2023）是 Reason+Act 循环的经典 agent 模式。Auto-compaction 是在长 trace 中防止 context overflow 的机制：上下文达到模型窗口 90% 时触发，优先用 provider-native 压缩（如 Anthropic 的 compaction API），失败则降级到 summary-based 压缩。这对长任务（>100 步）的稳定运行至关重要。

2.5 Retrospective vs Prospective Budget

Prospective budget：运行前设定上限，超支即停。问题是不同模型在不同 budget 下的 trace 不同，无法 paired 比较。Retrospective budget：先无限制跑完，再在 trace 上回溯施加 cap，同一 trace 可以在多个 cap 下评估。这是论文为了实现"同模型同基准同 trace 的 paired 比较"而设计的方法论创新。

三、归纳总结

3.1 攻防 Scaling 不对称框架

进攻（CTF）Scaling 规律：
  成本 ↑ → 成功率 ↑（单调上升）
  工具 volume ↑ → solve 数 ↑（可替代 per-call quality）
  策略：多试、多算、多调，量变引起质变
  最佳模型特征：高推理预算 + 低 refusal + 持久交互

防御（SOC）Scaling 规律：
  成本 ↑ ≉ 成功率↑（弱相关，甚至负相关）
  工具 volume ↑ → 点数平/降（高调用数常伴随低分）
  策略：选对工具、导航对遥测、选择性富化
  最佳模型特征：工具纪律 + 精准决策 + 上下文管理

3.2 成本感知评估三原则

  1. 报告 operating points 而非 leaderboard：model × task × cost cap × tools × scoring rule 的组合，而非单一"X 模型最强"
  2. 分离 model-token cost 和 priced-tool cost：防御任务的富化 API 有真实分析师侧成本，不能与推理 token 混为一谈
  3. 强制 decontamination check：任何公开基准的绝对分数，必须搭配 no-tools / no-context / perturbed-question 控制组

3.3 Refusal 会计原则

报 success rate 时必须同步报 refusal count，否则会误导：
- 防御任务：refusal 影响小（可后续重试得分）
- 进攻任务：refusal = 直接失败，0% 成功率可能是 100% 拒绝，而非 0% 能力

3.4 基准质量警示

公开 + 老旧基准（如 BOTS v1，2017 年）的绝对分数不可信作为能力证据，因为：
- 模型训练数据极可能已包含答案
- no-tools 探针能拿到 50-75% 分数说明严重污染
- 正确用法：作为 reproducible harness + cost-accounting testbed，而非 clean leaderboard

四、趋势判断

4.1 Agent 评估从"峰值榜"转向"运营象限"

传统 leaderboard（X 模型 Y% 成功率）正在被 operating-point 分析取代。趋势判断：未来 1-2 年，顶级 Agent 评估将普遍采用 cost-success 二维图，而非一维成功率榜。这对 Agent 工程化的启示是——成本控制将成为一等公民指标。

4.2 防御 Agent 的能力瓶颈在"工具纪律"而非"推理预算"

当前 frontier 模型（Claude Opus 4.8、GPT-5.6）在防御任务上的差距，主要来自工具调用效率，而非原始推理能力。趋势判断：防御 Agent 的下一个突破点不是更大模型，而是更好的工具选择策略和上下文管理。

4.3 公开基准污染将成为系统性问题

BOTS v1（2017）的无工具 50-75% 分数证明污染严重。随着模型训练数据持续膨胀，所有公开基准都将面临这个问题。趋势判断：私有 holdout、动态生成、对抗性扰动将成为基准设计的标配。

4.4 Refusal 会计将成为评估标准

论文揭示 raw success rate 不报告 refusal 等于误导。趋势判断：未来安全 Agent 评估论文必须报告 refusal-adjusted success rate，否则会被视为方法论缺陷。

五、关联分析

5.1 与 SPORK（2607.03333）的关联

SPORK 提出自推测 fork 加速 Agent 工具调用，核心是 EQ1 成本模型（最小化 fork 开销）。本论文的成本感知评估框架为 SPORK 这类加速方案提供了评估方法论——不仅要测速度，还要测"每美元买到的能力"。两者在"成本是 Agent 一等公民"上高度一致。

5.2 与 Beyond the Leaderboard（2607.05775）的关联

该论文提出 LLM Agent 六大失败模式分类法。本论文的 refusal 会计与其中"策略性拒绝"失败模式直接呼应——refusal 既是模型行为，也是评估陷阱。两者共同指向：Agent 评估必须区分"能力不足"和"策略拒绝"。

5.3 与 Hermes Agent 的关联（核心借鉴点）

Hermes Agent 日常执行大量工具调用（terminal/search/read_file/patch 等），本论文的成本感知框架直接适用：
- Hermes 的 cron job 有 token 预算，本论文的 retrospective cap 方法可用于评估"每个 cron 在不同预算下的完成率"
- Hermes 的工具调用纪律（skill 选择、工具选择）直接对应论文的"disciplined tool use"概念
- 论文的 no-tools 控制组思路可用于评估"Hermes 不用工具能完成多少任务"——这是 skill 系统价值的量化指标

5.4 与 Jetson Orin 边缘推理的关联

边缘设备的推理预算比云端更受限。本论文的"固定预算下的成功率"评估框架，直接适用于评估边缘 LLM Agent——在 Jetson 有限显存和算力下，哪种工具调用策略能最大化任务完成率。

5.5 与量化交易的关联（间接）

量化交易的回测评估与本论文的 cost-aware 评估有方法论同构：两者都强调"扣除成本后的净收益"而非"峰值收益"。本论文的 priced-tool cost 概念对应量化的交易成本（手续费/滑点），retrospective cap 对应回测中的成本敏感性分析。

七、行动启示与借鉴点评估

借鉴点清单与优先级

P0（高收益、可立即执行）

  • Hermes cron job 成本感知评估：为每个 cron job 记录 token 消耗 + 工具调用数 + 成功率，按 retrospective cap 分析"不同预算下的完成率"。直接复刻论文方法，用于优化 cron 配置。
  • 现状：cron 有 token 预算但无成本-成功率分析
  • 工作量：2-3 小时（解析 cron 日志 + 写分析脚本）

  • 关联 skill：cron-log-analysis, observability-dashboard

  • Refusal/失败原因会计：Hermes 工具调用失败时，区分"能力不足"（参数错误、逻辑错）和"策略拒绝"（权限拒绝、安全拒绝），避免把拒绝误读为能力缺陷。

  • 现状：失败原因未分类统计
  • 工作量：1-2 小时（在 watchdog/error-monitoring 中加 refusal 分类）

P1（中收益、需工程改造）

  • 工具调用纪律指标：为每个 task 记录"工具调用数 / 任务完成度"，识别高 volume 低效率的模式（如 DeepSeek v4 Flash 在 BOTS 的 4,938 调用只拿 73.9%）。用于诊断 Hermes 是否有"工具滥用"问题。
  • 关联 skill：observability-dashboard, agent-reliability-engineering

  • 工作量：3-4 小时（扩展日志格式 + 仪表板）

  • No-tools 控制组思路：对 Hermes 的核心能力（如笔记生成、项目脚手架），定期跑"无工具"基线，量化 skill/工具系统的增量价值。如果无工具也能完成 50%，说明 skill 系统价值被高估。

  • 工作量：2 小时（设计控制实验）

P2（低收益或需较大改造）

  • priced-tool cost 会计：Hermes 调用的外部 API（智谱、Tavily、web_search）有真实成本。记录每次调用的实际花费，做"cost per completed task"分析。
  • 障碍：需追踪每个 API 的计费规则

  • 工作量：4-6 小时

  • retrospective cap 回放：对完成的 trace 重放，在不同 token 预算处截断，看任务完成率如何随预算变化。适合分析长任务（如 daily-paper-reading 全流程）。

  • 障碍：需保存完整 trace，Hermes 当前日志可能不够细粒度
  • 工作量：6-8 小时
