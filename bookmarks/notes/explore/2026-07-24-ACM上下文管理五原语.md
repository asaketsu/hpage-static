# Agentic Context Management：从"存储"到"全生命周期"的 Agent 上下文管理范式

> 作者：Gaurav Dadhich（Maximem AI）
> 代码：github.com/maximem-ai（含开源 eval harness）

## 一、核心问题与研究动机

生产级 AI Agent 的主要失败原因不是"推理能力不足"，而是"无法管理推理上下文中应该有什么"。

论文指出当前行业将这个问题框定为"记忆"（memory）——一个存储和检索问题。这个框定本身是局限的。Agent 需要在每一轮对话中做出五种决策：

1. 刚说的内容中哪些值得保留
2. 以什么结构保留
3. 已保留的所有信息中，哪些属于当前轮次需要的上下文
4. 下一轮可能需要什么
5. 当相关上下文超出模型预算时该怎么办

这五个决策发生在五个不同时刻，而"存储"只覆盖了其中一个。

行业现状佐证：McKinsey 2025 报告显示，多数企业在试验 AI Agent，但只有约 1/4 报告扩展中，不到 10% 在单个业务功能中成功规模化。绝大多数 Agent 试点永远无法进入生产。

## 二、核心理论框架：ACM 五原语

论文提出 **Agentic Context Management（ACM）** 学科定义，分解为五个原语：

### 原语 1：Architecting（架构设计）
- 在存储任何记忆之前，必须决定给定 Agent 的记忆形态
- 哪些信息类别重要、如何提取、存储在哪、保存多久、如何检索和压缩
- 关键论点：**通用固定 schema 无法同时服务金融支持 Agent 和编码助手**——它们的类别、保留策略和压缩需求完全不同
- Maximem Synap 采用自主 LLM 推理的设计步骤，根据 Agent 用途生成定制架构

### 原语 2：Ingesting（摄入）
- 原始信号（对话轮次、多模态文档、工具调用及响应）必须转化为结构化、可检索的记忆
- **核心观察：检索质量受限于摄入质量**
- 反例：存"用户提到了定价计划"永远无法检索到"用户在4月3日从 Starter 升级到 Pro"这个具体事实
- 摄入是异步队列驱动的多阶段管线：资格审查→提取记忆类别（事实/偏好/事件/情感/时间事件）+ 实体/关系/时间有效性→实体解析→多存储持久化
- **实体解析**：同一实体以多种表面形态出现（"Sarah"/"Sarah Chen"/"SC"），通过置信度排序的级联匹配策略解决——从精确标识符到渐进式宽松的词法/语义/上下文信号

### 原语 3：Scoping（作用域管理）
- 在摄入和检索时，系统必须决定哪些信息与未来相关，在什么作用域内
- **三级作用域层次**（从窄到宽）：
  - user（个体用户/子 Agent）
  - customer（用户所属的组织）
  - client（跨多组织的平台运营者）
- 摄入和检索都应**从窄到宽**解析：先 user，再 customer，再 client，严格执行隔离
- 全局知识层单独存在（如公共实体的规范身份）
- **作用域泄漏失败模式**：一个用户的偏好出现在另一个用户的会话中

### 原语 4：Anticipating（预取）
- Agent 不知道自己不知道什么。如果从不主动请求，就不可能检索到
- 借鉴计算机系统的**推测性预取**（speculative prefetching），应用于 Agent 上下文
- 不同于缓存：缓存重放已查询的答案；预取从 Agent 的行为演化中预测尚未请求的上下文，在请求到达前准备好
- **价值在于延迟而非去重**：将阻塞式检索往返变为缓存读取
- 当前实测命中率 60%+

### 原语 5：Compacting & Consolidation（压缩与合并）
- 当相关上下文超出下游模型预算时，系统必须在不丢弃关键信息的前提下削减
- **核心论点：压缩必须是可验证的操作**
  - 无验证的压缩比不压缩更糟糕——它产生自信的错误答案
  - 先例：Zhang et al. (2025) 将 18,282 token 压缩到 122 token，任务准确率从 66.7% 降到 57.1%，**低于完全不提供上下文的基线**
- Maximem Synap 的验证压缩：检查原始对话的关键信息是否能从压缩结果中恢复，输出显式验证分数和压缩比，验证不达标时自动降级重试

### 原语间的耦合
五个原语相互耦合：架构原语选择的配置改变了其他四个原语应该做什么。这种耦合是**将上下文作为系统管理**（而非拼装五个独立工具）的核心论据。

## 三、经济论证：为什么全生命周期管理是必需的

### 3.1 不做任何管理的成本是 O(n²)

朴素"全追加"模式（每轮重新发送完整历史）：
- 第 k 轮输入上下文 ≈ k·t tokens
- n 轮累积输入 token：C_append ≈ (t/2)·n² = **O(n²)**
- 因为提供商按输入 token 计费，成本随对话长度二次增长

如果系统将上下文限制在固定预算 W：
- 累积 token：n·W = **O(n)**
- 全追加与有界上下文的成本比：t(n+1)/(2W)，随 n 线性增长
- 示例值（t=500, W=4000）：100 轮时 6×，200 轮时 13×

### 3.2 朴素压缩会摧毁准确率

有界预算是必要的，但如何决定边界决定了是否保持准确率。

- **粗糙摘要**（crude summarization）：限制 token 但有损且无验证，损失可能是灾难性的
- **验证压缩**（validated compaction）：O(n) 成本 + 保持保真度

三种方案的准确率-成本前沿：
- 全追加：O(n²) 成本，完整（直到上下文腐蚀）
- 粗糙摘要：O(n) 成本，有损未验证 → 准确率悬崖
- 验证压缩：O(n) 成本，保持且检查 ← **目标**

### 3.3 检索不等于充分性

答案质量 ≤ min(摄入质量, 检索质量, 推理充分性)

每一个环节都会限制输出质量：
- 存入垃圾 → 摄入质量限制你
- 检索到错误材料 → 检索质量限制你
- 检索到部分相关材料但非全部推理所需 → 推理充分性限制你（**最被忽视的瓶颈**）

**五域检索对照研究**（10,000 文档/域 × 5 域 × 1,000 查询/域，MRR@10 评分）：
- 代码检索（CodeXGLUE）：向量 0.91 vs 关键词 0.29（语义鸿沟最大时向量完胜）
- 科学QA（SciQ）：关键词 0.81 vs 向量 0.61（术语是精确实体时关键词完胜）
- 事实QA（SQuAD）：持平
- 多跳推理（HotpotQA）：略偏向关键词
- **向量税**：索引同一语料库，向量嵌入生成比关键词索引慢 **60-100 倍**

关键发现：现有评测（包括 HotpotQA）只评"金标文档是否出现在 Top-K"，**无法检测最重要的 Agent 失败——检索到了相关文档但缺失完成推理链所需的桥接文档**。

**结论：检索必须结合词法和语义信号——关键词+向量混合检索**。再加上图检索保留关系信息和来源管理，形成三路混合。

## 四、参考实现：Maximem Synap 系统

### 客户端界面
- 异步优先 SDK（Python 正典，JavaScript 桥接）
- 记忆写入立即返回摄入 ID，永不阻塞
- 统一的作用域感知检索调用
- 会话压缩调用 + 流式通道
- 租户隔离在存储层（每租户命名空间）和查询层（作用域谓词）双重强制

### 多语言存储栈（polyglot）
- 向量存储（嵌入）
- 图存储（实体-关系图）
- 关系存储（真相来源 + 短期上下文）
- 对象存储（原始内容 + 每 Agent 配置）
- 时序存储（使用遥测）
- 内存存储（队列/缓存/协调）

### 生产集成模式（核心三调用模式）

每轮对话围绕模型调用的三步操作：
1. **FETCH**：作用域感知检索过去上下文（scope={user, customer}）
2. **COMPACT**：验证压缩当前会话
3. **MODEL**：组装（检索+压缩+最近轮次）调用模型
4. **INGEST**：异步摄入新轮次（立即返回摄入 ID）

关键：此模式中**没有** schema 设计、嵌入模型选择、索引管理和隔离逻辑——这些都是生命周期的工作。

### 压缩的线性成本证明

验证不是免费的——压缩+检查需要消耗 token。但压缩不是一次性事件：每 p 轮触发一次，每次处理已压缩上下文+最近轮次。N 轮总 token 成本：N·W·(1+c/p)——即 O(n) 乘以固定因子。

对比 O(n²) 全追加基线，节省随对话长度增长：
- t=500, W=4000, p=8, c=2（固定 1.25× 开销）
- 100 轮节省 ~80%
- 200 轮节省 ~90%
- 500 轮节省 ~96%

## 五、关键实验结果

### LongMemEval 基准（500 题，6 类能力）

总分 **92.0%（460/500）**，使用 gpt-5-mini 作为答案模型和裁判

分项：
- 单会话用户信息：100%（70/70）
- 单会话用户偏好：100%（30/30）
- 知识更新：100%（78/78）
- 时间推理：100%（133/133）
- 单会话助手信息：87.5%（49/56）
- **多会话推理：75.2%（100/133）← 最弱类别**

### LoCoMo 基准（~300 轮长对话）

总分 **93.2%**（类别 1-4，排除对抗性类别 5）

分项：
- 多跳推理：97.3%
- 开放域：93.4%
- 时间：90.8%
- 单跳：88.8%

### 竞争格局（LongMemEval 自报数据，非控制对比）

- Maximem Synap：92.0%（gpt-5-mini）
- SuperMemory：85.2%（Gemini-3 Pro）
- Zep：71.2%（gpt-4o）
- Mem0：未公布
- Letta (MemGPT)：未公布

关键观察：Maximem Synap 使用**更小的答案模型**（gpt-5-mini）达到了最高分——增益来自上下文层而非模型能力。

### 弱点诚实声明

残留错误集中在多会话类别（75.2%）——必须跨多个独立会话连接信息的推理，恰好是论文 3.3 节描述的"推理充分性"机制。

## 六、创新点分析

1. **范式重构**：将"记忆"（存储问题）重新定义为"上下文管理"（生命周期问题），这是概念层面的核心贡献。不是更好的记忆工具，而是更高的抽象层级。

2. **五原语分解**：将模糊的"上下文管理"操作化为五个可独立评估的原语，每个原语都有对应的**命名失败模式**（Table 1）：垃圾累积、细节丢失、身份碎片化、作用域泄漏、跨会话遗忘、检索在关键路径上、准确率悬崖、二次成本增长。

3. **经济论证的数学严谨性**：不只是说"管理上下文很重要"，而是证明了不管理的成本是 O(n²)，有界管理是 O(n)，且验证压缩可以在线性成本下保持保真度。

4. **作用域层次**：将多租户隔离作为一等公民。大多数记忆工具扁平化为单用户作用域，要么丢失组织上下文，要么泄漏用户数据。

5. **检索充分性缺口**：指出现有基准的根本缺陷——只衡量"检索命中"而非"推理所需一切是否出现"，这是一个未被现有评测捕获的关键失败模式。

6. **混合检索经验证据**：五域对照实验量化了向量与关键词检索各自的优势域，以及"向量税"的 60-100 倍索引延迟成本。

## 七、局限性与未来方向

### 论文承认的局限
- 两个基准只衡量对话召回和基于召回内容的推理，**不衡量延迟、token 效率和上下文腐蚀抵抗**
- 跨厂商对比不可比（不同方法学、不同答案模型）
- 参考实现 Maximem Synap 是商业产品，核心机制未公开（压缩验证机制、预取预测机制均为专有）
- 五域检索研究是单操作者、单关键词引擎对单向量存储，无分块，小规模

### 未来方向：决策级与组织级上下文
- 当前生命周期管理对话级和组织级上下文
- 前沿是**决策级上下文**：不仅捕获发生了什么，还捕获组织为什么做出该决策
- 难题：大多数决策是隐式的从未被记录；记录的理由往往是事后辩护而非真实追踪；将决策与结果关联需要因果归因；知道过去的决策何时被取代本身就是问题

## 九、借鉴点评估（关联 Hermes Agent）

### P0 — 可立即执行

**1. 验证压缩门禁（Validated Compaction Gate）**

论文核心论点：无验证的压缩比不压缩更糟糕（18,282→122 token 导致准确率低于无上下文基线）。Hermes 已有 `context-compressor` skill，但缺乏压缩后验证。

建议：在 `context-compressor` 中增加压缩后验证步骤——压缩完成后，用 LLM 检查关键信息是否可从压缩结果恢复，输出验证分数，不达标时自动降级重试。

**2. 混合检索路由（Hybrid Retrieval）**

论文五域实验证明：向量检索在语义鸿沟大的场景完胜（代码 0.91 vs 0.29），关键词检索在精确实体场景完胜（科学 0.81 vs 0.61）。Hermes 已有 `hybrid-search` skill（semantic+keyword+entity 三路）。

建议：为 `knowledge-query` skill 增加**场景感知路由**——检测查询类型自动选择检索策略，而非统一用向量检索。代码/概念查询 → 向量优先，实体/配置查询 → 关键词优先。

**3. 记忆垃圾治理（Junk Rate Audit）**

论文引用的审计案例：某记忆库 32 天存入 10,134 条，仅 38 条可用，垃圾率 99.6%（启动文件重述、cron 噪声、配置转储）。这与 Hermes 的 `memory-consolidation` skill 直接相关。

建议：立即执行一次 Hermes 记忆垃圾审计——扫描 `~/.hermes/memories/` 统计低价值条目比例（重复、过短、配置转储），评估是否需要更新 `memory-consolidation` 的清理规则。

### P1 — 值得规划

**4. 作用域感知检索（Scope-Aware Retrieval）**

论文三级作用域（user→customer→client）与 Hermes 的多 profile 架构对应。Hermes 已有 cross-profile 软防护，但缺乏主动的作用域感知检索。

建议：在 `knowledge-query` 中增加 profile scope 参数，检索时从窄到宽解析（当前 profile → 共享知识 → 全局知识），带严格隔离。

**5. 预取机制（Anticipatory Prefetch）**

论文的预取原语（60%+ 命中率）在 Hermes 中可体现为：`session-boot` 时预加载可能需要的上下文（近期未完成任务+关联记忆），而非被动等待用户请求。

### P2 — 长期方向

**6. 验证压缩的线性成本模型**

论文证明了验证压缩的 N·W·(1+c/p) 线性成本公式，200 轮节省 90% token。Hermes 长会话（如 cron 任务连续执行）可参考此模型设计周期性压缩触发策略（每 p 轮触发一次）。

**7. 决策级上下文**

论文的前沿方向——捕获"为什么做了这个决策"而非仅"发生了什么"。Hermes 的 `error-case-library` skill 部分覆盖了错误决策追踪，但缺乏成功决策的推理过程记录。
