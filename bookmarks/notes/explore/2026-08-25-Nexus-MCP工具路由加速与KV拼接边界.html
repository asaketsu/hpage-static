一、内容整理

1.1 核心问题：MCP Schema 的 Prefill 墙

  • MCP（Model Context Protocol）Agent 每轮对话都要把全部工具的 JSON schema 重新编码一遍，self-attention 对序列长度是 O(N²)，工具注册表涨到几百个时，prefill 成本主导 TTFT（time-to-first-token）
  • 序列长度 N = H + ΣS_k，H 是对话历史，S_k 是第 k 个工具 schema 的 token 长度
  • 直觉优化：把每个 schema 一次性编译成 KV block，推理时直接移植进活跃上下文——但这条路被 RoPE 的位置依赖性死死卡住
  • 论文核心问题重述：重定位的 schema KV block 到底能信多深？修复它要付出什么代价？

1.2 负结果先行：两个物理边界（论文最有价值的部分）

边界一：锚点/离锚保真边界（RoPE 相位漂移）

  • RoPE 按位置角度旋转 Q/K 特征对，key 编译时假设锚点位置 m₀，实际消费在位置 n_past，相位误差 Δθ = (n_past − m₀)·θ，高频维度漂移最快
  • 实测数据（dkl_sweep.json，10 queries/offset）：
  • 锚点处（Δpos=0）：D_KL ≈ 0，top-1 agreement = 1.0，输出完全一致
  • 离锚后：散度先升到 ~10⁻² nats（前 64 token 内），然后平台期——整个 0–2048 偏移范围内稳定在 0.008–0.038 nats，top-1 agreement 始终 = 1.0
  • 退休方案 LegoLink（散射式部分重计算）在 n_past=1024 时 D_KL ≈ 5.7 nats——比连续后缀裸拼接差两个数量级，是"修复反而破坏分布"的反面教材
  • P=256 不是保真悬崖，而是保守的修复起点：漂移已明显脱离锚点底噪、但 top-1 仍安全的区域
  • 为什么 top-1 一致还要修复？top-1 agreement 弱于分布一致性：残差 ~10⁻² nats 在温度/核采样下仍会导致路径分叉，且逐 token 误差在多轮 Agent 轨迹中复利放大。深度自适应重解码把 D_KL 压到精确 0，换来的 never-regress 是在任何解码参数下都成立的可审计保证

边界二：免参考漂移门控失败

  • 自然想法：用便宜的 per-head K-variance 代理预测深拼接何时灾难性漂移
  • 实测（gating_nogo.json）：代理与真实漂移的 Spearman ρ = 0.193，远低于 0.40 目标——代理无法排序高低漂移头，门控会无差别触发
  • per-head 漂移本身存在（max 175–207，mean 91–105），但标量代理抓不住它
  • 结论：有效在线门控需要真参考（= 要避免的全 prefill 成本）或自定义 attention kernel，所以修复机制退回到确定性深度自适应曲线

1.3 架构：检索解耦路由（主杠杆，深度无关）

用户查询
  → nomic-embed-v1.5 (INT8) 嵌入
  → SLB 扫描（INT8 SIMD 点积，top-k）
  → 边际门 τ=0.0136 (P20 校准)
      ├─ 高置信 → 直接定路由
      └─ 低置信(~20%) → MiniLM 级交叉编码器重排
  → 解析出 tool id
  → 压缩 IR 签名（中位数 19 token）上生成参数
  → FSM 掩码 logits（工具名 radix trie）+ GBNF JSON 语法约束
  → 工具调用
  • SLB（Semantic Lookaside Buffer）：工具嵌入（名称+描述，search_document: 前缀）INT8 量化，branchless SIMD 点积扫描（NEON / AVX-512-VNNI / AVX2）。工具名携带主导路由信号
  • 边际门：top-2 分数边际超过校准阈值（对抗样本边际的 P20，τ=0.0136）自动路由，否则升级到交叉编码器——只对最低置信的 ~20% 决策开火
  • 压缩 IR：JSON schema 压缩成带类型提示的函数签名（如 create_repository(name: string, private?: boolean)），中位数 19 token / p99 32 token，主上下文省 ~80% token，参数绑定能力不丢
  • 执行边车（sidecar）：需要新鲜序列验证路由时，从位置 0 分配临时序列，锚点拼接永远在输出精确区。边车带修剪滑动窗口保持多轮共指（"open a pull request there"），笨重工具载荷替换为短语义代理

1.4 系统实现

  • Aeon Tool Block（.atb）：schema 离线编译产物，128 字节头（RoPE 锚点+缩放参数）+ 页对齐（2MB）连续 F16 K/V 张量。运行时校验头的 RoPE 参数，缩放制度不匹配直接拒绝而非静默腐蚀 attention
  • 拼接+缝合：K/V 行写入活跃 KV 游标处，随后失效 ⌈S·R(n_past)/100⌉ 个 token 的后缀并重解码缝合
  • 转置 V 拼接：soft-capped attention（Gemma-2）禁用 FlashAttention，V cache 是 token-innermost 转置布局——实现了 layout-aware 的 strided 拷贝，在 Gemma-2-9B 上保真验证通过
  • 安全边界（fail-closed）：离散 GPU 后端的转置跨设备拷贝是病态路径，splicer 直接拒绝并回退 prefill。云端/token-stream API 同样无法移植物理 cache 地址，回退纯文本 prefill（1.0×，零加速）

1.6 局限性（作者自陈）

  • 单元组：所有数字来自一台主机（M4 Max UMA）+ 一个模型元组（Qwen2.5-14B Q4_K_M）+ 一个 embedder + 一个 llama.cpp build；转置 V 机制额外在 Gemma-2-9B 上验证
  • 小样本：端到端臂 n≤30，区间宽，明确声明是"包络"而非总体估计
  • 深拼接只做了微验证：接入 agent（enable_deep_splice）但未作为多轮生产路径跑通
  • 检索天花板：dense + 交叉编码器召回有工作负载依赖的上限，门控改善低置信决策但不能消除硬混淆

二、查询拓展

2.1 RoPE 相位漂移

RoPE 通过旋转 Q/K 特征对注入相对位置信息，注意力分数依赖 query/key 的相对旋转。绝对相位"错位"的 key 会被后续所有 query 斜读。低频维度（长波长）容忍偏移，高频维度（θ 大）漂移最快——这就是为什么拼接块只在编译锚点的邻域内忠实。YaRN/NTK 等频率插值方法共享同一套 RoPE 机器但目标不同（扩窗 vs 块重定位）

2.2 KV Cache 复用的两条路线

  • 就地复用（工业主流）：PagedAttention、prefix-shared KV（vLLM/SGLang 系）让块留在计算时的位置上复用，永不搬家——绕开 RoPE 问题
  • 重定位移植（Nexus 探索的）：把块搬到新位置，必须付修复代价。Nexus 的贡献是给出了"能信多深"的定量边界（P=256 阈值 + 平台期散度曲线）
  • RedKnot 推进到 attention head 粒度的就地复用；Nexus 反其道做粗粒度 per-tool 块搬迁

2.3 MCP 与 schema 膨胀

MCP 已成 Agent 工具调用事实标准，代价是每个工具带一份冗长 JSON schema。工具一多（论文测到 250 个），schema 占据 prompt 主体。RAG-MCP 代表"检索前置"路线：prefill 前只取相关 schema。Nexus 在此之上加了两层：系统级 KV 移植 + 零样本校准边际门（无需训练对齐）

2.4 SLB 命名溯源

Lookaside Buffer 是 CPU 术语（TLB 的兄弟），指旁路快速查找缓存。Nexus 的 SLB = 语义版：INT8 工具嵌入向量库 + SIMD 扫描，微秒级。类比：工具注册表就是"地址空间"，查询嵌入就是"虚拟地址"，SLB 把路由从 LLM 主干路径上整个摘出来

三、归纳总结

3.1 核心框架：双杠杆分层

┌─────────────────────────────────────────────┐
│ 杠杆一（主）：检索解耦路由 —— 深度无关       │
│   嵌入检索(SLB) + 边际门 + 压缩IR参数生成    │
│   250工具 89% 精度 | 1.66× 首参数加速        │
│   17.6µs 路由开销，不随深度/工具数膨胀       │
├─────────────────────────────────────────────┤
│ 杠杆二（辅）：KV 拼接 —— 有物理边界          │
│   n_past≤256 锚点拼接：输出精确 (D_KL≈0)     │
│   n_past>256：深度自适应修复 R(n_past)       │
│   → 按梯度升级到全量重 prefill               │
│   never-regress：保真不回归（延迟可短暂<1）  │
├─────────────────────────────────────────────┤
│ 两个负结果钉死设计空间：                     │
│   ① 离锚 RoPE 漂移（散布重计算=破坏）       │
│   ② 免参考漂移门控失败（ρ=0.193）           │
└─────────────────────────────────────────────┘

3.2 never-regress 的精确定义

  • 保证的是输出保真：top-1 agreement 保持 + D_KL ≈ 0，在任何解码参数下可审计
  • 不保证延迟：0.98× 的短暂倒挂来自修复后缀的重解码开销
  • 这是"用一点 TTFT 买硬保证"的设计哲学，拒绝接受"小但非零"的残差（其下游影响是工作负载依赖的）

3.3 创新点清单

  1. 把工具 schema 加速从"无条件 KV 移植"重构为"检索解耦路由 + 深度自适应修复"的组合
  2. 用输出分布散度（D_KL）刻画 RoPE 拼接保真边界，给出可复现的阈值（P=256）与平台期现象
  3. 两个高价值负结果：散射式重计算反而破坏分布（5.7 nats）；K-variance 免参考门控与真实漂移零相关（ρ=0.193）
  4. fail-closed 工程哲学：缩放制度不匹配拒绝拼接、离散 GPU 拒绝转置 V、云端 API 回退纯 prefill——宁可零加速不冒腐蚀风险
  5. 全链路微秒级路由：INT8 SIMD + 校准边际门，250 工具 17.6µs

四、趋势判断

趋势1：工具检索解耦将成为 Agent 网关标配

依据：拼接全部 schema 的 oracle 在 N≥50 直接溢出上下文，而 SLB 路由在 N=250 保持 89% 且开销微秒级。工具生态只会膨胀不会收缩，路由前置是唯一随规模平展的方案。Hermes 这类多工具 Agent 系统迟早要面对 50+ 工具的注册表

趋势2：KV 块重定位是学术富矿但工业主线仍是就地复用

依据：论文自己承认深拼接"接入但未作为多轮生产路径跑通"，且全加速仅限 UMA 本地场景，云端 token-stream API 无物理 cache 可移植。PagedAttention/前缀共享的工业地位短期不会动摇。Nexus 的持久贡献是边界刻画（负结果），不是可部署加速器

趋势3：负结果论文的价值正在被系统性低估

依据：本文把两个失败实验（LegoLink 散射重计算、K-variance 门控）放在第四章先行陈述，并全部锚定到 committed artifact（json 文件）。这种"负结果+可复现工件"的写法比正结果更节省整个领域的时间。单作者+单机测量+诚实置信区间的风格也值得注意

趋势4：参数生成与路由应分而治之

依据：Nexus 用 19 token 压缩 IR 生成参数（100% 指定参数正确）而非在拼接 KV 上生成——把"选哪个工具"（语义问题）和"填什么参数"（语法+绑定问题）拆到不同表示层。FSM+GBNF 约束解码保证 JSON 有效性 100%，这条组合拳对任何工具调用 Agent 通用

五、关联分析

5.1 与 MemDecay 笔记的关联

MemDecay（2026-07-15 精读）同属 KV Cache 管理谱系：MemDecay 管的是"驱逐什么"（区域感知衰减），Nexus 管的是"移植什么、信多深"。两者共同确认：KV cache 不是同质块，位置/区域/用途的异质性决定处理策略。MemDecay 的 system prompt 半衰期 10× 于 scratchpad 与 Nexus 的 P=256 锚点边界互为印证——不同区域的 KV 有不同的物理/语义容差

5.2 与 Kara / LongStraw 笔记的关联

  • Kara（2026-07-04 精读）：滑动窗口压缩 KV，同样面对"压缩后保真边界"问题。Kara 用窗口截断，Nexus 用相位漂移定量刻画——两者都证明 KV 操作存在不可逾越的保真红线
  • LongStraw（2026-07-17 精读）：长上下文 Agent 的 KV 显存治理。Nexus 的 ~80% 主上下文 token 节省与 LongStraw 的显存增量思路互补：一个省 prefill 计算，一个省存储

5.3 与 Hermes Agent 的直接关联

  • Hermes 的工具体系（terminal/search/patch + MCP deferred tools）正面临论文描述的 schema 膨胀：本会话 deferred catalog 已有 20+ 工具，每次会话启动都要注入全部工具 schema
  • Hermes 的工具选择目前靠 LLM 内部决策（等价于论文中的 concatenate-all oracle），未做检索前置——工具数再涨就会撞上下文墙
  • SPyCE（2026-07-16 精读）的技能分层检索与 Nexus 的 SLB 路由是同构问题在不同层的解：前者检索"怎么做"，后者检索"用什么做"

5.4 与 Jetson 边缘部署的关联

Nexus 的 UMA（统一内存）架构与 Jetson Orin 的统一内存模型完全同构——CPU/GPU 共享物理内存，正是"直接写物理 cache 地址"所需的前提。论文在 M4 Max 上的实测对 Jetson 有直接参考价值：14B Q4_K_M 模型的 KV 拼接在统一内存上可行，离散 GPU 上 fail-closed

六、金句摘录

「We present the negative results first because they motivate the architecture: they fix the shape of the repair curve and force routing to be depth-independent rather than to depend on a deep splice.」— 负结果先行的论证结构，架构是被物理边界逼出来的

「Never-regress is a guarantee on output fidelity—not on latency, which can dip to 0.98× before converging to parity.」— 精确区分"保证什么"与"不保证什么"，罕见的诚实

「Driving the divergence to exactly 0 makes the spliced output bit-identical to a full prefill—a guarantee that is auditable and holds under any decoding parameters.」— 可审计性作为一等设计目标

「The qualitative boundaries ... are properties of RoPE and hold model-agnostically, whereas the quantitative envelope ... is calibrated to one model tuple and must be re-measured elsewhere.」— 单机测量的诚实边界声明

七、行动启示（借鉴点评估）

P0：工具注册表的检索解耦路由（可直接移植）

  • 现状：Hermes 工具 schema 全量注入 system prompt，每轮会话启动付全额 prefill
  • 借鉴：为工具注册表建嵌入索引（工具名+描述，nomic-embed INT8），查询时先检索 top-k 工具再注入 schema——只注入被选中的 1-3 个工具的完整 schema
  • 工作量：中（约 1-2 天）。嵌入可离线预计算，检索逻辑 ~100 行 Python
  • 收益：工具数从 20 涨到 200 时 system prompt 不膨胀；直接对齐论文 1.66× 首参数加速 + 80% token 节省的量级

P1：压缩 IR 签名用于参数生成（可直接移植）

  • 借鉴：工具 JSON schema 压缩成 name: string, private?: boolean 式函数签名（中位 19 token），参数生成用 IR 而非全 schema
  • 适用：Hermes 的 MCP 工具（deferred catalog）调用前先给 IR，需要全 schema 的复杂工具再展开
  • 工作量：小（半天）。schema→IR 的压缩器 ~50 行

P1：工具名 radix trie + GBNF 约束解码（需工程改造）

  • 借鉴：FSM 掩码 logits 限定工具名集合，GBNF 语法约束 JSON 参数——100% JSON 有效性、零占位符泄漏
  • 障碍：Hermes 走 API 推理（GLM/Zhipu），无 logits 级访问权限；本地 Ollama 路径（nexa-local-inference）可用
  • 工作量：中。仅对本地推理路径有意义

P2：RoPE 拼接保真边界的量化认知（知识储备）

  • 借鉴：任何"KV 块搬家"优化（前缀缓存复用、跨会话 KV 移植）都要过 RoPE 相位漂移这道关。锚点内精确、离锚平台期 10⁻² nats、散布重计算是毒药——这三条定性结论 model-agnostic
  • 应用：Jetson 本地推理栈（llama.cpp 路径）做多会话 KV 复用时的设计约束

P3：fail-closed 哲学（已有部分实现）

  • 借鉴：不确定就拒绝并降级，而非冒险腐蚀——Hermes 的 model-fallback-chain、search-fallback-chain 已是此哲学，本文提供 KV 层的又一实例
  • 增量价值：认知强化，无新工程

八、拓展应用推荐

  • 多 Agent 系统的工具分片：agent-team（Kanban/编排）场景下按角色预分配工具子集，本质是人工版 SLB 路由——可结合 Nexus 的嵌入检索做自动分片

  • Jetson 本地 Agent 栈：nexa-local-inference + Ollama 路径实现 per-tool KV 块编译缓存，Jetson UMA 架构是论文方案的原生适配土壤；先做锚点内（n_past≤256）拼接即可拿 1.63× 加速
  • Skill 检索的边际门借鉴：skill-ab-testing / skill-review 的候选筛选可引入 top-2 边际门思想——高置信自动通过，低置信 20% 升级到更贵的评审（等价于交叉编码器层）

  • 诚实边界声明模板：「qualitative boundaries generalize / quantitative envelope is tuple-specific」的二分声明，直接可套用到单机测试报告
