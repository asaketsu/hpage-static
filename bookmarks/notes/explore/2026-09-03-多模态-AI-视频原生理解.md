## 摘要

视频理解正经历从"离线整段→一次性问答"到"实时流式→边看边答边沉默"的范式跃迁。核心矛盾在于：decoder-only 架构把视觉 token 塞进自回归序列，导致长视频 prefill 高延迟 + 解码步步拖累；交叉注意力架构（MOSS-VL/MOSS-Video-Preview）将视觉特征走旁路通道，感知与生成物理隔离，在 256 帧场景实现 5× TTFT 加速和 2.7× 解码吞吐提升。同时，绝对时间戳注入 + 3D 统一位置编码（XRoPE / Interleaved-MRoPE）成为 2026 年时序建模的新共识，Qwen3-VL 用 256K 上下文实现 2 小时视频 99.5% needle-in-haystack 精度。Sora 关停标志纯视频生成的"炫技时代"结束，视频理解（而非生成）成为厂商竞争焦点。

## 一、三范式精确定义：离线 vs 流式 vs 实时（关键发现 1）

> 来源：MOSS-Video-Preview 论文（arXiv:2606.07639，复旦/上海创智学院，2026-06）

文献中"streaming"用法混乱，MOSS 团队首次给出精确边界——**核心判据只有一个：模型能否在生成回复期间继续感知新帧**。

- **离线（Offline）**：整段视频输入完毕后才输出唯一答案。视频结束时模型才回答。
- **流式（Streaming，已有系统）**：帧按时序到达，模型可在播放中途响应；**但生成回复期间停止摄取新帧**。当前主流 VLM（Qwen2.5-VL、InternVL 等）实际都是此模式。修正被延迟至少一个回复长度。
- **实时（Real-time，本文）**：模型**在回复生成过程中持续感知新帧**，可在证据出现的瞬间修正甚至打断当前回复。无话可说时主动选择 `<|silence|>`。

> ⚠️ 关键洞察：差异不在于"能否修正"（流式也能在后续轮修正），而在于"修正是否及时"。流式使感知与生成串行互斥；实时让两者并发。

形式化表示：交互序列 x₁:N 中，每个 xᵢ 来自文本词表、视频帧占位符 `` 或沉默符号 `<|silence|>`。三个特征映射范式区别：

1. 默认轮次用户输入为空，助手已开始接收帧并用 `<|silence|>` 回答 → 捕捉"无提问时持续感知"
2. 视频帧**交错在助手回复内部** → 感知与生成并发于同一序列（实时与流式的本质区别）
3. `<|silence|>` 显式编码"此刻无需回复" → 防止静态场景被反复描述

```
范式对比速查：
┌──────────────┬─────────┬───────────┬──────────┐
│ 属性          │ 离线     │ 流式       │ 实时      │
├──────────────┼─────────┼───────────┼──────────┤
│ 帧按时序到达  │ ✘       │ ✔         │ ✔        │
│ 回复期间持续感知│ —       │ ✘         │ ✔        │
│ 修正及时性    │ —       │ 延迟下一轮  │ 即时      │
│ 主动沉默      │ ✘       │ 部分       │ ✔        │
└──────────────┴─────────┴───────────┴──────────┘
```

## 二、交叉注意力 vs Decoder-only：架构选型的结构必然性（关键发现 2）

### 2.1 为何 cross-attention 天然适配实时

Decoder-only（Qwen3-VL、GPT-5、Claude 4.5 等）把视觉 token 塞进自回归序列 → 每个新帧扩展生成中的序列 → 感知和生成共享一个上下文，必须显式编排。

Cross-attention（Flamingo 范式，MOSS 继承）把视觉特征作为**旁路 K/V** → 帧读取和 token 生成物理隔离在两条通道 → 隔离是默认状态。

### 2.2 MOSS-VL 架构实例（Llama-3.2-11B-Vision 改造）

```
视觉通道: frame → ViT(patch14, 560px, 5 inter-layer+1 global=6×1280=7680维)
         → 2D pooling(压缩 1/stride²) → linear projector(7680→4096)
         → cross-attention K/V（仅 8/40 层: [3,8,13,18,23,28,33,38]）

语言通道: Llama-3.2-11B backbone (32 self-attn + 8 gated cross-attn)
         → 每帧占 1 个 <img> placeholder → 帧的位置索引 = placeholder 索引
         → 同一帧所有视觉 token 共享同一位置索引 → 时序信号纯化为"第几帧"

注入公式: h ← h + tanh(g_attn)·CrossAttn(h, V)   # tanh 门控初始≈0→不扰动基座 LLM
         h ← h + tanh(g_ffn)·FFN(h)
```

### 2.3 实测性能（单卡 H200, 256帧/视频）

| 指标 | MOSS-VL (11B, cross-attn) | Qwen2.5-VL-7B (decoder-only) | 倍率 |
|------|---------------------------|------------------------------|------|
| TTFT (首 token 时间) | ~2s | ~10s | **5× 加速** |
| 解码吞吐 (tok/s) | ~2.7× baseline | baseline | **2.7×** |

> 架构优势来源不是工程 trick，而是结构本身：视觉 K/V 在 prefill 时编码一次，解码步复用 → 不像 decoder-only 每步拖一大池视觉 token 做自注意力。

### 2.4 四阶段训练流程

| 阶段 | 目标 | 数据量 | 可训练模块 |
|------|------|--------|-----------|
| Stage 1 | 视觉-文本对齐 | 15M 图文对 | ViT + projector + cross-attn（冻结 backbone）|
| Stage 1.5 | 视频时序获取 | 1.8M (1369K视频) | 全模型 |
| Offline SFT | 通用指令跟随 | 8M | 全模型 |
| Real-Time SFT | 看答+沉默决策 | 836K 合成 | 全模型（lr 降至 5e-6）|

> 设计逻辑：先用大量通用数据建立稳健离线模型，再用小规模实时合成数据做"专业化注入"。实时 SFT 不是从头训练，是在离线 checkpoint 上叠加行为。

## 三、时序建模的 2026 新共识：绝对时间戳 + 3D 统一位置编码（关键发现 3）

### 3.1 MOSS-VL：绝对时间戳 + XRoPE

- **绝对时间戳**：每帧注入精确时间锚点 → 支持可变帧率适配、精准动作定位、运动动力学推理（通过 dt 估算速度/加速度）
- **XRoPE (Cross-attention Rotary Position Embedding)**：文本 token 和视觉特征映射到统一 3D 坐标空间（时间×高度×宽度）

### 3.2 Qwen3-VL：Interleaved-MRoPE + Text-Timestamp 对齐

> 来源：Qwen3-VL 技术报告（arXiv:2511.21631，阿里云，2025-11）

三大架构升级：

1. **Interleaved-MRoPE**：原 MRoPE 按 t→h→w 顺序分块 → 时序信息全挤在高频维度。新方案交错分布 t/h/w → 全频率覆盖 → 长视频理解显著提升且不牺牲图像能力
2. **DeepStack**：融合多层 ViT 特征 → 细粒度细节增强 → 图文对齐更锐利
3. **Text-Timestamp 对齐**：从 T-RoPE 升级为"时间戳-视频帧"交错输入 → 帧级时间信息与视觉内容精确对齐 → 原生支持秒和 HMS 两种时间输出格式

实测：256K 上下文 30 分钟视频 needle-in-haystack 100% 精度，1M token 扩展到 2 小时视频 99.5% 精度。

### 3.3 位置编码演进对比

```
演进路线：
T-RoPE (Qwen2-VL)     → 时间/高度/宽度独立旋转，时序在高频维度堆积
MRoPE (Qwen2.5-VL)    → 分块分配，仍有时序频率不均
Interleaved-MRoPE (Qwen3-VL) → 交错分布，全频率覆盖，长视频最优
XRoPE (MOSS-VL)       → 跨注意力统一 3D 空间，文本和视觉共享坐标轴
绝对时间戳 (MOSS-VL)  → 注入每帧，可变帧率适配 + 物理运动推理
```

## 五、对现有 Skill/笔记的改进建议

- **P0**：`embodied-ai-control` skill 已含 FLOWER VLA 中间融合架构，应补充 MOSS-VL 交叉注意力范式作为"感知-生成分离"的架构参考。VLA 的 vision encoder→cross-attn→LLM backbone 路径与 MOSS 完全同构。
- **P1**：`llm-inference-optimization` skill 可补充交叉注意力的推理效率优势（K/V 编码一次复用 vs decoder-only 每步拖视觉 token 池）作为长视频场景的架构选型依据。
- **P2**：已有的 [[2026-08-29-多模态-AI-Visual-Perceiver]] 笔记中 Perceiver Resampler 与本笔记的 MOSS cross-attn 高度相关，应建立双向关联。

## 六、Actionable Insights

1. **实时视频理解是下一个差异化赛道**：智能眼镜、具身机器人、直播助手、共看 Agent 都需要"边看边答边沉默"。当前所有开源 VLM 仍是流式模式，实时范式有先发优势窗口。
2. **架构选型铁律**：长视频（256帧+）场景优先考虑 cross-attention 架构；短视频/单图场景 decoder-only 性价比更高。MOSS-VL 已开源（GitHub: OpenMOSS/MOSS-VL），LlamaFactory 支持 LoRA 微调。
3. **绝对时间戳是时序建模的必要组件**：相对位置编码无法处理可变帧率和物理运动推理。任何自建视频 VLM 都应注入显式时间信息。
4. **实时 SFT 数据合成是关键瓶颈**：MOSS 的贡献不在 SOTA 性能，而在首次提出"指令不变、最佳回复随流演进、间隙填充沉默"的数据合成管线。没有这类数据，架构再好也无法学会何时修正何时沉默。

## 七、关键风险与盲点

- **评估缺失（官方承认）**：MOSS 论文明确说未提出实时理解的量化基准。"仅看准确率可被'拖延回答'虚高"——一个等到事件结束后信息明确才回答的模型可人为拿高分却违背实时初衷。决策级延迟（事件结束→模型决定回复的等待时间）目前无人测量。（社区验证级别：论文自述，待后续工作）
- **性能差距未消除**：MOSS-VL 在通用基准上仍落后 Qwen2.5-VL-7B，作者归因于数据和规模而非架构。交叉注意力是否在 scale up 后仍保持优势尚未验证。
- **跨浏览器/设备实时推理的工程门槛**：实时范式需要流式帧注入 + 并发感知-生成，对推理引擎有定制要求（SGLang 已支持 MOSS-VL，vLLM 支持待确认）。
