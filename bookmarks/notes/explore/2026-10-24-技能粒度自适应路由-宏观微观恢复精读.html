一、内容整理

1.1 核心问题：粒度是运行时控制变量，不是库设计问题

以往 Agent 技能研究（SkillRouter、Graph-of-Skills、SkillWeaver、轨迹挖掘）都聚焦执行前的检索、组装、合成——"该暴露哪个技能"。本文指出编码 Agent 在执行中还有一个被忽视的控制问题：同一个任务可以用三种粒度完成——

  • 微观（μ）：原始工具调用（文件检查、搜索、编辑、语法检查、测试）
  • 宏观（M）：宏技能（把"移动模块+重写import+验证"打包成一个时序扩展动作）
  • 混合（H）：宏技能起步，观察到宏失败后单向降级回微观恢复

关键论据：SWE-Skills-Bench 已实证注入技能的收益不均、甚至因抽象层级与任务不匹配而降低软件工程性能。检索解决不了粒度错配——错配发生在运行时，就得在运行时控制。

1.2 形式化：可行动作包络

论文把粒度定义为"对可行动作集的约束"：G = {μ, M, H}，给定历史 h_t，混合模式的动作包络为——

A(g, h_t) =
  S_μ                若 g = μ（只许微观）
  S_M                若 g = M（只许宏观）
  S_M                若 g = H 且 无可恢复宏失败 F(h_t)
  S_μ                若 g = H 且 观察到 F(h_t)（降级）

这是与"技能检索"的核心形式区分：控制器改变的是下游 Agent 可用的动作抽象层级，而不是往上下文里塞哪段技能文本。控制器输出决策元组 d = (mode, strategy, enable_recovery, reason)——第四个字段 reason 专为审计留痕。

1.3 三条设计不变量（可审计性的来源）

  1. 执行前路由只用执行前证据——路由器可看任务元数据和初始仓库特征，禁止偷看本次运行的验证结果（防止验证结果泄漏进路由形成自我实现）
  2. 恢复是事件驱动的——只有观察到宏失败、验证失败、故障注入或恢复路由器显式决策，才允许 M→μ 转移
  3. 成功由验证器定义——确定性验证器在最终工作区通过才算成功，模型自己声称"完成"不算数

1.4 技术组件

  • 复杂度特征（10 维，全部执行前可提取）：源码路径数、Python/非 Python 文件数、实体串数、AST 节点数、AST 最大深度、import 数、跨文件依赖数、文本任务旗标、重构任务旗标——刻意排除执行衍生信息，防路由器泄漏
  • 学习型路由器：不是神经网络，是最大深度 4 的决策树，离线用历史执行日志（成功+token成本）训练，序列化成 JSON，运行时确定性遍历——零在线推理、零黑盒、全可审计
  • 宏技能契约（七元组）：m = (name, args, pre, effect, V_m, F_m, fallback)——前置条件、允许的副作用、内部验证例程、可观察失败类别集合、微观点位回退路径。没有失败类别暴露，恢复转移就无法决策
  • 宏技能准入：必须经过回放 + 确定性验证 + 副作用文档化 + 回退行为声明，才能进可执行库（针对轨迹挖掘技能"脆"的问题）
  • FSM 恢复执行器：宏失败是状态转移而非终局；每步记录转移数、失败数、恢复触发点、首次失败位置
  • 失败分类学（五类）：前置条件不匹配 / 部分副作用（改了一半状态才失败）/ 验证失败 / 故障注入 / 其他
  • 原型仅 3 个手写宏：inspect_python_module（模块摘要）、replace_and_verify（替换+语法检查+可选测试）、move_module_and_update_imports（移动+import重写+验证）——刻意做小，保证前置条件/副作用/验证行为全部可审计

1.5 评测协议 GranBench-Code

四族任务各 20 个：

  • Simple：单文件 bug、文档示例、配置修复
  • Medium：多文件中等依赖修改
  • Refactor：模块移动、符号重命名、import 重写、API 迁移
  • Recovery：宏失败、部分执行污染、降级恢复（受控故障注入）

六个对照变体共享同一 LLM/工具/验证器，只暴露不同动作空间：

  • A-Micro / B-Macro：固定粒度，无恢复
  • C-Heuristic：启发式路由；D-Learned-ModeOnly：学习型模式路由
  • E-FSM-Downgrade：启发式路由+无条件降级；F-Learned-Full：学习型模式路由+学习型恢复路由

主指标：验证成功数；效率：CostPerSuccess（含失败在内的总 token / 总成功数）；过程指标：轨迹长度、宏采纳率、失败恢复率、路由对齐、转移正确率。

1.6 关键实验数据

固定粒度 vs 路由（12 个混合任务）——

变体           成功率   步数   token    宏采纳率  G-score
A-Micro        1.000   6.00   7217.75   0.000   0.1667
B-Macro        0.583   2.71   3609.00   0.916   0.4305
C-Heuristic    0.750   3.22   4097.67   0.833   0.4103

微观完美成功但最贵；宏观省一半 token 但脆（58.3% 成功）；启发式路由只是折中，仍因结构特征误分类损失 25% 任务。

故障时机决定恢复价值（7 任务，注入宏失败）——

故障时机   变体                 成功率   token
Before     C-NoRecovery          0.000    ——
Before     E-FSM-Downgrade       1.000   11293.43
After      C-NoRecovery          1.000    2440.14
After      E-FSM-Downgrade       1.000    7566.71

最重要的单点发现：恢复的价值取决于失败时机。宏技能在早期失败（Before）→ 无恢复=全灭，降级=满血复活；宏技能在晚期失败（After，改完工作区才抛错）→ 验证已能通过，无条件降级反而白烧 3 倍 token。

学习型路由碾压启发式（12 任务）——

变体                  成功率   token     启发式对齐  经验标签对齐
C-Heuristic-ModeOnly   0.750   4172.89    1.000       0.667
D-Learned-ModeOnly     1.000   5518.33    0.667       1.000

经验结果标签比手写规则强：复杂同步任务的结构特征会误导启发式，学习路由正确把它派给微观执行。

端到端：选择性恢复是最终答案（7 任务）——

故障时机   变体              成功率   token     G-score   降级率
Before     E-FSM-Downgrade    1.000   11293.43   0.0845   1.000
Before     F-Learned-Full     1.000    9763.57   0.1061   0.857
After      E-FSM-Downgrade    1.000    7566.71   0.2142   1.000
After      F-Learned-Full     1.000    3694.43   0.5720   0.143

学习型模式路由 + 学习型恢复路由（F）：早期故障下保持满恢复且更省；晚期故障下降级率从 1.000 压到 0.143、token 省一半（3694 vs 7566），G-score 提升 2.7 倍。结论：模式选择避免"用不该用的宏"，选择性恢复避免"不该降级时降级"——两者互补。

二、查询拓展

2.1 时间抽象（Options / MAXQ / HTN）

宏技能=时序扩展动作，直接对应经典分层强化学习的 options（Sutton 等）、MAXQ 值函数分解（Dietterich 2000）、HTN 规划（Erol 1994）。本文的差异化：不学端到端分层策略，而是用可检查的控制器约束可行动作集——把"学一个分层策略"降维成"学一个浅层路由器+一个确定性 FSM"。

2.2 执行监控与修复（Execution Monitoring）

M→μ 降级机制血统上属于经典规划的执行监控与机器人学的故障恢复（"plan repair"），以及编辑失败后的自动程序修复。新意在于把它形式化为显式执行转移（有日志、有计数、有正确率指标），而不是非正式的"重试一下"或"重新规划"。

2.3 SWE-Skills-Bench 与技能注入归因

引用证据链：技能注入收益不均且依赖抽象层级与上下文匹配（SWE-Skills-Bench）；函数调用技能的收益必须区分"接口对齐"与"过程迁移"（Chen 2026）。本文是这条批判线的 constructive 回应——与其争论技能该不该注入，不如控制注入后的执行粒度。

2.4 决策树路由器的工程含义

深度 4 的 CART + JSON 序列化 + 确定性遍历 = 路由决策的推理成本约等于查表。这实际上是"用可审计的浅层学习替代 LLM 自路由"的立场宣言——路由不需要智能，需要的是经验分布的压缩。

三、归纳总结

3.1 框架总图

任务 τ ──> 特征提取 φ(τ)（10维结构特征，无执行信息）
              │
              ▼
      粒度控制器 ρ（决策树depth4/JSON）──> d=(mode, strategy, recovery, reason)
              │
              ▼
   ┌──────────┴──────────┐
   μ 微观            M 宏观 ──失败──> F(h_t)触发
   原始工具            宏技能契约      │
                                    ▼ (recovery开启)
                              FSM降级 ──> μ 微观恢复
                                    │
                                    ▼
                        确定性验证器 V（成功判据唯一）
                                    │
                        执行日志 ──> 离线训练路由器/挖掘新宏

3.2 核心论点链

  • 论点1：粒度错配是运行时问题 → 检索式技能系统结构性解决不了
  • 论点2：固定粒度必输 → 微观贵而稳、宏观省而脆，G-score 差 2.6 倍
  • 论点3：无条件恢复也不行 → 晚期失败时降级是纯浪费（3×token）
  • 论点4：出路=学习型模式路由+选择性恢复路由 → 经验标签对齐 1.000，晚期故障 token 减半
  • 论点5：宏技能必须带失败契约 → F_m（失败类别）和 fallback 是恢复可行的前提条件

3.3 与既有技能研究的关系定位

  • SkillRouter/Graph-of-Skills：管"选哪个"（执行前）→ 本文管"用多粗的执行"（运行时）
  • 轨迹挖掘（Voyager 系）：管"技能从哪来" → 本文加准入门禁（回放+验证+副作用文档）
  • 分层 Agent（HiMAC 等）：规划层自适应 → 本文动作层自适应，控制器可检查

四、趋势判断

趋势1：技能系统从"检索问题"转向"控制问题"

依据：SWE-Skills-Bench 实证技能注入可负收益 + 本文证明运行时粒度控制可挽回。技能库的价值公式正在从"存了多少"变成"可控可验证可恢复多少"。

趀势2：浅层可审计路由器将挤压 LLM 自路由的常规场景

依据：深度 4 决策树用经验标签达到 100% 对齐，超过启发式；推理成本≈查表。对高频、模式化的任务分发（如 cron 场景），LLM 路由是奢侈品。

趋势3：失败时机会成为一等公民特征

依据：Before/After 故障下最优策略完全相反。任何恢复机制不区分"死在半路"和"死在终点后"，就会在 50% 的场景里烧冤枉钱。这一洞见会外溢到所有 Agent 重试逻辑设计。

趋势4：技能契约将从"说明书"进化为"机器可读接口"

依据：七元组契约中 F_m（失败类别集）和 fallback 字段是恢复转移的决策输入——没有它们 FSM 就瞎了。SKILL.md 式自然语言技能文档会被迫补充结构化失败语义。

五、关联分析

5.1 与 ViSkill 技能策略协同进化（2026-10-11 笔记）的关联

ViSkill 解决"技能与策略怎么共同进化"，本文解决"进化出来的技能在运行时怎么用得稳"。两者拼起来是完整链条：ViSkill 的蒸馏选择管入口质量，本文的准入门禁+失败契约管运行时行为。互补点：ViSkill 缺失败后怎么办，本文缺技能怎么被创造。

5.2 与 UHP 统一Harness协议-HarnessRouter（2026-10-18 笔记）的关联

HarnessRouter 是跨运行时的粗粒度路由（选哪个 harness），本文是运行时内的细粒度路由（选微观/宏观动作）。层级关系：UHP 路由器在上层，粒度控制器可以视为 harness 内部的二级路由器——两级路由共享"可审计、确定性"的设计哲学。

5.3 与 MUSE-Autoskill 技能全生命周期（2026-10-01 笔记）的关联

MUSE 覆盖创建→评估→退役，本文的宏技能准入（回放+确定性验证+副作用文档+回退声明）正是 MUSE 评估环节缺失的定量门禁。且本文提供了 MUSE 没有的成本语言：CostPerSuccess 可直接作为技能退役判据。

5.4 与 Hermes 自身 daily-paper-reading skill 的镜像关系

本 skill 自身的降级链（Tavily→DDG→curl 列表页；extract_arxiv.py 子命令→本地缓存正则）就是朴素版的"宏观技能+微观恢复"——本次执行恰好实证：section 子命令 SSL 失败（宏技能失败）后，降级到本地正则提取（微观恢复）完成全部章节抽取。Hermes 已在无形式化框架下手动实现本文机制的雏形，缺的是失败分类与选择性恢复判断。

5.5 与 Agent-Skill编写与评测方法论（2026-10-19 笔记）的关联

该笔记强调技能的可评测性，本文给了最锐利的评测协议：验证器定义成功 + 过程指标（宏采纳率/恢复率/转移正确率）+ G-score 效率合成。可视为评测方法论的量化补全。

六、金句摘录

「Skill libraries should be treated not only as retrievable resources, but also as controllable, verifiable, and recoverable execution abstractions.」

「Recovery is an explicit execution transition rather than an informal retry.」—— 把"重试"从事后遮羞布升格为一等公民状态机转移。

「The FSM downgrade recovers early failures perfectly but wastes tokens on late failures.」—— 恢复策略必须感知失败时机。

七、行动启示

  • 启示1（失败分类）：Hermes 技能执行日志补五类失败标注（前置不匹配/部分副作用/验证失败/超时/预算耗尽），error-case-library 目前只有事后根因，无运行时分类
  • 启示2（选择性恢复）：重试前先跑廉价验证器判断"工作是否已完成"——本文数据：这一步可省 51% token（3694 vs 7566）
  • 启示3（路由降级）：高频模式化分发（cron 任务→skill 匹配）可用浅层决策树替代 LLM 判断，训练数据就在 session 历史的成功/成本里
  • 启示4（技能契约）：SKILL.md frontmatter 增加 failure_classes 与 fallback 字段，让恢复决策有结构化输入

八、拓展应用推荐

  • 场景A（Hermes skill-health-tier 巡检）：引入 CostPerSuccess 作为技能健康度定量判据——纯调用次数统计无法区分"贵而稳"和"便宜但常败"
  • 场景B（量化交易执行层）：订单失败恢复策略直接套用时机分类——早期拒单（重发/换通道=宏观恢复）vs 晚期部分成交（只补差额=微观修复），无条件全量重发对应 E-FSM 的 token 浪费
  • 场景C（Jetson 边缘部署）：决策树 JSON 路由器零 LLM 调用、微秒级遍历，适合边缘设备的技能分发前置层
  • 场景D（多 Agent 委派）：delegate_task 前用粒度控制器判断"整任务委派（宏）vs 拆步自做（微）"，避免委派开销大于任务本身
  • 场景E（RL 训练管线）：AutoDL 发射脚本已是宏技能；失败时机的 Before/After 区分可用于决定"重启整个训练（宏恢复）vs 只修参数续跑（微观恢复）"

九、指南分析

  • 方法论价值1（控制变量分离）：论文把"选什么技能"与"用什么粒度执行"切成两个正交问题分别形式化——这种"把复合决策正交分解"的写法值得在系统设计类论文中复用
  • 方法论价值2（不变量先行）：三条设计不变量（证据分离/事件驱动/验证器定义成功）在系统描述前立好，使后续每个组件都可对照检查——比"先描述系统再补约束"的写法可审计性强得多
  • 方法论价值3（故障注入作为一等评测手段）：Recovery 族任务显式注入受控故障并区分时机——评测不止测"能不能成"，还测"怎么失败的、失败后怎么办"
  • 反例警示：实验规模偏小（12+7 任务、3 个手写宏、单向降级），结论方向可信但数字外推需谨慎；作者自己也把完整研究标注为"pilot study"并预留了 unconstrained/LLM-router 基线
  • 判据可复用：G-score = 成功率/(平均步数×归一化token) 把效率合成单一可比数字，适合任何"多目标权衡"的 Agent 评测场景直接抄
