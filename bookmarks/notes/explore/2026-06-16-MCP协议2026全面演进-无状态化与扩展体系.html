摘要

Model Context Protocol（MCP）自 2024 年 11 月 Anthropic 开源以来，18 个月内从开发工具进化为 AI 连接外部世界的事实标准。2025 年 12 月 Anthropic 将 MCP 捐赠给 Linux 基金会下的 Agentic AI Foundation，实现厂商中立治理。Python/TypeScript SDK 月下载量达 9700 万次。2026-07-28 版本候选（RC）引入了协议层无状态化重构——移除 session 概念、移除握手流程、引入显式 handle 模式——使远程 MCP 服务器可在普通轮询负载均衡器后运行。同时，扩展系统（Extensions） 成为一级公民，MCP Apps（服务端渲染 UI）和 Tasks（异步任务）作为首批扩展落地。

一、核心发现

发现 1：无状态化重构——MCP 从"有状态会话"到"自包含请求"

2026-07-28 RC 的核心变化是协议层无状态化，由 6 个 SEP（Spec Enhancement Proposal）协同实现：

变化 SEP 细节
移除握手 SEP-2575 initialize/initialized 消失，client 信息/能力通过 _meta 在每个请求中携带；新增 server/discover 方法按需获取服务器能力
移除 session SEP-2567 Mcp-Session-Id header 和协议级 session 消除，不再需要粘性路由或共享 session store
限制 server→client 请求 SEP-2260 服务器发起的请求仅允许在主动处理 client 请求期间进行，不再有"凭空出现"的 prompt
多往返请求 SEP-2322 替代 SSE held streams；服务器返回 InputRequiredResult，client 用 inputResponses + 回显 requestState 重新发起调用，任何实例都可恢复
强制路由 header SEP-2243 Streamable HTTP 上必须携带 Mcp-Method 和 Mcp-Name header，服务器在 header 与 body 不一致时拒绝
缓存元数据 SEP-2549 List/resource 结果携带 ttlMs 和 cacheScope（模仿 HTTP Cache-Control），替代长生命周期 SSE 做变更通知
Trace Context SEP-414 _meta 中携带 W3C Trace Context（traceparent、tracestate、baggage），通过 OpenTelemetry 实现跨 SDK 分布式追踪

前后对比：

旧版（2025-11-25）：必须先 initialize 建立会话，获取 Mcp-Session-Id，后续每个请求都携带此 ID，客户端被绑定到唯一服务器实例（sticky routing）。

新版（2026-07-28）：单个自包含请求即可完成，任何实例都能处理。客户端信息通过 _meta 嵌入请求体。

关键洞察：协议层无状态 ≠ 应用无状态。需要跨调用保持状态的服务器使用显式 handle 模式——工具调用返回一个标识符（如 basket_id），模型将其作为参数传回。模型可以跨工具组合 handle、推理它们、在步骤间传递，这在以前由传输元数据隐藏的外部管理 session 状态中是不可能实现的。

部署影响：远程 MCP 服务器不再需要 sticky session、共享 session store 和深度包检测，可以在普通轮询负载均衡器后运行。

发现 2：扩展系统成为一级公民

SEP-2133 将扩展正式化：

  • 以 reverse-DNS ID 标识（如 io.modelcontextprotocol.apps）
  • 通过 client/server capabilities 上的 extensions map 协商
  • 居住在 ext-* 仓库中，有委托维护者
  • 独立于规范版本发布
  • SEP 流程新增 Extensions Track（实验性 → 官方）

首批扩展：

MCP Apps（SEP-1865）：服务器可发布交互式 HTML 界面，在沙箱化 iframe 中渲染。工具预先声明 UI 模板（用于预取/缓存/安全审查），UI 通过相同的 JSON-RPC 协议回传，确保所有操作都经过与直接工具调用相同的审计/授权路径。由 Anthropic 与 OpenAI 联合开发，已在 Claude、ChatGPT、Goose、VS Code 中工作。发布合作伙伴包括 Amplitude、Asana、Box、Canva、Figma、Slack、Salesforce 等。

Tasks 扩展（SEP-2663）：异步任务从实验性升级为正式扩展。服务器用 tools/call 返回 task handle，client 通过 tasks/get、tasks/update、tasks/cancel 驱动。任务创建是服务器导向的：client 声明支持的能力，服务器决定是否创建任务。任务状态包括 working、input_required、completed、failed、cancelled。

发现 3：OAuth 2.1 授权——从混乱到可用

MCP 的 OAuth 授权经历了一个混乱的演进过程：

2025-03-26 版本的问题：MCP 服务器同时充当 resource server 和 authorization server，模糊了两者边界。企业级部署需要的是远程 MCP 服务器 + 资源所有者安全访问其数据的能力。

2025-11-25 版本的改进：
- 引入 Client ID Metadata Documents (CIMD)：允许动态客户端注册而无需预注册
- 增强采样（Enhanced Sampling）
- 引入 Elicitation：服务器暂停执行并请求用户输入
- URL-mode：安全敏感交互（OAuth 流程、凭证输入、支付设置）——将用户发送到外部 URL
- Form-mode：结构化输入/澄清——选择不同解释
- 客户端安全要求
- 服务端 Agent Loops：服务器可在采样请求中包含工具定义，指定工具选择行为，内部实现多步推理

2026-07-28 版本进一步规范化授权：resource_metadata discovery 端点、authorization_servers 声明、scopes_supported 定义（如 mcp:tools、mcp:resources）。企业可使用 Keycloak 等标准 IdP 做认证后端。

发现 4：NSA 发布 MCP 安全指南——国家级安全背书

美国国家安全局（NSA）发布了《Model Context Protocol (MCP): Security Design Considerations》网络安全信息指南（CSI），这是首个国家级机构对 MCP 协议安全性的正式评估。

核心安全关注点：
- 应用层协议：MCP 是应用层协议，提供简单约定的消息模式和传输格式
- Prompt Injection 风险：工具返回的数据可能包含恶意指令
- 权限模型：Tools（写侧）需用户审批/拒绝，Resources（读侧）需访问控制
- 传输安全：stdio 用于本地，Streamable HTTP 用于远程（需 TLS）

2026 MCP 企业路线图明确四大缺口：
1. 结构化审计追踪和可观测性（对接 SIEM/APM）
2. 企业级认证（SSO 集成流程）
3. Gateway 和 Proxy 模式（授权传播和会话亲和性）
4. 配置可移植性（跨客户端）

发现 5：MCP vs A2A——互补而非竞争

Google 的 A2A（Agent-to-Agent） 协议与 MCP 定位不同：
- MCP：标准化 AI 如何连接到工具和数据（垂直连接）
- A2A：标准化 Agent 之间如何通信和协作（水平连接）

两者互补：一个 Agent 可以通过 MCP 连接工具，通过 A2A 与其他 Agent 协作。

Agent 支付协议（x402 和 Stripe MPP）开始解决 Agent 发起交易的支付侧，但组织内部的成本治理仍未解决。

二、协议架构全景

三角色模型

角色 描述
Host 用户交互的 AI 应用（Claude Desktop、Cursor、ChatGPT、自定义应用）
Client 宿主内部，管理到服务器的连接。一对一对应单个服务器；一个宿主可运行多个 client
Server 通过协议向 AI 暴露能力

三种原语

  • Tools — AI 可执行的动作（发消息、创建记录、运行查询、触发部署）。写侧。用户可审批/拒绝。
  • Resources — AI 可读取的数据（文件、DB 行、API 响应、文档）。读侧。
  • Prompts — 引导 AI 行为的可复用模板。

协作模式

  • Sampling：服务器在执行中请求 AI 模型生成补全。模型推理中间状态、验证假设、生成内容。用户可审查/编辑。
  • Elicitation：服务器暂停执行并请求用户输入。
  • Server-Side Agent Loops：服务器内部实现多步推理——研究型服务器可以 spawn agents、协调工作、交付一致结果，无需自定义编排代码。

四、实践启发与对 Hermes 系统的影响

1. Hermes 的 MCP 集成应跟进 2026-07-28 规范

Hermes 已有 native-mcp 和 mcporter 两个 skill。关键跟进点：

  • 无状态化：如果 Hermes 的 MCP client 依赖 session ID，需要在升级时适配新协议。好消息是无状态化简化了客户端实现。
  • Extensions 协商：extensions map 是新的能力协商机制，Hermes client 应支持声明和检测扩展。
  • Tasks 扩展：异步任务模式对 Hermes 长任务编排有直接参考价值——与现有的 delegate_task 和 cronjob 模式互补。

2. MCP Apps 对飞书/微信交互的启示

MCP Apps 的"服务端渲染 HTML 界面在沙箱 iframe 中"模式，与 Hermes 的飞书 Card 2.0 交互设计有异曲同工之处。如果未来 MCP 生态中出现飞书/微信的 MCP Apps 服务器，可以直接复用 Hermes 的卡片渲染能力。

3. 安全启示

NSA CSI 指南强调的 prompt injection 风险对 Hermes mcp-security-audit skill 有直接参考价值。现有的安全审计框架应纳入：
- Tools 返回数据的可信度分级
- Sampling 请求中的指令注入防护
- Elicitation 交互中用户输入的 sanitize

五、知识缺口与后续方向

  1. 2026-07-28 最终发布后的迁移指南：从 2025-11-25 到 2026-07-28 是 breaking change，现有 MCP 服务器需要迁移。需跟踪官方迁移文档。
  2. MCP Gateway/Proxy 模式：企业路线图提到的 gateway 和 proxy 模式（授权传播、会话亲和性）尚无具体实现。与 Hermes Gateway 架构有潜在融合点。
  3. x402 支付协议：Agent 发起交易的标准化，对 Hermes 量化交易的自动下单有参考价值，但当前规范尚不成熟。
  4. MCP 可观测性：W3C Trace Context 和 OpenTelemetry 集成是正确的方向，但实际部署中的 SIEM/APM 对接方案仍需验证。
