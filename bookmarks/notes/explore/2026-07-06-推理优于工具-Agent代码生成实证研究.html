一、内容详细整理

1.1 核心问题与研究动机

团队使用 AI 编码助手时，倾向于不断增加 Agent 能力——浏览器测试工具、设计导向的 system prompt——假设「能力越多 = 软件越好」。这个假设从未被严格验证过。

本文设计了一个严格的对照实验：让 90 个独立的 Agent 运行从同一份详细规格说明书构建同一个应用（实时回顾看板），逐一改变单一变量（模型、工具、prompt、推理努力），测量功能质量和首次可靠性。

核心发现一句话：多数首次失败来自推理不足，而非可见缺陷——用更强的模型或更高的推理努力能预防，而检查工具抓不到。

1.2 实验设计

任务：所有运行构建同一个应用——自托管的实时回顾看板（React+Vite 前端 + Node.js 后端），包含看板创建、SQLite 持久化、拖拽卡片、嵌套评论、WebSocket 实时同步、Docker 单容器部署、CSV 导出、开发者文档。

评分体系：
- 14 个功能标准，每个 0-3 分（首次通过=3，首次失败修复=2，未解决=1），满分 42 分
- 视觉质量单独 1-5 分评分（由 LLM 从截图评分 + 人工验证）

变量矩阵：
- 5 个模型家族：Claude Opus 4.7（48次）、Opus 4.6（27次）、Sonnet 4.6（10次）、Gemini 3.1（3次）、Qwen（2次）
- 2 个 Agent 框架：Claude Code、Antigravity
- 2 个推理努力级别：High、xHigh
- 测试工具（Playwright）：有/无
- 设计 prompt：无/完整版/一段话精简版

1.3 关键发现一：能力层级主导结果

模型家族是最大的变异来源，远超任何工具、prompt 或努力设置。

前沿模型聚拢在天花板附近：
- Opus 4.7：均值 41.3/42（48 次运行）
- Opus 4.6：均值 40.7/42（27 次运行）
- Sonnet 4.6：均值 41.0/42（10 次运行）

低成本本地模型 Qwen 处于完全不同的区间：
- 均值 30.5/42（24-37 分范围）
- Token 消耗估算成本 $41-$179（前沿模型中位数约 $3.60）

核心洞察：前沿模型与弱模型之间约 10 分的差距，远大于任何工具/prompt/努力在同一层级内产生的差异（1-2 分）。

1.4 关键发现二：测试工具增加成本但不增加质量

Playwright 工具在 Opus 4.7 上使成本上升 42-68%，但功能分数零变化。

Token 分解揭示了溢价的去向：
- 输出 token 基本不变（46k→42k @High）
- 缓存读取 token 暴涨 2-3 倍（2.3M→5.3M @High，2.3M→7.0M @xHigh）

工具溢价 = 上下文反复读取，模型不断重新消化被工具往返和截图膨胀的会话，而非额外工程产出。

关键验证：所有 23 个启用工具的运行都实际调用了测试功能——不是被忽略了。但即使在有可见界面缺陷的运行中，工具仍未减少首次失败。

1.5 关键发现三：推理努力廉价地买到首次可靠性

这是全文最重磅的发现，对 Hermes Agent 设计有直接指导意义。

将推理努力从 High 提升到 xHigh（Opus 4.7）：
- 首次完美运行率：28% → 89%（Fisher exact p < 0.001）
- 纠正性提示词：18 次运行共 16 个 → 3 个（约 5 倍减少）
- 均值分数：41.0 → 41.8
- 成本溢价：仅 9%（base 条件）到 29%（带工具条件）

对比：测试工具花了 42-68% 的成本溢价却零收益；推理努力花了 9-29% 换来 5 倍可靠性提升。ROI 差距悬殊。

1.6 关键发现四：首次失败高度集中

90 次运行中 100 个首次标准失败，分布极不均匀：

  • Docker 部署：40/90 次首次失败（44%）
  • 本地开发环境：15/90 次（17%）
  • 拖拽卡片移动：14/90 次（19%）
  • 其他 11 个标准合计仅 31 次

两个环境标准占全部首次失败的 55%。 反复罪魁是：原生 SQLite 模块在最小容器中无法编译、Web 框架的破坏性变更移除了通配路由。

1.7 关键发现五：修复后总分掩盖了模型差异

这对 Agent 基准测试有重大方法论启示。

因为「失败后修复」仍得 2/3 分，42 分总分主要衡量模型最终能达到什么，而非首次交付什么。

Opus 4.6 → Opus 4.7 的变化：
- 均值差异 < 1 分（40.7 vs 41.3）
- Docker 首次通过率：19% → 75%

同一层级模型看起来「可互换」，但首次可靠性天差地别。 作者建议：基准报告应同时发布「首次可靠性」和「修复负担」，而非仅报告修复后总分。

1.8 关键发现六：设计 prompt 提升视觉但不提升功能

  • 无设计 prompt：所有 45 次运行视觉评分恰好 3.0
  • 完整设计 prompt：均值 4.5/5
  • 一段话精简版：均值 4.7/5（甚至更高）

核心洞察：模型「制作精美界面的能力」已经存在，不需要被「教会」，只需被「显式调用」。推理努力和测试工具都无法触发它——一段简短通用的设计指令就能。

但设计 prompt 有隐性功能代价：
- 拖拽失败率从 11% 升至 28%
- 自定义动画界面的丰富交互代码比朴素默认更容易出错
- 即使在 xHigh 努力下，设计 prompt 仍然消耗部分可靠性

1.9 关键发现七：配置内变异性真实存在

同配置重复运行的输出差异巨大：
- Opus 4.6 @High：手写 CSS 行数 41-626（约 15 倍跨度），源文件 10-17 个
- 功能分数始终在 38-42 窄带内
- xHigh 将功能散布压缩到近乎均匀的 42

实践含义：任何单个 Agent 输出应被视为宽分布中的一个样本，而非代表性结果。推理不足是变异性的主要来源。

二、查询拓展

2.1 推理努力（Reasoning Effort / Extended Thinking）

Claude 的 Extended Thinking 功能允许模型在回答前进行更长的内部推理。推理努力级别（如 High、xHigh）控制模型在内部思考上投入的 Token 预算。Anthropic 文档指出，更高的推理努力适合需要多步推理的复杂任务，但会增加延迟和成本。本文首次在代码生成场景中量化了推理努力对首次可靠性的 ROI。

2.2 OpenSpec 规格驱动开发

OpenSpec 是一种以规格说明书（specification/change）驱动的 AI 编码工作流。开发者编写详细的变更规格，Agent 负责实现。本文使用 OpenSpec 格式编写实时回顾看板的完整规格（含功能列表、技术栈、持久化要求等），确保每次运行的输入完全一致。

2.3 Antigravity Agent 的隐藏 Prompt 问题

论文发现 Google 的 Antigravity Agent 会注入用户不可见、不可控的 system prompt。这在安全层面是已知隐患（OWASP LLM01 Prompt Injection），在研究层面则意味着「通过不同后端比较模型时，实际上可能也在比较不同的隐藏 prompt」。作者建议任何比较模型或审计输出的研究者首先确认服务路径是否注入了隐藏 prompt。

2.4 STROBE 观察性研究报告指南

本文遵循 STROBE（Strengthening the Reporting of Observational Studies in Epidemiology）指南。虽然 STROBE 原为流行病学观察性研究设计，但作者将其应用于 AI Agent 研究——因为本实验中条件是「分配」而非「随机化」的，p 值仅作为关联强度的描述性总结，不声称因果识别。这种学术严谨性在 AI Agent 实证研究中较为罕见。

2.5 修复后总分 vs 首次可靠性的方法论分歧

当前主流 Agent 基准（SWE-bench、HumanEval 等）主要报告最终通过率，允许 Agent 多轮自我修复。本文指出这种评分方式系统性低估了模型间的真实差异——一个能自修复的模型和一个首次就对的模型获得几乎相同的分数，但前者需要用户投入更多纠正干预。这对生产环境中的 Agent 选型具有重大影响。

3.2 四种投入的 ROI 对比

  • 推理努力（High→xHigh）：成本 +9-29%，首次完美率 28%→89%，修复负担 -5 倍。ROI：极高
  • 测试工具（Playwright）：成本 +42-68%，功能分数不变，可靠性不变。ROI：负
  • 设计 prompt（完整/精简）：成本 +35-56%，视觉 3.0→4.5+，功能略降。ROI：视觉维度高，功能维度负
  • 模型升级（4.6→4.7）：成本相近，Docker 首次率 19%→75%。ROI：高

3.3 Agent 评估三轴模型

论文提出应从三个维度评估 Agent，而非单一总分：

  • 最终功能分（Post-repair total）：衡量能力上限
  • 首次可靠性（First-try reliability）：衡量无人工干预的交付质量
  • 修复负担（Repair burden）：衡量所需人工纠正次数

当前主流基准只报告第一轴，导致模型间真实差异被压缩为 <1 分。

四、趋势判断

趋势1：推理努力将成为 Agent 调优的一等参数

推理努力级别（如 Claude 的 Extended Thinking）目前是隐藏的配置选项，但本文数据表明其 ROI 远超工具扩展。预计未来 Agent 框架会将推理努力暴露为显式调优参数，配合任务复杂度自动选择。依据：推理努力 xHigh 对首次可靠性提升 5 倍，成本仅增 9-29%。

趋势2：Agent 基准测试将从「通过率」转向「首次可靠性 + 修复负担」

SWE-bench 等主流基准报告最终通过率，允许无限次自我修复。本文证明这会压缩模型间的真实差异。预计下一代基准将引入首次尝试通过率、纠正提示次数等指标，更贴近生产环境需求。依据：Opus 4.6→4.7 总分差 <1 分但 Docker 首次率从 19%→75%。

趋势3：工具 ROI 量化将成为 Agent 工程标配

本文通过 Token 分解证明 Playwright 的成本溢价全部花在上下文反复读取上，而非额外工程产出。预计未来 Agent 监控/可观测性系统将自动计算每个工具的 Token ROI、可靠性贡献率，淘汰负 ROI 工具。依据：工具成本 +42-68% 但可靠性零提升。

趋势4：能力调用（invocation）比能力教学（teaching）更重要

设计 prompt 的精简版（一段话）效果与完整版相同甚至更好。模型已有制作精美界面的潜在能力，只需被显式激活。这暗示 Agent 设计应聚焦于「正确调用已有能力」，而非试图「教会模型新能力」。依据：精简 prompt 视觉评分 4.7 vs 完整版 4.5。

五、关联分析

5.1 与 Hermes Agent 工具调用架构的关联

本文直接关联 Hermes 的工具体系设计。论文证明「视觉测试工具对 Agent 可靠性零贡献，成本 +42-68%」，这与 Hermes 的 agent-reliability-engineering skill 中「七层优雅降级架构」理念一致——不是工具越多越可靠。可落地的改进：评估 Hermes 当前 cron job 和 skill 链中是否有类似 Playwright 的「负 ROI 工具」，即增加了 Token 消耗但未提升任务成功率的工具调用。

5.2 与推理努力优化的关联

Hermes 当前使用 model-switch skill 按场景切换模型。本文数据支持一个新维度：在同一模型内按任务复杂度调整推理努力。对于多步推理任务（如代码生成、深度分析），提升推理努力的 ROI 远高于增加工具或 prompt 工程化。关联笔记：2026-07-05-ReasoningEffort.md。

5.3 与 Agent 基准测试方法论关联

2026-06-23-LedgerAgent.md 和 2026-07-02-ReGRPO.md 等 Agent 研究论文精读中，均涉及 Agent 评估指标。本文提出的「首次可靠性 + 修复负担」三轴评估模型可直接应用于 Hermes 的 skill-stress-test skill——当前压力测试只评估最终通过率，应增加首次成功率维度。

5.4 与隐藏 Prompt 安全隐患关联

论文发现的「Antigravity Agent 注入隐藏 system prompt」问题，直接关联 Hermes 的 agent-security-governance skill 和 llm-prompt-injection playbook。实际风险：如果 Hermes 的 Gateway 层或 Provider 适配层注入了隐藏 prompt，可能导致 Agent 行为不可预测且难以调试。应在 Agent 审计流程中加入「prompt 透明度检查」。

5.5 与「一次性上下文」原则的关联

AGENTS.md 中的「上下文一次性原则」要求委派任务时 context 一次写透。本文的推理努力发现为这一原则提供了理论支持：更多的前期推理（更高 effort + 更完整的初始 context）比后期修复（纠正性 prompt）ROI 高得多。xHigh 的 3 个纠正性 prompt vs High 的 16 个，正是「一次做对」优于「反复修补」的量化证据。

六、金句摘录

「Spend on capability and effort to get reliable software, ask explicitly for visual quality when it matters, and do not expect a verification tool to fix failures it cannot see.」

「Most first run failures came from weak reasoning, which a stronger model or more effort prevents, not from visible flaws a checking tool would catch.」

「The tool premium is context re-reading, the model repeatedly re-ingesting a session inflated by tool roundtrips and screenshots, not additional engineering output.」

「Any single agent output should be treated as one sample from a wide distribution rather than as a representative result.」

七、行动启示与借鉴点

P0 — 可立即执行

  • 推理努力调优：对 Hermes 的复杂 cron job（如每日论文精读、深度分析）评估是否值得提升推理努力级别。当前统一使用同一 effort 可能不是最优配置。
  • 首次可靠性追踪：在 watchdog 和 error-monitoring 中增加「首次成功率」指标，追踪哪些 cron job 经常需要重试（即修复负担高），这些是推理不足或模型选型不当的信号。

P1 — 可在近期执行

  • 工具 ROI 审计：审查 Hermes 当前启用的所有工具（terminal、web_search、web_extract、send_message 等），量化每个工具的 Token 消耗 vs 任务成功率贡献。淘汰负 ROI 的工具调用模式。
  • prompt 透明度检查：审查 Hermes Gateway → Provider → Model 链路中是否有隐藏的 system prompt 注入，确保 prompt 可审计。

P2 — 需工程改造

  • skill-stress-test 增强：在 Skill 压力测试框架中加入「首次可靠性」和「修复负担」维度，不使用纠正性提示地评估 Skill 的首次成功率。
  • 推理努力自动调度：基于任务复杂度自动选择推理努力级别——简单查询用 Low，多步推理用 High，复杂分析/代码生成用 xHigh。

P3 — 暂不适用

  • 容器部署/环境缺陷修复（Hermes 不涉及 Docker 部署场景）
  • 设计 prompt 的视觉质量优化（Hermes 输出以文本为主，非 UI 应用）
