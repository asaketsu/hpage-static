边缘PLC与软PLC：控制逻辑从专用硬件走向通用计算

摘要

软PLC（Soft PLC）是把 IEC 61131-3 控制运行时从专用 PLC 硬件迁移到通用 CPU（x86 IPC / ARM SoC / 服务器）上执行的架构形态；"边缘PLC"则是它的部署位置演进——跑在产线边缘的 converged edge controller 上，与容器化分析、OPC UA、MQTT broker 共存于同一台 Linux/Windows 机器。驱动力有两个：x86 六核+处理器廉价到可以"浪费"两个核做实时隔离，以及 IT/OT 融合让控制器必须同时干传统控制和非实时数据服务的活。2026 年的两强格局是 CODESYS（OEM 授权模式，Wago/Schneider/Pilz/Rexroth 等数十家厂商内嵌）与 TwinCAT 3（Beckhoff 硬件绑定），二者架构哲学根本不同：CODESYS 是可移植的 OS 无关库，确定性取决于硬件厂商选的 OS 层；TwinCAT 用 TcRTE 内核扩展直接隔离 CPU 核，确定性由 Beckhoff 软硬件一体保证。

关键发现

1. 软PLC 为什么现在成立：专用核隔离消除了历史污点

  • 十年前 PC-based 控制被踢出精密伺服圈的理由是延迟不确定；现代 Intel Core / AMD Ryzen 嵌入式六核+处理器可以把 2 个核独占给实时任务（isolcpus + CPU affinity + 关 C-state），剩余核跑 HMI/日志/网络服务
  • 加权决策矩阵实测结论（iotdigitaltwinplm）：两平台总分 147 vs 158 极接近，"多厂商硬件自由度"通常是决胜项——这不是性能问题，是供应链问题

2. 架构对比：确定性从哪来（最核心技术点）

TwinCAT 3                           CODESYS
┌─────────────────┐                ┌─────────────────┐
│ IEC 61131-3 应用 │                │ IEC 61131-3 应用 │
├─────────────────┤                ├─────────────────┤
│ TcRTE 内核扩展    │                │ 可移植 HAL 库     │
│ 抢占定时器中断     │                │ (绑定宿主调度器)   │
│ 专核独占隔离      │                ├─────────────────┤
├─────────────────┤                │ 宿主 OS 层        │
│ Windows/BSD 内核 │                │ PREEMPT_RT Linux │
└─────────────────┘                │ 或 QNX/VxWorks    │
  jitter: 1-5 μs                   └─────────────────┘
  (Beckhoff IPC 调优)                PREEMPT_RT: 5-20 μs
                                    硬 RTOS: 1-5 μs
  • CODESYS 确定性是平台选型的函数，TwinCAT 确定性是 Beckhoff 硬件配置的函数——工程含义：买 CODESYS 方案要先问硬件厂商底下是什么 OS
  • 实操坑：TwinCAT 隔离核要设对 CPU mask 且 BIOS 关 C-state，漏一步出难查的 jitter 尖峰；CODESYS on PREEMPT_RT 要配 SysCpuMultiCore CPU pinning + SysTarget watchdog

3. EtherCAT 深度差距：发明者红利

  • Beckhoff 发明 EtherCAT 并捐赠规范给 ETG，TwinCAT 主站是参考实现：主站与实时核融合，每任务周期一帧处理全部从站响应，分布式时钟同步误差 <1 μs（数十节点）
  • CODESYS EtherCAT Master SL 是软件栈（跑在宿主网络驱动之上），≥2ms 周期 + jitter 预算 >20μs 场景够用；亚毫秒伺服环 + 分布时钟同步 <5μs 选 TwinCAT 更稳
  • 反向优势：CODESYS 因内嵌于数十家厂商控制器，Profibus/PROFINET/CANopen/Modbus/EtherNet-IP/CC-Link 通常预集成——接旧现场总线网，CODESYS 生态省事

4. 容器化与硬件无关化（边缘PLC的IT/OT融合实体）

  • TwinCAT/BSD：FreeBSD 底座 + 非实时分区跑 Docker（分析容器/MQTT broker/Node-RED 与 PLC 共存）
  • CODESYS Virtual Control SL：容器化的软PLC runtime，几乎任何 x86/ARM 硬件可跑（含 RHEL 服务器）——PLC 逻辑走向"云原生部署"的形态
  • 免费试用边界（Intel ECI 文档）：CODESYS Linux runtime 无 license 可跑但每 2 小时自动停机，OPC UA client 30 分钟停——开发评估够用，生产必须买授权

5. CODESYS 4（2026-09-24 发布）：PLC 界的"现代化工作流"宣言

  • 不是替代 CODESYS 3，是并行第二系统；编译器/库/runtime 完全相同（V3.5 SP19+）
  • 革命点在工程形态：项目=文本文件文件夹（JSON/XML），Git 原生 diff；c4-cli 命令行支撑 CI/CD 无 IDE 构建（bootapp compile/library save-compiled），构建机免 license
  • 1.0 现实限制：仅 ST+LD 编辑器、无在线修改/断点/强制变量、无 FBD/SFC、无安全库——生产就绪场景只有两个：ST 库开发+自动构建、Modbus TCP 小型设备项目；现场调试仍用 CODESYS 3
  • 免费到 2028 年底；对版本控制地狱（TIA Portal 单二进制工程）是降维打击

与现有工作的关联

  • P1 · 与 IEC 61131-3 ST 笔记(10-20)直接衔接：ST 语言是软PLC生态的一等公民（CODESYS 4 只支持 ST+LD 再次印证）；本篇补齐了"ST 跑在什么 runtime 上"的架构层
  • P2 · 对 DUCK 机器人项目的参照：TwinCAT TcCOM（C++ 模块与 IEC 任务同实时保证共存）与我们"RL 策略 ONNX + 固件位置环"分层是同构问题——工业界的答案是"一个实时域内分层"而非"两个盒子串联"
  • P2 · 对嵌入式技能栈：PREEMPT_RT Linux + CPU 亲和性 + IRQ 路由的调优清单，与 Jetson 实时性话题通用

Actionable Insights

  1. 选型速查：Beckhoff 已在 BOM / 亚 100μs 周期 / 分布时钟多轴同步 / C++或Simulink集成 → TwinCAT；多硬件平台 / 已选 CODESYS 系厂商 / 自研 ARM 边缘控制器 / 禁单一供应商锁定 → CODESYS
  2. 评估 CODESYS 用 Linux 免费版做 PoC 时，脚本里记得每 <2h 重启 runtime
  3. 新写控制代码只用 PLCopen 标准 FB + 厂商专有 FB 包一层 wrapper，EtherCAT 配置存独立版本化 XML——跨平台迁移成本降一个量级
  4. CODESYS 4 + c4-cli 值得现在就装（免费窗口）练 Git 化 PLC 工程流，2029 才收费

关键风险与盲点

  • 决策矩阵分数来自单一博客（iotdigitaltwinplm，标注基于公开文档+项目经验，社区级证据非官方 benchmark）——权重应按项目重算
  • OpenPLC/OSCAT 等开源 runtime 被原文排除在 OEM 决策外（安全认证/现场总线深度/长支持缺失），但学习/原型场景仍是有用选项
  • CODESYS 4 是 1.0.0.0，6-8 周一版快速迭代，功能矩阵随时会变

一页速查

软PLC=IEC 61131-3 runtime 跑通用 CPU；边缘PLC=它+容器/云连接共存在边缘机
CODESYS：OEM 授权、OS 无关库、PREEMPT_RT 5-20μs/硬RTOS 1-5μs、现场总线广
TwinCAT：Beckhoff 绑定、TcRTE 抢核 1-5μs、EtherCAT 参考实现、TcCOM 融 C++
决胜项：多厂商自由度(CODESYS) vs EtherCAT 深度(TwinCAT)；矩阵 147:158
CODESYS 4(2026-09)：Web UI+文本项目+Git+c4-cli CI/CD，免费到 2028，1.0 仅库开发+小项目可用
免费 Linux runtime 2h 停机；Virtual Control SL=容器化 PLC
