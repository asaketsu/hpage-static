# 端侧离线语音待办 — 从 ASR 到 LLM 的完整工程实践

> 来源：[老码小张 - 微信公众号](https://mp.weixin.qq.com/s/JtgYXwboDKpJsNRmLsjBbg) | 2026-05-22

---

## 一、项目概述

**做一个完全离线的 Android App：语音待办**

核心链路三步：

```
按住录音 → Sherpa-ONNX 流式语音识别实时出字
松手停止 → 转录文本送入本地 LLM
大模型输出 → 总结内容 + 提取待办事项
```

**全程离线**：无云端 API，无数据上传，无"请检查网络连接"。

### 为什么做这件事？

两个趋势交汇：

| 趋势 | 现状 | 代表项目 |
|------|------|---------|
| 端侧 ASR 成熟 | 流式语音识别可在手机端实时运行 | Sherpa-ONNX, Whisper.cpp |
| 端侧 LLM 爆发 | 手机上跑 Gemma/Qwen 已成为现实 | LiteRT-LM, MLC-LLM, Apple On-Device Models |

**问题**：这两件事一直是分开的。ASR Demo 是 ASR Demo，LLM Chat 是 LLM Chat，没人把它们串起来做成真正可用的端到端离线应用。

## 二、完整技术架构

```
麦克风 → AudioRecord(16kHz/Mono/PCM16)
         → Sherpa-ONNX Online Transducer(流式识别)
         → CT-Transformer 标点恢复
         → LiteRT-LM Engine(本地大模型推理)
         → JSON 解析 → 总结 + 待办事项
```

### 2.1 数据持久化

| 组件 | 用途 |
|------|------|
| **Room 数据库** | 存储转录记录：原文、总结、待办列表(JSON)、时间戳 |
| **SharedPreferences** | 存储当前激活的模型路径、maxTokens、文件大小，App 重启后自动加载 |

## 三、语音识别：Sherpa-ONNX Online Transducer

### 3.1 为什么选 RNN-T 而非 Whisper？

| 对比维度 | Sherpa-ONNX RNN-T | Whisper |
|---------|-------------------|---------|
| 流式输出 | ✅ 天然支持，每 90ms 轮询 | ❌ 自回归，需整段音频 |
| 模型大小 | ~75MB (编码器67MB+解码器4.9MB+联合网络1MB) | ~1.5GB+ |
| 延迟 | 低，适合实时交互 | 高，适合离线批处理 |
| 中文支持 | ✅ 2002 个 BPE token，覆盖 CJK | ✅ |

### 3.2 音频采集参数

```
采样率: 16kHz
声道:   Mono (单声道)
格式:   PCM 16-bit
Buffer: 每次读取 1024 个采样点
归一化: [-1.0, 1.0] 浮点数组
```

### 3.3 标点恢复（CT-Transformer）

**容易被忽略但极其重要的环节**：原始 ASR 输出没有标点，可读性很差。

- 加载 **72MB** 的 CT-Transformer 标点模型
- 对流式结果（≥24 字符）和最终结果（≥16 字符）分别做后处理
- **优雅降级**：如果标点模型加载失败，没有标点也比崩溃好

## 四、本地大模型推理：LiteRT-LM Engine

### 4.1 为什么选 LiteRT-LM 而非 MLC-LLM 或 llama.cpp？

| 对比维度 | LiteRT-LM | MLC-LLM | llama.cpp |
|---------|-----------|---------|-----------|
| 官方支持 | ✅ Google 官方方案 | 社区项目 | 社区项目 |
| Android 集成 | ✅ 与 Play Services TFLite 深度集成 | 需自行编译 | 需自行编译 |
| 运行时更新 | ✅ Play Services 自动更新 | ❌ | ❌ |
| 算子优化 | ✅ .litertlm 格式已做移动端优化 | 需自行量化 | 需自行量化 |
| API 设计 | Engine → Conversation → sendMessageAsync | 较复杂 | 较复杂 |

### 4.2 支持的模型

| 模型 | 大小 | 最低内存 | 特点 |
|------|------|---------|------|
| Gemma-4-E2B-it | 2.5 GB | 8 GB | 多模态，32K 上下文 |
| Gemma-4-E4B-it | 3.5 GB | 12 GB | 多模态，32K 上下文 |
| Gemma-3n-E2B-it | 3.5 GB | 8 GB | 多模态，int4 量化 |
| Gemma-3n-E4B-it | 4.7 GB | 12 GB | 多模态，int4 量化 |
| **Gemma3-1B-IT** | **557 MB** | **6 GB** | **轻量纯文本，推荐入门** ✅ |
| Qwen2.5-1.5B-Instruct | 1.5 GB | 6 GB | 中文能力强，q8 量化 |
| DeepSeek-R1-Distill-Qwen-1.5B | 1.7 GB | 6 GB | 推理能力强，q8 量化 |
| TinyGarden-270M | 276 MB | 6 GB | 函数调用专用 |
| MobileActions-270M | 276 MB | 6 GB | 手机操作专用 |

### 4.3 API 使用

```kotlin
val config = EngineConfig(
    modelPath = modelPath,
    backend = Backend.CPU(),
    maxNumTokens = maxTokens,
    cacheDir = context.cacheDir.absolutePath
)

val engine = Engine(config)
engine.initialize()

val conversation = engine.createConversation(
    ConversationConfig(
        systemInstruction = Contents.of(Content.Text(systemPrompt))
    )
)

// 流式推理
conversation.sendMessageAsync(contents, callback)
```

### 4.4 Prompt 工程：结构化 JSON 输出

端侧模型指令遵循能力远不如云端大模型，采用以下策略：

**系统提示词：**
```
你是一个中文语音转文字的智能助手。用户会给你一段语音识别的文本，你需要：

1. 对文本进行总结，提炼核心内容
2. 从中提取待办事项（如果有的话）

请严格按照以下 JSON 格式输出，不要输出其他内容：

{"summary":"总结内容","todos":["待办1","待办2"]}

如果没有待办事项，todos 为空数组。
```

**解析策略：**
- 用 `substringAfter("{").substringBeforeLast("}")` 提取 JSON 主体
- 再用 Gson 反序列化
- **比正则匹配更鲁棒** — 小模型偶尔会在 JSON 前后加废话，这个策略能容忍

**降级策略：** 如果 JSON 解析失败，直接把原始 LLM 输出作为总结，待办列表为空。用户不会看到崩溃。

## 五、模型下载：断点续传 + 完整性校验

大模型文件动辄几个 GB，不方便直接打包在 APK 中，初始化时需要下载：

| 策略 | 实现 |
|------|------|
| **断点续传** | 检测本地已有部分文件大小，通过 HTTP Range 头从断点继续 |
| **重定向处理** | HuggingFace 下载链接会经过 CDN 重定向，手动跟随最多 10 次 301/302/307/308 |
| **完整性校验** | `file.length() == expectedSize`，每个模型的预期大小在 ModelConfig 中硬编码 |
| **Wi-Fi 提醒** | 首次下载时检查网络类型，非 Wi-Fi 给出建议但不阻断 |
| **速度显示** | 每 500ms 上报一次进度，包含下载速度 |

## 六、踩过的坑与解决方案

### 坑 1：Sherpa-ONNX 的 AssetManager 陷阱

**问题**：`OnlineRecognizer` 构造函数接受一个 `AssetManager` 参数用于从 assets 加载模型。但模型是从 assets 复制到 filesDir 后再按文件路径加载的。如果传入 Activity 的 AssetManager，它会尝试从 assets 目录找文件，路径对不上。

**解决**：传 `null` 作为 AssetManager，强制走文件路径加载模式。

> 参考：[k2-fsa issue #2562](https://github.com/k2-fsa/sherpa-onnx/issues/2562)

### 坑 2：ONNX Runtime 和 TFLite 的 JNI 冲突

**问题**：Sherpa-ONNX AAR 自带 `libonnxruntime.so`，而 LiteRT-LM 依赖的 Play Services TFLite 也带了 `libtflite_jni.so`。两个库在 merge 阶段会冲突。

**解决**：Gradle `packaging.jniLibs.pickFirsts` 配置 `pickFirst` 策略。

```gradle
android {
    packaging {
        jniLibs {
            pickFirsts += listOf("**/*.so")
        }
    }
}
```

### 坑 3：部分下载文件被误判为完整

**问题**：最初 `isModelDownloaded()` 只检查 `file.exists() && file.length() > 0`。用户下载到一半退出 App，下次进来系统认为模型已下载。

**解决**：用 `file.length() == expectedSize` 精确校验。每个模型的预期大小在 ModelConfig 中硬编码，下载完成和 App 重启时都会校验。

## 七、性能数据

在 **Snapdragon 8 Gen 2（12GB RAM）** 设备上实测：

| 指标 | Gemma3-1B-IT | Qwen2.5-1.5B-Instruct |
|------|-------------|---------------------|
| 模型加载时间 | ~3s | ~5s |
| 100 字转录总结 | ~8s | ~12s |
| ASR 实时出字延迟 | <200ms | <200ms |
| 内存占用（ASR+LLM） | ~1.2 GB | ~1.8 GB |

> Gemma-4-E2B 在 12GB+ 内存的旗舰机上也能跑，但推理速度明显更慢，适合对质量要求高、不介意等待的场景。

## 八、未来扩展方向

语音待办只是一个切入点。端侧 ASR + 端侧 LLM 的组合，可以做的事情远不止"总结 + 提待办"：

| 场景 | 流程 | 价值 |
|------|------|------|
| **会议纪要** | 长录音 → 分段转写 → 逐段总结 → 生成完整纪要 | 会议场景 |
| **实时翻译** | ASR 识别 → LLM 翻译 → 目标语言输出，全程离线 | 跨国交流 |
| **语音助手** | ASR → LLM 意图识别 → 本地 Action 执行 | TinyGarden/MobileActions 就是为此设计的 |
| **隐私场景** | 医疗问诊记录、法律咨询记录——数据绝不能离开设备 | 合规刚需 |

> **核心结论**：当 ASR 和 LLM 都能在手机上离线运行时，"语音 AI"不再等于"云端语音 AI"。这才是最兴奋的地方。

## 九、Jetson 视角的启发

这篇文章对 Jetson 边缘 AI 项目有直接参考价值：

| 手机端方案 | Jetson 对应方案 | 说明 |
|-----------|----------------|------|
| Sherpa-ONNX (RNN-T) | Sherpa-ONNX (GPU 加速) | Jetson 上可用 CUDA 加速，延迟更低 |
| LiteRT-LM (TFLite) | TensorRT + ONNX Runtime | Jetson 上用 TensorRT 提速 3-10 倍 |
| CT-Transformer 标点 | 同方案或 ONNX 部署 | 72MB 模型可轻松部署 |
| 8GB 内存限制 | 8GB 统一内存 | 类似，需选 1B-1.5B 模型 |
| CPU 推理 | GPU + TensorRT 推理 | Jetson 优势明显 |

**可迁移架构**：麦克风 → AudioRecord → Sherpa-ONNX → CT-Transformer → TensorRT-LLM → JSON → 本地应用
