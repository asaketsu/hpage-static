一、内容整理

核心问题与研究动机

Agent 的工具目录越来越大，无法每步都塞进 prompt，于是检索器决定 Agent "看见"哪些工具。关键事实：很多请求需要多个工具——常常因为一次调用的产出（ID/凭证）是另一次调用的输入。

对这类请求，检索器必须返回完整集合：漏掉任何一个必需工具，那一步就执行不了。COLT 因此把工具检索定义为 completeness 问题，近期对已部署工具搜索的评测也把 completeness 与 recall 并列报告。

现有评测无法回答这个问题，两个原因：

  • 基准被单工具查询主导：ToolRet 的 7,961 条查询里 55%（4,402 条）只有一个目标工具，对这些查询 completeness 退化成 hit rate
  • 多工具检索结构各在各的数据、各对各的基线上评测过：扁平稠密检索、LLM 查询分解、LLM 导航层级、server-then-tool 匹配、工具依赖图、训练式集合级检索器——假设不同、开销不同（标注数据 / 查询期 LLM 调用 / 图构建），从未同台

论文要回答三件事：哪种结构能给多工具请求返回完整集合？各自在检索期花什么？不完整时怎么失败的？

方法论：六个结构族 × 两个多工具测试床 × 三层度量

六类结构代表实现（共享组件固定：bge-base-en-v1.5 做嵌入、DeepSeek-V3.2 temperature=0 做全部 LLM 步骤）：

  • 扁平：BM25 词法；bge-base / e5-base 稠密，无训练
  • 分解：一次 LLM 调用把请求拆成子请求，各用 bge 检索，轮流合并（无公开训练代码，取通用实现）
  • 层级（LLM 导航）：AnyTool 官方 agent 代码，只跑 search 阶段（≤64 API、每 agent 5 叶工具、20 万 token 上限）
  • server-then-tool：MCP-Zero，LLM 按"服务器域 + 操作"写请求，匹配器保留 top5 服务器 × 每请求 top3 工具（原版用商业嵌入，本文换 bge 保持变量固定）
  • 依赖图：Graph-of-Skills 默认构建（含索引期 LLM 校验的语义边，查询期无 LLM）+ 确定性变体消融
  • 集合级（训练式）：COLT 按原配置在每个测试床重训（AppWorld 90 条官方训练查询，57 条开发集选 checkpoint；MCP-Bench 五折交叉验证）；HYSET 简化版（无执行奖励、最大集合放宽）

测试床：

  • AppWorld：345 条官方测试查询（129 normal + 216 challenge），456 个 API，用 In-N-Out 的参数级依赖标签。必需集合 = 查询调用的 API ∪ 其参数的产出 API；剔除 6 个凭据 supervisor API 后，必需集合大小 2-12（中位 6）。258 条构成单链，87 条为多组件混合（中位 7 个 API）
  • MCP-Bench：257 个工具 / 28 个真实 MCP 服务器，103 条任务（97 条需多工具）；任务无工具集标签，作者从详细描述+依赖分析反推参考集合（按服务器数分层：55 单服务器 / 30 双 / 18 三，中位集合 6/10/11）

度量：

  • completeness@k：R(q) ⊆ L_k(q) 的查询占比（严格集合包含，不是平均命中）
  • recall@k：|R∩L_k| / |R| 的均值
  • 检索期成本：每查询的 LLM 调用数、prompt/completion token、LLM 阶段墙钟延迟（训练数据与索引构建单列为"前置要求"，不计入每查询成本）
  • 显著性：按查询成对 bootstrap 95% CI（2,000 次重采样）
  • 失败归因：每个缺失必需 API 按深度（排名 17-50 vs 完全缺失）× 依赖角色（target = 无消费者；prerequisite = 为他人产出输入，分"未识别"与"级联"）分类，按 target→未识别前置→级联→仅备选的顺序取首要原因

关键实验结果与数据

发现一：聚合分数混合了两个截然不同的区制（ToolRet，7,961 查询 / 44,453 工具 / 35 池）

分层：单目标 4,402、双 1,937、三 1,089、四及以上 533。

completeness@10 按目标数（bge-base / e5 / COLT stage1 / 分解 / GoS）：

  • 1 个目标：.672 / .635 / .642 / .664 / .583
  • 2 个目标：.426 / .405 / .525 / .450 / .255
  • 3 个目标：.169 / .174 / .234 / .233 / .092
  • 4+ 个目标：.129 / .118 / .129 / .169 / .079
  • 多目标加权：.303 / .291 / .377 / .341 / .178
  • 全量聚合：.507 / .481 / .523 / .520 / .402

关键：排序发生反转。单目标上 bge 最好或并列最好，但在 2/3 目标上被 COLT stage1 与分解反超（成对 CI 排除 0）；4+ 目标上只有分解稳定更高。而 recall@10 在多目标上仍有 .533-.613——大部分必需工具被检索到了，但集合很少完整。

发现二：AppWorld / MCP-Bench 主表（C@16 / R@16）

  • BM25：AppWorld .000 / .188；MCP .126 / .395
  • bge-base：.020 / .190；MCP .272 / .676
  • e5-base：.064 / .336；MCP .330 / .717
  • 分解（LLM+bge）：.035 / .417；MCP .359 / .776
  • AnyTool（层级导航）：.301 / .757；MCP .398 / .783
  • MCP-Zero（server-then-tool）：.000 / .234；MCP .243 / .638
  • GoS（依赖图）：.096 / .366；MCP .243 / .536
  • COLT（集合级训练）：.328 / .702；MCP .583 / .887
  • HYSET 简化版：.000 / .213；MCP .039 / .148

四点结论：

  • 零样本 + ≤1 次 LLM 调用的结构，没有一个能在 k=16 完成 AppWorld 的 10%（最高 .096）
  • COLT 与 AnyTool 在 AppWorld 上统计不可区分（差 CI [-.081, .029]），但难度剖面不同：COLT .589 normal / .171 challenge，AnyTool .426 / .227——训练式更擅长简单题，导航式更抗难题
  • MCP-Bench 上 COLT 领先所有其他臂（所有 CI 排除 0）：按服务器数 .782 / .467 / .167（1/2/3 服务器）；除 AnyTool (.278) 外没有任何臂完成过三服务器任务
  • recall 与 completeness 脱钩：分解把 AppWorld recall 从 .190 拉到 .417，completeness 只从 .020 到 .035——"召回变好了"是假象

发现三：检索期成本（每查询中位数）

  • BM25 / bge / e5 / GoS / COLT / HYSET：0 次 LLM 调用、0 token、0 秒
  • 分解：1 次调用，221 / 580 token，5.7 / 15.7 秒
  • MCP-Zero：1 次调用，333 / 697 token，4.4 / 12.3 秒
  • AnyTool：31 / 38 次调用，99,739 / 90,479 token，307 / 311 秒（≈5 分钟）
  • COLT 前置要求：同池标注查询 90 条（AppWorld）/ 每折 75 条（MCP-Bench）
  • 全量暴露参照（不计入对比，因不是检索问题）：AppWorld 目录 64,874 token、MCP-Bench 59,278 token——都在上下文内，可行，但代价是每次 Agent 调用都付

发现四：失败模式三分（AppWorld k=16，345 查询）

  • COLT：232 条不完整，首要原因 target 缺失 163 条、未识别前置 69 条；但 58% 的缺失 API 排在 17-50 名（MCP-Bench 上 90%）——这是排序深度问题，加大 k 或用 reranker 就能捞回来
  • AnyTool：241 条不完整，首要原因未识别前置 162 条；317 / 538 个缺失 API 属此类——它找到了请求点名的 API，却不去拿给它供输入的 API 就停了（258/345 个池不足 16 个 API，列表本身太短）
  • 扁平 / 图 / HYSET：首要原因是 target 本身没找到（bge 284/338、GoS 250/312）
  • MCP-Zero 列表止于第 12 名，故 0% 缺失落在 17-50 区间

发现五：依赖形状的影响（按必需集合大小标准化后）

  • 单链 258 条：AnyTool .376 ≈ COLT .372（CI 含 0），其余 ≤.159
  • 混合 87 条：COLT .195、AnyTool .080、其余全 0
  • 集合大小 5-12 区间内标准化后：混合减单链的差，COLT +.132（CI [.049, .217]）、AnyTool −.065（CI [−.153, .019]）——混合形状不惩罚 COLT，但 AnyTool 无证据获益

发现六：下游验证（AppWorld 官方简化 ReAct agent，60 条任务）

  • 暴露 gold 必需 API（A）：46/60 成功；暴露 COLT top16（C）：23/60（McNemar p = 5.6×10⁻⁶）
  • COLT top16 完整的 21 条任务：C 成功 21/21，A 成功 20/21
  • 不完整的 39 条任务：C 只成功 2/39，A 却成功 26/39——差距不能只用任务难度解释
  • 代价转嫁：C 条件下步数中位 32 vs 19，30/60 回合撞上"未暴露 API"错误（A 只 8 次），prompt token 约翻倍（15.1M vs 7.4M）

局限性与未来方向

  • 全部 LLM 步骤用 DeepSeek-V3.2 单模型 → LLM 依赖型结构的 completeness/调用数与"标注数据 vs LLM 调用"的权衡只对该模型成立。作者引 GatewayBench：GPT-5.4→GPT-5.1 会让层级网关任务成功率掉 37.6 分，扁平网关只掉 11.9 分——层级导航对模型能力远比扁平暴露敏感
  • 稠密臂及其衍生臂都用 base 尺寸嵌入（bge-base / e5-base）；更强通用或工具专用嵌入在 ToolRet 上分数更高，所以"10% 天花板"限定于该尺寸编码器
  • 未纳入：全量暴露（非检索问题）、In-N-Out 图检索器（需 gold target 输入，不是查询级检索器）、历史式检索（无公开代码）
  • MCP-Bench 参考集合来自生成器计划，非唯一 gold；MCP 工具不声明 output schema，导致 GoS 确定性边为 0（只能靠 LLM 补 254 条边）

二、创新点分析

  • 评测范式的重定义：把工具检索从"平均命中几个"改为"整套是否齐全"，并给出按目标工具数分层的报告规范。单目标占 55% 的基准会把 completeness 聚合分虚高成 .507，而多目标区制只有 .303——这是方法论级贡献，不是又一个 retriever
  • 首次同台六族：此前只有 Zhang et al. 对比了"检索优先 vs 规划优先"两个范式，本文覆盖扁平/分解/层级/server-then-tool/依赖图/集合级六族，且共享嵌入与 LLM 变量
  • 失败归因框架：target miss / unrecognized prerequisite / cascade 三分，直接把"该修检索第一步"还是"该修排序深度"还是"该修依赖补齐"区分开——这是本文最可移植的部分（对任何工具/技能/API 目录都成立）
  • 成本-完整性二维定位：completeness@16 × 每查询 LLM token 的散点，把"训练一次"与"每查询烧 10 万 token"放在同一坐标系里，让部署决策可计算
  • 下游闭环：21/21 vs 2/39 的强对比 + 步数/错误/token 三重代价测量，把 completeness 从代理指标升级为有因果证据的预测指标

三、归纳总结

  • 单工具评测会选错检索器：bge 在单目标上最好，在多目标上被反超；聚合分不能用来给"需要多工具的 Agent"选检索器
  • 完整性只有两条购买路径：带标注的域内请求（75-90 条即够训练集合级检索器）或每查询几十次 LLM 调用（≈5 分钟）。零样本 + 单次调用的天花板是 10%
  • recall ≠ completeness：把召回从 .19 提到 .42，完整性只从 .02 到 .035——分解/改写类技巧改善的是"多捞到一些"，不是"捞全"
  • 两种成功路线的失败可修：COLT 的漏掉多在 17-50 名（reranker/加预算可救），AnyTool 漏的是前置（依赖补齐可救）——修法不同，不能互换
  • 检索不完整的代价会转嫁到执行期：步数 32 vs 19、prompt token 翻倍、反复撞未暴露 API 错误——省检索成本 = 花执行成本
  • 一句话：多工具请求的正确度量是"集合包含"，不是"平均命中"；而齐套性要么用标注数据买断，要么用查询期 LLM 调用租用，没有免费方案

四、趋势判断

  • 工具检索正从"检索问题"变成"供应链问题"：依赖图（producer-consumer）、参数级边（In-N-Out）、前置补齐成为一等公民。2026 年 Graph-of-Skills / Tool Graph Retriever / In-N-Out 的集中出现，加上本文把 prerequisite 单列为失败主因，说明社区已承认"工具不是孤岛"
  • 检索器分层：小标注 > 大 LLM。COLT 只用 75-90 条域内标注就拿到 .583（MCP-Bench），而 AnyTool 每查询 5 分钟只到 .398——"训一个小集合级检索器"在成本曲线上完胜"查询期让 LLM 导航"。这预示工业落地会走向"每个工具池一个小检索头"，而非通用大模型导航
  • 层级导航的脆弱性被量化：GatewayBench 的 37.6 vs 11.9 分掉幅 + 本文 5 分钟延迟，两件事叠加意味着层级发现只适合离线/长任务（批处理 Agent、夜间流水线），不适合交互式 Agent
  • MCP 生态的结构缺陷暴露：MCP 工具不声明 output schema → 确定性依赖边为 0。若 MCP 协议层补上 output schema/副作用声明，整个依赖图族会立刻可用——这是协议标准比算法更关键的典型案例
  • 评测规范会被迫升级：分层 completeness + 每查询成本 + 失败归因三件套，很可能成为工具检索论文的下一版报告标准（类似 MTEB 的成本列）

五、查询拓展

  • COLT（Qu et al., CIKM 2024, arXiv 2405.16089）：completeness-oriented 工具检索，本文唯一稳定领先的臂——值得追其第二阶段的 collaborative learning 细节
  • In-N-Out（Lee et al., TACL 2026, arXiv 2509.01560）：参数级 API 依赖图数据集，本文 AppWorld 依赖标签的来源，也是"前置补齐"路线的数据基础
  • Graph-of-Skills（arXiv 2604.05333, EMNLP 2026）：massive agent skills 的依赖感知结构检索——与本文的 GoS 臂同源，且已读过相关笔记（技能粒度自适应路由 2610.31461 引用过它）
  • GatewayBench（arXiv 2610.23449）：MCP 网关能力+安全评测，本文引用其"层级网关对模型能力更敏感"的关键数字
  • HYSET（arXiv 2607.25718）：query-conditioned hyperedge 预测的集合级检索，本文只跑简化版，值得看原版执行奖励
  • Tool recommendation for multi-step agents（Partee et al., arXiv 2610.23707）：生产部署的两阶段工具推荐，按 completeness@10 与计费会话成本评估——与本文互补的工业视角
  • Comparative approaches to agent retrieval over large skill libraries（arXiv 2608.06196）：解释为何从嵌入邻域取的图边无法扩展检索半径——本文 GoS 消融的机制解释
  • 待补：附录 A5 的逐尺寸单元格（部分 <10 查询，统计效力弱但可看趋势）

六、关联分析（借鉴点评估）

对 Hermes Agent 的借鉴（本机实测对照）：

  • 我们的现状就是"全量暴露"：实测本机 510 个 skill，name+description 合计 47,951 字符 ≈ 15k token，每次请求都在付。对比本文 AppWorld 目录 64,874 token / MCP-Bench 59,278 token——我们便宜 4 倍，但"每调用都付一遍"的机制完全相同。本文的价值是给出这条路的替代方案及其真实价格
  • 最痛的是 prerequisite 缺口，不是 target 缺口：本文 AppWorld 上 AnyTool 的 162/241 首要失败来自"找到了点名的 API，没拿给它供输入的 API"。Hermes 完全同构——duck-five-stage-standup / squat_rest.py 技能被点名，但 duck-real-robot-deployment 的电压/IMU 前置检查没加载；ONNX 部署被点名，note-md-to-html-toolchain 前置缺失；rl-standing-gate-eval 被点名，duck-launch-safety 静态检查前置缺失。这类失败在日志里表现为"技能用了但步骤漏了"，正是本文定义的 unrecognized prerequisite
  • 失败归因框架可直接搬：任何一次"技能没解决问题"的复盘，先分 target miss（list 里根本没有该技能）/ prerequisite miss（技能在，前置技能没跟）/ ranking depth（技能在第 17 名之后）。三分法比现在笼统的"技能不匹配"精确一个量级
  • COLT 的启示是"标注很便宜"：75-90 条域内查询就够训一个集合级检索器。Hermes 完全可以用历史会话（"用户说 X → 实际加载了哪几个 skill"）当标注，规模远超 90 条——这是把 paper 的配方落到本地的可行路径
  • 成本转嫁数字对 cron 设计有直接含义：检索不完整 → 步数 32 vs 19（+68%）→ token 翻倍。cron job 的失败重试与"技能没读全"正是这种隐性成本，比检索成本贵得多

对 Jetson Orin 边缘部署的借鉴：

  • 本地 Ollama 小模型做工具选择时，"零样本 + 单次调用"的天花板只有 10%——不要指望小模型靠一次检索调用摆平多工具任务，要么给它标注微调（算力够，75-90 条样本量极小），要么走固定的硬编码流水线（cron/脚本化），而不是交给模型现场检索
  • AnyTool 每查询 100k token / 5 分钟的代价在 Jetson 上是不可承受的（本地推理 5 分钟级）——层级导航只适合在云侧用，边缘端应走训练式小检索器（检索期零 LLM 调用）

对量化交易的借鉴：

  • "回测命中率"与"这套信号是否齐全"同构：单因子命中率高 ≠ 完整信号集（技术面+量能+结构阶段）到位。本文的教训是按信号数分层的完整性指标比聚合命中率更能预测实盘结果
  • recall/completeness 脱钩 = 因子数量增加但组合不完整：多加三个因子把 recall 从 .19 提到 .42，但"该有的都有"只有 3.5%——对应到盯盘就是"看到很多信号但缺关键的阶段判读（Wyckoff）"，与用户 1015 的纠偏（只报价格异动不做结构判读 = 失职）机制同源
  • 失败归因三分可移植：交易建议失败先分"标的没选对（target miss）"/"标对但缺前置条件（未识别前置：如破位未看量能）"/"深度不够（排序深度：备选池第 17 名之后）"

八、指南分析

若要在自建 Agent/工具池上复用本文结论，操作要点：

  • 先测分层完整性，别测聚合命中：按"请求需要的工具数"分层报 completeness@k。聚合分会掩盖 3-5 倍差距（.507 vs .303 vs .129）；单目标占多数的池子尤其危险
  • 判天花板：若你的方案是"零样本 + 每查询 1 次 LLM 调用"，把期望值定在 10% 以下，不要用聚合命中率自我安慰
  • 选路线的判据是"有没有 75-90 条域内标注"：有 → 训集合级检索器（检索期零 LLM 调用、零延迟、最高完整性）；没有 → 只能买 LLM 导航（每查询 30-40 次调用、≈5 分钟、且对模型能力敏感），或干脆走硬编码流水线
  • 失败归因决定修法：缺失工具在 17-50 名 → 加 k 或加 reranker；缺失的是前置 → 补依赖边/依赖补齐；target 本身没找到 → 修第一步检索/查询改写。三者修法不可互换，先归因再动手
  • 把执行期成本算进检索决策：不完整检索的隐性账单是步数 +68%、prompt token ≈2x、反复撞权限/未暴露错误。宁可多花检索 token，不要省在执行期
  • 协议缺陷优先补：MCP 工具不声明 output schema → 确定性依赖边直接为 0。工具/技能目录的第一优先级投资是结构化声明输入输出（我们的 SKILL.md requires: 是同一件事），算法优化排在其后
  • 验证门：上线前用"完整集合 → 任务成功"的对照实验（本文 21/21 vs 2/39）确认 completeness 对你这套任务是有效代理指标；若完整集合与不完整集合成功率无差异，说明任务本身不依赖工具齐套，检索投入应下调
