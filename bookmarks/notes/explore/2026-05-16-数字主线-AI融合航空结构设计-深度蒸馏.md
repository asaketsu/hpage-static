## 核心发现一：GenAI Workbench — 多模态工程数据的统一数字主线范式

### 背景

arXiv:2603.00251（Bank & Herber, 2026）提出的 GenAI Workbench 是目前学术界最完整的"AI + 工程系统设计"框架。它不是简单的 LLM 调用 CAD API，而是一套**从非结构化工程数据中提取结构化知识、构建统一数字主线**的方法论。

### 核心架构

GenAI Workbench 的三层架构直接对应数字主线的三个层次：

```
┌─────────────────────────────────────────────────┐
│  Layer 3: AI Application Layer                   │
│  - 需求自动提取与冲突检测                          │
│  - 架构自动生成（从需求→SysML模型）                │
│  - 设计空间探索（参数化搜索）                       │
├─────────────────────────────────────────────────┤
│  Layer 2: Knowledge Graph Layer                   │
│  - DSM（设计结构矩阵）自动构建                     │
│  - 需求→架构→部件→仿真→验证的追溯图谱              │
│  - B-rep 几何与系统图的关联映射                     │
├─────────────────────────────────────────────────┤
│  Layer 1: Data Ingestion Layer                    │
│  - 多模态数据：文档/图纸/3D模型/CAE结果             │
│  - 语义提取：NLP → 结构化需求库                     │
│  - 几何提取：B-rep → 系统图节点                     │
└─────────────────────────────────────────────────┘
```

### 对数字主线的启示

传统数字主线强调的是"数据流的连续性"——从需求工具到 CAD 到 CAE 到 PLM，数据不断裂。GenAI Workbench 的突破在于：

1. **语义层统一**：不同工具的数据格式（Word 文档、STEP 文件、Nastran .f06）通过 LLM 统一为语义图谱。不需要所有工具都支持同一种数据格式。
2. **追溯自动化**：传统追溯靠人工在 DOORS/Jama 中手动建立需求↔测试用例的映射。GenAI 用 LLM 自动提取需求并匹配到设计元素。
3. **变更传播的 AI 预测**：这是最核心的突破。传统数字主线只能告诉你"A 变了会影响 B"（静态追溯链），但 GenAI 可以预测"A 变了后 B 应该怎么改"（动态推荐）。

### 实践案例推演

假设一个航空支架设计场景：

```
需求变更: "支架质量上限从 5kg 调整为 3.5kg"

传统数字主线:
  → 追溯链: 需求 → 结构参数 → FEA模型 → 验证报告
  → 人工判断: 需要重新做拓扑优化
  → 时间: 2-5 个工作日

GenAI Workbench 增强后:
  → AI 自动识别受影响的所有参数（截面尺寸、壁厚、材料等级）
  → AI 自动生成拓扑优化方案（nTop CLI 批量执行）
  → AI 自动提交 FEA 验证（Nastran batch）
  → AI 自动生成验证报告并与原需求对比
  → 时间: 2-5 小时（人工审批环节仍保留）
```

## 核心发现二：MBSE + SysML v2 — 数字主线的结构化骨架

### SysML v2 的关键突破（2025.09 发布）

SysML v2 不仅是建模语言的升级，它从根本上改变了 MBSE 与结构设计的关系：

| SysML v1 的局限 | SysML v2 的突破 | 对结构设计的意义 |
|----------------|----------------|----------------|
| 图形化语法，机器难以解析 | 文本化语法（KerML），可直接程序化处理 | Agent 可自动读取/生成/修改模型 |
| 参数化分析能力弱 | Parametric Diagram 原生支持数学约束 | `质量 = f(密度, 体积)` 直接写入模型 |
| 需求追溯靠人工链接 | Requirements 块原生支持追溯+验证 | 需求→验证用例自动关联 |
| 与 CAE 无标准接口 | Analysis Case 可直接映射仿真参数 | MBSE→FEA 的标准通道 |
| 无不确定性建模 | PSUM 扩展支持概率约束 | `应力 < σ_allow * (1 - CoV * 1.5)` |

### MBSE→结构设计→拓扑优化的标准集成路径

这是目前知识库中识别出的**最大研究空白**：arXiv 搜索 "SysML structural optimization" 返回 0 结果。但基于 SysML v2 的能力，可以构建以下集成路径：

```
Step 1: SysML v2 需求模型
  Requirement Structural_Performance {
    subject = Wing_Rib
    constraint { mass < 5.0 kg }
    constraint { stiffness > 100 N/μm }
    constraint { fatigue_life > 1e6 cycles }
    constraint { manufacturing = additive }
  }

Step 2: 自动映射为优化输入
  - objective: minimize mass
  - constraints: 
      stress < σ_yield / 1.5        // 来自 SysML 约束
      compliance < C_max            // 来自刚度要求
      overhang_angle < 45°          // 来自 AM 制造约束
      min_feature_size > 0.5mm      // 来自 AM 制造约束

Step 3: nTop CLI 自动执行
  ntop automate run --input json_from_sysml.json \
    --notebook wing_rib_optimization.ntop \
    --output results/

Step 4: 结果回写 SysML v2
  - Verification Case: mass=4.2kg ✓, stiffness=112 N/μm ✓
  - 自动生成追溯矩阵（需求→约束→优化结果→验证）
```

### OMG 标准生态的 2026 现状

| 标准 | 版本 | 发布时间 | 成熟度 | 对数字主线的影响 |
|------|------|----------|--------|-----------------|
| SysML v2 | 2.0 | 2025.09 | ★★★☆☆ | 核心建模语言，工具链刚开始落地 |
| UAF 1.3 | 1.3 | 2026.04 | ★★★☆☆ | 统一架构框架，支持 DoDAF/NAF |
| DDS 1.4 | 1.4 | 2015 | ★★★★★ | 成熟的实时数据分发 |
| DDS-SECURITY | 1.2 | 2026.02 | ★★★★☆ | 数字孪生通信安全 |
| PSUM | — | 2024 | ★★☆☆☆ | 不确定性建模，工具支持刚起步 |
| OSLC | — | 持续演进 | ★★★☆☆ | 工具互操作标准 |

**关键判断**：2026 年是 MBSE + 数字主线标准化的"窗口期"——SysML v2 已发布但工具链不成熟，PSUM 刚起步，MBSE→拓扑优化无标准接口。对于开源项目（如 AERIS-10），这是抢占生态位的好时机。

## 核心发现三：AI Agent 作为数字主线的"执行引擎"

### Agent-Computer Interface (ACI) 设计模式

从"航空结构设计AI短期基础设施"笔记中提炼出的 ACI 设计模式，是让 AI Agent 在数字主线上实际工作的关键：

```
┌──────────────────────────────────────────────────┐
│              AI Agent (LLM 推理层)                 │
│  - 需求理解 → 参数提取 → 任务编排 → 结果校验       │
├──────────────────────────────────────────────────┤
│              ACI (工具接口层)                       │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  │
│  │ Nastran IF │  │ CATIA IF   │  │ nTop IF    │  │
│  │ .bdf/.f06  │  │ COM/API    │  │ JSON/CLI   │  │
│  │ batch submit│ │ param ext  │  │ auto run   │  │
│  ├────────────┤  ├────────────┤  ├────────────┤  │
│  │ 材料库 API │  │ 规范库 RAG │  │ 截面库 API │  │
│  │ 查询/校验  │  │ 语义检索   │  │ 计算查表   │  │
│  └────────────┘  └────────────┘  └────────────┘  │
├──────────────────────────────────────────────────┤
│              数字主线 (数据层)                      │
│  PLM + 图数据库(Neo4j) + 时序库 + 文件系统         │
│  需求 → 架构 → 结构 → 仿真 → 制造 → 服役          │
└──────────────────────────────────────────────────┘
```

### FEA 自动化流水线的现实挑战

航空结构 FEA 是整个数字主线中最耗时的环节，直接决定了 Agent 的迭代速度：

| 分析类型 | 单次耗时 | Agent 可行性 | 瓶颈 |
|---------|---------|-------------|------|
| 线性静力 | 30s-5min | ✅ 可行 | 批量提交+解析 |
| 屈曲分析 | 2-15min | ✅ 可行 | 需要任务队列 |
| 非线性分析 | 30min-数小时 | ⚠️ 受限 | 等待时间过长 |
| 疲劳/损伤容限 | 小时级 | ❌ 不现实 | 需要异步模式 |

**设计原则**：Agent 的"思考时间"主要花在等 FEA 上，不是 LLM 推理上。因此：
- 任务队列设计是核心（支持 10-20 次并发 FEA 调用）
- 超时控制和失败重试必须有
- 非线性/疲劳分析走异步模式（Agent 提交后做别的事，结果回来再续）

### text-to-cad 的启示：代码即几何 + 句柄引用

earthtojake 的 text-to-cad 项目为数字主线提供了一个关键思路：**AI 生成的不是二进制 CAD 文件，而是可读、可调试、可局部修改的 Python 代码**。

这对数字主线的意义：
1. **可追溯性**：每次设计变更都是一次代码 diff，天然有版本历史
2. **可审计性**：代码可以直接阅读审查，不像黑箱操作
3. **可复用性**：参数化模板可以跨项目复用
4. **Agent 友好**：LLM 生成代码比操作 GUI 容易得多

`@cad[flange]` 句柄引用机制尤其值得借鉴——为数字主线中的每个工程对象分配全局唯一标识，支持：
- "把 @struct[wing_rib_03] 的壁厚改为 2mm" → 精准定位、精准修改
- 变更传播自动追踪：修改 @struct[wing_rib_03] → 自动标记依赖它的下游分析为"需更新"

## 核心发现四：数字孪生 + 数字主线的融合 — 从"静态映射"到"AI 自主决策"

### 2026 范式转变

基于已有笔记的综合分析，2026 年数字孪生+数字主线正在经历关键范式转变：

| 维度 | 过去（2024 前） | 现在（2026） | 差异 |
|------|---------------|-------------|------|
| 孪生体的角色 | "可视化大屏" — 被动显示 | "AI Agent 的推理沙箱" — 主动决策 | 从工具到伙伴 |
| 数据流方向 | 单向：物理→数字 | 双向：数字→控制物理 | 闭环控制 |
| 建模速度 | 手工建模，周/月级 | 3DGS/NeRF 自动重建，小时级 | 2 个数量级提升 |
| 决策主体 | 人看大屏→人做决策 | AI 在孪生体中自主推理→人审批 | 效率 10x |

### 闭环数字孪生（Closed-loop DT）在航空结构中的应用

Gartner 2026 预测的核心概念，映射到航空结构设计：

```
设计阶段:
  数字主线提供: 需求→设计→分析→验证的完整追溯
  数字孪生提供: 设计方案的虚拟验证环境
  AI Agent: 自动探索设计空间、推荐最优方案

制造阶段:
  数字主线提供: 设计→工艺→制造参数的映射
  数字孪生提供: 制造过程仿真（AM 模拟）
  AI Agent: 实时监控偏差、自动调整工艺参数

服役阶段:
  数字主线提供: 设计基准→制造记录→服役状态的连续性
  数字孪生提供: 结构健康监测的实时映射
  AI Agent: 预测性维护（预测→行动→验证→学习）
```

### DDS 协议在数字孪生通信中的关键角色

DDS（Data Distribution Service）作为 OMG 标准，为航空结构数字孪生提供：
- **实时数据分发**：传感器→模型→控制器的低延迟通信
- **QoS 策略**：可靠性、时效性、持久性可配置
- **安全通信**：DDS-SECURITY 1.2（2026.02）提供加密和认证
- **边缘计算**：DDS-XRCE 支持资源受限设备（与 ESP32/Jetson 项目直接相关）

## 实践启发

### 启发 1：数字主线的 MVP 不是全生命周期，而是"变更影响分析"

从已有笔记提炼的最务实路径：不要一上来就搞"从需求到退役"的全生命周期数字主线。先聚焦**变更影响分析**这一个场景：

- 输入：一个设计变更请求（ECR）
- 输出：受影响的部件清单 + 需要重做的分析清单 + 预估工时
- 价值：变更评估时间 -60%（图查询自动传播）

实现路径：Neo4j 图数据库 + SysML v2 的追溯模型 + 简单的变更传播算法。

### 启发 2：ACI 描述要像"给新同事写操作手册"

每个工具接口的标准化描述格式：

```yaml
name: run_nastran_analysis
description: 提交 NASTRAN 线性静力分析
input:
  inp_file: str    # .bdf 输入文件路径
  scratch_dir: str # 临时文件目录
  output_format: enum  # 'f06' | 'op2'
output:
  status: enum     # 'success' | 'error'
  stress_results: list[dict]
  displacement: dict
  duration_ms: int
constraints:
  - 单模型运行时间上限 10min
  - 并发数不超过 4
  - 失败自动重试 2 次
```

### 启发 3：历史案例库是 ROI 最高的数据源

从已完成项目中抽取的"输入参数→分析过程→结论→评审意见"数据集，同时服务于：
- RAG 检索（相似工况的历史方案推荐）
- Agent Eval Set（金标准评估集）
- 新人培训（可查询的知识库）

**短期建议**：先聚焦 50 个高质量案例 > 500 个低质量案例。

### 启发 4：MBSE + 拓扑优化的标准接口是蓝海

arXiv 搜索 "SysML structural optimization" 返回 0 结果。这意味着：
- 学术界尚未形成系统性方法
- 谁先做出来谁就定义了标准
- 与 nTop CLI 的集成路径已经清晰（见上文 Step 1-4）
- 对 AERIS-10 / struct-gen 项目是差异化优势
