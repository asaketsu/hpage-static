## 一、内容整理

### 1.1 核心问题与研究动机

- **问题本质**：工具增强 LLM Agent 依赖不可信的运行时 Observation（网页、邮件、文档、API 返回），当工具输出不再只是"提供数据"而开始"指定具体动作"时，它们实质上变成了 **commands（命令）**，可以驱动超出用户意图的真实副作用（发消息、改对象、提交交易）。
- **结构性矛盾的定位**：现有防御陷入"安全-实用性"拉锯——收紧外部内容影响能提高安全，但开放任务本身需要运行时反馈来实例化后续动作（如动态获取订单号后才能继续）。
- **根因诊断（本文最锋利的一刀）**：这个矛盾源于**把"动作诱导（action induction）"与"执行授权（execution authorization）"混为一谈**。外部内容能影响候选调用的形成 ≠ 这个调用拥有执行权限。
- **形式化定义**：
  - 违规定义：`Violation_t ≜ Execute(c_t) ∧ ¬Permitted_U(c_t | X_<t)` —— 关键在"是否越过真实工具执行边界"，而非"模型是否读了外部内容"。
  - 核心原则：`Induced(c_t, O_i) ⇏ Permitted_U(c_t | X_<t)` —— 被诱导不蕴含被授权。

### 1.2 SARA 方法论（四模块）

**总体架构**：观测侧 + 执行侧两阶段，围绕三份运行时信息（用户授权根 K、持久动作来源 F_t、审计执行证据 H_t）运转。

```
用户请求 U ──Contract()──> 授权根 K（任务级权限上界）
                                │
工具输出 O_t ──Probe(上下文隔离)──> STATIC / ACTIONABLE
                                │ ACTIONABLE 时轨迹 CLEAN→EXPOSED
                                ▼
候选调用 c_t+1 ──授权审查──> 放行 / 拦截
   依据：K（用户授权）+ F_t（动作来源）+ H_t（审计证据）
   门禁：G_t(目标支持) ∧ C_t(执行链支持) ∧ A_t(参数支持)
```

- **模块 1：授权根构建（Authorization Root, §4.2）**
  - 从用户原始请求 U 提取任务级授权契约 `K = Contract(U)`，每条契约项 `k_j = (e_j, operation_j, scope_j, Σ_j)`：效果类型 / 允许操作 / 作用对象范围 / 用户显式提供的静态参数。
  - K 是执行决策的**独立权限根**：运行时信息只能实例化已有权限，**不能创建新权限**。
- **模块 2：上下文隔离动作探针（Action Probe, §4.3）**
  - 探针不判断"是否恶意"，只问一个问题：这条 Observation 脱离用户目标约束后，**是否足以独立促使模型实例化某个具体工具行为**。
  - 输出三元组 `(z_t, Q_t, M_t)`：STATIC/ACTIONABLE 判定、工具级动作足迹、参数来源锚点 `m = (τ, p, norm(v))`（工具名 + 参数路径 + 归一化值）。
  - 关键设计：**上下文隔离**——探针看不到用户目标，避免被任务语境"洗白"。
- **模块 3：持久来源保留（Persistent Provenance Retention, §4.3）**
  - 一旦 ACTIONABLE，轨迹进入 EXPOSED 状态，动作足迹与参数锚点**跨步骤持久保留**为活跃动作来源 F_t，激活持续授权审查。
  - EXPOSED ≠ 攻击判定，而是"持续性差异化审查义务"。
- **模块 4：执行边界证据驱动授权（§4.4）+ 无历史提升（NHP）**
  - 触发分级：EXPOSED 后，有真实副作用的调用全部走完整审查；查询/读类仅在"与探针足迹工具重叠 且 参数无法从用户请求直接判定"时升级审查；其余走快速路径（结果仅作 DATA_ONLY 证据）。
  - 审计执行证据 H_t：开放任务的动态对象（如订单号）只能通过运行时交互获得，授权必须用"已被允许且实际执行成功的调用"建立的正向证据。
  - **No-History-Promotion**：禁止"历史重复出现"本身把动作来源提升为执行权限——防止诱导动作在多步中反复出现后"洗白"成合法权限（这是对 Binding Drift 类漂移传播的直接防御）。

### 1.3 关键实验结果与数据

- **基准与规模**：AgentDojo（92 良性任务 + 3528 攻击实例）+ AgentDyn（141 良性任务 + 5202 攻击实例）；4 种 IPI 攻击形态（ignore_previous / system_message / important_instructions / tool_knowledge）。
- **主实验（Table 1，GPT-4o-mini / Gemini-2.5-Flash-Lite 双主干）**：
  - GPT-4o-mini：AgentDojo ASR 15.79%→**0.06%**，AgentDyn 16.07%→**0.17%**
  - Gemini-2.5-Flash-Lite：AgentDojo 33.28%→**0.62%**，AgentDyn 30.91%→**0.63%**
  - 无攻击效用（BU）66.67 / 攻击下效用（UA）63.44，均不低于 Agent-only 基线（72.46/56.01 的量级），远优于 CaMeL（BU 40.94 的重度实用损失）
- **跨主干一致性（Table 2）**：Llama3.1-8B / Llama3.3-70B / Qwen2.5-14B / Qwen3-32B 全部 ASR 大降（8/8 组合），最差残差 1.75%（Llama3.1-8B），其余 <0.3%。
- **消融（Table 3，证明四模块缺一不可）**：
  - 去 AIT（动作诱导追踪）：ASR 0.06→3.37 / 0.17→3.02 —— **贡献最大**
  - 去 PSG（参数支持门禁）：ASR →2.49 / 2.73
  - 去 AE（审计证据）：ASR 几乎不变（0.00/0.12）但 UA 崩塌（63.44→53.49 / 54.92→42.10）—— AE 是**实用性**支柱
  - 去 NHP（无历史提升）：ASR →0.65 / 0.75
- **成本（Table 4）**：AgentDojo 总输入 25.86K tokens（Agent-only 的 1.91×），低于 IPIGuard（45.22K）和 CaMeL 的 Guard 开销结构；换来的是更优的"安全-效用-成本"运营点。
- **定位诚实**：SARA 是运行时授权机制而非形式化安全保证；语义判断仍有误报/漏报，恢复依赖宿主 Agent 的重规划能力。

## 二、查询拓展

### 2.1 间接提示注入（IPI）
通过网页/邮件/文档等第三方资源嵌入操作语义，劫持 Agent 已有工具权限的攻击。与直接注入不同，IPI 的入口是 Agent 正常读取的数据流，因此"过滤输入"与"保留运行时适应性"天然冲突——本文正是对这一冲突的结构性回应。

### 2.2 AgentDojo 与 AgentDyn
- AgentDojo：可执行 IPI 评估基准，四个套件（Banking/Slack/Travel/Workspace），把 IPI 后果从"文本污染"推到"真实工具执行"。
- AgentDyn：动态环境基准（Shopping/GitHub/DailyLife），强调动态规划、跨应用交互、第三方环境反馈——合法任务本身依赖运行时信息决定后续行为，是检验"防御不误伤动态任务"的试金石。

### 2.3 对比防御谱系（从输入控制到动作归因）
- **输入/模型侧**：StruQ（结构化通道分离）、Instruction Hierarchy（指令优先级）、SecAlign（注入鲁棒训练）——强化信任边界。
- **动作归因侧**：CaMeL（能力控制，安全但实用性损失大，BU 40.94）、IPIGuard、MELON、AttriGuard、ClawGuard、AIRGuard。
- SARA 的差异化：**不切断 Observation 对任务实例化的参与**（保留动态适应性），只切断"诱导→权限"的等价链。

## 三、归纳总结

### 3.1 核心创新点提炼

- **概念切割**：首次把"动作诱导"与"执行授权"作为两个独立运行时角色正式分离，并给出形式化定义（Induced ⇏ Permitted）。
- **溯源持久化**：动作来源不是一次性判断，而是跨步骤持久跟踪，防止多步执行中的"来源洗白"。
- **分级审查**：EXPOSED 后副作用调用全审、读类条件升级、其余快速路径——安全收益不靠全局阻塞换取。
- **正向证据授权**：用"已授权且成功执行的调用"作为动态对象合法性的唯一来源，替代对 Observation 的信任。

### 3.2 与相关工作的本质区别
- vs CaMeL：CaMeL 靠收紧信息流（非可信数据不能流向敏感工具），实用损失大；SARA 允许数据参与实例化，只在权限判定处拦截。
- vs 纯检测器（PI Detector）：检测器把 BU 打到 44.20（大量误杀）；SARA 探针只标记"动作诱导语义"不判恶意，误杀面小一个量级。
- vs Binding Drift 研究：Binding Drift 形式化"实体绑定漂移/传播"；SARA 的 NHP 机制是对"权限漂移"的工程化解法——同一谱系，一个诊断、一个治疗。

## 四、趋势判断

### 趋势1：Agent 安全防线从"输入过滤"迁移到"执行边界授权"
依据：SARA 消融显示输入侧探针（AIT）贡献最大安全收益，且 CaMeL/PI Detector 等输入收紧型方案全部付出显著实用性代价；问题定义本身（Violation 在执行边界成立）就宣告了输入侧防御的先天不足。

### 趋势2：来源追踪（provenance）成为 Agent 运行时标配
依据：SARA 的跨步持久来源、SlotGuard 的类型化槽位溯源、execution-provenance 笔记、EVOMAL 的安全边界迁移——2026 下半年多篇工作不约而同把"值从哪来"作为运行时决策输入，与零信任架构的"持续验证"原则合流。

### 趋势3：安全机制的成本披露将成为论文标配
依据：SARA 用专节（RQ4）披露 1.91× 输入 token 开销并与 7 个基线对比成本结构；此前 Cost-Aware Security Agent Eval（2607.15263）已把"防御成本"提升为一级评估维度。

### 趋势4：开放权重小模型的 Agent 安全是剩余短板
依据：Table 2 中 Llama3.1-8B 是唯一残差 >1% 的主干，其余主干 <0.3%——8B 级模型的语义判断能力是防御机制效用上限的瓶颈，边缘部署（Jetson 级）需特别关注。

## 五、关联分析

### 5.1 与 SlotGuard（2607.17147，2026-07-21 笔记）的关联
SlotGuard 处理转录本中"秘密值泄露"，SARA 处理"外部内容诱导动作"——两者同属 Agent I/O 边界治理：一个管出（脱敏），一个管进（授权）。SARA 的参数来源锚点 `m=(τ,p,norm(v))` 与 SlotGuard 的 HMAC 类型化槽位可组合：槽位标记数据敏感级，锚点标记动作来源，形成双向门禁。

### 5.2 与 BindingDrift（2607.18316，2026-07-23 笔记）的关联
Binding Drift 揭示"锁得越严漂移越多"的悖论（3-8.5×），SARA 的 NHP 正是对"漂移洗白"路径的封堵：历史中出现过的诱导动作永远不会自动获得权限。两者结合提示：交叉验证（Binding Drift 的廉价方案）+ 权限不提升（SARA）是双保险。

### 5.3 与 MCP 工具描述注入笔记（2026-08-21）及 EuclidMCP（2026-07-26）的关联
MCP tool-description-inj 场景中，工具 schema 本身就是注入面。SARA 威胁模型明确假设"工具 schema 可信"，这是它的边界——MCP 注册时的 schema 消毒（注册门禁）与 SARA 的运行时授权是互补层，不是替代关系。

### 5.4 与 Hermes Agent 的直接映射
Hermes Gateway 的工具调用链（LLM→tool_call→executor）正是 SARA 定义的"执行边界"。当前 Hermes 有确认门禁（rm -rf 等二次确认）但无来源追踪——无法区分"参数值来自用户消息"还是"来自上一轮 web_extract 的被注入内容"。SARA 的探针+锚点机制恰好补这块。

## 七、拓展应用推荐

### 7.1 对 Hermes Agent 的借鉴点（按优先级）

- **P0｜参数来源锚点**：为 tool_call 参数记录来源（user-message / tool-output / agent-generated），高风险动作（文件删除、外部发送、支付类）执行前检查"敏感参数是否全部来自 user-message 锚点"。工作量：Gateway 中间件 ~200 行，复用 SARA 的 `(τ,p,norm(v))` 三元组结构。
- **P0｜无历史提升规则**：写入 agent-security-governance skill 铁律——"同一动作在历史中出现过 N 次"永远不能作为放行依据；权限只能来自用户原始指令的契约解析。工作量：规则级，半天。
- **P1｜上下文隔离探针**：对 web_extract/terminal 输出中的"指令性内容"（ignore previous / system message 伪装）做独立小模型/正则检测，命中即给会话打 EXPOSED 标记并激活后续副作用工具的加强审查。工作量：正则版 1 天，模型版需评估延迟预算。
- **P2｜授权契约解析**：任务开始时从用户消息提取 `(效果类型, 操作, 范围)` 契约，作为 cron/长任务会话的权限白名单。适配 Hermes 的 Strict Authorization 层。

### 7.2 对量化交易系统的借鉴点
- 交易指令参数（代码、价格、手数）的来源锚点：策略引擎输出 vs 行情数据携带 vs 新闻文本提取——行情/新闻是不可信 Observation，其诱导的交易参数必须过授权审查。与 agent-trading-safety 的凭证隔离层叠加。

### 7.3 对 Jetson 边缘部署的借鉴点
- 8B 级主干是 SARA 效用瓶颈（残差 1.75%），边缘 Agent 的探针建议用正则+小分类器而非 LLM 判定，规避模型能力下限。

## 八、指南分析

### 8.1 落地 SARA 式防御的工程清单

1. **先划边界**：列出系统的"真实执行边界"（哪些 tool_call 有外部副作用），只有过边界的调用才需要授权审查——审查面最小化是实用性前提。
2. **授权根独立**：用户消息进会话时即解析契约 K，K 不受后续任何 Observation 修改——权限的单向性是整个机制的根。
3. **探针只标记不判定**：检测"动作诱导语义"（低误杀）而非"恶意内容"（高误杀）；PI Detector 的 BU 崩塌（44.20）就是反面教材。
4. **分级审查**：EXPOSED 后副作用全审 + 读类条件升级 + 其余快速路径；DATA_ONLY 证据不参与权限判定。
5. **正向证据闭环**：动态对象（ID、订单号）合法性只能来自"已授权成功执行"的调用链，不能用"Observation 里出现过"替代。
6. **成本预算**：预留 ~2× 输入 token 给守卫层；探针调用与主调用分离计费，避免延迟叠加。
