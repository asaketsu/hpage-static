# 本地模型部署：Gemma 4 31B 大模型本地跑

> 日期：2026-07-27 | 类型：auto-explore | 来源：Unsloth 官方文档 + Reddit r/LocalLLaMA KL散度基准 + HuggingFace API

## 摘要

Google DeepMind 发布 Gemma 4 开源模型家族（Apache-2.0），旗舰 **31B Dense** 模型支持 256K 上下文、多模态（文本+图像）、混合思考模式。本地部署推荐 **Q4_K_M GGUF 量化**（~18GB），可通过 llama.cpp / Ollama / Unsloth Studio 运行。关键发现：Gemma 4 31B 的量化误差特性异常——即使 Q8_0 在长文档上 KL 散度也达 0.45，远高于其他模型，源于滑窗注意力架构。对于 16GB 统一内存设备（如 Jetson Orin Nano），推荐改用 26B-A4B MoE（4B active）或 12B 版本。

## 关键发现

### 1. 模型家族与硬件需求（总内存 = RAM + VRAM）

| 变体 | 架构 | 上下文 | 4-bit | 8-bit | FP16 |
|------|------|--------|-------|-------|------|
| E2B | Dense + PLE | 128K | 4GB | 5-8GB | 10GB |
| E4B | Dense + PLE | 128K | 5.5-6GB | 9-12GB | 16GB |
| 12B Unified | Dense（多模态） | 256K | 7-8GB | 13-14GB | 25GB |
| 26B-A4B | MoE（4B active） | 256K | 16-18GB | 28-30GB | 52GB |
| **31B** | **Dense** | **256K** | **17-20GB** | **34-38GB** | **62GB** |

- 31B 是目前最强 Gemma 4 模型，质量最高但推理较慢
- 26B-A4B MoE 是速度/质量最佳平衡点（仅 4B 激活参数，比 31B 快）
- **QAT 变体**可将内存降低约 3 倍（质量保持）
- **MTP（Multi-Token Prediction）**实现 1.4-2.2x 更快推理，无精度损失

### 2. 量化等级选择（GGUF）

- **Q4_K_M** — 大多数用户最佳选择，日常编码/写作/Q&A 与 FP16 差异极小
- **Q5_K_M** — 有额外显存且需要更好复杂推理质量时选择
- **Q8_0** — 近原始质量，但相对 Q5 提升边际
- **IQ4_XS** — 最小可用格式，测试或差 1-2GB 显存时用
- **避免 Q3/Q2** — 质量下降过陡

### 3. ⚠️ 关键架构陷阱：量化误差累积（Reddit KL散度基准）

oobabooga4 对 Gemma 4 31B 各量化等级做了 KL 散度排名测试，发现**异常结果**：

- 即使 **Q8_0** 在长文档上 KL 也达 **0.45**，非拉丁文字达 **0.24**
- Q8_0 → Q5_K_S 各类别 KL 约翻倍，科学和工具使用保持最低（0.07/0.08）
- 对比其他模型 Q4_K_M 通常 KL < 0.1，Gemma 4 31B Q4_K_M KL 高达 ~0.5

**根因**：Gemma 4 部分层使用**滑窗注意力（sliding window attention）**，且最后几层复用同一 KV cache，导致低精度下误差沿上下文长度累积。

**启示**：
- 传统「Q8 = 几乎无损」假设对 Gemma 4 31B **不成立**
- 中文/非英文场景量化损失更大（imatrix 偏向英文+短上下文）
- 对质量敏感的任务，建议至少 Q6_K 或考虑 26B-A4B 的更高量化等级

### 4. Thinking 模式控制

- 启用：在 system prompt 开头加 `<|think|>` token
- 禁用：`--chat-template-kwargs '{"enable_thinking":false}'`（用 llama-server 而非 llama-cli）
- 多轮对话铁律：**只保留最终可见答案进历史**，不把 thought blocks 喂回下一轮
- 推理参数：temperature=1.0, top_p=0.95, top_k=64（Google 默认）

### 5. 三种运行方式

**llama.cpp（最直接，OpenAI 兼容 API）：**
```bash
./build/bin/llama-server \
  -m ./models/gemma-4-31b-it-Q4_K_M.gguf \
  -ngl 999 -c 8192 \
  --host 0.0.0.0 --port 8080
```

**Ollama（最简单）：**
```bash
ollama run gemma4:31b
# 或自定义 GGUF → Modelfile → ollama create
```

**Unsloth Studio（GUI，支持微调）：**
- MacOS/Windows/Linux 统一 Web UI
- 自愈工具调用 + Web 搜索 + 代码执行
- 2x 更快微调，70% 更省显存

## 对工作的价值

1. **Jetson Orin Nano（16GB 统一内存）适配性评估**：
   - 31B 4-bit 需 17-20GB → **超出**，partial RAM/disk offload 可跑但很慢
   - **推荐 26B-A4B MoE Q4_K_M**（16-18GB，4B active，速度更快）
   - 或 **12B Unified Q4_K_M**（7-8GB，含多模态，最轻松）

2. **替代云端 API**：31B 本地跑通后可替代部分 GLM-5.1/DeepSeek 调用，零成本、隐私安全、无限速

3. **量化选型决策**：鉴于 Gemma 4 滑窗注意力导致的误差累积，**中文/长上下文任务应选 Q6_K 以上**，不要盲信「Q4 够用」通用建议

4. **多模态能力**：12B/26B-A4B/31B 均支持图像输入，可用于本地视觉问答、文档理解，配合现有 F5-TTS/Whisper 可构建全本地多模态管道
