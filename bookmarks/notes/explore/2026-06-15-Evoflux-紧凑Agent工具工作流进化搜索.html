摘要

紧凑型语言模型（1.5B–4B）在成本、延迟和部署风险上具有显著优势，但面对 MCP 式工具使用时表现极差——执行可行性仅约 3%。Evoflux 提出了一种推理时进化搜索方法，将紧凑 Agent 的工具使用重新定义为可执行工作流修复（executable workflow repair），而非一次性函数调用。在 MCP-Bench（250 个工具、live MCP 服务器）上，Evoflux 将执行可行性从 ~3% 提升至 17–24%，而相同数据上的 SFT 和 SFT+DPO 仅能持平甚至崩溃到低于 zero-shot 基线。

核心洞察：在教师轨迹预算稀缺时，执行驱动的搜索比权重更新更可靠。

核心问题与研究动机

问题定义

MCP（Model Context Protocol）风格的工具使用远比"孤立的函数调用"复杂：

  1. 工具发现：从 live catalog 中动态发现和解析工具
  2. Schema 满足：匹配参数 schema、类型约束
  3. 依赖追踪：跨中间输出保留依赖关系（步骤 B 的输入来自步骤 A 的输出）
  4. 执行证据落地：最终响应必须基于真实执行结果

现有方案的失败模式

小型 planner 生成的"看起来合理"的工作流图，在实际执行中会遇到四类失败：

  • 工具解析失败：工具名称/路径在 catalog 中不存在或已变更
  • 参数验证失败：类型不匹配、必填参数缺失、值域越界
  • 依赖追踪失败：跨步骤的数据流断裂，中间结果丢失
  • 执行失败：工具本身运行出错、超时、返回异常

关键论点

小语料蒸馏（small-corpus distillation）无法有效解决上述问题。

几百条教师轨迹能教会工作流的格式，但极少覆盖恢复行为（recovery behavior）——即当计划在变化的工具目录上失败时的修复能力。这是 Evoflux 要解决的核心矛盾。

方法论

整体架构

Evoflux 将工具使用建模为类型化工作流图（typed workflow graph）上的搜索问题：

Query → Planner LLM → 初始工作流图 → 进化搜索循环 → 最优可行工作流 → 执行 → 结果
                         ↑                                    ↓
                         └────────── 执行反馈 ←──────────────┘

进化搜索的五个核心机制

1. 结构化编辑（Structured Edits）

对工作流图施加有类型的编辑操作，而非随机变异。从源码分析，编辑操作封装在 action.e 字段中：

{
  "op": "...",       // 编辑操作类型
  "args": {...}      // 编辑参数
}

编辑操作直接作用于类型化图结构（节点=工具调用，边=数据依赖），保证变异后的图仍然合法。

2. 执行反馈（Execution Feedback）

每个候选工作流都会被真实执行（而非模拟评分）。执行结果包含完整的结构化日志：

{
  "ok": true/false,
  "violation": "错误描述或null",
  "final_output": {...},
  "logs": [
    {"node_id": "...", "kind": "...", "tool": "...",
     "ok": true, "error_type": null, "latency_ms": 42, "output": {...}}
  ]
}

日志中的失败节点直接指导下一轮编辑——知道哪个步骤失败、为什么失败，进化才能定向修复。

3. 自适应强度（Adaptive Intensity）

进化循环的变异强度根据执行反馈自适应调整。当候选工作流接近可行（仅个别节点失败）时，减少变异幅度进行微调；当整体结构偏离时，增大变异幅度进行重构。

4. 元引导重设计（Meta-Guided Redesign）

当多轮编辑仍无法修复时，触发元级别的整体重设计——planner LLM 重新审视任务结构和工具目录，生成全新的工作流骨架，而非在失败候选上继续修补。

5. 多样性剪枝（Diversity Pruning）

维护种群的多样性，避免进化陷入局部最优。种群上限 K=15，通过多样性度量定期剔除过于相似的候选。

关键超参数（源码提取）

  • B = 15：进化预算（每个 query 的迭代次数）
  • K = 15：种群上限（最大候选数量）
  • fb-repeats = 4：反馈小批量重复次数
  • alpha = 0.05：LCB（Lower Confidence Bound）置信参数
  • max-steps = 25：每次执行的最大工具调用数
  • plan-retries = 10：执行失败时的最大重新规划次数

竞争方法对比

论文将 Evoflux 与三类基线进行对比：

  • Zero-shot：planner 直接生成工作流，不经过进化
  • SFT / SFT+DPO：用 Evoflux 搜索挖掘的轨迹做微调
  • ReAct：传统的 Thought-Action-Observation 循环

评估平台：MCP-Bench

  • 来源：Accenture 的 MCP-Bench
  • 规模：250 个工具，live MCP 服务器
  • 复杂度分级：single（单服务器）、2server、3server、all
  • 评估指标：执行可行性（execution feasibility）

关键实验结果

主要结果

  • Zero-shot 基线：执行可行性 ~3%（紧凑模型几乎无法可靠执行 MCP 工具工作流）
  • Evoflux：执行可行性提升至 17–24%（5–8 倍提升）
  • SFT / SFT+DPO：仅能持平、低于基线，甚至崩溃到 zero-shot 以下
  • ReAct：可达更高峰值，但方差大、token 成本高

关键发现

  1. 搜索优于微调（在稀缺预算下）：相同数据上，搜索过程的迁移效果远超权重更新
  2. 小语料微调的隐藏风险：SFT+DPO 在小语料上不仅不提升，反而可能损害 zero-shot 能力（崩溃现象）
  3. ReAct 的高方差问题：虽然能达到更高峰值，但不稳定性使其在生产环境中不可靠
  4. 执行驱动是关键：进化搜索的反馈来自真实执行，而非模拟评分

模型支持

从源码 README 分析，支持多种推理后端：
- vLLM 本地推理：Qwen2.5-7B-Instruct（planner）+ gpt-oss-20b（judge）
- OpenRouter：API 推理
- AWS Bedrock：云端推理
- Ollama / LMStudio：轻量本地推理

创新点分析

1. 问题重构：从"函数调用"到"工作流修复"

最重要的贡献是问题重构。传统方法将工具使用视为"一次性函数调用"问题（生成 → 执行 → 完成），而 Evoflux 将其重构为"可执行工作流修复"问题——初始计划可以失败，进化搜索在执行反馈指导下逐步修复。

2. 进化搜索 vs 权重更新的实证对比

论文提供了一个清晰的实证：在教师轨迹稀缺时，投资于推理时搜索比投资于权重微调更划算。这对工业界的资源分配策略有直接指导意义。

3. 类型化工作流图

将工具调用建模为有类型的 DAG（有向无环图），而非自然语言描述。这使得编辑操作可以精确作用于图结构，保证类型安全。

4. 无需权重更新

Evoflux 完全在推理时运行，不修改模型权重。这意味着：
- 对任何 planner 模型即插即用
- 不会损害模型的已有能力
- 工具目录变更时无需重训练

局限性与未来方向

明确的局限性

  1. 绝对值仍然偏低：从 3% 提升到 17–24%，意味着仍有 76–83% 的任务无法完成。紧凑模型在复杂 MCP 工具使用上的能力天花板仍然很低
  2. 延迟开销：进化搜索需要多次执行工作流，每个 query 的 B=15 次迭代意味着显著的计算开销。对于实时交互场景可能不可接受
  3. 仅验证 MCP-Bench：单基准评估，泛化性待验证
  4. Judge 模型依赖：需要独立的 judge 模型评分，引入了额外的推理成本和潜在偏差

潜在的未来方向

  1. 与大模型协同：进化搜索发现的修复模式可以用于蒸馏到小模型，形成"搜索→蒸馏→搜索"的迭代提升闭环
  2. 自适应预算分配：根据任务难度动态调整进化预算 B，简单任务少搜索、复杂任务多搜索
  3. 缓存与增量更新：缓存已验证的工作流模式，当工具目录部分变更时做增量修复而非全量重新搜索
  4. 多 Agent 并行进化：多个 worker 并行探索不同的变异方向，加速搜索收敛

借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

🔨 P0：工作流修复思维模式 → Hermes Agent 错误恢复

现状：Hermes Agent 在工具调用失败时主要依赖"自动重试 + 错误信息回传"的简单策略。
借鉴：Evoflux 的"执行反馈→结构化编辑→重新执行"循环可以直接迁移。当工具调用链失败时，不只是重试同一调用，而是根据执行日志中的错误类型，对工作流图做有类型的编辑修复。
估算工作量：2-3 天，实现一个轻量的 workflow repair hook。

🔨 P1：进化搜索 → Skill 链组合优化

现状：Hermes Agent 的 skill 链组合目前依赖人工编写和 LLM 一次性决策。
借鉴：对于复杂的多步任务，可以用进化搜索探索不同的 skill 组合顺序，用执行结果作为适应度函数。
估算工作量：1 周，需要设计 skill 组合的图表示和编辑操作。

⚠️ P2：紧凑模型 + MCP 工具 → Jetson 边缘部署

现状：Jetson Orin 上运行的小模型在工具使用时成功率低。
借鉴：Evoflux 的方法可直接应用于 Jetson 上的紧凑模型（Qwen2.5-3B/7B），通过推理时搜索提升工具使用可靠性。
关键障碍：Jetson 的算力限制使得 B=15 次迭代的延迟可能过高。需要做预算压缩（B=3-5）或异步并行。

❌ P3：量化交易场景暂不适用

量化交易的工具链相对固定（行情API、下单API、风控API），工具目录不频繁变更，不需要动态发现和进化修复。
