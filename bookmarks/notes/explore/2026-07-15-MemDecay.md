# MemDecay：面向 LLM Agent 的区域感知 KV Cache 驱逐策略

## 元数据

- **标题**: MemDecay: Region-Aware KV Cache Eviction for Efficient LLM Agent Inference
- **作者**: Venkatesha Matam, Keon Kim
- **日期**: 2026-07-12
- **arXiv ID**: 2607.10582
- **领域**: cs.LG, cs.AI
- **代码**: github.com/venkateshamatam/memdecay（含 harness.py + traces.py + results/ 原始数据）

## 核心问题与研究动机

LLM Agent 在长时序工作流中累积大量异构上下文：系统指令、计划、用户消息、工具输入输出、检索文档、中间推理（scratchpad）。这些内容功能不同，生命周期差异巨大——系统指令需要全程保留，而过时的工具输出和 scratchpad 往往几步后就失去价值。

然而当前 KV Cache 驱逐策略（H2O、StreamingLLM 等）对整个序列统一评分：要么按累积注意力，要么按时间窗口，要么按 attention sink。**它们完全忽略了 agent 编排层已知的语义结构**。

核心洞察：Agent 的上下文不是均匀 blob，而是由不同角色、不同预期寿命的 token 区段组成。应该利用编排层已有的 region 标签来指导缓存管理。

## 方法论（详细）

### 整体架构

MemDecay 是一个推理时（training-free）KV Cache 驱逐策略，运行在 agent 编排器和 LLM 解码引擎之间：

- 编排器为每段 prompt 标注 region 标签（system, plan, user, tool_in, tool_out, retrieval, scratchpad）
- 解码引擎按 region 对齐的 page 追加 KV 条目
- MemDecay 维护注意力统计和衰减时钟，在缓存预算紧张时驱逐最低分非钉扎 page

### 区域配置（Table I）

默认区域配置（校准会替换为实际拟合值）：

- system: 高优先级，衰减率≈0，**钉扎（pinned）**
- plan: 高优先级，小衰减率，可选钉扎
- user: 中优先级，中衰减率
- tool_in: 低优先级，大衰减率
- tool_out: 中优先级，校准衰减率
- retrieval: 低优先级，大衰减率（实测推翻此默认）
- scratchpad: 低优先级，大衰减率

### 核心公式：区域感知保留分数

每个 token i 的保留分数为：

```
s_i(t) = b_{r(i)} · exp(-λ_{r(i)} · Δt_i(t)) + α · a_i(t)
```

三项含义：
1. `b_{r(i)}` — 区域基础优先级：token 插入时的初始价值
2. `exp(-λ_{r(i)} · Δt_i(t))` — 区域特定时间衰减：结构保护随时间递减
3. `α · a_i(t)` — 注意力重要性：EWMA 平滑后的注意力权重，持续被使用的 token 保持存活

**注意力刷新机制**：当 token 收到的注意力超过阈值 τ（设为 2/|K_t|，随上下文长度自适应缩放）时，重置衰减时钟。刷新只重置时钟，不改变其他状态——结构先验从刷新点重新应用。

**关键设计：recency 只通过衰减时钟进入**——分数中不含独立的 recency 项，避免时间被重复计算。

### Page 粒度驱逐

生产服务栈（如 vLLM PagedAttention）以固定大小 page 存储 KV。MemDecay 的 page 分数为成员 token 分数的均值。区域标签标记连续跨度，因此最多一个 page 会跨越区域边界。实测：短上下文 35% 的 16-token page 跨越边界，长上下文降至 17%——区域越长，边界跨越越少。

### 校准协议

从实际 agent trace 测量 region-conditioned 注意力生命周期：
- 对每个 region 拟合 log-线性模型：log(Ā_r(Δt)) ≈ log(c_r) - λ̂_r · Δt
- 加权最小二乘拟合（按观测密度加权）
- 半衰期 t^{1/2}_r = ln2 / λ̂_r

### 分层扩展（Tiered Extension）

基础策略的驱逐是不可逆的。分层扩展提供梯度降级路径：
- 低于第一阈值 → 低精度量化（INT4/INT8）
- 低于第二阈值 → 卸载到主机内存 + 后台预取
- 低于最终阈值 → 丢弃

如果后续查询使卸载的 page 重新相关，可以恢复（以主机内存和传输带宽为代价）。

## 关键实验结果

### 实验设置

- 模型：Qwen2.5-1.5B-Instruct（float32, M3 Pro）、Qwen2.5-3B-Instruct（float16, T4 GPU）
- 上下文：短上下文 405-507 tokens（5阶段），长上下文 1,656-1,723 tokens（8阶段）
- 8个场景 × 3种值变体 = 24个 episode，每个 episode 4个 planted fact
- 每个配置格 96 个探测（probe），总计 4,320 个评分驱逐探测

### 结果一：区域注意力半衰期跨数量级差异（Table II）

各区域注意力半衰期（解码步数），95% 置信区间：

**1.5B 短上下文**：
- system: 150 [126, 182]
- plan: 33 [27, 38]
- user: 27 [24, 31]
- tool_in: 26 [21, 32]
- tool_out: 33 [27, 38]
- retrieval: 48 [38, 61]
- scratchpad: 14 [13, 15]

**3B 长上下文**：
- system: 189 [174, 206]
- plan: 52 [49, 55]
- user: 35 [30, 40]
- tool_in: 26 [22, 29]
- tool_out: 39 [32, 50]
- retrieval: 66 [50, 92]
- scratchpad: 16 [15, 17]

关键发现：
- system 半衰期是 scratchpad 的 **10 倍以上**（148-189 vs 14-16），每个设置下置信区间不重叠
- system 在更大模型上更持久（189 vs 148 at matched context）
- scratchpad 在所有设置下以 14-16 步半衰期快速衰减，与模型和上下文长度无关
- **retrieval 是最持久的活动区域**（48-76 步），推翻了 Table I 中对其赋予的大衰减率默认值——校准的结果

### 结果二：钉扎保证指令存活

- 钉扎（pinning）在每个设置下将 system 区域事实保留在 full-cache 精度
- 没有任何基线能保留超过 24 个中的 13 个 system 区域事实
- recency-based 保留（StreamingLLM）随上下文增长完全崩溃
- 结构先验在上下文增长时仍然有效

### 结果三：非钉扎内容上 H2O 获胜

在非钉扎内容上，累积注意力保留（H2O）优于 MemDecay 的当前公式化。消融实验定位了原因。

### 消融实验：注意力项不变性

变体 α ∈ {0.2, 0.5, 0.8} + 禁用钉扎，其余不变。结果：四种配置产生近乎相同的保留集和探测结果（576 行中仅 4 行保留数量不同）。

原因分析：
- page 均值将单个 token 的注意力贡献除以 page 大小
- ρ=0.9 的 EWMA 在驱逐时已遗忘早期注意力
- α·a_i 项比结构项低 1-2 个数量级——恰好对需要拯救的旧 token 无效

**诊断结论**：将结构先验与注意力结合需要对注意力项进行**幅度归一化**（如相对于均匀注意力水平 1/|K_t|）。这是一个设计变更而非调参变更。

### 开销

- 评分 + page 选择：0.27 ms（466-token cache）
- 应用一次驱逐：4.2 ms
- 但读取注意力的代价很高：k=1 时评分解码步 69.8 ms vs 非评分 26.0 ms（M3 Pro）
- 生产部署应间隔采样注意力（k>1）或复用其他用途产生的分数

## 创新点分析

1. **语义结构驱动的缓存管理**：首次将 agent 编排层的 region 标签作为 KV Cache 驱逐的一等信号。不是发明新的注意力指标，而是利用已有的上下文结构。

2. **双信号融合**：将区域结构先验（静态）与注意力使用信号（动态）组合为单一可解释的保留分数。结构先验决定起点和衰减速度，注意力刷新让"正在被使用"的 token 保持存活。

3. **测量驱动校准**：不是拍脑袋设衰减率，而是从实际 trace 中拟合 region-conditioned 注意力衰减曲线。论文诚实地报告了校准推翻默认值的情况（retrieval 的实际半衰期远大于默认假设）。

4. **不可逆性诚实评估**：明确承认 base policy 不可逆——evicted token 无法恢复，并提出了 tiered extension（量化→卸载→丢弃）作为未来方向。

## 局限性与未来方向

### 局限性

- **不可逆性**：被驱逐的 token 无法恢复，agent trace 中存在 saliency shift（后续查询使旧 token 重新相关）
- **跨区域信息流**：Agent 经常将内容跨区域复制（如在 scratchpad 中引用 tool output），默认配置下两份副本都会快速衰减
- **标签质量依赖**：假设编排器提供 region 标签，无标签的工作负载需要分类器，对噪声标签的鲁棒性未测量
- **粒度限制**：每个 token 一个分数，跨 head/layer 统一，未做 head-adaptive 预算分配
- **规模局限**：仅测试 1.5B/3B 模型在 450-1700 token 上下文，远低于生产级长上下文场景
- **Eager attention 要求**：读取注意力权重需要 eager attention，与生产 fused kernel 不兼容

### 未来方向

1. **注意力项幅度归一化**：最关键的改进——当前 α·a_i 项在驱逐时已比结构项低 1-2 个数量级
2. **在线自适应衰减率**：从观测到的刷新频率中在线更新
3. **依赖感知驱逐**：将 plan 与其依赖的 tool output 和证据关联，联合保留或丢弃
4. **8B 级模型在 4k+ token 上的验证**：在真实 agent 工作负载（SWE-bench、BFCL、browsing traces）上测试
5. **轻量 region 分类器**：当编排器不提供元数据时自动推断区域标签

## 借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

### P0：Agent 上下文管理的区域感知分层

**现状**：Hermes Agent 的对话历史和工具输出当前是扁平管理，超长会话时 context window 会被工具输出和中间推理填满，系统指令和关键计划的生存无法保证。

**借鉴**：MemDecay 的 region 分类（system → plan → user → tool_out → retrieval → scratchpad）与 Hermes 的编排模式完全对齐。可以在 Hermes Gateway 层实现一个轻量级 region tagger，为每段 prompt 打标，然后用区域半衰期指导哪些内容优先保留 / 压缩 / 丢弃。

**收益**：长会话场景下系统指令不丢失，工具输出过期自动降级，节省 context window。

### P1：memorygraph 分层降级路径

**现状**：memorygraph 当前是"存在或不存在"的二元模型，没有梯度降级。

**借鉴**：MemDecay 的 tiered extension（量化→卸载→丢弃）可以直接映射到 memorygraph 的 archival tier：
- 高频访问的 memory → 保持在 L1 活跃层
- 低频但有价值的 memory → 降级到 L2 压缩层（摘要化）
- 极低频 memory → 降级到 L3 archival 层（仅关键词索引）

**关联**：与 Memory Compaction Rate-Distortion (2607.08032) 的四层记忆压缩框架互补——那篇解决了"压多少"，MemDecay 解决了"按什么顺序压"。

### P2：注意力衰减校准方法论

**现状**：Hermes 目前没有测量过不同类型内容（system prompt vs 工具输出 vs 用户消息）在 LLM 注意力中的实际生命周期。

**借鉴**：论文的校准协议（log-线性拟合 + 半衰期估计 + 场景 bootstrap CI）可以直接复用，在 Hermes 的实际工作负载上跑一次测量，得到适合的衰减参数。

**关键发现可复用**：retrieval 区域的实际半衰期远大于直觉默认值——Hermes 的 RAG 检索结果可能比预期更有价值，不应过早从 context 中清除。

### P3：Jetson 边缘部署的 KV Cache 管理启示

**现状**：Jetson Orin Nano 的 8GB 统一内存中，KV Cache 是推理瓶颈之一。当前 vLLM/Ollama 的默认驱逐策略是 recency-based。

**借鉴**：MemDecay 的核心公式（s = b·exp(-λ·Δt) + α·a）计算量极小（0.27ms），完全可以在 Jetson 上实时运行。但 eager attention 的开销（69.8ms vs 26.0ms）在 Jetson 上会更高，需要 k>1 的间隔采样策略。

**障碍**：需要修改推理引擎（vLLM/Ollama）的注意力读取接口，当前 Jetson 上默认使用 fused attention，不支持逐 token 注意力读取。
