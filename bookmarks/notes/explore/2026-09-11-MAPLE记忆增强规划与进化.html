核心问题与研究动机

领域从业者（排产员、调度员、车队协调员）懂业务约束但缺运筹学训练。LLM 优化 Agent 虽能将自然语言转成求解器代码，但真实运营是动态的：新订单到达、资源不可用、优先级变化——每次都要求数据、约束、目标的更新。

现有方法处理孤立请求，存在三大缺口：
- 无法保证快速适配时保留先前已接受的决策（如"保留之前讨论过的某客户的车辆分配"）
- 无法复用有价值的搜索状态（历史候选解在新约束下可能仍有用）
- 修订失败时没有状态回滚保护

论文将此设定命名为 live dynamic optimization（实况动态优化）：在累积自然语言修订下维护可执行优化程序。这一设定超越了"多轮规划基准只测计划变化"和"动态优化只研究数值层面种群修复"两条线，是二者的交叉。

内容整理：方法论（MAPLE 四大组件）

MAPLE 维护可执行状态 S_t = (D_t 数据, W_t Workbench 优化程序, A_t 已接受计划, P_t 候选解种群)，外加事件历史 E_t。更新函数 S_t = Φ(x_0, u_{1:t}, S_{t-1}, E_{t-1})。被拒绝的修订不改变已提交状态——事务性更新语义。

1. TSS（Typed Search-Space Scaffolding，类型化搜索空间脚手架）——构建期
- 模型只写两个函数：build_problem(public_context) 读表、声明决策段与目标；evaluate(genome, data) 解码候选解并返回目标值+约束违反
- 决策段类型：binary / categorical / 有界整数 / 有界实数 / 排列 / 分配
- 声明类型即绑定固定算子：实数向量→模拟二进制交叉+多项式变异；排列→顺序交叉+交换变异；离散/分配→逐基因父选择+类型有效变异。四类算子全部保持声明的表示空间，模型永远不碰搜索代码
- 声明的公式类型选求解器：线性/MILP→精确求解器；非线性/组合→GA；多目标→NSGA-II

2. LPD（Live Problem Decomposition，实况问题分解）——修订定位
- 读公共更新+决策声明+事件历史，识别对数据、决策、评估逻辑或历史绑定的改动
- 价格变化只改表；新约束需要改 evaluate()；编辑器只接收目标函数、其余保留

3. LSM（Live State Memory，实况状态记忆）——历史绑定
- 事件 + 已接受决策 + 搜索候选三元存储
- "保留先前提到的客户分配"→事件记录定位客户（可能需三跳引用链），已接受计划供车辆号，类型化绑定查询校验当前决策域有效性，运行时在搜索中强制执行该分配
- 事件在更新被接受后才追加进历史（写后提交）

4. Restart Selector（重启选择器）——复用风险控制
- 模型基于变更摘要评估复用风险，推荐 Warm（修复历史初始化，至多填充半数种群）或 Full（全新初始化）
- Algorithm 1 固定门禁：模型引用的风险原因 M 必须与实际结构变化 SupportedMechanisms(Δ_t) 相交（V≠∅），解释中引用的变更字段 E 必须与真实变更字段 ChangedFields(Δ_t) 相交（C≠∅），且 r=high 且 v=true 四条件同时满足才采纳 Full——模型的判断要过证据验证关，防止幻觉式重启

5. 验证与提交：编译每个编辑→检查函数接口→跑小输入例→错误触发至多 B=3 次模型修复→固定求解器跑→检查输出字段结构→失败则拒绝修订保留旧态，通过则提交 D/W/A/P 并追加事件。

内容整理：关键实验结果与数据

基准 NLDO：5 族（选择/排程/排班/路径/云资源放置）× 3 序列 = 15 轨迹、195 状态、180 更新，含单目标与多目标，t11-t12 有破坏性替换。主模型 DeepSeek-V4-Pro，10 随机种子，200 候选×至多 200 代。

主结果（严格前缀协议：首次拒绝即清零后续全部状态）：
- MAPLE：15/15 轨迹全部完成，scalar 在线质量 0.951，Pareto HV 0.875
- Persistent ReAct：0.501 / 0.042；ReAct 0.333 / 0.023；OptiMUS 0.281 / 0.084；ORLM 0.120 / 0.000
- 动态多目标场景对手全线崩溃（最高 0.084），MAPLE 领先一个数量级——没有可执行状态维护的 Agent 无法承受连续修订

消融证据链：
- 去掉 TSS：可行率 100%→80.6%，HV 0.879→0.665，720 个更新-种子结果中 140 个无效（路由程序漏检"一车一路线"、云放置未拒绝 GPU 不兼容分配）——自由生成代码的隐性约束缺失是主要失败源
- 换成整块拷贝变异算子：HV 0.774→0.618，类型化算子贡献显著
- Token 成本：TSS 版 51.6k/轨迹 vs 无 TSS 72.8k——类型化脚手架同时提升质量和降低 29% 成本（模型不重写搜索代码）
- LPD 预测与实际保存编辑一致率 170/180；LSM 解析 30/30 实体引用（含 6 个三跳链）、18/18 混合请求（单独用事件记录或单独用已接受计划各只能解 6 个，两类记录缺一不可）
- 跨模型（Kimi k2.7）：scalar 0.937 / Pareto 0.766——架构收益不绑定单一模型

重启策略（Q4）：MAPLE 0.879 vs Always Warm 0.868 vs Always Full 0.824。前 10 次更新 MAPLE 与 Always Warm 均为 0.915；破坏性更新后 MAPLE 选 Full 得 0.696 vs Warm 0.636。加任务场景 Warm 优势巨大：routing +0.708 HV。复用与重启的收益是场景依赖的，语义判断优于任何单一数值规则（按单元格变化比例的规则在 4 个加任务测试中全部选错）。

创新点分析

  • 提出并形式化 live dynamic optimization 设定，填补"NL2Opt 单次生成"与"动态优化数值研究"之间的空白，配套 NLDO 基准将轨迹连续性（协议严格前缀）与解质量分开评估——评估设计本身就是贡献
  • TSS 的"模型声明、系统执行"分工：LLM 只负责语义层（决策类型+评估逻辑），搜索算子/求解器全部固定——把 LLM 自由度限制在它擅长的层，用类型系统消除整类失败模式
  • Algorithm 1 将 LLM 的风险评估转化为可验证断言（引用原因∩实际变化），是"模型判断+确定性门禁"混合决策的干净范例
  • 事件历史与已接受计划的双记录设计，消融证明二者互补而非冗余

局限性与未来方向

  • 主基准为合成数据（作者已声明）；真实业务表的噪声、口径不一致未覆盖
  • 严格前缀协议对对手偏严（Persistent ReAct 数学前缀可回升到 0.763/0.185，其失败多为缺辅助字段而非解不可行）——MAPLE 优势幅度在宽松协议下缩小
  • 重启收益统计显著性有限：MAPLE vs Always Warm 平均增益 0.010，95% 置信区间 [0.001, 0.021]，符号检验 p=0.219，六序列中五个为正但样本量小
  • Workbench 编辑面限定为两个函数（build_problem/evaluate），更深的结构性重构（新增决策段类型）不在支持范围
  • 未涉及多用户并发修订与修订冲突消解

归纳总结

一句话：MAPLE 用"类型化脚手架 + 可执行状态事务提交 + 语义重启门禁"让 LLM Agent 在自然语言持续修订下维持优化问题的求解能力（0.951/0.875），比最强基线高一个数量级，且证明限制模型自由度（TSS）反而同时提升质量、降低成本。

对 Agent 系统的三条可迁移规律：
- 规律一：LLM 写声明，运行时执行——把生成面收窄到语义层，失败模式从"隐性约束缺失"（140/720 无效）降到"类型错误"（可静态检查）
- 规律二：更新必须事务化——编译+接口检查+小例运行+输出检查四道闸，失败回滚旧态，事件只在接受后写入
- 规律三：复用/重建决策要"模型判断+证据门禁"——纯数值规则（变化单元格比例）在加任务场景全错，纯模型判断有幻觉风险，二者交叉验证最优

趋势判断

  • Agent 状态管理从"记忆检索"走向"可执行状态维护"：本文与 Memory Compaction (2607.08032)、MemDecay (2607.10582)、Agent 记忆迁移性 (2609.xxxx) 一脉相承——记忆不是文本片段，而是带事务语义的可执行对象（程序+数据+解+事件），这是 2026 下半年 Agent 架构的明确走向
  • "模型声明+固定运行时"成为 LLM 工程主流范式：与 TSS 同构的模式在 tool-making（SOP→工具编译）、skill 编译（SPyCE）、harness-native RL（OpenForgeRL）中反复出现——LLM 的自由度收窄到类型化接口层，执行层确定性化
  • LLM 判断的"证据门禁化"：Algorithm 1 的"引用原因必须与实际变化相交"模式，可直接泛化为 Agent 自我评估的可验证化（类似 Binding Drift 的廉价交叉验证降 79% 失败）
  • 动态多目标场景基线全线崩溃（≤0.084）说明连续修订是当前 Agent 能力的断层线，基准将向更长轨迹、更强破坏性方向演化

指南分析

若要将 MAPLE 方法应用到自己的系统，操作要点：

  • 遵循"两个函数"边界：让 LLM 只写 build_problem（声明）和 evaluate（评估），搜索循环、算子、求解器全部固定——不要让模型生成完整求解代码
  • 决策类型先行：先枚举决策段类型（离散/连续/排列/分配），每种类型配一套经过验证的算子，类型声明即自动绑定
  • 重启门禁三查：模型说"风险高要重启"时，一查引用的机制是否在支持列表、二查引用的字段是否真的变了、三查建议动作是否一致，三查通过才执行
  • 失败即回滚：任何检查不过，保留旧状态不动，只允许至多 B=3 次修复尝试，超限拒绝修订——宁可拒绝也不提交坏状态
  • 评估分离：连续性（协议全过）与解质量分开打分，拒绝一次不等于后续全废（用数学前缀做宽松对照）
  • 记忆双轨：事件记录（谁在何时改了什么）与已接受结果（最终值）分开存，引用解析需要两轨配合，单轨各只能解 1/3 混合请求
