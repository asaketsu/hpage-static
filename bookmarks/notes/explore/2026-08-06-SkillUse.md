## 内容整理

本论文核心贡献是 **Skill-Use benchmark**，首次将 Agent 的 skill 使用能力分解为三个正交维度进行评估：

- **Trigger（触发）**: Agent 能否从 skill 的名称+描述推断出相关性并主动检索
- **Compliance（合规）**: Agent 是否忠实执行 skill 规定的操作步骤
- **Boundary（边界）**: Agent 是否避免 skill 禁止的操作

关键数据：79 个真实 skill × 177 个可执行 task × 9 大领域 × 1,314 个评分项 × 8 个前沿模型 × 2 个 harness（Claude Code + Codex）。最强组合 SU 仅 0.613。

### 核心技术概念

- **Progressive disclosure**: Agent 初始只看到 skill 名称和一句话描述（metadata m），不含完整程序 p。必须先判断相关性再检索——这是 Claude Code/Cursor/Codex/OpenClaw 的实际接口
- **Skill-exclusive requirement**: 必须读 skill 才能完成的操作（通过 masked-skill check 过滤掉通用知识可解的假需求）
- **门控式 SU 评分**: SU = Trigger × [α·Compliance + (1-α)·Boundary]，未触发则整段归零，避免"不用 skill 碰巧成功"的假阳性
- **Masked-skill check**: 把候选 requirement 的 skill 内容遮蔽后交给强模型测试——如果仅看 prompt 就能完成，则丢弃该 requirement
- **Multi-agent adversarial review**: 跨模型家族交叉审查 task scope 和 rubric verifiability，迭代回写失败案例直到无新问题
- **Harness-as-variable**: 同一模型在 CC 和 Codex 下排名不同，证明 skill use 是 model×harness 联合属性

### 方法论要点

评估实例 x = (s, q, E, R)：
- s = skill，分为 m（名称+描述+路径）和 p（完整程序）
- q = 用户任务（含输入资产：代码库/文档/数据集）
- E = 隔离 Docker sandbox（全工具访问）
- R = 隐藏 rubric（仅用于评分）

Agent 收到 (q, E, m)，运行产生轨迹 τ = (o₀, a₁, o₁, ..., aT, oT) 和终端状态 zT。评分基于完整轨迹而非仅最终结果。

## 1. 核心问题与研究动机

LLM Agent 生态中，Skill（结构化技能文档）已成为主流接口——Claude Code、Cursor、OpenClaw、OpenAI Codex 都采用 progressive disclosure 机制：Agent 只看到 skill 的名称和一句话描述，必须主动判断该 skill 相关后检索完整程序再执行。

**现有评估的盲区**：
- Skill-centric benchmarks（如 SkillsBench、SkillLearnBench）只评估 skill 本身质量或对任务成功的边际贡献，不看消费端 Agent 的行为
- Instruction-following benchmarks（如 IFEval、AgentIF）直接在 prompt 里给约束，不经过 progressive disclosure
- SLBench 最接近，但 **preload 了完整 skill**，绕过了检索环节

**核心问题**：Agent 能否自主识别相关 skill → 检索 → 忠实执行？这三个环节缺一不可。

## 2. 方法论：Skill-Use Benchmark

### 2.1 三维度评估框架

将 skill use 分解为三个正交维度：

- **Trigger（触发）**：Agent 是否从名称+描述推断出 skill 相关并检索了它。定义为指示函数 g(y;s) = 1[Retrieve(s) ∈ τ]
- **Compliance（合规）**：Agent 是否忠实执行了 skill 规定的程序步骤。C(y) = Σ wᵢφᵢ(y) / Σ wᵢ
- **Boundary（边界）**：Agent 是否避免了 skill 禁止的操作。B(y) = Σ wᵢφᵢ(y) / Σ wᵢ

**SU 总分**（门控式）：
> SU(y) = g(y;s) × [α·C(y) + (1-α)·B(y)]
> α = 0.7（Compliance 权重更大，因为它是核心执行能力）

关键设计：**SU 是门控的**——只有 Trigger=1（成功检索到 skill）后，Compliance 和 Boundary 才计分。未触发的 skill 得分为 0。

### 2.2 Benchmark 构成

- **79 个真实 skill**（来自 GitHub 社区仓库 + SkillsBench + SkillLearnBench）
- **177 个可执行 task**（覆盖 9 个领域）
- **9 大领域**：软件开发、基础设施、数据科学、数据库、文档与内容处理、安全、商业运营等
- **1,314 个评分项**（平均每个 rubric 7.4 项，范围 3-16）
- 每个 task 在 **隔离 Docker sandbox** 中运行，全工具访问
- 评分项分 4 类：Evaluability gates（零权重，仅标记可评性）、Compliance 项、Boundary 项、Task-outcome 项

### 2.3 三阶段构建管线

1. **Skill & Task 构建**：从 105,586 个候选中筛选 79 个 skill → 构建 in-scope task → 每个task必须包含至少一个 skill-exclusive requirement（不读 skill 就无法完成的操作）
2. **Rubric 构建**：三层 rubric → skill-derived items 形成 SU 信号
3. **End-to-End 验证**：
   - **Masked-skill check**：丢弃那些不读 skill、仅看 prompt 也能满足的"通用需求"——确保每个 scored requirement 都是 skill-exclusive
   - **Multi-agent adversarial review**：不同模型家族的审查者交叉确认 task scope 和 rubric verifiability，失败回写为新规则，迭代直到无新失败

### 2.4 问题形式化

每个评估实例是元组 x = (s, q, E, R)：
- s = skill（m=名称+描述+路径, p=完整程序）
- q = 用户任务
- E = 可执行 sandbox
- R = 评分 rubric（Agent 不可见）

Agent 初始只收到 (q, E, m)，不含 p。运行后产生轨迹 τ = (o₀, a₁, o₁, ..., aT, oT) 和终端产物状态 zT。

## 3. 关键实验结果

### 3.1 主实验（8 模型 × 2 Harness）

评估模型（7 个家族）：Claude Opus 4.7、Claude Opus 4.8、GPT-5.5、DeepSeek-V4-Pro、GLM-5.1、MiniMax-M3、Kimi-K2.6、Qwen3.6-Max

**Claude Code (CC) Harness 下的核心数据**：
- Claude Opus 4.7: Trigger 0.966 / Compliance 0.609 / Boundary 0.712 / SU 0.599
- Claude Opus 4.8: Trigger 0.940 / Compliance 0.625 / Boundary 0.704 / SU 0.597
- GPT-5.5: Trigger 0.972 / Compliance 0.611 / Boundary 0.718 / **SU 0.613（CC最高）**
- DeepSeek-V4-Pro: Trigger 0.324 / Compliance 0.439 / Boundary 0.658 / SU 0.250
- GLM-5.1: Trigger 0.324 / Compliance 0.455 / Boundary 0.639 / SU 0.267
- MiniMax-M3: Trigger 0.833 / Compliance 0.569 / Boundary 0.706 / SU 0.501
- Kimi-K2.6: Trigger 0.337 / Compliance 0.447 / Boundary 0.580 / SU 0.190
- Qwen3.6-Max: Trigger 0.446 / Compliance 0.475 / Boundary 0.625 / SU 0.318

**Codex Harness 下**：
- Claude Opus 4.7: Trigger 0.836 / SU 0.535
- Claude Opus 4.8: Trigger 0.881 / **SU 0.559（Codex最高）**
- GPT-5.5: Trigger 0.966 / SU 0.503（Compliance† 从 CC 的 0.625 降到 0.490）

### 3.2 核心发现

**发现 1：可靠 skill use 仍未达到**
- 最强配置 SU 仅 0.613（GPT-5.5 under CC）
- Triggering 和 conditional execution 是两个独立瓶颈
- 即使触发了 skill 的轨迹中，最高 Compliance† 也仅 0.638（Claude Opus 4.8 under CC）
- **Boundary 普遍高于 Compliance**：模型更容易"不做禁止的事"而非"做完所有规定的步骤"

**发现 2：Skill use 性能依赖 Harness，不是模型的固有属性**
- CC 下排名头部是 GPT-5.5，Codex 下头部是 Claude Opus 4.8
- 两个 harness 的 per-model SU 向量相关性仅"中等"
- CC→Codex：Trigger 分布压缩（弱模型提升），但 conditional Compliance 分布扩大（强模型下降，GPT-5.5 Compliance† 降 >0.1）
- Codex 降低 skill 选择门槛但要求更高执行持续性

**发现 3：具体程序 > 开放式程序**
- 文件处理、数据库、数据科学 skill 的 Compliance 最高（规定了具名工具、文件格式、明确操作）
- 商业分析、软件架构 skill 的 Compliance 最低（开放式规划任务）
- Security & Compliance 是唯一 Boundary < Compliance 的领域：模型执行了安全步骤但仍在需要克制时调用了 skill

**发现 4：Preload 显著提升 Trigger**
- 在配对实验中，preload 完整 skill 后 SU 上升（因为 Trigger 上升）
- 对 native Trigger 弱的模型效果最大，接近饱和的模型几乎无效
- 这说明 native injection 下 **检索（retrieval）是主要瓶颈**

**发现 5：Skill 库增大主要造成"不触发"而非"选错"**
- 单 skill 时所有模型可靠选择正确 skill
- 10 个 skill 时可见下降（弱模型尤其）
- 之后曲线趋于平稳——库增大是"准入成本"，非持续下降
- 多数失败是"完全没调用任何 skill"，选错的情况罕见（仅在 TDD/软件架构等描述重叠时）

**发现 6：Skill use 能力 ≠ 过度调用抑制能力**
- 53 个 out-of-scope task 测试中，within-scope SU 与 out-of-scope avoidance **负相关**
- 最擅长遵循 skill 的模型，可能是最不擅长在不需要时抑制调用的模型
- 两种能力基于不同判断：一种管"进入 skill 后的行为"，另一种管"是否该进入"

**发现 7：Skill 帮助/损害的分界线在 SU ≈ 0.5**
- 779 次触发 run 中，按 SU 分箱对比配对基线（禁用 skill 库）
- SU > 0.5 时 skill 带来正向 task completion gain
- SU < 0.5 时模型部分/错误使用 skill，task completion 反而更差

## 4. 创新点分析

1. **首次将 skill use 分解为 Trigger/Compliance/Boundary 三正交维度** — 以往只看最终成功率，无法定位失败在检索还是执行
2. **门控式 SU 评分** — 未触发则不计分，避免"未用 skill 但碰巧完成"的假阳性
3. **Masked-skill check 机制** — 确保 benchmark 中每个 scored requirement 都是真正的 skill-exclusive，排除通用知识可解的假需求
4. **Multi-agent adversarial review** — 跨模型家族交叉验证，消除单一模型偏好带来的 rubric 偏差
5. **Harness-as-variable 设计** — 同时在 CC 和 Codex 上评估，证明 skill use 是 model×harness 的联合属性，推翻"换 harness 无所谓"的假设
6. **Out-of-scope 测试** — 不仅测"该用时会用"，还测"不该用时会克制"，揭示了 within-scope 能力和 out-of-scope 克制能力的负相关悖论

## 5. 局限性与未来方向

**论文承认的局限**：
- 只测了 CC 和 Codex 两个 harness，其他 harness 可能呈现不同模式
- 79 个 skill 和 177 个 task 虽来自真实仓库但经过严格筛选，可能不完全代表长尾场景
- α=0.7 的权重选择虽报告了敏感性分析，但最优值可能因应用而异
- Out-of-scope 只有 53 个 task，统计功效有限

**隐含局限**：
- Docker sandbox 的执行环境可能屏蔽了真实生产环境的网络/权限复杂性
- LLM-as-judge 使用 GPT-5.4，评判本身可能有系统偏差
- 只测"单 skill 任务"——实际 Agent 常需组合多个 skill

**未来方向**：
- 扩展到更多 harness 和多 skill 组合场景
- 训练 Agent 提升 progressive disclosure 下的 skill retrieval 能力
- 研究 within-scope 能力与 out-of-scope 克制能力的解耦训练

## 6. 借鉴点（关联 Hermes Agent / Jetson / 量化）

### P0 — Skill 触发可靠性是 Hermes 的核心风险

论文揭示的核心问题在 Hermes 上同样存在：Hermes 有 **200+ 个 skill**，progressive disclosure 机制让 Agent 只看到名称+描述。论文证明：
- 即使最强模型，在 10+ skill 库中 Trigger 也显著下降
- 库增大主要导致 **"不触发"**（不调用任何 skill），不是选错

**可执行改进**：
- Hermes 当前在 system prompt 中列出所有 skill 的名称+描述（<300 个），根据 Finding 5，这正是"10 skill 后下降趋稳"的区域——大部分失败是 Agent 认为没有 skill 相关
- 可考虑为高频 skill（如 cron 任务常用的 daily-paper-reading、note-dual-format）在 system prompt 中增强描述（加入更具体的触发关键词），降低漏触发率

### P0 — Boundary 维度：Security skill 需要克制机制

论文发现 Security & Compliance 是唯一 Boundary < Compliance 的领域——模型执行了安全步骤但仍在不该用时调用了安全 skill。Hermes 的 security/red-teaming 类 skill 有 50+ 个，存在过度调用的风险（如对普通编程任务误触发渗透测试流程）。

**可执行改进**：在 security skill 的 description 中明确标注"仅在以下场景触发"，强化 Boundary 语义。

### P1 — Skill 注入模式（Native vs Preload）

论文证明 preload 完整 skill 对 Trigger 弱的模型提升最大。Hermes 目前是 native 模式（只展示名称+描述）。

**可考虑**：对 Cron 任务（固定流程、已知 skill），直接 preload 常用 skill 的完整内容，避免每次执行时的检索开销和漏触发风险。当前 cron job 已经通过 `skill_view()` 手动加载，本质上是一种 manual preload。

### P1 — SU ≈ 0.5 是"skill 有帮助"的分界线

论文的 paired gain 实验证明：SU < 0.5 时用 skill 反而降低 task completion。这对 Hermes 的 skill 维护有直接指导意义——如果某个 skill 在实际使用中 Compliance 很低（Agent 经常不遵循），它可能 **有害而非有益**。

**可执行改进**：定期审计低使用率 skill，如果发现"被加载但未遵循"的模式，应简化或删除该 skill 而非保留。

### P2 — 三维度评分框架可用于 Skill 自测

Trigger/Compliance/Boundary 的分解思路可用于 Hermes 的 self-evaluation：
- Trigger：Agent 是否在正确时机调用了 skill（vs 手动提醒才调用）
- Compliance：Agent 是否按 skill 步骤执行（vs 只读不执行）
- Boundary：Agent 是否在 skill 不适用时避免调用

可在 skill-stress-test skill 中增加这三维度评分。

### P2 — Harness 差异性验证

论文证明 CC 和 Codex 下排名完全不同。Hermes 本身是一个 harness，换不同模型（GLM/Claude/GPT）时，最优 skill 可能不同。

**启示**：Hermes 的 skill 优化不应假定模型固定——换模型时需要重新评估 skill 触发率和合规率。

## 查询拓展

### 可继续探索的问题

- **Hermes 的 Trigger 率是多少？** Hermes 拥有 200+ skill，在 progressive disclosure 下的实际触发率未见量化。可参考 Skill-Use 方法做抽样审计
- **Cron 任务的 skill 触发是否可靠？** Cron job 的 prompt 通常显式指定 skill_view(name=...)，本质上是 manual preload——但自动触发的场景（如 session-boot、idle-busy-loop）的可靠性未知

## 趋势判断

### 这篇论文在领域中的位置

Skill-Use 是 2026 年 Agent 评估赛道的重要节点。它标志着 benchmark 从 **"看结果"** 转向 **"看过程"**——不再只关注任务是否完成，而是分解 Agent 行为路径上的每个决策点。

### 技术趋势

- **Skill 生态化**：Claude Code 引领的 progressive disclosure 模式已成为行业标准（OpenClaw/Cursor/Codex 跟进），社区仓库的 skill 数量快速增长
- **Harness-as-variable 成为共识**：多篇 2026 论文证明 harness 对 Agent 性能的影响不亚于模型本身，甚至能逆转排名
- **过程级评估**：从 final-outcome 评分转向 trajectory-level rubric，Skill-Use 的 1,314 个评分项 × Docker sandbox 是这个方向的代表
- **Trigger 作为独立瓶颈被识别**：preloading 显著提升性能，说明 progressive disclosure 的检索成本是真实存在的工程问题

### 对 Hermes 的启示

Hermes 作为 multi-skill harness，正处在这篇论文描述的问题中心。SU=0.613 意味着即使最强配置也有近 40% 的 skill 使用存在缺陷——在 Cron 自动化场景下，这可能导致静默失败（skill 未触发但 cron 报告"成功"）。

---

## 总结

Skill-Use 是第一个系统性评估 **Agent 在 progressive disclosure 下自主使用 skill 能力** 的 benchmark。核心贡献是将 skill use 分解为 Trigger/Compliance/Boundary 三维度，揭示了一个残酷现实：即使是最强的模型+harness 组合，SU 也只有 0.613。Skill use 不是模型的固有属性，而是 model×harness 的联合涌现特性。对 Hermes 而言，这篇论文提供了 skill 触发可靠性评估的三维度框架，值得直接借鉴用于 skill 审计和优化。
