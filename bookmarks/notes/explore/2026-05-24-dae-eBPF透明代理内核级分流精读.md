## 一、dae 是什么

dae（大鹅）是基于 eBPF 的 Linux 高性能透明代理方案，是 v2rayA 的继任者。与 Mihomo/Clash、Sing-box 等用户态方案的核心差异：**直连流量在内核态直接路由转发，完全不经过代理进程**，性能损耗趋近于零。

## 二、核心架构

### 2.1 eBPF 挂载点：tc (traffic control)

```
网卡收包 → [tc eBPF程序] → TCP/IP协议栈 → netfilter(iptables/nftables) → 用户空间
                  ↑
           dae 在此处拦截分流
           直连流量直接路由转发（不经过协议栈完整处理）
           代理流量重定向到 tproxy 端口
```

**关键设计**：dae 在 tc 挂载点（网络驱动最早阶段）加载 eBPF 程序，在数据包进入 TCP/IP 协议栈**之前**就完成分流决策。

### 2.2 分流信息来源

| 信息 | 获取方式 | 性能 |
|------|---------|------|
| 源/目的 IP、端口、协议 | 解析 MACv2 帧 | 纳秒级 |
| MAC 地址 | 解析 MACv2 帧 | 纳秒级 |
| **进程名** | cgroupv2 挂载点监听 socket/connect/sendmsg 系统调用，读取进程控制块命令行 | **远快于 procfs 扫描**（Clash 等是 10ms 级） |
| **域名** | 劫持 DNS 请求，关联域名与解析 IP | 比 FakeIP/SNI 嗅探更优 |

### 2.3 代理路径 vs 直连路径

```
代理流量：tc eBPF → 关联 socket buffer 到 tproxy 端口 → dae 用户空间 → 代理服务器
直连流量：tc eBPF → 直接三层路由转发（不进入 dae 进程）
         ↑ Linux 此时相当于纯粹的交换机/路由器
```

**LAN 接口绑定**：eBPF 将需代理流量的 socket buffer 直接关联至 tproxy 侦听端口的 socket。
**WAN 接口绑定**：将 socket buffer 从网卡出队列移至入队列，禁用 checksum，修改目的地址为 tproxy 端口。

## 三、Real Direct 机制（核心创新）

传统代理方案的致命问题：**即使设置直连，流量仍需经过 代理进程 → 用户空间处理 → 重新封装 → 内核态 → 传出**，浪费大量 CPU/内存/连接数。

dae 的 Real Direct：
- 直连流量在 tc 层直接执行三层路由转发
- 不做 SNAT → 形成非对称路由（旁路由场景）
- 零用户态切换、零内存拷贝
- BT 下载/游戏等场景：不占代理进程连接数、端口、内存

**旁路由定义**（dae 首创）：①被设为网关 ②对 TCP/UDP 进行 SNAT ③LAN/WAN 同网段。

## 四、DNS 处理策略

### 4.1 dial_mode 四种模式

| 模式 | DNS 经过 dae | 分流能力 | 适用场景 |
|------|-------------|---------|---------|
| `domain` | ✅ | 完整域名分流 | 默认推荐 |
| `domain+` | ✅ | 域名分流 + 不验证嗅探域名真实性 | 快速代理响应 |
| `domain++` | ❌ | 嗅探域名重新路由（最强） | DNS 不经过 dae 时仍需分流 |
| `ip` | ❌ | 仅 IP 分流 | DNS 不经过 dae |

### 4.2 域名获取方式对比

| 方案 | 优点 | 缺陷 |
|------|------|------|
| **DNS 劫持关联**（dae 采用） | 覆盖所有协议 | DNS 不经过 dae 则失效 |
| Fake IP | 无 DNS 污染 | 缓存污染严重、无法 IP 分流 |
| SNI 嗅探 | 实时获取 | 仅限 TLS/HTTP；eBPF 循环限制无法在内核实现 |

用户空间补充：`dial_mode` 为 domain 变体 + 流量需代理时，dae 在用户空间嗅探域名，将域名（非 IP）发给代理服务器，由代理服务器重新解析获得最优 CDN IP。

## 五、系统要求

| dae 版本 | 最低内核 |
|----------|---------|
| 0.8.x | Linux 5.17+ |
| 0.9.x / 1.0+ | Linux 6.1+ |

必选内核选项（一般完整发行版已开启）：
- `CONFIG_BPF`、`CONFIG_BPF_SYSCALL`、`CONFIG_BPF_JIT`
- `CONFIG_NET_CLS_BPF`、`CONFIG_NET_SCH_CLSACT`
- `CONFIG_CGROUP_BPF`

推荐系统：Debian 12+（内核 6.1+，最稳定）

## 六、支持协议

VMess / VLESS / Trojan / Shadowsocks / ShadowsocksR / Hysteria2 / TUIC v5 / Juicity / HTTP(S) / SOCKS5 / Naiveproxy / 链式代理

全锥 NAT 支持：Shadowsocks、Trojan(-go)、Socks5

## 七、配置文件结构

```ini
# global 段
global {
    lan_interface: ens18        # 绑定 LAN 网卡
    wan_interface: auto         # 自动检测 WAN
    dial_mode: domain           # DNS 模式
    auto_config_kernel_parameter: true
}

# subscription 段 — 订阅源
subscription {}

# group 段 — 节点分组
group {
    proxy {
        policy: min_moving_avg_10  # 自动选最低延迟
        filter: name(regex)
    }
    direct {
        policy: fixed(0)
        filter: name(keyword: '直连')
    }
}

# routing 段 — 分流规则（顺序匹配）
routing {
    # 特定规则放上方
    pname(curl, wget) -> direct
    domain(geosite:openai) -> proxy
    ip(geoip:private) -> direct
    domain(geosite:cn) -> direct
    domain(geosite:geolocation-!cn) -> proxy
    fallback: proxy
}
```

## 八、关键内核参数

```bash
# LAN 接口：启用转发 + 禁用重定向
net.ipv4.conf.<lan_if>.forwarding = 1
net.ipv6.conf.<lan_if>.forwarding = 1
net.ipv4.conf.<lan_if>.send_redirects = 0

# 全局转发
net.ipv4.ip_forward = 1
net.ipv6.conf.all.forwarding = 1

# WAN 接口 IPv6 RA（forwarding=1 会压制 accept_ra）
net.ipv6.conf.<wan_if>.accept_ra = 2
```

## 九、性能对比

| 维度 | dae | 传统方案 (Clash/Mihomo) |
|------|-----|----------------------|
| 直连性能 | 内核态路由，接近线速 | 用户态转发，显著开销 |
| 代理性能 | 略优 | 基准 |
| 进程名获取 | cgroupv2 系统调用（微秒级） | procfs 扫描（10ms 级） |
| DNS 泄露风险 | ipleak 300次检测无泄露 | 需额外配置 |
| 资源占用 | 直连零占用 | 直连仍占连接数/内存 |

## 十、部署架构（旁路网关方案）

```
[主路由器 192.168.0.1]
       ↑
[旁路由(dae) 192.168.0.2] ← DHCP 下发此 IP 为网关+DNS
       ↑
[客户端设备]
```

主路由 DHCP 配置：网关和 DNS 指向 dae 所在设备。dae 负责分流，直连流量直接三层转发回主路由。

## 十一、与 Hermes 体系的关系

dae 是网络基础设施层工具，与 Hermes Agent 体系无直接重叠。潜在应用场景：

1. **Jetson Orin 网关模式**：如果 Orin 作为旁路由部署，dae 可提供内核级分流
2. **Agent 网络策略**：按进程名分流可为不同 Agent 进程指定不同代理路径
3. **研究价值**：eBPF tc 挂载点的流量拦截模式可借鉴到其他网络工具开发
