## 一、核心发现

### 发现1：Agentic Engineering 的三层架构

基于对 Claude Code、Codex CLI、OpenCode 等 AI Agent 的分析，Agentic Engineering 呈现清晰的三层架构：

```
┌────────────────────────────────────────────────┐
│  L3: Orchestration（编排层）                     │
│  - 任务分解、规划、优先级管理                      │
│  - 多 Agent 协作（Manager-Worker / Pipeline）    │
│  - 上下文压缩与恢复                               │
├────────────────────────────────────────────────┤
│  L2: Execution（执行层）                         │
│  - 代码搜索、编辑、测试、调试                      │
│  - 工具调用（terminal/patch/read_file）           │
│  - 验证门禁（lint/test/build）                    │
├────────────────────────────────────────────────┤
│  L1: Foundation（基础层）                        │
│  - 代码理解（AST / 语义索引）                     │
│  - 上下文窗口管理（渐进式披露）                    │
│  - 模型路由（按任务复杂度选模型）                   │
└────────────────────────────────────────────────┘
```

**关键洞察**：大多数团队卡在 L2，但真正的差异化在于 L3（编排能力）和 L1（上下文管理）。

### 发现2：上下文管理是瓶颈，不是模型能力

Claude Code 的核心突破不是模型更强，而是**上下文管理策略**：

| 策略 | 描述 | 效果 |
|------|------|------|
| **渐进式披露** | 先加载函数签名，需要时再加载实现 | Token 消耗 ↓90% |
| **状态机循环** | 压缩→预算检查→搜索→执行→验证 循环 | 防止 context window 溢出 |
| **Steer Hook** | 用户中途可纠偏，不"一条路走到黑" | 减少无效迭代 |
| **检查点机制** | 长任务自动保存进度快照 | 中断后可恢复 |

**对 Hermes 的启示**：我们的 skill-auto-inject 和 session-segmentation 已经在走这个方向，但还缺乏 Claude Code 级别的**状态机循环**。

### 发现3：验证门禁从"建议"变为"强制"

从 5/13 笔记和竞品分析来看，所有成功的 AI Agent 都在加强验证层：

- **Claude Code**: Hard Gates — 代码提交前必须通过测试
- **Codex CLI**: 沙箱执行 + 沙箱外操作需批准
- **Hermes**: requesting-code-review skill — pre-commit 验证流水线

**趋势**：AI 生成代码的比例越高，验证层的重要性呈指数增长。60% AI 代码意味着验证必须是自动化的、不可跳过的。

### 发现4：多 Agent 协作的实用模式

从实践角度看，真正有效的多 Agent 模式只有 3 种：

| 模式 | 适用场景 | 代表工具 |
|------|---------|---------|
| **Delegate + Verify** | 主 Agent 委派子任务，完成后审核 | Claude Code subagent |
| **Pipeline** | 顺序处理（代码→测试→审查） | CI/CD + Agent |
| **Parallel Workers** | 独立子任务并行执行 | Codex CLI 并行模式 |

**注意**：Peer-to-Peer 和 Marketplace 模式虽然理论上优雅，但在当前技术条件下（成本、延迟、一致性）实用性低。

### 发现5：推理成本结构性下降，Agent 密集调用可行

5 月竞品数据：
- DeepSeek: 100 万 token 仅 2 分钱，两天两次降价
- Grok 4.3: $1.25/M input
- GPT-5.5 Instant: ~$2/M input
- Gemma 4: 免费

**推算**：Hermes 一个典型 Agent 任务（10 轮工具调用 × 平均 2K token）成本从半年前的 ~$0.05 降至现在的 ~$0.005。**成本约束正在解除，Agent 密集调用成为默认策略**。

## 二、关键概念

### 2.1 Agentic Engineering vs Vibe Coding

| 维度 | Vibe Coding | Agentic Engineering |
|------|-------------|---------------------|
| 方法 | 随意对话，凭感觉 | 系统化指令、验证门禁 |
| 上下文 | 全量灌入 | 渐进式披露、按需加载 |
| 验证 | 肉眼检查 | 自动化测试+lint+CI |
| 可靠性 | 时好时坏 | 可预测、可重复 |
| 适用 | 原型/探索 | 生产代码/复杂任务 |

### 2.2 状态机循环（Agent Loop）

```
[压缩上下文] → [检查token预算] → [分析任务] → [搜索相关文件]
     ↑                                        ↓
[验证结果] ← [执行操作] ← [生成编辑方案] ← [定位目标]
```

这是 Hermes 的 state-machine-loop skill 的理论基础，但需要更强的**预算管理**和**中断恢复**。

## 三、可落地的 Insights

### 3.1 对 Hermes 的进化建议

| 发现 | 行动 | 优先级 | 预期收益 |
|------|------|--------|---------|
| 上下文管理是瓶颈 | 强化 session-segmentation，增加自动压缩触发点 | P0 | 减少 30% token 浪费 |
| 验证门禁强制化 | 所有代码修改 skill 加入 verification-gate | P0 | 减少 50% 低质量输出 |
| 推理成本下降 | 将简单任务路由到本地小模型（Jetson Orin） | P1 | API 成本 ↓40% |
| 多 Agent 实用模式 | 优化 subtask-lifecycle skill 的 Delegate+Verify | P1 | 复杂任务完成率 ↑ |
| ARPO 训练范式 | 工具调用训练改用 step-level advantage | P2 | Agent 工具调用准确率 ↑ |

### 3.2 模型路由策略更新

```
复杂度评估 → 模型路由
─────────────────────────────────────────
简单查询(< 1K token)    → 本地 Qwen3-0.6B (Jetson)
常规任务(1-5K token)    → 智谱 GLM / DeepSeek-V4 (API)
复杂推理(5-20K token)   → Claude Sonnet / GPT-5.5 (API)
代码生成+修改           → Claude Code / Codex (专用 Agent)
超长上下文(>100K)       → Grok 4.3 (1M context)
```

### 3.3 技术债务清理

基于分析，以下 Hermes skill 需要更新：

1. **state-machine-loop** → 加入 token 预算硬上限和自动压缩
2. **subtask-lifecycle** → 增加 Delegate+Verify 模式的标准化流程
3. **session-segmentation** → 增加上下文饱和度检测的量化指标
4. **model-adapter** → 更新模型路由表，加入 DeepSeek-V4 / Grok 4.3
