## 核心问题与研究动机

当前 tool-calling Agent 在客户服务等策略合规领域面临两大失败模式：

1. **状态接地问题（State Grounding Issues）**：Agent 可能检索到正确的信息，但后续决策基于过时/缺失/错误的数据。标准 Agent 将观察结果、工具返回和政策指令全部放在 prompt 中，让 Agent 每次决定下一步时自行重建相关状态，导致状态管理隐式化。
2. **策略边界违规（Policy Boundary Violations）**：语法上有效的工具调用仍可能违反依赖当前任务状态的环境策略。

## 方法论（详细）

### 1. Ledger State（账本状态）

LedgerAgent 维护一个**以 schema 为锚点的账本**，将成功的工具返回投影为紧凑的强类型字典：

- **结构**: `L: P → V`，其中 P 是规范 schema 路径（如 `orders.1234`、`products.5678`），V 是工具返回值
- **更新规则**:
  - 仅从**成功 read-tool 返回**更新状态
  - 失败的工具和 write-tool 返回**不更新状态**
  - 成功 write 后，Agent 必须发出 read 调用以观察新状态（**"observe-not-assume" 规则**）
- **路径稳定性**: 路径是稳定地址，如 `orders.1234`

### 2. Ledger-Grounded Generation（账本接地生成）

- 每次模型调用前，LedgerAgent 将完整账本块添加到 prompt
- 账本块从 L 确定性生成，列出所有通过 read 工具实际观察到的记录
- 目的：让模型**轻松找到当前观察到的状态**，而非在 transcript 中挖掘

### 3. Policy Gate（策略门控）

在**任何环境改变调用执行前**立即运行，评估提议的调用是否符合当前账本 L 上的可执行谓词 Π：

| 结果 | 含义 |
|------|------|
| **allow** | 执行调用不变 |
| **revise** | 移除调用，向模型提供违反的谓词 |
| **block** | 阻止调用，拒绝请求的操作 |

- 谓词以代码形式指定（非自然语言编译），每个域一次性定义
- 实验中策略层共包含 28 个确定性门控谓词：航空 10 个、零售 12 个、电信 6 个

### 4. Agent 循环

- **零额外 LLM 调用**：账本更新、渲染、策略门控均为确定性操作
- **成本不变**：与基线方法成本相同

## 关键实验结果与数据

### 测试域与基准

- **航空**: τ²-bench, 50 任务, 单控制
- **零售**: τ²-bench, 114 任务, 单控制
- **电信**: τ²-bench, 114 任务, 双控制
- **远程医疗**: τ-Trait, 20 任务, 单控制

### 性能提升（Pass^1 / Pass^4）

**Kimi-K2.5**:
- FC 基线: 44.0% / 52.0%
- LedgerAgent: **53.9% / 70.6%**

**GLM-5**:
- FC 基线: 40.0% / 50.9%
- LedgerAgent: **48.5% / 67.1%**

**MiniMax M2.5**:
- FC 基线: 36.0% / 53.5%
- LedgerAgent: **36.6% / 58.1%**

### 与 IRMA 对比

- **Pass^1**: Ledger 27.2% vs IRMA 23.4%
- **Pass^4**: Ledger 17.1% vs IRMA 9.6%
- **Token 开销**: Ledger 0.0% vs IRMA 53.1%

### 错误分析

90.7% 的失败由两类原因构成：
- 遗漏必需动作: 70.3%
- 错误动作参数: 20.4%

域特定模式：
- 零售: 69.9% 遗漏动作
- 电信: 98.7% 遗漏动作
- 航空: 47.7% 遗漏 + 33.9% 错误参数
- 远程医疗: 25.9% 错误参数率最高

## 创新点分析

1. **显式状态表示**: 将任务状态从 transcript 中解耦，变为独立可查询的 ledger
2. **预防优于纠正**: 在环境改变前拦截策略违规，而非事后修正
3. **模型无关**: 无需训练，适用于任何 backbone 模型
4. **零 token 开销**: 比 IRMA 等上下文工程方法更高效
5. **高一致性**: 在 pass^k 指标上提升显著，尤其在高 k 值时

---

## 局限性与未来方向

1. **结构化域限制**: 设计用于结构化 tool-use 域，对非结构化/视觉/潜在状态效果有限
2. **领域规范需求**: 需要指定 path maps 和 policy predicates
3. **仅观察状态**: 不能证明未检索的事实
4. **基准局限**: 主要在基准测试中评估，非真实生产流量

## 借鉴点（关联 Hermes Agent / Jetson Orin / 量化交易）

### ✅ 已部分实现 → 标注增量价值

| 借鉴点 | 现状 | 增量价值 |
|--------|------|----------|
| Hermes Agent 的 state management | 通过 memory 和 session 管理状态 | Ledger 模式可将状态显式化，减少 transcript 挖掘成本 |
| 工具调用策略校验 | 部分通过 prompt 指令实现 | Policy Gate 模式可预执行校验，减少无效调用 |

### 🔨 可直接移植 → 估算工作量

| 借鉴点 | 工作量 | 说明 |
|--------|--------|------|
| Ledger 状态模块 | 1-2 天 | 为 Hermes 工具调用层添加 ledger 状态管理，记录已观察的工具返回 |
| Policy Gate 拦截器 | 0.5-1 天 | 在工具执行前增加谓词检查层，支持 allow/revise/block 三种结果 |

### ⚠️ 需工程改造 → 标注关键障碍

| 借鉴点 | 障碍 | 说明 |
|--------|------|------|
| observe-not-assume 规则 | 需改造工具调用链 | 当前 Agent 可能直接假设 write 成功，需强制 read 确认 |
| 领域规范复用 | 需设计配置系统 | path maps 和 predicates 需要可配置的域级规范 |

### ❌ 暂不适用 → 说明原因

- 非结构化任务（如创意写作、图像生成）不需要 ledger 状态管理
