中断/DMA/外设驱动实战 — 从 NVIC 优先级到 Cache 一致性，高速外设驱动的三层纪律

生成日期 2026-11-11

摘要

中断/DMA 驱动开发的核心不是"会开 DMA"，而是三层纪律：① 中断层——NVIC 优先级编码的是抢占层级，ISR 长度的红线是"超过 1 字节时间就转队列"；② 缓冲层——高吞吐收发的标准形态是 DMA 环形缓冲 + 半满(HT)/全满(TC)/空闲(IDLE) 三中断协同 + 软件乒乓，单缓冲靠半满中断拆成两半用，硬件 DBM 双缓冲(M0AR/M1AR)则彻底消灭重开 DMA 的窗口，实测 2Mbps 串口 66 分钟 0 丢包、385KB/s 无压力；③ 内存层——Cortex-M7 一类带 D-Cache 的 MCU 上，CPU 看 Cache、DMA 看内存，同一地址两个视图，必须按方向维护（CPU写DMA读→Clean，DMA写CPU读→Invalidate）、按 32 字节 Cache Line 对齐、用 MPU+链接脚本把 DMA Buffer 隔离成专门段。最隐蔽的坑都出现在"非整 Cache Line 长度"（31/33 字节）与"所有权不清"时，且表现为偶发、难复现、Debug 正常 Release 出错。

关键发现

F1 NVIC 的正确心智模型：优先级编码抢占层级，ISR 长度看"服务窗口"

NVIC 判定流（Cortex-M）:
  新中断到达 ──▶ 比当前优先级高? ──是──▶ 抢占(preempt)当前ISR, 嵌套
                    │否
                    ▼
              挂起(pend)记入NVIC pending位
                    │
  当前ISR返回 ──▶ tail-chaining: 不出handler模式, 直接向量到pending中最高优先级
  • 抢占优先级 vs 子优先级：只有抢占优先级能中断正在执行的 ISR；同抢占级/更低级的中断一律 pend，等 ISR 返回后 tail-chain。工程惯例：用优先级位编码抢占层级，层级内的排序只在负载高且持续时才有意义（ST 社区工程师口径）
  • 服务窗口思维：先算清每个中断的到达率和窗口。DMA HT/TC 若每 100ms 才来一次且不需要立即干预，就不配超高优先级——优先级是给"到达快 + 必须快响应"的源准备的
  • ISR 长度红线：串口类任何超过 1 字节时间 的处理都应"取数据→入队→立刻返回"，其余交给任务层。多外设并存时典型分配：UART=0（关键），SD/WiFi=1，LCD=2-3
  • AVR/PIC 等无嵌套硬件的架构里 ISR 内 sei() 重开中断是高危操作；Cortex-M 的 NVIC 天然支持嵌套+tail-chaining，延迟以周期计

F2 高吞吐串口接收的标准形态：环形 DMA + HT/TC/IDLE 三中断 + 软件乒乓

三个中断各司其职（HAL 侧全部汇入 HAL_UARTEx_RxEventCallback(huart, Size)，无需区分来源，只需累计游标）：

单缓冲(20B)收25B不定长包的时序:
  [0..9]半满──▶HT中断(处理前半)   [10..19]全满──▶TC中断(处理后半)
  [20..24]总线静默1字节时间──▶IDLE中断(把尾巴交出去)

  DMA(Circular)自动回卷到缓冲区起点, 无需重开
  • 为什么必须半满中断：只有 TC+IDLE 的常见教程写法有竞态——CPU 处理到一半，DMA 继续写把未读数据覆盖。半满中断把一个缓冲区拆成乒乓两半：DMA 写后半时 CPU 处理前半，天然形成所有权边界
  • IDLE 是不定长数据的实时性关键：70 字节包 + 32B 双缓冲场景，若只靠 TC，最后 6 字节要等下一帧才上交；字节流不连续时上层会误判丢包。TC(保吞吐) + IDLE(保实时) 组合才完整
  • 回调极简模式（博客园扑鱼，实测 FT232 2Mbps 66min 0丢包、转发延迟 ~400µs）：
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size) {
    static uint16_t pos = 0;
    uint16_t len = Size - pos;
    fifo_s_puts(&uart_rx_fifo, &rx_buf[pos], len);  // ISR内只做入队
    pos += len; if (pos >= RX_BUF_SIZE) pos = 0;
}
  • 硬件双缓冲（DBM）是更强形态（知乎 385KB/s 0丢包方案）：F1/F4 的 DMA 有 M0AR/M1AR 两个地址寄存器，置 DMA_SxCR_DBM 位后写满自动切换，CPU 与 DMA 各处理各的缓冲，连"重开 DMA 装载"的窗口都不存在；配合关掉无意义的 HT 中断（ATOMIC_CLEAR_BIT(..., HTIE)）进一步降中断频率
  • 软件 FIFO 是驱动层/应用层的隔离带：ISR 回调只压 FIFO，应用只读 FIFO，把"RX_Buf 会被覆盖"的时限压力转化为"FIFO 水位"的可监控压力。注意区分：DMA 外设自带的 FIFO（攒批减少总线传输）≠ 软件环形 FIFO（解耦时序），高速不定长场景常用直接模式+软件FIFO

F3 Cortex-M7 的内存一致性：CPU 看 Cache，DMA 看内存

        写路径              读路径
CPU ──▶ D-Cache ──dirty──▶ SRAM      CPU ──▶ D-Cache命中(可能是旧值!)
DMA ─────────直通────────▶ SRAM      DMA ─────────直通────────▶ SRAM
        ↑ 同一地址, 两个视图, MCU的DMA不参与硬件一致性协议(无ACE/CHI)

典型症状清单（tech-snippets 实战文，2026-06）：DMA 写完 CPU 读到旧数据 / CPU 填好发送包网卡发出上一帧 / 关 D-Cache 就稳但吞吐暴跌 / 加一句 Clean 偶尔好偶尔坏 / Debug 正常 Release 出错 / 20 字节 buffer 旁边变量被"污染"。

维护方向口诀：
- CPU 写 → DMA 读（发送）：启动 DMA 前 Clean（把脏行写回内存）
- DMA 写 → CPU 读（接收）：DMA 完成后 Invalidate（丢掉旧行，强制从内存取）
- 双向/不确定：慎用 CleanInvalidate——可能把 DMA 新写的数据被旧脏行覆盖

三个工程化手段（从"到处补维护函数"升级为系统设计）：

  1. Cache Line 对齐：维护 API 必须按 32 字节行边界扩展（align_down/align_up 后再调 SCB_CleanDCache_by_Addr）。20B buffer 与邻变量共享同一行时，Invalidate 会误杀邻变量的修改、Clean 会误提交
  2. 链接脚本隔离：__attribute__((aligned(32))) 只保起点，不保邻居。正规做法是 .dma_desc（Non-cacheable）与 .dma_buffer（Cacheable+手动维护）两个专用段，审查 map 文件一眼可见，MPU 可整段设属性
  3. MPU 固化属性：把"谁可缓存/可否 DMA 访问"的约定变成启动时硬件配置——描述符段 Non-cacheable 保确定性，大数据段 Cacheable 保吞吐，外设寄存器 Device 类型禁缓存

F4 内存区域不是只看大小：DTCM/AXI SRAM/SDRAM 的可达性差异

区域 CPU访问 DMA访问 适配用途
DTCM RAM 极快 多数 DMA 不可达 栈、实时控制变量、算法中间态
AXI SRAM 快(经Cache) 可达 大块 DMA Buffer 首选
外部 SDRAM 慢(须Cache) 可达 帧缓冲、张量、文件缓存

把 DMA buffer 放 DTCM = 直接失败（DMA 不搬运/外设无数据），且现象像"玄学"。第一原则：先问"谁访问它、走哪条总线、过不过 Cache、DMA 能否到达"，再问大小。

F5 所有权模型与回归测试：把偶发问题变成开发期必然暴露

  • 所有权状态机替代"到处加 Invalidate"：每个 buffer 明确处于 CPU-owned 或 DMA-owned，所有权切换点（提交描述符/中断回收）上做维护动作；DMA 拥有期间 CPU 禁止访问，调试打印也不例外——否则再多维护函数只是降低概率，不是根治
  • 边界回归用例：内存到内存 DMA 环回，偏移 0/1/15/31/32/33，长度 1/16/31/32/33/127/1500，CPU 前后算 CRC。31/33 字节这类非整行长度最能暴露问题；能在 D-Cache 开启+最高优化+RTOS 切换+中断压力下连跑数小时才算内存纪律可信
  • 团队规范落点：DMA buffer 统一宏声明、禁随手 static uint8_t buf[1024]、驱动评审必答"内存区域/方向/维护动作/对齐策略"四问

与现有工作的关联

  • P0｜DUCK pi5 STS 舵机串口读：servo-serial-read-write-quirks 记录的"定时读数必欠行程"本质是轮询窗口与运动时序错位。本篇 F2 的 DMA+IDLE 思路可迁移：IDLE 中断恰好解决"不定长回帧、不知道何时结束"的读回时序问题——pi5 是 Linux 侧（termios/异步IO）不直接用 MCU DMA，但 HT/TC/IDLE 的三中断协同+游标累计模式对 Linux 串口转发的线程设计同构
  • P1｜ASC 云台 ESP32 固件（用户 Arduino 自编译）：ESP32 内部 RAM 无 D-Cache 一致性问题，但 ESP32-P4/S3 + PSRAM 场景同理（esp_cache_msync），若后续摄像头帧缓冲上 PSRAM 必踩。CAM 采集 + 舵机 PWM 的双高优先级源即 F1 服务窗口思维的直接应用
  • P2｜未来 H7 级项目：若上 STM32H7/i.MX RT 做图像/以太网网关，F3/F4 的 MPU+链接脚本方案应直接进工程模板，31/33 字节回归用例作为 bring-up 第一项

Actionable Insights

  1. 写任何 DMA 收发驱动前先画三条线：中断到达率、缓冲所有权边界、数据流方向（决定 Clean/Invalidate）
  2. 不定长高速串口 = Circular DMA + HT/TC/IDLE 三中断 + 软件 FIFO，回调里只准入队；有 DBM 硬件就用双缓冲寄存器
  3. M7 平台 DMA buffer 三件套：32 字节对齐、专用链接段、所有权切换点维护；Never 在 DMA 活跃期读 buffer（包括 printf）
  4. 优先级分配先做"服务窗口"表（源×到达率×容忍延迟），再编码抢占层级；ISR 超过 1 字节时间即违例

关键风险与盲点

  • Cache 一致性方案与芯片强相关：本文以 STM32H7/Cortex-M7 为准（官方架构行为）；MPU/链接脚本细节各厂不同，落地前必查具体手册（来源级别：官方文档+工程实践文）
  • 2Mbps/385KB/s 数字来自爱好者实测（FT232 模块限制下的天花板），非厂商保证值；F407 理论上限更高
  • DBM 双缓冲仅 F1/F4 等部分系列支持；G0/H7 的 DMA(BDMA/MDMA) 结构差异大，不可直接照抄寄存器名

一页速查

NVIC: 抢占级编码层级 | ISR≤1字节时间, 其余入队 | 先算服务窗口再分配优先级
三中断: HT=乒乓切换点, TC=保吞吐, IDLE=不定长尾巴的实时性 | HAL 统一进 RxEventCallback(Size), 游标累计即可
双缓冲: 软件乒乓=半满中断拆单缓冲 | 硬件 DBM=M0AR/M1AR+DBM位, 满自动切换零窗口
Cache: CPU写DMA读→Clean(前) | DMA写CPU读→Invalidate(后) | 按32B行对齐 | .dma_desc/.dma_buffer 专用段+MPU
内存: DTCM 多数DMA不可达 | AXI SRAM=DMA首选 | SDRAM须Cache更要维护
测试: 偏移0/1/15/31/32/33×长度1~1500 环回+CRC, 31/33字节最暴露问题
