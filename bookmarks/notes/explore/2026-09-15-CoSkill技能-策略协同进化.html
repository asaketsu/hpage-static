查询拓展

  1. 技能进化三范式批判：论文将现有方法归纳为三类——(a) 外部编排（SkillRL, D2Skill, ReSkill, Trace2Skill）将技能库视为独立知识库，进化与策略学习脱节；(b) RL优化技能库管理（SAGE, ARISE, Skill1）将技能生命周期纳入RL但粒度太粗，技能被视为原子对象；(c) 元技能驱动优化（SkillOpt, EvoSkill, SkillEvolver, MetaSkill-Evolve）用执行反馈优化单个技能但依赖预定义工作流，推理Agent被冻结。CoSkill指出三者共同的结构性缺陷：技能被视为被动管理对象，而非可与推理策略协同进化的主动参与者。

  2. MSMDP建模：CoSkill将推理Agent和元技能Agent的交互建模为共享参数的多Agent半马尔可夫决策过程（MSMDP），关键创新在于元技能Agent的更新具有延迟信用分配——Reasoning Agent执行后，Meta-Skill Agent提出编辑，经过验证后才获得奖励。两个Agent共享同一LLM骨干（Qwen2.5-7B-Instruct），通过角色特定的观测空间和动作空间区分行为。

  3. Post-Edit Skill Verification机制：元技能Agent提出编辑后，不立即写入技能库，而是在私有编辑包上重新执行任务M次，计算平均改善Δ_skill = (1/M)ΣR^(m) - R^(0)。只有当编辑是有效的、非平凡的、且改善验证成功率时，才作为晋升候选。每个任务组内只晋升前K_prom个候选版本，原始包保留以保持血缘。这一机制防止了技能库的无序膨胀。

  4. GiGPO联合优化：Group-in-Group Policy Optimization为每个角色ρ∈{R,S}计算两级优势：episode级相对优势A_E（比较同任务rollout间的完整回报）+ step级相对优势A_S（比较同状态下的不同决策）。推理轨迹用(x,o_t)作为锚点状态，技能编辑用(x,o_t,Z_t^step)作为锚点。两个角色的loss联合更新共享actor：L(θ) = L_GiGPO^R(θ) + L_GiGPO^S(θ)。

  5. 与Hermes Agent的关联：论文的实验结论"对齐技能精炼与目标环境奖励比编辑器规模更重要"直接挑战了用GPT-4/Gemini等大模型作为技能编辑器的思路（如D2Skill用Gemini-3-Flash，CoSkill用7B模型反而更好）。这对Hermes Agent的Skill进化策略有直接启示：与其依赖外部大模型审查Skill，不如让Skill进化本身可学习、可对齐到实际任务表现。

核心问题与研究动机

现有AI Agent技能库方法的三大结构性缺陷：

  • 外部编排范式：技能库进化由外部LLM或人工规则驱动，脱离策略学习。技能库增长后内容可能过时、冗余或与策略不一致。
  • RL粗粒度管理：将技能生命周期（创建/删除/保留）纳入RL优化，但技能本身被视为不可分割的原子对象。有用的但不完美的技能可能被删除而非精炼。
  • 固定元技能工作流：用执行反馈优化单个技能，但依赖预定义的元技能程序（评分提示、SKILL.md规范、多Agent工作流），推理Agent被冻结，无法与策略协同适应。

核心洞察：将元技能建模为RL训练的可学习Agent（而非固定工作流），使其更新策略与推理策略协同进化，这是关闭技能-策略回路的关键。

方法论

层级技能库

技能库结构为 B = {B_k}_{k=1..K}，每个技能包 B_k = (s_k^task, S_k^step)：
- 任务技能 s_k^task：提供episode级全局指导
- 步骤技能集合 S_k^step：包含中间观测的局部程序

检索策略是层级约束的：
1. 全局检索任务技能：k = argmax_k sim(f(x), f(q_k))
2. 仅在该任务技能的子集中检索步骤技能：jt = argmax{j∈S_{k}^step} sim(f(o_t), f(o_{k,j}))

初始技能库从离线经验构建：ALFWorld 300个任务技能+1625个步骤技能，WebShop 300+1406。使用GPT-5.5生成初始技能库。

共享参数多Agent半马尔可夫决策过程

  • 全局状态：g_l = (x, ρ_l, H_l, B, B~_l, Z_l)，包含任务、活跃角色、交互轨迹、技能库、私有编辑包、待处理编辑
  • 角色特定观测：推理Agent观测 u^R_t = O_R(当前任务状态 ∪ 交互历史 ∪ 检索技能)；元技能Agent观测 u^S_t = O_S(推理上下文 ∪ 推理动作 ∪ 环境反馈)
  • 异构动作空间：共享策略π_θ和token空间V*，通过角色prompt引导不同语义动作空间
  • 时间嵌套：推理Agent先行动，环境返回(o_{t+1}, r_t, e_t)后，元技能Agent才观测并提出编辑

Post-Edit Skill Verification奖励

元技能Agent提出编辑序列后：
1. 在私有编辑包B~_i上重新执行任务M次
2. 计算平均改善：Δ_skill = (1/M)Σ R^(m) - R^(0)（baseline减数控制任务难度）
3. 只有有效、非平凡、改善验证成功率的编辑才成为晋升候选
4. 每个任务组内只晋升前K_prom个版本，原始包保留血缘

GiGPO联合优化

  • 推理轨迹存于D^R，元技能编辑存于D^S，按rollout索引配对
  • 两级优势：A_{i,t}^ρ = A_E,i^ρ + ω_ρ * A_S,i,t^ρ
  • Episode级：推理比较同任务rollout回报，编辑比较同任务+同基础技能的Δ_skill
  • Step级：推理锚点(x,o_t)，编辑锚点(x,o_t,Z_t^step)，比较同状态下不同决策
  • 两个角色分别归一化episode和step统计，防止任务执行和技能验证之间的奖励尺度泄露
  • 联合更新：L(θ) = L_GiGPO^R(θ) + L_GiGPO^S(θ)

关键实验结果与数据

主实验（Table 1）

ALFWorld成功率：
- CoSkill：98.4%（平均），5/6个任务类型100%
- 最强基线RetroAgent：94.9%（+3.5pp提升）
- SkillRL：89.9%（+8.5pp）
- D2Skill(Gemini-3-Flash)：90.6%（+7.8pp）
- GiGPO无技能：90.8%（+7.6pp）

WebShop成功率和分数：
- CoSkill：90.6%成功率 / 95.9分
- 最强基线：84.4% / 91.6分（+6.2pp / +4.3分）

关键发现：CoSkill用7B模型（Qwen2.5-7B-Instruct）超越用Gemini-3-Flash的D2Skill，证明"对齐技能精炼与目标环境奖励比编辑器规模更重要"。

消融实验（Table 2）

训练Step 20 → Step 120的成功率变化：

  • 完整CoSkill：70.31% → 95.31%
  • w/o Meta-Skill Agent RL：57.81% → 92.19%（早期差12.5pp，最终差3.12pp）
  • w/o 层级技能库：56.25% → 93.75%（早期差14.06pp，后期差距缩小）
  • Alternating Updates=10：62.50% → 78.12%（Step 60暴跌25pp！）
  • Alternating Updates=20：59.38% → 81.25%（Step 60暴跌18.75pp！）

关键发现：稀疏交替更新（Alternating Updates）造成最大的后期退化，说明高频协同训练（每步都联合优化）远优于低频交替。

学习动态（RQ3）

编辑行为分布：
- 有RL：收敛到97-99% Update，删除几乎消失
- 无RL：Update从73%降到54%，Delete从13%升到36%

技能库增长：
- RL减少累计晋升47.6%（387 vs 739次），但下游表现更强
- 无RL的冗余增长反映"编辑器看似活跃但贡献甚微"

检索可靠性：
- RL版本：最终窗口空步骤包率0.2%
- 无RL版本：空步骤包率12.4%
- 两者检索命中率都接近100%，但无RL版本逐渐退化

训练成本

ALFWorld训练160步：8张GPU × 66小时 = 约526 GPU-hours（使用veRL框架 + verl-agent）

创新点分析

  1. 元技能Agent化：将元技能从固定工作流转变为RL训练的可学习Agent，这是从"被动管理"到"主动协同"的范式转变。元技能Agent不再是工具，而是与推理Agent平等的协作者。

  2. 共享参数设计：两个Agent共享同一LLM骨干，通过角色特定观测和动作空间区分行为。这避免了参数冗余，同时使两个角色能共享底层语言能力。

  3. Post-Edit Verification作为RL奖励：不依赖人类标注或规则，而是用任务执行结果本身作为技能编辑的信用分配信号。Baseline减数+多次验证平均控制了任务难度和rollout方差。

  4. 层级检索约束：任务技能固定候选子树，步骤技能仅在子树内检索。这减少了无关技能的干扰，使检索和编辑都更聚焦。

  5. GiGPO两级优势：Episode级和Step级优势的组合使技能编辑获得精细的信用分配——不仅知道整体好不好，还知道哪一步该怎么做。

局限性与未来方向

  1. 评测环境局限：仅在ALFWorld（文本家务）和WebShop（电商搜索）两个环境验证，未测试更复杂的真实Agent场景（如编程、多工具协作）。
  2. 训练成本高：526 GPU-hours的训练成本对边缘部署或资源受限场景不可行。
  3. 初始技能库依赖离线生成：需要GPT-5.5预先生成300+技能，初始成本不可忽略。
  4. 共享骨干限制：两个Agent共享同一模型，可能无法表达足够不同的角色行为。论文承认未来需要"更高效的交互、信用分配和更新机制"。
  5. 未与Hermes Agent场景直接对比：论文未评估在Hermes这类多工具Agent系统上的适用性。

归纳总结

CoSkill的核心贡献是将AI Agent的技能进化从"被动管理"提升到"主动协同"：

  • 范式转变：元技能从固定工作流→RL训练的可学习Agent，与推理Agent共享骨干、协同进化
  • 机制创新：Post-Edit Verification将任务执行结果直接作为技能编辑的奖励信号，Baseline减数+多次验证消除难度偏差
  • 理论框架：MSMDP+GiGPO提供严格的联合优化理论，两级优势实现精细信用分配
  • 实验证据：98.4% ALFWorld / 90.6% WebShop成功率，7B模型超越Gemini-3-Flash基线，证明对齐比规模更重要
  • 关键消融：高频联合训练远优于低频交替（Alternating Updates=10时Step60暴跌25pp）

对Hermes Agent Skill自进化最核心的启示：技能编辑必须与任务执行结果对齐，而不是依赖外部大模型的语言判断。当前的Skill进化（skill-review、evolver等）本质上是"外部编排"范式，CoSkill提供了"联合优化"范式的具体实现路径。

趋势判断

  1. 技能进化将走向RL对齐：论文用消融实验证明RL对齐的Meta-Skill Agent优于外部LLM编辑（7B vs Gemini-3-Flash）。未来Agent的技能库进化将越来越依赖任务反馈而非人工规则或大模型审查。

  2. 层级技能库将成为标准架构：任务级+步骤级的层级约束检索比扁平检索更可靠（消融显示层级缺失导致早期训练差14pp）。这对Hermes当前扁平的SKILL.md结构提出改造需求。

  3. 验证驱动的技能晋升将成为共识：Post-Edit Verification（编辑后重新执行任务验证改善）是防止技能库膨胀的关键机制。当前Hermes的skill-review是事后审查，而CoSkill是事前验证。

  4. 共享参数多Agent将兴起：单模型多角色（通过角色特定prompt和观测空间区分）比多模型方案更经济、更协调。这对Hermes的"单Gateway多Agent"架构是直接印证。

  5. 高频联合训练将取代低频交替：消融实验显示Alternating Updates=10在Step 60暴跌25pp，说明技能-策略协同必须持续进行，不能间歇性执行。这对Hermes的Skill自动审查频率提出了新要求——不能每周才检查一次，而应每次执行后即时反馈。

关联

  • SPyCE (2607.13854)：技能-策略协同进化闭环 + 分层技能抽象（执行技能三元组 + 工作流技能二元组）+ merge-or-add合并规则。与CoSkill的层级技能库高度相关，SPyCE的merge规则可补充CoSkill的晋升机制。
  • OpenForgeRL (2607.21557)：Harness-native Agent端到端RL训练，代理拦截+轨迹重建。CoSkill的轨迹配对机制可借鉴OpenForgeRL的harness架构实现。
  • EvoSOP (2607.07321)：Agent自进化工具生命周期管理四模块（Construct/Merge/Evaluate/Prune）。CoSkill的Post-Edit Verification对应EvoSOP的Evaluate模块，但CoSkill更强调RL对齐而非规则评估。
  • Ecdysis (2026-09-12笔记)：Harness自进化失败归因。CoSkill的RQ3动态分析（无RL时Delete从13%升到36%）提供了失败归因的量化证据。
  • MAPLE (2026-09-11笔记)：记忆增强规划与进化。CoSkill的层级技能库与MAPLE的记忆层级有结构相似性。
  • 门控记忆路由 (2026-09-14笔记)：多Agent编排中的门控记忆路由。CoSkill的角色特定观测空间（O_R和O_S）是门控的一种实现。
  • Tool-Making (2607.08010)：SOP→工具离线编译流水线。CoSkill的初始技能库构建（离线生成300技能）是类似的离线编译过程。

拓展应用推荐

P0：Hermes Skill进化对齐到执行反馈

当前状态：Hermes的Skill进化（skill-review, evolver）依赖事后审查和人工规则，属于"外部编排"范式。

CoSkill启示：技能编辑的奖励信号应来自实际任务执行结果，而非外部LLM的语言判断。

可落实方案：在Hermes的post_task_hook或skill-review中引入Post-Edit Verification机制——每次修改Skill后，重新执行一个关联的测试任务，只有当执行结果改善时才晋升修改。参考CoSkill的Δ_skill计算：新Skill执行成功率 - 旧Skill执行成功率 > 阈值才接受。

工作量估算：中等（需要定义"关联测试任务"和"成功率度量"，约2-3天）。

P1：层级技能库改造

当前状态：Hermes的SKILL.md是扁平结构，所有技能在同一层级。

CoSkill启示：任务级+步骤级的层级约束检索比扁平检索更可靠（消融显示早期训练差14pp）。

可落实方案：为Hermes Skill引入category→skill→step的三层结构。顶层category（如devops, productivity）对应任务技能，skill对应步骤技能，检索时先定位category再在子集内检索具体skill。可通过修改skill_manage的category字段和检索逻辑实现。

工作量估算：较高（涉及skill索引、检索逻辑、frontmatter结构的多处改动，约1周）。

P2：技能晋升门控

当前状态：Hermes的skill_manage create/patch没有验证机制，任何修改都会被接受。

CoSkill启示：只有有效、非平凡、改善验证成功率的编辑才晋升（CoSkill用Δ_skill + 有效非平凡检查 + top-K晋升）。

可落实方案：在skill_manage的create/patch动作中加入"轻量验证"——创建/修改Skill后，运行一个简单的验证命令（如检查SKILL.md格式、执行示例命令），验证通过才commit。类似于CoSkill的Post-Edit Verification但更轻量。

工作量估算：低（可在skill_manage的action='create'/'patch'后追加验证步骤，约1天）。

P3：高频Skill审查替代低频

当前状态：Hermes的skill-review是定期回顾（手动或cron触发）。

CoSkill启示：Alternating Updates=10在Step 60暴跌25pp，说明稀疏更新比无更新更糟。

可落实方案：将Skill审查从"定期回顾"改为"每次执行后即时反馈"。在idle-busy-loop或post_task_hook中增加Skill执行效果检查，发现退化立即标记待审查。

工作量估算：中等（需要修改cron和hook逻辑，约2-3天）。

指南分析

如何在Hermes中实现CoSkill的核心思想

  1. 识别当前范式：Hermes当前处于"外部编排"范式（Skill由人工规则或evolver审查生成），属于CoSkill批判的第一类范式。需要向"联合优化"范式迁移。

  2. 最小可行改造：不需要完整实现多Agent RL（成本太高），但可以借鉴三个核心机制：

  3. Post-Edit Verification：修改Skill后验证效果（P0/P2）
  4. 层级检索约束：category→skill→step（P1）

  5. 晋升门控：只有通过验证的编辑才commit（P2）

  6. 渐进式路径：

  7. 第一步（1天）：在skill_manage中增加create/patch后的格式验证
  8. 第二步（2-3天）：为post_task_hook增加Skill执行效果反馈
  9. 第三步（1周）：改造Skill检索逻辑为层级结构

  10. 第四步（2周+）：实现基于执行反馈的Skill进化闭环

  11. 成本意识：CoSkill的完整RL训练需要526 GPU-hours，Hermes不需要也不可能复现。但核心思想——"技能编辑应与任务执行结果对齐"——可以用零训练成本实现：只需在修改Skill后执行一次验证任务，比较修改前后的成功率。

  12. 避免的陷阱：

  13. 不要照搬CoSkill的多Agent架构（Hermes不需要两个独立Agent）
  14. 不要追求RL训练（526 GPU-hours不现实）

  15. 不要忽略初始技能库成本（CoSkill用GPT-5.5生成300技能，Hermes可以逐步积累）
