# Screenshots or Tools? 混合 GUI-MCP 智能体的工具采纳鸿沟与上下文压缩

## 元数据

- **标题**: Screenshots or Tools? Eliciting Tool Use and Managing Multimodal Context in Hybrid GUI-MCP Computer-Use Agents
- **作者**: Siqi Fan, Minghao Li, Xiaoqian Ma, Wenhui Tan, Xiusheng Huang, Juntong Wu, Liujie Zhang, Shuo Shang, Weihang Chen
- **日期**: 2026-08-04
- **arXiv ID**: 2608.03327
- **领域**: Artificial Intelligence (cs.AI)
- **代码**: 已开源（checkpoints + code）
- **基准**: OSWorld-MCP（309 tasks, 9 application namespaces, 120 MCP tools）

---

## 核心问题与研究动机

混合计算机使用智能体（Computer-Use Agents, CUAs）有两条行动路线：

1. **截图路线**（GUI）: 通过点击像素坐标操作，通用但昂贵脆弱——每帧消耗 ~2K vision tokens，视觉历史随轮次膨胀
2. **工具路线**（MCP）: 调用文本级工具（MCP servers, CLIs, agent skills），精确廉价但无视觉确认

论文提出了一个**前置问题**: 当有用的工具已经可用时，模型真的会决定使用它吗？

核心发现: **可用性本身并不决定效果的符号（正/负）。** 同一套 MCP 工具和注入 harness 下，推理模型提升 +4.0pp，非推理模型下降 -5.9pp。

---

## 方法论

### 统一混合行动空间

GUI 动作和 MCP 工具通过**同一个调用面**呈现。每步模型发出一个 `<tool_call>` 对象：
- 要么 `computer_use`（11种原语: click, drag, scroll, key, type, wait, terminate 等）
- 要么检索到的 MCP 工具

两者出现在同一个 `<tools>` block 中，无外部控制器路由——模型必须在一个 action head 内选择走像素还是走文本工具。

### 上下文构建

- 系统消息 σ(T_t): 格式规则 + BM25 检索的 top-18 工具集
- 视觉记忆: 最近 k 张截图的滑动窗口（默认 k=4）
- 文本轨迹 H_t: 每步的一行摘要，全文保留
- 工具结果 r_i: 截断至 L=1500 字符

两个记忆通道运行在不同时间尺度: 像素按深度 k 窗口化，文本全量保留。

### 两个研究层面

**Action Level（动作层面）**: 模型选择点击像素还是调用文本工具
**Context Level（上下文层面）**: 工具调用成功后，选择保留下一张截图还是依赖文本结果

### 两个上下文旋钮

1. **图像历史深度 k**: window-4（最近4张） vs window-2（最近2张）
2. **Drop-on-success 规则**: 若上一步 MCP 调用执行成功（succ_mcp），则将下一张截图替换为文本占位符 π

### 多轮 GRPO 训练

- G=8 trajectories, 96 并行环境, T_max=50
- 回报: R(τ) = succ(τ) - λ_len·T/T_max - λ_cap·𝟙[T≥T_max]
- Dr.GRPO 风格长度去偏: z-score 组内归一化 + 1/T 广播
- **密集工具奖励 b_t**: 归一化**之后**添加（放在 R(τ) 内会被稀释至 ~10^-4），每次 trajectory 中每个 (tool, arguments) key 只触发一次，λ_mcp=0.1
- 梯度带筛选: 仅保留 pass rate ∈ (0.1, 0.9) 的 74 个任务

## 关键实验结果与数据

### 1. 符号反转（Sign Reversal）

同一套 MCP 工具 + harness，唯一变量是基座模型：

- **推理模型**（Qwen3-VL-8B-Thinking）: +4.0pp（提升）
- **非推理模型**（Qwen3-VL-8B-Instruct）: -5.9pp（下降）
- 两者均超过 2 SE 显著性

### 2. 采纳鸿沟（Adoption Gap）

即使受益的推理模型也严重低用:
- 任务级工具调用率: **17.8%**（55/309 tasks）
- 可达任务中的调用率: **23.9%**（55/230 tool-reachable tasks）
- VLC 域: 16/17 任务可达，但**从不调用工具**

### 3. 失败模式诊断

- **非推理模型**: 忽略工具、误名工具（97个虚构工具名 in 2 tasks）、虚假终止率 33.0%（102/309）
- **推理模型**: 虚假终止率 21.7%（67/309），无虚构工具名
- 关键差异: 非推理模型采纳更少却虚假终止更多

### 4. Token 成本分析

| 配置 | 输入 tokens | 峰值 p95 | tok/1%acc |
|------|------------|----------|-----------|
| Thinking GUI+MCP win4 | 342K | 11487 | 11.0K |
| Thinking ctx_opt(win2+drop) | 219K | 7243 | 7.7K |
| Instruct GUI+MCP win4 | 310K | 11437 | 14.9K |

ctx_opt 配置削减输入约 1/3，峰值上下文近 40%。

### 5. RL 结果 1: 工具奖励移动采纳，不移动能力

- 表格工具采纳率: 0.03 → 0.33（23 步训练内）
- 迁移到贪婪解码: 0.02 → 0.29（已学习策略，非采样噪声）
- 但 48 个 held-out 任务: **零个持续 fail→pass 翻转**
- 结论: **行为可引导，能力不可引导。瓶颈在工具调用语义**

### 6. RL 结果 2: 训练-推理观测规则匹配

- 仅推理压缩: ctx_opt 损失 -3.9pp（±1.0）
- 匹配重训练后:
  - 压缩 checkpoint 达到 **37.8%** vs 未压缩基线 **33.0%**（+4.8pp）
  - 输入成本仅 **53%**
  - D13 退化子集 rich-lean gap **归零**
  - 235 个非训练任务: +0.8pp（n.s.，无 OOD 损失）
- 关键发现: 富观测对照组学习更快（+20.5pp vs +11.5pp），但压缩运行输出 tokens 仅 10.7K vs 42.6K

### 7. 核心洞察

**两个层面共享一个形状: 更便宜的路线已存在，但训练中没有任何东西教会策略去走它。**

- 工具存在但未被使用
- 压缩观测可负担但不熟悉
- 培训信号需要教工具语义（而非仅奖励工具决策）
- 训练和推理的观测规则必须匹配

## 创新点分析

1. **前置问题转换**: 不问"工具集够不够好"，而问"模型是否决定使用已有工具"——将研究焦点从系统设计转向策略行为
2. **符号反转现象的发现**: 同一工具对不同模型产生相反效果，且方向由工具决策行为决定——这解释了之前互相矛盾的文献报告
3. **采纳鸿沟的形式化**: 将"工具被注入但未被使用"从模糊现象提升为可度量的失败模式
4. **密集奖励归一化后注入**: 发现传统轨迹级奖励会把工具信号稀释至 10^-4，必须在 z-score 归一化后单独添加
5. **训练-推理观测匹配**: 将压缩折扣从 OOD 问题重新框定为分布不匹配问题，通过匹配训练消除

---

## 局限性与未来方向

1. **工具语义瓶颈未解**: RL 能改变工具决策但不能提升工具能力，成功调用的参数质量仍是开放问题
2. **执行级成功 ≠ 语义成功**: succ_mcp 只验证调用解析成功，find-and-replace 可返回成功但零替换，drop 规则会丢弃视觉纠错信号
3. **增益主要在分布内**: 全量 37.8% 中约 4.1pp 来自 74 个训练任务，非训练任务增益不显著
4. **DiD 预注册标准未达**: +15pp 差异标准未满足（实际 +7.7~+9.0pp），作者诚实记录为失败而非修改阈值
5. **视觉不可完全替代**: 约 1/4 任务是工具不可达的（CAPTCHA、滑块重着色、重度浏览器交互），截图路线不可消除
6. **近无损非无损**: 表格和幻灯片任务仍需视觉确认

## 借鉴点评估（关联 Hermes Agent）

### P0: 工具采纳鸿沟检测器

**问题**: Hermes Agent 有大量 skills/tools，但实际使用率可能很低。论文发现推理模型仅使用 23.9% 的可用工具。

**建议**:
- 在 Gateway 日志中统计各 skill/tool 的实际调用率 vs 可调用率
- 识别"已注入但从未被使用"的 skills
- 对低采纳 skills 检查: 是否因为 skill description 不够清晰（类似非推理模型的"误名工具"），还是模型从未学会走这条路线
- 参考论文的 TIR 指标（tool invocation rate = MCP steps / total steps）建立工具使用健康度

### P0: 训练-推理上下文一致性原则

**问题**: 论文证明仅推理时压缩上下文会损失 -3.9pp，但匹配训练后反而提升 +4.8pp。这直接关联 Hermes 的 system prompt 和 context engineering。

**建议**:
- 确保 skill 的描述、触发条件与实际部署时的上下文构建方式一致
- 当修改 system prompt 或 context 注入方式时，考虑"分布偏移"效应——模型在 A 上下文下训练，在 B 上下文部署会退化
- 对 Hermes Gateway 的 context 构建流程做一致性审计

### P1: 上下文压缩中的工具结果冗余消除

**问题**: 论文的 drop-on-success 规则——工具调用成功后丢弃下一张截图（结果已在文本中），削减 1/3 输入 tokens。

**建议**:
- 在 Hermes 工具调用后的上下文管理中，检测工具输出是否已包含足够信息，避免重复保留冗余上下文
- 尤其适用于 web_extract 后再 read_file 同一内容的场景
- 实现 cost-aware context pruning: 工具成功后标记"信息已覆盖"，下游步骤跳过冗余读取

### P2: 密集奖励归一化后注入

**问题**: 论文发现轨迹级奖励将工具使用信号稀释至 10^-4，必须在归一化后单独添加。

**建议**:
- 如果 Hermes 未来引入在线 RL 或 RLHF 训练，工具使用行为需要密集奖励而非仅依赖任务级 outcome
- 对 agent skill 的评估不仅看最终成功率，还要看工具调用决策的中间步骤质量

### P3: 符号反转在跨模型工具使用中的启示

**问题**: 同一工具对不同能力模型产生相反效果。

**建议**:
- 不同 LLM provider 切换时（GLM-5.2 → 其他模型），工具/skill 的效果可能反转
- 部署新模型前应重新评估工具使用行为，而非假设 skill 效果可迁移
