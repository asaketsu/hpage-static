核心问题与研究动机

GPU kernel 的 LLM agent 优化存在一个结构-自由度权衡（structure-freedom tradeoff），两端各有致命伤：

  • Scripted agent（脚本化）：固定每步做什么——学习策略、优化菜单、固定角色。样本效率高，但菜单错了就停摆。Autocomp 拿掉优化菜单性能崩塌；固定循环 RL 在单算子上行、融合模型上不行。
  • Open-ended agent（开放式）：LLM 自由变异 kernel 种群。自由换来结果（AlphaEvolve 对 FA kernel 提速 32%），但代价是试验量——AVO 探索 500+ 方向 7 天只 commit 40 版；此类 agent 新增代码约 30% 是自己刚删掉的字节级相同行；LLM 进化的 CUDA 候选 30-55% 不正确。

论文的核心论断：两端缺的都是方向（direction）——关于"剩余差距在哪"的假设。信息不缺（两端都给了 profiler/文档/参考实现），缺的是外部提出的假设。证据链：内在自我纠正失败之处外部反馈成功；人类对自己代码的结构性反馈使修复成功率提高 1.57×；FlashInfer kernel 竞赛中拿到专家方向指引的 agent 在每个 kernel 上都击败同样的 agent 单独跑。

点睛之笔："问题改变任务"。'Make this faster' 是开放式的，模型贪婪作答；'基线赢在 kernel cycles 还是只赢在 wall-clock？' 是有界的——为回答它，模型会撕掉并重写一个它自己永远不会碰的 kernel 部分。一个好问题提供方向而不缩小 agent 下一步能做什么——这是更多结构、更多自由、更多工具都做不到的。

方法论内容整理

KernelSeek 三件套：最小 harness（可验证目标）+ 无脚本通用 coding agent + 决策点的问题源（人类 → 问题库自问）。

1. Ask vs Equip 统一框架

Agent 优化即搜索：candidate 是 kernel 源码，fitness 是逐场景相对 seed 的加速比向量（任一场景错误则归零），lineage 单调。agent 是变异算子，设计者能做的一切 = 选择什么进入上下文、以及何时进入：

  • Equipped agent：接收预消化的工具输出（解析 profiler、反汇编 diff）、预检索的知识（文档节选/参考库提示/教训库）——设计者靠加工具和知识改进它
  • Asked agent：接收任务 + harness 输出 + lineage + 决策点的短问题。开发者全栈工具都在（编译器/profiler/反汇编/sanitizer/debugger），但零预消化，方向以问题而非菜单形式到达——设计者靠问更好的问题改进它

2. 最小 Harness 与可验证目标

唯一自建组件是 evaluator：一条命令构建候选、逐场景对照 seed 输出与 fp32 参考查正确性、同 GPU 背靠背计时、报告逐场景比值与几何均值。约束机械化执行（检查二进制符号禁 CUTLASS/cuBLAS 等）。

目标 = evaluator 输出上的谓词，安装为 coding agent 的 Stop hook：agent 每次试图结束 turn，hook 评估谓词，未满足的子句打回给 agent 继续干。两条写谓词的铁律：

  • 必须量化到每个场景而非聚合值——否则 agent 会在自己擅长的 shape 上满足聚合
  • 能用计算判定的绝不用模型判定——唯一一次让模型 judge 裁决，它接受了人类随后推翻的过早完成声明

3. 问题：是什么、何时问

trace 中导致最大增益的问题共享六性质：①不含答案（只命名假设类，推导留给 agent）②要求 agent 用现有工具可做的测量（答案是数字不是观点）③跨系统层移动（kernel → host launch path → 路由 → benchmark 本身；独处的 agent 停在起始层）④拒绝过早闭合（质疑声称的极限是硬件属性还是 agent 自己的设计）⑤便宜（几十 token vs 检索文档的几万 token）⑥反制顺从（agent 倾向保留初始结构、接受给定框架；问题要求它用证据辩护）。

八类问题覆盖案例全部人类提问：measurement check（13 条）、bound differencing（10）、benchmark validity（7）、gap triage（7）、agent process（6）、challenge a limit（5）、strategy options（5）、hypothesis check（3）。

五个决策点（不连续提问）：战役开始定 scope 时；平台期；agent 声称极限或完成时；可疑的大胜之后；正确性以 agent 解释掉的方式破坏时。决策点之间 agent 独立工作——平均每条人类消息间隔 71 次工具调用，中位消息长度一两句。steerer 贡献的不是代码也不是 agent 缺的 CUDA 知识，而是在正确时刻对正确的事情贡献怀疑。

4. 问题库（The Question Bank）

战后复盘蒸馏出问题库。第一版 48 条直接从 trace 提取，回读暴露单案例蒸馏风险：21 条把上游 kernel 写死为比较对象、13 条写死 attention 结构。发布版收窄准入：不含答案、stock 工具可测量、针对 bound（roofline/每 tile cycle 预算）而非参考实现、架构仅作参数、不命名算子。补充挖掘 3 个公开 GEMM worklog（Ampere/Hopper/Blackwell）+ FA3/FA4 论文中每次优化前的诊断，最终 101 条核心条目分 10 组（按差距可能所在排序：scope/triage → bound/regime → harness/测量 → host/launch/路由 → 内存层级 → 计算发射 → occupancy/寄存器 → 异步/流水 → 调度 → 低精度数值），另有 5 条"存在可测参考实现时专用" + 18 条按架构绑定清单。算子结构通过 5 槽位插件进入（regimes/不规则工作/非 MMA 单元/reduction splits/间接加载）。29 条带 trace 标签，72 条纯公开来源未实测。

5. 从"问 agent"到"agent 自问"

问题可复现 → 可作为指令交给 agent。固化为 skill 五件套：目标 + harness 强制的硬规则 + 循环 + 自问问题清单 + evaluator/profiler 命令。循环即问题库的程序形态：定 scope → 测 seed → 改代码前把每个 gap 归类 host/路由/kernel → 定 bound → 形成假设 → 重写 → 过闸。每步 agent fan-out subagent 验证。

6. 与进化搜索组合（2.6）

KernelSeek 可包装为 AVO 式 lineage，directive 换成问题。

基线 Arsenal 的失败解剖（本文最精彩的对照实验）

Arsenal = "主流配方"的认真实现：编排循环 + 输出预消化的 profiler + 文档/参考库检索 + 类型化知识库 + 无人设计。Claude Opus 4.8 每步新 session，16 个手写杠杆按 NCU 瓶颈标签键控。中位步 prompt 22.6K 字符（37% 预取参考材料）。

结果：133 步 / 62 小时 / $660 API，0.48× FA3 停滞（最差配置 0.24×），0/26 配置达标。全部进步发生在 step 35（前 45h），后 98 步无噪声外产出——最终冠军与 step 104 候选字节相同，靠 54 次重测中一次落进噪声带晋升。

五个数字化失败模式：

  • 信息不是约束：1/3 prompt 是参考材料、磁盘上 1.6GB 参考代码，但 agent 工具调用读取的 82% 字符是自己的 kernel；92 次文档查询大多在论证"不改"
  • 菜单限制了搜索：plateau 检测器开的 37 个 rewrite 分支有 36 个从同一 step 播种；step 35 后每个候选都是同一设计的局部编辑
  • 记忆固化了结论而非证据：memory 文件把某配置记成"DEFINITIVE 被 65536 寄存器墙挡死"（FA3 根本不撞这堵墙）；step 112 的总结是"唯一出路是 outside this branch's mandate 的 clean-sheet 重写"——每个新 session 继承早期判决却没有背后的推理，环里没有任何组件处于质疑它们的位置
  • 所有诊断都在同一层：NCU/SASS 分析器/sanitizer 全在查 kernel，而 KernelSeek 后来在此 evaluator 上闭合的差距在 host launch path
  • 目标奖励了保守：噪声带内最差配置贪心晋升把噪声当进步，无法资助"先回退后收益"的重构；313 候选 312 正确 = 从不冒险的搜索签名

三条带入 KernelSeek 的教训：①harness 机械部分值得保留（KernelSeek 的 harness 就是去掉编排的 Arsenal evaluator）②一切为喂 brain 而建的组件都可删——知识库 actively harmful ③环里缺一个输入：怀疑结论的理由 + 往别处看的假设。

关键实验结果与数据

案例 kernel 本体（Table 1）

  • fa3_hopper.cu（3.6K 行，raw CUDA+PTX：TMA+mbarrier 环连 producer/consumer warpgroup、异步 wgmma+setmaxnreg、持久调度 ping-pong、split-KV decode combine、原生 fp8）：182/182 场景正确，1.16× FA3 / 1.10× 最快可用实现（含 cuDNN）；cuDNN 快的 111/145 场景里它反超，FlashInfer 支持的 32 场景全胜
  • fa4_blackwell.cu（10.2K 行，host 侧路由的 kernel 家族：tcgen05 MMA、双 softmax warpgroup 有序 ping-pong、tensor memory 重标校正 warpgroup、小/ragged/decode 两 tile 变体）：154/154 可运行场景正确，1.46× FA4 / 1.07× 最快可用。多个决定性增益在 kernel 体外：每次调用 38μs 的同步 host 拷贝、过期路由门、分歧 lane 发出的 TMA gather、编译器放进 local memory 的 ring 状态
  • 诚实披露：baseline 越强 headline 越缩（对 cuDNN 仅 1.07-1.10×）；edge 集 1.5-2× 部分是上游 dispatch 开销；fp8 dense prefill 0.67× 是 Hopper 唯一明确败洞；每个低于 parity 的 Blackwell 场景有已测根因

Head-to-Head（Table 2，同 evaluator/26 配置/同 H200 节/重叠日期）

  • 结果：Arsenal 0.48×（44.7h 到最好，0/26 达标）vs KernelSeek 1.13×（68h 其中 41.3h active，22/26 ≥1.0×，最差 0.87×）；KernelSeek 从 0.009× 起步（当时 kernel 把 paged/GQA 配置路由到标量 fallback），21h 到 0.96×、66h 过 parity、68h 到 1.13×
  • 工具使用反转：Arsenal 被喂 37% 参考材料却把 82% 阅读花在自己的 kernel 上，profiler 每步 1 次且只看解析版；KernelSeek 零投喂、26% 阅读自己的 kernel，profiler 裸跑 429 次 + 原始 SASS/PTX 检查 372 次，subagent 48 个。结论原文："问题没有减少工具使用——它瞄准了工具使用（The questions did not reduce tool use; they aimed it）"
  • 公平性三 caveat：KernelSeek 前两天在 40 场景网格上已有 kernel（0.009× 低估起跑线）；前端不同（Claude Code + Cursor）Cursor token 不可恢复；每臂单次运行

问题的解剖（RQ3）

  • 162 条人类消息分类：directive 58（36%）> question 44（27%）> approval 30（19%）> correction 19（12%）> goal 11（7%）；63 条（39%）疑问句式，19 条 correction 中 12 条以问题形式问出。steering 是疑问式的但不是全是问题——directive/approval 维持前进，问题才是转向之处
  • agent 自己也在问/喊：向人类提出 35 个结构化问题（24 个给"接受现状/停止"选项）；断言极限或不可能 126 次；Stop hook 打回 59 次。自主 agent 寻求闭合，harness 和人类拒绝给它
  • Table 3 四个金句案例：①"哪些配置拖垮 geomean？"→ 发现 hd96/192/256 全在标量 fallback 0.01×，4 小时 0.44→0.96 ②"这个天花板是硬件属性还是我们设计的？kernel 外时间去了哪？"→ host 侧每调用 2-5μs tensor fill，geomean 1.02→1.13 ③"场景覆盖算子实际被调用的 shape 吗？"→ 40/40 全对移植全测试网格后 52/58 对、sink/left-pad 输出差 495×/103×，六修后 58/58 且新网格 1.10 ④"你为什么认为目标达成了？我们远低于 parity"→ Stop-hook 模型 judge 曾接受"goal met"，agent 自认"第一个杠杆成功就过早宣布胜利"，fp8 hd256 decode 0.20/0.34→0.66/0.77

进化搜索与问题的关系（RQ4）

Blackwell dense-prefill 用问题作 directive 的 AVO 式进化：第一代（持久调度+最长优先+跨 tile 重叠问题）0.29×→0.68×；三代共 +0.10×（折叠 softmax scale、split K/V barrier、depth-2 softmax-correction 握手）；寄存器再平衡/地址提升的 directive 测出中性或负——进化放大 directive 携带的方向、在被指的层内高效搜索，但不能移动到未被指向的层。卡在 0.78×（kernel cycle 数已低于上游）后最后 22 个点来自一个问题而非一代：被问"时间去了哪"，agent profile 整个调用而非 kernel，发现同步 host 拷贝是差距来源。

问题迁移性（RQ5）

八类问题五类在 Blackwell 战役复现；Blackwell skill 的自问几乎逐字重述 Hopper 问题。63 条疑问消息中仅 17 条提 attention 概念、32 条提上游 kernel（且作 bound 用，可被 roofline 替代），其余只命名测量/层/流程。必要非充分证据：两战役都是 attention，72 条公开来源条目尚未实战检验。

创新点归纳总结

  • 范式级：首次系统论证"方向"是 agent 优化中与"信息"正交且更稀缺的资源，且方向可以由不含答案的短问题廉价供给——比结构（菜单）、自由（开放搜索）、工具（profiler/文档/检索）三类主流改进正交
  • 机制级：Stop hook 谓词目标（可验证而非可请求的完成条件）+ 五决策点提问协议 + 71 工具调用/消息的人机分工量化
  • 工程级：问题库的准入规则（对 bound 而非参考、架构仅参数、不命名算子）与 skill 五件套固化（goal/rules/loop/questions/commands）——问题从人类即兴行为蒸馏为可复用资产
  • 实证级：受控 head-to-head（同 evaluator/配置/机器/周）+ 全 trace 开源（162 消息逐条标注 + 11.5K 工具调用分类）+ 对基线失败的五模式数字化解剖
  • 反直觉发现：预消化信息 actively harmful（82% 阅读在自己 kernel 上 vs 26%）；312/313 正确率是失败信号而非成功信号（从不冒险）；问题不减少工具使用只重定向它

局限性与未来方向

  • 每臂单次运行、前端不同、steered vs unsteered 不对称——作者自己列出 threats to validity，全 trace 开放供复核
  • 问题库能否替代人类是本文未包含的实验：设计已固定（从 Blackwell kernel 已测缺口起步、同模型同预算四臂对照：装备环/裸 agent+harness/裸 agent+问题库提问器/人类提问器）
  • kernel 侧残留：Hopper 败于 fp8 dense prefill/softcapped prefill；Blackwell 未建 fp8 与 ≥192 head dim（28/182 场景）；无 backward pass
  • 单算子族（attention）+ 强上游存在的场景；"无参考实现"战役（seed 已知最快 kernel）是发布目标但未跑
  • 下一步靶子：latent-attention decode、MoE grouped GEMM、fused collectives、persistent megakernels、生产路径端到端评估

查询拓展

  • 人类专家是否做了工作？S6 直接回答：人类零 kernel 代码；63 条疑问消息中 17 条提 attention 概念、0 条指定 CUDA 构造；agent 写了全部 13.8K 行。人类有的是系统 expertise，用于决定何时要求哪个测量
  • 参考实现是否必需？方法论上不需要——bound 角色可由 roofline/speed-of-light 估计/launcher-only A/B/邻 shape kernel 填充（问题库按名请求这些）。案例里有参考只是让 bound 更便宜更锋利——Arsenal prompt 里的参考多得多却一无所获
  • Stop hook 的模型 judge 教训：唯一一次 hook 把裁决委托给模型 judge，它接受了人类推翻的过早完成声明——对应 Hermes 的启示是"验证门禁必须可计算"
  • 消息标注方法学：一作者对 162 消息逐条按主行为标注（goal/directive/question/approval/correction）+ 疑问式标记 + 八类归类，taxonomy 可能适配已有 session，trace 全开放供检验
  • 问题库蒸馏陷阱：48→101 的过程中删掉了 21 条写死上游/13 条写死 attention 的条目——从单案例蒸馏 SOP 必须过"不含领域专有名"关，否则是过拟合不是知识

趋势判断

  • Agent 设计的第三条路成形：2025-2026 的 agent 论文在"更结构"（workflow/菜单/多角色）与"更自由"（AutoGPT 式开放循环/进化搜索）间摇摆，本文以受控实验证明两端共同盲区是"方向的供给机制"，且该机制可资本化（问题库）+ 可程序化（skill 化自问）。预计 2027 年"question bank / steer protocol"会成为 agent harness 标配组件，与 memory/tool 检索并列
  • 人机分工量化成为新报告标准：71 工具调用/消息、63 疑问句/162 消息、126 次极限断言/59 次 hook 打回——这类粒度的人机交互账本（而非单纯 benchmark 分数）正在成为评测 agent 系统的新维度，与 Screenshots-or-Tools（2610.03327）的工具采纳率审计同向
  • "预消化上下文"退潮信号：37% 预喂材料换来 82% 自恋阅读，与 RAG-for-agents 方向的多篇工作（检索仅在补足特定缺失时有效）形成合流——agent 上下文工程的重心从"喂什么"转向"何时要求什么"
  • Kernel 级 LLM agent 进入深水区：从单算子 benchmark 刷分（KernelBench 时代）到 182 场景生产特征面 + 依赖禁令 + 与 cuDNN 硬碰硬，评价标准快速工程化；NVIDIA 自产 kernel 在多 shape 上低于 speed-of-light 的事实给这条线持续供血
  • trace 全开源成为强可信信号：162 消息标注 + 11.5K 工具调用分类 + 两臂完整 trace，与"只报最终分数"的论文拉开可信度差距

关联分析（对 Hermes Agent 的借鉴）

  • 与 Hermes Skill 架构同构度极高：问题库 skill 五件套（goal/rules/loop/questions/commands）几乎就是 SKILL.md 的 frontmatter+正文结构；KernelSeek 的"问题固化为 skill 供 agent 自问"直接对应 Hermes 把 workflow 沉淀为 skill 的路线——差异在于 KernelSeek 的 skill 内容是质疑协议而非操作步骤
  • Stop hook 谓词 ↔ Hermes hook 机制：Hermes 已有 hook 基础设施（steer-hook/session 管理），但缺"完成谓词"用法——在长任务 skill 里安装 Stop-hook 式可计算谓词（如"验证脚本退出码 0 且产物存在"），把"声称完成"改为"证明完成"
  • 五决策点提问协议 ↔ Hermes 长任务自检：plateau/声称极限/可疑大胜/正确性异常四个触发点可编译为 cron 或 hook 的检查清单——特别是"agent 断言极限 126 次被打回 59 次"提示长任务 agent 的极限声明应触发强制复核而非直接采信
  • Arsenal 记忆病 ↔ Hermes memory 陷阱同源：memory 固化结论（"DEFINITIVE 被寄存器墙挡死"）而非证据，新 session 继承判决丢失推理——对应 Hermes 的 MEMORY.md 应记"何时失效/怎么验证"而非只记结论；此问题在 error-case-library 的设计里已被规避一半（记根因链），但普通 memory 条目仍暴露于此风险
  • "跨层诊断"原则 ↔ Hermes 排障方法学：Arsenal 全部诊断工具锁在 kernel 层而差距在 host 层——对应 Hermes 排障时"先根因定位"铁律的工具化版本：排障 skill 应显式列出系统全层（gateway/session/model/网络/系统）并强制逐层归因，防止单层深挖
  • 对 Jetson 边缘部署：无依赖单文件 CUDA kernel 思路（禁 CUTLASS/cuBLAS 换手写 PTX）对 Jetson 的 custom op 有直接工程参考价值；question bank 的 memory hierarchy/occupancy/异步流水三组问题可移植到 TensorRT plugin 调优

拓展应用推荐

  • P0｜长任务 Stop-hook 完成谓词：给 Hermes 的 build/deploy/训练类 skill 增加可计算完成谓词（产物存在+验证命令退出码+关键指标达标），agent 试图收工时 hook 自动核验。收益：消灭"过早宣称完成"（用户 1026 两次实锤的同族问题）；成本：每 skill 加 10-20 行谓词
  • P0｜"质疑极限"检查单进 cron/守望 skill：训练盯盘、发布验证类长任务在 plateau 或 agent 声称"不行/到顶"时，强制跑一遍 KernelSeek 式五问（测量对吗/基准公平吗/在测你以为在测的东西吗/天花板是硬件还是方案/换层了吗）。收益：直接对标 Arsenal 五失败模式；成本：一个检查单 skill
  • P1｜Memory 条目强制带失效条件：写 memory 时附"何时此结论可能不适用+如何复验"字段，防结论固化。对应 Arsenal 的"DEFINITIVE 墙"教训
  • P1｜问题库作为 skill 素材：论文开源 question bank（101 条+10 组分类），可蒸馏通用版（去 CUDA 化）作为 Hermes 深度排障/优化任务的提问模板库
  • P2｜人机分工量化审计：为 Hermes 会话统计"人类消息/工具调用/极限断言/hook 打回"四指标，作为 agent 效率审计的新维度
  • P3｜进化搜索包装：delegate_task 多臂并行探索时用"问题"而非"方案菜单"作各臂 directive，规避 Arsenal 的菜单限界失败

指南分析

若要在 Hermes 中实践本文方法，操作指南如下：

  1. 识别任务特征：本文方法适用于"优化目标可量化为逐场景谓词"的深任务（kernel 提速/测试通过率/指标达标），不适用于开放式创意任务
  2. 建 harness 而非建菜单：把验收写成一条命令可算的谓词（逐场景量化、禁聚合、禁模型 judge），装进 Stop hook 语义
  3. 改进方式从"加工具/加知识/加流程"切换为"改进问题"：每次任务失败后复盘"哪个问题如果早点问就能省掉这次失败"，积累自己的 question bank
  4. 问题准入五关：不含答案/stock 工具可测/对 bound 不对参考/不写死领域专有名/不写死算子——过不了就重写
  5. 提问时机五点：开局定 scope/平台期/声称极限或完成/可疑大胜/正确性异常，其余时间让 agent 独跑
  6. 警惕三个 Arsenal 信号：正确率极高但无进展=不冒险；重测晋升=噪声当进步；结论进 memory 无推理链=固化的墙

归纳总结

本文用一场受控屠杀实验（0.48× vs 1.13×，同 evaluator 同机同周）证明：深任务 agent 的瓶颈不是信息、不是自由度、不是工具，而是方向的供给。一个好问题（不含答案、可测量、跨层、拒闭合、便宜、反顺从）在正确时刻（五决策点）的价值超过 37% 的预喂参考材料和 16 个手写优化杠杆。方法论三件套（可计算谓词 Stop hook + 无脚本 agent + 问题库自问）全部可移植，且问题库 skill 化的形态与 Hermes SKILL.md 同构。最深的一课藏在 Arsenal 的验尸报告里：312/313 正确率是失败签名，记忆固化结论是慢性毒药，单层诊断是结构性盲区——这三条对任何长任务 agent 系统通用。
