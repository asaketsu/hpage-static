# 航空结构设计领域 AI 短期基础设施建设指南

> **来源**：基于内部研究报告（2026-05-14）综合整理
> **背景**：航空结构设计领域 Agent 工程建设（`aero-agent-engineering`）
> **定位**：回答"在航空结构设计领域开展 AI 短期需要哪些基础设施"
> **方法论**：小批量推进法 · 双格式输出

---

## 0 · 总体框架

航空结构设计 AI 落地不是"买几块 GPU + 跑个模型"就完事的事。它是一套**从数据到工具到人**的系统工程。

根据已有研究报告的路线图，短期（0-6个月）基础设施聚焦三个层面：

| 层面 | 核心问题 | 对应阶段 |
|------|---------|---------|
| **数据层** | AI 拿什么算？ | 阶段 0 |
| **工具层** | AI 怎么算？ | 阶段 0 → 阶段 1 |
| **智能层** | AI 怎么思考？ | 阶段 1 → 阶段 2 |

这不是"基础设施"这个词的传统含义（机房/网络），而是**AI 能在其上运行的完整生态环境**。

---

## Part 1 · 计算基础设施

### 1.1 为什么航空结构设计对算力有特殊要求

航空结构 FEA（有限元分析）单次计算：
- 线性静力分析（Linear Static）：30s ~ 5min
- 屈曲分析（Buckling）：2 ~ 15min
- 非线性分析（Nonlinear）：30min ~ 数小时
- 疲劳/损伤容限分析：小时级别

AI Agent 如果要实现"跑分析 → 看结果 → 调参数 → 再跑"的闭环循环，每轮迭代都要等待 FEA 完成。**Agent 的"思考时间"主要花在等 FEA 上，不是 LLM 推理上。**

### 1.2 短期必做项

| 项目 | 说明 | 优先级 |
|------|------|--------|
| **NASTRAN 批量/自动化调用接口** | 解决"人点按钮等结果"的模式，让 Agent 能程序化提交和获取结果 | P0 |
| **CATIA V5 自动化 API 封装** | 从模型提取截面参数、材料分配、几何属性 | P0 |
| **本地 GPU 服务器（或云端租用）** | LLM 推理 1-2 张 A100/H100 足够；如果用云端 LLM API 则只需稳定的网络 | P1 |
| **FEA 结果自动解析与结构化** | NASTRAN .op2/.f06 输出解析，提取应力、变形、特征值等关键指标 | P0 |

### 1.3 关键原则

**不追求自建超算，但要打通自动化流水线。**

- NASTRAN 的命令行模式 + Python 脚本即可实现批量提交
- 重点是把"提交任务 → 等待 → 解析结果"这个链条自动化
- 考虑任务队列设计：一个 Agent 任务可能触发 10-20 次 FEA 调用，需要队列管理和超时控制

## Part 2 · 数据基础设施

这是**被严重低估**的一环。没有高质量数据，AI 就是空中楼阁。

### 2.1 核心数据库清单

| 数据库 | 内容 | 格式 | 难度 |
|--------|------|------|------|
| **材料力学性能库** | σ_b, E, ν, ρ, 疲劳极限等 | 结构化表 | ★☆☆ |
| **截面几何属性库** | 工字钢/角钢/变截面属性 | 计算程序或查表 | ★☆☆ |
| **规范条款库** | CCAR-25/RCS/MIL-HDBK-5 条款结构化 | 结构化+原文引用 | ★★★ |
| **载荷数据库** | 设计载荷/飞行载荷/离散源载荷 | 结构化 | ★★☆ |
| **历史分析案例库** | 过去项目的分析模型+结果+评审记录 | 半结构化 | ★★★ |

### 2.2 短期建设策略

**材料库和截面库**——如果已有 StructGen 项目，直接复用。

**规范条款库**——最关键也最困难：
- CCAR-25-R5 全文约 2000+ 条款
- 需要结构化标注：条款号、适用对象、计算要求、引用关系
- 建议用 RAG + Chunking 方式将规范文本向量化，支持语义检索
- ⚠️ 条款理解不能仅靠向量检索，必须精确匹配条款号

**历史案例库**——最高 ROI 的数据源：
- 从已完成项目中抽取：输入参数 → 分析过程 → 结论 → 人工评审意见
- 用作后续 Agent 的 Eval Set（评估集/金标准）
- 每条案例标注：成功/失败、失败原因、置信度

### 2.3 一个残酷的现实

> 研究报告中明确指出：**"AI 在航空领域最大的敌人不是模型能力不够，是数据质量不够。"**

- 材料数据有 5% 的误差 → 安全余度计算可能差一个数量级
- 规范条款版本不一致 → 可能引用作废条款
- 历史案例文档散落各处（Word/PDF/邮件/纸质）→ 数字化是巨大工程

**短期建议**：先聚焦 2-3 个高频材料、100+ 条核心条款、50 个历史案例，做精不做全。


## Part 3 · 工具链接口（CAE/FEA/CAD API 封装）

### 3.1 三大工具接口优先级

```
┌─────────────────────────────────────┐
│           Agent 交互层               │
├─────────────────────────────────────┤
│  NASTRAN 接口  │  CATIA 接口  │  材料库  │
├─────────────┬───┴────────────┬────────┤
│ .bdj/.dat  │  VBA/COM/      │  API   │
│ .op2/.f06  │  PythonOCC     │  查询  │
│ 批量提交    │  模型遍历      │        │
└─────────────┴────────────────┴────────┘
```

### 3.2 具体要做的事

**NASTRAN 接口（P0）**：
- 命令行封装：`subprocess.run('nastran scr=yes bat=no old=%s' % inp_file)`
- 结果解析：`.f06` 文本解析（应力、变形、安全余度等关键值提取）
- 批量管理：任务队列、并发控制、超时处理、失败重试

**CATIA 接口（P1）**：
- CATIA V5 有 COM 自动化接口（Python 的 `win32com`）
- 关键操作：遍历 Part → 提取截面参数 → 读取材料分配 → 生成 BOM
- ⚠️ CATIA 只在 Windows 可用，可能需要 Windows 虚拟机或 Citrix 环境

**后处理工具链（P1）**：
- FEMAP/Patran 结果后处理脚本
- 自定义结果提取和可视化脚本（matplotlib/Tecplot）

### 3.3 ACI（Agent-Computer Interface）设计

研究报告强调：**"Agent-Computer Interface 的描述要像给新同事写操作手册。"**

每个工具接口的描述格式：
```
名称: run_nastran_analysis
描述: 提交 NASTRAN 线性静力分析
输入: {inp_file: str, scratch_dir: str, output_format: 'f06'|'op2'}
输出: {status: 'success'|'error', stress_results: [...], displacement: {...}, duration_ms}
约束: 
  - 单个模型运行时间上限 10min
  - 并发数不超过 4
  - 失败自动重试 2 次
```

这些描述本身就是 Agent 的"操作手册"，写好了 Agent 才知道怎么调用。

## Part 4 · AI 模型与知识基础设施

### 4.1 LLM 选择策略

| 场景 | 推荐模型 | 原因 |
|------|---------|------|
| 通用推理/规划 | GLM-5.1 / Claude | 通用能力强，支持长上下文 |
| 代码生成（NASTRAN脚本） | Claude Code / Codex | 代码质量高 |
| 规范条款问答 | 本地部署中等模型 + RAG | 数据安全、领域精准 |
| 设计评审/报告生成 | GLM-5.1 | 中文能力好，格式控制强 |

### 4.2 RAG 架构

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│  用户问题     │───▶│ Embedding    │───▶│ 向量数据库    │
│ (工况描述等)  │    │ (BGE/千帆)   │    │ (Milvus/Pg)  │
└─────────────┘    └──────────────┘    └──────┬───────┘
                                              │ 检索结果
┌─────────────┐    ┌──────────────┐    ┌──────▼───────┐
│  LLM 推理    │◀───│  Prompt 组装  │◀───│ 条款库/案例库  │
│ (GLM-5.1)   │    │  混合检索排序  │    │ 材料库/规范    │
└─────────────┘    └──────────────┘    └──────────────┘
```

### 4.3 知识图谱（中长期）

- 飞机结构本体：部件关系、材料-工艺-载荷映射
- 规范条款关联网：条款之间的引用/依赖关系
- 损伤模式推理网：应力分布 → 失效模式 → 规范条款 → 处置方案

短期可以先做 RAG，中长期再上 KG。

### 4.4 扩散模型与逆设计

前沿趋势（已有研究验证）：
- **扩散模型用于结构拓扑优化**（如 LatticeOptDiff）
- 给定性能要求 → 反向生成满足要求的结构构型
- 目前仍以学术研究为主，**短期不建议投入**


## Part 5 · 安全与合规基础设施

### 5.1 这个环节不能省

航空结构设计直接关系到飞行安全，AI 输出必须受到严格约束：

| 安全措施 | 说明 | 实现方式 |
|---------|------|---------|
| **Guardrails（护栏）** | 事实/行动/执行/输出四类边界 | Prompt 设计 + 后处理校验 |
| **人工审批流程** | 关键结论必须人审 | 工单系统 + 审批状态追踪 |
| **可观测性** | 记录 Agent 每步操作 | 日志系统 + JSON 结构化记录 |
| **数据隔离** | 设计数据不出内网 | 本地部署 + 网络隔离 |
| **版本控制** | 模型/配置/Baseline 可追溯 | Git + 模型版本管理 |
| **不确定性声明** | 不确定时必须声明 | 输出格式中带 confidence 字段 |

### 5.2 关键安全铁律（来自研究报告）

1. Agent **不允许修改**已通过适航审查的设计参数
2. 所有 AI 结论**必须经过人工审核**——辅助工具，不是决策者
3. 不确定性**必须显式声明**——不允许假装确定
4. 证据链**必须完整可追溯**——结论能追溯到数据源
5. 漏报率**必须为零**——宁可误报，绝不放过问题

### 5.3 短期投入

最低限度：
- 一个带审批状态的数据库表（记录 Agent 输出 + 审核状态 + 审核人）
- 一套输出格式模板（JSON 结构：结论 + 置信度 + 证据 + 条款引用）
- 关键操作的日志记录（谁在什么时候调用了什么工具、得到了什么结果）

## Part 6 · 短期优先级矩阵

### 投入产出评估

| 基础设施 | 建设周期 | 投入难度 | 预期收益 | 建议顺序 |
|---------|---------|---------|---------|---------|
| NASTRAN/Python 自动化脚本 | 2-4 周 | ★★☆ | ★★★ | 1 |
| 材料/截面数据库整理 | 2-4 周 | ★★☆ | ★★★ | 2 |
| FEA 结果解析器 | 1-2 周 | ★☆☆ | ★★★ | 3 |
| 规范条款 RAG（CCAR-25） | 4-8 周 | ★★★ | ★★★ | 4 |
| 历史案例库 + Eval Set | 4-8 周 | ★★★ | ★★★ | 5 |
| CATIA 自动化接口 | 4-6 周 | ★★★ | ★★☆ | 6 |
| 任务队列 + 超时管理 | 1-2 周 | ★★☆ | ★★☆ | 7 |
| 可观测性日志系统 | 1-2 周 | ★☆☆ | ★★☆ | 8 |
| GPU 服务器/云端租用 | 即时 | ★☆☆ | ★☆☆ | 9 |
| 知识图谱 | 3-6 月 | ★★★ | ★☆☆ | 暂缓 |

### 前 8 周建议排期

```
Week 1-2:  NASTRAN 自动化 + FEA 解析器 + 任务队列（同时做）
Week 3-4:  材料数据库 + 截面库
Week 5-8:  规范条款 RAG + 首批 50 个历史案例
Week 8:    回顾评估，决定阶段 1-2 推进节奏
```
