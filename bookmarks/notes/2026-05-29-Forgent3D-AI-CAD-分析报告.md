## 二、核心问题：它解决什么？

传统 CAD 工作的痛点：

1. **AI 生成的 CAD 只停在代码层** — Agent 写了 `part.py`，但没有反馈回路验证几何是否正确
2. **GUI CAD 无法版本控制** — SolidWorks/Blender 的 `.sldprt`/`.blend` 文件无法 diff、merge
3. **迭代极慢** — 改一个参数 → 打开软件 → 调整 → 渲染 → 检查，循环耗时巨大
4. **物理仿真脱节** — 几何建模和物理仿真（碰撞、约束、运动）是两个独立世界

**Forgent3D 的解法：给 AI Agent 一个本地几何反馈闭环。**

```
描述需求 → Agent 生成代码(part.py+asm.xml) → Forgent3D 本地重建
    ↑                                              ↓
    ← 截图 + 尺寸 + 构建状态 ← Three.js 预览 + MJCF 物理仿真
```

## 三、技术架构深度拆解

### 3.1 技术栈

```
┌──────────────────────────────────────────────────┐
│                 Electron 桌面应用                  │

│  │ Three.js   │  │ Agent Bridge │  │ MCP 工具  │ │
│  │ 3D 查看器   │  │ (Claude/     │  │ (截图/    │ │
│  │            │  │  Codex/Cursor)│  │  尺寸/    │ │

│                                    └───────────┘ │
│  ┌──────────────────────────────────────────────┐ │
│  │        Python CAD 运行时 (build123d)          │ │
│  │   Open CASCADE 几何内核 + MJCF 装配格式       │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

### 3.2 关键技术组件

| 组件 | 技术 | 作用 |
|------|------|------|
| **CAD 引擎** | [build123d](https://build123d.readthedocs.io)（Python） | 基于 Open CASCADE 的参数化 B-Rep 建模 |
| **装配格式** | MJCF (MuJoCo XML) | 多体系统、关节约束、物理碰撞 |
| **查看器** | Three.js | 本地交互式 3D 预览 |
| **桌面壳** | Electron | 打包 CAD 运行时 + 查看器 + Agent 桥 |
| **Agent 通信** | MCP (Model Context Protocol) | Agent 调用重建、截图、查询尺寸 |
| **模型包** | `asm.xml` + `params.json` + `part.py` | 可编辑、可版本控制的模型格式 |

### 3.3 核心创新点：MJCF 装配 + 物理仿真

**不只是画图，是写可仿真的机械系统代码：**

- `asm.xml`（MJCF 格式）定义装配关系：关节类型、约束、碰撞几何
- `part.py`（build123d Python）定义零件几何：参数化驱动
- `params.json` 分离参数与代码：改两行 JSON 即可微调传动比、材料属性
- MuJoCo 引擎直接运行物理仿真：齿轮咬合、转动惯量、关节约束全部可验证

## 六、行业趋势分析

### 6.1 "Text-to-CAD" 赛道格局（2026）

2026 年 AI CAD 领域正在从"一次性生成图片/网格"向"可编辑、可验证的参数化代码"演进：

1. **第一代（已过时）**：Text-to-3D → 生成不可编辑的网格/点云
2. **第二代（当前主流）**：Text-to-CAD Code → Agent 生成 build123d/OpenSCAD 代码
3. **第三代（Forgent3D 所在）**：Agent-in-the-loop CAD → Agent 写代码 → 本地构建验证 → 截图反馈 → 迭代优化

### 6.2 为什么"写代码"比"画图"更有未来？

| 维度 | 传统 GUI CAD | 参数化代码流 |
|------|-------------|-------------|
| 版本控制 | ❌ 二进制文件无法 diff | ✅ 纯文本，Git 原生 |
| AI 迭代 | ❌ 鼠标拖拽无法自动化 | ✅ 改两行参数即微调 |
| 批量生成 | ❌ 人工逐个 | ✅ Agent 并发生成 N 个变体 |
| 物理验证 | 需导出到仿真软件 | 代码内嵌物理约束 |
| 协作 | 文件锁定/冲突 | Git merge/PR |
| 门槛 | 高（学软件操作） | 低（描述需求即可） |

### 6.3 对工业设计的影响

**"机械设计的底层逻辑，正在从'画图'变成'写代码'"** — 这不是夸张，而是正在发生的趋势：

- **参数化代码 = 可编程的设计**：传动比、材料属性、公差都可以变量化
- **Agent 驱动 = 设计意图的自动实现**：描述"需要一个减速比 3:1 的行星齿轮组"→ Agent 生成完整 MJCF 装配
- **物理仿真闭环 = 设计即验证**：不再需要等到制造阶段才发现干涉/碰撞

## 八、评价与局限

### ✅ 优势
- **真正的闭环**：Agent 不只写代码，还能"看到"结果并迭代
- **物理仿真**：MJCF/MuJoCo 集成在 CAD 工具中是独特卖点
- **纯代码 = 可自动化**：整个建模流程可以脚本化、CI/CD 化
- **MIT 开源**：无供应商锁定风险
- **桌面端打包**：用户无需配置 Python/CAD 环境

### ⚠️ 局限
- **早期阶段**：仅 93 commits，0 个 Open Issues（可能社区尚未形成）
- **build123d 依赖**：Open CASCADE 功能强大但学习曲线陡
- **复杂曲面受限**：B-Rep 建模在自由曲面（如汽车外形）上不如 NURBS 工具
- **无云协作**：纯本地，不支持多人实时协作
- **Agent 依赖**：效果高度依赖 LLM 的 CAD 编程能力
- **Electron 包体积**：桌面应用较重

## 九、结论

Forgent3D 代表了 AI CAD 的第三代范式：**Agent-in-the-loop 的参数化设计**。它不是最强的 CAD 工具，也不是最聪明的 AI，但它把两者通过"几何反馈闭环"正确地连接起来了。

核心价值不在于工具本身，而在于它验证的工作流范式：**描述 → 代码生成 → 本地构建验证 → 截图/尺寸反馈 → 迭代**。这个范式可以复用到任何"AI 生成需要物理验证的工程内容"的场景。

对于我们的项目（AERIS-10、struct-gen），最值得吸收的是：
1. **build123d 作为参数化几何引擎**的架构选择
2. **MJCF 装配格式**用于多体系统定义
3. **Agent 反馈闭环**的设计模式（截图 + 尺寸 + 构建状态）
