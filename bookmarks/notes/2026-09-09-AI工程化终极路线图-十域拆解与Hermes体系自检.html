二、对照 2026 英文圈路线图：新 / 旧 / 缺失判定

判定方法：与 roadmap.sh/ai-engineer（GitHub 364K star 的社区路线图权威）、roadmap.sh/ai-agents、以及多篇 2026 英文路线图文章交叉对照。

判定 项 依据
✅ 2026 前沿项（推文有，多数老图没有） MCP（05 域）、A2A（05 域）、上下文工程（02 域） MCP/A2A 是 2024 底-2025 起量、2026 成为事实标准；"context engineering" 一词 2025 中才流行
⚠️ 2024 老项（推文有，但 2026 已降权） 约束解码（02）、GraphRAG（04） 约束解码被结构化输出+grammar 工具吸收，从"必学"降为"知道即可"；GraphRAG 2024 热过一波，2026 主流仍是 hybrid+rerank
❌ 2026 缺失项（推文没有，英文圈已标配） Context engineering 细分方法论（02）：静态/动态分离、预算化检索、对话历史管理 你自有 skill（context-engineering-patterns）已沉淀这套方法论
❌ 缺失 DAG 编排 + 验证器模式（05）：multi-agent 已从"自由协作"进化到"结构化 DAG + 独立验证"（Anthropic DAG multi-agent OS） 与《MultiAgent已死》笔记互引
❌ 编译缺失 Evals 的自动化（06）：fail-fast 回归管线、CI 门禁 evals roadmap.sh 将 evals 列为一等公民，且 2026 强调"没有 evals 的 agent 上线 = 盲飞"
❌ 缺失 Deterministic guardrails（07）：2026 从"LLM 判官"进化到"确定性护栏"——关键流程用代码/规则硬约束，不靠模型自觉 你自有 skill（deterministic-guardrails）已沉淀
❌ 缺图中最弱域 08 LLMOps 只列 vLLM/TGI，缺 SGLang、prefix-cache-aware serving 2026 推理服务三巨头：vLLM/SGLang/TGI

总判定：10 域框架 = 2026 合格线（与 roadmap.sh 大框架一致，无缺失大项）；子项粒度 = 2024 深度。这是一张"编译自英文圈、无 2026 独家增量"的中文版知识地图——收藏价值有，指导价值一般。

二b、深度优先级建议（按你的体系）

十个域不是并列关系。按"对生产系统可靠性的杠杆"排序：

  1. Evals（06） — 没有评估体系，其他一切域都不可证伪。线上指标+回归测试是"交付系统"与"调提示词"的分水岭（推文金句的落地形态）。
  2. Agents 记忆与状态（05） — agent 区别于 chatbot 的本质。三级记忆（铁律/短期/Topic）+ DAG 编排。
  3. LLMOps 成本工程（08）——缓存、路由、量化 — 生产系统与 demo 的分水岭。
  4. Deterministic guardrails（07） — 从"模型自觉"到"代码硬约束"。
  5. 权重最低的三个：多模态（10）、知识图谱（10）、蒸馏（09）——除非业务需要，不必优先投入。

四、将路线图转化为行动计划（3 项 P0）

基于自检结论，路线图转化为可执行补强（按你"分析完就停=失败"的铁律，三项都在本会话落进体系）：

P0-1：Evals 短板补强——为 Hermes 建立 golden-set 回归测试

  • 做什么：为最高频任务（笔记全链路：URL→MD→HTML→上线验证）建立 golden set（输入+期望输出的核心断言），每次 skill/prompt 改动后跑一遍
  • 为什么：笔记链是你吞吐量最大的生产线，坏一次影响全线（09-09 发布根因事故就是例证：只 scan 不 sync 导致线上 404）
  • 落地：cron 周检 + content-judge 评分门禁（<阈值告警）

P0-2：DAG 编排落地——把 Multi-Agent DAG OS 模式移植到 Hermes

  • 做什么：将 Anthropic DAG 协作模式（任务分解→独立执行→验证器合并）移植为 Hermes 的 delegate_task 模式
  • - 为什么：你的三机体系（jbot/ubot/abot）+ sub-agent 已具备 DAG 硬件基础，缺的是"验证器"角色——目前 sub-agent 结果无独立验证，全靠主 agent 复核
  • 落地：为 delegate_task 增加 verifier 角色参数，先在笔记流水线试点（写作 agent + 验证 agent 分离）

P0-2b：模型路由预算化——adaptive-inference-routing 落地配置

  • 做什么：按任务复杂度动态分配 token 上限（简单查询不烧长 CoT）——skill 已沉淀但未配置化
  • 为什么：zhipu coding plan 免费额度有限 + AutoDL 计费 GPU 教训——预算化是成本工程的核心
  • 自适应路由配置已就绪（adaptive-inference-routing skill），差最后一步 config 绑定

P0-3：guardrails 确定性化——为关键 cron 任务加装硬门禁

  • 做什么:为 stock-iron-rules、morning-briefing 等高频 cron 加装脚本级门禁（pgrep/mtime/head 三验，失败即阻断推送）
  • 为什么：cron 任务是"无人值守"场景，LLM 判官不可靠时需要代码硬约束——你的 GO.sh 演示门禁模式已验证有效
  • 落地:已验证模式复用（asa 演示门禁三验法）
  • 已部分就绪：watchdog 监控所有 cron 失败并自修——watchdog skill 已将 cron 失败监控+自动修复闭环
    P0-3 落地补充：as a 演示门禁三验法已被 watchdog skill 吸收为 cron 门禁通用模式,且 watchdog 已在监控全部 cron——P0-3 实际已就绪，无需重复建设。

P0 清单终版：P0-1 evals 回归门禁（唯一真空白）、P0-2 DAG verifier 模式、P0-2b 路由预算化 config 绑定。P0-3 已就绪。

五、金句展开：The Real Shift（2026 AI Engineer 角色定义）

推文结语"学会交付 AI 系统，而不只是调试提示词"是整张图的点睛。2026 年英文圈对 AI Engineer 角色的定义已经收敛：

"An AI engineer in 2026 is someone who can take a model and turn it into a working system. A system that reads data, calls tools, remembers context, retrieves the right documents, gives structured output, and can be tested, deployed, monitored, and improved." —— Emerging AI Substack

拆解这句话的六个动词：
1. reads data — RAG/检索（03、04 域）
2. calls tools — function calling/MCP（05 前半）
3. remembers context — 记忆与状态（05 后半）
4. retrieves the right documents — 表征与混合检索（03、04 增量）
5. gives structured output — 结构化输出（02）
6. tested, deployed, monitored, improved — Evals + LLMOps（06、08）——这句是全句重心，对应你体系的唯一短板域

这正是推文金句与英文圈定义的同构点：两者都把重心放在句尾——前面五项是"能做"，最后一项是"可证明地可靠"。"可证明地可靠"正是你体系当前唯一缺口（Evals 域），也是"debugging prompts"（调提示词）与"shipping systems"（交付系统）的分水岭。

五b、Hermes 体系与路线图的哲学同构

推文十域与你的体系有一个更深层的同构：都把"agent 状态"作为核心资产。推文 05 域把 "Agent 记忆与状态" 列为独立子项——这正是你的 TieredMemory 三级架构（L1 铁律/L2 短期/L3 Topic）对应物，也是 Anthropic DAG OS 的"artifact 库"对应物。

三层对应关系：
| 抽象层 | 路线图 05 域 | 你的体系 | Anthropic DAG OS |
|--------|------------|---------|-----------------|
| 状态存储 | Agent 记忆与状态 | TieredMemory（L1/L2/L3） | artifact 库 |
| 状态流转 | Agent 工作流 | cron+delegate_task | DAG 编排 |
| 状态验证 | （缺失） | watchdog 自修 | 独立验证器 |
| 状态转写 | 人机协作 HITL | clarify/approvals | 用户审批节点 |

三层对应关系的启示：路线图把"记忆与状态"列为独立子项，说明业界已把 agent 状态从"实现细节"升维成"一等资产"。你的 TieredMemory 是对这个趋势的正确押注。但注意第四行——路线图缺"状态验证"层（agent 记忆会漂移、会过期、会被污染），你的 watchdog 只监控进程不监控记忆质量。这是比 Evals 更深一层的盲区，值得后续用 memory-refiner cron 周检记忆条目的时效性。

一图流总结（基于五b 对应关系）：

            抽象层          路线图05域           你的体系              Anthropic DAG OS
            ─────          ────────           ────────             ────────
状态存储 → Agent 记忆与状态 → TieredMemory(L1/L2/L3) → artifact 库
状态流转 → Agent 工作流    → cron+delegate_task → DAG 编排
状态验证 → (缺失)          → watchdog 自修      → 状态验证器
状态转写 → 人机协作 HITL   → clarify/approvals  → 用户审批节点
