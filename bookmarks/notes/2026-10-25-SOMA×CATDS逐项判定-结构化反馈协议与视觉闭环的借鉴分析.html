一、内容整理：SOMA 是什么（忠实还原）

1.1 定位与规模

"Solid Object Modeling with Agents"——给 coding agent 用的 CAD 桌面应用："You tell the agent what you need. It writes the model as Python code with CadQuery, SOMA builds it and shows the result. You look at it, measure it, point at what is wrong, and the agent changes the code." 面向 maker/tinkerer（要个树莓派壳/支架/安装座），"vibe coding, but for CAD"。自述 Early prototype，"SOMA itself is vibe coded"（大部分代码由 Claude Code 在人指导下写成）。

三件套架构：
- 代码工作区：模型是 Python 脚本，带终端（SOMA 检测并启动已装的 CLI agent）、编辑器、每模型一个 Git 仓库
- 3D 视图器：每次变更即重建
- agent 指令：App 托管的 AGENTS.md（规则）+ 按模型开关的 skill 规则包 + soma CLI 工具

1.2 App 托管 AGENTS.md（"managed by the app, do not edit"）

AGENTS.md 是应用生成的产物而非手写文档：项目布局表（model.py / parts/ / inputs/ 用户带入文件只读 / parameters.json 面板值 / output/model.step / exports/ / .soma/ 应用数据）+ model.py 九条规则 + 命令表 + Git 纪律 + 环境纪律 + 反馈协议。<!-- soma:skills --> 标记处由 App 按当前模型激活的 skill 动态注入规则清单——指令的运行时组装。

1.3 结构化反馈协议（最精华部分）

App 把 GUI 事件粘贴成带机器可读指针的短注进 agent 输入：

注入格式 内容
[Markup: .soma/feedback/markup-20260930-1405.png] 用户在 3D 视图上的画注（箭头/圈/手写尺寸），规则明令 agent "Open the image file and look at it"；标注可指旧版本 commit
[Selection: part "…", model.py line …] 用户点选的零件 + 其 add_part 调用行 + 点中的面
[Build error: …] 最近一次失败构建的消息
[Parameter: "Cylinder bore" (BORE) = 40 mm, set in the app, code default 38 mm, model.py line 12] 面板改参：用户值/代码默认值/定义行三对齐
[Result: "Wall thickness" (.soma/results/…), part "…": 0.80 mm at (x, y, z) mm] 用户点击分析结果云图上的点
[Skill: .soma/skills/<name>.md] 用户开关了规则包，agent 须重读并从此遵循

1.4 视觉自检闭环

soma render 保存当前模型截图，AGENTS.md 命令表明令 "Open the picture and look at it" to check your work, also inside: hide what is in the way——agent 被强制看自己的产出再交付。分析结果（壁厚/悬垂/间隙）也是"文本摘要 + 彩色 GLB + agent 可渲染查看"双通道。

1.5 param() 参数契约（params.py）

BORE = param(38.0, "Cylinder bore", min=30, max=42, step=0.5, unit="mm", group="Crank train")——默认值定类型（float/int/bool/options 选择）、用户面板值存 parameters.json 覆盖代码默认（"the number in the code is not always the one in the model"）、常量名即 key（改名=旧值遗留，语义变了必须换名并告知用户）、未用值有警告。parametric skill 规定：设计意图先写注释（什么驱动尺寸/什么不动/原点放哪）、参数独立（外宽/内宽/壁厚只许其二为参数，间距一律派生）、范围两端必建（min/max/选项/组合各跑一遍 build，在临时副本跑、永不写用户的 parameters.json）、按计算位置创建特征禁按索引选边（"参数变了，'第三条边'就不是那条边了"）。

1.6 其余机制速览

  • Git 时间线：build 成功才 commit（soma build says "Build ok"）；App 把 commit 渲染成时间线供用户预览/恢复；agent 禁 reset/rebase/checkout
  • 21 个 skill 规则包（app/resources/skills/）：design-workflow（先问需求≤5 问或 assume+标记；接口尺寸只来自 datasheet/inputs/ 文件 never from memory；粗到细三档 concept/prototype/production；一次一改+build+commit；每步 3-6 行汇报）、tolerances、fem、standard-parts（ISO/DIN 紧固件 CSV 维度表 + 配套孔工具 s.clearance_hole()）、sheet-metal、cnc 等，frontmatter 带 when/default: always|on-demand/order/{{var}} 应用级配置（如 ask=ask|assume、max_params=15、check=full|main|off）
  • 角色语义：role="reference"（用户带入件，半透明、切割留隙但不导出）/ role="hardware"（标准件）
  • 分析：soma analyze overhang|thickness|clearance 表面逐点值 + soma analyze fem（CalculiX，载荷工况是 Python 文件）
  • .soma 单文件：代码+结果+历史打包，"like a CAD file"
  • soma CLI：build/export/render/analyze/anim/drawing/dxfview/glb/env/serve/warm，"keep the model buildable at all times"
  • Model-Exception：GPL 代码，模型文件归用户任意授权

二、归纳总结：逐项对照判定（CATDS 现状 × SOMA 机制）

# SOMA 机制 CATDS 现状 判定 理由与动作
1 结构化反馈协议（GUI 事件→带指针的结构化注入：点选/标注/改参/构建失败） GUI 有看板/日志，用户反馈只有自由文本 NL；B2 拓扑快照是执行侧自检非用户侧输入 🟢 新增主线（最小动作+验收门） B1 契约管下行（LLM→CATIA JSON），反馈协议补上行（GUI/用户→LLM）的对称契约。最小动作：GUI 点选元素（面/特征/Body）→ 生成结构化上下文行（Part 名+特征链+当前参数值+拓扑锚点）拼进下一轮 prompt；构建失败注 [错误: 命令X 阶段Y 原因Z]；面板/命令改参注改前改后值。工作量 0.5-1 天。验收门：真机 10 次点选抽测，LLM 首轮正确引用该元素（无"哪个面？"反问）≥9 次
2 视觉自检闭环（soma render→"Open the picture and look at it"；markup 图 agent 必读） 无截图无多模态；nlp_processor 为纯文本 DeepSeek 型 chat API（SSE 流式），LLM 只见文本 JSON 回执 ⏸️ 增强阶段（触发：B2 文本快照误判/漏判 ≥2 次，或用户报"改错地方/看错元素"≥2 次） 两道前置：①NLP API 换多模态模型或加 vision 旁路（配置级改动，成本真实存在）；②pycatia 截图通道（CATIA Viewer API 可截）。文本 JSON 回执+B2 已覆盖大部分场景，视觉是补强不是缺口——与 #1 反馈协议（点选带指针）相比优先级靠后
3 param() 参数契约（min/max/step/unit/options + 用户值覆盖默认值 + 未用警告 + 改名语义） modify_feature_parameter 改参非重建（真机已验证），无范围契约、无"用户改过值 vs 默认值"分离 ⏸️ 增强（触发：下次改参功能迭代时并入） JSON 契约层给参数加 min/max+单位+语义名（中文 label 对齐参数树）；"参数独立（其二为参数其余派生）"与"范围两端必建"验收法直接增补进 T2C 默认值契约文档（docs/2026-09-11-T2C默认值契约.md）
4 Git 时间线（build 成功才 commit；App 时间线预览/恢复；agent 禁改历史） save 三态 + CATIA 原生 undo + 尺寸修改确定性重放 + 事务回滚；history.db 记命令无任意步恢复 ⏸️ 增强（触发：用户出现"回不到之前状态"痛点 ≥2 次） COM 会话全量重放成本高；务实路径=checkpoint 快照：每条成功命令后自动存 .CATPart 版本副本（磁盘配额内滚动保留），GUI 时间线列出可恢复。SOMA"build 成功才 commit"对应"命令成功才记 checkpoint"，契约一致

三、三个最值得吸收的思想（判定之外的增量）

3.1 "反馈即契约"

CATDS 的 B1 契约思想目前是单向的：下行（LLM→CATIA）有 JSON 契约+schema 校验，上行（用户/GUI→LLM）仍是自由文本。SOMA 证明了上行同样可以契约化：每个 GUI 事件都变成 [类型: 指针] 结构化注入，LLM 拿到的不是"用户说这个面"的模糊转述，而是"Part.X/Face.Y/参数 Z=40（默认 38）/第 12 行"的精确定位。双向契约才是完整的 agent-应用接口。

3.2 "agent 必须看自己的产出"

soma render + "Open the picture and look at it" 把多模态自检写成 agent 的强制规则而非可选能力。CATDS 的 B2 拓扑快照是这一思想的文本版（读回拓扑对拍预期）；SOMA 指出了下一级形态——让 LLM 长眼睛。触发条件未到时，至少可以把这条记入架构备忘：当多模态 NLP 就绪，自检从"读数对拍"升级为"看图确认"。

3.3 "范围两端必建"的参数验收法

不是测默认值，而是 min/max/每个选项/全 min 组合/全 max 组合各 build 一遍，在临时副本跑（永不污染用户面板值）。这对 CATDS 参数化改参的回归验收直接可用——真机测试文档的"改参用例"可加"边界档"（参数取规格边界值时改参仍成功且几何合理）。

四、批判性审视

  1. 极早期原型：314 stars / 17 天 18 release / 自述 "Early prototype, expect rough edges" + "SOMA itself is vibe coded"。成熟度远低于 text-to-cad（13.7k stars/970 commits/CI 齐备）。借鉴协议与思想，不借鉴工程实现——它的 Electron/渲染层没有经过我们需要的验证强度。
  2. 内核代差照旧：CadQuery/OpenCascade vs CATIA CGM，容差/缝合/曲面质量不可平移（T2C 批判 §四.2 已判）。SOMA 的 parametric skill 里"按索引选边在参数变化后失效"的坑，在 CATIA 语义建模里由 B2 拓扑快照+语义锚点解决——我们的解更严。
  3. GPL-3.0 传染：Model-Exception 只豁免模型文件许可，App 代码全量 GPL。CATDS 为企业内部项目：吸收协议格式（如注入语法）、思想（反馈契约）、数据结构定义（如 param 字段集）合法；复制任何源码片段=许可证污染。
  4. 无事务/无幂等：SOMA build 是脚本级全量重跑，失败即止；CATDS 的 COM 事务保护+幂等缓存+改参非重建在工程严谨性上反超——这是 CATDS 可以反向输出的部分（若 SOMA 团队来问）。
  5. 用户模型差异：maker（要个打印壳，容错高、迭代快）vs CATIA 工程师（型号设计+适航，每步可追溯）。SOMA 的"粗到细+一次一改"工作流对后者反而是纪律基线——已被我们的 composite 分解+事务覆盖。

八、趋势判断

  1. CAD-Agent 赛道三层分化确认：skill 库（text-to-cad）/ 桌面 harness（SOMA）/ 垂直独立应用（CATDS）——同一季度出现三种形态，验证了 T2C 判定的赛道分层；SOMA 补上了"应用壳"生态位
  2. "结构化反馈注入"正在成为 agent-应用接口的事实范式：SOMA 的 [类型: 指针] 注入与 MCP 的资源引用、Claude/Codex 的文件指针同构——上行契约化是 2026 agent 工程的收敛方向
  3. 多模态自检从加分项变基线："agent 必须看产出"在 SOMA 被写成硬规则，CAD/代码/文档场景都在收敛到这一标准
  4. maker 级 CAD-Agent 的迭代速度惊人（17 天 18 release），但企业级（适航/构型/可追溯）仍是空白——CATDS 的 B1-B7 严谨层在企业侧没有竞争者，时间窗口在
  5. GPL 协议的 CAD-AI 项目增多（SOMA/GPL-3.0 vs text-to-cad/MIT）——企业吸收开源思想时的许可证尽调成为常规动作

九、关联分析

  • 对《2026-09-11-text-to-cad×CATDS逐项判定》：T2C 判"skill 库层"，SOMA 判"应用壳层"，两者互补不重复；T2C 的 #7 能力边界声明在 SOMA 得到应用层印证（它也有明确 when/not-when）；T2C#8 现货件观察项在 SOMA 找到实现范式（#13）
  • 对《2026-09-15-CAD厂商AI布局全景更新》：SOMA 是厂商布局之外的开源第三势力——不带内核、不带 agent，纯做"结合层"；佐证"结合层独立成赛道"的判断
  • 对 CATDS B1-B7：#1 反馈协议是 B1 契约的上行延伸（B1+）；#4 checkpoint 与 save 三态互补；#2 视觉闭环是 B2 快照的多模态升级路径；#9 #10 确认 B 系严谨层与 B7 桥已覆盖 SOMA 对应物且更严
  • 对用户适航/构型管理领域：#8 接口输入文件区（inputs/ 只读+来源可查）与型号资料管理的"引用而非复制"原则同构——领域知识反过来验证了 SOMA 模式的工程正确性

十、拓展应用推荐

  1. CATDS 主线采纳 #1（本笔记 §五决策表）——最高性价比改良
  2. 反馈协议模式外推到 jbot 自己的 GUI/工具：Hermes 侧任何"用户点选/标注→LLM"场景（如 LanGPT 截图反馈、homepage 笔记批注）都可套 [类型: 指针] 注入格式
  3. "范围两端必建"验收法通用化：任何参数化产物（训练配置/部署参数/脚本门限）的回归验收都适用 min/max/组合档
