## 一、推理优化的成本动机

### 1.1 核心问题

> "The average LLM API call wastes 40-60% of input tokens on context the model doesn't need."

三大浪费源：

| 浪费类型 | 描述 | 量化 |
|----------|------|------|
| **上下文膨胀** | Agent 累积上下文，input tokens 从第 1 轮到第 30 轮增长 5-10x | — |
| **冗余计算** | 无缓存时模型对相同前缀反复计算 attention | 10K-token prefix = 数十亿 FLOPs 重复消耗 |
| **硬件未利用** | 默认服务配置 GPU 空闲（H100@$3/h 可能只跑 50 tok/s 而非 16,000+） | 利用率 <5% |

### 1.2 价格趋势

- LLM API 价格 2025→2026 下降约 80%
- GPT-4 级别性能从 $30/M tokens（2023-03）降至 $0.40/M tokens（2026）
- **但** Agent 工作流每个任务 50-200 次 LLM 调用，per-task 成本仍然显著

## 二、模型层：量化、剪枝、蒸馏

### 2.1 量化（Quantization）

| 方法 | 机制 | 效果 |
|------|------|------|
| **SmoothQuant** | 将量化难度从 activation 迁移到 weight | 2x 内存减少，精度损失可忽略 |
| **GPTQ / AWQ** | 用校准数据寻找每层最优量化参数 | FP16→INT8/INT4 |
| **TurboQuant**（Google 2026-03） | 压缩 KV cache 本身到 3 bit/value | KV cache 内存减少 6x，零精度损失 |

**选型建议**：量化是**成本/收益比最高**的优化，零训练成本即可减约 50% 开销，保持 95-99% 精度。

### 2.2 剪枝（Pruning）

- **结构化剪枝**：移除整个 attention head 或 MLP 列
- **非结构化剪枝**：逐权重置零
- 实测：6B 剪枝模型比 dense 对应体快 30%，MMLU 得 72.5（超过未剪枝 4B 的 70.0）

### 2.3 知识蒸馏（Distillation）

最优压缩管线：**P-KD-Q**（先剪枝 → 再蒸馏 → 最后量化），每步效益叠加。

## 三、系统层：连续批处理 + PagedAttention + 推测解码

> "Naive static batching leaves 60% of your GPU idle on average. The three techniques in this guide compound on each other. Together they are what makes vLLM serve 3-5x more traffic than a naive PyTorch inference loop on the same H100."

### 3.1 连续批处理（Continuous Batching）

**问题**：静态批处理必须等 batch 中最长序列生成完毕才能释放短序列的 GPU 槽位。785 个迭代步的 GPU 内存/算力在等待中白白浪费。

**机制**：也叫 iteration-level scheduling / in-flight batching。不再将 batch 视为整体，而是每个解码迭代步都可以重新洗牌哪些请求在活跃使用算力。

**效果**：相同硬件吞吐量提升 3-10x。Anyscale 实测生产工作流 23x 聚合吞吐提升。

### 3.2 PagedAttention

**问题**：PagedAttention 之前，框架为每个请求**预分配最大可能输出长度的连续 GPU 内存块**。

**机制**：将 KV cache 拆分为小的、可复用的 page，按需分配（类似操作系统虚拟内存分页）。

**效果**：内存浪费减少高达 90%，同时服务请求数提升 24x。

**进阶 KV 压缩**：
- **ChunkKV**：以语义 chunk 而非孤立 token 作为压缩单元
- **RocketKV**：两阶段管线——先粗粒度 KV 驱逐，再细粒度压缩

## 四、推测解码深度解析

### 4.1 核心原理

传统自回归生成逐 token 串行，GPU 在单 token 生成时大量算力闲置。推测解码用两阶段打破瓶颈：

1. **Draft 阶段**：小型快速模型快速生成 K 个候选 token（5-8 个候选续写）
2. **Verify 阶段**：目标模型在单次并行前向传播中处理全部 K 个 token
3. **Accept/Reject**：在每个位置比较 draft 与 target 分布，对齐则接受

> "The algorithm guarantees output matches exactly what the target model would produce independently." — **无损加速**

### 4.2 2025-2026 生产级基准

| 框架/模型 | 配置 | 加速比 |
|-----------|------|--------|
| vLLM + Llama 3.1-70B | 1B draft model | **2.31x** |
| Llama 3.1-8B (单 A100) | — | 1.8x 延迟降低 |
| TensorRT-LLM on H200 | Llama 3.1-405B FP8 | **3.6x** |
| SGLang + SpecForge | Llama 4 Maverick | 2.18x |
| EAGLE 方法 | — | 2.5-2.8x（Spec-Bench SOTA） |

### 4.3 进阶技术对比

| 技术 | 原理 | 优势 | 适用场景 |
|------|------|------|----------|
| **EAGLE / EAGLE-3** | 训练轻量 draft head | ~0.8 接受率，SOTA | 通用首选 |
| **Self-Speculative (SWIFT)** | 自适应跳过目标模型中间层 | 无需额外模型/训练 | 硬件受限场景 |
| **Ngram Speculation** | N-gram 查表做 draft | 零训练，极快 | 重复性高的文本 |
| **Medusa Heads** | 在模型上增加多头预测 +1/+2/+3 位置 | 并行多步 | 需修改模型 |
| **SpecForge** | SGLang 原生集成 | 预训练 speculator | SGLang 用户 |

### 4.4 Draft 模型选择准则

- **架构对齐**：同系列模型接受率更高
- **大小比例**：目标模型的 1/10 到 1/50
- **接受率阈值**：目标 60%+，低于 50% 可能反而拖慢

### 4.5 适用场景判断

**适合**：
- 交互式聊天（优先延迟）
- GPU 未充分利用的单用户推理
- 长文本生成（故事、文档、代码）
- token 模式可预测的工作负载

**不适合**：
- 已饱和 GPU 的高吞吐批处理
- 极短回复（无足够 token 可推测）
- 高随机性/创造性生成（低接受率）

## 六、应用层：Prompt 缓存与上下文压缩

### 6.1 Prompt Caching

- 复用之前计算的 KV tensor
- 10K+ token 上下文：缓存部分延迟降低 80-90%
- Anthropic 实现中，缓存的 input token 不计入费用

### 6.2 上下文压缩

- 智能裁剪：Agent 第 30 轮的 context 可能是第 1 轮的 5-10x
- 对话历史管理：保留关键信息，淘汰冗余
- 每轮 prompt 只发送必要 context

## 七、对 Hermes Agent 及边缘部署的启示

### 7.1 Hermes Gateway 推理优化

- **API 调用层**：已实现前缀缓存（system prompt + skill 描述共享前缀）→ 验证是否利用 Anthropic/OpenAI 的 prompt caching
- **Cron 批处理**：多 cron 任务共享相似 context，连续批处理可显著降低成本
- **推测解码**：对本地 Ollama（Jetson Orin）部署，推测解码可提升单用户交互响应速度

### 7.2 Jetson Orin 边缘部署

| 技术 | 边缘适用性 | 建议 |
|------|-----------|------|
| INT4 量化 | ✅ 高 | GGUF Q4_K_M 已在用 |
| 推测解码 | ⚠️ 中 | draft 模型占用额外内存，7B→1B 可行 |
| 连续批处理 | ❌ 低 | 边缘单用户场景无批处理需求 |
| PagedAttention | ✅ 高 | 内存受限场景价值大 |
| KV Cache 压缩 | ✅ 高 | TurboQuant 3-bit 可尝试 |

### 7.3 实践建议

1. **API 端**：启用 Anthropic prompt caching，对 10K+ system prompt 可降 80%+ 延迟
2. **本地端**：Jetson 上尝试 vLLM 的 EAGLE 推测解码（如内存允许）
3. **Cron 优化**：合并相似 prompt 的 cron 任务到同一批次，利用前缀缓存
4. **监控**：追踪每个 cron 任务的 token 消耗趋势，识别 context 膨胀
