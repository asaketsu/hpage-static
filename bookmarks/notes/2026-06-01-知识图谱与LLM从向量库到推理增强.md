# 知识图谱+LLM：从向量库 RAG 到推理增强

> 来源：[叶小钗·公众号](https://mp.weixin.qq.com/s/2pk4Mhr4nLMapJrTqpYX6Q) · 2026-05-04
> 标签：`#知识图谱` `#RAG` `#LLM` `#CDSS` `#GraphRAG` `#本体论` `#医疗AI`

---

## 核心论点

**向量库不是 RAG 的必选项**。它将知识压缩为孤立的"点"，语义检索很脆弱。知识图谱的回归是对知识本质的回应——不满足于"更像"，而是"更相关"与"更可信"。

> 真实的系统，往往是关键词、规则路由、向量检索与图谱查询的混合体。

---

## 一、向量库的问题

### 传统 RAG 四步

```
切分(Chunking) → 向量化(Embedding) → 检索(Retrieval) → 拼凑(Prompting)
```

### 致命缺陷：上下文割裂

| 场景 | 问题 | 后果 |
|------|------|------|
| 电商退款助手 | "T+1"主条款召回，"黑名单除外"在下一块未召回 | 高风险订单被误退款 |
| 医疗临床指南 | "适用症"与"妊娠期禁用"被切到不同块 | 孕妇用了禁用药 |
| 通用 | 文档分块破坏原文完整性（表格、论证逻辑） | 信息丢失 |

### 根因

- Embedding 编码长度有限（256-768 tokens，最新 8000）
- 太短：信息不足，匹配不上
- 太长：核心语义被稀释，"信息淹没"
- **语义相似 ≠ 语义正确**，它找的是"像"的，不是"对"的

## 二、知识图谱

### 三大元素

| 元素 | 含义 | 示例 |
|------|------|------|
| **实体** (Entities) | 节点，代表事物/概念 | 疾病、药物、症状 |
| **关系** (Relations) | 实体间的连接 | 表现为、引发、治疗 |
| **属性** (Attributes) | 实体/关系的特征 | 类型、用途、方法 |

### 知识库 vs 知识图谱

```
知识库（无关系）：糖尿病 → 属性列表（类型、并发症数组）  // 点状
知识图谱（有关系）：糖尿病 --表现为--> 口渴  --引发--> 心血管疾病  // 网状
```

> 图谱 = 强制将知识按**实体-关系-属性**标准结构化。

### 图谱核心优势

1. **跨领域关联**：二甲双胍→治疗→糖尿病，二甲双胍→可能导致→体重下降，二甲双胍→通过AMPK通路→代谢调节
2. **低成本扩展**：新关系只需添加三元组，不需要改数据库 schema
3. **推理能力**：可做路径推理（症状→疾病类别→检查指标→鉴别诊断）
4. **约束生成**：对大模型输出进行实时约束，降低幻觉

## 三、CDSS 案例复盘

### CDSS（临床决策支持系统）为什么失败

| 问题 | 原因 |
|------|------|
| **知识库不全** | ICD-11 几万个疾病，专业人员录入成本极高，校准困难 |
| **泛化能力不足** | 患者说"胸口很沉"，CDSS 需要"胸痛"标准术语才能匹配 |

> 好的医生不需要 CDSS，水平不行的医生也抽取不准。CDSS 鸡肋。

### 大模型时代 CDSS 重生

- 泛化能力鸿沟被 LLM 弥合（"胸口很沉"→自动映射"胸痛"）
- 知识图谱提供**确定性约束**，LLM 提供**语义理解**
- 快思考（LLM）+ 慢思考（图谱）= 靠谱的医疗 AI

## 四、图谱+LLM 架构

### 医疗置信度四维度

| 维度 | 含义 |
|------|------|
| **数据溯源** | 每条结论追溯到权威指南/文献/病历 |
| **一致性** | 多数据源推理结果一致 |
| **动态性** | 实时更新最新医学研究 |
| **可解释推理链** | 附带推理链+证据来源 |

### 三层防御体系

```
输入 → 路由判断
  ├─ 简单查询 → RAG 基础层 → 置信度验证
  └─ 复杂查询 → 图谱推理层 → 置信度验证
                           → 置信度>90% → 输出
                           → 置信度<90% → 专家复核
```

### 三种方案对比

| 方案 | 效果 |
|------|------|
| 纯 LLM | 有推理但无约束，幻觉风险高 |
| LLM + RAG | 有信息但拼凑缺乏逻辑性 |
| **LLM + 图谱 + RAG** | 结构化推理 + CoT + 溯源，可信度最高 |

## 五、本体论 (Ontology)

### 核心定义

> 本体论 = 去表述这个世界应该被如何定义（这个世界可以很小）。

图谱是网，**本体论是网背后的建模规则**。

### 本体论解决什么

不定义本体，"发热、肺炎、抗生素、白细胞升高"会被粗暴地等价为同类节点——但它们根本不是：
- 发热 = 症状
- 肺炎 = 疾病
- 抗生素 = 药物类别
- 白细胞升高 = 检查结果

本体论定义：
1. **实体类型**：疾病、症状、药物、检查、指南、禁忌证
2. **允许关系**：疾病表现为症状，药物治疗疾病，药物禁用于某类人群
3. **语义强度**：因果、相关、并发、风险提示、弱关联
4. **推理规则**：哪些关系可传递，哪些必须结合证据等级

> **本体论是让知识图谱具备行业 KnowHow 的建模规则。** 大模型可以帮提高抽取效率，但本体论决定抽取结果能不能被正确使用。

## 六、工程启示

### 向量库的正确角色

> 向量库不是主角，而是模糊问法的补充工具——处理"先定位、后精读"中的定位环节。

### 真实系统架构

```
关键词 + 规则路由 + 向量检索 + 图谱查询 = 混合体
```

### 未来方向

- 从"检索增强"走向"推理增强"
- 组件内化为 Agent 能力：自主规划、多步推理、自我校验
- Google NotebookLM 的技术路径可能是方向

---

## 思考

这篇文章对 RAG 系统的演进做了非常清晰的梳理，核心洞察是：**语义相似 ≠ 语义正确**。

**与我们系统的关系**：

| 我们的实践 | 对应文中概念 |
|-----------|-------------|
| Memory Graph (MCP) | 知识图谱 |
| mcp_memorygraph_create_relationship | 三元组 |
| recall_memories / search_memories | 向量检索+关键词混合 |
| 缺失：本体论定义 | ❌ 未定义实体类型/关系语义强度 |

**可改进**：
1. 为 Memory Graph 增加本体论层——定义实体类型和关系的语义强度
2. 记忆检索时区分"因果"和"弱关联"关系类型
3. 对关键决策类记忆增加溯源字段
