摘要

文章提出一个简洁的心智模型：RAG 是 AI 的记忆（从静态文档提取知识），MCP 是 AI 的双手（对实时系统执行操作）。单独使用各有局限，只有两者结合才能让 AI 在工作流中"有所依据"又"有所作为"。文章给出了数据管道支持代理的完整代码示例，展示了 RAG 检索 SLA 文档 + MCP 查询实时管道状态的混合架构。

核心内容

1. RAG — 赋予 LLM 长期记忆

  • 解决的问题：LLM 知识截止于训练日期，不知道内部文档、架构决策、运行手册
  • 工作流：文档索引(FAISS) → 语义检索(Top-k) → 注入上下文 → 生成答案
  • 适用场景：静态/半静态知识（文档、手册、合同、白皮书）

2. MCP — 让 LLM 能够行动

  • 定义：Anthropic 引入的开放标准，本质是带形式化规范的函数调用
  • 能力：查询实时数据库、触发工作流、读 Kafka、调 REST API、写记录
  • 适用场景：实时/近实时（管道状态、销售数据、库存、监控）

3. RAG + MCP 混合架构（核心价值）

  • 纯 RAG → 无法回答实时问题
  • 纯 MCP → 不知道组织策略/手册
  • 混合示例："SLA 是什么？昨晚管道违反了吗？"
  • RAG 检索 SLA 文档 → 策略阈值
  • MCP 调用实时管道状态 → 实际数据
  • LLM 综合分析 → 违规检测 + 行动建议

4. 代码架构参考

rag_vs_mcp_demo/
├── agent/           # LLM 路由（RAG/MCP/混合分类器）、主代理、编排器
├── rag/             # 嵌入(HuggingFace)、检索、向量存储(FAISS)
├── tools/           # 实时工具（管道状态、行计数）
├── data/            # SLA、数据质量标准、值班手册
└── examples/        # 演示查询

技术栈：OpenAI + LangChain + FAISS + sentence-transformers

🔍 借鉴点

  • LLM 路由器模式 → Hermes 的 agent 调度可以借鉴：根据查询关键词自动分流到 RAG/MCP/混合通道，减少不必要的全链路调用
  • Agentic RAG 四类代理架构 → 设计多代理系统时，按"知识检索型/工具调用型/混合型/编排型"分类，比一刀切更高效
  • MCP = AI 的 USB-C → 工具从硬编码转向协议化，Hermes 的 native-mcp 客户端就是这个方向

💡 启发

  • Hermes 本身就是 RAG + MCP 的实践者：obsidian 笔记索引 = RAG 记忆层，native-mcp + 工具系统 = MCP 行动层，这个认知可以帮助更好地优化系统架构
  • 路由器是瓶颈：文章的关键词路由器太简单，实际应该用 LLM 做意图分类（类似 Hermes 的 skill matching），否则复杂查询容易误路由
  • Agentic RAG 的核心不是 RAG 本身，而是"动态规划检索策略" — 即 Agent 自己决定查什么、查几次、查哪些源，这比固定 Top-k 检索强得多

🔮 预判

  • MCP 生态会快速膨胀 → 作为开放标准，会像 REST API 一样成为 AI 工具调用的默认协议，2026 年底主流 SaaS 都会提供 MCP 服务器
  • Agentic RAG + MCP 成为 AI 应用标配 → 纯 RAG 或纯 function calling 的系统会逐步被混合架构替代
  • 路由层成为新战场 → 哪个框架能做好意图→RAG/MCP 的智能路由，就能赢得开发者生态
