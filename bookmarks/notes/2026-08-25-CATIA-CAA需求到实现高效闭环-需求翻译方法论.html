一句话总纲

CAA 开发常见的低效路径是在对象、状态、边界和失败语义尚未确定之前过早进入接口设计。本文给出一套从需求到实现的分析方法：五步翻译（需求句→任务类型→业务对象→对象上下文→六世界→状态时序→后置条件）+ 批量原子性三策略 + 接口清单后置——接口选择应该是需求分析的结果，而不是需求分析的起点。

一、内容详细整理

1.1 核心谬误：过早进入接口设计

低效路径：需求刚说完 → 搜索接口 → 翻示例 → 试 QueryInterface → 一边写代码一边补对象关系/Update/Cancel/Undo。

Demo 成功的假象：成功路径跑通 ≠ 真实模型可用。典型坏例：

症状 根因
用户说的"孔"，代码处理的只是圆柱面 对象语义未翻译
CATPart 正常，CATProduct 找错对象 上下文未确认
参数改了，取到的还是旧结果 Update 屏障未定
Preview 污染正式模型 临时/正式未分离
Cancel 只关对话框不恢复文档 取消语义未定义
批量 86 个失败，前 85 个是否保留未定义 原子性未定
接口全成功，结果不符合业务语义 后置条件缺失

高效的 CAA 开发不是更快地找到能调用的方法，而是更早地把业务需求翻译成一份可以验证的 CATIA 技术模型。

1.3 任务类型七分类（主结构判定）

任务类型 核心特征 首要设计问题
查询型 读取不修改 对象范围/遍历成本/结果可信度
检查型 读取输出诊断 规则定义/证据定位/误报漏报
交互编辑型 选择输入预览提交 State Command/临时状态/Cancel/Undo
创建型 加入新对象 Factory/Container/规格关系/Update
批量修改型 大量对象同操作 原子性/Update 批次/失败隔离/性能
可视化型 高亮标记临时图形 ISO/Rep/Viewer/清理时机
集成型 与文件/DB/PLM 交换 身份映射/幂等性/外部补偿/权限

主结构意义：谁驱动（用户事件/遍历/消息）、状态存哪（Command/Batch/服务）、错误何时反馈（交互/汇总/日志）、如何结束（NULL State/批完成/外部确认）、Undo 是否存在。

1.4 对象翻译四问（用户语言→CATIA 对象）

以"孔"为例：Hole Feature / 圆柱 Face / 草图圆 / 导入实体孔 / 装配 Instance——不能默认一一对应。

1. 用户选中的是什么？
2. 真正要修改的是什么？
3. 两者之间能否稳定导航？
4. 修改完成后从哪里验证？

选择对象：Hole Feature
修改对象：直径规格
验证对象：Update 后的 Hole Result
显示对象：高亮+临时文本（非正式几何）

1.5 上下文图（对象层级）

CATIA Session → 当前 Document → Part → Part 根 → 规格容器 → Hole Feature
    → 直径规格 / Update 后 Result → Face/Edge
标记：取得上下文/Selection 层级/Setter 层级/Update 目标/结果读取/跨 Update 引用

关键警告：不要默认 Active Document = 目标 Document（装配/多窗口/编辑上下文可能不同）；命令入口确定工作上下文，深层服务不再猜环境。

1.6 六世界模型（核心概念）

一次用户操作跨越的六个状态世界：

世界 典型内容 常见 Bug
交互世界 Agent/Selection/Dialog Dialog 关了以为命令结束
规格世界 Feature/参数/父子关系 改规格以为 Result 已更新
计算世界 Update/Result/下游 Update 成功后仍用旧 Face
拓扑世界 Face/Edge/Vertex 几何身份跨 Update 失效
显示世界 ISO/Rep/Viewer Viewer 刷新以为模型已 Update
历史世界 Transaction/Undo/Redo 文档 Undo 以为客户缓存也恢复

影响矩阵（孔径示例，阶段×世界）：

            交互      规格      计算/拓扑   显示      历史
选择      存目标集合  不修改     不修改     高亮      本地输入Undo
Preview   留待提交    不修改     不修改     旧→新     不进文档历史
OK        锁定输入   批量修改    Update+检查  清Preview  一次命令历史
Update失败 保留输入   恢复本次   不接受失败   诊断      不形成成功历史
Cancel    清输入     不修改     不修改     清理临时   不留命令结果

1.7 Update 边界（正确性设计优先）

Update 决定结果何时可信，也是错误发生和事务恢复的边界。首先是正确性设计，然后才是性能设计。

  • 先问：下一步要相信规格还是计算后的结果？
  • 批量策略：集中写入全部规格 → 对共同 Part 更新一次 → 检查必要下游（而非逐个 Hole Update 整个 Part）
  • 例外：依赖前一个对象更新后几何时必须保留中间屏障
  • 五个判定：明确原因/目标足够小且可信/失败可定位/不使用失效拓扑/能决定继续-恢复-结束

1.8 批量原子性三策略

策略 语义 适合
All-or-Nothing 全部成功保留；任一失败恢复全部 强一致性/用户理解为一个整体/部分修改不可接受/Undo 一次全撤
Best-Effort 成功保留/失败跳过/出报告 对象独立/数据量大/尽可能多完成/失败可后补
分批提交 按 Document/业务分组独立提交 跨文档批处理，避免一坏全回滚

All-or-Nothing 是业务承诺，不是把循环放进同一个函数就会自动得到的能力。 需要依赖文档事务/本地 Undo 边界/明确恢复路径；框架无法可靠恢复就要调整粒度，不能在界面上承诺"全部回滚"代码却只能部分恢复。

1.9 Cancel/Undo 语义表

Preview 中 Cancel：删临时对象；不修改正式文档；不提交外部
提交前校验失败： 保留/刷新临时；不修改；可修改输入
Update 失败：    重建诊断；恢复本次写入；可重试或取消
OK 成功：        删除临时；保留；提交；可 Undo
命令后 Undo：    事务恢复；客户补偿

Cancel ≠ 关闭窗口：影子 Preview 删临时即够；实时编辑正式模型需恢复路径；外部副作用需独立补偿。Undo 粒度是产品语义（一次输入/一个对象/一次 Apply/整个命令/Document 分组）。

1.10 外部副作用单独建模

CATIA 文档可以 Undo ≠ 外部系统也自动恢复
  • 何时执行（提交前/后）？幂等重试？模型成功但外部失败如何补偿？Undo 同步外部？补偿数据谁持有？
  • 优先顺序：本地校验 → 提交并确认模型 → 可重试外部提交；强一致需明确协议+人工恢复。

1.11 三层架构（接口代码限制在适配层）

Command/Batch Orchestrator → 决定流程/状态/失败策略
Domain Operation           → 业务动作（校验孔/改直径/验证结果）
CAA Adapter                → QueryInterface/Factory/Container/Update/引用管理

1.12 一页式需求设计卡（20 项）

业务目标 / 工作上下文（Document 类型/编辑对象/跨文档/Instance-Reference）/ 输入（选择/参数/过滤）/ 对象翻译（看到的/修改的/验证的）/ 操作类型 / 临时状态（Preview/高亮/缓存/清理）/ 正式修改 / Update（目标/时机/结果检查/拓扑重解析）/ 提交语义 / 结束语义（OK/Apply/Cancel/Update失败/打断）/ 历史（输入Undo/Command Undo/Redo/外部补偿）/ 规模性能 / 验收（后置/恢复/测试模型）

当这张卡无法填写时，需求还没有达到可以稳定编码的程度。

1.13 十个 Go/No-Go 问题（编码前检查）

  1. 一句话可验证的成功结果？2. 用户对象 vs 修改对象已区分？3. Document/Container/编辑上下文明确？4. 主结构类型确定？5. Preview 是否改正式模型达成一致？6. Update 目标/时机/失败判断明确？7. 部分失败策略？8. Cancel/Undo/Redo 恢复哪些状态？9. 外部副作用是否建模？10. 最大规模与关键错误场景？

两三个问题只能回答"写着看" → 暂停接口开发继续收敛需求。

1.14 测试从需求模型生成（五组）

  • 上下文：无活动文档/非 CATPart/只读/跨文档选择/CATProduct 进入/多窗口切换
  • 对象：合法 Hole/圆柱 Face/草图圆/导入实体孔/目标被改/混入不支持对象
  • 输入提交：合法/零负超范围/重复选择/全部成功/中间失败/Update 失败/下游失败/结果不一致
  • 生命周期：Preview 后 Cancel/重复 Preview/Apply 多次/失败重试/命令打断/Exclusive 抢占/OK 清理
  • 历史：一次 Undo 全撤/Redo/失效拓扑不访问/失败不留历史/清空历史时 Payload 释放
  • 规模：1/100/上限/复杂下游/中途取消/日志非瓶颈

这种测试验证的是需求语义，而不仅是接口是否返回成功。

二、查询拓展

2.1 与 agent 需求工程的方法论同构

本文的 CAA 翻译方法论与 Agent/Hermes 的需求工程完全同构：

CAA 概念 Agent 体系对应
可验证需求句 任务验收标准（AGENTS.md 完成定义）
任务类型主结构 delegate 任务类型判定
六世界模型 上下文分层（L1/L2/L3）不越层假设
影响矩阵 Harness 工程的状态分离
后置条件 notes_7module_check 验收门禁
外部副作用 外部 API/文件写入的补偿设计
测试从需求生成 TDD（test-driven-development skill）

核心同构：都是"把边界前置想清楚，实现变成最易验证的部分"。

2.2 三层架构与 hexagon/clean architecture 的 CAA 化

Orchestrator/Domain/Adapter 三层 = Clean Architecture 的用例-域-基础设施映射。CAA 特化点：Adapter 层专属 QueryInterface 生命周期（Release/跨 Update 有效性）；Domain 层完全不依赖 CATIA 类型（可用纯 C++ 单测）。

三、归纳总结

3.1 方法骨架 9 步

① 可验证需求句（12 项模板）
② 判定任务主类型（7 类）
③ 对象翻译四问（用户语言→CATIA 对象）
④ 对象上下文图（层级 + 六标记）
⑤ 六世界影响矩阵（阶段×世界）
⑥ 状态与时间顺序（先状态后对话框）
⑦ Update 屏障 + 成功后置条件
⑧ 批量原子性 + Cancel/Undo/失败恢复
⑨ 建立接口清单（每接口补获取路径/所有权/有效期/副作用四项）

3.2 五条原则

  1. 用户语言中的对象 ≠ 可直接修改的 CATIA 对象
  2. 接口返回成功 ≠ 需求满足（必须由后置条件定义）
  3. Preview/正式模型/计算结果/显示/Undo 属于不同状态世界
  4. Update/Cancel/失败策略是方案的一部分，不能代码末尾补
  5. 接口选择是需求分析的结果，不是起点

四、趋势判断

趋势 1：CAA 开发方法论将与 AI 编码工具深度结合

依据：本文的方法论（需求句→翻译→接口清单）恰好是 AI 辅助开发（Codex/Claude Code 类）的最佳输入格式——把"可验证需求句+设计卡"喂给 AI，比喂"帮我写个修改孔径的命令"效率高一个数量级。本机已具备 CAA-Mate VSCode 插件（06-02 笔记）与 AI 接入基础（04-22 CATIA 接入大模型）。

趋势 2：CAA 开发岗位从"接口熟练度"转向"语义建模能力"

依据：本文反复强调的"问题不来自接口不会用，而来自语义边界未定"——接口知识可被 AI 补全（copilot/agent），但把业务需求翻译成可验证技术模型的能力仍是人/Agent 的核心壁垒。
