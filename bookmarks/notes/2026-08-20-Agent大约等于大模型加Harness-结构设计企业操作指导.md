## 〇、执行摘要（内容整理）

| 命题 | 展开含义 | 结构设计企业对应物 |
|------|---------|-------------------|
| Agent ≈ 大模型 + Harness | 模型负责理解/判断/规划，Harness 负责感知（目录/文件/工具）+ 执行 + 断点续跑 | 模型=设计知识大脑，Harness=连接 CATIA/nTop/PDM/规范库的手脚 |
| 大模型只有脑子 | 不会凭空感知你的目录、文件、工具 | 模型不知道你的截面库、材料库、上一版验算结果 |
| 任务断了不知道从哪继续 | 会话级记忆 ≠ 工程闭环 | 设计迭代横跨数周，中断恢复是常态需求 |
| 把判断落成动作，把结果交回大脑 | 循环：感知→判断→执行→回读 | 需求→载荷→选型→验算→优化→建模→验证的每一步都是"落动作+交回" |
| **Agent 的价值在于闭环，而非模型本身** | 交付物由循环产生 | 出 CATPart/验算报告/追溯矩阵的是管线，不是单次问答 |

**一句话**：结构设计企业买模型不等于买 Agent——**闭环管线（Harness）才是把设计知识变成交付物的那一半，且是必须自建的那一半**。

## 一、大模型 vs Harness 的职责分解（指南分析）

### 1.1 逐句拆解原命题

| 原句 | 职责归属 | 工程含义 |
|------|---------|---------|
| "理解、判断、规划下一步" | 模型 | 读规范、判工况、选方案、定参数 |
| "不会凭空感知到你的目录、文件和工具" | Harness 必须供给 | 工具清单（CATIA/nTop/自研验算器）+ 文件系统（项目目录/PDM）+ 上下文（历史验算）必须显式接入 |
| "把判断落成动作" | Harness 执行层 | 调 CLI/COM/subprocess 跑真软件，不是生成一段代码让工程师手动贴 |
| "把结果交回大脑" | Harness 回读层 | nTop 应力云图、CATIA Measure3D 测量值结构化后回传，供下一步判断 |
| "任务断了也不知道从哪继续" | Harness 状态层 | checkpoint/断点续跑是工程刚需，模型本身不提供 |

### 1.2 结构设计场景的 Harness 五件套

| Harness 组件 | 通用定义 | 结构设计企业实例（struct-gen 实证） |
|-------------|---------|----------------------------------|
| ① 工具桥 | 封装专业软件为可调用工具 | `NTopRunner`（subprocess ntopcl.exe）、`CatiaWorkflowBuilder`（pycatia COM）、BlenderBridge（三模式：embedded/headless/dry-run） |
| ② 数据供给 | 领域数据库接入 | `data/aero_sections/`（30+ 截面/3 材料/10 紧固件 JSON 库） |
| ③ 管线编排 | 多步流程状态机 | orchestrator.py 10 步：需求→概念→载荷→选型→验算→可靠性→连接→优化→建模→验证 |
| ④ 断点与降级 | 缺环境不中断 | ARM 无 CATIA → dry-run JSON；Blender 缺失 → 参数落盘；float('inf') → 999 |
| ⑤ 验证闭环 | 交付物可追溯 | TraceabilityMatrix 26+ 条：需求↔验算↔模型对齐；Measure3D.verify_against() 体积/质量比对 |

### 1.3 循环示意（原命题"循环转起来才谈得上交付"）

```
        ┌──────────── 模型（脑子）────────────┐
        │  读规范/判工况/选方案/定参数/解释结果  │
        └──────┬───────────────────▲──────────┘
        落成动作│                   │交回结果
        ┌──────▼───────────────────┴──────────┐
        │      Harness（手脚+感官）            │
        │  感知工具/文件/上下文 → 执行 → 回读   │
        │  nTop跑应力 → CATIA建模 → 测量验证   │
        └─────────────────────────────────────┘
```

## 二、结构设计企业 Agent 化操作路线（归纳总结）

### 2.1 三个成熟度台阶

| 台阶 | 特征 | 交付物 | 实证 |
|------|------|--------|------|
| L1 问答辅助 | 工程师问模型，手工执行 | 建议/公式/代码片段 | 通用 LLM 即可 |
| L2 单步半自动 | 模型出参数，工具执行单步 | 单个验算报告/单个模型 | struct-gen 单步模式 `--step stress` |
| L3 全流程闭环 | 管线自动串联，断点可续，结果可追溯 | 完整交付包（CATPart+报告+追溯矩阵） | struct-gen 10 步 orchestrator |

**目标=L3**。L2→L3 的跨越就是"从模型到 Agent"的跨越——增量全在 Harness 侧（状态管理/降级/验证），不在模型侧。

### 2.2 落地八步操作清单

1. **盘工具**：列全企业设计工具链（CATIA/NX/Nastran/nTop/自研验算器/PDM），每个确定接入方式（COM/CLI/Python API/文件交换）
2. **建数据层**：截面库/材料库/紧固件库/规范条款 JSON 化——模型可读、版本可管理（对接知识库白皮书的清洗分块产出）
3. **定管线**：按企业设计流程画步骤断面（需求→载荷→选型→验算→连接→优化→建模→验证），每步定义输入/输出 schema
4. **包工具桥**：每个工具一个 wrapper 类，统一接口（run/validate/dry_run），**缺环境必降级不崩溃**
5. **编排器**：状态机跑管线，每步落盘（小批量推进），失败可从断点重跑
6. **验证闭环**：追溯矩阵（需求↔验算↔模型），测量比对（设计值 vs 模型实测），MS≥0 门禁
7. **人机接口**：GUI 管理端（8 步进度条+实时日志）或对话式（Hermes skill 触发）；关键节点人工确认（发图前/规范判定）
8. **持续演进**：每次设计案例回流——验证失败的参数组合入库，形成企业私有"踩坑库"（对应 Alloomi"经验焊权重"的穷人版：经验固化进 skill/数据而非权重）

### 2.3 关键铁律（struct-gen 实战提炼）

- **本地优先，禁止远程通信层**：CATIA/nTop 是本地进程，subprocess/COM 直调，不建 HTTP/SSH 层——工程软件的稳定性容不下网络抖动
- **降级是设计出来的**：每个工具桥三模式（embedded > CLI > dry-run），开发机（ARM）也能跑通全流程 smoke test
- **规范必须显式**：CCAR-25/27/MIL-HDBK-5 不指定不启动；安全系数 1.5 是硬门禁（MS≥0）
- **交付物=文件不是对话**：CATPart/报告 MD+HTML/追溯矩阵 JSON 落盘，对话只是触发器
- **单位制陷阱**：航空英制（ksi/in/lb）与内部 SI 双轨，接口处显式转换——Harness 层职责，模型容易犯的错由代码兜住
- **float('inf') 类序列化地雷**：验算无载荷时的 inf 必须在序列化层转 null/999，否则整条管线崩——典型"模型不管，Harness 必管"

## 三、模型选什么 & Harness 配多少（趋势判断）

### 3.1 模型/Harness 投入配比（按成熟度）

| 台阶 | 模型投入 | Harness 投入 | 说明 |
|------|---------|-------------|------|
| L1 | 90% | 10% | 直接用 SOTA API |
| L2 | 60% | 40% | 模型+prompt 工程，工具逐步桥接 |
| L3 | 30% | 70% | 模型可换（GLM/DeepSeek/Claude 均可跑编排），**管线是资产** |

模型在 L3 是可替换件——这印证原命题"Agent 的价值在于闭环而非模型本身"。企业该沉淀的是管线+数据+验证，不是对单一模型的信仰。

### 3.2 与四预设笔记的衔接（上下文经济学在工程设计场景的应用）

| 任务 | 建议模式（借 DeepSeek Harness 概念） | 理由 |
|------|----------------------------------|------|
| 需求解析/方案比选 | 标准模式（全工具+联网查规范） | 需要知识面 |
| 参数试算/批量验算 | PTC 模式（代码串联工具调用） | 30 个截面试算=循环脚本，token 省 2/3 |
| 规范条款查询 | 精确检索（对接知识库白皮书 L2 召回层） | 条款号不能靠向量 |
| 正式发图前检查 | 极简+门禁（只跑 checklist，不许自由发挥） | 确定性压倒一切 |

### 3.3 趋势判断

1. **Harness 工程师会成为结构设计企业新岗位**：既懂 CATIA/Nastran 二次开发又懂 Agent 编排——本机 struct-gen 的 orchestrator+bridge 架构就是该岗位的技能图谱
2. **工程 Agent 的竞争在验证层**：谁敢让 Agent 出的图直接进审签流，谁就赢——验证闭环（追溯矩阵+测量比对）的可信度是分水岭
3. **AI OS 视角**（接 Yanhua 笔记评论区 139 赞观点）：大模型只是引擎，好用的是确定性极高的系统——结构设计 Agent 的终态是企业"设计操作系统"的一个进程

## 四、检查清单（拓展应用推荐）

企业自评 10 问（对应五件套×2）：

1. 我们的 CATIA/Nastran 有没有可编程接口封装？还是每次靠人点菜单？
2. 截面/材料/紧固件数据是 JSON/数据库，还是散在 PDF 手册里？
3. 设计流程的每一步有没有明确输入输出 schema？
4. 工具桥在缺软件的环境下能不能 dry-run 跑通？
5. 管线中断后能不能从断点继续，还是从头再来？
6. 交付物是文件+追溯矩阵，还是一段对话记录？
7. 规范条款引用是精确到条款号，还是"根据规范要求"？
8. 验算 MS 有没有硬门禁（<0 拦截）？
9. 每次设计迭代的经验有没有回流成数据/规则？
10. 换一个模型供应商，管线要不要重写？（答"要"= 模型耦合过深）

8 题以上答"是" → 已达 L3；5-7 → L2；<5 → 先建数据层和工具桥，别急着买模型服务。
