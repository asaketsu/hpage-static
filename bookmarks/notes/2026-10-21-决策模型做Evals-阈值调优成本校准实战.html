归纳总结

决策模型赛道半年内爆发（TypeSafe Jev → Perplexity Decider → Liquid d1 → Cloudflare Clef → OpenAI Decisions API），作为 LLM judge 的低成本替代做自动评估。Hamel 团队用 100 条公寓租赁 agent traces（二分类找 error）实测 6 个模型，核心发现：人人都在盲用默认 0.5 决策阈值，这是白白留在桌上的性能——某模型失败全打 0.40、通过全打 0.10，阈值 0.30 完美分类，默认 0.50 则一无所获。正确流程四步：①先定业务最低 precision/recall 要求（本文 80%/80%），排除不达标模型；②在约束内调阈值（分层五折交叉验证，非对称业务用 F-beta 而非机械 F1）；③把分数当置信度用之前先查校准曲线（Clef Flash 有组预测 8% 实际 60% 失败，Platt scaling 可修但 OpenAI 反而修差了）；④按 Pareto frontier 权衡性能-成本（Perplexity 0.82¢/百次 F1=0.79；OpenAI 3.72¢ F1=0.87，4.5 倍价）。作者点破：这些全是经典分类器评估方法论（P/R 权衡、阈值调优、校准），数据科学家的既有技能在 AI 时代直接复仇。

内容整理：四步选用法全文精读

测试设置：
| 项 | 值 |
|---|---|
| 数据 | 100 条公寓租赁 agent traces（对话+动作日志） |
| 任务 | 二分类：trace 是否含 error（订房失败/漏转人工） |
| 模型 | Jev 1.13、Perplexity Decider 1.1 27B、Liquid d1 / d1-ultra、Cloudflare Clef Flash、OpenAI Decisions (GPT-6 Luna) |
| 对比维度 | Performance（对比人工标注）+ Cost（token×单价）；延迟因不可控略过 |

① 理解决策阈值：
- 模型输出 0~1 分数，API 默认 ≥0.5 判 fail——默认值未经数据验证 = 劣质结果
- 阈值是 P/R 的权衡旋钮：调低多抓失败但多误报。刑审判罪重 precision（不冤枉好人），癌症筛查重 recall（宁可多查）——正确权衡点由业务目标决定，没有普适答案
- 交互图表结论：OpenAI 两类分数分得最开（F1 最高）；Perplexity / d1-ultra / OpenAI 三家满足 80%/80% 双底线进入候选

② 阈值调优（可直接抄的 coding agent prompt，已含约束）：

用保存的模型分数+二分类标签（1=失败）调决策阈值最大化 F1，约束 precision≥80% 且 recall≥80%。分层五折交叉验证：训练折选阈值、其余折测性能；多模型对比须用同一折分。只选训练折上双达标的阈值，无可行项就如实报告而非放宽要求。报告验证集 P/R/F1、未达标折、与默认 0.50 的对比。复用已存分数，不再调模型 API。

  • 实测：候选三家调优增益小于落选的 d1/Clef Flash（后者连底线都不够），但小幅 P/R 移动也影响业务成本，须有意选择而非默认
  • 警告：本文用 F1 是为简化，实际业务 P/R 权重几乎从不相等——F-beta（β<1 重 precision，β>1 重 recall）才对

③ 性能 vs 成本（Pareto frontier）：
| 模型 | F1（调优后） | 成本/百次评估 | 备注 |
|---|---|---|---|
| Perplexity Decider | 0.79 | $0.0082 | 候选中最便宜 |
| OpenAI Decisions (GPT-6 Luna) | 0.87 | $0.0372 | 最优性能，约 4.5 倍价 |
| Liquid d1-ultra | — | — | 低成本次优选项 |

④ 概率校准（分数当置信度用之前必查）：
- 0.80 分要真意味着"同类分数组约 80% 是失败"才算校准——每点约 20 条 traces 分组对比预测概率 vs 实际失败率
- Clef Flash 严重失准：某组预测均值 8%，实际 60% 失败；Perplexity/Liquid d1/Clef Flash 经 Platt scaling（log-odds 上拟合简单曲线）显著靠近对角线
- Jev 与 d1-ultra 天生校准好几乎不用修；OpenAI 反而被这版 Platt scaling 修差了——校准不是免费午餐，必须实测 Brier score 前后对比
- 校准 prompt 同样可直接用（五折同折分、log-odds 拟合、clip 离 0/1、报 Brier）

实践清单（作者 recap）：
1. judge prompt 满意后，先定最低 P/R 要求，排除不达标模型
2. 对比性能前先调阈值，选贴合业务目标的 P/R 权衡——别因为本文用 F1 就跟着用 F1
3. 分数当置信度前查校准；校准后须实测是否改善
4. 权衡性能-成本-延迟；流程是迭代的（改 prompt→重调阈值→重校准）
5. 跨任务性能波动大，必须自己测；一个 failure mode 配一个专判 judge（窄任务下模型间差距会缩小）；先用可接受的大模型，再试小模型能否平替省钱

边界认知：决策模型 vs LLM 的分界（引 Randy Olson）——分类/路由任务决策模型可平 LLM 且更便宜；需知识与推理的任务 LLM 拉开差距。OpenAI Decisions 最高 F1 最高价恰说明难任务值得为 LLM 付费。

指南分析

对我们可直接落地的三件事：

  1. 阈值调优 prompt 直接入库：把本文两个 coding agent prompt（调阈值+校准）存为评估工作流模板——任何二分类 judge（含我们未来的决策模型评估线）上线前跑一遍，替换盲用 0.5。约束式写法（不达标就报告而非放宽）值得照抄——这是防 coding agent 自作主张放宽要求的护栏设计
  2. 校准检查纳入 judge 验收：现有/未来的 LLM judge 分数若要用于分级决策（如笔记质量分档），上线前按"分组预测 vs 实际"画校准对比，失准先试 Platt scaling 并用 Brier score 验证
  3. 评估金字塔分层定稿：确定性检查（notes-eval-gate，零成本）→ 决策模型 judge（分类/路由类，廉价高频）→ LLM judge（知识与推理类，贵而强）——按任务难度升层，成本-性能 Pareto 思维贯穿
