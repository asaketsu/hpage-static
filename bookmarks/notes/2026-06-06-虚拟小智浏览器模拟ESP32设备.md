## 摘要

本文介绍了虚拟小智模拟器（SimDevice）的开发过程，旨在通过浏览器模拟基于ESP32的AI语音对话设备。开发背景源于硬件调试效率瓶颈，作者提出了基于 WebSocket/MQTT 的浏览器模拟方案。核心架构为三层：浏览器前端（Web Codecs + ScriptProcessor）→ ASP.NET Core 桥接层（SimDeviceBridge）→ 小智 AI 服务器。涉及 OTA 协议分析、Opus 音频编解码、21种情感 GIF 系统、唤醒词打断等完整功能链。整个项目约两周业余时间完成。

## 核心内容

### 1. 为什么要造这个轮子

小智（XiaoZhi）是一款基于 ESP32 的开源 AI 语音对话设备，通过 WebSocket/MQTT 与后端实时通信。调试痛点：

- 每次测试都需要真实硬件，场景受限
- 想测试 AI 服务是否正常，不想等设备重启
- 需要批量回归测试 TTS 音色或唤醒词
- 给非硬件团队演示 AI 对话效果

**理想状态**：打开网页 → 点击连接 → 像真实设备一样与 AI 对话。

完成后发现这不仅是调试工具，本身就是一个产品功能：**没买硬件的用户也能体验 AI 对话**。

### 2. 三层架构设计

为什么不能浏览器直连小智服务器？两个硬限制：

1. **WebSocket 不支持自定义 Header**：小智服务器要求 Device-Id、Client-Id、Authorization 等自定义 Header，浏览器 WebSocket API 不允许设置
2. **CORS 跨域限制**：OTA 接入流程需要先 HTTP POST 获取 WebSocket 地址和 Token，浏览器端全部被 CORS 拦截

解决方案——中间桥接层：

| 组件 | 技术 | 职责 |
|------|------|------|
| SimDeviceBridge | C# ASP.NET Core | 代替浏览器执行 OTA HTTP 请求，携带自定义 Header，建立 ClientWebSocket 连接，双向转发消息 |
| ScriptProcessor | 浏览器 getUserMedia | 麦克风 PCM 采集 → Int16 转换 → 上传 Bridge |
| Web Codecs API | Chromium AudioDecoder | Opus 帧硬件加速解码 → 实时播放 |
| 情感 GIF | noto-emoji 21种 | 服务器 emotion 字段驱动切换 |

### 3. OTA 协议与激活流程

小智设备上电后请求 OTA 接口（HTTP POST），Body 是设备硬件信息 JSON，Response 返回 WebSocket 地址和 Token。

**激活流程**：
1. 未绑定设备 → OTA 返回 activation 对象（含6位激活码）
2. 设备展示激活码，用户在 App 输入
3. 设备轮询 /activate 端点，直到激活成功

### 4. 音频管道：Opus 编解码

小智协议使用 **Opus 编码，16kHz 单声道，60ms/帧**。

**上行（麦克风 → 服务器）**：
- getUserMedia 采集 PCM → ScriptProcessor（2048 samples）→ Float32 转 Int16 → 发送 Bridge
- Bridge 用 Concentus（C# Opus 编码器）编码 → WebSocket 发给小智服务器

**下行（服务器 → 扬声器）**：
- 早期用 Concentus.js（WebAssembly）解码，延迟高、内存大
- 改用 Chromium 原生 **Web Codecs API（AudioDecoder）**，硬件加速解码，延迟降一个数量级

### 5. 实时模式与回声消除

普通模式：TTS 播放时暂停麦克风上传（防回声）。
实时模式：允许用户随时打断 AI → 同时上报麦克风 + 播放 TTS → 服务端 AEC 剔除扬声器输出。

### 6. 情感系统

- 服务器 llm 消息含 emotion 字段（如 "thinking"）
- 从 noto-emoji 提取 21 种情感 128px GIF 动图
- TTS 说话期间保持当前情感（不切换到扬声器图标），说话结束恢复最近 LLM 情感
- **细节决定灵魂**：AI 说话时脸上表情依然是"高兴"或"思考"

### 7. 唤醒词打断

浏览器用 **Web Speech Recognition API**（webkitSpeechRecognition）做实时唤醒词检测，监听到"你好小智"后立即发送 abort + 停止 TTS。

### 8. 踩过的坑

| 坑 | 描述 |
|-----|------|
| ScriptProcessor 即将废弃 | 官方推荐 AudioWorklet，但兼容性尚未成熟 |
| Web Codecs timestamp 严格递增 | AudioDecoder.decode() 要求 timestamp 严格递增（微秒），关闭重建必须归零否则 Chrome 抛 EncodingError |
| WebSocket 自定义 Header 无解 | 浏览器硬限制，只能靠中间代理 |
| GIF 重播 | 同一 emotion 不重新加载 GIF 会停止动画，需克隆节点重播 |
| 双重 disconnected | Close 帧处理 + finally 块各发一次，导致浏览器两次状态重置 |

## 关键概念

1. **OTA（Over-The-Air）**：物联网设备远程固件更新和配置下发协议，本文中用于设备注册和获取通信凭据
2. **Opus 编解码**：开源音频编解码器，适合实时语音通信，16kHz/60ms 帧是低延迟配置
3. **Web Codecs API**：Chromium 原生音视频编解码接口，支持硬件加速，比 WebAssembly 方案延迟更低
4. **ScriptProcessor vs AudioWorklet**：浏览器音频处理 API，前者即将废弃但兼容性好，后者是未来标准
5. **AEC（Acoustic Echo Cancellation）**：回声消除技术，在同时录音和播放时剔除扬声器输出
6. **SimDeviceBridge**：作者设计的中间桥接层，解决浏览器无法设置自定义 WebSocket Header 和 CORS 限制的问题

## 能力边界

- 仅适用于小智（XiaoZhi）平台的特定协议，不可直接复用于其他 IoT 设备
- Web Codecs API 仅 Chromium 系浏览器支持（Chrome/Edge），Firefox/Safari 不兼容
- 模拟器无法完全替代真实硬件测试（如射频性能、功耗、延迟抖动等物理层问题）
- Concentus（C# Opus）编码质量可能低于原生 Opus 库
- 需要部署 ASP.NET Core 桥接服务，增加了基础设施复杂度

## 最佳实践

1. **浏览器模拟 IoT 设备是可行的**——通过中间桥接层绕过浏览器安全限制
2. **音频编解码优先用原生 API**（Web Codecs > WebAssembly > JS 纯实现）
3. **Opus 60ms 帧是语音通信的良好平衡点**——延迟与质量的折中
4. **情感系统保持"说话中表情"**——小细节大幅提升用户体验
5. **设备协议分析先行**——先抓包理解 OTA/WebSocket 协议，再写模拟器
