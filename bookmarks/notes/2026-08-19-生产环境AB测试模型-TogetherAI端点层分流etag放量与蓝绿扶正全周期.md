> **一句话**：把 A/B 分流从应用层搬到**端点层**——一个对照组+最多 20 个变体按固定百分比切流量，放量/扶正/删除全是平台 API，**删除实验的那一刻流量自动 100% 回基线，客户端一行代码不用改**
> 实测锚点：95/5→80/20→50/50→删除全生命周期，配置 vs 实测占比偏差 <1 个点（1330+ 请求/阶段，3 RPS 稳定流）

## 一、内容整理

### 1. 为什么影子流量和应用层分流都不够

| 方案 | 能回答什么 | 回答不了什么 |
|---|---|---|
| **影子测试**（shadow） | 延迟/错误/吞吐等**运营指标**没问题 | 质量问题——影子响应被丢弃，没有用户基于它做动作；**留存/点赞率/任务完成率必须真实曝光** |
| **应用层自建**（feature flag + hash-mod-100 + 双端点 + 记录表格） | 能用 | ①实验与基础设施纠缠：路由逻辑跟着应用发版 ②分组比例随客户端缓存漂移 ③实验"结束"后分支代码不敢删（没人确定删掉安不安全） |
| **端点层 A/B**（本文） | 运营+质量双侧 | ——客户端无感知（端点名/API/密钥全不变），实验是独立于应用的生命周期对象 |

核心追问：新模型对用户真的更好吗？**不是基准分更高，而是产品实际在量的东西**。

### 2. 机制：实验细分的是对照组的份额

```
请求 → 基础流量分配（按权重/容量解析）
         ↓ 胜者=某实验的对照组？
       A/B 实验重采样（按各臂 percent：95% control / 5% variant）
         ↓
       滚动发布（蓝绿，源部署↔发布目标之间重采样）——组合顺序固定：分配→实验→发布
```

**五条配置铁律**：
1. 恰好一个 control + 1-20 个 variant，每个指向一个部署，percent 总和=100
2. **变体部署必须权重为零**（不出现在基础流量分配里）——变体若还能分到按容量加权流量，测量会悄悄出错
3. 对照组分配权重为零 = 实验收不到任何流量（实验细分的是对照组份额）
4. **A/B 百分比是固定流量占比，与副本数无关**——有意区别于按就绪副本走的流量分配权重：实验是测量仪器，测量期间分配必须恒定，不能跟着自动扩缩容漂移
5. 分组粘性靠请求采样键：`prompt_cache_key` 或 `user` 字段——同键请求路由一致（整个会话留在同一臂）；无键按请求随机（他们的验证实验用的就是无键流）

### 3. 生命周期：创建→放量→测量→收尾

**创建（95/5 起步）**：
```bash
tg beta endpoints ab my-org/candidate-model \
  --control $CONTROL_DEPLOYMENT --percent 5
```

**放量=重新发送完整成员列表**（没有单独 ramp API——一次 update 替换整个 members，实验永远恰好等于成员列表所说的样子，每次放量都是可显式审查的变更）：
```python
client.beta.endpoints.ab_experiments.update(
    id=experiment_id, endpoint_id=endpoint_id,
    update_mask="members",
    etag=experiment.etag,   # 队友的并发放量会被拒绝而非覆盖
    members=[
        {"deployment_id": control_dep, "percent": 80, "role": "AB_EXPERIMENT_MEMBER_ROLE_CONTROL"},
        {"deployment_id": variant_dep, "percent": 20, "role": "AB_EXPERIMENT_MEMBER_ROLE_VARIANT"},
    ],
)
```

**曝光阶梯**（多少流量给 B 组的经典权衡）：
| 配比 | 信号/风险 | 适用 |
|---|---|---|
| 95/5 | 信号慢（需要量/时间），风险最小 | 新模型第一次真实曝光 |
| 80/20 | 信号中等，风险可控 | 扛过 5% 阶段后要更有分量的读数 |
| 50/50 | 信号最快，一半用户 | 两个已知都不错选项之间的后期确认 |

最多 20 变体可跑**多路测试**（如 1 全精度 + 3 个量化变体 V1/V2/V3，总和 100 且恰一对照即可）。

**测量**：平台指标按部署拆分是"过滤器不是项目"（各组延迟/错误/吞吐直接可查）；产品指标是你的活——**连接键=部署 ID**：把响应元数据里的"由哪个部署服务"与评分/重试/任务完成一起记录；平台刻意不猜质量指标，只让归因简单。

**收尾两步**（变体赢）：①滚动发布蓝绿扶正（健康闸门/传播等待/回滚安全照常）②删除实验——所有实验路由消失，100% 走基础分配（已指向赢家）。**变体输**：直接删除，流量全回对照；变体部署缩容到零或删掉：
```bash
tg beta endpoints rm abx_abc123     # 删实验：100% 自动回基线分配
tg beta endpoints rm dep_variant123 # 或删变体部署：自动解开实验+分配
```

### 4. 边界情况问答（FAQ 精华）

| 问题 | 答案 |
|---|---|
| 变体实验中段劣化，爆炸半径？ | 只有它那一组——部署独立监控/独立扩缩容；修复=重发去掉病变体的成员列表，其用户在传播时间内回对照组（这也是 5% 起步的理由） |
| 实测占比真的等于配置？ | 有意义的量级上是的；小时间窗有采样噪声（1000 请求的 5% 是小样本）；偏差大且持续偏→查配置规则（多半违反了铁律 2/4） |
| A/B 与滚动发布能同端点共存？ | 能，组合顺序定义死：基础分配→A/B 实验→滚动发布；每端点仍限一个活跃滚动发布 |
| 分组对用户粘性？ | 采样键（prompt_cache_key/user）→ 同键同臂；研究在乎用户一致性（尤其多轮质量对比）就发稳定 user 字段 |
| 分流下自动扩缩容？ | 每成员按自己策略/份额扩缩：变体 5% 配 1-2 副本、对照 95% 配 2-8 副本是正常形态——分开盯各组副本数 |

### 5. 全生命周期实测（3 RPS 稳定流，逐请求归因）

| 阶段 | 配置 | 实测 | 请求数 |
|---|---|---|---|
| 1 | 95/5 | 95.3/4.7 | 1,330 |
| 2 | 80/20 | 79.2/20.8 | 1,348 |
| 3 | 50/50 | 50.2/49.8 | 1,348 |
| 删除后 | 100/0 | 100.0/0 | 360 |

**三个实操细节**：①每次放量真是一次调用；etag 1→2→3 递增，过期 etag 被拒绝不静默覆盖；②**传播快但非瞬时**——每次更新等约 75 秒再测量，路由层吸收变更的时间尺度与流量分配变更相同（30-60 秒）；③删除后 360 请求全落对照，**没有任何遗留分组逻辑需要收尾**。

### 6. 上手清单（官方四步）

前置：一个对照组部署在服务流量的端点 + 候选部署（创建好、READY、**不在流量分配里**）。
1. 95/5 创建 → 2. 跑到量够那天（5% 的全部意义=收集数据期间保持低曝光）→ 3. 一次 update 放量；结论定了用滚动发布扶正 → 4. 删除——没有其他要清理的。
文档：Dedicated Model Inference → A/B tests；控制台入口：端点 Traffic tests 标签页（A/B 与影子测试共用）。

## 三、归纳总结

| 维度 | 要点 |
|---|---|
| 一句话 | A/B 分流上移到端点层：实验是平台的独立生命周期对象（创建/放量/删除全是 API），客户端零感知、收尾零残留 |
| 核心设计 | 实验细分对照组份额：变体部署权重必须为零，流量完全归实验——污染源被配置规则消灭而非事后过滤 |
| 三条硬规则 | 变体权重零 / percent 恒定与副本数无关（测量仪器不许漂移）/ 总和 100 恰一对照 |
| 并发安全 | etag 乐观锁：队友并发放量被拒绝不覆盖——放量=重发完整成员列表，永远可显式审查 |
| 质量测量哲学 | 影子只验运营指标；质量（留存/完成率）必须真实曝光——平台只做归因（部署 ID 连接键），评判交给分析系统 |
| 生命周期美学 | 建议阶梯 95/5→80/20→50/50；扶正走蓝绿；删除即 100% 回基线——"实验结束"不需要勇气删代码 |
| 实测可信度 | 各阶段实测与配置偏差 <1 点；传播 30-60 秒（等 75 秒再测）；删除后零残留 |

## 四、趋势判断

1. **A/B 测试正从应用层下沉为推理平台的原语**：feature flag+hash-mod 自建会重演"自己搭负载均衡→云 LB"的历史——端点层分流、影子测试、蓝绿扶正会成为 LLM 平台标配三件套（Traffic tests 标签页已是先声）
2. **"基准分 vs 产品指标"的裁判权正在转移**：模型上线决策从基准分数转向留存/完成率——平台侧（Together）刻意只做归因不做评判，把质量定义留给产品团队——**评测的最后一公里长在业务系统里**
3. **etag 式可审查变更是基础设施 API 的礼貌**：放量=重发全量成员列表的设计让每次变更可 diff、可拒绝、可审计——"实验永远等于成员列表所说的样子"是对配置漂移的制度性防御
4. **采样键（prompt_cache_key/user）成为实验分组的通用基础设施**：粘性分组与 KV 缓存命中率共享同一个键——路由层与缓存层的耦合设计会越来越常见
5. **删除实验的"零收尾"是工程审美的新标准**：应用层自建 A/B 最大的隐性成本是"结束后的分支代码不敢删"——生命周期的干净退出与功能的干净上线同等重要
6. **多路测试（1 对照+20 变体）预示模型优选的工业化**：量化版本矩阵（全精度+V1/V2/V3）一次实验跑完——模型选择的搜索成本被平台吸收

## 六、拓展应用推荐

**① 概念迁移（无需 Together 账户即可用）**
- **"实验是独立生命周期对象"**：任何自建网关（nginx/自研路由）都可以把 A/B 从 if-else 升级为带 etag 的配置对象——删除即回收，杜绝僵尸分支
- **"变体权重必须为零"**：自建分流最常见的静默污染源就是候选还能分到正常流量——本文的配置铁律可直接抄进路由配置校验
- **测量仪器原则**：分流比例与容量解耦（固定 percent 不跟扩缩容漂移）——自建系统可在配置层强制

**② 若使用 Together AI 平台**
- 四步清单直接可用：95/5 创建→攒量→一次 update 放量→蓝绿扶正+删除
- 多路测试跑量化矩阵：1 全精度+3 量化变体一次实验出结论
- 研究多轮质量时务必发稳定 user 字段（粘性分组）

**③ 与本仓体系的组合**
- Hermes 的模型 fallback 链评估：给各档模型记录"部署 ID+质量信号"（用户反馈/任务完成），按连接键归因——低成本版的 A/B 思想
- skill-ab-testing 技能可补充本文的"放量阶梯+etag 并发纪律+零收尾"三原则

## 七、指南分析

**端点层 A/B 速查卡**

```
创建:  tg beta endpoints ab <model> --control $CTRL --percent 5
放量:  update(members=[80/20], etag=当前)   ← 一次调用=一次可审查变更
扶正:  滚动发布(蓝绿: 对照→变体) + 健康闸门
删除:  tg beta endpoints rm <实验ID>        ← 100% 自动回基线，零收尾

铁律:  变体权重必须为零 | percent 恒定与副本无关 | 总和100恰一对照
粘性:  prompt_cache_key / user 字段（多轮质量对比必发 user）
传播:  30-60 秒——放量后等 75 秒再测量
阶梯:  95/5(首曝) → 80/20(有分量读数) → 50/50(后期确认)
```

**三条可背的结论**
- 影子流量只验运营指标，质量必须真实曝光——被丢弃的响应教不会你用户怎么想
- 实验是测量仪器：测量期间分配不许漂移（percent 与副本数解耦）
- 生命周期的干净退出与干净上线同等重要——删除实验应当是"一次调用+零残留"

**何时重读本篇**：候选模型上线决策时（曝光阶梯）；自建分流系统设计时（五条铁律）；放量出并发事故复盘时（etag 段）；实验结束不敢删代码时（收尾两步）。
