一、内容整理

1.1 项目概述

nihaixia 是一个开源项目，将倪海厦（1954–2012）的中医思维、人纪系列教学内容、临床心法、天纪命理体系蒸馏为可激活的 Agent Skill。812 ⭐ / 152 Fork，使 AI 能以倪海厦的视角分析中医问题、解读症状、给出辨证思路与经方建议。

核心数据：
- 蒸馏规模：2,452 页讲义 / 3.5M 字符 → 3MB SKILL.md（35,285 行）
- 覆盖范围：129 条伤寒论 + 23 篇金匮要略 + 71 篇黄帝内经 + 345 种本草 + 849 个医案
- 默认分支：StableV2026.5.23
- 技术生态：OpenClaw · SkillHub
- 激活词：倪海厦 / 海厦视角 / 倪师 / 经方思维 / 倪海厦会怎么看

1.3 六经辨证 = 有限状态机

文章核心洞察：倪海厦的经方体系是规则驱动的，六经辨证本质是一套状态机：

太阳（表）→ 阳明（里热）→ 少阳（半表半里）
    ↓ 失治误治
太阴（脾寒）→ 少阴（心肾阳虚）→ 厥阴（阴阳逆乱）

每个状态有明确的输入条件（症状）、转移条件（误治/失治）和输出（方剂）。

1.5 经方规则示例

if-then 规则化表达：

if 脚冷至膝 && 手冷至肘 → 生附子
if 汗出恶风 && 卫气不固 → 炮附子
if 水肿 && 关节肿痛 → 生硫磺

1.6 倪氏六健康标准（系统监控指标）

  1. 一觉到天亮，无失眠
  2. 胃口正常，三餐有饱饿感
  3. 每天晨起大便
  4. 一天小便 5–7 次，淡清黄色
  5. 头面冷、手足温热（四季皆然）
  6. 晨起阳反应（男勃起/女乳房敏感）

类比系统监控的黄金信号（CPU、内存、IO 延迟）——用少量关键指标判断系统是否健康。

1.7 问题与局限

  • 3MB SKILL.md 过大：作为单文件 Prompt 非常大，不是所有模型都能完整加载
  • 蒸馏质量依赖原始 PDF 质量，部分 OCR 校正可能还有遗漏
  • 中医争议：倪海厦经方派观点激进，需要有自己的判断
  • 不能替代医生：项目声明写得很清楚，仅供学习

二、查询拓展

2.1 Agent Skill 与知识蒸馏

Agent Skill 是 LLM 时代的新型知识载体——不再是传统 RAG 的向量数据库检索，而是将领域知识结构化编码后直接注入 LLM 的 system prompt。nihaixia 项目将 2452 页 PDF 蒸馏成结构化的 SKILL.md，本质是知识压缩+结构重组。其 modules/ 模块化设计解决了一个核心矛盾：3MB 单文件太大塞不进上下文，按需加载子模块可控制 token 预算。

2.2 OpenClaw / SkillHub 生态

项目标注 "Built with OpenClaw · SkillHub"，topics 含 openclaw、openclaw-skill。OpenClaw 是一个 Agent Skill 发布和发现平台，类似 HuggingFace 之于模型，但定位是 Agent Skill 的"应用商店"。nihaixia 是这个生态中的优质垂直领域 Skill 样本。

2.3 六经辨证与有限状态机

六经辨证（太阳→阳明→少阳→太阴→少阴→厥阴）的传变规律与计算机科学中的有限状态机（FSM）高度对应：每个"经"是一个状态节点，"传变条件"（误汗/误下/失治）是状态转移边，"方剂"是状态输出的 action。这种类比让程序员可以用已有的系统设计直觉理解中医辨证逻辑。

2.4 OCR 校正与古籍数字化

神农本草经 339 页文稿需 OCR 校正 13 处生僻缺字（淬热/䀮䀮/䐜满/解㑊/胻/䏚），这些字在现代汉语中已极少使用，常规 OCR 引擎识别率低。项目中采用人工逐字校正，体现了古籍数字化的最后一公里仍需人工介入。

3.2 传统知识→AI Skill 的方法论

nihaixia 验证了一条可复制的方法论：

  • 结构清晰的知识 → 可以蒸馏为 AI 可用知识库
  • 规则驱动的体系（如经方 if-then）→ 天然适合 LLM 表达
  • 模块化拆分 → 解决大知识库的上下文窗口限制
  • 分类索引（cases/ 按病种分）→ 按需加载降低 token 消耗
  • 表达风格 DNA（expression_style.md）→ 让 AI 不仅知道内容，还能模仿表达风格

四、趋势判断

4.1 垂直领域 Agent Skill 将成为知识载体的新形态

依据：nihaixia 证明传统知识（中医）可以结构化蒸馏为 3MB Agent Skill。这种模式可复制到法律（法条+判例）、教育（教材+习题）、工程（规范+案例）等任何规则驱动的领域。OpenClaw/SkillHub 生态正在构建 Agent Skill 的分发渠道。

4.2 模块化 Skill 架构是解决上下文窗口限制的主流方案

依据：3MB 单文件 SKILL.md 太大无法全量加载，nihaixia 采用 SKILL.md（路由）+ modules/（按需加载）+ cases/（分类索引） 的三层架构。这与 RAG 的"检索后注入"思路不同——它是"结构化预拆分 + 按需调用"，更适合 Agent 主动决策的场景。

4.3 中医 AI 蒸馏是 NLP 工程的高质量参考实现

依据：2452 页 PDF → 3.5M 字符 → 35,285 行 Skill → 可调用 Agent，这条链路涵盖 OCR 校正、结构提取、去重清理、知识重组、风格建模等完整 NLP 工程。对于做知识库、RAG 系统的工程师来说，是一个端到端的参考实现。

4.4 "规则驱动"的传统知识最适合被 AI 蒸馏

依据：倪海厦经方体系的 if-then 规则（脚冷至膝→生附子）天然适合 LLM 表达。相比之下，温病派的"辨证论治"更依赖经验直觉，难以规则化。未来最适合被 AI 蒸馏的领域，将是那些有明确规则体系的传统知识。

五、关联分析

5.1 与 Hermes Agent Skill 体系的关联

nihaixia 的架构与 Hermes 的 Skill 体系高度一致：
- SKILL.md（主文件+路由规则）= Hermes 的 SKILL.md（YAML frontmatter + Markdown body）
- modules/（按需加载子模块）= Hermes 的 references/（skill_view 按需加载）
- cases/（分类索引）= Hermes 的 scripts/ / templates/ 分类目录
- 激活词机制 = Hermes 的 trigger 条件

可直接借鉴：nihaixia 的模块化拆分策略（大 Skill 拆成 9 个子模块按需加载）可用于解决 Hermes 中大 Skill 的上下文窗口问题。

5.2 与数字克隆项目（~/uclaw/project/ 相关 skill）的关联

nihaixia 的 expression_style.md（表达风格 DNA）与数字克隆项目的 voice-style-profiling（语音风格画像）和 emotional-decision-model（情感决策模型）在方法论上高度相似——都是从大量原始素材中提取"这个人怎么说话/怎么思考"的风格模型，然后注入 AI 使其模仿。

5.3 与知识蒸馏工程实践的关联

nihaixia 的蒸馏流水线（PDF→OCR→结构提取→模块化→Skill）是一套完整的知识工程实践。其 references/research/_distill_log.txt 记录了蒸馏过程，这种"蒸馏日志"的做法可用于任何大规模知识库建设项目的过程追溯。
