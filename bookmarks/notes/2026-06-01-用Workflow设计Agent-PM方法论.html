用 Workflow 设计 Agent：从场景到架构的 PM 方法论

来源：微信公众号 · 2026-04-09
标签：#Agent设计 #Workflow #Harness #PDCA #产品方法论 #ReAct #PlanExecute

核心论点

Agent 不是设计出来的宏大架构，而是从一个个具体问题的解法里生长出来的产品。

  • Pipeline / Workflow 是编排方式（多次调用怎么组织）
  • Agent 是应用形态（最终表现出什么能力）
  • Workflow 不是比 Agent 低一等，是实现 Agent 最自然的方式

LLM 本质是被动的：一次输入→一次输出。Agent 的"主动"行为全是工程层做的。LLM 在 Agent 中的角色 = 每次被调用时做一次判断。

一、Agent 两种经典策略

策略 模式 代表
ReAct 循环：思考→行动→观察→再思考 Claude Code、Cowork
Plan & Execute 先整体规划→再逐步执行 Manus

共同本质：都是对 LLM 多次调用的编排。用一个 workflow 完全可以搭出等价效果。

二、为什么用 Workflow

LLM 的不确定性问题

一次对话可以重试，但 Agent 内部多次 LLM 调用的不确定性会沿链路层层放大：
- 意图识别偏了 → 规划建立在错误前提
- 规划漏了一步 → 执行用正确方式做错误的事

没有 workflow = 黑盒。用户说"结果不对"，你不知道哪个环节出了问题。

Workflow 的三层价值

价值 含义
让你知道"里面有什么" 把"脏器"画出来，才能定位问题
给不确定性划边界 哪些节点是确定性逻辑，哪些交给 LLM，一目了然
让 PM 回到舒适区 不需要懂模型推理，只需要像以前一样梳理用户场景和流程

可控编排 ≠ 不让 LLM 做决策，而是给它划好决策的边界。

传统流程图 vs Agent Workflow

维度 传统流程图 Agent Workflow
设计对象 事情怎么流转 能力怎么组合
每个节点 做什么 做什么 + 谁来做、怎么做
PM 角色 画流程 能力分配（LLM vs 规则 vs 混合）

三、从场景到架构

三个场景，一个骨架

场景 复杂度 骨架
简单数据查询："上个月华东区销售额？" 低 意图→规划→执行→验证→输出
归因分析："签单多，怎么业绩还差了？" 中 同上，规划需推理指标关系
异常场景："新疆办事处业绩占比"（出现负值） 高 同上，验证捕获异常

五环节 = PDCA

Plan  = 意图识别 + 任务规划
Do    = 任务执行
Check = 结果验证
Act   = 总结输出（通过）或回到 Plan（不通过）

Agent 设计本质 = 把人解决问题的过程显性化、结构化。

四、三层价值定位

层 环节 价值 LLM迭代路线上？
智能层 意图识别 + 任务规划 决定 Agent 有多智能 ✅ 会被模型吃掉
稳定层 任务执行 + 结果验证 决定 Agent 有多稳 ❌ 你的护城河
体验层 总结输出 决定 Agent 有多像人 部分在

知行合一：规划是知，执行验证是行。执行和验证是别人抄不走的。

五、逐环节打磨要点

意图识别

  • 定义意图空间（能处理哪些类型的问题）
  • 同一意图不同说法→同一分类
  • 新增意图像插件一样加入

任务规划

  • LLM 介入最深的环节
  • 定义规划输出的结构化约束（指标是否存在、维度是否合法、时间范围是否合理）
  • 让规划结果可被下游校验

任务执行

  • 通常不涉及 LLM，是确定性的
  • 关键：执行顺序编排、超时控制、错误捕获、重试策略

结果验证（常被忽略但极重要）

  • 不能完全信任 LLM 的计划，也不能完全信任数据源
  • 定义明确验证规则：空值处理、负数标记、逻辑自洽检查
  • 越扎实→用户信任感越强

总结输出

  • 格式匹配任务类型（查询给数字，归因给结构化结论+数据支撑）
  • 异常主动标注并解释

六、Claude Code 案例验证

核心 = 一个极简的 while 循环（标准 ReAct）。复杂度全在 harness 层：

组件 设计
18+ 种工具 独立注册和调度，每个工具有自己的权限门控
上下文管理 窗口快满时多级压缩（清旧工具输出→摘要历史→持久化外部存储）
子 Agent 深度 不能再生子 Agent，防递归失控

Anthropic 官方定位：包裹在 LLM 外面的 Agentic harness。

设计哲学：保持循环简单，把投资放在 harness 上。

七、行业走过的弯路

2024 年纯 prompt Agent 大面积阵亡：

问题 原因
可控性≈0 同样输入，今天3步明天7步还失败
成本不可预测 简单任务触发十几轮调用
调试无从下手 根本没有"哪里"的概念

2025 年活下来的团队，无一例外地回过头补了 workflow 层。

模型决定 Agent 能做到多好，harness 决定最差不会差到哪里。

八、适用边界

什么时候用 Workflow

能提前画出流程图？ → 用 workflow（哪怕有分支有循环）

什么时候不用

任务开放度极高，连大环节都无法确定（开放式研究、未知代码库探索、创意发散）

渐进演进路线

固定 workflow（冷启动）
  → 可配置路由（场景多了，硬编码维护不住）
    → 部分节点开放工具选择（验证能力到位）
      → 全自主 Agent（目标+工具集，自规划路径）

升级原则：每放开一层自主性，要求对应环节的验证能力先到位。没有验证能力就放开自主性 = 拆掉刹车踩油门。

编排方式会变，但组件质量会沉淀。 Workflow 不是通往全自主 Agent 路上的妥协，而是必经的建设阶段。

思考

这篇文章是对 Agent 设计方法论最清晰的产品视角论述，与此前多篇笔记形成完整知识链：

上一篇 本文的呼应
Eval Loop 验证环节 = Check = content-judge 评分
知识图谱+LLM Harness 层的上下文管理 ≈ 图谱的语义导航
本体论/UModel 意图空间定义 = 本体论的"消除歧义"
Harness vs Protocol Workflow = Harness 路线的最佳实践

对 PM 角色的定义精准：不是懂模型，而是懂得怎么把模型的能力放进合理的结构里。这同样适用于 Agent Builder——先用 workflow 把下限守住，再逐环节打磨质量让上限提升。
