一、内容整理

0. 一句话定位

LangGraph 是 LangChain 团队开发的基于图的 Agent 编排框架——把 Agent 工作流建模为状态机/图，用显式的 State/Node/Edge 取代隐式的 prompt 链，换取可控、可恢复、可观测的生产级能力。2025-10 发布 v1.0（API 稳定承诺），2026-02 发布 2.0（guardrail nodes/内建 rate limiting/强化 checkpoint），月下载量 3,870 万次（2026-04 PyPI）——工程采用型工具的典型：企业大量用但不按 star（star 仅 25-30K）。

1. 核心概念体系

五大原语：

原语 定义 类比
State 节点间流动的数据结构（TypedDict/Pydantic） 数据库一行
Node 处理状态的函数（普通函数或 LLM 调用） 微服务
Edge 节点间的固定转换 同步调用
Conditional Edge 基于状态的条件分支 if/switch
Checkpoint 每个 super-step 后持久化的 StateSnapshot git commit

状态管理精髓：State 用 Annotated[List[str], operator.add] 声明合并策略——多个节点（含并行节点）写同一字段时按 reducer 合而非覆盖。这是 LangGraph 与朴素函数链的本质差异：状态是共享黑板（Blackboard），节点是读写者。

图的执行语义：
- Pregel 风格 super-step：每个 step 内所有就绪节点执行，barrier 同步后进入下一步
- 图是显式、可检视、可测试的：能可视化、debugger 单步、从任意 checkpoint 回放

2. 双 API：Graph API 与 Functional API

2025 年起 LangGraph 提供两套等价表达：

Graph API（StateGraph） Functional API（@entrypoint/@task）
范式 声明式：先构图再执行 命令式：普通函数+循环+条件
上手 需学图概念 现有代码零重构接入
checkpoint 粒度 每节点执行后（并行组各一份） 每 entrypoint 执行后（task 更新现有 checkpoint 不新建）
time-travel 更好支持（细粒度 fork） 较粗
适用 需要精确状态控制的复杂工作流 渐进式给存量应用加 HITL/记忆/流式 
# Graph API
builder = StateGraph(AgentState)
builder.add_node("research", research_node)
builder.add_conditional_edges("decide", route_fn, {...})
graph = builder.compile(checkpointer=MemorySaver())

# Functional API
from langgraph.func import entrypoint, task
@task
async def search(q): ...
@entrypoint(checkpointer=saver)
async def workflow(inputs):
    results = [await search(q) for q in inputs["queries"]]

3. 生产四支柱

① Checkpoint 持久化（最受误解）
- 开发用 MemorySaver，生产必须换 AsyncPostgresSaver/AsyncRedisSaver——"上 production 前第一件事"（社区最高频事故：server 重启 agent state 归零）
- thread_id 是主键：无它不能保存/恢复/续跑
- checkpoint ≠ durable execution：checkpoint 保存数据不保存执行——进程死了，需要外部编排层检测失败、决定重入点、重启图（Temporal 插件正是补这个：支持双 API+interrupts+Send+continue-as-new，Python SDK 1.27+）
- 成本研究（2026 Crab 研究）：75%+ 的 agent turn 不产生恢复相关状态——全量 checkpoint 大部分是浪费，语义感知方法可把恢复正确率从 8% 提到 100% 同时削减开销

② Send API（动态并行）

from langgraph.types import Send
def spawn(state):
    return [Send("researcher", {"query": q}) for q in state["queries"]]

map-reduce 式并行：节点数在运行时由状态决定——静态图结构+动态执行实例。并行 subgraph 同时跑多个 agent。

③ HITL 人机交互（interrupt 模式）

graph = builder.compile(interrupt_before=["human_review"])
# 中断→人审→恢复（同一 thread_id 续跑）
graph.invoke(None, config={"configurable": {"thread_id": "s1"}})

无困境的人机协作：审批/修正/分支实验都建立在 checkpoint fork 上。

④ 可观测性
- LangSmith 集成：langsmith.tracing = True 自动记录全部运行
- LangGraph Platform：部署为 API 服务（fastapi 包一层 CompiledGraph 即可起步）
- 图本身可检视：可视化+单步+任意 checkpoint 回放——"显式优于隐式"的可调试性红利

4. Prebuilt 与高层封装

封装 用途 本质
create_react_agent 标准 ReAct 工具调用 agent（LLM 调用+工具执行循环+条件路由全自动） 图机制上的语法糖
create_supervisor（langgraph-supervisor 包） 快速搭 Supervisor-Worker 多 agent 高层 API
create_agent（langchain v1.0） LangChain 新入口，底层就是 LangGraph 循环 与 create_react_agent 同感

实践法则：标准工具 agent 直接 create_react_agent；需要并行节点/supervisor-worker/自定义重试/复杂分支时迁手动 StateGraph——底层原语完全一致。Worker 可以是另一个 Supervisor（层级团队架构，适合大型项目）。

5. 生产应用模式（真实案例）

采用方：AppFolio（Realm-X）、Exa、NVIDIA 公开采用为生产 agent 基础设施；Uber、LinkedIn、Klarna 有公开案例。

典型生产形态（与《企业Agent技术选型》笔记的 DAG 骨架一致）：

触发（webhook/cron/队列）
→ 确定性节点（分类路由/数据收集/统计验证，execute_code）
→ Agent 节点（create_react_agent 沙箱执行探索性任务）
→ interrupt_before 人工门（高风险操作）
→ 写回节点（确定性）+ 全程 checkpoint + LangSmith trace

2.0 新增生产能力：guardrail nodes（护栏成为一等节点类型）、内建 rate limiting、强化 checkpoint persistence。

常见生产事故清单（shareuhack 总结）：MemorySaver 忘换（state 归零）；无终止循环烧钱（20 分钟 $200）；无 rate limit 被上游限流雪崩；checkpoint 写入后无清理（存储膨胀）。

7. 生态位与选型（2026）

Alice Labs 框架排名（18+ 生产部署验证）：#1 LangGraph（复杂状态工作流首选）→ #2 Claude Agent SDK（Anthropic 原生）→ #3 CrewAI（角色团队）→ #4 AutoGen/AG2（研究对话）→ #5 Semantic Kernel（.NET）→ #6 LlamaIndex（RAG）→ #7 Pydantic AI（类型安全）。

选型决策（本仓 skill 版+研究补充）：

需要复杂状态工作流+显式控制（分支/重试/HITL/checkpoint）→ LangGraph
  ├─ 存量代码渐进接入 → Functional API
  ├─ 全新精确控制 → Graph API
  └─ 月级长任务/跨进程可靠性 → + Temporal 插件
标准工具调用 agent，不想构图 → create_react_agent（依然是 LangGraph）
角色化团队快速原型 → CrewAI

LangGraph vs LangChain（2026）：LangChain=组件库（模型/工具/检索抽象），LangGraph=编排运行时——v1.0 后官方定位明确：create_agent（LC）底层跑在 LangGraph 上，两者是上下游而非竞争。

二、查询拓展

  1. Pregel/super-step 执行语义的深度——与 Beam/Materialize 类流处理的同构，barrier 同步的代价
  2. Send API 的并行 subgraph 状态合并——reducer 冲突（两个 Send 写同字段）的解决语义
  3. Temporal 插件的 continue-as-new——超长图（万级 step）的分段策略
  4. Crab 语义感知 checkpoint 的实现——如何判定"恢复相关状态"（75% 浪费的避免）
  5. guardrail nodes（2.0）与确定性护栏 skill 模式的对照——框架内置 vs 自建的边界
  6. LangGraph Platform 的部署计费模型 vs 自托管（fastapi+Postgres saver）的成本曲线
  7. 与 OpenAI Agents SDK / Claude Agent SDK 的互操作——A2A 协议下跨框架 worker 互认

三、归纳总结

维度 要点
一句话 把 Agent 建模为显式状态图：State（黑板）+Node+Edge+Checkpoint，换可控/可恢复/可观测的生产能力
双 API Graph=声明式精确控制（time-travel 细）；Functional=命令式零重构接入（checkpoint 粗）——底层原语一致
生产四支柱 checkpoint 持久化（Postgres/Redis）/Send 动态并行/interrupt HITL/LangSmith 观测
关键澄清 checkpoint 保存数据不保存执行——durable execution 需 Temporal 类编排层补
Prebuilt 路径 create_react_agent 起步→需要并行/supervisor/自定义重试时迁 StateGraph
生态位 2026 框架排名第一；月下载 3,870 万但 star 仅 25-30K（工程采用型工具特征）
版本 1.0（2025-10）API 稳定；2.0（2026-02）guardrail/rate-limit/持久化强化

四、趋势判断

  1. LangGraph 已成为编排层的"事实标准"候选：下载量与生产案例（NVIDIA/Uber/LinkedIn/Klarna）说明企业用脚投票——编排框架的竞争从功能转向可靠性工程
  2. checkpoint 语义正在专业化：从"全量快照"到"语义感知"（75% 浪费可避免）——持久化开销会成为下一个优化热点，Temporal 类 durable execution 集成会普及
  3. 双 API 并存长期化：声明式（新项目精确控制）与命令式（存量渐进接入）服务不同人群——框架成熟度标志就是能同时服务两者
  4. prebuilt 与手构的边界在上移：create_react_agent/create_supervisor 覆盖越来越多标准场景，手构 StateGraph 的场景收窄到真正定制化的控制流
  5. guardrail 成为框架一等公民：2.0 的 guardrail nodes 印证确定性护栏从外部库向框架内置迁移——自建护栏的价值转向框架未覆盖的领域逻辑
  6. 框架间互操作是下一战场：A2A/MCP 标准化后，LangGraph 图中的节点可以是任何框架的 agent——编排层胜出者定义协议而非绑定实现

七、指南分析

概念地图（一张图记住 LangGraph）

State(黑板+reducer) ── Node(函数) ── Edge/ConditionalEdge(路由)
        │                                  │
        ▼                                  ▼
   Checkpoint(每super-step快照)      Send(动态并行实例)
        │                                  │
        ▼                                  ▼
   thread_id(主键/fork/time-travel)   HITL(interrupt_before)
                                           │
                                           ▼
                              观测(LangSmith) + 护栏(2.0 guardrail)

开发五步法（skill 版照录）：定义 State（含 Annotated reducer）→写节点函数→构图（entry/edges/conditional）→compile(checkpointer)→invoke/stream。生产再加第六步：换持久化 saver + 挂 trace。

生产上线检查清单
- [ ] MemorySaver 已替换为 Postgres/Redis saver
- [ ] 每个含 LLM 的节点有终止条件（max_iterations/recursion_limit）
- [ ] 高风险节点 interrupt_before 人工门
- [ ] rate limiting 已配置（2.0 内建或自建）
- [ ] checkpoint 有清理策略（TTL/数量上限）
- [ ] LangSmith trace 已开，错误告警已接
- [ ] 长任务的 durable 方案已评估（Temporal or 自建监督进程）

避坑
- 别把 LangGraph 当 LangChain 的替代——是上下游（LC 组件喂给 LG 编排）
- 别信"有 checkpoint 就 durable"——进程死了需要编排层重启
- 别在 Functional API 里期待细粒度 time-travel——那是 Graph API 的能力
- 别无脑全量 checkpoint——75% turn 无恢复价值，存储和延迟都浪费
- 别用 star 数判成熟度——看月下载 3,870 万和企业案例
