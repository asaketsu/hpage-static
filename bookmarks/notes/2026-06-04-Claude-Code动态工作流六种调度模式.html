核心观点

Claude Code 动态工作流：让 AI 针对当前任务实时生成调度脚本（JavaScript），用独立子 Agent 各占干净上下文窗口，由确定性脚本编排执行。解决了单 Agent 三大退化模式。

单 Agent 三大退化模式

模式 表现 根因
偷懒 50 个检查项查到 20 个就宣布完成 长上下文里的行为退化（非幻觉）
自我偏爱 评判自己产出时倾向给好评 单上下文同时承担生成和验证
目标漂移 上下文压缩有损，边缘条件逐步丢失 压缩次数越多，原始需求偏离越大

根因不是模型能力，是单上下文窗口同时承担规划和执行的架构局限。

动态 vs 静态工作流

维度 静态（手动写脚本） 动态（AI 自生成）
编排方式 预先写死调度逻辑 Claude 看任务后实时生成
适用场景 已知拆分方式的任务 "大概知道做什么，不确定最优拆法"
可控性 更高 略低但更灵活
本质 通用模板 针对当前任务量身定制

Opus 4.8 的能力已足够自己写出高质量 Harness。

六种调度模式

模式 原理 适用场景
分类路由 分类 Agent 判断类型 → 分发给不同处理 Agent 任务分流、输出格式选择
扇出合并 拆成独立小步 → 各自 Agent → 合并汇总 大规模并行修改（最常用）
对抗验证 每个生成 Agent 配一个独立验证 Agent 专挑毛病 直接解决"自我偏爱"
生成过滤 先大量生成 → 按标准筛选去重 → 只留通过的 创意发散后收敛
锦标赛 N 个 Agent 不同策略做同一事 → 两两比较淘汰 排序、选最优方案
循环到完成 不设固定轮次，跑到满足停止条件 根因分析、Bug 复现

可组合：先扇出 → 分支内部对抗验证 → 合并时锦标赛选最优。

六大实战场景

1. 大规模迁移和重构

Bun 从 Zig 重写成 Rust 的模式：
- 拆成独立单元（调用点/失败测试/模块）
- 每单元一个子 Agent 在独立 worktree 里修
- 另一个 Agent 做对抗性 Review
- 通过后再合并

价值最大：天然避免交叉污染，不丢上下文。

2. 深度验证

文章中的事实性声明：
- 提取所有声明 → 每个声明派一个子 Agent 核实
- 可再加一层：验证信息源本身是否可靠

3. 排序

对 1000 条工单按严重程度排序：
- 锦标赛模式两两比较
- 比较判断比绝对评分可靠得多
- 每次比较是独立 Agent

4. 规则遵守

CLAUDE.md 规则跑着跑着被忘：
- 一条规则一个验证 Agent，用怀疑论者视角检查
- 反向：扫 session 日志 → 找反复出现的纠正 → 聚类验证 → 提炼新规则

5. 根因分析

单 Agent 容易认准一个假设一路追到底：
- 从日志/文件变更/数据状态分别生成独立假设
- 每个假设面对验证者和反驳者
- 适用于代码调试、销售分析、数据管道故障等

6. 大规模分流

处理不完的支持队列：
- 分类 + 去重 + 自动修复/升级
- 隔离区模式：读不可信内容的 Agent 禁止执行高权限操作，读写分离防 prompt injection

什么时候不需要工作流

判断标准：你能一句话描述清楚 + 自己能快速验证 → 不需要。

需要的特征：
1. 任务可拆成独立并行单元
2. 验证成本高到不想自己检查

动态工作流 token 消耗显著更多，适合复杂、高价值任务。

用法速查

操作 方法
开启 Prompt 里要求创建工作流，或触发词 ultracode
描述模式 直接用六种模式名称
定期执行 搭配 /loop + /goal 硬性完成条件
限制消耗 Prompt 加 "用 10k token"
保存脚本 运行时按 s，存到 ~/.claude/workflows
团队共享 通过 Skill 分发

💡 对我们的价值

✅ 直接关联

  • Hermes Agent 架构：我们已有 delegate_task 子 Agent 编排，但调度逻辑是静态的
  • Harness Architecture Skill：已沉淀六层 Harness 设计模式
  • 代码审查：critical-code-reviewer Skill 的对抗验证思路与此一致

⚠️ 可改进

  • 我们的 delegate_task 目前不支持子 Agent 之间通信（max_spawn_depth=1），动态工作流需要更灵活的编排
  • 锦标赛模式和循环到完成模式在我们当前架构中无法直接实现
  • 规则提炼场景（扫 session 日志 → 提炼新规则）可做成自动化 Cron Job

🔥 行动项

  1. 评估 Hermes 的 delegate_task 是否可扩展支持"扇出合并 + 对抗验证"组合模式
  2. 将"扫 session 日志提炼规则"做成 cron job（每月一次，自动提炼反复纠正模式）
  3. 在代码审查 Skill 中引入"怀疑论者视角"验证 Agent 模式

趋势判断

Harness 可能像 prompt engineering 一样是大模型发展的中间状态。模型不够强时需要精巧调度逻辑和多 Agent 制衡；模型足够强后，这些逻辑会被内化。今天还在想怎么编排子 Agent，下一代模型可能不需要外部编排。
