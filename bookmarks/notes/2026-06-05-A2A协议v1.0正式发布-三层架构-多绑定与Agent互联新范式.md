## 一、协议背景与定位

### 1.1 核心问题

当前 AI Agent 生态的最大瓶颈不是单个 Agent 的能力，而是 **Agent 之间的互操作性**。不同框架（LangGraph、Google ADK、BeeAI、CrewAI）构建的 Agent 各自为政，无法直接协作。

MCP 解决了 Agent → Tool 的标准化连接，而 **A2A 解决 Agent → Agent 的标准化通信**。两者互补而非竞争。

### 1.2 A2A vs MCP 定位对比

| 维度 | MCP | A2A |
|------|-----|-----|
| 连接模式 | Agent → Tool（工具调用） | Agent → Agent（对等协作） |
| 内部状态 | Tool 需要暴露接口 | Agent 保持不透明（不共享内部状态/记忆/工具） |
| 通信协议 | JSON-RPC over stdio/SSE | JSON-RPC / gRPC / HTTP+REST |
| 发现机制 | 无（需手动配置） | Agent Card（自动发现） |
| 任务管理 | 无（无状态工具调用） | Task Lifecycle（有状态任务管理） |
| 治理 | Anthropic 主导 | Linux Foundation（Google 贡献） |

### 1.3 发展历程

- 2025-04：Google 发布 A2A 协议草案 v0.1.0
- 2025-06：v0.2.6 发布，增加 gRPC 绑定
- 2025-09：v0.3.0，增加 Push Notification 和 List Tasks
- 2026-XX：**v1.0.0 正式发布**，三层架构定型，进入 Linux Foundation

## 二、三层架构设计

A2A v1.0 最大的架构创新是 **三层解耦设计**：

```
Layer 1: Canonical Data Model (Protocol Buffer)
    Task → Message → Part → Artifact → Extension

Layer 2: Abstract Operations (绑定无关)
    SendMessage → SendStreamingMessage → GetTask → ListTasks → CancelTask → SubscribeToTask

Layer 3: Protocol Bindings (具体映射)
    JSON-RPC 2.0 | gRPC | HTTP+JSON/REST | 自定义绑定
```

### 2.1 Layer 1：规范数据模型

所有核心对象以 **Protocol Buffer (.proto)** 为单一权威定义源。SDK、JSON Schema 等衍生品必须从 proto 生成，不可手动编辑。

核心对象：

- **Task**：基本工作单元，有唯一 ID 和状态生命周期
- **Message**：Client/Agent 之间的通信轮次，包含 `role`（user/agent）和多个 `Part`
- **Part**：最小内容单元（文本/文件引用/结构化数据）
- **Artifact**：Agent 生成的输出（文档/图片/数据），由 Part 组成
- **AgentCard**：Agent 的 JSON 元数据（身份、能力、连接端点、认证要求）
- **Extension**：扩展机制，超出核心规范的附加功能

### 2.2 Layer 2：抽象操作（11 个）

| 操作 | 说明 | 阻塞模式 |
|------|------|---------|
| SendMessage | 主要交互入口 | 默认阻塞，可设 `return_immediately` |
| SendStreamingMessage | 流式实时更新 | 始终流式 |
| GetTask | 查询任务状态 | 阻塞 |
| ListTasks | 分页列出任务（支持过滤） | 阻塞 |
| CancelTask | 取消进行中任务 | 幂等 |
| SubscribeToTask | 订阅已有任务的流式更新 | 流式 |
| CreatePushNotificationConfig | 创建 Webhook 推送 | 阻塞 |
| GetPushNotificationConfig | 获取推送配置 | 阻塞 |
| ListPushNotificationConfigs | 列出所有推送配置 | 阻塞 |
| DeletePushNotificationConfig | 删除推送配置 | 幂等 |
| GetExtendedAgentCard | 认证后获取详细 Agent Card | 阻塞 |

**关键设计决策**：
- `SendMessage` 可以返回 `Task`（有状态）或直接返回 `Message`（简单交互无需任务跟踪）
- 流式操作支持两种模式：Message-only stream（直接响应）和 Task lifecycle stream（带状态更新）
- 游标分页（cursor-based）替代偏移分页，避免深分页性能问题

### 2.3 Layer 3：多协议绑定

**JSON-RPC 2.0 over HTTP(S)**（默认绑定）：
- 所有操作映射为 JSON-RPC 方法
- 流式通过 Server-Sent Events (SSE) 实现
- 与 MCP 的传输层一致

**gRPC**：
- Protocol Buffer 原生映射
- 高性能场景首选
- 适合 Agent 集群内部通信

**HTTP+JSON/REST**：
- 传统 REST API 风格
- 降低非 Agent 系统的集成门槛
- 适合监控系统、管理面板等

**Agent Card 声明支持**：
```json
{
  "supportedInterfaces": [
    {"url": "https://agent.example.com/a2a/v1", "protocolBinding": "JSONRPC", "protocolVersion": "1.0"},
    {"url": "https://agent.example.com/a2a/grpc", "protocolBinding": "GRPC", "protocolVersion": "1.0"},
    {"url": "https://agent.example.com/a2a/json", "protocolBinding": "HTTP+JSON", "protocolVersion": "1.0"}
  ]
}
```
客户端按优先级选择第一个支持的绑定。

## 三、Task 生命周期

```
SUBMITTED → WORKING → INPUT_REQUIRED → COMPLETED
                    → AUTH_REQUIRED
                    → FAILED
                    → CANCELED
                    → REJECTED
```

- **SUBMITTED**：任务已提交，等待处理
- **WORKING**：Agent 正在处理
- **INPUT_REQUIRED**：需要用户输入（Human-in-the-loop）
- **AUTH_REQUIRED**：需要认证授权
- **COMPLETED/FAILED/CANCELED/REJECTED**：终态

**设计哲学**：Async First。原生支持长任务和 Human-in-the-loop。

## 四、Agent 发现机制

### 4.1 Agent Card

每个 A2A Server 必须发布 Agent Card（JSON 元数据），包含：

- **身份信息**：name、description、provider、version
- **能力声明**：streaming、pushNotifications、extendedAgentCard
- **技能列表**：skills 数组，每个 skill 有 id、name、description、tags、examples
- **认证方案**：securitySchemes（支持 OpenID Connect 等）
- **默认输入/输出模式**：如 application/json、text/plain
- **协议绑定**：supportedInterfaces

### 4.2 发现途径

1. **Well-Known URI**：`https://{server_domain}/.well-known/agent-card.json`
2. **注册中心/目录**：查询策展的 Agent 目录
3. **直接配置**：预配置的 Agent Card URL

### 4.3 Agent Card 签名

支持对 Agent Card 进行数字签名验证，防止中间人篡改。

## 五、安全设计

### 5.1 数据访问与授权范围

- 每个 A2A 操作请求 **必须** 实施授权检查
- 结果 **必须** 限定在调用者的授权边界内
- 即使未指定 `contextId` 等过滤参数，也必须限制结果范围
- 授权模型可基于：用户身份（User-based）、组织角色（RBAC）、自定义

### 5.2 In-Task 授权

- 凭据 **应该** 通过安全通道（HTTPS）带外传输
- 带内凭据交换需要：绑定到原始 Agent + 加密保护
- 防止凭据在 Agent 链中传播泄露

### 5.3 Extended Agent Card 访问控制

- 公开 Agent Card 不含敏感信息
- 认证后通过 `GetExtendedAgentCard` 获取完整版本
- 不同认证级别可能返回不同细节
- 客户端 **应该** 缓存并替换公开 Card

## 九、对 Hermes 系统的影响

### 9.1 与 MCP 的关系

Hermes 当前大量使用 MCP（智谱 MCP、记忆图谱等）。A2A 不是替代 MCP，而是补充：

- **MCP**：Agent → Tool（Hermes 调用 lark-cli、搜索工具等）
- **A2A**：Agent → Agent（Hermes jbot/ubot/abot 三机之间的协作）

### 9.2 三机协作升级路径

当前 Hermes 三机使用 NFS4 共享文件系统 + JSONL 追加式经验池。可以评估引入 A2A：

1. **Phase 1**：将每个 Hermes 实例暴露为 A2A Server，发布 Agent Card
2. **Phase 2**：用 A2A 的 Task Lifecycle 替代当前的 JSONL 经验交换
3. **Phase 3**：引入 Agent Card 签名验证，增强三机间的信任模型

### 9.3 与 A2A 互补的协议生态

```
MCP (Agent → Tool)      ← 当前已集成
A2A (Agent → Agent)     ← 本次学习重点
ACP (Agent Communication Protocol)  ← Anthropic 推出
UCP (Universal Communication Protocol) ← 统一协议尝试
```

### 9.4 具体行动建议

1. **评估 a2a-sdk Python 集成**：`pip install a2a-sdk`，测试 Hermes 作为 A2A Server
2. **设计 Hermes Agent Card**：定义 jbot/ubot/abot 各自的能力声明
3. **与 exchange-protocol Skill 对比**：评估 A2A 的 Task Lifecycle 是否优于当前 JSONL 方案
4. **安全增强**：Agent Card 签名验证 + 授权范围控制，与 MCP 安全互补
