## 核心结论

> **QM 开始把 Agent 当作组织成员来管理。**

未来一家公司里每个员工都有 Agent。YC 开源的 QM 不是"同时运行多少 Agent"，而是让 Agent 拥有清楚的工作空间、可复用的做事方法、受控制的行动权限、能恢复的任务状态、以及出了问题找得到人的责任链。

---

## 一、为什么一个聊天框无法承载整个组织？

### 个人 Agent → 公司 Agent 的复杂度跃迁

| 个人 Agent | 公司 Agent |
|-----------|-----------|
| 权限属于这个人 | 老板私聊/财务频道/项目群/公共讨论区看到的信息不能一样 |
| 结果交回这个人 | 结果投递到哪里？属于谁？ |
| 个人 Skill | 不一定适合全团队，需要治理 |
| 复制 Prompt | 维护十个被不同人改过的版本极难 |
| 无需批准链 | 付款/删除数据/发消息需要清楚的批准与责任链 |

### 公司 Agent 必须回答的六个问题

1. 任务属于谁？
2. 可以读取哪些资料？
3. 可以使用谁的凭据？
4. 结果投递到哪里？
5. 失败后谁来接管？
6. 能不能还原完整执行过程？

## 二、QM 的四大核心设计

### ① Scope（范围）= Agent 的工作空间

| Scope 层级 | 说明 |
|-----------|------|
| personal | 个人私聊中的偏好，不自动成为全公司规则 |
| channel | 频道中的文件和记忆，不向其他团队开放 |
| team | 团队级 |
| org | 全组织（需管理员门控） |
| group | 群组 |

每个范围拥有：自己的记忆、文件、凭据视图、权限、定时任务、Web 应用和持久沙箱。

> Scope 减少了**上下文污染**——全公司共享无边界的长期记忆，Agent 会混淆个人偏好、项目规则和过期信息。

### ② Skill = 组织资产（非个人技巧）

| 维度 | 说明 |
|------|------|
| **归属** | Skill 归属于具体 Scope，通过授权分享给其他人/团队 |
| **提升到 org** | 需要管理员门控 |
| **治理问题** | 谁负责维护？谁可以调用？适用范围？更新如何同步？出错能否回退？ |

> 复制 Prompt 很容易。维护十个被不同人改过的版本很难。**Skill 进入组织后才从个人技巧变成组织能力。**

### ③ 后台运行 = 持续存在的工作

| 同步 Agent（聊天框） | 后台 Agent（组织任务） |
|---------------------|---------------------|
| 人问→等回复→检查 | 每天生成简报/追踪状态/分类邮件/监控CI/触发流程 |
| 无状态问题 | 任务是否重复？失败从哪恢复？新旧冲突？结果交给谁？人接管后能否继续？ |

QM 仓库包含：cron、任务队列、调度器、运行记录、结果投递和记忆服务。

> Agent 不再是一段对话，而是一项**持续存在的工作**。

### ④ 权限 = 三种安全姿态

| 模式 | 行为 |
|------|------|
| **Strict** | 大多数工具调用需人工批准 |
| **Auto** | 筛查带来源标记的外部数据和工具结果 |
| **Dangerous** | 放宽暂停和内容筛查，但命令策略和硬拒绝仍存在 |

> 模型和沙箱视为**不可信边界**。Agent 可以提出动作，但身份、范围、授权、结果投递和确定性副作用门由中央 Core 管理。

> **风险容忍度必须成为系统配置，不能隐藏在 Prompt 里。**

---

## 三、QM 的架构定位

- QM 同时接入 **Pi、OpenCode、Codex、Claude Code** 等不同 Harness
- 模型和执行框架可替换
- 身份、范围、权限、记忆、调度和审计留在共同的 **Core** 里
- YC 明确表示 QM 仍处于早期、存在 bug
- Scope 隔离是**设计目标**，不是数据绝不泄漏的承诺

> QM 更适合作为一个**架构样本**，而非已加固的公开多租户服务。

## 四、设计公司 Agent 前的五个必答问题

| 问题 | 要点 |
|------|------|
| **1. 最小协作单位是什么？** | 个人/频道/项目/团队/组织？数据如何跨范围流动？ |
| **2. 每项能力属于谁？** | 记忆、文件、Skill、连接器和凭据由谁创建、维护、分享？ |
| **3. 后台任务如何持续运行？** | 有没有调度、幂等、超时、重试、恢复和结果投递？ |
| **4. 哪些动作必须等待人类？** | 审批按单次/会话/项目/组织规则生效？ |
| **5. 出问题时能否还原过程？** | 请求者、上下文来源、工具调用、批准动作、文件变化、投递是否全记录？ |

> 这些问题没有回答清楚之前，增加 Agent 只会**扩大系统中的不确定性**。

## 五、关键洞察

| 洞察 | 说明 |
|------|------|
| **Agent 产品的竞争正在进入组织层** | 模型能力和工具数量仍重要，但系统还要让人安全共享能力 |
| **知识需要归属** | 来自哪里，适用于谁，能不能在当前任务中使用 |
| **上下文越多 ≠ 判断越好** | 全公司共享无边界的记忆 = 混淆和污染 |
| **风险容忍度 = 系统配置** | 不能隐藏在 Prompt 里，必须可配置、可审计 |
| **Agent ≠ 对话** | Agent 是一项持续存在的工作，需要状态恢复和责任链 |
