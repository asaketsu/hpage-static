一句话总纲

泊舟的 AI 交易员工作流方法论，真正值得学习的不是量化策略本身，而是「Agent 安全边界卡得死」+「每一步都有文件日志和可见结果」+「dry-run 作为回测与实盘之间的必设缓冲层」——这三个结构性做法正好是本机铁律体系当前最缺失的层。回测脚本里的 shift(1) 未来函数防漏、凭证不进 Agent 对话、demo profile 常驻校验、停止条件显式清单——四条可立即进 skill 的安全补丁。

一、内容详细整理

1.1 五段工作流（完整可执行链）

① 行情读取（已收盘 K 线，本地保存 JSON）
② 回测执行（MA5/MA20+RSI14+ATR14，backtest.py + reports/*.json）
③ dry-run 观察（打印计划方向/数量/价格/停止原因，不调用任何写入）
④ 模拟订单准备（展示参数，等人工确认才执行）
⑤ 人工确认 + 执行 + 查询状态 + 落日志

每步的产物：①行情文件 ②backtest.py + reports/backtest-report.json + backtest-analysis.md ③dry-run 日志 ④订单预览 ⑤logs/order-result.json

1.2 策略核心（BTC-USDT 1H 现货）

指标 作用
MA5/MA20 短期/中期趋势；MA5 穿 MA20 生成信号
RSI14 过滤过热（只接受 50-70 入场）
ATR14 估计波动；入场价 −2×ATR 作保护价位
仓位 权益小比例，不使用杠杆

1.3 安全边界清单（12 条禁止动作 + 4 项验收）

禁止执行：

  1. 只允许读取本地数据和执行 Python 回测
  2. 不调用账户/下单/改单/撤单/提币/转账等任何交易写入工具
  3. 不使用未收盘 K 线
  4. 不省略手续费/点差/滑点/仓位上限
  5. 不把回测结果描述成未来收益预测
  6. 不要求用户手动创建目录/写代码/跑 Python

验收结果必须包含：

  1. backtest.py 是否生成 + 核心信号逻辑含 shift(1)（防未来函数）
  2. reports 两份产物是否生成
  3. 数据区间/有效样本/交易次数/总费用
  4. 最大回撤/波动率/夏普值
  5. 样本不足时明确标记「不足以判断」

1.4 停止条件（11 条）

profile 不是 demo
行情延迟超限
K 线有缺口或最后一根未收盘
指标计算为空
下单数量不符合最小数量/精度
余额和本地记录不一致
连续三次调用失败
同一信号重复准备订单
日志无法写入
dry-run 和回测参数不一致
终端关闭/日志缺失/账户状态无法确认

1.5 凭证安全（两种 Key 严格隔离）

Key 类型 用途 持有者
DeepSeek API Key Pi 调模型 Pi 会话
OKX API Key/Secret/Passphrase 本地 CLI 访问模拟盘 本机 okx config init，不进 Pi 对话

铁律：Secret/Passphrase 永不进入 Agent 对话/代码文件/日志；用专门子账号，关闭提币权限，开 IP 白名单。

1.6 为什么选数字货币做实验

  1. OKX 模拟盘：行情/账户/订单全链路可虚拟验证
  2. 全天运行：不同时段观察新 K 线，早发现重复信号/日志中断/停止条件失效
  3. 风险隔离：只用 BTC-USDT 现货模拟盘，不用杠杆、不连真实账户

三、可立即落地的三处优化

优化 1：新增 --dry-run 模式到 iron_rules_engine.py（P0）

现有问题：--close 模式输出买入计划（含价格/仓位），Agent 层无二次确认缓冲就推送；如果用户不在飞书旁，可能错过人工确认窗口。

补丁方案：新增 --dry-run 参数：

# dry-run 行为：
# 1. 读取最新已收盘 K 线
# 2. 计算信号（方向/数量/价格/止损/目标）
# 3. 打印"计划中的订单"，不调用任何写入
# 4. 检查 demo/production profile、行情延迟、K 线完整性
# 5. 输出"是否建议执行" + 停止原因（如有）
# 6. 落日志 logs/dryrun-{date}.json

触发时机：--close 扫描前自动跑一次 dry-run（先干跑确认环境安全，再输出可执行计划）。

优化 2：新增「Agent 停止条件清单」到 skill 文档（P1）

将泊舟 11 条停止条件本土化为 A 股版本：

# A股铁律 Agent 停止条件（候选新增）
1.  非交易日（交易日历不可读或今日非交易日）→ 静默
2.  数据源不可用（腾讯QT/新浪日K 连续 3 次失败）→ 停
3.  持仓数据无法读取（watchlist.json 损坏）→ 停
4.  备选池数据不可用（dynamic_watch_pool.json 空或过期 >1 天）→ 停
5.  持仓记录与账户余额不一致 → 停
6.  同一信号 24h 内重复出现 → 标记"重复信号"并跳过
7.  RSI/MA 指标计算为空或数据 <20 条 → 停
8.  周五 + 长假前 + 有持仓 → F7 极高优先级
9.  回测数据 <30 条 → 明确标记"不足以判断"
10. 参数变更未双跑对比 → 不发布新建议
11. 凭证异常（AK/SK 缺失或配置不可读）→ 停

优化 3：凭证安全核查（一次性 P1）

核查 stock-iron-rules 与 ths-auto-trader skill 的凭证处理：

文件 检查项
~/.hermes/skills/ths-auto-trader/ 凭证是否在代码中硬编码（不应有）

依据：泊舟文章评论区最高赞评论是 @leaf_sanren "抛开炒币不谈，我最服的是你把 Agent 的安全边界卡得死"——读者记住的不是策略，是安全工程。这暗示 AI 交易领域的竞争维度正在从策略收益（已高度同质）转向可审计/可停止/可凭证隔离的工程基础设施。

九、指南分析

9.1 文章质量

  • 安全边界工程是核心——评论区共识（"最服的是你把安全边界卡得死"），非营销软文
  • 代码/提示词完整给出（命令块是"给 Pi 执行的"，读者照抄即可）
  • 诚实：明确"不构成投资建议"+"回测不代表未来"+"模拟订单不证明真实可用"
  • 可执行：从安装 Pi 到确认模拟订单，每步有产物

9.2 局限

  • 币圈视角：全篇基于 OKX 现货模拟盘，与 A 股 T+1/涨跌停/同花顺 UI 生态差异大——方法论可迁移，具体实现不可
  • 单策略：仅 MA+RSI+ATR，无多维评分/周期分析/铁律过滤——本机体系已覆盖
  • 无回测量化：未给夏普/回撤/胜率等具体数字——无法横向对比
  • 未讨论 Agent 幻觉：Pi 生成代码可能错，无代码审计/单测机制——本机的 lab_exit_grid_v2.py 参数网格是更好的验证方式
