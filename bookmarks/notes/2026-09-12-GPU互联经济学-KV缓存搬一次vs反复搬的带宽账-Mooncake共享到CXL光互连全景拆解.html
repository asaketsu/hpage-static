零、结论先行

文章的核心贡献不是讲技术——是算了一笔"搬一次 vs 反复搬"的带宽账，把"为什么 GPU 接上了更多内存仍然在等数据"这个问题用具体数字打透。 对我们最深的增量：Mooncake 论文的"跨节点缓存共享让 prefill GPU 计算时间减 26%"是 PagedAttention 笔记的产业级证据补充——vLLM 在单机内做内存分页共享，Mooncake 在跨机维度做缓存共享，两者同构（都是"已有结果不重算"），但解决的是不同尺度的浪费。文章的投资视角（美光/海力士/Marvell 各赚哪段钱）对我们不是直接可用知识，但"客户实际多完成了多少工作？总共多花了多少钱？用过以后还愿不愿意继续买？"这三问是任何"降本增效"方案的通用验收框架。

一、问题层：GPU 在等什么

1.1 内存墙的两个面

面 症状 已有笔记的解法
装不下 模型+运行时数据超出内存容量 Engram 196B 表卸载 Host Memory；PagedAttention 按需分配
搬不快 计算芯片要用的数据迟迟送不到，算得再快也得等 本篇聚焦——连接是瓶颈

"能不能把算力发挥到极致的关键，就是每算一个数，从内存拿过来的速度是不是足够快。如果一秒钟只能拿 10 个数，而 GPU 一秒钟能算 100 个数，那内存堆得再多、算力再快，也没有用。"

1.2 KV 缓存的特殊地位

模型读输入（Prefill）时算出供后续生成使用的中间数据（KV Cache），体积可以比原始文字大几个数量级。PagedAttention 解决的是"存在哪里/怎么分配"，本篇解决的是"搬多快/跨机器能不能共享"。

二、核心账本：搬一次 vs 反复搬（文章最硬的一段）

2.1 场景设定

  • 模型：Qwen3-32B
  • 一次文档读取请求的 KV 缓存：~8.6 GB
  • 假设连接通道带宽：50 GB/s

2.2 方式一：搬回来放 HBM 里反复用

8.6 GB ÷ 50 GB/s ≈ 0.17 秒（搬回来一次）
→ 之后缓存在 HBM 里，GPU 高速反复读取
→ 搬一次的 0.17s 成本被均摊到后续所有生成步骤

结论：如果重新计算这些内容需要 >0.17s，花时间取回已有结果就划算。

2.3 方式二：一直放远处，每生成一个 token 都要取一次

每秒生成 40 token → 每秒需读取缓存 40 次
8.6 GB × 40 次/s ≈ 344 GB/s 需求
通道只有 50 GB/s
→ 数据送不过来 → GPU 闲下来 → 等于浪费

结论：远处增加内存只增加"能存多少"，不提高"每秒能送来多少"——带宽 ≠ 容量。

2.4 与 PagedAttention 笔记的互证

维度 PagedAttention 本篇
解决的浪费 单机内内存分配浪费（80%→<4%） 跨机数据搬运浪费（GPU 闲等）
共享对象 Page Table 指向同一物理 block（系统提示词） 跨节点 KV 缓存迁移（Mooncake）
带宽考量 GPU 内部 HBM 带宽足够 跨机网络带宽 50GB/s 不够 344GB/s 需求
共同原则 已有结果不重算 已有结果不重算

三、跨机共享：Mooncake 实证

3.1 实验设计

两组各 10 个 prefill 节点，每个节点缓存额度 ~300 万 token：
- 对照组：缓存不跨节点共享
- 实验组：缓存可跨节点共享和迁移

3.2 结果

指标 不共享 共享
Prefill 平均 GPU 计算时间 100（基线） 74（-26%）

"省下来的时间让 GPU 有机会处理其他请求。"

与 Plano 的 model affinity 互证：Plano 的"会话粘性避免换模型→缓存失效"是 agent 层的缓存复用，Mooncake 是基础设施层的缓存共享——两者都证明"已有计算结果不重算"是真实的降本杠杆。

四、连接的三层物理（文章产业拆解）

4.1 铜连接 vs 光互连

维度 铜连接 光互连
优势 短距离成本低/工程成熟 长距离/高带宽可行
劣势 速率提高→信号损耗+维持功耗 散热/光纤/维修更讲究
技术 — NPO（封装附近光电转换）/ CPO（与主芯片共封装）

4.2 CXL 协议

允许兼容主机通过相应链路访问扩展设备中的内存——Engram 笔记的"CXL 内存池化是产业走势"在这里被展开为具体产品线。

4.3 Marvell 的三件产品

产品 作用 状态
Structera X 内存扩容控制器（接 DDR4/DDR5） 已出货（超大规模客户部署）
Structera S 交换芯片（连接/分配内存资源） 产品线中有
Alaska P 信号调节芯片（维持高速 PCIe 信号） 产品线中有
Photonic Fabric 光连接扩展共享内存 FMS 演示→等客户导入

4.4 外部内存模块的复合结构

"DDR5 提供容量，模块上的 HBM 承担缓存作用，光连接负责与计算端传数据。"

关键洞察：内存往外扩，HBM 不消失而是出现在新位置——美光/海力士（HBM+DDR5）和 Marvell（连接）有机会同时参与采购，不是零和博弈。

五、客户账本：连接值多少钱

5.1 教学算例

原：100 元 → 100 份任务 → 1 元/份
加连接后：110 元 → 130 份任务 → 0.85 元/份（-15.4%）

客户愿意多花钱，是希望同样一批 GPU 多干活——与 SoL-Pi 的"token 效率而非分数"同源：性能提升要看每单位成本的实际产出。

5.2 两个真实案例

案例 做法 效果
Meta 不常用数据移到压缩内存/SSD 内存用量降 20-32%（百万台服务器）
Marvell Structera X 旧 DDR4 继续用 客户少买新内存 + Marvell 卖控制器

"客户实际多完成了多少工作？总共多花了多少钱？用过以后，还愿不愿意继续买？"

七、批判性审视

  1. 8.6 GB 的场景偏极端：文章自己也说"特定输入长度和保存精度下的例子，普通的一句提问未必需要这么多内存"——但这个数字被用于算"344 GB/s 需求"，如果缓存只有 0.5 GB（普通对话），344→20 GB/s，50 GB/s 通道就够——极端案例的结论不能直接外推
  2. Mooncake 的 26% 是 prefill 阶段：不是端到端——decode 阶段（写回答）的收益未报告；如果 decode 才是瓶颈，prefill 省 26% 的整体收益可能小得多
  3. 50 GB/s 带宽假设偏保守：NVLink 是 900 GB/s，PCIe 5.0 是 ~128 GB/s——文章用 50 可能是 CXL 的数，但没标清楚
  4. 投资视角的幸存者偏差：文章选 Marvell 是因为它是"连接"概念的最佳标的，但没讨论如果 NVIDIA 自己做连接芯片（NVLink/NVSwitch），Marvell 的市场空间会被压缩
  5. Meta 20-32% 的口径：是"内存用量下降"不是"总成本下降"——文章诚实标注了但标题/叙事容易让人混读
