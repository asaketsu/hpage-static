# Eval Loop：用评估闭环消灭 AI 输出的 Slop

> 来源：[微信公众号](https://mp.weixin.qq.com/s/ktXBBApfLFFi7q3No0g1Pw) · 2026-06-01
> 标签：`#EvalLoop` `#AI质量` `#Hermes` `#LLM评估` `#Agent系统`

---

## 核心论点

**AI 输出质量差，不是 prompt 的问题，是系统缺了一层**。

所有人都死磕 prompt（输入端），却完全忽略了输出端的质量拦截。Prompt 是假设，输出是结果，**eval 是把两者闭环的唯一东西**。没有 eval，你永远在猜。

> 更好的枪往黑处打，照样打不中目标。

---

## Slop 藏在哪里

| 位置 | 表现 | 危害 |
|------|------|------|
| **内容输出**（推文/文章/邮件） | 技术上挑不出毛病，但空洞无物，与 AI 时间线上每个账号一样 | 当众出丑 |
| **产品输出**（Agent/客服/管道） | 极其肯定的语气给出错误答案、幻觉数字、格式损坏 | 静默规模化失血 |

**共同病因**：未经测量的 AI 输出直接到达受众，中间没有任何关卡。

---

## Eval Loop 三环节

```
生成输出 → 按标准打分 → 抓出低于线的 → 修掉失败 → 重新打分 → 只让通过的放行
```

| 环节 | 作用 | 类比 |
|------|------|------|
| **发货前** | 新 prompt/model 跑 case 集，确认没有退步 | 回归测试 |
| **运行时** | 输出生成时实时打分，到达用户前截住失败 | 护栏 |
| **生产环境** | 持续抽样真实输出打分，质量下降当天发现 | 监控 |

## Benchmark 三零件

### 1. Test Cases（测试用例）

**内容侧**：挑出 20-50 篇最好的作品——爆款帖子、被收藏最多的文章、敢署名的内容。这是"好"长什么样。

**产品侧**：从日志里拿真实输入，不是 happy-path 例子。真正搞崩你的是 weird case。

### 2. Metrics（度量）

**内容侧评分表四维度**：

| 维度 | 标准 |
|------|------|
| 具体性 | 告诉读者一件明天就能动手做的动作，不是 vibe |
| 可读性 | 受众任何人都能看懂，无 jargon 高墙 |
| 结构性 | 有步骤可复制，不只是打鸡血 |
| 新颖性 | 读者不知道还能这样做 |

**总判据**：有人会收藏这篇、回头照着做吗？不会 = slop。

**产品侧度量选择**：

| 任务类型 | 度量方法 |
|---------|---------|
| 单一正确答案 | exact match |
| 结构校验 | JSON/KV validator |
| 开放生成 | 语义相似度 + LLM-as-judge |

> 评分表越具体，分数越可信。"好不好看" = 模糊 → 模糊分数。"至少有一个可复制粘贴的模板" = 具体 → 可信分数。

### 3. Threshold（阈值）

- **起点：0.7**，低于此线一律不发货，没有例外
- 阈值生效的唯一方式：永远不会因为"这篇我挺喜欢"就让 0.6 的过了
- 整套意义 = 把深夜的 ego 从决策里拿掉

## 六步搭建（Hermes 实现）

| 步骤 | 动作 | 关键点 |
|------|------|--------|
| **① 接入通知** | Hermes + Telegram/Slack | 关卡要能打断你才有用 |
| **② 灌入标杆** | 20-50 篇最好作品存入记忆 | 成为 agent 永久可查的 ground truth |
| **③ 创建 Judge 技能** | 评分表编码为技能 | LLM-as-judge，比你自己更一致（没有 ego） |
| **④ 度量套件技能化** | 测试用例+度量函数变技能 | 度量库按需取用，agent 自己管理 |
| **⑤ 回归测试+审批** | 改动触发重跑所有 case | Slack approval button，分数 delta 可见 |
| **⑥ Cron 监控生产** | 定期采样+打分+掉线预警 | 失败输出自动回写为新 test case → 复利 |

**复利机制**：踩过的坏输出 → 自动变成新 test case → 套件每周自动变硬 → 地板在睡觉时自己抬高。

## 思考

这篇文章精准诊断了当前 AI 使用中的一个系统性盲区：**所有人都在优化生成端，没人搭建评估端**。

**与我们系统的关系**：

| 我们的实践 | 对应文中概念 | 差距 |
|-----------|-------------|------|
| Skill 压力测试（skill-stress-test） | 发货前回归测试 | ✅ 已有 |
| Watchdog + 传感器网格 | 生产环境监控 | ✅ 已有雏形 |
| 错误案例库（error-case-library） | Test cases 自动积累 | ⚠️ 需强化闭环 |
| **运行时 Judge 技能** | 实时打分护栏 | ❌ 缺失 |
| **内容质量评分表** | 评分标准编码 | ❌ 缺失 |

**可立即行动的改进**：
1. 创建 `content-judge` Skill，编码内容质量四维度评分表
2. 为 cron 产出的推送内容加评分步骤，低于阈值不发送
3. 将踩过的坏输出自动回写为 test case，实现复利

> 一旦质量变成了一个数字，slop 就从你不断感受到的一个情绪，变成了一个可以修的 bug。你没法 debug 一个感觉，但你可以 debug 一个从 0.82 掉到 0.61 的分数。

## 补充一：运行时 Judge 实现方案

### 设计原则

运行时 Judge 不是事后打分，是**生成交付前的最后一道门**。核心设计：

1. **嵌入生成流程末端**：内容生成 → Judge 打分 → ≥ 阈值放行 / < 阈值自动修正
2. **评分表可执行化**：评分标准编码为结构化模板，LLM 按模板逐项打分
3. **零人工介入**：Judge 由 LLM-as-judge 自动执行，不需要人读

### 内容质量评分表（编码模板）

```json
{
  "content_judge": {
    "dimensions": {
      "specificity": {
        "weight": 0.30,
        "prompt": "文中是否包含至少一个明天就能动手做的具体动作？不是 vibe，不是方向，是可复制粘贴的步骤或模板。",
        "scoring": "0=纯抽象概念 | 0.3=有方向无步骤 | 0.6=有步骤但模糊 | 0.8=有具体步骤可执行 | 1.0=可直接复制粘贴落地"
      },
      "readability": {
        "weight": 0.25,
        "prompt": "目标受众能否不查字典看懂？无 jargon 高墙，逻辑链完整，段落有明确主线。",
        "scoring": "0=行业黑话堆砌 | 0.3=需要背景知识 | 0.6=基本可读 | 0.8=流畅易懂 | 1.0=小白也能照做"
      },
      "structure": {
        "weight": 0.25,
        "prompt": "是否有可复制的步骤序列？不只是打鸡血，有 '先做A→再做B→最后C' 的行动路径。",
        "scoring": "0=纯观点无结构 | 0.3=有段落无逻辑 | 0.6=有逻辑无步骤 | 0.8=有步骤可复制 | 1.0=步骤完整+验证标准"
      },
      "novelty": {
        "weight": 0.20,
        "prompt": "读者读完会不会觉得'原来还能这样'？还是跟 AI 时间线上每个账号一样。",
        "scoring": "0=完全老生常谈 | 0.3=旧观点换包装 | 0.6=有新角度 | 0.8=有独特见解 | 1.0=颠覆认知+可验证"
      }
    },
    "threshold": 0.70,
    "verdict_prompt": "总判据：有人会收藏这篇、回头照着做吗？不会 = slop。"
  }
}
```

### 产品侧评分表（编码模板）

```json
{
  "product_judge": {
    "dimensions": {
      "factual_accuracy": {
        "weight": 0.35,
        "prompt": "输出的数字/引用/事实是否可验证？幻觉检测。",
        "scoring": "0=明显幻觉 | 0.3=部分不可验证 | 0.6=可验证但无来源 | 0.8=有来源可验证 | 1.0=每个声明都有证据"
      },
      "format_integrity": {
        "weight": 0.25,
        "prompt": "输出格式是否符合要求（JSON/KV/Markdown）？结构是否完整？",
        "scoring": "0=格式损坏 | 0.3=部分符合 | 0.6=格式对但缺字段 | 0.8=完全符合 | 1.0=格式+语义+类型全对"
      },
      "completeness": {
        "weight": 0.25,
        "prompt": "是否完整回答了用户的问题？有没有遗漏关键部分？",
        "scoring": "0=完全跑题 | 0.3=部分相关 | 0.6=相关但不完整 | 0.8=完整回答 | 1.0=完整+超出预期"
      },
      "edge_case_handling": {
        "weight": 0.15,
        "prompt": "是否处理了边界情况（空输入/特殊字符/极大值）？",
        "scoring": "0=无处理 | 0.3=有意识无方案 | 0.6=有基本处理 | 0.8=全面覆盖 | 1.0=覆盖+优雅降级"
      }
    },
    "threshold": 0.70
  }
}
```

### Judge 执行流程

```
生成输出
  ↓
识别输出类型（content / product / code）
  ↓
加载对应评分表模板
  ↓
LLM-as-judge 逐维度打分（0-1 × 权重）
  ↓
加权总分 ≥ 0.7 → 放行交付
加权总分 < 0.7 → 自动修正（标注失败维度）→ 重新生成 → 最多重试 2 次
  ↓
记录评分到 ~/.hermes/evolution/judge-scores.jsonl
  ↓
连续 <0.7 → 自动写入 error-case-library → 复利
```

### 失败输出自动回收（复利机制）

每次 Judge 打分 < 0.7 的输出，自动追加为 test case：

```json
{
  "id": "TC-JUDGE-YYYY-NNN",
  "date": "2026-06-01",
  "source": "content_judge|product_judge",
  "original_output": "...",
  "failed_dimensions": ["specificity=0.3", "novelty=0.2"],
  "total_score": 0.45,
  "expected_fix": "增加具体可执行步骤，提升新颖性",
  "status": "pending"
}
```

**复利效应**：每周 cron 重新跑失败 test case → 如果仍失败 → 地板持续抬高。

## 补充二：与现有系统的集成路径

### 已有 Skill 映射

| 文中概念 | 已有 Skill | 当前状态 | 需要补充 |
|---------|-----------|---------|---------|
| 发货前回归测试 | `skill-stress-test` | ✅ 完整 | 无 |
| 测试用例积累 | `error-case-library` | ✅ 有雏形 | 增加 Judge 失败输出自动回收 |
| 运行时护栏 | **缺失** | ❌ | 新建 Judge 评分层 |
| 内容评分表 | `doc-qa`（文档侧） | ⚠️ 有但不覆盖内容 | 增加 content_judge 维度 |
| 产品评分表 | `ai-generated-quality` | ⚠️ 有代码侧 | 增加 product_judge 维度 |
| 生产监控 | `sensor-grid` + `watchdog` | ✅ 完整 | 增加 Judge 评分趋势传感器 |
| 进化闭环 | `evolver` | ✅ 完整 | 读取 judge-scores.jsonl 作为进化输入 |

### 集成方案（最小改动）

**Step 1：内容生成末端加 Judge 层**

在所有内容输出型 cron（morning-briefing、daily-paper-push、news-aggregator）的 prompt 末尾注入：

```
## Judge 评分（必须执行）
生成内容后，按以下四维度打分：
- 具体性(0-1)：是否有可复制粘贴的动作？
- 可读性(0-1)：目标受众能看懂吗？
- 结构性(0-1)：有步骤序列吗？
- 新颖性(0-1)：读者会觉得"原来还能这样"吗？
加权总分 = 具体性×0.30 + 可读性×0.25 + 结构性×0.25 + 新颖性×0.20
总分 < 0.7 → 必须修正后重新输出，最多重试 2 次。
```

**Step 2：sensor-grid 增加 Judge 趋势传感器**

```
| 传感器 | 检测对象 | 对应文件 | 信号输出 |
|--------|---------|---------|---------|
| Judge 评分趋势 | judge-scores.jsonl | ~/.hermes/evolution/judge-scores.jsonl | 7日滑动均值 ↓0.05 → 🟡 |
```

**Step 3：evolver 读取 Judge 分数驱动进化**

```
evolver COLLECT 阶段新增：
- 读取 judge-scores.jsonl 中最近 7 天的评分
- 识别 score < 0.7 的模式（哪些维度反复低分）
- 将低分模式转化为 GENERATE 输入（优化 prompt/skill）
```

### 不需要新建独立 Skill 的理由

评分表已可嵌入现有 skill（doc-qa / ai-generated-quality），Judge 执行可嵌入 cron prompt。独立的 `content-judge` Skill 可以创建，但优先级低于**把评分表嵌入现有流程**。

### 关键决策点

| 选项 | 成本 | 效果 |
|------|------|------|
| A. 创建独立 `content-judge` Skill | 中（新建+测试） | 通用，任何 skill 可调用 |
| B. 嵌入 cron prompt（评分指令） | 低（改 prompt 即可） | 见效快，但分散 |
| C. 两步走：先用 B 快速验证，验证后沉淀为 A | 最低+最优 | ✅ 推荐 |

**推荐 C**：先在 2-3 个内容型 cron 中嵌入评分指令，跑一周看数据。验证有效后再创建独立 Skill。

## 补充三：从理论到实践的 30 天路线图

| 周 | 目标 | 交付物 |
|----|------|--------|
| **W1** | 评分表嵌入 cron | 3 个内容 cron 加入 Judge 评分指令 |
