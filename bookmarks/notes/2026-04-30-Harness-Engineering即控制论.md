## 摘要

OpenAI 2026年2月发布《Harness Engineering》一文提出"人类掌舵、Agent执行"的编程范式。本文作者从控制论视角论证：AI编程的本质就是控制论在软件工程的具体实现。核心论点是程序员的角色从"代码生产者"转变为"环境架构师、反馈回路设计者、质量标准编码者"。文章将控制论的"目标→感知偏差→施加干预→消除偏差"循环映射到AI编程全流程，并给出七个可直接落地的实践建议。

## 核心内容

### 1. Harness Engineering 七个实践

源自 OpenAI 官方文章 + 作者经验总结：

**① 给目录不给整本说明书。** AGENTS.md 控制在约100行，仅作为索引目录，AI需要时根据目录找到深层知识（渐进式披露）。过长的 SKILL.md 同理，会挤占上下文、模糊重要等级。

**② 规则沉淀到仓库。** 代码仓库是AI唯一能看到的世界。设计决策、架构约定、团队共识必须以版本化 Markdown/代码提交到仓库，否则AI就像迟到三个月的新员工。

**③ 必须有架构约束。** 仅靠 Prompt 无法约束AI生成完全符合要求的代码。通过脚本、流水线校验架构合规性，防止架构漂移。明确哪些地方需要限制、哪些允许AI自由发挥。

**④ 构建AI可观测系统。** 将日志、监控通过文件/MCP暴露给AI，让AI自己闭环"开发→测试→修复"。人的Review反而成为效率瓶颈。

**⑤ 等待成本高于纠错成本。** PR生命周期应尽量短，AI代码产出速度远超人类Review速度。但金融支付等安全敏感场景此条存疑。

**⑥ 自动清理垃圾代码。** AI生成代码会参考已有实现，一次坏实现会被多次复制。运行后台任务定期扫描偏差、发起重构PR，持续小步还债。

**⑦ 人类建议沉淀到仓库。** Code review评论、重构PR、用户反馈中的人类要求必须提取为规则，否则随着时间流逝无法影响AI未来输出。

### 2. 控制论核心映射

控制论的三个关键词：信息、控制、反馈。

**信息**是消除不确定性的东西。宇宙趋向熵增，获得信息就是克服熵。在AI编程中，AGENTS.md、SKILL.md、规则文件就是信息——减少AI生成代码的不确定性。

**控制**的本质是通过克服不确定性，对系统施加影响以达到既定目标。被控对象必须满足两个条件：存在多种发展可能性、人可以在可能性之间选择。AI生成的代码仓库完全满足。

**可能性空间缩小**是核心机制。通过规范/框架/约束把AI生成路径从M缩小到m。例子：让AI写冒泡排序有一万种写法，但限定C++、基础库、大驼峰命名后，生成结果就更确定。

**控制力累积**解释了为什么大任务要拆小步。AI单次控制能力有限，通过多次负反馈（老鹰抓小鸡的多次俯冲），总控制能力累积达到目标。

**共轭控制**（L⁻¹AL）解释了工具的作用：把不可控的事转化为可控过程。感受器（L）收集参数给AI，AI通过工具决策，效应器（L⁻¹）将参数转换为代码。MCP/Skill脚本就是效应器。

### 3. 传感器：反馈回路的关键

两类传感器让控制循环自矫正：

**业务无关传感器**：语法检测、编译、代码规范、安全扫描、部署失败日志。不用了解业务就知道代码不对。必须接入AI生产代码全流程。

**业务相关的传感器**：用例规约中的前置/后置条件、业务规则、涉众利益、质量需求、设计约束。必须写到AI可检测、可验证的程度。简单的Prompt也许能生成正确代码，但缺少评判标准——判断是否100%满足业务规则。

### 4. 程序员角色转变

| 古法编程 | Harness Engineering |
|----------|-------------------|
| 编写代码 | 设计环境 |
| 调试bug | 明确意图 |
| 代码审查 | 构建反馈回路 |
| 编写测试 | 将工程判断编码成机器可读规则 |
| 重构代码 | 校准传感器与执行器 |

**核心暴论**：领域建模不会消失，会更重要。程序员的核心价值不是"实现"而是"评估"。

## 🔍 借鉴点

**AGENTS.md < 100行规则** → 我们当前的 AGENTS.md 已经较精简，但应定期检查是否膨胀。SKILL.md 也应控制长度，详细内容放到 references/ 子文件中渐进式披露。

**传感器理念** → 我们的 evolver/self-evolver skill 本质就是在构建"业务无关传感器"（错误自动发现→修复→沉淀为规则）。可以进一步强化：将代码规范检查、lint 输出暴露给AI形成闭环。

**共轭控制 L⁻¹AL** → 我们的 Skill 脚本（如 doc-qa 的校验脚本、software-copyright 的检查脚本）就是效应器 L⁻¹。应该持续丰富这类"将AI决策转化为可执行操作"的工具。

**业务规则可验证化** → SKILL.md 不应只是描述性文档，应包含可执行的校验逻辑（脚本、断言、CI检查）。

**自繁殖系统警惕** → AI首次写的烂代码会被后续实现复制参考，坏实现会指数级扩散。这强化了"代码仓库必须保持整洁"的重要性，也是我们 auto-dream/evening-summary 定期清理的理论支撑。

## 💡 启发

**控制论是AI Agent系统的元理论。** 我们一直在做的 AGENTS.md → skill → evolver → memory 这套体系，本质就是在构建一个控制论系统：目标（AGENTS.md）→ 控制器（AI）→ 被控系统（代码/文档）→ 传感器（evolver/doc-qa/lint）→ 反馈回路（memory/self-evolver）。理解了这个元框架，后续的架构决策就有理论依据了。

**可能性空间理论指导 skill 设计。** 每个 skill 的 SKILL.md 就是在缩小AI完成任务的可能性空间。写得越精确，AI越不容易偏离目标。但也不能过度约束——需要明确哪些地方限制、哪些地方允许AI自由发挥。

**传感器建设是当前最大短板。** 我们的 evolver 主要捕捉"错误"，但缺少"架构漂移检测"、"代码风格一致性检查"等传感器。未来可以建设更多自动化检测脚本。

## 🔮 预判

**Harness Engineering 会成为AI编程的主流方法论。** OpenAI 已经在推动这个概念，未来所有AI编程框架（Hermes/OpenClaw/Claude Code/Codex）都会朝这个方向演进：更丰富的传感器、更自动化 的反馈回路、更完善的规则体系。

**领域建模会以新形式复兴。** 不是回到UML工具，而是以结构化Markdown、可执行的用例规约、AI可读的业务规则等形式重新出现。BA/产品经理的角色也会变成"规则编码者"。

**SKILL.md 会从"描述性"进化为"可执行"。** 未来的 skill 不仅包含指令文本，还包含校验脚本、断言、CI配置。这与我们的 doc-qa skill 的方向一致。
