## 摘要

提出企业 AI 转型的三步路线图：知识库化（结构化 Wiki）→ 技能化（可调用 Skill）→ 智能体化（多 Agent 协同自主完成任务）。核心批判是大多数公司停在"第零步"（让员工用 AI 工具），以及将 RAG/向量数据库等同于知识库的认知误区。真正的分水岭不在技术而在"谁来负责持续结构化"——没有专人维护，知识库必沦为垃圾堆。

## 核心内容

### 第零步：伪转型

大多数企业的"AI 化"停在让员工把 AI 工具用起来。这是必要条件但远非充分条件——工具普及不等于流程再造，更不等于知识资产化。

### 第一步：知识库化

将所有核心知识——代码、流程文档、视频教程、员工访谈——用 Agent 蒸馏成 Markdown 格式的 Wiki。

关键区分：**Wiki ≠ 向量数据库**。向量数据库只做语义检索；Wiki 是 Agent 能直接读懂、直接调用的结构化知识。RAG 只是检索入口，不是知识库。所谓知识库，是真正做好了结构化的事情。

### 第二步：技能化

基于知识库，把每一个核心业务流程写成可调用的 Skill。这些 Skill 专属于企业，引用自己的知识库，拿走别人也跑不起来。

### 第三步：智能体化

多个智能体协同调度知识库和技能，自主完成任务。人只在决策节点和例外情况时介入。

### 分水岭：谁来负责结构化

如果还是让业务同事临时把材料丢给 AI，知识库很快变成新垃圾堆。真正值钱的是把流程、例外、判断标准**持续**整理成机器能调用的形态。Wiki 放在向量库前面——先有结构化，再做检索增强。

## 🔍 借鉴点

- **三步框架可直接作为咨询输出** — 面对企业客户"怎么做 AI 转型"时，这个路线图 + 知识审计前置就是现成的方法论
- **"拿不走"是企业 Skill 的护城河设计原则** — Skill 绑定企业专有知识库、本地路径、环境变量，迁移成本本身就是壁垒
- **Wiki 前置于向量库的架构决策** — 先做结构化（Agent 可执行），再补充语义检索（发现盲区），顺序不能反
- **持续结构化机制是核心瓶颈** — 不是一次性工程，需要专人或自动化流程（cron + evolver 模式）持续维护

## 💡 启发

- **Hermes 架构就是三步法的个人级验证** — SKILL.md（知识库化）→ skills/ 目录 300+ 技能（技能化）→ delegate_task + cron 调度（智能体化），我们踩过的坑（知识腐烂、格式不一致）恰好验证了"持续结构化"的难度和必要性
- **"第零步"陷阱的普遍性** — 不只是企业，个人用 AI 也是如此。装了 ChatGPT 不等于会 prompt engineering，会 prompt 不等于有知识体系。工具普及是表层，结构化积累才是深层
- **向量库的重新定位** — 不是知识库的替代品，而是知识库的**发现层**。类比：Wiki 是教材（精确可执行），向量库是索引（广谱模糊），两者互补而非互斥。原论点"向量数据库只做语义检索"过于绝对

## 🔮 预判

1. **企业 AI 转型的瓶颈将从"技术能力"转向"知识管理能力"** — 能做 RAG 的团队很多，能持续维护结构化知识库的极少，后者才是真正的竞争壁垒
2. **"知识审计"将成为新职业/新服务** — 类似当年的 ERP 实施顾问，企业需要有人盘点哪些知识存在、缺失、过期，这是三步路线的隐性第零步
3. **Agent 原生的知识格式（Markdown Wiki）将取代传统文档管理** — Confluence/SharePoint 的"文档仓库"模式无法被 Agent 直接调用，Markdown + 元数据才是正确方向
4. **"技能化"阶段会出现行业标准** — 类似 Skill 的描述协议（如 Agent Card / A2A），企业 Skill 的标准化定义和调用接口将形成生态
