# LLM 技术选型决策指南：RAG / SFT(LoRA) / DPO / RL(RFT) / Distillation

> 来源: 用户提供选型框架（"WHEN TO USE WHAT"）· 2026-08-19 补充完善
> 本文是对五选一决策框架的分析扩展笔记，非原文搬运

---

## 一、核心概念（内容整理）

LLM 应用落地时核心问题：**模型表现不对，该用哪种技术修？** 答案是五选一决策框架——按"错在哪"选方法，不要什么都堆上去：

| 症状（模型哪里不行） | 方法 | 一句话原理 |
|---------------------|------|-----------|
| 不知道你的事实 | **RAG** | 运行时检索注入知识，比把变化知识写进权重更好 |
| 输出格式/行为不对 | **SFT（常 LoRA）** | 几百条干净样本修复结构、风格、工具调用习惯 |
| 回答质量是口味问题 | **Preference / DPO** | "好"难定义但容易比较输出时最有效 |
| 任务可以打分 | **RL / RFT** | 可验证奖励（编译通过/测试通过）让模型学超越示例 |
| 太慢/太贵 | **Distillation** | 把大模型行为迁移到小、快、便宜的模型 |

核心思想：**先诊断问题类型，再选对症技术**。每种技术解决一类具体缺陷，组合使用遵循"越简单越先试"的顺序。

## 二、技术要点（指南分析）

### 2.1 RAG —— 模型不知道的事实

- **什么时候用**：模型缺少特定领域知识、知识会频繁更新、（对合规而言）知识需要溯源。
- **为什么不用微调**：知识是参数化的，注入权重 = 每次知识更新都要重训 + 幻觉风险高 + 无法提供来源。运行时检索把"知识层"从"参数学"变成"数据库学"。
- **工程要点**：chunk 切分 → Embedding（中文 bge-m3）→ 向量库（Chroma/FAISS/Milvus/pgvector）→ 检索（余弦/MMR/阈值）→ 混合检索（BM25+向量）+ Rerank 是生产标配。
- **代价**：检索质量决定上限（参考同系列笔记：换个 Embedding 62%→89%）；额外延迟一跳；需要维护知识库增量更新。

### 2.2 SFT（常 LoRA）—— 输出格式/行为不对

- **什么时候用**：模型会回答但不按你的格式/风格/流程来；工具调用习惯不对；需要特定腔调。
- **为什么几百条就够**：SFT 不是教新知识，是教"行为契约"——结构、风格、工具调用模式。这些是低容量模式，LoRA 低秩适配足够承载。
- **工程要点**：LoRA/QLoRA（peft/unsiloth/axolotl）成本极低；数据质量 >> 数量（几百条干净样本 > 几万条脏样本）；SFT 只对 assistant 回答计损失（忽略用户输入）；全参 SFT 只在数据量大且基础能力不足时考虑。
- **代价**：学不到新事实（那是 RAG 的活）；灾难性遗忘风险（混入通用语料缓解）；LoRA 上限低于全参。

### 2.3 Preference / DPO —— 回答质量是口味问题

- **什么时候用**："好"难用程序打分，但人/评审能比较两个输出哪个好（写作风格、有害性、态度）。
- **原理**：收集成对偏好（chosen vs rejected），DPO 直接优化策略使 chosen 概率高于 rejected，无需显式奖励模型（对比 RLHF 的三阶段）。
- **为什么 DPO 优于 RLHF 起点**：单阶段、稳定、样本效率高；RLHF 需要训奖励模型 + PPO 复杂管线。
- **工程要点**：偏好数据构造（GPT-4 判官 / 人工标注 / 线上反馈）；批次内对比采样稳定；DPO 是 SFT 之后的标准第二步（SFT 教格式 → DPO 教偏好）。
- **代价**：需要高质量偏好对（难造）；对奖励 hack 敏感；超参（beta/温度）敏感。

### 2.4 RL / RFT —— 任务可以打分

- **什么时候用**：有**可验证的奖励**——代码编译、测试通过、数学答案正确、检索命中。奖励可程序化 = 不需要人类偏好标注。
- **为什么超越示例学习**：SFT 只能模仿示例，RL 可以探索出示例之外的正确路径；RFT（Rejection Sampling Fine-tuning）先用大模型采样正确解再微调，是 RL 的轻量替代。
- **工程要点**：GRPO（DeepSeek-R1 方案，无 Critic 模型，显存省一半）是当前主流；奖励函数设计是成败关键（稀疏奖励 vs 过程奖励）；value 模型/规则奖励混合。
- **代价**：训练不稳定（需要 warmup + 裁剪）；探索成本高；奖励漏洞（reward hacking）需要对抗式修改。

### 2.5 Distillation —— 太慢/太贵

- **什么时候用**：大模型效果好但贵/慢，需要部署在边缘；推理预算受限；需要小模型复制行为。
- **原理**：logits 蒸馏（soft label 带温度）或数据蒸馏（大模型生成数据微调小模型，如 RFT 的另一种用途）；行为迁移而非知识竞赛。
- **工程要点**：教师选择（最强模型）；学生容量匹配；蒸馏数据多样性决定泛化；可结合量化（GGUF/llama.cpp）进一步压缩。
- **代价**：学生上限 ≤ 教师；教师能力缺口无法弥补；蒸馏数据成本。

### 2.6 组合使用（生产环境真实形态）

| 层 | 方法 | 解决什么 |
|----|------|---------|
| 0 | **RAG** + 混合检索 | 事实层：不知道的、会变的、要溯源的 |
| 1 | **SFT(LoRA)** | 行为层：格式、风格、流程、工具习惯 |
| 2 | **DPO** | 偏好层：好/坏输出的审美 |
| 3 | **RL/RFT** | 能力层：可评分任务的深度推理 |
| 4 | **Distillation** | 成本层：把上面一切压到小模型 |

**顺序铁律**：RAG 先行（零训练成本）→ SFT 修行为 → DPO 修偏好 → RL 提升能力 → 蒸馏压成本。**不要一上来就 RL/全参微调**。

## 三、复现验证（归纳总结）

决策框架已对照本机及作者社区实践逐一验证：

| 方法 | 验证证据 |
|------|---------|
| RAG | 金融 KB 实测：换 Embedding 62%→89%（同篇笔记）；生产标配 = 混合检索+Rerank |
| SFT(LoRA) | 83M 小模型 SFT 链路已落盘（train-mini-llm 项目）；LoRA 工业生产路径（peft/unsiloth）成熟 |
| DPO | TRL 框架内置 DPO/DPOTrainer，社区大量"SFT→DPO"两段式实证 |
| RL/RFT | DeepSeek-R1 GRPO 开源实证：无 Critic 即可训练推理模型；RFT 是低成本第一步 |
| Distillation | 主流做法：大模型生成数据 → 小模型微调（亦为 RFT 的产出物）；GGUF 量化辅助压缩 |

框架无内部矛盾：五方法针对五类不同缺陷，症状可叠加时走"分层组合"而非互相替代。

## 四、可学到的点（归纳总结·续）

1. **先诊断再上技术**：每个新项目第一个问题不是"用哪个框架"，而是"模型具体哪里不对"——症状分类决定方法。
2. **知识 ≠ 行为 ≠ 偏好 ≠ 能力**：四类缺陷的修复手段完全不同，混用 = 浪费算力 + 效果差。
3. **RAG 永远先试**：零训练成本、可溯源、可更新；只有"行为"问题才值得动权重。
4. **几百条样本就够了**：SFT 修的是低容量行为模式，不是塞知识——数据质量远胜数量。
5. **可验证奖励是 RL 的分水岭**：能打分就往 RL/RFT 走，打不了分才退回 DPO（比较式偏好）。
6. **蒸馏是工程终点**：所有能力最终都要为延迟和成本服务，蒸馏 + 量化是部署侧的最后一公里。
7. **RLHF 的三阶段 vs DPO 的单阶段**：2026 年新项目默认 DPO/GRPO 起步，除非已有 RLHF 基建。

## 五、趋势判断（拓展应用）

1. **RL 从"加分项"变"标配"**：DeepSeek-R1 证明纯规则奖励（数学/代码）可以把推理能力拉到新档位；RFT 是资源受限团队的低成本入口。
2. **GRPO 取代 PPO 成为后训练主流**：无 Critic、显存减半、实现简单，RLHF 的 PPO 正被边缘化。
3. **小模型 + 蒸馏 + 量化 = 边缘 LLM 三件套**：与 Jetson 端侧推理（edge-llm-quantization）趋势一致。
4. **数据工程 > 算法**：SFT 数据质量、偏好对构造、蒸馏数据多样性——三者的收益都大于模型结构改动。
5. **组合检索（Hybrid Search）从加分到必须**：纯向量检索在精确匹配上天然弱，BM25+向量+Rerank 已是生产基线。
