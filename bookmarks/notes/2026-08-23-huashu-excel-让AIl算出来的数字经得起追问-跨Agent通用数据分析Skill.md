## 一句话总纲

> **核心命题**：AI 做数据分析的错误不会抛异常——"错在三个地方，零报错、零 NaN、零警告"。huashu-excel 存在的全部理由，是让那句"这个数你怎么算的？"能被答上来。用八步流程（体检→清洗→对齐→分析→对账→交付→验图→质控）+ 六个脚本（含 master check 与独立复核）确保 AI 算出来的数字可追溯、可验证、经得起追问。

## 一、内容详细整理

### 1.1 立论案例（效果对比）

同一份脏表问"1 月总销售额"：

| 做法 | 结果 | 误差 |
|------|------|------|
| 主流 `pd.read_excel()` | 34,893,234 | **+161%**（含合计行/小计行/重复行，零报错） |
| huashu-excel | 13,367,767 | 0（先体检发现问题，再用对账校验） |

**主流做法的三个隐蔽错误**：合计行被当门店、华东小计被当门店、粘贴事故重复行被算两次——**没有任何一处会报错**。

### 1.2 八步标准作业流程

```
1 体检  表结构体检（先用 openpyxl 读原始单元格，再动 pandas）
2 清洗  变成规范分析表，每步可追溯
3 对齐  摸底→查外部基准→告诉用户→问他要什么→定口径
4 分析  扫陷阱，走配方，每条发现推到"所以呢"
5 对账  行数守恒/总和守恒/与表内合计交叉验证（master check）
6 交付  Excel/图表/报告，口径随数字一起交付
7 验图  渲染自检（越界/重叠/遮挡/双轴/图文数字打架）
8 质控  另派一个没参与创作的 agent 从原始数据重算，拆你的台
```

**第 3 步"对齐"为什么值得单独成一步**：用户说"帮我分析一下"时还不知道自己要什么。澄清不放在最开始，放在"你已经看懂数据、他也能看懂你的描述"之后。带着错的问题做完整分析，返工成本远高于等这一次。

**第 8 步"质控"是最容易被省掉的一步，而它抓到的问题比前面所有闸门加起来还多**。

### 1.3 脚本矩阵（7 个，均在 `scripts/`）

| 脚本 | 功能 | 时机 | 退出码语义 |
|------|------|------|-----------|
| profile_table.py | 表结构体检 | 算任何数字前 | — |
| clean_table.py | 清洗 + 可审计 pandas 脚本 | 体检后 | — |
| scan_traps.py | 分析陷阱扫描 | 下结论前 | — |
| verify_numbers.py | 数字对账 | 交付前 | **1 = 有对不上的** |
| verify_visual.py | HTML 渲染自检 | 交付前 | **1 = 图画错了** |
| verify_docx.py | Word 自检 | 交付前 | **1 = Word 换台机器就走样** |
| make_chart.py | 图表推荐与生成 | 交付时 | — |
| make_report.py | xlsx/docx/HTML 报告 | 交付时 | — |

### 1.4 依赖哲学

**"装上就能用"**——依赖只有 openpyxl。CSV 路径和报告生成连它都不用，纯标准库。不用 pandas、不用绘图库、不用 LibreOffice、不联网、不依赖任何 agent 平台特性（不需要 subagent、不需要沙盒）。

> "体检要在'还没决定用什么工具处理这张表'的时刻就能跑，所以它自己必须几乎没有前置条件。已在屏蔽 pandas/numpy/openpyxl 的解释器里验证过全流程跑通。"

### 1.5 自适应能力

```
skill 会在开工时探测所处环境的能力，选那个环境下的最佳工作流——
能起并行子任务就并行分析，只能串行就串行轮转视角，
跑不了脚本就转成"我告诉你在 Excel 里怎么点"
```

## 二、查询拓展

### 2.1 五个差异化（与"别的工具"的比较）

1. **不是一个分析师，是一个团队**：依次成为领域专家/数据分析师/战略顾问/视觉设计师/前端工程师/质控——角色间打架的地方保留下来（信息量最大的部分）
2. **先看原始单元格，再动 pandas**：`pd.read_excel()` 读进来的那一刻，合并单元格/单元格格式/原始类型就全丢了；体检脚本先用 openpyxl 读原始格子
3. **把"合计"行当成免费的校验和**：所有工具都把汇总行当噪音过滤掉，但那是原表作者的真值——拿清洗后的明细自己求和去对，对不上就报出来（对应 ICAEW《Financial Modelling Code》2024 的 master check）
4. **默认给五数概括，不给均值**：业务数据几乎总是右偏的，`df.describe()` 把 mean/std 放前面——均值在偏态分布下描述的不是任何一个真实对象。改用 Tukey 抗差统计：min/Q1/中位数/Q3/max + IQR
5. **机器判事实，人判品味**：行数对不对、总和守不守恒、数能不能追回源单元格——机器验死；分析有没有意义——明确交还给人

### 2.2 六个分析陷阱（scan_traps.py）

| 陷阱 | 会让你得出什么错误结论 |
|------|------------------------|
| 辛普森悖论 | 分组内都是 A 好，合起来变成 B 好 |
| 幽灵分组 | "张伟"和"张伟 "被算成两个人 |
| 小基数 | 样本 3 个的组报"增长 200%"，其实是多了 4 个 |
| 时间断点 | 缺失月份不会报错，但趋势线撒谎 |
| 双峰分布 | 混了两群对象，均值描述的是一个不存在的人 |
| 极端集中 | 前 20% 贡献 80%，均值没有代表性 |

### 2.3 图表诚实性原则（Cleveland & McGill 1984）

感知精度阶梯：位置(共同基线) > 位置(非对齐) > 长度/角度 > 面积 > 体积/曲率 > 明暗/色饱和

> "位置判断比长度准 1.4-2.5 倍，比角度准 1.96 倍"

**规则**：类别超过 3 个拒绝生成饼图（饼图靠角度+面积编码，在精度阶梯上排第 3、4）；柱形轴强制从 0；折线不强制从 0；整刻度；不完整末期画虚线；色盲友好色板。

### 2.4 理论基础与出处

| 来源 | 用在哪 |
|------|--------|
| Hadley Wickham, Tidy Data | 清洗的目标形态与五类脏数据分类 |
| John Tukey, EDA (1977) | 五数概括/抗差统计/箱线图 |
| ICAEW, Financial Modelling Code (2024) | master check/可追溯引用 |
| Cleveland & McGill (1984) | 视觉编码感知精度阶梯 |
| Gene Zelazny, Say It With Charts | 先定信息再选图 |
| Barbara Minto, 金字塔原理 | 结论先行/MECE/SCQA |
| Ronny Kohavi et al. | Twyman's Law/常见陷阱 |
| Cassie Kozyrkov | 探索与推断的分工红线 |
| Panko (1998), EuSpRIG | 电子表格错误的实证规模（86% 含错误） |

**立论之根**（Andrew Ngai，三届微软 Excel 世界冠军）：

> "如果你用错误的数据训练 AI，它会给你错误的结果——但它还会装出对这些错误结果非常自信的样子。"

### 2.5 与 huashu-design 的关系

幻灯片/PPT 交给 [huashu-design](https://github.com/alchaincyf/huashu-design)。huashu-excel 只出分析内容和图表；演示文稿是另一个专业（"硬做出来的结果是'一眼看得出是自动生成的'"）。

## 三、归纳总结

### 3.1 核心哲学

```
数据 → 体检（openpyxl 原始格子）→ 清洗（可追溯）
    → 对齐（带着摸底问用户）→ 分析（扫陷阱）
    → 对账（master check，与合计行交叉验证）
    → 交付（口径随数字）→ 验图（渲染自检）
    → 质控（独立 agent 重算，拆台）
```

**每一步都有可执行的脚本，不是抽象原则**——这就是 skill 工程化的最高形态。

### 3.2 三句话核心

1. **AI 算错不会报错**——用 master check 和独立复核对抗
2. **体检在选工具之前就跑**——零依赖，纯标准库
3. **退出码验的是"算得对"，不是"结论对"**——第 8 步质控抓的是结论层

### 趋势 1：跨 Agent 通用 Skill 将成为工具接口的标准形态

### 趋势 2：AI 数据分析的瓶颈从"能不能算"转向"能不能被追溯"

> 依据：立论案例（+161% 误差，零报错）+ Andrew Ngai 立论 + Twyman's Law + ICAEW master check——业界已共识：AI 的"自信幻觉"在数据分析域比代码域更危险，因为错误的结果看起来和正确的结果完全一样。

## 五、关联分析

### 5.1 与本机数据分析链路的关联

本机已有的数据能力：
- `execute_code` 工具：跑 Python 脚本，但无内置对账/验图/质控
- `xlsx-generator` skill：生成 XLSX，但缺"对账"意识
- `error-case-library` skill：记录错误，但没系统化"数据陷阱扫描"

huashu-excel 的**七个脚本**恰好补了这些缺口——尤其是 verify_numbers.py（master check）和质控第 8 步（独立 agent 重算），本机没有任何等价物。

### 5.2 与 skill-stress-test 的关联

本文第 8 步"另派一个没参与创作的 agent 从原始数据重算"——**就是 skill-stress-test 在数据分析域的具体实现**。用 subagent 独立重算来拆台，是"执行/评判分离"（Harness Engineering 准则 2）的标准应用。

### 5.3 与 note-content-completeness 的对照

本文的"每跑完一个脚本，必答三问再往下走：我看到了什么/这意味着什么/下一步要查什么"——与笔记 7 模块自检、note-content-completeness 的密度门禁同构。都是"产出不是终点，追问产出才是"。

### 5.4 与 experience-bank 的关联

本文的七个脚本每个都有明确"什么时候用"的判定——可直接作为 experience-bank 卡片沉淀：

- "AI 算错不会报错 → master check 必跑"
- "饼图>3 类=拒绝 → Cleveland-McGill 依据"
- "体检在选工具前 → 零依赖哲学"

## 六、拓展应用推荐

### 6.1 安装路线

```bash
# 跨 agent 通用安装
npx skills add alchaincyf/huashu-excel

# 或手动 clone 到 ~/.agents/skills/huashu-excel/
git clone https://github.com/alchaincyf/huashu-excel ~/.agents/skills/huashu-excel
```

本机可直接调用：

```
"帮我分析下这份 Excel" → 走完整八步
"这个数怎么对不上" → 体检 + 对账
"这个表有多少行脏的" → 只跑 profile_table.py
"这个数靠谱吗" → 对账 + 独立复核
```

### 6.2 可借鉴的方法论（沉淀到本机 skill）

1. **master check 思想**：任何数据分析后，拿中间结果对源数据里的已知汇总——不通过绝不交付
2. **验图退出码**：verify_visual.py 的越界/重叠/遮挡/双轴检查，可进 note-dual-format 的 HTML 自检环节
3. **自适应能力探测**：开工时先探测环境能力再选工作流——可进 skill 通用模式
4. **第 3 步对齐**：澄清放在看懂数据之后，而不是最开始——改进本机数据分析 skill 的用户交互模式
