## 一、内容整理

### 核心定义

**OAG = Ontology-Augmented Generation（本体增强生成）**：在 RAG 的向量检索之上，增加一层**本体（Ontology）语义内核**，把企业中的"对象—关系—行为"显式建模，让 AI 从"知道"升级为"推理并做到"。

> 一句话区分: **RAG 让 AI 从闭卷变开卷，OAG 让 AI 从开卷变上岗。**

### OAG 三要素（架构骨架）

| 要素 | 中文 | 作用 |
|------|------|------|
| **Objects（对象）** | 业务实体 | 带属性/行为/历史/约束的活数据，不再是冰冷的表行列 |
| **Links（链接）** | 关系拓扑 | 对象间显式关系构成知识图谱，支持多跳推理 |
| **Actions（动作）** | 可执行操作 | 预定义业务流程：明确输入/前置条件/执行效果 |

三要素结合 → AI 从"被动响应"转向"主动决策"，具备多跳推理 + 合规校验 + 业务回写。

### OAG 三层架构（PolarDB-PG 本体引擎为例）

| 层 | 定义什么 | 举例 |
|----|---------|------|
| 语义层 | 业务世界的"名词" | 对象/属性/关系 |
| 数据流转层 | 业务世界的"动词" | 操作/动作/流程 |
| 智能决策层 | 规则/权限/Agent/模型绑定 | Agent 权限、决策规则 |

### RAG vs OAG 核心区别

| 维度 | 传统 RAG | OAG |
|------|---------|-----|
| 检索内容 | 零散文本片段 | 结构化实体及关系网络 |
| 上下文质量 | 噪声大、关联弱 | 精准、完整、可追溯 |
| 推理能力 | 无 | 多跳推理 |
| 业务理解 | 仅文本语义 | 对象 + 关系 + 规则 |
| 执行能力 | 只读 | 可执行（Actions） |
| 定位 | "资料库" | "商业大脑" |

### 已落地玩家（原文照录）

| 公司 | 落地方案 |
|------|---------|
| Palantir | OAG 定位"以决策为中心"，LLM 通过本体访问确定性逻辑工具（预测模型/优化器）执行 Actions 闭环 |
| PolarDB-PG（阿里云） | 数据库内嵌 Ontology 引擎，覆盖供应链/运维/营销 |

| 迈富时 | OntologyForce OS，覆盖汽车/零售/工业设备/医药/冷链 |

## 二、归纳总结

### RAG 的三大局限（原文金句）

1. **检索的是"碎片"，不是"关系"**——知道订单A延迟、知道仓库B有库存，但不知道二者该不该配对
2. **只有"只读"，没有"执行"**——能告诉你"该怎么做"，但不会帮你做
3. **没有"业务逻辑"**——"客户"在 CRM/ERP/财务系统指代不同实体，RAG 消除不了语义歧义

### OAG 的范式跨越（原文离散制造案例复述）

"压铸机#05 异常停机"报警 → OAG 本体驱动的智能体同时做四件事:
a. **精准定位**：锁定该设备正在生产的全部订单，识别关键客户 A 的紧急交付件
b. **智能调度**：自动派单给擅长此设备且当前可用的工程师，同步推送故障历史+所需备件
c. **全局优化**：动态调整排程，将该设备后续任务分配至其他可用机台，重算整体交付时间
d. **主动协同**：通知生产班长调整班次，向客户发送延迟预警 + 新交付承诺

## 三、趋势判断

1. **企业 AI 焦点从"问答"转向"决策+执行"**：2026 年 RAG 市场进入瓶颈期（员工得到 3 份文档自己翻），OAG 承接下一波落地预算
2. **"本体（Ontology）"成为企业 AI 新基建**：不再依赖 LLM 泛理解，而是把业务逻辑显式编码进知识图谱
3. **共享本体作为多 Agent 认知主干**：社区数据显示企业级多 Agent 部署可减少 3-5 倍 Agent 间冲突
4. **"语义层→决策层"三层架构会成为标准范式**（参考 PolarDB-PG），数据库层直接承载 Ontology 引擎

## 四、拓展应用

### 飞机设计企业如何落地 OAG — 4 个完整案例

> 用户领域背景: 飞机设计企业（适航 CCAR/构型管理 MC0-MC9/EBOM/FMEA）
> 每个案例均含 OAG 三要素（Objects/Links/Actions）+ 落地路径

---

#### 案例 1：构型管理 OAG —— 从"找型号资料"到"自动出构型变更方案"

**痛点**：型号资料体系按 MC0-MC9 层级管理，RAG 检索只能返回相关文档片段，**无法判断 A 构型变更是否影响 B 构型的派生关系**。

| OAG 要素 | 内容 |
|---------|------|
| **Objects** | 型号(Platform) / 系列(Series) / 构型(Configuration) / 零件(Part) / 图纸(Drawing) / 工程更改指令(ECO) / 适航审查项 |
| **Links** | 构型∈系列, 系列∈型号, 零件→图纸, ECO→影响零件集合, 构型→关联FMEA, 构型→适航项目集 |
| **Actions** | `提出ECO` / `影响域分析` / `自动派生新构型` / `触发适航审查` / `更新EBOM` / `回写PDM` |

**落地场景**：
> "某型机机翼加强框材料从 3003 铝改为 2024 铝" →
> OAG 多跳推理: 加强框零件 → 影响构型集 → 关联 FMEA 重新评分 → 涉及适航项目集(FAA 25.605 结构强度) → 自动生成 ECO 草案 + 影响域报告 → 触发构型管理工程师审批节点
> 输出: **一份可直接流转的构型变更包**，而非"3 份相关图纸清单"。

---

#### 案例 2：FMEA 本体增强 —— 从"查故障模式"到"自动更新 RPN 并推送管控"

**痛点**：RAG 查到某系统历史 FMEA 条目，但**不会判断新设计变更是否引入新故障模式、是否会级联到下游系统**。

| OAG 要素 | 内容 |
|---------|------|
| **Objects** | 系统(System) / 子系统 / 部件 / 故障模式 / 故障效应 / 故障原因 / 探测方法 / RPN 评分 |
| **Links** | 部件→所属子系统, 故障模式→引发效应集, 效应→影响航路阶段(起飞/巡航/降落), 故障原因→关联工艺/材料 |
| **Actions** | `重算RPN` / `触发严重度升级` / `生成管控项` / `推送质量工程师` / `关联设计裕度复核` |

**落地场景**：
> "液压系统新增一个单向阀" →
> OAG 推理: 单向阀失效模式(卡开/卡关) → 效应传播到起落架收放失效(起飞阶段禁用) → 严重度=9 → RPN 超过阈值(100) → 自动生成管控项(增加冗余阀+测试程序) → 推送系统工程师审批 → 回写质量管理系统
> 输出: **一份带管控措施闭环的 FMEA 更新单**。

---

#### 案例 3：适航符合性 OAG —— 从"翻条款"到"自动匹配验证方案"

**痛点**：CCAR-25 共 30+ 章节，设计师问"某型机某系统是否符合"，RAG 只能返回条款原文，**不知道本型号已在哪些构型/机队完成过符合性验证**。

| OAG 要素 | 内容 |
|---------|------|
| **Objects** | 适航条款(Regulation) / 符合性验证方法(CoM) / 验证数据(试飞/计算/检查) / 型号合格证(TypeCert) / 构型 |
| **Links** | 条款→适用构型集, 条款→CoM方法, 验证数据→支撑条款, 构型→已验证条款集 |
| **Actions** | `条款适用性分析` / `验证数据匹配` / `生成符合性矩阵` / `识别验证缺口` / `推送适航工程师` |

**落地场景**：
> "某构型机翼油箱防火设计是否满足 CCAR-25.953" →
> OAG 推理: 条款 → 适用构型集(该构型∈集) → 匹配 CoM(地面检查+试验数据) → 检索已有验证数据(发现某型机已验证，构型差异在蒙皮厚度) → 判定"差异可接受"或"需补充试验" → 生成符合性矩阵条目
> 输出: **可直接进入适航审查包的条款符合性结论**。

---

#### 案例 4：多学科设计优化 OAG —— 从"查仿真报告"到"自动触发参数敏感性分析"

**痛点**：气动/结构/系统/重量多学科数据分散，RAG 查到某次仿真结果但**不会联动多物理场重算**。

| OAG 要素 | 内容 |
|---------|------|
| **Objects** | 设计变量 / 响应量 / 物理场(气动/结构/刚度/疲劳) / 约束 / 优化目标 |
| **Links** | 设计变量→影响响应量集, 物理场→使用求解器(CATIA/Nastran/CFD), 约束→关联适航条款 |
| **Actions** | `触发敏感性分析` / `调度仿真求解器` / `生成Pareto前沿` / `推送多学科协调会议` |

**落地场景**：
> "某型机垂尾面积减小 5%" →
> OAG 推理: 垂尾面积↓ → 影响方向静稳定性(需重跑气动) + 尾撑弯矩(需重跑结构) + 重量减少(需重算平衡) → 并发触发 3 个求解器 → 汇总结果 → 判定是否进入 Pareto 最优面 → 推送设计评审节点
> 输出: **一份多学科影响评估报告，而非"3 份相关仿真文件"**。

## 五、指南分析

### 飞机设计企业开展 OAG 应用落地的 6 步路径

| 步骤 | 行动 | 参考实践 |
|------|------|---------|
| ① 选型场景 | 从构型管理/FMEA/适航符合性/多学科的**高痛点闭环场景**切入 | 选一个 RAG 已经"不够用"的具体场景 |
| ② 本体建模 | 梳理目标场景的 Objects/Links/Actions 三要素，用 RDF/OWL 或图数据库编码 | 参考 PolarDB-PG 三层架构 |
| ③ 构建语义层 | 在 PDM/CATIA/EBS 之上建立统一语义层，让"某零件"在所有系统指代同一实体 | 解决跨系统语义歧义 |
| ④ 接入 Agent | 把 LLM 作为推理引擎，通过本体访问确定性工具（CAD 内核/仿真求解器/ECM 系统） | Palantir Actions 模式 |
| ⑤ 闭环验证 | 从"AI 输出建议"→"人工审批"→"回写业务系统"形成闭环 | 参照浪潮海岳全链路 |
| ⑥ 横向扩展 | 一个场景跑通后，复用本体骨架扩展到相邻领域 | 构型管理本体→FMEA 本体→适航本体 |

### 推荐工具选型

| 层次 | 选项 |
|------|------|
| 本体编码 | RDF + OWL / 知识图谱(Neo4j / Alibaba Graph) |
| Ontology 引擎 | PolarDB-PG(内置) / 浪潮海岳本体孪生 / 自建图数据库 |
| Agent 框架 | LangGraph / Palantir AIP 思路 / 自建多 Agent |
| LLM | 领域化微调(可选) + 通用模型 |
| 回写通道 | CATIA CAA / PDM API / EBS 接口 |

## 六、关联分析

### 与"检索策略才是 alpha"的同构

- RAG 时代: **检索策略** = 向量切分/重排/混合召回 → alpha 在"找到"
- OAG 时代: **本体策略** = 对象定义/关系编码/动作封装 → alpha 在"理解并做到"
- 两者不冲突，OAG 是 RAG 的**超集+执行层**——RAG 解决"开卷"，OAG 解决"上岗"

### 与《飞机设计企业 AI 知识库白皮书》的互印证

上一份白皮书聚焦"知识库建设"（数据治理 + 检索 + 向量库），本质还是 RAG 范式。OAG 是**知识库的自然演进**：把静态知识库升级为动态决策系统。

### 与《Agent ≈ 大模型 + Harness》的互印证

OAG 的三要素（Objects/Links/Actions）**正是 Harness 在业务层面的具体化**——语义层是静态 Harness，Actions 是动态工具，本体是共享的上下文骨架。
