一、内容整理

1.1 对话主线：1G 领域知识如何选基座〔千问原文〕

问题设定：拥有 1G 领域知识数据（远超一般几千条 QA 对），微调一个垂域小模型。1G 数据的意义：模型不仅能学会"怎么说话"，还能真正"掌握专业知识"。

首选：Qwen3-8B（Instruct 或 Base）
- 中文语义理解、产业专业术语、非标表达领先
- 8B 是微调"甜点尺寸"——效果与成本平衡，单张 3090/4090 即可
- Instruct 版：已有对话能力，注入知识事半功倍（做行业顾问/客服）
- Base 版：白纸，适合二次预训练（CPT）从头注入风格独特的领域知识

备选：GLM-5（逻辑推理/代码/Agent 专精）、Yi-Large 2（34B 稠密，长文档深度生成上限高）
英文/出海：Llama 4 Maverick（生态最强）、Mistral Large 2（GDPR 合规 + MoE 推理效率）

1.2 三条微调策略建议〔千问原文〕

  1. 数据质量大于数量：1G 已足够庞大，微调前必须去污除杂；1000 条精心设计的优质问答远胜 10 万条粗糙爬虫数据。
  2. 防范灾难性遗忘：混入 5-10% 通用高质量对话，维持通用能力。
  3. 优先 LoRA/QLoRA：参数高效微调大幅降低显存需求。

1.3 Unsloth LoRA 代码框架要点〔千问原文〕

加载:  Qwen3-8B + load_in_4bit=True(QLoRA) + unsloth梯度检查点
注入:  r=32, alpha=32, dropout=0.05
       target_modules = q/k/v/o_proj + gate/up/down_proj (7模块全注入)
数据:  Alpaca 格式 (### 指令/### 输入/### 回答)
训练:  batch=2 × grad_accum=4, lr=2e-4, adamw_8bit,
       测试期 max_steps=30, 正式 num_train_epochs=3~5
保存:  save_pretrained_merged("merged_16bit")  ← 推荐方式A
       或仅存 LoRA Adapter(方式B, 体积小适合热加载)

调优建议：OOM 时保 4bit、batch 降至 1、max_seq_length 4096→2048；1G 大数据配 3-5 epoch + 线性/余弦衰减；务必做好 Label Mask（仅对回复部分计算 loss，防模型过度学习指令模板）。

1.4 海光 DCU 64G 适配方案〔千问原文〕

核心认知："环境大于代码"。海光 DCU（K100_AI 64G）基于 AMD CDNA 架构，软件栈是 DTK（DCU Toolkit）而非原生 CUDA。

  1. 环境：Ubuntu 22.04 + 海光官方 Docker 镜像（dtk2604 标识）；严禁社区公版库；DTK 版本与内核驱动严格对齐（DTK 26.x ↔ ROCm 6.x）；ROCM_PATH=/opt/dtk/
  2. 代码迁移：移除 Unsloth（NVIDIA 专用加速库，DCU 不可用）→ 标准 transformers+peft+trl；.to("cuda") 无需修改（DTK 复用 cuda 接口）；fp16→bf16（国产平台稳定性更佳）
  3. 硬件调优：numactl 绑 NUMA 节点；64G 显存充裕，batch 提至 4-8 + grad_accum=2；算子崩溃查 CUDA Graph 特性，必要时 --enforce-eager
  4. 流程铁律：先 100 条数据 30 steps 冒烟，确认无报错再全量

1.5 Qwen3-VL-8B 能否代替 Qwen3-8B：强烈不建议〔千问原文〕

四条理由：
1. 定位不同：Base 是注入知识的"白纸"（Causal LM）；VL-Instruct 是含 ViT 视觉编码器 + 跨模态对齐层的"成品助手"，已做过大量 SFT+DPO
2. 资源浪费：视觉编码器显存翻倍，1G 纯文本数据下 Vision 参数全部闲置
3. 代码不兼容：纯文本 LoRA 代码套 VL 要么报错，要么需重写参数过滤逻辑（target_modules 避开视觉层）
4. 知识冲突：纯文本微调破坏 VL 固有的多模态指令格式——既丢看图能力，纯文本能力也可能降

何时用 VL：仅当 1G 数据含大量图文对（说明书截图+文字/X光片+诊断/图表+分析）且需要看图/文档解析能力时。

收尾判断（原文最后一问）：有现成问答对 → Instruct 版更省事；纯文档 → Base 版 CPT 效果更好。

二、查询拓展

2.1 QLoRA：4bit 量化训练的原理与显存账

Unsloth 框架的 load_in_4bit=True 是 QLoRA（Dettmers 2023）：把冻结的基座权重量化到 4bit（NF4 NormalFloat）存储，前向时反量化到 BF16 计算，只训练 LoRA 低秩矩阵。显存账：8B 模型 FP16 需 ~16GB，QLoRA 4bit 降到 ~6GB（权重）+ LoRA/优化器/激活 ~2-3GB ≈ 单卡 3090（24GB）舒适运行，甚至 16GB 卡可跑（batch=1+短序列）。这正是千问说"8B 是甜点尺寸"的算术基础。代价：训练速度比 FP16 LoRA 慢 20-30%（反量化开销），但对个人微调完全可接受。

2.2 Unsloth 的真实现状〔核实〕

千问原文称"Unsloth 是专为 NVIDIA 显卡优化的底层加速库，在海光 DCU 上无法使用"。核实结果：论据已过时，结论仍正确——Unsloth 2026 年已官方支持 AMD GPU（unsloth.ai/docs/get-started/install/amd，基于 ROCm），还发布了 Radeon 2x 加速的新闻。但海光 DTK 是 ROCm 的深度定制分支（不同的 HIP runtime/算子库版本），Unsloth 官方支持矩阵不含 DCU，社区也无可用的安装路径。因此 DCU 路线仍需回退标准 transformers+peft+trl——修正的是理由（"只支持 NVIDIA"→"不支持 DTK 定制分支"），不是结论。

2.3 海光 DCU 生态实况〔核实〕

DCU 大模型落地的社区资源已相当成熟：FlyAIBox/dcu-in-action（国产加速卡海光 DCU 实战集：大模型训练/微调/推理）、知乎系列（Qwen 在海光 DCU/DTK 上的部署实现）、博客园（海光 K100 DCU vLLM 推理环境构建）。共同验证了千问方案的关键点：官方 Docker 镜像是环境搭建的正解、torch.cuda 接口兼容、bf16 优先。K100 E4x16 64GB 双宽卡的真实测评也已在社区流通。DCU 微调的坑集中在环境版本对齐（DTK↔驱动↔PyTorch 适配版），不在代码逻辑——印证"环境大于代码"。

2.4 CPT vs SFT 的分野与 token 账

千问原文的"Instruct 注入知识 / Base 二次预训练"二分法背后是 token 量级差异：1G 纯文本 ≈ 2.5-3 亿 token。若走 Base+CPT，8B 模型见过一遍就要 0.25-0.3 亿 token/GB × 训练吞吐（单卡约 3-5K token/s）≈ 单卡 16-24 小时/epoch——可行但需要耐心与算力规划；若走 Instruct+SFT（先把文档转成 QA 对），数据量缩减 10-50 倍（10-30 万条），训练时间缩短到小时级。单卡用户的现实选择是后者：用 Qwen3-8B 自己把文档蒸馏成 QA 对（self-instruct 蒸馏），再 SFT——这是"穷人版 CPT"。

2.5 灾难性遗忘的机理与混数据的数学

微调时模型参数朝领域数据分布移动，若学习率过大/数据单一，会覆盖预训练学到的通用表征。混入 5-10% 通用数据的作用是正则化：每批次都有梯度信号把参数拉回通用流形。更精细的做法（千问未提）：EWC（弹性权重巩固，对重要参数加正则罚）、LoRA 本身的低秩约束天然限制漂移幅度（ΔW 秩 ≤ r）——这也是 LoRA 相对全量微调"天然防遗忘"的隐藏优势。

四、趋势判断

趋势1：8B 正在成为"个人垂域微调的标准尺寸"

依据：千问"甜点尺寸"判断 + QLoRA 4bit 后单卡 24GB 可跑 + Qwen3/GLM/Yi 全系在 7-9B 档密集布防。驱动力是硬件门槛：8B@4bit ≈ 6GB 权重，正好卡进消费级显卡；再往上的 14B+ 需要专业卡，再往下的 2B 级知识容量不够装 1G 语料。

趋势2：国产算力微调生态正在"镜像复刻"主流生态

依据：DCU 有官方 Docker 镜像 + 适配版 PyTorch + dcu-in-action 实战集——与 CUDA 生态的 unsloth/llamafactory 教程体系形成镜像。差距在工具层创新（Unsloth 类加速库、bitsandbytes 类量化训练库），不在基础层。信创场景下"标准栈 + 官方镜像"的路线会越来越顺。

趋势3：文档→QA 对的蒸馏预处理将成为垂域微调的标准前置步骤

依据：千问对话收尾的判断（有 QA 用 Instruct / 纯文档用 Base）隐含一个痛点——多数领域资产是文档不是 QA 对。用大模型把文档蒸馏成 QA 对（self-instruct）再 SFT，比直接 CPT 便宜一个量级且效果相当，正在成为事实标准（ UltraData-SFT 等数据集就是这条路线的产物）。

趋势4：多模态与纯文本基座的选型纪律正在形成共识

依据：千问对"VL 代替 Base"的四条反对理由本质是架构经济学：视觉参数在纯文本任务中是纯浪费（显存+算力+代码复杂度）。反过来说，VL 的正确微调姿势是图文对数据 + 冻结视觉编码器只调语言侧——两种基座的微调方法论正在分家。
