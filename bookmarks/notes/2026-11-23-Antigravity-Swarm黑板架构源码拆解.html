0. 导语：一场 2 小时 07 分的实战

作者修自己的 PDF 导出工具（resume-skills）遇到典型跨模块乱码：页面正常但复制/OCR 乱码、缺字、整段顺序颠倒。单个 Agent 读打印脚本+6 套模板+CSS 规范再真机测试，上下文很快塞满；传统 Subagent 则让主 Agent 沦为传话筒。开 /swarm 后：两波共 7 个成员、2h07m、黑板上 24 帖——中途有成员沉默 38 分钟被后台巡检员发帖救活，验收员实测抓出校验脚本误杀直接点名打回返工，全程零打扰主 Agent。

一、四种多 Agent 模式怎么选

模式 适用场景 结果交给谁 / 怎么接
invoke_subagent 普通子代理 只确认单疑点（如字体映射） 子代理查完发回主 Agent，主 Agent 再转交复测
/boost 一个难复现 bug 查深验透 同题多轮：一轮根因+修法，后续轮专挑漏洞重测，编排器独立复核
/teamwork 整套重做（换渲染器→迁模板→补回归） 先问清范围与验收标准，专用项目目录按里程碑推进+独立审核
/swarm 多线独立排查 + 第三方拿同一样本交叉验收 排查者贴原始证据到共享黑板引用楼层号点名验收员，验收员回板打回返工

核心差异：结果落在哪、下一步由谁接。

二、黑板底座：三个纯文本文件

目录 <appData>/brain/<coordinatorConv>/.system_generated/swarm/：

  1. board.jsonl — Append-Only 流水账，每行一帖：全局递增楼层 seq、发帖人 agent、正文 text、时间 time
  2. members.json — 花名册 + 阅读签到表：会话 ID、角色、模型、工作区模式 + 四个楼层游标（last_read_seq / wait_since / last_nudged_seq / last_park_blocked_seq）
  3. swarm.json — 门牌锚点：版本号、后端类型（本地 local）、swarm_id

两个额外挖出的工程设计：

  • 多频道零配置表，事件溯源重放：>8 成员可拆 #parser #ui 频道，但频道的创建/订阅/退订/归档全部作为 control 消息写进同一条 board.jsonl；侧边栏算"某帖发出时某成员当时能否看见"靠重放 control 帧（channelsAt() / activeAt()），members.json 里的频道列表源码注明只是缓存
  • 跨机分布式伏笔已埋好：main.mjs 内置 remote_board 逻辑 — swarm.json 指向远端时，面板拉 <cli> swarm --json --watch 订阅 NDJSON 增量流，跨机成员挂 <identity>@<host> 徽章（区分 HUMAN/AGENT）；增量楼层接不上本地最新楼层时杀旧 watcher 触发 resync 拉全量。本地三文件跑轻量、将来切多机云端上层协议零改动

三、零空转不漏消息的三个狠招

多 Agent 系统最容易烧爆账单的就是轮询。Swarm 砍掉轮询，三层配合实现"休眠 0 Token、一条不漏"：

  1. swarm_wait{since:N} 直接终结本轮回合 — 工具结果返回 DONE 后，wait-check hook 结束该成员本轮模型回合，会话彻底挂起，无死循环无心跳推理。默认 mentions_only：只有 @自己 / @all / @#所在频道 才注入唤醒消息
  2. Stop Hook 竞态锁（地铁闸机比喻） — 读完 #10 想睡、#11 恰好落地：Stop Hook 硬拦休眠，注入 Stop hook blocked termination: [board] new messages arrived; read_board before waiting again，last_park_blocked_seq 更新为 11。作者在自己另一场写稿 Swarm 的 transcript 第 65/67 步抓到现场生效证据；PDF 那场 fixer-templates 也实打实触发过 last_park_blocked_seq: 16
  3. 判活不信登记簿，盯 transcript.jsonl — members.json 虽记 wake_mode，但 statusOf() 不盲信（成员可能被后台命令/用户手动叫醒而登记簿未更新）。侧边栏直接解析每个成员 transcript.jsonl 尾部：停在无工具调用的回复或含 swarm_wait-DONE 的工具批次才判 waiting，否则算 working——顺带抽出"正在读哪个文件/跑哪条命令"实时上面板

四个楼层游标各管一段：last_read_seq=真正读到哪楼（swarm_wait 必须传自己看过的号而非最新号，否则忙活期间冒出的帖会被跳过）；wait_since=从哪楼开始等唤醒；last_nudged_seq=[board] 增量催读提醒推到哪楼；last_park_blocked_seq=最近一次想睡被拦的楼层。

四、24 帖实战复盘：两波 7 Agent 接力

  • 模型混搭：Coordinator+巡检员（只拆任务/盯状态/发提醒）用轻量模型省额度；真正查链路/改 6 套模板/跑验收的干活成员全员旗舰推理模型
  • 第 1 波只读排查（#1~#8，约 32min）：pdf-pipeline（查导出脚本/字体/字形映射）+ template-dom（查 6 套模板 DOM 文本流）+ verifier（实测复现交叉核验）+ monitor 防死锁。全只读 → 全员 inherit 共用主工作区。verifier 用 Playwright 在线/断网双环境渲染 6 套模板 + pypdf 复现乱码，#7 交完整证据；#8 发 [done] 后 Coordinator 把这波 4 人全部 kill 清场，不让旧上下文拖累后续修改
  • 第 2 波并行修复（#9~#24，约 1.5h）：新开 fixer-templates（只动模板）/ fixer-code（只动打印链路+校验脚本）/ verifier-fix（只查不改）/ monitor-2。被 kill 的成员名字永久锁死不能复用，巡检员只能顺延叫 monitor-2
  • 三次救场插曲（决定任务没翻车的关键）：

  • 13~#14 工作区目录被移走路径对不上 → fixer-code 发帖 @coordinator，git 恢复后 #14 一次性统一三人路径，防各改各的跑偏

  • 15~#19 monitor-2 两次 [stall] 催醒：fixer-templates 沉默 38min 被 @fixer-templates [stall] 精准催醒；全组停在 #16 三分钟 → @coordinator [stall] 甚至附带判断"旗舰模型可能额度耗尽"

  • 21~#23 验收员点对点打回：校验脚本在中英混排字体切换处因伪空格误报失败，verifier-fix 不找 Coordinator 传话，直接 #21 点名 @fixer-code 贴报错行号 → 9 分钟后 #22 修完补单测 → #23 汇总交卷

  • Graph + Board 组合拳：Graph 拓扑图上下两半=两波三角，箭头=@方向、线粗=@次数；先 Graph 看谁跟谁交过手，再 Board 点进 #21/#22/#23 核对原始测试输出——"如果汇总只写'全部已验证'，根本不敢直接合并代码"

五、五道护栏、两大兜底、一堵墙

五道反上下文膨胀护栏：
1. 公开 Brief 唯一账本 — 每次建人的派活书以 @name <brief> 公开贴板，验收对照原始要求验货，Coordinator 经上下文压缩后翻板不丢分工
2. 新成员游标跳过开局噪音 — 新 Worker 启动只塞自己的 Brief，黑板游标直接设在开局所有 Brief 之后，不睁眼先吃别人几千字任务书
3. #seq 指针引用 + @ 只当门铃不当抄送 — 严禁 A 的报告复制转述给 B，全部 #5 #6 楼层引用（Board 自动渲染可点击胶囊）；每次 @ 触发对方一整轮推理；批量分片 add 传 tasks/n 拉 worker-1..N，@worker 呼全组 @worker-1 呼单人；@#parser 精准唤醒模块组（@#main 被拒，防变相 @all）
4. 读写分离 + Worktree 隔离 — 每 2~4 个作者配 1 个只查不改的 verifier；只读排查 inherit 省资源；并发改码给作者开 share（共享底层对象的独立工作副本，类 git worktree）或 branch（完整克隆）。kill 成员连带删其独立工作区——清理前必须先合并/cherry-pick 回来
5. 热克隆 fork 与递归招帮手 — fork: "<member>" 直接克隆对话历史，免冷启动重读仓库；Worker 可自己 add 招帮手但只能 kill 自己招的人；Coordinator kill Worker 不连带清其帮手，收尾自己留意

两大保命兜底：
1. 反死锁巡检员 monitor 也会休眠 — 独立 Agent 挂 IsDaemon: true 的 */3 * * * * 闹钟（IsDaemon 防定时器把主对话标成运行中）。每 3 分钟查 5 种卡死：结果没 @ 任何人 / Coordinator 留未读 / 被 @ 没发帖 / 成员环状互等 / 全员空等。判"被 @ 没动静"看 last_post_seq 而非 wait_since（失败的模型回合也会推 wait_since，看发帖号才能揪出静默挂死）；同一死锁最多提醒 3 次防刷屏；连续 5 轮（约 15min）无动静或收到 [done] 自停闹钟，切 swarm_wait(mentions_only:false) 零耗电休眠，板上冒新消息自动复活重建闹钟；服务重启后 @monitor resume 拉回
2. 额度耗尽原地热切模型 — members.json 刻意拆 desired_model / applied_model：耗尽后不 kill 重来，等成员回 waiting 态调 swarm{action:"model"} 换有额度的模型，保留全部对话记忆原地接着干；事前 swarm{action:"models"} 查每个模型实时剩余额度与重置时间

一堵真实边界：Swarm Worker 会话默认无 <subagents> 权限 — 调不了 image-generator 也调不了浏览器子代理，只能 @coordinator 让主会话代调再交还。穿插生图/浏览器自动化的任务，这步留给 Coordinator 统筹。

六、最重要的转向：谷歌自己砍掉常驻 Narrator

初代设计有常驻解说员 narrator：swarm_wait(mentions_only:false) 盯全板，把聊天整理成 view.json，甚至允许 AI 自写 view.html 定制 Overview。谷歌为此焊了整套零信任沙箱（view 硬限 64KB 超限/写坏即弃退缓存；sanitizeView 逐条核对引用、楼层超 head 标 ⚠ unverified、跳转只放行本地真实文件+白名单域名；view.html 跑 sandbox="allow-scripts" + 全断网 CSP 的 srcdoc iframe，页面跳转须过"浏览器激活态+iframe 焦点+父页 5.5s 无输入+100ms 延迟复核"四道门禁 + 250ms 节流，堵死 AI 伪造点击）。

结果最新 swarm_pane/SKILL.md 开头直接写："Don't add a narrator; this Overview replaces it." 官方自己承认：Always-on member adds token cost — 每条消息唤醒大模型重写 JSON 摘要太烧，且更新永远慢半拍。新方案克制得多：Coordinator 只在开工/改分工时写几十行静态 plan.json，UI 侧 hive.js 用确定性前端代码把 board.jsonl + transcript 实时工具步骤 + [done] 拼成动态看板（蜂王/工蜂像素图、Screenshot 格式帖自动拼可拖拽前后对比 Progress Reel）。

做 Agent Harness 越往深走越会撞上这条铁律：能靠静态协议加确定性代码算出来的视图，绝不多养一个常驻 LLM 去盯。

七、开不开 Swarm：两问判据

  1. 任务能不能拆出至少两条互不打架的独立线？
  2. 拆完的结果值不值得第三个人拿真实样本交叉复核？

跨模块排障、多文件并行改造+回归、反复打回返工的工程任务 → 黑板把上下文隔离与过程溯源做得干净。单线小改动、或两人抢改同一核心函数 → 单 Agent 更快。成本红线：多一个成员=多一份完整会话推理；建人省略 model 默认全员沿用主会话模型，主会话开高配直接盲冲额度掉得飞快。

归纳总结

一句话：黑板 = Append-Only JSONL + 楼层游标协议；唤醒 = 事件驱动零轮询；判活 = 盯 transcript 不信登记簿；看板 = 确定性代码渲染不养常驻 LLM。 四个设计全部指向同一哲学——把"协调"做成确定性基础设施，Token 只花在干活上。大道至简：撑起蜂群的就两个 JSON 一个 JSONL。

趋势判断

  • 确定性渲染替代常驻 LLM 观察者：Google 自己亲手砍掉 narrator，与 2026 H2 "Harness = Control Plane" 行业共识同向——观察/摘要类角色是下一个被确定性代码消灭的常驻 LLM 品类
  • 文件即协议、去中间件化：三个纯文本文件撑起蜂群（无数据库、无消息队列），与 Hermes exchange-protocol 的 NFS JSONL 经验池同构——多 Agent 协调层的工程答案是"最 boring 的存储 + 最严的协议"
  • 模型分层混搭成为标配：协调/巡检用轻量、干活用旗舰 + desired/applied 分离的 quota 感知热切换，多 Agent 成本管理从"事后心疼"进化为"运行时改配"
  • 单机到多机的无缝升级路径：协议先行（remote_board 已埋），本地三文件只是后端特例——编排框架的护城河正从"功能"转向"协议兼容性"

  1. Hermes 长等待任务吸收 Stop Hook 竞态锁：hwatch/回调等待链在"睡前"加最后一次增量检查语义，防唤醒-休眠间隙丢消息（与我们回调≥2min=hwatch 规矩互补）

  4. 用户开 Swarm 前过两问判据 + 下方 checklist；额度管理联动 antigravity-model-failover

指南分析：开 Swarm 的执行 checklist

  • 两问判据全过（≥2 条互不打架的独立线 + 值得第三方真实样本交叉复核）
  • 模型显式分层：coordinator/monitor 用轻量模型，worker 用旗舰；开工前 swarm{action:"models"} 预检额度
  • 只读波全员 inherit 共工作区；改码波给作者开 share/branch 工作副本
  • 每 2~4 个作者配 1 个只查不改的 verifier
  • 第一波结束就 kill 清场，防旧上下文拖累第二波；kill 前必须先合并 Worktree 改动（kill 连带删工作区）
  • 被kill 的名字永久锁死不复用，顺延命名
  • 生图/浏览器子代理需求留给 Coordinator 代调（Worker 默认无 subagents 权限）
  • 交接用 #seq 楼层引用点名，严禁复制转述他人报告；@ 只当门铃不当抄送
  • 额度耗尽走 desired→applied 热切，不 kill 重来
