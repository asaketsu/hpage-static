一、核心发现

发现1：推理引擎三足鼎立格局已定

2026年 LLM 推理引擎市场已形成 vLLM / SGLang / TensorRT-LLM 三强格局，各有明确场景定位：

引擎 优势 最佳场景 冷启动
vLLM 生态最广、社区活跃、模型支持最多 通用生产部署、多模型切换 快
TensorRT-LLM 单请求吞吐最高、NVIDIA硬件深度优化 长期固定模型、NVIDIA独占部署 慢（需编译）
SGLang 共享前缀复用最优、结构化生成一流 多系统提示复用、JSON/代码生成 中等
Ollama 本地开发极简 开发测试、个人使用 快

关键洞察：在 H100 benchmark 中，TensorRT-LLM 在低并发单请求吞吐和 TTFT 最优，但在高并发(100+)时 scaling 不如 vLLM/SGLang。SGLang 在共享前缀命中率高时表现突出，但独特提示基准测试中容易低估。

决策树：
- 通用部署 → vLLM
- NVIDIA固定硬件+稳定模型 → TensorRT-LLM
- 共享前缀复用+结构化输出 → SGLang
- 本地开发 → Ollama

发现2：投机解码进入2.0时代（EAGLE → P-EAGLE）

2026年投机解码的最重大突破是 P-EAGLE（Parallel EAGLE），由 AWS 贡献到 vLLM：

  • EAGLE 3：基于特征级自回归的投机解码，不再需要独立的 draft model
  • P-EAGLE：将 EAGLE 的串行 draft 生成改为并行，消除了"投机越多、draft越慢"的瓶颈
  • vLLM 中使用：--speculative-config '{"method": "eagle3", "model": "amazon/gpt-oss-20b-p-eagle", "num_speculative_tokens": 5, "parallel_drafting": true}'
  • 在 H200 上实现 3.6x 加速（NVIDIA数据）

投机解码方法论演进：
1. 原始方法（Leviathan et al.）：独立小模型 draft + 大模型 verify
2. Medusa：多头 token 预测，去掉独立 draft model
3. EAGLE 1/2/3：特征级自回归 + 动态树 + 训练时 rollout
4. P-EAGLE：并行 draft，突破串行瓶颈

何时使用投机解码：

IF (GPU利用率 < 50%) AND (平均响应长度 > 100 tokens) AND (draft model 能放入显存)
  → 开启投机解码
IF (GPU利用率 > 80%) OR (内存压力大)
  → 先优化批处理，不开投机解码

ICLR 2026 重要论文发现：Multi-Token Prediction with Gated LoRA 被识别为高吞吐场景下最有前途的 draft 架构。

发现3：KV Cache 成为推理优化的核心战场

arXiv:2603.20397 的综述论文将 KV Cache 优化系统归纳为五大方向：

  1. Cache Pruning（剪枝）：移除不重要的 KV 对，基于注意力权重评分
  2. Cache Merging（合并）：将相似的 KV 对合并，减少存储
  3. Cache Quantization（量化）：FP8 KV Cache，vLLM 原生支持 --kv-cache-dtype fp8
  4. Cache Sharing（共享）：前缀缓存（Prefix Caching），多个请求复用相同前缀的 KV
  5. Cache Compression（压缩）：DeepSeek MLA 的低秩投影方法

DeepSeek MLA（Multi-Head Latent Attention）深度解析：

传统 MHA 的 KV Cache 大小：2 × d_h × H × N × B（每个注意力层）
MLA 通过低秩投影将 KV 压缩为潜在向量 c_KV：

c_KV_n = W_DKV × x_n        （压缩：d_model → d_c，d_c << d_h × H）
K = W_UK × C_KV              （解压：d_c → d_h × H）
V = W_UV × C_KV              （解压：d_c → d_h × H）

效果：KV Cache 大小从 2 × d_h × H 降到 d_c + d_R，压缩比 r = d_h×H/d_c。实测 DeepSeek-V3 的 MLA 不仅降低了推理成本，性能反而超过标准 MHA。

TransMLA（NeurIPS 2025）：提出将已有的 GQA 模型（如 LLaMA）迁移到 MLA 的方法，这意味着 MLA 不只限于 DeepSeek 系。

发现4：量化方案的精准选择指南

2026年量化方案的选择已形成清晰的决策矩阵：

方法 精度保持 部署硬件 最佳场景 70B模型显存
AWQ INT4 99%+ NVIDIA GPU (H100/A100/4090) 生产服务、精度优先 ~35GB
GPTQ INT4 97-99% NVIDIA GPU 广泛模型支持 ~35GB
GGUF Q4_K_M 92-98% CPU/Apple Silicon/消费GPU 本地部署、边缘设备 按需
FP8 99%+ H100/B200 专用 最快推理速度 ~70GB
INT8 99.5%+ 大多数GPU 精度敏感场景 ~70GB

2026年共识：AWQ 已成为生产 INT4 的事实标准。Spheron 数据显示 70B 模型 AWQ INT4 在单张 A100 80G 上可达到 ~1800 tok/s，成本约 $0.253/M tokens。

混合精度策略：AWQ 的核心创新是 Activation-aware Weight Quantization — 识别激活中的 outlier 通道，对这些通道保持高精度，其余量化到 4-bit。这避免了直接量化导致的精度崩塌。

发现5：内存带宽是真正的瓶颈

多个来源确认的 2026 核心洞察：在大 batch 推理中，内存带宽（而非计算）是主要瓶颈。

这带来几个重要推论：
1. 投机解码在高吞吐场景仍有价值（之前有争论认为高并发下投机解码无效）
2. KV Cache 优化的 ROI 比模型量化更高（减少内存搬运）
3. 连续批处理（Continuous Batching）的效果取决于 KV Cache 管理效率
4. 前缀缓存（Prefix Caching）在系统提示复用场景效果显著

二、技术栈全景

生产级推理优化组合拳

请求 → 推理引擎
├── PagedAttention（内存效率）
├── 连续批处理（高吞吐）
├── 模型量化（INT4 AWQ）
├── GQA/MLA（减少KV缓存）
├── 投机解码 EAGLE3（加速生成）
├── 前缀缓存（共享系统提示）
├── FP8 KV Cache（缓存压缩）
└── Chunked Prefill（长提示优化）

vLLM 生产级配置示例（2026最佳实践）

vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --max-num-batched-tokens 4096 \
  --quantization awq \
  --kv-cache-dtype fp8 \
  --speculative-config '{
    "method": "eagle3",
    "model": "amazon/gpt-oss-20b-p-eagle",
    "num_speculative_tokens": 5,
    "parallel_drafting": true
  }' \
  --enable-metrics \
  --port 8000

三、与现有工作的关联

1. 与数字孪生低代码平台项目

  • 数字孪生平台需要部署垂域模型做结构设计辅助 → 需要推理优化方案
  • 建议：7B 级垂域模型用 vLLM + AWQ INT4 部署，单 GPU 即可
  • 多用户并发场景开启 Prefix Caching（系统提示复用）

2. 与垂域LLM航空结构设计

  • 垂域模型（如基于 Qwen/Llama 微调的结构设计模型）部署时需要量化
  • 建议：微调后用 AWQ 量化到 INT4，性能损失 <1%，推理成本降低 2-3x
  • 对于需要部署到边缘（工程师工作站）的场景，GGUF Q4_K_M 方案

3. 与 Hermes Agent 系统

  • Hermes 本身需要高效推理 API → 后端用 vLLM
  • Agent 场景特点：多轮对话 + 系统提示固定 → 极适合 Prefix Caching
  • 建议：当前 Ollama 适合开发，生产环境切换到 vLLM

4. 与量化交易系统

  • 金融 LLM 推理需要低延迟 → 投机解码 + FP8
  • 实时行情分析 → Chunked Prefill 减少长上下文处理延迟
