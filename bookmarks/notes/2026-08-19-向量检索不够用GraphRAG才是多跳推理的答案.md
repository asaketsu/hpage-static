## 一、核心概念（内容整理）

向量 RAG 找的是"像不像"，GraphRAG 找的是"有没有关系"。当问题需要**跨文档实体关联**时（A 用 X、B 依赖 A、C 集成 B），向量检索把相关片段拼不起来，必须上知识图谱。

微软开源 GraphRAG（2024-2025 年 RAG 领域最重要突破之一，2 万+ star）四阶段流程：

```
文档 → ① 文本切分 → ② 实体关系抽取 → ③ 社区检测 → ④ 社区摘要
                                              ↓
查询 → 局部检索（实体+关系） 或  全局检索（社区摘要）
```

判断标准一句话：用户常问"A 和 B 什么关系""整体情况如何""X 影响了哪些东西"，向量 RAG 搞不定 → 上 GraphRAG；只问"退货流程是什么"这种单文档可回答 → 向量 RAG 够了，别折腾。

## 二、技术要点（指南分析）

### 2.1 GraphRAG vs 向量 RAG（原文对比表照录）

| 维度 | 向量 RAG | GraphRAG |
|------|---------|----------|
| 擅长问题 | "X 是什么""怎么做 X" | "X 和 Y 什么关系""整体趋势是什么" |
| 检索粒度 | 文本片段（chunk） | 实体+关系+社区摘要 |
| 全局性问题 | 差（只能找局部相似片段） | 强（图结构天然支持全局推理） |
| 多跳推理 | 靠迭代检索，容易丢线索 | 图遍历一次到位 |
| 建索引成本 | 低（切分+Embedding） | 高（LLM 抽取实体关系） |
| 索引耗时 | 500 篇约 5 分钟 | 500 篇约 30-60 分钟 |
| 索引成本 | Embedding API 费用 | LLM 调用费用（抽取很费 token） |
| 查询延迟 | 200-500ms | 500-2000ms（图遍历+社区摘要） |

### 2.2 四阶段关键设计

**阶段一：文本切分（追求实体完整性，非均匀）**

向量 RAG 追求 chunk 均匀（200-500 字符）；GraphRAG 追求**实体完整性**——一个 chunk 包含完整实体描述和关系。微软默认 **1200 token（约 1800 字符）**，比向量 RAG 大很多。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
def graph_rag_chunking(documents, chunk_size=1200, chunk_overlap=100):
    """GraphRAG 专用切分：chunk 比向量 RAG 大，保证实体完整"""
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap,
        separators=["\n\n", "\n", "。", "；", "，", " "],
    )
    return splitter.split_documents(documents)
```

⚠️ **坑 1：chunk 太大导致抽取遗漏**——作者用 2400 字符时 LLM 只抽前半部分关系，后半部分实体被忽略（长文本注意力衰减）。**1200 token 是经验值，别改大。**

**阶段二：实体和关系抽取（最核心、成本最高）**

用 LLM 从每个 chunk 抽实体（PERSON/ORGANIZATION/PRODUCT/TECHNOLOGY/CONCEPT/LOCATION）+ 关系（是 CEO/依赖/包含）+ 强度 0-1。Pydantic 结构化输出约束格式。

⚠️ **坑 2：实体名称不统一**——同一实体抽成多个名字 → 图里全是孤立节点。必须加**实体合并层**（归一化 + 别名表；Java 类比：三个系统里同一个用户按手机号归一化）。不合并 = 图白建。

**阶段三：社区检测（社区 = 紧密关联的实体组）**

500 文档可能抽出上万实体/几万关系，直接检索效率低。用 **Leiden 算法**（比 Louvain 更精确）把图分成社区——"产品线 A 相关全部人/技术" = 一个社区。

```python

for e in entities: graph.add_node(e.name, type=e.type, description=e.description)
for r in relationships:  # 已有边取最大权重
    ...
communities = nx.community.greedy_modularity_communities(graph, weight='weight')
```

⚠️ **坑 3：社区粒度不好控制**——太大丢细节，太小没信息量。微软用**分层社区**：先大社区、再在大社区里检测子社区，查询按问题粒度选层级。

**阶段四：社区摘要（支持全局检索）**

每个社区生成 LLM 摘要作为"这一片的浓缩知识"，全局查询时 Map-Reduce 汇总。

⚠️ **坑 4：社区摘要成本高**——100 个社区 = 100 次 LLM 调用。**小社区用规则摘要，大社区才用 LLM。**

### 2.3 查询阶段：局部 vs 全局

| 模式 | 机制 | 适合问题 |
|------|------|---------|
| **局部检索** | 向量检索找起始实体 → 图遍历找关联实体关系 | "A 和 B 什么关系""X 影响了什么" |
| **全局检索** | Map-Reduce 社区摘要，多社区并行汇总 | "整体趋势""所有产品线依赖" |

智能路由：LLM 判断问题类型（local/global）自动选择。

### 2.4 GraphRAG 成本优化（原文表照录）

| 优化手段 | 节省比例 | 代价 |
|---------|---------|------|
| 实体抽取用小模型（GPT-4o-mini） | 省 70% | 抽取质量下降约 15% |
| 小社区用规则摘要不用 LLM | 省 30% | 小社区摘要质量略差 |
| 增量索引（只处理新文档） | 省 80%+ | 需要维护索引版本 |
| 实体抽取缓存（相同 chunk 不重复） | 省 50% | 需要 hash 去重 |
| 批量 API 调用（OpenAI Batch API） | 省 50% | 延迟增加 24 小时 |

**作者建议**：开发阶段用 GPT-4o-mini 验证效果，确认后再用 GPT-4o 重建索引；或本地模型（Qwen-14B）零 API 成本。

### 2.5 完整踩坑清单（原文表照录）

| 坑 | 症状 | 解决 |
|----|------|------|
| chunk 太大 | LLM 抽取后半部分实体被忽略 | 默认 1200 token 别改大 |
| 实体名称不统一 | 图里全是孤立节点 | 加实体合并层 |
| 社区粒度不好 | 太大丢细节，太小没信息量 | 分层社区检测 |
| 社区摘要成本高 | 100 社区 100 次 LLM 调用 | 小社区规则摘要 |
| 全局检索慢 | Map 阶段串行 10 次 LLM | asyncio 并行 |
| 增量更新难 | 新文档可能影响社区结构 | **定期全量重建**（微软增量更新还在迭代） |
| 图太大查询慢 | 上万节点图遍历卡 | 图数据库（Neo4j）替代 NetworkX |

## 三、复现验证（归纳总结）

本文为分析型笔记，无本机运行验证。核心结论链与上篇（Embedding 62→89）一致：**检索方案的收益来自"匹配问题类型"**——Embedding 选型解决"语义距离=语义相关"，GraphRAG 解决"跨文档关系推理"，两者是 RAG 能力栈的不同层而非替代品。

## 四、可学到的点（归纳总结·续）

1. **问题类型决定架构**：单文档问答 → 向量 RAG；跨文档关系 → GraphRAG；多模态 → 下篇预告。先诊断问题再选方案。
2. **图的价值在"关系"不在"实体"**：实体抽取只是原料，社区检测 + 社区摘要才是让全局推理可行的关键。
3. **成本大头在抽取**：500 篇 $30-50（GPT-4o）。开发/生产双模型策略（mini 验证→4o 重建）是标准省钱姿势。
4. **分层社区 = 多粒度查询自由度**：一个层级不够，微软用分层解决粒度矛盾。
5. **增量更新仍是痛点**：目前最稳妥是全量重建——社区结构会被新文档影响，这是 GraphRAG 工程化的最大现实约束。
6. **1200 token chunk 是反直觉经验值**：向量 RAG 习惯小 chunk，GraphRAG 要大 chunk 保实体完整，但过大会因注意力衰减漏抽取。

## 五、趋势判断（拓展应用）

1. **GraphRAG 与混合检索并行演进**：生产 RAG 已是 BM25+向量+Rerank（Embedding 篇），再叠加图结构 = "三引擎检索"成为知识密集型企业的标准。
2. **本地模型做抽取是降本终点**：Qwen-14B 等开源模型零 API 成本做实体抽取，与 edge-llm-quantization（Jetson 端侧）趋势一致。
3. **图数据库回春**：Neo4j/知识图谱场景因 GraphRAG 重新热门，NetworkX 只适合原型。
4. **多模态 RAG 是下一个前沿**：colpali 视觉检索 + 表格抽取（下篇预告），检索从纯文本走向图文混排。
