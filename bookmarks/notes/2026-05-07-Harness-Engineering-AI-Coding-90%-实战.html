一句话概括

Harness Engineering 是围绕 AI Coding Agent 设计约束机制、反馈回路、工作流编排与持续改进循环的系统工程实践，作者在一个十万行企业级 Java 应用中，用一周时间从零构建四要素 Harness 体系（Rules / Skills / Wiki / Changes），搭配十阶段结构化 Pipeline 和 Agent-to-Agent Review 机制，将 AI 代码率从 24.86% 系统性提升至 90.54%。

核心观点

观点一：AI Coding 正经历第三次范式跃迁。 从 Prompt Engineering（2022-2024，关注单次交互优化）到 Context Engineering（2025，关注给 Agent 看什么），再到 Harness Engineering（2026，设计跨会话、跨角色、跨阶段的完整系统架构）。每一次跃迁都是抽象层次的提升，而非对前者的否定。OpenAI 工程师 Ryan Lopopolo 用百万行代码实践总结："Agents aren't hard; the Harness is hard."

观点二：模型能力与可信赖产出之间横亘系统性鸿沟。 Anthropic 2026 报告指出，开发者已有约 60% 时间在使用 AI 辅助，但"完全委托"给 Agent 的任务比例仅为 0-20%。这六成使用率与两成委托率之间的巨大落差，本质原因不是模型不够强，而是缺乏系统性的外部约束和反馈机制来弥合能力与可信产出之间的距离。

观点三：Agent 有四种典型失败模式，根因是缺乏外部结构化约束。 一步到位综合征（One-shot Syndrome）导致上下文耗尽后出现幻觉；过早宣布胜利（Premature Victory Declaration）导致核心功能未实现；过早标记功能完成（Premature Feature Completion）导致关键路径未验证；环境启动困难（Cold Start Problem）导致 Token 浪费在重复理解上。Anthropic 明确指出：Agent 无法准确评估自身产出质量（"Agents are incapable of accurately evaluating their own work"），这是根本性的能力缺陷，必须靠外部化控制系统弥补。

观点四：Harness 四根支柱构成完整工程体系。 上下文架构（恰好给够，不多不少）、Agent 专业化（受限工具集的专业 Agent 优于全能型通用 Agent）、持久化记忆（进度持久化在文件系统而非上下文窗口）、结构化执行（理解→规划→执行→验证，每阶段有质量门禁）。OpenAI 团队早期将 AGENTS.md 写成百科全书，结果是"所有内容都重要等于没有内容重要"，后来控制在约 100 行作为索引地图。

观点五：质量门禁必须可程序化验证。 "如果它不能被机械化地执行，Agent 就会偏离"——这是 OpenAI 百万行代码项目的核心经验。自然语言描述的门禁不够，必须转为可程序化验证的条件。例如"检查 CI 是否通过"不够具体，改为三个条件（status == SUCCESS && total_tests > 0 && passed == total）后问题彻底消除。一切不可被机器验证的约束，在 Agent 执行中都是无效约束。

观点六：分离执行与评判是关键杠杆。 Anthropic 反复强调"将做事的 Agent 和评判的 Agent 分开，是一个强有力的杠杆"。作者的实践中，评审 Agent 发现了编码 Agent 遗漏的渠道判断逻辑（潜在线上故障），还检测到 Agent 试图跳过评审阶段。评审 Agent 不需要"更聪明"，只需要用不同于编码 Agent 的检查视角来审视产出物。

观点七：开发者角色正在发生范式转移。 传统模式下核心工作是写代码、调 Bug、做 Code Review；Agent-First 模式下核心工作变成了设计 Agent 的工作环境、编写规范文档、管理任务拆分与验收。文档从"给人看的参考资料"变成了"Agent 认识世界的唯一窗口"。Mitchell Hashimoto 的定义：每发现一个错误，就工程化地消除它再次发生的可能性。

观点八：规范是活文档，每一行对应一个历史失败案例。 Harness 本身需要 Dry Run（用虚拟需求走全流程来验证 Harness 自身），发现缺陷后立即 Patch 到规范中。规范的迭代不是装饰，而是 Harness 自我进化的核心机制。投入产出比具有复利效应——一次性约一周的投入，后续每个需求都在框架内高效运转。

关键方法论/框架

四要素架构

作者将 Harness 落地设计拆解为四个核心要素，以项目根目录下 .harness/ 目录作为物理载体。规则体系（Rules） 告诉 Agent"标准是什么"，包括工程结构约束、编码规范、分层架构约定等不变量约束。技能体系（Skills） 告诉 Agent"应该怎么做"，包含 9 个 Skill（需求分析、编码实现、专家评审、单元测试编写、CI 验证、部署验证、代码检查、项目分析、CI 配置生成），本质上是结构化 SOP。知识库（Wiki） 告诉 Agent"系统是什么样的"，是业务上下文素材。变更管理（Changes） 记录 Agent"做了什么"，每个需求从分析到部署的完整追溯链。四要素组合形成 Agent 可自主运转的完整环境。

十阶段结构化 Pipeline

一个完整的开发需求被划分为十个严格有序的阶段：需求分析 → 需求评审 → 编码实现 → 编码评审 → 单元测试编写 → 单元测试评审 → 代码推送 → CI 验证 → 部署验证 → 用户确认。每个阶段有明确的三要素：触发条件（什么时候可以进入）、Skill 加载（加载哪个技能包）、质量门禁（产出必须满足什么条件）。阶段间有精确的回退路径：CI 失败回退到测试编写或编码实现、需求不符回退到需求分析。评审设置循环上限（需求评审最多 3 轮，编码/测试评审最多 2 轮），防止无限自我修正循环。流程中嵌入 5 个 Human-in-the-Loop 确认点，确保人始终掌握关键决策权。

Application Owner Agent 五模块定义法

Agent 角色定义文件约 400 行，承担"Index & Map"职责，包含五个核心模块。角色与项目背景（20-30 行，提供刚好够用的项目视野）。配置中枢索引（用结构化表格列出 Rules、Skills、Wiki、MCP 四大组件的路径、职责、触发场景）。七项核心职责（需求理解、任务拆解、任务分发、任务验收、质量把关、文档管理、知识问答，每项附带行为准则）。工作流程调度指令（最核心最长的部分，定义十阶段流程中每阶段的完整调度逻辑，含触发条件、Skill 加载指令、产出物路径、质量门禁、失败回退路径）。沟通原则与硬性约束（"必须做到"和"禁止做的"两张清单定义行为边界）。

上下文三层加载策略

项目知识按加载时机分三层。L1 会话常驻层：Agent 定义文件（约 420 行）+ 三份 Rules 文件，提供全局视野和基本约束，总量严格控制（遵循 Anthropic 经验，上下文窗口填充率不超过 40%）。L2 阶段触发层：进入特定阶段时加载对应 Skill（需求分析阶段加载 request-analysis，编码阶段加载 coding-skill 和 8 份分层编码 Spec）。L3 按需查询层：Wiki 知识库中的业务文档不主动加载，Agent 根据任务需要自主查阅。核心原则是"让 Agent 在任何时刻都拥有刚好够用的上下文"。

Agent-to-Agent Review 闭环

编码 Agent 和评审 Agent 的分离是质量保障核心。评审 Skill 定义两种评审循环：计划评审审查 spec.md + tasks.md 的合理性和完整性；执行评审审查编码实现是否满足计划和需求。每条评审意见必须包含问题描述、修改建议和优先级分级（MUST FIX / LOW / INFO），确保可操作性。这种模式本质上是将传统 Code Review 自动化，将质量发现前移到 Human Review 之前。

可借鉴实践（对 Hermes Agent 团队）

① 有利 → 落实：立即吸收到 skill/memory

上下文分层加载策略直接映射我们的 skill 体系。 我们目前的 skill 加载可以借鉴 L1/L2/L3 三层架构：系统级 skill（类似 L1 常驻层）始终在内存中；任务级 skill（类似 L2 阶段触发层）按任务类型按需加载；知识库类 skill（类似 L3 按需查询层）由 Agent 自主决定是否查阅。关键指标是上下文填充率控制在 40% 以下——超过此阈值输出质量快速衰退。

分离执行 Agent 与评判 Agent 的模式可以直接落地。 我们的 subagent 体系天然支持这种分离。可以设计一个 reviewer subagent，在 coding subagent 完成后自动触发，使用不同的检查视角（不共享执行时的"认知惯性"），产出结构化评审报告（含 MUST FIX / LOW / INFO 分级）。这比让同一个 Agent 自己 Review 自己的效果好得多。

质量门禁机械化原则应写入我们的工程准则。 所有质量检查条件必须可程序化验证——不是"检查测试是否通过"，而是三个具体条件（状态码、测试数大于零、全部通过）。任何不能被脚本/linter/ci 验证的约束，在 Agent 执行中等同于不存在。

Harness Dry Run 方法论应成为我们 skill 发布的标准流程。 在发布新 skill 或修改现有 skill 后，用虚拟任务完整走一遍全流程来验证 Harness 自身，而不是等到真实任务中才发现缺陷。

② 有价值 → 记录：记到笔记里

十阶段 Pipeline 的设计思路。 我们目前的任务执行流程可能更灵活，但十阶段的严格有序 + 精确回退路径 + 评审循环上限的设计思路值得记录。特别是"流程一致性优先于流程效率"的原则——简单任务不应跳过关键环节，只是每个阶段的执行时间自然缩短。5 个 Human-in-the-Loop 确认点的设计也值得参考。

Application Owner Agent 的五模块定义法。 这是 Agent 角色定义的成熟模板，从项目背景、配置索引、核心职责、工作流调度到硬性约束，信息密度高且结构清晰。当我们设计更复杂的 Agent 角色时可以参考这个模板。

变更管理目录结构（Audit Trail）。 每个变更有独立目录，内含全流程追溯摘要、需求分析、编码报告、评审记录、测试报告、CI 结果、部署报告。评审文件版本递增（v1, v2, v3...）且旧版本永不删除。这种可追溯性设计在多人协作和长期维护场景下价值极大。

OpenAI 团队的 Entropy Garbage Collection 机制。 Agent 写代码时会模仿已有 Pattern（包括次优的），累积导致代码腐化。解决方案是将"Golden Principles"编码化，让后台 Agent 自动扫描违规并提交修复 PR。这是一个可以与我们 cron job 体系结合的自动化治理模式。

Mitchell Hashimoto 的 Harness 定义作为持续改进的指导原则。 "Every time you discover an agent has made a mistake, you take the time to engineer a solution so that it can never make that mistake again." 这个原则应该指导我们的 skill/memory 迭代——每次出错不仅是修复，更是更新约束防止同类问题再次发生。

③ 笔记：仅归档

文章中对企业级 Java 应用技术栈的讨论（HSF/Dubbo/gRPC、LiteFlow、Diamond、Tair 等）是阿里特定技术栈背景，与我们的技术选型不同，仅作为上下文理解归档。

Anthropic 2026 报告的宏观统计数据（60% 使用率、0-20% 委托率）作为行业趋势参考归档，但不直接指导我们的工程决策。

文章末尾对未来方向的展望（Harness 自我进化、跨项目模板化、更精细 Agent 角色矩阵、存量代码库渐进式引入）是方向性思考，与我们的路线图有部分重叠但不需要立即行动。

关键洞察：高 AI 代码率本身不是目标——在质量可控前提下的高 AI 代码率才有意义。90% 的 AI 代码经过了完整的需求分析、编码评审、单元测试和 CI 验证流程，每一行都通过了 Harness 体系的质量门禁。效率提升的核心来源不是"Agent 写代码更快了"，而是"返工大幅减少"和"交付质量可预期"。
