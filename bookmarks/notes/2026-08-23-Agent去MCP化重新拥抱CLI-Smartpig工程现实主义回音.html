一句话总纲

核心命题：MCP 解决"如何标准化连接"，CLI 解决"如何直接把事情做完"——Agent 从 Demo 进入真实工程环境后，两者重新分工：本地执行层走 CLI，跨平台集成层走 MCP，能用文件就别用 API，能用 CLI 就别再包一层 Server。

一、内容详细整理

1.1 五大 CLI 优势

原因一：CLI 已经存在，MCP 往往需要再造一层

Git、Docker、kubectl、ffmpeg、psql、gh 等成熟工具本身就有稳定命令行接口。为了让 Agent 使用它们再包装成 MCP Server，相当于增加了一层协议、进程、配置和维护成本。Agent 如果直接读 --help、执行命令、检查退出码，很多适配层没有存在必要。

原因二：CLI 更节省上下文

MCP 工具通常要向模型暴露工具名称、描述和参数 Schema，工具一多，Agent 还没开始工作，上下文里已经塞进一本"工具说明书"。CLI 则可以渐进式探索：先知道有哪些命令 → 需要时再执行 help → 只读取当前子命令的参数。不是一次性把整个工具箱倒进上下文，而是用到什么再拿什么。

原因三：CLI 更容易调试和复现

MCP 调用失败时，问题可能来自客户端、Server、传输协议、Schema、权限或底层 API 六个层面。CLI 失败更直接：一条命令、stdin/stdout/stderr、退出码。开发者可以复制同一条命令在终端重现问题，Agent 操作也更容易写进日志、脚本和 CI。

原因四：CLI 天然具备组合能力

Unix 管道、文件、环境变量和重定向，本身就是一套成熟的 Agent 工具协议：获取数据 | 过滤 | 转换 | 保存。Agent 不一定需要几十个精心定义的工具，有时只需要 shell 加几个可靠、边界清晰的命令。

原因五：CLI 更接近真实执行环境

代码、依赖、Git 状态、容器、构建工具都在本地环境里。通过 CLI，Agent 操作的就是开发者实际使用的那套系统，不需要在 MCP Server 和真实环境之间同步状态。

1.2 MCP 仍然合适的场景（文章不极端）

  • 跨客户端复用同一个集成
  • 连接远程 SaaS 和企业数据
  • 提供结构化参数与返回值
  • 统一认证、权限、审计和交互界面
  • 向不具备完整终端能力的 Agent 暴露工具

1.3 文章给出的架构分层

真正发生的不是"MCP 被 CLI 淘汰"，而是两者正在重新分工：

  • CLI 成为 Agent 的本地执行层
  • MCP 回到标准化集成层

决策准则（三句话）：

能用文件，就不用 API。
能用 CLI，就不额外包装 Server。
只有真正需要协议边界时，才使用 MCP。

二、查询拓展

2.1 协议边界三层次

层次 形态 适用场景
L0 文件/数据 直接读文件/JSONL/SQLite 本地只读，无认证，最高吞吐最低开销
L1 CLI/进程 命令行调用，读退出码和 stdout 本地执行/写操作，有成熟 CLI，需要组合能力
L2 MCP/协议 标准化 JSON-RPC 工具调用 跨客户端复用、远程 SaaS、结构化参数、统一认证

核心判断：越底层越贴近真实环境，越上层越贴近抽象标准化。Agent 工具调用的本质是在"贴近性"和"抽象复用性"之间做权衡。

2.2 上下文预算视角

MCP 工具的一次"暴露"成本：工具名 + 描述 + 参数 Schema + 示例——平均 200-800 tokens/工具。10 个工具 = 2-8k tokens；100 个工具 = 20-80k tokens。对一个 128k context 的模型，光工具描述就可能吃掉 15-60%。

CLI 的"暴露"成本：只有 shell 工具一个 Schema，具体命令在需要时临时读 --help——从"工具描述即上下文成本"变成"按需查 help 的可忽略成本"。

2.3 可组合性视角

能力 CLI MCP
管道组合（A \| B \| C） ✅ 原生 ❌ 需显式编排
子命令嵌套（gh issue list --state open） ✅ 原生 ⚠️ 需设计参数 Schema
标准 I/O ✅ 原生 ❌ 需自定义传输
退出码检查 ✅ 原生 ⚠️ 需 Server 透传

三、归纳总结

3.1 核心命题

MCP 解决的是"如何标准化连接"。
CLI 解决的是"如何直接把事情做完"。
当 Agent 从 Demo 进入真实工程环境，后者往往更重要。

3.2 分层分工模型

┌─ MCP 层（标准化集成层）────────────────────────┐
│ 跨客户端复用 / 远程 SaaS / 统一认证审计           │
│ 典型：飞书/Notion/GitHub MCP（本机已用 3 类）     │
├─ CLI 层（本地执行层）───────────────────────────┤
│ shell 调用 / --help 渐进探索 / 管道组合           │
│ 典型：git/docker/kubectl/python3/curl           │
└─────────────────────────────────────────────────┘

3.3 文章不极端的关键

文章明确声明"MCP 仍然适合"的场景——不是"MCP 已死"的口号，而是分层分工的冷静判断。这是比"喊口号"更高一个段位的工程现实主义。

四、趋势判断

趋势 1：Agent 工具层的"分层选型"将成为工程共识

依据：本文章、05-30 两篇"去 MCP 化"笔记、以及本机实际工作流（terminal 工具占调用量的 40%+ 远超任何 MCP tool）——本地执行优先 CLI 已经是隐性共识，正在显性化。

趋势 2：CLI 的"渐进式 --help 探索"模式会成为低成本工具调用的标准范式

依据：本文章把"渐进式探索"列为 CLI 第二大优势——这与本机 execute_code 工具的设计（Python 脚本内含多步 tool 调用，按需查文件内容，不进上下文）同构。本质都是上下文按需加载而不是工具描述一次全量暴露。

5.2 与本机 mcporter 技能的实证对照

本机 mcporter skill 是 MCP 的 CLI 桥——用 CLI 封装 MCP，让 Hermes 通过 mcporter tool list / mcporter tool call 调用 MCP 服务器。

这恰好是本文"分层分工"的实证落地：MCP 服务器走 MCP 协议，但 Hermes 侧通过 CLI 接入，两边各取所长。

5.3 与 execute_code 工具的架构同构

本机 execute_code 工具允许一次 Python 脚本里调用多个工具（web_search/web_extract/terminal）——本质就是"CLI 组合能力"在 Agent 层的映射：

  • MCP：一次性暴露 N 个独立工具
  • execute_code：暴露一个 Python 工具，具体工具在脚本里按需调用

上下文成本从 O(工具数×Schema) 降到 O(一个 Python Schema)。

5.4 与本机"渐进式上下文加载"skill 的关联

2026-08-22-ErnestRyu-RLforLLM课程-UCLA数学系极简理论路线.md 讲"课程分层学习"，本篇的"工具分层调用"是同一思想的工程变体——信息按需加载，不是全量倾倒。

六、拓展应用推荐

6.1 分层选型决策表（可沉淀到 skill）

输入：某个工具/能力要不要接入 Agent

问题 1：这个能力是本机已有文件/数据库？
  → 是：直接读文件/SQLite，不建任何东西
  → 否：进入问题 2

问题 2：这个能力有成熟 CLI？
  → 是：直接 shell 调用（--help 渐进探索），不建 MCP
  → 否：进入问题 3

问题 3：这个能力需要跨客户端复用/远程 SaaS/统一认证？
  → 是：MCP（标准化集成层）
  → 否：自建 HTTP API / 直接 curl

6.2 对已有 MCP 服务器的"去封装"审计

服务器 是否有成熟 CLI 替代 建议
GitHub MCP ✅ gh CLI 可降级 CLI（本机已是混合）
Notion MCP ❌ 无 CLI 保留 MCP
SQLite MCP ✅ sqlite3 CLI 可降级 CLI
