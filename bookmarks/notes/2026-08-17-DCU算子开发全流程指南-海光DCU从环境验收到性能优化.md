### 0. 核心方法论

> **"先跑通再优化，先正确再快速"** — 覆盖环境验收 → 开发流程 → 避坑调试全链路

### 1. 核心概念

| 概念 | 定义 |
|------|------|
| 算子（Operator） | AI 模型最小计算单元（矩阵乘/卷积/激活等），模型运行 = 算子按序或并行执行 |
| 算子覆盖率 | DCU 正确支持的算子数 / 目标模型所需总数（**海光 DCU 覆盖度已超 99%**） |
| 编译验证 | HIP 源码 → DCU 二进制 → 实际数据对比 CPU/GPU 参考结果（数值正确 + 性能达标） |

### 2. 开发全流程（7 步）

| 步骤 | 内容 | 关键点 |
|------|------|--------|
| ① 环境准备 | 装 DTK（DCU Toolkit），确认 `hipcc`、运行时库、`LD_LIBRARY_PATH` | 集群用 SLURM `--gres=dcu:N` 申请资源 |
| ② Tensor 契约 | 明确输入输出规格（设备/dtype/shape/内存布局） | C++ binding 层用 `TORCH_CHECK` 前置校验 |
| ③ HIP Kernel | `.hip` 后缀源文件 | Wavefront=64、FP8 FNUZ 格式等硬件差异 |
| ④ C++ Binding | 契约检查 + Stream 管理 + Launch 配置 + pybind11 导出 | 与 PyTorch 集成层 |
| ⑤ 编译与缓存 | `hipcc` 编译 | 缓存管理：源码/版本变化时自动失效 |
| ⑥ 正确性验证 | 数值回归 + 多 shape/dtype + 错误路径测试 | — |
| ⑦ 性能优化 | `hipprof` 分析瓶颈 → 算子融合 → 性能对比 | — |

### 3. 常见坑与调试技巧（核心避坑清单）

**硬件差异（vs NVIDIA）：**
- **Wavefront=64**：归约逻辑需调整；分支分歧代价为 NVIDIA 的 2 倍
- **寄存器预算仅 64KB**（V100 的 1/4）：需用 `__launch_bounds__` 防溢出
- **FP8 格式为 FNUZ**：不可直接复用 CUDA 代码

**编译环境：**
- 必须加 `--offload-arch` 指定目标架构
- 警惕编译缓存导致"改代码未生效"
- 物理机必须 `source /opt/dtk/env.sh`

**正确性：**
- 重点检查 Stream（**不能默认 stream 0**）
- 增加 BF16/FP16 需重算累加精度
- 保持"真理版本"做跨语言交叉验证

**性能：**
- 计时必须 `torch.cuda.synchronize()`
- 单算子优化需放回真实模型测端到端
- 避免盲目照搬 CUDA 优化（双缓冲 LDS、K 维 Tile 过大等不适用）

**调试工具箱：**

| 工具/命令 | 用途 |
|-----------|------|
| `torch.cuda.is_available()` | 快速环境校验 |
| `fuser -k` | 显存残留清理 |
| 四实验瓶颈诊断法 | 定位瓶颈 |
| `rocprof` | 硬件计数器分析 |
| `numactl` | NUMA 绑核 |

### 4. 完整案例：逐元素仿射变换算子（y = x × scale + bias，FP16）

**目录结构：**
```
my_dcu_op/
├── __init__.py        # Python接口、架构检查、缓存管理
├── binding.cpp        # Tensor契约检查、pybind导出
├── op.h               # C++函数声明
└── op_kernel.hip      # HIP kernel实现
```

**HIP Kernel（`op_kernel.hip`）：**
```cpp
#include <hip/hip_runtime.h>
#include <hip/hip_fp16.h>

__global__ void affine_half_kernel(
    const __half* input, __half* output,
    float scale, float bias, long numel) {
    long index = static_cast<long>(blockIdx.x) * blockDim.x + threadIdx.x;
    if (index >= numel) return;
    float value = __half2float(input[index]);
    output[index] = __float2half(value * scale + bias);
}

void launch_affine_half(
    const at::Tensor& input, at::Tensor& output,
    float scale, float bias) {
    constexpr int threads = 256;
    const auto numel = input.numel();
    const int blocks = static_cast<int>((numel + threads - 1) / threads);
    hipLaunchKernelGGL(
        affine_half_kernel,
        dim3(blocks), dim3(threads), 0, 0,
        reinterpret_cast<const __half*>(input.data_ptr<at::Half>()),
        reinterpret_cast<__half*>(output.data_ptr<at::Half>()),
        scale, bias, numel);
}
```

**C++ Binding（`binding.cpp`）：**
```cpp
#include <torch/extension.h>
#include "op.h"

torch::Tensor affine_half(const torch::Tensor& input, double scale, double bias) {
    TORCH_CHECK(input.is_cuda(), "input must be on accelerator");
    TORCH_CHECK(input.scalar_type() == at::kHalf, "input must be FP16");
    TORCH_CHECK(input.is_contiguous(), "input must be contiguous");
    auto output = torch::empty_like(input);
    launch_affine_half(input, output, static_cast<float>(scale), static_cast<float>(bias));
    return output;
}

PYBIND11_MODULE(TORCH_EXTENSION_NAME, module) {
    module.def("affine_half", &affine_half, "FP16 affine example");
}
```

**Python 在线编译加载（`__init__.py`）：**
```python
from pathlib import Path
import torch
from torch.utils.cpp_extension import load

def load_extension():
    if torch.version.hip is None:
        raise RuntimeError("This extension requires a HIP PyTorch build")
    root = Path(__file__).resolve().parent
    return load(
        name="my_dcu_op_ext",
        sources=[str(root / "binding.cpp"), str(root / "op_kernel.hip")],
        extra_cflags=["-O3", "-std=c++17"],
        verbose=True,
    )

_ext = load_extension()
affine_half = _ext.affine_half
```

**测试脚本（`test_affine.py`）三层验证：**
```python
import torch
from my_dcu_op import affine_half

# 1. 小确定性输入测试
input_tensor = torch.tensor([[1.0, 2.0, 3.0]], device="cuda", dtype=torch.float16)
scale, bias = 2.0, 0.5
result = affine_half(input_tensor, scale, bias)
reference = input_tensor * scale + bias
print("匹配:", torch.allclose(result, reference, atol=1e-3))

# 2. 随机数值回归测试（多种 shape）
torch.manual_seed(42)
for rows, hidden in [(4, 8), (64, 128), (1024, 2048)]:
    x = torch.randn(rows, hidden, device="cuda", dtype=torch.float16)
    out = affine_half(x, 1.5, -0.3)
    ref = x * 1.5 + -0.3
    print(f"shape={rows}x{hidden}, allclose={torch.allclose(out, ref, atol=1e-2)}")

# 3. 性能微基准（对比 PyTorch 原生，前后必须 synchronize）
import time
x_large = torch.randn(4096, 4096, device="cuda", dtype=torch.float16)
for name, fn in [("自定义算子", lambda: affine_half(x_large, 2.0, 0.5)),
                 ("PyTorch原生", lambda: x_large * 2.0 + 0.5)]:
    torch.cuda.synchronize()
    start = time.time()
    for _ in range(100): fn()
    torch.cuda.synchronize()
    print(f"{name}耗时: {(time.time() - start) * 1000 / 100:.3f} ms/iter")
```

### 5. 验收清单（10 条照录）

1. 参考数学定义一致
2. 错误输入有明确报错
3. 空输入不发射非法 grid
4. 使用 PyTorch 当前 stream
5. launch 后检查 HIP 状态
6. 随机与边界测试通过
7. benchmark 前后有同步
8. 缓存包含源码指纹
9. 性能使用真实 shape 验证
10. 训练场景已实现 backward 或明确禁止

## 二、查询拓展

1. **Wavefront=64 vs Warp=32 的归约实现差异**：`__shfl_down_sync` 在 HIP 下的语义/宽度差异，block-level 归约写法
2. **FP8 FNUZ vs E4M3/E5M2**：海光 FNUZ 格式的位定义，与 NVIDIA/Intel FP8 的转换损失
3. **DTK 与 ROCm 版本对应关系**：hipcc 参数差异（`--offload-arch=gfx906` 等海光架构号）
4. **rocprof vs hipprof**：文档两处分别提及，实际是同工具还是不同层（系统级 vs kernel 级）
5. **SLURM `--gres=dcu:N` 多卡拓扑**：DCU 的 P2P 通信（xGMI？）对多卡算子的影响
6. **算子覆盖率 99% 的余下 1%**：哪些算子是 DCU 未覆盖的长尾（通常是新出的 FlashAttention 变体/量化算子）

## 三、归纳总结

| 维度 | 要点 |
|------|------|
| 方法论 | 先跑通再优化、先正确再快速——与 CUDA 算子开发同构但硬件约束更紧 |
| 最大差异 | 三大硬件坑：Wavefront=64（归约+分支分歧2x代价）、64KB 寄存器预算（1/4 of V100）、FP8 FNUZ |
| 工程核心 | Tensor 契约前置检查 + Stream 正确性（禁默认 stream 0）+ 编译缓存指纹管理 |
| 验证体系 | 三层测试（确定性小输入 → 随机多 shape 回归 → 性能微基准）+ 10 条验收清单 |
| 可移植性 | HIP 是类 CUDA 的 C++ 方言，代码结构可从 CUDA 迁移但不可盲搬优化技巧 |

## 四、趋势判断

1. **国产算力生态进入"算子补全"深水区**：覆盖率 99% 意味着平台竞争点从"能不能跑"转向"跑多快+长尾算子跟进速度"
2. **HIP/ROCm 生态成为国产 GPU 事实标准接口**：海光 DCU 用 HIP，多家国产卡兼容 ROCm 系工具链——学会一家的算子开发可半通用于多家
3. **算子开发 AI 化的前置条件成熟**：本文的"契约定义→kernel→binding→三层测试"流水线结构化程度高，是 LLM 生成算子代码的理想骨架（类似 Triton 的崛起逻辑）
4. **性能移植不能盲搬是普遍规律**：双缓冲 LDS、Tile 大小等 CUDA 优化在寄存器预算紧张的硬件上反而劣化——国产硬件优化需要自己的 profile 驱动方法论
