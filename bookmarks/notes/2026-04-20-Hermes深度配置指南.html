核心观点

Hermes Agent 的真正门槛不是安装，而是配置。文章提出四步调教法：模型配置→技能优化→记忆强化→工具扩展，外加人设定制和自动化。

四步框架

一、模型配置 — 喂对"大脑"

  • hermes setup 先跑一遍，拉平常见坑
  • ~/.hermes/config.yaml 是控制中枢，决定长期体验
  • 密钥放 ~/.hermes/.env，不要写进 config.yaml
  • 按任务切换模型：代码/排错→强推理，日常→通用，批量→便宜模型
  • hermes model 随时切换

模型配置决定的不是小体验，而是智商上限。

二、技能库 — 养好"经验"

  • Skill ≠ 提示词模板，是沉淀的工作方法（触发条件+步骤+避坑+验证）
  • 值得沉淀的场景：复杂多工具任务、从错误恢复的任务、用户纠正过的流程
  • 判断标准：如果你不想下次再解释一遍，就值得沉淀
  • Skill 不是静态的，路径/命令变了就该 patch
  • 本地技能在 ~/.hermes/skills/

聊天记录会翻过去，但技能库会留下来。

三、记忆系统 — 强化"记忆力"

五层记忆架构：
1. 会话内记忆 — 当前任务上下文
2. 技能记忆 — 复杂任务沉淀的复用方案
3. 检索索引 — 知道何时找已有 Skill
4. 用户画像 — 偏好、忌讳、习惯
5. 全文检索 — 从历史对话翻上下文

长期记忆插件 plur-hermes：pip install plur-hermes
- plur_learn 存偏好/规则/经验
- plur_recall 按需搜索
- plur_forget 删过时内容

所谓"越用越聪明"，本质是长期记忆体系搭起来了。

四、工具箱 — 装好"手脚"

  • Skill vs Tool 选择：规则/流程/提示能解决的→Skill；需要程序/API/系统能力的→Tool
  • 值得做 Tool 的：今天已经在反复手动做的动作
  • MCP 是能力外延的关键：hermes mcp add

五、人设 + 自动化

  • SOUL.md 不是装性格，是长期协作规则文件
  • 定时任务是 Agent 从"被动响应"→"主动工作"的分界线
  • 网关接入（微信/飞书/Telegram）让它"随时随到"

🎯 启发与借鉴

1. Skill 沉淀的判断标准 — "不想再解释一遍就值得沉淀"

这个标准极其精准。回顾我们的实践：
- ✅ 已做到：quant-trading、wechat-article-extract 等复杂流程已沉淀
- ⚠️ 可改进：很多一次性 debug 过程没有沉淀，下次遇到同样问题还得重来
- 行动：下次遇到 "第三次解释同一件事" 的场景，立即触发 skill_manage create

2. Skill 生命周期管理 — 不是写完就完，要持续 patch

文章核心观点：路径变了、命令变了、工具行为变了 → 就该 patch。
- ✅ 我们有 skill-optimizer cron 做周度审计
- ⚠️ 但很多 skill 写完后从未 patch 过，可能已经过期
- 行动：检查 quant-trading skill 的脚本路径/命令是否全部正确

3. 记忆五层架构 — 我们的缺口在"检索索引"层

文章提出的五层记忆（会话→技能→检索索引→用户画像→全文检索）：
- ✅ 会话内记忆：session 内 context
- ✅ 技能记忆：skills 库
- ❌ 检索索引：缺自动化的"知道何时去查已有 Skill"机制
- ✅ 用户画像：MEMORY + USER profile
- ⚠️ 全文检索：session_search 可用但不够精准
- 行动：利用已有的 RAG 索引 + hybrid-search，给 Skill 触发加语义匹配

4. 按任务切模型 — 我们已经在做但可以更激进

  • 当前：主力 GLM-5.1，Gemini 备选，用户手动切换
  • 启发：可以给不同 cron job 配不同模型（简单任务用便宜模型，分析任务用强模型）
  • 行动：给管家简报/天气等简单 cron 配 gemini-flash，quant 分析保留 GLM-5.1

5. "装好 ≠ 用好" — 持续调教思维

文章最核心的启发：Hermes 的价值不在安装，而在持续调教。类比到我们的实践：
- 系统 audit 不应该是一次性的，应该变成定期 cron（已有 system-health-check）
- 记忆系统的价值在于"存得准"而不是"存得多"
- 自动化是 Agent 从工具变助手的分界线
