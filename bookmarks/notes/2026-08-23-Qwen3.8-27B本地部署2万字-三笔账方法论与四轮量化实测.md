## 一、内容详细整理

### 1.1 模型定位

- **Qwen3.8 27B**：阿里 2026-08-14 开源，Apache 2.0，27B 稠密
- 官方定位**端侧 Agent 模型**：写代码/调工具/读长文，256K 上下文可扩 1M
- SWE-bench Pro 61.7（官方口径）
- 两个钱包相关设计：
  - **混合注意力**：64 层里只有 16 层全注意力 → KV Cache 省约 75%
  - **MTP 内置**：推测解码头在模型文件里，开参数生成翻倍

### 1.2 选型总表（按显存对号入座）

| 显存 | 推荐 | 配置 | 关键数据 |
|------|------|------|----------|
| 12GB | Q2_K_XL | 32K 窗口 | 占 10.92GB，短任务可用（**agent 长任务会掉两成完成率，短任务限定**） |
| 16GB | Q2_K_XL → Q3_K_XL | 128K | Q2 占 14.66GB；社区数据 Q3 33/41 > Q2 27/41（agent 长任务优先 Q3） |
| 18-20GB | Q4_K_M + q4 KV | 64-128K | 18GB 开 64K（17.1GB），20GB 开 128K（18.5GB） |
| 24GB | Q4_K_M + q4 KV + MTP3 | **192K**（别开 256K） | 22.6GB，59.52 tok/s；硬开 256K 只剩 154MiB |
| 32GB+ | Q4_K_M + q4 KV + MTP3 | 满开 256K | 24.4GB，53.15 tok/s（推荐首选）；Q8attn 30.3GB 更快 11% |
| 8GB 及以下 | ❌ 无验证方案 | — | 混合卸载能启动但太慢 |

**硬线**：Q4_K_M 最省配法（q4 KV、32K）也要 16,338 MiB——16GB 卡装不下，18GB 起步。

### 1.3 全文最重要：三笔账（第五章核心）

**误解**：窗口开大 = 模型变慢。

**实测铁证**：同一个 256K 配置——
- 空载（只有一两句话）：78.80 tok/s
- 满载（塞满 250K 内容）：47.70 tok/s
- **显存只差 8 MiB**

**三笔账**：

| 账 | 什么决定 | 什么影响 |
|----|---------|---------|
| **窗口账** | 启动时 KV Cache 预分配 | 只占显存，**不影响速度** |
| **内容账** | 实际 token 数 | Prefill 时间 + 生成速度衰减 |
| **显存账** | 模型 + KV Cache + 运行开销 | 永远比文件大（Q4 文件 16GB → 实际 16.3GB+） |

**推论**：显存够就放心开大窗口，平时聊短的一点不亏；按文件大小买卡必翻车。

### 1.4 量化实测四轮（诚实边界声明的典范）

**测试结论**：

1. **Q4_K_M vs Q8_0 300 对盲测**：81.67% vs 79.33%，差异不显著（同源对比最接近）
2. **72 道短题**：Q4_K_M 拿 47/72 全场最高；Q2_K_XL 41 分与 30GB 版"打平"
3. **但"同分不等于同一个东西"**：Q2 思考要多花 **2.14 倍** token
4. **NVFP4（英伟达 4-bit）四轮测不出比 Q4_K_M 聪明**：官方说法未被复现
5. **IQ2_S 断崖**：32-token 预测准确率 25% → 8-10%，大量循环/空响应/工具调用失败

**作者的诚实声明**（值得逐字学习）：

> "我没没能证明高位版本更聪明，四轮都没有。……但这句话有边界：不等于'Q4 和 Q8 一样好'（没测出不是证明相同），也不等于'量化没有代价'。"

**推荐 Q4_K_M 的三条依据**（与"更聪明"无关）：显存更低 / 单任务耗时最短（13.81s vs Q8_0 的 22.16s）/ 四轮无可靠质量劣势。

### 1.5 速度配置结论

| 配置 | 结论 |
|------|------|
| **MTP3** | 生成快一倍，多占 2.9GB——4090 上 MTP3 最优，5090 上有人测 MTP2 最优，官方推荐 6 在两边都是差档 |
| **DFlash 2** | 日常对话 MTP3 还快 9.4%；只在"250K 已读入+生成上千 token"时划算（**N 卡结论，Mac 上相反**） |
| **KV Cache q4** | 256K 下省 4GB，速度只掉 4.1%——24GB 卡必须压否则装不下 |
| **offload** | 挪几层速度 73.6→24.4；挪到省 10GB 只剩 9 tok/s——**别指望，换小模型或缩窗口** |

### 1.6 五个坑

1. **模型"变笨"先查输出预算**：作者 17 题只对 9，输出上限 4096 后 17/17 全对——思考过程吃光输出预算被截断，从外面看像"答错"
2. **换框架配错 chat template/reasoning parser**：思考与答案错位，看着像质量问题
3. **网上方案未必适合你的机器**：LOW GGUF 短对话快 12.8%，长文反而慢——**同一模型不同场景排名会反过来**
4. **你的数和文章对不上**：同一配置不同任务差 10%——跑分必须连着任务一起看
5. **"model loaded"会骗人**：16GB Mac 初始化 OOM 但进程不退出，健康检查也过——**必须发真实请求验证**

### 1.7 Agent 关键技巧

> **"历史开头不变可复用"**：Agent 多轮对话中，前缀（系统提示+早期历史）不变 → KV Cache 复用 → **190 多秒变 4-5 秒**。截断开头，缓存全废。

这是 llama.cpp prompt cache 与 vLLM prefix caching 的实战价值——Agent 场景的命根子。

## 二、查询拓展

### 2.1 GB vs GiB 的坑

Q2_K_XL = 9.83GB = 9.15GiB 是**同一个文件**。HuggingFace 页面和 wget 进度条显示 GiB——照着核对文件大小别对不上号。

### 2.2 Unsloth 动态量化 vs 传统量化

Q8_0 是传统量化（均匀砍每层精度）；Q4_K_M / Q2_K_XL 是 Unsloth 动态量化（校准数据先跑一遍，重要层少砍、不重要层多砍）。

> "位数不是唯一变量，怎么压才是。"——解释了为什么 Q2_K_XL 能和 30GB 版短题打平。

### 2.3 思考膨胀的量化代价

| 版本 | 单 token 速度 | 任务耗时 | 思考量 |
|------|--------------|---------|--------|
| IQ2_S | 32.38 tok/s（全场最快） | 22.16s（与最慢 Q8_0 一样） | 3.11 倍 |
| Q4_K_M | — | 13.81s（最快） | 基准 |

**核心洞察**：量化省的是每 token 时间，但低位版"为了答对多想两三倍"——速度收益全被吃回。**评价量化版本要测"任务级耗时"而不是 tok/s。**

## 三、归纳总结

### 3.1 三笔账方法论（可迁移到任何模型）

```
窗口账：启动参数决定，只占显存不影响速度 → 显存够就开大
内容账：实际 token 决定 prefill+生成速度 → 塞满才慢
显存账：文件大小 < 实际占用（+KV Cache+开销）→ 留 20% 余量
```

### 3.2 量化选型认知框架

1. **位数不是唯一变量**（动态量化工艺 > 位宽）
2. **tok/s 不等于任务速度**（思考膨胀）
3. **没测出差距 ≠ 没有差距**（诚实边界）
4. **同分不等于同一个东西**（量化方式/显存/长文表现都不同）
5. **场景决定排名**（短对话 vs 长文的量化版本排名会反过来）

### 3.3 工程诚实度五要素（本文典范）

1. 承认自己犯过的错（Q8attn 当成 8-bit；信了 NVFP4 宣传）
2. 区分"没测出"和"证明了"（p=1.0000 的解读）
3. 交代测试边界（样本小/不是同源对比/题目太简单）
4. 承认数据会浮动（同配置不同任务差 10%）
5. 结论都带适用场景（N 卡 vs Mac / 短任务 vs 长任务）

## 四、趋势判断

### 趋势 1：27B 级端侧 Agent 模型正在成为"个人 GPU 工作站标配"

> 依据：Qwen3.8 27B 两天 HF 下载破百万 + 本文 12GB 就能跑的结论 + SWE-bench Pro 61.7——性能/显存比已跨过"日常够用"线。本机 Jetson 8GB 虽跑不动 27B，但同类设计的更小版本会下探。

### 趋势 2：量化评测的焦点从"准确率"转向"思考膨胀率"

> 依据：本文实证 IQ2_S 单 token 最快但任务最慢（3.11 倍思考膨胀）+ Unsloth 文档的 32-token 预测准确率断崖——量化损耗的显性指标正在从"答没答对"变为"想多久才答对"。这呼应 Φ-Bench 的"持续优化能力"考察——任务级指标 > 单点指标。

## 六、拓展应用推荐

### 6.1 三笔账 checklist（进本地部署 skill）

```
□ 窗口账：显存预算 = 模型 + KV Cache(窗口) + 20% 余量
□ 内容账：真实任务 token 数 → 预估 prefill 时间 + 生成速度衰减
□ 显存账：实际占用 > 文件大小，永远留余量
□ 量化账：测任务级耗时，不只看 tok/s（思考膨胀）
□ 验证账：model loaded ≠ 能用，必须发真实请求
```

### 6.2 对 A100 局域网池的参考

本机 A100 池（80GB×8）跑 Q4_K_M 可全性能开 1M 窗口；但按本文"一卡多用"原则，W4A16 (vLLM) 占 45.5GB 才是最优解的场景判断同样适用。

### 6.3 Agent 前缀复用（进 Hermes 架构认知)

Hermes 多轮会话 = 典型的"历史开头不变"场景——若本地推理走 llama.cpp/vLLM，开 prompt cache / prefix caching 是免费的 40 倍加速。这对本机 Nexa 本地推理的配置有直接指导意义。
