归纳总结

一句话：一个 64 KB 的 Python 管道缓冲区让 π0.5 真机 rollouts 悄悄多出几百毫秒延迟——仿真消融说 280ms 延迟无害，真机上却是性能杀手；修掉后端到端推理从 230ms 压到 87ms，模型甚至涌现出训练数据里人类操作员的动作习惯。

三个核心发现：
1. 延迟是 sim-to-real gap 的隐形维度。他们的仿真消融（10K+ runs）结论"≤280ms 延迟对精度无影响"在真机上被彻底证伪——不是参数问题，是仿真物理太简单，mask 掉了真实世界的级联损伤。
2. off-the-shelf AI 代码慢得离谱。HF LeRobot 默认代码里有：每次调用重复转 bf16（25ms）、录了不用的 autograd 图（35ms）、无意义的 200 token padding——全是白送的浪费。
3. 延迟阈值以下才有涌现行为。端到端 <120ms 后，模型开始复现人类示教的"快速接近→停顿确认→小修正再抓"节奏，甚至出现交叉手放置与换手——示教数据里的人类风格只有执行链够快才能"显影"。

内容整理：延迟排查与优化全链路

背景

  • 上一篇文章消融了训练/rollout 参数，目标：在 YAM 采集 rigs 上训练的模型迁移到另一套略不同的 YAM 底座机器人上跑（小实验室没有 CAD 复制整套 rig 的能力）。
  • 已确认结论：相机粗内参（FOV）要匹配、expert+backbone 都要训、光照影响大、臂内参极度敏感（编码器累积 2° 偏差足以让精度归零）。
  • 烧了 ~1000 GPU-hours 训 checkpoint、10K+ 仿真消融、三查臂零位之后——性能还是不达标，差点放弃去做 RL pass 学"漂移的内参"。

事故：64 KB 管道缓冲

  • 转机纯属偶然：有人去推理 dashboard 里看视频流（本来盯 rollout 的人应该盯机械臂手按 e-stop），发现画面有几百毫秒延迟。
  • 根因：Python 的 buffered pipe 要攒满 64 KB 帧数据才交付——推理代码用的帧太小，攒够 64 KB = 攒了好几帧。之前一直以为是 Web 视频协议的固有缓冲（通常默认 1s+），没人当真。
  • 修掉后性能明显改善：此前 pick 的首次接近段和 place 段有无法解释的系统性 bias，全部消失。

反直觉：仿真为什么没发现

  • 又跑了 1000 次仿真专门注入不同量级的视觉延迟——仿真依旧显示几乎无变化。
  • 他们的解释（standing theory）：延迟 → near misses 增多 → 场景附带损伤（容器倾斜、物体翻滚/滑动，摩擦各异）→ 物体被撞出工作区 → 分布外 → 动作更狂乱 → 撞翻更多目标，恶性循环。仿真的简化物理模型（阻尼碰撞）把这条损伤链全部 mask 掉了。
  • 金句级洞察：benchmark 分数 ≠ 感知性能——LLM 可以 benchmark 高但实际难用，VLA 同样可以"通常能完成任务"但方式很难看（near miss 乱撞）。

推理优化账本（230ms → 87ms）

优化措施 节省 备注
权重一次性转 bf16 25ms HF 代码惯例存 fp32、每次调用都转，白送 10%
CUDA graph 捕获 expert 69ms 10 步动作生成 86→17ms，"大部分时间在什么都不干"
修 autograd 图 bug 35ms 整个模型的 autograd 图被录制但从未使用
图像转换移到 GPU 数ms
prompt padding 200→96 tokens 5ms 任务标签本来就短，pad 到 200 纯浪费
SigLIP 视觉编码器 ONNX 导出 12ms 121ms 基数上的 10%
Gemma backbone fp16 ~大幅 ONNX 只省 10ms（反常）→ 发现 RTX 5090 Mobile bf16 半速，换 fp16（盯 NaN）后 Gemma 只要 25ms
合计 ~143ms 230 → 87ms，近 3×

延迟位置比延迟总量更重要

  • 修掉 100+ms 的缓冲延迟：性能只小幅提升。
  • 再修 90ms 的相机延迟（该相机有 4 帧固有延迟，换 120Hz 运行大幅摊薄）：性能大幅跳升。
  • 再压 143ms 的推理延迟：巨大提升 + 涌现行为。
  • 三段同为"延迟"，价值完全不同——感知链延迟比推理链延迟更致命。

结果：涌现行为

  • 端到端 <120ms 后，模型复现人类操作员的"快接近→停顿看爪位→小修正→抓取"节奏。
  • 单次 session 中观察到交叉手放置（cross-handed placement）与换手（hand swap）——示教数据中少量包含，模型学到了且能表现出来。
  • 开源为 prism-pi（基于 LeRobot）；作者称桌面版 RTX 5090 + 快相机可做到 sub-50ms，"solidly realtime"。

关联分析

  • 与 DUCK 真机部署直接同构：pi5 上跑 ONNX 策略、STS 舵机速度寄存器带宽、执行层 20Hz 重训决策——全部是"执行链时间结构"命题。本文提供了 VLA 侧的同源证据：延迟/带宽是 sim-to-real gap 的一等公民维度，且它的伤害机制是级联的（near miss → 场景污染 → OOD → 更乱），不是线性精度损失。
  • 与仿真消融方法论冲突：DUCK 训练链的 sim 里同样没建模舵机带宽/通信缓冲/相机帧延迟。本文警示：仿真说"X 无影响"的结论只能信方向不能信数值——凡是仿真消融判"无害"的执行链因素，真机都要留复查位。这直接呼应 H1 乱蹬诊断（起始姿态分布外 + 执行层带宽待标定）的教训结构。
  • 与模型经济学一致：性能不达标时先查代码层浪费（fp32 重复转换/autograd 白录/padding 白算），再谈换硬件换模型——230ms 里 143ms 是纯浪费，不修这些直接上更强 GPU 等于花钱买浪费。
  • 与行为级验收思想共振：用户 0926 定调的"验收看行为级差异而非存活指标"，与本文"benchmark 分数 ≠ 感知质量（VLA 通常能完成但方式难看）"是同一命题的工业界印证。涌现的"停顿-修正"节奏 = 示教数据风格的显影，这提示示教/训练数据里的人类风格只有执行链达标才会显现——反过来说，真机表现"生硬"可能不是模型没学到，而是执行链太慢把它埋了。

趋势判断

  • VLA 部署工程正在独立成学科：训练侧卷算力的边际收益递减后，推理延迟工程（CUDA graph/量化/ONNX/帧率）成为真机性能的下一个洼地。prism-pi 这类"参考实现"开源会成为标配打法。
  • eval 从成功率走向行为质量："能完成但难看"的 VLA 会被市场淘汰，行为级评估（节奏/修正/风格）将从学术概念变成采购指标——与 DUCK 验收体系"行为级对比"超前一致。
  • sim-to-real 研究重点迁移：从"物理参数域随机化"扩展到"执行链时间结构建模"（延迟分布/带宽/帧率进仿真）——延迟消融在真机上重新做一遍，会是下一批论文的富矿。
  • 示教数据的隐藏价值显影：执行链达标后"涌现"出的人类操作风格，意味着数据采集质量（节奏、习惯、策略性动作）比想象中更重要——数据公司（PrismaX 本业）讲这个故事有商业动机，但机制可信。

指南分析

对我们系统的可执行清单：
1. DUCK pi5 部署链延迟分解审计：端到端拆段测量（相机帧到达→obs 组装→ONNX 推理→舵机指令下发→执行），逐段记 ms。重点怀疑：Python 队列/管道缓冲、帧拷贝、串口写入节奏。已有 headless_test.py 链路可加打点。
2. 推理侧免费午餐：确认部署脚本 torch.inference_mode()（对拍 autograd 白录 35ms 的教训）、权重 dtype 转换只在加载时做一次、输入 padding 最小化。ONNX 已含 normalizer 是对的，CUDA graph 可在 pi5 上评估（NPU/GPU 支持度待查）。
3. 仿真消融结论降权使用：今后凡仿真判"无害"的执行链因素（延迟/带宽/背压），真机验收清单里必须留复查项；仿真判"有害"的可信，判"无害"的存疑。
4. 行为级验收固化：延迟优化前后各录一批 rollout，对照"接近-停顿-修正"式行为节奏差异，而只看成功率/存活时长。
