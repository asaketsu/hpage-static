归纳总结

一句话：Anthropic 官方立场——企业 Agent 的「每团队一个子 Agent + 总编排」常是 Conway 定律复刻组织架构，而非能力必需；默认应是一个主循环 + Skills/工具渐进披露，子 Agent 只留给上下文膨胀、真并行、指令冲突三类场景。

三个核心判断：

  1. 多专家编排是组织病不是技术解：各团队自建 Agent 再盖编排层，立即产生上下文管理损耗、子 Agent 膨胀（数百个重叠无人管）、Frankenprompt（人人往系统提示加一句→规则冲突）、局部 eval 稀释（无人守端到端）、延迟翻倍（一家客户实测单循环比多 Agent harness 快约 2×）。
  2. 模型的进步在吃掉脚手架：自 Opus 4.5 起单循环能扛的远超团队预期；Claude Code 面向更强模型把系统提示砍了 80%+（含 Skills/工具渐进披露相关裁剪）；刚性多 Agent 结构反而挡住新模型多干活。原文金句：measure, change one thing at a time, and keep what holds up（度量 → 一次改一件 → 留得住的才留）。
  3. 折入有工程闭环：不是一把梭重写——先建端到端 eval（10 条黄金例即可起步）→ 子 Agent 降级为工具（主 Agent 持对话）→ 逐个折成 Skills + MCP 工具，一次一个，比总分更看「哪些任务翻转了」；折入版更差才保留子 Agent。

内容整理：Claude 官方「折入主循环」方法论

1. 大组织建 Agent 的五种失败模式

失败模式 机制 症状
上下文管理 跨 Agent 来回传摘要 细节丢失、传话游戏保真度递减
子 Agent 膨胀 每团队各养一个 数百个重叠子 Agent，无标准无 owner
Frankenprompt 人人往系统提示加一句 规则冲突、语气不一
局部 eval 各优化子任务 无人维护端到端集，领导看被稀释分数
延迟 嵌套模型循环叠加 单循环实测约 2× 更快

另一常见过度设计路径：意图分类 → 固定多步推理 → 用户分群桶 → 分叉推荐 → 再盖编排。反馈共识：一条清晰系统提示 + 4-5 个瘦数据工具 + 硬输出护栏就盖住大半场景。

2. 子 Agent 仍适用的三个充要场景

  • 单循环因上下文膨胀出现可测的性能下降
  • 多任务需真并行，用完即丢的新鲜上下文窗
  • 单 Agent 选不好工具或系统提示指令打架

边界案例：前沿研究、核验（generator-verifier）、模块化权限仍适用；Anthropic 自家 multi-agent research system 仍在用。「每个问题类型/每个团队一个子 Agent」= Conway 定律，不是能力上限。

3. 目标形态：单循环 + 渐进披露

用 Skills 渐进披露上下文、用 tool search 渐进披露工具——先见短描述，需要再全量加载。三点理由：

# 理由 证据
1 共享上下文更好答 长程任务前几步结果留在同一窗，比子 Agent 回传摘要更能串起来；更少上下文窗、更少有损交接
2 渐进披露防膨胀 不必把一切塞进超长系统提示（这是以前拆子 Agent 的主因）；Claude Code 对更强模型砍系统提示 80%+
3 模型更强 Opus 4.5 起单循环承载力超预期；Opus 5.5/Fable 5.1 无法关 thinking，新模型自述进度、自检，部分 harness 冗余

循环规格（原文设计）：

  • 一个模型、一个上下文窗、开放式工具循环；harness 只设轮次/成本预算与写门禁
  • 每轮模型批量发工具调用，harness 并行执行，原样结果回同一模型
  • 写计划的模型也是执行的模型，可中途改计划（这是与编排-专家结构的本质差异）
  • 排序与领域流程 → Skills；校验/审批/记忆查找等硬限制 → 工具；廉价且几乎总相关的步骤仍可用代码预载（如实体解析）

治理配套：一个小而集中的中央团队守系统提示与端到端质量，新工具与 eval 上线前先 vet。若走多 Agent：从最简可工作模式起步，按上下文边界拆（独立研究路径、干净接口组件、黑盒核验），勿按问题类型拆——后者每传一次保真度掉一截。

4. 迁移路径（四步，一次一个）

  1. 任务完成度 eval：中央一份端到端集 + 各 Skill 配小集（10 条黄金例起步）；编排期盯路由准确率，折入后盯「是否加载对 Skill/调对工具」；难回放的内部系统用关键事件时间戳做定向回放。
  2. 合并领域 Agent：优先合「链式产出、同数据、常连调」的对（生产流量里 A 后常跟 B = 紧耦合对）。
  3. 子 Agent 当工具：主 Agent 继续对用户说话，子 Agent 只回结构化结论，主 Agent 对真数据核验其结论；仅当子 Agent 必须直接对用户说话才全量交接。这是折入前的基线（无需重写），但残留三损：各自 prompt/owner/eval、有损摘要、嵌套循环延迟。
  4. 折成 Skills + MCP 工具：一次折一个，对比有无子 Agent；不只看总分，看哪些任务翻转了。反例警示：折入后延迟降了，但主 Agent 自己拿订单查询工具答完，没再问物流专员要送达日——原流程断裂，且该断裂 2 跑里只现 1 次（每任务必须多跑几次）。

5. 多团队共养一个 Agent

所有权从「各养一个 Agent」转为「养 Skills/工具」：

载体 放什么 纪律
MCP 工具 动作、实时数据、固定形状结果 按用户意图分组（勿一 API 一工具）；系统提示内工具定义 超 30-50 个选型劣化 → tool search + 延迟加载；前置条件与权限放工具内检查、返回模型可读的拒绝
Skills 团队怎么干活：步骤、规则、判断 各队 DRI 保证成形、不重叠、带 eval；用 /skill-creator 自建审计剪枝、/skill-doctor 看成本与使用率删死重
知识库 偶尔才要的政策/指标/规格 放搜索或 Skill 内参考文件；禁止代码检索后硬贴进 prompt

6. 配套工具链（官方 migration kit）

趋势判断

  1. Anthropic 的立场演化有清晰轨迹：2025-06 multi-agent research system（多 Agent 高光）→ 2026 技能化（Skills/Agent Skills 开源）→ 2026-10 本文（折入主循环）。不是自我否定——多 Agent 研究系统仍在用——而是「模型每强一代，脚手架就减一层」的减法主线。Claude Code 系统提示砍 80% 与本文同属这条线。
  2. 治理权重从「编排设计」移向「eval 与门禁」：本文把编排层的注意力整个搬到 eval 体系（中央端到端集 + 各 Skill 小集 + 任务翻转检查 + 多跑防偶发）。未来 Agent 团队的核心资产不是架构图而是黄金例集。
  3. 组织病显性化：Conway 定律从软件架构蔓延到 Agent 架构，「各团队养 Skill 而非养 Agent」的所有权转移，本质是把接口边界从组织边界改为上下文边界——这会成为企业 Agent 落地的组织变革命题。
  4. 对 Skill 生态：skill-creator/skill-doctor 工具化意味着 Skill 库治理进入「可测量、可修剪」阶段，Skill 会从文档形态演进为带 eval、带成本核算的一等工程资产。

指南分析

架构评审清单（新 Agent 设计先过这四问）：

  1. 为什么不是一个主循环？（对照三条件：上下文膨胀/真并行/指令冲突——都不满足就回单循环）
  2. 子 Agent 是按上下文边界拆的还是按问题类型/团队拆的？（后者 = 传话游戏，重拆）
  3. 系统提示里有多少条是写给旧模型的？（跑 prompt-audit 式审查，砍掉只会让 Agent 更慢更僵硬的补偿规则）
  4. eval 覆盖：每条生产 Agent 链有任务？每条不可破规则有任务？每任务多跑几次？

迁移操作序（从既有编排系统迁出）：

  • 第 0 步：建 10 条黄金例的端到端 eval（中央 owning），先测当前编排系统做基线
  • 第 1 步：子 Agent 降级为工具（不重写，拿折入前基线）
  • 第 2 步：挑最常连调的一对，合并成单领域 Agent
  • 第 3 步：一次一个把子 Agent 折成 Skills+MCP 工具，hillclimb 对比；看任务翻转不只看总分；折入版更差才保留
  • 全程纪律：度量 → 一次改一件 → 留得住的才留

对我们系统的两条落地项：

  • P0（低成本）：prompt-audit 思想自审——清点系统提示/skill 描述里为旧模型（glm-4.x 时代）写的补偿指令，模型已升 5.3 的今天逐条判废
  • P1：笔记/技能的「任务翻转」检查意识——吸收分析类改动后不只看总分，grep 是否有原流程断裂（订单查询案例的教训通用化）
