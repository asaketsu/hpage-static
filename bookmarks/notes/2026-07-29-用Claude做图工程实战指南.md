## 核心结论

图工程比听起来简单：**节点（node）= 一件工作，边（edge）= 依赖关系。** 大多数人的当前工作流已经是一个图——只是个糟糕的线性链。图工程的第一步不是学新东西，而是审视现有流程，问："每一步真的需要等前一步吗？"大多数时候，不需要。

---

## 一、图到底是什么？

| 概念 | 定义 |
|------|------|
| **Node（节点）** | 一个工作单元——一个 Agent、一个任务、一个输入一个输出。越小越精准越有用 |
| **Edge（边）** | 依赖关系——第二个节点真正需要第一个节点的输出。**不是"按顺序发生"** |

> 节点做工作，边传递它们之间流动的东西。图工程的一切就是在不同尺度上应用这两个理念。

---

## 二、你的当前工作流已经是图了（只是很烂）

### 线性链 vs 重画的图

```
❌ 线性链:
  Research → Summarize → Write → Check sources → Format → Publish
  六步排队等待，总时间 = 六步之和

✅ 重画为图:
  [Research + Check sources]（同时）→ Summarize → [Write + Format]（同时）→ Publish
  同样的工作，更少等待，独立任务不再排队
```

> 图工程的第一步不是学新东西。是看已有流程，问：**每一步真的需要等前一步吗？**

---

## 三、假边测试（The Fake-Edge Test）

最核心的实操工具——5 分钟内对任何工作流运行：

| 步骤 | 操作 |
|------|------|
| 1 | 把每一步写成一个方框 |
| 2 | 在连续步骤间画箭头 |
| 3 | 对每个箭头问：**步骤 A 的数据真的流入步骤 B 吗？** |
| 4 | 如果是 → 保留箭头（真依赖） |
| 5 | 如果否 → **删除箭头（假边）** |
| 6 | 没有入边的 → 可以立即开始 |
| 7 | 没有出边的 → 最终输出 |

> 你几乎会在任何工作流中找到 2-3 个假边。每个假边都是你在白白送出的时间。

**示例**："审查文件 A 的 Bug，然后审查文件 B 的 Bug"——看起来是顺序，但 B 从不看 A 的返回。同时运行，总时间 = 慢的那个，而非两个之和。

## 四、钻石模式（The Diamond）

> 一个节点扇出到多个并行节点，它们都汇入一个收敛节点——画出来像个钻石。

```
         ┌── Read Source 1 ──┐
Search ──┼── Read Source 2 ──┼── Synthesize
         └── Read Source 3 ──┘
```

| 规则 | 说明 |
|------|------|
| **并行节点必须真正独立** | 没有伪装成真边的假边 |
| **收敛节点必须真正需要全部** | 如果只需要一个，其他是浪费 |

> 钻石是工作流能取的最快形状。出现在任何"从多处收集→合并"的场景：研究流水线、代码审查、市场分析。

---

## 五、图在哪里悄悄失败

### 两个失败模式

| 失败 | 说明 |
|------|------|
| **坏节点未被发现** | 三个并行源，一个返回垃圾 → 垃圾直接流入综合节点 → 综合产出基于坏材料的自信回答 |
| **级联错误** | 线性链中坏步骤立刻可见；图中坏输出与好输出混合 → 错误更难追踪 |

### 解法：Checker Node（检查节点）

```
[并行节点层] → Checker Node → [收敛节点]
```

检查节点坐在并行层和收敛点之间，**唯一工作是评估每个输出**——不综合、不写、不做主要工作。

**检查节点应捕获的 5 类问题**：

1. 空或 null 输出
2. 相互矛盾的输出
3. 偏离原始任务的输出
4. 置信度太低的输出
5. 会破坏综合节点解析的格式错误

> 没有检查节点的图 = 假设上游一切正常。这个假设失败的频率超出你的预期。

## 六、静态图 vs 动态图

| 维度 | 静态图 | 动态图 |
|------|--------|--------|
| **结构** | 预先定义，固定 | 运行时自生长 |
| **预测性** | 高 | 低 |
| **调试** | 容易 | 难（运行的结构 ≠ 你画的） |
| **适合** | 可重复 + 结构不变 | 范围取决于发现 |

### 选择规则

| 用静态图 | 用动态图 |
|---------|---------|
| 任务可重复 | 范围取决于沿途发现 |
| 速度和可预测性重要 | 某些节点需根据输出决定下一步 |
| **永远先用静态**，碰壁才转动态 | 需要审计精确运行记录的**永远不用动态** |

> 大多数感觉需要动态图的工作流，其实只需要设计得更好的静态图。

---

## 七、线性 vs 图对比表

| 维度 | 线性 | 图 |
|------|------|-----|
| 设置时间 | 低 | 较高 |
| 总运行时间 | 慢 | **快** |
| 易调试 | ✅ 是 | 较难 |
| 中途错误处理 | 差 | **好（检查节点）** |
| 一次性任务 | ✅ 是 | 过度设计 |
| 可重复工作流 | ✅ 是 | **更好** |
| 随任务增长扩展 | ❌ 否 | **✅ 是** |

> 对于跑一次的一次性任务，线性几乎总是更快构建和运行。图在时间节省可复利、或中途错误代价高到检查节点值回成本时才值得。

## 八、用 Claude Code 构建

### workflow 关键字

> Claude Code 有一个 `workflow` 关键字。没有它，Claude 把 Prompt 当序列逐步执行。有它，Claude 解析结构、识别无依赖的节点、自动并行运行。

```python
workflow: research-and-compare

nodes:
  research_a:
    task: "Research competitor A's pricing, features, and recent news"
    output: competitor_a.md

  research_b:
    task: "Research competitor B's pricing, features, and recent news"
    output: competitor_b.md

  research_c:
    task: "Research competitor C's pricing, features, and recent news"
    output: competitor_c.md

  checker:
    task: "Review each research file. Flag any that are incomplete or off-topic."
    depends_on: [research_a, research_b, research_c]
    output: checker_report.md

  compare:
    task: "Using the research files, write a structured comparison."
    depends_on: [checker]
    output: comparison.md
```

**三个要点**：

1. `research_a/b/c` 没有 `depends_on` → Claude 同时启动三个
2. `checker` 依赖全部三个 → 等全部完成才运行
3. `compare` 只依赖 `checker`，不直接依赖研究节点 → 检查节点是守门人

> `depends_on` 是你设计任何图唯一需要理解的东西。无依赖 = 并行。有依赖 = 等待。

## 九、思维转变

| 线性思维 | 图思维 |
|---------|--------|
| "先做什么？" | "**什么真正需要等什么？**" |
| Prompt 告诉 Claude 按顺序做什么 | Prompt 告诉 Claude 每部分需要什么，让它自己算顺序 |
| 换一个节点会打破整条链 | 换一个节点不影响其他 |

### CLAUDE.md 项目级默认设置

```python
# Workflow defaults

When running a workflow:
- All nodes without depends_on run in parallel by default
- Checker nodes should flag incomplete outputs, not silently pass them
- Output files go to /outputs with the node name as filename
- If a node fails, pause and report before continuing
- Never merge outputs from flagged nodes into the final synthesis
```

> 一个文件设一次，项目里每个 workflow 都继承。
