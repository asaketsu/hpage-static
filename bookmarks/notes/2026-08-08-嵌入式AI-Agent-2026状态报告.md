# 2026 嵌入式 AI Agent 状态报告 — MCU 上的 Sense-Think-Act 循环

> **来源**：Shawn Hymel《State of Edge AI on Microcontrollers in 2026》+ ForestHub《AI Agents for Embedded Systems》
> **日期**：2026-08-08
> **标签**：TinyML / Edge AI / ESP32 / STM32 / 嵌入式AI / MCU Agent

## 一句话定义

> 在微控制器（MCU）上，"AI Agent" 不是运行 LLM 的聊天机器人，而是一个**自主的 sense-think-act 循环**——结合传感器输入、ML推理、决策逻辑和执行器控制，在无人工干预、无云端依赖的情况下持续运行。

---

## 内容整理

### MCU 上的 "Agent" 到底是什么

2024-2025 年的"AI Agent"通常指基于 LLM 的系统——具备工具调用、记忆维护、目标追逐能力。但这种模型无法直接移植到 MCU 上。MCU 只有 KB 级 RAM（不是 GB），不能运行语言模型。

MCU 上的 AI Agent 是完全不同的架构——更接近机器人学而非聊天机器人：

- **专用 ML 模型**（异常检测、分类、目标检测）
- **基于规则的决策逻辑**（阈值、状态机、条件执行）
- **物理动作**（GPIO控制、电机驱动、继电器切换、告警传输）
- **反馈**（动作结果反馈到感知管线）

### 从推理到 Agent 的四级进阶

| 级别 | 架构 | 说明 |
|------|------|------|
| Level 1: 推理 | `传感器 → 模型 → 预测` | 模型运行，产出结果，有人决定怎么做。这是"串口监视器 Demo" |
| Level 2: 反应系统 | `传感器 → 模型 → 决策逻辑 → 动作` | 固件根据预测自动响应（超阈值→切GPIO/发MQTT）。当前大部分生产级 Edge AI |
| Level 3: 有状态 Agent | `传感器 → 模型 → 状态机 → 条件动作 → 反馈 → 传感器` | 维护跨推理周期的状态。记住异常分数持续上升了4小时。从"建议"升级到"警告"再到"紧急"基于趋势而非单次读数 |
| Level 4: 多 Agent 系统 | `Agent A ←→ 协调协议 ←→ Agent B` | 多个 MCU 上的 Agent 协作。振动监控 Agent 与另一个 Agent 共享状态，同时异常→推断系统性原因 |

### Agent 架构四子系统

**Sense（感知）**

```c
typedef struct {
    float vibration_rms;
    float temperature_c;
    float current_a;
    uint32_t timestamp_ms;
} sensor_reading_t;
```

感知任务在固定调度上运行（10Hz~1kHz），读取原始 ADC/I2C 数据，执行校准，写入共享环形缓冲区。多传感器时需同步——确保推理操作的是时间对齐的数据。

**Think（决策）**

```c
agent_decision_t agent_think(sensor_reading_t* readings, int count) {
    // 预处理：计算振动频谱 FFT
    float spectrum[128];
    compute_fft(readings, spectrum, count);

    // 运行异常检测模型
    float anomaly_score = run_anomaly_model(spectrum);

    // 有状态逻辑：追踪分数趋势
    update_score_history(anomaly_score);
    float trend = compute_trend();

    // 决策：当前分数+趋势
    if (anomaly_score > CRITICAL_THRESHOLD) {
        return DECISION_CRITICAL;
    } else if (anomaly_score > WARNING_THRESHOLD && trend > 0) {
        return DECISION_WARNING;
    }
    return DECISION_NORMAL;
}
```

核心差异：**决策逻辑不只是模型输出上的阈值**。它整合状态（分数历史）、趋势（是否在恶化）、交叉参考（振动异常+温度上升=轴承故障，电流异常+振动正常=电气故障）。

**Act（执行）**

| 决策 | 动作 | 硬件 |
|------|------|------|
| NORMAL | 定期更新仪表盘 | MQTT publish via Wi-Fi |
| WARNING | 发送告警，提高采样率 | MQTT + 定时器重配置 |
| CRITICAL | 触发本地告警，通知，记录 | GPIO继电器 + MQTT + Flash日志 |

动作也能修改 Agent 自身行为：
- **自适应采样**：异常发展时提高采样率，正常时降回低频——省电
- **模型级联**：平时跑轻量筛选模型，被触发后加载更准确的分类模型。ESP32-S3 的 PSRAM 支持运行时加载不同模型

**Learn（受限）**

MCU 上的学习能力非常有限。全模型重训练需要反向传播和优化器状态——超出 MCU 内存。

当前可行的：
- **阈值自适应**：根据确认的误报/漏报调整决策阈值
- **基线漂移补偿**：随季节变化缓慢更新"正常"参考值
- **统计模型更新**：对基于统计边界的模型（非神经网络），增量更新均值和方差

全模型重训练在设备外完成——PC 或云端——通过固件更新部署。

### 预测性维护 Agent 实例

**硬件**：ESP32 + MEMS加速度计 + MQTT broker

**状态机**：
```
MONITORING → (异常分>0.7) → ALERT
ALERT → (分数<0.5 持续1小时) → MONITORING
ALERT → (分数>0.9 或 上升趋势>2小时) → CRITICAL
CRITICAL → (维护确认 via MQTT) → MONITORING
```

**各状态行为**：

| 状态 | 采样率 | 推理间隔 | 动作 |
|------|--------|----------|------|
| MONITORING | 100 Hz | 每10秒 | 定期 MQTT 状态报告 |
| ALERT | 500 Hz | 每2秒 | MQTT 告警 + LED 警告 |
| CRITICAL | 1 kHz | 每500ms | 继电器告警 + 持续 MQTT + 原始数据记录 |

这不只是一个模型在循环跑。Agent 根据观察结果调整行为，通过定义的阶段升级，在每个阶段采取不同物理动作。

### 多传感器融合 Agent

**硬件**：STM32H7 + 加速度计 + 热电偶 + 电流互感器

**管线**：
1. 读取三个传感器（同步到公共时间戳）
2. 振动异常模型 → score_v
3. 热趋势模型 → score_t
4. 电流特征模型 → score_c
5. **融合逻辑**：加权组合+领域规则

**融合规则编码工程知识**：
- `score_v > 0.8 AND score_t > 0.6`：可能是轴承故障——摩擦导致振动+发热
- `score_c > 0.8 AND score_v < 0.3`：可能是电气故障——电流异常但无机械振动
- `三者 > 0.5`：可能是外部原因——电源问题或环境温度骤升

融合逻辑是 Agent 智能所在——不在任何单一模型中，而在模型如何与领域知识组合。

### 2026 MCU Edge AI 生态格局

**厂商框架**（垂直整合）：
- **STMicroelectronics**: STM32Cube.AI + NanoEdge AI Studio
- **NXP**: eIQ ML 开发环境
- **Renesas**: Reality AI Tools + RUHMI Framework
- **Nordic**: Edge AI Add-on for nRF Connect SDK
- **Espressif**: ESP-DL/NN

**开放推理运行时**：
- **Google LiteRT for Microcontrollers**（原 TFLite Micro）——最广泛使用的 MCU 推理引擎，裸金属/RTOS环境，静态内存竞技场
- **Microsoft ONNX Runtime**——擅长有OS的边缘设备，但无官方 MCU 裸金属运行时
- **Apache microTVM**——编译器驱动的 MCU ML 部署，但已不再积极维护

**端到端平台**：
- **Edge Impulse** → 2025年被 Qualcomm 收购
- **Neuton.AI** → 2025年被 Nordic 收购
- **Imagimob** → 2023年被 Infineon 收购

**趋势**：硅片厂商正在收购工作流层，使 Edge AI 成为"平台的一部分"而非外部依赖。

### 硬件加速器趋势

2025 年的关键发展：
- **STM32N6**：集成神经加速器的高端 MCU，面向视觉和 ML，保持 MCU 式编程模型
- **NXP i.MX RT 系列**：高性能 Cortex-M + DSP/ML加速，模糊 MCU 和应用处理器界限
- **Ethos-U**：出现在 ST/NXP/Renesas 的高端 MCU 和跨界设备中，但配厂商专属软件栈
- **CMSIS-NN**：利用 SIMD 指令和缓存感知内存访问，让"普通"Cortex-M 设备也能高效运行

## 归纳总结

**核心洞察**：MCU 上的 AI Agent 不是缩小版 LLM Agent，而是完全不同的架构——更接近机器人学的 sense-think-act 循环。智能不来自基础模型，而来自专用 ML 模型 + 规则决策 + 物理动作 + 反馈的组合。

**四级进阶路径**：推理（Level 1）→ 反应系统（Level 2，当前生产主流）→ 有状态 Agent（Level 3，趋势追踪+状态升级）→ 多 Agent 协调（Level 4，早期阶段）。

**最大约束是内存**：ESP32 的 520KB SRAM 跑三模型 Agent 几乎没有余量。内存规划必须前置。

**核心价值在融合逻辑**：Agent 智能不在单一模型中，而在多传感器交叉验证 + 领域知识编码。振动+温度同时异常→轴承故障；电流异常但振动正常→电气故障——这种融合推理才是 Agent 的价值。

## 趋势判断

- **2026 年 MCU Edge AI 继续稳步成熟，不会有爆发时刻**——工具链改善、文档改善、更多芯片内置 ML 加速，但内存、功耗、实时性的基本约束不变
- **厂商垂直整合加速**：Qualcomm 收 Edge Impulse、Nordic 收 Neuton.AI、Infineon 收 Imagimob——生产级最优路径将优先支持自有芯片
- **多 Agent 协调框架是下一个突破口**：RTOS 并发原语已就绪（FreeRTOS on ESP32），模型优化已有（Cube.AI），缺失的是 Agent 协调层
- **Agent 不会取代领域专家**：恰恰相反，随着 Edge AI 普及，领域知识和系统思维变得更值钱——知道传感器在真实环境中的行为、数据如何漂移、模型如何失败
- **$5 MCU 上跑自主 AI Agent 的交叉点正在形成**：ML推理、RTOS调度、无线通信三大构建块已就绪，连接它们的集成工具正在构建中

## 关联分析

- **与 OttoClaw 项目的直接关联**：用户刚分析过的 OttoClaw（ESP32-S3 AI桌面机器人）正是本文 Level 3 Agent 的实例——22种AI自主情绪=有状态决策，5阶段关系成长=跨周期状态维护，6路舵机AI控制=物理动作层。OttoClaw 的 Agent Loop 就是本文描述的 sense-think-act 循环
- **与 ESP32 短线选股 Agent 的异同**：量化选股 Agent 在云端跑（Python+腾讯API），而嵌入式 Agent 在 MCU 上跑——但都是"推理→决策→动作"模式。区别在于嵌入式 Agent 受到严格的内存/功耗约束
- **与 Jetson Orin 平台的层级关系**：ForestHub 明确定义了两层——MCU Tier（ESP32/STM32，KB级RAM）和 Edge Agent Tier（Linux边缘设备如 Jetson，跑小 LLM）。用户的 Jetson Orin 属于后者——可跑 LiteRT-LLM / Ollama 等本地推理
