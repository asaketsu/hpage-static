一、模型定位：不是小号 ChatGPT，是 AI 零件

Qwen3.5-0.8B（2026年3月2日发布，同批还有 2B/4B/9B）：

规格 数值 工程含义
语言参数 ~8 亿（0.8B） 定义多模态模型的部署下限，而非 Qwen3.5 能力上限
类型 带视觉编码器的因果语言模型 原生图文多模态，不是纯文本小模型
能力 问答/OCR/文档理解/图像描述/空间定位/视频理解/工具调用 覆盖端侧常见感知+理解任务
架构 24 层混合：Gated DeltaNet 线性注意力 ↔ 普通注意力交替 线性注意力省内存，但OpenCL 后端不支持（实测踩坑）
原生上下文 262,144 token 是架构窗口上限，不是"手机可用上下文"——长文本还有 KV 缓存/视觉 token/运行时内存开销
语言 201 种语言和方言 多语言场景覆盖广

官方克制表态（比参数更重要）：模型卡推荐用途是原型验证、任务特定微调、研究和开发——官方没有把它包装成通用主力模型。

基准暴露的边界

基准 得分 判读
BFCL-V4（工具调用） 25.3 工具调用可用但要窄任务+微调
TAU2-Bench（通用 Agent） 11.6 不能当自主 Agent 用
AA-LCR（长上下文） 4.7 能接长文本 ≠ 能在长文本里持续做对复杂决定

核心命题：小参数模型的强项不是无所不知，而是在一个边界清楚的任务里把成本压到足够低。

二、四类已验证的真实用法

真实项目的共同需求：本地运行、数据不出设备、任务可收窄。

第一类：浏览器/手机离线助手

  • WebML Community WebGPU 演示：浏览器首次加载 ~850MB 后本地处理图片和指令
  • Gerbil SDK：浏览器内聊天、图像描述、嵌入任务
  • Qualcomm AI Hub：预导出文件 + GenieX 部署路径
  • MNN 实测（Redmi Note 14+ / Snapdragon 7s Gen 3）：21.2 token/s 解码、792MB 峰值内存——中端 Android 离线对话已不是 PPT
  • ⚠️ 同测试 OpenCL 没跑通：混合线性注意力运行时支持缺失——模型够小是一回事，NPU/GPU 算子能不能接住是另一回事

第二类：企业内部窄任务

  • MLX LoRA 微调 Text-to-SQL（Mac 上完成微调）
  • 分类与路由（Transformers 未原生注册序列分类头，社区在推动）
  • 特征：输入格式固定，输出可被数据库语法检查器/业务规则二次验证——模型只需把人话稳定翻译成结构化结果

第三类：专业知识实验

  • 孟加拉法律问答：2,165 条双语问答微调 0.8B/2B/4B 对比
  • Android 离线文档问答
  • 定位：实验和辅助检索，不是让 0.8B 当律师。可用形态 = 模型理解问题+整理材料，检索系统提供原文，规则或人工做最终判断

第四类：机器人/检索系统的小部件

  • 移动机器人语义区域地图：吞吐 +3.3 token/s、延迟 -21.7%（vs 几何地图策略）
  • Prism-Reranker：0.8B~9B 构建检索重排器，同时输出相关性+贡献+证据
  • 桌面宠物（llama.cpp + Electron）：分析投喂文件改变宠物人格——低风险、强个性、离线交互很符合能力半径
  • 共同点：模型不站在系统中央发号施令，而是完成一个具体步骤

三、六个值得做的方向（原文 + 工程拆解）

方向 1：端侧隐私助手

本地摘要、日记整理、文件分类、图片描述、离线问答。数据不出手机/电脑。

工程要点：
- 部署链：llama.cpp（GGUF）/ MNN（Android）/ WebGPU（浏览器）
- 关键决策：量化档位（Q4_K_M 平衡质量/体积）；峰值内存预算（实测 ~792MB 参考线）

方向 2：结构化信息处理

意图分类、内容路由、字段抽取、Text-to-SQL、固定格式生成。

工程要点：
- 输出越容易用规则校验，小模型越靠谱——SQL 可语法检查、JSON 可 schema 校验、分类可白名单过滤
- 微调成本：MLX LoRA 一张 Mac 即可完成
- 这正是 Needle 2（前篇笔记）"字节级语法约束"的思路：用确定性校验兜住概率性输出

方向 3：垂直领域微调

设备手册问答、企业术语、客服分流、轻量 RAG。

工程要点：
- 拼的不是百科知识，而是少量高质量任务数据（法律问答实验仅 2,165 条）
- 微调后必须配独立评估集，防"训练集表演"

方向 4：视觉轻应用

票据初筛、界面理解、图片描述、简单 OCR、无障碍辅助。

工程要点：
- 官方视觉基准兜底：OCRBench / RefCOCO / RealWorldQA 已有基本能力
- RefCOCO 79.3（思考模式）说明指代表达定位可用

方向 5：工业巡检与开放目标识别 ⭐（原文重点）

低空无人机、移动巡检机器人、固定监控、车载/船载/矿载视觉。

三个易混任务的区分（原文精华）：

任务 定义 例子 输出
OVD（开放词汇目标检测） 按临时输入的类别名找一类目标 无人机找"路面积水"“未戴安全帽的人" 边界框
REC（指代表达理解） 按属性/位置/关系描述定位特定一个对象 "左侧第二辆白色汽车" 边界框
VQA（视觉问答） 围绕图片回答问题 "图中有几名工人""配电柜是否冒烟" 文本（无框）

一句话：OVD 找一类，REC 找那一个，VQA 回答问题。

依据（官方基准）：
- ODinW13 开放词汇检测：31.6（思考）/ 33.2（非思考）——基础能力已具备
- RefCOCO：79.3 / 77.8——按描述定位物体可用
- RealWorldQA + 多项视频理解任务已测

应用想象：工业巡检/应急管理/城市治理/安全生产/矿山安监——用户临时描述"冒烟的配电柜""禁停区车辆"，模型理解开放指令+定位候选+生成异常说明。相比每加一个类别就重新标注训练一个检测器，这条路线想象空间大。

⚠️ 边界声明：官方基准证明的是基础能力，不是某台无人机已能 7×24 稳定巡检。真正部署还要补：目标芯片输入分辨率、量化精度、单帧延迟、峰值内存、温升功耗、误检漏检、连续运行曲线。

方向 6：具身设备的语义模块

机器人地图加语义、解释传感器状态、自然语言→有限动作参数。

工程要点（稳妥组合）：

0.8B → 开放语义 + 人机交互（低频）
传统检测器 → 高频固定目标（可验证）
规则系统 + 控制器 → 安全边界（确定性）

不是让 0.8B 独自控制设备。

反面清单：暂时别交给它单独完成

开放域知识问答、复杂编程、多轮长链路 Agent（TAU2 11.6 分摆着）、医疗诊断、法律结论、无人值守高风险控制。

"能运行"和"能负责"是两条完全不同的线。

四、工程落地的四问过滤器（动手前自检）

原文给出的判断框架，可直接复用为立项检查单：

① 错误能否自动发现？（输出可规则校验？）
② 数据是否必须留在本地？（隐私/合规硬约束？）
③ 任务能否通过微调收窄？（边界清楚的任务？）
④ 换成 2B 后，能力提升是否值得多付一倍以上的内存和延迟？

四个问题里答不上两个，就别被 0.8B 这个数字带着跑。

五、工程使用总结：与我的系统架构对照

5.1 现实系统架构（原文结论）

0.8B → 开放语义、异常描述、本地交互（端侧）
传统检测器 + 规则 + 控制器 → 可验证部分（确定性）
云端大模型 / 人工 → 复杂问题（升级路径）

这不是能力降级——大量真实软件功能不需要模型写论文做奥数，只需要看懂一张图、判断一句话类别、填对几个字段、断网时给个够用的回答。

5.2 与 Hermes 生态的映射（工程借鉴）

文中场景 我的系统对应 落地方式
端侧隐私助手 Jetson 本地推理（nexa-local-inference） Qwen3.5-0.8B GGUF 进 Ollama，做语音唤醒后的低成本低延迟预处理
结构化抽取 飞书消息→结构化指令 分类/路由任务微调，输出过 JSON schema 校验
检索重排（Prism-Reranker 思路） RAG 索引重排 0.8B 做 first-stage rerank，降低主模型 token 消耗
工业巡检 OVD/REC 航空结构巡检研究延伸 无人机巡检图片的开放词汇初筛（"裂纹""腐蚀""铆钉缺失"）
具身语义模块 具身智能研究方向 VLA 系统的语义层：自然语言→有限动作参数，安全边界交给规则
置信度升级链 Fallback 三级链 0.8B 低置信度 → qwen3.7-flash → glm-5.2 → 人工

与 Needle 2 笔记的互补：Needle 2（14MB）证明了极端压缩下工具调用可行；Qwen3.5-0.8B 提供了视觉多模态和更强语言能力，两者是端侧 AI 零件光谱上的两个档位——按内存预算（28MB vs ~800MB）和任务复杂度选型。

5.3 选型速查

场景 选 0.8B 还是 2B？ 判据
分类/路由/固定格式 0.8B 输出可校验，多付一倍内存不值
离线对话/文档问答 看 RAM 中端手机 0.8B（792MB 峰值参考），旗舰可 2B
视觉定位/巡检 0.8B 起步 RefCOCO 79 够原型，量产再评估 2B
复杂 Agent/长链路 都不要 TAU2 11.6 / AA-LCR 4.7 明示边界
