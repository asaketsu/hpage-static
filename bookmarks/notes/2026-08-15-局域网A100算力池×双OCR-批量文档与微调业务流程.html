一、内容整理

1.1 场景定义与核心问题

给定条件：局域网（无公网）内一台 A100 80G 服务器；客户端为 Jetson/PC；文档量大（万级 PDF 扫描件）；有两类需求——①批量文档分析（扫描件→结构化文本）②模型微调（行业字体识别差、领域术语多）。

核心问题拆解：
1. 依赖冲突：PaddleOCR（PaddlePaddle 框架）与 Unlimited-OCR（torch 2.10 + py3.12）不能共存一个环境
2. 算力调度：推理常驻 vs 训练窗口的 GPU 分时
3. 客户端异构：Jetson/PC/手机都要能零门槛调用
4. 断点续传：万级文档批处理必须可中断可恢复
5. 训练数据闭环：解析结果如何回流为微调数据

1.2 架构方案（三层分工）

客户端层（Jetson/PC，requests 即可）
   └─ batch_pipeline.py：扫描→上传→轮询→下载，本地 state.json 断点续传
网关层（A100 :8800，FastAPI + SQLite）
   ├─ 路由规则：图片/短PDF→Paddle；>3页长文档→Unlimited-OCR
   ├─ 幂等去重：file_hash+engine 相同直接复用结果
   └─ 崩溃恢复：启动时 running→queued 重排队
引擎层（进程隔离）
   ├─ PaddleOCR :8801（venv，PP-OCRv6+StructureV3，~4G 显存常驻）
   └─ Unlimited-OCR :8802（vLLM Docker，3B 模型 bfloat16，~28G 显存）

关键决策依据：
- Paddle 用 venv（微调需直访数据集，CUDA 与宿主兼容）；UOCR 用 Docker（官方镜像免配环境，torch 2.10 隔离）
- 显存分时：白天推理（4+28G），夜间 23:00 systemd timer 停 UOCR 容器腾 28G 给训练，早 7 点自动恢复
- 长文档 >40 页自动分卷（防超 32K token），结果拼接

1.3 批量文档处理流程（分析业务线）

操作流程（三条命令）：

# A100 侧一次性部署（30 分钟）
bash server/setup/00_env_check.sh && bash server/setup/01_install_paddle.sh \
  && bash server/setup/02_install_uocr.sh && bash server/setup/03_systemd.sh

# 客户端批量（万级 PDF）
python3 client/batch_pipeline.py --source /mnt/scans --gateway http://192.168.x.x:8800

# 单文件验证
python3 client/quick_client.py --file 合同.pdf --gateway http://192.168.x.x:8800

断点续传机制：客户端每处理完一个文件写 state.json；网关侧同 hash 任务去重——双向断点，任一侧重启都不重算。

结果双格式：Markdown（人读/RAG）+ JSON（坐标/置信度/引擎元数据）。

1.4 模型微调流程（训练业务线）

PaddleOCR 场景微调（适用：票据/行业字体/固定版式识别差）：

200-2000 张标注样本 → Label Studio 标注 → prepare_data.py 转 Paddle 格式
→ finetune.sh（PP-OCRv6 mobile rec，lr=1e-4，epochs=50，A100 约 1h）
→ CER 评测 ≤1% 达标 → rec_model_dir 指向新模型重启服务

Unlimited-OCR SFT（适用：领域术语/表格口径，合同研报类）：

50-100 份人工精校金标准 → prepare_sft_data.py（多页卷分+单页 gundam 双样本）
→ swift_sft.sh（ms-swift LoRA rank16，A100 80G batch2×grad8×3epochs）
→ edit distance 评测（改善<2%=数据不足，扩金标准）
→ swift export 合并 LoRA → 重建 vLLM 容器

数据飞轮：解析结果人工抽检 → 低置信度样本回流标注池 → 每月增量微调 → 版本化存档。

二、查询拓展

2.1 vLLM mem-fraction-static 与显存预算

vLLM 的 KV Cache 池 = (总显存 × mem-fraction) - 模型权重。80G 卡设 0.35 ≈ 28G（3B bf16 权重 ~6G + KV 池 ~22G）。R-SWA 恒定 KV 特性使 28G 足够 40 页长文档；若要更高并发可提到 0.5，但需压缩夜间训练窗口。

2.2 ms-swift 训练多模态模型

ms-swift（ModelScope）2026-07-21 起官方支持 Unlimited-OCR 训练。LoRA rank16/alpha32 是 3B 模型常用起点；max_length 32768 对齐推理配置保证 R-SWA 训推一致。custom_logit_processor（no-repeat ngram）训练时不需要——那是解码期技巧。

2.3 PaddleOCR 微调入口变迁

PaddleOCR 3.x 起微调走 PaddleX CLI（paddlex --pipeline PaddleOCR --sub_modules ...），不再是 2.x 的 train.py。子模块可独立指定：检测用 server 版免微调、只微识别头，是性价比最高的组合（识别错误占 OCR 失败的大头）。

2.4 局域网服务发现

网关可注册 mDNS（_ocr-gateway._tcp），客户端 avahi-browse 自动发现——复用《局域网音响系统探查》笔记的三路发现协议栈，无需记住 IP。

  • 崩溃恢复（running→queued 自动重排）

  • 无 GPU mock 测试 13 项

🎯 使用性评估

  • 部署成本：A100 侧 30 分钟（4 个脚本顺序执行）；客户端零安装（requests）
  • 吞吐估算：Paddle 票据类 ~2000 页/h（A100）；UOCR 长文档 ~40 页/次前向、批处理约 300-500 页/h
  • 依赖风险：paddlepaddle-gpu 版本与宿主 CUDA 强绑定（脚本已锁 3.0.0+cu126）；vLLM 镜像 CUDA 13.0 需驱动 ≥535
  • 已验证：路由/去重/状态机/清洗逻辑（13 项测试）；未验证：真实 GPU 部署端到端

💡 指导性意见

  1. 先跑分析业务再上训练：批量处理跑两周积累标注池，比直接标数据省一半人工
  2. Paddle 微调优先于 UOCR SFT：前者 1h/200 张图见效，后者需要 50+ 份精校金标准（人工成本高）
  3. 分时训练别贪夜间全占：留 22:00-23:00 空档跑评测，防止评测挤占推理早高峰
  4. Jetson 别抢 A100 的活：本地 PaddleOCR CPU 版处理简单单页（选型指南结论），只把重活送 A100

四、趋势判断

趋势1：局域网算力池化是数据敏感场景的主流形态

依据：本场景文档（合同/票据）不宜出内网；OCR 恰好是"模型不大、数据敏感"的完美池化对象。
判断：企业/团队级 A100 共享会复制"NAS 普及"路径——网关化（HTTP API）+ 任务队列是标准形态，K8s 是过度设计。

趋势2：推理服务与训练任务的分时复用是单卡团队的必修课

依据：A100 80G 同时放得下 4G+28G 推理与 40G+ 训练预算，但放不下双份峰值；systemd timer 两行配置解决冲突。
判断：未来的推理框架会内建"训练模式切换"，但当前 timer+容器启停仍是最简可靠方案。

趋势3：OCR 微调走向"数据飞轮"而非"一次性训练"

依据：解析结果天然带置信度，低置信样本即标注候选；每月增量微调比一次大训练更稳（防灾难遗忘用小 lr）。
判断：文档处理系统的长期价值一半在解析质量，一半在标注池运营——项目里 prepare_data/prepare_sft_data 就是飞轮入口。

五、关联分析

5.1 与百度双 OCR 选型指南笔记的关联

本项目是选型指南的工程落地：笔记给"何时用哪个"的判据，项目给"如何用"的代码。路由规则（≤3 页 Paddle / >3 页 UOCR）直接来自笔记 §3.1 决策树。

5.2 与 edge-llm-quantization / Jetson 体系的关联

Jetson 作为客户端角色回归本架构（不再是推理端）——与 edge-llm-quantization 的"端侧轻量化"形成互补分工：端侧跑简单单页（Paddle CPU 版），重活送 A100。局域网音响探查笔记的 mDNS 服务发现协议栈直接复用。

5.3 与 Miles 双门笔记的关联

网关的安全设计对应权限管理：CIDR 白名单（谁可访问）、类型白名单+大小限制（能提交什么）、hash 命名（防路径穿越）。缺证据门禁——结果置信度目前只在 JSON 元数据里，未做"低置信度自动标记需人工复核"的门禁逻辑，列入 v1.1。

5.4 与 Hermes 自身架构的呼应

网关的 SQLite 队列+幂等设计复用了 homepage scan_data.py 的 flock 防并发经验；分时 timer 模式来自 LuxTTS/F5-TTS 双 daemon 的 GPU 预算管理实践——单机 GPU 调度的经验是跨项目可迁移的。
