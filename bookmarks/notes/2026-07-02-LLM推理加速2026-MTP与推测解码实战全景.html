一、核心问题：为什么 LLM 推理慢

LLM 自回归解码是内存带宽受限（memory-bandwidth-bound）的：每次前向传播都要把全部模型权重从 VRAM 加载一遍，却只产出 1 个 token。在 batch size 小（1-4）的场景下，计算单元大量闲置，瓶颈纯粹是「把权重搬一遍」。

这意味着：模型越大，单 token 延迟越高，但每 token 的实际计算量（FLOPS）并没有增加多少。这是一个内存墙问题，不是算力问题。

推测解码（Speculative Decoding）的全部价值在于：让一次前向传播猜出多个 token，再用主模型并行验证，从而在不损失质量的前提下实现 2-9 倍加速。

二、2026 年推测解码方法谱系

vLLM 在 2026 年已支持 7+ 种推测解码方法，分为两大阵营：

2.1 模型驱动法（高收益）

方法 草稿来源 额外显存 接受率 最佳 batch 特点
MTP 主 checkpoint 内置头 0 GB 0.65-0.80 1-64 无需额外模型，即开即用
EAGLE-3 独立 1-3B 草稿头 2-4 GB 0.80-0.88 1-32 接受率最高，通用性最强
Draft Model 独立小模型 2-4 GB 变化大 1-32 需要匹配的草稿模型
PARD 并行草稿模型 2-4 GB 中高 1-32 草稿延迟低
MLP Speculator MLP 头 1-2 GB 0.60-0.75 1-16 轻量但增益有限

2.2 轻量启发法（中等收益）

方法 草稿来源 额外显存 特点
N-gram n-gram 匹配 ~0 无需训练，适合重复文本
Suffix Decoding 后缀树 ~0 动态推测深度，无需草稿模型

关键洞察：轻量法（N-gram/Suffix）的优势在于高峰流量时不会增加额外负载——它们几乎不消耗 GPU。模型驱动法则相反：低 QPS 时收益最大，高 QPS 时草稿模型的计算反而成为负担。

三、MTP：训练即加速的革命

Multi-Token Prediction（MTP）是 2026 年最重要的推理加速技术。它的核心思想是在训练时就教模型预测未来多个 token。

3.1 原理

标准训练：主头预测 token+1。
MTP 训练：主头预测 token+1，头2预测 token+2，头3预测 token+3，头4预测 token+4。

每个「未来头」是一个轻量的 transformer decoder block，共享主干的残差流（residual stream）。推理时这些头「免费」运行——主干前向传播后，多个头在同一个 forward pass 内同时提议多个候选 token，主模型再并行验证。

3.2 关键优势

  • 零额外显存：头在主 checkpoint 内，共享主干，不占额外空间
  • 零质量损失：主模型仍然逐个验证每个候选 token（验证是并行的），接受率 0.65-0.80
  • 即开即用：检查 config.json 中 num_nextn_predict_layers 字段即可判断是否支持
import json
cfg = json.load(open("config.json"))
print("MTP heads:", cfg.get("num_nextn_predict_layers", 0))
# 0 = 无 MTP; 1-2 = 有 MTP 头

3.3 已支持 MTP 的模型（2026 Q3）

  • DeepSeek V4：1 个 MTP 头（num_nextn_predict_layers: 1），2-token/forward
  • GLM-5.1：1 个 MTP 头（这正是本机使用的 zai provider 模型）

四、性能实测：H200 SXM5 上的对比

DeepSeek V4 FP8 在 H200 SXM5（batch 1-4）上的实测数据：

模式 tokens/sec TTFT p50 成本/百万 token 加速比
标准解码 ~1,700 38 ms $0.54 1.0x
MTP (1头) ~3,400 38 ms $0.27 2.0x
MTP + chunked prefill ~3,400 8 ms $0.27 2.0x (TTFT -79%)
EAGLE-3 ~6,200 38 ms $0.15 3.6x
DFlash (块扩散) ~9,000 8 ms $0.10 5.3x

成本公式：($/hr / 3600) / (tokens/sec / 1_000_000)，H200 spot $3.31/hr（2026-06 价格）

核心发现：
1. MTP 把成本直接砍半（$0.54→$0.27），且零配置成本
2. EAGLE-3 在接受率上领先 MTP（0.80-0.88 vs 0.65-0.80），但需要单独训练/维护草稿模型
3. DFlash 块扩散是当前吞吐量王者（5.3x），但它需要专门的 DFlash checkpoint
4. Chunked prefill 是 TTFT 杀手——把 prefill 和 decode 重叠执行，TTFT 从 38ms 降到 8ms（-79%）

五、vLLM 实战配置

5.1 开启推测解码

# EAGLE 方式
vllm serve <model> \
  --speculative-config '{"method": "eagle", "model": "<draft-model>", "num_speculative_tokens": 5}'

# MTP 方式（模型原生支持时）
vllm serve deepseek-ai/DeepSeek-V4 \
  --speculative-config '{"method": "mtime", "num_speculative_tokens": 3}'

# N-gram 方式（零成本，适合重复文本）
vllm serve <model> \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 3, "prompt_lookup_max": 4}'

# Draft Model 方式
vllm serve <model> \
  --speculative-config '{"method": "draft_model", "model": "<small-model>", "num_speculative_tokens": 5}'

5.2 方法选择决策树

你的模型原生支持 MTP？(检查 num_nextn_predict_layers)
├─ 是 → MTP（零成本，2x 加速）
├─ 否，但有匹配的草稿模型？
│   ├─ 追求最高接受率 → EAGLE-3
│   ├─ 追求最大吞吐 → DFlash
│   └─ 通用场景 → Draft Model
├─ 否，没有草稿模型？
│   ├─ 文本高度重复（代码/模板）→ N-gram
│   └─ 需要动态推测深度 → Suffix Decoding
└─ RL 训练/QPS 波动大 → Dynamic Speculative Decoding

六、与 Jetson 边缘部署的关系

方法 Jetson 可行性 原因
MTP ✅ 最优 零额外显存，GLM-5.1 原生支持
EAGLE-3 ⚠️ 可行 草稿头 1-3B，Jetson 8GB 需 FP4/INT4 量化
Draft Model ❌ 困难 需同时驻留两个模型，VRAM 不足
N-gram ✅ 可行 纯 CPU 操作，零开销

Jetson 实战建议：MTP + N-gram 组合是边缘场景的最优解。MTP 利用模型原生头实现 2x，N-gram 在代码/日志等重复文本场景提供额外增益，两者可以叠加。

七、核心发现总结

  1. MTP 正在成为标配：DeepSeek V4 和 GLM-5.1 出厂即带 MTP 头，未来新模型大概率标配。这是从「需要额外草稿模型」到「训练即加速」的范式转移。

  2. 推测解码不是「有就得开」：它是低 QPS/低 batch 的优化。高并发场景下，草稿模型的计算开销可能抵消加速收益。vLLM 的 Dynamic Speculative Decoding 正是为了解决 QPS 波动场景。

  3. Chunked prefill 是独立的 TTFT 杀手：即使不开推测解码，单独开 chunked prefill 就能把 TTFT 从 38ms 降到 8ms。它和推测解码正交，可以叠加。

  4. EAGLE-3 是当前通用王者：放弃 feature prediction 转向 direct token prediction，接受率 0.80-0.88 远超 MTP 的 0.65-0.80。代价是需要单独训练草稿头。

  5. 成本可以砍到 1/5：标准解码 $0.54/M → DFlash $0.10/M，在 batch 1-4 场景下，推测解码的经济价值巨大。

八、对现有系统的改进建议

  • GLM-5.1 MTP 利用：本机使用 zai provider 的 GLM-5.1/5.2，该模型原生带 MTP 头。若 zai 后端已开启 MTP，当前 cron 任务的实际 token 成本应低于账面值。值得验证 provider 侧是否已启用。
  • Jetson 本地推理：nexa-local-inference Skill 使用 Ollama 部署，应检查 Ollama 是否支持 MTP 推理路径。若不支持，考虑迁移到支持 MTP 的推理后端（如 llama.cpp 的 MTP 分支）。
  • llm-inference-optimization Skill：当前 Skill 聚焦 PagedAttention/量化/推测解码理论，建议补充 MTP 实战配置章节和 2026 方法谱系表。
