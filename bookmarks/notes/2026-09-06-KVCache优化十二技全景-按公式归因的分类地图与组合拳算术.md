## 一、内容详细整理

### 1.1 问题定义：KV cache 是唯一会长的显存项

- 权重推理期间基本固定；**KV cache 随序列每个 token 增长**，且默认每个活动序列各存一份
- 量化锚点：**Llama 3.1 70B 一条 128K 序列 ≈ 40 GB BF16 KV cache**；四条满长序列再加 160 GB（还没算权重和开销）
- 两种独立成本：**占显存** + **注意力反复读它**——不同技术分别解决不同部分，"有的改变模型存什么，有的少留 token 或少用 bit，有的逻辑 cache 不动只改进引擎怎么读/分配/共享/搬移"

### 1.2 总公式与 12 技术归因（全文骨架）

$$\text{KV cache} = 2 \times \text{层数} \times \text{KV头数} \times \text{序列长} \times \text{头维} \times \text{字节数}$$

（首项 2 = K 和 V；BF16 两字节，FP8 一字节）

| 公式项 | 技术 | # |
|--------|------|---|
| KV 头数 ↓ | GQA / MQA | 1 |
| 唯一层缓存数 ↓ | 跨层注意力 CLA | 2 |
| 保留 token 数 ↓ | 滑动窗口 / 驱逐 | 3 / 9 |
| 存储表示宽度 ↓ | MLA 潜在压缩 | 4 |
| —（换成固定状态） | 混合循环层 | 5 |
| 存+读双省 | 压缩稀疏注意力（DSA³） | 6 |
| 只省读不省存 | Quest 查询感知稀疏读 | 7 |
| 每 value 位数 ↓ | 量化 | 8 |
| 分配浪费 ↓ | 分页 PagedAttention | 10 |
| 重复块 ↓ | 前缀复用 | 11 |
| 显存↔CPU 搬移 | 卸载 Offloading | 12 |

**关键澄清**（原文强调）：稀疏注意力是单独一行——**少读 token ≠ 从显存删 token**。"GPU 满时，更快的注意力 kernel 不会为另一条序列腾地方，除非它同时少存字节。"

### 1.3 架构类技术（1-6，需要训练/换模型）

**① GQA/MQA——少存 KV 头**
- MHA：8 个 Q 头配 8 对 KV 头；**MQA：8 Q 头共享 1 对 KV**；GQA 居中（8 Q 头分 2 组，每组 4 头共享一对 KV）
- GQA 论文路线：MHA checkpoint 转换 + **5% 预训练算力恢复训练**，质量接近 MHA、速度接近 MQA
- Llama 3.1 70B：64 Q 头 + 8 KV 头 → 128K 上下文 **40 GB（64 KV 头本需 320 GB）**

**② 跨层注意力 CLA——相邻层共享缓存**
- 共享因子 2 = 两层用一套 KV → 唯一层缓存减半；CLA 论文（1B/3B）在 MQA 基线上**再省 2×**
- 与 GQA 乘性复合（减不同项）；**不能运行时开**——checkpoint 和引擎必须对"哪层拥有哪份缓存"达成一致

**③ 滑动窗口——局部层只留近期 token**
- 窗口 1024 的层只存最近 1024 个位置，环形缓冲覆盖旧槽，分配恒定
- 全局层仍看全程；**Gemma 3 = 5 局部 : 1 全局**（局部窗 1024，全局 128K）
- 节省只在序列超过窗口后才出现

**④ MLA——存潜在压缩表示**
- 不存每头完整 K/V，压缩 hidden state 成更小的 latent，解码时用学到的投影恢复（投影可吸收进 Q 和输出路径避免重建全 KV 张量）
- DeepSeek-V2：比 67B MHA **省 93.3% KV cache，最大生成吞吐 5.76×**
- 示例算术：64 标准标量 vs 12（8 latent + 4 位置）= 5.33×（仅示例比例）；**不是推理开关，属训练产物**

**⑤ 混合循环层——增长缓存换固定状态**
- Mamba/门控 DeltaNet 不存每 token KV，**更新固定大小状态**
- **Qwen3-Next：48 层 = 12 个重复块 ×（3 GDN + 1 全注意力）**，只有 12 层全注意力产生增长 cache（16 Q/2 KV/256 维 → 128K 仅 3 GB；48 层全注意力会是 12 GB）
- Jamba：1 注意力 : 7 Mamba，256K 上下文 **4 GB vs Mixtral 32 GB**

**⑥ 压缩稀疏注意力（DeepSeek V4 的 DSA³）——存与读双省**
- 两步：每 m 个相邻 token 压成 1 个压缩条目（n → n/m）+ 每新 token 用选择器只挑最相关的 k 个压缩条目读 + 小滑动窗保近期细节
- **V4-Pro @1M token：10% KV cache + 27% 单 token FLOPs（vs V3.2）；V4-Flash：7% cache + 10% FLOPs**（整机数字，含混合布局与精度选择）
- 必须训练期内置

### 1.4 引擎类技术（7-12，不改模型）

**⑦ Quest——查询感知稀疏读（只省读）**
- cache 分页，每页存 key 的 min/max 摘要；新 query 先给页摘要打分，**只加载得分最高的页**——全 cache 仍驻留（现在被忽略的页以后可能重要）
- 论文：自注意力延迟 **7.03×** 降低，整机推理 **2.23×** 加速

**⑧ 量化——每个数用更少 bit**
- BF16→FP8 减半，4-bit 到 25%；scale 决定精度（一个极端值拉宽共享 scale 会伤普通值）
- **KIVI 差异化分组**：K 按 channel（同特征跨 token）分组，V 按 token 分组；2-bit cache 峰值内存 **2.6×** 降、batch **4×** 增
- vLLM 直接开：`--kv-cache-dtype fp8`；新版可保留滑动窗层原生精度（局部层对量化更敏感时）

**⑨ 驱逐——预算内丢位置**
- **H2O**：留近期 + 累积注意力高的 heavy hitter；**SnapKV**：用 prompt 末端观察窗选位置（16K 输入 8.2× 内存效率 / 3.6× 生成加速）；**PyramidKV**：低层大预算高层小预算（LongBench 留 12% 追平全 cache）
- **警告**（原文难得的工程审慎）：重要性跨轮变化——**现在低注意力的工具结果，几个调用后可能必需**；系统指令/分隔符可能不成比例地重要；评测要用**完整 agent 轨迹+延迟引用+结构化 prompt**，"好的 NIAH 分不覆盖这些"

**⑩ 分页 PagedAttention——分配不浪费**
- 连续预留按最大长度 → 短请求浪费 + 空洞碎片；分页把显存切等块，请求用池中任意位置的块，块表记逻辑顺序
- 论文：**近零浪费、吞吐 2-4×**
- **隐藏效应**：固定池会吞掉量化收益——引擎前后都留 8 GB，FP8 让池里装下双倍 token（26,214 → 52,428），**nvidia-smi 可能纹丝不动**

**⑪ 前缀复用——活动请求间共享前缀块**
- 系统提示/工具定义常重复；自动前缀缓存按**链式哈希查键**（块+其全部前序），命中即指到已有 KV 块，分歧后才新算
- **防假匹配**：必须全前缀一致，不能只看中间 4 个 token 相同
- **失效雷区**：系统提示里的时间戳、工具 schema 的 JSON 键序、chat 模板空白差异都会打断匹配——**稳定 prompt 模板提高命中率**

**⑫ 卸载——GPU→CPU 分层**
- 暂停序列/待复用前缀的块搬到 CPU 内存（慢但大），需要时搬回
- **重要限制**：新的 OpenAI 兼容 API 请求**不会自动恢复**上一请求的 KV——除非引擎仍追踪该序列、精确前缀命中、或外部存储恢复
- vLLM：`--swap-space 16 --cpu-offload-gb`（原生 CPU 后端）；**先测恢复延迟和 CPU 带宽**

### 1.5 组合拳算术（原文示例）

从 40 GB GQA cache 出发：

```
CLA2  唯一层减半      40 → 20 GB
FP8   字节减半        20 → 10 GB
50% token 预算(驱逐)  10 → 5 GB
```

> 乘法对容量规划有用，但它隐藏了**模型质量和 kernel 支持**：CLA 要训练、FP8 引入量化误差、驱逐丢上下文、引擎还得支持合成后的布局。

### 1.6 场景→技术速查（照录）

| 场景 | 解法 |
|------|------|
| 选模型时 | 看 KV 头数、局部/全局层比、latent 维度、循环层——决定部署前的 cache 起点 |
| 伺服现有模型 | **先试 FP8，再标准化前缀**（都保全 token 集）；驱逐只在工作负载专项质量测试后 |
| 显存看着没变 | 查 cache 容量与块计数——固定池吸收了节省 |
| 延迟是问题 | 测 cache 读与注意力时间——Quest 式稀疏读即便不释放容量也有用 |
| 不活动会话占 GPU | 试卸载与调度——搬冷块可能比进一步压热块更重要 |

## 三、归纳总结

1. **公式归因是骨架**：12 技术全部映射到 cache 公式的某一项（头数/层数/token 数/宽度/位数/重复）——**先定位要改哪个约束，再选动哪个技术的决策树**，这是全文最大价值
2. **"省存"与"省读"必须分开记账**：Quest/稀疏注意力只省读（cache 仍全量驻留），GPU 满时**只有少存字节才能多塞序列**——多数科普把两者混为一谈
3. **架构类（1-6）vs 引擎类（7-12）的分界线是"要不要训练"**：GQA/CLA/MLA/混合层/DSA³ 都是 checkpoint 属性，**不能运行时开**；FP8/分页/前缀/卸载是引擎开关
4. **三个最被低估的工程细节**：①固定池吞掉量化收益（nvidia-smi 不动≠没生效，要看容量）②前缀命中被时间戳/JSON键序/空白差异静默打断 ③驱逐对 agent 多轮场景的危险（低注意力工具结果后文必需）
5. **恢复训练成本谱系**：GQA 5% 预训练算力即可转换 vs CLA/MLA/混合层必须从头训——**存量模型改造的门槛差异巨大**
6. **每技术一个锚点数字**：GQA 40GB vs 320GB / CLA 再 2× / MLA 93.3%↓ / Qwen3-Next 3GB vs 12GB / V4-Pro 10% / Quest 7.03× / KIVI 2.6× / SnapKV 8.2× / 分页 2-4× / Jamba 4GB vs 32GB——**数字骨架可当面试速查卡**
7. **评测审慎是暗线**：驱逐一段明确反对只用 NIAH（针在草堆）评测 agent 场景——**静态检索测试不代理多轮动态重要性**

## 四、趋势判断

1. **KV cache 优化从"论文竞赛"进入"组合部署"阶段**：单技术收益边际递减，产业重心转向**乘性组合**（架构项×精度项×token 预算）与引擎调度（分页/前缀/卸载）——选型能力比发明能力更稀缺
2. **固定状态层（Mamba/GDN）正在从异端变标配**：Qwen3-Next 3:1、Jamba 1:7 的比例探索表明**"少量全注意力层+大量循环层"是长上下文的性价比解**——与 DeepLoop（深度循环）在参数侧的哲学同向
3. **DSA³（V4）代表"存读双省"的新一代**：10% cache + 27% FLOPs 的整机数字若可复制，1M token 上下文的成本曲线被改写——2026-2027 旗舰模型的标配方向
4. **agent 负载成为 cache 技术的新评测基准**：系统提示+工具 schema 的前缀复用红利、驱逐在多轮调用中的风险——**agent 时代的 cache 设计以"稳定模板+延迟引用"为中心**
5. **"显存没变"的观测陷阱会越来越常见**：固定池+量化+前缀的三重作用让 nvidia-smi 失去诊断力——**容量审计（块数/token 数）取代显存占用成为一线指标**

2. **原理篇增补节的呼应**：4.1 链式哈希（本篇⑪前缀复用的防假匹配机制）/ 4.2 层间交互（本篇②CLA 的层共享）/ 4.3 语义阈值（本篇⑨驱逐的重要性判定）——**增补过的三个点在本文各有对应技术节，可交叉引用**
3. **与 TwoTower/DeepLoop 的"复用三重奏"**：KVCache=激活复用（缓存计算结果）/ DeepLoop=参数复用（循环用同一组块）/ TwoTower=结构复用（克隆 AR 模型成双塔）——**复用是贯穿推理、训练、架构三层的统一主题**，三篇笔记互链成"复用哲学"小系列
4. **混合循环层（⑤）与 DeepLoop 直接技术亲缘**：Qwen3-Next 的"3 GDN + 1 全注意力"重复块与 looped transformer 的"K 块循环 R 轮"都是**以重复结构换效率**——一个省 cache，一个省参数
5. **与部署指标笔记的衔接**：本篇"省存 vs 省读"的分账正是部署篇 TTFT/TPOT/吞吐/显存四指标的**因果上游**——技术选型表（§1.6）可直接并入部署篇的"怎么办"章节
6. **对量化技能群（gguf-quantization/llm-inference-deploy）的补充**：KV cache 量化（FP8/KIVI 2-bit）与权重量化是两条独立轴——**部署检查清单应双轴都列**（权重 bit × cache bit）
