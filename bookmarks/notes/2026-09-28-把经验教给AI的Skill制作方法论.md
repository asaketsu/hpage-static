## 一、核心流程（一句话版）

**定义任务 → 做出第一版 → 输入真实案例 → 找到错误位置 → 写成通用规则 → 换案例复测**

背景：dontbesilent 开源项目 dbskill GitHub 10k+ Star，方法间接创造七位数收入。案例 Skill 是 `dbs-beta-content-value`（内容诊断：粘贴文案→5 项输出：开头能否留住人/谁关心谁离开/观众得到什么/流量与商业倾向/最该先改哪里）。

## 二、第一步：把愿望拆成可检查的任务

"判断内容有没有流量"不能直接指导 AI——里面混着多个子问题。任务定义必须写清 3 件事：
1. **用户给什么**（想法/标题/文稿/已发布内容）
2. **Skill 给什么**（观看人群/去留原因/流量倾向/修改方向）
3. **不负责什么**（不预测具体播放量，不审查学术严谨性）

句式模板：`用户提供＿＿；Skill 判断/完成＿＿；最后交付＿＿；遇到＿＿时停止或转交。`

**关键洞察**：第一版跑偏的根源常是任务中心没写准——AI 把"论证完整、结构清楚"当成了内容价值，而用户要检查的是"观众会不会看"。任务中心错，后面分析再详细也没用。

## 三、三类错误定位表（本文最精华）

收到错误答案，先定位错误发生在哪一层，**不同层改法不同**：

| 错误位置 | 表现 | 应改什么 |
|---|---|---|
| **任务目标** | 把内容严谨/论证完整当成有流量 | 重写任务定义 |
| **判断过程** | 读完全文后用后文价值抬高开头评价 | 改变分析顺序，先隔离后文判断开头 |
| **对外表达** | 输出"首屏闸门""目标人群通过"等术语 | 保留内部方法，重写给用户看的语言 |

三问定位法：①它回答的是我交给它的任务吗？②它用了正确的信息和判断顺序吗？③结论能让使用者马上知道发生了什么、下一步做什么吗？

**先定位再修改，避免堆积互相冲突的补丁**——这正是我们"禁止原地连续堆补丁，根因清楚后一次性干净重写"铁律的民间版。

## 四、把一次纠正变成规则（反馈四要素）

"这个回答不对"只能让 AI 重答一次。可沉淀的反馈包含 4 部分：
1. **指出具体结论**（哪句判断错了）
2. **说明现实中的结果**（观众在这里会怎么反应）
3. **解释错误原因**（AI 忽略了什么差别）
4. **提出可重复的判断方式**（以后先看什么）

**案例**：心理学文案首句"心理学从来不是教你无条件接纳的"——Codex 读完原文觉得后文有争议性会有流量；dontbesilent 指出：观众只听到第一句就以为要讲"心理学教什么"，多数人没兴趣直接划走，**后文再好也参与不了已离开观众的去留决定**。

沉淀成的规则：单独读标题/封面/首句→写出观众以为接下来讲什么→判断该问题存在于多少人脑中→判断预期收益→开头留不住时明确告知"后面的好内容多数人看不到"。

## 五、用理论解释经验（规则的三个理论用途）

为什么必须改变分析顺序？——找到**信息觅食理论**（information foraging）：人根据眼前线索估计继续寻找的收益，标题和首句决定"值不值得花时间"。

理论三用途：①解释经验规则为何成立 ②帮规则跨案例迁移 ③提示规则失效边界。
**顺序铁律**：先让真实错误出现，再找理论解释——一开始就堆理论，AI 每个都分析一遍，输出变长任务变模糊。

## 六、Skill 复用：已有 Skill 参与制作新 Skill

制作新 Skill 时调用已有 Skill 分工：`dbs-goal`/`dbs-jtbd` 把模糊愿望整理成具体任务；理论类 Skill 找解释；检查类 Skill 验收输出。**旧 Skill 参与新 Skill 制作 = 复利结构**——每完成一次迭代，下次制作更快。

## 七、可复测性是规则的及格线

规则能不能离开原话题继续工作？**只能解释原案例的是"一次答案修改"，在多个相邻案例都能工作的才开始成为 Skill 能力**。复测三件套：正例、反例、换领域案例。

## 八、最值钱的部分：人对现实的判断

Codex 能整理规则/找理论/改文件/秒级重跑，**最稀缺的是 dontbesilent 对内容和流量的判断**：
- 容易被反驳的观点可能带来更多评论
- 片面归因可能降低理解成本（反而利于传播）
- 文章后面再精彩，观众可能死在第一句话
- 正确的专业分析没人看懂=对用户无价值
- 高流量建议与商业目标可能冲突

**制作 Skill 最重要的准备：找到一个你能判断好坏的问题**——不必提前写出方法，不必懂 prompt 术语，但至少能看到 AI 结果后说出"哪里不符合现实、现实中会发生什么"。

## 九、💡 对我们的价值分析

### ✅ 已在做的（印证到令人惊讶的程度）
- **反馈四要素** ≈ 我们的纠偏三要素【纠偏内容→根因→修复】+ 纠偏铁律"先复述符号换算再发令"
- **三类错误定位** ≈ 我们"先根因定位再动手"调试铁律的同构展开（目标/过程/表达 ↔ 架构/实现/接口）
- **规则跨案例复测** ≈ skill-ab-testing（候选版验证后替换）+ "已验证脚本禁改"
- **旧 Skill 参与做新 Skill** ≈ skill-pipeline 组合模式 + skill-orchestrator
- **经验依赖性判据**（只解释单案例=伪规则）与 agent-autonomy 的自进化三判据完全一致

### ⚠️ 可改进的（差距）
- 我们的纠偏沉淀多停在 memory/skill 文字层，**没有"换案例复测"这道门**——昨天建的 session-evolution-scan 只做覆盖判定，没有复测环节，可能沉淀出"只解释原案例"的伪规则
- 反馈四要素中第 4 条（可重复的判断方式）经常缺——纠偏沉淀常记"别做X"而没写"以后先看什么"

### 🔥 重点行动
1. **给 session-evolution-scan 加复测门**：每条待沉淀规则，先在另一个 session 的相似场景"影子验证"一次再 patch——补上"跨案例工作"及格线
2. **反馈四要素模板化**：写进 evolver/experience-bank 的沉淀格式（具体结论/现实结果/错误原因/可重复判断法）——缺第 4 条不予入库
3. **母提示词直接抄**：第九节制作清单+母提示词可整体移植为 Hermes 的 skill-maker 前置模板

## 十、内容整理（归纳总结与关联分析）

**归纳总结**：把个人经验教给 AI 的完整管线=任务三定义（给什么/给什么/不负责什么）→快出第一版→真实案例暴露错误→三类定位（目标/过程/表达）→四要素反馈（结论/现实/原因/可重复判断）→理论加固（解释+迁移+边界）→跨案例复测→旧 Skill 复利参与新 Skill。核心命题：**最稀缺的不是 AI 能力，是人对现实的判断力；Skill 工程的本质是把这种判断力一条条变成可执行规则**。

**关联分析**：这是 Jev 双篇（09-27/09-28）的"上游"——Jev 讲决策层的架构，本篇讲决策规则从哪来（人的经验→纠偏→沉淀）；与我们 09-21 建的 session-evolution-scan 循环几乎完全同构（会话纠偏→候选清单→拍板→patch），本篇补了我们缺的两块：**错误分层定位**和**跨案例复测门**。与"用户纠偏铁律"（第二次问同一件事=系统失败）互证——dontbesilent 的方法论就是这句话的工程化。

## 十二、趋势判断

1. **"经验工程"正在成为独立方法论**：把专家判断力转成 AI 规则的需求会催生一批"经验工程师"角色——比 prompt engineer 更靠近领域知识
2. **AI 协作者自述视角会成为新内容形态**：本文由 Codex 第一人称撰写是聪明的设计——内部过程只有"被纠正的对象"能完整讲出，可信度高
3. **Skill 复利结构是个人 AI 资产的护城河**：单条规则可抄，"规则+理论+复测+复用"的体系抄不走——与 dbskill 10k Star 的门槛一致
4. **纠偏数据是下一个稀缺资源**：模型能力商品化后，"哪句话错了、为什么错、现实会怎样"的标注数据（只有领域专家能产）成为差异化输入——与航空领域的"事故调查文化"同构
