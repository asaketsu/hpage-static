智算项目现场第1问：100人并发，到底需要多少张GPU？

来源：微信公众号「柏源Infra」· 作者 DH · 2026-07-29
原文：mp.weixin.qq.com/s/UAgwvah_muq0iMVIIrjNlg
系列：智算项目现场 30 问系列 · 第 1 问

核心结论

客户说的 "100人并发" 并不能直接换算成 GPU 数量。

"支持100人并发" 可能是 100 个账号、100 人在线、100 个请求同时到达，或 100 路请求同时生成 Token。决定 GPU 数量的不是用户标签，而是请求进入系统后产生的计算、显存和通信压力。

负责任的回答：

现在还不能直接判断。先确认并发口径、上下文长度、响应速度、模型精度和高可用要求，再根据目标模型在候选硬件上的实测吞吐确定配置。

一、先把"100人并发"说清楚

现场提到的"100人并发"至少对应四种口径：

口径 含义 负载
100个账号 100 名员工，多数一天登录一两次 高峰期可能只有 5-10 路请求
100人同时在线 打开了系统，未必都在生成内容 中等
100个请求同时到达 接近技术并发 需区分是否同一秒集中涌入
100路请求同时生成 Token 模型同时维护 100 个请求的上下文和 KV Cache 压力最大

现场沟通不接受"反正就是100人左右"这样的口径。不澄清，后面的所有计算都没有可靠基础。

二、不能直接换算成 GPU 数量

GPU 够不够取决于两件事：
1. 模型能不能放得下（显存）
2. 模型运行后能否达到需要的吞吐和响应速度（性能）

70B 模型权重容量参考

精度 模型权重理论容量
FP16 / BF16 ~140GB
8-bit 权重 ~70GB
4-bit 量化 更低

这只是权重本身。运行时还需要：中间结果、框架开销、通信缓存、KV Cache，且不能把显存塞满，需留余量。

Dense vs MoE 必须区分

  • Dense 模型：总参数 = 每次推理参与计算的参数量
  • MoE 模型：总参数量与激活参数量可能相差很大
  • 总参数量 → 影响权重显存
  • 激活参数量 → 影响单 Token 计算量和推理速度

只看 "70B" 无法判断实际部署压力。对 MoE：用总参数量判断权重能否装下，用激活参数量估算单 Token 计算和 GPU 数量。

"模型能启动" ≠ "方案成立"

有些方案用较少 GPU 确实能启动模型，但一增加并发，首 Token 时延骤升、输出速度下降，变成"模型能跑，但业务不好用"。能够启动只说明显存勉强够；能够稳定支撑业务才说明具备服务能力。

三、同样是 70B/100人，负载可能相差几十倍

场景 并发特征 GPU 压力
内部知识库 100 账号，20 在线，真正同时生成的仅 5-10 路；8K 上下文，输出 200-300 Token ✅ 连续批处理可提升利用率，绝不能按 100 路配置，否则严重过度建设
Coding 助手 高峰期 20-30 路同时生成，输入输出更长，需保持较快输出 ⚠️ "模型能否放进显存" 已非主要问题，持续推理能力才是主要压力
长文档分析 32K/64K+ 上下文，大量长上下文请求 🔴 长上下文明显增加 KV Cache 显存占用，即使权重已量化也可能耗尽显存

四、真正要算的三个指标

1. 峰值活跃请求数

不是注册用户、也不是在线用户，而是高峰期有多少个请求同时处于推理状态。

平均并发往往很好看，但系统通常不是被平均值压垮的，而是被高峰压垮。容量规划必须看峰值，以及峰值持续多长时间。

2. 每路请求需要多快（体验 = 首Token时延 + 输出速度）

  • 首 Token 时延：提交后多久看到第一个字
  • 持续输出速度：开始回答后每秒输出多少 Token

"能够返回答案" 不是性能指标，"别太慢" 也不是验收口径。

合理需求应写成：

首Token时延不超过多少秒；
正常负载下单路输出速度不低于多少 Token/s；
高峰期最多允许多少请求排队；
请求超时率和失败率控制在什么范围。

3. 整套系统需要多少 Token 吞吐

  • 10 路并发 × 20 Token/s = 至少 200 Token/s
  • 30 路并发 × 20 Token/s = 接近 600 Token/s

简化计算未含：Prefill 开销、上下文差异、请求波动、连续批处理效率、模型并行通信损耗。但至少把"100名用户"转化成了可测试的系统吞吐目标。

五、为什么上下文长度必须单独问

  • 普通聊天可能仅几千 Token
  • 知识库问答会把检索片段加入提示词
  • 代码助手可能需要输入整个文件
  • 长文档分析可能一次处理数万 Token

影响：
1. 上下文越长 → Prefill 计算量越大 → 首 Token 等待越长
2. 每个活跃请求都占 KV Cache → 并发 × 上下文同增时，KV Cache 可能从辅助开销变为主要显存消费者

采购不能只问"模型最大支持多少 K 上下文"，更应问：业务平时用多少？极端情况用多少？多少人同时用长上下文？

"最大支持 128K" 是模型能力描述，不代表系统可以让 100 人同时运行 128K 上下文。有些方案把模型最大上下文写进能力表却不说明并发条件，看起来先进，实际几乎无法验收。

六、8张GPU：TP8 还是 TP4+DP2？

方案 做法 优点 局限
TP8 一个模型副本拆到 8 张卡 单副本可用全部显存和算力 张量并行规模大 → 卡间通信频繁；并发低时利用率不理想
TP4+DP2 4 张卡一个副本，共两个副本 两副本分别处理请求，适合并发推理 需 4 张卡显存能容纳模型且性能达标

倾向：

推理项目在显存允许前提下，不要盲目追求更大的张量并行规模。能用更少的卡组成一个模型副本、再通过多副本提升并发，往往比把所有 GPU 绑定成一个大副本更灵活。最终仍要看实测数据。

七、为什么不能直接给"四张卡"或"八张卡"

GPU 型号只是推理链路中的一个变量，这些因素都会改变最终性能：

  • OAM 还是 PCIe 服务器
  • GPU 之间互联方式
  • 模型精度和量化方案
  • 推理框架
  • 是否启用连续批处理
  • 张量并行规模
  • 上下文/输出长度
  • 是否 Prefill 与 Decode 分离
  • 是否同时部署多模型
  • 是否预留高可用副本

项目早期可容量估算，但最终配置应基于目标硬件和目标模型做压力测试。

若有人张口就承诺"八张卡支持 100 人并发"，应追问：在什么模型版本、精度、上下文长度、响应速度下支持？若这些条件都没有，所谓"支持 100 人并发"没有工程意义。

八、现场怎么把需求问清楚（四层）

① 用户口径

  • 系统共有多少注册用户？
  • 高峰期多少人同时在线？
  • 预计多少请求同时生成？
  • 请求均匀到达，还是存在集中高峰？

② 模型和数据

  • 部署哪个模型、哪个版本？
  • 原始精度还是量化版本？
  • 是否同时运行多个模型？
  • 是否接入知识库、代码库或长文档？
  • 常用和最大上下文分别是多少？
  • Dense 还是 MoE？总参数量和单 Token 激活参数量分别是多少？

③ 性能目标

  • 首 Token 最长可等多久？
  • 单用户期望多少 Token/s？
  • 平均输入/输出长度？
  • 高峰期是否允许排队？
  • 失败后如何重试？

④ 运行要求

  • 是否要求双副本/高可用？
  • 是否有部门资源隔离？
  • 用户数预期增长多少？
  • 是否为测试和新模型预留资源？

若客户无法一次性回答，也应把当前假设写进方案，例如：
"按照 100 名注册用户、高峰期 10 路活跃请求、8K 上下文、平均输出 300 Token、单路不低于 20 Token/s 进行容量估算。"
这样配置数字建立在什么条件上一目了然，业务变化时也能判断为何原配置不适用。

九、更接近现场的估算示例

假设：内部 100 用户，高峰期 20 在线，同时生成 ≤10 路；70B 量化模型；8K 上下文；平均输出 300 Token；首 Token ~3s；单路 ≥20 Token/s；预留高可用。

简化目标：10 路 × 20 Token/s = ≥200 Token/s 持续输出。

验证路径（不是理论换算，而是实测）：
1. 候选服务器上单个模型副本需要多少张卡
2. 10 路并发时总吞吐多少
3. 单路输出是否 ≥20 Token/s
4. 首 Token 时延是否符合
5. 8K 上下文下显存还剩多少
6. 部署高可用副本后需多少服务器

实测决策逻辑：
- 单副本只提供 120 Token/s → 增加副本或提高配置
- 单副本达 250 Token/s 但高峰首 Token 超标 → 拆分副本减排队
- 4 卡能达到目标 → 两副本比一个 8 卡副本更灵活
- 4 卡只能放下模型但性能不足 → 扩大单副本规模

最终 GPU 数量来自目标场景下的测试结果，而不是来自"100人"这个数字。

十、这个问题到底怎么答

方案设计不是抢答题。

过早给出一个看似明确的数字，后面往往需要用更多模糊表述去掩盖前面的假设。与其在项目后期解释为什么性能没达标，不如在项目开始时多问几个问题。

结语（原文金句）

  • "100人" 可能是 100 个账号，也可能是 100 路请求同时生成
  • 可能是普通 8K 知识问答，也可能是 64K 长文档分析
  • 可能只要求返回结果，也可能要求低时延、高吞吐、双副本高可用

真正需要确认的是：高峰期有多少活跃请求、每路请求多长、需要多快返回、模型什么精度和推理框架，以及系统准备怎样处理故障和未来增长。

对 MoE 模型：只按总参数量估算计算需求会偏保守，只按激活参数量估算显存和 GPU 数量又会过于乐观。正确做法是：用总参数量判断权重能否装下，用激活参数量估算单 Token 计算量。
