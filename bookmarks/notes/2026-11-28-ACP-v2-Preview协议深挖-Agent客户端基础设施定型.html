〇、定锚：我的现状与目标

我日常运营一套多 Agent 基础设施：Hermes 网关接飞书事件、abot/jbot 双机通过 ssh 私有通道协作、delegate_task 编排子代理、飞书桥用 flock 管消息队列。真实踩过的坑一样不少：网关优雅重启的 5 秒窗口会黑洞入站消息且事件无跨重启回放、桥端串行循环被 600 秒长任务堵死导致全部消息无响应、子代理运行状态对宿主不可见、消息重试存在重复响应风险。

ACP v2 把这一整批坑做成了协议级标准答案。本文目标有三：战还原 v2 全部关键设计；提炼可直接平移到自有消息桥的可靠性模式；判断"对内 ACP / 对外 MCP"双标准格局的走向与接入时机。判断标尺：一切以"能否解决我自己基建里的已实锤故障"为价值锚点。

一、内容详细整理

1.1 发布背景：Draft → Preview 的四个月〔数据，2026〕

  • 2026-07：ACP v2 首个 Draft 发布，公开征求意见。
  • 2026-11-20：正式迈入 Preview 阶段（stable 前最后一道门槛），期间打磨了 17 个 Schema Alpha 版本。
  • Zed 与 JetBrains 两个团队在真实产品里落地：Claude 与 Codex 适配器已跑通完整端到端体验。
  • Rust / TypeScript / Kotlin / Python 四大官方 SDK 同步提供 v2 API；Rust（unstable_protocol_v2 feature）与 TypeScript（@agentclientprotocol/sdk/experimental/v2）已内置协议路由器，initialize 握手时自动按版本路由，一套服务同时兼容 v1 与 v2 客户端。
  • 配套开放 TCK 合规测试套件（opt-in v2 suite）；v2 JSON Schema 以 schema-v2.0.0-beta.N 标签发布。
  • 官方口径："If you were waiting for the Draft to stop moving before you started, this is the time to start."（设计已定型到可以动手，但未冻结。）

1.2 最核心重构：Prompt 生命周期彻底与 Turn 解耦〔方法，2026〕

ACP v1 最痛的约束：发一次 session/prompt，客户端必须死等整轮 Turn 结束（响应即 turn 结束信号）。v2 从根上重写状态机——Prompt 不再拥有整轮 Turn，它只负责"把用户消息插入会话"：

  • 插入即返回 messageId：Agent 逻辑上把消息插进会话就必须立刻返回必填的 messageId。收到成功响应 = 消息确已入列；收到 JSON-RPC 错误 = 没进。仅仅收到请求、进队列、分配 ID 都不算插入。
  • 忙时绝不拒收：客户端可在任意状态发新 Prompt，Agent 不得仅因为正在执行前台任务就拒收——要么立刻插入，要么按接收顺序挂起（hold），挂起期间请求保持 pending 直到真正插入才回包。
  • 失败也有出口：消息插入后工作失败，Agent 以 idle state_update 结束、stop reason 为 error，且 update 可携带 JSON-RPC error 对象，客户端可像处理错误响应一样按错误码反应。
  • 关键澄清（辟谣）：细粒度显式 Steering（中途纠偏）与 Queueing（队列管理）以及 Remote Transports 并没有绑定在本次 Preview 里。忙时插入的消息是纠偏当前工作还是开启下一轮，暂由 Agent 自行决定；但 v2 消息模型已为此留好无破坏性扩展位——后续只增方法与能力，不再搞大版本破坏。

一句话理解：v1 的 session/prompt 是"电话通话"（占线即拒接），v2 改成了"微信留言"（随时可发，忙时排队，响应只代表"已收到并入库"）。

1.3 后台任务与精准单点停止〔方法，2026〕

  • 主会话进入 idle 后终端里可能还挂着测试或长编译。v2 在 state_update 里新增 background 清单，明确列出独立于前台运行的终端、工具调用、子 Agent——客户端一眼可知会话是否清净、关窗口会杀掉哪些进程。
  • 快照语义：background 列表是整表替换（非合并），[] 表示无后台工作；omitted/null 表示"未报告"而非"没有在跑"。报告 background 的 Agent 必须在每个 state_update 都带此字段。
  • 先宣告后列入：条目出现在快照前必须有对应的 terminal_update / tool_call_update / subagent_update 宣告；退出前必须先发 exitStatus 或最终状态。
  • 工具调用新增 paused 状态；工具或终端可声明 capabilities.cancel，客户端即可调 tool_call/cancel 或 terminal/cancel 精准掐断某一条失控后台命令——不再需要 session/cancel 把整轮 Turn 全干废。
  • 活性判定禁令：终端输出不是活性信号——输出缺失或过期不得判定进程挂掉或退出。
  • 取消的边界：session/cancel 只覆盖前台工作，background 清单内的任务继续跑；前台取消时 Agent 必须（MUST）对等待中的权限请求发 $/cancel_request 一并作废。

1.4 Subagents 正式进入 v2 基线〔方法，2026〕

  • 过去客户端需额外协商 capability 才能理解子 Agent。v2 里 Subagent 是协议基线能力，无需协商——每个客户端都必须处理子会话（哪怕选择不单独展示）。
  • 每个被委派的子 Agent 拥有独立 sessionId，其消息流、计划、工具调用以标准 session/update 推送；父会话用 subagent_update 宣告子会话诞生，用 session_message 上报跨会话协作消息。
  • 嵌套任意深度：子会话创建自己的子代理时，subagent_update 的外层 sessionId 指向它的直接父——形成代理树；协议禁止把已有会话移交给别的父、禁止成环、禁止猜测父节点。
  • 父→子消息不是 user_message：必须以上行 session_message（senderSessionId=父）呈现在子会话 transcript 里，客户端渲染为"来自父会话"而非"来自用户"——身份归属不混淆。
  • 成本聚合规则：父会话成本已包含全部后代成本，客户端禁止把子会话成本再加到祖先上（防双算）；子会话无成本报告 = 成本未知而非零。
  • Replay：断线重连回放时，子会话宣告先于其历史，每个子会话有独立的 replay_complete；无法如实重建归属关系的子会话宁可不回放也不许猜。

1.5 断线自愈三防线〔方法，2026〕

面向即将到来的 Remote Transports，网络闪断是常态，v2 一次性补齐：

  • replay_complete 回放完结哨兵：客户端用 session/resume 恢复时，Agent 推完历史后必发 replay_complete；实时更新必须等在它之后。若断在哨兵之前，客户端立刻知道历史被截断——"是否回放完整"从猜测变成确定。
  • idempotencyKey 幂等防重：session/prompt 新增 1–255 字符幂等键（客户端不发 ID，Agent 拥有消息 ID）。没收到回包就拿同一个 key 重试，Agent 识别后返回原 messageId，绝不重复插入两条用户消息。
  • 全方法 Retry Classes：协议为每一个 RPC 方法写清能否安全重试、重发会产生什么效果——重试策略从"程序员经验"升级为"协议契约"。

1.6 Wire Format 全面收紧，与 MCP 对齐〔方法，2026〕

  • 砍掉 JSON-RPC Batch（与 MCP 规范一致）；请求 ID 禁止 null（只能是字符串或整数）。
  • 四个强制错误码：-32601（方法未实现/未声明）、-32002（会话不存在或本连接不活跃）、-32600（初始化完成前调用）、-32022（协议版本不兼容，响应列出 Agent 支持的版本列表）——版本协商失败从"普通初始化错误"升级为结构化可处理信号。
  • _meta 统一 Patch 语义：omitted = 不变，null = 清空，object = 按 key 更新；compaction_update 的 status 也改为 patch 字段——所有按 ID upsert 的实体只需带 ID 即可提交增量。

1.7 生态现状与迁移〔数据，2026〕

  • v1 / v2 同服共存：Preview 阶段无需抛弃 v1。SDK 协议路由器按连接协商版本；Claude 与 Codex 官方适配器是现成的双版本参考实现。
  • 迁移清单（对实现了 July Draft 的人最可能破坏性的 8 条）：prompt 响应必带 messageId；忙时不拒收；session/new/session/resume 响应携带 availableCommands；resume 回放以 replay_complete 结尾；每个客户端必须处理 subagent_update；_meta patch 化、batch 移除、ID 禁 null；每命令带 type discriminator；elicitation 字符串属性去 pattern。
  • v2 基线还包含：Client 文件系统与终端执行 API 被移除（Agent 需要客户端侧工具时改用 client-provided MCP servers）；capabilities 重组为统一 capabilities + 必填 info；支持标记从布尔改对象（{} = 支持，omitted/null = 不支持）；8 个双版本稳定特性（elicitation、终端认证、工具调用名、session notices、session compaction、客户端系统提示词、plan operations、subagent sessions）。

二、查询拓展

2.1 命名消歧：业界其实有三个"ACP"〔补充，2026〕

搜英文资料必先消歧，三个同名缩写完全不同：

  • Agent Client Protocol（本文主角）：Zed 主导、JetBrains 联合推进，JSON-RPC over stdio，解决编辑器/宿主 ↔ 编码 Agent 通信。
  • Agent Communication Protocol（IBM）：REST 风格 agent-to-agent 通信，解决流式/记忆/异步执行三大 MCP 缺口。
  • Agent Commerce Protocol（IBM Research → Linux Foundation）：代理商务交易层（定价/报价/支付确认/交易状态）。

本文及公众号原文全部指第一个。检索时认准域名 agentclientprotocol.com 与 "Zed + JetBrains" 特征词。

2.2 官方一手公告 vs 公众号转述的增量细节〔补充，2026-11-20〕

通读官方 Preview 公告与 73K 字符迁移指南后，补充公众号未覆盖的关键点：

  • Preview 公告由 ACP Lead Maintainer Ben Brandt（Zed Industries）署名发布；JetBrains 的 Sergey Ignatov 已升任联合 Lead Maintainer——治理层面双厂商对等。
  • held prompt 的响应保持 pending 直到真正插入——客户端的请求超时语义要按此设计，不能按固定超时判失败。
  • v1 的 unstable usage 字段移到 v2 unstable schema 的 idle state_update 上（end-turn usage）。
  • auth 语义收紧：authMethods 非空 ⇒ Agent 必须同时实现 auth/login 与 auth/logout；为空 ⇒ 客户端禁止调用两者。无单独 logout 支持标记。
  • 版本协商细则：Client 发自 supported 的最高版本，Agent 选 ≤ 请求版本的最高支持版；无匹配才回 -32022 + {requested, supported[]}。v2-only 端点收到 v1 请求时不需要理解新错误码也能正常报初始化失败——向后兼容用心极深。
  • 双栈验证清单（官方给了 6 条）：同端点双版本 Client 各自路由正确；v2 Client→v1-only Agent 降级；更高版本请求选择最新支持版；prompt 完成与取消走双版本各自断言；关掉 v2 不影响 v1；v1 无身份请求打 v2-only 端点回 -32022 且不启动任何 v2 会话工作。

2.3 Steering / Queueing 的深水区：session/inject RFD 已起草〔补充，2026〕

官方说"Steering and queueing definitions are coming"，社区已跑在前头：

  • GitHub Discussion #1220 提出并已起草为 PR #1261（docs/rfds/v2/session-inject.mdx）：session/inject 方法，带 queue / steer 两种模式。
  • 核心洞察：各家 Agent 的可编程面今天就不一样——Codex 已提供非打断式 mid-turn steer（适合 steer 模式）；Claude Agent SDK 尚未暴露（mid-turn 输入只能排队、turn 后投递，仅硬中断可用，只能 queue 模式）。
  • 提案的关键论点：没有标准化之前，客户端无法诚实地告诉操作者"你这条消息会纠偏当前轮还是排队等下一轮"——这正是需要协议定义的原因，也解释了 v2 为何暂留给 Agent 自行决定。
  • RFD 讨论中 ACP 维护者回应积极（"happy to put it in the v2 bucket"），落地路径清晰。

2.4 历史脉络：从 Zed 单推到双厂商共治〔补充，2025–2026〕

  • 2025-08 前后：Zed 发布 ACP v1，与 Google 合作让 Gemini CLI 率先作为参考实现（gemini --acp / 早期 --experimental-acp）；Zed 共同创办人 Nathan Sobo 类比 LSP："语言智能从 IDE 分离"重演为"Agent 智能从编辑器分离"。
  • 2026-02：JetBrains 全线 IDE（IntelliJ/PyCharm/WebStorm 等）通过 ~/.jetbrains/acp.json 配置接入第三方 agent。
  • 2026-07：ACP v2 Draft；RFD 流程同步稳定了 8 个 v1/v2 双版本特性。
  • 2026-11-20：v2 Preview；ACP Registry（统一分发层：一次 PR 合入即全客户端可用）已收录 Claude Code、Codex CLI、GitHub Copilot CLI、OpenCode、Gemini CLI、Qwen Code、goose 等主流 agent。

2.5 社区争议与态度反转〔反驳→再反转，2026〕

早期（2025 末）中文社区（Emacs China 等）的冷观："事实上这个 ACP 目前也只有 gemini-cli 在跟进……codex 团队明确说了不会跟进，建议社区自行适配。"一年后的现实：官方 codex-acp 适配器由 agentclientprotocol 组织维护并作为 v2 双版本参考实现，Claude Code 同样有官方级适配器。争议的反转本身是个信号：当协议成为分发渠道（Registry），拒绝的成本就高于接入的成本。对 Emacs 等终端编辑器，社区已有初步适配库，但生态仍薄弱——这是少数派的现实。

三、归纳总结

3.1 v2 精准打击的四大工程坑（框架）

┌─────────────────────┬──────────────────────────┬────────────────────────────┐
│ 工程坑               │ v1 现状                  │ v2 解法                    │
├─────────────────────┼──────────────────────────┼────────────────────────────┤
│ ① 忙等阻塞           │ prompt 占线即拒/死等整轮 │ 插入即回 ID + 忙时挂起队列 │
│ ② 子代理黑盒         │ 需协商 capability 才可见 │ 基线化子会话+代理树        │
│ ③ 断线瞎猜           │ 重连后不知历史全不全     │ replay 哨兵+幂等键+重试级  │
│ ④ 误杀整轮           │ 只能 session/cancel 全停 │ background 清单+单点取消   │
└─────────────────────┴──────────────────────────┴────────────────────────────┘

底层是一条设计哲学贯穿：把"会话状态"从 RPC 请求-响应的生命周期里解放出来——消息插入、进度、完成、失败全部走 notification 流（session/update / state_update），请求响应只做"接受确认"。这与分布式系统里"提交与执行解耦"是同构思想。

3.2 协议分层格局：组合而非竞争

        ┌───────────────────────────────────────┐
        │  编辑器/宿主 ↔ 编码 Agent              │ ← ACP (Zed+JetBrains)
        ├───────────────────────────────────────┤
        │  Agent ↔ Agent（跨组织协作）           │ ← A2A (Google 50+伙伴)
        ├───────────────────────────────────────┤
        │  Agent ↔ 工具/数据/资源                │ ← MCP (Anthropic→跨行业)
        ├───────────────────────────────────────┤
        │  Agent ↔ 商业交易                      │ ← UCP / ACP-commerce
        └───────────────────────────────────────┘
  • MCP：工具接入层，跨厂商采纳最完整（16 个月+生产部署经验）。
  • A2A：agent 协作层，长任务异步生命周期（submitted/working/completed/failed）。
  • ACP：宿主集成层，LSP 式"实现一次、处处可用"+ Registry 分发。
  • 2026 年中的行业共识：protocols compose rather than compete——生产级 agent 系统同时用多个协议，各管一段。

3.3 三维护筛

  • 优点（哪里成立/适用条件/证据强度）：忙时插入+挂起队列是消息队列正统语义，杜绝"占线拒收"这类把传输层问题暴露给用户的反模式——证据强度高（RFC 2119 MUST 级规范文字+两大 IDE 真实产品落地+17 个 alpha 迭代打磨）。快照式 background 清单把"关窗口会杀什么"从猜变成查。错误码结构化（-32022 带版本列表）让兼容性失败可编程处理。
  • 缺点（前提假设/偏差）：①Preview 未冻结，官方明说"发现更大的问题宁可现在修"——生产绑定仍有小概率破坏性变更；②Steering 语义留白是最大的悬而未决：忙时插入到底是纠偏还是下一轮，当前 Agent 各说各话，跨 Agent 的客户端行为不可预期；③Remote Transports 未定，断线三防线目前只在 stdio 场景低频触发，真实价值要等远程化落地才被检验；④双栈（v1+v2）并存期，客户端/Agent 维护两套实现是真实成本（官方迁移指南花了大量篇幅教"共享业务逻辑、分离 wire 形状"）。
  • 借鉴点（可直接迁移的动作）：可靠性三防线（幂等键/回放哨兵/重试分级）是协议无关的分布式消息桥模式，可平移到任何长连接桥接设计；"先宣告后列入"的实体生命周期纪律适用于一切状态同步协议；"扩展位预留"（只增方法不改已有消息）是大版本演进的低成本路径。

四、趋势判断

趋势1：双标准格局已从口号变为可验收的现实（上升）

依据：2025 年"对内连宿主走 ACP，对外连工具走 MCP"还只是行业评论；2026-11 的落地证据链 = ACP Registry 收录全部主流编码 agent + MCP 侧同步长出 Skills/Tasks/Elicitation 成为 agent 协作总线 + ACP v2 把子代理/后台任务/断线恢复做进基线。两协议在各自象限内闭环，交叉点（client-provided MCP servers）反而互相成就。对我意味着：自研 Agent 基建的对外接口设计可放心以这两个协议为参照系，不必再赌私有协议。

趋势2：协议栈分层组合取代"大一统协议"幻想（分化）

依据：2026 年中的生态图已稳定为 MCP（工具）/ A2A（协作）/ ACP（宿主）/ UCP（商务）四层，各有治理主体（Anthropic 系、Google 系、Zed+JetBrains、Linux Foundation），且互不吞并——IBM 试图用同名 ACP 统一 agent 通信的路线反而被边缘化为商务层。风险提示：命名混乱（三个 ACP）会在未来两年持续制造检索与集成成本。

趋势3：IDE 从"逐家适配插件"进入"多 Agent 并行生态"（上升，LSP 历史重演）

依据：LSP 之前每个编辑器给每个语言写集成，LSP 之后实现一次处处可用——ACP 正在复制该曲线：Registry 一次 PR 全端分发、JetBrains 全线 + Zed 内建支持、第三方统一控制台（如 OpenHands Agent Canvas 一界面切换 Claude/Codex/Gemini）。机会：面向 ACP 实现自研 agent 等于同时获得整个编辑器生态的分发渠道。

趋势4：下一个爆发点是 Remote Transports + Steering/Queueing（蓄势）

依据：官方明说两者"designed with in mind but not tied to this release"，且扩展位已留（只增方法不破坏消息）；社区 session/inject RFD（PR #1261）已获维护者背书；Codex 已有 steer 实现、Claude SDK 只有 queue——现实差异倒逼标准化。远程传输落地后，"移动端/远程编排器直连云端 agent 会话"成为新场景，断线三防线价值将被真正检验。

五、关联分析

5.1 与自有 Hermes/飞书桥基建的工程同构（四组硬映射）

  • 网关重启黑洞 ↔ replay_complete：实锤案例（2026-11-27：优雅重启 teardown 窗口 5 秒丢失用户消息，飞书事件无跨重启回放）。ACP v2 的答案是 resume + 回放哨兵——入站消息持久化 + "历史/实时"边界标记正是待修项该采用的设计。
  • 桥端串行堵死 ↔ 忙时插入/hold：实锤案例（同聊天 flock 串行循环被 600 秒长任务堵死 = 全部消息无响应，两次事故）。ACP 的"忙时不拒收、插入或按序挂起"给出协议级正解：接收与执行解耦。
  • 消息重复风险 ↔ idempotencyKey：飞书事件重试投递场景下，桥端按 event_id 去重已是实践；ACP 把它升格为"提交键 + 原响应重放"模式，可借鉴其"Agent 保留 key 期间返回原 messageId"的语义。
  • delegate_task 子代理 ↔ Subagents 基线：自有的子代理编排（独立上下文、最终摘要回传父会话）与 ACP 子会话模型高度同构；ACP 额外的"成本聚合防双算、代理树嵌套归属"是自有编排尚未覆盖的细节。

5.2 与 abot/jbot 跨机协作通道的关联

当前双机协作走 ssh + stdin 脱敏 + 45 秒单轮的私有通道。ACP Remote Transports（HTTP/WebSocket）若落地，"远程编排器作为 ACP 客户端直连另一台机的 agent"将是标准化替代方案——但需注意其断线语义与安全边界（token/权限）尚未定型，短期不值得迁移，值得跟踪。

5.3 与已有笔记/项目的关联

  • MCP故障注入与Agent容错精读——容错主题同构：该篇讲 MCP 层的故障注入测试，本篇 ACP v2 给出宿主层的重试/回放/取消契约，两者合起来是 Agent 系统可靠性的两层防线。
  • 八成MCP-Server只需SKILL-md与CLI-抽象层为谁而存在——MCP 生态分层反思的延续：MCP 收敛为工具层标准后，"宿主层标准归 ACP"进一步印证了分层而非万能插头的判断。
  • 多Agent协作-Stigmergy痕迹协作——ACP 的 session_message 跨会话消息与环境痕迹协作是两种 Agent 间通信范式：前者显式消息、后者环境标记。
  • 企业级Agent形态架构-十二观点收敛分析——企业级形态中"宿主/编排器"一层的标准化落地正是 ACP。
  • 项目 agent-mesh：多 Agent 协作网格的节点间通信设计可参考 ACP 的实体 ID/快照/宣告纪律。

七、行动启示与回访

我的结论先行：

  • 保留：可靠性三防线（幂等键/回放哨兵/重试分级）+ "先宣告后列入"实体纪律——协议无关，直接纳入自有消息桥与编排器的设计语汇。
  • 放弃：任何"为自有 Agent 手写全新私有通信协议"的念头——宿主↔Agent 一层已被 ACP 圈定，私有协议只剩维护成本没有分发收益。
  • 改造：Hermes 网关"入站持久化待修项"按 ACP 模式改造——消息落盘先行（等价"插入即确认"）+ 重启后回放 + replay 边界标记，替代当前的"重启窗口黑洞"。

行动项：

  • 行动1：给飞书桥补"幂等投递"语义 | 时间：一周内 | 触发条件：下一次桥端重启或事件重试 | 验收标准：同一事件重复投递时桥端只响应一次且日志可查重。
  • 行动2：跟踪 session/inject RFD（PR #1261）与 v2 stable 节奏 | 时间：每两周扫一次 agentclientprotocol.com/updates | 验收标准：steering/queueing 语义定型或 v2 stable 发布时能在 48 小时内输出影响评估。
  • 回访日期：2026-12-12（两周后核对 v2 是否有新 breaking change 与 RFD 进展）。
  • 待验证假设/证伪条件：若 2027 年 Q2 前 v2 仍未 stable、或 JetBrains 从 Lead Maintainer 席位退出、或 Registry 停止增长，则"双标准格局定型"的判断需要下调为"Zed 单边标准"；反之若 MCP v(next) 吸收了忙时插入语义，则需重估两协议合流可能。

八、拓展应用推荐

  • 自研 Agent 接 IDE：用官方 SDK（Rust/TS/Kotlin/Py）+ TCK 套件验证，一步接入 Zed + JetBrains 全线分发。
  • 任何长连接消息桥设计：幂等键 + 回放哨兵 + 重试分级三件套可直接套用于飞书/Telegram/自建 WebSocket 桥的可靠性层。
  • 子代理可观测性：subagent_update 宣告 + 独立 sessionId + 成本聚合防双算的模型，可平移到 delegate_task 类编排器的状态上报设计。
  • 协议版本演进：-32022 结构化版本协商 + SDK 路由器双栈共存，是任何自研协议做大版本升级时的现成模板。
  • 技术选型报告：本文的四层协议栈图可直接用作企业 Agent 基建选型的坐标系。

九、指南分析

  • 协议工程学范本：ACP v2 的演进路径是开源协议治理的教科书案例——Draft 公开征求意见 → 17 个 alpha 小步迭代 → 双厂商真实产品联调 → RFD 治理新特性 → Preview（"可动工但未冻结"）→ 官方适配器当参考实现 + TCK 当验收门。可复用判据：破坏性变更必须同时交付迁移指南 + 双版本路由 + 回滚路径。
  • 扩展位预留手法："只增方法与能力、不改已有消息"是本项目最值得抄的设计纪律——steering/queueing/remote transports 三个未完成特性都靠这招实现了"发布不必等特性齐"。
  • 反例警示：命名混乱（三个 ACP）说明协议起名前的生态查重是必要动作；早期"某大厂不跟进"的判断在一年内被反转，说明生态判断要看分发利益结构（拒绝成本 vs 接入成本），不要把单个厂商的口头态度当作终局。
