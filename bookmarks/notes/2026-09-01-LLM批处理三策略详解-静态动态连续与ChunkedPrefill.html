一、内容详细整理

第一性原理：GPU 在等内存，不在算数

一块 A100：312 teraFLOPS（BF16 算力）vs 2 TB/s（内存带宽）。LLM 解码完全依赖后一个数字。

生成单个 token = 把模型里每一个权重从内存读一遍。读取主导时间，计算单元大部分时间在等数据——这份闲置算力是"免费容量"。

批处理的本质：权重只加载一次，多条序列推过同一次前向传播，内存成本摊给所有人。一批 60 条和一批 1 条坐的是同一次权重读取。

吞吐量曲线的形状：陡峭上升后变平——
- 拐点以下：内存受限，批处理几乎免费
- 拐点以上：算力受限，每加一条序列都要花真时间
- 拐点随模型/GPU/序列长度移动，必须在自己的硬件上实测

LLM 破坏了传统批处理的三个前提

分类器/embedding 模型的批处理是装箱问题（pad 到公共长度→叠张量→一次前向），成立依赖三件事，而自回归 LLM 全破坏：

传统前提 LLM 现实
一次前向传播产生完整答案 一次传播只产 1 个 token，400 token 回复=400 次前向
行与行互不依赖 行依赖自己的历史（每步读写 KV cache）
每行成本开始前已知 成本到结束才知道（stop token 决定，12 或 4000 token 后）

Padding 救不了：它拉平输入宽度，拉不平请求占用 GPU 的时长。固定批次按最慢成员速度跑——三种策略是对这个问题的三种回答，按"为此做了多少"递增。

策略一：静态批处理（Static Batching）

做法：收集固定数量请求→一起跑→等最后一个结束全部返回。

最慢成员问题的两笔账：R3 在 t=9 就停止生成，却坐到 t=15（等 R2）——① 用户答案早好了却多等延迟；② 槽位被占，排队请求进不来。

量化：Anyscale 在 40GB A100 + OPT-13B 实测——输出长度分布拉开后，静态批处理掉到 ~81 token/s，连续批处理高一个数量级。

它仍然正确的场景：输出长度无差异的负载——分类、embedding、打分（每条输出固定大小：一个标签/一个向量，几乎同时结束，没有人等落后者）。此时静态批处理更简单且零损失。

# vLLM 静态批处理：llm.generate 一次性交整个负载
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct")
outputs = llm.generate(prompts, SamplingParams(max_tokens=64))

👉 HF pipeline 的 batch_size 参数也是静态批处理——评测脚本可用，线上流量不合适。

策略二：动态批处理（Dynamic Batching）

新增的东西：计时器。批次在"达到大小上限"或"窗口到期"时触发（先到先得）。

修好了"等凑批"（R1/R2 在窗口到期就开跑，不用等第 3 个），但没修最慢成员：R1 在 t=7 结束仍要等到 t=12。

每批决定一次→控制权交给引擎直到全部结束。对固定输出模型这就是完整答案——Triton 内置的正是它：

dynamic_batching {
  preferred_batch_size: [4, 8]
  max_queue_delay_microseconds: 100
}
  • preferred_batch_size：调度器试图凑成的批大小列表
  • max_queue_delay_microseconds：请求等同伴的最长时间

策略三：连续批处理（Continuous Batching）— 现代引擎吞吐量的来源

扔掉的假设："批次是一个工作单元，跑到全部结束"。

迭代级调度：调度器跑一次迭代→拿回控制权→再决定一次。序列发出最终 token 的瞬间离开批次，等待中的请求下一轮占这个槽位。批次组成每个迭代都在变——没有槽位等最慢序列，输出长度天差地别 GPU 也保持饱和。

新限制是内存不是算力：每条活跃序列占一份随 token 增长的 KV cache；40GB A100 驻留 13B 模型时一次只能容纳几条长序列。池子用尽时调度器逐出（preemption）一条运行中请求，之后再重算——看起来像没余量，其实只是同一段 prefill 被算两遍。

各引擎命名对照：vLLM/SGLang/TGI = continuous batching；TensorRT-LLM = in-flight batching；LMDeploy = persistent batching。

衍生问题与解法：Chunked Prefill（分块预填充）

新问题：每轮重建批次修好最慢成员，又引入卡顿——新请求的一次性 prefill 是一大块吃算力的前向传播（32K prompt = 一整块），所有活跃解码排在后面等，"别人的输出说到一半停住，因为有人贴了一篇长文档"。

解法：把 prompt 切成固定大小 token 段（如 2K/块），安排在若干次前向传播中，每次扩展该请求的 KV cache。注意力数学不变（后面的块 attend 前面块处理过的内容），第一个 token 在最后一块处理完后到达。

深层价值：Prefill 是算力受限，解码是内存受限——一个批次同时含两者，就把芯片的两部分都用上了。

块大小权衡（无通用最优）：
- 更小块 → 调度器更多机会跑解码 → 活跃请求 ITL（token 间延迟）尖峰更低
- 更大块 → 处理新 prompt 更高效 → TTFT（首 token 延迟）通常更好，但活跃解码可能等更久
- 块太小 → GPU 利用率降 + 注意力开销增（后面块要重读前面块创建的 KV cache）

# vLLM V1 默认开启 chunked prefill
vllm serve meta-llama/Llama-3.1-8B-Instruct --max-num-batched-tokens 8192
# SGLang
sglang serve --model-path ... --chunked-prefill-size 8192   # -1 关闭

结论（原文）

三种策略的区别只在于什么时候固定批次，每种对应一种工作负载形态。对输出长度可变的线上流量，连续批处理是唯一站得住的——且每个主流引擎默认就给你。全文建立在一个 GPU 事实上：一次前向传播的瓶颈是把权重从内存读出来，不是数学运算。

归纳总结

  1. 一条主线贯穿全文：批次什么时候定下来。静态=开始前一次；动态=计时器每批一次；连续=每次前向传播都重定。决策频率越高，GPU 饱和度越高，工程复杂度也越高——这是"调度粒度换吞吐量"的连续谱。
  2. 每代策略修上一代的病、留自己的病：静态批处理病在最慢成员；动态修了凑批等待、仍病在最慢成员；连续修了最慢成员、病在长 prefill 卡顿；chunked prefill 修了卡顿、引入块大小权衡。技术演进链=缺陷传递链。
  3. 内存/算力二相性是理解一切的钥匙：解码内存受限（权重读取主导）、prefill 算力受限（并行注意力计算）——批处理摊薄内存成本，chunked prefill 让两类负载混跑榨干两部分芯片。
  4. 没有银弹，只有负载匹配：固定输出（分类/embedding/打分）用静态最简；可变输出线上流量必须连续批处理；块大小取决于模型/GPU/prompt 分布/SLO 指标——"要在自己的硬件上量"出现两次不是偶然。
  5. 量化的表达力：81 token/s vs 高一个数量级（静态 vs 连续）——同一个 GPU 同一个模型，调度策略差异就是 10 倍吞吐，这是"软件吃掉硬件红利"的典型样本。

二、趋势判断

  1. 连续批处理已成事实标准并默认化：vLLM V1 默认开 chunked prefill、各引擎默认 continuous batching——"要不要用"的讨论结束了，剩"怎么调参"（块大小/最大 token 数/逐出策略）。
  2. 推理引擎竞争焦点从吞吐量转向延迟分布：吞吐量优化接近物理上限（权重读取摊无可摊），TTFT/ITL 尖峰等尾延迟指标成为差异化战场——chunked prefill 的块大小权衡正是这个转向的缩影。
  3. 调度粒度继续细化：从批级→迭代级的路径会继续走到 token 级（与投机解码/多 token 预测汇合），调度器越来越像操作系统的进程调度器。
  4. "在自家硬件上实测拐点"会是推理部署的必修课：模型/GPU/序列长度的组合空间爆炸，任何通用建议都只是起点——这与 GPU capacity estimation 技能的方法论一致。

指南分析

策略选择速查表（从原文提炼）：

你的负载 该用策略 理由
分类/embedding/打分（固定输出） 静态批处理 同时结束无短板，最简单零损失
