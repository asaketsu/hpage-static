摘要

白家杰以真实项目 JK Launcher（Unity 桌面启动器工具）为样本，完整还原了从零搭建 Harness Engineering 的全过程。文章不谈理念只讲工程落地，逐层拆解 Rule → Skill → Sub Agent → Workflow → Scripts → dev-map → 任务看板的演化路径，每一层都是被真实问题逼出来的，不是预设架构。

核心价值判断

这篇文章对我们 Hermes 系统有极高的参考价值。作者的核心方法论与我们已经建立的 Skill/Cron/Memory/Exchange 体系高度吻合，但他在几个关键点上比我们走得更深、表述得更清晰，值得系统性吸收。## 第一章：六个核心概念定义

文章开篇先厘清六个核心概念，这是后面所有工程实践的地基。作者强调"概念没分清楚，后面就很难搭得稳"。

概念 定位 比喻 解决什么问题
Rule 工程规矩/底线 研发制度 减少混乱，不创造价值
MCP 外接能力接口 标准插座 让AI接入CI/签名/发布等外部系统
Skill 标准操作手册 SOP 固定动作不靠临场发挥
Sub Agent 分工角色 项目组成员 角色分离，避免一人演全部
Workflow 接力赛规则 指挥链 前进/暂停/打回有明确依据
Scripts 硬门禁 闸机 做没做到由脚本判定，不是AI自述

关键认知：Rule是软约束（AI可能忘/绕/偷懒），Scripts是硬约束（不过不行的门禁）。真正成熟的Harness最后一定越来越依赖脚本而非提示词。

第二~四章：SPEC → Rule → Skill 演化

搭建顺序不是凭直觉，而是被问题逼出来的：

  1. 先磨SPEC — 和AI反复聊需求，聊到烦为止。SPEC必须无不确定词（禁止"建议/可以/推荐/可选"），所有边界条件必须写死。
  2. 补Rule — SPEC只解决"知道做什么"，不解决"稳定做到位"。Rule管最容易被偷懒的底线动作（编译→测试→验证三连）。
  3. 下沉Skill — Rule越写越长时，把固定步骤拆成Skill。Rule只说"你必须做"，Skill说"具体怎么做"。好处：Rule变轻、执行稳定、维护成本低。

这三步对应我们的实践：AGENTS.md（SPEC+Rule）→ SKILL.md（Skill）→ Cron（自动化），已高度吻合。## 第五章：三种多Agent路线对比

作者对多Agent形态做了系统性PK，最终选择结构化调度：

路线 优点 缺点 结论
强化单Agent 成本最低 角色冲突严重 早期有效，不能是最终形态
去中心化协作（AutoGen式） 灵活、像AI团队开会 路径不稳定、责任边界不清 明确放弃
结构化调度 流程清晰、可审计、可维护 前期设计成本高 最终选择

决策逻辑：真正贵的不是token，真正贵的是失控。对长期维护的工程，可控、可追踪、可复用比灵活更重要。

结构化调度内部又PK了两种：固定角色固定流程 vs 动态招聘式。选前者，因为工作流结构本身相对固定（需求→方案→开发→审查→测试），不需要为"理论灵活性"牺牲稳定性。

第六~七章：七个Agent的演化

七个Agent不是拍脑袋拆的，而是逐层被问题逼出来的：

  1. 需求分析 → 把模糊想法变成结构化需求
  2. 方案设计 → 把需求翻译成可落地方案
  3. 开发实现 → 按约束写代码
  4. 闸门总控（可行性分析）→ 开发前最后一道门，判断需求够不够清、方案有没有漏、能不能安全落地
  5. 代码审查 → 对照需求+方案做技术收口
  6. 测试验证 → 功能+边界+回归+稳定性做结果收口
  7. PM → 只做路由/交接/回退，不做专业判断

六轮补稳过程暴露的典型问题和修复：

轮次 问题 修复
1 下游自己改上游文档 禁止下游改上游，只能提阻塞由PM打回
2 PM越界给专业意见 PM收缩为"总路由器"，不给专业判断
3 代码审查/测试太浅 加强为需求+方案对照的深度收口
4 Rule被解释性执行 可判定约束下沉到脚本
5 AI推卸责任给"历史遗留" 基线对比（改前改后各跑一遍）
6 流程本身难维护 抽出流程定义文件+角色契约+流程校验脚本

PM角色定位极为精准："不是最懂研发的PM，而是最守流程边界的PM"。PM一旦越界，整个系统滑回"一个中央大脑说了算"。## 第八章：总验证脚本 — Harness的质变点

总验证脚本是最容易被低估但实际价值极高的模块。它不是一个检查工具，而是把"完成"的定义从AI主观汇报变成客观判定。

覆盖四类检查：A.静态规范（XAML无中文/无Emoji/无高版本语法/无硬编码）B.基础门槛（编译过/测试过/测试数不减少）C.工程一致性（规则同步/csproj完整）D.基线对比（改前改后增量检查）。

核心洞察：没有事后验证的Harness停留在"任务完成幻觉"——AI改了代码、写了文档、推进了流程，但系统本身不知道结果是对还是错。总验证脚本补上的是一整个反馈闭环，让Harness从"能推动事情"进化为"能判断结果"。

第九章：dev-map + 任务看板

当项目进入持续迭代，PM和Agent缺乏全局视野，容易"新方案冲旧方案"和"重复造轮子"。

模块 维护者 解决什么 像什么
dev-map 开发Agent 模式/落点/影响面，少重复造轮子 开发导航图
任务看板 PM 任务历史/阶段/文档入口 项目态势板

关键原则：不是堆字数，而是一套够准的索引。先告诉AI从哪几条线进门，再让它自己翻代码对细节。维护上让流程里的AI自己改、自己闭环（谁动代码谁改地图，谁管需求谁改看板）。

最小起步路径（7步）

  1. 先磨SPEC（和AI反复聊需求到烦）
  2. 补最关键的Rule（不贪多，只盯底线）
  3. 高频固定动作下沉为Skill
  4. 单Agent失稳时再拆多Agent
  5. 多Agent复杂时补流程定义文件+角色契约
  6. 持续迭代时补dev-map+任务看板
  7. 想往外推时再接MCP## 对Hermes系统的借鉴与启发

✅ 已吻合（确认方向正确）

  • SPEC → Rule → Skill 的分层体系，对应我们的 AGENTS.md + SKILL.md + Cron
  • 基线对比机制，我们的 sensor-grid 已在做（错误率/漂移检测）
  • 小批推进法，我们已是标配
  • 流程校验脚本，我们的 notes_lint / auto-defense-check 已在跑
  • dev-map 概念，我们有 ~/uclaw/project/INDEX.yaml

🔥 有利（应立即吸收）

  1. PM"总路由器"定位：我们的 OPM Meow 角色应严格限定为路由+交接，不做专业判断。当前 AGENTS.md 中 OPM 有"ROI评估"职责，存在越界风险
  2. 下游禁改上游产物：delegate_task 的子agent不应修改调用者提供的 context 文件，应提阻塞而非自行修补
  3. 角色契约概念：给每个 team role 补一份输入/输出/阻塞条件的接口说明，写入对应 skill
  4. 总验证脚本思想：任务完成不该由agent自述，应有可执行的检查脚本判定。可融入 subtask-lifecycle skill

📝 有价值（记录备查）

  1. 不同Agent配不同模型档位 — 我们已部分在做（cron用简单模型），可进一步细化
  2. 流程定义文件抽离 — 当协作复杂度继续上升时考虑
  3. 任务看板 — 比我们的 active_tasks.json 更结构化，值得后续迭代

⚠️ 我们有而他缺失的

  • 双机交换协议（他只有单机）
  • 自进化闭环（evolver/auto-dream）
  • 持久记忆系统（跨session恢复）
  • 生图四通道等创意能力
