〇、定锚：我的现状与目标

我手上有一个刚完成的 okf-minimal 项目：按官方 SPEC v0.2 从零实现了 OKF 的解析、导航、Attested Computation 执行与 attestation，并用 TF-IDF 基线做了同题 A/B 对照（确定性导航 20.0% 正确 vs 相似度检索 30.77% 错误）。我的痛点是：自家知识体系（Hermes 三级记忆 + 3400+ 笔记）已经出现"检索措辞敏感、过时知识平等竞争"的 RAG 式症状；我的目标是判断 OKF 范式里哪些设计值得吸收、哪些是营销噪音，两周内能落地什么。本篇是判断的依据，不是泛泛的科普。

一、内容整理

1.1 OKF 是什么（SPEC v0.2 逐条，全部来自官方规范原文）

  • 知识载体是一个目录的 Markdown 文件 + YAML frontmatter，"If you can cat a file, you can read OKF; if you can git clone a repo, you can ship it"〔方法，2026-06〕。没有 schema 注册中心、没有中心权威、没有必需工具链。
  • 目录即身份：概念 ID = 文件路径去掉 .md（如 metrics/churn_rate）。概念 = 一个需要"唯一真实版本"的知识单元：指标定义、表结构、API 契约、runbook。一文件一概念〔方法，2026-06〕。
  • frontmatter 唯一必需字段是 type（如 Metric / Table / Attested Computation）——"a concept carrying just type is fully conformant"，最小合规文件只要三行〔数据，2026-06〕。
  • 信任家族：verified[] {by, at} + actor 约定（Agent=producer/version、人=human:id、进程=process:id）。信任分三级：unverified → machine-confirmed → human-reviewed，判定键是 human: 前缀〔方法，2026-06〕。
  • 生命周期家族：status: draft/stable/deprecated（缺省 stable）+ stale_after 绝对时刻。deprecated 概念保留供历史查询复现，但消费者必须能识别它不是当前版本〔方法，2026-06〕。
  • 溯源家族：sources[] 记录每条知识的来源（resource/author/usage_count/last_modified）——存客观信号、不存主观分数，"a score is subjective, unportable, and goes stale"〔方法，2026-06〕。
  • Attested Computation（v0.2 灵魂增量）： sanctioned 计算存 body 的 # Computation 围栏，Agent 只能绑定声明的 parameters、不得改写计算本体；executor 返回 receipt（executed_sql/job_id/result），attester 做规范化等价比对——"a rewritten query, a swapped computation file, or a mutated dependency fails the check"〔方法，2026-06〕。
  • 消费者宽容性：MUST NOT 因缺可选字段、未知 type、未知键、断链、缺 index 拒绝 bundle。断链被定义为"尚未写下的知识"，是特性不是缺陷〔方法，2026-06〕。

1.2 普通 RAG 的设计基线（作为对照组的公理化描述）

  • 知识被切成 chunk（通常 256-1024 token），嵌入为向量，检索按余弦相似度排序取 top-k，LLM 基于检索结果生成〔方法，业界标准〕。
  • chunk 没有身份、没有生命周期、没有信任等级——2023 年的 PPT 和 2026 年的政策在向量空间里是平等公民。
  • 更新 = 重新嵌入 + 重建索引；同步一致性是公认的工程噩梦（原文："嵌入与数据的同步简直就是噩梦"〔观点，2026〕）。

1.3 本项目实测数据（A/B 对照，全部真跑）

  • 同一问题 "Q2 churn rate definition"，语料含策划 OKF bundle + 2023 董事会 PPT + Slack 争吵 + 过时 wiki〔案例，2026-11-18 实测〕：
  • RAG 基线（TF-IDF 词面相似度）：3 个措辞变体 0/3 命中 sanctioned 文档，top-1 在 legacy 定义/董事会 PPT/过时 wiki 之间漂移；照 wiki 公式执行得 30.77%（混入 trial/internal 账户，错误）
  • OKF 导航：恒定入口 metrics/churn_rate + 依赖闭包（computation + 2 表 + policy 共 6 概念），5 次运行 fingerprint byte-identical；attested 执行得 20.0%（与合成仓库 ground truth 一致）
  • 篡改检测：删掉排除 JOIN 的 tampered SQL 被 attester 拒绝（canonical-SQL mismatch）
  • 导航平局裁决实测：纯词面打分时 "q2" token 恰在 computation 的路径里导致平局——解法是回归 §8 本意走 index 条目路由 + OKF 原生信号裁决链（lifecycle → type 路由 → trust → 稳定 id），零随机零阈值〔案例，2026-11-18〕。

二、查询拓展

2.1 OKF 的局限与反对意见（验证型：OKF limitations criticism）

  • 官方 SPEC 自己的 "Considered and deferred" 清单承认：receipt/verdict 线格式、attester ABI 与沙箱、attestation 缓存、语义层模板（Looker/dbt）全部推迟到未来版本〔补充，2026-06〕——Attested Computation 目前只是接口约定，跨组织互验尚未闭环。
  • LinkedIn 规范解读确认："The specification is deliberately permissive. Consumers should tolerate unknown concept types..."——宽容性是刻意设计，代价是不同生产者的 bundle 质量方差极大〔支持，2026-06〕。
  • 冷启动与维护成本是最大隐性反对：bundle 不会自己长出来，官方假设"后台 AI Agent 是维护引擎"（代码更新→自动改文档），但这本身就是一套需要建设的自动化，不是格式的免费赠品〔补充，2026-11 推断〕。

2.2 生态时效（时效型：open knowledge format 2026 adoption）

  • v0.1 发布于 2026-06-12（Apache 2.0），官方 repo 已 1.5k stars，SPEC 已迭代到 v0.2（supersede 了 timestamp→generated.at、body Citations→sources 两处 breaking change）〔数据，2026-11-18 实测 GitHub API〕。
  • GitHub 上 "open-knowledge-format" 相关仓库已有 41 个，出现了 open-ckf-compiled-knowledge-format（编译型知识格式，schema-stable）等变体流派，以及官方 starter 模板〔数据，2026-11-18 实测搜索〕。

2.3 同类标准对照（对照型：llms.txt vs OKF vs sitemap）

  • Semrush 对比分析指出：XML sitemap 列站点页面、llms.txt 给爬虫指路，都是向外的；OKF 是向内的——直接把组织自己的知识打包成 Agent 可直读的文件〔补充，2026〕。三者不竞争，是不同层面。
  • 公众号原文的 5 处失真（wiki 链接语法、字段名、版本、org 名、"99% 猜错"修辞）我在项目里已逐条审计——概念方向对，实现细节必须以 SPEC 为准〔反驳原文，2026-11-18〕。

三、归纳总结

3.1 核心框架：两种范式在十个设计维度上的分野

维度             RAG（概率检索）              OKF（确定性导航）
─────────────────────────────────────────────────────────────
知识单元    chunk：无身份，切分破坏结构    concept：路径即身份，一文件一概念
组织方式    向量空间（几何邻近）           目录树 + 链接图（拓扑结构）
查询机制    embedding 相似度排序          index 渐进披露 + 链接 BFS 闭包
元数据      检索层外挂，来源/时间易失     frontmatter 一等公民
时间维度    无生命周期，新旧平等竞争      deprecated / stale_after 显式降级
信任维度    无（语料不区分作者）          三级 trust tier，human: 前缀锚定
可验证性    生成过程不可审计              Git 全历史 + attestation 收据比对
更新成本    重嵌入同步噩梦                纯文本 diff / PR
确定性      同题不同答（措辞敏感）         同题同答（byte-identical）
失败模式    静默错误（错 SQL 也自信）      显式失败（attester 拒绝/断链报告）

本质差异一句话：RAG 把"知识在哪里"交给概率去猜，OKF 把它做成工程事实。RAG 回答"什么跟这相似"，OKF 回答"这就是那个东西、谁写的、还作数吗"。

3.2 信任与生命周期：OKF 最被低估的设计

RAG 的 chunk 是无主之地，OKF 给每个知识点配了三样 RAG 世界里不存在的东西：

  • 责任链：generated.by（谁写的）与 verified[].by（谁确认的）分离——写者不必是确认者，就像作者与审签人分离
  • 时效边界：stale_after 是绝对时刻而非相对 TTL——"过没过期"是一次朴素比较，不需要知道"什么时候读的"
  • 可机械验证的计算：Attested Computation 把"数字必须按指定方式产出"固化成接口。本项目实测：sanctioned SQL 与 tampered SQL 只差一个 JOIN，数字差 10.77 个百分点，attester 机械区分——这在 RAG 里没有任何对应物

3.3 三维护筛（对"OKF 替代 RAG"这一核心主张）

  • 优点：确定性、可审计、零基础设施（Git 即仓库）三条都实测成立；证据强度：本项目 13 断言 + 34 pytest 全绿，A/B 差距（0/3 vs byte-identical；30.77% vs 20.0%）是结构性而非调参可消除的
  • 缺点：①探索性查询天然弱——问"我们公司有什么值得关注的趋势"这种未知未知，链接图无路可走，还是得检索；②冷启动贵——bundle 要人工策划，官方叙事里"Agent 自动维护"本身是需要建设的系统；③SPEC deferred 清单很长，跨组织 attestation 互验是空中楼阁；④宽容性是双刃剑——不拒绝任何东西的标准也无法保证任何东西
  • 借鉴点：直接迁移的是 trust tier + lifecycle 元数据（可加到任何知识库，包括我自己的笔记体系）；需要改造的是导航——纯 index 条目路由在概念多的 bundle 会退化，实测已见平局需要裁决链，大规模场景需 hybrid（索引+轻量打分）

四、趋势判断

趋势1：分层混合架构成为主流（方向：上升）

依据：2026-06 OKF 发布到 11 月已 v0.2 + 41 个生态仓库；同时官方博客口径是"OKF 没有取消检索"。原文的三层架构（智能路由器 → OKF 精确层 / RAG 探索层）与 Anthropic/Google 的公开实践（结构化记忆 + 检索兜底）同向。对我的机会：先在"定义/契约/政策"类知识上落 OKF，检索层保留。

趋势2：知识格式标准进入战国（方向：分化）

依据：llms.txt（2025）→ OKF v0.1（2026-06）→ v0.2（2026 下半年）→ CKF 编译型变体（2026-11 已现身 GitHub），一年三代。风险：格式间的转换成本会落在用户头上；盯官方 repo 的 minor bump 即可，不必赌变体。

趋势3：可验证性（attestation）是下一战场（方向：上升）

依据：v0.2 的最大增量全是信任机器（trust tier/lifecycle/attested computation），deferred 清单里 receipt 线格式、attester ABI 都指向"Agent 产出的数字要能机械验真"。这与 Agent 经济学的刚需合流。对我的机会：attester 思想（执行收据 + 规范化比对）可以先用在自己的 Agent 产数管线里，不等标准。

趋势4：个人知识管理吸收 OKF 元数据（方向：缓慢上升）

依据：我的笔记体系 3400+ 篇已出现 RAG 式症状（过时笔记平等竞争），而 OKF 的 frontmatter 方案零成本可加。风险：维护纪律跟不上就是装饰性元数据。

五、关联分析

5.1 与 okf-minimal 项目的关联

本笔记全部实测数据的来源项目（~/uclaw/project/okf-minimal）：7 概念合规 bundle、§3-§11 全覆盖实现、A/B demo。笔记的每个论断都能在项目里找到对应断言。

5.2 与 Hermes 三级记忆体系的关联（同构映射）

L1 MEMORY.md 每 session 全量注入 = 确定性导航（不需要检索，一定到达）；L2 短期/L3 Topic 索引按需检索 = 检索层。我的记忆架构早就隐性采用了 OKF 哲学：铁律必须是确定性的（注入），才敢让其余知识走概率检索。OKF 等于把这个直觉做成了带信任分级的显式标准。

5.3 与飞机构型管理的关联〔领域扩展，非原文内容〕

OKF 与适航构型管理（Configuration Management）深层同构：

  • 概念文件的"唯一真实版本" = 构型基线（Configuration Baseline）的单一数据源原则
  • status: deprecated = 被替代件（superseded part）：保留可追溯、禁止新设计使用——与 EBOM 中"用而不断"的替代件管理一字不差
  • verified by human:xxx = 检验签章/适航审查批准（authorised signature），process:xxx = 自动化检验工序
  • Git log/blame = 构型记录（Configuration Records）/更改单追溯链
  • Attested Computation = 工艺规程（工艺参数锁定）+ 检验收据（实测值与规程比对）

这套映射说明 OKF 不是发明新思想，而是把高可靠行业 fifty 年的构型纪律移植到 Agent 知识层。反过来看：凡是"错误知识会出人命/亏大钱"的领域（航空/医疗/金融），构型化知识管理是必然而非选型。

5.4 与 bm25-cjk 多跳检索笔记的关联

同属"确定性检索"谱系：BM25 多跳用关键词索引+判别器逼近确定性，OKF 直接用人工策划的链接图一步到位。前者迁移成本低，后者确定性上限高。

六、金句摘录

"If you can cat a file, you can read OKF; if you can git clone a repo, you can ship it." — SPEC §1，最小主义设计的教科书表述

"从概率性的「瞎猜」转向确定性的「精确导航」。" — 原文核心命题

"RAG 很强大，擅长处理『未知中的未知』。但对于已经知道的东西……需要的是确定性和精准性，不是概率式的猜测。" — 分层架构的哲学基础

"a score is subjective, unportable, and goes stale." — SPEC §5.1，解释为何只存信号不存分数：这一句适用于一切评分系统设计

七、行动启示与回访

我的结论：保留"确定性导航 + 信任分级"的设计思想（已实测成立）；放弃"OKF 全面替代 RAG"的叙事（探索性查询结构性弱）；改造自己的知识体系——给高频引用的笔记加 trust/lifecycle frontmatter 试验。

  • 行动1：给 20 篇高频引用的技术笔记加 status/stale_after/verified 三字段，观察一个月内是否改变引用行为 | 时间：本周末 | 触发条件：无（直接做） | 验收标准：至少能识别出 3 篇"还在被引用但已过时"的笔记
  • 行动2：okf-minimal 补多 bundle/跨 bundle 导航能力评估，验证概念规模上到 500+ 时 index 路由是否退化 | 时间：两周内 | 触发条件：出现真实多 bundle 需求 | 验收标准：500 概念 bundle 上导航仍 byte-identical 且平局率 <10%
  • 回访日期：2026-12-02（两周）
  • 待验证假设/证伪条件：若一个月的行动1 显示加元数据后引用行为无变化（没人看 status），说明元数据是装饰——OKF 思想对我体系的适用性被高估，应停止扩散试验

八、拓展应用推荐

  • 企业语义层：指标字典/API 契约/表结构 → OKF bundle，Agent 查数走导航不走检索（场景→用法：churn_rate 案例的直接放大）
  • Agent 记忆持久层：长期记忆按 OKF 组织，L1 铁律=根 index，跨会话 Agent 共享知识有了标准容器
  • 适航/构型文档基线〔领域〕：型号资料的"现行有效版本"管理，deprecated 语义与替代件管理天然对齐
  • CI 知识门禁：validate.py 进 pipeline，文档 PR 不过合规校验不许合——"validate before you ship"
  • LLM 输出验证管线：attester 的"执行收据+规范化比对"模式独立于 OKF 可复用（任何 Agent 产数场景）

九、指南分析

  • 宽容性标准设计：SPEC 通篇 MUST/SHOULD/MAY 分级，且把"消费者 MUST NOT 拒绝"写成硬规则——推广期标准宁可放弃校验力也要保证互操作，这是 v0.x 标准的生存策略，值得任何自定协议借鉴
  • 最小必需面：唯一必需字段 type、三行即合规——采用门槛压到地板；对照很多企业 schema 设计一上来 20 个必填字段的失败模式
  • 写者与确认者分离（generated vs verified）、信号与分数分离（sources 信号 vs 主观评分）、定义与计算分离（Metric vs Attested Computation）——三个分离是整份 SPEC 最值得抄的建模手法
  • 本项目开发过程的可复用判据：导航系统先走策划索引再全库扫描（纯词面打分必平局）；平局裁决链要用领域原生信号而非调权重；A/B 对照的数字要真执行出来（20.0% vs 30.77%）而不是宣称
