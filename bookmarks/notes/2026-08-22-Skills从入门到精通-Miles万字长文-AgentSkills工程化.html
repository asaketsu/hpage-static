一句话总纲

Skill 最小就是一份"教 AI 怎么做事的说明书"（触发条件/资料/顺序/边界/完成标准五件事），学习顺序不能反：先做稳定复用的小 Skill，再逐步加文件拆分、工具接入、评测和企业治理。

一、内容详细整理

1.1 Skill 到底是什么

截至 2026-08，Agent Skills 已成开放规范。最低形态 = 一个文件夹 + SKILL.md：

my-skill/
└── SKILL.md

SKILL.md 结构：YAML frontmatter（名称+描述）+ 正文（做事方法）。

渐进式加载（progressive loading）：Agent 启动时只读名称和描述 → 任务匹配后读正文 → 正文按需指向其他资料。

解决的实际问题：提示词一次对话用完就散；Skill 把一类任务的做法存成文件，可复用/分享/版本管理。

最小 Skill 可以只有一段提示词——有明确用途、能被发现、能重复执行，就是一个成立的 Skill。

1.2 第一个最小 Skill：五件事 + 三条测试

选材原则：别选"做行业研究"这种宽任务，找一件做过很多次、结果好坏看得出来的工作。

示范：根据项目记录写周报。动手前先写三条测试请求：

  1. 正常任务（确定标准流程）
  2. 信息不足（处理缺失输入）
  3. 高风险动作边界（划出不能做的事）

五件事（SKILL.md 第一版只需写清）：

  • 什么请求应该触发
  • 需要读取什么资料
  • 按什么顺序处理
  • 哪些事不能做
  • 怎样才算完成

description 要认真写：Agent 主要靠它判断是否调用。"帮助处理项目内容"没用；"生成项目周报、整理本周进展、汇总风险"才像用户真的会提的任务。

测试方法：至少跑三条测试 + 两条相似但不该触发的请求（"修改 Jira 状态"/"给客户写延期说明"）。总抢任务 → 收窄 description；该用时找不到 → 补真实触发说法。

1.3 内容多了怎么拆文件

开放规范的可选目录：

my-skill/
├── SKILL.md        ← 任务入口、执行顺序、关键边界、完成条件
├── references/     ← 业务制度、字段说明、API 文档、长案例
├── assets/         ← 输出模板、图片、字体等成品素材
├── scripts/        ← 格式校验、数据转换等确定性操作
└── evals/          ← 测试请求与预期结果（企业常用，非规范强制）

主文件要告诉 Agent 什么时候读哪份资料——资料包可以很大，不需要的文件不进上下文。

500 行提醒灯：官方建议 SKILL.md 保持 500 行以内——不是硬门槛，是"执行路线/参考资料/样例已混在一起"的信号。

脚本不急着加：模型擅长模糊文字，脚本适合确定规则。判断风险描述是否清楚 → 模型；检查日期格式/文件名/必填字段 → 脚本。

1.4 接外部能力：知识库/MCP/API

必须守住的边界：Skill 能描述怎样使用能力、携带调用脚本，但不凭空创造网络、权限和凭证。

知识库三种接法：

  1. Skill 中的脚本调用 HTTP API
  2. 查询能力做成 MCP Tool，Skill 指导 Agent 何时搜索
  3. Agent 运行时注册自定义工具，Skill 只写查询规则

分工原则：知识库提供事实，API/MCP 提供入口，Skill 决定怎么查怎么判断怎么写——不要揉成一个名词。

MCP 地址可以写进 Skill 吗：可以写名称/用途/所需工具/连接条件/配置模板，但这只是声明依赖，不建立连接。地址/认证/权限在宿主或 Agent 配置层完成，密钥不进 Skill。

跨平台原则：把"工作方法"和"连接实现"分开——Skill 写依赖和降级方式，连接/密钥/权限留在运行时。（Anthropic Claude API 上传的 Skills 运行在无网络沙箱，不能直接访问外部 API。）

1.5 多 Skill 和 Agent 怎么配合

  • Skill A 调 Skill B：可行但开放规范没有 dependencies: [skill-b] 通用字段——是否执行取决于宿主开放度/B 可见性/Agent 配置
  • 三种处理：偶尔配合（入口 Skill 写使用条件）/ 经常配合（Agent 或角色包预装）/ 顺序严格（交给 Workflow 编排）
  • 角色要求（"以安全审查员视角检查"）改变任务工作方式，但不自动切换模型/工具/权限
  • 独立子 Agent：Claude Code 的 context: fork 和 agent 扩展字段是平台特有，非开放规范——跨平台要确认三件事：子 Agent 预加载/能发现/能调用什么

1.6 Skill 越做越大出什么问题

判断大 Skill 是否有问题，看它大在哪里：

  • 资料多（references/ 里大量文档）→ 不是坏事，按需读取
  • 任务范围和执行面一起变大 → 才容易失控：description 写不准 + 权限故障点膨胀

上下文预算实例：Claude Code 自动压缩后每个重挂载 Skill 最多保留 5000 tokens，所有重挂载 Skills 共用 25000 tokens——内容太长或连续调用太多，较早的 Skill 可能被丢弃。

拆太细也有问题：几十个极小 Skill → 名称描述参与发现，越多越相近越容易选错。Claude API 每请求最多 8 个 Skills。

拆分四判据（作者经验）：

  1. 触发请求是否相近
  2. 产出是否一致
  3. 权限是否相近
  4. 业务负责人是否相同

四项大体一致 → 留一个 Skill；一项明显分开 → 值得拆。

1.7 怎么把 Skill 测稳

五类评测覆盖：

  1. 应该触发的正常请求
  2. 不应该触发的相似请求
  3. 说法模糊的边界请求
  4. 缺输入/工具不可用/数据冲突
  5. 与其他 Skill 共存时是否还选得对

负例要有价值：周报 Skill 的负例不要写"今天天气怎么样"——"修改 Jira 状态""给客户发送进度""写项目复盘"更近，能测出边界是否真清楚。

排错顺序（避免"不管什么问题都加 Prompt 字数"）：

没触发 → 改名称与 description
触发但漏步骤 → 改正文和文件导航
读到规则仍做错 → 补真实示例 或 确定规则交给脚本
工具失败 → 查连接/参数/凭证/权限
多 Skill 抢任务 → 收窄描述或重新分组

1.8 企业级 Skill 多出的工作

安全分级：

  • 只读/草稿 → 低风险
  • 发消息/改系统/部署/删除 → 严格审批+确认+审计

权限不能只写在提示词：Skill 写"只读"不会把可写 Token 变只读——用户身份/源系统 ACL/MCP 权限/沙箱网络策略才决定 Agent 实际能碰什么。

第三方 Skill 按软件包审查：引用资料/脚本/外部地址/网络调用/子进程/硬编码凭证/数据外传路径。来源可信不代表后续依赖永远可信。

版本与责任：Git + PR 评审 + 固定版本 + 回滚方法。每个 Skill 要能回答：谁维护规则/谁批准脚本权限/生产版本/评测最近跑的时间/出问题谁停用回滚。

共存测试：新 Skill 上线前与同角色已有 Skills 一起测——抢触发/输出退化/把只读任务带进高权限路径。

1.9 FDE 落地方法论

先跟一线走完真实工作 → 分层放置：

事实和正式材料   → 知识库
系统能力         → API、MCP、App、Tool
专家判断方法     → Skill
角色模型工具组合 → Agent
定时审批重试     → Workflow
身份与权限       → IAM、运行时、源系统

第一版只覆盖最常见高价值用例 → 真实试跑记录漏读/误用/人工修改量 → 证明有用再做分发/版本/监控/交接。

二、查询拓展

2.1 渐进式加载的工程本质

渐进式加载是上下文预算管理的标准解法：

L1 元数据层：name + description（常驻，参与发现）
L2 正文层：SKILL.md body（任务匹配后加载）
L3 资料层：references/assets/scripts（按需读取）

这与本机 Hermes 的 L1/L2/L3 分层加载（AGENTS.md 常驻/Skill 按需/Wiki 查询）完全同构——Agent Skills 规范把这个模式标准化了。

2.2 各平台上下文限制对照（文中披露的实测数据）

平台 限制
Claude Code 压缩后 每个重挂载 Skill ≤5000 tokens；所有重挂载 Skills 共用 25000 tokens
Claude API 每次请求最多携带 8 个 Skills
SKILL.md 建议长度 500 行以内（提醒灯，非硬门槛）

对本机的启示：Hermes 的 skill 注入机制没有这么紧的 token 限制，但 400+ Skill 的 description 总量已经可观——description 的"发现成本"是真实的。

2.3 "工作方法 vs 连接实现"分离

这是本文最有工程价值的原则之一：

  • Skill 层：依赖声明 + 使用方法 + 降级方式
  • 运行时层：连接、密钥、权限

同花顺 Financial-API 的 Skill 设计（Key 只进 credentials.env 不进 Skill）与这条原则完全一致——行业正在收敛到这个约定。

三、归纳总结

3.1 Skill 成熟度分层

L0 一段提示词（最小 Skill：能触发能复用）
L1 五件事结构（触发/资料/顺序/边界/完成标准）
L2 文件拆分（references/assets/scripts + 主文件导航）
L3 外部能力（知识库/MCP/API，方法与连接分离）
L4 评测（五类覆盖 + 排错顺序）
L5 企业治理（安全分级/版本责任/共存测试）

3.2 拆分四判据（决策表）

判据 一致 分开
触发请求 相近 不同人群不同任务
产出 一致 不同类型交付物
权限 相近 只读 vs 可写
业务负责人 同一人 不同团队

→ 四项大体一致留一个；一项明显分开就拆。

四、趋势判断

趋势 1：Agent Skills 开放规范成为跨平台交付契约

依据：文中明确"截至 2026-08 已形成开放规范"，ChatGPT/Claude Code/同花顺/pm-skills 全部遵循同一 SKILL.md 结构。Skill 可像 npm 包一样跨平台分发正在成为现实。

趋势 2：Skill 治理（evals/版本/共存测试）成为企业落地瓶颈

依据：本文花 1/3 篇幅讲企业级（安全分级/责任矩阵/共存测试）——个人写 Skill 容易，企业管 Skill 难。Skill 数量增长后，治理能力决定落地深度。

趋势 3：上下文预算倒逼 Skill 瘦身

依据：Claude Code 5000/25000 token 限制 + Claude API 8 Skills 上限。平台限制会推动"description 精准化 + 正文拆分到 references"成为写 Skill 的默认纪律。

六、拓展应用推荐

6.1 可立即落地的 5 项

  1. 拆分四判据进 skill-review：给本机 400+ Skill 的合并/拆分决策加客观标准（触发/产出/权限/负责人四问）
  2. 五类评测补齐 stress-test：特别是负例类（相似但不该触发的请求）和共存类（新 Skill 是否抢旧 Skill 的活）——与 EnvHarness 借鉴的"Rule 型变体"天然配合
  3. 排错 SOP 显式化：skill 不工作时按"没触发→desc / 漏步骤→正文 / 做错→示例或脚本 / 工具失败→连接 / 抢任务→收窄"顺序排——写进 skill-review
  4. description 精准化巡检：本机 skill 的 description 质量参差（"帮助处理项目内容"式的空描述）——可写脚本扫描无实义的 description
  5. 500 行提醒灯：给 SKILL.md 加行数统计（本机部分 skill 已超），配合 skill-review 的体检

6.2 企业治理层（中长期）

  • Skill 安全分级（只读/草稿 vs 写入/部署）映射到本机工具权限三层模型
  • 共存测试纳入新 skill 上线流程（skill_manage create 后跑一次与近邻 skill 的触发竞争测试）

6.3 学习方向

  • Agent Skills 开放规范原文（agent skills spec）
  • Anthropic skill-authoring guide（500 行建议的出处）
  • 同花顺 Skill 的凭据处理（credentials.env 模式，与本文"密钥不进 Skill"互证）

七、指南分析

7.1 文章质量

  • 路径清晰：最小 Skill → 拆文件 → 接工具 → 评测 → 治理，五级递进可跟随
  • 反直觉判断有价值："定义边界先做产品"（作者吃过一个月定义之争的亏）；"资料多不是坏事，任务范围+执行面一起变大才失控"；"权限不能只写在提示词里"
  • 实测数据：Claude Code 5000/25000 token、API 8 Skills 上限——平台限制的一手披露
  • 负例设计哲学："负例要足够近才能测出边界"——与单元测试的边界用例思维一致

7.2 局限

  • 平台限制数据是 Claude 系为主，ChatGPT/其他平台披露少
  • 企业治理部分是框架性指导，缺具体工具链示例（Git 流程/评测 CI 的落地细节）
  • 未涉及 Skill 的版本迁移/破坏性变更处理（SKILL.md 格式演进时旧 Skill 怎么办）

  • 本机 400+ Skill 正处在文中"拆太细也有问题"的区间：description 相近的 skill 已有（多个搜索/笔记类）——拆分四判据和共存测试是直接对症的解药
  • 评测补齐是最高性价比动作：负例类+共存类评测接进 skill-stress-test，与 EnvHarness 三型变体生成合并成一个"Skill 质量工程"工作流
  • 排错 SOP 消灭"加字数"本能：skill 失效时按五步排错，而不是继续往 SKILL.md 堆内容
  • description 是发现的第一道门：巡检空泛 description（可脚本化：扫描无实义动词的描述）
