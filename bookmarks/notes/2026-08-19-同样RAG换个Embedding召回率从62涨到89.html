《同样 RAG，换个 Embedding 召回率从 62% 飙升到 89%》笔记

生成日期 2026-08-19

来源: 微信公众号「小黄学编程」《同样 RAG，换个 Embedding 召回率从 62% 飙升到 89%》（RAG 系列第三篇）
日期: 2026-08-19

一、核心概念（内容整理）

RAG 的"心脏"是 Embedding + 向量数据库。Embedding 决定向量空间的形状，向量数据库决定能否在这个空间里高效搜索——两个选对了，检索天花板才够高。

作者的真实案例：金融 KB 项目，同样的切分、提示词、生成模型，只换了 Embedding 模型，检索准确率从 62% 涨到 89%。Embedding 不是"调个 API 都差不多"。

核心公式：

用户问题 → Embedding → 向量 → 向量库 Top-K 检索 → 相关文档 chunk → 拼进 prompt → LLM 回答

Embedding 质量直接决定"距离近"是否等价于"语义相关"。

二、技术要点（指南分析）

2.1 Embedding 是什么

把文本映射成一组数字（向量），语义相近在向量空间里距离近，语义远则距离远。RAG 检索 = 把用户问题转成向量，找距离最近的文档向量。

"苹果手机" → [0.12, -0.34, 0.56, ...]  ← 跟下面距离近
"iPhone"   → [0.15, -0.31, 0.52, ...]  ← 跟上面距离近
"水果店"   → [-0.23,  0.45, -0.12, ...] ← 跟上面距离远

2.2 主流 Embedding 模型对比（原文三张表照录）

英文为主的开源模型

模型 维度 最大长度 特点 适用场景
bge-large-en-v1.5 1024 512 tokens 英文最强开源 英文知识库

nomic-embed-text 768 8192 tokens 超长上下文 长文档检索

2.3 作者推荐（原文核心结论）

  • 中文项目无脑选 bge-m3：多语言（中英混排不用分库）/ 长上下文 8192 tokens（比 bge-large-zh 长 16 倍）/ 多功能（稠密+稀疏+多向量）/ 免费本地部署
  • 英文项目或极致方便：text-embedding-3-small（调 API）

原文落盘代码：

# bge-m3（推荐）
from langchain_community.embeddings import HuggingFaceBgeEmbeddings
embedding = HuggingFaceBgeEmbeddings(
    model_name="BAAI/bge-m3",
    model_kwargs={"device": "cuda"},    # 有 GPU 用 GPU，没有用 cpu
    encode_kwargs={"normalize_embeddings": True},  # 归一化，余弦相似度
)

# OpenAI（英文）
from langchain_openai import OpenAIEmbeddings
embedding = OpenAIEmbeddings(model="text-embedding-3-small")

2.4 向量数据库选型（原文 6 方案对比表照录）

数据库 类型 特点 适用场景 上手难度
Chroma 嵌入式 轻量、开箱即用、纯 Python 开发测试、小规模 最低
FAISS 内存库 Meta 开源、速度极快、纯内存 大规模数据、不需持久化 低
Milvus 分布式 企业级、高性能、云原生 生产环境、大规模 中高
Qdrant 独立服务 Rust 实现、过滤能力强、轻量 需要元数据过滤 中
Weaviate 独立服务 内置多模态、GraphQL API 多模态检索 中
pgvector PG 扩展 跟 PG 一体、运维简单 已有 PG 基础设施 低

作者选型建议（Java 类比原文照录）：开发阶段用 HashMap/Caffeine（Chroma/FAISS），生产环境上 Redis 集群（Milvus/Qdrant），已有 Redis 不折腾（pgvector）。别一上来就上 Milvus。

原文落盘代码：

# Chroma：最简单
from langchain_community.vectorstores import Chroma
vectorstore = Chroma.from_documents(
    documents=chunks, embedding=embedding, persist_directory="./chroma_db",
)

# FAISS：最快
from langchain_community.vectorstores import FAISS
vectorstore = FAISS.from_documents(chunks, embedding)
vectorstore.save_local("./faiss_db")

# Milvus
from langchain_community.vectorstores import Milvus
vectorstore = Milvus.from_documents(
    documents=chunks, embedding=embedding,
    connection_args={"host": "localhost", "port": "19530"},
    collection_name="knowledge_base",
)

# pgvector
from langchain_community.vectorstores import PGVector
vectorstore = PGVector.from_documents(
    documents=chunks, embedding=embedding,
    connection_string="postgresql://user:***@localhost:5432/vectordb",
)

2.5 向量检索三种方式

方式 特点 代码
余弦相似度 最常用，衡量方向一致性，值域 [-1, 1] vectorstore.similarity_search(query="...", k=5)
MMR（最大边际相关性） 兼顾相关+多样性，避免 5 个几乎一样的 chunk；λ=0 最大多样，λ=1 最大相关 vectorstore.max_marginal_relevance_search(query, k=5, fetch_k=20, lambda_mult=0.5)
相似度+分数阈值 只返回 >threshold 的结果 similarity_search_with_relevance_scores(query, k=10, score_threshold=0.7)

2.6 向量库增量更新

新增：vectorstore.add_documents(new_chunks)
删除（Chroma）：vectorstore._collection.delete(where={"source": "old_policy.pdf"})
删除（Milvus）：vectorstore.delete(expr='source == "old_policy.pdf"')

生产环境策略：不要每次重建整个向量库。给每个文档分配唯一 ID（文件名哈希）→ 更新时删旧版本 chunk → 加新版本 chunk → 定时任务扫描目录检测变更 → 大规模用批量写入。

2.7 作者踩过的 4 个坑

  1. Embedding 维度不一致：换模型 → 维度变 → 旧向量库不能用。项目初期定死模型；必须换就得重建。
  2. 没做归一化：余弦相似度要求归一化向量，有些模型输出没归一化。encode_kwargs={"normalize_embeddings": True}
  3. 中文用错模型：用英文为主的 embedding（如 ada-002）处理中文，效果惨不忍睹。中文必用 bge-m3/bge-large-zh
  4. FAISS 持久化路径：保存加载路径要一致，会生成多个文件（.faiss + .pkl），移动别漏

三、复现验证（归纳总结）

作者金融 KB 案例：62% → 89%（同切分/提示词/生成模型，仅换 Embedding），提升 27pp。

四、可学到的点（归纳总结·续）

  1. Embedding 是 RAG 的第一性：模型/提示词/切分再精妙，向量空间"形状"不对一切白搭。62%→89% 是"换 Embedding 的杠杆"的直接证据。
  2. 中文项目 bge-m3 是默认答案：多语言+长上下文 8192+多功能+免费本地，四合一；比 bge-large-zh 在长文本上长 16 倍。
  3. 开发 vs 生产选型分层：Chroma/FAISS（嵌入式/内存）→ Milvus/Qdrant（独立服务）→ pgvector（已有 PG 则最省事）。别一步到位。
  4. 归一化是余弦检索的前提：不 normalize 直接算余弦，结果不对——encode_kwargs 里必须加。
  5. 维度换模型 = 重建向量库：维度是向量库的"硬约束"，选型时一并锁定。
  6. MMR 是"去重神器"：检索结果重复度高的场景（法律/政策文档常见问题）用 MMR，λ=0.5 是通用甜点。
  7. 增量更新 = 哈希差量：给文档分配哈希 ID，避免全量重建——生产环境的成本分水岭。

五、趋势判断（拓展应用）

  1. 混合检索是"从能用→好用"的下一步：BM25 + 向量融合的混合检索 + Rerank 重排序已是生产 RAG 标配（文章下篇预告）。纯向量检索在"精确关键词匹配"上弱于 BM25，两者互补。
  2. 多向量检索（Multi-Vector）兴起：bge-m3 同时支持稠密+稀疏+多向量，一个模型覆盖三种检索范式——这是 Embedding 模型演进的明确方向。
  3. 本地化部署趋势：数据不出境要求下，bge 系（免费、可本地 GPU/CPU 部署）在金融/政务场景是刚性需求，商用 API 只适合非敏感场景。
