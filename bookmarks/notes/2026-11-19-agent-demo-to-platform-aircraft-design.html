1. 原文战还原：六大工程支柱

以下内容忠实还原推文论点（§3 起为领域扩展，两者严格区分）。

1.0 总论：Demo 与 Platform 的分水岭

  • 现状批评：多数人做 Agent 停留在「接一个大模型 + 配置几个 Tool + MCP 连外部服务 + 写一套 Prompt」的初级阶段，误以为这就是完整 Agent 系统。
  • 核心判断：能调用工具和能稳定交付任务是两回事。Demo 的核心是让模型完成任务；Agent Platform 必须解决权限、状态、调度、记忆、可靠性、可观测性，以及系统出问题后如何恢复。
  • 竞争转移判断：未来 Agent 竞争不在模型推理能力与 MCP 接入数量，而在 Agent Runtime 和 Harness 的工程能力。

1.1 编排层（Orchestration）

  • 真 Agent 应在 Plan → Act → Observe 之间持续循环，根据工具返回结果重新判断下一步，必要时拆解给子 Agent，同时管理上下文、执行状态、重试与异常恢复。
  • 误区警示：子 Agent 越多 ≠ 越智能。多 Agent 同时工作带来更多上下文传递、状态同步、执行冲突和调度成本。
  • 判据（原文金句级）：如果一个确定性的 Workflow 就能完成任务，完全没有必要强行引入多个 Agent。应该交给模型的是动态判断和不确定性处理，而不是把所有步骤包装成自主决策。

1.2 工具层与权限引擎（Permission Engine）

  • MCP 的价值是标准化发现与调用，但 MCP 本身不保证工具调用安全可靠。
  • 拥有 GitHub、数据库、文件系统和企业业务系统访问能力的 Agent，若无权限边界，非常危险。
  • 要求：独立 Permission Engine 对每次高风险操作做权限检查；读取数据和修改数据应有不同权限；删除文件、执行命令、发送邮件、修改生产数据库等操作按风险设置明确限制与人工审批。
  • 判据：自主决策 ≠ 无限授权。

1.3 记忆与任务状态（Memory / Task State）

  • 批判「Agent Memory = 向量数据库」的简化：Session Memory、Task State、Long-term Memory、User Preferences 根本不是一回事。
  • 会话记忆解决当前上下文；长期记忆解决跨会话信息保留与检索；任务状态需要记录执行进度、工具调用结果、外部操作是否完成、失败后从哪里恢复。
  • 长任务不能因上下文压缩、服务重启、API 超时丢掉已完成工作 → Task Queue、Durable Workflow、Checkpoint、幂等设计的重要性。
  • 案例（原文）：数字人 Agent 管线（口播稿生成 → 数字人视频 → 字幕 → 包装 → 上传 → 交付），跨多个外部 API、持续数分钟。若上传环节失败，系统应知道前面哪些步骤已完成，而不是重新生成数字人、重新扣一次 API 费用。
  • 判据：明确区分哪些操作可安全重试、哪些已产生外部副作用，用幂等键、任务状态、补偿机制避免重复执行。

1.4 可观测性与评测（Observability & Evaluation）

  • 失败时至少要能回答：收到什么任务、选了哪个模型、调用了什么工具、工具返回什么、为什么进行下一步决策、失败发生在哪个环节。
  • 没有完整 Trace、日志、Token 成本记录和评测机制，无法区分失败根因是模型推理错误、工具接口异常、权限不足还是上下文管理问题。
  • 记录只是第一步，更重要的是可复现的评测与回归测试：每次修改 Prompt/模型/工具接口/编排逻辑，都应验证任务成功率、成本、延迟、失败类型是否变化。
  • 判据：否则「系统越复杂，你越不知道它为什么成功，也不知道它为什么失败」。

1.5 网关与统一治理（Agent Gateway）

  • 单 Agent 企业很多问题可用简单代码解决；当出现几十个 Agent（销售/客服/内容/研发/数据分析）时，统一身份认证、Agent Registry、模型路由、工具注册、权限策略、版本管理与审计成为实际需求。
  • Platform 价值不是把 Agent 放到一起，而是提供统一执行与治理体系，让不同 Agent 复用基础设施、在明确权限和资源边界内完成任务。

1.6 原文收束

  • 六个工程问题清单：何时用确定性 Workflow 何时用 Agent 动态规划？何时引入子 Agent 何时直接调用工具？如何管理长期运行任务？如何设计可恢复执行状态？如何控制高风险工具调用？如何评测 Agent 比上一版更可靠？
  • 终句判据：从 Agent Demo 到 Agent Platform，中间隔着的不是更多 Prompt、也不是更多子 Agent，而是一整套真正的软件工程能力。

2. 领域同构总表：Agent Platform 六支柱 ↔ 航空工程体系

3. 逐支柱领域策略与应对方法

3.1 编排策略：确定性 Workflow 承载流程骨架，Agent 只嵌判断点

领域事实：飞机设计 80% 以上的业务流程是确定性的——构型更改五步流程、符合性验证流程（选 MC 方法→执行→出报告）、型号资料编制与评审流程、试飞改装流程。这些流程的步骤、角色、门禁在程序文件中早已定义，不需要也不应该让 Agent「自主规划」。

策略：

  1. 流程骨架用确定性 Workflow 引擎实现（状态机/BPM），Agent 不接管流程控制权——流程偏离程序文件本身就是审核不符合项。
  2. Agent 只嵌入三个判断点：
  3. 检索与映射判断：条款检索（CCAR-25.x ↔ 设计需求映射）、历史符合性文件检索、相似案例检索——不确定性来自语义匹配，正是模型强项；
  4. 草案生成判断：更改单影响分析报告初稿、MOC 方法建议、符合性文件初稿——输出是「草案」，入库前强制人审；
  5. 审查辅助判断：文档一致性检查（交叉引用、版本号、术语）、评审意见归类与分发建议。
  6. 子 Agent 克制原则（直接采纳原文判据）：气动、结构、系统、航电各自建 Agent 并行操作同一 EBOM 节点 = 原文警告的「上下文传递、状态同步、执行冲突」在构型管理场景的复现——航空行业早在人工时代就为「多人改同一张图」建立了构型管理，Agent 时代不应退化。跨专业影响分析走单一 Agent + 检索，不走多 Agent 并发改写。

验收判据：流程步骤符合程序文件率 100%；Agent 建议采纳与否不阻塞流程（人审即门）。

3.2 权限策略：三档分级 + 密级分域，映射 Permission Engine

领域事实：型号资料涉密、设计数据是型号核心资产；DOA 体系下任何设计更改都有授权边界；「修改生产数据库」在航空语境=「更改设计基线/发出有效更改单」——属最高风险操作。

策略（三档权限矩阵）：

档位 操作类型 航空场景示例 门禁
R 只读检索 查询条款库、历史 MOC 报告、AD/SB 通告、公开技术资料 「CCAR-25.963 对油箱的要求及历史符合性文件」 低：身份认证即可，记录查询日志
D 草案生成 生成不落库的草稿：影响分析初稿、资料初稿、会议纪要结构化 更改单影响分析报告 draft 中：人工确认后才可入库；草稿带 AI 生成水印
W 写/执行 更改 EBOM、发起更改单、提交审定文件、调用外部系统执行 修改基线、向审查方提交数据 高：默认禁止 Agent 直接执行；强制走既有签审链（等价于人工审批）

密级分域部署：涉密数据域内私有化部署（本地推理），公开/非密数据可用云端模型——跨域单向隔离，涉密域的 Agent 不具备对外网络调用能力（MCP 工具注册按域白名单管理，这正是原文「工具注册与权限策略」的落点）。

应对方法：Permission Engine 的规则表直接从既有程序文件的权限矩阵翻译生成，不另行发明——制度已存在，缺的只是执行层。

3.3 记忆与状态策略：构型基线思想移植到 Agent 任务管理

领域事实：飞机设计的长任务天然存在且代价高昂——全机有限元迭代、CFD 气动优化、载荷循环计算、配平与操稳迭代，单轮数小时到数天；跨专业数据传递（气动载荷→结构分析）有严格的版本依赖关系。

策略：

  1. 任务状态机显式化：每个长任务（算例/更改单/资料编制）建状态记录——已完成步骤、依赖的输入基线版本、产出的中间文件指纹（md5）。原文数字人管线案例的领域对应：气动优化迭代到 80% 时集群故障，恢复时应从最近 checkpoint 继续，而不是重跑已收敛的 800 步迭代。
  2. 幂等键 = 算例编号 / 更改单号：同一更改单号的重试不重复执行已批准步骤；同一算例号的重跑先查已有产出指纹。外部副作用的定义域要写清楚：已发出的更改通知单、已提交审查方的文件 = 不可重入操作，只能补偿（发撤销单），不能静默重发。
  3. 记忆分层（采纳原文四分法）：
  4. Session Memory：当前编制任务的上下文（在稿文档+引用资料）；
  5. Task State：算例/更改单的进度与依赖（持久化，独立于模型上下文存活）；
  6. Long-term Memory：条款库、历史符合性文件、典型设计方案——RAG 索引而非塞入上下文；
  7. User Preferences：工程师个人用语习惯、常用模板——低优先级，可丢弃。
  8. 上下文压缩不等于状态丢失：长编制任务跨数天、多会话，任务恢复依据落盘的 Task State 而非对话历史——对话可以断，任务状态必须持久。

3.4 可观测与评测策略：Trace 按审定证据标准记录，评测回归复用验证体系

领域事实：适航文化对「可追溯」的要求是全球最严之一——需求到验证的追溯矩阵、工具鉴定的版本锁定、任何结论可回溯到输入与过程。这恰是原文 Observability 章节想要的，航空企业有制度地基。

策略：

  1. Trace 记录字段对齐审定证据：任务输入、模型与版本号、Prompt 版本、工具调用序列与返回摘要、最终输出、人工确认人+时间戳。模型/Prompt 版本锁定 = 构型管理思想直接移植——AI 资产（模型权重、Prompt、工具链配置）作为配置项纳入 CM 管理，版本变更走更改控制。
  2. 评测回归 = 符合性验证的 AI 版：
  3. golden set 构建：从历史符合性文件、典型更改单、审定问答中抽取带标准答案的题目集（建议首批 100–300 条，覆盖高频场景）；
  4. 回归触发：每次更换模型/改 Prompt/改工具接口，重跑 golden set，对比任务成功率、引用准确率（条款号是否真实）、幻觉率、成本、延迟——对应原文「验证任务成功率、成本、延迟和失败类型是否发生变化」；
  5. 引用可溯源是硬指标：Agent 回答的每条结论必须附条款号/文档链接，无法溯源的回答标记为「未验证」，这条直接消灭「幻觉入正式文件」的最大风险。
  6. 失败根因四分类（采纳原文框架并领域化）：模型推理错误 / 工具接口异常（如 PDM 系统接口超时）/ 权限不足 / 上下文管理问题——trace 里按此分类打标，月度出帕累托，指导投入优先级。

3.5 治理策略：Agent Registry 对齐工具鉴定，AI 分级对齐 EASA AI Assurance

领域事实与外部锚点：

  • DO-330/ED-215（DO-178C 配套工具鉴定标准）：TQL1–5 五级鉴定（TQL1 严苛度接近 DAL A 软件），判定核心问题是「工具输出是否被人工独立验证——若未验证则工具必须鉴定」。DO-178C 用三条准则（criterion 1/2/3）× 软件 DAL 等级定 TQL：如 DAL A 软件 criterion 1 工具=TQL-1，criterion 3 工具=TQL-5。
  • EASA AI Concept Paper（Issue 2 已发布，Issue 03 提案中）：AI 应用分级 Level 1（辅助人类）→ Level 2（human-AI teaming，AI 自动决策+人类监督）→ Level 3（自主）；提出 learning assurance / AI Assurance 分级（Issue 03 提案 AL1–AL5 映射 DAL/SWAL：AL1↔DAL A/SWAL1、AL3↔DAL C/SWAL2…），W 形开发保证周期把 V 模型适配到学习型组件。
  • SAE G-34 委员会 AS6983（航空安全相关 AI 产品开发与鉴定过程标准）仍在制定中（WIP）——说明「AI 进安全关键设计流程」的监管框架未定型。

策略：

  1. Agent Registry = 工具台账升级版：每个 Agent 登记——用途、接入的模型与版本、工具清单（MCP Server 列表）、权限等级（R/D/W）、密级域、评测成绩、责任人。质量体系本来就要求工具台账，AI Agent 是新工具类目，直接并入既有制度而非另起炉灶。
  2. DO-330 判据直接移植为 Agent 鉴定判据：Agent 输出被人工独立验证（L0/L1 阶段 100% 人审）→ 免鉴定，按「辅助工具」管理；Agent 输出省略/替代了人工验证过程（未来 L2 场景）→ 必须鉴定。这给「哪些 Agent 能上、上到什么程度」提供了与适航逻辑一致的判定线。
  3. AI 权限等级对齐 EASA 分级：当前及可见周期内，设计核心流程（适航符合性判断、安全关键设计决策）锁定 Level 1（辅助），Level 2 仅限非安全类运营场景试点（如资料翻译、格式转换），Level 3 在 AS6983/EASA 框架定型前不进入型号设计流程——这不是保守，是把监管不确定性转化为明确的边界条件。
  4. 版本与审计：Agent 平台自身的每次部署变更（模型路由、权限规则、工具注册）留审计记录，等价于质量体系的更改控制。

4. 落地方案指导：三阶段路线图

总原则（贯穿三阶段）：涉密数据不出域、写操作强制人审、AI 资产纳入构型管理、评测先于推广。

L0 阶段（0–6 个月）：只读检索助手层——建立信任与语料

项 内容
定位 Level 1 纯辅助，只读不写，零入库
场景 条款检索（CCAR/AD/SB）、历史符合性文件问答、EBOM/技术资料查询、跨文档比对
架构 私有化模型（涉密域）+ RAG 索引（条款库/资料库）+ 统一查询门户；云端模型仅限公开资料域
关键动作 ①资料数字化与密级标注先行（数据治理是前置工程）②golden set 首批 100–300 条 ③引用溯源硬门禁：每条答案附条款号/文档 ID
验收门禁 条款引用准确率 ≥95%；无溯源回答占比 = 0；用户周活与检索命中率
风险 语料质量差→答案质量差；对策：先治理高价值语料（近 5 年符合性文件+有效条款库）

L1 阶段（6–18 个月）：确定性 Workflow + Agent 判断点——嵌入业务流程

项 内容
定位 Level 1 增强：草案生成 + 流程嵌入，人审 100%
场景 更改单影响分析初稿（检索受影响系统/资料/试验项）、MOC 方法推荐、符合性文件初稿、评审意见归类、会议纪要→行动项分发
架构 Workflow 引擎承载流程骨架（状态机）+ Agent 判断点嵌入 + Permission Engine（R/D/W 三档）+ 任务状态持久化（checkpoint/幂等键）
关键动作 ①权限矩阵从程序文件翻译生成 ②AI 资产（模型/Prompt/工具链）纳入 CM 配置项 ③长任务状态机上线（算例/更改单）④评测回归制度固化（改 Prompt 必重跑 golden set）
验收门禁 人审覆盖率 100%（红线）；影响分析报告初稿采纳率 ≥60%；更改单编制周期缩短（实测对比，如 -30% 目标）；评测回归全绿才发版
风险 幻觉入正式文件（对策：人审+溯源双门禁）；流程责任模糊（对策：AI 输出定位为「输入材料」，签审责任仍在人）

L2 阶段（18–36 个月）：平台化治理——Agent Gateway 对齐 DOA 审计

项 内容
定位 多 Agent 统一治理，基础设施复用，审计就绪
场景 设计/资料/审定/供应链/培训多类 Agent 并存；统一身份认证、模型路由、工具注册、审计中心
架构 Agent Gateway（认证/路由/限流/审计）+ Agent Registry（台账+评测成绩）+ 评测中心（golden set 集中管理）+ 密级分域全覆盖
关键动作 ①Agent Registry 并入质量体系工具台账 ②审计中心对接内外部审核要求（SOI 式抽查 trace 可回放）③按 DO-330 判据划分「免鉴定/需鉴定」Agent 清单 ④跟踪 EASA AI Concept Paper Issue 03 / AS6983 定稿动态，预研 Level 2 场景
验收门禁 全量 Agent 入 Registry；trace 回放可支撑一次完整内审；跨 Agent 权限越界测试零通过；敏感操作审批流 100% 留痕
风险 监管框架未定型（AS6983 WIP）→ Level 2+ 自动决策暂缓；供应商锁定 → 模型路由层抽象多供应商

组织配套（贯穿三阶段）

  1. 责任界定：AI 输出法律定位=「辅助材料」，符合性判断与签审责任始终在人（DOA 授权人员）——写入程序文件。
  2. 能力建设：培养「懂适航 + 懂 Agent 工程」的桥接角色（对标原文 FDE 定位），而非只培训 Prompt 技巧。
  3. 投入顺序：数据治理 > 权限与审计 > 评测 > 模型能力——模型能力反而是最易获得的一环（行业通用），恰是原文「竞争不在模型能力」的领域印证。

6. Pitfalls / 待验证点

  • 〔领域红线〕Level 2/3 自动决策短期不可入设计核心流程：EASA Level 3 概念仍在研究、AS6983 未定稿——落地节奏以此为硬约束，任何「全自主设计 Agent」宣传在适航语境下现阶段不成立。
  • 〔根本矛盾〕涉密域模型能力差距：私有化模型与前沿云端模型存在能力差，涉密场景的 Agent 效果上限受此约束——L0/L1 场景选型应优先「检索增强」类任务（对模型推理要求低、对语料质量要求高），回避对模型创造力要求高的任务。
  • 〔评测冷启动〕golden set 构建成本被低估：历史符合性文件质量参差、格式异构，资料治理可能占 L0 阶段 50% 以上工作量——路线图排期时不要按「接上就能用」估计。
  • 〔责任灰区〕AI 草稿被「顺手」入库：制度上 AI 输出必须经授权人签审，但实际执行中工程师可能批量默认采纳——需要把「AI 生成内容确认」做成签审流的显式步骤（勾选+署名），而不是口头要求。
  • 〔待验证〕EASA Issue 03 与 AS6983 的定稿时间表：直接影响 L2 阶段 Level 2 场景开放时点，建议列入技术状态跟踪清单，每半年复查。
  • 〔原文局限〕原文是企业通用视角（作者 FDE 背景，案例为互联网/内容生产管线），未触及「强监管行业的合规前置」问题——本笔记 §3.2/§3.5/§4 的密级分域、DO-330 移植、Level 分级均为领域扩展，非原文内容。

7. 归纳与关联

  • 归纳：原文六支柱可压缩为一个判断——「Agent 的工程本质是把软件工程的老问题（状态、权限、审计、可靠性）在 LLM 时代重解一遍」。航空行业的特殊利好：这些老问题在适航体系里都有成熟答案，翻译成本远低于发明成本。原文的「确定性 Workflow 优先」判据与航空流程的天然确定性相遇，使航空企业反而是 Agent 落地条件最好的行业之一（只要不追求 Level 3）。
  • 关联自身体系：本笔记的 Permission Engine ↔ 本地 Agent 运行时的权限边界配置；Trace/审计 ↔ 会话记录与工具调用留痕；评测回归 ↔ golden set 门禁。原文「Agent Gateway/Registry」的提法对多 Agent 治理有直接参考价值。
  • 趋势判断：EASA/FAA/CAAC 的 AI 审定框架将在 2027–2030 逐步收拢（Issue 03 → 定稿，AS6983 → 发布），率先把 AI 资产纳入构型管理、把 Trace 按审定证据标准留痕的企业，将在框架落地时拥有「合规存量」——治理先行不是成本，是期权。
