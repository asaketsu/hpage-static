一句话定义

RAG 真正有价值的地方，从来不是"让 AI 可以读 PDF"。 而是让一个企业第一次拥有一层，可以被 AI 检索、理解、引用，并且有权限使用的知识系统。企业 RAG 首先是知识工程，然后才是大模型工程。

常见误区

把 PDF 切成 Chunk，Embedding 一下，丢进向量数据库，然后接个大模型。这确实能做出 Demo，但离真正的企业知识库还差得很远。

核心原理

用户问一个问题，系统先从企业内部找到相关资料，再把资料交给 LLM 回答。所以 RAG 最重要的可能根本不是最后那个 LLM，而是前面的 Retrieval。 如果检索出来的东西就是错的，模型越强，只会把错误答案说得越像真的。

两条流水线

第一条：知识入库

PDF / Word / 网页
  → 文档解析
  → OCR / 表格 / 结构恢复
  → Chunk
  → Metadata
  → Embedding
  → 索引

最容易被低估的是第一条。 人看到的是章节、表格和上下文，但机器拿到的可能只是坐标和文字。如果这里解析错了，后面的 Embedding、向量数据库、Rerank 全部建立在错误数据上。

现在一些 Document AI 工具已经开始把 PDF 恢复成包含章节、表格、图片、页眉页脚和来源信息的结构化文档，而不是单纯抽文本。

第二条：用户提问

Question
  → Query 理解
  → 权限过滤
  → Hybrid Search（Dense + Keyword/Sparse）
  → Rerank
  → Context
  → LLM
  → Answer + 引用来源

两个最容易踩的坑

坑 1：文档解析被低估

人看到的 机器拿到的
章节、表格、上下文 坐标和文字

如果解析错了，后面全部建立在错误数据上。

坑 2：不要迷信纯向量搜索

企业知识里有大量 SKU、产品型号、合同编号、人名和数字。语义搜索很强，但精确关键词同样重要。

搜索方式 擅长 弱项
Dense（向量） 语义相似、模糊匹配 精确编号/人名/数字
Keyword/Sparse 精确匹配 语义理解
Hybrid（混合） 两者兼顾 需要调参

成熟的 RAG 做 Dense + Keyword/Sparse 的 Hybrid Search，再把召回结果交给 Reranker 排一次。

Chunk 后处理细节：去重 + 相邻合并（LangChain 实现）

在入库流水线的 Chunk → Metadata 步骤之间，有一个经常被忽略但影响检索质量的环节——Chunk 去重和相邻 Chunk 合并。

为什么需要

问题 原因 后果
重复 Chunk PDF 多页有相同页眉页脚/水印/版权声明 召回时同一内容出现多次，浪费 Context 窗口
过碎 Chunk 固定长度切分把一个完整语义段拆成两半 Embedding 丢失上下文，检索精度下降

LangChain 去重实现

from langchain.schema import Document
import hashlib

def deduplicate_chunks(chunks: list[Document]) -> list[Document]:
    """基于内容哈希去除完全重复的 Chunk"""
    seen = set()
    unique = []
    for chunk in chunks:
        # 对文本做规范化后取哈希（去掉首尾空白+统一换行）
        normalized = chunk.page_content.strip().replace('\r\n', '\n')
        content_hash = hashlib.md5(normalized.encode()).hexdigest()
        if content_hash not in seen:
            seen.add(content_hash)
            unique.append(chunk)
        # 保留 metadata 中的来源信息
    print(f"去重: {len(chunks)} → {len(unique)}（删除 {len(chunks) - len(unique)} 个重复）")
    return unique

相邻 Chunk 合并实现

def merge_adjacent_short_chunks(
    chunks: list[Document],
    min_length: int = 100,
    max_length: int = 800,
) -> list[Document]:
    """
    合并过短的相邻 Chunk：
    - 如果当前 Chunk 长度 < min_length，与下一个 Chunk 合并
    - 合并后长度不超过 max_length
    - 两个 Chunk 必须来自同一文档同一页（metadata 检查）
    """
    if not chunks:
        return []

    merged = [chunks[0]]
    for current in chunks[1:]:
        prev = merged[-1]
        prev_len = len(prev.page_content)
        curr_len = len(current.page_content)

        # 条件：前一个太短 + 合并后不超限 + 同文档同页
        same_source = (
            prev.metadata.get('source') == current.metadata.get('source')
            and prev.metadata.get('page', -1) == current.metadata.get('page', -2)
        )
        if prev_len < min_length and prev_len + curr_len <= max_length and same_source:
            # 合并
            prev.page_content = prev.page_content + '\n' + current.page_content
            # 合并 metadata（保留来源、取页码范围）
            prev.metadata['merged'] = True
            prev.metadata['page_end'] = current.metadata.get('page', prev.metadata.get('page'))
        else:
            merged.append(current)

    print(f"合并短 Chunk: {len(chunks)} → {len(merged)}")
    return merged

完整流水线集成

from langchain.text_splitter import RecursiveCharacterTextSplitter

# 1. 结构化解析后的文档
docs = load_structured_documents("report.pdf")

# 2. 切分
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", ".", " ", ""],
)
chunks = splitter.split_documents(docs)

# 3. 去重（关键步骤）
chunks = deduplicate_chunks(chunks)

# 4. 合并过短的相邻 Chunk（关键步骤）
chunks = merge_adjacent_short_chunks(chunks, min_length=100, max_length=800)

# 5. 添加 Metadata（来源/页码/时间戳/权限标签）
for i, chunk in enumerate(chunks):
    chunk.metadata['chunk_id'] = f"chunk_{i:04d}"
    chunk.metadata['created_at'] = '2026-08-10'

# 6. Embedding + 索引

效果对比

指标 未处理 去重+合并后
Chunk 数量 1200 850（去重 250 + 合并 100）
平均 Chunk 长度 350 字符（部分仅 30 字符） 520 字符（语义更完整）
召回重复率 ~20% <3%
Context 窗口浪费 高（页眉页脚占位） 低

核心原则：Chunk 质量直接决定 Embedding 质量和检索精度。去重 + 相邻合并是入库流水线中 ROI 最高的两个操作，实现简单但效果显著。

企业 RAG 真正复杂的地方

不是技术实现，而是业务问题：

  • 旧文档怎么办？
  • 新旧政策冲突怎么办？
  • 不同部门权限怎么办？
  • 知识什么时候更新？
  • 回答错了怎么发现？

企业 RAG 首先是知识工程，然后才是大模型工程。

AI Coding 改变了实现方式

以前做 RAG 要花大量时间写 Parser、API、Vector DB、后台、Docker。现在这些工程代码完全可以交给 Codex / Claude Code 之类的 Coding Agent 去实现。

于是人的价值反而往上移动了。

你真正需要知道的是：
- 为什么这个 PDF 要结构化解析？
- 为什么这里要 Hybrid Search？
- 为什么这里需要 Rerank？
- 为什么这个问题应该查知识库，而另一个问题应该直接查 SQL？

AI 可以帮你写 RAG，但你必须知道什么才是一套正确的 RAG。

最终判断

如果今天让我重新理解企业 AI，我不会再把 RAG 看成一个"知识库聊天机器人"。我会把它看成一层新的企业基础设施：

把散落在 PDF、Word、网页、数据库和员工脑子里的知识，变成 AI 可以检索、理解、引用，并且有权限地使用的知识层。

等这一层真正建立起来，上面接的就不只是 Chatbot 了。还可以是客服 Agent、销售 Agent、内部 Copilot、内容 Agent、决策 Agent……

RAG 真正有价值的地方，从来不是"让 AI 可以读 PDF"。而是：让一个企业第一次拥有一层，可以被 AI 调用的知识系统。
