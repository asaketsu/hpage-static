归纳总结

一句话：多 Agent 不是架构升级，是一笔「上下文隔离/职责分离/并行」换「token 15×、协调成本、信息丢失、错误放大」的交易——面试和工程共同及格线是能说清单 Agent 卡在哪、拆开多花了什么、换回了什么，且有对照数据。

三个最锋利的判断：

  1. 「单 Agent 也能并行调工具」是伪拆分理由。并行调工具适合每路只做一次查询；每路都要自己搜→读→判断→再搜好几轮时，几路中间材料挤在一个上下文里互相污染——拆子 Agent 买的不是并行，是每一路干净的上下文。研发平台拆、电商下单不拆，判据不是流程固定与否，而是每一步要不要大量探索、要不要独立上下文与权限、能不能并行。

  2. 拆分的四种理由对应单 Agent 的四种卡点，不能混着说：①上下文被中间结果塞满（隔离需求）②工具多且相似选不准（工具域隔离）③提示词分支爆炸/角色冲突（职责分离，写代码和审代码不能同一上下文）④互不依赖子任务只能串行（真并行）。面试只答「任务复杂所以拆」= 失分。

  3. 多 Agent 的钱要四个账户分开记账：token（Anthropic：普通对话 1× → Agent 4× → 多 Agent 15×；作者实测 192× 预算爆炸，主 Agent 只占总用量 1/5，只盯主 Agent 严重低估）；协调成本（拆任务/读报告/纠错）；信息交接丢失（Cognition Flappy Bird 案例：背景做成马里奥风+鸟不像——各自决策说得通、拼起来对不上）；错误沿链放大（上游猜测到下游变已知事实）。

内容整理：六问决策链

一、要不要拆（判断门）

值得拆的任务特征（五条全对照）：
| 特征 | 例子 |
|------|------|
| 子任务依赖少、可各做各的 | 广度调研、多来源分头检索、按模块分头审查 |
| 过程长、结论短 | 读海量日志/代码只要一个结论 |
| 需要不同工具或权限 | 只读检索 vs 能写执行 |
| 需要没参与过程的人检查 | 独立 Critic |
| 任务够值钱 | 付得起 15× 开销 |

不该拆：各部分强依赖要共享决策（编码典型——可并行部分比研究少）、几步能做完、流程每步可写死（用 Workflow）。

Skill vs SubAgent 判据（一句话记忆）：缺「会不会做」→ 加 Skill（同一上下文同一权限）；缺「别弄乱主上下文/要不同权限/要独立检查者/要并行多轮」→ 拆 Agent（Claude Code：子 Agent 独立上下文+独立系统提示词+独立权限，只交回摘要）。

五概念连讲（美团真题）：Function Calling=调工具的机制；MCP=统一协议接工具和数据源；Skill=做事方法打包按需加载；Workflow=步骤代码写死；SubAgent=另起上下文干一段活只交结果。组合：Workflow 串主流程 → 节点 Agent 调 MCP 工具 → 大探索步骤派子 Agent。

二、怎么拆（五种结构+三条边界）

结构 特征 适用
主从（manager） 子 Agent 当工具调，只有主 Agent 对用户 要一个 Agent 掌控流程综合结果
流水线 阶段顺序写死 接近 Workflow
并行分片 同类任务切块各做再合并 长文档按章节抽取
执行+审查（evaluator-optimizer） 干活+对照测试 review 循环 质量门禁
意图转交（decentralized） 分诊后整对话单向转交 客服类

拆分边界三问：上下文边界（拿一份任务说明就能干完，不需要主 Agent 全部讨论？）｜工具权限边界（只读/能写分开，碰生产数据单独一个）｜能否单独验收（测试过没过、文件生成没、结论有无出处——没法单独检查的产出汇总时也查不出错）。按职位起名≠找到边界：「产品经理 Agent/架构师 Agent」读同一批材料做互相依赖的决定=只是多了几次转述。

规模要写进提示词（Anthropic 踩坑：简单问题曾派 50 个子 Agent）：事实查询 1 Agent 3-10 次工具调用；直接比较 2-4 子 Agent 各 10-15 次；复杂研究 10+ 子 Agent 分工清楚。

任务说明六要素：交付什么｜做什么不做什么怎么分界｜已确认事实+文件路径（免重查）｜用哪些工具优先哪些来源｜交回格式｜完成判据+步数/token 上限。检验法：给没参与讨论的新同事能否直接开工。

嵌套管控（Claude Code 2026-10-23 文档）：子 Agent 默认可再派、最深第三层（环境变量可调）；同会话并发子 Agent 默认上限 20。设计要管：深度、并发数、全树共享预算、循环检测（祖先链+同参数重复调用识别）、全局步数/时间兜底。

三、怎么通信（三种通道）

通道 优点 代价
经主 Agent 中转 好控制好追踪 主 Agent 成瓶颈，报告全进它上下文
共享状态（黑板） 看表知进度，主 Agent 读表不靠记 要管写入：单认领+权威副本+版本化冲突可见
直接对话/转交 平级协作（Claude Code agent teams，实验性默认关） token 明显更多，没规则的群聊抢答

往下传：任务说明自带背景；大材料给路径/链接不整段贴（防上下文膨胀）。子 Agent 一般不参与主 Agent 运行中上下文（隔离本是拆的理由）；缺信息就「需要输入」状态提前返回（A2A 同款设计）。

往回传（两种主张的兼顾法）：Cognition 要共享完整过程记录（隐含决策在过程里）vs Anthropic 存外部只回轻量引用（防传话游戏）。实操默认：短结论+关键证据+待办交回，详细日志落文件，主 Agent 有疑问再读。固定字段：状态/结论/证据（路径、链接、测试结果）/假设与未核实项。产出会变则结论绑版本（文件哈希）。

A2A vs MCP 分工：MCP 把 Agent 连到自己的工具（调函数，确定）；A2A 把 Agent 连到 Agent（对方有模型/工具/记忆，是黑盒，可能跑很久中途回头要信息）。A2A 核心件：Agent Card（/.well-known/agent-card.json）、有生命周期任务（可停「需要输入」）、artifact、JSON-RPC 2.0 + SSE/gRPC。用 A2A 的门槛：跨团队/厂商开发、分开部署才值；同进程主从用框架自带子 Agent 就够，上 A2A 只是多网络/认证/版本管理成本。

四、谁汇总、冲突怎么办

汇总四约束（防主 Agent 幻觉——蔚来真题：子 Agent 全对、主 Agent 汇总幻觉）：每条结论标出处（标不出不写）｜汇总后独立核对（Anthropic 专设 CitationAgent）｜关键数字照抄不许模型改写｜汇总步不给检索工具（防半路自己找新材料）。

矛盾仲裁四步（恒生电子真题）：①先确认真冲突（时间点/口径/来源不同常是假冲突）②按规则采信（权威数据源>文档>模型推断；新版>旧版；有证据>无证据）③规则判不了就查权威系统/派专门复核 Agent/交人④冲突写进结果，不许汇总模型自己挑一个。投票只在各 Agent 出错原因互不相关时有效——同模型读同份错资料会一起错。

Critic 三问：查什么（客观依据优先：测试/格式/出处/清单项，主观用评分标准）｜同模型吗（Huang et al. ICLR 2024：无外部反馈大模型难自纠推理错，改完可能更差→Critic 要独立上下文+外部信号+条件允许换模型）｜不通过怎么办（给具体问题+证据清单，定向补证只补缺的几条，不整个重做）。防循环：最多 N 轮/连续两轮问题数不降即停/预算到线即停，没解决的写进结果交人。Critic 自己也要评测（作者实测：像素检查工具把清屏改成不执行→残留火球误判为飞机；同批检查也真抓出 NaN/撞山/机头瞬转）。

幻觉不放大：证据跟着结论走（无出处标「未核实」）；下游把上游输出当说法不当事实；关键事实交接处核对一次；最终引用能追原始出处。

五、工程要管住的六件事

  1. 失败兜底：超时+步数上限；偶发错误有限重试、同错误反复不再试；失败也带部分结果返回（做到哪/哪些未核实）；长任务断点续跑不从头来；副作用操作（写库/发消息/下单）幂等。成功率是乘法：5 环节各 95% 独立不重试→整体 77%。
  2. 预算覆盖全树：开工前分份额，运行时全树累加（时间+token 双轨谁先到谁停），子 Agent 继承剩余预算。作者 192× 事故根因=预算只在题面没变成停止条件。
  3. 权限最小化：检索/审查只读；实现只写自己工作目录/分支；发消息/写生产/部署只留主 Agent 或需人确认。
  4. 链路追踪：一任务一 trace ID，子 Agent 各一段记任务说明/工具/结果/token/时间——否则错误无法归因到 Agent，成本无法分账。
  5. 评测先有单 Agent 基线（快手真题）：端到端同批任务单/多 Agent 各跑几遍（跑一遍不够）；分环节看路由准确率/子 Agent 完成率/Critic 判对率/汇总结论可追溯率。起步 20 个代表问题就够（Anthropic 起点；人工测试发现 Agent 偏爱 SEO 内容农场而非权威源）。
  6. 延迟必涨：每多一层=多一轮调用+一份任务说明+一次汇总；并行只缩互不依赖的几路，整体耗时=最慢一路（Anthropic 研究系统是同步批次执行，一个子 Agent 慢全体等）。

六、面试两分钟主线

拆的理由（现象+数据+拆前试过什么）→ 结构（几 Agent、职责/输入/输出/权限）→ 通信（经谁中转、传什么回什么）→ 汇总（谁汇总、冲突规则、谁检查、不过怎么办）→ 工程（兜底/预算/权限/追踪）→ 效果（vs 单 Agent 的成功率/耗时/成本）。必带一个具体的坑（子 Agent 重复干活/结论打架/汇总改错数字）+ 怎么发现怎么改。四大失分点：为多 Agent 而多 Agent｜只拿并行当理由｜只有架构图没对照数据｜没想过失败/冲突/停止条件。

趋势判断

  1. 面试风向标：2026 秋招 Agent 岗已从「画架构图」卷到「拿对照数据说服面试官」——快手直接问对照评测、小红书追问「就算做了改进有什么用」。信号：Agent 工程师岗位的评价标准正在从「会用框架」转向「会做实验」，与 MLE 岗位十年前的演化路径同构。
  2. 共识收敛：Anthropic（做多 Agent 的）自己写明适用边界、Cognition（反多 Agent 的）原则与 OpenAI「先榨干单 Agent」实际兼容——行业正在收敛到「上下文隔离是第一理由，并行是第四理由」的共识，纯并行叙事退场。
  3. 失败研究成为独立赛道：Cemri 等对失败记录的系统性归类（设计/对齐/检查）说明「多 Agent 失败学」正在成为独立研究对象——类比软件工程的 postmortem 文化，预计 2027 出现标准化失败分类库。
  4. A2A 生态位清晰化：跨组织部署是 A2A 唯一硬场景的判断逐渐成为行业默认，同框架内主从不上网络协议——A2A 不会重演 MCP 的普及曲线，会停在 B2B 集成层。

指南分析

可直接套用的三个模板：
- 拆分决策清单（照抄即用）：强依赖要共享决策？→不拆｜几步能完？→不拆｜每步可写死？→Workflow｜只缺「会不会做」？→Skill｜要干净上下文/独立权限/独立检查/并行多轮探索？→拆。
- 子 Agent 任务说明模板（六要素）：[交付物] + [边界与分界] + [已知事实+文件路径] + [工具与来源优先级] + [回传格式：状态/结论/证据/未核实] + [完成判据+步数/token 上限]。发任务前过一遍「新同事能否直接开工」。
- 矛盾仲裁 SOP（四步）：确认真假冲突→规则采信（权威源>文档>推断）→查证/复核 Agent/交人→冲突显式写进结果。

红线清单（工程止血点）：预算只在题面不在运行时=炸弹｜主 Agent 只占全树 token 1/5，只盯主 Agent 记账必低估｜副作用操作不幂等+重试=双倍扣款｜投票救不了同源错误。

拓展应用推荐

  1. 立即可用——Hermes 编排任务的话术升级：下次用 delegate_task 派多子任务时，任务 context 直接套「六要素模板」（尤其补上「已确认事实+文件路径」和「回传四字段」），可预期减少子 Agent 重查与回传噪音。
  2. 给 Kanban 多 Agent 工作流的检查表：把「红线清单」四条做成 worker 派发前的静态检查（预算是否覆盖全树、副作用是否幂等），对应 agent-workflow-orchestration 技能可补一节「派发前门禁」。
  3. 面试/写作素材库：本篇的「失分点反向清单」+ 六方向追问地图，可作为后续写 Agent 架构类文章或做内部分享时的审稿自查表——特别是「只有架构图没有对照数据」这条，适用一切技术方案评审场景。
  4. 对量化多模型系统的移植：多因子研究流程（数据/因子/回测分头跑）天然匹配「并行分片+执行审查」结构，仲裁四步可直接映射到因子信号冲突处理——但先过「值不值 15×」的门。
